# FPGA Research Digest - 2026-09-13

## Executive Summary

- **AXI-Lite VALID rule**: Once AWVALID/WVALID/ARVALID is asserted it must stay high until READY goes high — violating this can cause silent deadlocks in the KV260's PS→PL path at 0xA0000000/0xA0010000.
- **Vivado 2025.1/2025.2 BRAM change**: Block Memory Generator and FIFO IPs are no longer directly instantiable from the IP Catalog in 2025.x — they must be added via IP Integrator block design; this directly affects the `create_bd.tcl` workflow.
- **Vitis 2025.2 `xil_printf` breakage**: A known issue causes `xil_printf.h` to be unresolvable in some 2025.2 BSP configurations; workaround is to explicitly add `#include "xil_printf.h"` and confirm the standalone library path in the platform component's `vitis-comp.json`.
- **AXI-Stream TKEEP rule**: TKEEP must equal `DATA_WIDTH/8` bits; sparse (null) TKEEP between packet boundaries is not supported by AXI DataMover — only at the TLAST beat.
- **Vivado 2025.2 new feature**: SystemVerilog Interfaces support in IP Integrator simplifies AXI connections; new ultra-low-area mode for AXI SmartConnect via `STRATEGY` parameter reduces resource overhead on the KV260.

## 1. AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- **VALID must stay high**: On all AXI channels, once VALID is asserted it cannot be de-asserted until the corresponding READY is seen. Violating this causes silent deadlocks — the PS may hang waiting for an ACK that never comes because the PL saw VALID drop mid-transfer.
- **READY may be withheld indefinitely**: The slave (BRAM controller) is allowed to hold READY low for any number of cycles; your bare-metal polling loop must tolerate this without timeout corruption.
- **AXI-Lite write order**: A write transaction requires both the Write Address channel (AW) and Write Data channel (W) to complete — the slave may accept them in any relative order. Do not assume AW precedes W.
- **AXI BRAM Controller collision policy**: The AXI BRAM Controller does **not** detect read/write port collisions on the underlying BRAM. Simultaneous PS read and PS write to the same address produce undefined data at the read port.
- **AXI-Stream TKEEP width**: Always `DATA_WIDTH / 8`; for 32-bit data that is 4 bits. Sparse TKEEP is only valid on the TLAST beat; in between, all TKEEP lanes must be asserted.
- **AXI4-Lite known IP generation issue**: UG1483 documents a known issue where Model Composer/System Generator generates incorrect AXI4-Lite interfaces under certain parameterizations in 2025.2 — validate with IPI's address editor after generating.

### Code Example

```c
/* Bare-metal AXI-Lite write with proper channel ordering */
#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL

static inline void axi_write32(u32 addr, u32 data)
{
    /* Zynq MPSoC PS AXI-Lite: single store is atomic from PS side */
    *(volatile u32 *)addr = data;
    dsb();   /* Data Synchronization Barrier — flush store buffer before next access */
}

static inline u32 axi_read32(u32 addr)
{
    u32 val = *(volatile u32 *)addr;
    dsb();
    return val;
}

/* Write pattern and verify */
int verify_bram(u32 base, u32 pattern)
{
    axi_write32(base + 0x00, pattern);
    axi_write32(base + 0x04, ~pattern);
    u32 rd0 = axi_read32(base + 0x00);
    u32 rd1 = axi_read32(base + 0x04);
    return (rd0 == pattern && rd1 == ~pattern) ? 0 : -1;
}
```

### Relevance to Your Project

Your `main.c` writes patterns to BRAM0 at `0xA0000000` and BRAM2 at `0xA0010000`. The `dsb()` barrier after each access is critical: without it the Cortex-A53's store buffer may reorder write→read, making the readback see stale cache data rather than the PL BRAM. The AXI-Lite handshake is handled transparently by the PS interconnect, but the VALID stability rule governs what happens if you ever move to a custom RTL master.

## 2. Vivado Block Design / IP Integrator

### Key Findings

- **BRAM/FIFO no longer in IP Catalog (2025.x)**: Block Memory Generator and FIFO IPs must now be instantiated exclusively via IP Integrator block design. Direct `create_ip` in non-IPI scripts will fail with an "IP not found" error.
- **IP locking on version mismatch**: When Vivado detects older IP versions in a `.bd`, it locks them. Always run `upgrade_ip [get_ips]` or use **Report IP Status** → **Upgrade All** before synthesis.
- **Connection Automation**: Use `apply_bd_automation` after every new IP addition; it configures clocks, resets, and AXI interfaces automatically and reduces manual wiring errors.
- **Out-of-Context (OOC) mode**: Block designs synthesized OOC must be fully generated before they can be added to a non-project Tcl flow. Use `generate_target all [get_files *.bd]` after block design completion.
- **Address Editor**: After adding a new AXI slave (e.g., second BRAM), always run `assign_bd_address` and verify the offset/range in the Address Editor. Missing address assignment is the #1 cause of silent AXI no-response.

### Code Example

```tcl
# Add and configure AXI BRAM Controller in IP Integrator
create_bd_cell -type ip -vlnv xilinx.com:ip:axi_bram_ctrl:4.1 axi_bram_ctrl_0
set_property CONFIG.SINGLE_PORT_BRAM {1} [get_bd_cells axi_bram_ctrl_0]
set_property CONFIG.DATA_WIDTH {32} [get_bd_cells axi_bram_ctrl_0]

# Create Block Memory Generator
create_bd_cell -type ip -vlnv xilinx.com:ip:blk_mem_gen:8.4 blk_mem_gen_0
set_property CONFIG.Memory_Type {Single_Port_RAM} [get_bd_cells blk_mem_gen_0]

# Connect BRAM controller to memory
connect_bd_intf_net [get_bd_intf_pins axi_bram_ctrl_0/BRAM_PORTA] \
                    [get_bd_intf_pins blk_mem_gen_0/BRAM_PORTA]

# Assign addresses
assign_bd_address [get_bd_addr_segs axi_bram_ctrl_0/S_AXI/Mem0]
set_property offset 0xA0000000 \
    [get_bd_addr_segs zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0]
set_property range 64K \
    [get_bd_addr_segs zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0]
```

### Relevance to Your Project

Your `create_bd.tcl` script builds the block design with two BRAM controllers. The address assignment step (`assign_bd_address` + offset override) is what maps BRAM0 to `0xA0000000` and BRAM2 to `0xA0010000`. If this step is skipped or the range is wrong, the PS read/write will timeout silently and your UART will print FAIL even though the RTL is correct.

## 3. Vivado TCL Scripting

### Key Findings

- **UTF-8 BOM breaks batch mode**: A Tcl script saved with a UTF-8 BOM causes `invalid command name "?"` at startup. Save all TCL files as UTF-8 without BOM.
- **`exec` for OS commands**: In batch mode, unrecognized commands are NOT passed to the OS (unlike interactive/Tcl modes). Always use `exec make` or `exec bash script.sh` explicitly.
- **Non-project mode + block design**: OOC-synthesized block designs can be added directly to a non-project flow with `add_files`. If not OOC, call `generate_target all` first from within an open project before switching to non-project mode.
- **`write_project_tcl` is idempotent**: Use it to regenerate your `create_bd.tcl` from an existing project state — it captures all IP configuration, connection, and address assignment in reproducible form.
- **Batch mode invocation**: `vivado -mode batch -source create_bd.tcl -notrace` suppresses per-command echo; drop `-notrace` to debug step-by-step.

### Code Example

```tcl
# Non-project mode: synthesize + implement + write bitstream
# (Assumes block design already generated OOC externally)

read_vhdl    [glob ../vhdl/*.vhd]
read_xdc     [glob ../xdc/*.xdc]
add_files    [glob ../bd/*.bd]

synth_design -top kv260_top -part xck26-sfvc784-2LV-c
opt_design
place_design
phys_opt_design
route_design
write_bitstream -force output/kv260_top.bit

# Export hardware handoff for Vitis
write_hw_platform -fixed -force -file output/kv260_top.xsa

puts "Build complete: [exec date]"
```

### Relevance to Your Project

Your `create_bd.tcl` is the single source of truth for the block design. Running it in batch mode (`vivado -mode batch -source create_bd.tcl`) lets CI/CD reproduce the entire design without a GUI, which is essential for headless builds. Pair it with the non-project synthesis snippet above to get from source to bitstream in one script.

## 4. Vitis Bare-Metal / Standalone

### Key Findings

- **`xil_printf.h` unresolvable in Vitis 2025.2**: A confirmed forum issue — adding `#include "xil_printf.h"` explicitly in `main.c` and verifying the standalone library is in the BSP include path (check `vitis-comp.json` → `include_paths`) resolves the issue.
- **Default UART mismatch on KV260**: The generated BSP may default stdin/stdout to UART0 (MIO 18/19) but the USB-UART bridge on the KV260 carrier connects to UART1 (MIO 36/37). Fix: in `vitis-comp.json` set `stdin` and `stdout` to `psu_uart_1`.
- **Interrupt controllers not auto-initialized**: The standalone BSP deliberately does NOT configure the GIC (Generic Interrupt Controller). You must call `XScuGic_Initialize()` and `XScuGic_Connect()` manually for any interrupt-driven flow.
- **`xil_printf` float limitation**: `xil_printf` does not support `%f` — only `%d`, `%x`, `%c`, `%s`, `%l`. Use `printf` from newlib if floats are needed (adds ~20KB to binary size).
- **Linker script section placement**: For bare-metal on the Cortex-A53, DDR starts at `0x00000000`; OCM is at `0xFFFC0000`. BRAM-mapped AXI regions (0xA0000000+) are memory-mapped I/O and must NOT be placed in any linker section — access only via volatile pointers.

### Code Example

```c
#include "xil_printf.h"
#include "xparameters.h"
#include "xscugic.h"

/* Configure UART1 for KV260 (if BSP defaults to UART0, fix in vitis-comp.json instead) */
#define UART_BAUD   115200

int main(void)
{
    xil_printf("KV260 AXI-BRAM Demo\r\n");

    /* Write and verify BRAM0 */
    volatile u32 *bram0 = (volatile u32 *)0xA0000000UL;
    bram0[0] = 0xDEADBEEF;
    if (bram0[0] == 0xDEADBEEF)
        xil_printf("BRAM0[0]: PASS\r\n");
    else
        xil_printf("BRAM0[0]: FAIL (got 0x%08X)\r\n", (unsigned)bram0[0]);

    /* Write and verify BRAM2 */
    volatile u32 *bram2 = (volatile u32 *)0xA0010000UL;
    bram2[0] = 0xCAFEBABE;
    if (bram2[0] == 0xCAFEBABE)
        xil_printf("BRAM2[0]: PASS\r\n");
    else
        xil_printf("BRAM2[0]: FAIL (got 0x%08X)\r\n", (unsigned)bram2[0]);

    return 0;
}
```

### Relevance to Your Project

This is the core of your demo. The UART1 BSP fix is the most common first-boot failure on KV260 — everything compiles and runs, but no output appears on the host terminal because data is going to the wrong UART. Fixing `vitis-comp.json` takes 30 seconds and saves hours of debugging.

## 5. XDC Timing Constraints

### Key Findings

- **`set_input_delay` / `set_output_delay` are I/O boundary constraints only**: They describe the external system path delay relative to a clock edge. For internal AXI-BRAM paths between PS and PL, the interconnect timing is already constrained by the Zynq MPSoC PS IP — you generally do not need to add AXI path constraints manually.
- **`set_clock_groups -asynchronous`**: Use this for truly asynchronous clock domain crossings (e.g., PL fabric clock vs. PS reference clock). Forgetting it on async CDCs causes tools to attempt impossible timing closure.
- **PS-PL interface clock**: The `pl_clk0` output of the Zynq MPSoC PS IP is the primary fabric clock. Vivado auto-constrains it; verify the frequency matches your block design setting (typically 100 MHz for a simple demo).
- **Constraint order matters**: `create_clock` must appear before any `set_input_delay`/`set_output_delay`/`set_clock_groups` that reference it. A common mistake is putting I/O constraints before clock definitions.
- **False paths on async resets**: If your VHDL top uses an async reset synchronized to `pl_clk0`, add `set_false_path -from [get_ports rst_n]` to prevent the reset path from causing timing violations on the first cycle.

### Code Example

```tcl
# Minimal XDC for KV260 bare-metal AXI-BRAM demo
# pl_clk0 is auto-created by Vivado from the Zynq PS IP; verify frequency here:
create_clock -period 10.000 -name pl_clk0 [get_pins zynq_ultra_ps_e_0/pl_clk0]

# If you have a PL-side async reset input (board button, etc.):
set_false_path -from [get_ports {reset_n}]

# Clock groups: separate PS internal clocks from fabric clock
set_clock_groups -asynchronous \
    -group [get_clocks clk_pl_0] \
    -group [get_clocks {clk_fpga_0}]

# I/O example (only needed if you have external I/O pins beyond UART):
# set_input_delay  -clock pl_clk0 -max 2.0 [get_ports {gpio_in[*]}]
# set_output_delay -clock pl_clk0 -max 2.0 [get_ports {gpio_out[*]}]
```

### Relevance to Your Project

Your `kv260_top.vhd` is a wrapper connecting the PS to BRAM. For this topology the timing is largely self-contained — Vivado handles PS-PL AXI timing automatically. The key constraint you must add is `set_false_path` for any async reset and `set_clock_groups` if you add a second clock domain in the future. A missing `set_false_path` on reset is the #1 cause of spurious timing failures in otherwise simple designs.

## 6. Kria KV260 / K26 SoM Platform Specifics

### Key Findings

- **Boot mode default is QSPI32**: The KV260 ships with boot FW in QSPI non-volatile memory. For bare-metal JTAG development, switch boot mode DIP switches to JTAG (all off) to bypass FSBL and load directly from Vitis/JTAG.
- **SOM240 connector**: The K26 SOM connects to the carrier card via a 240-pin SOM240_1 connector. PL I/O available to PL design depends on which SOM240 pins are routed to the carrier — the KV260 carrier exposes Raspberry Pi and PMOD headers, all connected via EMIO through the PL.
- **UART1 is the USB-UART bridge**: MIO pins 36/37 connect to the USB-UART bridge on the carrier board. UART0 (MIO 18/19) is brought out to the JTAG header, not the USB connector.
- **AXI GP0 port base**: The PS AXI GP0 (General Purpose) master port is the correct port for 0xA0000000 range; GP1 maps to 0xB0000000. Confirm in the Zynq PS IP configuration that HPM0_LPD or HPM0_FPD is enabled for your address range.
- **Power domains**: The K26 has separate VCC_PSINTLP (PS low-power), VCC_PSINTFP (PS full-power), and VCC_PSPLL power domains in addition to the PL VCCINT. For bare-metal demos that don't use the PS full-power domain, this is transparent, but be aware that some PS peripherals require VCC_PSINTFP to be enabled in the board's power sequencing.

### Code Example

```tcl
# Zynq MPSoC PS configuration for KV260 bare-metal demo
# Run inside IP Integrator after create_bd_cell for zynq_ultra_ps_e_0

# Enable AXI HPM0 LPD (maps to 0xA0000000 range) — critical for BRAM access
set_property CONFIG.PSU__USE__M_AXI_GP0 {1} [get_bd_cells zynq_ultra_ps_e_0]

# Set PL clock to 100 MHz
set_property CONFIG.PSU__CRL_APB__PL0_REF_CTRL__FREQMHZ {100} \
             [get_bd_cells zynq_ultra_ps_e_0]

# Enable UART1 for KV260 USB-UART (MIO 36/37)
set_property CONFIG.PSU__UART1__PERIPHERAL__ENABLE {1} \
             [get_bd_cells zynq_ultra_ps_e_0]
set_property CONFIG.PSU__UART1__PERIPHERAL__IO {MIO 36 .. 37} \
             [get_bd_cells zynq_ultra_ps_e_0]

# Disable UART0 unless you need the JTAG UART as well
set_property CONFIG.PSU__UART0__PERIPHERAL__ENABLE {0} \
             [get_bd_cells zynq_ultra_ps_e_0]
```

### Relevance to Your Project

The most common first-bring-up failure on KV260 is the UART port mismatch. The PS IP must have UART1 (MIO 36/37) enabled and mapped, and the BSP `stdin`/`stdout` must point to `psu_uart_1`. The second most common issue is the AXI GP port: without `PSU__USE__M_AXI_GP0 = 1`, the HP0 LPD port is not active and all AXI transactions to the PL fabric silently fail.

## 7. AMD/Xilinx Tool Updates (Vivado/Vitis 2025.x)

### Key Findings

- **Vivado 2025.2 SystemVerilog Interface support**: IP Integrator now supports SystemVerilog interfaces for AXI connections between SV instances, simplifying multi-IP wiring. (Not directly relevant for VHDL-only projects but useful if mixing languages.)
- **New ultra-low-area AXI SmartConnect mode**: `STRATEGY` parameter on AXI Switch and AXI SmartConnect enables an ultra-low-resource mode — useful for resource-constrained paths where multiple AXI masters share one slave.
- **Versal Gen 2 device support**: 2025.2 adds XC2VE35xx and XC2VM35xx/38xx Versal AI Edge/Prime Gen 2 devices. Not directly relevant to K26/KV260 but signals the tool maturity trajectory.
- **BRAM/FIFO IP Catalog removal (2025.1+)**: Block Memory Generator and FIFO Generator are no longer in the standalone IP Catalog. Must use IP Integrator. Scripts using `create_ip -name blk_mem_gen` outside of IPI context will fail.
- **Vitis 2026.x known issues tracked**: AMD's support article 000040220 tracks Vitis 2026.x known issues. As of this digest, the tool chain latest stable release for production use is 2025.2; 2026.1 downloads are available but carry active known issue tracking.
- **Open-source component release notes**: AMD publishes per-release open-source notes on the Xilinx wiki covering PetaLinux, embeddedsw (bare-metal drivers), and XSCT updates.

### Code Example

```tcl
# Vivado 2025.2: AXI SmartConnect with ultra-low-area mode
create_bd_cell -type ip \
    -vlnv xilinx.com:ip:smartconnect:1.0 axi_smc

# Set ultra-low-area strategy (new in 2025.2)
set_property CONFIG.STRATEGY {0} [get_bd_cells axi_smc]
# 0 = default, 1 = performance, 2 = area (ultra-low in 2025.2+)
set_property CONFIG.NUM_SI {1} [get_bd_cells axi_smc]
set_property CONFIG.NUM_MI {2} [get_bd_cells axi_smc]

# Connect PS master → SmartConnect → BRAM0, BRAM2
connect_bd_intf_net \
    [get_bd_intf_pins zynq_ultra_ps_e_0/M_AXI_HPM0_LPD] \
    [get_bd_intf_pins axi_smc/S00_AXI]

connect_bd_intf_net \
    [get_bd_intf_pins axi_smc/M00_AXI] \
    [get_bd_intf_pins axi_bram_ctrl_0/S_AXI]

connect_bd_intf_net \
    [get_bd_intf_pins axi_smc/M01_AXI] \
    [get_bd_intf_pins axi_bram_ctrl_1/S_AXI]
```

### Relevance to Your Project

If you upgrade from Vivado 2025.1 to 2025.2, the `create_ip` call for Block Memory Generator in any standalone script (outside IPI) will break. Update `create_bd.tcl` to use IPI exclusively for BRAM instantiation. The ultra-low-area SmartConnect mode is worth enabling for the two-BRAM topology to reduce LUT overhead on the interconnect fabric between the PS and your BRAMs.
