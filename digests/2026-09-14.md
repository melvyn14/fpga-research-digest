# FPGA Research Digest - 2026-09-14

## Executive Summary
- **AXI BRAM write-enable timing bug**: The AXI BRAM Controller IP has a documented errata where it asserts write-enable one clock early and extends the WE pulse beyond expected duration — directly relevant to your two-BRAM write paths.
- **Cache coherency on Cortex-A53**: Bare-metal writes to AXI-mapped BRAM from the A53 can be silently stale if caches are not flushed; always use `Xil_DCacheFlushRange()` after writes and `Xil_DCacheInvalidateRange()` before reads in the KV260 bare-metal demo.
- **Vitis Unified IDE is now the default** in 2025.2 (Classic IDE deprecated) — ensure your Vitis 2025.1 workflow is migrated before the next toolchain update.
- **Non-project TCL flow is the cleanest path** for reproducible builds: `read_vhdl` → `read_bd` → `synth_design` → `opt_design` → `place_design` → `route_design` → `write_bitstream` covers the entire flow in one script.
- **TLAST must always be set** when sending the final beat of an AXI-Stream packet — forgetting it causes Xilinx slave cores to stall indefinitely waiting for packet completion.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings
- AXI handshake rule: once `VALID` is asserted it must **not** be deasserted until `READY` is seen; violating this causes silent data corruption or deadlock.
- AXI-Lite has no burst support — each transaction is a single 32-bit word; the AXI BRAM Controller in AXI4 mode supports bursts but requires `AWLEN`/`ARLEN` to be set correctly.
- Documented AXI BRAM Controller errata: WE asserted one clock before expected, WE pulse extended beyond expected duration — can cause double-writes in fast back-to-back transactions.
- AXI-Stream `TLAST`: if not asserted on the final beat, Xilinx slave cores (DMA, FIFO) stall waiting for end-of-packet; this is a frequent "why is my data stuck?" root cause.
- `TKEEP` must be all-HIGH on every non-final beat; on the final beat it marks valid byte lanes. `TSTRB` distinguishes data bytes from position bytes (rarely needed in simple streaming).
- `set_clock_groups -asynchronous` between PS and PL clocks prevents Vivado from trying to time-close paths that cross asynchronous domains.

### Code Example
```c
/* AXI-Lite write/read to BRAM0 at 0xA0000000 — bare-metal C */
#include "xil_io.h"
#include "xil_cache.h"

#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL

static inline void bram_write32(uintptr_t base, uint32_t offset, uint32_t val)
{
    Xil_Out32(base + offset, val);
    /* Flush D-cache line so PL sees the write, not the cached copy */
    Xil_DCacheFlushRange(base + offset, 4);
}

static inline uint32_t bram_read32(uintptr_t base, uint32_t offset)
{
    /* Invalidate before read so stale cached data is not returned */
    Xil_DCacheInvalidateRange(base + offset, 4);
    return Xil_In32(base + offset);
}
```

### Relevance to Your Project
Your `main.c` writes patterns to BRAM0 (0xA0000000) and BRAM2 (0xA0010000) and reads them back. The cache flush/invalidate wrappers above are the bare-metal equivalent of making those reads deterministic. The WE timing errata is worth keeping in mind if you ever see intermittent FAIL on back-to-back write bursts.

## Vivado Block Design / IP Integrator

### Key Findings
- **Connection automation** (`Run Connection Automation`) wires resets and AXI busses but does not assign addresses — always follow it with `Validate Design` then open the **Address Editor** to confirm offsets.
- The Address Editor only activates when the design contains a bus master (Zynq PS or MPSoC IP); right-click → **Auto Assign Address** resolves "unmapped peripheral" DRC errors instantly.
- **Export Block Design** (`File → Export → Export Block Design`) generates a re-runnable TCL script that recreates the entire BD from scratch — the canonical way to version-control block designs.
- Vivado 2025.2 adds **SystemVerilog Interface support** for AXI connections, allowing SV `interface` bundles to be used directly in IPI instead of individual port mappings.
- When modifying an existing BD, always run `validate_bd_design` in TCL before synthesis to catch connection errors early.
- IP customization parameters can be locked to specific versions via `set_property CONFIG.xxx` — prevents silent IP upgrades between tool versions.

### Code Example
```tcl
# Assign addresses programmatically after connection automation
assign_bd_address
# Lock BRAM0 to 0xA000_0000, range 64K
set_property offset 0xA0000000 [get_bd_addr_segs {mpsoc/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property range  64K         [get_bd_addr_segs {mpsoc/Data/SEG_axi_bram_ctrl_0_Mem0}]
# Lock BRAM2 to 0xA001_0000, range 64K
set_property offset 0xA0010000 [get_bd_addr_segs {mpsoc/Data/SEG_axi_bram_ctrl_2_Mem0}]
set_property range  64K         [get_bd_addr_segs {mpsoc/Data/SEG_axi_bram_ctrl_2_Mem0}]
validate_bd_design
```

### Relevance to Your Project
Your project hard-codes BRAM0 at `0xA0000000` and BRAM2 at `0xA0010000` in `main.c`. The TCL above locks those addresses in `create_bd.tcl` so a fresh IP Integrator re-run never silently re-assigns them to a different offset.

## Vivado TCL Scripting

### Key Findings
- **Non-project mode** is preferred for CI/headless builds; project mode adds overhead (`.xpr`, run management) that complicates scripting.
- The canonical non-project batch flow: `read_vhdl` / `read_bd` → `synth_design -top` → `opt_design` → `place_design` → `route_design` → `write_bitstream`.
- `open_bd_design` is only valid in project mode; in non-project mode use `read_bd` followed by `generate_target all [get_files *.bd]`.
- `write_hw_platform` replaces the deprecated `write_hdf` command as of Vivado 2020.2; always use it to export `.xsa` for Vitis.
- `report_timing_summary -file timing.rpt` after `route_design` captures timing closure status for CI gating.
- Variables can be passed from the shell: `vivado -mode batch -source run.tcl -tclargs $PART $TOP` and read inside the script with `lindex $argv 0`, `lindex $argv 1`.

### Code Example
```tcl
#!/usr/bin/env tclsh
# Non-project batch flow for KV260 demo
set part "xck26-sfvc784-2LV-c"
set top  "kv260_top"

read_vhdl   ../vhdl/kv260_top.vhd
read_bd     ../bd/kv260_bd.bd
generate_target all [get_files kv260_bd.bd]

synth_design  -top $top -part $part -flatten_hierarchy rebuilt
opt_design
place_design
phys_opt_design
route_design
report_timing_summary -file reports/timing_summary.rpt

write_bitstream -force output/kv260_top.bit
write_hw_platform -fixed -force -file output/kv260.xsa
```

### Relevance to Your Project
Your `create_bd.tcl` script creates the block design interactively. The snippet above shows how to wrap it into a fully non-project batch build, enabling `make` or CI to regenerate bitstream and XSA from clean every time.

## Vitis Bare-Metal / Standalone

### Key Findings
- **Vitis Unified IDE is now default** (2025.2); Classic IDE is deprecated. The unified IDE changes the workspace layout — component-based projects replace the old application + BSP pairing.
- `xil_printf` is a lightweight printf substitute (no float support by default) that writes to UART0 (PS MIO); it requires the standalone BSP's `xil_printf.c` and `outbyte.c` to be compiled in.
- Float support in `xil_printf` requires adding `-DCONFIG_HAVE_FLOAT=1` to BSP CFLAGS or switching to full `printf` (larger code footprint).
- Linker script (`lscript.ld`) DDR region must match the actual DDR address for the KV260 (K26 SoM): DDR starts at `0x00000000`, total 4 GB. Stack and heap defaults (8 KB each) are often too small for complex bare-metal apps — increase via the BSP settings.
- The `xparameters.h` generated by Vitis/Vivado contains `XPAR_PSU_CORTEXR5_0_CPU_CLK_FREQ_HZ` and the BRAM base addresses — always regenerate this after changing the block design address map.
- For standalone `A53` target on KV260, Vitis creates an ELF targeting APU core 0 at EL3; boot is typically via JTAG or QSPI stored FSBL+application.

### Code Example
```c
/* Minimal bare-metal print + AXI BRAM pass/fail test */
#include "xil_printf.h"
#include "xil_io.h"
#include "xil_cache.h"
#include "xparameters.h"

#define BRAM0_BASE  XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR
#define TEST_WORDS  16

int main(void) {
    xil_printf("KV260 AXI-BRAM test starting...\r\n");

    for (uint32_t i = 0; i < TEST_WORDS; i++) {
        Xil_Out32(BRAM0_BASE + (i * 4), 0xDEAD0000 | i);
    }
    Xil_DCacheFlush();

    uint32_t fail = 0;
    for (uint32_t i = 0; i < TEST_WORDS; i++) {
        uint32_t v = Xil_In32(BRAM0_BASE + (i * 4));
        if (v != (0xDEAD0000 | i)) {
            xil_printf("FAIL word %u: got 0x%08X\r\n", i, v);
            fail++;
        }
    }
    xil_printf(fail ? "OVERALL: FAIL (%u errors)\r\n"
                    : "OVERALL: PASS\r\n", fail);
    return 0;
}
```

### Relevance to Your Project
This is essentially your `main.c` pattern — using `XPAR_*` constants from `xparameters.h` rather than hard-coded addresses makes the code portable across re-exported XSA files. Adding `Xil_DCacheFlush()` after the write loop solves the most common "reads return stale data" issue in bare-metal AXI-BRAM testing.

## XDC Timing Constraints

### Key Findings
- For internal AXI-Lite paths (PS to PL via AXI interconnect), **no `set_input_delay`/`set_output_delay` is needed** — these are on-chip paths fully covered by `create_clock` on the PL clock.
- `set_clock_groups -asynchronous -group [get_clocks clk_pl_0] -group [get_clocks clk_pl_1]` prevents timing analysis across independent PL clock domains.
- Use `create_generated_clock` for clocks derived from MMCM/PLL outputs to give Vivado accurate frequency data for those clock domains.
- **Virtual clocks** (`create_clock -name vclk_ext`) are used when constraining board-level I/O against a clock that doesn't enter the FPGA on a dedicated port.
- `set_false_path -from [get_ports rst_n]` on asynchronous resets prevents false timing violations on reset distribution nets.
- Vivado 2025.1 UG835 updated `set_output_delay` documentation to clarify that positive delay = data must be stable N ns after the launch clock edge at the receiving device.

### Code Example
```tcl
# KV260 top-level XDC timing constraints
# PL clock from PS (100 MHz)
create_clock -period 10.000 -name clk_pl_0 [get_ports {pl_clk0}]

# Declare PS and PL clocks asynchronous so Vivado doesn't try to
# time-close paths that cross the PS/PL boundary via fabric
set_clock_groups -asynchronous \
    -group [get_clocks clk_pl_0] \
    -group [get_clocks -include_generated_clocks clk_pl_0]

# Async reset false path — reset distribution should not be timed
set_false_path -from [get_ports {pl_resetn0}]

# If driving external GPIO pins (e.g. LEDs on carrier board):
# set_output_delay -clock clk_pl_0 -max 2.0 [get_ports {led[*]}]
# set_output_delay -clock clk_pl_0 -min -1.0 [get_ports {led[*]}]
```

### Relevance to Your Project
Your design is PS-to-PL AXI only with no off-chip timing paths, so this constraint file is intentionally minimal. The `set_clock_groups` call is the one line that prevents "unable to analyze path" warnings when Vivado encounters the PS clock domain boundary.

## Kria KV260 / K26 SoM

### Key Findings
- **Boot modes**: K26 SoM MODE[3:0] pins on the SoM connector select boot device; the KV260 Starter Kit ships with QSPI32 as default. JTAG mode (MODE=0000) is the easiest for bare-metal development iteration.
- **Bare-metal QSPI deployment**: bare-metal ELF must be flashed to QSPI along with FSBL and PMU firmware; use Vitis `program_flash` command or XSCT scripts for automated programming.
- **UART pinout**: USB-UART is routed through a Silicon Labs CP2105 bridge on the KV260 carrier card; it enumerates as two COM ports — UART0 (PS MIO) is the first interface and connects to the A53 console.
- **MIO Bank 501**: PS MIO signals available on the SoM connector for carrier card connectivity; bank voltage is 1.8V — use level-shifters for 3.3V interfaces on carrier board.
- **EMIO GPIO**: PL-side GPIOs are accessible via EMIO; they appear in the PS AXI GPIO register space and can be used without separate AXI GPIO IP in the PL.
- **Power domains**: VCCO for PL sideband = 1.8V; detailed power budgets available via AMD Power Design Manager (PDM) tool; thermal design guide is UG1090.

### Code Example
```tcl
# XSCT script: switch KV260 to JTAG boot and load bare-metal ELF
connect
targets -set -filter {name =~ "APU*"}
rst -system
after 3000
targets -set -filter {name =~ "A53*#0"}
rst -processor -clear-registers
dow /path/to/kv260_bram_test.elf
con
# Monitor UART0 output at 115200 baud via USB-UART bridge
```

### Relevance to Your Project
Your demo targets the Kria KV260 with UART output over USB (MIO UART0). The JTAG boot + XSCT `dow`/`con` flow is the fastest iteration loop during bare-metal development — far faster than QSPI programming cycles. The Silicon Labs dual-UART note explains why the host may see two COM ports and why the wrong one shows no output.
