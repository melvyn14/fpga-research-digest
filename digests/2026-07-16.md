# FPGA Research Digest - 2026-07-16

## Executive Summary

- **AXI-Lite backpressure is the #1 hang cause**: Xilinx's own generated slave core had a confirmed bug where ARREADY was lowered without checking `RVALID && !RREADY`, causing the bus to freeze under backpressure. Always verify your slave holds AWREADY/WREADY low when the B-channel is stalled.
- **Vivado 2025.1 adds two new IP Integrator views** — dedicated "Clocking and Reset" and "Interrupt and AXI-4 Lite" panels — plus non-power-of-2 (NPOT) address assignments for AXI SmartConnect. Worth regenerating your block design under 2025.1 to pick up these improvements.
- **`write_bd_tcl` with `-use_bd_files`** is the correct way to version-control complex block designs; avoid storing only the GUI-exported Tcl when the BD is deeply nested (Vivado may fail to replay it).
- **KV260 bare-metal JTAG flow**: The board ships in QSPI32 boot mode; for development, switch to JTAG by writing `0x0100` to register `0xff5e0200` via XSDB. This avoids reflashing QSPI every iteration.
- **PL clock must come from PS**: On KV260 there is no independent PL clock source — all fabric clocks must be routed from the PS via the FCLK pins configured in the Zynq UltraScale+ IP GUI.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- **Backpressure hang pattern**: When `BVALID=1` and `BREADY=0` (master holding the write-response channel low), the slave **must** hold `AWREADY` and `WREADY` low. Xilinx's generated demonstration core failed to do this, causing silent bus freezes. The read-channel equivalent: when `RVALID=1` and `RREADY=0`, `ARREADY` must be deasserted.
- **Write address and write data channels are independent**: The AXI4 spec allows `AWVALID` and `WVALID` to arrive in any order; the slave must buffer whichever arrives first and wait for both before issuing `BVALID`.
- **Vivado 2025 address-space bug**: A known Vivado 2025 issue limits AXI full (not lite) peripherals to a 1 kB (10-bit) usable address decode window — watch for this if you ever expand beyond AXI-Lite on this project.
- **BRESP values**: Always return `OKAY (2'b00)` for normal transactions. Reserve `SLVERR (2'b10)` for decode errors. Returning `EXOKAY` on a non-exclusive transfer is a protocol violation.
- **Zipcpu's EasyAXIL pattern** is the community-recommended minimal correct AXI-Lite slave skeleton — it handles all backpressure cases and has formal proofs.

### Code Example

```vhdl
-- Minimal AXI-Lite slave write-response backpressure guard
-- Prevents AWREADY from going high when B-channel is already occupied
process(S_AXI_ACLK)
begin
  if rising_edge(S_AXI_ACLK) then
    if S_AXI_ARESETN = '0' then
      axi_awready <= '0';
      axi_bvalid  <= '0';
    else
      -- Only accept new write address when B channel is free
      if (axi_awready = '0' and S_AXI_AWVALID = '1' and
          S_AXI_WVALID = '1' and
          not (axi_bvalid = '1' and S_AXI_BREADY = '0')) then
        axi_awready <= '1';
      else
        axi_awready <= '0';
      end if;

      -- Assert BVALID once both address and data are captured
      if (axi_awready = '1' and S_AXI_AWVALID = '1' and
          axi_wready = '1'  and S_AXI_WVALID  = '1') then
        axi_bvalid <= '1';
        axi_bresp  <= "00"; -- OKAY
      elsif S_AXI_BREADY = '1' then
        axi_bvalid <= '0';
      end if;
    end if;
  end if;
end process;
```

### Relevance to Your Project

Your `kv260_top.vhd` exposes two AXI-Lite slave ports (BRAM0 at `0xA0000000`, BRAM2 at `0xA0010000`) driven by AXI BRAM Controllers. If either controller's B-channel stalls (e.g. because the Cortex-A53 issues back-to-back writes faster than the controller can respond), you risk a bus hang that manifests as a PASS/FAIL read returning garbage — not an obvious AXI error. Add a write-response timeout watchdog in your `main.c` test loop as a safety net.

## Vivado Block Design / IP Integrator

### Key Findings

- **Vivado 2025.1 new views**: Two new dedicated panels in IP Integrator — "Clocking and Reset" and "Interrupt and AXI-4 Lite" — give a structured view of these critical subsystems without hunting through the canvas.
- **NPOT address support**: 2025.1 now supports non-power-of-2 address assignments across SmartConnect paths in the Address Editor, removing a long-standing alignment limitation.
- **Run Connection Automation**: When you add an AXI BRAM Controller, clicking *Run Connection Automation* auto-instantiates AXI SmartConnect, Block Memory Generator, and Proc Sys Reset, and wires them correctly. Do not wire them manually — automation avoids common clock/reset topology errors.
- **AXI SmartConnect vs AXI Interconnect**: For new designs, always prefer SmartConnect (PG247). It is the successor to AXI Interconnect (PG059) and provides lower latency, better QoS, and automatic protocol conversion. On Kria/UltraScale+, AXI Interconnect is legacy.
- **Regenerate Output Products**: After any IP parameter change, right-click the IP → *Generate Output Products* → *Global* before synthesis. Stale output products are a leading cause of "IP is out of date" warnings that silently use old parameters.

### Code Example

```tcl
# Vivado 2025.1 — programmatic address assignment after Connection Automation
# Run this in the Tcl console after block design is connected

open_bd_design [get_bd_designs design_1]

# Assign base address for BRAM Controller 0
set_property offset 0xA0000000 [get_bd_addr_segs \
  {ps_e/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property range 64K [get_bd_addr_segs \
  {ps_e/Data/SEG_axi_bram_ctrl_0_Mem0}]

# Assign base address for BRAM Controller 1
set_property offset 0xA0010000 [get_bd_addr_segs \
  {ps_e/Data/SEG_axi_bram_ctrl_1_Mem0}]
set_property range 64K [get_bd_addr_segs \
  {ps_e/Data/SEG_axi_bram_ctrl_1_Mem0}]

validate_bd_design
save_bd_design
```

### Relevance to Your Project

Your `create_bd.tcl` sets `0xA0000000` and `0xA0010000` as base addresses for the two BRAM controllers. The snippet above is the idiomatic way to set these programmatically and matches what your TCL script should be doing. If you ever regenerate the block design from scratch in 2025.1, verify that the Address Editor didn't auto-assign different offsets — the new NPOT feature sometimes picks unexpected alignments on first generation.

## Vivado TCL Scripting

### Key Findings

- **`write_bd_tcl` vs `write_project_tcl`**: Use `write_bd_tcl` (or *File → Export → Export Block Design*) for the block design itself. Use *File → Project → Write Tcl* with the **"Recreate Block Designs using Tcl"** checkbox for a single script that recreates the entire project including sources.
- **`-use_bd_files` flag**: When your BD is complex or nested, pass `-use_bd_files` to `write_project_tcl`. This stores the BD as a `.bd` file reference rather than inlining the Tcl, which avoids Vivado failing to replay deeply nested designs.
- **Batch mode invocation**: `vivado -mode batch -source create_hw_proj.tcl` runs non-interactively. Use `-tclargs arg1 arg2` to pass parameters (e.g., target part, output directory) into the script as `$argv`.
- **Idempotent BD creation pattern**: Guard with `if {[get_bd_designs design_1] eq {}}` before `create_bd_design` so re-sourcing the script doesn't error on an existing design.
- **AMD AR #55692**: Official Xilinx answer record documenting the correct Tcl commands to preserve and recreate block designs — reference this for version-control workflows.

### Code Example

```tcl
# Idempotent block design creation with batch-mode argument support
# Usage: vivado -mode batch -source create_bd.tcl -tclargs xck26-sfvc784-2LV-c

set part_name [lindex $argv 0]
if {$part_name eq ""} { set part_name "xck26-sfvc784-2LV-c" }

create_project kv260_project ./kv260_project -part $part_name -force

# Only create the BD if it doesn't already exist
if {[get_bd_designs design_1] eq {}} {
  create_bd_design "design_1"
}
current_bd_design design_1

# Source the block design population script
source [file join [file dirname [info script]] populate_bd.tcl]

# Export BD Tcl for version control
write_bd_tcl -force ./tcl/design_1.tcl

# Generate bitstream
launch_runs impl_1 -to_step write_bitstream -jobs 8
wait_on_run impl_1
```

### Relevance to Your Project

Your `create_bd.tcl` appears to build the full block design including PS configuration and BRAM controllers. The `-use_bd_files` pattern and the idempotent guard are worth adding so the script can be re-run safely in CI without blowing away an existing project. The `$argv` part parameterization lets you target different speed grades without editing the script.

## Vitis Bare-Metal / Standalone

### Key Findings

- **BSP platform flow in 2025.1**: Vitis Unified IDE (the Eclipse-free flow) requires exporting the XSA from Vivado, then creating a *Platform Project* from the XSA, then an *Application Project* against that platform. The BSP libraries (standalone, xiltimer, etc.) are configured per platform.
- **`xil_printf` vs `printf`**: `xil_printf` is lighter (no floating-point formatting, no malloc) and routes directly to UART0/UART1 configured in the BSP. For debug output in a bare-metal loop, always use `xil_printf`. Use `printf` only if you've confirmed heap/stack are large enough in the linker script.
- **Linker script heap/stack**: Default standalone linker scripts allocate 0x400 (1 KB) heap and 0x1000 (4 KB) stack. For any non-trivial AXI test loop with formatted output, bump heap to at least `0x10000` in `lscript.ld`.
- **KV260 UART routing**: On KV260, USB-UART is routed through the CP2108 on the baseboard to PS MIO48/49 (UART1). Confirm BSP `STDIN_BASEADDRESS` and `STDOUT_BASEADDRESS` resolve to `0xFF010000` (UART1), not `0xFF000000` (UART0).
- **Interrupt controller**: For AXI-Lite BRAM polling (no interrupts), the GIC and scugic driver are not needed. Only enable them in the BSP if you add interrupt-driven I/O to avoid unnecessary BSP bloat.

### Code Example

```c
/* main.c — AXI-BRAM write/read/verify loop with robust error reporting */
#include "xil_printf.h"
#include "xil_io.h"
#include "xparameters.h"

#define BRAM0_BASE  0xA0000000UL
#define BRAM1_BASE  0xA0010000UL
#define TEST_WORDS  16

static int bram_test(const char *name, u32 base) {
    int errors = 0;
    for (u32 i = 0; i < TEST_WORDS; i++) {
        u32 pattern = 0xDEAD0000 | i;
        Xil_Out32(base + (i * 4), pattern);
    }
    /* Fence: read back a dummy word to flush write pipeline */
    (void)Xil_In32(base);

    for (u32 i = 0; i < TEST_WORDS; i++) {
        u32 expected = 0xDEAD0000 | i;
        u32 actual   = Xil_In32(base + (i * 4));
        if (actual != expected) {
            xil_printf("[FAIL] %s[%02d]: exp=0x%08X got=0x%08X\r\n",
                       name, i, expected, actual);
            errors++;
        }
    }
    return errors;
}

int main(void) {
    xil_printf("\r\n=== KV260 AXI-BRAM Test ===\r\n");
    int errs = 0;
    errs += bram_test("BRAM0", BRAM0_BASE);
    errs += bram_test("BRAM1", BRAM1_BASE);
    xil_printf(errs == 0 ? "PASS\r\n" : "FAIL (%d errors)\r\n", errs);
    return errs;
}
```

### Relevance to Your Project

Your `main.c` does exactly this pattern. The read-after-write fence (`(void)Xil_In32(base)`) is worth adding if not already present — AXI-Lite writes from the Cortex-A53 can be buffered by the interconnect and a subsequent read may return stale data without it. Also verify your BSP `xparameters.h` has `XPAR_AXI_BRAM_CTRL_0_BASEADDR = 0xA0000000` and `XPAR_AXI_BRAM_CTRL_1_BASEADDR = 0xA0010000` — mismatches here are a silent but common source of FAIL results.

## XDC Timing Constraints

### Key Findings

- **PL clock source**: KV260 has no independent PL clock; all fabric clocks come from the PS via `FCLK_CLK0`–`FCLK_CLK3`. These PS-generated clocks are **auto-constrained** by Vivado when using the Zynq UltraScale+ IP — you do not need a `create_clock` for them in your XDC.
- **`set_clock_groups -asynchronous`**: If your design uses multiple FCLK domains (e.g., one for AXI, one for a custom PL fabric), define them as asynchronous groups once rather than multiple `set_false_path` directives. This is more maintainable and less error-prone.
- **I/O constraints for BRAM internal paths**: For an AXI-BRAM design where all I/O is PS↔PL (no external I/O pins), you typically need **no** `set_input_delay` or `set_output_delay` constraints — those apply only to board-level signal paths. Only constrain if you add PMOD/GPIO connections.
- **Pblock planner**: New in Vivado 2025.1, the Pblock Planner GUI makes it easier to floor-plan PL logic away from PS-side primitives if you encounter placement congestion around the AXI interconnect.
- **Timing closure tip**: For AXI-Lite at 100 MHz (the default `FCLK_CLK0` for Kria), timing closure should be trivial. If you see failing paths, check if the SmartConnect or BRAM Controller has a slow path through a DSP — use `report_timing_summary -delay_type max` to identify the worst-case path.

### Code Example

```xdc
# KV260 AXI-BRAM XDC — minimal constraints file
# PS-generated clocks are auto-constrained; only explicit PL clocks need create_clock.

# If using a secondary FCLK for a custom PL fabric (e.g. 200 MHz):
# create_clock -period 5.000 -name fclk_pl200 [get_pins ps_e/inst/PS8_i/PLCLK[1]]

# Async between FCLK_CLK0 (AXI, 100 MHz) and FCLK_CLK1 (custom PL, 200 MHz):
# set_clock_groups -asynchronous \
#   -group [get_clocks -include_generated_clocks fclk_clk0] \
#   -group [get_clocks -include_generated_clocks fclk_clk1]

# False path on reset synchronizer crossing (safe to ignore metastability here
# because the reset is held for many cycles):
set_false_path -from [get_pins ps_e/inst/PS8_i/EMIOSDIO0CDN] -to [all_registers]

# Bitstream configuration for K26 SoM (QSPI x4 single)
set_property CONFIG_VOLTAGE        1.8          [current_design]
set_property CFGBVS                GND          [current_design]
set_property BITSTREAM.CONFIG.SPI_BUSWIDTH 4    [current_design]
set_property BITSTREAM.CONFIG.CONFIGRATE  85.0  [current_design]
```

### Relevance to Your Project

For the current AXI-BRAM demo (pure PS↔PL, single 100 MHz clock, no external I/O), you need almost no XDC timing content beyond the bitstream configuration properties at the bottom of the snippet. The `CONFIG_VOLTAGE 1.8` and `CFGBVS GND` settings are **required** for K26 SoM — omitting them triggers a DRC error during bitstream generation.

## Kria KV260 / K26 SoM

### Key Findings

- **Boot mode register**: Boot mode is controlled by `0xFF5E0200`. For JTAG: write `0x0100`; for QSPI32 (production default): write `0x2100`; for eMMC: write `0x6100`. Switch via XSDB/XSCT during a debug session to avoid reflashing QSPI during development.
- **K26 SoM ships empty**: QSPI and eMMC are blank from the factory. KV260 starter kits pre-load the Kria boot FW into QSPI. If you receive a bare K26 SoM (not the KV260 kit), you must program it before any boot.
- **MIO/EMIO routing on KV260**:
  - UART1 → MIO48/MIO49 (USB-UART via CP2108)
  - I2C0 → MIO30/MIO31 (INA260 power monitors)
  - GPIO → EMIO[0:11] (Raspberry Pi header, accessible from PL via EMIO)
  - SOM240_1/SOM240_2 connectors expose MIO501, MIO502 banks and HPIO bank 66
- **PL power domain**: PL is powered by the VCC_PAUX (1.8 V) and VCC_INT domains derived from the KV260 baseboard regulators. These rails are always on when the board is powered — no explicit PL power sequencing needed for bare-metal.
- **KV260 BIST tutorial (2025.1)**: A community guide on Hackster.io documents recreating the KV260 Built-In Self Test with Vivado/Vitis 2025.1 tools — directly relevant if you want to validate your toolchain setup.

### Code Example

```tcl
# XSDB/XSCT script: switch KV260 to JTAG boot and download bare-metal app
# Run from Vitis XSCT console or: xsct jtag_boot.tcl

connect

# Switch boot mode to JTAG (prevents PS from trying to load from QSPI)
targets -set -filter {name =~ "PSU"}
mwr 0xFF5E0200 0x0100
rst -system

# After reset: target Cortex-A53 #0
after 2000
targets -set -filter {name =~ "Cortex-A53 #0"}

# Optionally load FSBL or go straight to bare-metal ELF
dow ./Release/kv260_bram_test.elf
run

# Monitor UART1 output (typically /dev/ttyUSBx at 115200 baud externally)
```

### Relevance to Your Project

Your project uses exactly this JTAG-first development flow. The `mwr 0xFF5E0200 0x0100` step is essential for reliable iteration — without it, after a power cycle the PS starts from QSPI, which may contain a stale or missing bitstream, causing the Cortex-A53 to spin before your ELF can be downloaded. Add this step to your XSCT launch script in Vitis.

## AMD/Xilinx Tool Updates (Vivado/Vitis 2025.x)

### Key Findings

- **Vivado 2025.1 headline features**:
  - *Pblock Planner*: new GUI for floor-plan creation — useful for isolating PL fabric from PS-adjacent primitives
  - *NPOT address assignments*: SmartConnect now supports non-power-of-2 address ranges in IPI Address Editor
  - *Simplified AXI connections*: automatic wrapper creation for all AMD IP and BDs when connecting SV instances
  - *PS Wizard new views*: Block diagram and swim-lane views in the PS Wizard IP, plus dedicated "Clocking and Reset" and "Interrupt and AXI-4 Lite" panels in IPI
  - *Power Design Manager for Kria SOM*: new power analysis tool integrated into Vivado 2025.1
- **Vitis 2025.x highlights**: Enhanced GEMV and FFT for AI Engine; vectorized bitonic SIMD sorting. Less relevant for bare-metal AXI work, but signals the unified IDE is maturing.
- **2025.2 already available**: AMD released Vivado/Vitis 2025.2 with further enhancements (bare-metal 4K streaming guide for KV260 published on Hackster covering 2025.2 flow).
- **RTL-based AXI Switch IP**: New in 2025.x — a fully customizable RTL AXI Switch that bridges different AXI interface types and widths, useful if you later need to fan out to more than two BRAM banks.
- **Known issues**: No unresolved critical known issues listed for Vivado 2025.1.1 at time of digest. Check AMD AR #000037546 for the latest 2025.x known-issues list before starting a new project.

### Code Example

```tcl
# Vivado 2025.1 — leverage new ultra-low-area SmartConnect mode
# Set the STRATEGY parameter on SmartConnect to reduce LUT usage
# for a simple 1-master, 2-slave topology (no QoS needed)

set_property CONFIG.STRATEGY {1} \
  [get_bd_cells axi_smc]  ;# 1 = ultra-low-area mode (new in 2025.1)

# Verify the addressing works with NPOT ranges (new 2025.1 capability):
# 96 KB range (non-power-of-2) now valid in Address Editor

  {ps_e/Data/SEG_axi_bram_ctrl_0_Mem0}]
validate_bd_design  ;# will pass in 2025.1, would error in <=2024.x
```

### Relevance to Your Project

Migrating your `create_bd.tcl` to use `STRATEGY {1}` on the SmartConnect instance will reduce LUT consumption for your simple 1-PS-master / 2-BRAM-slave topology with no QoS requirements. The new PS Wizard swim-lane view in 2025.1 also makes it easier to verify that your FCLK and AXI HP port configurations are correct without reading raw property dumps.
