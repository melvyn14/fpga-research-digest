## Executive Summary

- **AXI-Lite VALID/READY deadlock is the #1 bug in slave IP**: Vivado's own auto-generated AXI-Lite example slave contains the combinatorial READY-from-VALID anti-pattern—avoid it in your BRAM wrapper by registering all handshake signals.
- **BRAM address cap at 32 KB per controller instance**: The AXI BRAM Controller v4.x only supports up to 32 KB of usable BRAM per port; your two-BRAM layout (BRAM0 @ 0xA0000000, BRAM2 @ 0xA0010000, 64 KB apart) is the correct approach to stay within this boundary.
- **KV260 PL clock must come from PS**: There is no standalone PL clock on the KV260 carrier—your block design must route the PS's `pl_clk0` into the PL fabric for any AXI-connected IP to function.
- **Vivado 2025.2 adds ultra-low-area mode for AXI SmartConnect/Switch**: A new `STRATEGY` parameter reduces resource usage—useful if your KV260 design expands beyond two BRAMs.
- **Non-project-mode TCL scripting is the best path to reproducible builds**: `vivado -mode batch -source create_bd.tcl` gives you a single command to regenerate the entire block design and bitstream, matching your repo's existing TCL approach.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- **The VALID/READY handshake rule**: A master must assert VALID and hold it until the handshake completes; it must NOT wait for READY before asserting VALID. Violating this can cause deadlock if both master and slave wait for the other.
- **Backpressure is the hardest case**: If BREADY is held low by the CPU (PS side), the slave must lower AWREADY and WREADY accordingly. Simulation often misses this because testbenches typically never hold BREADY low.
- **Combinatorial READY path is an Fmax killer**: Vivado's auto-generated AXI-Lite slave uses a combinatorial path for READY; while functionally correct it reduces Fmax and complicates place & route. Register the READY output in custom IP.
- **AXI-Lite vs AXI-Stream**: AXI-Lite is address-mapped, single-transaction (ideal for CSRs and BRAM reads/writes). AXI-Stream has no address channel and is optimized for high-throughput pipelines (video, DSP). Your BRAM demo correctly uses AXI-Lite for register-style memory access.
- **Latched-flag reset bug**: Forgetting to clear internal handshake flags (`aw_hs_done`, `w_hs_done`) after the write-response handshake (`BVALID`/`BREADY`) is a common source of one-shot-only write behavior.

### Code Example

```vhdl
-- Safe AXI-Lite write-address handshake: register AWREADY,
-- never make AWREADY combinatorially depend on AWVALID.
process(S_AXI_ACLK)
begin
  if rising_edge(S_AXI_ACLK) then
    if S_AXI_ARESETN = '0' then
      S_AXI_AWREADY <= '0';
      aw_hs_done    <= '0';
    else
      if S_AXI_AWVALID = '1' and S_AXI_AWREADY = '0' and aw_hs_done = '0' then
        S_AXI_AWREADY <= '1';
        aw_hs_done    <= '1';
      else
        S_AXI_AWREADY <= '0';
      end if;
      -- Clear flag after write-response handshake
      if S_AXI_BVALID = '1' and S_AXI_BREADY = '1' then
        aw_hs_done <= '0';
      end if;
    end if;
  end if;
end process;
```

### Relevance to Your Project

Your `kv260_top.vhd` top-level wrapper passes AXI-Lite signals from the Zynq MPSoC PS through to the AXI BRAM Controllers at 0xA0000000 and 0xA0010000. If you are writing a custom AXI slave wrapper in VHDL, the pattern above prevents the most common handshake deadlock. Even with Xilinx's own AXI BRAM Controller IP (which handles handshaking internally), understanding the handshake helps when debugging simulation traces of write transactions.

## Vivado Block Design / IP Integrator

### Key Findings

- **Connection Automation auto-instantiates AXI Interconnect**: When you add an AXI BRAM Controller to a block design containing a Zynq UltraScale+ MPSoC, running "Connection Automation" will instantiate an AXI Interconnect (or SmartConnect), a Block Memory Generator, and a Proc Sys Reset, and wire them up—saving significant manual work.
- **Address Editor requires a bus master**: The Address Editor tab is only available when the design contains a bus master (e.g., the Zynq PS). It allows manual entry of Offset Address and Range per slave port.
- **32 KB address range limit per AXI BRAM Controller port**: Each AXI BRAM Controller instance only uses the first 32 KB of its assigned address range even if a larger range is mapped. Your layout (BRAM0 at 0xA0000000, BRAM2 at 0xA0010000) cleanly separates two 64 KB windows, but only the lower 32 KB of each is actually backed by BRAM.
- **SmartConnect is preferred over AXI Interconnect for new designs**: SmartConnect has lower resource overhead and better QoR; Vivado 2025.2 adds an ultra-low-area mode via a `STRATEGY` parameter.
- **Regenerate IP outputs after any address change**: After editing the Address Editor, always run "Validate Design" and "Generate Block Design" before synthesis or the wrapper may carry stale port widths.

### Code Example

```tcl
# Vivado IP Integrator: add BRAM controller and run connection automation
create_bd_cell -type ip -vlnv xilinx.com:ip:axi_bram_ctrl:4.1 axi_bram_ctrl_0
set_property -dict [list \
  CONFIG.SINGLE_PORT_BRAM {1} \
  CONFIG.DATA_WIDTH {32}] [get_bd_cells axi_bram_ctrl_0]

# Run automation: creates AXI SmartConnect, Block Memory Generator, Proc Sys Reset
apply_bd_automation -rule xilinx.com:bd_rule:axi4 \
  -config { Clk_master {/zynq_ultra_ps_e_0/pl_clk0} \
            Clk_slave  {Auto} \
            Clk_xbar   {Auto} \
            Master     {/zynq_ultra_ps_e_0/M_AXI_HPM0_FPD} \
            Slave      {/axi_bram_ctrl_0/S_AXI} \
            intc_ip    {New AXI SmartConnect} \
            master_apm {0}} \
  [get_bd_intf_pins axi_bram_ctrl_0/S_AXI]

# Assign address: BRAM0 at 0xA000_0000, 64K window
assign_bd_address [get_bd_addr_segs axi_bram_ctrl_0/S_AXI/Mem0]
set_property offset 0xA0000000 \
  [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property range 64K \
  [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
```

### Relevance to Your Project

Your `create_bd.tcl` builds the block design programmatically. The `apply_bd_automation` call above matches the pattern used to create the AXI SmartConnect that bridges `M_AXI_HPM0_FPD` on the Zynq PS to your two BRAM controllers. If regenerating the project from scratch, this snippet is the core of the connection logic.

## Vivado TCL Scripting

### Key Findings

- **Batch mode is the reproducible build standard**: `vivado -mode batch -source create_bd.tcl` opens Vivado, runs the script, and exits—no GUI required. This is exactly what your repo's TCL approach enables.
- **Non-project mode vs. project mode**: In non-project mode you manage all sources manually and must re-run each stage (synthesis, implementation, bitstream) if files change. In project mode (what your `create_bd.tcl` likely uses) Vivado tracks dependencies automatically.
- **`write_bd_tcl` exports a reconstructible script**: After building a block design in the GUI, `write_bd_tcl -force my_bd.tcl` exports the entire design as a reproducible script—useful for capturing a working GUI design into version control.
- **Source ordering matters**: In TCL scripts, IP cores must be created before connections are made; use `validate_bd_design` after all connections to catch errors before generating outputs.
- **`generate_target all` triggers wrapper generation**: After `generate_target all [get_files *.bd]`, Vivado generates the VHDL/Verilog wrapper that instantiates your block design in the top-level entity.

### Code Example

```tcl
# Non-project mode: RTL-to-bitstream in a single batch script
# Run with: vivado -mode batch -source build.tcl

# Create in-memory project targeting Kria K26 (xczu5eg-sfvc784-2-e)
create_project -in_memory -part xczu5eg-sfvc784-2-e

# Source the block design creation script
source ./tcl/create_bd.tcl

# Generate all targets (wrapper HDL files)
generate_target all [get_files *.bd]
make_wrapper -files [get_files *.bd] -top
add_files -norecurse [glob ./*/hdl/*.v]

# Add top-level VHDL
add_files -norecurse ./vhdl/kv260_top.vhd
add_files -fileset constrs_1 ./xdc/kv260_timing.xdc

# Run synthesis, implementation, and bitstream generation
launch_runs synth_1 -jobs 4
wait_on_run synth_1
launch_runs impl_1 -to_step write_bitstream -jobs 4
wait_on_run impl_1

puts "Build complete: [get_property DIRECTORY [current_run]]/top.bit"
```

### Relevance to Your Project

Your repo already has `create_bd.tcl` for block design reconstruction. Wrapping it in a driver script like above makes the full flow (synthesis → bitstream) a single command, enabling CI-style headless builds without needing the Vivado GUI at all.

## Vitis Bare-Metal / Standalone

### Key Findings

- **`xil_printf` is lighter than `printf`**: The standalone BSP provides `xil_printf` which omits floating-point formatting—much smaller code size and no dependency on the libc printf infrastructure. Your `main.c` PASS/FAIL output is well-served by it.
- **BSP must be regenerated after hardware changes**: Every time you change the block design and re-export XSA, you must regenerate the BSP in Vitis so the `xparameters.h` definitions (`XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR`, etc.) update to match the new address map.
- **Memory-mapped access via volatile pointers**: The correct pattern for AXI BRAM access in bare-metal C is a `volatile uint32_t *` cast to the base address—the `volatile` qualifier prevents the compiler from optimizing away reads.
- **Cache coherency warning**: The Cortex-A53 has L1/L2 data caches enabled by default in standalone BSP. Writes to AXI BRAM may remain in cache and never reach the PL. Use `Xil_DCacheFlushRange()` after writes or mark the BRAM region as device memory in the MMU if cache coherency is a concern.
- **Linker script heap/stack**: The default standalone linker script places heap and stack in OCM (on-chip memory). For larger BRAM tests, verify your linker script has enough stack space.

### Code Example

```c
#include "xil_printf.h"
#include "xil_cache.h"
#include "xparameters.h"

#define BRAM0_BASE  XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR
#define BRAM2_BASE  XPAR_AXI_BRAM_CTRL_1_S_AXI_BASEADDR
#define TEST_WORDS  8

int main(void) {
    volatile uint32_t *bram0 = (volatile uint32_t *)BRAM0_BASE;
    volatile uint32_t *bram2 = (volatile uint32_t *)BRAM2_BASE;
    int pass = 1;

    /* Write test patterns */
    for (int i = 0; i < TEST_WORDS; i++) {
        bram0[i] = 0xA0000000 + i;
        bram2[i] = 0xA0010000 + i;
    }

    /* Flush D-cache so writes reach PL BRAM */
    Xil_DCacheFlushRange((UINTPTR)BRAM0_BASE, TEST_WORDS * 4);
    Xil_DCacheFlushRange((UINTPTR)BRAM2_BASE, TEST_WORDS * 4);

    /* Invalidate before read so cache doesn't serve stale data */
    Xil_DCacheInvalidateRange((UINTPTR)BRAM0_BASE, TEST_WORDS * 4);
    Xil_DCacheInvalidateRange((UINTPTR)BRAM2_BASE, TEST_WORDS * 4);

    /* Verify */
    for (int i = 0; i < TEST_WORDS; i++) {
        if (bram0[i] != (0xA0000000 + i)) { pass = 0; }
        if (bram2[i] != (0xA0010000 + i)) { pass = 0; }
    }

    xil_printf(pass ? "PASS\r\n" : "FAIL\r\n");
    return 0;
}
```

### Relevance to Your Project

Your `main.c` writes patterns to BRAM0 (0xA0000000) and BRAM2 (0xA0010000) and reads them back. If you ever see writes succeed but reads return stale data, cache flushing/invalidation (shown above) is the first thing to add. The `Xil_DCacheFlushRange` + `Xil_DCacheInvalidateRange` pair is the safe idiom for PS↔PL memory exchange in bare-metal standalone.

## XDC Timing Constraints

### Key Findings

- **Define the primary clock first**: All derived clocks and I/O constraints depend on a primary clock definition. For AXI BRAM designs on Kria, the primary clock is `pl_clk0` generated by the Zynq PS—Vivado creates this constraint automatically when the Zynq PS IP is present in the block design.
- **`set_input_delay` and `set_output_delay` are in nanoseconds**: Values can be positive or negative depending on the relative phase of clock and data outside the device. For AXI-Lite to BRAM (all internal), these are not needed—they apply to board-level I/O.
- **K26 SOM carrier XDC decoupling**: The K26 SOM design manual recommends a two-file constraint approach—one XDC for the SOM itself, one for the carrier card (KV260)—to keep SOM-level and board-level constraints separate.
- **`create_clock` period must match PS output**: If you configure `pl_clk0` to 100 MHz in the PS IP settings, ensure any explicit `create_clock` constraints in your XDC use `10.000` ns period.
- **False paths for async reset**: If your VHDL uses an asynchronous reset (common in Xilinx examples), add `set_false_path -from [get_ports aresetn]` to prevent the timing engine from trying to time the reset assertion path.

### Code Example

```tcl
# kv260_timing.xdc - Timing constraints for KV260 AXI-BRAM demo

# pl_clk0 is created automatically by the PS IP at 100 MHz.
# Explicitly constrain here if your block design does NOT auto-generate it:
# create_clock -period 10.000 -name pl_clk0 [get_pins zynq_ultra_ps_e_0/pl_clk0]

# Asynchronous reset is not a timing path - mark as false path
set_false_path -from [get_ports sys_resetn]

# If you have board I/O signals (e.g., status LEDs via GPIO on KV260 carrier):
# set_output_delay -clock pl_clk0 -max 2.0 [get_ports led_*]
# set_output_delay -clock pl_clk0 -min -1.0 [get_ports led_*]

# Prevent timing analysis across unrelated clock domains
# (e.g., if you ever add a second clock source)
# set_clock_groups -asynchronous \
#   -group [get_clocks pl_clk0] \
#   -group [get_clocks pl_clk1]
```

### Relevance to Your Project

For a purely PS-internal AXI-BRAM design with no external I/O other than UART (which is a PS-side MIO pin, not a PL pin), your XDC constraints are minimal. The most important constraint is verifying that `pl_clk0` is at 100 MHz and adding `set_false_path` for your reset signal to keep timing closure clean. As the design grows to add external PL I/O (sensors, HDMI, etc.), the I/O delay constraints become critical.

## Kria KV260 / K26 SoM

### Key Findings

- **Default boot mode is QSPI32**: KV260 ships with QSPI32 boot mode. Bare-metal applications with PL bitstreams need to be packaged as BOOT.BIN containing the FSBL, bitstream, and application ELF, or loaded via JTAG during development.
- **PL has no independent clock**: The KV260 carrier provides no dedicated PL oscillator. The `pl_clk0` output from the Zynq MPSoC PS (configured in the PS IP block) is the only available clock source for AXI-connected PL IP.
- **UART is on PS MIO, not PL**: The USB-UART path uses PS MIO pins—no XDC constraints needed for UART, and it works independently of whether the PL bitstream is loaded.
- **JTAG bitstream loading during development**: During development, `program_hw_devices` in Vivado Hardware Manager (or `fpga -f top.bit` in XSCT) loads the bitstream over JTAG without touching QSPI, enabling fast iteration.
- **AXI access requires bitstream loaded first**: In the bare-metal flow, the PS starts executing code immediately after reset, but reads/writes to AXI BRAM addresses will hang or return garbage if the PL bitstream has not been loaded. The FSBL handles bitstream loading before handing off to the application.

### Code Example

```tcl
# XSCT (Xilinx Software Command-line Tool) script for JTAG bare-metal load
# Run from Vitis/XSCT shell: xsct load_jtag.tcl

connect

# Target the APU (Cortex-A53 core 0) on the Kria KV260
targets -set -nocase -filter {name =~ "*PSU*"}
rst -system

# Load the bitstream into PL first
targets -set -nocase -filter {name =~ "*PL*"}
fpga -f ./output/top.bit

# Now target APU for application
targets -set -nocase -filter {name =~ "*A53*#0*"}
rst -processor

# Load and run the ELF
dow ./output/kv260_bram_demo.elf
con

puts "Application running - check UART for PASS/FAIL"
```

### Relevance to Your Project

This XSCT script automates the development-loop workflow: reset board → load bitstream → run ELF → observe UART output. It replaces the manual "Program Device" + "Run" steps in the Vitis GUI. For your AXI-BRAM demo, the sequence (bitstream first, then ELF) is critical—running the ELF before loading the bitstream will result in AXI bus hangs on the BRAM accesses.

## AMD/Xilinx Tool Updates (2025.x)

### Key Findings

- **Vivado 2025.2 AXI SmartConnect ultra-low-area mode**: A new `STRATEGY` parameter for AXI Switch and AXI SmartConnect IP reduces resource usage for designs that don't need full AXI4 burst throughput—relevant if adding more IP to your KV260 design.
- **Vivado 2025.2 SystemVerilog improvements**: Simplified AXI connections between SV instances and automatic wrapper creation for all AMD IP and BDs reduces manual wiring overhead.
- **Vivado 2025.2 physical optimization**: Reduced PhysOpt compile time and global/module-level optimization control (retiming updates)—faster iteration on timing closure.
- **Vitis 2025.2 AI Engine enhancements**: Primarily targets Versal AI Edge Gen 2; not directly relevant to KV260 bare-metal BRAM demos but marks the direction of AMD's software toolchain.
- **BRAM Controller v4.1 bug fix (2025.1 IP release)**: Fixed a potential deadlock between peripheral and cache data AXI interfaces when using frequency-optimized pipeline mode—if your AXI BRAM controller is configured with pipeline optimization, upgrading to the 2025.1 IP version is recommended.
- **Vivado 2025.2 added Versal AI Edge Gen 2 device support**: New device families are now supported; K26 SoM continues to use `xczu5eg-sfvc784-2-e` which is fully supported.

### Code Example

```tcl
# Vivado 2025.2: configure AXI SmartConnect with ultra-low-area strategy
# (reduces LUT usage at the cost of some bandwidth features)
create_bd_cell -type ip \
  -vlnv xilinx.com:ip:smartconnect:1.0 axi_smc

set_property -dict [list \
  CONFIG.NUM_SI {1} \
  CONFIG.NUM_MI {2} \
  CONFIG.STRATEGY {1}] \
  [get_bd_cells axi_smc]
# STRATEGY=0: default; STRATEGY=1: ultra-low-area (Vivado 2025.2+)

# Connect PS to SmartConnect, then to BRAM controllers
connect_bd_intf_net \
  [get_bd_intf_pins zynq_ultra_ps_e_0/M_AXI_HPM0_FPD] \
  [get_bd_intf_pins axi_smc/S00_AXI]
connect_bd_intf_net \
  [get_bd_intf_pins axi_smc/M00_AXI] \
  [get_bd_intf_pins axi_bram_ctrl_0/S_AXI]
connect_bd_intf_net \
  [get_bd_intf_pins axi_smc/M01_AXI] \
  [get_bd_intf_pins axi_bram_ctrl_1/S_AXI]
```

### Relevance to Your Project

If you upgrade your block design to use AXI SmartConnect instead of (or in addition to) the older AXI Interconnect IP, the 2025.2 ultra-low-area `STRATEGY=1` parameter is worth testing to keep LUT utilization low on the xczu5eg. The BRAM Controller v4.1 deadlock fix in 2025.1 IP is directly applicable—check your IP catalog version and update if you are on an older revision.
