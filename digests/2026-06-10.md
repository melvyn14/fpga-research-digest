## Executive Summary
- The AXI BRAM Controller takes **1 cycle to assert ARREADY**, then **~2 more cycles before RVALID/RDATA** — if `main.c` ever moves from `Xil_In32`/`Xil_Out32` to a custom AXI-Lite master, this latency must be modeled or polling loops will read stale/garbage data.
- Your two BRAM controllers at `0xA0000000` and `0xA0010000` are correctly spaced 64KB apart — this is the *minimum* alignment Vivado's Address Editor enforces (offset must have enough trailing zero bits to cover the controller's address range), so don't shrink that gap if you add a third BRAM.
- `xil_printf` (used for your PASS/FAIL UART output) does **not support `%f`** — only `%d`, `%ld`/`%lx`, `%c`, `%s`, `%x`. Keep all BRAM compare results as integers/hex.
- Memory-mapped AXI peripheral regions (your BRAM controller address space) are marked as **strongly-ordered/Device memory, non-cacheable** in the standard standalone BSP translation table — so no `Xil_DCacheFlush()`/invalidate is needed around your `Xil_Out32`/`Xil_In32` pattern-write/read-back loop. Don't add cache maintenance calls; they're unnecessary overhead for this design.
- Vitis Unified IDE 2025.1 changed the build dependency model: the **platform component must be built explicitly before the application component** (it no longer auto-rebuilds an out-of-date platform like Vitis Classic did). If your build scripts assume Classic behavior, add an explicit platform build step.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings
- The AXI BRAM Controller (PG078) takes one clock cycle to raise `AXI_ARREADY` after `AXI_ARVALID`, and then **two more clock cycles** before `AXI_RVALID`/`AXI_RDATA` are presented — total read latency from address-valid to data-valid is ~3 cycles.
- A frequently-cited gotcha: Xilinx's own AXI-Lite slave template/demo code has had outstanding handshake bugs for years around backpressure — if you ever write a custom AXI-Lite peripheral (instead of using AXI BRAM Controller + BMG), don't copy the template verbatim without testing `BREADY`/`RREADY` deassertion cases.
- Core AXI handshake rule (applies to AXI-Lite and AXI-Stream alike): **a transfer happens exactly when `xVALID && xREADY` are both high in the same cycle** — never gate that condition on anything else, or you'll miss or duplicate transfers.
- For AXI4-Lite writes, `AWVALID`/`AWREADY` and `WVALID`/`WREADY` handshakes can occur in *any relative order* (or simultaneously), but the slave must not issue `BVALID` until **both** have completed.
- AXI-Stream specific: once `TVALID` is asserted, it **must stay asserted** until `TREADY` is seen high (a master can't "change its mind"). `TREADY` should be a registered signal, not pure combinational logic, to avoid timing closure issues.
- Not directly used in your current AXI-Lite-only design, but relevant if you extend to streaming (e.g., DMA to BRAM): some Xilinx IP cores silently stall a pipeline if `TLAST` is never asserted on the final beat.

### Code Example
```c
/* main.c style pattern — AXI-Lite write/read-back via AXI BRAM Controller.
 * No cache maintenance needed: PL AXI peripheral space is Device memory
 * (strongly ordered) in the default standalone MMU table, and Xil_Out32/
 * Xil_In32 already compile to single ldr/str — ordering is guaranteed. */
#define BRAM0_BASEADDR 0xA0000000U
#define BRAM2_BASEADDR 0xA0010000U
#define BRAM_SPAN_BYTES 0x1000U   /* test footprint, well within 64KB region */

int test_bram(u32 base, const char *name) {
    int errors = 0;
    for (u32 off = 0; off < BRAM_SPAN_BYTES; off += 4) {
        u32 pattern = 0xA5A50000U | (off & 0xFFFFU);
        Xil_Out32(base + off, pattern);
    }
    /* AXI-Lite write completes (BVALID/BREADY) before Xil_Out32 returns;
       no extra delay needed for BRAM controller. */
    for (u32 off = 0; off < BRAM_SPAN_BYTES; off += 4) {
        u32 expected = 0xA5A50000U | (off & 0xFFFFU);
        u32 got = Xil_In32(base + off);
        if (got != expected) {
            xil_printf("%s MISMATCH @0x%08x: exp=0x%08x got=0x%08x\r\n",
                       name, base + off, expected, got);
            errors++;
        }
    }
    xil_printf("%s: %s (%d errors)\r\n", name, errors ? "FAIL" : "PASS", errors);
    return errors;
}
```

### Relevance to Your Project
Your `main.c` already does pattern-write/read-back to BRAM0 (`0xA0000000`) and BRAM2 (`0xA0010000`) over AXI-Lite via the AXI BRAM Controller IP — the snippet above mirrors that flow and documents *why* no cache flushing or extra wait states are required, which is a common source of "do I need Xil_DCacheFlush here?" confusion when porting bare-metal code from DDR-based examples.

## Vivado Block Design / IP Integrator

### Key Findings
- The **Address Editor** only appears once a master with an address space (e.g., the Zynq UltraScale+ MPSoC PS, via its `M_AXI_HPM0_FPD`/`M_AXI_HPM1_FPD` ports) is in the diagram. Connection Automation auto-populates an offset/range entry per AXI slave when you run it.
- Offset alignment rule: the **Range** field determines how many low-order bits of the **Offset Address** must be zero. A 64KB range (0x10000) requires the offset's low 16 bits to be zero — exactly why `0xA0000000` and `0xA0010000` (both 64KB-aligned) work cleanly for two adjacent AXI BRAM Controllers.
- After Connection Automation, Vivado typically inserts a **Processing System Reset** IP and an **AXI Interconnect/SmartConnect** automatically, mapping each peripheral into the PS address map — review these auto-inserted blocks rather than assuming defaults are optimal (e.g., SmartConnect vs. AXI Interconnect affects area/latency).
- `validate_bd_design` is essential after any manual TCL edits to a block design — it propagates parameter changes between connected IP (e.g., data width, address width) and will flag unconnected/incompatible interfaces before you attempt synthesis.
- `regenerate_bd_layout` is purely cosmetic (re-arranges the GUI canvas) — it does not affect functionality, but running it after scripted `connect_bd_*` calls makes the design reviewable in the GUI.

### Code Example
```tcl
# Address assignment for two AXI BRAM Controllers (matches BRAM0/BRAM2 layout)
# Run after connect_bd_intf_net wires each ctrl's S_AXI to the PS interconnect.

set bram0_seg [get_bd_addr_segs axi_bram_ctrl_0/S_AXI/Mem0]
set bram2_seg [get_bd_addr_segs axi_bram_ctrl_1/S_AXI/Mem0]

assign_bd_address -target_address_space [get_bd_addr_spaces ps/Data] $bram0_seg
assign_bd_address -target_address_space [get_bd_addr_spaces ps/Data] $bram2_seg

set_property offset 0xA0000000 [get_bd_addr_segs {ps/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property range  64K        [get_bd_addr_segs {ps/Data/SEG_axi_bram_ctrl_0_Mem0}]

set_property offset 0xA0010000 [get_bd_addr_segs {ps/Data/SEG_axi_bram_ctrl_1_Mem0}]
set_property range  64K        [get_bd_addr_segs {ps/Data/SEG_axi_bram_ctrl_1_Mem0}]

validate_bd_design
regenerate_bd_layout
save_bd_design
```

### Relevance to Your Project
This is essentially what `create_bd.tcl` must do for BRAM0/BRAM2: instantiate two `axi_bram_ctrl` + `blk_mem_gen` pairs, run connection automation against the PS `M_AXI_HPM0_FPD` (or HPM1), then **explicitly pin the offsets** to `0xA0000000`/`0xA0010000` rather than trusting auto-assignment, since auto-assignment order can shift if IP instantiation order changes between regenerations — explicit `set_property offset/range` calls make the address map reproducible across Vivado re-runs.

## Vivado TCL Scripting

### Key Findings
- **Non-project mode** is the recommended approach for reproducible CI/scripted builds: you manage all sources, constraints, and run stages yourself via TCL — nothing is cached in a `.xpr` project file.
- In non-project mode you must explicitly tell synthesis the top-level entity and target part (`-top`, `-part`) since there's no project file to infer them from.
- Standard non-project flow stages: `synth_design` → `opt_design` → `place_design` → `phys_opt_design` (optional) → `route_design` → `write_bitstream`. Steps 1/3/5 (synth/place/route) are mandatory; opt/phys_opt are optional but recommended for timing-critical designs.
- For batch execution: `vivado -nojournal -mode batch -source build.tcl -notrace -tclargs <args> 2>&1 | tee build.log` — capturing the log is essential for CI debugging.
- `write_bd_tcl` (or "File > Project > Write Tcl" with "Recreate Block Designs using Tcl" checked) regenerates a faithful TCL recreation of a block design — useful for diffing block-design changes in git since `.bd` files are JSON blobs that don't diff cleanly.

### Code Example
```tcl
# build_kv260.tcl - non-project mode batch flow skeleton
set part "xck26-sfvc784-2LV-c"   ;# K26 SoM device

read_vhdl -library work [glob ./vhdl/*.vhd]
read_bd ./bd/kv260_bd.bd
generate_target all [get_files ./bd/kv260_bd.bd]
read_xdc ./xdc/kv260_constraints.xdc

synth_design -top kv260_top -part $part
opt_design
place_design
phys_opt_design
route_design

write_checkpoint -force ./build/kv260_routed.dcp
report_timing_summary -file ./build/timing_summary.rpt
report_utilization -file ./build/utilization.rpt
write_bitstream -force ./build/kv260_top.bit
```

### Relevance to Your Project
Your repo's `tcl/create_bd.tcl` likely runs in **project mode** (typical for IP Integrator-driven designs since the block design GUI needs a project context). If you want a fully scripted/CI-friendly rebuild (e.g., GitHub Actions producing a fresh `.bit`/`.xsa` on every push), pairing `create_bd.tcl` (project mode, for the BD) with a separate non-project `build_kv260.tcl` for synth/impl/bitstream gives you the best of both — interactive BD editing plus reproducible headless builds.

## Vitis Bare-Metal / Standalone

### Key Findings
- `xil_printf` (from `xil_printf.h`) is a lightweight `printf` replacement for standalone apps — smaller code/stack footprint than full `stdio`, but **format specifier support is limited to `%d`, `%l`/`%ld`, `%x`/`%lx`, `%c`, `%s`** (no floating point).
- BSP UART selection: the standalone BSP can default to the wrong UART instance. For Vitis Unified IDE, this is set in `vitis-comp.json` via `standalone_stdin`/`standalone_stdout` — must match the UART instance wired to your USB-UART bridge (commonly `psu_uart_1` on KV260 carrier boards).
- The **platform component must be built before the application component** in Vitis Unified IDE 2025.x — unlike Vitis Classic, an out-of-date platform is *not* automatically rebuilt when you build the app. Forgetting this step is a common cause of "stale hardware" bugs (app links against an old `.xsa`).
- The linker script (`lscript.ld`, found under `<app>/src/`) defines memory regions (DDR, OCM) derived from the hardware platform's address map — if you ever add a DDR-backed buffer alongside your BRAM test, verify `lscript.ld` reflects the correct DDR range for the A53 (vs. R5) memory view.
- For multi-core or multi-app scenarios, remember each application's `lscript.ld` independently sets DDR base/size — two apps with overlapping DDR regions will silently corrupt each other's `.data`/`.bss`/heap.

### Code Example
```c
// vitis-comp.json relevant excerpt - ensure UART matches KV260 USB-UART bridge
{
  "type": "standalone",
  "os": {
    "standalone": {
      "stdin":  "psu_uart_1",
      "stdout": "psu_uart_1"
    }
  }
}
```
```c
// main.c - PASS/FAIL summary using only xil_printf-supported specifiers
int main() {
    init_platform();
    xil_printf("KV260 AXI-BRAM Demo starting...\r\n");

    int err0 = test_bram(BRAM0_BASEADDR, "BRAM0");
    int err2 = test_bram(BRAM2_BASEADDR, "BRAM2");

    xil_printf("Overall: %s\r\n", (err0 == 0 && err2 == 0) ? "PASS" : "FAIL");
    cleanup_platform();
    return 0;
}
```

### Relevance to Your Project
Your PASS/FAIL UART reporting over USB-UART depends entirely on `stdout` being routed to the correct PS UART instance in the BSP — if the carrier card's USB-UART is wired to `psu_uart_1` (typical on KV260) but the BSP defaults to `psu_uart_0`, you'll get silent output. Double-check `vitis-comp.json` (Unified IDE) or `MSS` `STDOUT` parameter (Classic) matches your actual hardware. Also, since you're rebuilding hardware (`create_bd.tcl`) and software together, the platform-before-app build order is directly relevant to your iteration loop.

## XDC Timing Constraints

### Key Findings
- `set_input_delay`/`set_output_delay` require knowing **which clock domain** registers the I/O — for AXI-connected PL peripherals (like your BRAM controllers), there typically are **no external I/O delay constraints needed** since everything is internal to the PL/PS fabric; these constraints matter for true top-level pins (e.g., GPIO/LEDs/external memory).
- For Zynq UltraScale+ designs, PS-generated clocks (from `M_AXI_HPM0_FPD`, etc.) are auto-constrained by the Clocking Wizard / PS IP; manual `create_clock` is rarely needed unless you add a PL-only clock source.
- `set_clock_groups -asynchronous` is the standard way to tell Vivado that two clock domains (e.g., a PL-generated clock vs. the PS AXI clock) have no fixed phase relationship and shouldn't be timed against each other — prevents false timing failures across CDC (clock-domain-crossing) logic.
- If your design ever drives external pins directly via EMIO/GPIO (e.g., debug LEDs on the carrier card), each pin needs a `set_property PACKAGE_PIN`/`IOSTANDARD` constraint plus, for any *synchronous* interface, appropriate `set_input_delay`/`set_output_delay` relative to the capturing clock.
- Vivado's **Timing Constraints Wizard** (Tools > Timing Constraints Wizard) can auto-generate a baseline XDC skeleton by analyzing the design's unconstrained ports — useful starting point even for AXI-only designs that pick up a stray external port.

### Code Example
```tcl
# kv260_constraints.xdc - typical additions if EMIO/GPIO debug pins are added
# (Not required for the current AXI-Lite-only BRAM0/BRAM2 design, but
#  needed the moment external pins are introduced, e.g. status LEDs)

# Treat a PL-side debug clock as asynchronous to the PS AXI clock domain
set_clock_groups -asynchronous \
    -group [get_clocks -of_objects [get_pins ps/inst/pl_clk0]] \
    -group [get_clocks -of_objects [get_pins dbg_clk_wiz/clk_out1]]

# Example output delay for a status LED driven combinationally off pl_clk0
set_property PACKAGE_PIN H12 [get_ports led_status]
set_property IOSTANDARD LVCMOS33 [get_ports led_status]
set_output_delay -clock [get_clocks pl_clk0] -max 2.000 [get_ports led_status]
set_output_delay -clock [get_clocks pl_clk0] -min 0.500 [get_ports led_status]
```

### Relevance to Your Project
Because BRAM0/BRAM2 communicate purely over the PS-PL AXI interconnect (no top-level I/O pins), your current design likely needs **minimal or no custom XDC** beyond what the K26 SoM base XDC and block-design auto-constraints provide. This section becomes directly relevant the moment you extend the demo with physical I/O (e.g., a GPIO LED to indicate PASS/FAIL on the carrier board) — at that point you'll need pin/IOSTANDARD constraints and possibly clock-group exceptions if that GPIO is driven from a PL-generated clock.

## Kria KV260 / K26 SoM

### Key Findings
- The KV260 Starter Kit ships with boot mode pins set for **QSPI32**, with a pre-loaded boot firmware in QSPI non-volatile memory. For bare-metal development/debug, **JTAG download** (via XSCT/Vitis debugger) is the standard flow — no need to reprogram QSPI for each iteration.
- To temporarily override the boot mode at runtime, you can write the **MPSoC `BOOT_MODE_USER` register at `0xFF5E0200`** and issue a reset — useful for testing alternate boot configurations without touching board straps.
- The K26 SOM uses a **hierarchical boot process**: FSBL first loads a "SOM-only" PMU configuration object, then the boot firmware dynamically applies a **PMU configuration object overlay** specific to the carrier card (KV260 vs. KR260 vs. custom carrier) — this is how the same SOM image adapts MIO assignments to different carrier boards.
- Detailed MIO/EMIO pin mappings for the K26 SOM are documented in the **K26 SOM XDC file** and the **Kria SOM Carrier Card Design Guide (UG1091)** — consult these before assigning any new EMIO-routed signal (e.g., extra GPIO) to avoid conflicts with carrier-card-reserved MIO.
- The PMU (Platform Management Unit) is a MicroBlaze-based unit with 32KB ROM (Boot ROM) + 128KB RAM, responsible for power-domain sequencing — relevant if your design ever needs to power-gate/un-gate PL power islands dynamically.

### Code Example
```tcl
# Confirm target part for K26 SoM in scripted Vivado flows

# If using the official Kria KV260 base platform XSA as a starting point

# set_property pfm_name {kv260_custom_platform} [get_files kv260_custom.xsa]
```


### Relevance to Your Project
Your bare-metal demo almost certainly runs via **JTAG download from Vitis** during development (consistent with the KV260's default QSPI32 boot + JTAG debug workflow). If you later want a "power-on and run" demo (no host PC needed), you'd package the bitstream + ELF into a boot image and program QSPI — at that point the PMU overlay and boot-mode details above become directly actionable.

## AMD/Xilinx Tool Updates (2025.x)

### Key Findings
- **Vivado 2025.1** introduces **Intelligent Design Runs (IDR)** — an automated timing-closure flow triggered via right-click on a failing implementation run, which iterates strategies automatically. Useful if adding more IP (e.g., a third BRAM or a DMA) ever pushes your design into timing failures.
- A new **Pblock planner** in 2025.1 centralizes floorplanning/pblock creation — relevant if you partition the design for incremental builds.
- Vivado 2025.1 also added the ability to **boot the PS first and dynamically load the PL later** — a useful pattern for bring-up flows where you want Linux/U-Boot running before the bitstream with your BRAM peripherals is loaded (PL programming via `fpgautil`/`xmutil` on PetaLinux, though your demo is bare-metal).
- **Vitis Unified IDE** is now the default IDE for 2025.x — it supports configuring and running standalone (bare-metal) apps on KV260/KR260 directly via USB, but enforces the platform-before-application build ordering noted earlier.
- Community tutorials (e.g., MicroBlaze V on KR260 with Vitis 2025.1) confirm the 2025.1 bare-metal flow works end-to-end for Kria boards, though some report needing to manually re-export the platform after any block-design change — don't assume the IDE picks up a regenerated `.xsa` automatically.

### Code Example
```tcl
# Example: scripted XSA export after block design changes (Vivado 2025.1)
# Run after synth/impl complete - required input for Vitis platform rebuild
write_hw_platform -fixed -include_bit -force ./export/kv260_wrapper.xsa
```

### Relevance to Your Project
Each time `create_bd.tcl` changes the BRAM address map or adds an IP, you must **re-export the `.xsa`** (`write_hw_platform`) and then **rebuild the Vitis platform component** (not just the application) before `main.c` will see the updated memory map — a step that's easy to forget in 2025.x's Unified IDE since it no longer auto-detects a stale platform.
