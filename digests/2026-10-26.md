# FPGA Research Digest - 2026-10-26

## Executive Summary

- **AXI-Lite deadlock risk**: Never wait for READY before asserting VALID — this violates the spec and can deadlock your PS↔PL path. The KV260 write path (PS → BRAM0/BRAM2 over AXI-Lite) must obey this rule on both the address-write (AW) and data-write (W) channels.
- **BRAM read latency**: The AXI BRAM Controller has a minimum 1-cycle read latency that is not always guaranteed. If your bare-metal C read-back loop sees stale data, register the BRAM output or add a wait cycle after asserting `ARVALID` before sampling `RDATA`.
- **TCL non-project mode robustness**: Always use timestamped log files and check `get_property STATUS [get_runs impl_1]` in your `create_bd.tcl` — synthesis can pass while implementation silently fails.
- **Vitis stdout routing**: For xil_printf to appear on USB-UART on Kria, `standalone_stdin`/`standalone_stdout` BSP settings must point to `psu_uart_1` (not the default). Regenerate the BSP after changing this.
- **Vivado 2025.1 VHDL coverage**: Full VHDL code coverage is now available in the ML Standard Edition simulator — useful for verifying that your `kv260_top.vhd` wrapper exercises all branches in simulation.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- A transfer occurs **only** when both `VALID` and `READY` are sampled high on the same rising clock edge. The source must assert `VALID` without waiting for `READY` first; once asserted, `VALID` cannot be de-asserted until the handshake completes.
- **VALID-before-READY rule**: Waiting for READY before asserting VALID is the single most common AXI-Lite deadlock. If both master and slave wait for each other's signal, the bus stalls indefinitely.
- **Write-channel ordering**: The `AW` (address) and `W` (data) channels are independent and can complete in either order. The subordinate (e.g., AXI BRAM Controller) must wait for both before asserting `BVALID`. Software reading back data must wait for `BVALID` before issuing `ARVALID` if read-after-write ordering is required.
- **Register slices for timing closure**: Each AXI register slice adds exactly one cycle of latency but zero throughput loss, and is the standard tool for closing timing across long interconnect routes.
- **AXI VIP pitfall**: Vivado AXI Verification IP timing depends heavily on clock configuration and VIP parameters. Misconfigured simulation time resolution or VIP parameters will cause control signals to not align as coded.
- **AXI-Stream TLAST constraint**: TLAST must not change while the channel is stalled (`TVALID && !TREADY`). Some older Xilinx IP versions violated this on the penultimate burst beat — verify with the IP change log if you add streaming peripherals.

### Code Example

```c
/* AXI-Lite write + read-back with proper ordering on Kria KV260 */
#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL

static inline void axi_write32(uint32_t addr, uint32_t val) {
    *(volatile uint32_t *)addr = val;
    /* Compiler barrier — prevents reordering past this point */
    __asm__ volatile ("dsb sy" ::: "memory");
}

static inline uint32_t axi_read32(uint32_t addr) {
    __asm__ volatile ("dsb sy" ::: "memory");
    return *(volatile uint32_t *)addr;
}

/* Wait for write response before issuing read (read-after-write safety) */
void bram_write_verify(uint32_t base, uint32_t offset, uint32_t pattern) {
    axi_write32(base + offset, pattern);
    uint32_t rb = axi_read32(base + offset);
    xil_printf("BRAM[0x%08X] WR=0x%08X RD=0x%08X %s\r\n",
               base + offset, pattern, rb,
               (rb == pattern) ? "PASS" : "FAIL");
}
```

### Relevance to Your Project

Your bare-metal loop writes patterns to BRAM0 (`0xA0000000`) and BRAM2 (`0xA0010000`) and reads them back. The `dsb sy` barrier in bare-metal C ensures the Cortex-A53 does not reorder the store before the AXI write completes at the interconnect level. Without it, the processor's write buffer may let the subsequent read return stale cached data rather than the value just written to the BRAM.

## Vivado Block Design / IP Integrator

### Key Findings

- **Connection Automation**: The "Designer Assistance" ribbon (Block Automation + Connection Automation) detects common interface signals and wires them in a single step. Toggle Auto → Manual to override any individual connection.
- **Address Editor**: Addresses are auto-assigned as subordinates are added. If validation reports "unmapped peripheral", right-click the Address Editor and select **Auto-Assign Address**. The tab only appears when the design contains at least one bus master.
- **Validate Design**: Run `validate_bd_design` (or the GUI equivalent) after every structural change. Real-time DRC does not catch incorrect clock frequencies or missing resets.
- **External reset synchronization**: The AMD IP Integrator 2025.2 tutorial recommends routing all external resets through a **Processor System Reset** block to synchronize them to the clock domain, rather than wiring raw reset ports directly.
- **Saving diagrams**: In project mode, always save the block design (`save_bd_design` in Tcl) before generating an HDL wrapper; unsaved changes to the diagram are not picked up by synthesis.

### Code Example

```tcl
# Tcl snippet: automate connections after adding AXI BRAM Controller
apply_bd_automation -rule xilinx.com:bd_rule:axi4 \
    -config { Clk_master {Auto} Clk_slave {Auto} Clk_xbar {Auto} \
              Master {/zynq_ultra_ps_e_0/M_AXI_HPM0_FPD} \
              Slave {/axi_bram_ctrl_0/S_AXI} \
              intc_ip {New AXI Interconnect} \
              master_apm {0} } \
    [get_bd_intf_pins axi_bram_ctrl_0/S_AXI]

# Validate and assign addresses
validate_bd_design
assign_bd_address
save_bd_design
```

### Relevance to Your Project

Your `create_bd.tcl` script drives the full block design. Use `validate_bd_design` as a check step and `assign_bd_address` to ensure BRAM0 (`0xA0000000`, 64 KB) and BRAM2 (`0xA0010000`, 64 KB) land at the expected PS address-map offsets that your `main.c` hard-codes.

## Vivado TCL Scripting

### Key Findings

- **Batch vs interactive**: Develop scripts interactively in Tcl mode, then switch to batch mode for CI. Running `vivado -mode batch -source script.tcl` exits with non-zero code on Tcl error, but synthesis can succeed while implementation fails — always check `get_property STATUS [get_runs impl_1]`.
- **Timestamped logs**: Vivado overwrites `vivado.log`/`vivado.jou` each run. Rename them immediately after a run to preserve failed-run diagnostics: `file rename vivado.log vivado_${timestamp}.log`.
- **Non-project mode commands**: Use `read_vhdl`, `read_xdc`, `read_bd` etc. instead of `add_files`. Non-project mode allows conditional logic around each implementation step and repeated optimizations without resetting the project.
- **`wait_on_run` blocking**: Calling `wait_on_run synth_1` blocks the Tcl shell indefinitely in interactive mode. Only use it inside a batch script.
- **Checkpoints**: Write DCPs after synthesis and routing with `write_checkpoint`. This enables incremental re-runs that skip completed stages and allows loading a routed design for timing analysis without re-running implementation.
- **Exit codes**: Wrap your batch script in a `catch` block and call `exit 1` on error so CI pipelines catch failures correctly.

### Code Example

```tcl
#!/usr/bin/env tclsh
# Non-project mode: read → synth → impl → bitstream

set timestamp [clock format [clock seconds] -format %Y%m%d_%H%M%S]
set log_dir   ./logs/$timestamp
file mkdir $log_dir

open_project ""   ;# non-project mode — no project file

read_vhdl  [glob ./vhdl/*.vhd]
read_xdc   ./constraints/kv260_top.xdc
read_bd    ./bd/system.bd

synth_design -top kv260_top -part xck26-sfvc784-2LV-c
write_checkpoint -force $log_dir/post_synth.dcp

opt_design
place_design
route_design
write_checkpoint -force $log_dir/post_route.dcp

# Fail fast if timing is not met
set wns [get_property SLACK [get_timing_paths -max_paths 1 -nworst 1]]
if {$wns < 0} {
    puts "ERROR: Timing not met (WNS=${wns}ns)"
    exit 1
}

write_bitstream -force ./output/kv260_top.bit
puts "Bitstream written successfully"
```

### Relevance to Your Project

Your `create_bd.tcl` script generates the block design in project mode. Wrapping it with the pattern above — timestamped logs, status checks, and checkpoints — will catch silent failures and make re-runs faster during iterative debug of the BRAM address mapping.

## Vitis Bare-Metal / Standalone

### Key Findings

- **stdout routing is not automatic**: On Kria KD240/KV260, `xil_printf` output does not appear on the USB-UART unless the BSP `standalone_stdin` and `standalone_stdout` settings are explicitly changed to `psu_uart_1`. The default often points to `psu_uart_0` (or none). Regenerate the BSP after the change.
- **Memory sizing**: Adding `xil_printf` (the lightweight version, ~1 KB) increases code size. If the linker script's heap/stack sections are tight, you will get a link error. Check the `lscript.ld` `.text` section limit; for a KV260 design targeting DDR, use `psu_ddr_0` with a generous size.
- **Interrupt GIC flow**: The standard flow for PL interrupts on Zynq UltraScale+ is: initialize XScuGic, register the handler, enable the interrupt ID on the GIC, and call `Xil_ExceptionEnable()`. Missing the last step is the most common reason interrupt handlers never fire.
- **PL interrupt IDs in xparameters.h**: A 2024.2 forum post reports that custom PL interrupt IDs do not appear in `xparameters.h` if the interrupt port is not connected in the block design. Verify the `pl_ps_irq0[0:0]` net is driven in IPI.
- **Standalone library xil_printf size**: `xil_printf` is approximately 1 KB vs. standard `printf` at ~20 KB. Always prefer `xil_printf` in bare-metal to stay within typical BRAM-mapped code regions.

### Code Example

```c
/* Interrupt handler skeleton for Zynq UltraScale+ / Kria KV260 */
#include "xscugic.h"
#include "xil_exception.h"
#include "xparameters.h"

#define PL_IRQ_ID  XPAR_FABRIC_AXI_GPIO_0_IP2INTC_IRPT_INTR

static XScuGic gic;

void pl_irq_handler(void *cb) {
    xil_printf("PL interrupt fired\r\n");
}

void setup_gic_interrupt(void) {
    XScuGic_Config *cfg = XScuGic_LookupConfig(XPAR_SCUGIC_SINGLE_DEVICE_ID);
    XScuGic_CfgInitialize(&gic, cfg, cfg->CpuBaseAddress);

    XScuGic_Connect(&gic, PL_IRQ_ID,
                    (Xil_InterruptHandler)pl_irq_handler, NULL);
    XScuGic_Enable(&gic, PL_IRQ_ID);

    Xil_ExceptionInit();
    Xil_ExceptionRegisterHandler(XIL_EXCEPTION_ID_IRQ_INT,
                                 (Xil_ExceptionHandler)XScuGic_InterruptHandler,
                                 &gic);
    Xil_ExceptionEnable();   /* <-- commonly forgotten */
}
```

### Relevance to Your Project

Your bare-metal `main.c` uses `xil_printf` for PASS/FAIL output. If you ever extend the design to add an interrupt-driven BRAM controller, the GIC setup above is the correct scaffold. For now, verify that `psu_uart_1` is selected as stdout in the BSP to ensure your PASS/FAIL output actually reaches the USB-UART terminal.

## XDC Timing Constraints

### Key Findings

- **set_input_delay / set_output_delay model external paths**: These commands tell Vivado's timing engine how long signals spend outside the FPGA, relative to a clock edge at the port. Values can be positive or negative depending on phase relationships.
- **Min/max maps to hold/setup**: `set_input_delay -min` → hold analysis; `set_input_delay -max` → setup analysis. Forgetting the `-min` version causes hold violations to go unchecked.
- **Constraint ordering matters**: Create generated clocks and `set_clock_groups` before defining input/output delays. Constraints applied out of order can silently override each other in the Timing Constraints editor.
- **Asynchronous clock domains**: Use `set_clock_groups -asynchronous` with each domain in its own `-group` argument. For Kria designs, the PS clock (`clk_pl_0`) and any user-generated PL clocks are typically asynchronous and need this treatment.
- **Kria BRAM path**: For a pure PS→PL AXI-Lite BRAM path with no external I/O, `set_input_delay`/`set_output_delay` are not needed — the constraint file only needs the primary PL clock definition (if the PS does not drive it) and any `set_clock_groups` for multi-domain designs.

### Code Example

```xdc
# Primary PL clock from PS (100 MHz typical on KV260)
# The PS drives clk_pl_0 automatically; only constrain
# if you have a secondary oscillator on a HDIO pin.

# Example: 100 MHz clock from PS to PL (auto-derived, for reference only)
# create_clock -period 10.000 -name clk_pl_0 [get_pins zynq_ultra_ps_e_0/pl_clk0]

# Async clock group: PS system clock vs. user PL clock from MMCM
set_clock_groups -asynchronous \
    -group [get_clocks clk_pl_0] \
    -group [get_clocks clk_out1_clk_wiz_0]

# GPIO output to PL pin: model external 2 ns setup / 1 ns hold
set_output_delay -clock clk_pl_0 -max 2.000 [get_ports {led[*]}]
set_output_delay -clock clk_pl_0 -min -1.000 [get_ports {led[*]}]
```

### Relevance to Your Project

The KV260 AXI-BRAM demo operates entirely over internal PS→PL AXI interconnect with no external I/O in the critical path. Your XDC file likely only needs a `set_clock_groups` call if your block design includes a clock wizard. For any future expansion with external pins (e.g., HDIO LEDs or status signals), use the min/max pattern above and verify with `report_timing_summary`.

## Kria KV260 / K26 SoM

### Key Findings

- **Boot mode strapping**: Boot device is selected by `MODE[3:0]` pins on the carrier board. The KV260 ships preset for QSPI32 (mode value `0010`), with the boot firmware in on-board QSPI flash. Changing boot mode requires physical rework of the carrier or a JTAG override.
- **Reserved MIO pins**: These MIO lines are claimed by the boot firmware and should not be driven by bare-metal PL logic:
  - MIO12 — firmware update enable
  - MIO31 — PMU hardware shutdown input
  - MIO35 — PMU external watchdog
  - MIO36/37 — default Linux UART console (PS UART0)
- **Bare-metal UART**: The Kria boot firmware and PetaLinux BSP default to UART on MIO36/37 (PS UART0). For Vitis bare-metal, map `xil_printf` to `psu_uart_1` (MIO40/41) to avoid contention with the boot console.
- **MIO voltage**: All three MIO banks are powered by the SOM at **1.8 V**. External pull-ups or level shifters on carrier-side MIO lines must target 1.8 V, not 3.3 V.
- **Power domains**: AMD recommends splitting carrier power into three groups: (1) always-on infrastructure, (2) PS domain (MIO + PS-GTR peripherals), and (3) PL domain (HDIO peripherals). Powering them in the wrong order can prevent PL configuration.
- **K26 SOM PL access**: The KV260 carrier breaks out PL I/O on the HDIO and LVDS banks. For BRAM-only designs (purely internal), no HDIO constraints are needed, and XDC can be minimal.

### Code Example

```c
/* Kria KV260 bare-metal UART init — use psu_uart_1 (MIO40/41) */
#include "xuartps.h"
#include "xparameters.h"

/* Ensure BSP stdout = psu_uart_1 before calling xil_printf */
void uart_init(void) {
    XUartPs uart;
    XUartPs_Config *cfg = XUartPs_LookupConfig(XPAR_PSU_UART_1_DEVICE_ID);
    XUartPs_CfgInitialize(&uart, cfg, cfg->BaseAddress);
    XUartPs_SetBaudRate(&uart, 115200);
    /* xil_printf will now route through psu_uart_1 at 115200 baud */
}
```

### Relevance to Your Project

If your USB-UART terminal shows garbage or nothing at all on the KV260, the first thing to check is whether the BSP `stdout` is set to `psu_uart_1`. The reserved MIO36/37 console conflict is a very common cause of silent bare-metal failures on Kria boards.

## AMD/Xilinx Tool Updates (Vivado/Vitis 2025.x)

### Key Findings

- **Vivado 2025.1 adds VHDL code coverage**: Full VHDL code coverage is now available in the ML Standard Edition simulator (not just SystemVerilog). This means you can generate a coverage report for `kv260_top.vhd` in simulation without a paid simulator license.
- **New AXI Switch IP**: Vivado 2025.1 introduces a fully customizable RTL-based AXI Switch IP that bridges between different AXI interface types (AXI4, AXI-Lite, AXI-Stream). This simplifies mixed-protocol designs.
- **New device support**: Vivado 2025.1 adds support for AMD Spartan UltraScale+ and next-generation Versal AI Edge devices. No change to Kria/Zynq UltraScale+ support.
- **IP change log (2025.1)**: Key IP changes in the 2025.1 release include:
  - AXI Ethernet Lite: added 8-queue PTP frame scheduling
  - PCIe: discontinued Bridged Endpoint on xc7z010/xa7z010 (insufficient resources)
  - Advanced IO Wizard: added Sync LVDS mode for Versal devices
- **Vitis 2025.x**: No breaking changes to the Kria KV260 bare-metal flow were found. The Vitis platform creation flow for Kria remains consistent with the 2023.2–2024.2 documented path.
- **2025.2 also available**: Vivado/Vitis 2025.2 has been released with additional IP changes (see AMD Answer Record 000039903). Consider upgrading from 2025.1 if the Kria KV260 platform support is updated.

### Code Example

### Relevance to Your Project

Enable the new VHDL coverage feature to confirm that your `kv260_top.vhd` wrapper exercises the AXI-Lite handshake logic for both BRAM0 and BRAM2 paths in simulation before committing to hardware. This catches missing branch coverage (e.g., read without preceding write) with zero additional tooling cost on ML Standard Edition.
