# FPGA Research Digest - 2026-06-16

## Executive Summary

- **Vivado 2025 AXI address space bug**: Custom AXI peripherals in Vivado 2025.x are silently limited to a 1 KB usable address space even when configured for wider widths — directly impacts any custom AXI-Lite slave IP added alongside the BRAM controllers in your block design.
- **IP config format changed to JSON**: Vivado 2025.2 switched AMD IP configuration files from XML to JSON for better revision control and faster load times — expect `.xci` files to look different when diffing between tool versions.
- **AXI-Lite BRESP deadlock risk**: Both the Write Address (AW) and Write Data (W) channels must complete their handshakes *before* the slave is permitted to assert BVALID — software polling a write-done register can deadlock if the firmware never reads BRESP.
- **AXI SmartConnect ultra-low-area mode**: Vivado 2025.2 added a `STRATEGY` parameter to AXI Switch and SmartConnect IP for ultra-low-area mode — useful when PL resource budget is tight on the K26 SoM.
- **Bare-metal KV260 guide updated for 2025.2**: A fresh Hackster.io guide covers the full flow from Vivado block design through Vitis bare-metal application for KV260, including the new Vitis Unified IDE project structure.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- AXI-Lite defines five independent channels: Write Address (AW), Write Data (W), Write Response (B), Read Address (AR), and Read Data (R). Each uses VALID/READY handshake — a transfer occurs only when *both* signals are high on the same rising clock edge.
- **VALID must not be deasserted** once asserted until READY rises. Violating this rule (e.g., deassert AWVALID because the master got impatient) constitutes a protocol violation that may silently corrupt transactions.
- On writes, both AW and W channel handshakes must complete before the slave may assert BVALID. The AXI4 spec does not mandate which comes first — a robust slave must handle either ordering.
- AXI-Lite slaves are forbidden from returning EXOKAY on BRESP; only OKAY (2'b00) or SLVERR (2'b10) are valid.
- **AXI-Stream TVALID stickiness**: Once TVALID is asserted it must remain high until TREADY is seen. Deasserting it mid-burst is a protocol violation that breaks downstream FIFOs and interconnects.
- TLAST pitfall: Some Xilinx primitives will not forward a packet unless TLAST is asserted. If TLAST is set while the channel is back-pressured (TREADY low), it must remain asserted — a common bug in hand-rolled stream logic.
- Vivado 2025 known issue: Custom AXI-Full peripherals may be constrained to a 1 KB effective address range even when configured for wider address widths (16-bit+). Workaround: use standard Xilinx IP (AXI BRAM Controller) rather than Vivado-generated peripheral templates for wide address maps.

### Code Example

```vhdl
-- Minimal AXI-Lite slave write path with correct BRESP handshake
-- Waits for both AW and W handshakes before asserting BVALID
process(clk)
begin
  if rising_edge(clk) then
    if rst = '1' then
      aw_done   <= '0';
      w_done    <= '0';
      s_bvalid  <= '0';
      s_bresp   <= "00"; -- OKAY
    else
      -- Latch AW handshake
      if s_awvalid = '1' and s_awready = '1' then
        aw_done <= '1';
        addr_reg <= s_awaddr;
      end if;
      -- Latch W handshake and write data
      if s_wvalid = '1' and s_wready = '1' then
        w_done   <= '1';
        data_reg <= s_wdata;
      end if;
      -- Issue response only when both channels completed
      if aw_done = '1' and w_done = '1' and s_bvalid = '0' then
        mem(to_integer(unsigned(addr_reg(11 downto 2)))) <= data_reg;
        s_bvalid <= '1';
        s_bresp  <= "00"; -- OKAY
        aw_done  <= '0';
        w_done   <= '0';
      end if;
      -- Deassert BVALID after master accepts response
      if s_bvalid = '1' and s_bready = '1' then
        s_bvalid <= '0';
      end if;
    end if;
  end if;
end process;
```

### Relevance to Your Project

Your KV260 bare-metal demo writes to BRAM0 at `0xA0000000` and BRAM2 at `0xA0010000` using AXI-Lite. The BRESP channel issue is particularly relevant: if your C code writes a pattern and immediately reads back without checking BVALID completion, there's a race window. The AXI BRAM Controller IP handles this correctly, but a custom slave would not. The Vivado 2025 address-space bug does not affect you when using Xilinx's AXI BRAM Controller IP (which has its own hardened address decode), but would bite any companion custom peripheral you add later.

## Vivado Block Design / IP Integrator

### Key Findings

- **Connection Automation** in IP Integrator can wire the Zynq UltraScale+ PS `M_AXI_HPM0_FPD` master port directly to an AXI SmartConnect, then to your BRAM controllers with a single right-click → "Run Connection Automation."
- The TCL Console echoes every GUI action as a Tcl command, making it a live learning tool: open the block design, click a connection, and capture the exact `connect_bd_intf_net` syntax for your automation script.
- **Regenerating the block design**: After editing a `.tcl` script that re-creates the BD, use `source create_bd.tcl` in the Vivado Tcl console or in batch mode. Always call `validate_bd_design` and `save_bd_design` at the end of the script.
- Xilinx changes the block design TCL API between tool versions — a `.tcl` exported from 2024.x may fail in 2025.x due to renamed IP parameters. Always re-export from the current tool version.
- **IP config format change**: Vivado 2025.2 changed `.xci` (IP customization) from XML to JSON. If your repo diffs show unexpected file churn, this is likely why.
- In 2025.2, AXI SmartConnect gained a new `STRATEGY` parameter supporting an ultra-low-area mode — reduces LUT count for designs where interconnect area is a concern.

### Code Example

```tcl
# Minimal block design re-creation script for KV260 AXI-BRAM demo
# Run: vivado -mode batch -source create_bd.tcl

open_project kv260.xpr
open_bd_design [get_files *.bd]

# Add Zynq UltraScale+ PS (K26 preset)
set ps [create_bd_cell -type ip -vlnv xilinx.com:ip:zynq_ultra_ps_e:3.5 zynq_ps]
set_property -dict [list \
  CONFIG.PSU__USE__M_AXI_GP0 {1} \
  CONFIG.PSU__UART0__PERIPHERAL__ENABLE {1} \
] $ps

# AXI SmartConnect (1 master, 2 slaves)
set sc [create_bd_cell -type ip -vlnv xilinx.com:ip:smartconnect:1.0 axi_sc]
set_property CONFIG.NUM_SI {1} $sc
set_property CONFIG.NUM_MI {2} $sc

# Two AXI BRAM Controllers
set bc0 [create_bd_cell -type ip -vlnv xilinx.com:ip:axi_bram_ctrl:4.1 axi_bram_ctrl_0]
set bc1 [create_bd_cell -type ip -vlnv xilinx.com:ip:axi_bram_ctrl:4.1 axi_bram_ctrl_1]

# Wire PS → SmartConnect → BRAM controllers
connect_bd_intf_net [get_bd_intf_pins $ps/M_AXI_HPM0_FPD] \
                    [get_bd_intf_pins $sc/S00_AXI]
connect_bd_intf_net [get_bd_intf_pins $sc/M00_AXI] \
                    [get_bd_intf_pins $bc0/S_AXI]
connect_bd_intf_net [get_bd_intf_pins $sc/M01_AXI] \
                    [get_bd_intf_pins $bc1/S_AXI]

# Assign addresses
assign_bd_address [get_bd_addr_segs $bc0/S_AXI/Mem0] \
  -offset 0xA0000000 -range 8K
assign_bd_address [get_bd_addr_segs $bc1/S_AXI/Mem0] \
  -offset 0xA0010000 -range 8K

validate_bd_design
save_bd_design
```

## Vivado TCL Scripting

### Key Findings

- **Non-project mode** gives maximum reproducibility: no `.xpr` file is created; everything is driven by TCL. The flow is `read_vhdl` → `read_xdc` → `synth_design` → `write_checkpoint` → `opt_design` → `place_design` → `route_design` → `write_bitstream`.
- Saving Design Checkpoints (`.dcp`) after each major step is critical in non-project mode — it allows re-running from any stage without full re-synthesis.
- Batch execution: `vivado -mode batch -source run.tcl -notrace` runs the script and exits. Add `-log run.log -journal run.jou` to capture output.
- **Project mode** is simpler for block designs: the BD TCL API only works reliably inside an open project. Non-project mode requires manual `open_bd_design` and `generate_target` calls.
- Use `get_timing_paths -max_paths 10 -slack_lesser_than 0` after routing to catch critical paths before generating bitstream.
- Vivado Tcl API changes between versions — use `version` command at script start to guard against API incompatibilities.

### Code Example

```tcl
#!/usr/bin/env tclsh
# Non-project mode batch flow for KV260 AXI-BRAM demo
# Usage: vivado -mode batch -source build.tcl

set PART "xck26-sfvc784-2LV-c"
set OUTDIR "./output"
file mkdir $OUTDIR

# Read sources
read_vhdl   [glob ./vhdl/*.vhd]
read_xdc    ./constraints/kv260_top.xdc

# Synthesis
synth_design -top kv260_top -part $PART -flatten_hierarchy rebuilt
write_checkpoint -force $OUTDIR/post_synth.dcp
report_utilization -file $OUTDIR/utilization_synth.rpt

# Implementation
opt_design
place_design
phys_opt_design
write_checkpoint -force $OUTDIR/post_place.dcp

route_design
write_checkpoint -force $OUTDIR/post_route.dcp

# Timing check — fail fast if negative slack
set wns [get_property SLACK [get_timing_paths -max_paths 1 -nworst 1 -setup]]
if {$wns < 0} {
    puts "ERROR: Timing not met, WNS = $wns ns"
    exit 1
}

# Bitstream
write_bitstream -force $OUTDIR/kv260_top.bit
puts "Build complete: $OUTDIR/kv260_top.bit"
```

### Relevance to Your Project

Your current `create_bd.tcl` runs in project mode (it opens the `.xpr`). Consider adding a thin wrapper `build.tcl` that calls `source create_bd.tcl`, then drives synthesis through bitstream non-interactively — this enables CI/CD-style reproducible builds and surfaces timing violations before you flash hardware.

## Vitis Bare-Metal / Standalone

### Key Findings

- The Vitis **Standalone BSP** (`standalone_v9.x`) provides `xil_printf`, `Xil_Out32`/`Xil_In32` register accessors, cache maintenance (`Xil_DCacheFlush`), and timer functions — no OS required.
- `xil_printf` uses UART0 by default on Zynq UltraScale+. On KV260 the USB-UART is connected to PS UART0 (MIO 38/39). Verify the BSP `STDIN_BASEADDRESS` and `STDOUT_BASEADDRESS` match `0xFF000000` (UART0) in `xparameters.h`.
- **Cache coherency**: After writing to PL-mapped AXI space from the A53, call `Xil_DCacheFlush()` before reading back — the A53 L1/L2 caches can hold stale data if the PL address range isn't marked as device/strongly-ordered in the MMU table.
- Vitis Unified IDE (2023.1+) replaces the Eclipse-based workspace with a new project structure — the application source and BSP are now separate components referenced in a `vitis-comp.json`.
- **Linker script**: The auto-generated `lscript.ld` maps code to DDR (`ps_ddr_0` at `0x00000000`, 2 GB). For BRAM-resident code, add a custom `MEMORY` region pointing at your BRAM address and change the `.text` section assignment.
- Stack and heap sizes in `lscript.ld` default to 1 KB each — increase them if using `printf` (which can consume several KB of stack).
- A bare-metal KV260 project template (miya4649/Vitis_KV260_KR260_Template) provides a minimal working starting point with LED blink that can be adapted.

### Code Example

```c
#include "xil_io.h"
#include "xil_printf.h"
#include "xil_cache.h"

#define BRAM0_BASE  0xA0000000UL
#define BRAM1_BASE  0xA0010000UL
#define TEST_WORDS  16

int main(void) {
    xil_printf("\r\n=== KV260 AXI-BRAM Test ===\r\n");

    /* Flush D-cache before touching PL-mapped space */
    Xil_DCacheFlush();

    /* Write phase */
    for (int i = 0; i < TEST_WORDS; i++) {
        Xil_Out32(BRAM0_BASE + (i * 4), 0xA0000000 + i);
        Xil_Out32(BRAM1_BASE + (i * 4), 0xB0000000 + i);
    }

    /* Read-back phase */
    int pass = 1;
    for (int i = 0; i < TEST_WORDS; i++) {
        u32 r0 = Xil_In32(BRAM0_BASE + (i * 4));
        u32 r1 = Xil_In32(BRAM1_BASE + (i * 4));
        if (r0 != (0xA0000000 + i)) {
            xil_printf("BRAM0[%d] FAIL: got 0x%08X\r\n", i, r0);
            pass = 0;
        }
        if (r1 != (0xB0000000 + i)) {
            xil_printf("BRAM1[%d] FAIL: got 0x%08X\r\n", i, r1);
            pass = 0;
        }
    }
    xil_printf("Result: %s\r\n", pass ? "PASS" : "FAIL");
    return 0;
}
```

### Relevance to Your Project

This matches the core pattern of your `main.c`. The `Xil_DCacheFlush()` call before the read-back loop is the most common omission that causes intermittent failures — the A53 may serve the read from cache rather than going out to the PL BRAM. Add the flush call between your write and read phases if you see unreliable PASS/FAIL results.

## XDC Timing Constraints

### Key Findings

- **`set_input_delay`** and **`set_output_delay`** express external system-level delays relative to a clock edge at the FPGA boundary. Values are in nanoseconds and can be positive or negative depending on phase relationships.
- For AXI-connected PS–PL interfaces (like `M_AXI_HPM0_FPD`), the PS7/PS8 block handles internal timing — you do **not** need `set_input_delay`/`set_output_delay` on AXI ports crossing only the PS–PL boundary within the device.
- You **do** need I/O timing constraints for any signal reaching a physical pin: clocks (`create_clock`), synchronous inputs (`set_input_delay`), and synchronous outputs (`set_output_delay`).
- `set_clock_groups -asynchronous` is required whenever two clocks in the design are unrelated (e.g., the PL fabric clock from the PS vs. an external clock on a PMOD pin).
- AMD UG835 (2025.1) documents all Tcl timing commands with exact syntax — the online version is current for 2025.1 tool releases.
- Vivado's **Timing Constraint Wizard** (Tools → Timing Wizard) generates a first-pass XDC with all detected clocks and I/O constraints — useful to auto-generate then manually refine.
- IDELAY/ODELAY primitives provide fine-grained per-pin delay compensation (up to ~1.25 ns on UltraScale+) for high-speed interfaces; not needed for low-speed AXI-Lite demos.

### Code Example

```xdc
# KV260 / K26 SoM XDC - minimal constraints for AXI-BRAM demo
# The PS provides the PL fabric clock; declare it so Vivado can time paths

# PL Fabric Clock from PS (100 MHz example - match your block design setting)
create_clock -period 10.000 -name clk_pl_0 [get_pins zynq_ps/inst/PS8_i/PLCLK[0]]

# If you have an external clock input on a PMOD pin:
# create_clock -period 20.000 -name ext_clk [get_ports ext_clk_pin]
# set_clock_groups -asynchronous -group [get_clocks clk_pl_0] \
#                                -group [get_clocks ext_clk]

# Example: constrain a GPIO output driven by PL logic to a PCB load of 3 ns
# set_output_delay -clock clk_pl_0 -max 3.000 [get_ports {led[*]}]
# set_output_delay -clock clk_pl_0 -min -1.000 [get_ports {led[*]}]

# False path on asynchronous reset (if used)
# set_false_path -from [get_ports rst_n]

# Disable timing on debug-only pins
# set_false_path -to [get_ports {debug[*]}]
```

### Relevance to Your Project

Your KV260 AXI-BRAM demo likely has minimal I/O constraints since the PS–PL AXI bus is fully internal. The critical constraint is `create_clock` on the PL fabric clock (`PLCLK[0]`) so Vivado can verify internal register-to-register timing on any VHDL logic in `kv260_top.vhd`. Without it, Vivado may report "no clocks found" and skip timing analysis entirely.

## Kria KV260 / K26 SoM

### Key Findings

- The K26 SoM integrates a Zynq UltraScale+ MPSoC (ZU5EV or ZU3EG) with 4 GB LPDDR4, 16 GB eMMC, and a fixed MIO configuration baked into the SOM hardware — carrier card designers work with EMIO and the PL only.
- **Boot modes**: The KV260 starter kit ships configured for QSPI32 boot from eMMC. For bare-metal development, SD card boot is the most convenient mode (JTAG is also supported for debug without filesystem setup).
- **MIO allocation** on K26: UART0 is fixed to MIO 38/39, GEM3 (Ethernet) to MIO 64–77, SD1 to MIO 46–51, USB0 to MIO 52–63. These are set in the PS configuration of the SOM and cannot be changed on the carrier card — only EMIO signals are routable to PL pins.
- The default `k26-starter-kits` reference bitstream includes an EMIO fan control signal — a useful reference for how the SOM maps EMIO to PL pins on the KV260 carrier.
- PS GEM3 is used for Ethernet on KV260 (KR260 uses GEM1) — relevant if adding networking to a future demo.
- For custom carrier card development, AMD provides a "Custom Carrier Card Flow" that defines how to set MIO/EMIO in Vivado and export the hardware to Vitis.
- Kria apps documentation (xilinx.github.io/kria-apps-docs) provides the canonical bare-metal flow with XSA generation, BSP creation, and application build steps.

### Code Example

```tcl
# Vivado PS8 configuration for K26 SoM on KV260 carrier
# These MIO settings match the fixed SOM hardware -- do not change MIO 38/39 (UART0)
set_property -dict [list \
  CONFIG.PSU__UART0__PERIPHERAL__ENABLE    {1} \
  CONFIG.PSU__UART0__PERIPHERAL__IO       {MIO 38 .. 39} \
  CONFIG.PSU__SD1__PERIPHERAL__ENABLE     {1} \
  CONFIG.PSU__SD1__PERIPHERAL__IO        {MIO 46 .. 51} \
  CONFIG.PSU__USB0__PERIPHERAL__ENABLE    {1} \
  CONFIG.PSU__GEM3__PERIPHERAL__ENABLE    {1} \
  CONFIG.PSU__GEM3__PERIPHERAL__IO       {MIO 64 .. 77} \
  CONFIG.PSU__USE__M_AXI_GP0             {1} \
  CONFIG.PSU__FPGA_PL0_ENABLE            {1} \
  CONFIG.PSU__CRL_APB__PL0_REF_CTRL__FREQMHZ {100} \
] [get_bd_cells zynq_ps]
```

### Relevance to Your Project

Your demo relies on `M_AXI_HPM0_FPD` (PS AXI master port 0) to reach the PL BRAM controllers, and on UART0 (MIO 38/39) for `xil_printf` output over USB-UART. The TCL above is the canonical PS configuration block for KV260 — verify your `create_bd.tcl` sets `PSU__UART0__PERIPHERAL__IO` to `MIO 38 .. 39` and `PSU__USE__M_AXI_GP0` to `1`.

## AMD/Xilinx Tool Updates (Vivado/Vitis 2025.x)

### Key Findings

- **Vivado 2025.2** (latest as of this digest) adds support for Versal AI Edge Series Gen 2 and Versal Prime Series Gen 2 adaptive SoCs.
- **IP configuration format change**: `.xci` files now use JSON instead of XML — improves `git diff` readability and load times. Existing XML `.xci` files are auto-migrated on project open.
- **AXI SmartConnect & AXI Switch**: New `STRATEGY` parameter enables ultra-low-area mode — relevant for resource-constrained K26 designs.
- **ML engine QoR improvement**: Vivado's ML-based strategy engine reports up to 8% improvement in resource utilization, power, and timing metrics by learning from prior implementation runs.
- **Simplified AXI connections**: Automatic wrapper creation for SystemVerilog instances with AXI ports — reduces manual wiring steps in block designs.
- **PhysOpt compile time reduction**: Physical optimization stage runs faster in 2025.2.
- **Embedded software (Vitis 2025.1) highlights**: New "What's New in Embedded Software" page lists BSP updates, new driver versions, and Vitis Unified IDE improvements. Standalone BSP updated; verify BSP version in `standalone_v*.mld`.
- **Known issue (Vivado 2025)**: AXI-Full peripheral address space may be limited to 1 KB — affects custom IP templates generated by the "Create and Package New IP" wizard. Workaround: manually edit the `ADDR_WIDTH` generic and regenerate the address decoder.

### Code Example

```python
# Example: post-processing Vivado 2025.2 JSON IP config with Python
# (Previously would have required XML parsing)
import json, pathlib

xci = pathlib.Path("ip/axi_bram_ctrl_0/axi_bram_ctrl_0.xci")
cfg = json.loads(xci.read_text())

# Print current memory depth setting
params = cfg.get("ip_inst", {}).get("ip_component_parameters", {})
depth  = params.get("BRAM_DEPTH", {}).get("value", "unknown")
print(f"BRAM depth: {depth}")

# Programmatically bump data width
if "DATA_WIDTH" in params:
    params["DATA_WIDTH"]["value"] = "32"
    xci.write_text(json.dumps(cfg, indent=2))
    print("Updated DATA_WIDTH to 32")
```

### Relevance to Your Project

If you upgrade from Vivado 2024.x to 2025.x, the `.xci` format change means your repo will show large diffs on first open even with no functional changes — commit a note in your PR description to avoid confusion. The AXI address-space bug does not affect the standard AXI BRAM Controller IP, but would bite a custom AXI peripheral. Run Vivado in 2025.1 (the version your project targets) and hold off on 2025.2 until you've verified no BD API regressions in your `create_bd.tcl`.
