# FPGA Research Digest - 2026-10-25

## Executive Summary

- **AXI-Lite VALID/READY deadlock**: A sender's VALID must never be conditioned on READY — once raised, VALID must stay asserted until the handshake completes. This is the single most common bare-metal AXI bug and applies directly to custom PL IP interacting with your BRAM0/BRAM2 slaves.
- **Address locking in IP Integrator**: You can lock specific slave address segments in the Vivado 2025.x Address Editor so that subsequent connection-automation runs don't move your fixed base addresses (0xA0000000, 0xA0010000) unexpectedly.
- **Vivado 2025.1 adds RTL-based AXI Switch IP and IP Integrator "Interrupt and AXI-4 Lite" view** — useful for future expansion of your block design without hand-wiring the interrupt controller.
- **Kria SOM boots from QSPI first** — `boot.bin` must be in QSPI flash; the board differs from generic ZynqMP references where SD is the default. For bare-metal, your FSBL must target QSPI32 (pin config 0x2).
- **Linker script auto-assignment may map all sections to an unexpected memory region** — always inspect `lscript.ld` after Vitis generates it and verify that `.text`, `.data`, and stack/heap point to DDR at the expected address range for your platform.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- **VALID must not depend on READY.** The AMBA AXI spec (§A3.3.1) forbids conditioning VALID on the receiver's READY. Doing so creates a combinational dependency that can deadlock. VALID, once asserted, must stay high until the handshake completes (`VALID && READY` both high on a rising clock edge).
- **READY may depend on VALID** — this is the permitted asymmetry. A receiver may choose not to assert READY until it sees VALID, but the sender cannot do the reverse.
- **Register all AXI module I/O.** Combinational paths between VALID and READY across module boundaries routinely cause timing closure failures. Vivado's AXI Register Slice IP is the standard fix — it adds one cycle of latency and breaks the path without changing protocol behavior.
- **Simulation protocol checkers are essential.** AXI handshake violations (dropped VALID, wrong WSTRB masking, premature BREADY deassertion) are not flagged by synthesis and can be invisible in waveform inspection without a protocol monitor. Xilinx provides an AXI Protocol Checker IP.
- **BRESP = "00" (OKAY) is the only valid response for AXI-Lite** — EXOKAY (exclusive access) is not supported in AXI-Lite. Always drive BRESP to `"00"` in custom PL slaves.
- **Write response channel timing**: BVALID must be held until the master asserts BREADY. The master may pre-assert BREADY before the slave raises BVALID; this is the fast-path mode Vivado's M_AXI_GP interface uses.

### Code Example

```vhdl
-- Minimal AXI-Lite write response channel (VHDL)
-- Must hold BVALID until BREADY is seen
process(aclk)
begin
  if rising_edge(aclk) then
    if aresetn = '0' then
      s_axi_bvalid <= '0';
      s_axi_bresp  <= "00";
    elsif write_data_accepted = '1' then   -- your own internal flag
      s_axi_bvalid <= '1';
      s_axi_bresp  <= "00";               -- OKAY, never EXOKAY for AXI-Lite
    elsif s_axi_bready = '1' then
      s_axi_bvalid <= '0';               -- deassert only after master accepts
    end if;
  end if;
end process;
```

### Relevance to Your Project

Your PS AXI master drives two AXI-Lite BRAM controllers at 0xA0000000 and 0xA0010000. If you add custom PL IP between the PS and the BRAMs, the VALID/READY rule is the first thing to verify. The write-response snippet shows the correct way to hold BVALID — a common omission in hand-written VHDL slaves that causes your C read-back loop to hang indefinitely waiting for the transaction to complete.

## Vivado Block Design / IP Integrator

### Key Findings

- **Connection Automation for BRAM controllers**: In the Connection Automation dialog, set both `BRAM_PORTA` and `BRAM_PORTB` on the AXI BRAM Controller to `Auto` — IP Integrator instantiates and connects the Block Memory Generator automatically. You do not need to wire the BRAM ports by hand.
- **Address Editor tab only appears when a bus master is present.** If you add an AXI slave without a master in the design, the tab is hidden.
- **Address locking (Vivado 2025.2 UG994)**: You can lock specific address segments so automated re-runs do not reassign them. Useful for keeping BRAM0 at 0xA0000000 and BRAM2 at 0xA0010000 across regenerations.
- **Connection Automation may change IP configuration** — after running automation, verify that BRAM width and depth match what your C code expects (the default BRAM Generator output width is often 32-bit x 16K, which matches your 64KB address window per controller).
- **Default address range is 64KB** (0x10000) per AXI BRAM Controller, matching the 0x10000 offset between your two BRAMs. Confirm this in the Address Editor before generating bitstream.
- **Regenerate Output Products** after any IP parameter change — stale cached outputs cause confusing synthesis mismatches that appear as module-not-found errors.

### Code Example

```tcl
# TCL to assign and lock a slave segment address in a Vivado block design
# Locks BRAM0 at 0xA0000000 (64KB range) after running connection automation
set_property offset 0xA0000000 [get_bd_addr_segs {mig_7series_0/S_AXI/Mem0}]
set_property range  64K        [get_bd_addr_segs {mig_7series_0/S_AXI/Mem0}]
# Lock to prevent automation from reassigning
set_property is_locked true    [get_bd_addr_segs {mig_7series_0/S_AXI/Mem0}]

# For your KV260 design (adjust seg name to match your bd):
# set_property offset 0xA0000000 [get_bd_addr_segs {axi_bram_ctrl_0/S_AXI/Mem0}]
# set_property range  64K        [get_bd_addr_segs {axi_bram_ctrl_0/S_AXI/Mem0}]
# set_property is_locked true    [get_bd_addr_segs {axi_bram_ctrl_0/S_AXI/Mem0}]
```

### Relevance to Your Project

Your `create_bd.tcl` sets addresses for two BRAM controllers. Adding `is_locked true` after setting those offsets prevents any future `apply_bd_automation` call from silently relocating them — a subtle bug that causes your C `Xil_In32(0xA0000000)` reads to return stale or zero data without any compile error.

## Vivado TCL Scripting

### Key Findings

- **Non-Project Mode keeps the design in memory only during the session.** After each session ends, the in-memory design is discarded. Unlike Project Mode, there is no `.xpr` file to re-open — your script must rebuild the full in-memory state from scratch each run. Always save Design Checkpoints (DCPs) explicitly.
- **Manual DCP management is required.** In Non-Project Mode you must call `write_checkpoint` after synthesis and after implementation, or you lose those results. Project Mode does this automatically.
- **Batch invocation**: `vivado -mode batch -source my_script.tcl` — the `-mode batch` flag prevents the GUI from opening and exits on completion. Use it for CI/CD runs.
- **Strategy presets in Non-Project Mode (2026.1 UG892)**: The `config_flows` command accepts `-synth_strategy` and `-impl_strategy` options to apply named preset strategies without constructing them by hand.
- **Source files are read from their current locations** in Non-Project Mode, which is correct for version-controlled flows — Vivado does not copy files into a project directory.
- **A 2024.2 community benchmark showed Non-Project Mode was not faster** than Project Mode and was sometimes slower. The speed assumption is a myth for most designs; choose the mode for scriptability and repeatability, not runtime.

### Code Example

```tcl
# Minimal Non-Project Mode flow for the KV260 AXI-BRAM design
set part "xck26-sfvc784-2LV-c"   ;# K26 SoM part

# 1. Read sources
read_vhdl   ../vhdl/kv260_top.vhd
read_xdc    ../xdc/kv260_top.xdc

# 2. Synthesize and checkpoint
synth_design -top kv260_top -part $part
write_checkpoint -force post_synth.dcp
report_timing_summary -file reports/post_synth_timing.rpt

# 3. Implement and checkpoint
opt_design
place_design
route_design
write_checkpoint -force post_route.dcp
report_timing_summary -file reports/post_route_timing.rpt

# 4. Write bitstream
write_bitstream -force kv260_top.bit
```

### Relevance to Your Project

Your `create_bd.tcl` already uses the TCL scripting flow. Adding explicit `write_checkpoint` calls after synthesis and implementation lets you resume from a checkpoint rather than re-running the full build on every iteration, which is valuable when iterating on the BRAM address map or XDC constraints.

## Vitis Bare-Metal / Standalone

### Key Findings

- **`xil_printf` is a lightweight subset** — it supports `%d`, `%x`, `%s`, `%c` but not floating-point format specifiers. For full `printf` with `%f`/`%e`, link against the Newlib `libc` (add `-lm` and ensure `_sbrk` is implemented in the BSP, or use `xil_printf` for debug output only).
- **BSP source is at `<Vitis Install>/data/embedded/lib/bsp/standalone`** and is versioned on the AMD GitHub. Pin your BSP version to match your Vitis release.
- **Linker script `lscript.ld` auto-generated** by Vitis. On Zynq PCIe and some other designs, the linker script places all sections in the wrong memory region. For KV260 bare-metal, verify that `.text` and `.data` sections are mapped to `ps7_ddr_0` or `psu_ddr_0` (DDR), not to an AXI peripheral region.
- **Stack and heap sizes**: Default values are often too small for complex applications. Edit `lscript.ld` to increase `_STACK_SIZE` and `_HEAP_SIZE` before adding printf-heavy debug code; a stack overflow on a bare-metal system typically manifests as a hard fault with no diagnostic output.
- **Interrupt controllers**: On ZynqMP (K26), you use either `XScuGic` (GIC-400) for SPI/PPI interrupts or `XGpio` for simple AXI GPIO. For AXI-Lite BRAM, no interrupt is needed for polling access; interrupts become relevant when adding a custom IP with a done/interrupt output.
- **`Xil_DCacheFlushRange` / `Xil_DCacheInvalidateRange`**: Required when DMA or PL writes to a DDR region that the CPU also reads — without a cache flush, the CPU may read stale cached data. For AXI-Lite BRAM (PL-side BRAM, not DDR), cache coherency does not apply because the BRAMs are in PL address space.

### Code Example

```c
#include "xil_printf.h"
#include "xil_io.h"

#define BRAM0_BASE  0xA0000000U
#define BRAM2_BASE  0xA0010000U
#define TEST_OFFSET 0x00000000U
#define TEST_WORD   0xDEADBEEFU

int test_bram(u32 base, const char *name) {
    Xil_Out32(base + TEST_OFFSET, TEST_WORD);
    /* Memory barrier: ensure AXI write completes before read */
    dsb();
    isb();
    u32 readback = Xil_In32(base + TEST_OFFSET);
    if (readback == TEST_WORD) {
        xil_printf("%s PASS: wrote 0x%08X, read 0x%08X\r\n",
                   name, TEST_WORD, readback);
        return 0;
    }
    xil_printf("%s FAIL: wrote 0x%08X, read 0x%08X\r\n",
               name, TEST_WORD, readback);
    return 1;
}

int main(void) {
    xil_printf("KV260 AXI-BRAM test starting...\r\n");
    int result = 0;
    result |= test_bram(BRAM0_BASE, "BRAM0");
    result |= test_bram(BRAM2_BASE, "BRAM2");
    xil_printf("Overall: %s\r\n", result == 0 ? "PASS" : "FAIL");
    return result;
}
```

### Relevance to Your Project

This mirrors your existing `main.c` pattern. The key addition is the `dsb()` / `isb()` barriers after `Xil_Out32` — on the Cortex-A53, the AXI write may be buffered in the CPU's store buffer without a barrier, causing the immediately following `Xil_In32` to read before the write reaches the BRAM. This is the most common cause of sporadic FAIL results on otherwise correct hardware.

## XDC Timing Constraints

### Key Findings

- **`set_input_delay` and `set_output_delay` model external timing**, consuming part of the `set_max_delay` budget for the corresponding path. An input delay of 2 ns on a 10 ns clock period leaves 8 ns for the on-chip path.
- **Apply `-max` and `-min` separately for outputs.** Vivado performs both setup and hold analysis on `set_output_delay`. Using the combined form without `-max`/`-min` often sets the same value for both, which may be incorrect for your board's external logic.
- **`set_input_delay` defaults to rising-edge reference.** Use `-clock_fall` for signals latched on the falling edge (DDR inputs, for example).
- **`set_input_delay` and `set_output_delay` affect synthesis** in Vivado 2025.2 (UG903). Constraints applied before synthesis influence register placement and retiming decisions.
- **For bare-metal AXI-Lite BRAM**: The PS-PL AXI interface clocks are entirely internal (generated by the ZYNQ PS block). External I/O timing constraints (`set_input_delay`/`set_output_delay`) are only needed for ports that go off-chip (UART, HDMI, GPIO, etc.). Internal AXI paths between the PS and PL are constrained by `create_clock` on `pl_clk0` and the ZYNQ block's own timing model.
- **`set_clock_groups -asynchronous`**: Required when you have two unrelated clocks in the design (e.g., `pl_clk0` and an external HDMI reference). Without it, Vivado attempts cross-domain timing analysis, which usually fails and generates misleading critical-path reports.

### Code Example

```tcl
# XDC for KV260 bare-metal AXI-BRAM demo
# PS provides pl_clk0; no external clock needed for PS-to-PL AXI-Lite

# PS PL clock (driven by the Zynq PS block - already constrained by the PS IP)
# create_clock is NOT needed here; the Zynq PS generates the clock constraint automatically.
# Only add constraints for external I/O ports:

# Example: 125 MHz HDMI reference on J4 pin (not in the AXI-BRAM demo, but shown for reference)
# create_clock -period 8.000 -name hdmi_clk [get_ports hdmi_clk_p]

# Example: constrain an off-chip GPIO output (50 MHz, 4 ns setup margin)
# set_output_delay -clock [get_clocks pl_clk0] -max  4.0 [get_ports {led[*]}]
# set_output_delay -clock [get_clocks pl_clk0] -min -1.0 [get_ports {led[*]}]

# Clock groups: mark pl_clk0 and any external clocks as asynchronous
# set_clock_groups -asynchronous \
#   -group [get_clocks pl_clk0] \
#   -group [get_clocks hdmi_clk]

# For a pure PS-PL AXI-Lite design with no off-chip I/O, the .xdc may only need:
set_property BITSTREAM.GENERAL.COMPRESS TRUE [current_design]
```

### Relevance to Your Project

For your current KV260 AXI-BRAM demo with no off-chip PL I/O, minimal XDC is needed — the PS block IP generates the required clock constraints automatically. The section above clarifies which constraints are required vs. optional, preventing unnecessary constraint warnings that can obscure real timing issues when you add external I/O later.

## Kria KV260 / K26 SoM

### Key Findings

- **KV260 boots from QSPI first.** Unlike generic ZynqMP boards that can boot from SD directly, the K26 SOM is preconfigured to boot initially from QSPI flash. For bare-metal, `boot.bin` must be written to QSPI. A FSBL reporting `QSPI 32 bit Boot Mode` is the expected behavior.
- **Two SOM variants exist**: `sm-k26` (includes eMMC) and `smk-k26` (no eMMC; the Starter Kit uses this with preprogrammed firmware in QSPI). Verify which variant you have before assuming eMMC is available as a fallback boot source.
- **QSPI boot mode codes (UG1137 2025.2)**: QSPI24 = `0x1`, QSPI32 = `0x2`. The K26 uses 32-bit QSPI (Winbond W25Q128 on the SOM). Your FSBL must not attempt NAND or SD as the primary boot source.
- **Power supply**: The K26 SOM derives all PS and PL core supplies from a single +5V carrier input. PL I/O bank voltages are set by carrier-card-defined rails on the KV260. The KV260 carrier provides 1.8V on HPIO banks and 3.3V on HDIO banks — check this before driving external signals.
- **PS MIO vs EMIO**: UART0 (the USB-UART you use for `xil_printf` output) is on PS MIO. You do not need to route it through the PL EMIO path. Confirm `UART0_RXD` and `UART0_TXD` MIO numbers in the KV260 schematic (typically MIO[2:3] or MIO[18:19] depending on the board version).
- **K26 SOM two 240-pin connectors** expose PS MIO, PS-GTR, PS I2C, PL HPIO/HDIO, and GTH pins to the carrier. The carrier (KV260 board) routes a subset to connectors and peripherals.

### Code Example

```tcl
# Vivado TCL: configure Zynq UltraScale+ PS block for KV260 bare-metal
# Enables UART0 on MIO (for xil_printf USB-UART) and sets pl_clk0 to 100 MHz

set_property -dict [list \
  CONFIG.PSU__UART0__PERIPHERAL__ENABLE {1} \
  CONFIG.PSU__UART0__PERIPHERAL__IO    {MIO 18 .. 19} \
  CONFIG.PSU__CRL_APB__PL0_REF_CTRL__FREQMHZ {100} \
  CONFIG.PSU__USE__M_AXI_GP0           {1} \
] [get_bd_cells zynq_ultra_ps_e_0]
```

### Relevance to Your Project

Confirming UART0 is on PS MIO (not EMIO) ensures `xil_printf` output reaches the USB-UART chip on the KV260 carrier without any PL routing. The 100 MHz pl_clk0 setting matches the AXI-Lite BRAM controller's expected clock frequency and avoids setup violations at the PS-to-PL AXI interface.

## AMD/Xilinx Tool Updates (Vivado/Vitis 2025.x)

### Key Findings

- **Vivado 2025.1 new IP: RTL-based AXI Switch.** A new AXI Switch IP was added alongside the existing SmartConnect, allowing simpler routing configurations in block design without the full SmartConnect overhead.
- **IP Integrator new views in 2025.1**: "Clocking and Reset" and "Interrupt and AXI-4 Lite" views were added to IP Integrator, making it easier to audit connections without scrolling the full block diagram.
- **New device support in 2025.1**: Versal AI Edge Gen 2, Versal Prime Gen 2, and Spartan UltraScale+. Does not directly affect K26/KV260, which uses ZynqMP.
- **Selective device download**: The Vivado 2025.1 installer now allows selecting individual Versal devices instead of entire product families, reducing download size for non-Versal workflows.
- **Open-source component versions (Vitis 2025.1)**: Linux kernel bumped to 6.12, Zephyr RTOS support added as early access, new Versal Gen 2 driver support in the device drivers layer.
- **Vitis AI 5.1 (aligned with Vivado 2025.1)**: Adds multi-NPU instance support and BF16 for several models; Docker de-emphasized in favor of Apptainer. Not relevant for bare-metal BRAM work.
- **Vitis 2025.2 "What's New"** was also published — but the community notes above are for 2025.1 specifically. For 2025.2 details, check the AMD product page directly.

### Code Example

```tcl
# Vivado 2025.1+ TCL: use the new RTL-based AXI Switch IP in a block design
# (simpler than SmartConnect for static 1-to-N routing)
create_bd_cell -type ip -vlnv xilinx.com:ip:axi_switch:1.0 axi_switch_0
set_property -dict [list \
  CONFIG.NUM_SI {1} \
  CONFIG.NUM_MI {2} \
] [get_bd_cells axi_switch_0]

# Connect PS AXI master -> switch input
connect_bd_intf_net [get_bd_intf_pins zynq_ultra_ps_e_0/M_AXI_HPM0_FPD] \
                    [get_bd_intf_pins axi_switch_0/S00_AXI]

# Connect switch outputs -> BRAM controllers
connect_bd_intf_net [get_bd_intf_pins axi_switch_0/M00_AXI] \
                    [get_bd_intf_pins axi_bram_ctrl_0/S_AXI]
connect_bd_intf_net [get_bd_intf_pins axi_switch_0/M01_AXI] \
                    [get_bd_intf_pins axi_bram_ctrl_1/S_AXI]
```

### Relevance to Your Project

The new RTL AXI Switch could replace or supplement the SmartConnect in your block design when adding a third or fourth BRAM slave — it has lower LUT overhead than SmartConnect for static N-to-1 topologies. The new IP Integrator "AXI-4 Lite" view will make it easier to audit your two BRAM address assignments visually without opening the Address Editor.
