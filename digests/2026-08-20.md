# FPGA Research Digest - 2026-08-20

## Executive Summary

- **AXI-Lite backpressure is the #1 source of subtle bugs**: when the PS holds BREADY or RREADY low, the BRAM controller must de-assert AWREADY/WREADY/ARREADY accordingly — simulation with constant READY=1 hides this class of failures entirely.
- **BRAM Enable pin must be tied high**: leaving it unconnected silently gates write-enable, causing data to be written one address early with phantom zeros at the intended address — directly relevant to the dual-BRAM write/read-back loop in this project.
- **Vivado non-project mode TCL is the fastest path to a reproducible build**: synthesis + P&R run entirely in memory without `.xpr` project files; the `create_bd.tcl` approach used by this project is the right foundation.
- **Kria bare-metal BRAM access requires enabling HPM0 LPD/FPD AXI ports** in the Zynq MPSoC IP before connection automation can map slave addresses starting at 0xA0000000.
- **Vivado 2025.1 IP catalog taxonomy was restructured** — if IP Integrator cannot find AXI BRAM Controller after upgrading, search for it under the new "Memories & Storage Elements" taxonomy rather than by old category path.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- AXI-Lite uses five independent channels: AW (write address), W (write data), B (write response), AR (read address), R (read data). All use the VALID/READY handshake; the transfer occurs only when **both** VALID and READY are high on the same rising clock edge.
- **Critical rule**: once a master asserts VALID, it must hold VALID and the accompanying signals stable until the corresponding READY is received. Masters must never wait for READY before asserting VALID — doing so can deadlock.
- **Backpressure pitfall**: if the PS holds BREADY low (it has not yet consumed the write response), the BRAM controller slave must hold BVALID asserted and must not accept new transactions until the handshake completes. Similarly, ARREADY must be withheld if RREADY is low and the read data register is full.
- **BRAM Enable gotcha**: the `ENA`/`ENB` port of Xilinx Block Memory Generator must be tied high (or driven by the controller) — if left unconnected it defaults to driven-low in some configurations, effectively disabling all writes silently.
- **BRESP values**: `"00"` = OKAY (normal), `"10"` = SLVERR (slave error). For a simple BRAM controller the correct implementation is to always return `"00"` and never drive `"10"` unless implementing error detection. Incorrect BRESP values can cause the AXI Interconnect to flag spurious errors.
- **Write timing**: the standard AXI BRAM Controller v4.x asserts write-enable one cycle after the W-channel handshake completes — account for this in simulation waveforms; seeing data written one address late is expected pipelined behavior, not a bug, unless ENA is not properly tied.

### Code Example

```vhdl
-- Minimal AXI-Lite slave write-response channel (VHDL)
-- BVALID must stay asserted until BREADY handshake completes
process(S_AXI_ACLK)
begin
  if rising_edge(S_AXI_ACLK) then
    if S_AXI_ARESETN = '0' then
      axi_bvalid <= '0';
      axi_bresp  <= "00";
    else
      if (axi_awready and S_AXI_AWVALID and
          axi_wready  and S_AXI_WVALID  and
          not axi_bvalid) = '1' then
        axi_bvalid <= '1';
        axi_bresp  <= "00";   -- always OKAY for simple slave
      elsif S_AXI_BREADY = '1' and axi_bvalid = '1' then
        axi_bvalid <= '0';    -- clear only after master accepts
      end if;
    end if;
  end if;
end process;
```

### Relevance to Your Project

Your project writes patterns to BRAM0 (0xA0000000) and BRAM2 (0xA0010000) then reads back to verify PASS/FAIL. If you ever see intermittent FAIL on reads that should pass, first check: (1) is BRAM `ENA` tied high in the block design? (2) is your bare-metal C code waiting for the write response before issuing the read (no BRESP polling is needed for AXI-Lite — the store instruction completes synchronously from the CPU's perspective, but the AXI transaction must fully complete before a subsequent read is issued)? Add a `dsb()` / `dmb()` barrier in C between write and read loops to enforce ordering on the Cortex-A53.

## Vivado Block Design / IP Integrator

### Key Findings

- **Connection Automation** (`apply_bd_automation`) can set up clock/reset connections and AXI interconnects automatically, but the recommendation is to use **explicit TCL commands** (`connect_bd_intf_net`, `connect_bd_net`) for AXI-BRAM connections to avoid surprises from automation heuristics.
- **Address Editor** errors ("peripheral unmapped") are resolved by right-clicking in the Address Editor pane and choosing **Auto-Assign Address**, or via TCL: `assign_bd_address`. Then use `set_property` on the created segment to set a specific offset/range if the default is wrong.
- `assign_bd_address` followed by `set_property offset 0xA0000000 [get_bd_addr_segs ...]` is the precise way to pin a BRAM slave at a known address in TCL scripts.
- **Validate Design** (`validate_bd_design`) should be called after every structural change in TCL scripts before generating output products — it catches unconnected ports and address conflicts early.
- After regenerating the block design from TCL, always run `generate_target all [get_files *.bd]` and then `export_ip_user_files` before launching synthesis to ensure wrapper and IP outputs are up to date.

### Code Example

```tcl
# Assign BRAM0 to 0xA0000000 and BRAM2 to 0xA0010000 in TCL
assign_bd_address [get_bd_addr_segs {axi_bram_ctrl_0/S_AXI/Mem0}]
set_property offset 0xA0000000 \
  [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property range 64K \
  [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]

assign_bd_address [get_bd_addr_segs {axi_bram_ctrl_1/S_AXI/Mem0}]
set_property offset 0xA0010000 \
  [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_1_Mem0}]
set_property range 64K \
  [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_1_Mem0}]

validate_bd_design
```

### Relevance to Your Project

Your `create_bd.tcl` constructs the block design programmatically. The address assignment snippet above shows the exact TCL idiom to guarantee BRAM0 lands at 0xA0000000 and BRAM2 at 0xA0010000 regardless of what `assign_bd_address` auto-selects — critical for matching the hardcoded base addresses in `main.c`.

## Vivado TCL Scripting

### Key Findings

- **Non-project mode** runs synthesis, P&R, and bitstream generation entirely in memory without a `.xpr` file. Invoked as `vivado -mode batch -source build.tcl`. Faster than project mode and ideal for CI/CD pipelines.
- **Project mode TCL export** (`File → Write Project Tcl`) generates a reproducible script from an existing GUI project — use this to bootstrap non-project scripts from a block design you built interactively.
- **Design checkpoints** (`.dcp` files) are the non-project mode equivalent of project saves: write them after synthesis (`write_checkpoint post_synth.dcp`) and after P&R (`write_checkpoint post_route.dcp`) so you can re-run individual stages without re-running everything.
- Use `open_checkpoint` to resume from a saved `.dcp` — this is faster than re-synthesizing when iterating on placement/routing or timing constraints.
- `launch_runs` with `-jobs N` parallelises synthesis and implementation across CPU cores: `launch_runs impl_1 -jobs 4`.
- In batch scripts, always check `[get_property PROGRESS [get_runs synth_1]]` and `STATUS` properties before proceeding to the next stage to detect silent failures.

### Code Example

```tcl
# Minimal non-project mode build script for kv260-axi-bram-demo
read_vhdl   [glob ../vhdl/*.vhd]
read_xdc    [glob ../xdc/*.xdc]

# Synthesize
synth_design -top kv260_top -part xck26-sfvc784-2LV-c
write_checkpoint -force post_synth.dcp
report_timing_summary -file post_synth_timing.rpt

# Implement
opt_design
place_design
route_design
write_checkpoint -force post_route.dcp
report_timing_summary -file post_route_timing.rpt

# Bitstream
write_bitstream -force kv260_top.bit
```

### Relevance to Your Project

If your `create_bd.tcl` currently generates both the block design and manages synthesis in project mode, consider splitting it: a `create_bd.tcl` that builds the BD and exports the wrapper, and a separate `build.tcl` that does synthesis/P&R in non-project mode consuming the exported XDC and wrapper VHDL. This makes the build reproducible from a clean checkout without requiring the Vivado GUI.

## Vitis Bare-Metal / Standalone

### Key Findings

- **BSP stdout/stdin assignment**: in the BSP settings (`xparameters.h` / BSP configuration), `STDOUT_BASEADDRESS` must point to the UART connected to your USB-serial bridge. On KV260 this is typically `XUARTPS_1_BASEADDR` (PS UART1 on MIO 36/37, which routes to the USB UART on the carrier). If `xil_printf` produces no output, this is the first thing to check.
- **`xil_printf` vs `printf`**: `xil_printf` is a lightweight formatted print with no floating-point support and no buffering — output is immediate. `printf` from newlib requires `_write()` syscall implementation and uses buffering; call `fflush(stdout)` if mixing both. For a PASS/FAIL demo, `xil_printf` is the correct choice.
- **Linker script pitfalls**: the auto-generated `lscript.ld` for Zynq UltraScale+ may have incorrect OCM base addresses (should be `0xFFFC0000`, size `256K`). Always verify the DDR region matches your board's actual DDR size (2GB on K26 = `0x00000000` to `0x7FFFFFFF`).
- **Memory barriers for AXI I/O**: on Cortex-A53, use `Xil_DCacheFlush()` or ARM `dsb()` intrinsic between a write loop and a read-back loop that targets memory-mapped I/O to prevent store-buffer reordering. The MMU maps PL AXI regions as Device memory (non-cacheable, strongly ordered) by default in standalone BSP, so explicit barriers are usually not needed — but verify by checking the `mmu_tbl.c` generated by BSP.
- **Interrupt controller**: GIC-400 is used on the Cortex-A53 cluster. Use `XScuGic` driver. For a simple BRAM demo without interrupts, polling is fine, but for future extensions (DMA done, timer) register handlers with `XScuGic_Connect`.

### Code Example

```c
/* Bare-metal AXI-BRAM write/read-back pattern in C (Vitis standalone) */
#include "xil_io.h"
#include "xil_printf.h"

#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL
#define PATTERN     0xDEADBEEFUL

int main(void) {
    /* Write pattern to both BRAMs */
    Xil_Out32(BRAM0_BASE, PATTERN);
    Xil_Out32(BRAM2_BASE, PATTERN ^ 0xFFFFFFFFUL);

    /* ARM DSB ensures stores retire before loads */
    __asm__ volatile("dsb sy" ::: "memory");

    /* Read back and verify */
    u32 r0 = Xil_In32(BRAM0_BASE);
    u32 r2 = Xil_In32(BRAM2_BASE);

    if (r0 == PATTERN && r2 == (PATTERN ^ 0xFFFFFFFFUL))
        xil_printf("PASS: BRAM0=0x%08X, BRAM2=0x%08X\r\n", r0, r2);
    else
        xil_printf("FAIL: BRAM0=0x%08X, BRAM2=0x%08X\r\n", r0, r2);

    return 0;
}
```

### Relevance to Your Project

This matches your existing main.c structure. The `dsb sy` barrier is a defensive best-practice even though the AXI-Lite PL region is normally strongly ordered in the standalone MMU tables. If you ever see intermittent FAIL with correct-looking logic analyzer traces, adding this barrier is the fastest hypothesis to test.

## XDC Timing Constraints

### Key Findings

- **Primary clock**: for the KV260 / K26 SoM, the PL fabric clock is generated by the Zynq MPSoC PS (`pl_clk0`). Vivado IP Integrator creates the `create_clock` constraint automatically from the Zynq PS IP configuration — do **not** manually add a `create_clock` on the same net or you will get a multi-driver clock warning.
- **`set_input_delay` / `set_output_delay`**: for a design with no external I/O ports on the PL (your BRAM demo communicates only PS-to-PL internally via AXI), these constraints are **not required** — all paths are internal register-to-register timing and Vivado handles them via `create_clock` alone.
- **`set_clock_groups -asynchronous`**: use this when two clocks are unrelated and you do not want Vivado to analyze cross-domain paths between them. On KV260 with a single `pl_clk0`, this is not needed unless you add a second clock domain (e.g., an MMCM-derived clock for a second AXI slave).
- **`set_false_path`**: use for paths that are truly non-functional for timing (e.g., test/scan paths, static configuration registers written once at boot). Do not use it to silence legitimate timing violations — fix the design instead.
- **I/O timing formula**: `set_input_delay -max = Tco_max + Tboard_max - Tsetup_slack`; `set_output_delay -max = Tboard_max + Tsu_ext`. For KV260 PMOD/RPi connector GPIO, reference the PYNQ Composable Pipeline XDC file for working example values.
- Timing reports should show **Worst Negative Slack (WNS) ≥ 0** and **Total Negative Slack (TNS) = 0** after route for a passing design.

### Code Example

### Relevance to Your Project

For your current single-clock PS-to-PL AXI-BRAM demo, timing constraints beyond what IP Integrator auto-generates are minimal. The most important action is to run `report_timing_summary` after routing and verify WNS ≥ 0. If timing fails on the AXI interconnect paths, try lowering `pl_clk0` to 100 MHz (from 150+ MHz) in the Zynq PS IP configuration.

## Kria KV260 / K26 SoM

### Key Findings

- **Boot modes**: MODE[3:0] pins on the SOM connector select the boot device. Default factory setting is **QSPI32**. For development, switch to **SD** (MODE = 0110) or **JTAG** (MODE = 0000). Boot mode can also be changed dynamically via XSDB: `targets -set -filter {name =~ "PSU"}; mwr 0xFF5E0200 0x0100` (sets JTAG mode without hardware pin change).
- **PS UART for bare-metal**: UART1 (MIO 36/37) routes to the USB UART on the KV260 carrier card and appears as `/dev/ttyUSB1` (or ttyUSB0 depending on OS enumeration). Baud 115200, 8N1. If `xil_printf` output is not appearing, confirm the BSP selects `XUARTPS_1` not `XUARTPS_0`.
- **AXI HP / HPM ports**: for PS-to-PL AXI master (PS writes to PL BRAM), enable **M_AXI_HPM0_LPD** or **M_AXI_HPM0_FPD** in the Zynq MPSoC PS IP. HPM0_LPD operates at the LPD clock and is preferred for low-latency single-master setups like this BRAM demo.
- **PL power domain**: PL is powered by VCCO_PL (1.8V/3.3V banks) and VCC_PL_INT (core voltage). The KV260 carrier handles this automatically; no explicit power sequencing is needed for the SOM — the on-board PMIC manages it.
- **Address space**: the PS AXI master (HPM0) can access PL-side AXI slaves in the range `0xA000_0000` to `0xBFFF_FFFF` (GP AXI slave address space on Zynq UltraScale+). Your BRAM0 at 0xA0000000 and BRAM2 at 0xA0010000 are both within this window.
- **JTAG programming for bare-metal**: use `program_hw_devices` in Vivado Hardware Manager or XSCT script to load the bitstream (`xsct program.tcl`); then load the ELF from Vitis Debugger or XSCT.

### Code Example

```tcl
# XSCT script to program bitstream and run bare-metal ELF on KV260
connect
targets -set -filter {name =~ "xck26*"}
fpga -file kv260_top.bit

# Switch to Cortex-A53 core 0
targets -set -filter {name =~ "Cortex-A53 #0"}
rst -processor
dow kv260_bram_demo.elf
con
```

### Relevance to Your Project

This XSCT flow is the fastest way to iterate on your bare-metal demo without reflashing SD/QSPI on every build. Connect Vivado Hardware Manager to the KV260 via USB JTAG, program the bitstream, then run the ELF — the entire cycle takes under 30 seconds vs. minutes for an SD card reflash.

## AMD/Xilinx Tool Updates (Vivado/Vitis 2025.x)

### Key Findings

- **Vivado 2025.1**: IP catalog taxonomy was restructured — AXI BRAM Controller now appears under "Memories & Storage Elements > Block Memory" rather than the previous path. If a TCL script uses `set_property ip_repo_paths` pointing to a cached IP directory, re-run `update_ip_catalog` after upgrading.
- **AXI Ethernet Buffer fix**: PTP 1588 frame handling at the Buffer→MAC interface was corrected in 2025.1 (not relevant to the current BRAM demo, but notable for future Ethernet extension).
- **Vitis 2025.1**: The unified IDE (Eclipse-based) continues alongside the VS Code-based Vitis flow introduced in 2023.x. For bare-metal projects, the classic workspace approach remains fully supported.
- **Known issues to watch**: the AMD Adaptive Support answer record `000037919` lists all IP change log entries for 2025.1 — check it when upgrading an existing project to identify IPs that require re-generation.
- **Vitis 2026.x known issues**: answer record `000040220` documents 2026.x known issues — relevant if evaluating an upgrade beyond 2025.1.
- **Non-project mode scripts**: Vivado 2025.1 batch TCL (`-mode batch`) adds improved progress reporting. The `get_property PROGRESS` idiom now returns float percentages rather than strings in some contexts — update any parsing logic in CI scripts that parses progress output.
- **Part targeting**: the K26 SoM uses part `xck26-sfvc784-2LV-c`. Confirm this part string is used in `synth_design -part` in any non-project mode scripts — using the wrong speed grade suffix causes implementation to target a different device variant.

### Code Example

```tcl
# Update IP catalog after Vivado upgrade and re-generate stale IPs
update_ip_catalog -rebuild

# Check for IPs that need upgrade in an existing project
open_project kv260_project.xpr
set stale_ips [get_ips -filter {UPGRADE_VERSIONS != ""}]
foreach ip $stale_ips {
  set name [get_property NAME $ip]
  set upgrade [get_property UPGRADE_VERSIONS $ip]
  puts "Upgrading $name to $upgrade"
  upgrade_ip $ip
}
generate_target all [get_ips]
```

### Relevance to Your Project

When upgrading from an earlier Vivado version to 2025.1, run the IP upgrade script above before regenerating your block design. For a minimal two-BRAM design the IPs are unlikely to have breaking changes, but the AXI BRAM Controller v4.1 did receive minor fixes across versions — always verify the IP version in the `.bd` file matches what your installed Vivado provides.
