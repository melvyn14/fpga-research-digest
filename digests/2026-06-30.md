## Executive Summary
- **AW/W channel ordering is a real Xilinx-IP-proven failure mode, not just spec pedantry** — ZipCPU's documented case studies found AW/W timing-assumption bugs in shipped Xilinx IP (AXI Ethernet-Lite, AXI Quad SPI). If `kv260_top.vhd` has any custom AXI-Lite shim around the BRAM controllers rather than direct PS-to-`axi_bram_ctrl` wiring, this is worth an explicit audit.
- **Address Editor alignment rule**: a BRAM with an N-byte range must have its base address aligned to N (i.e., `log2(N)` trailing zero bits). With BRAM0 at `0xA0000000` and BRAM2 at `0xA0010000`, both are 64KB-aligned, consistent with each BMG having a range ≤ 64KB — worth double-checking range matches actual BMG depth after any regeneration, since a too-large auto-assigned range can silently overlap the next peripheral.
- **Vitis 2025.2 confirmed deprecating Vitis Classic** in favor of the Unified IDE; 2025.1 (this project's pin) is one of the last releases where Classic is still fully supported. Worth noting for reproducibility if anyone else builds this project later on a newer toolchain.
- **The official Kria docs describe almost exactly this project's hardware flow**: connect a BRAM controller's `S_AXI` to the PS `M_AXI_HPM0` via Connection Automation, confirm the BRAM's address in the Address Editor, then read/write that same address from a bare-metal Vitis app — strong validation that `create_bd.tcl`/`main.c` are following the standard, supported pattern rather than something exotic.
- **No XDC timing work should be needed** for a pure internal-AXI BRAM design; `set_input_delay`/`set_output_delay` only become relevant if the design grows external PL I/O (e.g., status LEDs, PMOD GPIO).

## AXI Protocol / AXI-Lite / AXI-Stream
### Key Findings
- Core handshake rule (true for all five AXI channels: AW, W, B, AR, R): a transfer completes only on a clock edge where both `VALID` and `READY` are `1` simultaneously. Once a source asserts `VALID`, it must hold both `VALID` and the payload steady until `READY` is observed — it cannot withdraw `VALID` speculatively.
- `VALID` must never be a function of `READY`. Combinationally gating `VALID` on `READY` (a common shortcut for "I'll only claim valid once you're ready") is a textbook AXI protocol violation and a documented root cause of bus deadlocks, because it can create a combinational dependency loop between master and slave.
- AW and W are independent channels — there is no required ordering between them. A master is allowed to present `WVALID`/`WDATA` before, after, or simultaneously with `AWVALID`/`AWADDR`. Slave logic that assumes "address always arrives first" can deadlock against masters (including some Xilinx-generated ones) that present W first.
- AXI4-Lite specifically has no burst support (`AWLEN`/`ARLEN` don't exist) — every transaction is exactly one beat. This caps throughput but also simplifies the slave-side state machine considerably versus full AXI4.
### Code Example
```vhdl
-- Robust AXI-Lite write FSM skeleton handling AW/W in any arrival order.
-- Captures whichever of address/data arrives first, fires the actual
-- BRAM write once BOTH have been latched.
process(clk)
begin
  if rising_edge(clk) then
    if rst = '1' then
      aw_done <= '0';
      w_done  <= '0';
    else
      if s_axi_awvalid = '1' and s_axi_awready = '1' then
        awaddr_r <= s_axi_awaddr;
        aw_done  <= '1';
      end if;
      if s_axi_wvalid = '1' and s_axi_wready = '1' then
        wdata_r <= s_axi_wdata;
        w_done  <= '1';
      end if;
      if aw_done = '1' and w_done = '1' then
        -- both halves of the write are latched; commit and clear
        bram_we   <= '1';
        bram_addr <= awaddr_r;
        bram_din  <= wdata_r;
        aw_done   <= '0';
        w_done    <= '0';
      else
        bram_we <= '0';
      end if;
    end if;
  end if;
end process;

s_axi_awready <= not aw_done;
s_axi_wready  <= not w_done;
```
### Relevance to Your Project
For a 2-BRAM demo using the stock `axi_bram_ctrl` IP, this AW/W ordering subtlety is handled for you by Xilinx's IP. It only matters if `kv260_top.vhd` contains hand-written AXI-Lite glue (e.g. a custom register file alongside the BRAM controllers) — in that case, explicitly verify the FSM doesn't assume AW arrives before W, since the Cortex-A53's AXI master (via the PS interconnect) is not contractually obligated to present them in that order.

## Vivado Block Design / IP Integrator
### Key Findings
- The Address Editor enforces alignment: a slave with an N-byte range must sit on an N-aligned boundary (range `0x10000` → base must end in `0000` and be a multiple of `0x10000`). Both project addresses (`0xA0000000`, `0xA0010000`) satisfy this for 64KB windows.
- Address ranges across different segments must not overlap — Vivado's bitstream generation will hard-fail validation if they do, so this is caught early rather than silently producing wrong behavior.
- Avoid mapping any AXI slave to address `0x0` — some software drivers treat a `NULL`-valued base address specially and may assert; irrelevant here since both BRAMs sit well above zero, but worth remembering if a third peripheral is ever added.
- "Run Connection Automation" / "Run Block Automation" use AMD's declarative `bd_rule` definitions under the hood (e.g. `xilinx.com:bd_rule:axi4`); the same calls are scriptable directly via `apply_bd_automation` in TCL for non-interactive regeneration.
### Code Example
```tcl
# Pattern for adding a 3rd AXI BRAM controller via TCL automation
# (mirrors the BRAM0/BRAM2 pattern this project already uses)
set axi_bram_ctrl_2 [create_bd_cell -type ip -vlnv xilinx.com:ip:axi_bram_ctrl:4.1 axi_bram_ctrl_2]
set_property -dict [list CONFIG.SINGLE_PORT_BRAM {1}] $axi_bram_ctrl_2

apply_bd_automation -rule xilinx.com:bd_rule:axi4 \
    -config { Master "/zynq_ultra_ps_e_0/M_AXI_HPM0_FPD" Clk "Auto" } \
    [get_bd_intf_pins axi_bram_ctrl_2/S_AXI]

# Force a specific, predictable base address rather than trusting auto-assign:
set_property offset 0xA0020000 [get_bd_addr_segs \
    {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_2_Mem0}]
set_property range  64K        [get_bd_addr_segs \
    {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_2_Mem0}]
validate_bd_design
```
### Relevance to Your Project
Given BRAM0/BRAM2 are 64KB apart (`0xA0000000`, `0xA0010000`), a logical next BRAM would land at `0xA0020000` if the same spacing convention continues — explicitly setting `offset`/`range` as above (rather than relying purely on auto-assign) keeps `main.c`'s hardcoded base addresses in sync with the hardware after any future block-design regeneration.

## Vivado TCL Scripting
### Key Findings
- Non-project ("in-memory") mode is the standard headless/CI build pattern: no `.xpr` is written to disk, and the developer is fully responsible for sourcing constraints and saving checkpoints/reports at each stage — a good fit for a repo that checks in `tcl/` scripts as the source of truth rather than a generated project file.
- `write_bd_tcl` (or File → Export → Export Block Design in the GUI) regenerates a TCL script that can recreate a block design — useful as a sanity check that `create_bd.tcl` still matches the live BD after manual GUI edits, though AMD notes exported BD TCL is not guaranteed portable across Vivado versions.
- For idempotent re-runs of a block-design script against an existing checkpoint, guard cell creation with existence checks (`get_bd_cells -quiet`) or simply wipe and rebuild the BD at script start — re-running `create_bd_cell` against a name that already exists throws an error and aborts the script.
- Recommended non-project timing workflow: run `opt_design`, then check utilization/timing, then `place_design`, then re-check timing after placement — catching timing problems before the (much slower) routing step.
### Code Example
```tcl
# Idempotent BD creation guard, useful at the top of create_bd.tcl
proc safe_create_bd_cell {vlnv name} {
    if {[get_bd_cells -quiet $name] eq ""} {
        return [create_bd_cell -type ip -vlnv $vlnv $name]
    } else {
        puts "INFO: $name already exists, reusing"
        return [get_bd_cells $name]
    }
}

set axi_bram_ctrl_0 [safe_create_bd_cell xilinx.com:ip:axi_bram_ctrl:4.1 axi_bram_ctrl_0]
```
### Relevance to Your Project
If `create_bd.tcl` is ever re-sourced against a partially-built design (e.g. during iterative development), wrapping cell creation calls like this avoids the script aborting mid-way through with a confusing "cell already exists" error — a common source of "works once, fails on re-run" TCL scripts.

## Vitis Bare-Metal / Standalone
### Key Findings
- `xil_printf` is intentionally a lightweight, non-reentrant printf substitute (no float formatting, smaller footprint than newlib's full `printf`) — the standard choice for bare-metal UART status reporting like a PASS/FAIL demo.
- The standalone BSP's UART stdin/stdout target is configurable independently of the physical UART instance in hardware — in Vitis 2025.x Unified IDE this lives in `vitis-comp.json` under the platform component, as `standalone_stdin`/`standalone_stdout` properties; worth checking explicitly if UART output ever goes silent after a platform regeneration, since it can default to a different UART than expected.
- GIC (interrupt controller) setup is irrelevant for a purely polled read/write/compare loop; it only becomes necessary if the demo evolves to use interrupt-driven UART TX or an AXI timeout watchdog.
- Community reports continue to flag that "Update Hardware Specification" on an existing Vitis platform project doesn't always fully propagate AXI peripheral or address-map changes — recreating the platform project from a fresh XSA remains the more reliable path after any block-design edit.
### Code Example
```c
// Bare-metal PASS/FAIL pattern test matching the project's two-BRAM check
#include "xil_io.h"
#include "xil_printf.h"

#define BRAM0_BASE 0xA0000000U
#define BRAM2_BASE 0xA0010000U
#define TEST_WORDS 16U

static int test_bram(const char *name, UINTPTR base) {
    int fail = 0;
    for (u32 i = 0; i < TEST_WORDS; i++) {
        Xil_Out32(base + (i * 4U), 0xDEAD0000U | i);
    }
    for (u32 i = 0; i < TEST_WORDS; i++) {
        u32 expected = 0xDEAD0000U | i;
        u32 actual   = Xil_In32(base + (i * 4U));
        if (actual != expected) {
            xil_printf("%s word %lu MISMATCH: wrote 0x%08lx read 0x%08lx\r\n",
                       name, (unsigned long)i,
                       (unsigned long)expected, (unsigned long)actual);
            fail = 1;
        }
    }
    xil_printf("%s: %s\r\n", name, fail ? "FAIL" : "PASS");
    return fail;
}

int main(void) {
    int rc = 0;
    rc |= test_bram("BRAM0", BRAM0_BASE);
    rc |= test_bram("BRAM2", BRAM2_BASE);
    xil_printf("Overall: %s\r\n", rc ? "FAIL" : "PASS");
    return rc;
}
```
### Relevance to Your Project
This mirrors the described `main.c` write/read/compare/PASS-FAIL structure. One detail worth confirming in the real source: whether reads/writes go through `Xil_Out32`/`Xil_In32` directly (recommended for AXI-mapped PL memory) versus a raw pointer dereference, since pointer dereferences depend on the MMU table marking the `0xA000_0000` region as Device/Strongly-Ordered rather than cacheable — the BSP-generated translation table normally handles this correctly for PL-mapped address ranges, but it's a common source of intermittent "works once, garbage after" bugs if a custom memory map ever overrides it.

## XDC Timing Constraints
### Key Findings
- For a design where BRAM lives entirely inside the PL accessed only via internal AXI (no top-level I/O pins), clocking/reset/timing for the PS-PL AXI interface is automatically inferred from the Zynq UltraScale+ PS IP and its automation — no manual `set_input_delay`/`set_output_delay` is needed in this case.
- The general sizing rule when external I/O *is* added: `set_output_delay -max` should be set to the downstream device's required setup time; `set_input_delay -max` should be set to the upstream device's clock-to-output (Tco) delay, both relative to the board-level clock edge the signal is launched/captured from.
- For any clock domain that should not be timed against another (e.g. a debug/free-running oscillator vs. the AXI fabric clock), use `set_clock_groups -asynchronous` explicitly — otherwise Vivado attempts to relate them and may report spurious timing failures or, worse, silently assume a false timing relationship exists.
- HDL Coder-style generated AXI4-Lite CDC constraint files (useful as a reference even if not using HDL Coder) typically pair `set_max_delay -datapath_only` with `set_false_path` on the synchronizer registers crossing clock domains, rather than leaving CDC paths fully unconstrained.
### Code Example
```tcl
# Only relevant if the demo later adds external PL I/O (e.g. a status LED)
create_clock -period 10.000 -name pl_clk [get_ports pl_clk_p]

set_output_delay -clock pl_clk -max 3.000 [get_ports status_led]
set_output_delay -clock pl_clk -min 0.300 [get_ports status_led]

# If a second, unrelated clock domain is ever introduced:
set_clock_groups -asynchronous \
  -group [get_clocks pl_clk] \
  -group [get_clocks {clk_pl_0 -of_objects [get_bd_cells zynq_ultra_ps_e_0]}]
```
### Relevance to Your Project
Given the current scope (BRAM accessed purely over internal AXI, no PL-side pins), `kv260_top.vhd`'s XDC almost certainly needs nothing beyond the board's default PS clock/reset constraints. Keep this in the back pocket only if the demo grows a physical PASS/FAIL indicator (LED) or external trigger input.

## Kria KV260 / K26 SoM
### Key Findings
- The official Kria "Baremetal Flow Example" documents essentially this exact recipe: wire a BRAM controller's `S_AXI` to the PS `M_AXI_HPM0` via Connection Automation, note the assigned address from the Address Editor, then write a standalone Vitis app that reads/writes that address and reports the result — strong external validation that this project follows AMD's own supported reference flow rather than an unusual configuration.
- K26 SOM boot mode is set via `MODE[3:0]` pins on the carrier card (JTAG / SD / QSPI); Kria starter kits including the KV260 ship preset to QSPI32 boot by default. For active development, JTAG boot via Vitis debug is typical; QSPI/SD is for standalone power-on boot without a host connection.
- The K26 SOM's MIO/EMIO mapping and carrier-card pin assignments are defined in board-support XDC/trace-delay files shipped with the Vivado board files — relevant only if the design is extended beyond pure internal AXI BRAM access.
- Vivado board files for KV260 (`xilinx.com:kv260_som:part0:...`) drive PS configuration (DDR, clocking, MIO) automatically when the board preset is applied to the Zynq UltraScale+ MPSoC IP — the mechanism `create_bd.tcl` almost certainly relies on for PS setup.
### Code Example
```tcl
# Confirming the board preset is applied to the PS (sanity check for create_bd.tcl)
set ps [get_bd_cells zynq_ultra_ps_e_0]
set preset_applied [get_property CONFIG.PSU__PRESET_APPLIED $ps]
if {$preset_applied ne "1"} {
    puts "WARNING: KV260 board preset not applied to PS — DDR/clocking/MIO may be misconfigured"
}
```
### Relevance to Your Project
Worth a quick manual check that `create_bd.tcl`'s PS instantiation references the KV260 board part and applies the board preset, rather than configuring DDR/MIO/clocking manually from a bare ZU5EG part — using the board preset is what guarantees the K26 SOM's specific DDR timing and MIO assignments match the physical hardware.

## AMD/Xilinx Tool Updates (2025.x)
### Key Findings
- Vivado 2025.1 ships a new fully customizable RTL-based AXI Switch IP and a new Pblock planner; the AXI Switch IP is more relevant if this demo ever grows beyond two AXI slaves into a multi-master/multi-slave topology than for the current point-to-point BRAM connections.
- Vivado 2025.1 also adds the ability to boot the PS first and dynamically load the PL afterward, for faster OS/bring-up — not directly applicable to a bare-metal-only flow, but relevant context if the project ever adds a Linux/PetaLinux variant alongside the bare-metal one.
- Vitis 2025.2 makes the Unified IDE the default and fully deprecates Vitis Classic IDE; 2025.1 (this project's pinned version) is one of the last releases where Classic project creation is still available, so bare-metal platform/app project creation steps will look different on any future toolchain upgrade.
- AMD's official "Vivado What's New" / "Vitis What's New" pages remain the canonical, version-specific source for known issues — worth checking directly against 2025.1 specifically before any toolchain upgrade is attempted on this project.
