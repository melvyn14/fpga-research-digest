## Executive Summary
- **Xilinx's own AXI-Lite reference VHDL has a documented backpressure bug** (raises `AWREADY`/`ARREADY` without checking `BREADY`/`RREADY` state) — if `kv260_top.vhd` wraps or mimics the AXI BRAM Controller's example interconnect logic, verify `*READY` deassertion is correctly gated, especially since the AXI Interconnect/SmartConnect between the PS `M_AXI_HPM0_FPD` port and the two BRAM controllers can stall on simultaneous read+write.
- **`apply_bd_automation` + `assign_bd_address`** are the two TCL commands that do 90% of the work in `create_bd.tcl` — connection automation wires the Zynq `M_AXI_HPM0_FPD` master to the AXI Interconnect, and the address editor command assigns the `0xA0000000`/`0xA0010000` ranges to BRAM0/BRAM2. Confirm both BRAM controllers' AXI4 address ranges don't overlap and are within the PS's mapped HPM0 window (default 1GB at `0x80000000`–`0xBFFFFFFF` on ZU+).
- **For Vitis bare-metal**, `xil_printf` over USB-UART (PS UART0/UART1, typically MIO 38/39 muxed via PMU firmware on KV260) requires the UART peripheral's clock/baud divisor to be set correctly in the BSP — mismatched `bsp.mss` UART clock config is a common cause of garbled PASS/FAIL output.
- **AXI BRAM Controller writes/reads from the PS need no XDC timing constraints** — the AXI bus runs fully inside the PL fabric clocked by `FCLK_CLK0`, so `set_input_delay`/`set_output_delay` only matter for the physical USB-UART TX/RX pins and any other PL-to-board I/O (e.g., status LEDs).
- **Vivado/Vitis 2025.1** ships a new fully-customizable RTL AXI Switch IP and PS-first boot with dynamic PL loading — the latter is directly relevant to a bare-metal KV260 flow since it lets the APU boot and run before the bitstream containing the BRAM controllers is loaded, which changes when `XPAR_*` addresses become valid.

## AXI Protocol / AXI-Lite / AXI-Stream
### Key Findings
- All five AXI channels (AW, W, B, AR, R) use the same READY/VALID handshake rule: a transfer happens only on the clock edge where both VALID and READY are `1`; once VALID is asserted it **cannot be withdrawn** until READY arrives, but READY *can* be withheld indefinitely by the slave.
- Xilinx's own example AXI-Lite slave (used as a template by many custom IP wizards) asserts `AWREADY`/`WREADY` based only on `AWVALID && WVALID`, without checking whether the write-response channel (`BVALID`/`BREADY`) has backpressure — this can cause a write to be silently dropped or double-accepted under burst traffic.
- `BVALID` must only be asserted **after** the final `WVALID`/`WREADY` handshake of that transaction completes — asserting it concurrently with the data-phase handshake violates ordering and can wedge an AXI Interconnect/SmartConnect.
- A slave must never let `AWVALID && AWREADY` and `ARVALID && ARREADY` both fire in the same cycle if it can't service both — losing one of the two transactions is a classic "looks fine in directed sim, fails under interconnect arbitration" bug.
- For the AXI BRAM Controller IP specifically: it deasserts `WREADY` when its internal write pipeline to the BRAM is full — if you ever swap the stock `axi_bram_ctrl` for a custom AXI-Lite-to-BRAM bridge, you must replicate this backpressure or risk write data loss during back-to-back transactions.
- Best practice from the AXI formal-verification community: register all `xREADY` outputs (don't combinationally derive READY from VALID of the same cycle) and add a 1-2 entry skid buffer if you need zero-bubble throughput.

### Code Example
```vhdl
-- Minimal, protocol-correct AXI-Lite write-address/data acceptance pattern
-- (registered READY, independent of downstream BVALID backpressure)
process(S_AXI_ACLK)
begin
  if rising_edge(S_AXI_ACLK) then
    if S_AXI_ARESETN = '0' then
      axi_awready <= '0';
      axi_wready  <= '0';
      aw_en       <= '1';
    else
      -- Accept AW only when not already holding an outstanding write
      if (not axi_awready) and S_AXI_AWVALID and S_AXI_WVALID and aw_en = '1' then
        axi_awready <= '1';
        axi_wready  <= '1';
        aw_en       <= '0';
      elsif S_AXI_BVALID = '1' and S_AXI_BREADY = '1' then
        -- Free to accept the next AW only after the response is consumed
        aw_en       <= '1';
        axi_awready <= '0';
        axi_wready  <= '0';
      else
        axi_awready <= '0';
        axi_wready  <= '0';
      end if;
    end if;
  end if;
end process;
```

### Relevance to Your Project
The two AXI BRAM Controllers in `kv260_axi_bram_demo` sit behind the Zynq PS's `M_AXI_HPM0_FPD` master through an AXI Interconnect/SmartConnect. If `main.c` issues back-to-back writes to BRAM0 followed immediately by a readback (the PASS/FAIL check), any backpressure mishandling in the interconnect's arbitration between BRAM0 and BRAM2 paths could cause an occasional dropped write that only shows up as an intermittent FAIL. If `kv260_top.vhd` contains any hand-written AXI-Lite glue (rather than pure IP-Integrator-instantiated `axi_bram_ctrl`), audit it against the patterns above — particularly the `aw_en`/`BVALID` interlock.

## Vivado Block Design / IP Integrator
### Key Findings
- **Connection Automation** ("Run Connection Automation" / `apply_bd_automation`) auto-wires a Zynq UltraScale+ Processing System's `M_AXI_HPM0_FPD` port to an AXI Interconnect or SmartConnect, including clock and reset connections — using it instead of manual wiring avoids a very common mistake of forgetting to connect `M_AXI_HPM0_FPD_ACLK` to `pl_clk0`.
- The **Address Editor** assigns memory-mapped offsets/ranges from the master's (PS) perspective. Each AXI BRAM Controller's S_AXI interface gets a unique entry; Vivado will flag overlapping ranges in red, but it will *not* automatically prevent you from assigning an address outside the PS's enabled HPM0 aperture (default `0x80000000`-`0xBFFFFFFF`, 1 GB) — addresses like `0xA0000000`/`0xA0010000` fall within this window, which is correct.
- "**Regenerate Layout**" only cleans up the visual canvas; it does **not** re-run validation. After any TCL-driven change to the block design (e.g., re-running `create_bd.tcl`), always follow with `validate_bd_design` before `generate_target`.
- When re-running a `create_bd_design` TCL script against an existing `.xpr`, stale cell names from a previous run can collide — `create_bd_cell` will throw `ERROR: [BD 41-737]` if the cell already exists. Idiomatic non-project scripts guard with `if {[get_bd_cells -quiet <name>] eq ""}` or simply delete and recreate the whole BD with `create_bd_design -force`.
- BRAM size mismatches between the `axi_bram_ctrl` and the paired Block Memory Generator (BMG) are a frequent IPI error (`CONFIG.SINGLE_PORT_BRAM` / data-width mismatch) — both IPs must agree on `READ_WRITE_MODE` and data width, and the BMG must be configured for the controller's "wrapper" memory map mode if ECC is enabled.

### Code Example
```tcl
# Typical pattern inside create_bd.tcl for wiring PS -> Interconnect -> 2x BRAM ctrl
apply_bd_automation -rule xilinx.com:bd_rule:axi4 \
  -config { Clk_master {Auto} Clk_slave {Auto} Clk_xbar {Auto} \
            Master {/zynq_ultra_ps_e_0/M_AXI_HPM0_FPD} \
            Slave {/axi_bram_ctrl_0/S_AXI} \
            intc_ip {New AXI Interconnect} \
            master_apm {0}} \
  [get_bd_intf_pins axi_bram_ctrl_0/S_AXI]

apply_bd_automation -rule xilinx.com:bd_rule:axi4 \
  -config { Clk_master {Auto} Clk_slave {Auto} Clk_xbar {Auto} \
            Master {/zynq_ultra_ps_e_0/M_AXI_HPM0_FPD} \
            Slave {/axi_bram_ctrl_1/S_AXI} \
            intc_ip {/axi_interconnect_0} \
            master_apm {0}} \
  [get_bd_intf_pins axi_bram_ctrl_1/S_AXI]

# Assign the fixed addresses used by main.c
set_property offset 0xA0000000 [get_bd_addr_segs \
  zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0]

  zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0]

  zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_1_Mem0]
set_property range  64K [get_bd_addr_segs \
```

## Vivado TCL Scripting
### Key Findings
- **Batch mode** (`vivado -mode batch -source script.tcl`) runs the script non-interactively and exits — best for CI/regeneration pipelines. **TCL mode** (`vivado -mode tcl`) drops you into an interactive console and is best for *developing* the script incrementally.
- **Non-project mode** (no `.xpr`, everything via `read_vhdl`/`read_xdc`/`synth_design`/`opt_design`/`place_design`/`route_design`/`write_bitstream` in one script) gives full control and avoids `.xpr`/`.cache`/`.runs` directory bloat in git — but you lose the GUI's incremental run management, so iterative debugging is slower.
- **Project mode with a recreation script** (`write_project_tcl`) is the common middle ground: keep only the TCL script and source files in git, regenerate the `.xpr` on demand with `source create_project.tcl` — this is exactly the pattern implied by a `tcl/create_bd.tcl` checked into a repo.
- For reproducibility across Vivado versions, always pin the part explicitly (`create_project ... -part xck26-sfvc784-2LV-c` for KV260's K26 SoM) rather than relying on a board file, since board file definitions occasionally change between releases.
- A robust top-level non-project script structure:
  ```
  create_project -in_memory -part <part>
  source create_bd.tcl          ;# builds the BD
  make_wrapper -files [get_files <bd>.bd] -top
  add_files -norecurse <wrapper>.vhd
  add_files -fileset constrs_1 <constraints>.xdc
  synth_design -top <wrapper> -part <part>
  opt_design; place_design; route_design
  write_bitstream -force <output>.bit
  ```

### Code Example
```tcl
#!/usr/bin/env -S vivado -mode batch -source
# build.tcl - regenerate KV260 AXI-BRAM project from scratch
set part "xck26-sfvc784-2LV-c"
set proj_dir "./build"

create_project kv260_axi_bram $proj_dir -part $part -force

# Re-create the block design (idempotent guard)
if {[get_bd_designs -quiet kv260_bd] ne ""} {
  close_bd_design [get_bd_designs kv260_bd]
}
create_bd_design "kv260_bd"
source ./tcl/create_bd.tcl

validate_bd_design
save_bd_design

make_wrapper -files [get_files kv260_bd.bd] -top
add_files -norecurse [get_files -of_objects [get_filesets sources_1] *kv260_bd_wrapper.vhd]
update_compile_order -fileset sources_1

set_property top kv260_bd_wrapper [current_fileset]

launch_runs synth_1 -jobs 4
wait_on_run synth_1
launch_runs impl_1 -to_step write_bitstream -jobs 4
wait_on_run impl_1

puts "Build complete: [get_property DIRECTORY [current_project]]"
```

### Relevance to Your Project
Since the repo already separates `tcl/create_bd.tcl` from the VHDL top-level, wrapping it in a top-level `build.tcl` like the above gives you a one-command, version-pinned rebuild (`xck26-sfvc784-2LV-c` is the exact K26 SoM part) — useful for confirming the 2025.1 toolchain still reproduces an identical address map for BRAM0/BRAM2 after any Vivado upgrade.

## Vitis Bare-Metal / Standalone
### Key Findings
- The **standalone BSP** generates `xparameters.h` per peripheral from the hardware handoff (`.xsa`); for an `axi_bram_ctrl`, watch for `XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR` / `XPAR_AXI_BRAM_CTRL_1_S_AXI_BASEADDR` — these should match the `0xA0000000`/`0xA0010000` addresses from the address editor. A mismatch here (stale `.xsa` vs. updated BD) is the #1 cause of "writes go nowhere" bugs.
- `xil_printf` is a lightweight printf with **no floating-point support** and a reduced format-specifier set (`%d`, `%x`, `%s`, `%c`, `%u`, `%lu`, etc.) — using `%f` silently prints garbage or nothing; this matters for any PASS/FAIL diagnostic messages that might want to print computed values.
- Standalone BSPs for Cortex-A53 (APU) on Zynq UltraScale+ include a GIC (ARM GICv2/GICv3-compatible) driver; even if your bare-metal app is purely polling (no interrupts needed for AXI-Lite BRAM access), the BSP still links in `xscugic` unless explicitly excluded — keep this in mind for binary size but it's otherwise harmless.
- Linker scripts (`lscript.ld`) for A53 standalone apps place `.text`/`.data`/`.bss` in OCM or DDR depending on the memory selected in "Edit BSP Settings" → the **stack/heap size** (`-Wl,--defsym=_HEAP_SIZE=` / stack pointer init) is a common silent-corruption source if your app prints large buffers — increase `STACK_SIZE` in `lscript.ld` if PASS/FAIL output gets truncated or the app hangs after several BRAM passes.
- For UART-based PASS/FAIL output on KV260, the default `stdout`/`stdin` is whichever UART is marked in the hardware design (`bsp.mss` `stdin`/`stdout` parameters) — confirm it matches the actual USB-UART bridge (typically `psu_uart_1` on Kria carrier boards) or `xil_printf` output will go to a UART with no physical connection.

### Code Example
```c
#include "xil_printf.h"
#include "xil_io.h"
#include "xparameters.h"

#define BRAM0_BASE  XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR  /* 0xA0000000 */
#define BRAM2_BASE  XPAR_AXI_BRAM_CTRL_1_S_AXI_BASEADDR  /* 0xA0010000 */
#define TEST_PATTERN 0xDEADBEEF
#define NUM_WORDS    16

int test_bram(u32 base_addr, const char *name) {
    int i, errors = 0;

    for (i = 0; i < NUM_WORDS; i++) {
        Xil_Out32(base_addr + (i * 4), TEST_PATTERN ^ i);
    }

    for (i = 0; i < NUM_WORDS; i++) {
        u32 readback = Xil_In32(base_addr + (i * 4));
        u32 expected = TEST_PATTERN ^ i;
        if (readback != expected) {
            xil_printf("%s [%d]: wrote 0x%08x, read 0x%08x -- FAIL\r\n",
                       name, i, expected, readback);
            errors++;
        }
    }

    xil_printf("%s: %s (%d errors)\r\n", name,
               errors == 0 ? "PASS" : "FAIL", errors);
    return errors;
}

int main(void) {
    int total_errors = 0;
    xil_printf("\r\n--- KV260 AXI BRAM Demo ---\r\n");
    total_errors += test_bram(BRAM0_BASE, "BRAM0");
    total_errors += test_bram(BRAM2_BASE, "BRAM2");
    xil_printf("Overall: %s\r\n", total_errors == 0 ? "PASS" : "FAIL");
    return total_errors;
}
```

### Relevance to Your Project
This matches the described `main.c` pattern exactly (write pattern → readback → PASS/FAIL over USB-UART). Two things worth double-checking in your actual code: (1) that `XPAR_AXI_BRAM_CTRL_*_S_AXI_BASEADDR` from the generated `xparameters.h` still equals `0xA0000000`/`0xA0010000` after any BD regeneration (regenerate the `.xsa` and re-run "Update Hardware Specification" in the BSP if you change the address map), and (2) that `bsp.mss` `stdout` points at the UART wired to the KV260's USB-UART bridge so PASS/FAIL is actually visible.

## XDC Timing Constraints
### Key Findings
- For a design where **all logic is driven by `pl_clk0`** (Zynq UltraScale+ PS-generated FCLK) and the only PL I/O is the USB-UART (via PS MIO, not EMIO) and maybe a status LED, you typically need **very few XDC constraints** — the AXI BRAM Controller, BMG, and AXI Interconnect/SmartConnect are all internal, fully-synchronous logic that Vivado times automatically once the clock is defined.
- `set_input_delay`/`set_output_delay` model the external system relative to a clock at a port: `set_input_delay -clock sys_clk -max <ns> [get_ports din]` and `set_output_delay -clock sys_clk -max <ns> [get_ports dout]`. Crucially, **input setup numbers represent the driving device's clock-to-out**, and **output delay numbers represent the receiving device's setup requirement** — not the FPGA's own setup/hold, which STA computes separately.
- `set_clock_groups -asynchronous -group [get_clocks clk_a] -group [get_clocks clk_b]` is required whenever you have genuinely unrelated clock domains (e.g., a free-running reference clock used for an LED blink vs. `pl_clk0`) — without it, Vivado will attempt (and fail/over-constrain) timing analysis across domains it can't relate.
- If your design has **no external PL-side high-speed I/O at all** (true for a pure AXI-Lite-to-BRAM demo with only PS-routed UART), the auto-generated constraints from the Zynq PS IP (clock definitions for `pl_clk0`/`pl_clk1`) plus default `false_path`/`clock_groups` from IP Integrator are usually sufficient — a hand-written `.xdc` may only need to exist for an optional LED or PMOD header.
- A common 2025.x gotcha: if you add a board-level constraint file copied from an older Kria example targeting a different carrier card, **port names in `set_property PACKAGE_PIN` must match your top-level entity's port names exactly** (case-sensitive in VHDL-derived netlists) — a mismatched pin constraint silently produces an unconstrained/unrouted port rather than an error in some flows, so check the implemented design's I/O report.

### Code Example
```tcl
# kv260_axi_bram.xdc - minimal constraints for a PS-clocked design with
# only a UART (via MIO, no constraint needed) and an optional status LED
# on a PMOD/GPIO pin routed through EMIO or PL fabric.

# If using an EMIO/PL GPIO for a "test running" LED on the KR260 carrier
# (adapt PACKAGE_PIN per your carrier's schematic):
set_property PACKAGE_PIN H12 [get_ports led_status]
set_property IOSTANDARD LVCMOS33 [get_ports led_status]

# Output delay relative to the PL fabric clock, for a slow LED — generous
# margin since this is not timing-critical:
create_clock -period 10.000 -name virtual_pl_clk0 -waveform {0 5} [get_pins -hier *pl_clk0*]
set_output_delay -clock virtual_pl_clk0 -max 2.000 [get_ports led_status]
set_output_delay -clock virtual_pl_clk0 -min 0.500 [get_ports led_status]

# If a secondary free-running reference clock exists for the LED PWM,
# declare it asynchronous to the AXI fabric clock:
set_clock_groups -asynchronous \
  -group [get_clocks -of_objects [get_pins -hier *pl_clk0*]] \
  -group [get_clocks -of_objects [get_pins -hier *led_pwm_clk*]]
```

### Relevance to Your Project
If `kv260_top.vhd` exposes no PL-side I/O beyond what's wired through the PS (UART on MIO, JTAG, etc.), your `.xdc` can likely remain nearly empty — the Zynq PS IP's auto-generated constraints handle `pl_clk0` and the AXI fabric. Only add the snippet above if/when you wire an external LED or PMOD signal directly from `kv260_top.vhd`; until then, an empty or near-empty XDC is *correct*, not an oversight.

## Kria KV260 / K26 SoM
### Key Findings
- The K26 SoM's `PS_MODE[3:0]` pins (routed through the SOM connector to the carrier card) set the Zynq UltraScale+ boot mode; KV260's starter-kit carrier defaults to **QSPI boot** of the certified Linux image, but a bare-metal `BOOT.BIN` can be loaded into a user partition and booted via the existing firmware's "user application hook," or loaded directly over **JTAG via XSDB** for development iteration without touching the QSPI image — the latter is the fastest loop for your AXI-BRAM PASS/FAIL demo.
- KV260 MIO pins 38-51 are typically reserved for **PS GEM1 Ethernet** in the standard carrier card config — if your design's pin/IP assignments were derived from a different Kria board variant's BD, double check MIO usage doesn't collide with Ethernet (otherwise networking silently breaks, which doesn't affect a bare-metal-only flow but matters if you ever boot Linux on the same image).
- PS and PL are on **separate power domains** on Zynq UltraScale+; for bare-metal-only designs the PMU firmware still needs to sequence PL power-up and clock/reset release (`FCLK_RESET0_N`) before the AXI Interconnect and BRAM controllers are usable — if your `main.c` accesses BRAM immediately at `main()` entry without the platform's standard PS7/PSU init sequence (`psu_init()` generated from the `.xsa`), you can get bus errors because the PL fabric clock/reset hasn't been released yet.
- The K26 SoM's exact Vivado part number is **`xck26-sfvc784-2LV-c`** (or `-i` for industrial-grade SOMs) — using the wrong speed grade/temperature grade part in a from-scratch `create_project` (vs. using the certified Kria platform `.xpfm`) can cause timing closure differences vs. the AMD reference designs.
- For debugging "PS can't see PL peripherals at all," the most common root cause on KV260 is a missing or stale **`.xsa` export** after a BD change — `Vitis` must re-import the updated `.xsa` (Vitis 2025.1 Unified IDE: "Update Hardware Specification" on the platform component) or `XPAR_*` addresses in `xparameters.h` will be stale relative to the actual bitstream.

### Code Example
```tcl
# Confirm PL fabric clock/reset are released before BRAM access becomes valid
# (run in XSCT/XSDB connected over JTAG, useful for live debug on KV260)
connect
targets -set -filter {name =~ "*A53*0*"}

# Read FPD_SLCR / CRL_APB registers to confirm FCLK0 is enabled
mrd 0xFF5E0080   ;# CRL_APB.PL0_REF_CTRL - check SRCSEL/DIVISOR fields
mrd 0xFF0A0100   ;# PMU_GLOBAL.PL_STATUS or equivalent - confirm PL "Programmed" bit

# Once confirmed, a manual peek/poke of BRAM0 to sanity-check the bus
# before trusting main.c's higher-level test:
mwr 0xA0000000 0xCAFEF00D
mrd 0xA0000000 1
```

### Relevance to Your Project
If you ever see the BRAM PASS/FAIL test hang or bus-error on first boot but work fine after a JTAG re-run, suspect the PL power/clock sequencing described above — it's worth adding a quick PL-ready check (or simply calling the generated `psu_init()` before any BRAM access, which the standard Vitis bare-metal template does automatically). Also worth confirming: which exact Kria carrier (KV260 starter kit vs. a custom carrier) your `.xsa`/BD was generated against, since MIO assignments for UART differ between carriers.

## AMD/Xilinx Tool Updates (Vivado/Vitis 2025.x)
### Key Findings
- **Vivado 2025.1** introduces the ability to **boot the PS first and dynamically load the PL bitstream later** ("PS-first boot, dynamic PL load") — for bare-metal flows this means the APU can start executing before the BRAM controllers exist in the fabric; any design relying on this flow must explicitly wait for/trigger PL configuration (e.g., via `XFpga` driver) before touching `0xA0000000`/`0xA0010000`.
- A new **fully customizable RTL-based AXI Switch IP** ships in 2025.1 — a potential drop-in alternative to AXI Interconnect/SmartConnect if you ever want finer control over how the PS master fans out to BRAM0/BRAM2 (e.g., explicit per-master arbitration weighting), though for a 2-slave demo the default SmartConnect remains simplest.
- The **Vitis Unified IDE is now the default** (Classic Vitis IDE deprecated) — platform/BSP creation, "Update Hardware Specification," and build steps have moved/renamed in the UI vs. 2023.x/2024.x tutorials; if following an older Kria bare-metal tutorial, expect menu paths to differ (e.g., platform creation is now under a "Create Platform Component" wizard rather than "New > Platform Project").
- A new **Pblock planner** and improved directive/subdirective support are aimed at larger designs for QoR — not directly relevant to a 2-BRAM demo, but useful context if the project later grows (e.g., adding more PL peripherals and needing floorplanning).
- IP change-log highlights for 2025.1 include fixes to BRAM statistics/byte-count mismatches in certain AXI IP — worth a quick scan of the IP release notes (Answer Record 000037919) if you upgrade an existing 2024.x project's IP versions and see unexpected BRAM controller behavior changes after `Report IP Status` → `Upgrade Selected IP`.

### Relevance to Your Project
If/when you move this project's Vivado/Vitis project files to 2025.1 from an older release, run `report_ip_status`/`upgrade_ip` on the block design *before* regenerating the wrapper and re-exporting the `.xsa` — IP version drift between `axi_bram_ctrl`/Block Memory Generator and what the BSP's `xparameters.h` expects is a common source of "worked yesterday, FAILs today" after a tool upgrade. Also factor in the PS-first/dynamic-PL-load option only if you adopt a flow where Linux or U-Boot loads the bitstream after APU boot — for a pure standalone `BOOT.BIN` containing both FSBL+bitstream+app, the traditional combined boot flow remains simplest.
