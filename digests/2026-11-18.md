# FPGA Research Digest - 2026-11-18

## Executive Summary

- **AXI-Lite VALID must never depend on READY**: Vivado-generated slave templates (including 2018.3-era examples) have been confirmed buggy by formal verification; always check generated cores with a property checker before trusting them in silicon.
- **AXI Interconnect is being retired**: AMD is discontinuing AXI Interconnect in the next major release — migrate your block design to AXI SmartConnect (PG247) now to avoid forced upgrades at tape-out.
- **KV260 HPM port changed between tool versions**: 2022.1 KV260 tutorials connect BRAM via HPM0 FPD, but 2024.x guides for sibling boards switch to AXI HPM LPD — verify the correct master port in your Vivado version before wiring the BRAM controller.
- **Vivado 2025.1 adds a new RTL-based AXI Switch IP**, but it is intentionally excluded from IPI block design automation; use SmartConnect for block designs and AXI Switch only in pure RTL flows.
- **Non-project mode batch flow is the most reproducible automation path**: `vivado -mode batch -source script.tcl` gives you full control but requires explicit report commands, since nothing is auto-generated.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- **VALID must never depend on READY.** The initiator of a transaction must assert VALID unconditionally, without waiting for the target to assert READY first. A design that de-asserts VALID before receiving READY violates the protocol and can deadlock.
- **Response channel dependency is legal and required.** BVALID (write response) can only be asserted after both AWREADY and WREADY have been seen. RVALID can only be asserted after ARREADY. These are the only cross-channel dependencies permitted.
- **Vivado's own AXI-Lite demo cores have had protocol bugs.** Formal verification author ZipCPU reported that the generated AXI-Lite slave in Vivado 2018.3 failed formal AXI checks — it did not correctly drop READY lines to prevent new transactions when the outgoing acknowledgement channel was stalled. Treat generated templates as a starting point, not a reference-correct implementation.
- **Stalling downstream does not excuse upstream VALID violations.** A slave can hold READY low indefinitely, but the master must keep VALID asserted until READY arrives. If your master polls READY before asserting VALID, you have a latent deadlock.
- **AXI-Stream has no address channel.** For the BRAM demo there is no AXI-Stream involved, but it is a common confusion: AXI-Lite has separate write-address, write-data, write-response, read-address, and read-data channels; AXI-Stream has only a single unidirectional data channel.

### Code Example

```vhdl
-- Minimal AXI-Lite slave state machine skeleton (VHDL)
-- Illustrates correct VALID/READY behavior for the write path

process(aclk)
begin
  if rising_edge(aclk) then
    if aresetn = '0' then
      awready  <= '0';
      wready   <= '0';
      bvalid   <= '0';
      bresp    <= "00";
    else
      -- Address and data accepted on same cycle (AXI-Lite common pattern)
      if (awvalid = '1' and wvalid = '1' and awready = '0' and wready = '0') then
        awready <= '1';
        wready  <= '1';
        -- Latch address and data here
      else
        awready <= '0';
        wready  <= '0';
      end if;

      -- Assert BVALID only after both address and data were accepted
      if (awready = '1' and wready = '1') then
        bvalid <= '1';
        bresp  <= "00";  -- OKAY
      elsif (bready = '1' and bvalid = '1') then
        bvalid <= '0';  -- De-assert only after slave sees bready
      end if;
    end if;
  end if;
end process;
```

### Relevance to Your Project

Your project drives two BRAM controllers (BRAM0 at `0xA0000000`, BRAM2 at `0xA0010000`) over AXI-Lite from the A53. If the BRAM controller IP in your block design is based on an older Vivado template, run the ZipCPU AXI-Lite formal properties (`axil_slave.sby`) against it to confirm there is no VALID/READY hazard. For the C side, verify that your `Xil_Out32`/`Xil_In32` calls do not need explicit memory barriers — the Cortex-A53 strongly-ordered device memory type used for PL-mapped addresses handles ordering, but a `dmb` before the read-back loop is good defensive practice.

## Vivado Block Design / IP Integrator

### Key Findings

- **Connection Automation is the right starting point but not always correct.** For standard PS→BRAM paths, Run Connection Automation (the banner button) correctly wires the AXI master port and inserts SmartConnect. It knows the board's physical pin assignments (Board Awareness). However, it can be confused when two HP master ports cover overlapping address ranges.
- **Lock addresses after assigning them manually.** After assigning your BRAM base addresses (0xA0000000 and 0xA0010000) in the Address Editor, right-click each segment and select Lock. Locked segments survive a "Run Connection Automation" re-run without being reassigned.
- **The Address Editor tab only appears with a bus master present.** If you open a fresh block design and see no Address Editor tab, it means no AXI master IP (PS, AXI Master, etc.) has been placed yet.
- **AXI Interconnect is deprecated.** AMD announced it will be removed in the next major release; migrate existing designs to AXI SmartConnect (PG247). SmartConnect handles clock-domain crossing and width conversion automatically.
- **To view Diagram and Address Editor side by side:** right-click either tab and choose *New Vertical Group*.

### Code Example

```tcl
# TCL snippet: assign BRAM addresses after create_bd_design completes
# Run after apply_bd_automation to lock addresses

set bram0 [get_bd_addr_segs -of_objects [get_bd_cells axi_bram_ctrl_0]]
set bram2 [get_bd_addr_segs -of_objects [get_bd_cells axi_bram_ctrl_1]]

assign_bd_address [get_bd_addr_segs {axi_bram_ctrl_0/S_AXI/Mem0}]
set_property offset 0xA0000000 [get_bd_addr_segs \
    {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property range 64K [get_bd_addr_segs \
    {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]

assign_bd_address [get_bd_addr_segs {axi_bram_ctrl_1/S_AXI/Mem0}]

    {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_1_Mem0}]

    {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_1_Mem0}]

Using TCL-based address assignment (above) instead of relying on GUI automation ensures the addresses are always reproducible across clean rebuilds — critical for CI/CD-style flows.

## Vivado TCL Scripting

### Key Findings

- **Non-project mode is the most reproducible flow for CI.** Invoke with `vivado -mode batch -source build.tcl`. All sources, synthesis options, implementation strategies, and report generation must be declared explicitly in the script — nothing is auto-generated by the tool.
- **Source order matters.** In non-project mode, files are compiled in the order `read_vhdl` / `read_verilog` commands appear. Packages and components must appear before entities that depend on them.
- **Reports are not auto-generated.** Add explicit `report_timing_summary`, `report_utilization`, and `report_drc` commands; otherwise your batch run produces no reports at all.
- **Block design export pattern.** For IP Integrator designs, the typical non-project flow exports the block design to a wrapper HDL, then proceeds with synthesis: `generate_target all [get_files *.bd]` → `make_wrapper` → `read_vhdl <wrapper>` → `synth_design`.
- **`apply_bd_automation` can be called from TCL** but AMD recommends driving it through the GUI or a GUI-recorded script rather than hand-authoring it, because argument syntax is fragile across releases.

### Code Example

```tcl
# Non-project mode build script skeleton for KV260 AXI-BRAM demo

set outputDir ./output
file mkdir $outputDir

# 1. Read sources
read_vhdl -library xil_defaultlib ./vhdl/kv260_top.vhd

# 2. Create and populate block design (source the BD creation script)
source ./tcl/create_bd.tcl

# 3. Generate wrapper and targets
generate_target all [get_files *.bd]
set wrapper [make_wrapper -files [get_files *.bd] -top]
read_vhdl $wrapper

# 4. Read constraints
read_xdc ./xdc/kv260_top.xdc

# 5. Synthesize
synth_design -top kv260_wrapper -part xck26-sfvc784-2LV-c

# 6. Reports
report_utilization -file $outputDir/util_synth.rpt

# 7. Implement
opt_design
place_design
route_design

# 8. Final reports and bitstream
report_timing_summary -file $outputDir/timing.rpt
report_drc           -file $outputDir/drc.rpt
write_bitstream -force $outputDir/kv260_top.bit
```

### Relevance to Your Project

Your existing `create_bd.tcl` is already the core of a non-project flow. Wrapping it in the skeleton above makes the entire build reproducible from a single `vivado -mode batch -source build.tcl` command — no GUI interaction needed, and the output directory always holds fresh reports.

## Vitis Bare-Metal / Standalone

### Key Findings

- **xil_printf is intentionally small (~1 KB).** It supports `%d`, `%x`, `%s`, `%c`, and `%u` but not `%f` (floating point). For UART debugging in your PASS/FAIL loop, it is exactly the right choice — it avoids pulling in newlib printf which can add 50–100 KB to the image.
- **xparameters.h is the single source of truth for addresses and interrupt IDs.** It is regenerated from the XSA every time you update the hardware platform in Vitis. Never hardcode peripheral addresses in C if `xparameters.h` already defines them.
- **Exception/interrupt headers:** `xil_exception.h` provides `Xil_ExceptionEnable()`, `Xil_ExceptionRegisterHandler()`, and related macros. For bare-metal interrupt-driven designs, initialize the exception table before enabling interrupts in the PS.
- **Linker script heap/stack.** The generated `lscript.ld` defaults are often too small for complex applications. For a minimal BRAM test, 64 KB heap and 256 KB stack are sufficient. Larger xil_printf usage or dynamic allocation requires at least 1 MB heap.
- **Vitis Classic IDE deprecated in 2025.1.** AMD officially deprecated the Classic Vitis IDE (Eclipse-based) in the 2025.1 release. The Vitis Unified IDE (VS Code–based) is now the primary development environment. Build/run flows have changed — `xsct` scripts that worked in Classic may need updating for Unified.

### Code Example

```c
/* Minimal AXI-BRAM read/write test for KV260 bare-metal */
#include "xil_printf.h"
#include "xil_io.h"
#include "xparameters.h"

/* If not in xparameters.h, use your block design addresses */
#ifndef XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR
#define BRAM0_BASE 0xA0000000UL
#define BRAM2_BASE 0xA0010000UL
#else
#define BRAM0_BASE XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR
#define BRAM2_BASE XPAR_AXI_BRAM_CTRL_1_S_AXI_BASEADDR
#endif

#define TEST_PATTERN_A 0xDEADBEEFUL
#define TEST_PATTERN_B 0xCAFEBABEUL

int main(void) {
    u32 readback;
    int pass = 1;

    xil_printf("KV260 AXI-BRAM test start\r\n");

    /* Write patterns */
    Xil_Out32(BRAM0_BASE, TEST_PATTERN_A);
    Xil_Out32(BRAM2_BASE, TEST_PATTERN_B);

    /* Memory barrier before readback */
    __asm__ volatile("dmb sy" ::: "memory");

    /* Read back and verify */
    readback = Xil_In32(BRAM0_BASE);
    if (readback != TEST_PATTERN_A) {
        xil_printf("FAIL: BRAM0 expected 0x%08X got 0x%08X\r\n",
                   TEST_PATTERN_A, readback);
        pass = 0;
    }

    readback = Xil_In32(BRAM2_BASE);
    if (readback != TEST_PATTERN_B) {
        xil_printf("FAIL: BRAM2 expected 0x%08X got 0x%08X\r\n",
                   TEST_PATTERN_B, readback);
        pass = 0;
    }

    if (pass)
        xil_printf("PASS: both BRAMs verified\r\n");

    return 0;
}
```

### Relevance to Your Project

This is a production-ready version of your existing PS-to-PL connectivity test. The `dmb sy` barrier ensures the A53's store buffer is flushed before the read-back, preventing a false PASS when the CPU returns its own cached write. The `xparameters.h` guard makes the code portable across BSP regenerations.

## XDC Timing Constraints

### Key Findings

- **For internal AXI-Lite PS-to-PL paths, you generally need no I/O constraints.** Paths between the Zynq PS and PL fabric are internal to the device; `create_clock` on the PS clock output is sufficient. `set_input_delay` and `set_output_delay` apply to actual device I/O pins.
- **Clock ordering matters for runtime.** AMD recommends defining `create_clock` and `create_generated_clock` first, then I/O delays, then timing exceptions (`set_false_path`, `set_multicycle_path`, `set_clock_groups`). Out-of-order constraints increase implementation runtime.
- **`set_clock_groups -asynchronous` is the preferred way to cut unrelated clocks.** For example, cutting the PL design clock from the BRAM controller and an independent reference clock from an oscillator.
- **`-add_delay` on `set_output_delay` stacks constraints.** Use it for DDR-style output delays that require both rising-edge and falling-edge constraints on the same port: call `set_output_delay` twice — once without `-add_delay` (to set the initial constraint) and once with it.
- **Vivado can infer sampling clocks automatically** if you omit the `-clock` argument on `set_input_delay`; this works for simple cases but is less explicit and harder to audit.

### Code Example

```tcl
# Minimal XDC for KV260 AXI-BRAM demo
# The PL fabric clock is sourced from the PS (pl_clk0, 100 MHz typical)
# No external I/O delay constraints needed for a pure PS-to-BRAM design.

# PS fabric clock (driven by Zynq PS block output pl_clk0)
# The IPI block design creates this automatically; add it here only if
# you have RTL outside the BD that needs it.
# create_clock -period 10.000 -name clk_pl [get_ports pl_clk0]

# False-path any async resets coming from the PS
set_false_path -from [get_pins */PS8_i/FCLKRESETN[0]]

# Cut timing between unrelated clocks if you add a second clock source
# set_clock_groups -asynchronous \
#     -group [get_clocks clk_pl] \
#     -group [get_clocks clk_ext]

# If PL output pins to board are present (LEDs, etc.) constrain them:
# set_output_delay -clock clk_pl -max 2.000 [get_ports led[*]]
# set_output_delay -clock clk_pl -min -1.000 [get_ports led[*]] -add_delay
```

### Relevance to Your Project

Your KV260 demo is a closed PS↔PL loop with no external I/O timing constraints, so the XDC file is minimal. The key constraint is the false-path on FCLKRESETN to prevent timing violations on the asynchronous reset path. If you add board-facing LEDs or PMOD I/O in a future iteration, the `set_output_delay` template above is the starting point.

## Kria KV260 / K26 SoM

### Key Findings

- **Boot sequence is fixed by the factory-flashed QSPI.** The KV260 primary boot device is 512 Mbit QSPI flash pre-programmed at the factory with BOOT.BIN. For bare-metal development, you can override boot by inserting a microSD with your own BOOT.BIN — the boot mode is determined by the board's JTAG/SD/QSPI switch, not software.
- **MIO banking: three banks at 1.8V on the SOM.** Bank 500 is used by the SOM itself (QSPI, eMMC, I2C, TPM SPI). Bank 501 carries PMU power-management and some user I/O. Bank 502 is fully user-defined and exposed on the carrier card. All MIO banks are powered at 1.8V — do not connect 3.3V signals to MIO pins directly.
- **KV260 vs KR260 MIO differences.** The two carrier boards differ in which MIO functions are enabled via PMU overlay configuration. Notably, GEM1 RGMII Ethernet is listed for the KR260 but not the KV260. Any HPM port changes between carrier-specific Vivado preset files should be verified in the board preset XML.
- **HPM port selection has changed between guide versions.** The 2022.1 KV260 tutorials connect the BRAM controller to M_AXI_HPM0_FPD. A 2024.x KR260 guide switches to M_AXI_HPM0_LPD (the low-power domain master). Check which master port your block design uses and ensure the AXI address space mapping is consistent.
- **A53 bare-metal targets Core 0.** When using XSCT to download and run bare-metal apps, target selection is `targets -set -nocase -filter {name =~ "Cortex-A53*#0"}`. The PMU must be initialized before the A53 on Zynq UltraScale+ (PMU firmware handles clock and power sequencing).

### Code Example

```tcl
# XSCT script to download and run bare-metal ELF on KV260 (A53 Core 0)
# Run from Vitis XSCT console or vitis -exec xsct run_app.tcl

connect

# Target the APU A53 Core 0

# Download the application
dow ./Debug/kv260_bram_test.elf

# Set a breakpoint at main (optional)
bpadd -addr &main

# Run
con

# In a production flow, replace 'con' with 'run' + poll for 'exit' or
# parse UART output via a serial monitor script.
```

### Relevance to Your Project

Your project targets exactly this flow: A53 Core 0 running bare-metal C, writing patterns to BRAM0 and BRAM2 and reading them back over UART. The key operational concern is ensuring the QSPI/SD boot mode switch is set correctly before powering on, and that your HPM master port in Vivado matches what the AMD board preset file specifies for your version of the tools.

## AMD/Xilinx Tool Updates: Vivado/Vitis 2025.x

### Key Findings

- **Vivado 2025.1 adds Versal AI Edge Gen 2, Versal Prime Gen 2, and Spartan UltraScale+ device support.** No new Kria-specific device families were announced, but device support for the XCK26 (K26 SoM) continues.
- **New RTL-based AXI Switch IP in 2025.1.** This is a fully customizable RTL bridge between different AXI interface types and widths. Important caveat: it is NOT for use in IPI block diagram designs and does not participate in any IP integrator automation. Use SmartConnect for block designs; AXI Switch is for hand-wired RTL.
- **AXI Interconnect (PG059) is deprecated and will be removed in the next major release.** Migrate all block designs to AXI SmartConnect (PG247). The older `AXI Interconnect v2.1` to `SmartConnect v1.0` migration path is documented in PG059.
- **Vitis Classic IDE (Eclipse) is deprecated in 2025.1.** The Vitis Unified IDE (VS Code–based) is now the primary development environment. XSCT scripting continues to work, but Eclipse-style project configurations may need migration.
- **Vitis 2025.1 adds initial C++17 support in HLS** via Clang 16, plus improved AI Engine API and data type features. These are HLS/AIE features, not relevant to bare-metal C development, but worth noting for future PL acceleration work.
- **Known issue (Vitis Libraries 2025.1):** Vitis GUI projects may fail on RHEL 8.3 / CentOS 8.2 due to `LD_LIBRARY_PATH` conflicts. Workaround: remove `${env_var:LD_LIBRARY_PATH}` from the project settings.

### Code Example

```tcl
# Vivado 2025.1: check if the deprecated AXI Interconnect is present
# in a block design and report a warning

open_project ./kv260.xpr
open_bd_design [get_files *.bd]

set deprecated_cells [get_bd_cells -filter {VLNV =~ *axi_interconnect*}]
if {[llength $deprecated_cells] > 0} {
    puts "WARNING: Deprecated AXI Interconnect found: $deprecated_cells"
    puts "Migrate to AXI SmartConnect before the next major Vivado release."
    foreach cell $deprecated_cells {
        puts "  Cell: $cell  VLNV: [get_property VLNV $cell]"
    }
} else {
    puts "OK: No deprecated AXI Interconnect found."
}
```

### Relevance to Your Project

If your `create_bd.tcl` was authored against Vivado 2024.x or earlier and uses `axi_interconnect` for the PS→BRAM path, run the detection script above. The KV260 BRAM demo is simple enough that the migration to SmartConnect is a one-cell replacement in the block design. Plan this migration before upgrading to whatever release follows 2025.x, since AXI Interconnect removal will break the build silently if `create_bd.tcl` still references it.
