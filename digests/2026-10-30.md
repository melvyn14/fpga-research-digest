# FPGA Research Digest - 2026-10-30

## Executive Summary

- **AXI-Lite BRAM output register latency** is a hidden timing killer: enabling both the BRAM primitive output register _and_ the AXI BRAM Controller output register can worsen timing — use one or the other (controller-side preferred); see the Timing section for details.
- **TCL `write_bd_tcl` embeds the Vivado version** — always pin both the tool version and IP versions in your create_bd.tcl to avoid silent cross-release port or parameter mismatches.
- **`xil_printf` does not support `%f`** in the Vitis bare-metal BSP; print floats as integer + fractional parts manually — critical for any sensor/debug readout added to your UART output in main.c.
- **Kria KV260 boot firmware must be ≥ 01.06** (June 2025 UG1089) for reliable PS power-domain management; stale boot firmware can fail to re-enable the PL power domain after reboot.
- **Vivado 2025.1 ships a new Vitis Server backend** and updated XSA export that splits fixed and extensible regions; bare-metal projects should re-export the platform XSA after any Vivado 2025.1 upgrade.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings
- **BRAM output-register latency trap:** The AXI BRAM Controller has a fixed internal BRAM latency that cannot be configured via IP properties. Adding both a BRAM primitive output register AND a controller output register can actually worsen timing instead of helping. One community designer found that enabling the BRAM primitive output register violated timing at 250 MHz and had to add two controller output registers instead to close it.
- **Clock-domain mismatch on read paths:** An AMD support thread (Vivado 2014.4, confirmed still relevant) reports stale or wrong read-data returned from the AXI BRAM controller after back-to-back reads. Root cause: read-data path not properly constrained across clock domains. Always verify read-data stability in simulation before hardware bring-up.
- **AXI-Lite can run on a slower clock than the PL fabric:** Clock-domain crossing (CDC) between a fast algorithmic clock and a slower AXI4-Lite interface can help timing closure. Adds latency but removes the most critical timing paths from the AXI bus itself.
- **AXI-Stream TVALID cannot be de-asserted** once raised until TREADY is asserted (per AMD UG897). Violating this causes bus lockup. TREADY _may_ depend on TVALID; TVALID _must never_ depend on TREADY (would create combinatorial loops).
- **TLAST must be driven correctly on every packet.** A common mistake is returning to IDLE state immediately after asserting TLAST without waiting for the other side's TREADY, which corrupts the final beat.
- **XPM_FIFO_AXIS only supports FWFT mode** and requires power-of-two depth. Max FIFO size is 150 Megabits (width × depth).

### Code Example
```vhdl
-- AXI-Lite read path with registered output to avoid BRAM latency issues
-- Place this in your kv260_top.vhd or a slave BRAM wrapper
process(s_axi_aclk)
begin
  if rising_edge(s_axi_aclk) then
    if s_axi_arvalid = '1' and axi_arready = '1' then
      axi_rdata_reg <= bram_dout;   -- capture one cycle after ARVALID+ARREADY
      axi_rvalid    <= '1';
    elsif s_axi_rready = '1' then
      axi_rvalid    <= '0';
    end if;
  end if;
end process;
```

### Relevance to Your Project
Your design drives two AXI-Lite BRAM controllers at 0xA0000000 and 0xA0010000. If read-back PASS/FAIL is intermittently failing, check: (1) confirm the AXI BRAM Controller output register is enabled (not the BRAM primitive register), and (2) use the Vivado Timing Summary to verify the BRAM read-data path has a valid setup slack. A quick sanity check is adding a one-cycle read-data delay in main.c before sampling the result.

## Vivado Block Design / IP Integrator

### Key Findings
- **`write_bd_tcl` embeds tool version** — the generated script header checks the Vivado release and may refuse to run on a different version. Use the `-no_ip_version` flag (available in 2025.x) to strip IP version tags when sharing scripts across minor releases.
- **Custom IP repository must be present** before the block-design TCL script is sourced; if it is missing, the script fails silently at IP instantiation. Add `set_property ip_repo_paths` before `create_bd`.
- **`apply_bd_automation` is version-sensitive** — connection automation rules change between releases. In Vivado 2025.x the rules for `zynq_ultra_ps_e` S_AXI HP ports differ from 2024.x; always verify auto-connections in the address editor after running automation.
- **Address editor must be validated** after every IP addition. The most common issue is an overlapping address segment when adding a second BRAM controller (e.g. both at the default 64KB offset).
- **Regenerate output products after any IP parameter change** — stale output products are a silent error source; the Tcl command is `generate_target all [get_files *.bd]`.

### Code Example
```tcl
# create_bd.tcl snippet: safe IP repository + address assignment pattern
# (mirrors the structure expected in kv260_claude/kv260/tcl/create_bd.tcl)

set_property ip_repo_paths [list "$origin_dir/ip_repo"] [current_project]
update_ip_catalog -rebuild

create_bd_design "kv260_bd"

# Instantiate Zynq UltraScale+ PS
set ps [create_bd_cell -type ip -vlnv xilinx.com:ip:zynq_ultra_ps_e:3.5 zynq_ultra_ps_e_0]
apply_bd_automation -rule xilinx.com:bd_rule:zynq_ultra_ps_e \
  -config {apply_board_preset 1} [get_bd_cells $ps]

# Instantiate two BRAM controllers and memories
foreach {name offset} {bram_ctrl_0 0xA0000000 bram_ctrl_2 0xA0010000} {
  set ctrl [create_bd_cell -type ip -vlnv xilinx.com:ip:axi_bram_ctrl:4.1 $name]
  set_property CONFIG.DATA_WIDTH {32} [get_bd_cells $name]
}

# Validate and assign addresses (non-overlapping 64KB segments)
assign_bd_address [get_bd_addr_segs {bram_ctrl_0/S_AXI/Mem0}]
set_property offset 0xA0000000 [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_bram_ctrl_0_Mem0}]
set_property range  64K        [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_bram_ctrl_0_Mem0}]

assign_bd_address [get_bd_addr_segs {bram_ctrl_2/S_AXI/Mem0}]
set_property offset 0xA0010000 [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_bram_ctrl_2_Mem0}]
set_property range  64K        [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_bram_ctrl_2_Mem0}]

validate_bd_design
generate_target all [get_files *.bd]
```

### Relevance to Your Project
Your create_bd.tcl script defines the entire PS+BRAM block design. The address assignment pattern above ensures BRAM0 (0xA0000000) and BRAM2 (0xA0010000) are non-overlapping with explicit 64KB ranges — misaligned ranges are the #1 cause of "always reads 0" in bare-metal BRAM tests.

## Vivado TCL Scripting

### Key Findings
- **`write_bd_tcl` for version control** is the recommended approach (AMD UG994, 2025.2). Export the block design after every significant IP change so the `.tcl` script is the source of truth.
- **Version-drift is the main long-term hazard.** The generated script can fail silently across Vivado minor versions if IP VLNV versions change. Always test the script on a clean project after upgrades.
- **Non-project mode** (`open_checkpoint` / `write_checkpoint` flow) is faster for CI; it skips the project overhead. Use `synth_design -mode out_of_context` for IP synthesis, then `link_design` to assemble the full netlist.
- **Check IP status before running** — skip regeneration when IP is already up to date using:
  ```tcl
  if {[get_property NEEDS_REFRESH [get_ips]]} { upgrade_ip [get_ips] }
  ```
- **Variable-driven scripts** reduce version drift: set `set vivado_version [version -short]` at the top and use it in assertion guards.

### Code Example
```tcl
# Non-project batch build skeleton for kv260 AXI-BRAM demo
set origin_dir [file dirname [info script]]
set vivado_ver [version -short]

# Assert minimum tool version
if {[package vcompare $vivado_ver 2025.1] < 0} {
    puts "ERROR: Requires Vivado >= 2025.1, got $vivado_ver"
    exit 1
}

# Source the block design
source "$origin_dir/create_bd.tcl"

# Synthesize
synth_design -top kv260_top -part xck26-sfvc784-2LV-c

# Apply constraints
read_xdc "$origin_dir/../xdc/kv260_top.xdc"

# Implement and write bitstream
opt_design
place_design
route_design
write_bitstream -force "$origin_dir/../../output/kv260_top.bit"
write_hw_platform -fixed -include_bit -force "$origin_dir/../../output/kv260.xsa"
```

### Relevance to Your Project
Adding a batch TCL build script to your repo (alongside create_bd.tcl) enables headless CI builds of the kv260-axi-bram-demo bitstream. The `write_hw_platform` at the end produces the XSA that Vitis uses to generate the BSP for main.c.

## Vitis Bare-Metal / Standalone

### Key Findings
- **`xil_printf` has no `%f` support** — this is a known limitation in the Vitis standalone BSP (confirmed in 2025.1 Hackster project targeting KR260). Print floats as `(int)val` and `(int)((val - (int)val) * 1000)` for tenths.
- **UART selection is in `vitis-comp.json`** under `standalone_stdout` and `standalone_stdin`. For KV260/K26 the correct value is typically `psu_uart_1` (the FTDI-connected UART). Wrong UART = silent xil_printf with no error.
- **Missing `xil_printf.h` in scripted builds** — an AMD forum thread (2025.2) reports the include path is sometimes dropped when building a platform component via script. Workaround: explicitly add `${XILINX_VITIS}/data/embeddedsw/lib/bsp/standalone/src/common` to the BSP include path.
- **BSP regeneration after hardware change** — after re-exporting the XSA from Vivado, Vitis must regenerate the BSP (`vitis -s update_sw_design`). Missing this step causes old memory maps or missing peripheral drivers in the generated xparameters.h.
- **Linker script memory regions** — the default linker script places code + data in DDR starting at 0x0. For KV260 bare-metal, ensure the stack/heap sizes in the linker script are adequate (minimum 0x1000 for stack, 0x800 for heap in small demos).

### Code Example
```c
/* main.c pattern: AXI-Lite BRAM write/read-back with UART verification
 * Addresses match kv260-axi-bram-demo: BRAM0=0xA0000000, BRAM2=0xA0010000 */
#include "xil_printf.h"
#include "xil_io.h"

#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL
#define TEST_WORDS  4

static int bram_test(u32 base, const char *name) {
    u32 pattern[TEST_WORDS] = {0xDEADBEEF, 0xCAFEBABE, 0xA5A5A5A5, 0x12345678};
    int pass = 1;
    for (int i = 0; i < TEST_WORDS; i++)
        Xil_Out32(base + i * 4, pattern[i]);
    /* One-cycle barrier — issue a dummy read to flush the write buffer */
    (void)Xil_In32(base);
    for (int i = 0; i < TEST_WORDS; i++) {
        u32 rd = Xil_In32(base + i * 4);
        if (rd != pattern[i]) {
            xil_printf("%s[%d]: FAIL (wrote 0x%08X, read 0x%08X)\r\n",
                       name, i, pattern[i], rd);
            pass = 0;
        }
    }
    xil_printf("%s: %s\r\n", name, pass ? "PASS" : "FAIL");
    return pass;
}

int main(void) {
    xil_printf("\r\n--- KV260 AXI-BRAM Test ---\r\n");
    int ok = bram_test(BRAM0_BASE, "BRAM0") & bram_test(BRAM2_BASE, "BRAM2");
    xil_printf("Overall: %s\r\n", ok ? "PASS" : "FAIL");
    return ok ? 0 : 1;
}
```

### Relevance to Your Project
This pattern matches what main.c already does conceptually. The key addition is the **dummy read barrier** between writes and reads — without it, the Cortex-A53 write buffer can cause a read-before-write scenario on AXI-Lite, which is a common cause of `FAIL` on first-boot tests even when the hardware is correct.

## XDC Timing Constraints

### Key Findings
- **AXI-internal paths do not need manual XDC constraints** — the Zynq UltraScale+ PS-PL interface constraints are generated automatically from the block design. Only board-level I/O ports (LEDs, buttons, external connectors) need manual `set_input_delay` / `set_output_delay`.
- **Unconstrained board I/O ports** cause high-severity DRC warnings in implementation. Even if they don't affect timing, they must be constrained or explicitly waived (`set_false_path`).
- **`create_clock` must precede all I/O delay constraints** — Vivado's constraint application order matters; place clock definitions at the top of the XDC.
- **Clock groups for PS-PL clock isolation** — if you add a second fabric clock (e.g., for AXI-Stream at a different rate), use `set_clock_groups -asynchronous` to prevent the timing engine from creating spurious cross-domain paths.
- **`set_output_delay` syntax for UltraScale+** requires separate max and min values for hold/setup analysis:
  ```
  set_output_delay -clock <clk> -max 2.0 [get_ports <port>]
  set_output_delay -clock <clk> -min -1.0 [get_ports <port>]
  ```

### Code Example
```tcl
# kv260_top.xdc - minimal constraint set for KV260 AXI-BRAM demo
# PS fabric clock is auto-constrained by the block design; only add board I/O here.

# --- Board-level output: status LED on KV260 carrier (example pin) ---
# Adjust the pin assignment to match your KV260 XDC pin table
set_property PACKAGE_PIN B11      [get_ports led_o]
set_property IOSTANDARD  LVCMOS33 [get_ports led_o]

# Constrain relative to the PL fabric clock (generated by PS, ~100 MHz)
# Use set_false_path if led_o is purely async (driven by software-written register)
set_false_path -to [get_ports led_o]

# --- Clock groups: isolate PS-generated clocks from each other ---
# Required if you add a second PL clock (e.g., AXI-Stream at 200 MHz)
# set_clock_groups -asynchronous \
#   -group [get_clocks -of_objects [get_nets clk_100mhz]] \
#   -group [get_clocks -of_objects [get_nets clk_200mhz]]

# --- Waive unconstrained I/O DRCs (if no board-level I/O is used) ---
# set_false_path -from [get_ports *]
# set_false_path -to   [get_ports *]
```

### Relevance to Your Project
Your kv260 demo's only board-level output is USB-UART (routed through the PS MIO, not the PL fabric, so it needs no PL XDC constraint). If you add PL-side debug outputs (e.g., logic-analyzer probe points), apply `set_false_path` to each to silence DRC warnings without affecting timing closure.

## Kria KV260 / K26 SoM

### Key Findings
- **Boot firmware ≥ 01.06 required** (UG1089 v1.4, June 2025): older firmware has a bug where a reboot can fail to re-enable the PS power domain. Update via SD-card or JTAG before debugging intermittent boot failures.
- **PL power domain is independently controlled** via MIO33 (PL_PWR_EN). Bare-metal code or the FSBL can inadvertently disable the PL power domain; ensure the FSBL does not call `XPm_RequestDevice(PM_DEV_PLD_0)` without a matching release.
- **QSPI primary, SD secondary boot** — the KV260 first-stage boot loads from QSPI, then hands off to U-Boot on SD. For bare-metal JTAG debugging, ensure Vivado Hardware Manager loads the bitstream _after_ the PS is initialized (i.e., after FSBL runs or JTAG PS init script completes).
- **MIO-routed peripherals** include SD card, GbE, and UART; EMIO is used for I2C0. For a bare-metal demo using only AXI-Lite, MIO33 (PL power) and the UART MIO are the only MIO concerns.
- **Custom SOM platform tutorial** (AMD XD101, 2025.1) recommends starting from the K26 board file, which has the authoritative MIO configuration. Do not manually re-enter MIO settings in the PS IP GUI — import from the board preset.

### Code Example
```tcl
# Tcl snippet: apply K26 board preset to PS in block design
# This sets MIO correctly for KV260 (UART, SD, GbE, I2C)
set ps [get_bd_cells zynq_ultra_ps_e_0]
apply_bd_automation -rule xilinx.com:bd_rule:zynq_ultra_ps_e \
    -config {apply_board_preset "1"} $ps

# Verify that UART1 is enabled after preset
get_property CONFIG.PSU__UART1__PERIPHERAL__ENABLE [get_bd_cells $ps]
# Expected: 1

# Verify PL fabric clock is enabled (required for AXI-Lite masters)
get_property CONFIG.PSU__CRL_APB__PL0_REF_CTRL__FREQMHZ [get_bd_cells $ps]
# Expected: 100 (or your target frequency)
```

### Relevance to Your Project
The apply_board_preset step is the single most important guard against MIO misconfiguration. If UART output is absent on a fresh build, verify this setting first — a missing preset leaves UART1 disabled and xil_printf silently does nothing.

## AMD/Xilinx Tool Updates (Vivado/Vitis 2025.x)

### Key Findings
- **Vivado 2025.1 released May 29, 2025; Update 1 (2025.1.1) released September 17, 2025.** UG973 covers installation, licensing, and known issues.
- **Vitis 2025.1 ships a new Vitis Server backend** — a persistent daemon that replaces per-invocation tool startups. Build times improve for iterative flows; bare-metal and embedded flows benefit most.
- **XSA export split for extensible platforms** (2025.2): fixed XSA for the static region and extensible XSA for the dynamic region. Bare-metal bare-board projects use only the fixed XSA and are unaffected, but be aware if you later add PR regions.
- **`write_hw_platform` with `-fixed` and `-include_bit`** is the 2025.x recommended command for generating the XSA from a completed implementation. Earlier syntax (`write_hwdef`) is deprecated.
- **Vitis AI 5.0** ships with 2025.1 compatibility, adds ONNX runtime support, and adds Versal AI Edge VEK280 early access. Not directly applicable to KV260 bare-metal, but relevant if the project evolves to add ML inference.
- **Known issue: missing `xil_printf.h` include path** in scripted platform builds (AMD forum, 2025.2). Workaround: add standalone BSP source path explicitly in `vitis-comp.json`.

### Code Example
```tcl
# 2025.x recommended XSA export after implementation
# Run from Vivado Tcl console after route_design completes

write_hw_platform \
    -fixed \
    -include_bit \
    -force \
    [file normalize "$origin_dir/../../output/kv260_2025.xsa"]

# Verify the XSA was written
if {![file exists "$origin_dir/../../output/kv260_2025.xsa"]} {
    error "XSA export failed — check implementation status"
}
puts "XSA written successfully: kv260_2025.xsa"
```

### Relevance to Your Project
After upgrading from an earlier Vivado to 2025.1, re-export the XSA using `write_hw_platform -fixed -include_bit`. Re-open the Vitis workspace and update the platform component — stale XSAs are the #1 cause of "application builds but UART is silent" after a tool upgrade.
