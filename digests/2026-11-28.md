# FPGA Research Digest - 2026-11-28

## Executive Summary
- **AXI-Lite formal hazard**: Vivado's auto-generated AXI-Lite slave core contains protocol violations caught by formal property checking — specifically around VALID not being cleared after reset and read-channel stalls when RREADY is deasserted. For the KV260 AXI-BRAM demo, manually verify the BRAM controller handshake behavior or use ZipCPU's formal properties.
- **XSCT BSP deprecated in 2025.1**: AMD marked all Kria XSCT BSPs as deprecated; the System Device Tree (SDT) flow is now recommended for new bare-metal projects. Existing XSCT-based projects still work but won't receive updates.
- **Address Editor overlap pitfall**: Vivado's Run Connection Automation can assign overlapping AXI address segments when multiple ports share similar ranges; fix by manually unassigning conflicting segments and setting non-overlapping offsets in the Address Editor.
- **Non-project TCL and `write_bd_tcl`**: For scripted/CI builds, `write_bd_tcl -no_ip_version` generates a portable block design script using the latest IP versions — but regenerate it in the same Vivado release you intend to build with to avoid IP version mismatches.
- **VHDL 2019 in Vivado 2025.1**: Simulation now supports VHDL 2019 constructs (conditional expressions, conditional return, mode views), useful for modernizing VHDL testbenches and interface descriptions in the KV260 project.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings
- **Vivado-generated AXI-Lite slave has formal violations**: ZipCPU ran formal property checks against Xilinx's Vivado-generated AXI-Lite slave core and found multiple specification errors, including incorrect VALID/READY sequencing and missing post-reset clearing of VALID signals.
- **RREADY stall bug pattern**: A common BRAM-based AXI controller bug accepts new read requests while a prior read response is still stalled (RREADY deasserted). The AXI spec prohibits a slave from waiting for a master's RREADY before asserting RVALID, but it also requires that once RVALID is high it must stay high until the handshake completes.
- **Reset rule**: After any reset, all xVALID signals (AWVALID, WVALID, ARVALID, RVALID, BVALID) must be deasserted on the cycle the reset releases.
- **AXI-Stream FWFT-only on Xilinx FIFOs**: The XPM_FIFO_AXIS macro operates exclusively in First-Word Fall-Through mode; data is visible on the output without asserting a read enable, which affects AXI-Stream consumer logic design.
- **TKEEP semantics**: Each TKEEP bit corresponds to one byte of TDATA. Bytes with TKEEP=0 are null bytes and may be dropped; for a 32-bit data bus that is always full words (as in BRAM writes), set all TKEEP bits high.
- **AXI-Lite vs. AXI4 for BRAM**: AXI-Lite is appropriate for BRAM register-style access (no bursts, fixed 32/64-bit transfers), which matches the KV260 project's pattern-write/readback use case.

### Code Example
```vhdl
-- AXI-Lite slave: correct post-reset VALID clearing
process(S_AXI_ACLK)
begin
  if rising_edge(S_AXI_ACLK) then
    if S_AXI_ARESETN = '0' then
      axi_rvalid <= '0';   -- must deassert on reset
      axi_bvalid <= '0';
      axi_awready <= '0';
      axi_wready  <= '0';
      axi_arready <= '0';
    else
      -- normal handshake logic follows
      if (axi_arready = '0' and S_AXI_ARVALID = '1') then
        axi_arready <= '1';
      else
        axi_arready <= '0';
      end if;
    end if;
  end if;
end process;
```

### Relevance to Your Project
Your `kv260-axi-bram-demo` uses two AXI-Lite BRAM controllers at 0xA0000000 and 0xA0010000. The read-channel stall pattern is the most likely silent failure mode: if the Cortex-A53 CPU does not assert RREADY quickly enough between back-to-back reads, a naive controller can accept a second ARVALID while the first response is still pending. Use ILA or formal tools to verify correct RVALID/RREADY handshake behavior across both BRAM0 and BRAM2.

## Vivado Block Design / IP Integrator

### Key Findings
- **Address Editor is master-only**: The Address Editor tab only appears in IP Integrator when the design includes at least one AXI bus master (e.g., the Zynq PS or an AXI Interconnect master port).
- **Automation overlap bug**: When Run Connection Automation wires up multiple slaves to the same interconnect, it can assign overlapping offset addresses. The fix is to open the Address Editor, right-click the conflicting segment, choose "Unassign," then manually set a non-overlapping offset and range.
- **Interconnect re-customization**: Adding a master port to AXI Interconnect requires re-customizing the IP; Vivado automatically adds the needed clock and reset pins afterward.
- **External port addressing**: If an AXI interconnect port is exposed as an external interface (made external), the Address Editor becomes available to assign memory-map segments to external slaves, useful for custom PL peripherals.
- **IP outside the BD**: AXI IP instantiated outside the block design can still be memory-mapped; UG994 documents the interfacing pattern using `assign_bd_address` Tcl commands.
- **2025.2 UG994/UG995 available**: AMD updated both user guides to 2025.2; check these before the older versions for current BD workflows.

### Code Example
```tcl
# Fix overlapping address segments in Tcl
# After automation assigns a conflicting range:
assign_bd_address -offset 0xA0000000 -range 0x10000 \
  [get_bd_addr_segs {axi_bram_ctrl_0/S_AXI/Mem0}]
assign_bd_address -offset 0xA0010000 -range 0x10000 \
  [get_bd_addr_segs {axi_bram_ctrl_1/S_AXI/Mem0}]
```

### Relevance to Your Project
BRAM0 (0xA0000000) and BRAM2 (0xA0010000) are separated by exactly 64 KB. If you ever re-run Connection Automation after modifying the design, check the Address Editor immediately afterward — automation commonly assigns both controllers to overlapping ranges starting at 0xA0000000. The Tcl snippet above re-pins both segments after automation runs.

## Vivado TCL Scripting

### Key Findings
- **Non-project mode**: Vivado runs a non-project flow entirely from Tcl; it creates an in-memory project with no saved `.xpr` file, and all design state must be preserved via `write_checkpoint`. Reports must be generated explicitly with `report_timing_summary`, `report_utilization`, etc.
- **BD in non-project mode**: Use `create_bd_design` to start a block design in non-project mode. The BD can be populated from a `write_bd_tcl`-generated script that is then `source`d.
- **`write_bd_tcl -no_ip_version`**: This flag omits version pinning for each IP, so the script uses the latest IP version available in the target Vivado release. Recommended for CI environments where the tool version changes over time.
- **BRAM instantiation keyword**: In a generated BD script, Block Memory Generator is instantiated as `xilinx.com:ip:blk_mem_gen:8.4` (version may vary); use `create_bd_cell -type ip -vlnv xilinx.com:ip:blk_mem_gen` with `-no_ip_version` to stay version-agnostic.
- **Version mismatch caution**: AMD explicitly states that a BD Tcl script generated in one release should be rebuilt with `write_bd_tcl` in the target release, not ported directly.

### Code Example
```tcl
# Non-project mode: full batch flow skeleton
# Launch: vivado -mode batch -source build.tcl

# 1. Create in-memory design
create_project -in_memory -part xck26-sfvc784-2LV-c

# 2. Source BD script (generated by write_bd_tcl)
source ./tcl/create_bd.tcl
make_wrapper -files [get_files kv260_design.bd] -top
add_files -norecurse ./kv260_design/kv260_design.gen/sources_1/bd/kv260_design/hdl/kv260_design_wrapper.v

# 3. Add constraints
add_files -fileset constrs_1 ./xdc/kv260_top.xdc

# 4. Synthesize and implement
launch_runs synth_1 -jobs 4
wait_on_run synth_1
launch_runs impl_1 -to_step write_bitstream -jobs 4
wait_on_run impl_1

# 5. Save checkpoint and report
open_run impl_1
report_timing_summary -file timing_summary.rpt
write_checkpoint -force ./checkpoints/impl_final.dcp
```

### Relevance to Your Project
Your `create_bd.tcl` script drives the block design. If you move to Vivado 2025.2 or later, regenerate it with `write_bd_tcl -force -no_ip_version ./tcl/create_bd.tcl` from within Vivado 2025.2 to pick up updated AXI BRAM Controller IP without version-string churn in the diff.

## Vitis Bare-Metal / Standalone

### Key Findings
- **XSCT BSP deprecated in 2025.1**: AMD's 2025.1 open-source release notes explicitly list all Kria XSCT-based Board Support Packages as deprecated. Existing projects continue to function; the SDT (System Device Tree) flow is recommended for new bare-metal work.
- **SDT flow**: The System Device Tree-based BSP flow generates BSP libraries and drivers from the hardware platform's device tree, replacing the legacy `hsi` commands. For the KV260, this means using the platform XPFM rather than a manual XSCT BSP.
- **`xil_printf` still available**: It remains part of the standalone BSP's lightweight I/O library in both XSCT and SDT flows. It is a reduced-footprint alternative to `printf` with no floating-point support, appropriate for bare-metal UART debug on Cortex-A53.
- **Standalone BSP libraries for Zynq UltraScale+**: The BSP provides `xgpiops`, `xuartps`, `xscugic` (GIC interrupt controller), `xspips`, `xiicps`, and AXI peripheral access via memory-mapped I/O macros (`Xil_Out32`, `Xil_In32`).
- **Linker script pitfall**: The default linker script places `.text` in DDR. For the KV260, DDR starts at 0x00000000; ensure your BRAM peripheral addresses (0xA0000000 and above) are not placed in a memory region that overlaps with peripheral space in the linker script.

### Code Example
```c
#include "xil_printf.h"
#include "xil_io.h"

#define BRAM0_BASE  0xA0000000UL
#define BRAM1_BASE  0xA0010000UL
#define TEST_PATTERN 0xDEADBEEFUL

int main(void) {
    u32 readback;

    xil_printf("KV260 AXI-BRAM test start\r\n");

    /* Write pattern to BRAM0 offset 0 */
    Xil_Out32(BRAM0_BASE, TEST_PATTERN);

    /* Read back */
    readback = Xil_In32(BRAM0_BASE);
    if (readback == TEST_PATTERN) {
        xil_printf("BRAM0 PASS: 0x%08X\r\n", readback);
    } else {
        xil_printf("BRAM0 FAIL: got 0x%08X\r\n", readback);
    }
    return 0;
}
```

### Relevance to Your Project
Your `main.c` likely uses `Xil_Out32`/`Xil_In32` for the pattern write/readback loop. The SDT migration path is non-trivial but worth planning: if you upgrade to Vitis 2025.2 or later, the XSCT BSP may cease receiving new driver fixes for the K26 SOM peripherals.

## XDC Timing Constraints

### Key Findings
- **Purpose of I/O delay constraints**: Vivado's timing engine sees only internal FPGA logic; `set_input_delay` and `set_output_delay` extend the timing model to cover the path from an external source/destination to the first/last register stage.
- **Clockless option (UG949)**: Vivado can automatically identify the sampling clock for each port without you naming it in the constraint — omitting the `-clock` flag lets the engine pair each port with the clocks it discovers. This simplifies constraint files for simple synchronous I/O.
- **Pure combinational I/O**: Paths that are entirely combinational (no register on the FPGA side) cannot use `set_input_delay`/`set_output_delay`; use `set_max_delay -datapath_only` or `set_min_delay` instead.
- **DDR I/O**: For dual-edge clocked I/O, use `-max` and `-min` on both `-clock_fall` and normal clock edges, combined with `-add_delay` to accumulate the two constraints.
- **Timing Constraints Wizard**: Available in Vivado's Constraints menu, it auto-recommends system-synchronous I/O delay values based on detected interfaces — useful for the KV260's GPIO or custom PL interfaces.
- **KV260 internal clocks**: For PS-to-PL AXI designs like this project, the main clock is generated inside the PS (`fclk_clk0`) and distributed to the PL, so no external clock I/O delay constraint is needed for the AXI interface itself — only for signals routed to the carrier card's external I/O pins.

### Code Example
```tcl
# XDC: Example constraints for KV260 AXI-BRAM demo
# PS FCLK does not need set_input_delay - it's internal

# If you expose a PL GPIO to the carrier card J2 header:
# Assume 2 ns board propagation delay, 100 MHz PL clock
set_input_delay  -clock [get_clocks pl_clk0] -max  3.0 [get_ports {pl_gpio_in[*]}]
set_input_delay  -clock [get_clocks pl_clk0] -min  1.0 [get_ports {pl_gpio_in[*]}]
set_output_delay -clock [get_clocks pl_clk0] -max  2.0 [get_ports {pl_gpio_out[*]}]
set_output_delay -clock [get_clocks pl_clk0] -min -1.0 [get_ports {pl_gpio_out[*]}]

# False path the JTAG/programming interface from timing
set_false_path -from [get_ports sys_rst_n]
```

### Relevance to Your Project
The KV260 AXI-BRAM demo's critical timing is entirely PS-to-PL internal; the AXI clock (`fclk_clk0`) is generated by the Zynq PS block. No I/O delay constraints are required for the BRAM read/write paths. Add constraints only if you later expose PL logic to external carrier card pins (PMODs, RPi header, etc.).

## Kria KV260 / K26 SoM

### Key Findings
- **MIO bank layout**: The K26 SoM uses three MIO banks; Bank 500 is reserved for SoM-internal peripherals (QSPI flash at MIO[5:0], SD/eMMC, I2C, SPI). Banks 501 and 502 are partially available to the carrier card design via the SOM240 connectors. EMIO routes PS GPIO through the PL to the SOM connectors.
- **Boot mode is fixed on the Starter Kit**: The KV260 Starter Kit boot firmware in QSPI flash is read-only. The board always boots Linux from QSPI. For bare-metal, you use Vitis/XSDB to load the ELF via JTAG after Linux boots, or you generate a custom BOOT.BIN that includes your bare-metal application as the first-stage payload.
- **No FSBL generation needed for JTAG**: For JTAG-based bare-metal debug, Vitis provisions the PS automatically before downloading the ELF. No separate FSBL or boot image is required.
- **SoM connector pinout**: The SOM240_1 and SOM240_2 connectors carry AXI-routable signals, power, and MIO/EMIO. The authoritative pinout is in the K26 SoM Data Sheet (DS987); always cross-reference before connecting carrier card I/O to the PL design.
- **Element14 community AXI node crash**: A community report notes the K26 SoM can crash while enabling an AXI node when Linux is running; for bare-metal, this doesn't apply, but it's a relevant data point if you later add a Linux + bare-metal hybrid flow.
- **PMU and MIO carrier configuration**: The Platform Management Unit (PMU) handles dynamic carrier card MIO configuration at runtime. For bare-metal, MIO configuration from the Zynq PS block in Vivado is authoritative.

### Code Example
```tcl
# Vivado BD Tcl: Configure Zynq PS for KV260 bare-metal
# (inside create_bd.tcl, after create_bd_cell for zynq_ultra_ps_e_0)
set_property -dict [list \
  CONFIG.PSU__FPGA_PL0_ENABLE {1} \
  CONFIG.PSU__CRL_APB__PL0_REF_CTRL__FREQMHZ {100} \
  CONFIG.PSU__USE__M_AXI_GP0 {1} \
  CONFIG.PSU__MAXIGP0__DATA_WIDTH {32} \
  CONFIG.PSU__UART0__PERIPHERAL__ENABLE {1} \
  CONFIG.PSU__UART0__PERIPHERAL__IO {MIO 18 .. 19} \
] [get_bd_cells zynq_ultra_ps_e_0]
```

### Relevance to Your Project
Your project uses `fclk_clk0` at 100 MHz for the AXI fabric and routes UART0 over MIO for the USB-UART pass-through. MIO 18/19 is the standard UART0 mapping for the KV260 Starter Kit. Confirm this against your Vivado PS block configuration to ensure xil_printf output reaches the correct physical UART.

## AMD/Xilinx Tool Updates (Vivado/Vitis 2025.x)

### Key Findings
- **Vivado 2025.1**: Added VHDL 2019 simulation constructs (conditional expressions, conditional return, mode views for interfaces). New production device support: Spartan UltraScale+ XCSU10P, XCSU25P, XCSU35P.
- **Vivado 2025.2**: Released late 2025 — now the latest stable release. Includes updated UG994 (IP Integrator) and UG903 (Timing Constraints) documentation. The 2026.1 engineering preview adds XPM_FIFO_AXIS_SV (SystemVerilog interface variant) and LogicCore xFFT/FIR Compiler updates.
- **Vitis 2025.1**: XSCT BSPs for Kria deprecated; SDT flow promoted. New AI Engine DSP library functions, CFLOAT MAC support, Vector IFFT float block. FIR Compiler v7.2 (AXI-Stream) updated.
- **Vitis 2025.2**: Released alongside Vivado 2025.2; release highlights available at AMD's Vitis What's New page.
- **Security advisory (2025-12-17)**: AMD advisory 000039030 — missing secure flag in Trusted Firmware-A (TF-A) affects software through 2025.1. For bare-metal (no TF-A), this does not apply directly; relevant only if you later add a secure-world component.
- **Partial reconfiguration known issues updated**: The DFX (Dynamic Function eXchange) guide for 2025.2 carries a fresh known-issues section; not directly relevant for static BRAM designs but worth checking before adding PR regions.
- **IP Upgrade limitation**: UG994 notes that selectively upgrading a subset of IP in a block design is unsupported; all IP in the BD must be upgraded together when moving to a new Vivado release.

### Code Example
```vhdl
-- VHDL 2019 feature: conditional expression (new in Vivado 2025.1 sim)
-- Useful in testbenches for the KV260 BRAM demo
library ieee;
use ieee.std_logic_1164.all;

entity tb_axi_bram is
end entity;

architecture sim of tb_axi_bram is
  signal clk   : std_logic := '0';
  signal resetn : std_logic;
begin
  clk <= not clk after 5 ns;  -- 100 MHz

  -- VHDL 2019 conditional expression (replaces ternary workaround)
  resetn <= '0' when now < 20 ns else '1';

  -- DUT instantiation would follow...
end architecture;
```

### Relevance to Your Project
If you upgrade from Vivado 2025.1 to 2025.2, regenerate your `create_bd.tcl` with `write_bd_tcl` immediately after opening the project in the new tool version. The "upgrade all IP together" requirement means you cannot upgrade just the AXI BRAM Controller without also upgrading the AXI Interconnect and Zynq PS IP in the same session.
