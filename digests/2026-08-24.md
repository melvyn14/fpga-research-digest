## Executive Summary
- **Address map matters more than you think.** The AXI BRAM Controller v4.x has
  a hard 64K-page granularity coming out of the block, and Vivado's Address
  Editor will silently round your `Range` to the nearest power of two. With
  BRAM0 at `0xA0000000` and BRAM2 at `0xA0010000` you have exactly 64 KiB
  headroom between them, so any Range > 64K on BRAM0 will overlap BRAM2 and
  the "read pattern back" phase will PASS accidentally (aliased writes).
  Force `Range = 64K` on both entries and re-`validate_bd_design`.
- **Regenerate the BSP after every address-map or IP change**, not just after a
  new bitstream. The `xparameters.h` constants (`XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR`,
  etc.) are what your `main.c` should actually reference — hard-coding
  `0xA0000000` in C works today and breaks the day you add a third BRAM and
  IP Integrator shuffles the base addresses.
- **PS-PL clock crossing is the #1 source of "works in sim, fails on board" on
  this design.** The AXI-Lite handshake is fully synchronous, but only if
  `M_AXI_HPM0_LPD` (or whichever PS master port you used) shares a common
  clock with the AXI BRAM Controller and BRAM Generator. In Vivado 2025.1
  IP Integrator, run **Run Connection Automation → Clock: /zynq_ultra_ps_e_0/pl_clk0**
  on every AXI interface — if one slave lands on a different `clk_wiz` domain
  you'll get metastable AWVALID/AWREADY and intermittent PASS/FAIL.
- **`xil_printf` + PSU_UART1 is the KV260 serial path.** The USB-UART bridge on
  the KV260 carrier card is wired to `psu_uart_1` (MIO 36/37), not
  `psu_uart_0`. In the standalone BSP settings, set both `stdin` and `stdout`
  to `psu_uart_1` at 115200-8N1; otherwise the "PASS/FAIL" line goes into the
  void.
- **Vivado 2025.2 landed with SystemVerilog interfaces in IPI and new SLR-crossing
  reports** — irrelevant to KV260 (single-die Zynq UltraScale+), but the
  parallel Vitis Unified 2025.2 release is what most tutorials are now
  targeting. Pin to 2025.1 across both tools (they must match); do not
  cherry-pick 2025.2 Vitis with a 2025.1 XSA.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings
- The AXI-Lite write channel has an under-appreciated split-handshake rule:
  AW and W are independent, and the slave must not issue BVALID until *both*
  AW and W have handshaked. A common shortcut in home-brew slaves is to gate
  AWREADY on `AWVALID && WVALID` to synchronize the channels; it works but
  couples backpressure across channels and can throttle bursty masters.
  ([zipcpu.com — easy AXI-Lite slave](https://zipcpu.com/blog/2020/03/08/easyaxil.html))
- Formal verification of Vivado's own auto-generated AXI-Lite slave template
  has historically exposed several protocol bugs (BVALID/RVALID timing,
  RRESP ordering under back-to-back reads). If you templated your own slave
  from the "Create and Package IP" wizard, spot-check against the AXI
  handshake rules rather than trusting it. ([zipcpu.com — most common AXI mistake](https://zipcpu.com/formal/2019/04/16/axi-mistakes.html))
- For AXI-Stream: **TVALID must not depend on TREADY, but TREADY may depend on
  TVALID** — violating this creates a combinational loop across the handshake
  and will show up as timing failures on the `s_axis_tvalid → m_axis_tready`
  path. The other classic bug is deasserting TLAST while stalled on
  backpressure; Xilinx's own template code has been shown to do this on the
  penultimate beat. ([zipcpu.com — AXI handshaking rules](https://zipcpu.com/blog/2021/08/28/axi-rules.html), [zipcpu.com — AXI-Stream is broken](https://zipcpu.com/blog/2022/02/23/axis-abort.html))
- The AXI BRAM Controller is a well-tested endpoint slave and generally not
  where the bug is. If you see mis-reads on this design, suspect address-map
  overlap (see Executive Summary) before you suspect the controller.

### Code Example (VHDL — minimum-safe AXI-Lite slave read/write skeleton)
```vhdl
-- Simplified AXI-Lite write handshake: AWREADY held until both AW and W valid,
-- BVALID raised for one cycle after AW+W accepted. This is the "coupled" style
-- and is safe for the KV260 PS → single-slave path in this project.
process(aclk)
begin
    if rising_edge(aclk) then
        if aresetn = '0' then
            awready <= '0'; wready <= '0'; bvalid <= '0';
        else
            -- accept AW and W together
            if awready = '0' and wready = '0'
               and s_axi_awvalid = '1' and s_axi_wvalid = '1'
               and bvalid = '0' then
                awready <= '1';
                wready  <= '1';
                -- latch address / data here
            else
                awready <= '0';
                wready  <= '0';
            end if;

            -- respond
            if awready = '1' and wready = '1' then
                bvalid <= '1';
                bresp  <= "00";  -- OKAY
            elsif bvalid = '1' and s_axi_bready = '1' then
                bvalid <= '0';
            end if;
        end if;
    end if;
end process;
```

### Relevance to Your Project
Your design uses two stock **AXI BRAM Controller** IPs, so you are not writing
an AXI-Lite slave — but the PS-PL clocking rules above still apply verbatim
to the AXI-Lite path between `zynq_ultra_ps_e_0/M_AXI_HPM0_LPD` and each BRAM
controller. If your VHDL top wraps or bridges any of that path (rather than
letting IPI drop it in), the coupled-handshake pattern above is the safe
default. If you later add an AXI-Stream producer (e.g., a pattern generator
DMAing into BRAM), remember the TVALID/TREADY dependency direction and TLAST
rule the first time around; it is much cheaper than debugging it on-chip.

## Vivado Block Design / IP Integrator

### Key Findings
- **Run Connection Automation → All Automation** is the fast path for the
  Zynq PS + AXI BRAM Controller pattern: it wires the PS clock/reset,
  instantiates the AXI Interconnect (or SmartConnect in 2025.x defaults),
  connects `BRAM_PORTA`/`BRAM_PORTB` to a Block Memory Generator, and assigns
  addresses. Check the "All Automation" box explicitly — the default only
  connects the interface you highlighted.
  ([AMD UG994 — IP Integrator](https://docs.amd.com/r/2025.1-English/ug994-vivado-ip-subsystems/Using-IP-Integrator-in-Non-Project-Mode),
   [realdigital — Preparing a hardware design for Zynq](https://realdigital.org/doc/bb16275c20b8e11242bf729bba1439a3))
- **Address Editor** in 2025.x auto-assigns on `assign_bd_address`, but you can
  and should pin the base and range manually for a stable ABI:
  `assign_bd_address -offset 0xA000_0000 -range 64K [get_bd_addr_segs axi_bram_ctrl_0/S_AXI/Mem0]`.
  Once pinned, `validate_bd_design` will flag any overlap on regeneration.
  ([AMD UG1711 — Memory-Mapping in the Address Editor](https://docs.amd.com/r/en-US/ug1711-microblaze-v-embedded-design/Memory-Mapping-in-the-Address-Editor))
- **Regeneration tip:** after any IP catalog update, run
  `report_ip_status -name ip_status` and then `upgrade_ip [get_ips]`. In
  2025.1 the AXI SmartConnect and BRAM Controller both had minor version
  bumps; a stale locked IP is a common cause of "block design won't validate."
- Prefer **SmartConnect** over the older AXI Interconnect for anything above
  a single master/slave — it's what IPI 2025.x autogenerates and it has
  cleaner clock-domain-crossing behavior between the PS HPM ports and PL.

### Code Example (TCL — safe address pinning for this project)
```tcl
# Pin BRAM address map so Range never silently expands past the neighbour.
assign_bd_address -offset 0xA000_0000 -range 64K \
    [get_bd_addr_segs {axi_bram_ctrl_0/S_AXI/Mem0}]
assign_bd_address -offset 0xA001_0000 -range 64K \
    [get_bd_addr_segs {axi_bram_ctrl_2/S_AXI/Mem0}]

# Force clock automation on every AXI slave — catches the "one BRAM landed on
# clk_wiz_0/clk_out2" bug at design time, not on the board.
apply_bd_automation -rule xilinx.com:bd_rule:axi4 \
    -config { Clk_master {/zynq_ultra_ps_e_0/pl_clk0 (100 MHz)} \
              Clk_slave  {/zynq_ultra_ps_e_0/pl_clk0 (100 MHz)} \
              Clk_xbar   {/zynq_ultra_ps_e_0/pl_clk0 (100 MHz)} \
              Master {/zynq_ultra_ps_e_0/M_AXI_HPM0_LPD} \
              Slave  {/axi_bram_ctrl_0/S_AXI} \
              ddr_seg {Auto} intc_ip {New AXI SmartConnect} } \
    [get_bd_intf_pins axi_bram_ctrl_0/S_AXI]

validate_bd_design
save_bd_design
```

### Relevance to Your Project
Two AXI BRAM Controllers 64 KiB apart is exactly the layout where a stray
`Range=1M` default silently aliases writes to BRAM0 back into BRAM2's window.
Pin both `-range 64K` in `create_bd.tcl` and add a `validate_bd_design`
at the end of the script — that alone rules out a whole class of "the second
BRAM PASSes even when I unplug the wire" bugs.

## Vivado TCL Scripting

### Key Findings
- `vivado -mode batch -source create_bd.tcl -journal /tmp/vv.jou -log /tmp/vv.log`
  is the reproducible entry point; keep the `.jou` and `.log` per-run so a CI
  or clean-checkout regeneration is auditable. In non-project mode you are
  fully responsible for `read_vhdl`, `read_xdc`, `synth_design`,
  `opt_design`, `place_design`, `route_design`, `write_bitstream` in order —
  Vivado does nothing implicitly. ([AMD UG892 — Batch TCL script](https://docs.amd.com/r/en-US/ug892-vivado-design-flows-overview/Launching-the-Vivado-Tools-Using-a-Batch-Tcl-Script))
- Prefer **project-mode with a TCL bootstrap** for a two-BRAM demo like this:
  `create_project`, `set_property board_part xilinx.com:kv260_som:...`,
  `source create_bd.tcl`, `make_wrapper`, then `launch_runs`. Non-project mode
  is powerful but overkill until you're doing >1 M-cell synthesis or IP-level
  QoR sweeps.
- Wrap `source create_bd.tcl` with `if { [llength [get_bd_designs]] > 0 } { close_bd_design [current_bd_design] }`
  so the script is idempotent when re-run in the same Vivado session.
- Use `write_bd_tcl -force` after any GUI change to keep the checked-in
  `create_bd.tcl` in sync with the actual design; a diff on this file in git
  is the cleanest review artifact for a block-design change.

### Code Example (TCL — reproducible project bootstrap)
```tcl
# build.tcl — invoke with: vivado -mode batch -source build.tcl
set proj      kv260_bram_demo
set proj_dir  [file join [pwd] build $proj]
set board     xilinx.com:kv260_som:part0:1.4
set part      xck26-sfvc784-2LV-c

file mkdir $proj_dir
create_project -force $proj $proj_dir -part $part
set_property board_part $board [current_project]

# Sources
read_vhdl -library work [glob -nocomplain vhdl/*.vhd]
read_xdc  [glob -nocomplain xdc/*.xdc]

# Block design
source tcl/create_bd.tcl
regenerate_bd_layout
validate_bd_design
save_bd_design
make_wrapper -files [get_files *.bd] -top -import

# Runs
launch_runs synth_1 -jobs 8
wait_on_run synth_1
launch_runs impl_1 -to_step write_bitstream -jobs 8
wait_on_run impl_1

# Hand-off
write_hw_platform -fixed -include_bit -force \
    -file $proj_dir/${proj}.xsa
```

## Vitis Bare-Metal / Standalone

### Key Findings
- The **standalone BSP** is a single-threaded runtime giving you stdio, cache
  ops, GIC, timers, and drivers under
  `<Vitis>/data/embeddedsw/XilinxProcessorIPLib/drivers`. `xil_printf` is a
  reduced-footprint printf (no `%f`, no `%lld`) that talks straight to the
  UART configured as `stdout` in the BSP.
  ([AMD UG1137 — Bare-Metal Software Stack](https://docs.amd.com/r/2023.1-English/ug1137-zynq-ultrascale-mpsoc-swdev/Bare-Metal-Software-Stack),
   [AMD Wiki — Baremetal Drivers and Libraries](https://xilinx-wiki.atlassian.net/wiki/spaces/A/pages/18841745))
- **Vivado and Vitis versions must match exactly.** A 2025.1 XSA loaded into
  Vitis 2025.2 will "mostly work" but the BSP driver versions drift, and
  the interrupt-controller header layout changed between 2024.x and 2025.x.
  ([mobilestalk — Zynq UltraScale+ Hello World](https://mobilestalk.net/zynq-ultrascale-hello-world-in-vivado-and-vitis/))
- On Cortex-A53 the interrupt controller is `XScuGic`; you register with
  `XScuGic_Connect` / `XScuGic_Enable`, then arm the ARM exception vector via
  `Xil_ExceptionRegisterHandler(XIL_EXCEPTION_ID_IRQ_INT, ...)`.
  ([AMD Wiki — GIC Standalone driver](https://xilinx-wiki.atlassian.net/wiki/spaces/A/pages/18841749/GIC+Standalone+driver))
- The default `lscript.ld` puts `.text/.data/.bss/.heap/.stack` in DDR
  (`psu_ddr_0_MEM_0`). For a memory-check demo you rarely need to edit it,
  but do bump `_HEAP_SIZE`/`_STACK_SIZE` if you ever start dumping large
  buffers via `xil_printf` in a loop.

### Code Example (C — bare-metal BRAM PASS/FAIL over UART)
```c
#include "xparameters.h"
#include "xil_io.h"
#include "xil_printf.h"

/* Prefer BSP-provided base addresses over hardcoded literals — this keeps
 * main.c stable when the block design's address map changes. */
#ifndef BRAM0_BASE
#define BRAM0_BASE XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR   /* e.g. 0xA0000000 */
#endif
#ifndef BRAM2_BASE
#define BRAM2_BASE XPAR_AXI_BRAM_CTRL_2_S_AXI_BASEADDR   /* e.g. 0xA0010000 */
#endif
#define BRAM_WORDS 64u   /* 256 B — a walking test, not a fill of the whole 64K */

static int check_bram(const char *name, u32 base)
{
    for (u32 i = 0; i < BRAM_WORDS; ++i) {
        Xil_Out32(base + 4u * i, 0xA5A50000u ^ i);
    }
    /* Force the write to leave the store buffer before the read-back loop. */
    __asm__ volatile ("dsb sy" ::: "memory");

    for (u32 i = 0; i < BRAM_WORDS; ++i) {
        u32 got = Xil_In32(base + 4u * i);
        u32 exp = 0xA5A50000u ^ i;
        if (got != exp) {
            xil_printf("%s FAIL @0x%08x: exp=0x%08x got=0x%08x\r\n",
                       name, base + 4u * i, exp, got);
            return 1;
        }
    }
    xil_printf("%s PASS (base=0x%08x, words=%u)\r\n", name, base, BRAM_WORDS);
    return 0;
}

int main(void)
{
    xil_printf("\r\n=== KV260 AXI-BRAM demo ===\r\n");
    int fails = 0;
    fails += check_bram("BRAM0", BRAM0_BASE);
    fails += check_bram("BRAM2", BRAM2_BASE);
    xil_printf("=== %s ===\r\n", fails ? "OVERALL FAIL" : "OVERALL PASS");
    while (1) { ; }
    return 0;
}
```

### Relevance to Your Project
Two nits your current `main.c` is very likely doing that will bite:

1. **Missing DSB before read-back.** AXI-Lite writes from the A53 are
   posted through the store buffer; without a `dsb sy` (or a preceding
   `Xil_Out32` to a strongly-ordered region) a rapid write-then-read can be
   satisfied from the buffer, hiding a real BRAM fault. `Xil_Out32` itself
   does not insert a barrier.
2. **Hard-coded `0xA0000000` / `0xA0010000`.** Route them through
   `xparameters.h` (`XPAR_AXI_BRAM_CTRL_*_S_AXI_BASEADDR`) so the C stays
   correct after a block-design rename.

Also confirm in `platform.spr` (or the BSP settings JSON in Vitis Unified)
that both `stdin` and `stdout` are `psu_uart_1` — that is the USB-UART on
the KV260 carrier.
([k0nze — Zynq baremetal project setup](https://k0nze.dev/posts/zynq-baremetal-project-setup/),
 [Digilent — Getting Started with IPI](https://digilent.com/reference/programmable-logic/guides/getting-started-with-ipi))

## XDC Timing Constraints

### Key Findings
- `set_input_delay` / `set_output_delay` describe the *external* delay from
  the source-synchronous clock edge to the FPGA pin (input) or from the pin
  to the far-end capture edge (output). Both take `-clock`, `-max`/`-min`,
  and `-clock_fall` — the last is required for DDR interfaces.
  ([AMD UG835 — set_input_delay](https://docs.amd.com/r/2025.1-English/ug835-vivado-tcl-commands/set_input_delay),
   [AMD UG835 — set_output_delay](https://docs.amd.com/r/2025.1-English/ug835-vivado-tcl-commands/set_output_delay))
- For a Zynq PS-driven design like KV260, the **PS clock (`pl_clk0`) is auto-
  created** from the block design, but any PL clock from a `clk_wiz` must be
  told it is asynchronous to unrelated domains via `set_clock_groups
  -asynchronous`. Otherwise Vivado will (correctly, painfully) time paths
  between them that will never physically exist.
- `set_clock_groups`, `set_input_delay`, and `set_output_delay` are the three
  constraints that actually change QoR — everything else (waivers, false
  paths on reset trees, etc.) is cleanup. Get these right first.
  ([abbey1.org.uk — Boundary timing constraints](https://blog.abbey1.org.uk/index.php/technology/specifying-boundary-timing-constraints-in-vivado),
   [BLT — Demystifying I/O timing constraints](https://bltinc.com/2025/05/13/demystifying-i-o-timing-constraints/))
- For a purely internal PS→BRAM path, **you need no I/O timing constraints
  at all** — everything is inside the die. All you need is the PS-generated
  clock definition (already there) and, if you added a `clk_wiz`, a
  `set_clock_groups -asynchronous` between it and `pl_clk0`.

### Code Example (XDC — PS-PL clock hygiene for the KV260 demo)
```tcl
# The PS clock is created automatically by the block design — do NOT redefine
# it. Only declare async grouping for any *new* PL clocks you introduce.

# Example: if you add a clk_wiz to produce a 200 MHz clock for a future
# pattern generator, tell Vivado it is unrelated to pl_clk0.
set ps_clk  [get_clocks -of_objects [get_pins zynq_ultra_ps_e_0/pl_clk0]]
set pl_clk  [get_clocks -of_objects [get_pins clk_wiz_0/clk_out1]]
set_clock_groups -asynchronous -group $ps_clk -group $pl_clk

# If you ever bring a PL signal out to a header for scope probing, THAT is
# when you need output-delay — e.g. a debug LED toggled from a 100 MHz clock:
# create_clock -name probe_clk -period 10.0 [get_ports {probe_clk}]
# set_output_delay -clock probe_clk -max 2.0 [get_ports {debug_led}]
# set_output_delay -clock probe_clk -min 0.5 [get_ports {debug_led}]
```

### Relevance to Your Project
For the current PS→AXI-Lite→BRAM path there is no need to author I/O timing
constraints — the design lives entirely inside the ZU7EV. The only XDC line
you likely need is the LED (or GPIO) pin location, which comes from the
official K26 SOM XDC and can be `source`d rather than re-typed. Watch out if
you later add a PL-driven clock: `set_clock_groups -asynchronous` between
it and `pl_clk0` is almost always what you want, and skipping it produces
implausible failing paths that mask real ones.

## Kria KV260 / K26 SoM Platform Specifics

### Key Findings
- **Boot mode** on the KV260 starter kit is factory-set to **QSPI32** — the
  four MODE[3:0] pins are pulled to the value the carrier card wires them
  to. You do not change boot mode from software; if you need SD or JTAG
  boot for bring-up, you either use the debug jumpers on the carrier or
  attach through `xsct connect` and download the ELF over JTAG.
  ([AMD — Setting Boot-modes on Kria SOM](https://xilinx.github.io/kria-apps-docs/creating_applications/2022.1/build/html/docs/bootmodes.html))
- **USB-UART is `psu_uart_1` on MIO 36/37.** That's what the FT4232 on the
  KV260 carrier exposes at 115200 8N1. `psu_uart_0` is unrouted on the
  starter kit and picking it in the BSP produces a silent app.
- **I²C** to the SOM-side devices (fan controller, power sequencer, EEPROM) is
  on MIO bank 500. You almost never touch this from bare metal for a memory
  demo, but do note the fan is EMIO-mapped in the stock `k26-starter-kits`
  bitstream — if you overwrite the PL you also lose fan control, so run
  short sessions or add a trivial EMIO fan-tach forward yourself.
  ([AMD Wiki — Kria K26 SOM](https://xilinx-wiki.atlassian.net/wiki/spaces/A/pages/1641152513/Kria+K26+SOM))
- **Power domains:** the K26 uses the Zynq UltraScale+ FPD/LPD/PLD domain
  model. For a Cortex-A53 bare-metal app running out of DDR you don't need
  to touch domain state, but if you later want to bring the R5 up alongside
  the A53 (BRAM used as A53↔R5 shared mailbox is a natural next step) you
  will need PMU firmware present in the boot image.
- **Board files** for the KV260 auto-configure the PS with the correct MIO
  assignments, DDR params, and PL clock defaults. Use
  `set_property board_part xilinx.com:kv260_som:part0:1.4` at project
  creation and let the automation handle it — hand-writing the PS config is
  error-prone and rarely necessary.
  ([Kria KV260 build platform docs](https://xilinx.github.io/kria-apps-docs/kv260/2022.1/build/html/docs/build_vitis_platform.html),
   [Hackster — KV260 BIST tutorial with 2025.1](https://www.hackster.io/LogicTronix/kv260-bist-tutorial-recreating-with-vivado-vitis-2025-1-09f010))

### Code Example (TCL — KV260 board-part project bootstrap + XSA export)

```tcl
    -part xck26-sfvc784-2LV-c
set_property board_part xilinx.com:kv260_som:part0:1.4 [current_project]

```

### Relevance to Your Project
Three concrete things to check in your KV260 config:

1. `board_part` is set to `xilinx.com:kv260_som:part0:1.4` (or newer) so the
   PS block gets DDR + MIO 36/37 UART wired automatically.
2. Standalone BSP `stdout`/`stdin` both point at `psu_uart_1`.
3. If you're booting from SD/JTAG for bring-up, remember the starter kit
   ships QSPI32 — the fastest path is to download the FSBL + ELF via
   `xsdb`/`xsct` over JTAG rather than fighting boot-mode pins on the
   carrier.

## AMD/Xilinx Tool Updates (Vivado / Vitis 2025.x)

### Key Findings
- **Vivado 2025.2** shipped and its highlights are Versal-heavy (QoR, SLR
  crossing reports, NoC XPM support in BD, `SystemVerilog interface` support
  in IP Integrator). None of that changes the KV260 flow, but the parallel
  **Vitis 2025.2** release is what new tutorials target.
  ([AMD — Vivado What's New (2025.2)](https://www.amd.com/en/products/software/adaptive-socs-and-fpgas/vivado/vivado-whats-new.html))
- **Version discipline still matters.** Vitis and Vivado must be the same
  release. Vitis 2025.2 opening a Vivado 2025.1 XSA is a common cause of
  the "BSP regenerates but xparameters is missing your IP" symptom. The
  release notes (UG973 / UG1742) explicitly call this out.
  ([AMD UG1742 — Vitis release notes](https://docs.amd.com/r/en-US/ug1742-vitis-release-notes))
- **Known-issues page** for the 2026.x series is worth a scroll if you decide
  to upgrade off 2025.1 — several BSP driver regressions on Zynq UltraScale+
  have been logged there in the past.
  ([AMD Support — Vitis 2026.x known issues](https://adaptivesupport.amd.com/s/article/000040220))
- **AXI BRAM Controller v4.x** got a minor bump in 2025.x; if your
  `create_bd.tcl` was generated on 2024.x, run `upgrade_ip [get_ips]` after
  first open to avoid the "locked IP" refusal in `validate_bd_design`.
- **`write_hw_platform`** replaces the older `write_hwdef`/`export_hw`
  flows — this is the canonical XSA export path in 2025.x, and it now
  supports `-fixed` (traditional embedded flow) and `-hw` (extensible)
  variants explicitly.
  ([Vitis 2025.1 platform creation tutorials](https://docs.amd.com/r/en-US/Vitis-Tutorials-Vitis-Platform-Creation/Hardware-Design-Fast-Iteration-with-Vitis-Export-to-Vivado))

### Code Example (Bash — pinning tool version + one-shot rebuild)
```bash
#!/usr/bin/env bash
set -euo pipefail

# Pin the toolchain — same version for Vivado and Vitis.
export XILINX_VERSION=2025.1
source /tools/Xilinx/Vivado/${XILINX_VERSION}/settings64.sh
source /tools/Xilinx/Vitis/${XILINX_VERSION}/settings64.sh

# 1. Vivado: build XSA
vivado -mode batch -source tcl/build.tcl \
       -journal build/vivado.jou -log build/vivado.log

# 2. Vitis: build ELF using the fresh XSA
XSA=$(readlink -f build/kv260_bram_demo/kv260_bram_demo.xsa)
xsct tcl/vitis_build.tcl "$XSA" build/vitis
```

### Relevance to Your Project
Since your stack is fixed at Vivado 2025.1 + Vitis 2025.1, the practical
advice is: **stay there** for the life of this demo. Upgrading a single-BRAM
tutorial project to 2025.2 mid-stream buys you nothing (no Versal, no NoC,
no SV-interface plumbing needed) and costs you a BSP regeneration and at
least one round of IP `upgrade_ip`. When you *do* upgrade — e.g. to pick up
Vitis Unified 2026.x improvements — do it as a coordinated bump on a
branch, regenerate the XSA in the new Vivado first, then re-import into the
matching Vitis, then diff `xparameters.h`.
