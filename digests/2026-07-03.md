# FPGA Research Digest - 2026-07-03

## Executive Summary

- **AXI-Lite VALID/READY rule**: Once VALID is asserted by the initiator, it must stay asserted until the corresponding READY is received — deasserting VALID early violates the AXI spec and causes silent data loss or protocol lockups in the BRAM controller.
- **Vivado 2025.1 AXI full peripheral address space bug**: A Digilent forum report confirms a regression where AXI full peripherals appear limited to a 1 KB usable address space — relevant to your BRAM0 (0xA0000000) and BRAM2 (0xA0010000) mappings if you upgrade tools.
- **BIST tutorial for KV260 in 2025.1**: A Hackster.io guide reconstructs the KV260 BIST firmware entirely in Vivado/Vitis 2025.1, providing a reference flow that closely mirrors your AXI-BRAM demo.
- **New `run_connection_automation` pitfall**: Clock source for every AXI slave port must be explicitly confirmed after running connection automation — the tool occasionally assigns a mismatched clock, silently producing a non-functional design.
- **Dynamic PL boot in 2025.1**: Vivado 2025.1 enables PS-first boot with PL loaded dynamically, a significant change from the classic simultaneous PS+PL boot — relevant if you plan to deploy via QSPI rather than JTAG.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- **VALID cannot be deasserted early**: Once a master asserts AWVALID, WVALID, or ARVALID, it must hold that signal high until the corresponding READY is received. Deasserting prematurely is an AXI spec violation and will cause hangs or data corruption in the BRAM controller.
- **AXI-Lite is register/control, AXI-Stream is data**: AXI4-Lite is a single-transfer, no-burst, memory-mapped bus ideal for GPIO, UART, and BRAM register access from the PS. AXI4-Stream is unidirectional, address-free, and designed for high-throughput data pipelines (video, DSP).
- **AXI BRAM Controller v4.1**: The Xilinx AXI BRAM Controller IP (PG078) connects a Block Memory Generator to the AXI interconnect as an endpoint slave. Supports both Single-Port and True Dual-Port modes. Performance figures are taken from Out-of-Context implementation in each Vivado release.
- **ZipCPU VHDL AXI-Lite analysis**: Dan Gisselquist's blog documents specific errors in Xilinx's reference AXI-Lite VHDL designs (extra clock latency on responses, incorrect stall logic). His corrected demo (`demoaxilite.vhd`) is widely cited as a cleaner baseline for custom AXI-Lite slaves.
- **AXI VIP timing issues**: AXI4 VIP misconfiguration (wrong address/data widths, wrong burst type) is the primary cause of VIP stimulus not behaving as expected during simulation. The VIP will appear to accept transactions but respond incorrectly.

### Code Example

```vhdl
-- Minimal AXI-Lite write-channel handshake (slave side)
-- Key: hold AWREADY/WREADY low until both AWVALID and WVALID are seen
process(S_AXI_ACLK)
begin
  if rising_edge(S_AXI_ACLK) then
    if S_AXI_ARESETN = '0' then
      aw_en    <= '1';
      axi_awready <= '0';
    else
      if (axi_awready = '0' and S_AXI_AWVALID = '1' and
          S_AXI_WVALID = '1' and aw_en = '1') then
        axi_awready <= '1';
        aw_en       <= '0';
      elsif (S_AXI_BREADY = '1' and axi_bvalid = '1') then
        aw_en       <= '1';
        axi_awready <= '0';
      else
        axi_awready <= '0';
      end if;
    end if;
  end if;
end process;
```

### Relevance to Your Project

Your two BRAM controllers (at 0xA0000000 and 0xA0010000) use AXI-Lite. The `main.c` write-pattern/read-back loop relies entirely on correct VALID/READY handshaking. If the BRAM controller's `AWREADY` ever fails to deassert between transactions, the AXI interconnect can see a spurious second write — producing a FAIL in your PASS/FAIL check even when the hardware is otherwise correct. Verifying handshaking with ILA is recommended before concluding a FAIL is a logic bug.

## Vivado Block Design / IP Integrator

### Key Findings

- **`run_connection_automation` clock pitfall**: After running connection automation, inspect the clock connection for every S_AXI slave port. The tool can assign the wrong clock source (e.g., a PL clock instead of the PS `pl_clk0`). Set each to `Auto` or the explicit PS clock output.
- **Export Block Design → TCL**: Use `File → Export → Export Block Design` (or `write_bd_tcl`) to produce a portable TCL script that recreates your entire block design. This is the recommended version-control strategy for BD projects.
- **ILA for AXI debugging**: Insert an AXI Protocol Checker or ILA debug core on the AXI bus directly in IP Integrator (right-click a net → Debug). This captures handshake signals in hardware, which is far more reliable than trying to infer behavior from PASS/FAIL output.
- **Address ranges must not overlap**: In the Address Editor, confirm that BRAM0 (`0xA0000000`, 8 KB) and BRAM2 (`0xA0010000`, 8 KB) have non-overlapping ranges. Vivado will warn but sometimes still generate a bitstream with silent address aliasing.
- **Validate design before synthesis**: `validate_bd_design` in TCL (or `Tools → Validate Design` in GUI) catches unconnected ports, address conflicts, and clock domain mismatches before spending synthesis time.

### Code Example

```tcl
# After connection automation, confirm clocks are correct
foreach cell [get_bd_cells -hierarchical -filter {VLNV =~ *axi_bram_ctrl*}] {
  set intf [get_bd_intf_pins $cell/S_AXI]
  puts "BRAM ctrl: $cell  clock: [get_bd_pins -of_objects $intf -filter {TYPE==clk}]"
}

# Validate before generating output products
validate_bd_design
save_bd_design
```

### Relevance to Your Project

Your `create_bd.tcl` reconstructs the block design headlessly. After any tool upgrade (e.g., 2025.1 → 2025.2), re-run `validate_bd_design` immediately — the 2025.x series has changed how address segments are created, and a previously valid design may now produce an address conflict warning that causes implementation to fail silently.

## Vivado TCL Scripting

### Key Findings

- **`connect_bd_net` vs `connect_bd_intf_net`**: Use `connect_bd_net` for scalar signals (clock, reset, interrupt). Use `connect_bd_intf_net` for AXI interfaces and BRAM port bundles — mixing them causes cryptic errors like "cannot connect interface to net."
- **Address assignment**: `assign_bd_address` auto-assigns all unmapped segments. To pin a specific offset use `set_property offset 0xA0000000 [get_bd_addr_segs ...]` after the auto-assign, then rerun `validate_bd_design`.
- **TCL scripts are version-specific**: Block design TCL exports from Vivado 2024.x will not replay cleanly in 2025.x due to IP VLNV version changes. Pin IP versions explicitly with the `:version` suffix in `create_bd_cell`, or use `upgrade_ip` at script start.
- **Non-project mode gotcha**: In non-project mode you must call `generate_target all [get_files *.bd]` and then `export_ip_user_files` manually before synthesis — the GUI does this automatically but the batch flow does not.
- **`write_project_tcl` for full project replay**: Unlike `write_bd_tcl` (BD only), `write_project_tcl` captures sources, constraints, synthesis/implementation runs, and board settings — useful for creating a fully reproducible project from scratch.

### Code Example

```tcl
# Reproducible AXI BRAM BD snippet (version-pinned)
set bram_ctrl [create_bd_cell -type ip \
  -vlnv xilinx.com:ip:axi_bram_ctrl:4.1 bram_ctrl_0]
set blk_mem [create_bd_cell -type ip \
  -vlnv xilinx.com:ip:blk_mem_gen:8.4 blk_mem_gen_0]

set_property -dict {
  CONFIG.DATA_WIDTH  {32}
  CONFIG.Memory_Type {True_Dual_Port_RAM}
} $blk_mem

connect_bd_intf_net \
  [get_bd_intf_pins $bram_ctrl/BRAM_PORTA] \
  [get_bd_intf_pins $blk_mem/BRAM_PORTA]

# Assign address and pin to 0xA0000000
assign_bd_address [get_bd_addr_segs {$bram_ctrl/S_AXI/Mem0}]
set_property offset 0xA0000000 \
  [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_bram_ctrl_0_Mem0}]
set_property range 8K \
  [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_bram_ctrl_0_Mem0}]
```

### Relevance to Your Project

Your `create_bd.tcl` is the reproducibility backbone of the project. Pinning IP VLNV versions as shown above prevents silent IP upgrades when the TCL is replayed on a newer Vivado install — critical for a project that already has two BRAM controllers at specific base addresses.

## Vitis Bare-Metal / Standalone

### Key Findings

- **`xil_printf` goes to PS UART1 on KV260**: The KV260 starter kit routes the USB-UART bridge to PS UART1 (MIO 36–37). The Vitis standalone BSP `stdin`/`stdout` peripheral must be set to `psu_uart_1` in the BSP settings — selecting UART0 produces no output.
- **Standalone BSP interrupt controller**: To use interrupts with an AXI peripheral, add an AXI Interrupt Controller IP in the block design, set "Interrupt Output Connection" to Single, then run connection automation to wire it to the PS IRQ. The Vitis BSP then exposes `XScuGic` and `XIntc` drivers.
- **2025.1 BIST rebuild available**: A Hackster.io guide (LogicTronix) fully recreates the KV260 BIST application in Vivado/Vitis 2025.1, covering hardware design, BSP configuration, and UART output — useful as a cross-reference for your flow.
- **Linker script heap/stack sizing**: For BRAM write/read loops at multiple addresses, ensure the linker script allocates sufficient stack in OCM (On-Chip Memory). The default Vitis standalone linker script places heap at a fixed OCM region; growing array writes can silently overflow if the region is undersized.
- **XSDB/JTAG workflow**: During development, use `xsdb` TCL (`connect`, `targets`, `dow app.elf`, `run`) for fast iteration — no need to build a BOOT.BIN. Switch to QSPI deployment only after the design is validated.

### Code Example

```c
/* Bare-metal AXI-Lite BRAM write/read-back with xil_printf */
#include "xil_printf.h"
#include "xil_io.h"

#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL
#define TEST_WORDS  8

int main(void) {
    u32 i, readback;
    int pass = 1;

    /* Write pattern to BRAM0 */
    for (i = 0; i < TEST_WORDS; i++) {
        Xil_Out32(BRAM0_BASE + (i * 4), 0xDEAD0000 | i);
    }

    /* Read back and verify */
    for (i = 0; i < TEST_WORDS; i++) {
        readback = Xil_In32(BRAM0_BASE + (i * 4));
        if (readback != (0xDEAD0000 | i)) {
            xil_printf("BRAM0[%d]: FAIL (got 0x%08X)\r\n", i, readback);
            pass = 0;
        }
    }

    xil_printf(pass ? "BRAM0: PASS\r\n" : "BRAM0: FAIL\r\n");
    return 0;
}
```

### Relevance to Your Project

Your `main.c` already follows this pattern. The key operational detail is UART1 selection in the BSP — if you ever regenerate the BSP from scratch (e.g., after modifying the XSA in 2025.1), Vitis may reset the UART peripheral to the first detected instance, which on the KV260 is UART0 (not connected to USB). Confirm `stdin`/`stdout` is `psu_uart_1` after every BSP regeneration.

## XDC Timing Constraints

### Key Findings

- **`set_clock_groups` for PS/PL boundary**: The Zynq UltraScale+ PS generates `pl_clk0` (and up to `pl_clk3`). If your design also uses a PLL-derived clock, declare them as asynchronous groups: `set_clock_groups -asynchronous -group [get_clocks clk_pl_0] -group [get_clocks clk_out1_design_1]`. Without this, Vivado times every cross-domain path and may falsely fail timing.
- **`ASYNC_REG` attribute**: Any flip-flop used as a synchronizer across clock domains must carry the `ASYNC_REG` property. This tells Vivado to place the two-flop chain tightly and exempt the first stage from normal timing analysis. In VHDL: `attribute ASYNC_REG : string; attribute ASYNC_REG of sync_ff : signal is "TRUE";`
- **I/O delays for BRAM are usually not needed**: AXI-Lite to BRAM is an internal fabric path. External I/O constraints (`set_input_delay`, `set_output_delay`) apply to off-chip signals (e.g., PMOD pins, EMIO GPIOs). Do not add I/O delay constraints to AXI nets inside the PL — the tool will warn but they have no effect and clutter the constraint file.
- **Constraint Wizard**: In Vivado, `Tools → Constraint Wizard` introspects the synthesized netlist and suggests `create_clock`, `set_input_delay`, and `set_output_delay` values for unconstrained ports. Run after synthesis, before implementation, when you add new external ports.
- **CDC max delay for synchronizers**: For valid CDC synchronizer paths, use `set_max_delay -datapath_only` with 2× the destination clock period to suppress hold analysis while keeping setup analysis meaningful.

### Code Example

```tcl
# KV260 XDC: PS-generated clock + async clock group declaration
# pl_clk0 is auto-created by the PS IP; create_clock is not needed for it
# If a MMCM/PLL is in the design, add clock groups:

set_clock_groups -asynchronous \
  -group [get_clocks clk_pl_0] \
  -group [get_clocks -include_generated_clocks clk_out1_design_1_clk_wiz_0_0]

# CDC synchronizer attribute in XDC (alternative to VHDL attribute)
set_property ASYNC_REG TRUE [get_cells {u_sync/sync_ff_reg[0]}]
set_property ASYNC_REG TRUE [get_cells {u_sync/sync_ff_reg[1]}]

# Safe CDC max delay (destination clock period × 2)
set_max_delay -datapath_only 20.000 \
  -from [get_cells {cdc_src_reg}] \
  -to   [get_cells {u_sync/sync_ff_reg[0]}]
```

### Relevance to Your Project

Your `kv260_top.vhd` wrapper uses `pl_clk0` from the Zynq PS. As long as all PL logic is clocked from this single source, no clock group constraints are needed. However, if you ever add a secondary MMCM (e.g., for a video output clock), adding `set_clock_groups` immediately prevents the timing closure runs from timing cross-domain paths that are impossible to meet.

## Kria KV260 / K26 SoM

### Key Findings

- **Default boot mode is QSPI32**: The KV260 starter kit ships preset to QSPI32 boot mode. For bare-metal JTAG development, you must either switch the boot mode via MODE pins or use XSDB to override the boot mode register before loading your ELF.
- **UART is on PS MIO 36/37 (UART1)**: The USB-UART bridge on the KV260 carrier connects to K26 MIO pins 36–37, which map to PS UART1. PS UART0 (MIO 18–19) is not accessible from the carrier card's USB port.
- **RPi/PMOD headers are PL, not MIO**: Unlike typical Zynq boards where GPIO peripherals go to MIO, the KV260's 40-pin RPi header and PMOD connectors route through the PL fabric. Any custom GPIO or protocol on those pins requires a PL bitstream.
- **PS-first dynamic PL load (2025.1)**: Vivado 2025.1 introduces first-class support for booting the PS before the PL bitstream is loaded. For KV260 bare-metal, this means the C code can start executing from OCM before the AXI BRAM PL design is ready — add a check or delay before the first AXI write.
- **JTAG debugging requires udev rule**: On Linux host, install the Digilent JTAG driver udev rules (`/etc/udev/rules.d/`) to give non-root access to the JTAG cable. Without this, XSDB connects but fails to detect the ARM DAP.

### Code Example

```tcl
# XSDB script: override boot mode to JTAG and load bare-metal ELF
# Run in Vitis XSDB console or: xsdb -nodisp script.tcl

connect
targets -set -filter {name =~ "PSU"}

# Switch to JTAG boot mode (no SD/QSPI check)
mwr 0xFF5E0200 0x0100

# Reset and init PS
rst -system
after 2000

targets -set -filter {name =~ "Cortex-A53 #0"}
rst -processor

# Load and run ELF
dow /path/to/your/app.elf
con
```

### Relevance to Your Project

The XSDB flow above is the fastest iteration path for your AXI-BRAM demo — faster than rebuilding BOOT.BIN every cycle. The `mwr 0xFF5E0200 0x0100` register write switches the running system to JTAG mode without physically changing MODE pins, which is useful if your KV260 is in a fixed enclosure. After `con`, `xil_printf` output appears on the host USB-UART terminal.

## AMD/Xilinx Tool Updates (Vivado/Vitis 2025.x)

### Key Findings

- **Vivado 2025.1 — New RTL-based AXI Switch IP**: A fully customizable RTL AXI Switch IP was introduced that bridges between AXI interface types and widths. This replaces some use cases of the older AXI Interconnect (PG059) and may appear in connection automation for multi-master designs.
- **Vivado 2025.1 — PS-first / dynamic PL boot**: The tool now generates a boot flow where the PS starts first and the PL bitstream is streamed in afterward. This is transparent in JTAG mode but changes BOOT.BIN construction for QSPI deployment.
- **Vivado 2025.1 — Pblock Planner**: A new Pblock Planner GUI simplifies floor-planning for designs that need to place logic near specific hard blocks (e.g., keeping AXI BRAM controllers close to PS HP ports).
- **Vivado 2025 regression — AXI full peripheral 1 KB address space limit**: A Digilent forum report (2025) documents that AXI4 full peripherals appear limited to 1 KB of usable address space after implementation in Vivado 2025.x. AXI-Lite peripherals appear unaffected, but this is worth monitoring if you ever upgrade to AXI4 burst access for higher BRAM throughput.
- **Vitis 2025.1 — Never-ending streaming kernel**: Support for persistent/streaming kernels with low runtime overhead (relevant for future AXI-Stream additions to the design).
- **KV260 BIST in 2025.1 on Hackster.io**: LogicTronix published a complete walkthrough of recreating the KV260 BIST hardware and firmware in Vivado/Vitis 2025.1, including hardware export, BSP generation, and UART verification — the closest public reference to your project's flow.

### Code Example

```tcl
# Upgrade all IPs in a project to 2025.1 versions after tool upgrade
# Run from Vivado TCL console after opening the project

upgrade_ip [get_ips *]

# Check for any IPs that could not be upgraded
foreach ip [get_ips *] {
  set status [get_property IP_STATUS $ip]
  if {$status ne "ACTIVE"} {
    puts "WARNING: $ip has status $status — manual intervention needed"
  }
}

# Regenerate output products for upgraded IPs
generate_target all [get_ips *]
export_ip_user_files -of_objects [get_ips *] -no_script -reset -force
```

### Relevance to Your Project

If you upgrade from 2025.1 to a future release, run `upgrade_ip` before re-synthesizing. The AXI BRAM Controller (`axi_bram_ctrl`) and Block Memory Generator (`blk_mem_gen`) both receive minor version updates across tool releases. An un-upgraded IP in a newer Vivado will synthesize but may produce a critical warning that blocks bitstream generation.
