## Executive Summary

- **Critical AXI-Lite deadlock bug in Xilinx demo cores** — Xilinx's generated AXI-Lite slave templates fail to check backpressure on BREADY/RREADY, causing the bus to freeze when the master holds those low. Any custom IP you generate via "Create and Package IP" in Vivado may inherit this flaw. Apply the one-line fix before integrating with PS.
- **BRAM Controller must match port mode to block design topology** — using AXI4 (not AXI4-Lite) on the BRAM Controller unlocks burst access; pick AXI4-Lite only when you need the simplest control-register footprint. The KV260 project at 0xA0000000 and 0xA0010000 must have non-overlapping address ranges in the Address Editor or synthesis will produce silent misrouting.
- **JTAG is the right bare-metal boot path during development** — QSPI is for deployment. Use `mwr 0xff5e0200 0x0100` + `rst -system` via XSDB to force JTAG mode without touching the board's SD card boot switch, keeping iteration fast.
- **Vivado 2025.2 adds SystemVerilog Interface support** — simplifies AXI port wiring in block designs, reduces VHDL wrapper boilerplate. Worth evaluating for the kv260_top wrapper layer.
- **For internal AXI buses (PS→PL), do NOT add `set_input_delay`/`set_output_delay` constraints** — those are for signals crossing chip I/O pins. Internal AXI signals are already covered by the Zynq PS timing model; adding I/O constraints on them creates false violations.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- The five-channel AXI4 protocol (AW, W, B, AR, R) uses a two-way VALID/READY handshake. A transfer occurs only when both VALID and READY are high on the same rising clock edge. Neither side may deassert VALID once asserted until the handshake completes — but READY may depend on VALID without violating the spec.
- **Xilinx's generated AXI-Lite slaves do not check BREADY/RREADY backpressure.** If the master holds BREADY low (write response stalled) or RREADY low (read data stalled), the slave continues accepting new transactions it cannot complete, eventually deadlocking the bus. This is documented and confirmed by the ZipCPU AXI formal verification work.
- AXI4-Lite is appropriate for simple register-mapped peripherals (like a BRAM accessed word-at-a-time). AXI4 with burst support gives 4–16× higher throughput for block transfers but requires a more complex slave implementation.
- For AXI-Stream (AXIS), TLAST marks the end of a packet; TKEEP/TSTRB indicate which bytes are valid. Forgetting to handle TLAST in a sink causes packet framing errors in downstream processing.
- AXI protocol spec prohibits a master from asserting AWVALID or ARVALID based on the slave's AWREADY or ARREADY — the master must assert VALID unconditionally and wait.

### Code Example

```vhdl
-- Corrected AXI-Lite AWREADY logic with backpressure check
-- Without this check, holding BREADY low causes deadlock
process(S_AXI_ACLK)
begin
  if rising_edge(S_AXI_ACLK) then
    if S_AXI_ARESETN = '0' then
      axi_awready <= '0';
    else
      if axi_awready = '0' and S_AXI_AWVALID = '1' and
         S_AXI_WVALID = '1' and
         -- CRITICAL: do not accept new write if response channel is stalled
         not (axi_bvalid = '1' and S_AXI_BREADY = '0') then
        axi_awready <= '1';
      else
        axi_awready <= '0';
      end if;
    end if;
  end if;
end process;
```

### Relevance to Your Project

Your two BRAM slaves at 0xA0000000 (BRAM0) and 0xA0010000 (BRAM2) are accessed by the Cortex-A53 via the PS AXI HP or AXI GP ports. The PS master will generally not stall BREADY/RREADY under normal operation, but any future custom IP inserted between PS and BRAM must have the corrected backpressure logic above. Also verify in simulation that your write pattern → readback loop does not issue a new read while the previous RVALID is unacknowledged.

## Vivado Block Design / IP Integrator

### Key Findings

- **Connection Automation** automatically adds a Processing System Reset IP and an AXI Interconnect (or SmartConnect) to wire up peripheral AXI ports to the PS. Run it after placing all IP to let Vivado choose optimal routing, then review and adjust.
- **Address Editor rule**: each AXI slave must have a unique, non-overlapping address range. The editor allows you to set Base Address and Range independently. For two 64KB BRAMs: BRAM0 at 0xA000_0000 with 64K range, BRAM2 at 0xA001_0000 with 64K range.
- Do NOT use spaces in block design names or directory paths — Vivado silently breaks on them. Use underscores or CamelCase.
- After editing IP properties, always right-click the block design canvas → **Validate Design (F6)**. Errors in the address map or clock domain crossing show here before synthesis.
- SmartConnect (axi_smartconnect) is preferred over the older AXI Interconnect IP for new designs: it has lower latency, better QoS support, and handles clock crossing automatically between PS and PL clock domains.

### Code Example

```tcl
# Address Editor: assign two non-overlapping 64K BRAM ranges in TCL
assign_bd_address [get_bd_addr_segs {axi_bram_ctrl_0/S_AXI/Mem0}]
set_property offset 0xA0000000 [get_bd_addr_segs \
  {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property range 64K [get_bd_addr_segs \
  {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]

assign_bd_address [get_bd_addr_segs {axi_bram_ctrl_1/S_AXI/Mem0}]
set_property offset 0xA0010000 [get_bd_addr_segs \
  {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_1_Mem0}]
set_property range 64K [get_bd_addr_segs \
  {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_1_Mem0}]
```

### Relevance to Your Project

Your create_bd.tcl likely contains equivalent address assignment commands. If you ever see PASS on BRAM0 but garbage on BRAM2 (or vice versa), the first thing to check is whether the Address Editor has them correctly separated. Also verify the AXI BRAM Controller for each is configured for AXI4-Lite (sufficient for word-at-a-time access) and that both BRAM port depths are ≥ 512 bytes (minimum supported depth).

## Vivado TCL Scripting

### Key Findings

- **Everything you do in the Vivado GUI emits a TCL command to the console.** This is the fastest way to learn the scripting API: do it graphically, then copy the command from the TCL console to your script.
- **Non-project mode** (using `read_vhdl`, `read_xdc`, `synth_design`, `opt_design`, `place_design`, `route_design`, `write_bitstream` sequentially) gives the most control and is ideal for CI/CD pipelines. Project mode (`open_project`, `launch_runs`) is easier for interactive development.
- In batch mode (`vivado -mode batch -source script.tcl`), unknown commands are NOT passed to the OS shell — use `exec` explicitly for any shell operations.
- **Export Block Design** (`write_bd_tcl`) generates a complete TCL reconstruction script for your block design. Commit this file (not the .bd file) for clean version control — the .bd file is large XML that diffs poorly.
- Use `catch { ... }` in TCL to handle expected failures gracefully (e.g., IP already exists during re-run).

### Code Example

```tcl
# Non-project mode build script skeleton for kv260-axi-bram-demo
# Run: vivado -mode batch -source build.tcl

set outputDir ./output
file mkdir $outputDir

# Read sources
read_vhdl -library work [glob ./vhdl/*.vhd]
read_xdc  [glob ./constraints/*.xdc]

# Synthesis
synth_design -top kv260_top -part xck26-sfvc784-2LV-c

# Implementation
opt_design
place_design
phys_opt_design
route_design

# Reports
report_timing_summary -file $outputDir/timing.rpt
report_utilization    -file $outputDir/util.rpt

# Bitstream
write_bitstream -force $outputDir/kv260_top.bit
```

### Relevance to Your Project

Your create_bd.tcl is the core automation artifact. Pair it with a wrapper `build.tcl` like the example above so the entire project can be rebuilt from scratch with a single command — essential for reproducing the project on a new machine or validating changes cleanly. The `-part xck26-sfvc784-2LV-c` is the standard K26 part string.

## Vitis Bare-Metal / Standalone

### Key Findings

- **stdout/stdin BSP settings must point to the correct UART.** On KV260, the USB-UART bridge connects to `psu_uart_1` (MIO 40/41). If xil_printf output is silent, open the BSP settings in Vitis and ensure `stdout` is set to `psu_uart_1`, not `psu_uart_0`.
- The Standalone BSP is single-threaded and provides `xil_printf` (lightweight, no float formatting) and `printf` (full libc, much larger code size). Use `xil_printf` for PASS/FAIL diagnostics; reserve `printf` only if you need float formatting.
- **Linker script RAM region:** By default, the Vitis linker script places code in DDR at 0x0000_0000. For Kria bare-metal, ensure the memory region covers sufficient space — the default 256MB DDR map is fine, but if you added an OCM section, its base must be `0xFFFC0000` (not 0x0).
- `Xil_In32(addr)` / `Xil_Out32(addr, val)` are the idiomatic bare-metal AXI register access functions — they emit the correct memory-mapped I/O sequence and include cache coherency barriers on Cortex-A53.
- **BSP regeneration** is required after any hardware export change (`xsa` file update). In Vitis, right-click the BSP project → Update BSP Sources.

### Code Example

```c
#include "xil_printf.h"
#include "xil_io.h"

#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL
#define TEST_PATTERN 0xDEADBEEFUL

static int bram_rw_test(u32 base, const char *name) {
    Xil_Out32(base, TEST_PATTERN);
    /* ensure write completes before read (data memory barrier) */
    dmb();
    u32 readback = Xil_In32(base);
    if (readback == TEST_PATTERN) {
        xil_printf("%s: PASS (0x%08X)\r\n", name, readback);
        return 0;
    }
    xil_printf("%s: FAIL - wrote 0x%08X, read 0x%08X\r\n",
               name, (u32)TEST_PATTERN, readback);
    return -1;
}

int main(void) {
    xil_printf("=== KV260 AXI-BRAM Test ===\r\n");
    int rc = 0;
    rc |= bram_rw_test(BRAM0_BASE, "BRAM0");
    rc |= bram_rw_test(BRAM2_BASE, "BRAM2");
    xil_printf("Overall: %s\r\n", rc == 0 ? "PASS" : "FAIL");
    return rc;
}
```

### Relevance to Your Project

This mirrors what your main.c does. The `dmb()` (Data Memory Barrier) call is important on Cortex-A53 — without it, the compiler or CPU's out-of-order execution might reorder the read before the write has actually propagated to the AXI fabric, causing a false PASS (reading stale cache) or false FAIL. `Xil_Out32` / `Xil_In32` include the necessary barriers internally, but explicit `dmb()` between back-to-back write→read pairs adds extra safety.

## XDC Timing Constraints

### Key Findings

- **Do NOT add `set_input_delay`/`set_output_delay` to internal AXI buses.** These constraints apply only to signals that cross a physical chip I/O pin. AXI signals between the PS and PL are internal to the Zynq device and are already constrained by the Zynq PS timing model embedded in the tool.
- If Vivado reports unconstrained paths for internal AXI, the correct fix is to add a `set_clock_groups -asynchronous` or `set_false_path` between unrelated clock domains (e.g., PS `pl_clk0` vs. a free-running PL clock), not `set_input_delay`.
- The Timing Constraints Wizard (`Tools → Timing Constraints Wizard`) in Vivado will automatically detect unconstrained clocks and generate a skeleton XDC — run it on a fresh project to catch missing constraints before tapeout.
- For any physical I/O (GPIO, PMOD, etc.) routed through the PL, use: `set_input_delay -clock [get_clocks CLKOUT0] -max 2.0 [get_ports GPIO_IN]` and match with a `-min` constraint.
- Clock domain crossings (CDC) between `pl_clk0` (100 MHz typical) and other derived clocks require either a proper synchronizer in RTL or `set_clock_groups -asynchronous -group {clk0} -group {clk1}` in XDC.

### Code Example

```xdc
# Typical KV260 bare-metal XDC - internal AXI needs NO I/O delays
# Only the PL clock source needs constraining

# PS provides pl_clk0 - Vivado infers this from the Zynq PS IP
# No create_clock needed for pl_clk0

# If you have a secondary PL clock (e.g., from a BUFG or MMCM):
# create_clock -period 10.000 -name clk_100mhz [get_pins clk_wiz_0/clk_out1]

# False path for any asynchronous reset crossing:
set_false_path -from [get_ports {reset_n}]

# Clock groups if PS and PL clocks are asynchronous to each other:
# set_clock_groups -asynchronous \
#   -group [get_clocks -of_objects [get_pins zynq_ultra_ps_e_0/pl_clk0]] \
#   -group [get_clocks clk_100mhz]

# GPIO physical I/O (if applicable):
# set_input_delay  -clock [get_clocks clk_100mhz] -max 2.0 [get_ports {gpio_in[*]}]
# set_input_delay  -clock [get_clocks clk_100mhz] -min 0.5 [get_ports {gpio_in[*]}]
# set_output_delay -clock [get_clocks clk_100mhz] -max 2.0 [get_ports {gpio_out[*]}]
# set_output_delay -clock [get_clocks clk_100mhz] -min 0.5 [get_ports {gpio_out[*]}]
```

### Relevance to Your Project

Your kv260_top.vhd wraps the block design and exposes the PS-to-PL AXI interface internally. Since all AXI traffic stays inside the chip, your XDC should be minimal — primarily the board-specific pin assignments from the KV260 master XDC and any physical GPIO you expose. If you're seeing "unconstrained path" warnings, use the Timing Constraints Wizard to identify the actual source before adding constraints blindly.

## Kria KV260 / K26 SoM

### Key Findings

- **Boot mode selection:** K26 MODE[3:0] pins are tied on the carrier board. KV260 ships pre-configured for QSPI32. For bare-metal development, JTAG mode is fastest — force it via XSDB without touching hardware: `mwr 0xff5e0200 0x0100` then `rst -system`.
- **Two bare-metal boot paths:**
  1. **JTAG** (development): download `.elf` + bitstream directly via XSDB/Vitis debugger. No persistence across power cycle.
  2. **QSPI** (deployment): create a boot image (BOOT.BIN containing FSBL + bitstream + application ELF) and flash to QSPI. Use QSPI32 mode.
- **I/O mapping complexity:** KV260 pin assignments span two boards (K26 SoM + KV260 carrier). The signal path from your VHDL port → FPGA package pin → SoM connector → carrier connector → physical header is documented in the K26 SoM datasheet (DS987) and the KV260 carrier card schematics.
- The K26 uses a Zynq UltraScale+ MPSoC (XCZU5EV or XCZU5EG variant). The PS is a quad-core Cortex-A53 (APU) + dual-core Cortex-R5F (RPU). Bare-metal on the APU core 0 is the standard starting point.
- **USB-UART is on MIO 40/41** (mapped to `psu_uart_1`). This is the serial port you read PASS/FAIL from.

### Code Example

```tcl
# XSDB/XSCT script: force KV260 into JTAG boot mode and program bare-metal app
# Run from Vitis/XSCT console

connect
targets -set -filter {name =~ "PSU"}

# Force JTAG boot mode via register write
mwr 0xff5e0200 0x0100
rst -system
after 3000

# Initialize PS (alternative to FSBL when no Linux is present)
targets -set -filter {name =~ "APU*"}
source {/path/to/psu_init.tcl}
psu_init

# Load bitstream into PL
fpga -file {/path/to/kv260_top.bit}

# Load and run bare-metal ELF on Cortex-A53 core 0
targets -set -filter {name =~ "APU Core 0"}
dow {/path/to/kv260_bram.elf}
con
```

### Relevance to Your Project

This is the exact boot sequence for your AXI-BRAM demo. The `psu_init` call (generated by Vitis from your XSA) configures DDR, PLL, and MIO before your ELF runs — without it, `Xil_Out32`/`Xil_In32` may work intermittently because DDR is not initialized. The `fpga` command loads your bitstream, enabling the PL fabric and making the BRAM controllers at 0xA0000000/0xA0010000 accessible.

## AMD/Xilinx Tool Updates (2025.x)

### Key Findings

- **Vivado 2025.2** (current stable as of this digest) adds:
  - **SystemVerilog Interface support** for block designs — AXI ports can now be connected as SV interface bundles, reducing manual wire-up and wrapper code.
  - Reduced Physical Optimization (PhysOpt) compile time.
  - BUFG_FABRIC replication per SLR/VNoC column for high-fanout nets.
  - Improved SLR crossing reporting for multi-die devices.
  - New device support: Versal AI Edge Series Gen 2, Versal Prime Series Gen 2.
- **Vitis 2025.2** adds:
  - New AI Engine data types (MX6, MX4 block floating-point, cbfloat16) — relevant if you extend the project to the KV260's video accelerator blocks.
  - Improved AI Engine mapper/router efficiency.
  - Enhanced Versal design flows.
- **Known issues**: refer to the official UG973 (Vivado Release Notes) and UG1742 (Vitis Release Notes) Answer Records. The most common class of issues in each release involves IP version mismatches after project upgrade — always re-validate IP after opening a project from a prior tool version.
- For the kv260-axi-bram-demo, upgrading from 2025.1 to 2025.2 should be low-risk (no Versal or AI Engine dependency), but verify the AXI BRAM Controller and Block Memory Generator IPs are updated to their latest versions post-upgrade.

### Code Example

```tcl
# Check and upgrade all IP in a project after tool version upgrade
# Run from Vivado TCL console after opening the project

# Report which IPs need upgrading
report_ip_status

# Upgrade all IPs that have newer versions available
upgrade_ip [get_ips]

# Re-generate all IP outputs
generate_target all [get_ips]

# Re-validate the block design
open_bd_design [get_files *.bd]
validate_bd_design

# Re-export hardware to update the XSA for Vitis
write_hw_platform -fixed -include_bit -force ./kv260_top.xsa
```

### Relevance to Your Project

After any Vivado version upgrade, run this sequence before attempting synthesis. Skipping IP upgrade is the #1 cause of mysterious synthesis failures after tool updates. The `write_hw_platform` at the end updates the `.xsa` file consumed by Vitis — you must re-import it there (File → Open Platform in Vitis) and rebuild the BSP to pick up any changed memory maps or driver versions.
