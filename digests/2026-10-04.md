## Executive Summary

1. **AXI-Lite write-response race is the #1 silent hang cause**: if `BREADY` is deasserted while
   `BVALID` arrives on the same cycle, the write response is lost and the bus stalls permanently.
   Always keep `BREADY` registered and guard against simultaneous backpressure.
2. **C_READ_LATENCY must match your BRAM primitive**: the AXI BRAM Controller's
   `C_READ_LATENCY` parameter tells the controller how many cycles to wait before expecting
   `RDDATA`. Mismatching this causes silent read-garbage on the first few beats.
3. **Address alignment in the IP Integrator Address Editor must be power-of-two and
   non-overlapping**: your 0xA0000000 / 0xA0010000 split is correct (64 KB apart), but the
   Address Editor will silently auto-reassign if you regenerate the design—always lock addresses
   after manual assignment.
4. **Vivado 2025.2 is available** with Versal hard-IP configuration from RTL and inline HDL for
   utility IP, reducing block-design load time—relevant if you plan to uprev from 2025.1.
5. **Non-project TCL mode is the most reproducible CI path**: script your entire flow
   (read_vhdl → synth_design → opt_design → place_design → route_design → write_bitstream)
   so regeneration is one command and checkpoint-to-checkpoint incremental runs are trivially
   enabled.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- All five AXI4-Lite channels (AW, W, B, AR, R) use the same VALID/READY handshake. A transfer
  occurs only on the rising edge where both are asserted simultaneously.
- **Deadlock trap**: once VALID is asserted it must stay asserted until the handshake completes.
  Withdrawing VALID mid-transaction violates the spec and causes subtle simulation-only passing
  that breaks in silicon/timing-closure.
- **Write-response race**: it is legal for `BREADY` to be low on the same cycle `BVALID` rises.
  If the master does not handle the case where its own `BREADY` is tied high while a pipeline
  stall hits, the response is consumed but not recorded, hanging the next transaction.
- **Read latency mismatch**: AXI BRAM Controller parameter `C_READ_LATENCY` defaults to 1. A
  Block Memory Generator configured for output-register latency of 2 causes the controller to
  sample data one cycle early, returning garbage on the first read.
- **AXI-Stream TLAST mishandling**: a common bug is transitioning to IDLE immediately when
  TLAST is seen without checking TREADY. Always wait for TVALID & TREADY & TLAST before
  closing a packet.
- **XPM_FIFO_AXIS** (Xilinx Parameterized Macro) is the preferred AXI-Stream FIFO macro in
  UltraScale+ designs—it operates in FWFT mode only and avoids the old FIFO generator's
  mode-mismatch pitfalls.

### Code Example

```vhdl
-- AXI-Lite slave: safe BREADY / BVALID handshake (VHDL-2008)
process(clk)
begin
  if rising_edge(clk) then
    if rst = '1' then
      s_axi_bvalid <= '0';
    elsif aw_handshake and w_handshake then   -- write accepted
      s_axi_bvalid <= '1';
      s_axi_bresp  <= "00";                   -- OKAY
    elsif s_axi_bready = '1' then             -- master consumed response
      s_axi_bvalid <= '0';
    end if;
    -- NOTE: do NOT clear bvalid unless bready is seen.
    -- Clearing early loses the response and stalls the master.
  end if;
end process;
```

### Relevance to Your Project

Your `main.c` writes patterns to BRAM0 (0xA0000000) and BRAM2 (0xA0010000). Any write that
doesn't explicitly poll `BRESP` before the next write risks stacking transactions when the
AXI BRAM Controller's internal FIFO fills. Add a barrier read (read-back any address) between
burst writes to drain the response channel.

## Vivado Block Design / IP Integrator

### Key Findings

- **Connection Automation** wires clock/reset/AXI for you but defaults to 100 MHz; verify the
  clock frequency matches your XDC `create_clock` constraint after running it.
- **Address Editor auto-assignment**: right-click → "Assign All" fills gaps, but may relocate
  manually set addresses. Use "How to Lock the Address" (UG994) to pin BRAM0 at 0xA0000000
  and BRAM2 at 0xA0010000 permanently.
- **Address range**: each AXI BRAM controller defaults to 64 KB (0x10000). Your 0x10000 offset
  between the two BRAMs is exactly one 64 KB window—correct and tight; any range > 64 KB on
  either controller would cause an address collision.
- **Regenerate layout** after any IP customization; stale connection metadata from cached
  `.bd` state has caused false DRC failures across Vivado minor versions.
- Block design TCL export (`write_bd_tcl`) may break across major Vivado versions because IPI
  scripting internals change; pin your Vivado version or test TCL replay on every uprev.

### Code Example

```tcl
# Lock BRAM addresses in IP Integrator to prevent auto-reassignment
# Run in Vivado Tcl Console after opening the block design
set_property offset 0xA0000000 [get_bd_addr_segs {zynq_ps/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property range  64K        [get_bd_addr_segs {zynq_ps/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property offset 0xA0010000 [get_bd_addr_segs {zynq_ps/Data/SEG_axi_bram_ctrl_1_Mem0}]
set_property range  64K        [get_bd_addr_segs {zynq_ps/Data/SEG_axi_bram_ctrl_1_Mem0}]
# Lock to prevent re-assignment on next Connection Automation run
assign_bd_address -lock [get_bd_addr_segs {zynq_ps/Data/SEG_axi_bram_ctrl_0_Mem0}]
assign_bd_address -lock [get_bd_addr_segs {zynq_ps/Data/SEG_axi_bram_ctrl_1_Mem0}]
```

### Relevance to Your Project

Your block design uses `M_AXI_HPM0_LPD` (or `M_AXI_GP0`) to reach both BRAMs. Locking
addresses as above ensures that re-running `create_bd.tcl` from scratch always lands the BRAMs
at the expected addresses, so `main.c`'s hardcoded `0xA0000000` / `0xA0010000` always work.

## Vivado TCL Scripting

### Key Findings

- **Non-project mode** is the gold standard for reproducible builds: no `.xpr` or `.cache`
  state—every run is a clean compile from sources.
- In non-project mode, files are compiled in the order `read_*` commands appear. VHDL packages
  must be read before entities that reference them.
- Checkpoints (`write_checkpoint`) at synthesis, placement, and routing allow incremental re-runs
  that skip completed stages—critical for large designs with long route times.
- Vivado 2025.2 non-project mode example scripts live at
  `<Vivado_install>/examples/Vivado_Tutorial/` and are the canonical starting point.
- **`open_bd_design` + `generate_target all`** are required inside project mode before
  exporting; in non-project mode, read the exported netlist directly via `read_edif`.

### Code Example

```tcl
#!/usr/bin/env tclsh
# Non-project mode batch build for kv260-axi-bram-demo

set outputDir ./output
file mkdir $outputDir

# Read sources
read_vhdl -library xil_defaultlib [glob src/vhdl/*.vhd]
read_xdc  constraints/kv260_top.xdc

# Synthesize
synth_design -top kv260_top -part xck26-sfvc784-2LV-c
write_checkpoint -force $outputDir/post_synth.dcp

# Implement
opt_design
place_design
write_checkpoint -force $outputDir/post_place.dcp
route_design
write_checkpoint -force $outputDir/post_route.dcp

# Reports
report_timing_summary -file $outputDir/timing.rpt
report_utilization    -file $outputDir/utilization.rpt

# Bitstream
write_bitstream -force $outputDir/kv260_top.bit
```

### Relevance to Your Project

Your `create_bd.tcl` currently runs in project mode. Wrapping it in a non-project shell that
calls `synth_design` directly after `generate_target all` would let CI produce a `.bit` file
with a single `vivado -mode batch -source run_all.tcl` invocation—no GUI required.

## Vitis Bare-Metal / Standalone

### Key Findings

- **`xil_printf`** is a 1 KB lightweight printf replacement—no floating-point, no `%f`. Use it
  for UART status output; the standard `printf` adds ~70 KB to the binary.
- BSP is generated from the exported `.xsa` (hardware handoff) file; regenerate it whenever you
  change the Vivado block design or addresses, otherwise driver macros like `XPAR_AXI_BRAM_CTRL_0_BASEADDR` will be stale.
- **Linker script (`lscript.ld`)**: default places everything in DDR. For a bare-metal BRAM demo,
  consider placing `.data` and `.bss` in OCM (On-Chip Memory) for deterministic latency and to
  avoid DDR controller initialization.
- Interrupt controller (GIC on Cortex-A53) requires `XScuGic_Connect()` + `XScuGic_Enable()`
  before `Xil_ExceptionEnable()`—order matters; enabling exceptions before connecting a handler
  causes an unhandled interrupt abort.
- The standalone BSP wiki page documents all available drivers and their configuration macros;
  always cross-check `xparameters.h` after each `.xsa` export.

### Code Example

```c
/* Bare-metal BRAM write/readback pattern with explicit memory barrier */
#include "xil_io.h"
#include "xil_printf.h"

#define BRAM0_BASE 0xA0000000UL
#define BRAM2_BASE 0xA0010000UL
#define TEST_WORD  0xDEADBEEFUL

static int bram_test(uintptr_t base, const char *name) {
    Xil_Out32(base, TEST_WORD);
    /* dsb sy: ensure AXI write completes before the read issues */
    __asm__ volatile("dsb sy" ::: "memory");
    u32 val = Xil_In32(base);
    if (val == TEST_WORD) {
        xil_printf("%s PASS (0x%08X)\r\n", name, val);
        return 0;
    }
    xil_printf("%s FAIL expected 0x%08X got 0x%08X\r\n", name, TEST_WORD, val);
    return -1;
}

int main(void) {
    int rc = 0;
    rc |= bram_test(BRAM0_BASE, "BRAM0");
    rc |= bram_test(BRAM2_BASE, "BRAM2");
    return rc;
}
```

### Relevance to Your Project

The `dsb sy` barrier above is the Cortex-A53 idiom that ensures the AXI write has been
committed to the BRAM before the read-back issues. Without it the CPU's store buffer can reorder
the write past the read, causing false FAIL results that disappear under a debugger (Heisenbug).

## XDC Timing Constraints

### Key Findings

- **`set_input_delay`** defines Pad-to-Setup time: `-max` is the maximum data arrival latency
  (sets up the setup check), `-min` is the minimum (sets up the hold check).
- **`set_output_delay`**: `-max = tSetup + trace_delay`, `-min = -tHold + trace_delay`.
- For a pure PS-to-PL AXI design with no external I/O (only the JTAG/UART pins on the KV260),
  you typically need only a `create_clock` for the PL fabric clock and
  `set_clock_groups -asynchronous` between the PS clocks and PL clocks.
- The Vivado **Constraint Wizard** (Tools → Constraint Wizard) auto-generates `set_input_delay`
  / `set_output_delay` stubs for any unconstrained I/O ports—run it once to catch missing
  constraints.
- False path on crossing from PS to PL via the AXI interconnect: Vivado's timing engine handles
  the AXI CDC internally for the PS8 primitive; do not add user-level false-path or
  multi-cycle-path constraints on those paths.

### Code Example

```xdc
# kv260_top.xdc — minimal constraints for KV260 bare-metal AXI-BRAM demo

# PL fabric clock driven by PS (100 MHz typical from FCLK_CLK0)
# This is auto-created when using Zynq PS IP; add only if using a custom clock source:
# create_clock -period 10.000 -name pl_clk0 [get_ports pl_clk0]

# UART TX/RX false paths (CDC handled by PS8 primitive)
set_false_path -from [get_clocks clk_pl_0] -to [get_clocks clk_pl_0]

# Async clock groups between PS and PL clock domains
set_clock_groups -asynchronous \
    -group [get_clocks clk_pl_0] \
    -group [get_clocks -include_generated_clocks {clk_out1_*}]

# I/O timing for any external PL pins (none in this project, example only)
# set_input_delay  -clock pl_clk0 -max 2.0 [get_ports {some_input}]
# set_output_delay -clock pl_clk0 -max 1.5 [get_ports {some_output}]
```

### Relevance to Your Project

For the AXI-BRAM demo there are no PL-side user I/O pins—all connectivity is through PS AXI
ports. Your XDC needs only the auto-generated PS clock constraint and the `set_clock_groups`
line. An empty or missing XDC will still synthesize but Vivado will warn about unconstrained
paths; adding the above silences those warnings and ensures timing closure is reported cleanly.

## Kria KV260 / K26 SoM Platform Specifics

### Key Findings

- **Boot modes**: Quad-SPI (MIO[5:0], PS_Mode[3:0]=0010) is the default production boot;
  SD card (MIO[22:13], PS_Mode[3:0]=0011) is used for development. eMMC (PS_Mode=0110) is
  the on-SOM storage option. The boot mode pins are read by the ROM before any user code runs.
- **MIO Bank 502** (26 pins, 1.8 V) is used by the SOM itself for on-board peripherals.
  User PL I/O comes through the SOM connector on HDIO and HPIO banks at 1.8 V or 3.3 V
  depending on carrier card configuration.
- **Power domains**: Always-On (+5 V infrastructure), PS Power Domain (MIO / PS-GTR rails),
  PL Power Domain (HDIO / HPIO). PL fabric is unpowered until the PS boots and enables it—bare
  metal designs must not touch PL MMIO addresses before `XFpga_PL_BitStream_Load()` or
  equivalent initialization completes.
- **EMIO GPIO**: the K26 exposes PS EMIO GPIO through the SOM connector for PL-connected
  peripherals without consuming MIO; useful for debug LED/button without modifying the SOM
  hardware.
- **Secondary boot device** (UG1089): the KV260 carrier has a microSD slot on MIO; setting
  PS_Mode to SD enables booting a BOOT.BIN that includes the bitstream + FSBL + application.

### Code Example

```c
/* Check that PL is programmed before accessing AXI BRAM addresses.
 * On KV260 bare-metal this is guaranteed if the bitstream is embedded
 * in BOOT.BIN via Vitis "boot image" flow, but useful for debugging. */
#include "xfpga_config.h"  /* if using xfpga library */

/* Simple polling approach without xfpga: read PCAP status */
#define SLCR_BASE        0xFF180000UL
#define PCAP_STATUS_REG  (SLCR_BASE + 0x3124)
#define PCAP_PL_DONE_BIT (1U << 3)

static int wait_for_pl_done(void) {
    volatile uint32_t *pcap = (volatile uint32_t *)PCAP_STATUS_REG;
    for (int i = 0; i < 100000; i++) {
        if (*pcap & PCAP_PL_DONE_BIT) return 0;
    }
    return -1;  /* PL not configured */
}
```

### Relevance to Your Project

On the KV260 with a BOOT.BIN that includes the bitstream (the normal Vitis flow), the PL is
programmed before `main()` is called, so you don't need the check above in production. However,
during JTAG-based debugging where you program the bitstream separately, the PS may call `main()`
before the PL fabric is live, causing an AXI timeout when accessing 0xA0000000. Add the check
(or use `Xil_AssertNonvoid`) during bring-up to distinguish AXI-timeout panics from logic bugs.

## AMD/Xilinx Tool Updates: Vivado/Vitis 2025.x

### Key Findings

- **Vivado 2025.2** (released late 2025): supports configuring Versal hard IP (CIPS, NoC,
  transceivers) from top-level RTL; inline HDL for utility IP reduces IP load and re-synthesis
  times. UG973 (release notes) documents all known issues.
- **Vitis 2025.2** (UG1742, 2025-11-20): AI Engine API enhancements for Versal AI Edge
  (Block Floating Point MX6/MX4, cbfloat16), new DSP library functions. For KV260 bare-metal
  (non-AI Engine) work, the Vitis Unified IDE changes are the main relevance: the classic IDE
  workflow is deprecated in favor of the new Unified IDE component-based flow.
- **2025.2 IP Change Log** (AR 000039903): AXI BRAM Controller v4.1 received a CDC fix—if
  you see intermittent BRAM readback failures at higher clock speeds, uprev from 2025.1 to 2025.2.
- **Vitis 2025.1 release date**: 2025-07-08. If you installed shortly after GA you may be on
  an early patch; check for 2025.1.1 updates via the Vitis Update Manager.
- The **Vitis Unified IDE** replaces both Vitis Classic and Xilinx SDK for all new projects.
  Platform + domain + application component workflow replaces the old BSP/application project
  hierarchy—migration guide in UG1400.

### Relevance to Your Project

If you plan to uprev from Vivado/Vitis 2025.1 to 2025.2, the AXI BRAM Controller CDC fix is
directly relevant to your dual-BRAM design—the fix addresses exactly the class of intermittent
read errors that bare-metal loop tests can expose. Pin your IP version in the block design TCL
(`set_property CONFIG.Component_Name {axi_bram_ctrl_0}`) and test before upgrading in-place.
