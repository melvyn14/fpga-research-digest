# FPGA Research Digest - 2026-09-29

## Executive Summary

- **AXI-Lite VALID/READY rule**: Asserting `VALID` must never depend on `READY` on the same channel — this is the single most common AXI deadlock bug; your BRAM write path in `main.c` is safe if the processor never stalls waiting for AXI `WREADY` before asserting `AWVALID`.
- **AXI BRAM Controller ECC pitfall**: Enabling ECC on the Block Memory Generator adds a read-modify-write cycle for sub-word (byte/half-word) writes, costing one extra clock per access — keep ECC disabled for your simple read-back demo to avoid unexpected stall cycles.
- **Non-project mode TCL**: Export your block design as a TCL script via `write_bd_tcl`, strip project-specific lines, and source it in non-project mode; pre-generating the OOC synthesis wrapper is mandatory or the implementation step will error out.
- **KV260 boot sequence**: The board is hardwired to QSPI32 boot mode; for a bare-metal `run-on-hardware` debug session from Vitis you need a valid FSBL + PMU firmware in the boot image (`BOOT.BIN`) before your application `.elf` can reach the AXI fabric.
- **SmartConnect replaces AXI Interconnect**: In Vivado 2025.1+ the legacy AXI Interconnect IP is deprecated; prefer `axi_smartconnect` in your block design TCL (`create_bd.tcl`) and set `NUM_SI`/`NUM_MI` properties accordingly.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- The AXI protocol uses a two-signal handshake: transfer occurs **only when both `VALID` and `READY` are high on the same rising clock edge**.
- **Deadlock rule (ARM spec §A3.3.1)**: A source asserting `VALID` must never wait for `READY` before asserting `VALID`. Breaking this rule in custom IP causes protocol deadlock because the destination may wait for `VALID` before asserting `READY`.
- `AWVALID`/`WVALID` can be asserted simultaneously or `AWVALID` first; the BRAM controller accepts both orderings.
- AXI-Lite has no burst support (single beat only), no `ARID`/`AWID` ordering tags, and fixed 32-bit or 64-bit data width — ideal for control-register style access to BRAM.
- Common simulation pitfall: forgetting to de-assert `VALID` after a completed transfer causes the downstream IP to re-sample stale data on the next cycle.
- AXI-Stream (`TVALID`/`TREADY`/`TDATA`/`TLAST`) has no address phase — useful if you ever add a DMA or video pipeline to this platform.

### Code Example

```vhdl
-- Minimal AXI-Lite slave write path: never gate AWVALID on WREADY
process(s_axi_aclk)
begin
  if rising_edge(s_axi_aclk) then
    if s_axi_aresetn = '0' then
      aw_en   <= '1';
      axi_awready <= '0';
    else
      -- Accept write address independently of write data
      if (axi_awready = '0' and s_axi_awvalid = '1' and aw_en = '1') then
        axi_awready <= '1';
        aw_en       <= '0';
      elsif (s_axi_bready = '1' and axi_bvalid = '1') then
        aw_en       <= '1';  -- re-enable after response accepted
        axi_awready <= '0';
      else
        axi_awready <= '0';
      end if;
    end if;
  end if;
end process;
```

### Relevance to Your Project

Your `main.c` writes 32-bit words directly via `Xil_Out32(0xA0000000, value)` — this is a single-beat AXI-Lite transaction. The Zynq PS HP/GP AXI master correctly issues `AWVALID` independent of `WREADY`, so deadlock risk is on the PL slave side (your BRAM controller). Using the AMD `axi_bram_ctrl` IP ensures spec-compliant slave behavior. The read-back via `Xil_In32` performs a separate AXI-Lite read transaction; ensure the `aclk` driving `axi_bram_ctrl` meets timing to avoid metastability on the return path.

## Vivado Block Design / IP Integrator

### Key Findings

- **Connection Automation**: After placing an `axi_bram_ctrl` IP, right-click → *Run Connection Automation* to auto-wire `S_AXI`, `BRAM_PORTA`, and the clock/reset. Always verify the automation assigned the correct AXI master (Zynq GP0 vs. HP ports).
- **Address Editor**: BRAM controllers require explicit base addresses. Vivado auto-assigns from a pool but may collide if multiple IP share an address range; use the *Address Editor* tab to set `0xA0000000` (BRAM0) and `0xA0010000` (BRAM2) explicitly.
- **Block Design Validation**: Always run `validate_bd_design` in TCL (or *Tools → Validate Design* in GUI) before synthesis — it catches unconnected required ports, address collisions, and width mismatches that synthesis silently ignores.
- **OOC synthesis**: Block designs synthesize out-of-context by default; the OOC wrapper `<design>_wrapper.vhd` must be set as the top-level module in Vivado. If you use non-project mode, generate this wrapper explicitly with `make_wrapper -files [get_files *.bd] -top`.
- **IP Catalog refresh**: After upgrading Vivado, run *Tools → Report IP Status* to detect stale IP versions. Upgrading individual IP without re-running `generate_target` can leave mismatched stub files in synthesis.

### Code Example

```tcl
# Block design setup: address assignment for two BRAM controllers
set_property offset 0xA0000000 [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property range  64K         [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]

set_property offset 0xA0010000 [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_1_Mem0}]
set_property range  64K         [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_1_Mem0}]

# Validate and generate before synthesis
validate_bd_design
generate_target all [get_files *.bd]
make_wrapper -files [get_files *.bd] -top
```

### Relevance to Your Project

Your `create_bd.tcl` script drives the entire block design programmatically — the address assignments above must match the hard-coded addresses in `main.c` (`0xA0000000`, `0xA0010000`). Any address mismatch will cause silent reads of `0xFFFFFFFF` (bus error default) rather than the expected pattern, producing a spurious FAIL in your UART output.

## Vivado TCL Scripting

### Key Findings

- **Batch mode invocation**: `vivado -mode batch -source create_bd.tcl` runs headless; add `-tclargs "PART=xck26-sfvc784-2LV-c"` to pass the target part without hardcoding it in the script.
- **Export then strip**: GUI-generated designs can be exported via *File → Export → Export Block Design*, producing a `.tcl` that recreates the exact IP configuration. Remove the `create_project` and `set_part` lines to make it portable to a non-project wrapper.
- **Non-project mode caveat**: In non-project mode (`open_project` is never called), `create_bd_design` works only if you have called `link_design -part <part>` first to establish a target device context.
- **Idempotent scripts**: Guard `create_project` with `file exists` checks so repeated runs (CI re-runs) do not fail on pre-existing directories.
- **`get_bd_cells` filtering**: Use `-hierarchical -filter {VLNV =~ "xilinx.com:ip:axi_bram_ctrl:*"}` rather than hardcoded instance names to make scripts resilient to IP version bumps.

### Code Example

```tcl
#!/usr/bin/env tclsh
# Portable batch entry point for create_bd.tcl
# Usage: vivado -mode batch -source build.tcl -tclargs "xck26-sfvc784-2LV-c" "kv260_proj"

set part    [lindex $argv 0]
set projdir [lindex $argv 1]

# Guard: skip if project already exists
if {![file exists ${projdir}/${projdir}.xpr]} {
  create_project ${projdir} ./${projdir} -part ${part} -force
} else {
  open_project ./${projdir}/${projdir}.xpr
}

source create_bd.tcl          ;# creates block design
source synth_impl.tcl         ;# synthesis + implementation
```

### Relevance to Your Project

Your repository already has `create_bd.tcl`. Wrapping it with the guard pattern above lets your CI (or a fresh Vivado session) run reliably without manual cleanup of prior project directories, which is the most common cause of "file already exists" errors in CI pipelines.

## Vitis Bare-Metal / Standalone

### Key Findings

- **BSP regeneration**: After any XSA re-export from Vivado (address changes, IP updates), right-click the platform in Vitis → *Update Hardware Specification* → *Regenerate BSP Sources*; stale BSP headers (`xparameters.h`) will keep the old base addresses and cause silent FAIL.
- **`xil_printf` vs `printf`**: `xil_printf` is a lightweight UART-only formatter with no `%f` support; use `printf` (requires enabling the stdlib in BSP settings) for floating-point. `xil_printf` is correct for your demo.
- **Linker script memory regions**: The default standalone linker script places `.text` in DDR (`ps_ddr_0`) at `0x00000000`; for bare-metal on Kria, the FSBL unlocks DDR before handing off, so the default layout is correct. Do not place `.text` in OCM unless you need sub-µs latency.
- **`Xil_DCacheFlushRange`**: After writing a block to a cached DDR address (or AXI-mapped BRAM if caching is incorrectly enabled), flush the D-cache before reading back; otherwise you may read stale cache lines rather than actual PL memory contents.
- **Interrupt controller**: The Zynq UltraScale+ GIC-400 requires explicit initialization via `XScuGic_CfgInitialize` even in polling-mode demos — failure to initialize leaves the GIC in a state that can trap spurious interrupts.
- **KV260 template**: The community `miya4649/Vitis_KV260_KR260_Template` on GitHub provides a working bare-metal project skeleton that configures the FSBL, PMU firmware, and app ELF correctly for the 2025.x unified IDE.

### Code Example

```c
#include "xil_io.h"
#include "xil_printf.h"
#include "xil_cache.h"

#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL
#define TEST_PATTERN 0xDEADBEEFUL

int main(void) {
    u32 readback;

    /* Disable D-cache for AXI-mapped peripherals to avoid stale reads */
    Xil_SetTlbAttributes(BRAM0_BASE, NORM_NONCACHE);
    Xil_SetTlbAttributes(BRAM2_BASE, NORM_NONCACHE);

    Xil_Out32(BRAM0_BASE, TEST_PATTERN);
    Xil_Out32(BRAM2_BASE, ~TEST_PATTERN);

    readback = Xil_In32(BRAM0_BASE);
    if (readback == TEST_PATTERN) {
        xil_printf("BRAM0 PASS: 0x%08X\r\n", readback);
    } else {
        xil_printf("BRAM0 FAIL: got 0x%08X\r\n", readback);
    }

    readback = Xil_In32(BRAM2_BASE);
    if (readback == (~TEST_PATTERN & 0xFFFFFFFF)) {
        xil_printf("BRAM2 PASS: 0x%08X\r\n", readback);
    } else {
        xil_printf("BRAM2 FAIL: got 0x%08X\r\n", readback);
    }

    return 0;
}
```

### Relevance to Your Project

The `Xil_SetTlbAttributes` call is critical for your demo: if the Cortex-A53 MMU maps the AXI BRAM region as cacheable, `Xil_In32` may return cached data from a previous write rather than the actual BRAM contents, producing a false PASS. Mark both `0xA0000000` and `0xA0010000` as non-cacheable device memory.

## XDC Timing Constraints

### Key Findings

- **`set_input_delay` / `set_output_delay`**: These constrain the external board-level delay relative to a reference clock. For AXI-only internal PL designs (no board I/O except clocks), you typically only need a `create_clock` constraint; `set_input/output_delay` apply to I/O pins going off-chip.
- **False paths for reset**: Add `set_false_path -from [get_ports sys_rst_n]` to prevent Vivado from attempting to time asynchronous reset de-assertion paths across clock domains.
- **Clock groups**: If your design uses the Zynq PS clock (`clk_fpga_0`) and an independent PL clock, declare them as asynchronous with `set_clock_groups -asynchronous -group {clk_fpga_0} -group {pl_clk}`.
- **Constraint Wizard**: For any new I/O interface, run the Timing Constraints Wizard (*Tools → Timing Constraints Wizard*) before writing constraints manually — it auto-generates correct `set_input_delay` templates with `-min`/`-max` pairs.
- **Timing closure tip**: On UltraScale+ Zynq, `clk_fpga_0` frequency is set by the PS block design property `PCW_FPGA0_PERIPHERAL_FREQMHZ`; confirm the XDC `create_clock` period matches this or timing analysis is meaningless.

### Code Example

```tcl
# Minimal XDC for KV260 bare-metal AXI-BRAM demo
# Only constraints needed: primary PL clock + async reset false path

# PS-sourced 100 MHz clock to PL fabric (adjust period to match BD setting)
create_clock -period 10.000 -name clk_fpga_0 [get_pins {zynq_ultra_ps_e_0/inst/PS8_i/PLCLK[0]}]

# Asynchronous reset: no timing path needed
set_false_path -from [get_pins {zynq_ultra_ps_e_0/inst/PS8_i/EMIOAXIRESETN[0]}]

# If using an MMCM-derived PL clock alongside PS clock, declare async relationship
# set_clock_groups -asynchronous \
#   -group [get_clocks clk_fpga_0] \
#   -group [get_clocks mmcm_clkout0]
```

### Relevance to Your Project

Your `kv260_top.vhd` wrapper most likely routes `pl_clk0` from the Zynq PS to the AXI BRAM logic. The `create_clock` constraint above ensures Vivado performs meaningful timing analysis on the AXI handshake paths. Without it, timing is unconstrained and Vivado may produce a bitfile that passes implementation but fails at runtime due to setup violations at higher board temperatures.

## Kria KV260 / K26 SoM

### Key Findings

- **Boot mode**: KV260 starter kits are **hardwired** to QSPI32 boot mode (the DIP switches are for reference only). The QSPI flash holds the pre-loaded firmware (FSBL + PMU FW + U-Boot) in two redundant A/B images.
- **FSBL requirement for bare-metal**: To run your own bare-metal application, you must build a `BOOT.BIN` containing: FSBL (built from Vitis for the K26 PS), PMU firmware (`pmufw.elf`), and your application ELF. The FSBL initializes DDR, enables the PS-PL interface, and releases the PL reset — without it, AXI transactions from the PS to `0xA0000000` will receive bus errors.
- **MIO pinout**: UART0 is on MIO[14:15] on the KV260 carrier (USB-UART bridge), which maps to `/dev/ttyUSBx` on the host. The PS I2C buses are on MIO bank 500 (1.8V). The SOM240_1 connector bridges MIO signals to the carrier board.
- **EMIO GPIO**: PL-side GPIO is accessible via EMIO — the path is: `ZynqMP GPIO (EMIO) → PL fabric → SOM240_1 pin → KV260 carrier net → connector`. The Pmod ports on KV260 use this path.
- **Power domains**: The K26 SoM has separate VCC_PSINTFP (0.85V PS core), VCC_PSINTLP (PS low-power), VCCO_PSPLL, and VCCO_PSIO domains, all provided by the carrier board power tree. The PL fabric runs from VCCINT (0.72V) and VCCO banks (1.8V or 3.3V depending on I/O standard).
- **Kria board files**: The Vivado 2025.1 board repository includes K26, KV260 CC entries; use `xilinx.com:kv260_som:part0:1.4` as the board part to get correct MIO presets and DDR4 configuration.

### Code Example

```bash
# Build BOOT.BIN for KV260 bare-metal demo using bootgen
# Requires: fsbl.elf, pmufw.elf, kv260_axi_bram.bit, app.elf

cat > boot.bif << 'EOF'
the_ROM_image:
{
    [bootloader, destination_cpu=a53-0] fsbl.elf
    [pmufw_image]                        pmufw.elf
    [destination_device=pl]              kv260_axi_bram.bit
    [destination_cpu=a53-0]              app.elf
}
EOF

bootgen -image boot.bif -arch zynqmp -o BOOT.BIN -w on
# Flash with: program_flash -f BOOT.BIN -fsbl fsbl.elf -flash_type qspi-x4-single
```

### Relevance to Your Project

The `BOOT.BIN` construction above is the exact artifact needed to run your AXI-BRAM demo on real hardware. The `.bit` file programs the PL fabric (enabling the BRAM controllers), and the FSBL releases the PS-PL reset so the AXI bus becomes active before `main()` executes.

## AMD/Xilinx Tool Updates (Vivado/Vitis 2025.x)

### Key Findings

- **Vivado 2025.1**: Full production support for Versal AI Edge Series Gen 2; Zynq UltraScale+ (K26) remains fully supported. UG973 v2025.1 is the primary release notes document.
- **Vivado 2025.2**: Introduced an **ultra-low-area mode** for `axi_smartconnect` IP via a new `STRATEGY` parameter — reduces LUT count for designs with few AXI masters/slaves (like your 1-master, 2-slave BRAM topology).
- **AXI Interconnect deprecated**: The legacy `axi_interconnect` IP is deprecated in 2025.x; AMD recommends migrating to `axi_smartconnect`. If your `create_bd.tcl` still uses `axi_interconnect`, migrate before Vivado removes it entirely.
- **Vitis AI 5.0**: Compatible with Vivado/Vitis 2025.1; DPU IP verified — relevant if you plan to add inference to the KV260 later.
- **Known issue (2026.x)**: AMD article 000040220 documents Vitis 2026.x known issues; check adaptive support for the latest 2025.1-specific errata at `adaptivesupport.amd.com`.
- **Vitis Unified IDE**: The 2025.1 unified IDE consolidates HLS, application development, and platform management under one tool; the "component" model replaces the older workspace/domain structure. Bare-metal application projects are now "Application Components."

### Code Example

```tcl

# OLD (deprecated):

# NEW (2025.x recommended):

                    [get_bd_intf_pins axi_smartconnect_0/S00_AXI]

connect_bd_intf_net [get_bd_intf_pins axi_smartconnect_0/M00_AXI] \
                    [get_bd_intf_pins axi_bram_ctrl_0/S_AXI]
connect_bd_intf_net [get_bd_intf_pins axi_smartconnect_0/M01_AXI] \
                    [get_bd_intf_pins axi_bram_ctrl_1/S_AXI]
```

### Relevance to Your Project

If your `create_bd.tcl` uses `axi_interconnect`, replace it with the `axi_smartconnect` snippet above to future-proof the design against Vivado deprecation warnings and gain the area savings from `STRATEGY=MinArea` — ideal for a 1-to-2 fanout topology with only two BRAM slaves.
