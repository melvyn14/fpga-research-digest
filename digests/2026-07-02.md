# FPGA Research Digest - 2026-07-02

## Executive Summary
- **Critical Vivado 2025.x Breaking Change**: Block Memory Generator and FIFO Generator IPs are no longer instantiable from the standalone IP Catalog — they now require IP Integrator or migration to XPM_MEMORY macros. Your existing `create_bd.tcl` workflow using AXI BRAM Controller inside a block design is the correct approach and remains supported.
- **AXI-Lite Deadlock Risk**: A slave that waits for `WVALID` before asserting `AWREADY`, while the master waits for `AWREADY` before asserting `WVALID`, creates a hard deadlock. The Xilinx AXI BRAM Controller avoids this by accepting both channels independently, but any custom AXI-Lite wrapper must respect this rule.
- **KV260 JTAG Bare-Metal Boot**: Four files are required — `fsbl.elf`, `pmufw.elf`, bitstream (`.bit`), and application `.elf`. The XSDB command `mwr 0xffca0010 0x0` switches the board to JTAG mode; without this step the PS will not execute downloaded code.
- **Vitis 2025 BSP UART Pitfall**: After importing a new XSA, the platform shows "out-of-date" and `xil_printf` will silently drop output if stdout is mapped to the wrong UART instance (`psu_uart_0` vs `psu_uart_1`). Always verify the BSP setting and rebuild the platform before running tests.
- **Vivado 2025.2 Is Available**: AMD released 2025.2 after 2025.1 (which had no unresolved known issues at GA). 2025.2 introduces a known 1 KB address-space limit bug in custom AXI-Full peripheral templates — does not affect AXI BRAM Controller IP.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings
- **Five-channel independence**: AXI separates write address (AW), write data (W), write response (B), read address (AR), and read data (R) into independent channels precisely so slow responses on one channel do not block others. This enables pipelining between `BRAM0` and `BRAM2` in your design.
- **AWVALID/WVALID ordering**: The AXI spec allows write data to arrive on W before the address is accepted on AW, simultaneously, or after. Masters must NOT wait for `AWREADY` before asserting `WVALID` — doing so risks deadlock if the slave also waits.
- **Deadlock pattern to avoid**: A slave that gates `AWREADY` on `WVALID` AND a master that gates `WVALID` on `AWREADY` creates a circular dependency. The Xilinx AXI BRAM Controller accepts both independently, so this is safe on the slave side — but custom wrappers must not impose this ordering.
- **Backpressure propagation**: If `BREADY` (write response ready) is held low by the master, the slave must also lower `AWREADY` and `WREADY` to stop accepting new transactions. This is the most commonly missed backpressure case in simulation testbenches.
- **AXI-Lite vs AXI4**: AXI-Lite has no burst support, fixed 32-bit data width, and no byte-enable strobe support (though `WSTRB` is still present). For simple register-mapped BRAM access as in this project, AXI-Lite is correct and sufficient.

### Code Example
```c
/* Bare-metal AXI-Lite write followed by read-back with explicit ordering.
   The PS AXI master handles the handshake automatically, but correct
   address alignment is the application's responsibility. */
#include "xil_io.h"

#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL
#define PATTERN     0xDEADBEEFUL

static int axi_bram_write_read_test(u32 base, u32 pattern)
{
    /* Write: PS AXI master drives AWVALID+WVALID, waits for BVALID */
    Xil_Out32(base + 0x00, pattern);
    Xil_Out32(base + 0x04, ~pattern);

    /* Memory barrier: ensures write completes before read */
    Xil_DCacheFlush();

    /* Read back and verify */
    u32 r0 = Xil_In32(base + 0x00);
    u32 r1 = Xil_In32(base + 0x04);

    return (r0 == pattern && r1 == ~pattern) ? 0 : -1;
}
```

### Relevance to Your Project
Your `main.c` writes a pattern to `BRAM0` at `0xA0000000` and `BRAM2` at `0xA0010000` and reads back to check PASS/FAIL. The critical correctness point is that `Xil_Out32` / `Xil_In32` use AXI-Lite transactions driven by the Cortex-A53 interconnect; without a data cache flush or memory barrier between writes and reads, the CPU cache may satisfy reads from its own write buffer rather than from BRAM, producing false PASSes.

## Vivado Block Design / IP Integrator

### Key Findings
- **Address Editor auto-assign**: When block design validation reports unmapped peripherals, right-click anywhere in the Address Editor tab and select "Auto-Assign Address." The TCL equivalent is `assign_bd_address` — no arguments needed; Vivado assigns non-overlapping ranges automatically.
- **Preferred constraint after auto-assign**: Use `set_property range 64K [get_bd_addr_segs ...]` to pin the BRAM range explicitly, preventing range changes if IPs are re-added.
- **Export to TCL for version control**: `File → Project → Write Tcl` with "Recreate Block Designs using Tcl" checked produces a self-contained script. This is how reproducible builds like your `create_bd.tcl` are generated; note that exported scripts are version-specific and may not work across major Vivado releases without minor edits.
- **Vivado 2025.x IP Integrator change**: The Block Memory Generator (`blk_mem_gen`) is now only accessible inside a block design (IP Integrator), not as a standalone IP in RTL flows. In block designs it remains fully supported. The AXI BRAM Controller still pairs with it correctly.
- **Connection Automation**: After placing the Zynq UltraScale+ PS and AXI BRAM Controller, clicking "Run Connection Automation" wires the AXI interconnect, clock, and reset. It also creates the Block Memory Generator automatically if you selected "AXI BRAM Controller" mode.

### Code Example
```tcl
# Minimal TCL to assign BRAM addresses after auto-placement
# Run after create_bd.tcl has instantiated IP cores

# Auto-assign all unmapped slave segments
assign_bd_address

# Lock BRAM0 at 0xA000_0000, 64 KB
set seg0 [get_bd_addr_segs {ps_e/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property offset 0xA0000000 $seg0
set_property range  64K        $seg0

# Lock BRAM2 at 0xA001_0000, 64 KB
set seg2 [get_bd_addr_segs {ps_e/Data/SEG_axi_bram_ctrl_2_Mem0}]
set_property offset 0xA0010000 $seg2
set_property range  64K        $seg2

validate_bd_design
save_bd_design
```

### Relevance to Your Project
Your `create_bd.tcl` sets `BRAM0` at `0xA0000000` and `BRAM2` at `0xA0010000`. The snippet above shows how to lock these addresses programmatically, which is important if the block design is ever regenerated — auto-assign may produce different offsets without explicit anchoring.

## Vivado TCL Scripting

### Key Findings
- **Project mode vs non-project mode**: Project mode (`create_project`, `launch_run`) manages output products automatically. Non-project mode (`read_vhdl`, `synth_design`, `opt_design`, `place_design`, `route_design`, `write_bitstream`) gives full control but requires manual tracking of which stages need re-running after source changes.
- **Batch synthesis one-liner**: `vivado -mode batch -source run_impl.tcl -nojournal` runs headlessly; combine with `-tclargs` to pass parameters.
- **launch_run with wait**: In project mode, `launch_runs impl_1 -to_step write_bitstream` followed by `wait_on_run impl_1` is the recommended pattern for scripted builds; it blocks until the bitstream is written.
- **Tcl error handling**: Use `catch { <cmd> } err` and check `$err` to handle IP generation failures gracefully in automation scripts.
- **Console-to-Tcl mapping**: Every GUI action in Vivado produces an equivalent TCL command in the console — copy from the Tcl Console immediately after performing an action to capture the exact command for your scripts.

### Code Example
```tcl
#!/usr/bin/env vivado -mode batch -source
# Non-project mode: synthesize + implement + bitstream in one script

# Read sources
read_vhdl    ../vhdl/kv260_top.vhd
read_xdc     ../xdc/kv260_top.xdc
read_ip      ../ip/axi_bram_ctrl_0/axi_bram_ctrl_0.xci

# Synthesize
synth_design -top kv260_top -part xck26-sfvc784-2LV-c

# Optimise, place, route
opt_design
place_design
phys_opt_design
route_design

# Reports
report_timing_summary -file timing_summary.rpt
report_utilization    -file utilization.rpt

# Write bitstream
write_bitstream -force kv260_top.bit
```

### Relevance to Your Project
Your `create_bd.tcl` uses project mode (`create_project`, `create_bd_design`). Adding a companion `run_impl.tcl` in non-project mode enables fully headless CI builds — push to git, trigger a build server, get a bitstream artifact — without opening the Vivado GUI.

## Vitis Bare-Metal / Standalone

### Key Findings
- **XSA replaces HDF**: The `.xsa` file exported from Vivado (`File → Export → Export Hardware`) is the hardware handoff for Vitis. Always re-export XSA after any block design change.
- **Platform "out-of-date" state**: After importing a new XSA, the platform shows "out-of-date." Right-click the platform project → "Build Project" before running the application. Skipping this step means the BSP is built against the old hardware description.
- **UART stdout mapping**: In the BSP settings (`Board Support Package Settings`), both `stdin` and `stdout` must point to the correct UART instance. On KV260, the USB-UART bridge typically maps to `psu_uart_1`. Wrong mapping = `xil_printf` outputs nothing.
- **Vitis Unified IDE vs Classic**: Vitis 2023.2+ defaults to the Unified IDE, which uses a system device tree (SDT) and Python-based xparameters generation instead of HSI. For bare-metal projects targeting a single core (PSU_cortexa53_0), both modes work, but Classic mode is more familiar for existing flows.
- **Linker script for bare-metal**: The default `lscript.ld` places code in `psu_ddr_0_MEM_0` starting at `0x0`. For Kria, ensure the DDR region `0x00000000 - 0x7FFFFFFF` (2 GB) is correctly sized and the stack/heap are adequate for your application.

### Code Example
```c
/* Minimal bare-metal standalone template for KV260 AXI-BRAM test.
   Assumes BSP stdout = psu_uart_1 in BSP settings. */
#include "xil_printf.h"
#include "xil_io.h"
#include "sleep.h"

#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL

int main(void)
{
    xil_printf("KV260 AXI-BRAM Test Starting...\r\n");

    /* Write test pattern to both BRAMs */
    Xil_Out32(BRAM0_BASE, 0xCAFEBABEUL);
    Xil_Out32(BRAM2_BASE, 0xDEADBEEFUL);

    /* Read back and verify */
    u32 v0 = Xil_In32(BRAM0_BASE);
    u32 v2 = Xil_In32(BRAM2_BASE);

    if (v0 == 0xCAFEBABEUL && v2 == 0xDEADBEEFUL) {
        xil_printf("PASS: BRAM0=0x%08X BRAM2=0x%08X\r\n", v0, v2);
    } else {
        xil_printf("FAIL: BRAM0=0x%08X (exp 0xCAFEBABE) "
                   "BRAM2=0x%08X (exp 0xDEADBEEF)\r\n", v0, v2);
    }

    return 0;
}
```

### Relevance to Your Project
This matches the architecture of your `main.c`. The key addition here is the explicit `\r\n` in `xil_printf` — terminal emulators on bare-metal UART connections require `\r\n` (carriage return + line feed); using `\n` alone results in text that stair-steps rather than wrapping on new lines in minicom/PuTTY.

## XDC Timing Constraints

### Key Findings
- **PL clock source on KV260**: The programmable logic on K26 SoM must receive its clock from the PS block. There is no external PL clock oscillator on the KV260 carrier card. The PS generates clocks via its PLL (typically `pl_clk0` at 100 MHz) which must be connected to the design clock network in the block design.
- **AXI-Lite internally timed**: All AXI-Lite signals between PS and the AXI BRAM Controller are internal to the FPGA fabric and driven by the same `pl_clk0`. No `set_input_delay` / `set_output_delay` constraints are needed for AXI-Lite paths — Vivado's timing engine handles them automatically as register-to-register paths.
- **set_clock_groups best practice**: Use one `set_clock_groups -asynchronous` to declare all unrelated clock domains globally rather than many `set_false_path` constraints. This prevents missing new cross-domain paths added later.
- **False path for PS internal clocks**: Paths crossing from the PS internal domain to PL logic should be constrained with `set_clock_groups -asynchronous -group [get_clocks clk_pl_0] -group [get_clocks ...]` if multiple PL clocks exist.
- **Constraint wizard**: Vivado's Timing Constraint Wizard (run after synthesis) is the fastest way to generate correct clock constraints — run it once for clocks, once for I/O delays if any external I/O is present.

### Code Example
```xdc
# kv260_top.xdc — minimal constraints for PS-to-PL AXI-BRAM design

# pl_clk0 is generated by the Zynq PS block; 100 MHz
# Vivado auto-creates this constraint from the block design,
# but it is shown here explicitly for clarity.
create_clock -period 10.000 -name clk_pl_0 \
    [get_pins ps_e/inst/PS8_i/PLCLK[0]]

# If a second PL clock is used (e.g., pl_clk1 at 200 MHz):
# create_clock -period 5.000 -name clk_pl_1 \
#     [get_pins ps_e/inst/PS8_i/PLCLK[1]]

# Declare the two PL clocks as asynchronous to each other
# (only needed if your design uses both simultaneously)
# set_clock_groups -asynchronous \
#     -group [get_clocks clk_pl_0] \
#     -group [get_clocks clk_pl_1]

# No I/O timing constraints needed for AXI-Lite (internal paths only)
# Add set_false_path for any asynchronous external inputs (e.g., push buttons)
set_false_path -from [get_ports {reset_n}]
```

### Relevance to Your Project
For your single-clock AXI-BRAM design, the only constraint required is the `create_clock` for `pl_clk0`. If Vivado generates timing violations even with this constraint, the most common cause is forgetting to connect `pl_clk0` to the AXI interconnect's `ACLK` port in the block design — check the block design clock connections first.

## Kria KV260 / K26 SoM

### Key Findings
- **Default boot mode**: KV260 ships with QSPI32 boot mode (pre-loaded boot firmware in QSPI NOR flash). For bare-metal JTAG development, you need to force JTAG mode via XSDB: `mwr 0xffca0010 0x0` on the PMU, then `targets 8; con` on A53 core 0.
- **Four-file JTAG boot sequence**: FSBL (`fsbl.elf`) → PMU firmware (`pmufw.elf`) → Bitstream (`.bit`) → Application (`.elf`). All four must be loaded via XSDB `dow` commands. Missing `pmufw.elf` is the most common cause of silent hang at boot.
- **PL loaded after PS boot**: For KV260 Linux flows, PL overlays are loaded dynamically — do not package PL bitstream into `boot.bin` for the standard Kria OS flow. For bare-metal, FSBL loads the bitstream directly, which is correct.
- **Memory map for PL peripherals**: PL AXI peripherals appear in the PS memory space at addresses assigned in the block design. Your BRAM0 at `0xA0000000` and BRAM2 at `0xA0010000` are in the standard PL AXI GP0 aperture (`0xA0000000–0xAFFFFFFF`).
- **EMIO vs MIO**: MIO pins (multiplexed I/O) connect directly to the PS. EMIO pins route through the PL fabric. UART0 (`psu_uart_0`) and UART1 (`psu_uart_1`) typically connect via MIO; the USB-UART on KV260 carrier card connects via MIO to `psu_uart_1` (pins MIO48/MIO49).

### Code Example
```tcl
# XSDB script for JTAG bare-metal boot on KV260
# Run in Vitis XSDB console: xsdb boot_jtag.tcl

connect

# Switch to JTAG boot mode
targets -set -filter {name =~ "PSU"}
mwr 0xffca0010 0x0   ;# JTAG boot mode
rst -system

# Load PMU firmware first (required for PS initialization)
targets -set -filter {name =~ "MicroBlaze PMU"}
dow pmufw.elf
con

# Load FSBL on A53 core 0
targets -set -filter {name =~ "Cortex-A53 #0"}
rst -processor
dow fsbl.elf
con

# Wait for FSBL to complete DDR init, then load bitstream + app
after 3000
dow kv260_top.bit
dow hello_bram.elf
con

puts "Boot sequence complete. Check UART terminal."
```

### Relevance to Your Project
This XSDB script is the exact flow needed to test your `kv260-axi-bram-demo` on hardware. The `after 3000` delay is important — FSBL must complete DDR calibration before the bitstream and application can be loaded. Loading too early results in the application running without the PL configured, causing AXI reads/writes to return garbage or hang.

## AMD/Xilinx Tool Updates (2025.x)

### Key Findings
- **Vivado 2025.1 Block Memory Generator deprecated for standalone**: `blk_mem_gen` can no longer be instantiated as a standalone RTL IP; it is only supported inside IP Integrator block designs. Migration path: use `XPM_MEMORY_SPROM`/`XPM_MEMORY_DPROM`/`XPM_MEMORY_SDPRAM` Xilinx Parameterized Macros in RTL instead.
- **Vivado 2025.2 AXI peripheral address-space bug**: Custom AXI-Full slave peripheral templates generated by Vivado 2025.2 are limited to 1 KB usable address space. Workaround: use the AXI BRAM Controller IP (not the template wizard) or manually fix the address decode logic. Your design uses the AXI BRAM Controller and is **not affected**.
- **New in 2025.1 — Dynamic PL loading**: Vivado 2025.1 introduces first-class support for booting the PS first and loading PL dynamically, including new bitstream partial reconfiguration improvements. This enables faster OS boot on Kria platforms.
- **New in 2025.1 — RTL-based AXI Switch IP**: A new fully customizable RTL-based AXI Switch IP allows bridging between different AXI interface types and widths — useful for future design expansion beyond the current two-BRAM topology.
- **Vitis 2025 Unified IDE**: The Unified IDE is now the primary workflow; "Classic" (Vitis 2022-era) is still available but not the default. Key difference: Unified IDE uses System Device Tree (SDT) for xparameters generation; `xparameters.h` structure is unchanged but the generation pipeline is Python-based.
- **2025.2 now available**: AMD released 2025.2 after 2025.1. If upgrading, regenerate the XSA and rebuild the platform to pick up any IP updates; block designs created in 2025.1 should open in 2025.2 with minor IP version prompts.

### Code Example
```vhdl
-- XPM BRAM replacement for RTL flows (Vivado 2025.1+)
-- Replaces blk_mem_gen when not using IP Integrator
library xpm;
use xpm.vcomponents.all;

-- Single-port ROM example using XPM_MEMORY
xpm_memory_sprom_inst : xpm_memory_sprom
  generic map (
    ADDR_WIDTH_A        => 10,       -- 1024 depth
    DATA_WIDTH_A        => 32,       -- 32-bit wide
    READ_LATENCY_A      => 1,        -- 1-cycle read latency
    MEMORY_SIZE         => 32768,    -- bits: 1024 * 32
    MEMORY_PRIMITIVE    => "block",  -- use BRAM not LUT-RAM
    MEMORY_INIT_FILE    => "none",
    USE_MEM_INIT        => 0
  )
  port map (
    addra  => addr,
    douta  => data_out,
    clka   => clk,
    ena    => en,
    rsta   => rst,
    regcea => '1',
    sbiterra => open,
    dbiterra => open
  );
```

### Relevance to Your Project
Your current design uses `blk_mem_gen` inside a block design via the AXI BRAM Controller — this is fully supported in 2025.1 and is the **correct** approach. The XPM snippet above is relevant if you ever want to add a second BRAM that is NOT AXI-accessible (e.g., a local FIFO buffer in your VHDL top-level) — in that case, use XPM rather than trying to instantiate a legacy `blk_mem_gen` core in 2025.1 RTL.
