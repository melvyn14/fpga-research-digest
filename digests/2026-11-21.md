# FPGA Research Digest - 2026-11-21

## Executive Summary
- **AXI-Lite handshake bug pattern** in Vivado-generated slaves: the slave must keep VALID high and data stable until READY is asserted—never de-assert VALID prematurely; ZipCPU formal verification exposed this in multiple Xilinx template versions.
- **AXI BRAM Controller read-latency mismatch** causes incorrect read data: the latency setting in the AXI BRAM Controller IP must exactly match the BRAM Generator's output-latency parameter (typically both set to 2 for registered output).
- **Non-project mode in Vivado 2025.1** requires block designs to be fully generated before `read_bd` is called; `upgrade_ip [get_ips -all]` can silently fail—use explicit IP names instead.
- **Vitis BSP UART mismatch** on KV260: the BSP defaults stdout/stdin to UART0 but the USB-UART bridge on the KV260 is wired to UART1; fix by changing the standalone BSP settings in the Vitis IDE before building.
- **Vivado 2025.1 adds VHDL 2019 simulation constructs** and new Spartan UltraScale+ production device support; `report_dfx_summary` is now GUI-accessible.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings
- A transfer on AXI-Lite occurs only when both `AWVALID`/`WVALID` and `AWREADY`/`WREADY` are simultaneously asserted; the slave must accept both address and data before asserting `BVALID`.
- The **VALID-must-not-depend-on-READY** rule is the most commonly violated: once a master asserts VALID it may not de-assert it until READY is seen. Vivado-generated AXI-Lite slave templates have been found to violate this for the READY lines on the response channel (B and R channels).
- In Xilinx AXI BRAM Controller (single-port mode), Port A handles both reads and writes; the controller serializes accesses but does **not** detect read/write port collisions—software must avoid simultaneous overlapping accesses.
- AXI-Stream: `TLAST` and all payload signals (`TDATA`, `TUSER`, `TKEEP`) must remain stable while `TVALID` is asserted but `TREADY` is low; changing `TLAST` while stalled is a classic source of packet-boundary corruption.
- `XPM_FIFO_AXIS` (2025.1) correctly models the TVALID/TREADY/TLAST handshake—use it in place of hand-coded FIFOs to avoid handshake bugs.

### Code Example
```vhdl
-- AXI-Lite slave: correct read response sequence
-- RVALID must stay high until RREADY is seen
process(clk)
begin
  if rising_edge(clk) then
    if s_axi_arvalid = '1' and s_axi_arready = '1' then
      rdata_reg  <= bram_dout;
      s_axi_rvalid_i <= '1';          -- assert, then hold
    elsif s_axi_rvalid_i = '1' and s_axi_rready = '1' then
      s_axi_rvalid_i <= '0';          -- clear only after handshake
    end if;
  end if;
end process;
s_axi_rvalid <= s_axi_rvalid_i;
s_axi_rdata  <= rdata_reg;
s_axi_rresp  <= "00";
```

### Relevance to Your Project
Your `kv260_top.vhd` connects Cortex-A53 AXI-Lite master outputs to two BRAM controllers. Ensuring the read-valid hold pattern above is correct in any custom slave wrapper prevents silent read failures that show as FAIL on UART without an obvious bus error. Run the ZipCPU AXI-Lite formal properties (`faxi_slave.v`) in xsim against your wrapper as a sanity check.

## Vivado Block Design / IP Integrator

### Key Findings
- **Connection Automation**: after running `apply_bd_automation`, always verify the generated AXI Interconnect has the correct number of master/slave ports—automation sometimes misses a port when IP is added out of order.
- **Address Editor**: each slave must have a unique, non-overlapping address range. For the KV260 AXI-BRAM demo, BRAM0 at `0xA000_0000` and BRAM2 at `0xA001_0000` require the ranges to be explicitly set; automation may default both to the same base.
- **Regenerating the block design**: after any IP version upgrade, run `validate_bd_design` before re-generating outputs—this surfaces connectivity errors before the lengthy synthesis step.
- In Vivado 2025.1, `report_dfx_summary` is now accessible from the Reports menu, simplifying DFX (Dynamic Function eXchange) debugging for designs that use partial reconfiguration.

### Code Example
```tcl
# In Vivado Tcl console: set addresses after apply_bd_automation
assign_bd_address [get_bd_addr_segs {axi_bram_ctrl_0/S_AXI/Mem0}]
set_property offset 0xA0000000 [get_bd_addr_segs \
    {processing_system7_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property range 64K [get_bd_addr_segs \
    {processing_system7_0/Data/SEG_axi_bram_ctrl_0_Mem0}]

assign_bd_address [get_bd_addr_segs {axi_bram_ctrl_2/S_AXI/Mem0}]
set_property offset 0xA0010000 [get_bd_addr_segs \
    {processing_system7_0/Data/SEG_axi_bram_ctrl_2_Mem0}]
set_property range 64K [get_bd_addr_segs \
    {processing_system7_0/Data/SEG_axi_bram_ctrl_2_Mem0}]
```

### Relevance to Your Project
Your `create_bd.tcl` configures BRAM0 at `0xA000_0000` and BRAM2 at `0xA001_0000`. The snippet above mirrors that layout and can be dropped into your script after the automation step to guarantee correct addresses even if Vivado re-orders IP during regeneration.

## Vivado TCL Scripting

### Key Findings
- **Project mode script**: use `write_project_tcl` after a working manual project build to generate a reproducible script; re-run with `vivado -mode batch -source rebuild.tcl` to restore the full project.
- **Non-project mode (2025.1 UG994)**: block designs must be fully generated (`generate_target all`) before being referenced with `read_bd`; using `upgrade_ip [get_ips -all]` can cause silent failures—prefer explicit IP names.
- Tcl variables and procs in `~/.Vivado/Vivado_init.tcl` apply to every session; put common path helpers there to DRY up project scripts.
- In batch mode, omit `start_gui` and `open_run impl_1` to reduce runtime by roughly 15–20%.
- After `launch_runs impl_1 -to_step write_bitstream`, always check `[get_property STATUS [get_runs impl_1]]` before copying the bitstream—a background run that hits a constraint error can still return exit code 0 from `launch_runs`.

### Code Example
```tcl
# Minimal batch build script (project mode)
create_project kv260_demo ./kv260_demo -part xck26-sfvc784-2LV-c
set_property board_part xilinx.com:kv260_som:part0:1.4 [current_project]

add_files -norecurse ./vhdl/kv260_top.vhd
add_files -fileset constrs_1 -norecurse ./xdc/kv260_top.xdc

# Regenerate block design from TCL
source ./tcl/create_bd.tcl
make_wrapper -files [get_files *.bd] -top
add_files -norecurse [glob ./kv260_demo.gen/sources_1/bd/*/hdl/*.vhd]

set_property top kv260_top_wrapper [current_fileset]
update_compile_order -fileset sources_1

launch_runs impl_1 -to_step write_bitstream -jobs 4
wait_on_run impl_1
if {[get_property STATUS [get_runs impl_1]] ne "write_bitstream Complete!"} {
  error "Implementation failed"
}
```

### Relevance to Your Project
Combining `create_bd.tcl` with the wrapper above gives a single-command rebuild from a clean checkout, which is exactly the CI/batch story for your KV260 demo repo.

## Vitis Bare-Metal / Standalone

### Key Findings
- **UART BSP mismatch on KV260**: the standalone BSP defaults `stdin`/`stdout` to `psu_uart_0` (UART0), but the KV260 USB-UART bridge is physically wired to `psu_uart_1` (UART1). Set the BSP `stdin` and `stdout` to `psu_uart_1` under *BSP Settings → standalone → stdin/stdout* before building; `xil_printf` will silently produce no output otherwise.
- **BSP regeneration**: after any hardware platform update (new `.xsa`), always right-click the BSP and select *Update BSP Sources*—stale driver headers cause subtle runtime failures that look like AXI bus errors.
- **Interrupt controllers**: for bare-metal with the GIC (Zynq UltraScale+), call `XScuGic_CfgInitialize` and `Xil_ExceptionEnable` before registering any handler; a missing `Xil_ExceptionInit()` leaves the processor in an inconsistent exception state.
- Vitis 2025.1 release notes list new DSP library functions and additional AI Engine APIs; for a bare-metal AXI project these don't add immediate value but indicate AMD's focus on the accelerated embedded path.

### Code Example
```c
/* Minimal AXI-Lite read/write test over xil_io, as used in main.c */
#include "xil_io.h"
#include "xil_printf.h"

#define BRAM0_BASE 0xA0000000UL
#define BRAM2_BASE 0xA0010000UL
#define TEST_PATTERN 0xDEADBEEFUL

static int bram_test(u32 base, const char *name)
{
    Xil_Out32(base, TEST_PATTERN);
    u32 val = Xil_In32(base);
    if (val == TEST_PATTERN) {
        xil_printf("%s PASS (0x%08X)\r\n", name, val);
        return 0;
    }
    xil_printf("%s FAIL: wrote 0x%08X read 0x%08X\r\n",
               name, TEST_PATTERN, val);
    return -1;
}

int main(void)
{
    xil_printf("KV260 AXI-BRAM test\r\n");
    int rc = 0;
    rc |= bram_test(BRAM0_BASE, "BRAM0");
    rc |= bram_test(BRAM2_BASE, "BRAM2");
    xil_printf(rc == 0 ? "ALL PASS\r\n" : "FAILURES DETECTED\r\n");
    return rc;
}
```

### Relevance to Your Project
This mirrors the structure of your `main.c`. If you are seeing garbage or no output on the UART terminal, the BSP `stdout` → `psu_uart_1` fix is the first thing to check; it explains all PASS/FAIL output disappearing silently.

## XDC Timing Constraints

### Key Findings
- **Constraint ordering (UG903 2026.1)**: define I/O delays (`set_input_delay`, `set_output_delay`) *before* timing exceptions (`set_max_delay`, `set_false_path`) in the XDC file; out-of-order definitions can cause Vivado to silently ignore a constraint.
- **`set_clock_groups -asynchronous`**: this command takes *precedence* over `set_max_delay` and `set_false_path`; it does not combine with XPM CDC constructs—if you use XPM async FIFOs, do not use `set_clock_groups` on those crossing clocks.
- For a bare-metal AXI-BRAM design on KV260 that uses only the PL fabric clock (`clk_wiz` or the Zynq PS fabric clock), you typically need only: (1) the board clock constraint (auto-imported from the board preset), and (2) a `set_clock_groups -asynchronous` between the PS clock domain and any PL-only clock.
- `set_input_delay` measured capture edge is after clock latencies by default; when measuring relative to a board-level source clock that the FPGA does not receive, add `-clock_fall` or use `create_generated_clock` on the loopback, otherwise Vivado may report false violations.

### Code Example
```tcl
# Minimal XDC for KV260 bare-metal AXI-BRAM demo
# PS supplies the AXI fabric clock; no external I/O on PL side

# (Board preset auto-creates the 300 MHz reference constraint)
# If you use a PL clock wizard from the PS clock:
create_generated_clock -name clk_pl_100 \
    -source [get_pins clk_wiz_0/clk_in1] \
    -master_clock [get_clocks clk_out1_clk_wiz_0] \
    [get_pins clk_wiz_0/clk_out1]

# Isolate PS and PL clocks (they share no data paths in pure AXI designs)
set_clock_groups -asynchronous \
    -group [get_clocks -include_generated_clocks clk_out1_clk_wiz_0] \
    -group [get_clocks -include_generated_clocks clk_pl_100]

# False path on configuration nets (optional but suppresses noise)
set_false_path -from [get_ports sys_rst_n]
```

### Relevance to Your Project
Your KV260 demo drives the AXI interconnect from the Zynq PS fabric clock passed through a clock wizard. This minimal XDC prevents spurious timing violations between the PS reference and PL clocks, while keeping the constraint file short and maintainable.

## Kria KV260 / K26 SoM

### Key Findings
- **MIO bank layout**: the K26 SoM exposes three MIO banks, all powered at 1.8V on the module; Bank 500 is reserved for QSPI, SPI, I2C, and eMMC; Bank 501 carries PMU power-management signals plus user I/O exposed through the SOM240 connectors (see DS987 Electrical Specifications).
- **Dynamic carrier MIO config**: unlike classic Zynq boards with static MIO, the Kria platform uses PMU-driven incremental MIO configuration at boot. For bare-metal bypassing U-Boot, you must configure the UART MIO mux registers manually or accept the FSBL defaults.
- **Boot modes**: the KV260 supports JTAG boot (ideal for development—load `.bit` and `.elf` directly over JTAG cable) and SD/QSPI boot for deployment. Set the boot-mode pins to `0b0000` (JTAG) via the DIP switch on the carrier card for bare-metal development.
- **Bitstream management**: in Vitis 2025.x on KV260, use the `Program Device` dialog to load both the bitstream and the application ELF via JTAG; the tool sequences FSBL → bitstream → ELF automatically.
- The KV260 USB-UART (Micro-USB J4) is wired to `psu_uart_1` at MIO pins 36/37.

### Code Example
```tcl
# Vivado: set KV260 board part for automatic PS/PL preset including UART1
set_property board_part xilinx.com:kv260_som:part0:1.4 [current_project]

# After create_bd.tcl creates the Zynq PS block:
# Apply board preset to auto-configure UART1 MIO and DDR
apply_bd_automation -rule xilinx.com:bd_rule:zynq_ultrascale_mpsoc \
    -config {apply_board_preset 1} \
    [get_bd_cells zynq_ultra_ps_e_0]
```

### Relevance to Your Project
Applying the board preset in `create_bd.tcl` ensures UART1 MIO pins 36/37 are configured for `psu_uart_1`, which is the physical USB-UART path you use for PASS/FAIL output. Without the preset, the PS block leaves those MIO in GPIO mode and UART output is lost.

## AMD/Xilinx Tool Updates (Vivado/Vitis 2025.x)

### Key Findings
- **Vivado 2025.1**: added production support for Spartan UltraScale+ devices (XCSU10P, XCSU25P, XCSU35P); GUI now surfaces `report_dfx_summary` for DFX debugging; unified selective device installer for all Versal devices.
- **VHDL 2019 simulation constructs** are now supported in Vivado 2025.1 (`-language vhdl_2019` in `xvhdl`), including conditional compilation and package generics—useful for parameterized testbenches.
- **Vitis 2025.1**: new and enhanced DSP library functions; Vitis AI 5.1 adds support for VE2202/VE2602/VE2802/VE2302 Versal devices; Apptainer supported as Docker alternative.
- **Vivado 2025.2** release notes (November 2025): available on docs.amd.com; check UG973 for the 2025.1 known-issues list (Answer Records), which is not surfaced in the main release notes page.
- `upgrade_ip [get_ips -all]` is explicitly flagged as unsafe in UG896 2025.x—it can cause silent failures when IPs have interdependencies. Upgrade individual IPs by name.

### Code Example
```vhdl
-- VHDL 2019: package with generic type (Vivado 2025.1+, xvhdl -language vhdl_2019)
package bram_pkg is
  generic (
    type T;
    DATA_WIDTH : positive := 32
  );
  function zero_word return T;
end package;

-- Compile flag in Vivado Tcl:
-- set_property FILE_TYPE {VHDL 2019} [get_files kv260_top.vhd]
```

### Relevance to Your Project
Enabling VHDL 2019 on `kv260_top.vhd` lets you parameterize the AXI address and data widths without resorting to generics workarounds. The `report_dfx_summary` GUI addition is not directly relevant to a static design but useful if you later add partial reconfiguration to swap BRAM workloads at runtime.
