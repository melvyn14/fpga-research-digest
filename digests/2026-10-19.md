# FPGA Research Digest - 2026-10-19

## Executive Summary

- **AXI-Lite BVALID/BREADY trap**: BVALID must not be asserted before the final write-data handshake completes; slaves that only worked with BREADY tied high are a common bug pattern — the AMD AXI Protocol Checker (PG101) catches this in simulation where synthesis cannot.
- **Vivado 2025.1 new RTL AXI Switch IP**: Unlike SmartConnect (IPI-only), the new AXI Switch can be instantiated in RTL flows, handles cross-width/type bridging, and simplifies per-interface clock/reset wiring — directly relevant when adding PL peripherals on the KV260.
- **PL clock sourced exclusively from PS on KV260**: The KV260 has no standalone PL oscillator; the PS PL0 clock (default 100 MHz, set by FSBL) is the only clock source. Use a Clocking Wizard to derive other frequencies; changing the PS clock requires regenerating the FSBL.
- **`upgrade_ip [get_ips -all]` is dangerous**: `-all` includes sub-cores that may be deleted during parent upgrade, leaving dangling Tcl references. Upgrade only named top-level IPs.
- **Non-project Vivado flow requires explicit checkpoints and reports**: `write_checkpoint` after each stage and explicit `report_timing_summary` / `report_utilization` calls are mandatory — the project-mode auto-generation does not apply.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- **BVALID ordering rule**: BVALID must only be asserted after the final write-data handshake (`WVALID & WREADY`) completes. WVALID, WREADY, and BVALID may overlap in the same clock cycle, but never for the same transaction. Violating this is a legal but silent synthesis error.
- **BREADY pre-assertion is legal**: A master may raise BREADY before the slave raises BVALID, collapsing the write-response to one cycle. Designs that only work when BREADY is tied high are broken; the AMD Protocol Checker (PG101) will flag this.
- **Simultaneous read/write arbitration**: If both AWVALID and ARVALID fire in the same cycle to an unguarded slave, both transactions may be silently dropped. Add arbitration logic that accepts writes only when no read is in-flight (or vice versa), using combinational READY masking.
- **VALID must stay high until handshake**: Once AWVALID/WVALID/ARVALID is asserted, it must remain high until the corresponding READY goes high. Lowering VALID early creates protocol violations that AXI protocol checkers detect but simulation waveforms can hide.
- **Use AMD AXI Protocol Checker (PG101)**: Add it in simulation to catch ordering violations that synthesis tools cannot flag.

### Code Example

```vhdl
-- AXI-Lite write-response state machine: correct BVALID sequencing
-- BVALID must only rise AFTER the WVALID/WREADY handshake
process(clk)
begin
  if rising_edge(clk) then
    if rst = '1' then
      bvalid_r  <= '0';
      wdata_accepted <= '0';
    else
      -- Capture write-data acceptance
      if s_axi_wvalid = '1' and s_axi_wready = '1' then
        wdata_accepted <= '1';
      end if;
      -- Only assert BVALID after write data accepted
      if wdata_accepted = '1' then
        bvalid_r <= '1';
        wdata_accepted <= '0';
      end if;
      -- Deassert after master accepts response
      if bvalid_r = '1' and s_axi_bready = '1' then
        bvalid_r <= '0';
      end if;
    end if;
  end if;
end process;
s_axi_bvalid <= bvalid_r;
s_axi_bresp  <= "00"; -- OKAY
```

### Relevance to Your Project

Your `main.c` performs write-then-readback cycles to BRAM0 (0xA0000000) and BRAM2 (0xA0010000) via AXI-Lite. If the AXI BRAM Controller's BVALID is raised too early, the Cortex-A53 may sample a spurious response; adding the AMD AXI Protocol Checker in your simulation testbench will catch this before hardware bring-up. The simultaneous R/W pitfall is relevant if you ever add a second AXI master to the block design.

## Vivado Block Design / IP Integrator

### Key Findings

- **`write_bd_tcl` for reproducible builds**: Export the block design to a sourceable Tcl file. Only user-modified parameters are written (not IP defaults or tool-adjusted values after propagation), so the file is minimal and diff-friendly.
- **Canvas layout not saved by default**: Pass `-include_layout` to `write_bd_tcl` to preserve IP block positions on the IPI canvas.
- **Version lock-in**: Scripts generated by `write_bd_tcl` are tied to the Vivado release that created them. Do not source them in a different version without re-exporting.
- **Avoid `upgrade_ip [get_ips -all]`**: The `-all` flag includes sub-cores that may be removed when a parent IP upgrades, creating dangling Tcl object references. Upgrade only explicitly named top-level IPs.
- **New in Vivado 2025.1**: Two new IPI views — "Clocking and Reset" and "Interrupt and AXI-4 Lite" — provide filtered views of those specific connection categories, reducing canvas clutter on large designs.
- **`apply_bd_automation` for connection shortcuts**: Calling `apply_bd_automation -rule xilinx.com:bd_rule:axi4` after creating an AXI slave will automatically connect it to the AXI Interconnect/SmartConnect and the AXI address editor entry.

### Code Example

```tcl
# Export current block design to a reproducible Tcl script (run in Vivado Tcl Console)
write_bd_tcl -force -include_layout ./tcl/create_bd.tcl

# Rebuild from the exported script in a new session
open_project ./kv260.xpr
source ./tcl/create_bd.tcl
make_wrapper -files [get_files kv260_bd.bd] -top
add_files -norecurse ./kv260.gen/sources_1/bd/kv260_bd/hdl/kv260_bd_wrapper.vhd

# Upgrade specific IP (safe: names the top-level IP only, not sub-cores)
upgrade_ip [get_ips kv260_bd_axi_bram_ctrl_0_0]
upgrade_ip [get_ips kv260_bd_axi_bram_ctrl_1_0]
report_ip_status
```

### Relevance to Your Project

Your `create_bd.tcl` is the single source of truth for the BRAM0/BRAM2 block design. Using `write_bd_tcl -include_layout` keeps the IPI canvas layout reproducible across machines. If you ever upgrade the AXI BRAM Controller IP in Vivado 2025.1, upgrade each named IP explicitly rather than using `-all` to avoid sub-core reference errors.

## Vivado TCL Scripting

### Key Findings

- **Non-project mode flow**: Set the part/board target, read sources with `read_vhdl`/`read_xdc`, run `synth_design -top`, `opt_design`, `place_design`, `route_design`, `write_bitstream`. No `.xpr` file is created.
- **Explicit checkpoints are required**: In non-project mode, `write_checkpoint` must be called manually after each step. Project mode auto-generates DCPs; non-project mode does not.
- **Reports must be called explicitly**: `report_timing_summary`, `report_utilization`, `report_cdc`, etc. are not auto-generated in non-project mode.
- **RTL elaboration only**: `synth_design -rtl` elaborates without synthesis and can be followed by `start_gui` for cross-probing, useful for visual debugging of the VHDL hierarchy.
- **Namespace hygiene**: Put custom procedures in a named namespace (`namespace eval myns { proc myproc {} {} }`) to prevent collisions with Vivado's built-in procs.
- **Guard `get_*` results**: Always check that `get_cells`, `get_nets`, etc. return non-empty before using results; unguarded usage on empty returns causes cryptic errors.

### Code Example

```tcl
# Minimal non-project batch build script for KV260 AXI-BRAM demo
# Usage: vivado -mode batch -source build.tcl

set PART "xck26-sfvc784-2LV-c"
set TOP  "kv260_top"
set OUTDIR "./output"

file mkdir $OUTDIR

read_vhdl -library xil_defaultlib [glob ./vhdl/*.vhd]
read_xdc  ./constraints/kv260_top.xdc

synth_design -top $TOP -part $PART -flatten_hierarchy rebuilt
write_checkpoint -force $OUTDIR/post_synth.dcp
report_utilization -file $OUTDIR/utilization_synth.rpt

opt_design
place_design
write_checkpoint -force $OUTDIR/post_place.dcp

route_design
write_checkpoint -force $OUTDIR/post_route.dcp
report_timing_summary -file $OUTDIR/timing_summary.rpt

write_bitstream -force $OUTDIR/${TOP}.bit
```

### Relevance to Your Project

Your `create_bd.tcl` handles block design creation. Wrapping it in a non-project batch script (as above) enables CI/CD builds without opening the Vivado GUI, which is useful for automated testing of the BRAM connectivity changes. The explicit checkpoint pattern is also essential for debugging: loading `post_route.dcp` lets you inspect timing without re-running the full flow.

## Vitis Bare-Metal / Standalone

### Key Findings

- **`xil_printf` is a lightweight subset**: It is a reduced-footprint `printf` that does not support floating-point, `%f`, or `%e` format specifiers. Use standard `printf` (from `<stdio.h>`) only when you need floats and can afford the code-size overhead; for UART status messages, `xil_printf` is preferred.
- **BSP configuration via XSCT**: In Vitis 2025.1, BSPs are configured with `xsct` (Xilinx Software Command-line Tool). The `configbsp` and `setlib` commands set BSP parameters; calling `regenbsp` regenerates the BSP after changes.
- **Linker script `lscript.ld`**: The generated `lscript.ld` places code in `psu_ddr_0_MEM_0` (DDR) by default. For KV260 bare-metal, the DDR base is `0x00000000`. If you relocate to OCM (On-Chip Memory), change the region to `psu_ocm_ram_0` (base `0xFFFC0000`, 256 KB).
- **`Xil_DCacheFlushRange` before AXI writes**: The Cortex-A53 cache must be flushed/invalidated when AXI-Lite writes go to uncached PL registers. Forgetting this is the most common cause of "always reads 0" bugs in bare-metal PS-PL demos.
- **UART baud rate default**: The standalone BSP defaults to 115200 baud. The KV260's USB-UART bridge is typically connected to UART1 (PS MIO 48/49). Verify your `.xsa` matches the hardware assignment.

### Code Example

```c
/* Bare-metal AXI-BRAM write/read with cache maintenance */
#include "xil_io.h"
#include "xil_cache.h"
#include "xil_printf.h"

#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL
#define TEST_WORD   0xDEADBEEFUL

static int test_bram(u32 base_addr, const char *name) {
    /* Flush any cached write before AXI transaction */
    Xil_DCacheFlushRange(base_addr, 4);
    Xil_Out32(base_addr, TEST_WORD);
    /* Invalidate cache line so readback is from PL, not cache */
    Xil_DCacheInvalidateRange(base_addr, 4);
    u32 val = Xil_In32(base_addr);
    if (val == TEST_WORD) {
        xil_printf("%s PASS: read 0x%08X\r\n", name, val);
        return 0;
    }
    xil_printf("%s FAIL: expected 0x%08X, got 0x%08X\r\n",
               name, (u32)TEST_WORD, val);
    return -1;
}

int main(void) {
    xil_printf("KV260 AXI-BRAM Test\r\n");
    int rc = 0;
    rc |= test_bram(BRAM0_BASE, "BRAM0");
    rc |= test_bram(BRAM2_BASE, "BRAM2");
    xil_printf(rc == 0 ? "Overall PASS\r\n" : "Overall FAIL\r\n");
    return rc;
}
```

### Relevance to Your Project

Your existing `main.c` pattern of writing then reading back is correct. The critical addition is `Xil_DCacheFlushRange` / `Xil_DCacheInvalidateRange` before AXI-Lite transactions to prevent the Cortex-A53's L1/L2 cache from masking PL readback failures. If `main.c` already marks the AXI regions as device/strongly-ordered in the MMU (via `Xil_SetTlbAttributes`), the explicit flush/invalidate may be redundant — but it is never harmful to include.

## XDC Timing Constraints

### Key Findings

- **`set_input_delay` / `set_output_delay` syntax**: Both commands take a delay in nanoseconds relative to a clock edge at the design boundary. The value can be positive or negative depending on data/clock phase relationships.
- **Min/max pairs for setup and hold**: Most I/O constraints require both `-max` (setup) and `-min` (hold) variants. Omitting `-min` may cause Vivado to use conservative defaults or report false violations.
- **`-add_delay` for multi-edge constraints**: When a port is captured on both rising and falling edges (DDR I/O), use `-add_delay` on the second `set_input_delay` call to add to rather than replace the first constraint.
- **Internal path exception for PS-PL interfaces**: Paths crossing the PS-PL boundary on Zynq UltraScale+ are internally constrained by Vivado. Do not add `set_false_path` or `set_max_delay` to PS-PL AXI interface paths — this overrides AMD's internal timing model and can cause silent hold violations.
- **`create_clock` before `set_input_delay`**: A port must have a clock defined before delays can be set relative to it. For the KV260 PL clock (driven by PS), the clock is created in the XDC on the clocking-wizard output net, not on a physical package pin.

### Code Example

```xdc
# KV260: PL clock from PS (via Clocking Wizard output)
# The PS provides pl_clk0; the Clocking Wizard output is the design clock.
create_clock -period 10.000 -name clk_pl_0 [get_pins kv260_bd_i/clk_wiz_0/inst/mmcme4_adv_inst/CLKOUT0]

# Example GPIO input constraints (if connecting PL GPIO to carrier card pins)
# Use actual pin numbers from KV260 schematic/XDC template
set_input_delay  -clock clk_pl_0 -max  2.0 [get_ports {gpio_i[*]}]
set_input_delay  -clock clk_pl_0 -min  0.5 [get_ports {gpio_i[*]}] -add_delay
set_output_delay -clock clk_pl_0 -max  1.5 [get_ports {gpio_o[*]}]
set_output_delay -clock clk_pl_0 -min -0.5 [get_ports {gpio_o[*]}] -add_delay

# Suppress irrelevant CDC warnings on async reset synchronizers
set_false_path -from [get_ports reset_n] -to [all_registers]
```

### Relevance to Your Project

Your current design's AXI-Lite paths to BRAM0/BRAM2 are internal (PS-PL ports, not package pins), so they do not need `set_input_delay`/`set_output_delay`. However, if you add PL-side GPIO or a PMOD interface to the carrier card, you will need XDC I/O constraints. The `create_clock` example above is applicable to your block design's Clocking Wizard output — always create the timing clock on the wizard's output net, not the PS `pl_clk0` input net.

## Kria KV260 / K26 SoM

### Key Findings

- **No standalone PL oscillator**: The KV260 carrier card provides no direct PL clock. The PL must source its clock from the PS (`pl_clk0`–`pl_clk3`). The PS PL0 clock defaults to 100 MHz and is configured by the FSBL before the bitstream is loaded.
- **Clocking Wizard pattern**: Set the PS PL0 clock at 100 MHz in block design properties, then use a Clocking Wizard to derive other frequencies. Do not change the raw PS clock frequency without regenerating the FSBL (the new `.xsa` triggers a new FSBL configuration).
- **JTAG boot and psu_init**: When loading a bitstream via JTAG (without SD/QSPI boot), the PS PLLs may not be initialized. Running `psu_init.tcl` from the Vitis/XSCT console initializes the PS (including PLLs and DDR) before programming the PL. The FSBL normally handles this; JTAG bypasses it.
- **MIO bank assignments**: Bank 501 covers MIO[30:26] and MIO[51:38]; bank 502 covers MIO[77:52]. The SD0 controller on the KV260 carrier is wired to MIO 39–51 at 3.3 V (no level shifter). USB-UART is typically on MIO 48/49 (UART1).
- **K26 SOM variants**: The production `sm-k26` includes eMMC; the starter-kit `smk-k26` uses QSPI for pre-programmed firmware and carrier-card overlays for additional functionality. Bare-metal development typically targets the `smk-k26`.
- **PL power domains**: The KV260 PL I/O banks operate at 1.8 V (HPIO) and 3.3 V (HDIO/LVCMOS33). Check the `kv260_top.xdc` IOSTANDARD settings against the carrier card schematic before driving external pins to avoid board damage.

### Code Example

```tcl
# In Vivado block design: set PS PL clock to 100 MHz
# (In create_bd.tcl, after zynq_ultra_ps_e_0 is created)
set_property -dict [list \
  CONFIG.PSU__CRL_APB__PL0_REF_CTRL__FREQMHZ {100} \
  CONFIG.PSU__CRL_APB__PL1_REF_CTRL__FREQMHZ {100} \
  CONFIG.PSU__FPGA_PL0_ENABLE {1} \
] [get_bd_cells zynq_ultra_ps_e_0]

# JTAG-based bare-metal: initialize PS before loading bitstream
# Run this in XSCT console to simulate what FSBL does:
#   xsct% connect
#   xsct% targets -set -filter {name =~ "PSU"}
#   xsct% source psu_init.tcl
#   xsct% psu_init
#   xsct% targets -set -filter {name =~ "APU*"}
#   xsct% fpga kv260_top.bit
#   xsct% dow kv260_app.elf
#   xsct% con
```

### Relevance to Your Project

Your demo drives BRAM0 at 0xA0000000 and BRAM2 at 0xA0010000 from the Cortex-A53. The PS PL0 clock at 100 MHz is the right default. If you see the AXI transactions complete but readback always returns 0 when loaded via JTAG (no SD card), add a `psu_init.tcl` call before programming the PL — an uninitialized PS PLL can leave the AXI bus non-functional.

## AMD/Xilinx Tool Updates (Vivado/Vitis 2025.1)

### Key Findings

- **New RTL-based AXI Switch IP**: Vivado 2025.1 introduces an AXI Switch IP that can be instantiated in RTL flows (not just IPI), handles cross-type (AXI4/AXI-Lite/AXI-Stream) and cross-width bridging, and simplifies clock/reset connectivity (one clock/reset pair for the switch rather than one per interface port).
- **New IPI filtered views**: Two new IP Integrator views — "Clocking and Reset" and "Interrupt and AXI-4 Lite" — filter the canvas to show only the relevant connections for those subsystems, reducing cognitive load on large block designs.
- **New device support**: Versal AI Edge Gen 2 and Versal Prime Gen 2 are added. Spartan UltraScale+ is a new family in this release.
- **Selective device installer**: A new installer option allows installing only selected Vivado device families (e.g., Zynq UltraScale+ only), significantly reducing download and disk-space requirements.
- **Vitis AI 5.1 (uses 2025.1.1)**: The Vitis AI 5.1 release targets Vivado/Vitis v2025.1.1, adds multi-NPU reference designs, mixed-precision quantization, and Apptainer as a Docker alternative.
- **Open-source components**: Linux kernel upgraded to 6.12; Zephyr RTOS gains early-access driver support for several Zynq UltraScale+ peripherals.
- **Vitis 2025.2** (latest): The AMD "What's New" page shows Vitis 2025.2 as the current release; 2025.1 is the stable release used for most production Kria flows as of this digest.

### Code Example

```tcl
] [get_bd_cells axi_switch_0]

# (Run the Vivado installer with -platform argument for unattended install)
# vivado_installer.sh -batch -platform {Zynq UltraScale+}
```

### Relevance to Your Project

Vivado 2025.1 is your toolchain. The new AXI Switch IP is a cleaner alternative to SmartConnect for future RTL-based extensions to your BRAM demo (e.g., adding a DMA engine or a custom IP in RTL without going through IPI). The selective installer is immediately useful if you are working on a laptop or a CI runner with limited disk space — installing only the Zynq UltraScale+ device family is sufficient for the KV260 K26 SoM target `xck26-sfvc784-2LV-c`.
