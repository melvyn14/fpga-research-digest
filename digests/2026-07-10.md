# FPGA Research Digest - 2026-07-10

## Executive Summary

- **Vivado 2025 AXI address-space bug**: Custom AXI-full peripherals generated by the wizard are silently limited to 1 kB (10-bit address decode). Bits above bit 9 are forced to zero, causing address wrap-around. Workaround: manually patch the generated RTL address-width parameter or use the BRAM controller IP instead of a wizard-generated slave.
- **AXI-Lite BVALID/BREADY deadlock risk**: The write-response channel requires BVALID to stay asserted until BREADY is seen. If your slave lowers BVALID prematurely (common template bug), the master hangs waiting for a response that never comes — critical to verify in your `kv260_top.vhd` FSM.
- **KV260 JTAG boot mode requires TCL**: The KV260 has no physical boot-mode DIP switches. Boot mode must be changed programmatically via XSDB/JTAG TCL commands or by updating firmware — important for iterative bare-metal development.
- **Vivado 2025.1 introduced a fully customizable RTL-based AXI Switch IP** that bridges different AXI interface types and widths — a potential upgrade path if your design needs to fan out to more BRAM banks.
- **Standalone BSP memory-map alignment**: The Cortex-A53 linker script generated by Vitis must match your Vivado address-editor assignments (BRAM0 @ `0xA0000000`, BRAM2 @ `0xA0010000`). A mismatch causes silent read-back of `0x00000000` with no fault, making it appear as a FAIL rather than a bus error.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- The READY/VALID handshake is a two-party agreement: a transfer completes only when both signals are high **on the same rising clock edge**. Neither party may retract VALID once asserted (master rule); READY may be withheld indefinitely (slave backpressure).
- AXI-Lite has five independent channels: AW (write address), W (write data), B (write response), AR (read address), R (read data). Each channel must complete its own handshake. A common bug is ignoring the B channel so BVALID is never cleared, which stalls subsequent writes.
- Response codes: `2'b00` = OKAY, `2'b10` = SLVERR, `2'b11` = DECERR. For a bare-metal BRAM demo, always return OKAY (`"00"`); using SLVERR can cause the Zynq PS to raise an AXI error interrupt.
- **Vivado 2025 bug**: AXI full peripheral wizard limits address decode to 10 bits (1 kB). Changing `C_S_AXI_ADDR_WIDTH` in the generated template has no effect — you must patch the internal address-slice logic manually.
- Registered READY signals are required by the AXI spec to break combinatorial loops between master and slave. Vivado's example templates often violate this — the zipcpu blog's `easyaxil` pattern provides a correct VHDL reference.

### Code Example

```vhdl
-- Minimal AXI-Lite write-response FSM (B channel) - avoids the BVALID latch bug
process(S_AXI_ACLK)
begin
  if rising_edge(S_AXI_ACLK) then
    if S_AXI_ARESETN = '0' then
      axi_bvalid <= '0';
      axi_bresp  <= "00";
    else
      -- Assert BVALID one cycle after both AW and W handshakes complete
      if (aw_en = '0' and axi_awready = '1' and S_AXI_AWVALID = '1'
          and axi_wready = '1' and S_AXI_WVALID = '1') then
        axi_bvalid <= '1';
        axi_bresp  <= "00"; -- OKAY
      -- Hold BVALID until master asserts BREADY
      elsif S_AXI_BREADY = '1' and axi_bvalid = '1' then
        axi_bvalid <= '0';
      end if;
    end if;
  end if;
end process;

S_AXI_BVALID <= axi_bvalid;
S_AXI_BRESP  <= axi_bresp;
```

### Relevance to Your Project

Your `kv260_top.vhd` connects the PS AXI-Lite master to two BRAM controllers. If either BRAM controller's B channel has a latch bug, `main.c`'s pattern-write loop will hang on the second write. The Vivado 2025 address-decode bug does **not** affect you when using the Xilinx AXI BRAM Controller IP (PG078) — the bug only hits custom wizard-generated slaves. Your addresses (`0xA0000000` / `0xA0010000`) are 64 kB apart, well within the AXI interconnect's decode range.

## Vivado Block Design / IP Integrator

### Key Findings

- `apply_bd_automation` is convenient but produces surprises across Vivado versions. Prefer explicit `connect_bd_net` / `connect_bd_intf_net` calls in TCL for reproducibility.
- The Block Design Address Editor must be explicitly configured when two BRAM controllers share the same AXI interconnect — the auto-assigned ranges can overlap or leave gaps that cause decode failures at runtime.
- Hierarchical block design cells (created via `create_bd_cell -type hier`) improve readability and let you collapse subsystems in the GUI, but TCL export still produces a flat script; you must manually refactor into procedures.
- Vivado 2025.1 added a new RTL-based AXI Switch IP that supports mixed AXI4 / AXI-Lite / AXI-Stream bridging. The existing SmartConnect / AXI Interconnect IPs remain available but AMD recommends migrating to SmartConnect for new designs.
- `validate_bd_design` in TCL reveals critical warnings about unconnected clocks and reset nets before `generate_target all` — always run it as a gate before synthesis.

### Code Example

```tcl
# Explicit address assignment for two BRAM controllers in IP Integrator
# Run after all IPs are connected, before generate_target

# Assign BRAM0 to 0xA000_0000, 64K range
assign_bd_address [get_bd_addr_segs {axi_bram_ctrl_0/S_AXI/Mem0}]
set_property offset 0xA0000000 \
  [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property range 64K \
  [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]

# Assign BRAM2 to 0xA001_0000, 64K range
assign_bd_address [get_bd_addr_segs {axi_bram_ctrl_1/S_AXI/Mem0}]
set_property offset 0xA0010000 \
  [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_1_Mem0}]
set_property range 64K \
  [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_1_Mem0}]

validate_bd_design
```

### Relevance to Your Project

Your `create_bd.tcl` drives the entire block design. The explicit address assignments above should match the `0xA0000000` / `0xA0010000` offsets your `main.c` uses for memory-mapped writes. If the address editor auto-assigns different offsets, the C code will silently write to the wrong location and the PASS/FAIL comparison will always return FAIL.

## Vivado TCL Scripting

### Key Findings

- TCL scripts exported via **File → Export → Export Block Design** are version-sensitive: Xilinx tweaks the IP parameter names between releases. A script from Vivado 2024.x may require property-name corrections in 2025.1.
- The non-project mode flow (`open_checkpoint`, `link_design`, `opt_design`, `place_design`, `route_design`, `write_bitstream`) is ideal for CI/CD pipelines since it avoids `.xpr` file management.
- Parameterized block design scripts using Tcl variables and `if/elseif` branches can support multiple board targets from a single script — useful if you ever port the demo to a ZCU104.
- `report_timing_summary -file timing.rpt` should be called after `route_design` and its exit code checked — a non-zero status indicates unresolved timing violations that will produce a functionally broken bitstream.
- `get_property NEEDS_REFRESH [get_runs synth_1]` lets you skip re-synthesis in iterative flows when only XDC or C source files changed.

### Code Example

```tcl
# Non-project batch flow for KV260 AXI-BRAM demo
# Usage: vivado -mode batch -source build.tcl

set part "xck26-sfvc784-2LV-c"
set bd_name "kv260_bd"

# Create in-memory project
create_project -in_memory -part $part

# Source the block design creation script
source ./tcl/create_bd.tcl

# Generate all targets
make_wrapper -files [get_files ${bd_name}.bd] -top
add_files -norecurse ./kv260_claude/kv260/${bd_name}_wrapper.v

# Add XDC constraints
add_files -fileset constrs_1 -norecurse ./xdc/kv260_top.xdc

# Run implementation
launch_runs synth_1 -jobs 4
wait_on_run synth_1
launch_runs impl_1 -to_step write_bitstream -jobs 4
wait_on_run impl_1

# Check timing
open_run impl_1
set wns [get_property SLACK [get_timing_paths -max_paths 1 -nworst 1]]
if {$wns < 0} {
  puts "ERROR: Timing violation WNS=$wns ns"
  exit 1
}
puts "Timing clean. WNS=$wns ns"
```

### Relevance to Your Project

Your `create_bd.tcl` is already the right pattern. Wrapping it in the non-project batch shell above lets you rebuild the entire bitstream from a clean state with a single command — useful when iterating on BRAM depth or address map changes without opening the GUI.

## Vitis Bare-Metal / Standalone

### Key Findings

- The Vitis standalone (bare-metal) BSP for Cortex-A53 (`psv_cortexa53_0`) provides `xil_printf` which routes through the PS UART. On KV260, UART1 (MIO 36/37) is connected to the USB-UART bridge at 115200 baud by default in the board preset.
- `xil_printf` does **not** support floating-point format specifiers (`%f`, `%e`). Use `printf` from newlib if you need floats, but be aware newlib pulls in `_write` / `_read` syscall stubs.
- The Vitis 2025.x unified IDE flow creates a `vitis-comp.json` component manifest — this replaces the legacy `.mss` / `.bsp` project files. If you're adapting older tutorials, the project structure has changed.
- Linker script `lscript.ld` generated by Vitis maps `.text` to DDR (default base `0x0000_0000`). The HP ports of the PS give PL access to DDR — important if you later upgrade from BRAM to DDR-backed buffers.
- For iterative testing, `xsdb` (Xilinx System Debugger) can download and run `.elf` files over JTAG without rebuilding the boot image: `xsdb -eval "connect; targets -set -filter {name =~ \"APU*\"}; dow app.elf; con"`.

### Code Example

```c
/* Bare-metal AXI-Lite BRAM read-back with explicit cache flush
 * On Cortex-A53, the L1/L2 cache may serve stale data if you read
 * back immediately after a write to an uncached MMIO region.
 * AXI-Lite BRAM addresses should be declared volatile AND
 * marked as device memory in the MMU (Vitis does this automatically
 * for addresses in the PL region 0xA000_0000–0xBFFF_FFFF). */

#include "xil_io.h"
#include "xil_printf.h"

#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL
#define TEST_WORDS  16

int verify_bram(u32 base_addr, const char *name) {
    u32 pattern, readback;
    int pass = 1;

    for (int i = 0; i < TEST_WORDS; i++) {
        pattern = 0xDEAD0000 | (u32)i;
        Xil_Out32(base_addr + i * 4, pattern);   /* uncached MMIO write */
    }

    for (int i = 0; i < TEST_WORDS; i++) {
        pattern  = 0xDEAD0000 | (u32)i;
        readback = Xil_In32(base_addr + i * 4);  /* uncached MMIO read */
        if (readback != pattern) {
            xil_printf("%s[%d]: FAIL (wrote 0x%08X, read 0x%08X)\r\n",
                       name, i, pattern, readback);
            pass = 0;
        }
    }
    return pass;
}

int main(void) {
    xil_printf("KV260 AXI-BRAM demo\r\n");
    int ok0 = verify_bram(BRAM0_BASE, "BRAM0");
    int ok2 = verify_bram(BRAM2_BASE, "BRAM2");
    xil_printf("Result: %s\r\n", (ok0 && ok2) ? "PASS" : "FAIL");
    return 0;
}
```

### Relevance to Your Project

This pattern matches what your `main.c` likely does. Key addition: using `Xil_Out32` / `Xil_In32` (from `xil_io.h`) instead of raw pointer dereferences ensures the compiler treats them as volatile and prevents reordering. The BRAM addresses fall in the PL address space which Vitis maps as strongly-ordered device memory — no explicit cache flush needed.

## XDC Timing Constraints

### Key Findings

- On Zynq UltraScale+ (K26), the primary PL clock comes from `FCLK_CLK0` of the PS block. You do **not** need a `create_clock` for it — Vivado automatically propagates it. You only need `create_clock` for clocks entering through PL I/O pins.
- `set_clock_groups -asynchronous` is required when you have multiple unrelated clock domains (e.g., a 100 MHz AXI clock and a 200 MHz PL processing clock). Without it, Vivado reports false violations across the boundary.
- For AXI-Lite to BRAM paths on Zynq, timing is almost always met at 100 MHz without additional constraints since both master and slave are in PL fabric. The risk is at higher frequencies (>200 MHz) where BRAM output register timing tightens.
- `set_false_path -from [get_clocks clk_pl_0] -to [get_clocks clk_pl_1]` is the correct form for PS-generated clock domains; `set_clock_groups` with `-exclusive` is used for clocks that are mutually exclusive (e.g., MMCM output mux selections).
- The Vivado Constraint Wizard (available under **Tools → Timing → Constraint Wizard**) auto-detects I/O timing requirements and generates `set_input_delay` / `set_output_delay` templates — run it after placing all I/O if you add external signals.

### Code Example

```xdc
# XDC for KV260 AXI-BRAM demo
# FCLK_CLK0 is auto-propagated by Vivado from the PS — no create_clock needed.
# Only constraint needed: false path between PS clock domains if you use multiple.

# If using two PS clocks (e.g., 100 MHz for AXI, 200 MHz for PL logic):
set_clock_groups -asynchronous \
  -group [get_clocks clk_pl_0] \
  -group [get_clocks clk_pl_1]

# UART TX/RX are PS MIO — no PL constraints required; they're handled by PS.

# If you add any PL-side GPIO (e.g., LED on PMOD):
# set_output_delay -clock [get_clocks clk_pl_0] -max 2.0 [get_ports led_o]
# set_output_delay -clock [get_clocks clk_pl_0] -min 0.5 [get_ports led_o]

# Prevent tools from over-optimizing debug nets:
# set_false_path -to [get_pins -hierarchical -filter {NAME =~ */ILA_inst/*}]
```

### Relevance to Your Project

For a single-clock 100 MHz AXI-BRAM demo, your timing constraints file can be nearly empty — the PS-generated clock is auto-constrained and AXI-Lite to BRAM at 100 MHz closes with large positive slack. The constraints become critical only when you add a second clock domain or external I/O pins.

## Kria KV260 / K26 SoM

### Key Findings

- The K26 SoM lacks physical boot-mode switches. To enter JTAG mode for bare-metal development, you must change the boot mode register via XSDB: `mwr 0xFF5E0200 0x0100` sets JTAG boot, then `rst` reboots into JTAG mode. This persists only until next power cycle.
- KV260 UART1 is accessible via the USB Micro-B connector on the carrier board (UART-to-USB bridge). It maps to `/dev/ttyUSB1` (Linux host) or `COM<n>` (Windows). Note: `/dev/ttyUSB0` is typically the JTAG interface — check `dmesg` to confirm port assignment.
- The PS MIO bank 501 operates at 1.8 V. EMIO signals in the PL (connected to the 240-pin SOM connector) run at the VCCO voltage of the PL bank they're assigned to. Mismatching voltage standards in XDC causes DRC errors.
- For bare-metal without Linux, you need: FSBL (`fsbl.elf`), PMU firmware (`pmufw.elf`), and your application `.elf`. These are bundled into `boot.bin` via Bootgen. The KV260 also requires the board's PL configuration bitstream to be included in the boot image if using PL peripherals.
- The BIST (Board Interface Self-Test) tutorial for KV260 (LogicTronix, 2025) provides a complete working reference for Vivado/Vitis 2025.1 bare-metal flow on this exact board.

### Code Example

```tcl
# XSDB script to switch KV260 to JTAG boot mode and download bare-metal ELF
# Run from: xsdb boot_jtag.tcl

connect

# Force JTAG boot mode (write to boot mode register)
mwr 0xFF5E0200 0x0100
after 100

# Reset to apply new boot mode
rst -system
after 2000

# Connect to APU Cortex-A53 core 0
targets -set -filter {name =~ "Cortex-A53 #0"}

# Initialize PS (required before accessing DDR or PL)
source psu_init.tcl
psu_init

# Load and run the bare-metal application
dow kv260_bram_demo.elf
con

puts "Application running. Monitor UART at 115200 baud."
```

### Relevance to Your Project

This XSDB script replaces the need to build a full `boot.bin` during development. You can iterate on `main.c`, recompile, and re-download via JTAG in seconds without reprogramming QSPI flash. The `psu_init.tcl` is exported from Vivado's IP Integrator alongside the bitstream and initializes the PS clocks and DDR before your application runs.

## AMD/Xilinx Tool Updates (Vivado/Vitis 2025.x)

### Key Findings

- **Vivado 2025.1** added PS-first boot support: the PS can boot and run Linux/bare-metal before the PL is configured, enabling deferred PL loading at runtime. This is relevant if you eventually need to load different BRAM configurations dynamically.
- **New Pblock Planner** in Vivado 2025.1 provides a visual interface for creating and editing Pblocks, improving floorplanning for designs with multiple clock domains.
- **RTL-based AXI Switch IP** (new in 2025.1) supports mixed AXI4/AXI-Lite/AXI-Stream at different widths — more flexible than SmartConnect for heterogeneous bus-width designs.
- **Vitis 2025.1 / 2025.2**: Enhanced AI Engine GEMV and FFT kernels with 2D parallel AIE+PL architecture — not relevant for bare-metal A53 work, but signals AMD's continued investment in the unified flow.
- **Known issue in Vivado 2025**: The AXI peripheral wizard generates slaves with hard-coded 10-bit address decode, silently limiting usable space to 1 kB. This affects any wizard-created custom IP; use established IP cores (AXI BRAM Controller PG078) where possible.
- Vivado 2025.x improved directive/subdirective support for QoR and added a Timeline Trace Viewer post-simulation — useful for debugging AXI transaction ordering in simulation.

### Code Example

```tcl
# Vivado 2025.1: Check generated AXI peripheral for address-width bug
# After creating a custom AXI slave via the wizard, inspect the generated RTL:

# In Tcl console or batch:
set ip_dir [get_property IP_DIR [get_ips axi_myperipheral_v1_0]]
set rtl_file "$ip_dir/hdl/axi_myperipheral_v1_0_S00_AXI.v"

# Check for the broken address width (should be your design width, not 10):
set fp [open $rtl_file r]
set content [read $fp]
close $fp

if {[regexp {ADDR_LSB\s*=\s*2.*OPT_MEM_ADDR_BITS\s*=\s*(\d+)} $content -> bits]} {
  puts "Address bits: $bits (covers [expr {1 << ($bits + 2)}] bytes)"
  if {$bits < 14} {
    puts "WARNING: Address space < 64kB — may be affected by Vivado 2025 wizard bug"
  }
}

# Workaround: use AXI BRAM Controller IP (PG078) instead of the wizard
# It correctly decodes the full address range up to the BRAM depth.
```

### Relevance to Your Project

You are already using the AXI BRAM Controller IP (the correct approach), so the Vivado 2025 address-decode bug does not affect your current design. However, if you ever add a custom AXI slave (e.g., a status register block), generate it with the wizard and then immediately verify its `OPT_MEM_ADDR_BITS` parameter matches your intended address range before simulation.
