# FPGA Research Digest - 2026-07-05

## Executive Summary

- **AXI-Lite deadlock root cause confirmed**: A master that waits for AWREADY before asserting AWVALID will deadlock with a slave that waits for AWVALID before asserting AWREADY — always assert VALID unconditionally and hold it until the handshake completes. This is the most common bare-metal AXI debug pitfall.
- **Vivado 2025.2 ships ultra-low-area AXI SmartConnect mode**: Set `STRATEGY = 1` on the SmartConnect IP to drastically cut LUT usage between the Zynq PS AXI master and your BRAM slaves — valuable for resource-constrained KV260 designs.
- **KV260 QSPI flash is read-locked on the Starter Kit carrier**: For deployment without JTAG you must write a BOOT.BIN to the SD card or use `xmutil bootfw_update` from Linux; bare SOM purchasers have no such restriction.
- **BSP stdout must be assigned to the correct UART**: The KV260 USB-UART bridge is wired to `psu_uart_1`, but Vitis defaults BSP stdout to `psu_uart_0` — if `xil_printf` produces no output, this is the first thing to check.
- **Vivado 2025.1 introduced dynamic PL loading**: The PS can now boot first and load the PL bitstream on the fly, enabling faster iteration without a full FSBL rebuild cycle for bare-metal projects.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- **VALID-before-READY rule is mandatory for the master/initiator side**: A source must assert VALID based solely on its own internal state — never conditional on READY. Violating this rule creates a circular dependency that permanently stalls the bus.
- **VALID must remain asserted once raised**: Once a master drives AWVALID (or WVALID, etc.) high, it cannot deassert it until the corresponding slave drives READY high and the handshake completes. Premature deassertion is a protocol violation.
- **READY is free to float**: A slave may assert or deassert READY at any cycle — it is also allowed to wait until it sees VALID before raising READY (though the master cannot depend on this).
- **AXI BRAM Controller (PG078) supports both single and burst transactions**: The controller is optimised as an AXI endpoint slave; for bare-metal single-word reads/writes AXI-Lite mode is sufficient and avoids burst-wrap complexity.
- **Address range overflow causes silent transfer failures**: If the PS writes to an address beyond the slave's mapped range in the Address Editor, the transaction completes from the interconnect's perspective but data is discarded — always verify the offset address and range match your HDL constants.

### Code Example

```c
/* Bare-metal AXI-Lite write — safe, non-blocking pattern.
 * Xil_Out32 generates a single 32-bit AXI-Lite write; the PS AXI master
 * drives AWVALID/WVALID unconditionally per protocol spec. */
#include "xil_io.h"

#define BRAM0_BASE  0xA0000000UL
#define BRAM1_BASE  0xA0010000UL

static inline void bram_write(u32 base, u32 offset_bytes, u32 data) {
    Xil_Out32(base + offset_bytes, data);
}

static inline u32 bram_read(u32 base, u32 offset_bytes) {
    return Xil_In32(base + offset_bytes);
}

/* Write pattern, read back, verify */
void verify_bram(u32 base, const char *name) {
    const u32 PATTERN = 0xDEADBEEFUL;
    bram_write(base, 0, PATTERN);
    u32 rb = bram_read(base, 0);
    xil_printf("%s: %s (wrote 0x%08X, read 0x%08X)\r\n",
               name,
               (rb == PATTERN) ? "PASS" : "FAIL",
               PATTERN, rb);
}
```

### Relevance to Your Project

Your `main.c` writes patterns to BRAM0 at `0xA0000000` and BRAM2 at `0xA0010000` and prints PASS/FAIL over USB-UART. The deadlock rule is directly applicable: if you ever implement a custom AXI slave in VHDL (replacing the IP core), you must ensure your slave's AWREADY logic does not wait for software to toggle a register — assert READY as soon as the slave is idle, independent of any upstream signals.

## Vivado Block Design / IP Integrator

### Key Findings

- **"Run Connection Automation" wires BRAM, interconnect, and reset in one click**: IPI detects a BRAM Controller connected to a Zynq PS port and automatically instantiates an AXI Interconnect (or SmartConnect), a Block Memory Generator, and a Processor System Reset, saving 15+ manual wiring steps.
- **Address Editor "Auto Assign Address" must be run after adding new slaves**: Forgetting this step causes the PS to target address 0x0 for all slaves, resulting in AXI decode errors or silent data corruption at runtime.
- **Vivado 2025.1 adds dedicated "Clocking and Reset" and "Interrupt and AXI-4 Lite" views** in IPI, making it easier to audit clock domain crossings and interrupt wiring without scrolling through a dense diagram.
- **Vivado 2025.2 introduces new addressing GUI with automatic grouping** of equivalent address spaces, which simplifies managing multiple BRAM slaves at different offsets.
- **OOC synthesis uses HD.CLK_SRC for hold-time closure**: Set `set_param ips.includeClockLocationConstraints true` in your Tcl build script when generating IP out-of-context to ensure hold-timing closure is correct for all AXI IP blocks.

### Code Example

```tcl
# Regenerate block design and export hardware from TCL (2025.x compatible)
open_project ./kv260.xpr
open_bd_design [get_files *.bd]

# Assign all AXI slave addresses automatically
assign_bd_address

# Validate — catches unconnected ports and address overlaps before synthesis
validate_bd_design

# Generate output products for all IP (OOC)
generate_target all [get_files *.bd]

# Export XSA for Vitis
write_hw_platform -fixed -force ./kv260.xsa
```

### Relevance to Your Project

Your `create_bd.tcl` script automates the block design; the `assign_bd_address` call (or its equivalent `set_property offset/range`) must correctly place BRAM0 at `0xA0000000` (64 KB range) and BRAM2 at `0xA0010000` (64 KB range). The 2025.2 ultra-low-area SmartConnect mode (`STRATEGY=1`) is worth enabling to reduce LUT overhead on the relatively small K26 fabric.

## Vivado TCL Scripting

### Key Findings

- **Non-project mode runs entirely in memory — no project files created**: This makes CI/CD pipelines faster and avoids stale project-state bugs, but the developer is fully responsible for ordering `read_vhdl` → `synth_design` → `opt_design` → `place_design` → `route_design` → `write_bitstream`.
- **Project-mode Tcl uses macro commands; non-project mode uses WYSIWYG commands**: `launch_runs synth_1` (project mode) vs. `synth_design -top kv260_top -part xck26-sfvc784-2LV-c` (non-project mode) — they are not interchangeable.
- **`write_checkpoint` is essential in non-project mode**: Without checkpoints, a crash after routing means restarting from scratch. Save after synthesis and after routing at minimum.
- **Batch mode invocation**: `vivado -mode batch -source build.tcl` opens Vivado, runs the script, and exits — suitable for headless CI runners.
- **`set_param ips.includeClockLocationConstraints true`** should appear at the top of any build script that synthesizes AXI IP out-of-context.

### Code Example

```tcl
# Non-project mode RTL-to-bitstream for KV260 AXI-BRAM demo
# Usage: vivado -mode batch -source build.tcl

set_param ips.includeClockLocationConstraints true
set PART xck26-sfvc784-2LV-c
set TOP  kv260_top

# Read sources
read_vhdl    ../vhdl/kv260_top.vhd
read_xdc     ../xdc/kv260_top.xdc
read_ip      [glob ../ip/**/*.xci]

# Generate IP OOC before top-level synth
generate_target all [get_ips]
synth_ip      [get_ips]

# Synthesise
synth_design -top $TOP -part $PART -flatten_hierarchy rebuilt
write_checkpoint -force ./post_synth.dcp

# Implement
opt_design
place_design
phys_opt_design
route_design
write_checkpoint -force ./post_route.dcp

# Reports
report_timing_summary -file timing.rpt
report_utilization    -file utilization.rpt

# Bitstream
write_bitstream -force ./kv260_top.bit
write_hw_platform -fixed -force ./kv260.xsa
```

### Relevance to Your Project

Your existing `create_bd.tcl` runs in project mode. Migrating to the non-project snippet above would let you run the full Vivado build from a GitHub Actions runner (or any CI system) without a GUI licence seat, and produce a reproducible `.bit` + `.xsa` artefact in one command.

## Vitis Bare-Metal / Standalone

### Key Findings

- **BSP stdout defaults to `psu_uart_0`; KV260 USB-UART bridge is on `psu_uart_1`**: If `xil_printf` produces no console output after flashing, open BSP Settings → `stdin`/`stdout` and change both to `psu_uart_1`, then regenerate and rebuild.
- **115200 baud, 8N1 is the standard Kria serial configuration** — most terminal emulators need explicit 115200 setting as they may default to 9600.
- **`xil_printf` does not support floating-point format specifiers**: Use integer arithmetic and print numerator/denominator separately, or link the full `printf` via BSP settings (`use_xil_printf = false`), accepting a larger code footprint.
- **`Xil_DCacheFlushRange` must bracket any DMA-visible buffer**: For bare-metal designs that later add DMA, failure to flush the D-cache before a DMA transfer causes the DMA to read stale values from DDR — even though AXI-Lite BRAM writes bypass cache entirely.
- **Linker script `lscript.ld` places `.text` and `.data` in OCM or DDR**: Ensure stack/heap sizes are adequate; default Vitis bare-metal heap is often only 8 KB, which can cause silent `malloc` failures if you add logging buffers.

### Code Example

```c
/* Minimal Vitis 2025.x bare-metal init for KV260 UART + AXI-BRAM verification */
#include "xil_printf.h"
#include "xil_io.h"
#include "xparameters.h"   /* generated by Vitis from XSA */

/* AXI-BRAM base addresses — must match Address Editor in block design */
#define BRAM0_BASE  XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR
#define BRAM1_BASE  XPAR_AXI_BRAM_CTRL_1_S_AXI_BASEADDR

int main(void) {
    xil_printf("\r\n=== KV260 AXI-BRAM Test ===\r\n");

    /* Write test patterns */
    Xil_Out32(BRAM0_BASE + 0x00, 0xA5A5A5A5);
    Xil_Out32(BRAM0_BASE + 0x04, 0x5A5A5A5A);
    Xil_Out32(BRAM1_BASE + 0x00, 0xDEADBEEF);

    /* Verify */
    xil_printf("BRAM0[0]: %s\r\n",
        (Xil_In32(BRAM0_BASE + 0x00) == 0xA5A5A5A5) ? "PASS" : "FAIL");
    xil_printf("BRAM0[4]: %s\r\n",
        (Xil_In32(BRAM0_BASE + 0x04) == 0x5A5A5A5A) ? "PASS" : "FAIL");
    xil_printf("BRAM1[0]: %s\r\n",
        (Xil_In32(BRAM1_BASE + 0x00) == 0xDEADBEEF) ? "PASS" : "FAIL");

    return 0;
}
```

### Relevance to Your Project

This pattern mirrors your existing `main.c` but uses `XPAR_*` macros from `xparameters.h` instead of hard-coded addresses. This is safer: when you remap BRAM addresses in the Address Editor and regenerate the XSA, the macros update automatically, eliminating a common mismatch bug.

## XDC Timing Constraints

### Key Findings

- **Kria KV260 PL clock comes from the PS clock wizard output — constrain it with `create_clock`**: The K26 SOM does not expose an independent PL oscillator on most carrier card variants; your design's primary clock is derived from `pl_clk0` generated by the Zynq UltraScale+ PS IP.
- **`set_input_delay` and `set_output_delay` are only needed for off-chip I/O**: For a pure PS-to-PL AXI-BRAM design with no external I/O ports in the PL (GPIOs, Ethernet, etc.), you need only the clock constraint — the PS AXI timing is constrained internally by Vivado's platform constraints.
- **`HD.CLK_SRC` property ensures hold-closure for OOC IP**: The Tcl command `set_param ips.includeClockLocationConstraints true` must be set before generating AXI IP OOC, otherwise hold-time margin at the BRAM controller interface may be incorrectly optimistic.
- **False paths between asynchronous clock domains**: If you ever add a PL-side clock (e.g., from a PL oscillator) alongside `pl_clk0`, use `set_clock_groups -asynchronous` rather than `set_false_path` — the former is checked for setup/hold separately and prevents timing-clean paths from being masked.
- **XDC evaluation order matters**: Vivado processes XDC constraints in order; place `create_clock` before any `set_input_delay`/`set_output_delay`/`set_clock_groups` that reference it, or those commands silently apply to nothing.

### Code Example

```tcl
# kv260_top.xdc — minimal constraints for PS-to-PL AXI-BRAM design
# pl_clk0 is generated by the Zynq UltraScale+ PS IP at the frequency
# set in the block design (typically 100 MHz or 200 MHz).

# Primary PL clock — driven by PS clock wizard output port pl_clk0
create_clock -period 10.000 -name pl_clk0 \
    [get_pins -hierarchical -filter {NAME =~ */zynq_ultra_ps_e_0/inst/PS8_i/PLCLK[0]}]

# If a second async PL clock exists (e.g., from SI5344 on carrier card):
# create_clock -period 8.000 -name sys_clk [get_ports sys_clk_p]
# set_clock_groups -asynchronous -group [get_clocks pl_clk0] \
#                               -group [get_clocks sys_clk]

# I/O timing constraints are NOT needed for pure AXI-BRAM (no external ports).
# Add these only when PL drives external LVDS/GPIO/RGMII pins.
# Example for external GPIO output:
# set_output_delay -clock pl_clk0 -max 3.0 [get_ports {led[*]}]
# set_output_delay -clock pl_clk0 -min 0.5 [get_ports {led[*]}]
```

### Relevance to Your Project

Your AXI-BRAM demo has no external PL I/O beyond what the PS controls directly. The single `create_clock` for `pl_clk0` is the only XDC constraint you strictly require. If Vivado reports unconstrained paths, confirm the hierarchical pin path matches your PS8 instance name with `get_pins -hierarchical -filter {NAME =~ *PLCLK*}` in the Tcl console.

## Kria KV260 / K26 SoM

### Key Findings

- **Default boot mode on the KV260 Starter Kit is QSPI32, and the QSPI flash is write-protected**: The carrier card straps the MODE[3:0] pins for QSPI at power-on. You cannot erase/reprogram the QSPI from Vitis on a Starter Kit; use JTAG or SD card boot during development. Bare SOM (without carrier card) has no such restriction.
- **JTAG boot bypasses FSBL**: In Vitis Debug Configuration, select "Download Bitstream" and use `psu_init.tcl` instead of FSBL to initialise the PS — this is faster for iterative bare-metal debugging and avoids FSBL rebuild cycles.
- **MIO Bank 500 (1.8 V) hosts the PS I2C and sideband signals**: All VCCO on the SOM's MIO bank 500 is 1.8 V. Do not drive 3.3 V logic directly into these pins on a custom carrier card.
- **`xmutil bootfw_update` updates boot firmware from Linux**: On a KV260 running a Petalinux or Ubuntu image, this on-target utility updates FSBL/PMU firmware without needing a JTAG programmer.
- **Board files for K26 are bundled with Vivado 2025.x**: Use `Tools → Board Repository` (or set `BOARD_PART_REPO_PATHS`) to ensure the `kv260_starter_kit` board part is visible; this automates PS configuration (DDR, clocks, MIO) in the block design.

### Code Example

```tcl
# Vitis/XSDB script: JTAG boot KV260 bare-metal application
# Run in: xsdb (from Vitis Shell)

connect
targets -set -filter {name =~ "PSU"}

# Initialise PS (sets up DDR, clocks, MIO) — replaces FSBL in debug flow
source $env(XILINX_VITIS)/data/embeddedsw/lib/psv_pmu_0/xpfw_config.h
mwr 0xFFFF0000 0x14000000
namespace eval xsdb { source ./psu_init.tcl; psu_init }

# Reset A53 core 0, load ELF, run
targets -set -filter {name =~ "Cortex-A53 #0"}
rst -processor
dow ./kv260_bram_test.elf
con

# Monitor UART output at 115200 baud on /dev/ttyUSB1 (Linux host):
# screen /dev/ttyUSB1 115200
```

### Relevance to Your Project

The JTAG flow above is the fastest iteration loop for your demo: change C code → rebuild ELF → `dow` + `con` in XSDB without touching the bitstream or FSBL. Reserve the QSPI/SD boot path for final deployment testing. Confirm your UART console is on `/dev/ttyUSB1` (the second of the two KV260 USB-serial interfaces; the first is typically JTAG/XSDB).

## AMD/Xilinx Tool Updates (2025.x)

### Key Findings

- **Vivado 2025.1: PS-first boot + dynamic PL loading**: The PS can now boot and run application code before the PL bitstream is loaded, enabling staged bring-up where software verifies DDR and UART before asserting PL reset — useful for diagnosing whether a hang is in the PL or PS.
- **Vivado 2025.2: Ultra-low-area AXI SmartConnect/Switch mode**: Set the `STRATEGY` parameter to `1` on the `axi_smartconnect` IP to enable a new resource-optimised implementation — AMD reports significant LUT savings at the cost of maximum throughput. Suitable for the KV260 AXI-BRAM demo, which is latency-tolerant.
- **Vivado 2025.2: Simplified AXI connections between SV instances with automatic wrapper creation**: Reduces manual port-mapping boilerplate when mixing VHDL and SystemVerilog modules in the same block design.
- **Vivado 2025.2: BUFG_FABRIC replication per-SLR and per-VNoC column**: Improves clock distribution for large multi-SLR designs (not directly relevant to K26, which is a single SLR device, but relevant if porting to VCK190/VEK280).
- **Vitis 2025.2: ECC support for dataflow buffers in BRAM/UltraRAM**: HLS-generated pipelines can now use error-correcting BRAM buffers, reducing soft-error risk in deployed bare-metal/RTOS systems.
- **Known issue — Vivado 2025.x: AXI full peripheral address space limited to 1 KB in some IPI configurations**: A reported forum bug where AXI Full (not AXI-Lite) peripherals show only 1 KB usable address space in IP Integrator. Workaround: manually set the range in the Address Editor to the correct value (e.g., 64 KB for a 16-deep 32-bit BRAM).

### Code Example

```tcl
# Vivado 2025.2 TCL: enable ultra-low-area mode on AXI SmartConnect
# Run inside an open block design to reconfigure the interconnect IP

# Get the SmartConnect instance (name may vary)
set sc [get_bd_cells axi_smc]

# Set STRATEGY = 1 for ultra-low-area mode (new in 2025.2)
set_property CONFIG.STRATEGY {1} $sc

# Verify the change
report_property $sc CONFIG.STRATEGY

# Re-validate and regenerate
validate_bd_design
generate_target all [get_files *.bd]
```

### Relevance to Your Project

The 1 KB address space bug is directly relevant: if you recently saw BRAM reads returning garbage after the first 1024 bytes, this Vivado 2025.x IPI issue is a strong candidate. Check the Address Editor immediately. The dynamic PL loading feature in 2025.1 also pairs well with your bare-metal demo — you could boot the A53 with a minimal FSBL that validates UART/DDR, then load the AXI-BRAM bitstream programmatically using `XFpga_PL_BitSream_Load()`.
