# FPGA Research Digest - 2026-11-05

## Executive Summary
- **AXI-Lite deadlock risk**: Never wait for READY before asserting VALID — this violates the AXI spec and can cause the bus to hang indefinitely; the subordinate must have both AW and W before asserting BVALID.
- **Vivado non-project TCL**: Use `vivado -mode tcl -source script.tcl` with explicit `write_checkpoint` and report commands at each stage; non-project mode generates no default outputs and scripts must handle exit codes for CI.
- **Kria KV260 JTAG is safest for bare-metal dev**: Writing a self-booting image to QSPI would overwrite Kria boot firmware — use JTAG boot mode override to load the PS and bitstream during development.
- **XDC async clock groups vs. timing exceptions**: `set_clock_groups -asynchronous` silences cross-domain reports but does not make the crossing safe; still use CDC analysis or `set_max_delay -datapath_only` for paths that need bounding.
- **Vitis BSP stdout setup**: On Zynq UltraScale+, explicitly configure `stdin`/`stdout` to `psu_uart_1` in BSP settings; the BOOTROM initializes UART to 115200 baud but the BSP setting ensures xil_printf routes there.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings
- An AXI handshake transfers data only when VALID **and** READY are both high on the same rising edge — a master must assert VALID without waiting for READY, never the reverse.
- For AXI-Lite writes: the subordinate must receive both the AW (address) channel and the W (data) channel before it may assert BVALID; either channel may arrive first.
- Clearing "handshake-done" latch flags after the B-channel response handshake is a common omission — missing the clear leaves the slave thinking it already serviced the cycle.
- AXI-Stream: a beat transfers only when TVALID=1 **and** TREADY=1; checking TLAST without that qualification drops the last beat silently.
- Backpressure on AXI-Stream is unbounded by spec — a full FIFO can stall a packet indefinitely; design the upstream master to handle this.
- Xilinx's older generated AXI-Lite demo cores (pre-Vivado 2016.4) had a write-response loss bug; current IP is clean but verify with ILA capture if you see hang-on-write symptoms.

### Code Example
```vhdl
-- AXI-Lite slave write channel skeleton (bare minimum, no deadlock)
-- Both AW and W must arrive before we drive BVALID

architecture rtl of axi_lite_slave is
  signal aw_done : std_logic := '0';
  signal w_done  : std_logic := '0';
begin

  -- AW channel: accept address immediately
  AWREADY <= '1';
  process(clk) begin
    if rising_edge(clk) then
      if AWVALID = '1' then
        aw_addr <= AWADDR;
        aw_done <= '1';
      end if;
      if bfire = '1' then aw_done <= '0'; end if;  -- clear after response
    end if;
  end process;

  -- W channel: accept data immediately
  WREADY <= '1';
  process(clk) begin
    if rising_edge(clk) then
      if WVALID = '1' then
        w_data <= WDATA;
        w_done <= '1';
      end if;
      if bfire = '1' then w_done <= '0'; end if;   -- clear after response
    end if;
  end process;

  -- B channel: respond only when both channels done
  bfire   <= BVALID and BREADY;
  BVALID  <= aw_done and w_done;
  BRESP   <= "00";  -- OKAY

end architecture;
```

### Relevance to Your Project
Your KV260 demo drives two BRAM controllers (0xA0000000, 0xA0010000) over AXI-Lite from the Cortex-A53. The pattern above matches what the Xilinx AXI BRAM Controller IP implements internally. If you observe a hang on write (xil_printf never reaching "PASS"), capture with an ILA on BVALID/BREADY — the most common cause is BVALID never going high because one of AW/W was missed or the done flags were not cleared.

## Vivado Block Design / IP Integrator

### Key Findings
- Run **Connection Automation** from the banner after adding IP; keep the clock source field as "Auto" for each AXI connection so Vivado picks a consistent clock.
- The **Address Editor** tab only appears when the design contains an AXI master; if it is missing, open it via `Window → Address Editor`.
- Right-click in the Address Editor and choose **Auto-Assign Address** to resolve validation errors about unmapped peripherals — equivalent to the toolbar **Assign All** button.
- For AXI BRAM controllers, the Address Editor lets you set the base address and range; for the KV260 demo set BRAM0 = 0xA0000000 (64K range) and BRAM2 = 0xA0010000 (64K range).
- After editing addresses, always run **Validate Design** (F6) before generating the bitstream; validation catches unmapped segments that synthesis will silently ignore.
- The 2025.2 tutorial branch on GitHub (`Xilinx/Vivado-Design-Tutorials`) is the most current reference for IP Integrator workflows.

### Code Example
```tcl
# TCL snippet: auto-assign addresses and validate block design
open_project my_project/my_project.xpr
open_bd_design [get_files *.bd]

# Auto-assign all unmapped AXI address segments
assign_bd_address

# (Optional) manually set BRAM0 base and range
set_property offset 0xA0000000 [get_bd_addr_segs {mpsoc/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property range  64K         [get_bd_addr_segs {mpsoc/Data/SEG_axi_bram_ctrl_0_Mem0}]

set_property offset 0xA0010000 [get_bd_addr_segs {mpsoc/Data/SEG_axi_bram_ctrl_1_Mem0}]
set_property range  64K         [get_bd_addr_segs {mpsoc/Data/SEG_axi_bram_ctrl_1_Mem0}]

validate_bd_design
save_bd_design
```

### Relevance to Your Project
Matching the base addresses in the block design to the hard-coded constants in `main.c` (0xA0000000 and 0xA0010000) is the most common source of FAIL results on first boot. The TCL snippet lets you verify or correct the address map in a scripted, repeatable way rather than relying on manual GUI steps.

## Vivado TCL Scripting

### Key Findings
- Run Vivado in **batch/non-project mode** with `vivado -mode tcl -source run.tcl` for reproducible builds with no GUI dependency.
- Non-project mode generates **no default reports or checkpoints** — your script must call `write_checkpoint -force` after synthesis and implementation, and add explicit `report_timing_summary` and `report_utilization` calls.
- Pass per-build parameters via `-tclargs`; read them inside the script with `$argv` / `$argc` to keep scripts generic.
- Vivado's Tcl interpreter does **not** handle BOM (byte-order mark) — save `.tcl` files as UTF-8 without BOM; a BOM causes a cryptic parse error on the first line.
- Use `-nojournal -nolog` only in read-only flows; for real builds, redirect the journal (`-journal build.jou`) so it doesn't get overwritten by the next run.
- Exit code from `vivado -mode batch` is non-zero on Tcl errors — hook your CI wrapper to test `$?` and fail the pipeline accordingly.

### Code Example
```tcl
# Non-project mode RTL-to-bitstream skeleton
# Usage: vivado -mode batch -source build.tcl -tclargs my_project xc7z020clg400-1

set proj_name [lindex $argv 0]
set part      [lindex $argv 1]

# Read sources
read_vhdl  [glob src/*.vhd]
read_xdc   constraints/top.xdc

# Synthesize
synth_design -top kv260_top -part $part
write_checkpoint -force checkpoints/post_synth.dcp
report_utilization -file reports/utilization_synth.rpt

# Implement
opt_design
place_design
route_design
write_checkpoint -force checkpoints/post_route.dcp
report_timing_summary -max_paths 10 -file reports/timing_route.rpt

# Generate bitstream
write_bitstream -force output/${proj_name}.bit
```

### Relevance to Your Project
Your `kv260_claude/kv260/tcl/create_bd.tcl` likely scripts the block design creation. Pairing it with a build script like the one above lets you regenerate the full bitstream from scratch with a single command — invaluable when Vivado's project file drifts or when setting up CI on a new machine.

## Vitis Bare-Metal / Standalone

### Key Findings
- In the Vitis BSP settings, **explicitly set `stdin` and `stdout` to `psu_uart_1`** (UART1 is routed to USB on the KV260); failing to do this means xil_printf output goes nowhere even though the UART is initialized by BOOTROM.
- `xil_printf` is a ~1 KB lightweight implementation — it **does not support `%f` (float) or `%lld` (64-bit long)**; use `printf` from `libc` for those, but be aware it costs ~20–40 KB of flash.
- The linker script `lscript.ld` generated by Vitis places code in DDR at the default base; for multi-core bare-metal, each application must have its own non-overlapping DDR region — edit the script's memory map section.
- The BSP sources ship with Vitis and are also on GitHub under the `embeddedsw` repo — useful for understanding peripheral driver behavior without opening Vitis.
- Include `xil_io.h` (not just `xil_printf.h`) when you need direct memory-mapped I/O reads/writes alongside printf.
- The BOOTROM initializes UART at 115200 8N1; the application's BSP inherits that rate so you typically don't call `XUartPs_Initialize` in a simple test.

### Code Example
```c
/* bare-metal AXI-BRAM read/write test pattern */
#include "xil_printf.h"
#include "xil_io.h"

#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL
#define TEST_WORDS  4

static const u32 pattern[TEST_WORDS] = {0xDEADBEEF, 0xCAFEBABE, 0x12345678, 0xA5A5A5A5};

int main(void) {
    int pass = 1;

    /* Write phase */
    for (int i = 0; i < TEST_WORDS; i++) {
        Xil_Out32(BRAM0_BASE + i * 4, pattern[i]);
        Xil_Out32(BRAM2_BASE + i * 4, pattern[i] ^ 0xFFFFFFFF);
    }

    /* Read-back phase */
    for (int i = 0; i < TEST_WORDS; i++) {
        u32 r0 = Xil_In32(BRAM0_BASE + i * 4);
        u32 r2 = Xil_In32(BRAM2_BASE + i * 4);
        if (r0 != pattern[i] || r2 != (pattern[i] ^ 0xFFFFFFFF)) {
            xil_printf("FAIL word %d: BRAM0=0x%08X (exp 0x%08X)  "
                       "BRAM2=0x%08X (exp 0x%08X)\r\n",
                       i, r0, pattern[i], r2, pattern[i] ^ 0xFFFFFFFF);
            pass = 0;
        }
    }
    xil_printf(pass ? "PASS\r\n" : "FAIL\r\n");
    return 0;
}
```

### Relevance to Your Project
This mirrors the described AXI-BRAM demo flow. The complementary pattern (`pattern ^ 0xFFFFFFFF`) written to BRAM2 provides a simple sanity check that the two BRAMs are genuinely distinct — an address decoding bug where both masters hit the same physical RAM would read back matching values and fail the complement check.

## XDC Timing Constraints

### Key Findings
- For the PS-to-PL AXI clock on Zynq UltraScale+, `create_clock` is **not needed** for `pl_clk0` — the PS automatically generates the clock constraint; only create a clock on PL-side logic if you use a separate PL oscillator.
- Use `set_clock_groups -asynchronous -group [get_clocks clk_a] -group [get_clocks clk_b]` to cut timing analysis between unrelated clocks — this takes **precedence over timing exceptions** so apply it last in the XDC file.
- `set_clock_groups -asynchronous` suppresses timing reports for those paths but does **not** make the crossing safe; always back it with CDC analysis or synchronizer cells.
- For paths that cross PS/PL asynchronously where you need a bound (not just false path), prefer `set_max_delay -datapath_only` over `set_false_path` to get a timing check without full setup/hold analysis.
- `set_input_delay` / `set_output_delay` constraints for board-level I/O reference an `external_clock` — on the KV260, the UART and JTAG signals are handled through the PS, not the PL, so you typically don't need I/O delay constraints for a minimal BRAM demo.

### Code Example
```tcl
# Minimal XDC for KV260 AXI-BRAM bare-metal demo

# PL logic clock (100 MHz) driven from PS pl_clk0
# Note: Vivado auto-creates a constraint for the PS clock;
# only needed if you have an independent PL reference.
# create_clock -period 10.000 -name pl_clk0 [get_ports pl_clk0_in]

# Cut timing between PS AXI clock and any PL-only free-running clock
# (only relevant if you add a separate PL clock domain)
# set_clock_groups -asynchronous \
#   -group [get_clocks -include_generated_clocks pl_clk0] \
#   -group [get_clocks -include_generated_clocks pl_clk1]

# False path for async reset (if used)
set_false_path -from [get_ports aresetn]

# Bitstream compression for faster JTAG loading
set_property BITSTREAM.GENERAL.COMPRESS TRUE [current_design]
```

### Relevance to Your Project
A minimal AXI-BRAM demo with a single PS-sourced clock typically needs almost no manual XDC timing work — Vivado infers the PS clock automatically. The main constraint worth adding is `BITSTREAM.GENERAL.COMPRESS TRUE` to speed up JTAG programming during iteration, and a false path on any async reset signal driven from the PS.

## Kria KV260 / K26 SoM

### Key Findings
- The KV260 ships with **QSPI32 boot mode** and read-only boot firmware; writing a self-booting image to QSPI will brick the board's default boot path — use **JTAG** for development.
- Boot firmware **v1.07** (2026 toolchain) and **v1.06** (2025.2 toolchain) are the current releases; check `xilinx-wiki.atlassian.net` for the firmware update procedure if your board shipped with an older version.
- EMIO (Extended MIO) routes PS GPIO through the PL fabric to SOM240_1 connector pins — useful for driving Pmod or custom carrier-board peripherals from bare-metal without a PL-side IP core.
- The KV260 carrier board routes **UART1 to USB-JTAG** (the micro-USB connector) — this is `psu_uart_1` in the PS configuration; UART0 is wired to MIO and not broken out on the carrier board.
- For the AXI-BRAM demo, the PS AXI HP0 or GP0 port is the master — confirm in the block design that the Zynq PS IP has the correct AXI master port enabled and that it is the same port wired to the interconnect.
- MIO banks 500 (MIO 0–25) and 501 (MIO 26–51) are on the SOM; MIO 502 (MIO 52+) is on the carrier board via connectors.

### Code Example
```tcl
# TCL snippet: configure Zynq UltraScale+ PS for KV260 bare-metal AXI demo
# in create_bd.tcl after create_bd_cell of zynq_ultra_ps_e_0

set_property -dict [list \
  CONFIG.PSU__USE__M_AXI_GP0 {1} \
  CONFIG.PSU__MAXIGP0__DATA_WIDTH {32} \
  CONFIG.PSU__CRL_APB__PL0_REF_CTRL__FREQMHZ {100} \
  CONFIG.PSU__UART1__PERIPHERAL__ENABLE {1} \
  CONFIG.PSU__UART1__PERIPHERAL__IO {MIO 36 .. 37} \
  CONFIG.PSU__TTC0__PERIPHERAL__ENABLE {1} \
  CONFIG.PSU__FPGA_PL0_ENABLE {1} \
] [get_bd_cells zynq_ultra_ps_e_0]
```

### Relevance to Your Project
The PS settings above enable M_AXI_GP0 (the AXI master used in most simple BRAM demos), route UART1 to MIO 36–37 (which connects to the USB UART on the KV260 carrier), and enable the 100 MHz PL clock. These are the minimum PS settings for a bare-metal PS-to-PL connectivity demo.

- **Vivado 2025.1 issues**: `updatemem` command is not supported on Spartan UltraScale+; an ECO flow clock routing issue was reported; hold failures on routed designs affect Versal Gen 2 MIPI IP (not Zynq UltraScale+, so not directly relevant to KV260).

- AMD's Vitis highlights page lists 2025.1 feature additions but the detail is in the official release notes at `docs.amd.com` — worth reviewing before starting a new project on that version.
