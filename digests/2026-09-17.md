# FPGA Research Digest - 2026-09-17

## Executive Summary

- **AXI-Lite BRAM write-enable off-by-one**: The BRAM Controller can assert its write enable one clock early and write an extra word if the BRAM Enable (ENA) signal is not gated correctly — directly relevant to the dual-BRAM topology at 0xA0000000 and 0xA0010000.
- **Non-project mode block design must be pre-generated**: When using TCL in non-project mode (as `create_bd.tcl` does), the block design output products must be generated explicitly before synthesis or you get a hard error; use `generate_target all [get_files *.bd]`.
- **Vitis 2025.1 bare-metal UART is PS-initialized automatically**: `xil_printf` works as soon as PS init runs; no manual UART baud-rate setup needed, but linker script `DDR` region base must match the actual load address on the KV260 (0x00000000 for TCM or 0x00100000 for DDR).
- **AXI SmartConnect ultra-low-area mode added in 2025.2**: Setting `STRATEGY=LowArea` on SmartConnect reduces LUT overhead for simple PS→BRAM paths — consider upgrading from 2025.1 if resource budget is tight.
- **Kria KV260 boot firmware compatibility break in 2026.1**: Pre-built WIC images require boot firmware released with 2026.1 or later; earlier bare-metal flows remain compatible, but do not mix 2026.x WIC images with 2025.1-built XSA/BIT files.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- **VALID/READY handshake rule**: Once a master asserts `AWVALID` or `WVALID`, it must hold that signal and all associated data/address lines stable until the slave asserts the corresponding `READY`. Violating this causes silent data corruption, not a bus error.
- **No VALID-before-READY deadlock**: A master must never wait for READY before asserting VALID; a slave waiting for VALID before asserting READY creates a protocol deadlock. Symmetric dependency is legal; asymmetric dependency from master side is not.
- **BRAM Controller write-enable bug**: Reported in AMD Adaptive Support — the AXI BRAM Controller v4.x can assert `we` one clock early (12 words written instead of 11) when the BRAM Enable port (`ENA`/`ENB`) is left undriven or driven incorrectly. Fix: ensure the Enable port is tied to the BRAM Controller's internal enable output, not hardwired high.
- **AXI-Stream backpressure discipline**: When a downstream slave de-asserts `TREADY`, the upstream master must hold `TDATA` and `TVALID` stable indefinitely. Inserting a skid buffer (elastic register) between stages prevents combinatorial READY paths from becoming critical timing paths.
- **SmartConnect vs Interconnect behavioral difference**: Switching between `AXI SmartConnect` and `AXI Interconnect` IP at the same address map can produce different simulation results; SmartConnect handles outstanding transactions differently, which affects read-modify-write correctness.

### Code Example

```c
/* AXI-Lite write/read round-trip with explicit barriers (bare-metal, no cache) */
#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL

static inline void axi_write32(uintptr_t addr, uint32_t val) {
    *(volatile uint32_t *)addr = val;
    /* dsb() ensures the AXI write completes before the next instruction */
    __asm__ volatile ("dsb sy" : : : "memory");
}

static inline uint32_t axi_read32(uintptr_t addr) {
    __asm__ volatile ("dsb sy" : : : "memory");
    return *(volatile uint32_t *)addr;
}

void test_bram(void) {
    const uint32_t pattern = 0xDEADBEEF;
    axi_write32(BRAM0_BASE + 0x00, pattern);
    axi_write32(BRAM2_BASE + 0x00, ~pattern);
    uint32_t r0 = axi_read32(BRAM0_BASE + 0x00);
    uint32_t r2 = axi_read32(BRAM2_BASE + 0x00);
    xil_printf("BRAM0: %s\r\n", (r0 == pattern)  ? "PASS" : "FAIL");
    xil_printf("BRAM2: %s\r\n", (r2 == ~pattern) ? "PASS" : "FAIL");
}
```

### Relevance to Your Project

Your `main.c` writes patterns to BRAM0 (0xA0000000) and BRAM2 (0xA0010000) over AXI-Lite and reads them back. The `dsb sy` barrier ensures each AXI transaction has completed through the interconnect before the next begins, preventing a race between the Cortex-A53 store buffer and the BRAM Controller's VALID/READY sequencing. The BRAM Enable off-by-one bug directly affects any design using AXI BRAM Controller v4.x with the default `enable` port wiring.

## Vivado Block Design / IP Integrator

### Key Findings

- **Export Block Design → TCL is the canonical reproducibility method**: Use `File > Export > Export Block Design` to generate a self-contained TCL script. Manually strip project-level `create_project` commands before committing to version control; retain only IP configuration and connection logic.
- **Connection Automation misses address segments**: `apply_bd_automation` auto-connects clocks and resets but does not always assign address segments. Always follow with `assign_bd_address` and verify the Address Editor manually.
- **`validate_bd_design` is mandatory before synthesis**: Skipping this step can allow illegal topologies (undriven AXI clocks, mismatched data widths) to proceed to synthesis and produce cryptic errors instead of clear BD validation failures.
- **OOC synthesis not available in non-project mode**: Out-of-context (OOC) synthesis for BD sub-modules is a project-mode-only feature. Non-project mode synthesizes the entire design as a flat netlist.
- **Regenerate output products after any IP parameter change**: After modifying IP (e.g., changing BRAM depth), call `generate_target all [get_files *.bd]` before re-running synthesis; stale XCI outputs silently use old parameters.

### Code Example

```tcl
# Minimal non-project mode block design generation flow
# Run after sourcing create_bd.tcl

# Validate the design before generating
validate_bd_design

# Generate all output products (required in non-project mode)
generate_target all [get_files [get_property DIRECTORY [current_project]]/*.bd]

# Add the wrapper and synthesize
make_wrapper -files [get_files *.bd] -top
add_files -norecurse [glob ./*/hdl/*_wrapper.v]

# Synthesize, implement, write bitstream
synth_design -top kv260_top_wrapper -part xck26-sfvc784-2LV-c
opt_design
place_design
route_design
write_bitstream -force ./output/kv260_top.bit
```

### Relevance to Your Project

Your `create_bd.tcl` script runs in project mode but can be adapted for non-project batch use by removing `create_project` and adding the `generate_target` call shown above. This enables CI/CD-style bitstream generation without a Vivado GUI session.

## Vivado TCL Scripting

### Key Findings

- **Non-project mode workflow**: In non-project mode, Vivado reads source files and implements the design purely in-memory. Source file changes on disk are not auto-detected; you must reload changed sources explicitly with `read_vhdl`/`read_xdc`.
- **`get_property DIRECTORY` is safer than hardcoded paths**: Use `[get_property DIRECTORY [current_project]]` to resolve the project directory dynamically rather than embedding absolute paths, making scripts portable across machines.
- **`set_property` on IP before `generate_target`**: IP parameters must be set with `set_property CONFIG.*` on the IP core object before generating output products. Changing parameters after generation requires calling `generate_target` again.
- **Batch mode launch**: `vivado -mode batch -source create_bd.tcl` is the clean CI invocation. Use `-tclargs` to pass runtime variables like part number or output directory.
- **`write_hw_platform` replaces `write_dsa` in 2021+**: For Vitis integration, export the hardware platform with `write_hw_platform -fixed -include_bit -force output/kv260.xsa` — the old `write_dsa` command is removed.

### Code Example

```tcl
# Portable TCL snippet: set part from argument or fall back to KV260 default
set part "xck26-sfvc784-2LV-c"
if {[llength $argv] > 0} { set part [lindex $argv 0] }

# Open or recreate project
if {[file exists "./vivado_project/vivado_project.xpr"]} {
    open_project ./vivado_project/vivado_project.xpr
} else {
    create_project vivado_project ./vivado_project -part $part
}

# Source the BD creation script
source ./tcl/create_bd.tcl

# Validate, generate, wrap
validate_bd_design
generate_target all [get_files *.bd]
make_wrapper -files [get_files *.bd] -top
set wrapper [glob ./vivado_project/*/hdl/*_wrapper.v]
add_files -norecurse $wrapper
set_property top kv260_top_wrapper [current_fileset]
update_compile_order -fileset sources_1

# Export hardware for Vitis
launch_runs impl_1 -to_step write_bitstream -jobs 8
wait_on_run impl_1
open_run impl_1
write_hw_platform -fixed -include_bit -force ./output/kv260.xsa
```

### Relevance to Your Project

Your existing `create_bd.tcl` handles block design creation. The `write_hw_platform` command at the end of the snippet is the missing link between the Vivado bitstream and opening the project in Vitis 2025.1 — without it, Vitis cannot auto-detect the PS/PL memory map.

## Vitis Bare-Metal / Standalone

### Key Findings

- **PS initialization is implicit**: In standalone BSP, `ps7_init()` (Zynq-7000) or the equivalent MPSoC init is called before `main()` by the startup code. For the K26 (Zynq UltraScale+ MPSoC), do not call `XUartPs_CfgInitialize()` manually unless you need a non-default baud rate; `xil_printf` works immediately after BSP startup.
- **Default UART is UART1 on KV260**: The KV260 carrier card routes PS UART1 to the USB-UART bridge. In the BSP `xparameters.h`, confirm `STDOUT_BASEADDRESS` is set to the UART1 base address (0xFF010000), not UART0.
- **Linker script DDR origin**: The default standalone linker script places code at DDR offset 0x00100000. For a KV260 running without Linux, you can use the full DDR range starting at 0x00000000; adjust `lscript.ld` to avoid potential overlap with TF-A or PMU firmware loaded at high addresses.
- **`Xil_DCacheFlushRange` before DMA or PL access**: If D-cache is enabled, cached writes to the AXI-mapped BRAM region may not reach the PL. Mark the BRAM address range as device memory in the MMU, or call `Xil_DCacheFlushRange(BRAM0_BASE, size)` after writes.
- **Interrupt controller (GIC) initialization order matters**: Initialize `XScuGic` before enabling any PL interrupts; calling `XScuGic_Enable()` before `XScuGic_CfgInitialize()` causes a hard fault on the A53.

### Code Example

```c
#include "xparameters.h"
#include "xil_printf.h"
#include "xil_cache.h"
#include "xil_io.h"

#define BRAM0_BASE  XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR
#define BRAM2_BASE  XPAR_AXI_BRAM_CTRL_1_S_AXI_BASEADDR
#define BRAM_SIZE   0x2000U

int main(void) {
    /* Flush/invalidate D-cache for BRAM regions before access */
    Xil_DCacheFlushRange(BRAM0_BASE, BRAM_SIZE);
    Xil_DCacheFlushRange(BRAM2_BASE, BRAM_SIZE);

    uint32_t patterns[] = {0xA5A5A5A5, 0x5A5A5A5A, 0xDEADBEEF, 0x12345678};
    int fail = 0;

    for (int i = 0; i < 4; i++) {
        Xil_Out32(BRAM0_BASE + i * 4, patterns[i]);
        Xil_Out32(BRAM2_BASE + i * 4, ~patterns[i]);
    }

    /* Ensure writes complete before readback */
    __asm__ volatile ("dsb sy" : : : "memory");

    for (int i = 0; i < 4; i++) {
        uint32_t r0 = Xil_In32(BRAM0_BASE + i * 4);
        uint32_t r2 = Xil_In32(BRAM2_BASE + i * 4);
        if (r0 != patterns[i] || r2 != ~patterns[i]) {
            xil_printf("FAIL at offset %d: got 0x%08X / 0x%08X\r\n", i*4, r0, r2);
            fail++;
        }
    }
    xil_printf(fail ? "OVERALL: FAIL (%d errors)\r\n" : "OVERALL: PASS\r\n", fail);
    return fail;
}
```

### Relevance to Your Project

This is a direct drop-in replacement for the pattern test in your `main.c`. It uses `XPAR_AXI_BRAM_CTRL_*_BASEADDR` constants from `xparameters.h` (auto-generated from your XSA) instead of hardcoded addresses, and uses `Xil_DCacheFlushRange` to avoid cache coherency failures — a common source of intermittent FAIL results on the KV260 when D-cache is on.

## XDC Timing Constraints

### Key Findings

- **Always start with `create_clock` on the PS output clock**: In Zynq/Kria designs, the PL clock comes from the PS via `FCLK_CLK0`. Use `create_clock -period 10.000 -name pl_clk0 [get_pins PS/inst/PSS_ALTO_CORE_I/PLCLK[0]]` (adjust the cell path to match your PS IP instance name).
- **`set_input_delay` and `set_output_delay` are mandatory for clean timing reports**: Even for AXI-Lite to BRAM, unconstrained I/O paths produce false "no path" warnings that mask real timing failures. Constrain all IOs with at least a dummy value.
- **`set_clock_groups -asynchronous` for PS/PL boundary**: If your VHDL wrapper uses a separate free-running oscillator for any logic, declare it async relative to `pl_clk0` to prevent Vivado from attempting impossible cross-domain timing analysis.
- **`set_false_path` on reset**: Synchronous resets driven from PS GPIO or soft reset IP should be declared as false paths in timing if they span multiple clock domains.
- **Timing closure tip for AXI-Lite at 100 MHz**: The AXI BRAM Controller and AXI SmartConnect IP typically meet timing at 100 MHz on the K26 (speed grade -2LV) without manual Pblocking. If timing fails, check the interconnect for large fanout nets on `AWADDR` and use `set_max_delay -datapath_only` to relax cross-domain paths.

### Code Example

```tcl
# KV260 minimal XDC timing constraints for AXI-BRAM design

# PS-generated PL clock (100 MHz, 10 ns period)
# Adjust pin path to match your Zynq PS IP instance name
create_clock -period 10.000 -name pl_clk0 \
    [get_pins design_1_i/zynq_ultra_ps_e_0/inst/PSS_ALTO_CORE_I/PLCLK[0]]

# Declare all unconstrained inputs/outputs as false paths
# (replace with real set_input_delay/set_output_delay for production)
set_false_path -from [get_ports {reset_n}]

# Asynchronous relationship between PL clock and any free-running clk
# (uncomment if a second clock source is used)
# set_clock_groups -asynchronous \
#     -group [get_clocks pl_clk0] \
#     -group [get_clocks aux_clk]

# Relax reset path timing
set_false_path -to [get_cells -hierarchical -filter {IS_SEQUENTIAL && NAME =~ "*rst_reg*"}]

# Report timing summary after implementation
# report_timing_summary -delay_type min_max -report_unconstrained \
#     -check_timing_verbose -file timing_summary.rpt
```

### Relevance to Your Project

Your `kv260_top.vhd` wrapper instantiates the block design and drives AXI signals. The `create_clock` target pin path shown is the standard reference point for Zynq UltraScale+ PS clock output in Vivado 2025.1. Without this constraint, Vivado has no timing reference for the entire PL clock domain and all setup/hold analysis is skipped.

## Kria KV260 / K26 SoM

### Key Findings

- **SOM240_1 connector is the PS-PL bridge**: The K26 SOM connects to the KV260 carrier card via a 240-pin SOM240 connector. PL I/O banks (HP and HD) are accessible through this connector; MIO pins (PS UART, I2C, SD) are also routed here.
- **EMIO GPIO path**: PS GPIO connected via EMIO crosses PS→PL boundary, exits the K26 package, traverses SOM240_1, and reaches the carrier card. Latency is 1–2 extra clock cycles versus MIO-direct.
- **Bare-metal boot requires JTAG or SD card with BOOT.BIN**: The KV260 does not boot a bare-metal ELF directly from USB. You must package the ELF into a BOOT.BIN using Vitis's `bootgen` tool, or use JTAG download via `program_hw_devices` in Vivado Hardware Manager.
- **Boot firmware compatibility (2026.1 break)**: Pre-built WIC images for KV260 starting with 2026.1 require updated boot firmware. Bare-metal flows using custom BOOT.BIN are unaffected, but do not use 2026.1 WIC images with a 2025.1 PL bitstream without re-validating the boot sequence.
- **Power domains**: The K26 uses separate power rails for PS (VCCINT_PS, VCCO_MIO) and PL (VCCINT, VCCAUX, VCCO_HP). Ensure the carrier card provides correct voltages before applying PL configuration; voltage sequencing violations can corrupt BRAM contents.

### Code Example

```tcl
# Vivado TCL: JTAG-based bare-metal deployment workflow for KV260
# Run from Vivado Tcl Console after connecting JTAG cable

open_hw_manager
connect_hw_server -url localhost:3121
open_hw_target

# Select the K26 device (ARM DAP + PL JTAG chain)
set device [lindex [get_hw_devices] 0]
current_hw_device $device
refresh_hw_device $device

# Program PL bitstream
set_property PROGRAM.FILE {./output/kv260_top.bit} $device
program_hw_devices $device

# Download ELF to PS DDR via JTAG (requires arm_0 core)
set core [get_hw_cores arm_0]
set_property PROGRAM.FILE {./output/kv260_app.elf} $core
program_hw_cores $core

# Run the application
run_hw_cores $core
```

### Relevance to Your Project

This TCL workflow replaces the manual GUI steps in Vivado Hardware Manager for your KV260 bare-metal demo. It programs both the PL bitstream and PS ELF in one script invocation, enabling faster iteration during BRAM connectivity testing. The JTAG path is the most reliable for bare-metal debug since it bypasses the boot ROM and SD card entirely.

## AMD/Xilinx Tool Updates (2025.x)

### Key Findings

- **Vivado 2025.2 adds AXI SmartConnect ultra-low-area mode**: A new `STRATEGY=LowArea` parameter on `AXI SmartConnect` and `AXI Switch` IPs reduces LUT footprint for simple single-master topologies — beneficial for the PS→BRAM path.
- **Vitis 2025.1 improves Versal AI Engine dataflow**: Enhanced DSP library functions and new AI Engine APIs shipped in 2025.1 (not directly relevant to KV260 bare-metal, but affects platform creation if migrating to Versal).
- **`write_hw_platform` (XSA) is the Vitis 2025.x standard export**: `write_dsa` was removed in 2021; confirm any older TCL scripts in the project use `write_hw_platform` instead.
- **2025.1 IP change log**: The comprehensive Vivado 2025.1 IP change log is available at AMD Answer Record 000037919. Key IP updates include AXI BRAM Controller v4.1 patch-level fixes and SmartConnect routing improvements.
- **Known issue: Vitis 2025.x BSP re-generation after XSA update**: After updating the XSA (e.g., changing BRAM address), the standalone BSP in Vitis requires a full platform rebuild (`vitis -s rebuild_platform.py`) to regenerate `xparameters.h` with new base addresses. Simply updating the XSA file without rebuilding the platform produces stale address constants.

### Code Example

```tcl
# Vivado 2025.x: export XSA for Vitis after implementation
# (replaces write_dsa from pre-2021 flows)

open_project ./vivado_project/vivado_project.xpr
open_run impl_1

# Write fixed (post-implementation) hardware platform with bitstream
write_hw_platform \
    -fixed \
    -include_bit \
    -force \
    ./output/kv260_platform.xsa

puts "XSA written to ./output/kv260_platform.xsa"
puts "In Vitis: File > New Platform > browse to this XSA"
```

```python
# Vitis 2025.x: rebuild platform after XSA update (Python script for Vitis batch mode)
# Usage: vitis -s rebuild_platform.py
import vitis

client = vitis.create_client()
platform = client.get_platform("kv260_platform")
platform.update_hw(hw="./output/kv260_platform.xsa")
platform.build()
client.close()
```

### Relevance to Your Project

The Vitis BSP rebuild issue directly affects your workflow: after any Vivado change that modifies the AXI address map (adding/removing BRAM controllers, changing offsets), a stale `xparameters.h` will have the wrong `XPAR_AXI_BRAM_CTRL_*_BASEADDR` values, causing the C application to write to the wrong addresses and fail the PASS/FAIL check silently.
