## Executive Summary

1. **AXI BRAM Controller write-enable off-by-one bug**: The v4 AXI BRAM Controller IP has a documented timing issue where the write-enable signal asserts one clock cycle early, causing an extra word to be written. The BRAM Enable signal must be properly tied to gate this extra cycle — directly relevant if you see spurious data in BRAM readback.
2. **Dual-port mode for throughput**: AXI BRAM Controller dual-port mode (Port A = writes, Port B = reads) allows pipelining read and write transactions simultaneously; single-port serializes them. For a PS-to-PL read-back demo, dual-port removes head-of-line blocking.
3. **Vivado 2025.1 is on the AMD download page; 2026.1 tools are now available**: The download index now lists 2026.1 as current. If you're on 2025.1, check for the IP core update roll-up before adding new IPs to the block design to avoid version mismatches.
4. **XDC constraint files for KV260 are available in the Kria-PYNQ repo**: `kv260/base/vivado/constraints/base.xdc` shows how AMD constraints the K26 MPSoC pins, useful as a reference template for your own `set_input_delay`/`set_output_delay` entries.
5. **Vitis Unified IDE 2025.x XSA import flow**: Platform creation now goes through *File → New Component → Platform → Browse XSA*. The standalone domain is auto-generated; BSP settings (stdin/stdout UART) must still be explicitly set for `xil_printf` to route to the correct UART.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- **Five independent channels**: AXI has Write Address (AW), Write Data (W), Write Response (B), Read Address (AR), and Read Data (R) channels; AXI-Lite uses the same five channels with no burst support and fixed 32/64-bit width.
- **VALID/READY handshake invariant**: Once VALID is asserted by an initiator it **must not** be de-asserted until READY is received. Violating this can cause protocol deadlock on the interconnect.
- **AXI BRAM Controller write-enable timing bug (PG078)**: The BRAM write-enable asserts one clock early and stays active one cycle too long. The BRAM Enable (`ena`/`enb`) signal must be used to gate the extra cycle; leaving Enable always-high exposes this off-by-one.
- **Dual-port mode**: In AXI BRAM Controller v4 dual-port mode, Port A handles writes and Port B handles reads. Read and write transactions can overlap, improving throughput; in single-port mode they are serialized through Port A.
- **ECC constraint**: ECC (C_ECC=1) adds one extra pipeline clock cycle on the datapath. Available only at 32-, 64-, or 128-bit data widths.

### Code Example

```c
/* Bare-metal AXI-Lite write then read-back pattern (Cortex-A53, standalone) */
#include "xil_io.h"

#define BRAM0_BASE  0xA0000000U
#define BRAM2_BASE  0xA0010000U

static inline void bram_write32(uintptr_t base, u32 offset, u32 val) {
    Xil_Out32(base + offset, val);
}

static inline u32 bram_read32(uintptr_t base, u32 offset) {
    return Xil_In32(base + offset);
}

int bram_selftest(uintptr_t base, u32 n_words) {
    for (u32 i = 0; i < n_words; i++)
        bram_write32(base, i * 4, 0xDEAD0000 | i);

    /* AXI-Lite write response (BVALID/BREADY) is consumed internally by
       the BRAM controller; no explicit poll needed for single-beat writes */

    for (u32 i = 0; i < n_words; i++) {
        u32 rd = bram_read32(base, i * 4);
        if (rd != (0xDEAD0000 | i)) return -1;
    }
    return 0;
}
```

### Relevance to Your Project

Your `main.c` already writes patterns to BRAM0 at `0xA0000000` and BRAM2 at `0xA0010000`. If readback fails on isolated words (not all words), suspect the write-enable off-by-one: enable the BRAM Enable pin tie-off in the BRAM Generator IP configuration and re-test. The `Xil_Out32`/`Xil_In32` helpers from the standalone BSP are the correct access path — they emit proper AXI-Lite single-beat transactions.

## Vivado Block Design / IP Integrator

### Key Findings

- **Auto-Assign Address resolves unmapped peripheral errors**: Right-click anywhere in the Address Editor tab → *Auto-Assign Address*. Without this step, block design validation fails with "unmapped peripheral" errors.
- **Connection Automation does not set address offsets**: Running *Run Connection Automation* wires up AXI interfaces but does not always assign correct base addresses. Always validate the block design (`validate_bd_design`) after automation and check the Address Editor.
- **Regenerating IP outputs**: If you edit a block design after an initial synthesis run, right-click the block design in the Sources pane → *Generate Output Products* before re-running synthesis. Skipping this step causes stale IP netlists to be used.
- **Hierarchical address assignment**: You can scope address spaces to a hierarchy boundary, allowing memory outside the block design (e.g., external DDR) to be mapped without adding it as an IP in the diagram.
- **IP catalog version mismatches**: When opening a project built on an older Vivado version, IP cores will be marked "out-of-date." Use *Report IP Status* and upgrade selectively; upgrading all IPs at once can break existing parameters.

### Code Example

```tcl
# Validate and re-generate outputs after editing the block design
open_bd_design [get_files *.bd]
validate_bd_design
generate_target all [get_files *.bd]

# Assign addresses programmatically (useful in non-interactive TCL flows)
assign_bd_address
```

### Relevance to Your Project

Your `create_bd.tcl` script creates the block diagram with the AXI BRAM controllers. If you ever regenerate the block design from scratch (e.g., after a Vivado version bump), always call `assign_bd_address` after `connect_bd_intf_net` calls — otherwise BRAM0 at `0xA0000000` and BRAM2 at `0xA0010000` may end up at different offsets and the C firmware will read/write the wrong peripherals.

## Vivado TCL Scripting

### Key Findings

- **Batch mode invocation**: `vivado -mode batch -source script.tcl -tclargs "PART=xck26-sfvc784-2LV-c"` runs the script headlessly and exits automatically. Ideal for CI pipelines.
- **Non-project vs. project mode**: Non-project mode (no `create_project`, just `read_vhdl`/`synth_design`/`impl_design`/`write_bitstream`) keeps no managed project state on disk — faster for automated flows but you must save checkpoints manually with `write_checkpoint`.
- **Project mode with TCL export**: After building a project interactively, *File → Project → Write Tcl* exports a reproducible `create_project` script. Re-running this TCL reconstructs the entire project from source files — this is the recommended version-control workflow.
- **`get_bd_cells` / `connect_bd_intf_net`**: IP Integrator's TCL API allows full scripted block design creation. The exported TCL from *Write Tcl* includes these calls verbatim, making it safe to use as a template.
- **Handling timing closure in batch**: Use `set_property SEVERITY {Warning} [get_drc_checks NSTD-1]` to demote non-critical DRC checks; use `launch_runs impl_1 -to_step write_bitstream` to run synthesis through bitstream in one command.

### Code Example

```tcl
#!/usr/bin/env tclsh
# Non-project mode: read sources, synthesize, implement, write bitstream

set part "xck26-sfvc784-2LV-c"

read_vhdl  [glob ./vhdl/*.vhd]
read_xdc   [glob ./constraints/*.xdc]

synth_design -top kv260_top -part $part
write_checkpoint -force ./checkpoints/post_synth.dcp

opt_design
place_design
route_design
write_checkpoint -force ./checkpoints/post_route.dcp

write_bitstream -force ./output/kv260_top.bit
```

### Relevance to Your Project

Your `create_bd.tcl` is a project-mode block design TCL script. For a cleaner CI workflow, wrap it in a batch invocation like:

```bash
vivado -mode batch -source tcl/create_bd.tcl -tclargs
```

Add `validate_bd_design` and `assign_bd_address` as the last calls in the script so any address map regressions surface immediately during the automated build rather than at runtime.

## Vitis Bare-Metal / Standalone

### Key Findings

- **Vitis Unified IDE XSA import**: In 2025.x, create a Platform Component via *File → New Component → Platform*, browse to the exported `.xsa` from Vivado, and name the platform. The standalone domain is auto-created.
- **BSP stdin/stdout must be configured explicitly**: `xil_printf` routes to whichever UART peripheral is set as `stdout` in the BSP. On the KV260, the USB-UART is routed through `psu_uart_1`; if stdout is set to `psu_uart_0` (the default), nothing prints.
- **`xil_printf` vs `printf`**: `xil_printf` is a lightweight implementation that does not support floating-point format specifiers (`%f`, `%e`, `%g`). Use it for `%d`, `%x`, `%s`. For float output, link the full newlib `printf` via BSP settings (*enable_sw_intrusive_profiling* is not needed; just change the `stdout` library setting to `libxil`).
- **Linker script DDR placement**: The generated linker script places `.text`, `.data`, and `.bss` in the DDR (`ps_ddr_0`) starting at `0x00000000`. For bare-metal AXI testing this is correct; stack and heap are also placed in DDR by default at the high end.
- **Cache coherency**: Cortex-A53 caches are enabled in the standalone BSP by default. For MMIO registers (including your BRAM controllers), use `Xil_Out32`/`Xil_In32` which issue device-type memory accesses bypassing the cache. Do **not** use normal pointer dereferences on MMIO addresses without `volatile`.

### Code Example

```c
/* BSP stdout assignment check — run early in main() */
#include "xparameters.h"
#include "xuartps.h"
#include "xil_printf.h"

void init_uart(void) {
    /* stdout is routed to XPAR_PSU_UART_1_BASEADDR (USB-UART on KV260)
       via BSP settings. This just confirms the peripheral is alive. */
    XUartPs_Config *cfg = XUartPs_LookupConfig(XPAR_PSU_UART_1_DEVICE_ID);
    if (cfg == NULL) {
        /* Fallback: hang with LED toggle if UART unavailable */
        while (1);
    }
    /* xil_printf now goes to USB-UART */
    xil_printf("UART initialized at %d baud\r\n", cfg->BaudRate);
}
```

### Relevance to Your Project

Your `main.c` uses `xil_printf` over USB-UART to report PASS/FAIL. The most common reason for silent output is `stdout` pointing at the wrong UART device. Verify in *Vitis → Platform → standalone domain → BSP settings* that `stdout` is `psu_uart_1`. Also confirm that `Xil_Out32`/`Xil_In32` are used for all BRAM accesses (not raw pointer casts) to avoid cache coherency surprises.

## XDC Timing Constraints

### Key Findings

- **`set_input_delay` / `set_output_delay` syntax (UG835 2025.1)**: Both commands take the delay in nanoseconds relative to a clock edge at the device boundary. Positive `set_input_delay` means data arrives after the reference clock edge.
- **AXI-Lite to BRAM timing is internal**: Because your PS AXI master → AXI BRAM Controller → BRAM path is entirely internal to the PL (no I/O pads involved), you do **not** need `set_input_delay`/`set_output_delay` for this path. Clock domain constraints (`create_clock` on `pl_clk0`) are sufficient.
- **Kria-PYNQ `base.xdc` as reference**: The Kria-PYNQ project (github.com/Xilinx/Kria-PYNQ) includes `kv260/base/vivado/constraints/base.xdc` showing how AMD constrains MPSoC pin assignments for the KV260 carrier card. Use it as a template when adding external I/O.
- **`set_clock_groups -asynchronous`**: If your design has multiple clocks (e.g., `pl_clk0` for logic, `pl_clk1` for a different IP), add `set_clock_groups -asynchronous -group [get_clocks pl_clk0] -group [get_clocks pl_clk1]` to prevent the timing engine from attempting cross-domain analysis on unrelated clocks.
- **Constraint Wizard**: Vivado's *Timing Constraint Wizard* (available after synthesis) auto-detects clock sources and generates stub constraints. Run it once on a new design to catch any unconstrained paths.

### Code Example

```xdc
# Minimal XDC for KV260 bare-metal AXI-BRAM demo
# pl_clk0 is driven by the Zynq MPSoC PS at 100 MHz (configurable in PS IP)
create_clock -period 10.000 -name pl_clk0 [get_pins design_1_i/zynq_ultra_ps_e_0/inst/PS8_i/PLCLK[0]]

# If adding external GPIO on PMOD connector (example only)
# set_input_delay  -clock pl_clk0 -max 3.0 [get_ports pmod_io[*]]
# set_output_delay -clock pl_clk0 -max 2.0 [get_ports pmod_io[*]]

# Prevent false cross-domain paths if a second PL clock is used
# set_clock_groups -asynchronous \
#     -group [get_clocks pl_clk0] \
#     -group [get_clocks pl_clk1]
```

### Relevance to Your Project

For your current design (PS AXI master → AXI-Lite → BRAM → readback), the only required constraint is `create_clock` on the PL clock output pin. The internal AXI paths are automatically timed relative to that clock. Add I/O delay constraints only if you extend the design with external-facing signals.

## Kria KV260 / K26 SoM

### Key Findings

- **MIO vs EMIO**: The K26 SoM has dedicated MIO pins for on-chip PS peripherals (UART, I2C, SPI, SD, ENET). EMIO routes PS peripheral signals through the PL fabric to external carrier card pins; this requires PL to be running and bitstream loaded. For bare-metal UART-only projects, only MIO pins (and thus no PL bitstream) are strictly needed for communication.
- **Boot flow on bare-metal**: On Kria, the ROM loads FSBL from SD/eMMC, FSBL initializes the PS and loads the bitstream + application ELF. Unlike a standard Zynq board, Kria's board management controller (BMC) on the carrier card handles power sequencing before FSBL runs — do not assume instant-on after power-up.
- **Vivado board files for K26**: AMD ships Vivado board files for the K26 SoM and KV260 CC that automatically pre-configure the Zynq UltraScale+ PS IP (clocks, MIO, DDR) matching the KV260 hardware. Always use the board preset rather than manually entering PS settings.
- **Custom Kria SOM Platform (XD101 tutorial)**: AMD published a 2025.1-compatible tutorial (`XD101`) for creating a custom Kria Vitis platform. Key insight: the platform `.xsa` must include the `clk_wiz` for PL clocking to be independently configurable in Vitis.
- **PMODs and RPi header are PL-connected**: On the KV260, PMODs and the 40-pin header are connected to PL pins, not PS MIO. Using them requires XDC pin assignments and a bitstream, unlike UART which is on PS MIO.

### Code Example

```tcl
# In create_bd.tcl: apply KV260 board preset to Zynq UltraScale+ PS IP
# (assumes KV260 board files are installed in Vivado)
create_bd_cell -type ip -vlnv xilinx.com:ip:zynq_ultra_ps_e:3.5 zynq_ultra_ps_e_0
apply_bd_automation -rule xilinx.com:bd_rule:zynq_ultra_ps_e \
    -config { apply_board_preset "1" } \
    [get_bd_cells zynq_ultra_ps_e_0]

# Enable one HP AXI Slave port for PL master access (not needed for PS-master demo)
# Enable one GP AXI Master port for PS→PL (BRAM) access
set_property -dict [list \
    CONFIG.PSU__USE__M_AXI_GP0 {1} \
    CONFIG.PSU__USE__S_AXI_GP0 {0} \
] [get_bd_cells zynq_ultra_ps_e_0]
```

### Relevance to Your Project

Using `apply_board_preset "1"` in your `create_bd.tcl` ensures PS clock rates, DDR timing, and UART MIO pinout match the physical KV260 hardware. Without this, you risk DDR instability or UART baud rate errors. The `PSU__USE__M_AXI_GP0 {1}` setting enables the PS AXI master port that drives your AXI-Lite to BRAM path.

## AMD/Xilinx Tool Updates

### Key Findings

- **Vivado/Vitis 2026.1 is now current**: As of September 2026, the AMD download page lists 2026.1 as the latest release. Vivado 2025.1 remains supported but is one major version behind.
- **Vitis Unified IDE consolidation**: Vitis 2025.x unified Vitis IDE, Vitis HLS, and Vitis Analyzer into a single tool. Workflows from Vitis 2022.x (separate application project + BSP project) are replaced by Component-based projects. The new workflow: Platform Component → Application Component → System Project.
- **Vitis 2025.1 known issue — LD_PRELOAD errors**: A documented issue in Vitis Unified IDE 2025.1 causes `LD_PRELOAD` library errors on some Linux configurations. Workaround: unset `LD_PRELOAD` before launching Vitis, or apply the patch from the AMD support article.
- **FPGA Developer AMI 1.18.0 includes Vivado/Vitis 2025.1**: If using AWS F1/F2 instances for cloud synthesis, the 1.18.0 AMI is pre-configured.
- **UG835 (Vivado TCL Command Reference) updated to 2025.2**: `set_input_delay` and `set_output_delay` documentation now reflects 2025.2 English. The TCL command syntax is unchanged from earlier versions.

### Code Example

```bash
# Vitis Unified IDE 2025.x: create platform + app from command line (headless)
# Export XSA from Vivado first, then:

xsct << 'EOF'
setws ./vitis_workspace

# Create platform component from XSA
platform create -name kv260_platform \
    -hw ./vivado_output/kv260_top.xsa \
    -proc psu_cortexa53_0 \
    -os standalone \
    -out ./vitis_workspace

# Set stdout to USB-UART (psu_uart_1 on KV260)
bsp config stdout psu_uart_1

platform generate

# Create application component
app create -name kv260_bram_test \
    -platform kv260_platform \
    -domain standalone_domain \
    -template {Empty Application(C)}

app build -name kv260_bram_test
EOF
```

### Relevance to Your Project

If you're on Vitis 2025.1 and encounter the `LD_PRELOAD` error, it will prevent the IDE from launching on Linux. The `xsct` headless flow shown above is immune to this issue and also enables CI automation. The `bsp config stdout psu_uart_1` line is the critical fix for silent UART output on the KV260.
