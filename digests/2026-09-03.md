# FPGA Research Digest - 2026-09-03

## Executive Summary
- **AXI-Lite backpressure bug**: If the master holds BREADY low, the slave must lower AWREADY and WREADY — a common omission in hand-rolled slaves that causes deadlock on real silicon, especially when PS back-pressure propagates from a slow UART print loop.
- **XDC clock constraints for Kria**: For a bare-metal AXI-BRAM design, always create the PS-generated PL clock with `create_clock` on the net driven by `clk_pl_0`, then use `set_clock_groups -asynchronous` to isolate it from any unrelated debug clocks.
- **BSP stdout mis-assignment**: If Vitis bare-metal prints nothing over USB-UART, verify that the BSP `stdin`/`stdout` is set to `psu_uart_1` (the Kria USB-UART port), not `psu_uart_0`; regenerate the BSP after changing it.
- **Vivado 2025.2 adds NoC XPM support in block design**: `module_ref` can now instantiate NoC XPMs inside IP Integrator — relevant to future bandwidth-hungry BRAMs.
- **Non-project TCL mode** is the most reproducible build path for CI: `vivado -mode batch -source build.tcl` guarantees identical output every run without a `.xpr` file in the repo.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings
- The AXI specification requires that READY **must not** be combinatorially dependent on VALID — violating this causes deadlock.
- In AXI-Lite, all five channel handshakes (AW, W, B, AR, R) must independently deal with backpressure. A common Xilinx demo-core mistake: not lowering AWREADY/WREADY when BREADY is de-asserted by the master.
- Latched handshake flags (`aw_hs_done`, `w_hs_done`) must be cleared **on the response handshake beat**, not one cycle later.
- AXI-Lite is strictly single-outstanding: never pipeline write-address and write-data channels across multiple transactions before receiving BVALID/BREADY.
- For AXI-Stream peripherals connected via `axis_data_fifo`, ensure `TREADY` from the slave is registered — combinational TREADY paths frequently cause timing failures in Vivado at 100 MHz+.

### Code Example
```vhdl
-- AXI-Lite write-response channel: correct backpressure handling
-- BVALID stays high until master asserts BREADY
process(S_AXI_ACLK)
begin
  if rising_edge(S_AXI_ACLK) then
    if S_AXI_ARESETN = '0' then
      axi_bvalid <= '0';
      axi_bresp  <= "00";
    else
      if (axi_aw_hs and axi_w_hs) = '1' then
        axi_bvalid <= '1';
        axi_bresp  <= "00"; -- OKAY
      elsif S_AXI_BREADY = '1' then
        axi_bvalid <= '0'; -- deassert only when master accepts
      end if;
    end if;
  end if;
end process;
```

### Relevance to Your Project
Your design writes patterns from the Cortex-A53 to BRAM0 (`0xA000_0000`) and BRAM2 (`0xA001_0000`). If any BVALID response is dropped because BREADY de-asserts unexpectedly (e.g., during a `xil_printf` stall), a subsequent AXI-Lite write from the PS will hang waiting for the previous BREADY. Register the BVALID/BRESP path as shown above to decouple write completion from the PS pipeline.

## Vivado Block Design / IP Integrator

### Key Findings
- **Run Connection Automation** (Designer Assistance) after adding each IP block — it automatically wires AXI Interconnect, Processing System Reset, and memory-mapped addresses for attached AXI slaves.
- The **Address Editor** tab exposes three states per slave segment: *Unassigned*, *Assigned*, and *Excluded*. Set range to 4K (`0x1000`) for BRAM controllers to match the `axi_bram_ctrl` default depth.
- When externalising an AXI interface (e.g., for a custom top-level wrapper), the Address Editor can still map all slaves normally — the slave-segment assignments survive the port promotion.
- Regenerating the block design output products (`generate_target all [get_files *.bd]`) is required after any BD change before running synthesis; skipping this causes stale netlist errors.
- **SmartConnect** (`axi_smc`) is preferred over the older `axi_interconnect` for new designs — it auto-sizes data widths, handles clock domain crossing, and has lower overhead for single-master topologies like a PS→BRAM path.

### Code Example
```tcl
# In create_bd.tcl: assign address segments for two BRAMs
assign_bd_address [get_bd_addr_segs {axi_bram_ctrl_0/S_AXI/Mem0}]
set_property offset 0xA0000000 [get_bd_addr_segs \
  {processing_system7_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property range 4K [get_bd_addr_segs \
  {processing_system7_0/Data/SEG_axi_bram_ctrl_0_Mem0}]

assign_bd_address [get_bd_addr_segs {axi_bram_ctrl_1/S_AXI/Mem0}]
set_property offset 0xA0010000 [get_bd_addr_segs \
  {processing_system7_0/Data/SEG_axi_bram_ctrl_1_Mem0}]
set_property range 4K [get_bd_addr_segs \
  {processing_system7_0/Data/SEG_axi_bram_ctrl_1_Mem0}]
```

### Relevance to Your Project
Your two BRAMs at `0xA000_0000` and `0xA001_0000` require explicit address assignment matching those offsets. The TCL snippet above is a direct model for your `create_bd.tcl`. Using `axi_smc` instead of `axi_interconnect` for the SmartConnect will simplify the BD and reduce the risk of width-mismatch errors.

## Vivado TCL Scripting

### Key Findings
- **Non-project mode** (`vivado -mode batch -source build.tcl`) keeps the repo clean — no `.xpr`, no `.cache` directories, just source files and checkpoints.
- Key non-project flow commands: `read_vhdl`, `read_xdc`, `synth_design -top`, `opt_design`, `place_design`, `route_design`, `write_bitstream`.
- Save a design checkpoint (`write_checkpoint`) after each major step so partial runs can resume without re-running synthesis.
- `report_timing_summary` and `report_utilization` should be called after `route_design` and their output redirected to log files for CI comparison.
- Use `get_property PROGRESS [current_run]` to programmatically poll run completion in interactive mode.

### Code Example
```tcl
# Non-project mode full build script skeleton
read_vhdl  [glob ../vhdl/*.vhd]
read_xdc   [glob ../xdc/*.xdc]

# Synthesise
synth_design -top kv260_top -part xck26-sfvc784-2LV-c
write_checkpoint -force ./checkpoints/post_synth.dcp
report_utilization -file ./reports/utilisation.rpt

# Implement
opt_design
place_design
route_design
write_checkpoint -force ./checkpoints/post_route.dcp
report_timing_summary -file ./reports/timing.rpt

# Bitstream
write_bitstream -force ./output/kv260_top.bit
```

### Relevance to Your Project
Wrapping your `create_bd.tcl` inside this non-project flow lets a CI server rebuild your bitstream from scratch with a single command. Store `post_route.dcp` as a CI artefact so timing closure can be verified across commits.

## Vitis Bare-Metal / Standalone

### Key Findings
- `xil_printf` does **not** support floating-point format specifiers (`%f`, `%e`). Use integer arithmetic to print fixed-point values, or link in the full `printf` by enabling `STDOUT_BASEADDRESS` in the BSP.
- BSP `stdin`/`stdout` must point to the physical UART connected to your USB bridge. On Kria KV260, this is `psu_uart_1`; an incorrect assignment causes silent output (no PASS/FAIL prints).
- The standalone linker script places `.text` in OCM or DDR depending on the processor. For A53 bare-metal, confirm the DDR base address in `lscript.ld` is `0x0000_0000` (or `0x0_0000_0000` for 64-bit) — the K26 SoM maps 4 GB of DDR from address 0.
- For interrupt-driven designs, the GIC (`psu_acpu_gic`) is the A53 interrupt controller; initialise with `XScuGic_CfgInitialize` before enabling any PL interrupt sources.
- Cache coherency: the A53 has hardware-coherent L1/L2. When doing DMA or AXI master transactions from PL that bypass the cache, either flush/invalidate with `Xil_DCacheFlushRange` or mark the AXI region as device memory in the MMU table.

### Code Example
```c
#include "xil_printf.h"
#include "xil_io.h"

#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL
#define PATTERN     0xDEADBEEFUL

static int bram_test(uintptr_t base, const char *name) {
    Xil_Out32(base, PATTERN);
    u32 rd = Xil_In32(base);
    if (rd == PATTERN) {
        xil_printf("%s: PASS (0x%08X)\r\n", name, rd);
        return 0;
    }
    xil_printf("%s: FAIL (expected 0x%08X, got 0x%08X)\r\n",
               name, (u32)PATTERN, rd);
    return -1;
}

int main(void) {
    int rc = 0;
    rc |= bram_test(BRAM0_BASE, "BRAM0");
    rc |= bram_test(BRAM2_BASE, "BRAM2");
    return rc;
}
```

### Relevance to Your Project
The helper function above mirrors the pattern your `main.c` likely implements and adds explicit return codes useful for automated test parsing. Ensure `stdout` is `psu_uart_1` in BSP settings, or nothing prints over USB-UART.

## XDC Timing Constraints

### Key Findings
- `set_input_delay` and `set_output_delay` are specified in nanoseconds relative to a clock edge at the I/O interface — positive values tighten setup margins, negative values indicate data arriving before the clock edge.
- For pure AXI-BRAM designs with no off-chip I/O paths, you may not need `set_input_delay`/`set_output_delay` at all — the critical constraints are `create_clock` on the PS-generated PL clock and `set_false_path` for any asynchronous reset.
- `set_clock_groups -asynchronous -group {clk_pl_0} -group {other_clocks}` prevents Vivado from timing paths between unrelated clock domains, which is necessary if you have a free-running oscillator alongside the PS-generated clock.
- Always declare the PS clock using the actual net name, not the pad: `create_clock -period 10.000 [get_nets clk_pl_0]` for 100 MHz.
- The Constraint Wizard in Vivado (Flow → Constraint Wizard) can auto-detect unclocked primary inputs and suggest constraints, reducing manual XDC errors.

### Code Example
```xdc
# PS-generated PL clock at 100 MHz (10 ns period)
create_clock -name clk_pl_0 -period 10.000 \
  [get_nets -hierarchical -filter {NAME =~ */clk_pl_0}]

# False path from async active-low reset
set_false_path -from [get_ports aresetn]

# Isolate debug clock if a JTAG/BSCAN clock is present
set_clock_groups -asynchronous \
  -group [get_clocks clk_pl_0] \
  -group [get_clocks -filter {NAME =~ *jtag*}]
```

### Relevance to Your Project
For your KV260 AXI-BRAM demo, these three constraints are the minimum needed for a clean timing closure: the PS clock definition, a false path on the reset net, and clock group isolation. Without the `create_clock`, Vivado will complain about unclocked endpoints in the BRAM controller.

## Kria KV260 / K26 SoM

### Key Findings
- **Boot mode**: The KV260 ships in QSPI32 boot mode (MODE[3:0] strapped on the carrier). For bare-metal development, switch to JTAG boot mode using the JTAG cable and XSCT (`targets -set -filter {name =~ "APU*"}; dow app.elf; con`).
- **MIO assignments**: The K26 SoM exposes MIO[0:25] for PS-dedicated peripherals (UART, I2C, SPI). `MIO[52:77]` is not broken out on the K26; use EMIO for GPIO that must reach the PL fabric or the carrier-card connectors.
- **Power domains**: PL VCCO banks on the KV260 use 1.8 V for HR banks and 1.8 V for the sideband. The SD/QSPI power domain is separate; do not change VCCO on Bank 500 without checking the carrier schematic.
- **USB-UART**: The KV260 carrier routes USB-UART to `psu_uart_1` (MIO[36:37]). Baud rate 115200, 8N1 is standard for Vitis standalone apps.
- **Fan control**: Starting in 2022.1 Kria images, the default bitstream includes EMIO fan-control GPIO. If you replace the bitstream with your own, implement fan control via AXI GPIO or keep the fan on full to avoid thermal throttling during long synthesis runs on-board.

### Code Example
```tcl
# XSCT boot sequence for bare-metal on KV260 via JTAG
connect
targets -set -filter {name =~ "APU*"}
rst -system
after 3000
targets -set -filter {name =~ "APU*"}
loadhw -hw kv260_top.xsa -mem-ranges [list {0x80000000 0xbfffffff}]
configparams force-mem-access 1
targets -set -filter {name =~ "*A53*#0"}
dow kv260_app.elf
configparams force-mem-access 0
con
```

### Relevance to Your Project
This XSCT sequence is the canonical way to load your bare-metal ELF onto the K26 A53-0 core without modifying the QSPI boot image — useful for rapid iteration while the BRAM read-back loop is being debugged.

## AMD/Xilinx Tool Updates

### Key Findings
- **Vivado 2025.2** (released ~late 2025) adds: Versal QoR enhancements, SystemVerilog interface support in synthesis, and — critically — **NoC XPM support inside Block Design via `module_ref`**.
- **Vitis 2025.1** (UG1742, July 2025): focuses on Vitis Unified IDE stability; no major breaking changes to standalone/BSP flow for Zynq UltraScale+.
- **Vitis 2026.x Known Issues**: HLS component creation for example designs fails when certain device parts are not installed — workaround is to install the full device family during setup.
- Vivado 2025.1 ships with updated IP: `axi_bram_ctrl` v4.1 adds ECC support for 64-bit-wide BRAMs.
- The Vivado release notes (UG973) always list answer records for known implementation issues; check AR# for your specific device if bitstream generation fails silently.

### Code Example
```tcl
# Vivado 2025.x: check installed tool version in batch script
set vivado_version [version -short]
puts "Vivado version: $vivado_version"
if {[package vcompare $vivado_version 2025.1] < 0} {
  error "Requires Vivado 2025.1 or newer; found $vivado_version"
}

# Use SmartConnect (preferred over AXI Interconnect in 2025.x)
create_bd_cell -type ip -vlnv xilinx.com:ip:smartconnect:1.0 axi_smc
set_property CONFIG.NUM_SI {1} [get_bd_cells axi_smc]
set_property CONFIG.NUM_MI {2} [get_bd_cells axi_smc]
```

### Relevance to Your Project
You are targeting Vivado/Vitis 2025.1. Confirm your `axi_bram_ctrl` IP is at v4.1+ to get the latest bug fixes. If you ever upgrade to 2025.2, test that the BD re-generates cleanly — NoC XPM changes can affect `generate_target` behaviour for existing block designs.
