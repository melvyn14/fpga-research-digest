# FPGA Research Digest - 2026-11-07

## Executive Summary

- **AXI-Lite VALID/READY rule**: Once VALID is asserted, it must remain high until the handshake completes — dropping it early is the single most common custom-slave bug. Use Vivado's built-in AXI Protocol Checker IP during simulation to catch violations automatically.
- **Non-project mode TCL flow**: The recommended automation path for a reproducible KV260 build is: source `create_bd.tcl` → `make_wrapper` → `generate_target` → `synth_design` → `write_bitstream` → `write_hw_platform`. Vivado 2025.1 UG994 documents this exact sequence.
- **AXI BRAM Controller address mode**: In BRAM-controller mode the accessible address range is configured from the Address Editor, not the Block Memory Generator wizard. BRAM0 at `0xA0000000` and BRAM2 at `0xA0010000` must be explicitly assigned with `assign_bd_address`.
- **Vivado 2025.1 new AXI Switch IP**: Fully customizable RTL-instantiable bridge between AXI interface types — unlike SmartConnect it works outside block-design context. Vivado 2025.2 adds an ultra-low-area mode via a `STRATEGY` parameter to both AXI Switch and SmartConnect.
- **KV260 MIO bank power**: All three MIO banks on the K26 SoM are powered at 1.8V by the SOM. MIO500 handles onboard peripherals (QSPI, eMMC, I2C); MIO501/MIO502 are user-facing — important when deciding whether a signal should use MIO, EMIO, or PL I/O.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings
- **Handshake invariant**: A transfer completes only when both VALID and READY are high on a rising clock edge. The AXI spec (ARM IHI0022) requires that once a master asserts VALID, it must keep it asserted until the handshake occurs — deassert prematurely and the slave may lose the transaction silently.
- **AW/W channel ordering**: The write address (AW) and write data (W) channels are independent; a slave must not assume one arrives before the other. A slave that waits for AWVALID before sampling WDATA will deadlock with a master that sends data first.
- **Register slice for timing closure**: When a PS-to-PL AXI path fails setup timing (common above ~150 MHz), insert an AXI Register Slice IP between the interconnect and the slave. It adds one cycle of latency but breaks the combinatorial path without changing protocol behavior.
- **Protocol Checker**: Vivado's AXI Protocol Checker IP (`axi_protocol_checker`) can be inserted in simulation to flag spec violations in real time. Synthesis tools will not catch VALID/READY misuse.
- **Response channel stall bug**: A known class of bridge bug (found in open-source AXI↔Wishbone bridges) skips the RRESP/BRESP state when ACK and STALL change in the same cycle, leaving the AXI handshake incomplete.

### Code Example
```vhdl
-- AXI-Lite slave: WVALID/WREADY handshake (single-cycle response)
process(S_AXI_ACLK)
begin
  if rising_edge(S_AXI_ACLK) then
    if S_AXI_ARESETN = '0' then
      aw_en    <= '1';
      axi_awready <= '0';
      axi_wready  <= '0';
      axi_bvalid  <= '0';
    else
      -- Accept address only when data is also available (or use independent FSM)
      if aw_en = '1' and S_AXI_AWVALID = '1' and S_AXI_WVALID = '1' then
        axi_awready <= '1';
        axi_wready  <= '1';
        aw_en       <= '0';   -- one-shot, cleared until BREADY seen
      else
        axi_awready <= '0';
        axi_wready  <= '0';
      end if;
      -- Issue write response after capturing data
      if axi_awready = '1' and axi_wready = '1' then
        axi_bvalid <= '1';
      elsif S_AXI_BREADY = '1' and axi_bvalid = '1' then
        axi_bvalid <= '0';
        aw_en      <= '1';    -- ready for next transaction
      end if;
    end if;
  end if;
end process;
```

### Relevance to Your Project
Your `kv260_top.vhd` wraps the PS block design; any custom PL logic that sits on the AXI-Lite bus between the Zynq PS master and the BRAM controllers must implement the above handshake correctly. For the two BRAM slaves (`BRAM0 @ 0xA0000000`, `BRAM2 @ 0xA0010000`), the Xilinx AXI BRAM Controller IP handles the protocol, but the pattern above is the reference if you ever add a custom register file alongside the BRAMs.

## Vivado Block Design / IP Integrator

### Key Findings
- **Connection Automation**: Right-click any unconnected port and choose "Run Connection Automation" to let Vivado wire clocks, resets, and AXI buses automatically. The same function is scripted with `apply_bd_automation` in TCL.
- **Address Editor must be explicit in scripts**: When scripting a block design, `assign_bd_address` does not automatically set the offset. Use `set_property offset` and `set_property range` on the master segment to fix the address. Failing to do this results in Vivado assigning addresses at build time, which can differ across tool versions.
- **Out-of-context (OOC) synthesis**: Each IP in a block design can be synthesized OOC (the default), producing a DCP stub. If IPs appear as black boxes in the top-level synthesis, regenerate output products (`generate_target all [get_files *.bd]`).
- **IP upgrade workflow (2025.2)**: Upgrading IPs after a Vivado version bump requires `upgrade_ip`, followed by `generate_target` and `make_wrapper -files`. Skipping `make_wrapper` after an upgrade leaves the wrapper HDL out of sync.
- **Hierarchy validation**: Run `validate_bd_design` in TCL after all connections are made and before synthesis to catch unconnected mandatory ports and bus-width mismatches.

### Code Example
```tcl
# Minimal AXI BRAM block design snippet
create_bd_cell -type ip -vlnv xilinx.com:ip:axi_bram_ctrl:4.1 axi_bram_ctrl_0
create_bd_cell -type ip -vlnv xilinx.com:ip:blk_mem_gen:8.4   blk_mem_gen_0

# Connect BRAM controller to Block Memory Generator
connect_bd_intf_net \
  [get_bd_intf_pins axi_bram_ctrl_0/BRAM_PORTA] \
  [get_bd_intf_pins blk_mem_gen_0/BRAM_PORTA]

# Assign address (must match main.c base address 0xA0000000)
assign_bd_address [get_bd_addr_segs {axi_bram_ctrl_0/S_AXI/Mem0}]
set_property offset 0xA0000000 \
  [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property range  64K \
  [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]

validate_bd_design
```

### Relevance to Your Project
Your `create_bd.tcl` constructs the two-BRAM block design. The snippet above mirrors the structure for `BRAM0`; a second `axi_bram_ctrl_1` / `blk_mem_gen_1` pair wired the same way covers `BRAM2 @ 0xA0010000`. The explicit `set_property offset` call is critical — without it, a fresh Vivado version may assign a different address and break `main.c` without a compile error.

## Vivado TCL Scripting

### Key Findings
- **Non-project mode is fully scriptable**: UG994 (2025.1) documents the complete non-project sequence: `read_bd` or source `create_bd.tcl` → `make_wrapper` → `read_vhdl` / `read_xdc` → `generate_target all` → `synth_design` → `opt_design` → `place_design` → `route_design` → `write_bitstream` → `write_hw_platform`.
- **`generate_target all` is not optional**: Without this call, the AXI infrastructure stubs are missing and synthesis will fail with "black box" errors on the BRAM controllers.
- **Exporting a reference script**: After completing a design in the GUI, use *File → Export → Export Block Design* to get a valid `create_bd.tcl`. This is the fastest way to validate your hand-written script against what Vivado actually produces.
- **Variable quoting in TCL**: Paths with spaces must be quoted; file paths from Vivado properties sometimes include trailing whitespace — use `string trim` before passing them to file operations.
- **Non-project mode limitations**: Design run management, cross-probing, Flow Navigator, and design-state reporting are all unavailable. You must write your own checkpoint saves (`write_checkpoint`) and report generation (`report_timing_summary`, `report_utilization`).

### Code Example
```tcl
# Non-project mode: full KV260 build script skeleton
set part "xck26-sfvc784-2LV-c"
set_part $part
set_property target_language VHDL [current_project]

# Recreate block design from exported TCL
source ./tcl/create_bd.tcl
make_wrapper -files [get_files kv260_bd.bd] -top
read_vhdl  ./vhdl/kv260_top.vhd
read_xdc   ./constraints/kv260_top.xdc
generate_target all [get_files kv260_bd.bd]

# Synthesis
synth_design -top kv260_top -part $part
write_checkpoint -force ./checkpoints/post_synth.dcp
report_timing_summary -file ./reports/post_synth_timing.rpt

# Implementation
opt_design
place_design
route_design
write_checkpoint -force ./checkpoints/post_route.dcp
report_timing_summary -file ./reports/post_route_timing.rpt

# Outputs
write_bitstream   -force ./output/kv260_top.bit
write_hw_platform -fixed -force -file ./output/kv260.xsa
```

### Relevance to Your Project
Your `create_bd.tcl` is designed to be sourced from exactly this kind of non-project driver script. Adding `write_checkpoint` calls after synthesis and routing means you can re-enter the flow at any stage without a full rebuild — useful when iterating on constraints or VHDL changes without touching the block design.

## Vitis Bare-Metal / Standalone

### Key Findings
- **Standalone BSP is single-threaded by design**: AMD's UG643 defines the Standalone platform as a single-threaded, simple OS layer. It handles interrupt/exception setup, cache configuration, and processor bring-up. For the Cortex-A53 on KV260, the BSP targets `psu_cortexa53_0`.
- **`xil_printf` vs `printf`**: `xil_printf` is a lightweight replacement for UART output; it supports only a subset of format specifiers (no floating point). For integer register readbacks (hex dump of BRAM contents) this is sufficient. Full `printf` can be enabled via BSP settings at the cost of code size.
- **Volatile pointer for MMIO**: PL registers mapped via AXI-Lite must be accessed through `volatile` pointers to prevent compiler reordering/elimination. Never use a plain `uint32_t *` for memory-mapped I/O.
- **Linker script DDR placement**: The default `lscript.ld` places code in DDR starting at `0x0`. If your design uses TCM or OCM, you must edit the memory region addresses in the linker script. The BSP regenerates `lscript.ld` from the XSA — keep a patched copy under source control.
- **GIC for PL interrupts**: The KV260 uses the GIC-400 (PS GIC). PL-to-PS interrupts must be wired in the block design as `pl_ps_irq` ports on the Zynq PS IP, then registered in the BSP interrupt handler using `XScuGic_Connect`.

### Code Example
```c
#include "xil_printf.h"
#include "xparameters.h"

#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL
#define BRAM_DEPTH  256   /* 32-bit words */

static inline void bram_write(uintptr_t base, uint32_t offset, uint32_t val)
{
    *(volatile uint32_t *)(base + offset * 4) = val;
}

static inline uint32_t bram_read(uintptr_t base, uint32_t offset)
{
    return *(volatile uint32_t *)(base + offset * 4);
}

int bram_test(uintptr_t base, const char *name)
{
    uint32_t i, readback;
    int pass = 1;

    /* Write incrementing pattern */
    for (i = 0; i < BRAM_DEPTH; i++)
        bram_write(base, i, 0xDEAD0000 | i);

    /* Verify */
    for (i = 0; i < BRAM_DEPTH; i++) {
        readback = bram_read(base, i);
        if (readback != (0xDEAD0000 | i)) {
            xil_printf("%s FAIL @ word %u: expected 0x%08X got 0x%08X\r\n",
                       name, i, 0xDEAD0000 | i, readback);
            pass = 0;
        }
    }
    xil_printf("%s: %s\r\n", name, pass ? "PASS" : "FAIL");
    return pass;
}

int main(void)
{
    xil_printf("KV260 AXI-BRAM Test\r\n");
    bram_test(BRAM0_BASE, "BRAM0");
    bram_test(BRAM2_BASE, "BRAM2");
    return 0;
}
```

### Relevance to Your Project
This is a drop-in replacement/expansion for your `main.c` — it exercises the full depth of both BRAMs with a walking pattern and reports per-word failures. The `volatile` qualifier is critical: without it, `-O2` may cache the first read result and report false PASSes.

## XDC Timing Constraints

### Key Findings
- **`set_input_delay` / `set_output_delay` model board delays**: These commands tell the Vivado timing engine about delays that exist outside the FPGA boundary. Without them, I/O paths are unconstrained and Vivado may not meet timing on PS-PL interface clocks.
- **Value sign convention**: Output delay values can be positive (data arrives after the clock edge at the destination) or negative (data arrives before). The sign depends on the board's clock-to-data phase. For AXI-Lite interfaces on the KV260 HP/HPC ports, the PS internally manages the interface timing — external `set_input/output_delay` constraints on those signals are typically not needed.
- **Internal `fclk_clk0` path**: The PS-generated `pl_clk0` / `fclk_clk0` is an internal clock, so `create_clock` on the BUFG output is the correct constraint — not `set_input_delay`.
- **Asynchronous clock domains**: If your VHDL uses both `pl_clk0` and a secondary clock (e.g., a MMCM-derived pixel clock), add `set_clock_groups -asynchronous` to prevent Vivado from attempting cross-domain timing analysis on paths that cross clock domains with no synchronizer.
- **STARTUPE3 pin**: On UltraScale+ (which underlies the K26 SoM), the STARTUPE3 primitive provides access to the CCLK and PREQ pins; constraints on these use the internal path rather than package pins.

### Code Example
```tcl
# kv260_top.xdc — timing constraints for KV260 AXI-BRAM demo

# PS-generated clock (100 MHz example; must match block design FCLK setting)
create_clock -period 10.000 -name fclk_clk0 \
    [get_pins -hier -filter {NAME =~ */zynq_ultra_ps_e_0/pl_clk0}]

# If a MMCM is used for a secondary PL clock
# create_clock -period 8.000 -name mmcm_clk \
#     [get_pins -hier -filter {NAME =~ */clk_wiz_0/clk_out1}]

# Mark PS and PL clocks as asynchronous if both exist in the design
# set_clock_groups -asynchronous \
#     -group [get_clocks fclk_clk0] \
#     -group [get_clocks mmcm_clk]

# False path on async reset (active-low, synchronised inside PL logic)
set_false_path -from [get_ports sys_rst_n]

# I/O standard for UART pins (adjust bank voltage to match KV260 carrier)
set_property IOSTANDARD LVCMOS18 [get_ports uart_tx]
set_property PACKAGE_PIN <PIN_NAME> [get_ports uart_tx]
```

### Relevance to Your Project
Your AXI-BRAM demo drives PS-to-PL AXI-Lite over `fclk_clk0`. The `create_clock` on the PS output pin is the minimum required timing constraint. Vivado will issue a critical warning "No clocks specified" and may produce a bitstream that fails at runtime if this is missing. The `set_false_path` on the reset prevents Vivado from spending routing effort on an asynchronous path it cannot usefully constrain.

## Kria KV260 / K26 SoM

### Key Findings
- **MIO bank layout**: The K26 SoM has three MIO banks, all powered at **1.8V** by the SOM. MIO500 handles SOM-internal peripherals (QSPI flash, SPI, I2C, eMMC). MIO501 carries PMU power-management and some user I/O. MIO502 is fully user-defined. PL-side I/O (SmartConnect, HDMI, sensor interfaces) uses PL I/O banks at whatever voltage the carrier board supplies.
- **PMU overlay config**: Boot firmware applies a "SOM-only" PMU configuration first, then loads a carrier-specific overlay. KV260 and KR260 share the same SOM but differ in which MIO pins are activated (e.g., GEM1 Ethernet is KR260-only). This overlay is what changes when you switch carriers — the BOOT.BIN itself does not need to change.
- **Boot order (from release 22.1 onward)**: A Production SOM with eMMC always checks eMMC first. There is no U-Boot boot menu; the boot device order is baked into the pre-built BOOT.BIN. For bare-metal development, JTAG boot (`target 2; dow app.elf; con`) bypasses the eMMC entirely and is the fastest iteration path.
- **PL overlay loading**: Custom PL designs can be loaded at runtime as device-tree overlays (Linux) or as a full bitstream programmed at boot (bare metal). For bare-metal, the entire bitstream is programmed by the FSBL from the SD card or eMMC BOOT partition.
- **PS-PL AXI ports**: The KV260 PS exposes two AXI master ports to the PL: HPM0_LPD (low-power domain) and HPM0_FPD (full-power domain). Both can reach the BRAM slaves. The low-latency HPM0_LPD path is preferred for a simple AXI-Lite register bus.

### Code Example
```tcl
# TCL: Confirm KV260 part assignment in Vivado block design
set_property target_part xck26-sfvc784-2LV-c [current_project]

# In block design: enable HPM0_LPD AXI master from PS
set_property CONFIG.PSU__USE__M_AXI_GP0 {1} [get_bd_cells zynq_ultra_ps_e_0]
# Set pl_clk0 to 100 MHz
set_property CONFIG.PSU__FPGA_PL0_ENABLE {1}         [get_bd_cells zynq_ultra_ps_e_0]
set_property CONFIG.PSU__CRL_APB__PL0_REF_CTRL__FREQMHZ {100} \
    [get_bd_cells zynq_ultra_ps_e_0]
# UART1 on MIO — ensure UART1 is routed through PS (not PL) for xil_printf output
set_property CONFIG.PSU__UART1__PERIPHERAL__ENABLE {1} [get_bd_cells zynq_ultra_ps_e_0]
set_property CONFIG.PSU__UART1__PERIPHERAL__IO {MIO 36 .. 37} \
    [get_bd_cells zynq_ultra_ps_e_0]
```

### Relevance to Your Project
Your KV260 design uses UART over USB-serial for PASS/FAIL output. The PS UART1 is wired to MIO36/37 on the K26 SoM and routes to the KV260 carrier's USB-UART bridge. Verifying this PSU property in the block design TCL ensures the UART is active in every new project created from the script, without needing manual GUI configuration.

## AMD/Xilinx Tool Updates (2025.x)

### Key Findings
- **AXI Switch IP (new in 2025.1)**: A fully customizable RTL-based bridge between different AXI interface types and widths. Unlike AXI SmartConnect (block-design only), AXI Switch can be instantiated directly in RTL. Note: community reports suggest it is "not intended for IPI block diagram designs" — treat SmartConnect as the preferred choice inside block designs.
- **SmartConnect STRATEGY parameter (2025.2)**: A new `STRATEGY` parameter enables ultra-low-area mode on both AXI Switch and AXI SmartConnect, trading throughput optimization for LUT savings. Useful when the KV260 PL fabric is shared between multiple IPs.
- **Simplified AXI connections (2025.2)**: Automatic wrapper creation and management for all AMD IP and block designs reduces the manual `make_wrapper` / `generate_target` steps. Connection automation between SystemVerilog instances and AXI interfaces is enhanced.
- **Inline HDL of utility IP (2025.2)**: Utility IP (clocking wizards, resets, etc.) can be inlined into the design for faster IP loading and configuration iteration.
- **Vitis 2025.1**: Theia AI Integration (Early Access) for design assistance, enhanced 1D FFT support via AIE+PL (Versal targets), and new HLS CFLOAT MAC support. Apptainer replaces Docker as the container option for Vitis AI flows.
- **Non-project mode UG892 (2026.1)**: The updated `read_bd` command for importing block designs into non-project mode and `read_ip` for `.xci` files are both documented in the 2026.1 release of UG892 — be aware if following this guide with 2025.1 tools.

### Code Example
```tcl
# Vivado 2025.2: Configure SmartConnect with low-area strategy
# (applicable when PL fabric area is a constraint on KV260)
set_property CONFIG.NUM_SI {1} [get_bd_cells axi_smc]
set_property CONFIG.NUM_MI {2} [get_bd_cells axi_smc]
# Ultra-low-area mode (new in 2025.2)
set_property CONFIG.STRATEGY {MinArea} [get_bd_cells axi_smc]

# Vivado 2025.1+: apply_bd_automation now handles clock/reset for new IPs
apply_bd_automation -rule xilinx.com:bd_rule:axi4 \
    -config { \
        Clk_master {/zynq_ultra_ps_e_0/pl_clk0} \
        Clk_slave  {Auto} \
        Clk_xbar   {Auto} \
        Master     {/zynq_ultra_ps_e_0/M_AXI_HPM0_LPD} \
        Slave      {/axi_bram_ctrl_0/S_AXI} \
    } [get_bd_intf_pins axi_bram_ctrl_0/S_AXI]
```

### Relevance to Your Project
If you upgrade from Vivado 2024.x to 2025.1 or 2025.2, the new `STRATEGY` parameter on SmartConnect and the enhanced connection automation can reduce both manual wiring steps and LUT overhead. For your two-BRAM demo, MinArea strategy on the SmartConnect will produce a smaller bitstream with no functional impact.
