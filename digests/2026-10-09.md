# FPGA Research Digest - 2026-10-09

## Executive Summary
- **AXI-Lite VALID must never be de-asserted before READY** — a master that drops VALID early causes protocol violations that synthesis won't catch, only a protocol checker will; relevant to both BRAM0 and BRAM2 write paths in the KV260 demo.
- **Vivado 2025.1 introduced a new RTL-based AXI Switch IP and dedicated IP Integrator "Clocking and Reset" / "Interrupt and AXI-4 Lite" views** — these can simplify the block design for multi-BRAM configurations.
- **XPM_FIFO_AXIS** is AMD's recommended primitive for AXI-Stream FIFOs; the macro handles both single- and dual-clock domains and includes TVALID/TREADY/TLAST ports, eliminating hand-written FIFO logic.
- **KV260 linker scripts (lscript.ld) need to explicitly map BRAM address ranges** (0xA0000000 and 0xA0010000) so the bare-metal app can treat them as memory regions; default Vitis BSP generation may not include PL BRAM ranges.
- **For the KV260, `set_clock_groups -asynchronous`** should separate PS internal clocks from PL fabric clocks in the XDC file to prevent false timing paths across the PS-PL AXI interface.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings
- **VALID must be held until handshake completes.** The AMBA spec mandates that once VALID is asserted it must remain asserted until a handshake occurs (READY also high on a rising clock edge). Dropping VALID early is a protocol violation.
- **READY may be de-asserted freely** — unlike VALID, READY is not sticky. A slave that is permanently-high READY is technically legal but can hide pipelining problems.
- **No combinational path from VALID to READY** — a well-designed slave registers its READY output; a combinational path can cause timing closure issues at high clock rates and should be broken with an AXI Register Slice.
- **AXI Protocol Checker IP** should be inserted during simulation — synthesis tools do not flag handshake violations; only a checker will catch deadlocks where READY never arrives.
- **AXI-Lite does not support burst transfers** — each transaction is a single beat; for bulk BRAM writes, sequential single-beat AXI-Lite transactions are correct but inefficient compared to AXI4 bursting.
- **AXI-Stream TLAST** marks the final beat of a packet frame; for point-to-point data pipelines (e.g. DMA-to-BRAM), TLAST-triggered logic can act as a frame-complete interrupt.

### Code Example
```vhdl
-- AXI-Lite slave write channel with proper VALID/READY handshake
-- AWREADY and WREADY held low until both channels valid, then pulse
process(S_AXI_ACLK)
begin
  if rising_edge(S_AXI_ACLK) then
    if S_AXI_ARESETN = '0' then
      awready_reg <= '0';
      wready_reg  <= '0';
    else
      -- Accept address + data only when both AWVALID and WVALID are asserted
      if S_AXI_AWVALID = '1' and S_AXI_WVALID = '1' and
         awready_reg = '0' and wready_reg = '0' then
        awready_reg <= '1';
        wready_reg  <= '1';
      else
        awready_reg <= '0';
        wready_reg  <= '0';
      end if;
    end if;
  end if;
end process;

S_AXI_AWREADY <= awready_reg;
S_AXI_WREADY  <= wready_reg;
```

### Relevance to Your Project
The KV260 demo PS (Cortex-A53) drives AXI-Lite transactions to BRAM0 (0xA0000000) and BRAM2 (0xA0010000). The AXI BRAM Controller slave must respond with proper AWREADY/WREADY pulses. If the controller is configured in non-ECC mode with 32-bit width, a single-beat write is straightforward, but the bare-metal `Xil_Out32` write sequence (address phase then data phase) must observe the handshake — the hardware handles this, but inserting a protocol checker in simulation will confirm no violations are occurring.

## Vivado Block Design / IP Integrator

### Key Findings
- **`write_bd_tcl`** exports the entire block design as a re-creatable Tcl script — only user-modified parameters are written; defaults and tool-propagated values are omitted, so importing into a different Vivado version may behave differently.
- **`-include_layout` switch** on `write_bd_tcl` preserves IP placement in the canvas; omit it for a layout-agnostic, revision-control-friendly script.
- **IP upgrades:** Never use `upgrade_ip [get_ips -all]` — the `-all` flag includes sub-core IPs that are managed by parent IPs; upgrading them independently can create orphaned Tcl objects and break the design hierarchy.
- **`diffbd` utility** can compare two block designs textually, useful for auditing after an IP upgrade.
- **Vivado 2025.1 IP Integrator** added "Clocking and Reset" and "Interrupt and AXI-4 Lite" views for cleaner organization of high-level connectivity.
- **Address Editor regeneration:** After modifying address ranges, always click "Regenerate Layout" to update address decoding; failure to regenerate can leave the interconnect with stale segment sizes.

### Code Example
```tcl
# Export current block design to a Tcl script for revision control
# Run inside Vivado Tcl console or batch mode
write_bd_tcl -include_layout ./tcl/create_bd.tcl

# Non-project batch recreation from a saved script
vivado -mode batch -source ./tcl/create_bd.tcl -tclargs <project_name> <part>

# Safe IP upgrade: target specific IPs, not all
set ip_list [get_ips -filter {UPGRADE_VERSIONS != ""}]
foreach ip $ip_list {
    if {[get_property IPDEF $ip] ne "xilinx.com:ip:axi_bram_ctrl:*"} {
        upgrade_ip $ip
    }
}
```

### Relevance to Your Project
Your `create_bd.tcl` is already the correct approach for revision-controlled block design. One check: confirm that after running `create_bd.tcl`, the Address Editor shows BRAM0 at 0xA000_0000 (64K range) and BRAM2 at 0xA001_0000 (64K range) before generating bitstream. The 2025.1 IP Integrator views may re-label these connections visually, but addresses are unchanged.

## Vivado TCL Scripting

### Key Findings
- **Namespace isolation:** Write custom Tcl procs inside a namespace to avoid collisions with Vivado's built-in commands, especially when sourcing multiple scripts in a single session.
- **Guard against empty `get_*` returns:** Always check if `[get_cells ...]` or `[get_nets ...]` returns an empty string before operating on the result — unguarded operations on empty objects produce misleading error messages.
- **Scripted flow is revision-control-canonical:** AMD's methodology guide recommends keeping only source files and the Tcl recreation script under version control; generated project files (.xpr, .runs/) are reproducible artifacts.
- **`-tclargs` pass-through:** When invoking a script with `vivado -mode batch -source script.tcl -tclargs arg1 arg2`, the args appear in Tcl as `$argv`; use this to parameterize part numbers or project names without editing the script.
- **Non-project mode:** `synth_design -top <top> -part <part>` followed by `opt_design`, `place_design`, `route_design`, and `write_bitstream` runs the full flow without a persistent project directory — faster for CI.

### Code Example
```tcl
# Parameterized project creation with guard
namespace eval bram_demo {

  proc create_project {proj_name part} {
    set proj_dir "./${proj_name}"
    if {[file exists $proj_dir]} {
      puts "INFO: Project directory exists, skipping create_project"
    } else {
      create_project $proj_name $proj_dir -part $part
    }
  }

  proc check_ip {ip_name} {
    set cells [get_bd_cells -quiet $ip_name]
    if {$cells eq ""} {
      error "ERROR: IP $ip_name not found in block design"
    }
    return $cells
  }

}

# Entry point when called via -tclargs
set part [lindex $argv 0]
if {$part eq ""} { set part "xck26-sfvc784-2LV-c" }
bram_demo::create_project kv260_bram $part
```

### Relevance to Your Project
The `create_bd.tcl` script in the demo can be hardened with namespace isolation and empty-guard checks. Adding `bram_demo::check_ip axi_bram_ctrl_0` and `bram_demo::check_ip axi_bram_ctrl_1` after block design creation will catch connection failures before bitstream generation.

## Vitis Bare-Metal / Standalone

### Key Findings
- **`xil_printf` vs `printf`:** `xil_printf` is the BSP's lightweight formatter — no floating point, smaller code size; use it for UART debug output in bare-metal. Full `printf` is available but pulls in significant libc overhead.
- **BSP `standalone` version:** The standalone BSP source is in `<Vitis>/data/embedded/lib/bsp/standalone` and on the [Xilinx embeddedsw GitHub](https://github.com/Xilinx/embeddedsw). Reviewing the source before trusting behavior is good practice.
- **Linker script KEEP directive:** `KEEP(*(.vectors))` in lscript.ld forces the linker to retain the exception vector table even if the toolchain's dead-code elimination would otherwise discard it — critical for bare-metal on Cortex-A53.
- **Stack and heap:** Default Vitis-generated lscript.ld sets stack to 0x2000 (8 KB) and heap to 0x800 (2 KB); for demos with significant printf/sprintf use, increase heap to at least 0x10000.
- **AArch64 EL3 vs EL1:** On Zynq UltraScale+ / K26, bare-metal apps run at EL3 by default; EL1 is possible but requires explicit SCR_EL3 setup. The KV260 AXI-BRAM demo at EL3 has direct access to PL peripherals without MMU involvement.

### Code Example
```c
/* Bare-metal AXI-Lite BRAM read/write using memory-mapped I/O */
#include "xil_io.h"
#include "xil_printf.h"

#define BRAM0_BASEADDR  0xA0000000UL
#define BRAM2_BASEADDR  0xA0010000UL
#define TEST_PATTERN    0xDEADBEEFUL

int bram_test(u32 base, const char *name) {
    Xil_Out32(base, TEST_PATTERN);
    /* Memory barrier: ensure write completes before read */
    dsb();
    u32 read_val = Xil_In32(base);
    if (read_val == TEST_PATTERN) {
        xil_printf("%s PASS: 0x%08X\r\n", name, read_val);
        return 0;
    } else {
        xil_printf("%s FAIL: wrote 0x%08X, read 0x%08X\r\n",
                   name, TEST_PATTERN, read_val);
        return -1;
    }
}

int main(void) {
    xil_printf("KV260 AXI-BRAM Test\r\n");
    int status = 0;
    status |= bram_test(BRAM0_BASEADDR, "BRAM0");
    status |= bram_test(BRAM2_BASEADDR, "BRAM2");
    xil_printf(status == 0 ? "ALL PASS\r\n" : "SOME FAIL\r\n");
    return status;
}
```

### Relevance to Your Project
The demo's main.c likely already uses `Xil_Out32`/`Xil_In32` and `xil_printf`. Adding a `dsb()` (Data Synchronization Barrier) between the write and the read-back is important on the Cortex-A53 to prevent out-of-order execution from returning a stale cached value instead of the freshly-written BRAM content. This is especially relevant if the L1/L2 caches are enabled.

## XDC Timing Constraints

### Key Findings
- **Constraint ordering matters:** AMD UG903 mandates: clock definitions → clock properties → I/O delays → timing exceptions. Placing `set_clock_groups` before `set_false_path` avoids silent constraint override.
- **AXI PS-PL clock separation:** The PS's FCLK_CLK0 (used to drive the AXI interconnect) is internally generated; use `set_clock_groups -asynchronous` to isolate it from any independent PL fabric clocks to prevent false cross-domain paths.
- **Unconstrained I/O warnings:** Board-interface ports with no `set_input_delay`/`set_output_delay` generate high-severity warnings; for BRAM-only designs with no external I/O other than UART, the UART pins need delay constraints against the PS reference clock.
- **Register slices:** For high-frequency AXI-Lite designs, inserting Vivado's AXI Register Slice IP between the interconnect and BRAM controllers breaks combinational paths and dramatically improves timing closure.
- **`create_clock` not needed for PS clocks:** FCLK clocks are auto-constrained by the Zynq PS IP; adding a redundant `create_clock` for them causes a conflict warning.

### Code Example
```tcl
# XDC for KV260 AXI-BRAM demo

# PS FCLK_CLK0 is auto-constrained by Zynq PS IP at 100 MHz
# No create_clock needed for FCLK_CLK0

# If a standalone PL clock is present (e.g. from SYZYGY or PMOD):
# create_clock -period 10.000 -name pl_clk [get_ports pl_clk_in]

# Isolate PS internal clocks from any async PL clocks
# (omit if only FCLK-derived clocks exist in the design)
# set_clock_groups -name ps_pl_async -asynchronous \
#   -group [get_clocks -include_generated_clocks clk_pl_0] \
#   -group [get_clocks -include_generated_clocks pl_clk]

# UART TX/RX constraints (EMIO UART0 to KV260 USB-UART bridge)
# Adjust clock name to match your actual constraint netlist
set_false_path -from [get_ports uart_txd_0]
set_false_path -to   [get_ports uart_rxd_0]

# Input/Output delays for any synchronous PL I/O (example only)
# set_input_delay  -clock [get_clocks clk_pl_0] -max 2.0 [get_ports {some_input}]
# set_output_delay -clock [get_clocks clk_pl_0] -max 2.0 [get_ports {some_output}]
```

### Relevance to Your Project
For a pure AXI-BRAM demo with no synchronous external PL I/O, the main constraint need is ensuring the FCLK_CLK0 is correctly propagated to the AXI interconnect and that UART false paths are set. Vivado's timing report after `route_design` should show no critical warnings on AXI register paths when AXI BRAM Controller operates at 100 MHz.

## Kria KV260 / K26 SoM

### Key Findings
- **240-pin connectors:** The K26 SOM exposes PS MIO, PS-GTR transceivers, PS I2C platform control, PL HPIO, HDIO, PL GTH transceivers over two 240-pin connectors to the carrier card.
- **Boot storage:** SOM includes 512 Mb QSPI, 16 GB eMMC, and 64 Kb EEPROM. Two K26 variants exist: `sm-k26` (with eMMC) and `smk-k26` (starter kit, QSPI only with preprogrammed firmware).
- **Carrier detection:** After QSPI boot, the MPSoC detects the carrier card and applies the appropriate Device Tree Overlay — PL bitstreams on KV260 are loaded post-boot via this mechanism when running Linux; for bare-metal (no Linux), the bitstream is loaded directly by JTAG or FSBL.
- **PL power domain:** On the K24 sibling SOM, MIO34 connects to the power sequencer shutdown request pin — K26 has similar power management but the exact MIO assignment may differ; consult the K26 carrier schematic for the PL PGOOD/ENABLE rails.
- **No create_clock for PS clocks:** The Zynq MPSoC PS IP auto-generates clock constraints for FCLK outputs; duplicating them in XDC causes warnings.
- **JTAG boot mode:** For bare-metal development, boot mode straps on KV260 carrier should be set to JTAG; the FSBL is then bypassed and Vitis loads the ELF directly over JTAG/USB cable.

### Code Example
```tcl
# Vivado TCL: Target K26 SOM part for project creation
# XCK26-SFVC784-2LV-C is the commercial-grade K26 part
set part "xck26-sfvc784-2LV-c"
create_project kv260_bram ./kv260_bram -part $part

# Set board for KV260 Starter Kit (enables board-aware IP configuration)
set_property BOARD_PART xilinx.com:kv260_som:part0:1.4 [current_project]

# After block design creation, validate constraints target the correct part
report_property [current_project]
```

### Relevance to Your Project
The KV260 demo uses JTAG boot for bare-metal iteration. Confirming the board part in `create_bd.tcl` ensures the IP Integrator correctly constrains PS FCLK frequencies and MIO assignments. The KV260 board preset auto-configures the PS MIO for the USB-UART bridge, which is how `xil_printf` output reaches the developer's terminal.

## AMD/Xilinx Tool Updates (Vivado/Vitis 2025.1)

### Key Findings
- **Release date:** Vivado/Vitis 2025.1 was released 2025-07-08. UG1742 is the release notes document.
- **New devices:** Support added for Versal AI Edge Gen 2, Versal Prime Gen 2, and Spartan UltraScale+ family. Zynq UltraScale+ (K26) support continues unchanged.
- **New RTL-based AXI Switch IP:** A new IP core (separate from AXI Interconnect and SmartConnect) for use cases requiring programmable routing between AXI masters and slaves.
- **IP Integrator views:** New "Clocking and Reset" and "Interrupt and AXI-4 Lite" tabbed views for high-level block design connectivity.
- **Pblock Planner:** New GUI tool for floorplanning, useful for hard-constraining AXI BRAM regions in larger designs.
- **Selective device installer:** Reduces Vivado download size by letting users select only the device families they need.
- **Known community issue (Ubuntu 24.04):** Users reported `docnav` SSL errors and Vitis startup failures on Ubuntu 24.04; workaround is to use Ubuntu 22.04 or 20.04 for 2025.1.
- **2025.2 is also available** (doc references found for 2025.2 UG903), suggesting continued active development.

### Code Example
```tcl
# Check Vivado version in TCL to conditionally use 2025.1+ features
set vivado_ver [version -short]
puts "Vivado version: $vivado_ver"

if {[string match "2025.*" $vivado_ver] || [string match "2026.*" $vivado_ver]} {
    puts "INFO: 2025.x+ features available (AXI Switch IP, IP Integrator views)"
    # Use new RTL AXI Switch if needed
    # create_bd_cell -type ip -vlnv xilinx.com:ip:axi_switch:1.0 axi_switch_0

}

# Confirm part support

    error "ERROR: K26 part not installed in this Vivado version"
}
```

### Relevance to Your Project
Vivado 2025.1 is confirmed stable for K26/KV260 targets. The new IP Integrator views don't change block design functionality but make two-BRAM designs (BRAM0 + BRAM2) easier to organize visually. For CI pipelines, the selective device installer reduces setup time for KV260-only environments. Monitor AMD Answer Records for 2025.1 known issues specific to AXI BRAM Controller if experiencing unexplained synthesis/implementation failures.
