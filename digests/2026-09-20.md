# FPGA Research Digest - 2026-09-20

## Executive Summary
- **Vivado 2025 AXI address decode bug**: A known issue in Vivado 2025 limits AXI full peripheral address decoding to 10 bits (~1 KB). If your BRAM0/BRAM2 regions need more than 1 KB mapped, verify the address editor settings and apply any available patch from AMD support (AR#000040220).
- **AXI handshake rule critical for BRAM polling**: Once `AWVALID`/`WVALID` is asserted it must stay high until the corresponding `READY` is received. Deasserting early on the PS side causes silent hangs – ensure bare-metal write loops respect this invariant or rely on the Zynq AXI SmartConnect to buffer.
- **Non-project TCL reproducibility**: The `write_project_tcl` command (UG835, 2025.1) produces a reproducible rebuild script from an existing project; combine with explicit `create_bd_cell`/`connect_bd_intf_net` calls in `create_bd.tcl` rather than `apply_bd_automation` to eliminate non-deterministic connection surprises.
- **KV260 bare-metal QSPI boot required for PL designs**: Custom PL bitstreams loaded in Vitis debug mode may not persist after reboot. For production bare-metal AXI-BRAM tests, package the design to QSPI flash using `program_flash`.
- **Vitis 2026.1 now targets KV260**: The official `kria-vitis-platforms` repository has moved to 2026.1 tools; if you plan to upgrade from 2025.1, verify BSP driver compatibility for `xil_printf` and the UART PS peripheral.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings
- **Handshake invariant**: VALID once asserted must remain asserted until the corresponding READY is sampled. On the PS side, the Zynq HP/ACP ports handle this, but custom PL AXI slaves must never deassert VALID early or the interconnect may deadlock.
- **Vivado 2025 address decode regression**: A reported Vivado 2025 bug limits AXI full (AXI4) peripheral address decode to 10 bits, constraining usable space to 1 KB. Workaround: use AXI-Lite instead of AXI4 for BRAM (already done in the kv260-axi-bram-demo), or apply the AMD AR fix.
- **AXI-Lite is sufficient for BRAM scratchpad**: For single-beat reads/writes from the PS, AXI-Lite (no burst, no ID fields) avoids ordering hazards. The AXI BRAM Controller IP (PG078) supports AXI4-Lite natively at lower resource cost.
- **AXI-Stream TLAST discipline**: TLAST must fire on the last beat of every packet. If TLAST is omitted or miscounted, streaming FIFOs stall waiting for EOP. For non-streaming applications (like BRAM scratchpad), AXI-Lite is the correct choice.
- **TKEEP/TSTRB semantics**: TKEEP marks which bytes carry valid data (1=valid, 0=null); TSTRB differentiates data bytes from position bytes. Most Xilinx IP ignores TSTRB. Tie both to all-ones for full-width transfers.

### Code Example
```vhdl
-- Minimal AXI-Lite slave write path (single register)
-- Assumes s_axi_aclk, s_axi_aresetn, and standard AXI-Lite signals
process(s_axi_aclk)
begin
  if rising_edge(s_axi_aclk) then
    if s_axi_aresetn = '0' then
      awready <= '0';
      wready  <= '0';
      bvalid  <= '0';
    else
      -- Address phase: accept address only when AWVALID is high
      if awready = '0' and s_axi_awvalid = '1' and s_axi_wvalid = '1' then
        awready <= '1';
        wready  <= '1';
      else
        awready <= '0';
        wready  <= '0';
      end if;

      -- Response phase: always OK
      if awready = '1' and wready = '1' then
        bvalid  <= '1';
        bresp   <= "00"; -- OKAY
      elsif s_axi_bready = '1' and bvalid = '1' then
        bvalid  <= '0';
      end if;
    end if;
  end if;
end process;
```

### Relevance to Your Project
Your `kv260_top.vhd` wraps two AXI BRAM controller instances (BRAM0 at `0xA0000000`, BRAM2 at `0xA0010000`). The single-beat AXI-Lite nature of both transactions means the handshake above is the exact pattern the controller implements. If a PASS/FAIL mismatch appears, instrument `BVALID`/`BRESP` on an ILA to verify the slave returned OKAY before the PS read-back.

## Vivado Block Design / IP Integrator

### Key Findings
- **Prefer explicit TCL over `apply_bd_automation`**: `apply_bd_automation` applies heuristic rules that can silently add extra IP (clock buffers, SmartConnect) depending on context. For reproducible CI builds, connect every net explicitly with `connect_bd_intf_net` / `connect_bd_net`.
- **`assign_bd_address` then `set_property`**: After creating the address segment with `assign_bd_address`, set range and offset with `set_property range / offset` on the segment object. Vivado will not emit a warning if you leave address gaps.
- **`validate_bd_design` before `generate_target`**: Always run `validate_bd_design` in TCL before generating output products to catch unconnected ports early (especially `M_AXI_GP0` on the Zynq PS8 block).
- **Updating IP in-place**: In 2025.1, `upgrade_ip [get_ips *]` upgrades all IP in a project to the current version. Run this after any tool upgrade to avoid mixed-version IP issues in the block design.
- **`write_project_tcl` for version control**: Run after any manual block design change to regenerate the rebuild script. The `-no_copy_sources` flag avoids duplicating IP source in the repo.

### Code Example
```tcl
# Reproducible block design snippet for AXI BRAM on KV260
create_bd_cell -type ip -vlnv xilinx.com:ip:axi_bram_ctrl:4.1 axi_bram_ctrl_0
set_property CONFIG.PROTOCOL      {AXI4LITE}  [get_bd_cells axi_bram_ctrl_0]
set_property CONFIG.SINGLE_PORT_BRAM {1}       [get_bd_cells axi_bram_ctrl_0]
set_property CONFIG.ECC_TYPE       {0}         [get_bd_cells axi_bram_ctrl_0]

create_bd_cell -type ip -vlnv xilinx.com:ip:blk_mem_gen:8.4 blk_mem_gen_0
set_property CONFIG.Memory_Type    {True_Dual_Port_RAM} \
             [get_bd_cells blk_mem_gen_0]

connect_bd_intf_net [get_bd_intf_pins axi_bram_ctrl_0/BRAM_PORTA] \
                    [get_bd_intf_pins blk_mem_gen_0/BRAM_PORTA]

# Assign address
assign_bd_address [get_bd_addr_segs {axi_bram_ctrl_0/S_AXI/Mem0}]
set_property offset 0xA0000000 \
  [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property range  64K \
  [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]

validate_bd_design
generate_target all [get_files *.bd]
```

### Relevance to Your Project
Your `create_bd.tcl` likely mirrors this pattern. The explicit `offset`/`range` `set_property` calls are the safest way to guarantee `BRAM0=0xA0000000` and `BRAM2=0xA0010000` survive tool upgrades without silent remapping.

## Vivado TCL Scripting

### Key Findings
- **Non-project mode is leaner for CI**: `vivado -mode batch -source build.tcl` skips the project database and runs synthesis → implementation → bitstream without writing `.xpr`/`.runs` directories. Faster for headless flows.
- **`read_vhdl` / `read_xdc` order matters**: In non-project mode, sources must be read before `synth_design`. Constraint files must be read before `opt_design` / `place_design`.
- **`get_ips` vs `get_bd_cells`**: Use `get_ips` after `generate_target` (acts on locked IP containers); use `get_bd_cells` during BD construction.
- **`write_project_tcl` captures the whole project**: This command generates a self-contained TCL script that recreates the project from scratch – invaluable for version control. The script includes all IP customisation via `set_property CONFIG.*`.
- **Parameterised IP via `CONFIG.*`**: All IP parameters are settable via `set_property CONFIG.<PARAM> <VALUE> [get_bd_cells <name>]`. The full parameter list is discoverable with `report_property [get_bd_cells <name>]`.

### Code Example
```tcl
#!/usr/bin/env tclsh
# Non-project batch flow: synthesis to bitstream
set part "xck26-sfvc784-2LV-c"     ;# K26 SoM part

read_vhdl -library work [glob ../vhdl/*.vhd]
read_xdc  ../constraints/kv260_top.xdc

synth_design  -top kv260_top -part $part -flatten_hierarchy rebuilt
opt_design
place_design
phys_opt_design
route_design

write_bitstream -force ../output/kv260_top.bit
write_debug_probes -force ../output/kv260_top.ltx
puts "Bitstream generated."
```

### Relevance to Your Project
A CI-friendly version of this script, combined with your existing `create_bd.tcl`, would let you regenerate the complete bitstream from a clean checkout in one command: `vivado -mode batch -source build.tcl`. Add `set_property STEPS.SYNTH_DESIGN.ARGS.ASSERT {1}` to enable assertion checking during simulation.

## Vitis Bare-Metal / Standalone

### Key Findings
- **BSP regeneration is required after hardware change**: Every time `kv260_top.xsa` is re-exported from Vivado, you must regenerate the BSP in Vitis (`vitis -s regenerate_bsp.py` or via IDE). Stale BSPs cause wrong base addresses in `xparameters.h`.
- **`xil_printf` vs `printf`**: `xil_printf` is a lightweight printf without floating-point support (~5 KB). Use `printf` from newlib only when float formatting is needed – it adds ~50 KB. For PASS/FAIL output, `xil_printf` is sufficient.
- **Linker script `lscript.ld` pitfalls**: The default Vitis linker script places `.text` in DDR. For BRAM-only boot (no DDR) set the `ps7_bram_0` / `psu_ocm_ram_0` region as the load region. Mismatched memory regions cause silent boot failures.
- **Standalone BSP `sleep.h`**: `usleep()` / `sleep()` are available from `xtime_l.h` in standalone. The default timer is the triple-timer counter (TTC0). Ensure TTC0 clocks are enabled in the PS8 configuration in Vivado.
- **`XBram_Initialize` for ECC-enabled BRAM**: If ECC is enabled in the IP, use the `xbram` driver from the BSP to initialise the ECC registers before first read. Failing to do so causes correctable-error interrupts to fire on the first access.

### Code Example
```c
/* Bare-metal AXI-Lite BRAM write/readback pattern (PS side, no driver) */
#include "xil_printf.h"
#include "xil_io.h"

#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL
#define TEST_WORDS  16

int bram_test(u32 base, const char *name) {
    u32 i, val;
    int pass = 1;

    /* Write phase */
    for (i = 0; i < TEST_WORDS; i++) {
        Xil_Out32(base + (i * 4), 0xDEAD0000 | i);
    }

    /* Read-back phase */
    for (i = 0; i < TEST_WORDS; i++) {
        val = Xil_In32(base + (i * 4));
        if (val != (0xDEAD0000 | i)) {
            xil_printf("%s[%d]: FAIL expected 0x%08X got 0x%08X\r\n",
                       name, i, 0xDEAD0000 | i, val);
            pass = 0;
        }
    }
    xil_printf("%s: %s\r\n", name, pass ? "PASS" : "FAIL");
    return pass;
}

int main(void) {
    xil_printf("KV260 AXI-BRAM Test\r\n");
    bram_test(BRAM0_BASE, "BRAM0");
    bram_test(BRAM2_BASE, "BRAM2");
    return 0;
}
```

### Relevance to Your Project
This pattern is the exact idiom your `main.c` should use. `Xil_Out32`/`Xil_In32` issue the correct AXI-Lite single-beat transactions through the Zynq GP port. Wrapping it in a loop with address stride `4` confirms every word lane of the BRAM is accessible – catching any address decode misalignment.

## XDC Timing Constraints

### Key Findings
- **Always constrain the PS-to-PL clock**: The `pl_clk0` output from the Zynq PS8 block must be given a `create_clock` constraint in the XDC. Without it, all paths through PL logic are unconstrained and implementation may produce a non-timing-clean bitstream.
- **`set_input_delay` / `set_output_delay` for board-level I/O**: These commands model the external PCB path delay. For KV260 UART TX/RX pins, use the values from the KV260 schematic trace delays (typically 1–3 ns). Omitting these constraints leaves the timing analyser unable to verify setup/hold margins.
- **`set_clock_groups -asynchronous`**: When two clocks (e.g., `pl_clk0` and an external oscillator) are unrelated, add `set_clock_groups -asynchronous -group [get_clocks clk_out1*] -group [get_clocks pl_clk0*]` to suppress false cross-domain paths.
- **`set_false_path` for resets**: AXI reset signals from the `proc_sys_reset` IP are synchronised internally; add `set_false_path -from [get_pins */PRE]` to suppress nuisance hold-violation warnings.
- **`write_inferred_xdc`**: New in Vivado 2025.2 – writes inferred constraints from IP to a separate XDC file for review. Useful after upgrading IP to see what new constraints were auto-generated.

### Code Example
```xdc
# KV260 AXI-BRAM project: minimal timing constraints

# PS-sourced PL clock (100 MHz on pl_clk0)
create_clock -period 10.000 -name pl_clk0 \
  [get_pins zynq_ultra_ps_e_0/inst/PS8_i/PLCLK[0]]

# UART output to carrier card (KV260 USB-UART bridge)
# Board trace delay ~1.5 ns, external setup requirement ~2 ns
set_output_delay -clock pl_clk0 -max 3.5 [get_ports uart_txd]
set_output_delay -clock pl_clk0 -min -0.5 [get_ports uart_txd]

set_input_delay  -clock pl_clk0 -max 3.5 [get_ports uart_rxd]
set_input_delay  -clock pl_clk0 -min -0.5 [get_ports uart_rxd]

# Asynchronous reset is false path
set_false_path -from [get_nets *aresetn*]

# Suppress CDC warnings between PS and PL clocks
set_clock_groups -asynchronous \
  -group [get_clocks pl_clk0] \
  -group [get_clocks clk_out*]
```

### Relevance to Your Project
If your `kv260_top.xdc` only contains pin assignments, add these timing constraints to make implementation deterministic. Unconstrained PL clocks frequently produce marginal designs that pass on one build and fail on the next due to placement variance.

## Kria KV260 / K26 SoM

### Key Findings
- **Default boot mode is QSPI32**: KV260 Starter Kits ship pre-configured to boot from the on-board QSPI flash. Bare-metal applications loaded only via JTAG debug will not survive a power cycle. Use `program_flash` in Vitis to write to QSPI for persistent bare-metal boot.
- **Boot mode selection via MODE[3:0]**: The boot mode is hard-wired on the carrier card via `MODE[3:0]` pins. On the KV260, the hardware selects QSPI32 by default. JTAG override is available for development.
- **VCCO sideband is 1.80 V**: All KV260 PL I/O used for sideband communication operates at 1.80 V VCCO. XDC `IOSTANDARD` must be set to `LVCMOS18` for any PL pins that connect to the carrier card; using `LVCMOS33` will cause configuration errors.
- **PL bitstream and bare-metal co-existence**: On KV260, the canonical embedded Linux flow uses device tree overlays for PL. For a pure bare-metal flow, the bitstream must be loaded by the FSBL (or Vitis `ps_init`) before `main()` runs. The `create_fsbl_project` TCL command in Vitis handles this.
- **AXI-BRAM at GP0 port**: The PS8's `M_AXI_HPM0_FPD` (High-Performance Master, 128-bit) is the correct port for low-latency BRAM access. The `M_AXI_GP0_LPD` (32-bit) works but bottlenecks wide transfers.

### Code Example
```tcl
# Vitis XSCT: flash bare-metal ELF to KV260 QSPI (run from xsct terminal)
connect
targets -set -nocase -filter {name =~ "*PSU*"}
source hw_server_hw_init.tcl

# Download bitstream to PL
fpga -f ../output/kv260_top.bit

# Load ELF to DDR and run
dow  ../output/kv260_bram_test.elf
run

# To program QSPI flash for persistent boot:
# program_flash -f boot.bin -offset 0 -flash_type qspi-x4-single
```

### Relevance to Your Project
For the kv260-axi-bram-demo, the JTAG debug path works for iterative development. Once the design is stable, `program_flash` will make the demo self-starting on power-up – useful for demos or automated test rigs that cannot rely on a connected host PC.

## AMD/Xilinx Tool Updates (2025.x / 2026.x)

### Key Findings
- **Vivado 2026.1 is now latest stable**: As of mid-2026, AMD has released Vivado/Vitis 2026.1. The `kria-vitis-platforms` repo targets 2026.1. If you remain on 2025.1, Vitis IDE may show warnings about platform version mismatch.
- **Vitis 2026.1 new Vitis Server backend**: The unified Vitis IDE now runs a background `vitis_server` process. This changes how XSCT scripts attach to hardware; update any `connect`/`targets` sequences in automation scripts.
- **Motor Control DSP library (2026.1)**: Six new FP32 APIs added to the Motor Control library. Not directly relevant to BRAM demos but indicates active embedded library development.
- **`write_inferred_xdc` (2025.2)**: New command to export auto-inferred constraints from IP to a standalone XDC file, making it easier to audit what the IP Integrator has added.
- **Known issues tracker**: AMD maintains a public "Known Issues" article (AR#000040220) for Vitis 2026.x. Check it for any AXI-related regressions before upgrading your KV260 project.
- **Vitis Embedded 2025.1 improvements**: Enhanced DSP library functions, support for Zynq MPSoC (K26), and a refreshed Vitis IDE with project migration wizard from classic workspace format.

### Code Example
```tcl
# Vivado 2025.1/2026.x: upgrade all IP in an existing project
# Run from Vivado Tcl console after opening project

set ip_list [get_ips -all]
puts "Found [llength $ip_list] IP instances"

# Check for upgrades
foreach ip $ip_list {
  set state [get_property UPGRADE_NEEDED $ip]
  if {$state == 1} {
    puts "Upgrading: [get_property NAME $ip]"
  }
}

# Upgrade all at once
upgrade_ip $ip_list

# Regenerate output products
generate_target all [get_files *.bd]
export_ip_user_files -of_objects [get_files *.bd] -no_script -sync -force -quiet

puts "IP upgrade complete. Run generate_target then re-synthesize."
```

### Relevance to Your Project
If you upgrade from Vivado 2025.1 to 2026.1, run this snippet immediately after opening the project to avoid mixed-version IP in the block design. The AXI BRAM Controller and Block Memory Generator IPs may have minor version bumps with bug fixes relevant to your design.
