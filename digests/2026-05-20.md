# FPGA Research Digest - 2026-05-20

## Executive Summary

1. **AXI-Lite slave handshake bug in Xilinx templates** — if `BREADY` goes low while `BVALID` is high, `AWREADY` must also drop or the write-address channel hangs permanently. The Vivado-generated AXI-Lite slave template does **not** do this correctly; any custom slave derived from it inherits the bug.
2. **Vivado 2025.1 address-decode bug below 1 KB offsets** — AXI SmartConnect silently mis-routes transactions to slaves mapped below a 1 KB boundary. `BRAM2` at `0xA0010000` (offset 0x10000 from `BRAM0`) is safe, but double-check with the Address Editor that both ranges are non-overlapping and ≥ 4 KB each.
3. **KV260 JTAG boot requires four files in order** — `fsbl.elf` → `pmufw.elf` → bitstream → app ELF. Omitting `pmufw.elf` causes a silent stall before `main()` with no UART output.
4. **`xil_printf` silently drops `%lu`/`%ld`** — use `%u` with an explicit `(unsigned)` cast for all 32-bit BRAM read-back values; otherwise results appear as `0` or garbage with no compile warning.
5. **BRAM depth/width lives in the Address Editor, not the BMG wizard** — a BMG controller depth mismatch produces silent wrap-around addressing with no DRC error; always verify `assign_bd_address -offset / -range` in TCL matches `BRAM_BASE_ADDR` in `main.c`.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- **VALID/READY handshake rule**: a master must never de-assert `VALID` once asserted until `READY` is seen. Violating this on `AWVALID` or `WVALID` causes the SmartConnect to stall permanently.
- **AW+W channel ordering**: AXI-Lite allows `AW` and `W` channels to arrive independently, but Xilinx's BRAM controller expects `AWVALID` before or coincident with `WVALID`. Reversing the order produces silent write loss.
- **Vivado 2025.1 address-decode bug**: slaves mapped at offsets < 1 KB from the base of the SmartConnect's address space can receive mis-routed transactions. Both BRAMs at `0xA0000000` and `0xA0010000` are well above this threshold, so the project is unaffected — but be aware when adding future peripherals below `0x1000`.
- **B-channel (write response) dead-lock**: if `BREADY` de-asserts while `BVALID` is high and the slave's `AWREADY` does not also de-assert, the next write transaction can lock the address channel permanently. The Xilinx template slave has this bug; patch with the guard below.
- **AXI-Stream `TLAST`/`TKEEP`**: `TLAST` marks the end of a packet; `TKEEP` indicates which byte lanes carry valid data. Both must be driven correctly even for fixed-width 32-bit streams or downstream IP will flag protocol errors.

### Code Example

```c
/* main.c — AXI-Lite write with ARM memory-barrier guard.
   dsb sy ensures the store reaches the AXI fabric before the read-back. */
#include "xil_io.h"

#define BRAM0_BASE 0xA0000000U
#define BRAM1_BASE 0xA0010000U

static inline void axi_write(uintptr_t addr, uint32_t val) {
    Xil_Out32(addr, val);
    __asm__ volatile ("dsb sy" ::: "memory");  /* AXI write barrier */
}

static inline uint32_t axi_read(uintptr_t addr) {
    __asm__ volatile ("dsb sy" ::: "memory");
    return Xil_In32(addr);
}
```

### Relevance to Your Project

Your `main.c` currently uses direct pointer dereferences. Switching to `Xil_Out32`/`Xil_In32` with `dsb sy` barriers is the correct pattern for bare-metal AXI-Lite on Cortex-A53 and will prevent any out-of-order speculative reads from corrupting PASS/FAIL results.

## Vivado Block Design / IP Integrator

### Key Findings

- **`assign_bd_address` is authoritative** — the BMG IP wizard depth setting only affects BRAM capacity; the AXI address map is controlled exclusively by `assign_bd_address -offset / -range` in TCL. A mismatch between the two produces silent wrap-around.
- **Explicit offset + range in TCL**: always pin both BRAMs with `set_property offset` and `set_property range` rather than relying on `assign_bd_address` defaults, which can shift when IP is regenerated.
- **Connection automation pitfall**: `apply_bd_automation` sometimes connects `S_AXI` to the wrong master if multiple HP ports exist. Verify with `get_bd_intf_nets` after automation.
- **IP regeneration clears address assignments**: after upgrading IP versions, re-run `assign_bd_address` explicitly or all slaves revert to `AUTO`.
- **SmartConnect vs AXI Interconnect**: SmartConnect is preferred for Zynq UltraScale+ because it supports QoS and burst splitting; AXI Interconnect is legacy. Vivado 2025.1 warns if AXI Interconnect is used in new designs.

### Code Example

```tcl
# create_bd.tcl — pin both BRAMs at fixed addresses
assign_bd_address [get_bd_addr_segs {axi_bram_ctrl_0/S_AXI/Mem0}]
set_property offset 0xA0000000 [get_bd_addr_segs {ps/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property range  8K          [get_bd_addr_segs {ps/Data/SEG_axi_bram_ctrl_0_Mem0}]

assign_bd_address [get_bd_addr_segs {axi_bram_ctrl_1/S_AXI/Mem0}]
set_property offset 0xA0010000 [get_bd_addr_segs {ps/Data/SEG_axi_bram_ctrl_1_Mem0}]
set_property range  8K          [get_bd_addr_segs {ps/Data/SEG_axi_bram_ctrl_1_Mem0}]
```

### Relevance to Your Project

Your `create_bd.tcl` uses `assign_bd_address -offset 0xA0000000`. Confirm that `set_property range 8K` is also present — omitting it leaves the range as `AUTO` and Vivado may silently resize it after IP regeneration, breaking the `BRAM_BASE_ADDR` match in `main.c`.

## Vivado TCL Scripting

### Key Findings

- **Non-project (batch) mode**: `open_project` / `open_run` are not needed in batch mode; use `read_vhdl`, `read_xdc`, `synth_design`, `opt_design`, `place_design`, `route_design`, `write_bitstream` directly. This is faster and produces reproducible outputs.
- **Checkpoint discipline**: write a `.dcp` after each major step (`write_checkpoint -force post_synth.dcp`). If routing fails, you can restart from `opt_design` without re-running synthesis (10+ minutes saved).
- **Correct K26 part string**: `xck26-sfvc784-2LV-c` — the `2LV` speed grade is required; `2L` alone will cause `create_project` to fail with an unhelpful "part not found" error.
- **Incremental synthesis**: `set_property INCREMENTAL_MODE AGGRESSIVE [get_runs synth_1]` cuts re-synthesis time by ~60% when only C/VHDL source files change, not the block design.
- **`source` ordering**: always `source create_bd.tcl` before `make_wrapper` — the wrapper generation depends on the BD being fully assembled and validated.

### Code Example

```tcl
# build_vivado.tcl — non-project batch flow for KV260
set PART xck26-sfvc784-2LV-c

create_project -in_memory -part $PART
read_vhdl      ../vhdl/kv260_top.vhd
source         create_bd.tcl
make_wrapper   -files [get_files kv260.bd] -top
read_vhdl      [glob ./kv260.gen/sources_1/bd/kv260/hdl/*.vhd]

synth_design   -top kv260_top -part $PART
write_checkpoint -force post_synth.dcp

opt_design
place_design
route_design
write_checkpoint -force post_route.dcp

write_bitstream -force kv260_axi_bram.bit
write_hw_platform -fixed -force -file ../xsa/kv260_axi_bram.xsa
```

### Relevance to Your Project

Your `build.sh` calls `vivado -mode batch -source tcl/build_vivado.tcl`. Adding `write_checkpoint` calls after synthesis and routing means a routing timing failure no longer requires a full 10-minute re-run from scratch.

## Vitis Bare-Metal / Standalone

### Key Findings

- **XSA → Platform → BSP chain**: Vitis 2025.1 requires an explicit platform project built from the XSA before you can create an application. The `build_vitis.py` script must call `platform.build()` before `app.build()`.
- **`xil_printf` vs `printf`**: `xil_printf` is a lightweight implementation that does not support `%f`, `%lu`, or `%ld`. Use `%u` with `(unsigned)` cast for 32-bit values; use `%llu` only if you link the full `newlib` printf (which increases ELF size by ~80 KB).
- **XBram driver**: `XBram_WriteReg(BaseAddr, Offset, Data)` and `XBram_ReadReg(BaseAddr, Offset)` are the correct BSP calls. Direct pointer casts (`*(volatile uint32_t*)`) also work but bypass the cache-coherence path.
- **Linker script pitfall**: the default standalone linker script places `.data` and `.bss` in DDR. If `BRAM_BASE_ADDR` is accidentally placed in the linker memory map as a RAM region, the BSP startup code will zero-initialise it, wiping any pre-loaded test patterns.
- **Stack/heap sizing**: the default 0x2000 stack is sufficient for this project; increase to 0x8000 if you add interrupt handlers with deep call stacks.

### Code Example

```c
/* xbram driver usage — preferred over raw pointer dereference */
#include "xbram.h"

#define BRAM0_BASE  0xA0000000U
#define WORD_OFFSET 0x0U          /* byte offset, must be 4-byte aligned */

XBram_WriteReg(BRAM0_BASE, WORD_OFFSET,      0xDEAD1234U);
uint32_t val = XBram_ReadReg(BRAM0_BASE, WORD_OFFSET);
xil_printf("BRAM0[0] = 0x%08X\r\n", (unsigned)val);
```

### Relevance to Your Project

Your `main.c` uses raw `*(volatile uint32_t*)` pointer casts. These are functionally correct with cache disabled (which bare-metal Vitis does by default for PL-mapped addresses), but switching to `XBram_WriteReg`/`XBram_ReadReg` makes the intent explicit and will survive any future BSP cache configuration changes.

## XDC Timing Constraints

### Key Findings

- **`create_clock` on `pl_clk0`**: the PL clock from the PS block must be constrained explicitly; Vivado does not infer it automatically. The correct target pin is `[get_pins {ps/inst/PS8_i/PLCLK[0]}]`.
- **`set_false_path` for debug signals**: any GPIO or LED outputs driven from fabric registers that cross clock domains (e.g., a heartbeat LED) should be marked `set_false_path -to` to prevent them from consuming routing resources in the timing closure.
- **`set_input_delay` for EMIO**: if EMIO pins are used (e.g., a reset button), they require `set_input_delay -clock <clk> -max/-min` constraints or Vivado will report unconstrained I/O warnings that can mask real timing failures.
- **`set_clock_groups -asynchronous`**: required if the design has both `pl_clk0` and a derived MMCM clock; without it, Vivado performs pessimistic cross-domain analysis and may falsely report hold violations.
- **KV260 has no user XDC pins**: since `kv260_top.vhd` has no ports (all I/O internal to the K26 SoM), the XDC file only needs the clock constraint. An empty XDC is valid.

### Code Example

```xdc
# kv260.xdc — minimal constraints for internal-only design
create_clock -period 10.000 -name pl_clk0 \
    [get_pins {ps/inst/PS8_i/PLCLK[0]}]

# Relax timing on any debug probe outputs (if added later)
# set_false_path -to [get_ports {led[*]}]
```

### Relevance to Your Project

Your `xdc/` directory is intentionally empty. Add the `create_clock` line above — without it, Vivado's timing report has no reference clock and all path slacks are unconstrained, making it impossible to detect any future timing regressions if the design grows.

## Kria KV260 / K26 SoM

### Key Findings

- **MIO bank layout**: MIO[0:25] is bank 500 (1.8 V), MIO[26:51] is bank 501 (3.3 V). UART0 is on MIO[38:39] (bank 501). Do not reconfigure these banks in bare-metal without checking the SOM carrier board voltage rails.
- **JTAG boot mode**: DIP switches on the KV260 carrier must be set to `SW1 = 0000` (all off) for JTAG. In any other mode, the FSBL loaded from eMMC/SD will try to configure the PL from a stored bitstream, racing with XSDB.
- **`wait_pl_ready()` CSU poll guard**: after `fpga -file` in XSDB, the CSU may not have released the PL from reset before the application starts. Poll `CSU_PCAP_STATUS` bit 3 (`PL_INIT`) or insert `after 500` in the XSDB script before `con`.
- **`rst -system` is mandatory after `fpga -file`**: skipping it leaves the AXI fabric in reset; all reads return `0xDEADBEEF`. This is documented in CLAUDE.md and confirmed empirically.
- **DDR at 0x00000000, PL at 0xA0000000**: the K26 memory map is fixed by the PS hard-macro. BRAM at `0xA0000000` is in the AXI HP0 FPD address space, accessible from Cortex-A53 EL1.

### Code Example

```tcl
# XSDB — safe KV260 programming sequence with PL-init guard
connect
targets -set -filter {name =~ "*PSU*"}
rst -system
fpga -file xsa/kv260_axi_bram.bit
after 500                                   ;# wait for PL_INIT
rst -system                                 ;# required: releases AXI fabric
targets -set -filter {name =~ "Cortex-A53 #0"}
loadhw  -hw xsa/kv260_axi_bram.xsa -mem-ranges []
configparams force-mem-access 1
dow vitis_workspace/kv260_axi_bram_app/build/Debug/kv260_axi_bram_app.elf
con
```

### Relevance to Your Project

The `after 500` guard and the double `rst -system` pattern (before and after `fpga -file`) are both relevant to your XSDB sequence. The CLAUDE.md sequence already includes `rst -system` after `fpga -file`; adding `after 500` between the two `rst -system` calls makes it more robust on cold boots.

## AMD/Xilinx Tool Updates — Vivado/Vitis 2025.1

### Key Findings

- **RTL AXI Switch IP** (new in 2025.1): a lightweight 1-to-N AXI-Lite switch without the overhead of SmartConnect. Useful for future expansion of the BRAM address map.
- **Pblock Planner** (new GUI): interactive floorplanning with real-time congestion overlay. Not relevant for this project (no timing pressure) but useful when adding DSP or high-speed I/O.
- **Timeline Trace Viewer**: the Vitis 2025.1 debugger now includes a cycle-accurate AXI transaction timeline. Attach it to the running app to confirm that BRAM reads and writes are completing in expected cycles.
- **Boot-PS-first flow**: the A53 can now be released from reset and run bare-metal code before the PL bitstream is loaded. This allows software development to proceed without a working bitstream. Use `rst -processor` instead of `rst -system` in XSDB to release only the CPU.
- **Known issue — `write_hw_platform` with `xsa` path spaces**: paths containing spaces cause `write_hw_platform` to fail silently in 2025.1. Ensure the Vivado project path has no spaces (e.g., `~/vivado_proj` not `~/my projects/vivado`).

### Code Example

```tcl
# Vitis 2025.1 — boot PS first, load PL later
# In XSDB, release only the A53 without touching the PL:
connect
targets -set -filter {name =~ "Cortex-A53 #0"}
rst -processor          ;# releases CPU only, PL stays in reset
dow my_app.elf
con
# ... run PS-only tests ...
# Then load the bitstream when ready:
targets -set -filter {name =~ "*PSU*"}
fpga -file kv260_axi_bram.bit
rst -system             ;# releases AXI fabric
```

### Relevance to Your Project

The boot-PS-first flow lets you iterate on the bare-metal `main.c` (UART, timer, non-BRAM logic) without waiting 10–15 minutes for a full Vivado synthesis run. Only re-synthesize when `create_bd.tcl` or `kv260_top.vhd` changes.
