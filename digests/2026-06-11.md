## Executive Summary
- **AXI BRAM Controller WSTRB/byte-enable behavior** directly determines whether 32-bit
  writes from the Cortex-A53 land correctly in BRAM0/BRAM2 — verify the AXI4-Lite data
  width matches the BMG port width and that `Xil_Out32`/`Xil_In32` calls are
  word-aligned to avoid partial-strobe surprises.
- **Address Editor offset/range alignment**: for two separate BRAM controllers mapped at
  `0xA0000000` and `0xA0010000`, each range must be a power-of-two and not overlap —
  a 64KB range (`0x0001_0000`) per controller is the natural minimum and matches the
  16-bit gap already chosen between the two bases.
- **PL clocks on KV260 come exclusively from the PS** (`pl_clk0..3`, default 100 MHz) —
  any XDC `create_clock` for the fabric clock should reference the PS-generated
  `FCLK_CLK0` net, not a board oscillator, since the KV260 has no PL-side crystal.
- **Vitis Classic IDE is deprecated as of 2025.1** — if the project's Vitis workspace
  still uses the classic XSCT/Eclipse-based flow, plan a migration to the Vitis Unified
  IDE (VS Code-based) for `.c`/BSP/platform regeneration going forward.
- **AXI handshake combinational-path bug class**: a recurring Xilinx/community pitfall is
  asserting `BVALID`/`RVALID` (or equivalent ready signals) combinationally from
  `AWVALID`/`ARVALID` without checking downstream backpressure — relevant if the project
  ever swaps the AXI BRAM Controller for a custom AXI-Lite slave (e.g., a status/control
  register block alongside the BRAMs).

## AXI Protocol / AXI-Lite / AXI-Stream
### Key Findings
- AXI output signals (valid/ready/data) must never be purely combinational functions of
  inputs on the same channel — Xilinx's reference AXI-Lite slave templates register all
  outputs to avoid Fmax degradation and protocol violations under backpressure.
- A common bug: raising `AWREADY`/`WREADY` only when *both* `AWVALID` and `WVALID` are
  high (to "synchronize" address and data channels) without separately handling the case
  where the write-response channel (`BVALID`) is stalled by the master holding `BREADY`
  low — this can deadlock or drop transactions.
- `BVALID` must only assert **after** the final `WVALID && WREADY` handshake of a burst
  completes — asserting it in the same cycle as the last write data beat violates the
  AXI4 ordering rules and can produce undefined behavior in some interconnects/SoCs.
- For AXI4-Lite BRAM access, the AXI BRAM Controller (PG078) expects **1 cycle of read
  latency** from the BMG (default "Read Latency = 1" config) — mismatching this setting
  against the actual BMG output-register configuration is a classic source of garbage
  read-back data on the very first read after reset.
- `WSTRB` (write strobes) are generated per-byte by the AXI BRAM Controller based on
  burst type + address offset; for a 32-bit BMG data width, `WSTRB` is 4 bits wide. If
  C code ever writes via `Xil_Out8`/`Xil_Out16` instead of `Xil_Out32`, only the
  corresponding bytes get strobed — useful for partial-word tests but a frequent source
  of "PASS" on full words masking a wrong byte lane.
- For AXI-Stream (relevant if a future revision adds a streaming datapath alongside the
  BRAMs): `TLAST` must not be allowed to "leak" during a stall — i.e., if
  `TVALID && !TREADY` on what would be the last beat, `TLAST` must remain stable and
  asserted until the actual handshake occurs, otherwise downstream packetizers will
  miscount frame length.

### Code Example
```vhdl
-- Minimal pattern of a registered AXI4-Lite slave write-response FSM,
-- illustrating correct BVALID timing relative to WVALID/WREADY (PG078-style).
process(S_AXI_ACLK)
begin
  if rising_edge(S_AXI_ACLK) then
    if S_AXI_ARESETN = '0' then
      axi_bvalid <= '0';
      axi_wready <= '0';
      axi_awready <= '0';
    else
      -- Accept address+data together, only when response channel is free
      if (S_AXI_AWVALID = '1' and S_AXI_WVALID = '1'
          and axi_awready = '0' and axi_wready = '0'
          and (axi_bvalid = '0' or S_AXI_BREADY = '1')) then
        axi_awready <= '1';
        axi_wready  <= '1';
      else
        axi_awready <= '0';
        axi_wready  <= '0';
      end if;

      -- BVALID asserts the cycle AFTER the write handshake completes
      if (axi_awready = '1' and S_AXI_AWVALID = '1'
          and axi_wready = '1' and S_AXI_WVALID = '1'
          and axi_bvalid = '0') then
        axi_bvalid <= '1';
      elsif (S_AXI_BREADY = '1' and axi_bvalid = '1') then
        axi_bvalid <= '0';
      end if;
    end if;
  end if;
end process;
```

### Relevance to Your Project
The demo currently relies on the pre-built **AXI BRAM Controller** IP, so this hand-rolled
FSM isn't needed today — but it's the exact pattern that IP implements internally, and
it's the template you'd reuse if you add a third AXI-Lite peripheral (e.g., a
status/control register exposing pass/fail counters to software without UART). When
debugging "first read after reset returns garbage" on BRAM0/BRAM2, check the BMG's
**Read Latency** setting against the AXI BRAM Controller's `C_BRAM_INST_MODE` /
read-latency parameter in `create_bd.tcl` — a mismatch here is the #1 cause of spurious
FAIL on the first word of a read-back loop.

## Vivado Block Design / IP Integrator
### Key Findings
- **Connection Automation**: when running "Run Connection Automation" on an AXI BRAM
  Controller's `S_AXI` port, double-check the *Clock Connection* dropdown — IPI will
  default to whatever clock is "nearest" in the diagram, which for a two-BRAM design can
  silently pick different clocks for BRAM0 vs BRAM2 if they were added at different
  times.
- **Address Editor**: offset address and range are interdependent and must be aligned —
  a controller mapped to range `64K (0x10000)` must have an offset address that is a
  multiple of `0x10000`. For BRAM0 @ `0xA0000000` and BRAM2 @ `0xA0010000`, both are
  already 64KB-aligned, so a 64KB range per controller is the largest you can assign
  without the editor flagging an overlap — confirm this matches the actual BMG depth
  (`Memory Depth × Data Width / 8` should be ≤ 64KB, e.g., 4K×32 = 16KB, well within
  range).
- After connection automation, Vivado auto-inserts a **Processing System Reset** IP and
  an **AXI Interconnect/SmartConnect** — for a design with two AXI-Lite BRAM
  controllers, verify both end up on the *same* SmartConnect instance (or that you
  intentionally split them) since extra SmartConnect instances consume LUTs and add
  pipeline latency.
- **Output products regeneration**: after any edit to `create_bd.tcl` or IP
  reconfiguration, the block design's generated output products (wrapper HDL, simulation
  sources) must be explicitly regenerated — `generate_target all [get_files
  *.bd]` followed by `export_ip_user_files` and `export_simulation` if simulation is
  used. Skipping this after a fresh `git clone` + `vivado -mode batch -source
  create_bd.tcl` is the most common "stale wrapper" bug reported on forums.
- A recurring 2024–2025 forum issue: re-running a TCL-generated block design against a
  newer Vivado version (e.g., 2024.2 project re-opened in 2025.1) can fail if packaged
  IP referenced by `create_bd_cell` has a version bump — pin IP `VLNV` strings with
  explicit version numbers (e.g., `xilinx.com:ip:axi_bram_ctrl:4.1`) in the TCL rather
  than relying on "latest".

### Code Example
```tcl
# Address map setup for two AXI BRAM controllers, 64KB apart, non-overlapping ranges
# (run after both axi_bram_ctrl_0 / axi_bram_ctrl_1 S_AXI ports are connected)

assign_bd_address -offset 0xA0000000 -range 64K \
    [get_bd_addr_segs {axi_bram_ctrl_0/S_AXI/Mem0}] -force

assign_bd_address -offset 0xA0010000 -range 64K \
    [get_bd_addr_segs {axi_bram_ctrl_1/S_AXI/Mem0}] -force

# Sanity check: print the resulting address map
report_bd_address_map [get_bd_designs *] -detail
```

### Relevance to Your Project
Your `create_bd.tcl` almost certainly already calls `assign_bd_address` for BRAM0 and
BRAM2 — the snippet above is the canonical idiom and a good sanity-check target: run
`report_bd_address_map` after `create_bd.tcl` executes and confirm the printed ranges
are exactly `0xA0000000-0xA000FFFF` and `0xA0010000-0xA001FFFF` with no gaps/overlaps
flagged. If you ever add a third peripheral, remember the 64KB granularity constraint
above — the next free 64KB-aligned base after BRAM2 would be `0xA0020000`.

## Vivado TCL Scripting
### Key Findings
- **Two execution modes**: Project Mode (mirrors the GUI, writes `.xpr`/project files to
  disk) vs **Non-Project Mode** (in-memory only, nothing persisted unless you explicitly
  write it). For CI/regression builds of a small demo like this, non-project mode is
  faster and avoids stale `.xpr` / `.cache` directories being committed to git.
- `vivado -mode batch -source create_bd.tcl` runs the script and exits automatically;
  `-mode tcl` opens an interactive Tcl shell instead — useful for iterating on
  `create_bd.tcl` interactively before locking it down for batch use.
- To regenerate a `.tcl`-recreatable project from an existing `.xpr`, use **File → Project
  → Write Tcl...** with "Recreate Block Designs using Tcl" checked, or run
  `write_bd_tcl -force <path>.tcl` from the Tcl console for just the block design.
- Best practice for reproducible builds: wrap the whole flow (create project → source
  `create_bd.tcl` → `make_wrapper` → `generate_target` → synth → impl → bitstream) in a
  single top-level script with `-notrace` removed during development so every command is
  echoed to the log for debugging CI failures.
- IP version pinning matters: `create_bd_cell -type ip -vlnv
  xilinx.com:ip:axi_bram_ctrl:4.1 ...` is more reproducible across Vivado versions than
  letting Vivado pick "latest" (`-vlnv xilinx.com:ip:axi_bram_ctrl:*`), especially when
  the dev machine and CI runner are on slightly different 2025.x point releases.

### Code Example
```tcl
# top_build.tcl - non-project mode style entry point for the KV260 demo
set proj_name kv260_axi_bram
set part      xck26-sfvc784-2LV-c

create_project -in_memory $proj_name -part $part

# Build the block design (defines kv260_top BD, BRAM0 @ 0xA0000000, BRAM2 @ 0xA0010000)
source [file join [file dirname [info script]] kv260/tcl/create_bd.tcl]

# Wrap and add the VHDL top-level
make_wrapper -files [get_files kv260_top.bd] -top
add_files -norecurse [get_files -of_objects [get_filesets sources_1] *kv260_top_wrapper.vhd]

generate_target all [get_files kv260_top.bd]
export_ip_user_files -of_objects [get_files kv260_top.bd] -no_script -force -quiet

# Run synth/impl + bitstream non-project style
synth_design -top kv260_top_wrapper -part $part
opt_design
place_design
route_design
write_bitstream -force ./kv260_top_wrapper.bit
```

### Relevance to Your Project
Since `create_bd.tcl` is already the source of truth for the block design, wrapping it
in a `top_build.tcl` like above gives you a single command (`vivado -mode batch -source
top_build.tcl`) to go from a clean checkout to a bitstream — handy for verifying that
changes to BRAM sizes/addresses still produce a clean, addressable design before
re-running the full Vitis bare-metal test on hardware. Pin the `axi_bram_ctrl` and
`blk_mem_gen` VLNVs explicitly in `create_bd.tcl` if you haven't already, since Vivado
2025.1 may default to a newer minor IP version than 2024.x environments.

## Vitis Bare-Metal / Standalone
### Key Findings
- `xil_printf()` (from `xil_printf.h`) is the lightweight printf used in standalone BSP
  apps — it supports a reduced format-specifier set (no floating point by default) and
  uses far less code/stack than full `stdio printf`, which matters for a minimal
  bare-metal image with no heap configured.
- For UART-based PASS/FAIL output, the BSP's `stdin`/`stdout` peripheral selection
  determines which UART `xil_printf` targets. On Kria-family boards, the BSP sometimes
  defaults to a different UART instance than the one wired to the USB-UART bridge — for
  custom carrier-card-less designs (KV260 onboard USB-UART), confirm
  `psu_uart_1` (or the equivalent UUT for K26) is selected as both `standalone_stdin`
  and `standalone_stdout` in the BSP config (`vitis-comp.json` in the Unified IDE flow).
- **Vitis Classic is deprecated starting 2025.1** — new workspaces should use the Vitis
  Unified IDE (VS Code-based), where platform/BSP/app are managed via `vitis-comp.json`
  and `.vitis` workspace folders rather than the old `.xpfm`/Eclipse project structure.
  Existing classic workspaces still build but won't get new features.
- Linker script (`lscript.ld`) controls where `.text`/`.data`/`.bss`/heap/stack land in
  DDR/OCM — for a minimal bare-metal app with no DDR dependency check, ensure the
  generated `lscript.ld` places the program in a memory region that's actually backed by
  PS DRAM (`psu_ddr_0` for K26) and not accidentally in OCM-only space, which is far
  smaller and would cause silent overflow/corruption on a larger test pattern buffer.
- For interrupt-driven designs (not currently used by this demo, but a likely next step
  if the project grows): the GIC (`XScuGic`) requires explicit `XScuGic_Connect()` +
  `XScuGic_Enable()` calls per interrupt ID, and the CPU's interrupt enable
  (`Xil_ExceptionEnable()`) must be called *after* GIC setup — ordering mistakes here are
  the most common reason "the ISR never fires."

### Code Example
```c
#include "xil_printf.h"
#include "xil_io.h"
#include "xparameters.h"

#define BRAM0_BASE  XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR  /* 0xA0000000 */
#define BRAM2_BASE  XPAR_AXI_BRAM_CTRL_1_S_AXI_BASEADDR  /* 0xA0010000 */
#define TEST_WORDS  16

int run_bram_test(UINTPTR base, const char *name) {
    int errors = 0;
    for (int i = 0; i < TEST_WORDS; i++) {
        u32 pattern = 0xA5A50000 | i;
        Xil_Out32(base + (i * 4), pattern);
    }
    for (int i = 0; i < TEST_WORDS; i++) {
        u32 expected = 0xA5A50000 | i;
        u32 readback = Xil_In32(base + (i * 4));
        if (readback != expected) {
            xil_printf("%s [%2d] FAIL: wrote 0x%08x, read 0x%08x\r\n",
                       name, i, expected, readback);
            errors++;
        }
    }
    xil_printf("%s: %s (%d errors)\r\n", name,
               errors == 0 ? "PASS" : "FAIL", errors);
    return errors;
}

int main(void) {
    xil_printf("\r\n--- KV260 AXI BRAM Demo ---\r\n");
    int e0 = run_bram_test(BRAM0_BASE, "BRAM0");
    int e2 = run_bram_test(BRAM2_BASE, "BRAM2");
    xil_printf("Overall: %s\r\n", (e0 + e2) == 0 ? "PASS" : "FAIL");
    while (1) { /* idle */ }
    return 0;
}
```

### Relevance to Your Project
This mirrors the structure described for `main.c`: `Xil_Out32`/`Xil_In32` against
`XPAR_*_BASEADDR` macros generated from `create_bd.tcl`'s address assignments, with
`xil_printf` PASS/FAIL over UART. Two practical checks worth doing on your actual BSP:
(1) confirm `xparameters.h` defines `XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR ==
0xA0000000` and the second controller's base `== 0xA0010000` — a mismatch usually means
the BSP wasn't regenerated after a block-design address change; (2) if you migrate this
workspace to Vitis 2025.1's Unified IDE, re-check `standalone_stdout` in
`vitis-comp.json` still points at the correct UART, since BSP regeneration during
migration has been reported to reset UART selection to a board default.

## XDC Timing Constraints
### Key Findings
- On KV260/K26, **the PL has no dedicated oscillator** — all PL fabric clocks
  (`pl_clk0`–`pl_clk3`) are generated by the PS clock-and-reset block and routed into the
  fabric, defaulting to 100 MHz for `pl_clk0`. Any `create_clock` constraint for your
  fabric clock domain should target the net driven by the PS `FCLK_CLK0` output, not an
  external pin.
- `set_input_delay`/`set_output_delay` are for **external I/O timing** (board-level
  delays relative to a reference clock at a port). For a design where the PS-PL
  interface is entirely internal AXI (as in this BRAM demo, with no PL-side external
  I/O), these constraints are largely **not needed** — the AXI interconnect between PS
  and PL is handled by Vivado's automatically-inserted PS-PL interface timing, which is
  pre-characterized.
- `set_clock_groups -asynchronous` is the correct way to tell Vivado that two clock
  domains (e.g., a PL-generated clock from an MMCM vs. the PS `pl_clk0`) have no fixed
  phase relationship and shouldn't be timed against each other — using `set_false_path`
  pairwise between every signal crossing is more error-prone and easy to miss signals.
- A reported KV260-specific issue: exceeding the **maximum of 6 clocks per I/O bank**
  when migrating an existing design to KV260 — if your design adds more PL clock
  domains later (e.g., a PLL-derived clock for a future AXI-Stream block), watch for
  `[Place 30-574]`-style errors about clock-capable resources per bank.
- Output delay constraints conceptually represent the **setup requirement of the
  downstream device**: `set_output_delay -clock <clk> 4.0 [get_ports data_out]` on a 10ns
  clock period effectively gives the tool a 6ns budget (period − output delay) to meet
  timing to that pin.

### Code Example
```tcl
# Example XDC additions for a KV260-based design (add only if/when external
# PL I/O is introduced; the pure AXI BRAM demo typically needs none of this
# beyond the auto-generated PS-PL clock constraint).

# PL fabric clock from PS (100 MHz pl_clk0) - usually auto-constrained by the
# Zynq MPSoC IP, but explicit version for clarity:
create_clock -period 10.000 -name pl_clk0 \
    [get_pins design_1_i/zynq_ultra_ps_e_0/inst/pl_clk0]

# If a future AXI-Stream block adds a PL-side MMCM-derived clock that is
# asynchronous to pl_clk0:
set_clock_groups -asynchronous \
    -group [get_clocks pl_clk0] \
    -group [get_clocks mmcm_clkout0]

# Example output delay for a hypothetical debug LED/GPIO driven combinationally
# off pl_clk0, with a downstream device setup time of 2ns on a 10ns period:
set_output_delay -clock [get_clocks pl_clk0] -max 2.000 [get_ports {debug_led[*]}]
set_output_delay -clock [get_clocks pl_clk0] -min 0.500 [get_ports {debug_led[*]}]
```

### Relevance to Your Project
Because `kv260_top.vhd` wraps a block design whose only external interface is likely the
fixed IO / DDR / USB-UART (handled by the K26 SOM board files) plus the AXI-Lite path
internal to the PL, your project probably needs **little to no custom XDC** beyond what
the K26 SOM/KV260 board files already provide. The main thing to verify in
`kv260_top.vhd` and any project XDC: that `pl_clk0` (100 MHz from the Zynq MPSoC IP) is
the clock driving both `axi_bram_ctrl` instances and that Vivado's auto-generated
`create_clock` for it is present in the implemented design's timing report (check
`report_clocks` post-implementation) — if it's missing, BRAM read/write timing is
unconstrained and could pass simulation but fail intermittently on hardware.

## Kria KV260 / K26 SoM
### Key Findings
- **Boot modes**: K26 SOM boot device is selected via `MODE[3:0]` pins tied on the
  carrier card; supported modes include JTAG, SD, and QSPI. The KV260 starter kit ships
  pre-configured for **QSPI32** boot with FW in onboard QSPI flash — relevant if you ever
  need to reprogram the boot FW vs. just downloading a bitstream over JTAG for the
  bare-metal demo.
- **MIO/EMIO**: the K26 board file (used as the Vivado board-file basis for KV260
  designs) defines the MIO configuration baked into the SOM hardware — carrier-card
  designers (and KV260 users) generally should *not* override MIO assignments that the
  K26 board file already fixes (e.g., for DDR, boot QSPI, USB). EMIO is available for
  carrier-specific signals (e.g., the KV260's fan control is EMIO-routed by default).
- For a **pure PS-to-PL AXI demo with no external PL I/O**, you typically don't need to
  touch MIO/EMIO at all — the K26/KV260 board file's default PS configuration already
  enables DDR, USB-UART (via PS UART), and USB for JTAG/programming.
- **Custom carrier card flow** (UG1091 / Kria SOM Carrier Card Design Guide): if this
  project ever moves off the KV260 starter kit carrier to a custom carrier, the K26
  production SOM board file is the starting point, and you re-derive PL-side XDC
  constraints from the SOM's connector pinout XDC plus your carrier's schematic — the
  KV260 starter kit XDC is a good reference implementation of this split.
- The K26 SOM uses the **XCK26 Zynq UltraScale+ MPSoC** (`xck26-sfvc784-2LV-c` or
  `-i` speed grade variants) — confirm `create_project`/`create_bd.tcl` targets the
  correct exact part+speed grade for your specific KV260 unit (commercial vs industrial
  temp grade affects max clock/timing margins slightly).

### Relevance to Your Project
For a board-file-based KV260 design, `create_bd.tcl` should reference
`set_property board_part xilinx.com:kv260_som:part0:<version>` (version depends on your
2025.1 board-file package) so that the PS configuration (DDR, UART, USB) comes
pre-populated correctly without manual MIO/EMIO edits — this is almost certainly already
the case if your bare-metal demo boots and prints over USB-UART today. One thing worth
double-checking for **2025.1 specifically**: AMD periodically updates the KV260 board
files (board_part versions), and an older `board_part` reference in `create_bd.tcl`
combined with a newer Vivado install can cause "board part not found" errors — run
`get_board_parts -latest_file_version *kv260*` in the Tcl console to confirm the
installed version matches what the script expects.

## AMD/Xilinx Tool Updates (Vivado/Vitis 2025.x)
### Key Findings
- **Vitis Classic IDE is deprecated as of 2025.1** in favor of the Vitis Unified IDE
  (VS Code-based). Existing classic workspaces continue to function for now, but new
  features and fixes target the Unified IDE — if your `kv260_claude/kv260` Vitis
  workspace was created in an older release, plan a migration pass before relying on new
  2025.x BSP features.
- 2025.1 Vivado adds a **fully customizable RTL-based AXI Switch IP** and a **new Pblock
  planner** — not immediately relevant to a 2-BRAM demo, but worth knowing if the
  project grows to multiple AXI masters needing arbitration beyond what SmartConnect
  provides.
- 2025.1 IP release notes mention fixes to **BRAM statistic register** byte-count
  mismatches in certain BRAM-related cores — worth a quick check of the IP changelog
  (Answer Record 000037919) if you're using any BRAM IP beyond the basic Block Memory
  Generator / AXI BRAM Controller pairing.
- General 2025.1 release notes are published as **UG973** (Release Notes, Installation,
  and Licensing) — both 2025.1 and 2025.2 versions are now available; if upgrading from
  2025.1 to 2025.2 mid-project, re-check the "Known Issues" section of UG973 2025.2 for
  any block-design or BRAM-related regressions before regenerating output products.
- For embedded software, 2025.1 added **Git version control integration directly in
  Vitis** projects (Unified IDE) — potentially useful for tracking BSP/`vitis-comp.json`
