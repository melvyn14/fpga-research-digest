# FPGA Research Digest - 2026-07-12

## Executive Summary

- **AXI-Lite VALID rule**: Once `AWVALID`/`WVALID`/`ARVALID` is asserted, it must not be deasserted until the corresponding `READY` is received — violating this stalls or deadlocks the AXI interconnect. This is the single most common bare-metal AXI bug.
- **AXI-Stream `TLAST` is not optional with Xilinx IPs**: Many Xilinx-provided AXI-Stream sink cores silently hold data indefinitely if `TLAST` is never asserted — always drive it even on single-beat transfers.
- **Prefer explicit TCL over `apply_bd_automation`**: In Vivado block designs, `apply_bd_automation` introduces hidden property changes; scripting with explicit `create_bd_cell` / `connect_bd_intf_net` / `assign_bd_address` gives reproducible, reviewable results.
- **KV260 default boot mode is QSPI32**: Bare-metal debugging should use JTAG boot with `psu_init.tcl` (no FSBL needed); swap to QSPI only for deployment.
- **Vivado 2025.1 ships `write_hw_platform`** as the canonical XSA export command — `export_hardware` / `write_sysdef` from older guides are deprecated and may silently produce incomplete XSA files in 2025.x flows.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- **VALID must never be withdrawn**: The AXI spec mandates that once a master asserts `AWVALID`, `WVALID`, or `ARVALID`, it must hold the signal high until the slave asserts the corresponding `READY`. Dropping `VALID` early is undefined behaviour and commonly causes hangs in the Zynq interconnect.
- **READY can be delayed indefinitely**: Slaves are permitted to hold `READY` low; masters must tolerate this. Forgetting this causes bare-metal code that polls a BRAM address to occasionally see stale data.
- **AXI BRAM Controller ECC**: The `axi_bram_ctrl` IP supports optional ECC (enable via `C_ECC=1`) on 32-, 64-, or 128-bit data widths. A second AXI4-Lite control port exposes ECC status/inject registers — useful for fault-injection testing. Only HSIAO algorithm is available for 128-bit widths.
- **AXI-Stream `TLAST`**: Xilinx IP sinks (FIFO, DMA, Video Out) will not forward a packet unless `TLAST` is asserted on the final beat. `TKEEP` null bytes are only legal on the `TLAST` beat; sparse `TKEEP` mid-packet is illegal.
- **Vivado 2025 AXI full peripheral address-space bug**: A Digilent forum report (March 2026) documents a Vivado 2025 regression where AXI full peripherals appear limited to 1 kB of usable address space — verify address editor offsets and range after IP regeneration.

### Code Example

```vhdl
-- Minimal AXI-Lite slave read channel — correct VALID hold behaviour
process(clk)
begin
  if rising_edge(clk) then
    if s_axi_arvalid = '1' and s_axi_arready = '1' then
      -- Latch address only on accepted handshake
      read_addr <= s_axi_araddr;
      s_axi_rvalid <= '1';
      s_axi_rdata  <= bram_dout;  -- registered one cycle later in real designs
    elsif s_axi_rready = '1' then
      s_axi_rvalid <= '0';        -- deassert only after RREADY seen
    end if;
  end if;
end process;
-- ARREADY can be held low during read-data phase to apply back-pressure
s_axi_arready <= not s_axi_rvalid;
```

### Relevance to Your Project

Your bare-metal code writes to `0xA0000000` (BRAM0) and `0xA0010000` (BRAM2) over AXI-Lite. The write path has three channels (AW, W, B); make sure your C code waits for `BVALID`/`BRESP` before issuing the next transaction — simple pointer writes with a back-to-back loop can race the interconnect's `BREADY`. Add a `Xil_In32` read-back after each write as an implicit response fence.

## Vivado Block Design / IP Integrator

### Key Findings

- **Avoid `apply_bd_automation` in production TCL**: While convenient interactively, the automation proc sets hidden properties (clock frequency overrides, board-level pin assignments) that vary by Vivado version and can break cross-version reproducibility.
- **Core TCL idiom for BRAM**: Use `create_bd_cell -type ip -vlnv xilinx.com:ip:axi_bram_ctrl:4.1 axi_bram_ctrl_0`, then `create_bd_cell -type ip -vlnv xilinx.com:ip:blk_mem_gen:8.4 blk_mem_gen_0`, then `connect_bd_intf_net [get_bd_intf_pins axi_bram_ctrl_0/BRAM_PORTA] [get_bd_intf_pins blk_mem_gen_0/BRAM_PORTA]`.
- **`assign_bd_address` auto-maps, then override**: Call `assign_bd_address` then `set_property offset 0xA0000000 [get_bd_addr_segs ...]` to pin the BRAM at your expected base address.
- **Validate before bitstream**: Always call `validate_bd_design` in TCL before `generate_target all` — it catches unconnected mandatory ports (like missing `EXT_RESET_IN` on a Processor System Reset) that silently survive synthesis but fail in hardware.
- **Regenerate on IP version change**: After upgrading Vivado, run `upgrade_ip [get_ips *]` in the project TCL console and re-run `generate_target all` before synthesis to avoid stale stub files.

### Code Example

```tcl
# Snippet: create and connect AXI BRAM in block design via explicit TCL
create_bd_cell -type ip -vlnv xilinx.com:ip:axi_bram_ctrl:4.1 axi_bram_ctrl_0
set_property -dict [list \
  CONFIG.SINGLE_PORT_BRAM {1} \
  CONFIG.DATA_WIDTH       {32} \
  CONFIG.ECC_TYPE         {0}  \
] [get_bd_cells axi_bram_ctrl_0]

create_bd_cell -type ip -vlnv xilinx.com:ip:blk_mem_gen:8.4 blk_mem_gen_0
set_property -dict [list \
  CONFIG.Memory_Type {True_Dual_Port_RAM} \
  CONFIG.Write_Width_A {32} \
  CONFIG.Read_Width_A  {32} \
] [get_bd_cells blk_mem_gen_0]

connect_bd_intf_net \
  [get_bd_intf_pins axi_bram_ctrl_0/BRAM_PORTA] \
  [get_bd_intf_pins blk_mem_gen_0/BRAM_PORTA]

assign_bd_address [get_bd_addr_segs axi_bram_ctrl_0/S_AXI/Mem0]
set_property offset 0xA0000000 \
  [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property range 64K \
  [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
```

### Relevance to Your Project

Your `create_bd.tcl` builds the block design programmatically. Pinning the address segments explicitly (as above) instead of relying on auto-assignment ensures BRAM0 stays at `0xA0000000` and BRAM2 at `0xA0010000` across Vivado version upgrades, keeping your bare-metal address constants in `main.c` stable.

## Vivado TCL Scripting

### Key Findings

- **Non-project mode sequence**: `read_vhdl` → `read_xdc` → `synth_design -top` → `opt_design` → `place_design` → `route_design` → `write_bitstream -force` → `write_hw_platform -fixed -include_bit`. Skipping `opt_design` is legal but degrades QoR.
- **`write_hw_platform` replaces `write_sysdef`**: From Vivado 2019.2 onward, use `write_hw_platform` to generate the `.xsa` consumed by Vitis. The old `export_hardware` command in some tutorials refers to a Vitis GUI action, not a direct TCL equivalent.
- **Version-lock your scripts**: TCL scripts referencing explicit IP VLNVs (e.g., `axi_bram_ctrl:4.1`) will break when Vivado ships a new IP version; use `get_ipdefs -filter "NAME == axi_bram_ctrl" -latest_version` to get the current version programmatically.
- **In-memory compilation caveat**: In non-project mode, all elaborated state lives in memory — if a source file is edited, rerun from `synth_design` forward; there is no incremental rebuild.
- **Source ordering matters**: `read_vhdl` processes packages before entities only if listed in dependency order; use `-library` flag for non-default libraries.

### Code Example

```tcl
# Non-project mode: full compile + XSA export for Kria KV260
open_project {}  ;# ensure clean state

read_vhdl -library work [glob ../vhdl/*.vhd]
read_xdc  ../constraints/kv260_top.xdc
read_bd   ../bd/design_1.bd
generate_target all [get_files ../bd/design_1.bd]

synth_design  -top kv260_top -part xck26-sfvc784-2LV-c
opt_design
place_design
route_design

write_bitstream -force ../output/kv260_top.bit
write_hw_platform -fixed -include_bit -force ../output/kv260.xsa

report_timing_summary -file ../output/timing_summary.rpt
report_utilization    -file ../output/utilization.rpt
```

### Relevance to Your Project

Your `create_bd.tcl` creates the block design; a companion non-project build script (as above) can drive the full flow end-to-end from a Makefile, making CI/CD or remote builds possible without launching the Vivado GUI.

## Vitis Bare-Metal / Standalone

### Key Findings

- **`xil_printf` vs `printf`**: `xil_printf` is lightweight (no float support, no heap) and suitable for UART debug in bare-metal. For full `printf` with floating-point, enable `stdin`/`stdout` in the BSP and link against the newlib `printf` — but this adds ~50 kB to the binary.
- **`psu_init.tcl` for JTAG bare-metal**: On KV260, you can skip the FSBL entirely during development by running `psu_init.tcl` from the XSCT console to initialize the PS (DDR, clocks, MIO). Vitis Debug Configuration has a checkbox for this.
- **BSP peripheral drivers**: The BSP auto-generates `xparameters.h` with `XPAR_AXI_BRAM_CTRL_0_BASEADDR` and `XPAR_AXI_BRAM_CTRL_1_BASEADDR` constants — use these instead of hardcoded hex addresses to stay in sync with the block design.
- **Interrupt controller (GIC)**: For interrupt-driven AXI peripherals, use `XScuGic` (the ARM GIC-400 driver included in the standalone BSP). The KV260's Cortex-A53 uses the GIC-400; Zynq-7000 uses `XIntc` — do not mix them.
- **KV260 BIST in 2025.1**: A LogicTronix Hackster tutorial (2025) demonstrates the full recreate-from-source flow for KV260 BIST in Vivado/Vitis 2025.1, including the MIPI+VCU+ethernet AXI topology — useful as a reference for multi-peripheral AXI designs on the same platform.

### Code Example

```c
#include "xil_printf.h"
#include "xparameters.h"
#include "xil_io.h"

#define BRAM0_BASE  XPAR_AXI_BRAM_CTRL_0_BASEADDR
#define BRAM2_BASE  XPAR_AXI_BRAM_CTRL_1_BASEADDR
#define TEST_WORD   0xDEADBEEFU

static int bram_test(uintptr_t base, const char *name) {
    Xil_Out32(base, TEST_WORD);
    /* Memory barrier: ensures AXI write completes before read */
    __asm__ volatile ("dsb sy" ::: "memory");
    u32 rd = Xil_In32(base);
    if (rd != TEST_WORD) {
        xil_printf("FAIL %s: wrote 0x%08X read 0x%08X\r\n",
                   name, TEST_WORD, rd);
        return -1;
    }
    xil_printf("PASS %s: 0x%08X\r\n", name, rd);
    return 0;
}

int main(void) {
    xil_printf("KV260 AXI-BRAM test\r\n");
    int rc = 0;
    rc |= bram_test(BRAM0_BASE, "BRAM0");
    rc |= bram_test(BRAM2_BASE, "BRAM2");
    xil_printf(rc == 0 ? "ALL PASS\r\n" : "FAILURES DETECTED\r\n");
    return rc;
}
```

### Relevance to Your Project

Adding the `dsb sy` data synchronisation barrier between the `Xil_Out32` write and `Xil_In32` read prevents the Cortex-A53's out-of-order write buffer from letting the read return before the AXI write is visible to the BRAM controller — a subtle bug that manifests as intermittent FAIL on the first run after bitstream load.

## XDC Timing Constraints

### Key Findings

- **Always specify both `-min` and `-max` for I/O delays**: `set_input_delay` without `-min` defaults to 0, which may over-constrain fast paths and cause false timing failures. Specify `set_input_delay -clock clk -min 0.5 -max 3.0 [get_ports ...]`.
- **`set_false_path` for async resets**: If your design uses an external asynchronous reset input, apply `set_false_path -from [get_ports reset_n]` to prevent the router from treating it as a clocked path.
- **Separate synthesis and implementation XDCs**: Use `set_property USED_IN {synthesis implementation} [get_files clocks.xdc]` and `set_property USED_IN {implementation} [get_files impl_only.xdc]` — keep `set_input_delay`/`set_output_delay` in the implementation-only file to avoid synthesis clock-domain confusion.
- **Zynq/KV260 internal clocks**: Clocks generated by the Zynq PS (`pl_clk0`, etc.) are automatically constrained by the Vivado board files — do not re-constrain them manually or you create conflicting clock definitions.
- **Clock groups for CDC**: When your block design has multiple clock domains (e.g., AXI clock and a video pixel clock), add `set_clock_groups -asynchronous -group [get_clocks clk_pl_0] -group [get_clocks pixel_clk]` to prevent false cross-domain timing failures.

### Code Example

```tcl
# kv260_top.xdc — relevant constraint patterns for KV260 AXI-BRAM design

# PS-generated PL clock is auto-constrained; reference it by name
# create_clock is NOT needed for pl_clk0 — Vivado board files handle it

# Async reset from carrier card pushbutton
set_false_path -from [get_ports {reset_n}]

# External LED output — not timing-critical, relax the constraint
set_output_delay -clock [get_clocks clk_pl_0] -max 5.0 [get_ports {led[*]}]
set_output_delay -clock [get_clocks clk_pl_0] -min -1.0 [get_ports {led[*]}]

# If a second async clock domain is present (e.g., PL free-run clock)
# set_clock_groups -asynchronous \
#   -group [get_clocks clk_pl_0] \
#   -group [get_clocks pl_clk1]

# Timing exception: multicycle for wide bus registered comparator
# set_multicycle_path 2 -setup -from [get_cells cmp_reg[*]]
```

### Relevance to Your Project

The KV260 AXI-BRAM demo runs entirely on the PS-generated `pl_clk0`; the primary constraint need is the `set_false_path` for the reset input and possibly LED output relaxation. Adding explicit `set_false_path -from [get_ports reset_n]` removes the most common spurious timing violation reported after implementation.

## Kria KV260 / K26 SoM

### Key Findings

- **Boot mode selection**: The K26 SoM boot device is selected by `MODE[3:0]` pins on the carrier card. The KV260 starter kit ships with QSPI32 as the default (pre-programmed with Kria boot firmware). For bare-metal development, set MODE pins to JTAG (`0b0000`) or SD card (`0b1110`).
- **UART is MIO-routed, not EMIO**: The KV260's USB-UART (FTDI) is connected to PS MIO bank 501 pins for UART1 (`MIO 36/37`). This is hardwired on the carrier card; no EMIO or PL passthrough is needed — just set `UART1` in the PS IP configuration.
- **EMIO for PL-to-carrier GPIOs**: EMIO GPIOs (routed through PL fabric) are available on the SOM's 240-pin connector for carrier card expansion; the default KV260 bitstream uses one EMIO pin for fan control.
- **Power domains**: The K26 SOM has separate power domains for PL (`VCCINT`, `VCCO_*`) and PS (`VCC_PSINTFP`, `VCC_PSINTLP`). The starter kit carrier manages these automatically; bare-metal code must not attempt PS power domain gating.
- **2025.2 bare-metal 4K streaming**: A Hackster project (fredo2, 2025) demonstrates bare-metal 4K video streaming on KV260 with Vivado/Vitis 2025.2, confirming that complex multi-clock PL designs remain fully viable in standalone mode.

### Code Example

```tcl
# PS IP configuration for KV260 UART1 (MIO 36/37 -> USB-UART via carrier card)
# In create_bd.tcl — configuring the Zynq UltraScale+ PS
set_property -dict [list \
  CONFIG.PSU__UART1__PERIPHERAL__ENABLE  {1} \
  CONFIG.PSU__UART1__PERIPHERAL__IO     {MIO 36 .. 37} \
  CONFIG.PSU__UART1__BAUD_RATE          {115200} \
  CONFIG.PSU__CRL_APB__UART1_REF_CTRL__SRCSEL {IOPLL} \
  CONFIG.PSU__CRL_APB__UART1_REF_CTRL__DIVISOR0 {15} \
  CONFIG.PSU__CRL_APB__UART1_REF_CTRL__DIVISOR1 {1} \
] [get_bd_cells zynq_ultra_ps_e_0]

# Confirm boot mode for debug note in TCL output
puts "INFO: KV260 default boot = QSPI32. For JTAG debug, set MODE[3:0]=0b0000"
puts "INFO: UART1 routed to MIO 36/37 -> KV260 carrier USB-UART (115200 8N1)"
```

### Relevance to Your Project

Your `main.c` uses `xil_printf` which writes to UART1. Confirming the PS IP has `PSU__UART1__PERIPHERAL__IO` set to `MIO 36 .. 37` is essential — a misconfigured BSP (e.g., pointing to UART0 instead) produces a silently non-functional UART, making it impossible to see PASS/FAIL output without a debugger.

## AMD/Xilinx Tool Updates (Vivado/Vitis 2025.x)

### Key Findings

- **Vivado 2025.1 headline features**: PS-first boot with dynamic PL loading (partial reconfiguration from software without a full bistream reload); new Pblock Planner GUI; a fully RTL-customisable AXI Switch IP; improved `set_directive` / subdirective support for HLS.
- **Vitis 2025.1 embedded flow**: Improved streaming kernel support for low-overhead continuous data paths; function call graph viewer with heatmap for II/latency/DSP/BRAM utilization; enhanced data-driven pragma handling.
- **`write_hw_platform` is the canonical XSA command**: Confirmed in UG835 2025.2 and 2026.1 — `write_hw_platform -fixed -include_bit -force <name>.xsa` is the correct incantation; many 2021–2023 tutorials still show deprecated alternatives.
- **Vivado 2026.1 tools now available**: AMD has released 2026.1 tools (adaptive SoC download page updated). The project is on 2025.1; migration is straightforward but verify IP VLNV versions have not incremented.
- **Vivado 2025 AXI peripheral 1 kB address space regression**: Reported on Digilent forums (March 2026 thread "Vivado 2025 - AXI full peripheral limited to 1k usable address space") — affects AXI4 full-mode peripherals; workaround is to manually set the address range in the Address Editor after design generation.

### Code Example

```tcl
# 2025.x-correct full build + XSA export sequence
# (replaces deprecated: write_sysdef / export_hardware)

open_bd_design  [get_files design_1.bd]
validate_bd_design          ;# catch unconnected ports early
generate_target all [get_files design_1.bd]
make_wrapper -files [get_files design_1.bd] -top
add_files -norecurse [glob ./design_1.gen/sources_1/bd/design_1/hdl/*.vhd]

launch_runs synth_1 -jobs 4
wait_on_run synth_1
launch_runs impl_1 -to_step write_bitstream -jobs 4
wait_on_run impl_1

# Export XSA for Vitis 2025.x — include bitstream for bare-metal debug
write_hw_platform -fixed -include_bit -force \
  ./output/kv260_wrapper.xsa

puts "XSA written. Import into Vitis: File > New Platform Project > Browse XSA"
```

### Relevance to Your Project

If you are following a tutorial that uses `export_hardware` or `write_sysdef`, replace it with `write_hw_platform -fixed -include_bit -force <name>.xsa`. In Vitis 2025.1, importing an XSA generated by the old commands may produce a platform with missing BSP drivers or incorrect memory maps, causing `xparameters.h` to omit your BRAM base addresses.
