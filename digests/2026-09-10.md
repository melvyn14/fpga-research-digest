# FPGA Research Digest - 2026-09-10

## Executive Summary

- **BRAM/FIFO IP catalog change (Vivado 2025.1+):** The Embedded Memory Generator (BRAM) and FIFO IPs are no longer available for direct instantiation from the IP Catalog in Vivado 2025.1/2025.2 — they must be added via block design. This directly affects the KV260 AXI-BRAM project if you ever regenerate or port the IP.
- **AXI VALID must never be de-asserted mid-transfer:** Once AWVALID/WVALID/ARVALID is asserted, the master cannot lower it until the corresponding READY is received. Violating this causes silent deadlock in AXI-Lite slave logic and is a common bare-metal pitfall.
- **Vivado 2025.2 adds SystemVerilog Interface support** with automatic wrapper creation for all AMD IP and Block Designs, and an ultra-low-area mode for AXI SmartConnect/Switch IP via a STRATEGY parameter.
- **Kria KV260 boots from QSPI by default** (MODE[3:0] pins tie boot device on the carrier card). For bare-metal iteration, switch to JTAG boot to avoid reflashing the QSPI on every build.
- **Non-project-mode TCL with IP Integrator:** Requires the global synthesis option to generate the block design in-memory — combine `open_bd_design`, `validate_bd_design`, and `write_bd_tcl` in the same script for a reproducible, CI-friendly flow.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- **READY/VALID handshake rule (critical):** Once a master asserts VALID (AWVALID, WVALID, or ARVALID), it MUST NOT de-assert that signal until the slave drives READY high. De-asserting early is a protocol violation that causes AXI slaves — including Xilinx's AXI BRAM Controller — to lock up silently with no error status.
- **AXI-Lite has no burst support:** Each transaction is a single beat. Writing a pattern to BRAM over AXI-Lite requires one full address + data + response cycle per 32-bit word. For high-throughput writes, consider AXI4 full protocol with burst length > 1.
- **AXI-Stream is unidirectional:** TVALID/TREADY handshake with optional TLAST for packet boundaries. Use for DSP/video pipelines, not for random-access BRAM reads. AXI-Lite is the right choice for the KV260 AXI-BRAM demo.
- **BWRESP / RRESP values:** OKAY=2'b00, EXOKAY=2'b01, SLVERR=2'b10, DECERR=2'b11. Always check RRESP/BRESP in bare-metal drivers; a DECERR means the address is outside any mapped slave range.
- **AXI BRAM Controller ECC option:** The IP supports an optional second AXI4-Lite control port for reading/writing ECC registers. Useful for detecting single-bit errors in scratchpad memory.

### Code Example

```c
/* Bare-metal AXI-Lite write: poll BVALID to complete the write response phase */
#define BRAM0_BASE 0xA0000000UL

static void axi_lite_write(uintptr_t base, uint32_t offset, uint32_t value)
{
    /* Write address channel */
    Xil_Out32(base + offset, value);   /* Vivado BSP helper handles AW+W+B cycles */

    /* Explicit memory barrier — ARM Cortex-A53 can reorder stores */
    dsb();
}

static uint32_t axi_lite_read(uintptr_t base, uint32_t offset)
{
    uint32_t val = Xil_In32(base + offset);
    dsb();
    return val;
}

/* Usage */
axi_lite_write(BRAM0_BASE, 0x00, 0xDEADBEEF);
uint32_t rd = axi_lite_read(BRAM0_BASE, 0x00);
xil_printf("BRAM0[0] = 0x%08X  %s\n", rd, rd == 0xDEADBEEF ? "PASS" : "FAIL");
```

### Relevance to Your Project

Your main.c writes patterns to BRAM0 (0xA0000000) and BRAM2 (0xA0010000) using Xil_Out32/Xil_In32. Ensure `dsb()` (Data Synchronization Barrier) is called between write and read-back, otherwise the Cortex-A53's store buffer may return stale data before the AXI write reaches BRAM.

## Vivado Block Design / IP Integrator

### Key Findings

- **Connection Automation auto-adds Processor System Reset and AXI Interconnect:** When you run "Run Connection Automation" after adding an AXI peripheral, Vivado inserts `proc_sys_reset` and routes `aresetn`/`aclk` automatically. The AXI Interconnect (or SmartConnect) is also inserted as a crossbar between the PS AXI master and your BRAM controllers.
- **Address Editor is mandatory:** After adding BRAM controllers, the Address Editor must assign a non-overlapping base address and range (e.g., BRAM0 at 0xA000_0000 / 64KB, BRAM2 at 0xA001_0000 / 64KB). Mismatches between the XDC/XSA and your bare-metal code base addresses produce DECERR responses.
- **BRAM/FIFO IP catalog change in 2025.1:** Embedded Memory Generator (BRAM) and FIFO IPs can no longer be instantiated directly from the IP Catalog — they must be used via block design. If you upgrade from an older flow, regenerate outputs inside the block design.
- **Validate before generating:** Always run "Validate Design" (F6) before "Generate Block Design." This catches unconnected ports and clock-domain issues before synthesis.
- **2025.2 SmartConnect ultra-low-area mode:** Set the `STRATEGY` parameter on AXI SmartConnect to `1` for area-optimised implementations — useful on the K26 SoM where PL resource budgets are tight.

### Code Example

```tcl
# IP Integrator: add and configure AXI BRAM Controller in TCL
create_bd_cell -type ip -vlnv xilinx.com:ip:axi_bram_ctrl:4.1 axi_bram_ctrl_0
set_property -dict [list \
    CONFIG.SINGLE_PORT_BRAM {1} \
    CONFIG.DATA_WIDTH       {32} \
    CONFIG.ECC_TYPE         {0}  \
] [get_bd_cells axi_bram_ctrl_0]

# Assign address in the Address Editor
assign_bd_address [get_bd_addr_segs {axi_bram_ctrl_0/S_AXI/Mem0}]
set_property offset 0xA0000000 [get_bd_addr_segs \
    {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property range 64K [get_bd_addr_segs \
    {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
```

### Relevance to Your Project

Your `create_bd.tcl` automates the block design. Ensure address assignments in that script match the bare-metal base addresses (0xA0000000, 0xA0010000). After upgrading to 2025.1+, verify that BRAM IPs are still in the block design context and not orphaned IP catalog instances.

## Vivado TCL Scripting

### Key Findings

- **Batch mode syntax:** `vivado -mode batch -source my_script.tcl` — Vivado exits with the script's last return code. Use `-tclargs key value` to pass arguments into the script via `$argv`.
- **Non-project mode IP Integrator requirement:** To use `create_bd_design` / `add_bd_cell` in non-project mode, you must use global synthesis (not OOC). Set `set_property synth_checkpoint_mode None [get_files *.bd]` and call `generate_target all [get_files *.bd]` before synthesis.
- **`write_bd_tcl` for reproducibility:** After manually building a block design in the GUI, run `write_bd_tcl -force recreate_bd.tcl` to export a portable TCL script. This is the gold-standard approach for version-controlling block designs.
- **`source` a constraints file in batch mode:** Use `read_xdc constraints.xdc` (not `add_files`) in non-project mode to load XDC timing constraints before implementation.
- **Exit code checking:** Wrap critical commands with `if {[catch {synthesize_design -top kv260_top} err]} { puts "ERROR: $err"; exit 1 }` to propagate failures to CI.

### Code Example

```tcl
# Minimal non-project-mode flow: synthesis → implementation → bitstream
set project_name "kv260_axi_bram"
set top_module   "kv260_top"
set part         "xck26-sfvc784-2LV-c"

# Read sources
read_vhdl    [glob ./vhdl/*.vhd]
read_bd      ./bd/kv260_bd.bd
generate_target all [get_files kv260_bd.bd]
read_xdc     ./constraints/kv260.xdc

# Synthesize
synth_design -top $top_module -part $part -mode out_of_context

# Implement
opt_design
place_design
route_design

# Bitstream
write_bitstream -force ./output/${project_name}.bit
write_hw_platform -fixed -force ./output/${project_name}.xsa

puts "Done. Bitstream at ./output/${project_name}.bit"
```

### Relevance to Your Project

Your `create_bd.tcl` already scripted the block design. Wrapping it in the non-project-mode flow above enables a single `make` or CI command to go from source to `.bit` + `.xsa` without opening the GUI. The `write_hw_platform` step produces the `.xsa` that Vitis needs.

## Vitis Bare-Metal / Standalone

### Key Findings

- **Vitis 2025.1 platform support:** Covers Versal, Zynq MPSoC (which includes K26), Zynq 7000, and MicroBlaze. The Cortex-A53 on K26 uses the `psu_cortexa53_0` processor domain.
- **BSP configuration matters for bare-metal:** The standalone BSP sets the `stdin`/`stdout` peripheral (must match your UART MIO assignment on K26 — typically `psu_uart_1` for USB-UART). Wrong UART selection means xil_printf produces no output with no error.
- **`xil_printf` vs `printf`:** `xil_printf` is a lightweight formatted-output function that avoids floating-point and pulls in far less code from the standard library. For PASS/FAIL diagnostics it's preferred. Full `printf` requires enabling `newlib_small` or `libmetal` in the BSP settings.
- **Linker script heap/stack:** The default standalone linker script places stack and heap in OCM (On-Chip Memory). For designs that DMA to/from DDR, ensure your buffer addresses are in the DDR region and cache-coherent (or call `Xil_DCacheFlushRange` / `Xil_DCacheInvalidateRange`).
- **Hardware platform import:** After generating the `.xsa` from Vivado, create a Vitis platform project from it. Any time you change the block design (e.g., add an interrupt), regenerate the `.xsa` and re-import into Vitis — the BSP headers (`xparameters.h`) must reflect the new address map.

### Code Example

```c
#include "xil_printf.h"
#include "xil_io.h"
#include "xparameters.h"
#include "xil_cache.h"

#define BRAM0_BASE  XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR
#define BRAM2_BASE  XPAR_AXI_BRAM_CTRL_1_S_AXI_BASEADDR
#define PATTERN     0xA5A5A5A5UL

int main(void)
{
    xil_printf("KV260 AXI-BRAM test starting...\r\n");

    /* Disable D-cache for AXI-Lite region, or flush after writes */
    Xil_DCacheDisable();

    Xil_Out32(BRAM0_BASE + 0x00, PATTERN);
    Xil_Out32(BRAM2_BASE + 0x00, ~PATTERN);

    uint32_t r0 = Xil_In32(BRAM0_BASE + 0x00);
    uint32_t r2 = Xil_In32(BRAM2_BASE + 0x00);

    xil_printf("BRAM0: 0x%08X %s\r\n", r0, r0 == PATTERN  ? "PASS" : "FAIL");
    xil_printf("BRAM2: 0x%08X %s\r\n", r2, r2 == ~PATTERN ? "PASS" : "FAIL");

    return 0;
}
```

### Relevance to Your Project

Using `XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR` from `xparameters.h` instead of hardcoded hex addresses lets the linker/BSP stay in sync with the Address Editor. If you move a BRAM controller in the block design, only the `.xsa` reimport is needed — no source edits.

## XDC Timing Constraints

### Key Findings

- **`set_input_delay` / `set_output_delay` are system-level constraints:** They model the external path delay relative to a clock edge at the FPGA pin. On the K26 SoM, most I/O is internal (PS ↔ PL over AXI), so you typically only need these for actual board-level I/O (PMOD, RPi header).
- **For AXI-Lite BRAM demos, you primarily need a clock constraint:** `create_clock -period 10.000 [get_ports clk]` (or for the PS clock derived from the Zynq IP, no XDC clock constraint is needed — the PS IP defines its own clocks). AXI interfaces constrained by the block design's aclk do not need user-written set_input/output_delay.
- **`set_clock_groups -asynchronous`:** Use when you have independent clock domains (e.g., a user PL clock and the PS 100 MHz clock) to prevent false cross-domain timing paths from causing spurious failures.
- **Constraint Wizard:** Vivado's built-in constraint wizard (Tools → Timing → Constraint Wizard) auto-generates `set_input_delay` and `set_output_delay` for registered I/Os. Run it after placement on any design with external I/O.
- **DDR/SDR input constraints:** For source-synchronous interfaces (RGMII, etc.), use `-min` and `-max` pairs; for system-synchronous (pure internal logic), they are unnecessary.

### Code Example

```xdc
# Clock constraint for a 100 MHz PL clock input
# (Not needed if using only the PS-derived pl_clk0 — the Zynq IP defines it)
create_clock -period 10.000 -name pl_clk0 [get_ports pl_clk0_port]

# False path for reset (asynchronous assertion, synchronous de-assertion)
set_false_path -from [get_ports sys_rst_n]

# If you have two independent PL clock domains, suppress cross-domain analysis:
set_clock_groups -asynchronous \
    -group [get_clocks pl_clk0] \
    -group [get_clocks pl_clk1]

# Example I/O constraint for a PMOD output on the KV260 RPi header
set_output_delay -clock pl_clk0 -max 3.0 [get_ports pmod_out[*]]
set_output_delay -clock pl_clk0 -min 0.5 [get_ports pmod_out[*]]
```

### Relevance to Your Project

For the bare-metal AXI-BRAM demo, timing constraints are minimal: the PS provides `pl_clk0` (typically 100 MHz), and the AXI interconnect uses that clock. You only need explicit XDC constraints if you have custom PL-side I/O in `kv260_top.vhd` that is not driven by the block design's internal clocks.

## Kria KV260 / K26 SoM

### Key Findings

- **Default boot mode is QSPI32:** The KV260 ships with boot firmware in QSPI and MODE[3:0] pins preset for QSPI boot on the carrier card. For bare-metal development, use JTAG boot mode (MODE = 0000) to avoid re-flashing the QSPI every iteration.
- **SOM240 connector:** All PS I/O, MIO, and PL I/O route through the 240-pin SOM240_1 connector between the K26 SoM and the KV260 carrier card. EMIO GPIO path: `GPIO (EMIO) → PL fabric → ZynqMP Package Pin → SOM240_1 → KV260 carrier net → expansion connector`.
- **MIO assignment for USB-UART:** USB0 is on MIO 52–63, USB 3.0 on GT Lane2. GEM1 is on MIO 38–49. The USB-UART (CP2108) typically connects to PS UART1 (MIO 36–37 on K26C variant). Verify in the `.xsa`/`xparameters.h` that `XPAR_XUARTPS_1_BASEADDR` matches your BSP UART selection.
- **PL power domains:** The K26 SoM has separate power rails for PS (1.0 V core, 1.8 V I/O) and PL (0.85 V core, 1.8 V VCCO). PL is gated off until the PS boots and enables PL power — this means the AXI interface to BRAM is unavailable until after the PS initialization sequence completes.
- **AXI GP master ports:** The Zynq Ultrascale+ PS has four AXI master ports (HP0–HP3 for high performance, GP0/GP1 for general purpose). For simple BRAM demos, GP0 (32-bit, up to 150 MHz) is sufficient and simplest to configure in the Zynq IP block.

### Code Example

```tcl
# In create_bd.tcl: Configure Zynq Ultrascale+ PS for KV260 bare-metal
set_property -dict [list \
    CONFIG.PSU__USE__M_AXI_GP0          {1}  \
    CONFIG.PSU__USE__M_AXI_GP1          {0}  \
    CONFIG.PSU__UART1__PERIPHERAL__ENABLE {1} \
    CONFIG.PSU__UART1__PERIPHERAL__IO   {MIO 36 .. 37} \
    CONFIG.PSU__USB0__PERIPHERAL__ENABLE {1} \
    CONFIG.PSU__USB0__PERIPHERAL__IO    {MIO 52 .. 63} \
    CONFIG.PSU__CRL_APB__PL0_REF_CTRL__FREQMHZ {100} \
] [get_bd_cells zynq_ultra_ps_e_0]
```

### Relevance to Your Project

Confirming `PSU__USE__M_AXI_GP0 = 1` and `PSU__CRL_APB__PL0_REF_CTRL__FREQMHZ = 100` in your Zynq IP block ensures the GP0 AXI master is active at 100 MHz, driving the AXI interconnect that connects to BRAM0 and BRAM2.

## AMD/Xilinx Tool Updates

### Key Findings

- **Vivado 2025.2 headline features:**
  - New device support: Versal AI Edge Series Gen 2 and Versal Prime Series Gen 2 adaptive SoCs.
  - **SystemVerilog Interfaces support:** Automatic wrapper creation for all AMD IP and Block Designs when using SV interfaces — simplifies AXI connections between SV modules.
  - **AXI SmartConnect / AXI Switch ultra-low-area mode:** New `STRATEGY` parameter reduces LUT usage for area-constrained designs.
  - Reduced PhysOpt compile time and new global/module-level retiming optimization control.
  - BUFG_FABRIC replication per-SLR and per-VNoC column for high-fanout nets.
  - New ECO legalizer with timing-driven mode and DRC checks.
- **Vivado 2025.1 breaking change:** BRAM and FIFO IPs removed from standalone IP Catalog — must be instantiated through block design. Check your flow if migrating from 2024.x.
- **Vitis 2025.x / 2026.x:** Active known-issues articles tracked at `adaptivesupport.amd.com`. AR#000037919 lists all IP change-log information for the 2025.1 release cycle.
- **Vivado 2026.1 licensing change:** New licensing model introduced (see bard0.com/insights/vivado-2026-1-licensing.html for community analysis). Review before upgrading from 2025.x.
- **Vitis Libraries DSP 2025.2:** Updated DSP library release notes available at `docs.amd.com/r/en-US/Vitis_Libraries/dsp/release.html`.

### Code Example

```tcl
# 2025.2: Use ultra-low-area mode on AXI SmartConnect
# Set STRATEGY=1 to reduce LUT count at the cost of some throughput
set_property CONFIG.STRATEGY {1} [get_bd_cells axi_smc]

# Verify the property was applied
report_property [get_bd_cells axi_smc] CONFIG.STRATEGY
```

### Relevance to Your Project

If you upgrade from Vivado 2024.x to 2025.1+, the BRAM IP catalog change means you must verify that `axi_bram_ctrl_0` and `axi_bram_ctrl_1` are still valid block design instances (not orphaned IP Catalog entries). Running `validate_bd_design` will surface any broken references immediately. The SmartConnect `STRATEGY=1` setting is relevant if the K26 SoM's PL resources become tight as you expand the block design.
