# FPGA Research Digest - 2026-11-23

## Executive Summary

- **ZipCPU-confirmed AXI-Lite slave bug in Vivado-generated cores**: The ready logic in generated AXI-Lite slaves (at least through 2018.3, possibly later) fails to deassert ready under output-stall conditions, risking silent data loss on the read-response or write-response channels. Formally verify any generated slave or add explicit stall guards.
- **Kria XSCT BSP flow deprecated as of 2025.1**: The classic XSCT/BSP flow for Kria SOM is officially deprecated; the new SDT (System Device Tree) flow is the AMD-recommended path for new bare-metal designs on KV260. Existing projects may stay on XSCT but new designs should migrate.
- **Address locking in Vivado Block Design**: Segments can be locked so that `assign_bd_address` and the Address Editor cannot overwrite them. Use this in TCL automation to pin BRAM0 at 0xA0000000 and BRAM2 at 0xA0010000 and prevent regeneration from shifting them.
- **Non-project mode gives reproducible CI builds**: Running `vivado -mode batch -source build.tcl` with explicit `synth_design`, `opt_design`, `place_design`, `route_design`, and `write_checkpoint` calls produces a fully repeatable flow with no reliance on project-state files.
- **New AXI Switch IP in Vivado 2025.1**: A fully customizable RTL-based AXI Switch that bridges different interface types and widths is new in 2025.1, complementing AXI SmartConnect for multi-master, multi-slave topologies on the KV260.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- **Vivado-generated AXI-Lite slave ready-logic bug**: ZipCPU's formal verification work found that the Vivado 2018.3 example AXI-Lite slave core does not properly deassert the ready lines when the response channel is stalled, allowing an incoming transaction to be accepted when the outgoing acknowledgement channel cannot absorb it. Later Vivado versions added an extra register stage to address one of these issues but the fix should be independently verified.
- **VALID must be deasserted after every reset**: This is a fundamental AXI rule — `xVALID` must go low following any reset, before any transaction begins. Violating this can cause the interconnect to interpret power-on glitches as transactions.
- **AXI Interconnect lock-ups (PG059 v2.1, Dec 2025)**: AMD's AXI Interconnect guide documents a case where a VALID/READY transfer completes on one side of the Interconnect but the resultant transfer is never issued on the expected output interface. If your BRAM read/write loop hangs, check the Interconnect status registers described in PG059's Debugging section.
- **AXI-Stream TKEEP/TSTRB widths**: Each is `TDATA_width / 8` bits. TKEEP marks null vs. real data bytes; TSTRB distinguishes data bytes from position bytes. If TDATA is omitted, both signals are dropped. When adding a streaming pipeline in front of the BRAM, assert TLAST on packet boundaries and do not set TKEEP bits for bytes beyond the valid payload.
- **Odd-width streaming gotcha**: For AI Engine / PL interfaces, only the lower partial word can be active on TLAST; sending only the upper partial word (e.g., `TKEEP=0xF0` on a 64-bit bus) is invalid and stalls the channel.

### Code Example

```vhdl
-- Minimal AXI-Lite slave: safe ready/valid with stall guard
-- Prevents accepting new address while response channel is busy
process(clk)
begin
  if rising_edge(clk) then
    if resetn = '0' then
      arready <= '0';
      rvalid  <= '0';
    else
      -- Accept address only when we can commit a response
      if arvalid = '1' and arready = '0' and rvalid = '0' then
        arready  <= '1';
        rd_addr  <= araddr;
      else
        arready <= '0';
      end if;
      -- Hold rvalid until master accepts with rready
      if arready = '1' and arvalid = '1' then
        rvalid <= '1';
        rdata  <= bram_dout;  -- latch read data
      elsif rvalid = '1' and rready = '1' then
        rvalid <= '0';        -- clear only after handshake
      end if;
    end if;
  end if;
end process;
```

### Relevance to Your Project

Both BRAM controllers in `kv260-axi-bram-demo` are AXI-Lite slaves on `M_AXI_HPM0_LPD`. The stall-guard pattern above matches the generated core's expected behavior — if you are seeing occasional missed writes or reads that return stale data, add a formal property check that `rvalid` never goes high while a prior `rvalid` is still pending acknowledgement.

## Vivado Block Design / IP Integrator

### Key Findings

- **Connection automation vs. manual wiring**: AMD recommends running `apply_bd_automation` through the Vivado IDE rather than raw Tcl; for scripted flows use `write_bd_tcl` to capture the finished design and replay it.
- **Never use `upgrade_ip [get_ips -all]`**: The `-all` flag includes sub-core IPs that may be removed when their parent is upgraded, leaving dangling Tcl references and silent corruption of the IP cache.
- **Address locking**: After scripting `assign_bd_address` to pin BRAM offsets, call `set_property offset_lock true` on each segment to prevent connection automation or future IP addition from reassigning the range.
- **Version pinning for exported Tcl scripts**: An exported `write_bd_tcl` script is only guaranteed to work in the Vivado release it was created in; tag the script with the Vivado version in its header comments and in the git commit message.
- **IP repository path must be set before sourcing BD script**: If your block design script references custom IP, add the repository with `set_property ip_repo_paths` before calling `source create_bd.tcl` or the IP will not resolve.

### Code Example

```tcl
# Non-interactive block design creation with pinned BRAM addresses
open_project ./kv260.xpr

# Pin BRAM addresses before connection automation can reassign them
set bram0_seg [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property offset 0xA0000000 $bram0_seg
set_property range  64K         $bram0_seg

set bram2_seg [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_1_Mem0}]
set_property offset 0xA0010000 $bram2_seg
set_property range  64K         $bram2_seg

# Validate and generate wrapper
validate_bd_design
make_wrapper -files [get_files kv260.bd] -top
add_files -norecurse ./kv260.gen/sources_1/bd/kv260/hdl/kv260_wrapper.vhd
```

### Relevance to Your Project

Your `create_bd.tcl` script maps BRAM0 to `0xA0000000` and BRAM2 to `0xA0010000`. Explicitly setting and locking both address segments in the TCL script ensures `validate_bd_design` will error rather than silently reassign them if the script is re-run on a different Vivado state.

## Vivado TCL Scripting

### Key Findings

- **Non-project mode for CI/CD**: The batch invocation is `vivado -mode batch -source build.tcl`. In non-project mode Vivado never writes a `.xpr` file; the design lives in memory and you control every step explicitly.
- **Write checkpoints manually**: Non-project mode does not auto-save DCPs. Call `write_checkpoint -force ./checkpoint_post_route.dcp` after `route_design` to preserve a restorable snapshot for timing analysis.
- **Stage commands**: `synth_design`, `opt_design`, `place_design`, `phys_opt_design`, `route_design`, `write_bitstream` — in that order. `launch_runs` is project mode only.
- **Message limits**: Use `-verbose` on a command to override message suppression, and `set_msg_config -id "..." -new_severity "..." ` to promote specific warnings to errors (e.g., AXI address overlap warnings).
- **Export BD to TCL from IDE**: File → Export → Export Block Design generates a self-contained `create_bd.tcl` that recreates the in-memory design. This is the right source-of-truth for version control.

### Code Example

```tcl
#!/usr/bin/env tclsh
# Non-project mode build script for kv260-axi-bram-demo
# Usage: vivado -mode batch -source build_nonproject.tcl

set part "xck26-sfvc784-2LV-c"

read_vhdl   [glob ./vhdl/*.vhd]
read_xdc    ./constraints/kv260.xdc

# Source the block design (opens an in-memory project internally)
source ./tcl/create_bd.tcl

synth_design -top kv260_wrapper -part $part -flatten_hierarchy rebuilt
write_checkpoint -force ./dcp/post_synth.dcp

opt_design
place_design
phys_opt_design
route_design
write_checkpoint -force ./dcp/post_route.dcp

report_timing_summary -file ./reports/timing.rpt
report_utilization    -file ./reports/util.rpt

write_bitstream -force ./output/kv260.bit
```

### Relevance to Your Project

Adding this non-project build script to `kv260_claude/kv260/tcl/` lets you build the bitstream from a clean CI container without Vivado project-state files, keeping the repository lean and ensuring bit-exact reproducible builds across machines.

## Vitis Bare-Metal / Standalone

### Key Findings

- **Kria XSCT BSP deprecated in 2025.1**: AMD's 2025.1 open-source release notes list all Kria XSCT BSPs as deprecated. New designs should use the SDT (System Device Tree) flow. Existing XSCT-based projects are still buildable but will not receive feature updates.
- **Creating a BSP in Vitis Unified IDE**: File → New Component → Platform → select your XSA → choose "standalone" as the OS. The generated platform component wraps BSP drivers and linker scripts.
- **`xil_printf` vs `printf`**: `xil_printf` is a lightweight, non-floating-point printf targeting the first PS UART. For bare-metal debug on KV260, the USB-UART (J4, micro-USB) connects to PS UART1 (`ttyUSB1` on the host). Confirm the UART instance in the XSA's `system.mss` (`STDIN_PERIPHERAL` / `STDOUT_PERIPHERAL`).
- **SDT flow for new designs**: The System Device Tree flow generates a device-tree fragment describing the hardware, from which Vitis derives BSP drivers. This replaces the XSA-only flow for Kria and is the recommended path for Vitis 2025.1+.
- **Bare-metal 4K streaming demo (hackster, 2025.2)**: A recent KV260 bare-metal project demonstrates that Cortex-A53 bare-metal video work is still viable and Vivado/Vitis 2025.2 is usable for it, confirming the tool chain is production-stable.

### Code Example

```c
/* Minimal AXI-Lite BRAM read/write test for KV260 bare-metal
 * BRAM0 base: 0xA0000000, BRAM2 base: 0xA0010000
 * Build with Vitis standalone BSP; ensure xil_printf routes to UART1 */

#include "xil_printf.h"
#include "xil_io.h"
#include "sleep.h"

#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL
#define TEST_WORDS  8

int main(void) {
    xil_printf("KV260 AXI-BRAM test start\r\n");

    /* Write ascending pattern */
    for (u32 i = 0; i < TEST_WORDS; i++) {
        Xil_Out32(BRAM0_BASE + (i * 4), 0xDEAD0000 | i);
        Xil_Out32(BRAM2_BASE + (i * 4), 0xBEEF0000 | i);
    }

    /* Read back and verify */
    int pass = 1;
    for (u32 i = 0; i < TEST_WORDS; i++) {
        u32 r0 = Xil_In32(BRAM0_BASE + (i * 4));
        u32 r2 = Xil_In32(BRAM2_BASE + (i * 4));
        if (r0 != (0xDEAD0000 | i) || r2 != (0xBEEF0000 | i)) {
            xil_printf("FAIL @ word %d: got 0x%08X / 0x%08X\r\n", i, r0, r2);
            pass = 0;
        }
    }
    xil_printf(pass ? "PASS\r\n" : "OVERALL FAIL\r\n");
    return 0;
}
```

### Relevance to Your Project

This is functionally equivalent to your `main.c` logic. The key detail is `Xil_Out32`/`Xil_In32` using the cache-bypass memory-mapped I/O path; calling them through a cached virtual address without an explicit cache flush will cause read-back to return stale cache lines rather than BRAM content.

## XDC Timing Constraints

### Key Findings

- **Ordering is mandatory**: Define clocks first, then clock properties, then I/O delays (`set_input_delay`, `set_output_delay`), then timing exceptions (false paths, multicycle paths). The Vivado timing engine applies constraints in XDC file order; placing exceptions before the delays they reference can cause them to be silently ignored.
- **I/O delay semantics**: `set_input_delay` eats into the setup-time budget for the path that captures the input. `set_output_delay` consumes a portion of the max-delay budget for the output path. Both use the reference clock's rising edge unless `-clock_fall` is specified (for DDR interfaces).
- **Timing Constraints Wizard limitation**: The wizard proposes system-synchronous I/O delays but cannot change the reference clock; you must edit the XDC or use the Timing Constraints window to reassign it.
- **For bare-metal AXI BRAM projects**: The PS-to-PL AXI path is fully internal to the device and constrained by the PS block's internal clock. External I/O delay constraints are only needed for pins that physically cross the package boundary (e.g., PMOD, GPIO routed to the KV260 carrier board).
- **PS clock output constraint**: The PS's `pl_clk0` output requires only a `create_clock` on the BUFG output net — no `set_input_delay` needed since the PS generates it internally.

### Code Example

```xdc
# kv260.xdc — Minimal timing constraints for AXI-BRAM bare-metal demo

# 1. Clock — PS generates pl_clk0 at 100 MHz to PL via BUFG
create_clock -period 10.000 -name pl_clk0 [get_pins -hierarchical -filter {NAME =~ */BUFG_GT*/O}]

# 2. False path on asynchronous reset (PS reset to PL logic)
set_false_path -from [get_pins -hierarchical -filter {NAME =~ *zynq_ultra_ps_e_0*pl_resetn0*}]

# 3. I/O delay for external GPIO (only if routing signals to carrier board pins)
# set_input_delay  -clock pl_clk0 -max 2.0 [get_ports {gpio_i[*]}]
# set_input_delay  -clock pl_clk0 -min 0.5 [get_ports {gpio_i[*]}]
# set_output_delay -clock pl_clk0 -max 1.5 [get_ports {gpio_o[*]}]
# set_output_delay -clock pl_clk0 -min 0.0 [get_ports {gpio_o[*]}]

# 4. Timing exception ordering: exceptions after all clock and I/O delay definitions
set_false_path -through [get_nets -hierarchical -filter {NAME =~ *cdc_sync*}]
```

### Relevance to Your Project

For the AXI-BRAM demo the PL has no external I/O other than the LED/GPIO outputs on the KV260 carrier. Only `create_clock` on `pl_clk0` and a false path on the PS reset net are strictly needed. If you add external signals later, the template above provides the correct ordering.

## Kria KV260 / K26 SoM

### Key Findings

- **MIO bank layout (DS987 v1.2)**: eMMC is on MIO[22:13] (MIO[23] = eMMC reset). MIO bank 0 is fully occupied by on-module peripherals. MIO banks 1–2 are customizable and exposed through the SOM connector. EMIO provides additional PS I/O through the PL fabric — useful for UART, GPIO, or SPI when MIO is exhausted.
- **SOM240 connectors**: SOM240_1 carries MIO signals, PS-GTR, HPIO, and HDIO. SOM240_2 adds more HPIO, HDIO, and GTH transceivers. The KV260 carrier uses a subset of these pins; the full pinout is in AMD UG1091 (Carrier Card Design Guide).
- **Default boot mode: QSPI32**: The board ships with QSPI flash on the SOM as the primary boot device. MicroSD (J11 on the carrier) is the secondary fallback. For bare-metal development, boot via JTAG using `xsdb` / `program_hw_devices` to bypass the boot ROM entirely.
- **PS console UART**: The KV260's USB JTAG/UART connector (J4, micro-USB) routes UART1 of the PS to the host. Under Linux this appears as `ttyUSB1`; in bare-metal it is the target of `xil_printf` when `STDOUT_PERIPHERAL` is set to `psu_uart_1`.
- **PL peripherals on the carrier board**: PMOD and RPi headers are connected to PL I/O banks, not MIO. They require EMIO or fabric GPIO instantiation and must have XDC LOC constraints pointing to the correct HPIO/HDIO package pins.

### Code Example

```tcl
# TCL snippet to query Zynq PS MIO/EMIO configuration after design creation
# Run from Vivado Tcl console with block design open

set ps [get_bd_cells zynq_ultra_ps_e_0]

# Check which UART is enabled and its MIO assignment
get_property CONFIG.PSU__UART1__PERIPHERAL__ENABLE  $ps
get_property CONFIG.PSU__UART1__PERIPHERAL__IO      $ps

# Check HPM0 LPD AXI master (drives BRAM address space)
get_property CONFIG.PSU__USE__M_AXI_GP0             $ps
get_property CONFIG.PSU__MAXIGP0__DATA_WIDTH         $ps

# Show PL clock 0 frequency
get_property CONFIG.PSU__CRL_APB__PL0_REF_CTRL__FREQMHZ $ps
```

### Relevance to Your Project

Confirming `PSU__UART1__PERIPHERAL__IO = MIO 36 .. 37` and `PSU__USE__M_AXI_GP0 = 1` in Vivado before bitstream generation ensures the UART and AXI master are correctly configured. A misconfigured UART (pointing at UART0 or wrong MIO pins) is a common reason bare-metal `xil_printf` output never appears on the host terminal.

## AMD/Xilinx Tool Updates

### Key Findings

- **Vivado 2025.1 — New AXI Switch IP**: A fully customizable RTL-based IP that serves as a bridge between different AXI interface types and widths. Useful for multi-master designs where `AXI SmartConnect` is overkill; it has lower area overhead.
- **Vivado 2025.2 — Ultra-low-area mode for AXI Switch and AXI SmartConnect**: A new synthesis option reduces resource count for simple master/slave topologies — relevant if you later add a second PL master alongside the PS.
- **Vitis 2025.1 — Kria XSCT BSP deprecated**: All Kria XSCT-flow BSPs are listed as deprecated. The SDT (System Device Tree) flow is the AMD-recommended path for new bare-metal designs. Existing XSCT projects remain functional.
- **Vitis 2025.1 release date**: UG1742 release date is 2025-07-08.
- **Vivado 2025.1 release date**: UG973 release date is 2025-05-29.
- **OS support**: Vitis 2025.1 notes that Red Hat 9.2/9.3 and Ubuntu 22.04.2 will not be supported in the next release; plan OS upgrades accordingly.
- **IP packager improvement in 2025.1**: RTL IP can now be packaged directly as a Vitis kernel — allowing PL accelerators built as standard IP to be integrated into Vitis acceleration flows without separate packaging steps.
- **Spartan UltraScale+ 2025.1**: 92% timing pass rate at 250 MHz with no design changes using the push-button flow; indicates the place-and-route algorithms in 2025.1 are well-tuned for dense UltraScale+ fabrics (the K26 uses UltraScale+ architecture).

### Relevance to Your Project

If you upgrade from 2025.1 to 2025.2, the new ultra-low-area SmartConnect mode may reduce the LUT overhead of the AXI interconnect between the PS HPM0 port and your two BRAM controllers. The version-check snippet above should be added to `create_bd.tcl` to surface mismatches early in the CI pipeline.
