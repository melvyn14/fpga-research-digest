# FPGA Research Digest - 2026-10-14

## Executive Summary
- **VALID must never depend on READY in AXI-Lite**: asserting VALID conditionally on READY causes a deadlock that is hard to catch in simulation. Register your RVALID/BVALID independently, and use Vivado's AXI Protocol Checker IP to catch violations automatically.
- **Vivado 2025.1 added two new IP Integrator dedicated views** — "Clocking and Reset" and "Interrupt and AXI-4 Lite" — which make it easier to verify PS-PL clock and AXI-Lite connectivity at a glance before running implementation.
- **UART1 is the console UART on the KV260**, not UART0; the micro-USB J4 connector routes through a CP210x bridge at 115200 8N1. Confirm the UART instance in `xparameters.h` matches your BSP.
- **Linker script pitfall in Vitis**: the auto-generated linker script may place all sections in the wrong memory region (e.g., BAR0 or OCM). Always verify every section (`.text`, `.data`, `.bss`, `.heap`, `.stack`) is mapped to DDR for Cortex-A53 bare-metal on the KV260.
- **set_clock_groups -asynchronous** is the correct constraint for the PS-to-PL clock boundary; failing to add it lets the Vivado timing analyzer report false critical paths across asynchronous clock domains, potentially blocking implementation.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings
- **VALID must not depend on READY**: the AXI spec forbids making a VALID signal conditional on the corresponding READY. A master or slave that gates its VALID on the other side's READY creates a deadlock where neither signal is ever asserted first. This is the most common AXI implementation bug (ZipCPU, 2019; still relevant in 2025 designs).
- **VALID must stay asserted until handshake completes**: once VALID is raised, it must remain high until the cycle where both VALID and READY are simultaneously high.
- **Write address and data channels are independent**: AXI-Lite does not require AWVALID and WVALID to arrive in the same cycle. A slave must accept them in any order.
- **AXI-Lite has no burst signals**: there is no AWLEN, WLAST, ARLEN, or RLAST. Each transaction is exactly one beat. Do not confuse AXI-Lite with AXI4-Stream (which does have TLAST).
- **Use the AXI Protocol Checker IP**: synthesis tools do not catch protocol violations. Vivado's AXI Protocol Checker IP or ARM's formal SVA assertions should be inserted in simulation to catch VALID/READY ordering bugs before hardware.

### Code Example
```vhdl
-- AXI-Lite slave read channel: correctly register RVALID
-- RVALID is set independently of RREADY to avoid deadlock
process(clk)
begin
  if rising_edge(clk) then
    if rst_n = '0' then
      s_axi_rvalid <= '0';
      s_axi_rdata  <= (others => '0');
    elsif s_axi_arvalid = '1' and s_axi_arready = '1' then
      -- Address accepted: latch read data and assert RVALID
      s_axi_rdata  <= bram_rd_data;  -- data from BRAM read port
      s_axi_rvalid <= '1';
      s_axi_rresp  <= "00";          -- OKAY
    elsif s_axi_rvalid = '1' and s_axi_rready = '1' then
      -- Handshake complete: deassert RVALID
      s_axi_rvalid <= '0';
    end if;
  end if;
end process;
-- ARREADY is set independently; never conditioned on RREADY
s_axi_arready <= not s_axi_rvalid;  -- accept new address when not busy
```

### Relevance to Your Project
Your `kv260-axi-bram-demo` uses two AXI-Lite BRAM controllers (BRAM0 @ 0xA0000000, BRAM2 @ 0xA0010000). If you ever replace the Xilinx BRAM Controller IP with a custom slave, the pattern above is the correct RVALID registration. The generated Xilinx slave should already be compliant, but the AXI Protocol Checker IP is worth inserting in simulation to confirm — especially when integrating both controllers through the AXI Interconnect.

## Vivado Block Design / IP Integrator

### Key Findings
- **Vivado 2025.1 added two dedicated IP Integrator views**: "Clocking and Reset" and "Interrupt and AXI-4 Lite". These dedicated panels expose more connectivity information than the main block diagram canvas and help verify PS-PL clocking and AXI-Lite routing without scrolling through a dense BD.
- **Address Editor workflow**: in the Address Editor, each AXI slave (including your two BRAM Controllers) must be assigned a unique base address and range. Use the Range column to set 64K per controller. The auto-assigned addresses may not match your bare-metal defines, so always cross-check against `xparameters.h`.
- **`write_bd_tcl` for reproducible BD generation**: export the block design with `write_bd_tcl -force <path>`. The `-ignore_minor_versions` flag makes regenerated IPs snap to the latest minor version of each IP, reducing stale-IP warnings without changing major API compatibility.
- **Connection Automation**: after adding IP, run `apply_bd_automation` via TCL or the GUI to auto-connect clock, reset, and AXI wires. Manual wiring after automation often overwrites automation intent; run automation once, then lock individual connections.
- **Vivado 2025.2 added a PS Wizard swim-lane view** for more detailed PS configuration, separate from the two 2025.1 views.

### Code Example
```tcl
# Set fixed addresses for both BRAM Controllers in the Address Editor
# Run this after all IPs are placed in the BD
assign_bd_address [get_bd_addr_segs {axi_bram_ctrl_0/S_AXI/Mem0}]
set_property offset 0xA0000000 \
  [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property range 64K \
  [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]

assign_bd_address [get_bd_addr_segs {axi_bram_ctrl_1/S_AXI/Mem0}]
set_property offset 0xA0010000 \
  [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_1_Mem0}]
set_property range 64K \
  [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_1_Mem0}]
```

### Relevance to Your Project
Your `create_bd.tcl` script should include address assignments equivalent to the above so the project rebuilds reproducibly from TCL and the base addresses match the `0xA0000000` / `0xA0010000` values hard-coded in `main.c`. Any mismatch between the Address Editor and the software defines will cause silent write failures that appear as readback mismatches.

## Vivado TCL Scripting

### Key Findings
- **Non-project mode end-to-end**: the AMD-recommended non-project flow (UG994 2025.1) sources the BD TCL, calls `generate_target all`, sets `synth_checkpoint_mode None` on the BD, runs `synth_design`, `opt_design`, `place_design`, `route_design`, `write_bitstream`, then `write_hw_platform -fixed -force` to produce the XSA.
- **`synth_checkpoint_mode None` is mandatory**: without it, Vivado attempts hierarchical synthesis of the BD, which can fail or produce incorrect netlists for some IPs. Always set it on the BD file object before synthesis.
- **`write_bd_tcl` options to know**: `-force` overwrites an existing file; `-ignore_minor_versions` pins IPs to the latest minor version at regeneration time; `-bd_name` renames the exported diagram; `-no_ip_version` strips versions from VLNVs (use carefully — major-version upgrades will silently pick the new major).
- **Batch invocation**: run a non-project script from the command line with `vivado -mode batch -source build.tcl`. Avoid `-notrace` unless debugging is complete; the trace output is valuable for diagnosing regeneration failures.
- **`write_hw_platform` requires XSA properties**: the block design must set the required platform properties (PLATFORM.NAME, etc.) before `write_hw_platform` succeeds. Omitting these causes a "missing required properties" error in Vitis.

### Code Example
```tcl
# Minimal non-project build script (UG994 2025.1 pattern)
set_param general.maxThreads 8
set part "xck26-sfvc784-2LV-c"
set board "xilinx.com:kv260_som:part0:1.4"

create_project -in_memory -part $part
set_property board_part $board [current_project]

# Source the exported BD script
source ./tcl/create_bd.tcl
make_wrapper -force -files [get_files kv260_bd.bd] -top
add_files -norecurse ./kv260_bd_wrapper.v

# Prepare for synthesis
set_property synth_checkpoint_mode None \
  [get_files ./kv260_bd.bd]
generate_target all [get_files ./kv260_bd.bd]

# Full implementation flow
synth_design   -top kv260_bd_wrapper -part $part
opt_design
place_design
route_design
write_bitstream -force ./output/kv260.bit
write_hw_platform -fixed -force -include_bit ./output/kv260.xsa
```

### Relevance to Your Project
A script like this replaces the GUI project flow so the `kv260-axi-bram-demo` can be built in CI without a persistent `.xpr` file. Commit `create_bd.tcl` (exported via `write_bd_tcl`) alongside this build script and the XSA generation becomes fully reproducible.

## Vitis Bare-Metal / Standalone

### Key Findings
- **`xil_printf` is a lightweight printf stub**: it is included in the standalone BSP for all ARM cores and does not require `<stdio.h>`. It supports `%d`, `%x`, `%s`, `%c`, `%u` but not floating-point. For full printf, link in `printf` from newlib via `-DSTDIO_WANTS_FLOATING_POINT` or just use `xil_printf` for UART output.
- **Linker script memory map must be verified**: Vitis generates a linker script automatically, but it may assign sections to OCM (On-Chip Memory) or the wrong memory region. For Cortex-A53 bare-metal on the KV260, all sections should target DDR. Open `lscript.ld` and confirm `.text`, `.data`, `.bss`, `.heap`, and `.stack` all reference the `psu_ddr_0_MEM0` region.
- **UART1 is the console UART on KV260**: the micro-USB J4 connector routes through a CP210x USB-to-UART bridge to the PS UART1 peripheral. The `xparameters.h` value for `XPAR_XUARTPS_1_BASEADDR` should be used, not `..._0_BASEADDR`, unless the BSP is configured otherwise.
- **Standalone BSP source is open**: the BSP source ships with the Vitis install at `$XILINX_VITIS/data/embeddedsw/lib/bsp/standalone` and is also on the Xilinx GitHub. Patch it there if you need a BSP modification.
- **Interrupt controller initialization order**: for bare-metal interrupt use, initialize the `XScuGic` instance before registering individual handlers. Calling `XScuGic_CfgInitialize` with the wrong CPU ID is a common pitfall that results in interrupts routing to the wrong core.

### Code Example
```c
/* main.c pattern for KV260 AXI-BRAM bare-metal test */
#include "xparameters.h"
#include "xil_printf.h"
#include "xil_io.h"

#define BRAM0_BASE  XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR  /* 0xA0000000 */
#define BRAM2_BASE  XPAR_AXI_BRAM_CTRL_1_S_AXI_BASEADDR  /* 0xA0010000 */
#define TEST_PATTERN 0xDEADBEEF

static int test_bram(u32 base, const char *name)
{
    Xil_Out32(base, TEST_PATTERN);
    u32 rd = Xil_In32(base);
    if (rd == TEST_PATTERN) {
        xil_printf("%s: PASS (0x%08X)\r\n", name, rd);
        return 0;
    }
    xil_printf("%s: FAIL (got 0x%08X)\r\n", name, rd);
    return -1;
}

int main(void)
{
    xil_printf("KV260 AXI-BRAM test\r\n");
    int rc = 0;
    rc |= test_bram(BRAM0_BASE, "BRAM0");
    rc |= test_bram(BRAM2_BASE, "BRAM2");
    xil_printf(rc == 0 ? "All PASS\r\n" : "FAIL\r\n");
    return rc;
}
```

### Relevance to Your Project
This is structurally identical to what `main.c` in the `kv260-axi-bram-demo` project does. Key practice: use `XPAR_AXI_BRAM_CTRL_x_S_AXI_BASEADDR` from `xparameters.h` rather than hard-coded hex addresses in production code, so the software stays synchronized with the Address Editor even if you remap the BRAMs.

## XDC Timing Constraints

### Key Findings
- **Recommended constraint ordering (UG903 2025.2)**: clocks first, then clock groups, then bus skew, then I/O delays (`set_input_delay`/`set_output_delay`), then timing exceptions (`set_false_path`, `set_multicycle_path`). Violations of this ordering can cause the analyzer to process exceptions before the related clocks are defined, producing incorrect results.
- **`set_clock_groups -asynchronous` for PS-PL boundary**: the PS clock (`pl_clk0` or similar) and the PL fabric clock are typically asynchronous to each other relative to reset timing. Adding `set_clock_groups -asynchronous -group [get_clocks clk_pl_0] -group [get_clocks <other_clk>]` prevents false cross-domain timing failures.
- **I/O delays should reference the correct clock**: `set_input_delay` and `set_output_delay` must reference the clock that actually captures or launches the I/O path. Using the wrong clock source inflates slack reporting.
- **For AXI interfaces through the PS**: paths entirely within the PS-to-PL AXI interface are constrained by the Zynq IP's internal timing model; you generally do not need to add `set_input_delay` for AXI-Lite signals that stay within the PL fabric.
- **Constraint runtime ordering tip (UG903 2026.1)**: placing I/O delays before timing exceptions improves Vivado runtime because the analyzer can prune I/O-related paths earlier.

### Code Example
```tcl
# kv260_top.xdc — minimal timing constraints for PS-PL AXI-BRAM design

# 1. Primary clocks (PS provides pl_clk0 via Zynq IP; no create_clock needed
#    for PS-generated clocks — they are auto-constrained by the PS IP)

# 2. Clock groups: tell Vivado that pl_clk0 and any debug/JTAG clocks
#    are asynchronous so cross-domain paths are not falsely flagged
set_clock_groups -asynchronous \
  -group [get_clocks -of_objects [get_pins \
    zynq_ultra_ps_e_0/inst/PS8_i/PLCLK[0]]] \
  -group [get_clocks -include_generated_clocks dbg_hub/inst/clk]

# 3. I/O delays (only needed if you add PL I/O; AXI paths inside the PL
#    are self-contained and do not require set_input_delay)

# 4. False paths to asynchronous resets driven from PS GPIO
set_false_path -from [get_pins \
  zynq_ultra_ps_e_0/inst/PS8_i/EMIOgpio*] \
  -to [all_registers]
```

### Relevance to Your Project
For a minimal PS-to-PL AXI-BRAM design with no external I/O in the PL, the XDC file can be very short — essentially just the clock group constraint. The most common mistake is omitting it and then spending hours debugging false timing failures during `route_design` that disappear once the asynchronous relationship is declared.

## Kria KV260 / K26 SoM

### Key Findings
- **USB-UART uses PS UART1 via J4**: the KV260 StarterKit's micro-USB connector (J4) is wired through a Silicon Labs CP210x USB-to-UART bridge to PS UART1. The host requires the CP210x driver. Terminal settings: 115200 baud, 8N1, no flow control. Use `XPAR_XUARTPS_1_BASEADDR` in bare-metal, not UART0.
- **Boot mode is QSPI-fixed**: the K26 SoM has no boot-mode DIP switches. It boots from QSPI flash. For bare-metal development, the FSBL stored in QSPI loads the bitstream and application; in Vitis you typically override this by loading directly over JTAG via `xsct`.
- **Two 240-pin connectors expose PS MIO and PL I/O**: connector J1 and J2 expose PS MIO banks 501/502, PS-GTR transceivers, PS I2C, and PL HPIO/HDIO/GTH banks. Bank 504 is dedicated to the DDR4 controller and is not user-accessible.
- **UART1 MIO mapping**: PS UART1 Rx/Tx are fixed to MIO 48/49 on the K26 SoM (confirmed via the Buildroot KV260 board config and QNX BSP documentation). UART0 is connected to JTAG/debug logic on many carrier designs.
- **Power domains**: the K26 SoM has separate power rails for PS (VCC_PSINTLP, VCC_PSINTFP, VCC_PSAUX) and PL (VCCO_HPIO, VCCO_HDIO). Do not power-cycle PL without considering PS sequencing.

### Code Example
```c
/* Bare-metal UART1 initialization for KV260 (standalone BSP) */
#include "xuartps.h"
#include "xparameters.h"

static XUartPs uart_inst;

int uart_init(void)
{
    XUartPs_Config *cfg =
        XUartPs_LookupConfig(XPAR_XUARTPS_1_DEVICE_ID);  /* UART1 */
    if (!cfg) return -1;

    int rc = XUartPs_CfgInitialize(&uart_inst, cfg, cfg->BaseAddress);
    if (rc != XST_SUCCESS) return rc;

    XUartPs_SetBaudRate(&uart_inst, 115200);
    XUartPs_SetDataFormat(&uart_inst,
        &(XUartPsFormat){.BaudRate = 115200,
                         .DataBits = XUARTPS_FORMAT_8_BITS,
                         .Parity   = XUARTPS_FORMAT_NO_PARITY,
                         .StopBits = XUARTPS_FORMAT_1_STOP_BIT});
    return 0;
}
```

### Relevance to Your Project
Your `main.c` uses `xil_printf` for PASS/FAIL output. `xil_printf` internally calls the UART configured by the BSP's `stdin`/`stdout` settings. In Vitis, open the BSP settings → `standalone` domain → confirm `stdin` and `stdout` are both set to `psu_uart_1` (UART1). If they point to `psu_uart_0`, output will be silent over the USB-UART cable.

## AMD/Xilinx Tool Updates (Vivado/Vitis 2025.x)

### Key Findings
- **New AXI Switch IP v1.0 (Vivado 2025.1)**: a fully customizable RTL-based IP that bridges different AXI interface types and widths. It is instantiated into RTL designs with a generated component wrapper, not dragged into IP Integrator like a managed IP. No changes were shipped in 2025.2. The `STRATEGY` parameter for ultra-low-area mode was added in 2025.2.
- **New IP Integrator views (2025.1)**: two dedicated sub-panels — "Clocking and Reset" and "Interrupt and AXI-4 Lite" — provide structured views of PS-PL connectivity without requiring manual inspection of the block diagram canvas.
- **New device support (2025.1)**: Versal AI Edge Series Gen 2, Versal Prime Series Gen 2, and Spartan UltraScale+ family. No new Zynq UltraScale+ or Kria-specific silicon was added.
- **Vitis AI 5.1 targets 2025.1**: Vitis AI 5.1 is the companion AI framework release for Vivado/Vitis 2025.1.1. It adds Apptainer as a Docker alternative and BF16 support for several YOLO model variants.
- **Open-source components 2025.1**: Linux kernel upgraded to 6.12 in PetaLinux 2025.1. Zephyr RTOS gained early-access driver support for several Zynq peripherals.
- **PS Wizard swim-lane view (2025.2)**: a separate visual redesign of the PS configuration wizard, not a block-design IP Integrator view.

### Code Example
```tcl
# Vivado 2025.1: query the new IP Integrator dedicated views
# (run inside the Vivado Tcl Console after opening a BD)

# List all view names available in the current BD
report_bd_design

# Open the dedicated Clocking and Reset view
open_bd_design [get_files *.bd]
# In the GUI: Diagram → Window → Clocking and Reset  (new in 2025.1)
# In Tcl batch mode, validate the clocking connections programmatically:
validate_bd_design

# Export updated BD as TCL after any edits
write_bd_tcl -force -ignore_minor_versions ./tcl/create_bd.tcl
puts "BD exported to TCL"
```

### Relevance to Your Project
The new IP Integrator views in 2025.1 are directly useful when wiring the AXI-Lite interconnect and confirming that `pl_clk0` from the Zynq PS is correctly routed to both BRAM controllers. The "Interrupt and AXI-4 Lite" view will show whether both BRAM slaves are reachable from the PS master without requiring manual trace of nets in the block diagram. Rebuild with `validate_bd_design` before implementation to catch connectivity errors early.
