# FPGA Research Digest - 2026-11-12

## Executive Summary

- **AXI-Lite handshake rule #1**: VALID must stay asserted until READY is seen; never wait for READY before asserting VALID — violating this causes the AXI BRAM controller to stall silently with no error flag.
- **BRAM output register latency**: The AXI BRAM Controller's primitive output register can break timing closure — the fix is to disable the primitive register and enable only the Core output register, keeping functionality intact.
- **Non-project TCL pitfall**: Running `upgrade_ip [get_ips -all]` can silently delete sub-core IPs that the parent depends on; always upgrade parent IPs individually by name.
- **Vitis BSP stdout routing**: `xil_printf` output is silently dropped if BSP's `standalone_stdin`/`standalone_stdout` parameters are not set to the correct UART instance (`psu_uart_1` on KV260); verify in `vitis-comp.json`.
- **KV260 HPM port selection**: For bare-metal AXI-Lite masters on the Kria KV260, use `AXI HPM0 LPD` (not HPM0/HPM1 FPD) — the FPD ports may require additional GIC configuration that the bare-metal BSP doesn't set up.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- **VALID-before-READY rule**: The AXI spec requires the master to assert VALID independently and hold it until READY is seen. A common bug is gating VALID on READY, which creates a deadlock if the slave deasserts READY while waiting for the master.
- **Xilinx example IP known flaw**: The ZipCPU blog confirmed that Vivado's AXI-Lite example peripheral (up to at least 2018.3) silently drops acknowledgments unless `RREADY` and `BREADY` are held high throughout the transaction. User code must handle the case where BREADY/RREADY may not be high when the slave responds.
- **Unaligned transfers not supported on AXI-Lite**: The Xilinx AXI BRAM Controller does not support unaligned AXI-Lite transfers. Addresses must be 4-byte aligned; byte-lane selection must be done through the WSTRB strobes, not by offsetting the address.
- **Output register latency trap**: The BRAM primitive output register (`USE_BRAM_ENA_REG=1`) adds one extra clock cycle of read latency that the AXI BRAM Controller does not automatically account for. Result is stale read data or timing violations. Solution: disable the primitive output register, use only the core output register.
- **AWREADY combinatorial drop**: Third-party reports show that some AXI slaves drop AWREADY combinatorially when AWVALID is asserted, so the master sees its address never accepted. Xilinx's own AXI BRAM IP handles this correctly and can be used as a reference.
- **AXI-Stream vs AXI-Lite**: AXI-Stream has no address channel and is unidirectional; it is simpler but requires flow control via TREADY. AXI-Lite is better for register maps and control paths (like BRAM access); AXI-Stream is better for data pipelines.

### Code Example

```vhdl
-- Minimal AXI-Lite slave write channel (no BREADY/RREADY dependency)
-- Correct: VALID held until READY seen; BVALID driven independently

process(clk)
begin
  if rising_edge(clk) then
    if s_axi_awvalid = '1' and s_axi_awready = '1' then
      wr_addr <= s_axi_awaddr;
      wr_addr_latch <= '1';
    end if;
    if s_axi_wvalid = '1' and s_axi_wready = '1' then
      wr_data <= s_axi_wdata;
      wr_strobe <= s_axi_wstrb;
      wr_data_latch <= '1';
    end if;
    -- Respond only when both address and data are latched
    if wr_addr_latch = '1' and wr_data_latch = '1' then
      mem(to_integer(unsigned(wr_addr(ADDR_BITS-1 downto 2)))) <= wr_data;
      s_axi_bvalid <= '1';
      wr_addr_latch <= '0';
      wr_data_latch <= '0';
    end if;
    -- Clear BVALID once master accepts response
    if s_axi_bvalid = '1' and s_axi_bready = '1' then
      s_axi_bvalid <= '0';
    end if;
  end if;
end process;
-- AWREADY and WREADY can be permanently high for simple implementations
s_axi_awready <= '1';
s_axi_wready  <= '1';
s_axi_bresp   <= "00"; -- OKAY
```

### Relevance to Your Project

Your design uses two AXI-Lite BRAM controllers at `0xA0000000` (BRAM0) and `0xA0010000` (BRAM2). If read-back returns wrong data, check the BRAM output register configuration first. If writes appear to succeed but reads fail, verify that `WSTRB` is `0xF` for full 32-bit writes in your bare-metal C code (`Xil_Out32` handles this correctly). If you see AXI bus hangs, check that the `RREADY`/`BREADY` signals in the generated BSP driver are held high before polling.

## Vivado Block Design / IP Integrator

### Key Findings

- **Connection automation for BRAM**: In IP Integrator, after adding an AXI BRAM Controller, clicking "Run Connection Automation" and selecting the `S_AXI` port automatically connects it to the PS master port (`M_AXI_HPM0_LPD`) and creates the BRAM instance. This is faster and less error-prone than manual wiring.
- **Address editor**: After running automation, verify the base address in the Address Editor (`0xA000_0000`). The KV260 Kria SmartCamera reference uses `0xA000_0000`, which is in the correct PL-mapped range for HPM0 LPD.
- **Re-generating outputs**: After editing a block design, you must right-click → "Generate Output Products" before running synthesis. In non-project mode, `generate_target all [get_files *.bd]` performs this step.
- **Exporting a block design to TCL**: Use `File → Export → Export Block Design` in the GUI or `write_bd_tcl -force <output.tcl>` in the Tcl console to capture the entire block design as a reproducible script. This is the recommended way to version-control block designs.
- **Vivado 2025.x constraint-set bug**: Removing an XDC file from one constraint set also removes it from other constraint sets that reference the same file. Workaround: keep one XDC per constraint set, or copy rather than share XDC files between sets.

### Code Example

```tcl
# Vivado 2025.1 IP Integrator: Create and connect AXI BRAM in non-project mode
create_project -in_memory -part xck26-sfvc784-2LV-c

# Create block design
create_bd_design "system"

# Add Zynq MPSoC PS
create_bd_cell -type ip -vlnv xilinx.com:ip:zynq_ultra_ps_e:3.5 zynq_ultra_ps_e_0
apply_bd_automation -rule xilinx.com:bd_rule:zynq_ultra_ps_e \
  -config {apply_board_preset "1"} [get_bd_cells zynq_ultra_ps_e_0]

# Enable HPM0 LPD AXI master port
set_property -dict [list \
  CONFIG.PSU__USE__M_AXI_GP2 {1} \
  CONFIG.PSU__USE__M_AXI_GP0 {0} \
] [get_bd_cells zynq_ultra_ps_e_0]

# Add AXI BRAM Controller
create_bd_cell -type ip -vlnv xilinx.com:ip:axi_bram_ctrl:4.1 axi_bram_ctrl_0
set_property CONFIG.SINGLE_PORT_BRAM {1} [get_bd_cells axi_bram_ctrl_0]

# Add Block Memory Generator
create_bd_cell -type ip -vlnv xilinx.com:ip:blk_mem_gen:8.4 blk_mem_gen_0

# Connect BRAM controller to memory
connect_bd_intf_net [get_bd_intf_pins axi_bram_ctrl_0/BRAM_PORTA] \
  [get_bd_intf_pins blk_mem_gen_0/BRAM_PORTA]

# Run connection automation for AXI
apply_bd_automation -rule xilinx.com:bd_rule:axi4 \
  -config {Master "/zynq_ultra_ps_e_0/M_AXI_HPM0_LPD" Clk "Auto"} \
  [get_bd_intf_pins axi_bram_ctrl_0/S_AXI]

# Assign address: BRAM0 at 0xA000_0000, 64KB
assign_bd_address
set_property offset 0xA0000000 [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property range 64K [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]

# Validate and generate
validate_bd_design
generate_target all [get_files system.bd]
```

### Relevance to Your Project

The `create_bd.tcl` in your project likely mirrors this pattern. The critical step is ensuring `PSU__USE__M_AXI_GP2` (HPM0 LPD) is enabled rather than the FPD ports, which matches the bare-metal use case. The address assignment `0xA0000000` and `0xA0010000` for BRAM0 and BRAM2 must be explicitly set after `assign_bd_address` runs its automatic mapping.

## Vivado TCL Scripting

### Key Findings

- **Non-project mode is repeatable**: In non-project mode, the in-memory design is built fresh each run from TCL — there's no `.xpr` file and no state persistence between runs. This is ideal for CI/CD and reproducible builds.
- **Script order matters**: In non-project mode the order is: `read_bd` → `read_xdc` → `generate_target` → `synth_design` → `opt_design` → `place_design` → `route_design` → `write_bitstream`.
- **IP Tcl reference files**: Always use the `.xci` file (not `.dcp`) when referencing IP in scripts. The `.dcp` is a synthesized checkpoint and cannot be re-customized.
- **Upgrade warning**: `upgrade_ip [get_ips -all]` returns sub-core IPs and may delete them during parent IP upgrades, leaving dangling Tcl object references. Upgrade parent IPs individually: `upgrade_ip [get_ips axi_bram_ctrl_0]`.
- **Exporting from GUI for iteration**: Running `write_bd_tcl -force bd_export.tcl` after GUI modifications captures all property settings in one script. After upgrading to a new Vivado version, re-run this export to capture updated IP defaults.
- **Batch execution**: Run with `vivado -mode batch -source create_bd.tcl` for headless builds. The `-nojournal -nolog` flags suppress journal/log files in CI environments.

### Code Example

```tcl
# Non-project mode build script template for KV260 AXI-BRAM design
# Usage: vivado -mode batch -source build.tcl

# Target part for K26 SOM (commercial grade)
set_part xck26-sfvc784-2LV-c

# Read sources
read_bd  ./kv260/bd/system/system.bd
read_vhdl -library xil_defaultlib ./kv260/vhdl/kv260_top.vhd
read_xdc ./kv260/constraints/kv260_top.xdc

# Generate IP output products (must precede synthesis)
generate_target all [get_files system.bd]
export_ip_user_files -of_objects [get_files system.bd] -no_script -sync -force -quiet

# Synthesis
synth_design -top kv260_top -part xck26-sfvc784-2LV-c -flatten_hierarchy rebuilt

# Implementation
opt_design
place_design
phys_opt_design
route_design

# Reports
report_timing_summary -file timing_summary.rpt -warn_on_violation
report_utilization -file utilization.rpt

# Output
write_bitstream -force kv260_top.bit
write_hw_platform -fixed -force -include_bit -file kv260_top.xsa
```

### Relevance to Your Project

Your `create_bd.tcl` script can be enhanced with error checking: wrap critical commands in `if {[catch {<cmd>} err]} { puts "ERROR: $err"; exit 1 }`. Adding `report_timing_summary -warn_on_violation` at the end of the build catches timing failures before the bitstream is loaded, preventing confusing PASS/FAIL patterns from marginal timing.

## Vitis Bare-Metal / Standalone

### Key Findings

- **BSP stdout configuration**: `xil_printf` output is routed through the BSP's `standalone_stdin`/`standalone_stdout` settings. On KV260, this must point to `psu_uart_1` (USB UART). If set to `psu_uart_0` (the debug UART), output goes nowhere visible over the USB cable. Verify in `vitis-comp.json` or the platform component settings.
- **xil_printf vs printf**: `xil_printf` is a lightweight implementation that does **not** support floating-point format specifiers (`%f`, `%e`). Use `printf` from the full libc (which the linker script must include) or format floats manually if needed.
- **Linker script memory regions**: The default Vitis linker script (`lscript.ld`) maps `.text` and `.data` to DDR. For KV260, the DDR base is `0x00000000` and the PS-PL AXI address region starts at `0xA0000000` — ensure your code never accidentally accesses the BRAM address range as regular memory via a stray pointer.
- **Cache coherency**: On Zynq MPSoC (A53), the data cache is enabled by default in the standalone BSP. Writes to AXI-mapped peripherals (like BRAM) are not necessarily cache-line flushed. Use `Xil_DCacheFlushRange()` after writing, or use `Xil_Out32`/`Xil_In32` which bypass the cache via MMIO (they use device memory attributes in the MMU).
- **Interrupt setup minimal path**: For bare-metal polling (no interrupts), no GIC configuration is needed. If you add interrupt-driven BRAM access later, the GIC requires `XScuGic_Initialize()` before any `XScuGic_Connect()` calls.
- **2025.1 open-source component changes**: The Xilinx wiki 2025.1 release notes list BSP component updates. Key items include Cortex-R5 fixes; Cortex-A53 standalone BSP received stability patches for cache management APIs.

### Code Example

```c
/* KV260 bare-metal AXI-BRAM read/write with cache safety */
#include "xil_io.h"
#include "xil_printf.h"
#include "xil_cache.h"

#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL
#define TEST_OFFSET 0x00000000UL
#define PATTERN0    0xDEADBEEFUL
#define PATTERN2    0xCAFEBABEUL

int main(void) {
    u32 readback;
    int pass = 1;

    xil_printf("KV260 AXI-BRAM Test\r\n");

    /* Write patterns - Xil_Out32 uses device memory, no cache flush needed */
    Xil_Out32(BRAM0_BASE + TEST_OFFSET, PATTERN0);
    Xil_Out32(BRAM2_BASE + TEST_OFFSET, PATTERN2);

    /* Read back */
    readback = Xil_In32(BRAM0_BASE + TEST_OFFSET);
    if (readback != PATTERN0) {
        xil_printf("FAIL: BRAM0 expected 0x%08X got 0x%08X\r\n",
                   (unsigned)PATTERN0, (unsigned)readback);
        pass = 0;
    }

    readback = Xil_In32(BRAM2_BASE + TEST_OFFSET);
    if (readback != PATTERN2) {
        xil_printf("FAIL: BRAM2 expected 0x%08X got 0x%08X\r\n",
                   (unsigned)PATTERN2, (unsigned)readback);
        pass = 0;
    }

    xil_printf(pass ? "PASS\r\n" : "FAIL\r\n");
    return 0;
}
```

### Relevance to Your Project

Your `main.c` already uses this pattern. The key addition here is the cache-safety note: `Xil_Out32`/`Xil_In32` are correct for MMIO (they're implemented as volatile accesses through a device-memory MMU mapping), so no explicit cache flush is needed. If you ever switch to pointer-based access (`*(volatile u32*)addr`), you must mark the address region as device memory in the MMU or add explicit barriers.

## XDC Timing Constraints

### Key Findings

- **Constraint ordering matters for runtime**: AMD UG903 recommends ordering constraints as: clocks → I/O delays → timing exceptions → false paths → multicycle paths. `set_clock_groups` has higher precedence than `set_false_path` and should come before timing exceptions in the XDC.
- **`set_clock_groups` is not a timing exception**: Despite being listed near exceptions, `set_clock_groups` has higher precedence than `set_false_path`. Use it to cut timing paths between unrelated clock domains (e.g., between the PS `clk_wiz` output and the PL fabric clock).
- **`set_input_delay` skip on clock ports**: In Vivado 2025.1, `set_input_delay -clock [get_clocks] [all_inputs]` silently skips clock ports. This is intentional behavior documented in UG835.
- **`-add_delay` for multiple corners**: `set_output_delay` by default replaces existing delays. When specifying both setup and hold constraints, use `-add_delay` for the second call to accumulate both values rather than replace.
- **Unconstrained I/Os**: Any port not covered by `set_input_delay`/`set_output_delay` will not be timing-analyzed and may show up as a DRC warning. For AXI-only designs where all I/Os go through the PS block, add `set_false_path -from [all_inputs] -to [all_outputs]` to silence DRC warnings about unconstrained ports.
- **KV260 platform clock**: The main PL fabric clock is generated by the PS (`pl_clk0`), typically configured for 100 MHz. The XDC only needs to constrain the PL clock if you instantiate a clock wizard; the PS-generated clock is auto-constrained by the BD.

### Code Example

```tcl
# KV260 XDC timing constraints for AXI-BRAM bare-metal design
# kv260_top.xdc

# PS-generated PL clock (100 MHz) - auto-created by block design, listed for reference
# create_clock -period 10.000 -name pl_clk0 [get_pins zynq_ultra_ps_e_0/pl_clk0]

# Suppress timing analysis on PS I/O ports (PS handles its own timing internally)
set_false_path -from [get_ports] -to [all_registers]
set_false_path -from [all_registers] -to [get_ports]

# If using external async reset input:
# set_false_path -from [get_ports aresetn]

# Cut clock groups between PS internal clocks and PL fabric clock
# (prevents spurious cross-domain timing paths in reports)
set_clock_groups -asynchronous \
  -group [get_clocks -include_generated_clocks pl_clk0] \
  -group [get_clocks -include_generated_clocks clk_out1_system_clk_wiz_0_0]

# Example: set_input_delay for a hypothetical GPIO input (not needed for pure AXI design)
# set_input_delay -clock [get_clocks pl_clk0] -max 2.0 [get_ports {gpio_in[*]}]
# set_input_delay -clock [get_clocks pl_clk0] -min 0.5 [get_ports {gpio_in[*]}] -add_delay
```

### Relevance to Your Project

For a pure AXI-BRAM design (no external I/O pins), your XDC can be minimal — the PS block auto-constrains its own interfaces, and the AXI signals are entirely internal. The main constraint to add is `set_clock_groups -asynchronous` between the PS clock and any clock wizard output if you add one. The `set_false_path` on ports suppresses DRC warnings without affecting analysis of your AXI logic.

## Kria KV260 / K26 SoM

### Key Findings

- **MIO bank layout**: The K26 SOM has three MIO banks. Bank 500 (MIO 0–25) is used for QSPI flash, eMMC, I2C bus, and TPM SPI. Bank 501 (MIO 26–51) handles PMU power management and some user I/O. Bank 502 (MIO 52–77) is fully user-assignable. All banks run from the SOM's 1.8V rail.
- **SOM connectors**: The K26 uses two 240-pin SOM connectors. SOM240_1 is shared with K24 and carries MIO, PS-GTR, HPIO/HDIO subsets, and SOM power. SOM240_2 is K26-only and adds additional HPIO, HDIO, and GTH transceivers.
- **Boot sequence**: Primary boot device is QSPI flash on the SOM. BOOT.BIN contains FSBL + PMU firmware + ATF + bitstream (optional) + U-Boot/bare-metal ELF. Secondary boot device is microSD (SD1, via carrier card). Boot mode is set by physical strapping pins on the carrier; the KV260 carrier defaults to QSPI boot.
- **PS-PL isolation**: By default the PL is not powered or programmed. The bare-metal FSBL or the PS must explicitly release the PL reset. In Vitis, the generated FSBL handles PL programming from BOOT.BIN; ensure the bitstream is included in the boot image using `bootgen`.
- **HPM port recommendation**: For bare-metal AXI-Lite to PL, prefer `M_AXI_HPM0_LPD` (Low Power Domain, 32-bit, no need to configure the FPD interconnect). Using HPM0/HPM1 FPD requires that the FPD is fully initialized, which requires a more complex BSP initialization.
- **KV260 vs KR260 Ethernet**: The KV260 carrier does not have GEM0/GEM1 Ethernet; the KR260 does. For network connectivity on KV260, use USB or the PL-side Ethernet if present in your bitstream.

### Code Example

```tcl
# Vivado 2025.1: Configure PS for KV260 bare-metal AXI-Lite to PL
# Key settings for AXI BRAM access via HPM0 LPD

set_property -dict [list \
  CONFIG.PSU__CRL_APB__PL0_REF_CTRL__FREQMHZ  {100} \
  CONFIG.PSU__USE__M_AXI_GP2                  {1}   \
  CONFIG.PSU__USE__M_AXI_GP0                  {0}   \
  CONFIG.PSU__USE__M_AXI_GP1                  {0}   \
  CONFIG.PSU__UART1__PERIPHERAL__ENABLE       {1}   \
  CONFIG.PSU__UART1__PERIPHERAL__IO           {MIO 36 .. 37} \
  CONFIG.PSU__TTC0__PERIPHERAL__ENABLE        {0}   \
  CONFIG.PSU__FPGA_PL0_ENABLE                 {1}   \
] [get_bd_cells zynq_ultra_ps_e_0]

# GP2 = HPM0 LPD = 32-bit AXI master for PL access
# UART1 on MIO 36/37 = USB-UART via CP210x on KV260 carrier
# PL0 clock at 100 MHz drives the AXI fabric
```

### Relevance to Your Project

The `PSU__USE__M_AXI_GP2 = 1` setting enables the HPM0 LPD port that your BRAM controllers connect to. Setting `PSU__UART1__PERIPHERAL__IO = {MIO 36 .. 37}` maps the UART to the KV260's USB-to-UART bridge (CP210x chip), which is what you see output on over USB. If you're not seeing `xil_printf` output, verify these MIO assignments match your carrier card version.

## AMD/Xilinx Tool Updates (Vivado/Vitis 2025.x)

### Key Findings

- **Vivado 2025.1 IP changelog**: The IP release log includes CDC fix updates, YUV data type support in video IPs, and a new Versal GT Wizard addition. For AXI designs: no breaking changes to AXI Interconnect, AXI BRAM Controller, or Block Memory Generator were flagged for 2025.1.
- **Vivado 2025.x known issue — constraint sets**: Removing an XDC file from one constraint set removes it from all constraint sets that reference the same file. This is a confirmed bug in 2025.x. Workaround: use separate XDC file copies per constraint set.
- **LPDDR4 calibration bug**: LPDDR4 configured below 1600 MT/s with a speed bin above 1600 MT/s violates minimum clock frequency during calibration. Not relevant for BRAM-only designs but affects any future DRAM IP additions.
- **Vivado 2025.1.1 patch**: AMD released a 2025.1.1 patch release. As of this digest, no unresolved known issues are listed for 2025.1.1 (Versal-specific items excluded).
- **Vitis 2025.1 highlights**: Vitis HLS 2025.1 adds a `Performance` pragma for top-level designs (early access) and improved modeling for AXI-Lite inputs that change during execution. The Vitis Unified IDE has a known issue with Dhrystone ELF compilation on R52 (Versal AI Edge Gen2 only — not relevant for Kria KV260).
- **Vitis 2025.1 open-source components**: The Xilinx Wiki 2025.1 release notes cover changes to `embeddedsw` components. The standalone BSP received patches primarily for Cortex-R5; A53 standalone BSP cache management APIs were also patched for stability.
- **AMD docs.amd.com**: The 2025.1 versions of UG835 (Tcl command reference), UG903 (constraints), and UG994 (IP Integrator) are available at docs.amd.com. The `adaptivesupport.amd.com` domain is blocked in this cloud session's network policy, so direct AMD support article links cannot be fetched — browse them manually.
