# FPGA Research Digest - 2026-09-16

## Executive Summary

- **AXI-Lite VALID/READY rule**: A master must assert VALID *before* checking READY — waiting on READY before asserting VALID causes a protocol deadlock; this is the single most common AXI-Lite bug found even in Xilinx example code.
- **BRAM IP change in Vivado 2025.x**: The Block Memory Generator and Embedded FIFO Generator IPs are no longer instantiable directly from the IP Catalog in standalone mode — they must be placed inside a block design (IP Integrator), which affects any TCL flow that `create_ip` for BRAM outside a block design context.
- **AXI Interconnect deprecated**: AMD has discontinued the AXI Interconnect IP; AXI SmartConnect is the replacement and is already the default in connection automation. Designs still using `axi_interconnect` should migrate before the next major Vivado release removes it.
- **Kria KV260 bare-metal JTAG boot**: During development, the four-file JTAG flow (FSBL + PMU firmware + bitstream + application ELF) loaded via XSDB is the fastest iteration loop; QSPI32 is only needed for standalone deployment.
- **AXI SmartConnect multi-clock support**: Unlike the old Interconnect, SmartConnect natively handles multiple clock domains with one clock pin per domain — important if the PL AXI clock ever diverges from the PS `pl_clk0` used to drive BRAM controllers.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- **VALID must not wait for READY**: A source (master or slave) must assert VALID based solely on its own readiness. Asserting VALID only after READY is observed is a protocol violation and causes deadlock when both sides wait for each other. This mistake appears in some Xilinx template files.
- **Once VALID is asserted it must stay asserted**: Until the handshake completes (both VALID and READY sampled high on the same rising edge), VALID may not be de-asserted.
- **Backpressure propagation**: If a downstream consumer holds RREADY low, the slave must hold ARREADY low. Failing to propagate backpressure causes transactions to be lost silently.
- **Simultaneous read/write burst loss**: A design that accepts both AWVALID+AWREADY and ARVALID+ARREADY in the same cycle without tracking them separately will silently drop one burst.
- **AXI-Lite has no burst or ID field**: Unlike AXI4-Full, AXI-Lite transfers are always single-beat and the ID field is absent. The AXI BRAM Controller configured for AXI-Lite mode is correct for the KV260 demo — attempting AXI4 burst mode requires additional BRAM controller configuration and a full AXI4 master.

### Code Example

```vhdl
-- Minimal AXI-Lite single write, read-back in VHDL
-- Demonstrates correct VALID-before-READY assertion

process(clk)
begin
  if rising_edge(clk) then
    if rst = '1' then
      s_axi_awvalid <= '0';
      s_axi_wvalid  <= '0';
      s_axi_bready  <= '1';
    else
      -- Assert VALID unconditionally once data is ready
      -- Never gate on READY
      if write_req = '1' and s_axi_awready = '0' then
        s_axi_awvalid <= '1';
        s_axi_awaddr  <= target_addr;
        s_axi_wvalid  <= '1';
        s_axi_wdata   <= write_data;
        s_axi_wstrb   <= "1111";
      elsif s_axi_awready = '1' and s_axi_wready = '1' then
        s_axi_awvalid <= '0';
        s_axi_wvalid  <= '0';
      end if;
    end if;
  end if;
end process;
```

### Relevance to Your Project

Your `main.c` performs direct memory-mapped writes to `0xA0000000` (BRAM0) and `0xA0010000` (BRAM2). The Cortex-A53 AXI master (PS) handles the handshake automatically, but understanding the protocol is critical for debugging unexpected PASS/FAIL results: a slave that de-asserts WREADY prematurely without the master tracking the partial handshake would silently drop the write, causing the readback to return stale or zero data. Use the Vivado ILA (Integrated Logic Analyzer) on the AXI bus signals to verify VALID/READY pairing if you observe intermittent failures.

## Vivado Block Design / IP Integrator

### Key Findings

- **BRAM must live in block design (2025.x)**: As of Vivado 2025.1/2025.2, the Block Memory Generator and Embedded Memory Generator IPs cannot be instantiated as standalone IP — they exist only within IP Integrator block designs. RTL instantiation must use XPM (`xpm_memory_spram`, etc.) instead.
- **Address Editor caution**: Manual edits to the Address Editor are strongly discouraged by AMD unless you are an advanced user. Prefer "Assign All" automation and only override addresses (e.g., to fix `0xA0000000` and `0xA0010000`) using the offset field after automation runs.
- **Connection Automation scope**: Clicking "Run Connection Automation" after adding an AXI BRAM Controller will automatically instantiate an AXI SmartConnect, a Block Memory Generator, and a Processor System Reset, and wire them together — this is the recommended path rather than manually connecting ports.
- **Validate Design before generating**: Always run **Validate Design (F6)** before generating the bitstream. It catches unconnected AXI clock/reset pins and address space conflicts that synthesis will not flag clearly.
- **AXI SmartConnect replaces Interconnect**: The old `axi_interconnect` IP is deprecated and will be removed. Connection Automation now places `axi_smartconnect` by default.

### Code Example

```tcl
# In create_bd.tcl: assign specific base addresses after automation
# to match the hardcoded addresses in main.c

# Run connection automation first, then fix addresses:
assign_bd_address

# Override BRAM0 offset to match 0xA0000000
set_property offset 0xA0000000 [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property range  64K        [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]

# Override BRAM2 offset to match 0xA0010000
set_property offset 0xA0010000 [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_1_Mem0}]
set_property range  64K        [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_1_Mem0}]
```

### Relevance to Your Project

Your `create_bd.tcl` builds the block design programmatically. The address assignments above ensure the two BRAMs land at exactly `0xA0000000` and `0xA0010000` as expected by `main.c`. If addresses shift (e.g., after re-running `assign_bd_address`), the readback will fail silently because the PS writes to the wrong physical address — this is the most common cause of a persistent FAIL result after a seemingly clean build.

## Vivado TCL Scripting

### Key Findings

- **Non-project mode vs. project mode**: In non-project mode, Vivado holds the entire design in memory without creating an `.xpr` file. All sources must be read explicitly with `read_vhdl`, `read_xdc`, etc., and the block design must be generated (`generate_target all`) before it can be included in synthesis.
- **Block design in non-project flow**: The block design wrapper must be generated (`make_wrapper -files [get_files *.bd] -top`) before synthesis; otherwise synthesis errors out with a missing top-level module.
- **Batch execution**: `vivado -mode batch -source run.tcl` runs the script and exits automatically. Use `-log` and `-journal` flags to redirect output for CI pipelines.
- **IP Integrator in non-project mode**: As of 2025.1, `create_bd_design`, `add_bd_ip`, and `connect_bd_intf_net` all work in non-project mode. The block design is saved with `write_bd_tcl` for reproducibility.
- **`write_bd_tcl` for portability**: After interactively building a block design in the GUI, use `write_bd_tcl -force recreate_bd.tcl` to export a self-contained recreation script — useful for version control of block designs without committing `.xpr`/`.srcs` trees.

### Code Example

```tcl
# Non-project batch flow for kv260-axi-bram-demo
# Run with: vivado -mode batch -source build_all.tcl

# 1. Create in-memory project context (non-project mode needs a part)
set part "xck26-sfvc784-2LV-c"

# 2. Read sources
read_vhdl  ../vhdl/kv260_top.vhd
read_xdc   ../xdc/kv260_timing.xdc

# 3. Source the block design creation script
source create_bd.tcl

# 4. Generate block design outputs (wrapper + stub)
set bd_file [get_files *.bd]
generate_target all $bd_file
make_wrapper -files $bd_file -top
read_vhdl [glob ./kv260.gen/sources_1/bd/*/hdl/*_wrapper.vhd]

# 5. Synthesize, implement, write bitstream
synth_design   -top kv260_wrapper -part $part
opt_design
place_design
route_design
write_bitstream -force ./kv260.bit

puts "Build complete: kv260.bit"
```

### Relevance to Your Project

Your existing `create_bd.tcl` can be dropped directly into this non-project flow, enabling fully headless builds in CI. The key addition is the `make_wrapper` step — without it the `kv260_top` wrapper is missing and synthesis fails. This flow also makes the exact part string (`xck26-sfvc784-2LV-c`) explicit, preventing Vivado from defaulting to a generic UltraScale+ part.

## Vitis Bare-Metal / Standalone

### Key Findings

- **BSP stdout/stdin assignment**: The BSP `system.mss` must point `stdout` and `stdin` to the UART connected to the KV260's USB-UART bridge. For the K26 SoM this is `psu_uart_1` (115200 baud by default). A wrong UART assignment causes `xil_printf` output to be silently discarded.
- **xil_printf vs. printf**: `xil_printf` is a lightweight, non-buffered print that works without a heap; `printf` requires the heap and newlib. For bare-metal demos, prefer `xil_printf` to avoid linker script sizing issues.
- **Linker script memory regions**: The auto-generated `lscript.ld` places `.text` and `.data` in `psu_ddr_0_MEM_0` (DDR). If you target OCM (On-Chip Memory) for fast-boot scenarios, you must manually edit the `BASE_ADDRESS` and `SIZE` fields for the relevant region.
- **Cache coherency with AXI BRAM**: On Cortex-A53, D-cache is enabled by default in the standalone BSP. Reads from AXI-mapped BRAM may return cached (stale) data. Call `Xil_DCacheFlushRange(addr, len)` before a readback if you observe incorrect values after a write.
- **XSCT for BSP generation**: The Xilinx Software Command-line Tool (`xsct`) can create and build BSPs non-interactively: `xsct -eval "setws ./ws; platform create -name p1 -hw system.xsa; app create -name app1 -template {Hello World}; app build -name app1"`.

### Code Example

```c
/* main.c pattern: cache-safe AXI-BRAM write/readback on Cortex-A53 */
#include "xil_io.h"
#include "xil_cache.h"
#include "xil_printf.h"

#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL
#define TEST_WORDS  16

int verify_bram(uintptr_t base, u32 pattern) {
    /* Write phase */
    for (int i = 0; i < TEST_WORDS; i++)
        Xil_Out32(base + i * 4, pattern ^ (u32)i);

    /* Flush dcache lines covering the BRAM window before readback */
    Xil_DCacheFlushRange(base, TEST_WORDS * 4);

    /* Readback phase */
    for (int i = 0; i < TEST_WORDS; i++) {
        u32 rd = Xil_In32(base + i * 4);
        if (rd != (pattern ^ (u32)i)) {
            xil_printf("FAIL @ 0x%08lX: wrote 0x%08X read 0x%08X\r\n",
                       base + i * 4, pattern ^ (u32)i, rd);
            return -1;
        }
    }
    return 0;
}

int main(void) {
    xil_printf("KV260 AXI-BRAM test\r\n");
    int r0 = verify_bram(BRAM0_BASE, 0xDEADBEEF);
    int r2 = verify_bram(BRAM2_BASE, 0xCAFEBABE);
    xil_printf("%s\r\n", (r0 == 0 && r2 == 0) ? "PASS" : "FAIL");
    return 0;
}
```

### Relevance to Your Project

The `Xil_DCacheFlushRange` call is the single most likely fix if your project prints FAIL despite the Vivado bitstream looking correct. The Cortex-A53 data cache caches the first write to the AXI address and then serves the subsequent `Xil_In32` from cache rather than from BRAM. Adding the flush between write and readback eliminates the false FAIL without requiring cache-off operation.

## XDC Timing Constraints

### Key Findings

- **set_input_delay / set_output_delay**: Both commands express external system-level path delays relative to a reference clock at the device boundary. The value is in nanoseconds and may be positive or negative.
- **-max and -min flags are mandatory for proper STA**: Providing only `-max` allows Vivado to make optimistic assumptions about hold time. Always provide both: `set_input_delay -clock clk -max 5.0 [get_ports ...]` and `set_input_delay -clock clk -min 1.0 [get_ports ...]`.
- **-add_delay for multi-edge clocks**: When constraining DDR signals (captured on both rising and falling edges), use `-clock_fall -add_delay` on a second `set_input_delay` line for the same port; without `-add_delay`, the second line overwrites the first.
- **For AXI BRAM (PS-only master)**: AXI signals between PS and PL on the Zynq UltraScale+ are internal to the SoC; they do **not** require `set_input_delay`/`set_output_delay`. The PS-to-PL AXI interface is constrained automatically by the PS IP's built-in XDC. Only external pins (GPIO, UART, JTAG) need explicit I/O constraints.
- **set_clock_groups -asynchronous**: If PL logic uses a second clock (e.g., a BUFGCE-divided clock) alongside the AXI clock, add `set_clock_groups -asynchronous -group {clk_axi} -group {clk_pl}` to prevent false cross-domain timing paths from failing the build.

### Code Example

```xdc
# kv260_timing.xdc
# PS-generated PL clock (100 MHz typical for KV260 AXI clock)
# The PS IP already creates this constraint; include only if manually
# instantiating a clock buffer on pl_clk0.
create_clock -period 10.000 -name clk_pl [get_ports pl_clk0]

# UART TX/RX pins on KV260 carrier (MIO pins, handled by PS — no XDC needed)
# Only constrain true PL I/O if added.

# Example: external 100 MHz board oscillator on PL (if used)
# create_clock -period 10.000 -name sys_clk [get_ports sys_clk_p]

# Example: constrain an external SPI MISO input
# set_input_delay -clock clk_pl -max 5.0 [get_ports spi_miso]
# set_input_delay -clock clk_pl -min 1.0 [get_ports spi_miso]

# Suppress expected CDC paths if using two internal clocks
# set_clock_groups -asynchronous \
#     -group [get_clocks clk_pl] \
#     -group [get_clocks clk_axi]

# False path on asynchronous reset (active-low PS reset)
set_false_path -from [get_ports pl_resetn0]
```

### Relevance to Your Project

For the current demo (PS master → AXI SmartConnect → AXI BRAM Controller → BRAM), **no external I/O timing constraints are needed** beyond what the Zynq PS IP generates automatically. The most likely timing failure in an expansion of this project is a `set_clock_groups` omission when adding a second PL clock for higher-speed logic alongside the AXI clock.

## Kria KV260 / K26 SoM

### Key Findings

- **Boot mode hierarchy**: K26 is shipped in QSPI32 boot mode with AMD-supplied boot firmware in QSPI flash. For bare-metal development, switch to JTAG boot using the MODE switches on the KV260 carrier (SW1), then load FSBL + PMU FW + bitstream + ELF via XSDB. JTAG boot is the fastest dev cycle; QSPI is for deployment.
- **Four-file JTAG boot sequence**: FSBL (`fsbl.elf`), PMU firmware (`pmufw.elf`), bitstream (`.bit`), and application ELF (`.elf`). Missing or mismatched PMU firmware causes the PS to hang before FSBL hands off to the application.
- **PS GEM3 for Ethernet on KV260**: The KV260 uses PS GEM3 (not GEM0/1/2) for Ethernet. If your bare-metal application ever needs networking, the BSP's `lwIP` must be configured against GEM3 with the correct MIO pin mapping.
- **EMIO for PL-exposed GPIOs**: Any PL GPIO that needs to reach the carrier card connects through EMIO in the PS block design configuration. EMIO pins are numbered starting at GPIO bank 3 (offset 78) on the Zynq UltraScale+ MIO/EMIO map.
- **Power domains**: The K26 SoM has separate power domains for the PS (VCCINT_PS) and PL (VCCINT). Custom carrier cards must sequence these correctly; the KV260 starter kit handles this automatically via its PMIC sequencer.

### Code Example

```tcl
# jtag_boot.tcl — load and run a bare-metal app on KV260 via XSDB
# Run with: xsdb jtag_boot.tcl

connect

# Reset the system and switch to JTAG boot mode
targets -set -nocase -filter {name =~ "PSU"}
mwr 0xffca0038 0x1ff
after 500

# Load Platform Management Unit firmware first
targets -set -nocase -filter {name =~ "MicroBlaze PMU"}
dow pmufw.elf
con
after 200

# Load and run FSBL on APU core 0
targets -set -nocase -filter {name =~ "Cortex-A53 #0"}
rst -processor -clear-registers
dow fsbl.elf
con
after 5000
stop

# Program the PL bitstream
fpga kv260.bit

# Load and run the application ELF
dow hello_world.elf
con

puts "Boot complete — check UART for PASS/FAIL"
disconnect
```

### Relevance to Your Project

This XSDB script replaces manual Vitis GUI debugging sessions. Store it alongside your TCL build scripts and invoke it from a Makefile target (`make jtag_boot`) so rebuilds automatically reflash the board. The `fpga kv260.bit` line programs exactly the bitstream generated by your Vivado flow, ensuring the AXI address map matches what `main.c` expects.

## AMD/Xilinx Tool Updates (Vivado/Vitis 2025.x)

### Key Findings

- **Vivado 2025.1 supports Spartan UltraScale+**: The 2025.1 release added production support for the Spartan UltraScale+ family. The part number for K26 (`xck26-sfvc784-2LV-c`) is unchanged, but the tool's routing algorithms saw updates benefiting dense designs.
- **Block Memory Generator and FIFO now block-design only**: Direct `create_ip` instantiation of `blk_mem_gen` and `fifo_generator` from the IP Catalog has been removed. RTL designs must migrate to XPM macros (`xpm_memory_spram`, `xpm_fifo_sync`). Block designs (IP Integrator) continue to use the GUI IP versions.
- **AXI Interconnect (v2.x) deprecated**: AMD confirmed AXI Interconnect will be removed in a future major release. All new designs should use AXI SmartConnect. The `axi_interconnect` IP still builds in 2025.1 but shows a deprecation warning.
- **Vitis Unified IDE (2025.1)**: Vitis 2025.1 continues the unified IDE transition started in 2022.2. The classic Vitis (Eclipse-based) IDE is still available via `vitis -classic` but is on a sunset path. Bare-metal project creation is now fully supported in the unified flow.
- **XPM migration path for BRAM**: `xpm_memory_spram` is a single-port RAM macro; `xpm_memory_tdpram` is the true-dual-port equivalent that replaces `blk_mem_gen` in dual-port mode.

### Code Example

```vhdl
-- XPM replacement for blk_mem_gen in pure RTL designs (no block design)
-- xpm_memory_spram: single-port, 1024 x 32-bit BRAM

library ieee;
use ieee.std_logic_1164.all;

library xpm;
use xpm.vcomponents.all;

entity bram_xpm is
  port (
    clka  : in  std_logic;
    ena   : in  std_logic;
    wea   : in  std_logic_vector(3 downto 0);
    addra : in  std_logic_vector(9 downto 0);
    dina  : in  std_logic_vector(31 downto 0);
    douta : out std_logic_vector(31 downto 0)
  );
end entity;

architecture rtl of bram_xpm is
begin
  xpm_mem : xpm_memory_spram
    generic map (
      ADDR_WIDTH_A       => 10,
      BYTE_WRITE_WIDTH_A => 8,   -- enables byte-enable (wea is 4 bits)
      MEMORY_SIZE        => 32768, -- bits = 1024 words * 32 bits
      MEMORY_PRIMITIVE   => "block",
      READ_DATA_WIDTH_A  => 32,
      READ_LATENCY_A     => 2,
      WRITE_DATA_WIDTH_A => 32,
      WRITE_MODE_A       => "read_first"
    )
    port map (
      clka   => clka,
      ena    => ena,
      wea    => wea,
      addra  => addra,
      dina   => dina,
      douta  => douta,
      -- unused ports
      injectdbiterra => '0',
      injectsbiterra => '0',
      regcea         => '1',
      rsta           => '0',
      sleep          => '0'
    );
end architecture;
```

### Relevance to Your Project

Your project uses the Block Memory Generator inside a block design (IP Integrator), so the 2025.x change does not break your existing TCL flow. However, if you ever want to move the BRAM instantiation into `kv260_top.vhd` directly (bypassing IP Integrator for a cleaner RTL hierarchy), the XPM macro above is the correct path — `blk_mem_gen` standalone instantiation will fail in Vivado 2025.x.
