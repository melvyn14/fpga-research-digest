## Executive Summary
- **VALID must never depend on READY** — if your VHDL wrapper (`kv260_top.vhd`) has any custom glue logic around the AXI BRAM controllers, double check no signal asserts `S_AXI_AWVALID`/`WVALID`/`ARVALID` conditioned on the corresponding `READY`; this is the single most common cause of silent AXI hangs that look like a "FAIL" or a hang in your PASS/FAIL UART loop.
- **Use the Address Editor's "Auto Assign Address," then verify by hand** — with two AXI BRAM controllers (BRAM0 @ `0xA0000000`, BRAM2 @ `0xA0010000`) in the same block design, Vivado's automation usually places them contiguously; confirm the *Range* column matches each BMG's actual depth so you don't get overlapping or truncated decode windows in `create_bd.tcl`.
- **Vitis 2025.x defaults to the new Unified IDE** — `xil_printf`/UART output and BSP regeneration workflows changed; if you re-run `create_bd.tcl` and re-export the XSA, prefer creating a fresh platform project rather than "Update Hardware Specification," which AMD's own forums report as unreliable for anything beyond trivial AXI changes.
- **GIC/interrupt setup is irrelevant to a pure polled PASS/FAIL demo**, but if you later add an interrupt-driven UART or AXI timeout watchdog, the A53 APU GIC is configured via the standalone BSP, not manually.
- **Timing constraints for a BRAM-only PL design are mostly inherited from the Zynq UltraScale+ PS-PL clock/reset automation** — you generally don't need manual `set_input_delay`/`set_output_delay` for AXI BRAM unless you've added external I/O pins; if you have EMIO/PMOD signals, those need explicit XDC.

## AXI Protocol / AXI-Lite / AXI-Stream
### Key Findings
- AXI4-Lite is single-beat only — no burst, no `AWLEN`/`ARLEN` semantics — which matches a simple register/BRAM read-write demo well, but means each PASS/FAIL test iteration costs one full address+data handshake per word; for the patterned BRAM test this is fine but don't expect throughput.
- The protocol rule that trips up hand-written AXI glue logic: a source must assert `VALID` based only on its own internal state/data availability, **never** conditioned on `READY`. Once `VALID` is asserted it must stay asserted (and the payload must not change) until `READY` arrives. Violating this in either direction can deadlock the bus.
- A related write-channel mistake: assuming the master must wait for `AWREADY` before driving `WVALID`/`WDATA`. AXI explicitly allows (and Xilinx IP often expects) `AW` and `W` channels to be presented at the same time or in either order.
- The official Xilinx AXI BRAM Controller (PG078) is itself a useful reference implementation for how to wire `S_AXI_*` into a single/dual-port BRAM — worth diffing against if `kv260_top.vhd` contains a hand-written controller rather than the IP core.
### Code Example
```vhdl
-- Minimal compliant AXI-Lite write-address handshake (VHDL).
-- VALID is driven purely from internal state; it never looks at READY.
process(clk)
begin
  if rising_edge(clk) then
    if rst = '1' then
      awvalid_r <= '0';
    elsif awvalid_r = '0' and have_pending_write = '1' then
      awvalid_r <= '1';           -- assert based on own state only
    elsif awvalid_r = '1' and s_axi_awready = '1' then
      awvalid_r <= '0';           -- deassert only after READY seen
    end if;
  end if;
end process;
s_axi_awvalid <= awvalid_r;
```
### Relevance to Your Project
If `kv260_top.vhd` wraps the AXI BRAM controllers with any custom AXI-Lite shim (rather than connecting the PS M_AXI_HPM port directly to `axi_bram_ctrl` instances), audit every `*VALID` assignment for a `READY` dependency — this is the most likely root cause if BRAM0 or BRAM2 ever reports FAIL intermittently or the demo hangs instead of printing a result.

## Vivado Block Design / IP Integrator
### Key Findings
- The Address Editor only appears once a bus-master IP (here, the Zynq UltraScale+ MPSoC's `M_AXI_HPM0_FPD`) is in the diagram; "Auto Assign Address" computes offset+range per slave automatically but you should manually confirm no overlap between BRAM0 (`0xA0000000`) and BRAM2 (`0xA0010000`) after any regeneration.
- Connection Automation (the green "Run Connection Automation" links) wires clocks/resets/AXI interfaces using AMD's `bd_rule` definitions (e.g. `xilinx.com:bd_rule:axi4`) — convenient for the first pass, but re-running it after manually rewiring a port can silently re-route connections; check the diagram diff before regenerating in TCL-driven non-project flows.
- For board-level designs, `apply_bd_automation -rule xilinx.com:bd_rule:processing_system7` (or the MPSoC equivalent rule) configures PS pinout/clocking from the board preset in one call — useful to mirror in `create_bd.tcl` if you want the script to remain idempotent across Vivado regenerations.
### Code Example
```tcl
# Typical pattern for adding a second AXI BRAM controller + BMG pair via TCL
set axi_bram_ctrl_1 [create_bd_cell -type ip -vlnv xilinx.com:ip:axi_bram_ctrl:4.1 axi_bram_ctrl_1]
set_property -dict [list CONFIG.SINGLE_PORT_BRAM {1}] $axi_bram_ctrl_1

set blk_mem_gen_1 [create_bd_cell -type ip -vlnv xilinx.com:ip:blk_mem_gen:8.4 blk_mem_gen_1]

connect_bd_intf_net [get_bd_intf_pins axi_bram_ctrl_1/BRAM_PORTA] \
                     [get_bd_intf_pins blk_mem_gen_1/BRAM_PORTA]

apply_bd_automation -rule xilinx.com:bd_rule:axi4 -config { \
    Master "/zynq_ultra_ps_e_0/M_AXI_HPM0_FPD" \
    Clk "Auto" } [get_bd_intf_pins axi_bram_ctrl_1/S_AXI]

# After automation, re-check (don't blindly trust) the address map:
assign_bd_address [get_bd_addr_segs axi_bram_ctrl_1/S_AXI/Mem0]
```
### Relevance to Your Project
This is essentially the pattern your `create_bd.tcl` already follows for BRAM0/BRAM2. If you add a third memory or change BRAM depth, re-run `assign_bd_address` explicitly and `validate_bd_design` rather than relying solely on automation, since auto-assigned ranges can shift previously-fixed offsets your `main.c` hardcodes (`0xA0000000`, `0xA0010000`).

## Vivado TCL Scripting
### Key Findings
- Non-project ("in-memory") batch mode is the standard pattern for CI/headless builds: `read_vhdl`/`read_verilog` + `read_xdc`, then `synth_design -top <top> -part <part>`, `opt_design`, `place_design`, `route_design`, `write_bitstream` — no `.xpr` project file is created, which keeps repo-checked-in TCL scripts as the single source of truth (matches a `tcl/` directory workflow well).
- `apply_bd_automation` and `create_bd_cell` are the two workhorses for scripting a block design from scratch; capturing the *exact* sequence Vivado's GUI generates is best done by building once in the GUI then using **File → Export → Export Block Design** to get a faithful TCL baseline, then hand-trimming project-specific paths.
- Re-running a `create_bd.tcl` script against an existing `.xpr`/checkpoint can fail if cells already exist; idempotent scripts typically guard with `if {[get_bd_cells -quiet <name>] eq ""} { ... }` or simply delete and recreate the BD at the top of the script.
### Code Example
```tcl
# Non-project batch build skeleton suitable for a kv260/tcl/ directory
create_project -in_memory -part xczu5eg-sfvc784-1-e
read_vhdl -library kv260_top [glob ./vhdl/*.vhd]
read_xdc ./xdc/kv260_top.xdc
synth_design -top kv260_top -part xczu5eg-sfvc784-1-e
opt_design
place_design
route_design
write_bitstream -force ./build/kv260_top.bit
```
### Relevance to Your Project
Since the repo already separates `tcl/`, `vhdl/`, and `src/` (per the project brief), consider adding a single `build_all.tcl` non-project script that sources `create_bd.tcl`, wraps it (`make_wrapper -files ... -top`), and runs the synth/place/route/bitstream sequence above — this gives a reproducible, GUI-free build path that's easy to re-run after any AXI BRAM address change.

## Vitis Bare-Metal / Standalone
### Key Findings
- The standalone BSP auto-generates a linker script placing your app in DDR by default; you can override base address/size by editing the BSP's linker script settings if you need the app footprint constrained (relevant for minimal bare-metal demos that avoid a full DDR controller bring-up).
- `xil_printf` is the lightweight, non-reentrant printf used in nearly all bare-metal Xilinx examples specifically because full `printf` pulls in a much larger newlib footprint — appropriate for a UART PASS/FAIL reporter.
- UART output defaults to the physical UART (USB-UART on KV260 carrier) but can be switched to JTAG virtual UART in the BSP settings — useful fallback if the USB-UART isn't enumerating.
- After any hardware (XSA) change, AMD's own community guidance is split: "Update Hardware Specification" on the platform project sometimes fails to propagate AXI peripheral/address changes correctly; the more reliable path is deleting and recreating the platform project from the fresh XSA, then regenerating the BSP and app project.
### Code Example
```c
// Bare-metal PASS/FAIL pattern test, mirroring the project's two-BRAM check
#include "xil_io.h"
#include "xil_printf.h"

#define BRAM0_BASE 0xA0000000U
#define BRAM2_BASE 0xA0010000U
#define TEST_WORDS 16

int test_bram(const char *name, UINTPTR base) {
    int fail = 0;
    for (int i = 0; i < TEST_WORDS; i++) {
        u32 pattern = 0xA5A50000U | i;
        Xil_Out32(base + (i * 4), pattern);
    }
    for (int i = 0; i < TEST_WORDS; i++) {
        u32 expected = 0xA5A50000U | i;
        u32 actual = Xil_In32(base + (i * 4));
        if (actual != expected) {
            xil_printf("%s word %d MISMATCH: wrote 0x%08x read 0x%08x\r\n",
                       name, i, expected, actual);
            fail = 1;
        }
    }
    xil_printf("%s: %s\r\n", name, fail ? "FAIL" : "PASS");
    return fail;
}

int main(void) {
    int rc = 0;
    rc |= test_bram("BRAM0", BRAM0_BASE);
    rc |= test_bram("BRAM2", BRAM2_BASE);
    xil_printf("Overall: %s\r\n", rc ? "FAIL" : "PASS");
    return rc;
}
```
### Relevance to Your Project
This mirrors the described `main.c` structure almost exactly (write pattern, read back, PASS/FAIL over UART for both BRAMs). If the real `main.c` differs, the main risk areas to check are: (1) whether `Xil_Out32`/`Xil_In32` are used directly vs. a cached pointer dereference (AXI BRAM via PS is non-cacheable by default region attributes, but confirm the MMU table entry for the `0xA000_0000` range is marked Device/non-cacheable in the BSP-generated translation table), and (2) that the linker script's app region doesn't overlap the AXI BRAM address range (it shouldn't, since BRAM is memory-mapped PL, not DDR).

## XDC Timing Constraints
### Key Findings
- For pure PS-to-PL AXI designs with no external PL-side I/O (your case: BRAM lives entirely inside the PL via AXI, no top-level pins), you typically don't need hand-written `set_input_delay`/`set_output_delay` — clocking and reset come from the PS via `clk_wizard`/`zynq_ultra_ps_e` automation and Vivado infers timing from the PS-PL interface IP automatically.
- The general rule when you *do* have external I/O: `set_output_delay` should be sized off the **setup time of the downstream device** (e.g., a 10 ns period domain with 4 ns external setup → `set_output_delay -max 4.0`), while `set_input_delay -max` should be sized off the **upstream device's clock-to-Q** delay.
- If your design has any clocks that should not be timed against each other (e.g., a debug/free-running clock vs. the AXI fabric clock), use `set_clock_groups -asynchronous` rather than leaving them unconstrained — Vivado will otherwise attempt (and may fail) to relate them.
### Code Example
```tcl
# Only needed if EMIO/PMOD signals are added later (e.g. external LED/button via PL)
create_clock -period 10.000 -name sys_clk [get_ports sys_clk_p]
set_input_delay  -clock sys_clk -max 2.000 [get_ports btn_in]
set_input_delay  -clock sys_clk -min 0.500 [get_ports btn_in]
set_output_delay -clock sys_clk -max 3.000 [get_ports led_out]
set_output_delay -clock sys_clk -min 0.300 [get_ports led_out]

# If a secondary free-running debug clock exists and shares no logic:
set_clock_groups -asynchronous \
  -group [get_clocks sys_clk] \
  -group [get_clocks dbg_clk]
```
### Relevance to Your Project
Since BRAM0/BRAM2 are accessed purely over internal AXI from the PS, the current `kv260_top.vhd`/XDC likely needs little beyond the board's default PS clock/reset constraints. Only add explicit `set_input_delay`/`set_output_delay` if you extend the demo with real PL-side I/O (e.g., a GPIO LED to visually show PASS/FAIL alongside the UART print).

## Kria KV260 / K26 SoM
### Key Findings
- The K26 SOM supports JTAG, SD, and QSPI boot modes, selected via `MODE[3:0]` pins on the carrier card; KV260 starter kits ship preset to QSPI32 boot mode by default — relevant if you're booting your bare-metal ELF via JTAG/Vitis debug vs. flashing to QSPI/SD for standalone boot.
- PS MIO signals live on bank 501 on the K26; the carrier-card-specific pin mappings (including EMIO routes, e.g. fan control) are defined in the K26 SOM XDC files provided with the board support files — important if your design ever needs an EMIO-routed signal beyond the two AXI BRAMs.
- Vivado board files for the K26/KV260 automate PS configuration (DDR, clocking, MIO) when you instantiate the Zynq UltraScale+ MPSoC IP with the board preset selected, which is almost certainly what `create_bd.tcl` relies on via `apply_bd_automation` for the PS block.
- VCCO for sideband/low-speed signals on the K26 connector is 1.8V — relevant only if adding custom carrier-card I/O.
### Code Example
```tcl
# Applying the KV260 board preset to the PS in a non-project TCL flow
set_property board_part xilinx.com:kv260_som:part0:1.4 [current_project]
set zynq_ultra_ps_e_0 [create_bd_cell -type ip -vlnv xilinx.com:ip:zynq_ultra_ps_e:3.5 zynq_ultra_ps_e_0]
apply_bd_automation -rule xilinx.com:bd_rule:zynq_ultra_ps_e \
    -config {apply_board_preset "1"} [get_bd_cells zynq_ultra_ps_e_0]
```
### Relevance to Your Project
If `create_bd.tcl` doesn't already apply the board preset, manually-set MIO/DDR/clocking parameters can drift from what the K26 SOM actually requires, risking boot issues distinct from the AXI BRAM logic itself. Worth confirming the PS configuration block in `create_bd.tcl` references the KV260 board part rather than a generic ZU5EG part-only config.

## AMD/Xilinx Tool Updates (2025.x)
### Key Findings
- Vivado 2025.1 added a fully customizable RTL-based AXI Switch IP (bridges between different AXI interface types/widths) and a new Pblock planner — neither is strictly needed for a 2-BRAM demo but the AXI Switch IP could simplify future expansion if more AXI masters/slaves are added.
- Vivado 2025.2 adds simplified AXI connections between SystemVerilog instances and automatic wrapper creation for AMD IP/block designs, plus an "ultra-low-area" STRATEGY mode for AXI Switch/SmartConnect IP.
- Vitis 2025.2 makes the new Unified IDE the default and **deprecates the Classic Vitis IDE** — if instructions or muscle memory still reference "Vitis Classic" project creation, expect menu/workflow changes; bare-metal app/platform project creation flows moved into the unified, VS Code-like interface.
- AMD's official "Vivado What's New" and "Vitis What's New" pages are the canonical source for per-release known issues — worth bookmarking for the project's specific 2025.1 toolchain version pin.
### Code Example
```tcl
# Confirming installed tool version matches project pin (useful in CI/non-project scripts)

if {[version -short] ne "2025.1"} {
    puts "WARNING: expected Vivado 2025.1, found [version -short]"

```
### Relevance to Your Project
Since the project explicitly pins Vivado/Vitis 2025.1, a version-check guard like the snippet above at the top of `create_bd.tcl` would catch accidental builds against a newer/older installed toolchain (e.g., 2025.2's Unified-IDE-only Vitis) before they produce subtly incompatible BSPs or XSA files.
