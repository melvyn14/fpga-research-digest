# FPGA Research Digest - 2026-10-12

## Executive Summary

- **AXI-Lite VALID/READY deadlock**: The sender must assert VALID independently of READY — waiting for READY before raising VALID can deadlock. The KV260 bare-metal write loop in main.c must never gate AWVALID on ARREADY or BREADY.
- **Address Editor auto-assign**: After adding any IP to the block design in Vivado 2025.1, always run "Assign All" in the Address Editor (or `assign_bd_address` in TCL) before generating the bitstream — unmapped slaves silently break PS-to-PL reads.
- **xparameters.h is the ground truth**: BRAM base addresses (0xA0000000, 0xA0010000 in your project) come from Vivado's address editor and are emitted into `xparameters.h` by Vitis BSP generation. Never hard-code addresses in main.c without verifying them against the generated header.
- **Vivado 2025.1 ships a new AXI Switch IP**: A fully customizable RTL-based bridge between different AXI interface types and widths — useful if you later need to fan out the PS AXI GP port to more than two BRAMs.
- **Linker script DDR placement**: Vitis-generated linker scripts can place `.data` / `.bss` in the wrong memory region for Cortex-A53 bare-metal. Verify that all sections target DDR (0x00000000 for the KV260 PS DDR window) to avoid hard faults before the UART prints anything.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- **VALID independence rule**: The AXI spec forbids a master from waiting for READY before asserting VALID. Doing so can create a cycle — slave asserts READY only after seeing VALID, master asserts VALID only after seeing READY → permanent stall. Violations are invisible to synthesis and must be caught with a simulation protocol checker.
- **READY can drop after VALID**: READY is not sticky; the slave may deassert it between beats. VALID, once raised, must stay asserted until the handshake completes (both VALID and READY high on the same rising ACLK edge).
- **Permanently-high AWREADY is a trap**: Tying AWREADY or WREADY high is a common shortcut. It passes basic tests but breaks under back-pressure because BVALID acknowledgement can be missed if the master proceeds to the next write before receiving BRESP.
- **PS-to-PL GP port**: The Zynq UltraScale+ PS exposes M_AXI_HPM0_LPD and M_AXI_HPM0_FPD as general-purpose AXI masters into the PL. For the KV260, BRAM0 at 0xA0000000 and BRAM2 at 0xA0010000 sit in the PL address window — confirm exact ranges in the Vivado Address Editor for your build.
- **AXI-Stream vs AXI-Lite for BRAM**: AXI-Lite gives direct random-access to BRAM registers and is the right choice for pattern write/read-back at known offsets. AXI-Stream (+ AXI DMA) is better for burst-mode bulk data movement to/from DDR but adds driver complexity.

### Code Example

```c
/* Bare-metal AXI-Lite write + read-back with BRESP check via Xil_Out32/Xil_In32 */
#include "xil_io.h"
#include "xparameters.h"

#define BRAM0_BASE  XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR   /* e.g. 0xA0000000 */
#define BRAM2_BASE  XPAR_AXI_BRAM_CTRL_1_S_AXI_BASEADDR   /* e.g. 0xA0010000 */
#define PATTERN     0xDEADBEEFU

void axi_bram_test(void) {
    Xil_Out32(BRAM0_BASE + 0x00, PATTERN);
    Xil_Out32(BRAM2_BASE + 0x00, ~PATTERN);

    u32 r0 = Xil_In32(BRAM0_BASE + 0x00);
    u32 r2 = Xil_In32(BRAM2_BASE + 0x00);

    xil_printf("BRAM0: %s (0x%08X)\r\n", (r0 == PATTERN)  ? "PASS" : "FAIL", r0);
    xil_printf("BRAM2: %s (0x%08X)\r\n", (r2 == ~PATTERN) ? "PASS" : "FAIL", r2);
}
```

### Relevance to Your Project

Your main.c writes `0xDEADBEEF` patterns over AXI-Lite to BRAM0 (0xA0000000) and BRAM2 (0xA0010000) and prints PASS/FAIL. The snippet above mirrors that intent and shows how to use `xparameters.h` macros instead of literal addresses — insulating the test code from any future address-editor reassignment in Vivado 2025.1.

## Vivado Block Design / IP Integrator

### Key Findings

- **Block Automation vs Connection Automation**: "Block Automation" runs when you instantiate a Zynq PS and configures its DDR and fixed I/O. "Connection Automation" runs on individual IP blocks and auto-wires their AXI slave ports through an AXI Interconnect and Proc Sys Reset to the PS. Both must be run (or replicated in TCL) after adding each IP.
- **Address Editor auto-assign**: If any slave's address segment remains "Unmapped", Vivado will warn at validate_bd_design but may still generate a bitstream. The PS will address-fault on those slaves at runtime. Use Assign All or right-click → Auto-Assign Address as a final step before Generate Bitstream.
- **Editing Addresses (UG994 2025.1)**: You must first assign a path before the base address and range fields become editable. Toolbar buttons "Assign All" and "Unassign All" are in the Address Editor tab — it only appears when a bus master IP is present.
- **Validation errors**: Running `validate_bd_design` in Tcl (or Validate Design in the GUI) before generating outputs catches unconnected ports, unassigned addresses, and clock-domain inconsistencies. Do not skip it in automated flows.
- **Regeneration after IP upgrade**: When upgrading IP between Vivado releases, run `upgrade_bd_cells [get_bd_cells *]` followed by `validate_bd_design` before re-generating products.

### Code Example

```tcl
# Minimal Vivado Tcl: add second AXI BRAM controller and assign address
create_bd_cell -type ip -vlnv xilinx.com:ip:axi_bram_ctrl:4.1 axi_bram_ctrl_1
create_bd_cell -type ip -vlnv xilinx.com:ip:blk_mem_gen:8.4   blk_mem_gen_1
set_property CONFIG.Memory_Type {True_Dual_Port_RAM} [get_bd_cells blk_mem_gen_1]
connect_bd_intf_net [get_bd_intf_pins axi_bram_ctrl_1/BRAM_PORTA] \
                    [get_bd_intf_pins blk_mem_gen_1/BRAM_PORTA]
connect_bd_intf_net [get_bd_intf_pins axi_bram_ctrl_1/BRAM_PORTB] \
                    [get_bd_intf_pins blk_mem_gen_1/BRAM_PORTB]
# Wire AXI slave to interconnect output port (adjust M_AXI_GP0 port number)
connect_bd_intf_net [get_bd_intf_pins axi_interconnect_0/M01_AXI] \
                    [get_bd_intf_pins axi_bram_ctrl_1/S_AXI]
# Assign addresses
assign_bd_address [get_bd_addr_segs axi_bram_ctrl_1/S_AXI/Mem0]
set_property offset 0xA0010000 [get_bd_addr_segs {ps_e/Data/SEG_axi_bram_ctrl_1_Mem0}]
set_property range  64K        [get_bd_addr_segs {ps_e/Data/SEG_axi_bram_ctrl_1_Mem0}]
validate_bd_design
```

### Relevance to Your Project

Your create_bd.tcl already creates BRAM0 at 0xA0000000. The snippet above shows the pattern to extend to BRAM2 at 0xA0010000, matching your project's two-BRAM topology. The `assign_bd_address` + `set_property offset/range` sequence is the Tcl equivalent of editing rows in the Address Editor GUI.

## Vivado TCL Scripting

### Key Findings

- **Non-project (batch) mode**: Launch with `vivado -mode batch -source build.tcl` for fully automated flows — no `.xpr` file is written. Sources are loaded with `read_vhdl`, `read_xdc`, and `read_bd`; IP checkpoints are consumed from existing `.dcp` files when available.
- **Non-project vs project mode for BD**: When working with block designs in non-project mode, `read_bd` loads an existing `.bd` file but does NOT regenerate IP products. Call `generate_target all [get_files *.bd]` explicitly before `synth_design`.
- **Build step sequence**: `synth_design -top <top> -part <part>` → `opt_design` → `place_design` → `route_design` → `write_bitstream -force <output>.bit`. Skip `opt_design` only for tiny designs where runtime matters.
- **updatemem**: After bitstream generation, embed the ELF into the bitstream with `updatemem -meminfo <mmmi> -data <elf> -bit <bit> -proc <proc_path> -out <output>.bit`. This produces a combined programming file.
- **Part specification**: In non-project mode the part is not stored with the block design. Set it explicitly: `set_part xck26-sfvc784-2LV-c` for the KV260's K26 SoM.

### Code Example

```tcl
# Minimal non-project build script for KV260 AXI-BRAM demo
set part "xck26-sfvc784-2LV-c"
set bd_file   [file normalize "./kv260_claude/kv260/bd/kv260_bd.bd"]
set xdc_file  [file normalize "./kv260_claude/kv260/xdc/kv260_top.xdc"]
set vhdl_file [file normalize "./kv260_claude/kv260/vhdl/kv260_top.vhd"]
set elf_file  [file normalize "./kv260_claude/kv260/build/kv260.elf"]

set_part $part
set_property target_language VHDL [current_project]

read_vhdl $vhdl_file
read_bd   $bd_file
read_xdc  $xdc_file

generate_target all [get_files $bd_file]
make_wrapper -files [get_files $bd_file] -top
read_vhdl [glob ./kv260_claude/kv260/bd/hdl/*.vhd]

synth_design  -top kv260_top -part $part
opt_design
place_design
route_design
write_bitstream -force ./build/kv260.bit

# Embed ELF
updatemem -meminfo ./build/kv260.mmi \
          -data    $elf_file \
          -bit     ./build/kv260.bit \
          -proc    kv260_top_i/zynq_ultra_ps_e_0 \
          -out     ./build/kv260_with_elf.bit
```

### Relevance to Your Project

Your project already uses `create_bd.tcl`. This script shows how to wrap the full flow — from reading sources to writing the final bitstream with embedded ELF — in a single file that CI or a cron job can invoke with `vivado -mode batch -source build.tcl`, enabling reproducible automated builds without opening the Vivado GUI.

## Vitis Bare-Metal / Standalone

### Key Findings

- **xil_printf vs printf**: `xil_printf` is a lightweight implementation that avoids pulling in the full `libc` formatted I/O stack. It supports `%d`, `%x`, `%s`, `%c` but not `%f`. For a PASS/FAIL UART loop this is sufficient and produces smaller binaries. Use `print()` for literal strings.
- **BSP stdout selection**: The `stdin`/`stdout` peripheral is selected in the BSP settings (MSS file under `standalone_domain → stdin/stdout`). If the UART doesn't appear in the dropdown, re-export the hardware XSA from Vivado and reimport it — the UART IP must be present in the XSA.
- **Linker script DDR placement**: Vitis generates a default linker script placing all sections in OCM or the first detected memory region. For Cortex-A53 bare-metal on KV260, ensure all sections (`.text`, `.data`, `.bss`, `.heap`, `.stack`) target `ps_ddr_0` (DDR starting at 0x00000000) in the generated `lscript.ld`. Misplacement causes a hardfault before `main()` is reached.
- **Cache coherency with AXI**: Cortex-A53 data cache is enabled by default in the standalone BSP. After writing to BRAM via AXI-Lite (which is coherent at the PS side through the interconnect), reads back should be consistent. However, if you later use AXI DMA with DDR, flush the D-cache with `Xil_DCacheFlushRange()` before starting a DMA transfer.
- **BRAM driver**: The standalone BRAM driver (`xbram`) is located in `XilinxProcessorIPLib/drivers/bram_v*`. For basic AXI-Lite access, `Xil_Out32` / `Xil_In32` is simpler and sufficient; the full `xbram` driver adds ECC support.

### Code Example

```c
/* lscript.ld snippet — force all sections into DDR on KV260 */
/*
MEMORY
{
   ps_ddr_0_MEM_0 : ORIGIN = 0x0, LENGTH = 0x80000000
   psu_ocm_ram_0  : ORIGIN = 0xFFFC0000, LENGTH = 0x40000
}

SECTIONS
{
   .text   : { *(.text)   } > ps_ddr_0_MEM_0
   .data   : { *(.data)   } > ps_ddr_0_MEM_0
   .bss    : { *(.bss)    } > ps_ddr_0_MEM_0
   .heap   : { _heap_start = .; . += HEAP_SIZE;  _heap_end = .;  } > ps_ddr_0_MEM_0
   .stack  : { _stack_end = .; . += STACK_SIZE; _stack = .;      } > ps_ddr_0_MEM_0
}
*/

/* main.c — basic AXI-BRAM write/readback using xil_printf */
#include "xil_io.h"
#include "xil_printf.h"
#include "xparameters.h"

#define BRAM0  0xA0000000UL
#define BRAM2  0xA0010000UL

int main(void) {
    xil_printf("KV260 AXI-BRAM Demo\r\n");

    for (u32 i = 0; i < 4; i++) {
        Xil_Out32(BRAM0 + i*4, 0xA0000000 + i);
        Xil_Out32(BRAM2 + i*4, 0xB0000000 + i);
    }
    int pass = 1;
    for (u32 i = 0; i < 4; i++) {
        if (Xil_In32(BRAM0 + i*4) != 0xA0000000 + i) pass = 0;
        if (Xil_In32(BRAM2 + i*4) != 0xB0000000 + i) pass = 0;
    }
    xil_printf("Result: %s\r\n", pass ? "PASS" : "FAIL");
    return 0;
}
```

### Relevance to Your Project

Your project's main.c uses `xil_printf` for PASS/FAIL output over USB-UART. The linker script fragment ensures the binary loads into DDR so execution reaches `main()`, and the cache notes apply if you later extend the demo to use AXI DMA for bulk transfers to DDR.

## XDC Timing Constraints

### Key Findings

- **Recommended constraint order (UG903 2025.2)**: (1) Primary clocks → (2) Generated clocks → (3) Clock groups → (4) Bus skew → (5) I/O delays (`set_input_delay` / `set_output_delay`) → (6) Timing exceptions (false paths, multicycle paths). Deviating from this order can cause runtime issues and unexpected exception precedence.
- **Clock groups vs false paths**: `set_clock_groups -asynchronous` is bidirectional and overrides all other exceptions between those groups — it is the strongest constraint. `set_false_path` is one-directional. For PS-to-PL clock domain crossings (e.g., PL fabric clock driven by `pl_clk0` vs an external differential input), use `set_clock_groups`.
- **set_input/output_delay for AXI BRAM**: The AXI BRAM Controller's ports are entirely internal to the PL in a typical KV260 design — no external I/O path exists. Therefore, `set_input_delay` / `set_output_delay` are not needed for the BRAM data paths; Vivado's internal timing model covers them. You only need I/O constraints for signals that cross the device boundary (PMOD, FMC, etc.).
- **Specificity precedence**: More specific constraints override less specific ones of the same type. Scope false paths to exact cell pins rather than whole clock domains to avoid accidentally disabling timing on paths you care about.
- **False path for PS-PL crossing**: The PS-to-PL AXI interface is already constrained by the Zynq PS block; you do not need to add `set_false_path` for the M_AXI_HPM0 or M_AXI_HPM1 paths.

### Code Example

```tcl
# Minimal XDC for KV260 bare-metal AXI-BRAM demo
# pl_clk0 is 100 MHz from the PS (auto-generated by Vivado for Zynq PS IP)
# No external I/O → no set_input_delay / set_output_delay needed for BRAM paths

# If you add an async reset from an external button:
set_false_path -from [get_ports ext_reset_n]

# If PL uses a second independent clock (e.g. from a PMOD oscillator):
# create_clock -period 20.000 -name clk_ext [get_ports ext_clk]
# set_clock_groups -asynchronous -group [get_clocks clk_pl_0] \
#                                -group [get_clocks clk_ext]

# Keep constraint ordering canonical:
# 1. Clocks (auto-created by PS block, no manual create_clock needed for pl_clk0)
# 2. Clock groups (only if second domain)
# 3. I/O delays (none for internal BRAM paths)
# 4. Exceptions
set_false_path -from [get_ports ext_reset_n]
```

### Relevance to Your Project

Your kv260_top.vhd wrapper exposes only the PS and PL clock/reset — there are no external data I/O ports in the AXI-BRAM demo. This means your XDC can remain minimal. The main constraint needed is a false path for any external reset button, and a clock group constraint if you ever add a second PL clock domain.

## Kria KV260 / K26 SoM

### Key Findings

- **Boot mode is hardwired**: The KV260 carrier card hardwires QSPI boot mode. The production boot chain is: FSBL from QSPI → U-Boot → Linux. For bare-metal development, you bypass this by programming the bitstream + ELF directly over JTAG using Vivado Hardware Manager or `xsdb`, without overwriting QSPI.
- **JTAG access**: The K26 SoM routes JTAG through an on-board FTDI chip connected via USB. An external JTAG connector is also available on the KV260 carrier for use with an external probe (Xilinx Platform Cable, J-Link, etc.). For bare-metal bring-up, the USB JTAG path is sufficient.
- **PL address window**: On the Zynq UltraScale+ MPSoC, the PS General Purpose AXI master ports (M_AXI_HPM0_LPD, M_AXI_HPM0_FPD) map into the LPD and FPD PL regions respectively. The exact base addresses for PL slaves are set in Vivado's Address Editor and emitted into `xparameters.h`. For the KV260 demo, BRAM0 = 0xA0000000 and BRAM2 = 0xA0010000 are in the LPD PL window.
- **K26 SoM hardware**: The K26 carries a Zynq UltraScale+ MPSoC (xck26), 4 GB DDR4, 512 Mb QSPI flash, eMMC (production variant), and TPM 2.0. The KV260 carrier breaks out MIPI CSI-2, HDMI, USB, Ethernet, and PMOD connectors from the SoM's MIO/EMIO pins.
- **MIO allocation**: MIO[0:25] and MIO[46:77] are allocated to PS peripherals (UART0 on MIO[10:11] for the KV260 USB-UART, I2C, etc.). EMIO[0:95] fan out to the PL and can be connected to user logic in the block design.

### Code Example

```tcl
# XSDB (Xilinx System Debugger) script for bare-metal JTAG programming on KV260
# Run from Vitis or standalone: xsdb program_kv260.tcl

connect
targets -set -nocase -filter {name =~ "*PSU*"}

# Initialize PS (runs FSBL-like init to configure DDR)
source ./xsdb_init/psu_init.tcl
psu_init

# Program the bitstream
targets -set -nocase -filter {name =~ "*PL*"}
fpga -file ./build/kv260_with_elf.bit

# Run ELF on APU Cortex-A53 core 0
targets -set -nocase -filter {name =~ "*A53*#0*"}
rst -processor
dow ./build/kv260.elf
con

puts "KV260 programmed and running"
disconnect
```

### Relevance to Your Project

This XSDB script matches the KV260 bare-metal development flow — loading the combined bitstream+ELF generated by `updatemem` and starting the Cortex-A53. The `psu_init` step is critical: without it, DDR is unconfigured and the ELF cannot be loaded into RAM. The UART output should appear on USB-UART immediately after `con`.

## AMD/Xilinx Tool Updates (Vivado/Vitis 2025.x)

### Key Findings

- **New in Vivado 2025.1**: Added Versal AI Edge Series Gen 2 and Versal Prime Series Gen 2 device support. Added Spartan UltraScale+ family support. Introduced a **new AXI Switch IP** — described as "a fully customizable RTL-based IP which serves as a bridge between different AXI interface types and widths." Selective device installer reduces download size.
- **New in Vitis 2025.1 (embedded/open-source)**: Linux kernel upgraded to 6.12. SDTGen is now an independent tool (no longer requires XSCT). Zephyr early-access drivers available. Additional compiler support in the Vitis Unified IDE. The older `.tcl`/`.mdd` driver files (used by the pre-2022 build flow) are now explicitly marked as deprecated and will be removed in a future release.
- **Vitis 2025.2**: Adds AI Engine support for Versal Gen 2, mixed-precision NPU support, and more AIE columns. For Zynq UltraScale+ work like the KV260 project, 2025.1 is the stable target — the 2025.2 additions are Versal-focused.
- **Deprecation watch**: The `*.mdd` / `*.tcl` driver build flow is deprecated. If your project uses a Makefile that invokes `hsi` or the older `xsdk` CLI, migrate to the Vitis Unified IDE flow or the new CMake-based embedded build system introduced in 2022.x.
- **Documentation version**: Vivado UG892 and UG994 are current at 2026.1 / 2025.2 respectively on docs.amd.com. When searching AMD documentation, use version suffixes (`/2025.1-English/`) to pin results to your tool release and avoid reading 2026.x behavior into a 2025.1 installation.
