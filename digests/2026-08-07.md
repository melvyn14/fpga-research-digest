# FPGA Research Digest - 2026-08-07

## Executive Summary

- **BREAKING (2025.1/2025.2)**: The Embedded Memory Generator (BRAM) and FIFO IPs are no longer available for direct instantiation from the Vivado IP Catalog — they must now be integrated via block design/IP Integrator. This directly affects how you add BRAMs to the KV260 AXI-BRAM demo going forward.
- **AXI deadlock prevention**: Your AXI-Lite slave must gate write-readiness as `awvalid && wvalid && (!BVALID || BREADY)` to prevent the write-response channel from blocking new transactions — a common bare-metal hang cause.
- **KV260 bare-metal boot**: For JTAG debugging use `PSU_INIT.TCL` (not FSBL) and remove the SD card; for persistent deployment, program the bitstream + ELF into QSPI using XSDB.
- **Vivado 2025.2 AXI SmartConnect**: New `STRATEGY` parameter enables ultra-low-area mode for AXI Switch and SmartConnect IP — worth enabling in the KV260 design to reduce PL resource overhead.
- **Non-project TCL batch mode**: Run `vivado -nolog -nojournal -mode batch -source create_bd.tcl` to fully automate block design regeneration — critical for CI/CD on the demo repo.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- **VALID/READY contract**: Once VALID is asserted by the initiator it **cannot** be deasserted until the corresponding READY is received. Violating this causes protocol errors detectable with Vivado's AXI Protocol Checker IP.
- **Backpressure on BREADY**: When the master holds `BREADY` low after a write, the slave must also deassert `AWREADY` and `WREADY`. This is the most commonly missed case in bare-metal AXI-Lite slave implementations.
- **Write enable timing bug**: The Xilinx AXI BRAM Controller has a documented simulation issue where it can assert the BRAM write enable one clock cycle early, writing an extra word to the previous address. Root cause: `BRAM Enable` not properly gating the extra clock cycle.
- **Deadlock-safe write readiness formula** (from ZipCPU's EasyAxil analysis): combine address and data channel validity with response channel availability.
- **AXI-Stream vs AXI-Lite**: AXI-Lite uses a full address/data/response channel set (5 channels); AXI-Stream is purely TDATA/TVALID/TREADY with optional TLAST — do not confuse them when extending this demo with streaming PL accelerators.

### Code Example

```vhdl
-- Deadlock-safe AXI-Lite write acceptance in VHDL
-- Prevents the write response channel from blocking new address/data
process(S_AXI_ACLK)
begin
  if rising_edge(S_AXI_ACLK) then
    if S_AXI_ARESETN = '0' then
      axil_aw_ready <= '0';
      axil_w_ready  <= '0';
    else
      -- Only accept new write addr+data when response channel is free or master is ready
      if (S_AXI_AWVALID = '1' and S_AXI_WVALID = '1') and
         (S_AXI_BVALID = '0' or S_AXI_BREADY = '1') then
        axil_aw_ready <= '1';
        axil_w_ready  <= '1';
      else
        axil_aw_ready <= '0';
        axil_w_ready  <= '0';
      end if;
    end if;
  end if;
end process;
```

### Relevance to Your Project

Your demo writes patterns to BRAM0 (`0xA0000000`) and BRAM2 (`0xA0010000`) from the Cortex-A53 over AXI-Lite. If the VHDL top-level bridges AXI-Lite to the Block Memory Generator, the write-enable timing bug described above can cause the first write to land one address early — producing a spurious FAIL on the readback check even though the Cortex-A53 issued the correct transaction. Verify your simulation waveforms for `bram_en` vs `bram_we` alignment.

## Vivado Block Design / IP Integrator

### Key Findings

- **Connection automation**: `Run Connection Automation` in IP Integrator automatically wires AXI clock/reset pins and inserts an AXI Interconnect or SmartConnect when a new slave is added — always run it after adding each IP rather than wiring manually.
- **Address Editor**: Use **Auto Assign Address** after adding any slave IP. The Address Editor only activates when a bus master (Zynq PS, MicroBlaze) is present in the design.
- **Naming constraint**: Never use spaces in block design names or directory paths — Vivado silently fails TCL export and regeneration with spaces present.
- **BRAM change in 2025.x**: Block Memory Generator (BMG) and FIFO IPs must now be added through the block design IP catalog rather than standalone IP instantiation — direct catalog instantiation is removed in 2025.1+.
- **apply_bd_automation TCL command**: Automates connection rules programmatically; used in `create_bd.tcl` scripts after `create_bd_cell` calls.

### Code Example

```tcl
# After creating PS and BRAM controller cells, automate connections
apply_bd_automation -rule xilinx.com:bd_rule:axi4 \
  -config { \
    Clk_master {/zynq_ultra_ps_e_0/pl_clk0} \
    Clk_slave  {Auto} \
    Clk_xbar   {Auto} \
    Master     {/zynq_ultra_ps_e_0/M_AXI_HPM0_FPD} \
    Slave      {/axi_bram_ctrl_0/S_AXI} \
    ddr_seg    {Auto} \
    intc_ip    {New AXI SmartConnect} \
    master_apm {0} \
  } [get_bd_intf_pins axi_bram_ctrl_0/S_AXI]

# Assign addresses automatically
assign_bd_address

# Set specific base address for BRAM0
set_property offset 0xA0000000 \
  [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property range 64K \
  [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
```

### Relevance to Your Project

Your `create_bd.tcl` uses `apply_bd_automation` to wire up the AXI connections. In Vivado 2025.1+, if you see the BMG IP missing from the IP catalog during recreation, this is the intentional change — use `create_bd_cell -type ip -vlnv xilinx.com:ip:blk_mem_gen` within the block design TCL flow instead of the standalone IP catalog path.

## Vivado TCL Scripting

### Key Findings

- **Batch mode invocation**: `vivado -nolog -nojournal -mode batch -source create_bd.tcl` runs the script headlessly and exits. Drop `-nolog -nojournal` if you need audit trails.
- **Non-project mode**: The developer manages all sources manually; Vivado does not track runs or generate intermediate files. Faster for CI but requires explicit `read_vhdl`, `read_xdc`, `synth_design`, `impl_design`, `write_bitstream` calls.
- **Export Block Design**: Use `write_bd_tcl -force my_bd.tcl` in the Vivado TCL console to export a block design as a reproducible script — this is the recommended way to version-control block designs.
- **IP recreation**: When sourcing a BD TCL script on a clean machine, run `update_ip_catalog` first to ensure all IP definitions are current before calling `create_bd_design`.
- **Synthesis + implementation from script**:

### Code Example

```tcl
# Full non-project batch flow for KV260 AXI-BRAM demo
create_project -force kv260_bram ./kv260_bram -part xck26-sfvc784-2LV-c

# Read sources
read_vhdl [glob ./vhdl/*.vhd]
read_xdc  ./constraints/kv260_top.xdc

# Recreate block design from exported TCL
source ./tcl/create_bd.tcl
make_wrapper -files [get_files *.bd] -top
add_files -norecurse ./kv260_bram/kv260_bram.gen/sources_1/bd/design_1/hdl/design_1_wrapper.v

# Synthesize, implement, write bitstream
launch_runs synth_1 -jobs 4
wait_on_run synth_1
launch_runs impl_1 -to_step write_bitstream -jobs 4
wait_on_run impl_1
```

### Relevance to Your Project

Your repo's `create_bd.tcl` is the single source of truth for the block design. Wrapping it in the non-project batch flow above lets you reproduce the full bitstream from scratch on any machine with `vivado -mode batch -source build_all.tcl` — essential for CI and for collaborators who don't have the `.xpr` project file.

## Vitis Bare-Metal / Standalone

### Key Findings

- **JTAG vs QSPI boot for KV260**: JTAG mode downloads directly to RAM for iterative development; QSPI programs the boot image persistently. For JTAG, remove the SD card and use `PSU_INIT.TCL` in the debug configuration (not FSBL) to initialize the PS.
- **xil_printf vs printf**: `xil_printf` is a lightweight, non-malloc implementation targeting UART — safe for bare-metal. Standard `printf` links in newlib and bloats the ELF; avoid unless you need floating-point formatting.
- **BSP regeneration**: After any hardware change (new XSA export from Vivado), right-click the platform project → **Update Hardware** to regenerate the BSP and linker script. Forgetting this is the #1 cause of address-map mismatches.
- **Linker script memory regions**: The standalone BSP generates `lscript.ld` with `ps_ddr_0` as the default code/data region. For very small demos, you can place code in OCM (on-chip memory) to avoid DDR initialization latency.
- **Vitis 2025.1**: Third-party productivity tools now installable via an in-IDE marketplace utility.

### Code Example

```c
/* Minimal AXI-Lite BRAM write/read test for KV260 bare-metal */
#include "xil_printf.h"
#include "xil_io.h"
#include "xparameters.h"

#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL
#define TEST_WORDS  16

int main(void) {
    xil_printf("KV260 AXI-BRAM test starting...\r\n");

    /* Write phase */
    for (int i = 0; i < TEST_WORDS; i++) {
        Xil_Out32(BRAM0_BASE + (i * 4), 0xDEAD0000 | i);
        Xil_Out32(BRAM2_BASE + (i * 4), 0xBEEF0000 | i);
    }

    /* Read-back phase */
    int pass = 1;
    for (int i = 0; i < TEST_WORDS; i++) {
        u32 r0 = Xil_In32(BRAM0_BASE + (i * 4));
        u32 r2 = Xil_In32(BRAM2_BASE + (i * 4));
        if (r0 != (0xDEAD0000 | i) || r2 != (0xBEEF0000 | i)) {
            xil_printf("FAIL @ word %d: BRAM0=0x%08X BRAM2=0x%08X\r\n", i, r0, r2);
            pass = 0;
        }
    }
    xil_printf(pass ? "PASS\r\n" : "OVERALL FAIL\r\n");
    return 0;
}
```

### Relevance to Your Project

Your `main.c` already follows this pattern with `Xil_Out32`/`Xil_In32` and `xil_printf`. The key insight: after any Vivado change that shifts the AXI address map, you **must** re-export the XSA and regenerate the BSP — `XPAR_AXI_BRAM_CTRL_0_BASEADDR` in `xparameters.h` is auto-generated and must match `0xA0000000`.

## XDC Timing Constraints

### Key Findings

- **set_input_delay / set_output_delay**: These specify the external board-level path delay relative to a clock edge at the FPGA boundary, in nanoseconds. For AXI-Lite interfaces driven by the PS (internal), you typically do **not** need these — they apply to external I/O ports.
- **PS-to-PL clock constraints**: The `pl_clk0` generated by the Zynq PS is automatically constrained by Vivado; you do not need to add a `create_clock` for it. Only add constraints for external clocks entering PL pins.
- **K26 SOM XDC**: The SOM board file includes an XDC that maps the Zynq UltraScale+ MPSoC package to SOM connector pins. Carrier card designers layer their own XDC on top.
- **False path for PS-PL**: Declare `set_false_path` between PS clock domains and any asynchronous PL logic that is reset-synchronized separately.
- **clock_groups for MMCM outputs**: If you derive multiple clocks from a MMCM in PL, declare them as `set_clock_groups -asynchronous` to prevent Vivado from trying to time paths that cross unrelated clock domains.

### Code Example

```tcl
# KV260 XDC: constrain only external PL clocks
# pl_clk0 from PS is auto-constrained — do NOT add create_clock for it

# Example: external 125 MHz clock on PL pin (if used)
# create_clock -period 8.000 -name clk_125 [get_ports clk_125_p]

# Declare PS output clock as the primary PL clock source (informational)
# Vivado auto-creates this from the PS IP constraints:
# create_clock -period 10.000 -name clk_100mhz [get_pins zynq_ultra_ps_e_0/inst/PS8_i/PLCLK[0]]

# For any CDC crossing between PL clock domains:
set_clock_groups -asynchronous \
  -group [get_clocks -of_objects [get_pins clk_wiz_0/inst/mmcme4_adv_inst/CLKOUT0]] \
  -group [get_clocks -of_objects [get_pins clk_wiz_0/inst/mmcme4_adv_inst/CLKOUT1]]

# I/O timing for external signals (e.g. GPIO output on carrier card):
# set_output_delay -clock [get_clocks clk_100mhz] -max 2.0 [get_ports gpio_out]
# set_output_delay -clock [get_clocks clk_100mhz] -min -1.0 [get_ports gpio_out]
```

### Relevance to Your Project

For the AXI-BRAM demo, the only critical timing constraint is the PS `pl_clk0` driving the AXI fabric — which Vivado handles automatically from the Zynq PS IP. Your XDC likely only needs pin-location constraints for UART (if routed through PL) and any LED/GPIO outputs. Keep the XDC minimal to avoid over-constraining a design that is entirely PS-internal.

## Kria KV260 / K26 SoM

### Key Findings

- **Default boot mode**: KV260 Starter Kits ship with QSPI32 boot mode set by `MODE[3:0]` pins on the carrier card. This boots the pre-loaded firmware from onboard QSPI flash.
- **Bare-metal JTAG flow**: Remove SD card → set debug config to use `PSU_INIT.TCL` (not FSBL) → connect JTAG → download ELF. This bypasses the boot ROM sequence entirely and puts the PS into a known state.
- **QSPI programming for deployment**: Generate `BOOT.bin` (FSBL + bitstream + ELF) → use XSDB: `program_flash -f BOOT.bin -offset 0 -flash_type qspi-x4-single`.
- **EMIO vs MIO**: Most peripherals use MIO (PS-internal routing). PMODs and RPi headers route through PL via EMIO — these require a bitstream to be loaded before they function.
- **Fan control**: The carrier card fan is controlled via EMIO in the default K26 bitstream — critical to note so you don't accidentally remove this connection in a custom overlay.
- **Power domains**: The K26 SoM has separate power rails for PS (`VCCINT_PS`), PL (`VCCINT`), and I/O banks. The carrier card must sequence these correctly; the KV260 carrier handles this automatically.

### Code Example

```tcl
# XSDB script: JTAG bare-metal download to KV260
# Run in Vitis XSCT console or xsdb batch mode

connect
targets -set -nocase -filter {name =~ "PSU"}
mwr 0xFFFF0000 0x1AEB0001  ;# unlock SLCR
source psu_init.tcl         ;# PS initialization (generated by Vivado)
psu_init
after 1000

targets -set -nocase -filter {name =~ "Cortex-A53 #0"}
rst -processor
dow kv260_bram_test.elf     ;# download ELF to DDR
con                         ;# run
```

### Relevance to Your Project

Your demo targets JTAG-based development. Using `PSU_INIT.TCL` instead of FSBL skips the full boot sequence and gets the Cortex-A53 running your bare-metal app in seconds. Once the PASS/FAIL output is confirmed over USB-UART, the next step is typically `BOOT.bin` generation for QSPI deployment — which requires adding an FSBL built for the K26 to your Vitis workspace.

## AMD/Xilinx Tool Updates (2025.x / 2026.x)

### Key Findings

- **CRITICAL — BRAM IP removal from standalone catalog (2025.1+)**: Block Memory Generator and FIFO IPs can no longer be instantiated directly from the Vivado IP Catalog — they must be used within block designs. This affects any script or flow that previously called `create_ip -name blk_mem_gen` outside of a BD context.
- **Vivado 2025.2 — AXI SmartConnect STRATEGY parameter**: A new `STRATEGY` parameter on AXI Switch and AXI SmartConnect IP enables ultra-low-area mode, reducing LUT usage for simple 1-master / 1-slave configurations like the KV260 AXI-BRAM demo.
- **Vivado 2025.2 — SystemVerilog Interfaces**: Simplified AXI connections between SV instances with automatic wrapper creation — relevant if you move from VHDL to mixed-language designs.
- **Vivado 2026.1**: New tiered licensing model, support for Versal RF Series and AI Edge Series Gen 2, major NoC and QoR improvements. Spartan UltraScale+ FPGAs now supported.
- **Vitis 2025.1**: Third-party tool marketplace within the IDE; Bare-Metal Debug improvements documented in UG1702.
- **2025.1 IP Release Notes**: Full IP changelog available at AMD support article 000037919 — check this for any AXI BRAM Controller bug fixes before upgrading.

### Code Example

```tcl
# Vivado 2025.2: Enable ultra-low-area mode on AXI SmartConnect
# Set STRATEGY parameter when creating the SmartConnect in block design

set_property -dict [list \
  CONFIG.NUM_SI {1} \
  CONFIG.NUM_MI {2} \
  CONFIG.STRATEGY {1} \
] [get_bd_cells axi_smc]
# STRATEGY=1 enables the low-area optimization pass
# Reduces LUT count by ~30% for simple 1-to-N topologies

# Verify with:
report_utilization -file util_report.txt
```

### Relevance to Your Project

The BRAM-from-IP-catalog removal is the most impactful change for your project. If you or a collaborator tries to add a BRAM in Vivado 2025.1+ using the old flow (`IP Catalog → Block Memory Generator → right-click → Customize IP`), it will fail or be absent. Always add BRAMs through the block design. Additionally, the SmartConnect `STRATEGY=1` optimization is free savings — apply it in `create_bd.tcl` to reduce resource usage on the K26's PL fabric.
