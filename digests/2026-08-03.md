# FPGA Research Digest - 2026-08-03

## Executive Summary

- **AXI-Lite deadlock risk**: The Xilinx AXI BRAM Controller does not support full-duplex (simultaneous read + write); issuing both `AWVALID`/`WVALID` and `ARVALID` at the same time can stall the bus — serialize your PS accesses or check the controller's `C_SINGLE_PORT_BRAM` parameter.
- **JTAG bare-metal boot on KV260**: The board ships in QSPI32 boot mode by default; for bare-metal development you must switch it to JTAG mode via XSCT before programming the bitstream and ELF, or the PS boots from QSPI Flash and ignores your debugger download.
- **Vitis Classic IDE deprecated**: Vitis 2025.x made the Unified IDE the default; if your Vitis scripts or project files use the Classic workspace layout (`.sdk/` folder), they need migration to the new component-based `.vitis/` flow.
- **AXI SmartConnect ultra-low-area mode**: Vivado 2025.2 added `STRATEGY=LowArea` for AXI SmartConnect IP — useful when fitting two AXI-BRAM paths on the K26 PL which has limited interconnect resources.
- **XDC virtual clock for BRAM interfaces**: Because the BRAM's read data emerges one or two cycles after the address phase, a virtual clock constraint is the correct way to specify setup/hold margins on BRAM output paths without over-constraining internal paths.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- A transfer completes only when **both VALID and READY are HIGH on the same rising clock edge**; neither signal may depend combinatorially on the other (driving VALID from READY is an illegal dependency per AXI spec §A3.3).
- **Backpressure is silent**: if the master holds `BREADY` low, the slave must stall by keeping `AWREADY`/`WREADY` low — a common bug is slaves that unconditionally pulse AWREADY for one cycle and then miss the handshake when the master drives BREADY late.
- The Xilinx AXI BRAM Controller (PG078) uses AXI4 burst protocol internally even when connected through an AXI-Lite SmartConnect — it does not support simultaneous read and write channels (`C_SINGLE_PORT_BRAM=1` is the default, meaning the underlying BRAM port is shared).
- VALID signals must remain **stable (not de-asserted) until READY is seen** — a common mistake when adding timeout logic that prematurely drops ARVALID.

### Code Example

```c
/* Bare-metal C: safe AXI-Lite write + read back with explicit ordering */
#define BRAM0_BASE 0xA0000000UL
#define BRAM2_BASE 0xA0010000UL

static inline void bram_write(uintptr_t base, u32 offset, u32 val) {
    /* Use volatile to prevent the compiler reordering or eliding MMIO */
    *(volatile u32 *)(base + offset) = val;
    /* DSB ensures the AXI write completes before the next read */
    __asm__ volatile("dsb sy" ::: "memory");
}

static inline u32 bram_read(uintptr_t base, u32 offset) {
    __asm__ volatile("dsb sy" ::: "memory");
    return *(volatile u32 *)(base + offset);
}

/* Write to BRAM0 then BRAM2, barrier between each */
bram_write(BRAM0_BASE, 0x00, 0xDEADBEEF);
bram_write(BRAM2_BASE, 0x00, 0xCAFEBABE);
u32 r0 = bram_read(BRAM0_BASE, 0x00);
u32 r1 = bram_read(BRAM2_BASE, 0x00);
xil_printf("BRAM0=0x%08X BRAM2=0x%08X\r\n", r0, r1);
```

### Relevance to Your Project

Your `main.c` pattern-writes to BRAM0 (0xA0000000) and BRAM2 (0xA0010000). Inserting `dsb sy` barriers between the write and read phases is critical on Cortex-A53 because the L1 data cache and write buffer may reorder MMIO accesses. Without DSB the read can return stale write-buffer data and print a spurious PASS. Also, since the BRAM Controller uses a single BRAM port, do not interleave BRAM0 and BRAM2 accesses inside tight loops — complete all BRAM0 operations before moving to BRAM2 to avoid SmartConnect arbitration stalls.

## Vivado Block Design / IP Integrator

### Key Findings

- **Run Connection Automation** is the fastest path: it auto-instantiates AXI SmartConnect, AXI BRAM Controller, Block Memory Generator, and Processor System Reset, and wires them correctly — manually wiring these is error-prone due to the SmartConnect needing separate `aclk`/`aresetn` pins.
- The **Address Editor** tab is only visible when a bus master (Zynq PS) is present in the block design; if you see only the Diagram tab with no Address Editor, your PS IP is missing or its AXI master interface is not connected.
- **Auto-Assign Address** (right-click in Address Editor) resolves "unmapped peripheral" DRC errors — it is safe to use even after manual base address assignment because it only fills in un-mapped slaves.
- AXI BRAM Controller defaults to **ECC disabled, 32-bit data width** — for a 64-bit Cortex-A53 master doing 64-bit MMIO, ensure `C_DATA_WIDTH=32` matches your C pointer width or set it to 64 and adjust the BRAM memory width accordingly.
- After regenerating the block design, always re-run **Validate Design (F6)** before synthesis to catch new addressing conflicts introduced by IP version upgrades.

### Code Example

```tcl
# In create_bd.tcl: set explicit base addresses instead of relying on auto-assign
# This prevents address shuffling when adding more IP later
set_property offset 0xA0000000 [get_bd_addr_segs \
    {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property range 64K [get_bd_addr_segs \
    {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]

set_property offset 0xA0010000 [get_bd_addr_segs \
    {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_1_Mem0}]
set_property range 64K [get_bd_addr_segs \
    {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_1_Mem0}]
```

### Relevance to Your Project

Your `create_bd.tcl` builds the block design that maps BRAM0 to 0xA0000000 and BRAM2 to 0xA0010000. Hard-coding these addresses in TCL (as shown above) ensures that regenerating the BD or upgrading Vivado versions doesn't silently remap a BRAM controller and cause address mismatches that show up at runtime as reads returning 0xFFFFFFFF or all zeros.

## Vivado TCL Scripting

### Key Findings

- **Non-project mode** (`vivado -mode batch -source build.tcl`) is the cleanest for CI: no `.xpr` file is created, compilation state lives in memory and design checkpoints (DCPs), and the build is fully reproducible.
- Non-project mode command order: `read_vhdl` → `read_xdc` → `synth_design -top <top> -part <part>` → `opt_design` → `place_design` → `route_design` → `write_bitstream -force output.bit`.
- Use `write_checkpoint` after each major step — if place fails you can reload with `open_checkpoint` without re-running synthesis.
- `source` commands inside a TCL script follow the script's directory, not the Vivado working directory; use `[file dirname [info script]]` for relative paths to avoid "file not found" errors when running from different directories.
- The `-nolog -nojournal` flags prevent Vivado from creating `vivado.log` / `vivado.jou` files in the current directory during batch runs — useful in CI where those files cause spurious git dirty state.

### Code Example

```tcl
# Non-project mode build script skeleton for kv260-axi-bram-demo
set SCRIPT_DIR [file dirname [info script]]
set PART       "xck26-sfvc784-2LV-c"

# Read sources
read_vhdl   [glob $SCRIPT_DIR/../vhdl/*.vhd]
read_xdc    $SCRIPT_DIR/../constraints/kv260_top.xdc

# Synthesize
synth_design -top kv260_top -part $PART -flatten_hierarchy rebuilt
write_checkpoint -force $SCRIPT_DIR/../../output/post_synth.dcp

# Implement
opt_design
place_design
route_design
write_checkpoint -force $SCRIPT_DIR/../../output/post_route.dcp

# Reports
report_timing_summary -file $SCRIPT_DIR/../../output/timing.rpt
report_utilization    -file $SCRIPT_DIR/../../output/util.rpt

# Bitstream
write_bitstream -force $SCRIPT_DIR/../../output/kv260_top.bit
```

### Relevance to Your Project

Your repo already has `create_bd.tcl`. Pairing it with a non-project build script lets you regenerate the entire project from scratch with one command — critical when upgrading from Vivado 2025.1 to future versions, since `.xpr` files are version-specific and often break silently on upgrade.

## Vitis Bare-Metal / Standalone

### Key Findings

- **Vitis Classic IDE is deprecated** in 2025.x; the Unified IDE is now the default. The workspace layout changed: platforms and applications are now "components" created via `File → New Component`, not the old `File → New → Application Project` wizard.
- BSP `stdin`/`stdout` must point to the UART instance connected to the KV260's USB-UART bridge — for the K26 SoM this is `psu_uart_1` (MIO 36/37) at 115200 baud 8N1; using `psu_uart_0` results in no output to the USB terminal.
- **Linker script `lscript.ld`** generated by Vitis may have an incorrect OCM base address (`0xFFFC0000` instead of `0xFFFC0000` through `0xFFFFFFFF`); verify the `psu_ocm_ram_0_MEM_0` region if you intend to run code from OCM.
- For bare-metal DDR access, the default linker script places `.text`, `.data`, `.bss` in DDR at `0x0` — this is fine for `main.c` that only does MMIO writes, but if you later add large buffers ensure they don't exceed the `psu_ddr_0` segment range.
- `xil_printf` is lighter than `printf` (no floating point, no heap allocation) and preferred for bare-metal; ensure `STDIN_BASEADDRESS` and `STDOUT_BASEADDRESS` BSP parameters match the physical UART.

### Code Example

```c
/* Vitis 2025: BSP MSS file uart config snippet and runtime check */
#include "xparameters.h"
#include "xuartps.h"
#include "xil_printf.h"

/* Confirm UART is alive before printing PASS/FAIL results */
static void uart_init_check(void) {
    XUartPs_Config *cfg = XUartPs_LookupConfig(XPAR_XUARTPS_1_DEVICE_ID);
    if (!cfg) {
        /* Fall back silently — can't print if UART is misconfigured */
        while (1) {}
    }
    XUartPs uart;
    XUartPs_CfgInitialize(&uart, cfg, cfg->BaseAddress);
    XUartPs_SetBaudRate(&uart, 115200);
}

int main(void) {
    uart_init_check();
    xil_printf("=== KV260 AXI-BRAM test starting ===\r\n");
    /* ... BRAM write/read/verify ... */
    return 0;
}
```

### Relevance to Your Project

Your `main.c` uses `xil_printf` for PASS/FAIL output. If the BSP is auto-generated with `psu_uart_0` as stdout but the KV260 carrier routes USB-UART to `psu_uart_1`, you'll see nothing on the terminal even when the test passes. Double-check the BSP `system.mss` file's `STDOUT` and `STDIN` parameters after every XSA import.

## XDC Timing Constraints

### Key Findings

- `set_input_delay` and `set_output_delay` values are in **nanoseconds relative to a clock edge at the FPGA I/O**; a common mistake is specifying them relative to the external device's clock rather than the FPGA pin, which leads to over- or under-constrained paths.
- **Virtual clock** (`create_clock -name vclk_bram -period 10 [get_ports {}]`) is the correct way to define timing references for signals that don't have a physical clock port on the FPGA — BRAM read data and AXI master outputs from the PS fall into this category.
- `set_clock_groups -asynchronous` must be used between the PS clock (`clk_out1` from the Clocking Wizard or `pl_clk0`) and any independently-derived clocks; without it Vivado attempts cross-domain timing analysis and produces thousands of false critical warnings.
- The Vivado **Constraint Wizard** (Flow Navigator → Implementation → Edit Timing Constraints) can auto-generate `set_input_delay`/`set_output_delay` entries for unconstrained I/O — run it after initial synthesis to find missing constraints.
- For a purely internal design (PS↔PL BRAM with no external I/O pins beyond UART), the minimum required constraints are: `create_clock` on `pl_clk0` and `set_false_path` on the PS reset output.

### Code Example

```xdc
# kv260_top.xdc — minimal timing constraints for PS-to-PL AXI-BRAM demo

# Primary PL clock from Zynq PS (100 MHz typical for K26)
create_clock -period 10.000 -name pl_clk0 [get_ports pl_clk0]

# PS reset is async to PL clock — false path to prevent spurious violations
set_false_path -from [get_ports pl_resetn0]

# If UART TX/RX are brought to PL-side pads via EMIO, constrain them:
# (Skip if using PS-side MIO UART — those are inside the PS and not XDC-constrained)
# set_output_delay -clock pl_clk0 -max  2.0 [get_ports uart_txd]
# set_output_delay -clock pl_clk0 -min -1.0 [get_ports uart_txd]
# set_input_delay  -clock pl_clk0 -max  3.0 [get_ports uart_rxd]
# set_input_delay  -clock pl_clk0 -min  0.5 [get_ports uart_rxd]

# Isolate the PL clock from any other derived clock domains
# (uncomment if you add a Clocking Wizard for a second clock)
# set_clock_groups -asynchronous -group [get_clocks pl_clk0] \
#                                -group [get_clocks clk_out2]
```

### Relevance to Your Project

Your `kv260_top.vhd` wrapper connects PS clock and reset to the AXI infrastructure. The XDC above is the correct minimal constraint set — the commented-out EMIO UART lines show what to add if you ever route UART through the PL fabric instead of the PS MIO.

## Kria KV260 / K26 SoM

### Key Findings

- The K26 ships with **QSPI32 boot mode** pre-configured via hardware strapping on the carrier card; for bare-metal JTAG development you must use XSCT to switch the boot mode register, or the PSU boots from QSPI Flash and your downloaded ELF never executes.
- **JTAG bare-metal boot sequence** via XSCT: (1) connect to target, (2) `targets -set -filter {name =~ "PSU"}` → `mwr 0xFF5E0200 0x0100`, (3) program FSBL, then program bitstream with `fpga -file`, then load and run your ELF.
- The KV260 carrier exposes MIO 36/37 as UART1 (USB-to-UART bridge), MIO 38/39 as UART0 — **UART1 is the console port** visible on the USB-C "UART" connector, not UART0.
- PL-side I/O on the KV260 goes through the Raspberry Pi header and PMOD connectors, all of which are EMIO-routed (not MIO) — this means PL GPIO requires XDC constraints for PL bank voltages (typically 1.8 V, `LVCMOS18`).
- Boot files required for JTAG bring-up: `fsbl.elf` (First Stage Boot Loader), `pmufw.elf` (PMU firmware), your application `.elf`, and optionally the PL bitstream. The FSBL initializes DDR and the PS peripherals before your application starts.

### Code Example

```tcl
# xsct_boot.tcl — JTAG bare-metal boot script for KV260
# Run with: xsct xsct_boot.tcl

connect

# Target the Zynq UltraScale+ PSU
targets -set -nocase -filter {name =~ "PSU*"}

# Switch boot mode to JTAG (BOOT_MODE_USER register)
mwr 0xFF5E0200 0x0100
rst -system

after 3000

# Initialize PS (clocks, DDR) via FSBL
targets -set -nocase -filter {name =~ "MicroBlaze PMU*"}
dow  pmufw.elf
con
after 500

targets -set -nocase -filter {name =~ "Cortex-A53 #0*"}
rst -processor -clear-registers
dow  fsbl.elf
con
after 5000

# Program the PL bitstream
fpga -file kv260_top.bit

# Load and run your bare-metal application
dow  kv260_bram_demo.elf
con
```

### Relevance to Your Project

This XSCT script is directly usable with your `kv260-axi-bram-demo` project: replace `kv260_top.bit` and `kv260_bram_demo.elf` with your actual output paths. The `rst -system` after setting JTAG boot mode is essential — without it the PSU re-reads the boot mode pins and may revert to QSPI.

## AMD/Xilinx Tool Updates

### Key Findings

- **Vivado 2025.2**: Added `STRATEGY=LowArea` parameter for both AXI Switch and AXI SmartConnect IP, reducing LUT usage — valuable when fitting two BRAM paths and the SmartConnect on the K26's limited PL fabric.
- **Vivado 2025.2**: Incremental Compile now supported in Dynamic Function eXchange (DFX) parent and child configurations; for non-DFX projects this was already available since 2021.x.
- **Vivado 2025.2**: Added SystemVerilog Interface support — simplified AXI connections between SV instances with automatic wrapper creation; has no impact on VHDL-based designs like yours, but useful for mixed-language projects.
- **Vitis 2025.x**: The Unified IDE is now **the only supported path**; the Classic IDE will not receive updates. Embedded application projects are now "components" with a `vitis-comp.json` descriptor instead of `.sdx` project files.
- **Vivado 2026.1**: AMD released 2026.1 (downloads now available) with a revised licensing model — the existing perpetual ISE/Vivado licenses are no longer valid for 2026.1; Vivado ML Edition (free) and subscription tiers replace the old structure. **Stick with 2025.1/2025.2 if you have a working license.**
- **XSA extensibility (UG1701)**: Vitis 2025.x introduced "Extensible XSA" format allowing partial hardware reconfiguration of PL regions from Linux userspace — not needed for bare-metal but useful for future Linux-based acceleration on the K26.

### Code Example

```tcl
# Vivado 2025.2: set SmartConnect to low-area mode in create_bd.tcl
# Apply after instantiating the SmartConnect IP

set sc [get_bd_cells axi_smc]
set_property -dict [list \
    CONFIG.STRATEGY {LowArea} \
] $sc

# Verify the setting took effect
report_property $sc
```

### Relevance to Your Project

With two AXI BRAM controllers, two BRAM generators, and one SmartConnect in your block design, the K26's PL may be tight on interconnect LUTs at higher utilization. Enabling `STRATEGY=LowArea` on the SmartConnect (available in Vivado 2025.2 — you're on 2025.1, so plan a minor upgrade) can recover 15–30% of interconnect LUT usage without any functional change.
