# FPGA Research Digest - 2026-06-17

## Executive Summary

- **Xilinx's own AXI-Lite reference cores have known ready-signal bugs**: ZipCPU's analysis found Xilinx "messed up the ready signals when they built their demonstration core" — if your `kv260_top.vhd` ever moves from the AXI BRAM Controller IP to a hand-rolled AXI-Lite slave, do not copy the Xilinx template logic verbatim; verify AWREADY/WREADY/ARREADY deassertion behavior independently.
- **Write strobes must be fully asserted or the transaction is silently discarded**: AMD's AXI4 register-interface logic drops any write where `WSTRB` isn't all-ones. If you ever add a narrower-than-32-bit write path to the BRAM demo, confirm your C code sets full strobes — partial writes won't error, they'll just vanish.
- **`apply_bd_automation` is the one-call way to wire the Zynq PS** — `apply_bd_automation -rule xilinx.com:bd_rule:processing_system7 -config {make_external "FIXED_IO, DDR" ...}` (or the ZynqMP equivalent) does in one Tcl call what your `create_bd.tcl` likely does with several manual `connect_bd_intf_net` calls. Worth knowing if you ever rebuild the script for a new K26 carrier.
- **AXI BRAM Controller's ECC mode costs an extra clock cycle on the datapath** — irrelevant for plain pass/fail testing, but if you add error-injection or reliability testing to the demo, enabling `C_ECC=1` changes your read latency by one cycle and exposes a second AXI4-Lite ECC status/control port you'd need to wire up separately.
- **`write_bd_tcl` does not include block-design layout by default** — your `create_bd.tcl`, if originally captured this way, would have lost visual layout info unless `-include_layout` was passed; this only matters cosmetically (reopening the BD in the GUI), not functionally.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- BVALID is only legal to assert *after* the AW and W channel handshakes have both completed for that transaction — asserting it concurrently with WVALID/WREADY is a protocol violation that can cause undefined behavior.
- Backpressure correctness is the most common simulation-only bug: if BREADY is held low by the master, the slave must lower AWREADY/WREADY appropriately; if RREADY is held low, ARREADY must follow suit. These paths are rarely exercised unless you specifically test slow-master scenarios.
- AMD's official AXI4 register-interface generator (used by HDL Coder and similar tools) discards any write transaction where `WSTRB` is not fully asserted — there is no error response, the data is simply dropped.
- A practical pattern for handling write strobes: pre-combine `WSTRB` with `WDATA` into "would-be-written" shadow registers (`wskd_rN`) so your write logic only ever needs to consult one value instead of branching on strobe bits at write time.
- Independent community analysis (ZipCPU) found that Xilinx's own AXI-Lite demonstration/reference core mishandles the READY signals — a caution against copying Xilinx example RTL uncritically into hand-written slaves.

### Code Example

```vhdl
-- Write-strobe pre-combination pattern (avoids branching on WSTRB at commit time)
-- Apply at the moment WVALID/WREADY handshake completes
signal reg0      : std_logic_vector(31 downto 0);
signal wskd_reg0 : std_logic_vector(31 downto 0);

process(clk)
begin
  if rising_edge(clk) then
    -- Pre-compute "data after strobe applied" every cycle W data is valid
    for b in 0 to 3 loop
      if s_wstrb(b) = '1' then
        wskd_reg0(8*b+7 downto 8*b) <= s_wdata(8*b+7 downto 8*b);
      else
        wskd_reg0(8*b+7 downto 8*b) <= reg0(8*b+7 downto 8*b);
      end if;
    end loop;

    -- On handshake, commit the pre-combined value directly -- no strobe logic here
    if s_wvalid = '1' and s_wready = '1' then
      reg0 <= wskd_reg0;
    end if;
  end if;
end process;
```

### Relevance to Your Project

The AXI BRAM Controller IP your demo uses already implements correct WSTRB handling internally, so this isn't a live bug for you today. But it's the exact failure mode to check first if a future revision swaps the IP for a custom AXI-Lite register block (e.g., to add a status/control register alongside BRAM0/BRAM2) — a 32-bit write from C with `Xil_Out32` always sets full strobes, so you're safe as long as you don't introduce byte/halfword writes.

## Vivado Block Design / IP Integrator

### Key Findings

- **Connection Automation** (green bar at top of the BD canvas) can auto-wire resets and clocks for newly dropped IP — always double check the "reset" checkbox is selected so the reset network gets connected, not just clocks.
- The **Address Editor** tab only becomes visible once an AXI master interface is present in the design (or made external) — if you don't see it, verify your PS's `M_AXI_HPM0_FPD` (or GP0) port is actually connected to something before looking for missing address assignments.
- **Regenerate Layout** purely affects visual arrangement of blocks/wires — it has zero effect on functionality or generated bitstream, safe to use anytime for readability.
- `apply_bd_automation` is the scripted equivalent of clicking "Run Block Automation" — Designer Assistance rules exist for the Zynq PS, MicroBlaze, AXI Ethernet, and memory IP, auto-configuring sensible defaults (e.g., DDR/FIXED_IO external pins) in one call.
- `write_bd_tcl` intentionally omits visual layout by default (`-include_layout` brings it back) and only emits parameters the *user* changed — tool-default and propagated parameters are left out, which keeps exported scripts smaller but means re-running the script can yield slightly different default values across tool versions.
- Tcl scripts exported via `write_bd_tcl` are version-pinned — AMD explicitly warns the embedded version metadata means a script from one Vivado release should not be assumed to work unmodified in another.

### Code Example

```tcl
# Block Automation equivalent of "Run Block Automation" button, scripted
# (illustrative -- exact rule name varies by PS IP version)
create_bd_cell -type ip -vlnv xilinx.com:ip:zynq_ultra_ps_e:3.5 zynq_ps

apply_bd_automation -rule xilinx.com:bd_rule:zynq_ultra_ps_e \
  -config {apply_board_preset "1"}  [get_bd_cells zynq_ps]

# Connection Automation equivalent for an AXI BRAM controller's S_AXI port
apply_bd_automation -rule xilinx.com:bd_rule:axi4 \
  -config { Master "/zynq_ps/M_AXI_HPM0_FPD" Clk "Auto" } \
  [get_bd_intf_pins axi_bram_ctrl_0/S_AXI]
```

### Relevance to Your Project

Your `create_bd.tcl` likely issues explicit `connect_bd_intf_net` calls rather than relying on automation rules, which is more reproducible and easier to diff/review — a reasonable tradeoff for a small two-BRAM design. If the design grows (e.g., adding a GPIO or timer IP), `apply_bd_automation` calls can replace several lines of manual wiring per IP and reduce mistakes when wiring AXI clock/reset domains.

## Vivado TCL Scripting

### Key Findings

- Non-Project Mode is the recommended path for anyone wanting full control or CI integration: synthesis, place, route, and bitstream all happen in-memory without `.xpr` project files, making it faster and more reproducible than the GUI flow.
- The basic Tcl batch flow is: read sources → `synth_design` → `opt_design` → `place_design` → `route_design` → `write_bitstream`, run via `vivado -mode batch -source build.tcl`.
- In Non-Project Mode, you are fully responsible for tracking which stage needs rerunning after a source edit — there's no dependency graph like a `.xpr` project provides, so an incremental rebuild after an RTL change can silently use stale synthesis results unless you re-run from scratch or manage checkpoints carefully.
- `create_bd_cell -vlnv <vendor:lib:name:version>` adds any IP from the catalog or a hierarchical block by name — the most common create_bd_cell usage is dropping the Zynq PS, then immediately following with `apply_bd_automation` to auto-configure it.
- A scripted Vivado flow (Tcl + Makefile) is a common pattern for getting Vivado builds into CI pipelines, since the whole synthesis-to-bitstream sequence can run headlessly with `-mode batch`.

### Code Example

```tcl
# Combined block-design regeneration + non-project synth/impl wrapper
# vivado -mode batch -source build_all.tcl

set PART "xck26-sfvc784-2LV-c"

# Phase 1: regenerate the block design (project mode, since BD Tcl API
# is most reliable inside an open project)
open_project ./kv260_claude/kv260/kv260.xpr
source ./kv260_claude/kv260/tcl/create_bd.tcl
generate_target all [get_files *.bd]
close_project

# Phase 2: non-project synth/impl for CI-style reproducibility
read_vhdl   [glob ./kv260_claude/kv260/vhdl/*.vhd]
read_xdc    ./kv260_claude/kv260/constraints/kv260_top.xdc
synth_design -top kv260_top -part $PART
opt_design
place_design
route_design
write_bitstream -force ./output/kv260_top.bit
```

### Relevance to Your Project

Your project's `create_bd.tcl` already lives under version control, which is the right foundation for this kind of two-phase build script. The main gotcha if you adopt a fully scripted flow: BD Tcl commands (`create_bd_cell`, `connect_bd_intf_net`, etc.) generally require an *open project* with a live in-memory BD — plan for a project-mode phase 1 even if synthesis/implementation run non-project afterward.

## Vitis Bare-Metal / Standalone

### Key Findings

- `xil_printf` deliberately supports a reduced format-specifier set (`%d`, `%l`, `%x`, `%c`, `%s` — no `%f`) in exchange for a much smaller code/stack footprint than full `stdio printf`, which matters for tight bare-metal memory budgets.
- BSP UART selection is controlled by `standalone_stdin`/`standalone_stdout` settings — for boards with multiple UARTs you must explicitly point both to the correct instance (e.g., `psu_uart_1`) or output silently goes nowhere.
- The Standalone BSP is intentionally single-threaded with minimal overhead — no scheduler, no dynamic driver discovery, just the libraries and drivers you explicitly enable in the BSP settings.
- `lscript.ld` (the auto-generated linker script) is editable per-application; a common customization is constraining one application to a DDR sub-region (e.g., everything above `0x70000000`, capped at 256 MB) so multiple bare-metal images can coexist in memory without overlap — directly applicable if you ever run code on more than one A53 core.
- For interrupt-related bring-up issues, checking the GICD_ISENABLER# register via the debugger on the specific core target is the standard diagnostic step — confirms whether the interrupt was actually enabled at the distributor level versus a problem in your handler registration.
- Recent (2025.1) community projects (e.g., MicroBlaze V on KR260 with Vitis 2025.1) confirm the standalone/bare-metal flow is actively used and validated against the current 2025.1 toolchain, not just legacy versions.

### Code Example

```c
#include "xil_io.h"
#include "xil_printf.h"
#include "xparameters.h"

#define BRAM0_BASE   XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR  /* 0xA0000000 */
#define BRAM2_BASE   XPAR_AXI_BRAM_CTRL_1_S_AXI_BASEADDR  /* 0xA0010000 */

/* Confirm BSP UART matches hardware before relying on xil_printf output */
#ifndef STDOUT_BASEADDRESS
#error "BSP standalone_stdout not configured -- check BSP settings"
#endif

int main(void) {
    xil_printf("STDOUT base: 0x%08X\r\n", STDOUT_BASEADDRESS);
    xil_printf("BRAM0 base : 0x%08X\r\n", BRAM0_BASE);
    xil_printf("BRAM2 base : 0x%08X\r\n", BRAM2_BASE);
    return 0;
}
```

### Relevance to Your Project

Using `xparameters.h` macros (`XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR`) instead of hardcoding `0xA0000000`/`0xA0010000` directly in `main.c` makes the address assignment self-documenting and automatically correct if the block design's address map ever changes — worth adopting if your current `main.c` uses literal hex constants. The `STDOUT_BASEADDRESS` compile-time check is a cheap guard against a silently misconfigured BSP producing no UART output at all.

## XDC Timing Constraints

### Key Findings

- `set_input_delay -clock clk -max 5.0 [get_ports data_in]` and `set_output_delay -clock clk -max 3.0 [get_ports data_out]` are the canonical syntax forms — delays are specified in nanoseconds relative to a named clock's edge.
- `-clock_fall` lets you reference the falling edge of a clock instead of the (default) rising edge — relevant for DDR-style or half-rate interfaces, not typical for a simple AXI-BRAM bring-up demo.
- Setup-side input delay budget calculation: if the source clock period is 10 ns and the driving device's clock-to-Q delay is 2 ns, you have 8 ns of valid window — specify the delay with `-max`, not the full period.
- `set_clock_groups` is one of several constraints (alongside `create_clock`, `create_generated_clock`, `set_false_path`, `set_max_delay`, `set_multicycle_path`) that affect setup analysis — use `-asynchronous` between any two clock domains that have no fixed phase relationship.
- A useful first-pass workflow: Vivado's Timing Constraint Wizard auto-detects clocks and I/O ports needing constraints and emits a draft XDC, which you then hand-refine rather than writing every constraint from scratch.
- AMD's official syntax reference for both commands is current for 2025.1 (UG835), confirming no breaking syntax changes for this constraint pair in the version your project targets.

### Code Example

```xdc
# KV260 AXI-BRAM demo: PL fabric clock declaration (mandatory even with no I/O)
# Without this, Vivado has no clock to time internal AXI logic against
create_clock -period 10.000 -name clk_pl_0 [get_pins zynq_ps/inst/PS8_i/PLCLK[0]]

# If a future revision adds a debug UART or GPIO pin on the carrier:
# set_output_delay -clock clk_pl_0 -max 3.0 -min -1.0 [get_ports {debug_led[*]}]
# set_input_delay  -clock clk_pl_0 -max 2.0 -min  0.5 [get_ports {sw_in[*]}]

# Any asynchronous reset input should be excluded from setup/hold analysis
set_false_path -from [get_ports ext_rst_n]
```

### Relevance to Your Project

Since the BRAM demo's only interface to the outside world is PS-internal AXI plus USB-UART (handled entirely inside the PS, no PL pins involved), your XDC needs are minimal — the one constraint that actually matters is declaring the PL fabric clock so Vivado times the internal register paths in `kv260_top.vhd`. If `kv260_top.xdc` is missing a `create_clock` line, Vivado will report "no clocks found" and implicitly skip timing closure checks on your design.

## Kria KV260 / K26 SoM

### Key Findings

- Boot mode is selected by MODE[3:0] pins, exposed at the SOM connector for the carrier card to drive — KV260/K26 Starter Kits ship preconfigured for QSPI32 boot from eMMC by default.
- PS MIO signals on the K26 SOM are fixed at the hardware level (bank 501) — carrier card and PL designs only have access to EMIO-routed signals, not raw MIO, since MIO allocation is baked into the SOM itself and not reconfigurable per-carrier.
- Since 2022.1, the default Kria Linux reference bitstream maps an EMIO signal to the carrier's fan-control pin — a concrete example of how EMIO bridges PS peripherals to carrier-specific PL logic on KV260.
- For any non-standard pin definitions beyond the default carrier, the K26 SOM XDC file (provided in AMD's board files) is the canonical source — the K26 board file encodes the MIO configuration fixed by the SOM hardware design itself.
- Custom carrier card designers are pointed to UG1091 (Kria SOM Carrier Card Design Guide) for full power-domain and pinout detail — general web search didn't surface power-domain specifics beyond pointing to this primary document, worth pulling up directly if you ever design a custom carrier.
- The official "Baremetal Flow Example" in Kria Apps docs describes exactly your project's pattern: connect an AXI BRAM controller's `S_AXI` to the PS's `M_AXI_HPM0` port, wire `BRAM_PORTA` to a Block Memory Generator, and enable HPM0 in the PS configuration — this is effectively the reference design your demo is built from (page itself returned 403 on direct fetch this run, so details are from the indexed summary, not a live read).

### Code Example

```tcl
# PS8 configuration enabling the AXI master port the BRAM demo depends on
# (HPM0 must be explicitly enabled or M_AXI_HPM0_FPD will not exist on the PS cell)
set_property -dict [list \
  CONFIG.PSU__USE__M_AXI_GP0              {1} \
  CONFIG.PSU__MAXIGP0__DATA_WIDTH         {32} \
  CONFIG.PSU__UART0__PERIPHERAL__ENABLE   {1} \
  CONFIG.PSU__UART0__PERIPHERAL__IO       {MIO 38 .. 39} \
] [get_bd_cells zynq_ps]
```

### Relevance to Your Project

The "Baremetal Flow Example" from Kria's own docs is essentially a description of what `kv260-axi-bram-demo` already implements (BRAM controller -> M_AXI_HPM0 -> bare-metal read/write/printf). If you haven't already, it's worth diffing your `create_bd.tcl` against that reference to confirm `PSU__MAXIGP0__DATA_WIDTH` and HPM0 enablement match the documented defaults — a width mismatch here is a classic source of "BRAM appears at the wrong offset" bugs.

## AMD/Xilinx Tool Updates (Vivado/Vitis 2025.x)

### Key Findings

- The AXI BRAM Controller IP's official performance/utilization documentation now reflects Vivado 2025.1 as its baseline tool version — confirms the IP's current characterization data is current for the toolchain your project targets, not a stale older-version snapshot.
- AXI BRAM Controller's ECC feature (`C_ECC=1`) is only available for 32-, 64-, or 128-bit BRAM data widths, supports Hamming or HSIAO codes, and adds one extra clock cycle of datapath latency plus a second AXI4-Lite port for ECC status/control register access.
- The AXI BRAM Controller can be configured for single-port or dual-port access to the underlying Block Memory Generator, and supports both AXI4 and AXI4-Lite control modes — relevant if a future revision of the demo wants true dual-port (read+write concurrently) access instead of one port at a time.
- General release-note search for "Vivado 2025.1 / Vitis 2025.1" surfaced the official UG973 (Vivado) release notes document but did not yield specific itemized new-feature bullets distinct from the already-documented 2025.2 changes covered in a previous digest — recommend pulling UG973 2025.1 directly (docs.amd.com) if a precise 2025.1-only changelog is needed, since search results mostly indexed the document's existence rather than its content this round.
- A 2025.1-dated community project (MicroBlaze V + BMP180 sensor on KR260) confirms the bare-metal Vitis flow is being actively exercised and published against 2025.1 by the community, a reasonable signal of toolchain stability for embedded/bare-metal use cases at this version.
