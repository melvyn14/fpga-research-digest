## Executive Summary
- **Major reversal: AMD has walked back the Vivado 2026.1 free-tier Linux removal.** After the BASIC tier's Linux drop (shipped quietly in 2026.1 release notes on May 25) triggered sustained community backlash — Tom's Hardware, It's FOSS, Slashdot, Hacker News — AMD Embedded posted an official statement: *"We've heard the feedback from the FPGA and Linux developer community regarding upcoming Vivado licensing changes, and we will continue Linux support for all Vivado subscription tiers – including the free (BASIC) subscription with the upcoming Vivado 2026.1 release."* This directly resolves the multi-day "watch this space" item flagged in prior digests: a Linux build host on the free BASIC tier remains viable going into 2026.1, removing the forced choice between paying for CORE (~$1,200–$1,800/yr) or switching to Windows. One caveat worth tracking: AMD's stated expectation is still that BASIC is for "simple, entry-level needs" with "limited simulation and debug support," while production-grade workflows are pushed toward paid tiers — so this is a reprieve for hobbyist/individual use (this project's case), not a reversal of the tiering model itself.
- **A real, distinct AXI BRAM Controller timing bug surfaced this round**: when an `axi_bram_ctrl` is connected through the legacy **AXI Interconnect** (not SmartConnect), the controller can assert its BRAM write-enable one clock early, causing an extra word to be written — one of which lands at the *previous* address accessed, not the intended one. The bug was not reproduced when using AXI SmartConnect instead. This project already uses point-to-point/SmartConnect-style connections per the existing two-controller topology, so the practical action is simply to confirm `create_bd.tcl` is not instantiating a legacy `axi_interconnect` anywhere in the BRAM write path.
- The AXI4 rule that `AWVALID` must never wait on `WREADY` (or vice versa) has an underappreciated corollary: if a master holds `BREADY` low, a correctly-built slave must also gate `AWREADY`/`WREADY` low, or it risks accepting a second transaction whose write response then has nowhere to go (dropped/lost response). Not a live risk for this project's `axi_bram_ctrl`-based, single-master, sequential-transaction pattern, but a good check if a custom AXI-Lite slave is ever hand-rolled here instead of using the standard IP.
- The Kria boot firmware's PMU configuration object is deliberately locked down post-boot: `boot.scr` closes the PMU firmware node specifically to prevent any *new* power domain from being enabled after the initial SOM+overlay config load — relevant background if this project's bring-up ever needs an additional PL power domain or peripheral that wasn't part of the original carrier-card config object.

## AXI Protocol / AXI-Lite / AXI-Stream
### Key Findings
- New, distinct finding from this round: the **AXI BRAM Controller can assert write-enable one clock early when connected via the legacy AXI Interconnect IP**, causing an extra word write where one write lands at the previously-accessed address rather than the current one — reported as not reproducible when the same topology uses AXI SmartConnect instead. A suggested mitigation in the same thread is to ensure the BRAM "Enable" signal is correctly tied so the spurious extra write-enable clock is gated off.
- The AXI4 spec's `AWVALID`/`WREADY` independence rule has a corollary often missed in hand-rolled slaves: if `BREADY` is held low by the master, the slave must also de-assert `AWREADY`/`WREADY` to avoid accepting a transaction whose write response (`BRESP`) then has no consumer — a "lost response" deadlock class distinct from the basic AWVALID/WVALID ordering bug.
- Reconfirmed from zipcpu's AXI-Lite teardown of Xilinx's own demo wizard template: a well-built AXI-Lite slave should present `AWREADY` high by default when idle, so `AWVALID`+`AWREADY` can be high together on the very first cycle of a transaction — Xilinx's own generated template instead forces an extra wasted cycle by deasserting `AWREADY` until after `AWVALID` arrives.
- AXI-Lite from `axi_bram_ctrl` remains strictly single-beat/32-bit/no-burst (reconfirmed); this project's word-at-a-time write/readback loop in `main.c` already matches this ceiling exactly.

### Code Example
```tcl
# Defensive check for create_bd.tcl: confirm no legacy axi_interconnect cells
# exist anywhere in the BRAM write path, since the early-write-enable bug
# was reported specifically against axi_interconnect (not smartconnect).
set bad_cells [get_bd_cells -quiet -filter {VLNV =~ "*:axi_interconnect:*"}]
if {[llength $bad_cells] > 0} {
    puts "WARNING: legacy axi_interconnect cell(s) found: $bad_cells"
    puts "         AXI BRAM Controller early-write-enable bug was reported"
    puts "         against this IP; verify with a hardware readback sweep."
} else {
    puts "OK: no legacy axi_interconnect cells in block design."
}
```

### Relevance to Your Project
This project's existing two-`axi_bram_ctrl` topology should be checked once against this specific bug class: confirm `create_bd.tcl` connects each controller through SmartConnect (or direct point-to-point AXI-Lite from the PS HPM port, if no interconnect IP is used at all) rather than a legacy `axi_interconnect` cell. If confirmed clean, this bug is not a risk; if a legacy interconnect is present, it's worth a targeted hardware test writing a known pattern and checking that no word lands at an unintended adjacent address.

## Vivado Block Design / IP Integrator
### Key Findings
- A specific, easy-to-miss Address Editor guideline surfaced this round: **avoid assigning address 0 to any peripheral's base address** — some software drivers treat a 0 base address as equivalent to a null/unset pointer and can trigger driver-level assertions purely from the address value, independent of whether the mapping itself is otherwise valid.
- Reconfirmed: address ranges must be aligned such that the base address has enough trailing zero bits to cover the range size (e.g., a 64KB range needs the low 16 bits all zero) — BRAM0 (`0xA0000000`) and BRAM2 (`0xA0010000`) both already satisfy this for their 64KB ranges.
- `assign_bd_address` auto-maps an unmapped slave segment into a master's address space; `set_property` is then used on the resulting address segment object to override the auto-assigned range/offset if the default isn't what's wanted — this is the scriptable equivalent of manually typing an address into the Address Editor's Master Base Address column.
- Re-validating with `validate_bd_design` after any address change remains mandatory — it catches overlap and most negotiation issues, though (per the previously-reported Digilent decoder-width bug) not synthesized-decoder-width mismatches.

### Code Example
```tcl
# Scripted equivalent of manual Address Editor entry: map BRAM0 and BRAM2
# into the PS HPM master's space, then assert non-zero base addresses as
# a defensive check (address 0 can trigger driver-level null-pointer-style
# assertions in some software stacks, independent of mapping validity).
assign_bd_address -target_address_space [get_bd_addr_spaces ps_hpm0] \
    [get_bd_addr_segs axi_bram_ctrl_0/S_AXI/Mem0] -range 64K -offset 0xA0000000

assign_bd_address -target_address_space [get_bd_addr_spaces ps_hpm0] \
    [get_bd_addr_segs axi_bram_ctrl_2/S_AXI/Mem0] -range 64K -offset 0xA0010000

foreach ctrl {axi_bram_ctrl_0 axi_bram_ctrl_2} {
    set seg [get_bd_addr_segs -of_objects [get_bd_cells $ctrl]]
    if {[get_property OFFSET $seg] == 0} {
        puts "WARNING: $ctrl mapped at address 0 -- some drivers assert on this"
    }
}
validate_bd_design
```

### Relevance to Your Project
Neither BRAM0 nor BRAM2 is mapped to address 0, so the null-address driver-assertion pitfall doesn't apply today — but it's a one-line defensive check worth keeping in `create_bd.tcl` if the address map is ever regenerated from scratch rather than edited incrementally, since a future re-run of automatic address assignment without explicit offsets could in principle place a peripheral at 0.

## Vivado TCL Scripting
### Key Findings
- Reconfirmed the three Vivado launch modes relevant to this project's `create_bd.tcl` workflow: `vivado -mode gui` (interactive development), `vivado -mode tcl` (interactive console, no GUI), and `vivado -mode batch -source script.tcl` (the correct mode for unattended/CI regeneration) — batch mode opens Vivado, runs the script, and exits automatically on completion or error.
- A commonly recommended non-project-mode directory layout splits scripts by role: `scripts/` for TCL build scripts, `constraints/` for XDC, `ip/` for IP repo sources, `rtl/` for hand-written HDL, and `tb/` for testbenches — useful as a sanity-check against this project's existing `kv260_claude/kv260/{tcl,vhdl,src}` layout, which already follows the same separation-by-role principle.
- Non-project mode has no implicit checkpointing (reconfirmed); anything not explicitly written via `save_bd_design` / `write_checkpoint` is lost when the Tcl interpreter session ends.
- The project-vs-non-project mode tradeoff is explicitly about discipline vs. flexibility: project mode prevents accidentally skipping a build stage, while non-project mode trades that safety net for easier directory-structure and config-management control — a relevant tradeoff to keep in mind if this project's TCL flow is ever restructured.

### Code Example
```tcl
# Headless regeneration entry point matching this project's tcl/create_bd.tcl
# pattern -- batch mode is correct for CI/unattended runs, not interactive
# tcl mode (which stays open) or gui mode (which requires a display).
#   vivado -mode batch -source create_bd.tcl -log create_bd.log -journal create_bd.jou

# Explicit checkpoint discipline required in non-project mode -- nothing is
# auto-saved when the interpreter exits.
validate_bd_design
save_bd_design
write_checkpoint -force ./checkpoints/post_bd.dcp
```

### Relevance to Your Project
`create_bd.tcl`'s existing validate-then-save discipline already matches documented best practice for non-project mode, and the project's `tcl/`, `vhdl/`, `src/` directory split is consistent with the recommended role-based layout (substituting `src/` for the more generic `rtl/`+`tb/` split, appropriate since this is mostly a software/bare-metal-heavy project rather than an HDL-simulation-heavy one). No action needed beyond keeping the batch-mode invocation as the canonical regeneration path documented for collaborators.

## Vitis Bare-Metal / Standalone
### Key Findings
- Reconfirmed the BSP stdout configuration path: in the BSP settings UI, select the standalone OS under the processor, open "Modify BSP Settings," and set `stdout` under the `standalone` category to the desired UART — this is the GUI-level mechanism underlying the UART0-stdout default this project's `xil_printf` calls rely on.
- A concrete `xil_printf` limitation worth knowing if the project's PASS/FAIL print formatting is ever extended: `xil_printf` does **not** support the `%f` floating-point format specifier — only `%d`, `%l`, `%x`, `%c`, and `%s` are supported, since it's a lightweight implementation that intentionally omits floating-point formatting to save code size.
- The standard `XScuGic` bring-up example pattern (lookup config → `CfgInitialize` → connect handler → `XScuGic_Enable(&ScuGic, <interrupt_id>)`) is available as ready-made example code under the `scugic/examples` directory in Xilinx's embeddedsw repository structure — useful as a direct reference if a timer or AXI interrupt is ever added to this currently polled, interrupt-free design.
- Linker script (`lscript.ld`) memory region base addresses are project-specific and must be hand-verified against the actual hardware address map (reconfirmed); a concrete example from a different platform shows the RPU-targeted linker script requiring the DDR region to start above `0x70000000` and stay under 256MB for that platform's memory map — illustrating that linker base addresses are never safe to assume carry over between platforms/projects and must always be checked against the project's own address map.

### Code Example
```c
#include "xil_printf.h"
#include "xparameters.h"
#include "xil_io.h"

/* xil_printf has no %f support -- use integer-scaled formatting if any
 * future diagnostic output needs a fractional value (e.g. a computed
 * pass rate), rather than assuming floating-point format specifiers work. */
void print_pass_rate(u32 passed, u32 total) {
    u32 pct_x10 = (total > 0) ? (passed * 1000) / total : 0; /* one decimal, scaled by 10 */
    xil_printf("PASS RATE: %d.%d%%\r\n", pct_x10 / 10, pct_x10 % 10);
}

#define BRAM0_BASEADDR XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR /* 0xA0000000 */
#define BRAM2_BASEADDR XPAR_AXI_BRAM_CTRL_2_S_AXI_BASEADDR /* 0xA0010000 */
```

### Relevance to Your Project
The `%f`-unsupported limitation is a real constraint if this project's PASS/FAIL reporting is ever extended to print a computed statistic (e.g. percentage of words matched) rather than a simple binary PASS/FAIL per word — the scaled-integer workaround above avoids silently truncated or garbage output from an unsupported format specifier. The GIC/interrupt example reference and linker-script base-address reminder remain background knowledge for this project's current polled, single-region design, useful primarily if a future revision adds an interrupt source or a new memory region.

## XDC Timing Constraints
### Key Findings
- The official Kria platform documentation pattern for identifying clock domains: each platform's docs explicitly enumerate the PL design's clocks by source, frequency, and function, and call out which of those clocks are exposed as a "Platform interface" usable by accelerators/peripherals versus purely internal — a useful template for documenting this project's own clock usage (effectively just `pl_clk0` from the PS) even though the project currently has only one clock domain.
- A concrete, real-world `set_input_delay`/`set_output_delay` example (from a Zynq RGMII Ethernet FMC reference design) shows the actual syntax pattern used in production Xilinx-ecosystem XDC: `set_input_delay -clock [get_clocks *_gmii_to_rgmii_0_0_rgmii_rx_clk] -max -1.2 [get_ports ...]` — note the explicit `-clock` reference to a named generated clock and the negative `-max` value, which is normal for certain source-synchronous interface timing budgets and not a typo.
- Reconfirmed: `create_clock` should never be hand-applied to a PS-derived or MMCM/PLL-generated clock pin (including `pl_clk0`) — Vivado auto-derives this the moment the clock network is connected in the block design.
- `set_clock_groups -asynchronous` remains the correct mechanism for declaring two genuinely independent clock domains (e.g. an Ethernet RGMII clock vs. a fabric clock) as not requiring cross-domain timing closure against each other.

### Code Example
```tcl
# This project's actual clock-domain count is one (pl_clk0, PS-derived,
# auto-constrained) -- so the real-world RGMII example below is purely a
# reference pattern for if/when a second PL clock domain with board-level
# I/O is ever added (e.g. a PMOD peripheral), not something to add today.

# Reference syntax from a production Zynq RGMII XDC (NOT this project's need):
#   set_input_delay -clock [get_clocks rgmii_rx_clk] -max -1.2 [get_ports rgmii_rxd[*]]
#   set_input_delay -clock [get_clocks rgmii_rx_clk] -min -2.5 [get_ports rgmii_rxd[*]]

# If a second independent clock domain is ever introduced to this design:
create_clock -period 8.000 -name pmod_clk [get_ports pmod_clk_p]
set_clock_groups -asynchronous \
    -group [get_clocks pl_clk0] \
    -group [get_clocks pmod_clk]
```

### Relevance to Your Project
Confirms again that this project's actual XDC timing-constraint surface area is minimal (USB-UART pins plus an auto-derived `pl_clk0`), and that the RGMII-style `set_input_delay`/`set_output_delay` patterns above only become relevant the day a board-level, source-synchronous PL peripheral with its own clock is added — not applicable to the current PS-only AXI-to-BRAM topology. Worth keeping the documented-clock-table habit (source/frequency/function per the Kria platform docs pattern) as good practice even for this project's single-clock design, since it's cheap and makes future additions easier to reason about.

## Kria KV260 / K26 SoM
### Key Findings
- New detail on the PMU configuration object lifecycle this round: the FSBL first loads a minimal "SOM-only" PMU configuration object, after which the Kria Starter Kit boot firmware dynamically loads a "PMU object overlay" specific to the attached carrier card that extends the configuration to enable the carrier's actual subsystems and physical pin mappings — by default, permission to load any *further* overlay beyond this initial one is disabled for the KV260, and `boot.scr` explicitly closes the PMU firmware node in Linux to lock this down post-boot, since allowing arbitrary additional overlay loads is explicitly called out as "not secure and not system friendly."
- Reconfirmed: boot mode is selected by physical `MODE[3:0]` pin strapping on the carrier card, with these pins broken out at the SOM connector specifically so different carrier card designs can choose different default boot devices; the Kria Starter Kit ships preset to QSPI32.
- Reconfirmed: K26/K24 board file MIO configuration is fixed by the physical SOM hardware design and is selected via the `kv260_som` (or equivalent) board file in the block design TCL, not freely reassignable per-project.
- Reconfirmed: WIC (Wic disk image) boot images require boot firmware from the 2026.1+ release line; older boot firmware is explicitly incompatible with WIC images — not relevant to this project's bare-metal (non-WIC, non-Linux-image) flow, but worth tracking if the board's firmware is ever updated for unrelated reasons.

### Code Example
```tcl
# Bare-metal projects don't touch the PMU configuration object directly --
# that's owned by the Kria boot firmware/FSBL flow before the bare-metal
# app ever runs. This is purely documentation of what's already locked in
# by the time main.c executes on the Cortex-A53:
#
#   1. FSBL loads "SOM-only" PMU config object (minimal, board-independent)
#   2. Boot firmware loads carrier-card-specific PMU overlay (enables the
#      KV260 Starter Kit carrier's actual subsystems/pin mappings)
#   3. Further overlay loading is disabled by default -- the power-domain
#      map is fixed for the remainder of the boot, including during this
#      project's bare-metal application execution.
#
# Practical implication: if this project's BRAM/PL design ever needs a
# carrier-card power domain NOT enabled by the default KV260 overlay, that
# requires a boot-firmware-level config change, not anything settable from
# the bare-metal application or even from create_bd.tcl.
```

### Relevance to Your Project
This is useful background for understanding why the project's PS-to-PL AXI-BRAM design "just works" without any power-domain bring-up code in `main.c`: by the time the bare-metal app boots, the PMU has already enabled exactly the subsystems the KV260 Starter Kit's default overlay specifies, and that configuration is locked against further changes. If a future revision of this project ever needs a carrier-card peripheral or power domain outside that default overlay's scope, the fix would need to happen at the boot-firmware/PMU-overlay level — outside the scope of `create_bd.tcl` or the bare-metal application entirely.
