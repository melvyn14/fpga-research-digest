# FPGA Research Digest - 2026-11-14

## Executive Summary
- **AXI-Lite generated templates have known handshake bugs** — Vivado's AXI-Lite slave core was shown by formal verification to contain errors; always review generated code and run a simulation or formal check before trusting it in your BRAM demo.
- **TVALID must stay asserted until TREADY goes high** — a common source of lockups in custom masters; once you assert TVALID, you cannot deassert it until the transfer completes.
- **BRAM controller S_AXI connects to HPM0 FPD (or HPM0 LPD)** — the KV260/K26 AXI BRAM flow connects the BRAM controller's `S_AXI` to `M_AXI_HPM0_FPD`; HPM0 LPD is also valid depending on Vitis version and power domain preference.
- **write_bd_tcl + validate_bd_design is the proper TCL round-trip** — always call `validate_bd_design` after recreating a block design from TCL to propagate IP parameters; without it, generated output products may be stale.
- **Boot FW v1.06 targets the 2025.2 code base** — if running Vivado/Vitis 2025.1, verify your Kria KV260 boot firmware version; v1.05 had a known DisplayPort issue and v1.06 aligns to the 2025.2 SDT flow.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings
- **Vivado-generated AXI-Lite slave templates have formal verification failures** — ZipCPU applied formal properties to the Vivado-generated core (as of 2018.3; pattern persists) and found multiple handshake errors in the write-channel logic. Review any generated template before integrating.
- **VALID must remain asserted** — once a master asserts `AWVALID`, `WVALID`, or `ARVALID`, the signal must remain high until `AWREADY`/`WREADY`/`ARREADY` goes high. Deassert-before-ready is a protocol violation that can stall or corrupt the AXI interconnect.
- **TVALID cannot depend on TREADY (AXI-Stream)** — the master side must not gate `TVALID` on whether `TREADY` is high. The reverse (slave making `TREADY` depend on `TVALID`) is legal but should be avoided for maximum interoperability.
- **TLAST stuck low hangs the AXI DMA** — a common cause of `S2MM` DMA lockups is custom IP that never drives `TLAST` high. The DMA engine waits for a completed packet; without `TLAST`, the transfer never ends.
- **Response state bypass bug** — in OHWR's AXI-Lite bridge, when `wb.ack` and `wb.stall` changed in the same cycle, the `RESPONSE_READ` state was skipped, leaving the AXI-Lite handshake incomplete. Watch for similar edge cases in custom FSMs.
- **AXI Protocol Checker IP** — add Vivado's built-in AXI Protocol Checker to the block design during debug to catch handshake violations in simulation or on hardware before they cause silent data corruption.

### Code Example
```vhdl
-- Safe AXI-Lite write-response FSM skeleton (bare minimum)
-- Prevents the "skip RESPONSE state" bug
type axi_state_t is (IDLE, ADDR_ACK, DATA_ACK, RESP);
signal state : axi_state_t := IDLE;

process(clk)
begin
  if rising_edge(clk) then
    case state is
      when IDLE =>
        s_axi_awready <= '1';
        s_axi_wready  <= '0';
        if s_axi_awvalid = '1' then
          state <= ADDR_ACK;
        end if;

      when ADDR_ACK =>
        s_axi_awready <= '0';
        s_axi_wready  <= '1';
        if s_axi_wvalid = '1' then
          -- latch write data here
          state <= DATA_ACK;
        end if;

      when DATA_ACK =>
        s_axi_wready  <= '0';
        s_axi_bvalid  <= '1';
        s_axi_bresp   <= "00";  -- OKAY
        state <= RESP;

      when RESP =>
        -- hold BVALID until master accepts
        if s_axi_bready = '1' then
          s_axi_bvalid <= '0';
          state <= IDLE;
        end if;
    end case;
  end if;
end process;
```

### Relevance to Your Project
Your `kv260_top.vhd` acts as a wrapper; the AXI-Lite masters are inside the Zynq PS (M_AXI_HPM0_FPD). Your BRAM controllers are the AXI-Lite slaves. If you ever add a custom AXI-Lite slave in VHDL for control registers (e.g., test enable/disable), use the FSM pattern above to avoid the response-skip bug. The AXI Protocol Checker can be added to `BRAM0`/`BRAM2` ports in the block design to catch timing violations during simulation.

## Vivado Block Design / IP Integrator

### Key Findings
- **Connection Automation wires S_AXI → M_AXI_HPM0_FPD automatically** — in Vivado IPI, after adding the AXI BRAM Controller, clicking *Run Connection Automation* and selecting `S_AXI` will connect it to `M_AXI_HPM0_FPD` on the Zynq UltraScale+ PS and insert the AXI SmartConnect. Deselect HPM1 FPD if unused to avoid undriven ports.
- **Disable unused HPM ports explicitly** — leaving unused AXI master ports enabled on the Zynq PS IP can cause DRC errors during bitstream generation. Uncheck unused HPM/HPC ports in the PS customization dialog.
- **Address Editor must be re-assigned after adding IP** — when new AXI IP is added, the address is initially unmapped. Use *Assign All* in the Address Editor, then verify that `BRAM0` maps to `0xA000_0000` and `BRAM2` maps to `0xA001_0000` to match your bare-metal `main.c` base addresses.
- **validate_bd_design is mandatory after TCL recreation** — propagated parameters (data widths, clock frequencies) are not reflected in a recreated design until `validate_bd_design` is explicitly called.
- **IP lock after part mismatch** — if the board/part setting of a recreated project does not match the original, all IP in the block design becomes locked. Always set the board part at the top of the recreate script before calling `create_bd_design`.

### Code Example
```tcl
# Minimal KV260 block design setup skeleton (IPI Tcl)
create_project kv260_demo ./kv260_demo -part xck26-sfvc784-2LV-c
set_property BOARD_PART xilinx.com:kv260_som:part0:1.4 [current_project]

create_bd_design "kv260_bd"
update_compile_order -fileset sources_1

# Add Zynq UltraScale+ PS
set ps [create_bd_cell -type ip -vlnv xilinx.com:ip:zynq_ultra_ps_e:3.5 zynq_ultra_ps_e_0]
apply_bd_automation -rule xilinx.com:bd_rule:zynq_ultra_ps_e \
  -config {apply_board_preset "1"} [get_bd_cells zynq_ultra_ps_e_0]

# Add AXI BRAM Controller + BRAM
set bram_ctrl [create_bd_cell -type ip -vlnv xilinx.com:ip:axi_bram_ctrl:4.1 axi_bram_ctrl_0]
set bram      [create_bd_cell -type ip -vlnv xilinx.com:ip:blk_mem_gen:8.4  blk_mem_gen_0]
set_property CONFIG.Memory_Type {True_Dual_Port_RAM} [get_bd_cells blk_mem_gen_0]

# Connection automation
apply_bd_automation -rule xilinx.com:bd_rule:axi4 \
  -config {Master "/zynq_ultra_ps_e_0/M_AXI_HPM0_FPD" Clk "Auto"} \
  [get_bd_intf_pins axi_bram_ctrl_0/S_AXI]
connect_bd_intf_net [get_bd_intf_pins axi_bram_ctrl_0/BRAM_PORTA] \
                    [get_bd_intf_pins blk_mem_gen_0/BRAM_PORTA]

# Assign address
assign_bd_address
set_property offset 0xA0000000 \
  [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]

validate_bd_design
save_bd_design
```

### Relevance to Your Project
This directly mirrors your `create_bd.tcl` structure — two BRAM controllers at `0xA000_0000` and `0xA001_0000`. Running `assign_bd_address` followed by explicit `set_property offset` ensures the addresses in the XSA match your bare-metal write targets.

## Vivado TCL Scripting

### Key Findings
- **`write_bd_tcl` exports only the block design; `write_project_tcl` exports the full project** — for version control, the recommended pattern is `write_project_tcl -no_copy_sources -use_bd_files -force <name>.tcl`; the `-use_bd_files` flag keeps `.bd` files as source rather than inlining them.
- **Block design layout is not saved by default** — use `-include_layout` with `write_bd_tcl` to preserve the IP placement on the canvas.
- **`-all_properties` captures non-default settings** — without this flag, properties set to their defaults are omitted from the output; non-obvious configuration choices may be silently lost.
- **Non-project mode: set `synth_checkpoint_mode` to None for `.bd` files** — before synthesizing in non-project mode, run `set_property synth_checkpoint_mode None [get_files <design>.bd]` and then call `generate_target all` to produce the output products.
- **Custom IP repository must be registered before `create_bd_design`** — the recreate script includes a pre-check for this, but the IP catalog must be populated via `set_property ip_repo_paths` before any `create_bd_cell` call that uses custom IP.
- **`validate_bd_design` after creation** — without this call, propagated parameters are not reflected; run it before `generate_target all`.

### Code Example
```tcl
# Save the block design as a standalone TCL script (run from Vivado Tcl console)
write_bd_tcl -force -include_layout -all_properties \
  ./tcl/create_bd.tcl

# Non-project mode: synthesize a design with a block design
read_vhdl   ./vhdl/kv260_top.vhd
read_bd     ./bd/kv260_bd/kv260_bd.bd
set_property synth_checkpoint_mode None [get_files ./bd/kv260_bd/kv260_bd.bd]
generate_target all [get_files ./bd/kv260_bd/kv260_bd.bd]
read_xdc    ./constraints/kv260.xdc
synth_design -top kv260_top -part xck26-sfvc784-2LV-c
opt_design
place_design
route_design
write_bitstream -force ./output/kv260_top.bit
write_hw_platform -fixed -force -include_bit ./output/kv260.xsa
```

### Relevance to Your Project
Your `create_bd.tcl` is the authoritative source of truth for the block design. Keep it updated with `write_bd_tcl -include_layout -all_properties` after every IP change so a fresh checkout can fully recreate the hardware. The non-project-mode script above can serve as a CI-friendly build that runs in `vivado -mode batch -source build.tcl`.

## Vitis Bare-Metal / Standalone

### Key Findings
- **`xil_printf` output is controlled by `standalone_stdin`/`standalone_stdout` BSP settings** — in Vitis (both classic and Unified), the console UART is selected by setting these properties in `vitis-comp.json` (Unified) or the BSP settings GUI. If `xil_printf` produces no output, check that `standalone_stdout` points to the correct UART instance (`psu_uart_1` for the KV260 USB-UART path).
- **Linker script `lscript.ld` is auto-generated but editable** — it appears in the application's `src/` folder; edit stack/heap sizes here. A 1 MB heap (`0x100000`) is a reasonable starting point for bare-metal demos.
- **BSP `xil_exception.h` macros manage interrupts** — `Xil_ExceptionInit()`, `Xil_ExceptionRegisterHandler()`, and `Xil_ExceptionEnable()` are the standard bare-metal interrupt setup path for Cortex-A53.
- **GIC (Generic Interrupt Controller) driver is `XScuGic`** — on the Zynq UltraScale+ (K26), use `XScuGic_Initialize`, `XScuGic_Connect`, and `XScuGic_Enable` from `xscugic.h` to register and enable interrupt handlers from the PL.
- **Cache coherency for memory-mapped I/O** — when writing to PL peripherals over AXI, disable the D-cache for the BRAM address region, or use `Xil_DCacheFlushRange` after writes and `Xil_DCacheInvalidateRange` before reads to prevent stale cache lines from masking write-back updates.

### Code Example
```c
#include "xil_printf.h"
#include "xil_cache.h"
#include "xil_io.h"
#include "sleep.h"

#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL
#define PATTERN     0xDEADBEEFUL

int main(void) {
    xil_printf("KV260 AXI-BRAM test start\r\n");

    /* Flush D-cache for BRAM regions before access */
    Xil_DCacheFlushRange(BRAM0_BASE, 0x10000);
    Xil_DCacheFlushRange(BRAM2_BASE, 0x10000);

    /* Write pattern to BRAM0 */
    Xil_Out32(BRAM0_BASE, PATTERN);
    Xil_Out32(BRAM0_BASE + 4, ~PATTERN);

    /* Write pattern to BRAM2 */
    Xil_Out32(BRAM2_BASE, PATTERN);
    Xil_Out32(BRAM2_BASE + 4, ~PATTERN);

    /* Invalidate before read */
    Xil_DCacheInvalidateRange(BRAM0_BASE, 0x10000);
    Xil_DCacheInvalidateRange(BRAM2_BASE, 0x10000);

    /* Verify */
    u32 r0 = Xil_In32(BRAM0_BASE);
    u32 r2 = Xil_In32(BRAM2_BASE);
    if (r0 == PATTERN && r2 == PATTERN)
        xil_printf("PASS: BRAM0=0x%08X  BRAM2=0x%08X\r\n", r0, r2);
    else
        xil_printf("FAIL: BRAM0=0x%08X  BRAM2=0x%08X\r\n", r0, r2);

    return 0;
}
```

### Relevance to Your Project
This directly matches your project's goal (Cortex-A53 write/read-back PASS/FAIL over USB-UART). The `Xil_DCacheFlush`/`Invalidate` calls are the most common reason a bare-metal AXI-BRAM test shows stale data — the write hits the cache but never propagates to the PL, so the read-back returns the cached value rather than what's in BRAM.

## XDC Timing Constraints

### Key Findings
- **`set_input_delay` and `set_output_delay` reference the rising edge by default** — use `-clock_fall` to reference the falling edge for DDR-style I/O. Without the flag, both setup and hold checks target the rising clock edge.
- **XPM CDCs are incompatible with `set_clock_groups`** — `set_clock_groups` takes higher precedence and overwrites the constraints embedded in XPM clock-domain-crossing macros. Use `set_false_path` or `set_max_delay -datapath_only` for async paths involving XPM CDCs.
- **`set_clock_groups` silences the timing report but does not make the crossing safe** — this is the most misunderstood constraint in Vivado. Use it only after confirming that the CDC is handled in RTL (synchronizer FFs, handshake, or FIFO).
- **Ordering within the XDC matters** — AMD recommends: (1) clock definitions, (2) generated clocks, (3) I/O delays, (4) timing exceptions, (5) clock groups. Placing `set_clock_groups` before `set_input_delay` can produce incorrect analysis.
- **For pure PS-to-PL AXI designs, I/O delay constraints are not required** — the `set_input_delay`/`set_output_delay` commands apply to I/O pins. Internal PS-to-PL AXI paths are constrained automatically by the Zynq UltraScale+ PS IP. Only add I/O constraints if you have external physical I/O.

### Code Example
```tcl
# kv260.xdc – minimal constraints for a bare-metal AXI-BRAM demo
# (No external I/O, so no set_input_delay / set_output_delay needed)

# PL fabric clock driven from PS (100 MHz example)
# This clock is defined automatically by the Zynq PS IP;
# add it only if Vivado reports it as unconstrained.
# create_clock -period 10.000 -name pl_clk0 [get_pins zynq_ultra_ps_e_0/pl_clk0]

# If you have a debug ILA, constrain its clock too
# (ILA clock is usually the same as pl_clk0 — no extra constraint needed)

# Example: constrain an external PL pin if added later
# set_property PACKAGE_PIN <PIN_NAME> [get_ports {led[0]}]
# set_property IOSTANDARD LVCMOS18   [get_ports {led[0]}]
# set_output_delay -clock [get_clocks pl_clk0] -max 1.0 [get_ports {led[0]}]
# set_output_delay -clock [get_clocks pl_clk0] -min 0.0 [get_ports {led[0]}]
```

### Relevance to Your Project
Your current design routes everything through the PS AXI ports, so the Zynq PS IP provides all necessary timing constraints for the PS-to-PL path. The XDC file primarily needs `PACKAGE_PIN` / `IOSTANDARD` assignments for any PL I/O (e.g., LEDs or status outputs). If you later add a custom clock source or PL I/O peripherals, follow the ordering rule above.

## Kria KV260 / K26 SoM

### Key Findings
- **MIO banks:** The K26 has three MIO banks. Bank 500 handles onboard peripherals (QSPI, eMMC, I2C, TPM SPI) at 1.8V. Bank 501 carries PMU power-management and user I/O. Bank 502 is additional user I/O. All run from a 1.8V SOM rail — do not drive 3.3V on MIO pins.
- **Boot mode:** Starter Kits ship in QSPI32 boot mode. Boot firmware lives in the onboard QSPI flash and loads the PetaLinux image (or bare-metal BOOT.BIN) from SD card or eMMC. For a bare-metal demo, you need a `BOOT.BIN` on the SD card containing the FSBL, bitstream, and application ELF.
- **Boot FW v1.06 (Nov 2025)** targets the 2025.2 SDT code base. v1.05 had a known DisplayPort issue. Update the boot firmware if you are using features that depend on the boot image (e.g., secure boot, platform management).
- **HPM0 FPD vs. HPM0 LPD for PL peripherals** — both are valid AXI master ports for reaching PL IP. `HPM0_FPD` runs in the full power domain (higher performance); `HPM0_LPD` runs in the low power domain. For a simple BRAM demo, either works. `HPM0_FPD` is the conventional choice in AMD tutorials.
- **EMIO GPIO:** PL-side GPIO from the PS can be routed via EMIO (up to 96 bits). These are routed through the PL fabric and require constraints. MIO GPIO is simpler but has fewer pins and is used for onboard peripherals.
- **Dynamic MIO:** The KV260 and KR260 share the K26 SoM but differ in their carrier-specific MIO configuration. AMD uses the PMU's incremental configuration to apply carrier-specific MIO at boot rather than a fixed MIO map. Do not assume a static pinout between carrier card revisions.

### Code Example
```tcl
# BOOT.BIN creation using Vitis/bootgen (run from Vitis shell)
# boot.bif – Bootgen image format file for bare-metal KV260 demo
the_ROM_image:
{
  [bootloader, destination_cpu=a53-0] fsbl_a53.elf
  [destination_device=pl]            kv260_top.bit
  [destination_cpu=a53-0]            kv260_bram_test.elf
}
```

```bash
# Generate BOOT.BIN
bootgen -image boot.bif -arch zynqmp -o BOOT.BIN -w on

# Copy to SD card FAT32 partition
cp BOOT.BIN /media/$USER/boot/
```

### Relevance to Your Project
Your project boots from SD card. The `.bif` snippet above is the minimum needed to package your bitstream and ELF into a `BOOT.BIN`. Ensure the FSBL is the Vitis-generated `fsbl_a53.elf` for the K26 — it sets up DDR, the PL power rails, and the PS before jumping to your application. Without the FSBL, the PL clock (`pl_clk0`) is not stable and AXI transactions may fail silently.

## AMD/Xilinx Tool Updates (Vivado/Vitis 2025.x)

### Key Findings
- **Vitis Unified IDE is now the default; Classic Vitis IDE is deprecated** — as of Vitis 2025.1, the Unified IDE (Eclipse-based, with both hardware and software flows integrated) is the launch target. Classic IDE may still be accessible via `vitis -classic`, but future releases will remove it.
- **New AXI Switch IP in Vivado 2025.1** — a new RTL-based AXI Switch IP was added that supports bridging different AXI interface types and widths. **However**, AMD explicitly notes this IP is not intended for use in IPI/Block Diagram designs; it is for standalone RTL integration.
- **New device support:** Vivado 2025.1 adds Versal AI Edge Series Gen 2, Versal Prime Series Gen 2, and Spartan UltraScale+ device families.
- **New Pblock planner** — a redesigned Pblock (placement constraint) UI was introduced for more intuitive floorplanning on larger devices.
- **DSP Library updates** — new DSP library functions and AI Engine API updates are part of Vitis 2025.1; not directly relevant to bare-metal BRAM demo but relevant for future HLS or AI Engine work.
- **Ubuntu 24.04 Vitis launch issue** — community reports indicate Vitis 2025.1 may not start on Ubuntu 24.04. If you encounter this, check the AMD support forums for a workaround or use an older Ubuntu/RHEL version.
- **2025.1.1 point release** — a `v2025.1.1` point release exists (referenced in Vitis AI 5.1 notes). Check the AMD downloads page for patch availability.

### Code Example
```tcl
# Check tool version at the start of your build script
# to guard against running on the wrong Vivado release
set vivado_ver [version -short]
if { [string match "2025.1*" $vivado_ver] == 0 } {
    puts "ERROR: This script requires Vivado 2025.1.x, got $vivado_ver"
    exit 1
}
puts "INFO: Running on Vivado $vivado_ver"

# Example: use the new write_hw_platform (replaces write_dsa in older flows)
# write_hw_platform -fixed -force -include_bit ./output/kv260.xsa
```

### Relevance to Your Project
Your project specifies Vivado 2025.1 + Vitis 2025.1. The version guard above keeps CI builds reproducible. The deprecated Classic IDE warning means that if your Vitis workspace was created with Classic, consider migrating to the Unified IDE flow — the `vitis -classic` flag buys time, but the migration path exists now. Also confirm you are on 2025.1.1 if stability patches are available.
