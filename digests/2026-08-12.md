# FPGA Research Digest - 2026-08-12

## Executive Summary

- **AXI-Lite VALID/READY deadlock**: Never gate AWVALID/WVALID on RREADY — once VALID is asserted it must stay high until the corresponding READY fires. This is the single most common AXI-Lite bug on Zynq.
- **WSTRB byte-enable subtlety**: Each bit of WSTRB gates a byte lane on writes to the BRAM controller. Forgetting to drive WSTRB=4'hF on 32-bit writes silently corrupts BRAM contents.
- **Vivado 2025.1 BRAM/FIFO IP deprecation**: Block Memory Generator and FIFO Generator IPs are being phased out of the direct IP Catalog in 2025.x — use XPM macros (XPM_MEMORY_SPRAM / XPM_MEMORY_DPRAM) in RTL or keep using the AXI BRAM Controller IP in block designs.
- **Kria KV260 QSPI is locked read-only** to prevent bricking; bare-metal deployment must target JTAG or SD Card boot; JTAG requires PSU_INIT.TCL and removal of the SD card.
- **write_bd_tcl vs write_project_tcl**: Use `write_bd_tcl` (not `write_project_tcl`) to reproducibly re-create block designs from TCL — `write_project_tcl` with the `-use_bd_files` option references the `.bd` binary, breaking clean checkouts.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- **Handshake rule (spec-mandatory)**: A transfer completes when both VALID and READY are HIGH on the same rising clock edge. VALID must never be asserted based on the state of READY — doing so can create a circular dependency and deadlock both master and slave.
- **Once VALID is asserted it must remain asserted**: Deasserting VALID before READY rises violates the AXI spec and causes undefined slave behaviour in Xilinx IP (including the AXI BRAM Controller).
- **WSTRB pitfall**: WSTRB[n] = 1 means byte lane n of WDATA is valid. For the KV260 project writing 32-bit patterns over AXI-Lite, always drive WSTRB = 4'hF. Leaving any bit low silently prevents the corresponding byte from being written to BRAM.
- **AXI BRAM Controller early-write-enable bug**: A known issue exists where, when the AXI BRAM Controller is paired with AXI SmartConnect vs. AXI Interconnect, the BRAM enable/write-enable can fire one clock cycle earlier than expected, writing one extra word. Mitigation: gate the external BRAM EN signal or switch between interconnect variants.
- **AXI-Lite vs. AXI4 full**: AXI-Lite has no burst support — every transaction is a single beat. This makes it ideal for control-register or BRAM-address-mapped access from the PS on KV260, but throughput is limited to one 32-bit word per transaction.
- **XPM_FIFO_AXIL macro**: Vivado 2025.x ships an XPM_FIFO_AXIL parameterised macro for building AXI-Lite FIFOs directly in RTL without an IP core (UG974).

### Code Example

```vhdl
-- Correct AXI-Lite write channel slave handshake (no VALID/READY deadlock)
process(clk)
begin
  if rising_edge(clk) then
    if rst = '1' then
      awready <= '0';
      wready  <= '0';
    elsif awvalid = '1' and wvalid = '1' and awready = '0' and wready = '0' then
      -- Accept address and data simultaneously; only assert ready after BOTH valid
      awready <= '1';
      wready  <= '1';
      bvalid  <= '1';   -- respond immediately for single-beat AXI-Lite
    else
      awready <= '0';
      wready  <= '0';
      if bready = '1' then bvalid <= '0'; end if;
    end if;
  end if;
end process;

-- Always drive full-width write strobe for 32-bit writes
wstrb <= "1111";   -- all four byte lanes valid
```

### Relevance to Your Project

Your `main.c` writes 32-bit test patterns to BRAM0 (0xA0000000) and BRAM2 (0xA0010000) via the PS AXI-GP0 master. Verifying in simulation that WSTRB is always 4'hF and that the Cortex-A53 AXI master never deasserts WVALID mid-transaction will prevent the most common class of silent BRAM write failures.

## Vivado Block Design / IP Integrator

### Key Findings

- **Connection Automation**: Running "Run Connection Automation" after adding IP cores causes Vivado to automatically insert a Processor System Reset IP (for managing resets) and an AXI Interconnect (or SmartConnect in 2025.x) between the PS and peripheral IPs. Verify the inserted interconnect type — SmartConnect is preferred for UltraScale+.
- **Address Editor**: Each AXI slave must appear in the Address Editor with a unique, non-overlapping offset and range. For your project, BRAM0 at 0xA0000000 (64 KB) and BRAM2 at 0xA0010000 (64 KB) must not overlap; verify both appear in the Address Editor under the AXI GP master's address space.
- **Validate Design before generating**: Always run `validate_bd_design` in TCL or "Validate Design" in the GUI before generating the bitstream. This catches unconnected ports, address conflicts, and bus-width mismatches.
- **IP Integrator in 2025.1 non-project mode**: The full IP Integrator workflow (create_bd_design, add IP, connect, make_wrapper) is supported in non-project mode per UG994 2025.1 — use `open_bd_design` to open an existing .bd file without a full project.
- **Regenerating after IP version upgrade**: After a Vivado tool upgrade, IP cores show as "outdated". Run `upgrade_ip [get_ips *]` in TCL before re-running synthesis to avoid partial-update errors.

### Code Example

```tcl
# Validate and generate wrapper in non-project mode
open_bd_design [get_files *.bd]
validate_bd_design
make_wrapper -files [get_files *.bd] -top
add_files -norecurse [glob ./hdl_wrapper/*.vhd]
set_property top kv260_top_wrapper [current_fileset]
```

### Relevance to Your Project

Your `create_bd.tcl` generates the block design programmatically. Adding a `validate_bd_design` call before `make_wrapper` and verifying both BRAM controllers appear in the address map with the correct base addresses (0xA0000000, 0xA0010000) will catch misconfigurations before a 30-minute bitstream build.

## Vivado TCL Scripting

### Key Findings

- **Project mode vs. Non-project mode**: Project mode persists state on disk and auto-generates reports; non-project mode operates entirely in-memory with no auto-generated files. For CI/CD or headless FPGA builds, non-project mode offers cleaner control.
- **Batch mode execution**: `vivado -mode batch -source build.tcl` runs the script and exits automatically on completion. `vivado -mode tcl -source build.tcl` returns to the TCL prompt after the script finishes (useful for interactive debugging).
- **write_bd_tcl vs write_project_tcl**: Use `write_bd_tcl -force create_bd.tcl [get_files *.bd]` to capture the block design as a re-runnable script. `write_project_tcl` with the default `-use_bd_files` option embeds a reference to the binary `.bd` file, which cannot be reproduced from a clean checkout without that file.
- **Journal file mining**: Every GUI action is logged to `vivado.jou`. After manually fixing a block design issue in the GUI, inspect the journal file to extract the exact TCL commands — this is the fastest way to learn IP Integrator TCL syntax.
- **`upgrade_ip` in scripts**: Include `upgrade_ip -quiet [get_ips *]` early in build scripts to silently handle IP version transitions when switching Vivado versions.
- **Error handling**: Use `if {[catch {synth_design -top kv260_top_wrapper -part xck26-sfvc784-2LV-c} err]} { puts "ERROR: $err"; exit 1 }` to trap synthesis failures and exit with a non-zero code for CI systems.

### Code Example

```tcl
# Non-project mode full build flow for KV260 AXI-BRAM design
set part "xck26-sfvc784-2LV-c"
set top  "kv260_top_wrapper"

# Create in-memory project
create_project -in_memory -part $part

# Source block design creation script
source ./tcl/create_bd.tcl

# Validate and wrap
validate_bd_design
make_wrapper -files [get_files *.bd] -top
read_vhdl [glob ./hdl_wrapper/*.vhd]
read_xdc  ./xdc/kv260_top.xdc

# Synthesise, implement, write bitstream
synth_design   -top $top -part $part
opt_design
place_design
route_design
write_bitstream -force -file ./output/kv260_top.bit

puts "Build complete."
```

### Relevance to Your Project

Your `create_bd.tcl` already exists for batch block-design regeneration. Wrapping it in the non-project mode flow above and adding a `validate_bd_design` guard enables a fully headless build pipeline (e.g., GitHub Actions) without the GUI — critical for reproducible results across Vivado version upgrades.

## Vitis Bare-Metal / Standalone

### Key Findings

- **stdout peripheral mismatch**: `xil_printf` (and standard `printf`) routes through the BSP's configured stdout peripheral. If output is not appearing on USB-UART, verify the BSP setting `stdin`/`stdout` is set to the correct UART instance (ps_uart0 or ps_uart1 depending on KV260 carrier routing) in the BSP configuration, then regenerate the BSP before rebuilding.
- **Linker script (lscript.ld)**: Vitis auto-generates a linker script placing the application in DDR. For a bare-metal AXI test, the default DDR base (0x00000000 for Zynq UltraScale+) is usually correct. If your binary is not loading, check that the linker script DDR region matches the `ps_ddr_0_AXI_BASEADDR` in `xparameters.h`.
- **xparameters.h as ground truth**: The BSP-generated `xparameters.h` contains `XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR` and `XPAR_AXI_BRAM_CTRL_1_S_AXI_BASEADDR` — use these symbolic constants in `main.c` instead of hardcoded hex addresses to guard against address reassignment during block design changes.
- **Interrupt controller (GIC)**: On Zynq UltraScale+/K26, the GIC-400 handles Private Peripheral Interrupts (PPI, e.g. timer) and Shared Peripheral Interrupts (SPI, e.g. AXI peripheral interrupts). Initialise with `XScuGic_Initialize()` from the `scugic` driver included in the standalone BSP.
- **BSP regeneration order**: After any hardware export from Vivado, always: (1) update the hardware platform in Vitis, (2) regenerate the BSP, (3) rebuild the application. Skipping step 2 leaves stale `xparameters.h` with old addresses.

### Code Example

```c
#include "xparameters.h"
#include "xil_printf.h"
#include "xil_io.h"

/* Use BSP-generated symbolic addresses — safe against block design changes */
#define BRAM0_BASE  XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR
#define BRAM2_BASE  XPAR_AXI_BRAM_CTRL_1_S_AXI_BASEADDR
#define TEST_PATTERN 0xDEADBEEFU

int main(void) {
    xil_printf("=== KV260 AXI-BRAM Test ===\r\n");

    /* Write test pattern */
    Xil_Out32(BRAM0_BASE + 0x00, TEST_PATTERN);
    Xil_Out32(BRAM2_BASE + 0x00, ~TEST_PATTERN);

    /* Read back and verify */
    u32 r0 = Xil_In32(BRAM0_BASE + 0x00);
    u32 r1 = Xil_In32(BRAM2_BASE + 0x00);

    if (r0 == TEST_PATTERN && r1 == ~TEST_PATTERN)
        xil_printf("PASS: BRAM0=0x%08X  BRAM2=0x%08X\r\n", r0, r1);
    else
        xil_printf("FAIL: BRAM0=0x%08X (exp 0x%08X)  BRAM2=0x%08X (exp 0x%08X)\r\n",
                   r0, TEST_PATTERN, r1, ~TEST_PATTERN);
    return 0;
}
```

### Relevance to Your Project

The `main.c` hardcodes `0xA0000000` and `0xA0010000`. Replacing these with `XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR` and `XPAR_AXI_BRAM_CTRL_1_S_AXI_BASEADDR` from `xparameters.h` makes the code resilient to address reassignment in the block design — a one-line Vivado address editor change won't silently break the test.

## XDC Timing Constraints

### Key Findings

- **set_input_delay / set_output_delay basics**: Both commands require a reference clock (`-clock`). For signals crossing to external logic synchronous to the PL clock, reference the PL system clock. For signals from the PS (like AXI signals), reference the PS-generated clock.
- **Virtual clocks for external interfaces**: When an external interface runs from a clock that does not have a physical FPGA pin (e.g., a clock inside the PS driving AXI signals), define a virtual clock with the same period and use it as the timing reference:
  ```
  create_clock -period 10.0 -name virt_ps_clk
  set_input_delay -clock virt_ps_clk -max 2.0 [get_ports ext_in_*]
  ```
- **-max and -min both required**: Specifying only `-max` gives setup margin but leaves hold margin unconstrained. Always pair with `-min` (or `-add_delay` for DDR) for complete timing closure.
- **clock_groups for async domains**: If your design has a PL free-running clock alongside the PS AXI clock, declare them as asynchronous to prevent Vivado from trying to time paths between them: `set_clock_groups -asynchronous -group [get_clocks pl_clk] -group [get_clocks ps_clk]`.
- **HD.CLK_SRC on AXI BRAM Controller**: The AXI BRAM Controller Out-of-Context constraints include `HD.CLK_SRC` properties — these are required for correct hold timing closure in OOC synthesis mode. Do not strip the AXI BRAM Controller's own XDC from the project.
- **KV260 system clock source**: The K26 SoM PL clock is provided by the PS (`FCLK_CLK0` from the Zynq MPSoC PS). Constrain it with `create_clock -period 10.0 [get_pins */FCLK_CLK0]` (adjust period to match the configured PS clock frequency in the block design).

### Code Example

```xdc
# KV260 PL system clock from PS (100 MHz default for AXI-BRAM designs)
create_clock -period 10.000 -name pl_clk0 [get_pins i_ps/inst/PS8_i/PLCLK[0]]

# Declare PS AXI clock domain as async to any free-running PL logic clock
# (only needed if you have a second clock in your design)
# set_clock_groups -asynchronous \
#     -group [get_clocks pl_clk0] \
#     -group [get_clocks free_run_clk]

# Example I/O delay for external GPIO (if present on carrier card)
# create_clock -period 10.000 -name virt_io_clk
# set_input_delay  -clock virt_io_clk -max 3.0 -min 0.5 [get_ports gpio_in[*]]
# set_output_delay -clock virt_io_clk -max 2.0 -min 0.5 [get_ports gpio_out[*]]
```

### Relevance to Your Project

Your current design likely relies on Vivado's unconstrained timing for the AXI-BRAM path. Adding the `create_clock` constraint on `PLCLK[0]` gives Vivado a timing budget for the AXI path, enabling timing reports to confirm setup/hold margins — essential before treating PASS/FAIL results as definitive.

## Kria KV260 / K26 SoM

### Key Findings

- **Boot mode priority**: Boot mode is set by the MODE[3:0] pins on the SoM connector (tied by the carrier card). Supported modes: JTAG (0000), QSPI32 (0010), SD (1110). For development, always use JTAG or SD.
- **QSPI is locked on the KV260 Starter Kit**: The QSPI flash on the KV260 carries the factory boot firmware (boot.bin + u-boot + PMUFW) and is read-only to prevent bricking. You cannot write your own bare-metal image to QSPI. Target SD card or JTAG download for custom bare-metal applications.
- **Bare-metal JTAG procedure on KV260**: (1) Remove SD card so the board fails to boot Linux. (2) Set hardware target in XSCT/Vitis. (3) Run `source psu_init.tcl` to initialise PS DDR. (4) Download ELF with `dow application.elf`. (5) `con` to run. No FSBL required.
- **MIO vs EMIO pin assignment**: MIO bank 500 (PS-side, 1.8V) handles I2C, UART, and SD card signals on the K26 SoM. The PMODs and RPi 40-pin header on the KV260 carrier card connect to PL I/O — route these via EMIO in the block design (connect PL GPIO to the PS EMIO interface) or directly as PL ports.
- **Power domains**: The K26 SoM power system is divided into three domains: Always-On (VCCINT, VCCO at 5V main), Low-Power Domain (LPD, PS peripherals), and Full-Power Domain (FPD, including PS-PL AXI). AXI-GP0 (the interface used for BRAM access) operates in the FPD — ensure VCCINT_PL is stable before asserting PS-PL reset deassertion.
- **K26 XDC pin file**: AMD provides an official K26 SoM XDC with all MIO and PL I/O constraints. Use this as the base XDC for any carrier card design rather than building constraints from the UG1075 pinout tables manually.

### Code Example

```tcl
# XSCT script for bare-metal JTAG download to KV260 (no SD, no FSBL)
connect
targets -set -filter {name =~ "PSU"}
mwr 0xFF5E0200 0x0100    ;# Set boot mode to JTAG
rst -system
after 3000

targets -set -filter {name =~ "Cortex-A53 #0"}
rst -processor
source psu_init.tcl      ;# Initialise PS DDR and peripherals
psu_init

targets -set -filter {name =~ "Cortex-A53 #0"}
dow kv260_axi_bram_test.elf
con
```

### Relevance to Your Project

The KV260 AXI-BRAM demo is pure bare-metal. The XSCT script above is the exact flow needed to download and run your Vitis application without relying on a Linux boot chain — the safest iteration cycle for early hardware bringup.

## AMD/Xilinx Tool Updates (2025.1 / 2026.1)

### Key Findings

- **BRAM/FIFO IP deprecation (2025.x)**: The Block Memory Generator (BMG) and FIFO Generator IPs are being phased out of the IP Catalog in Vivado 2025.x for RTL designs. AMD recommends migrating to XPM_MEMORY_* macros. The AXI BRAM Controller IP in block designs is unaffected.
- **Known issue — IP staleness**: Vivado 2025.1 may fail to detect that an IP has been updated (stale IP warning not shown). Workaround: close and fully reopen the project after any IP upgrade, or run `upgrade_ip -quiet [get_ips *]` in a TCL batch step at the start of every build.
- **Known issue — IP update core dump**: In some configurations, running IP upgrades triggers a core dump requiring a full Vivado restart. Isolate IP upgrades from bitstream generation runs in CI.
- **Vitis 2025.1 improvements**: The Vitis Unified IDE (Eclipse-based) received updates to the BSP configuration flow and the embedded SW repository. The `embeddedsw` GitHub repo (https://github.com/Xilinx/embeddedsw) is the authoritative source for standalone BSP drivers — check the `2025.1` branch for driver bug fixes not yet reflected in local Vitis installations.
- **AMD 2026.1 tools now available**: As of August 2026, AMD has released Vivado/Vitis 2026.1. If upgrading from 2025.1, review the migration guide for any AXI IP or block design format changes before migrating an in-progress project.
- **XPM_FIFO_AXIL new in 2025.x**: A new parameterised AXI-Lite FIFO macro (XPM_FIFO_AXIL) was added in UG974 for 2025.x, enabling FIFO-style AXI-Lite buffering without an IP core.

### Code Example

```vhdl
-- XPM_MEMORY_SPRAM: replace Block Memory Generator in RTL (Vivado 2025+)
-- Place in architecture where BRAM instantiation previously used BMG IP
library xpm;
use xpm.vcomponents.all;

xpm_memory_spram_inst : xpm_memory_spram
  generic map (
    ADDR_WIDTH_A        => 10,      -- 1024 depth
    BYTE_WRITE_WIDTH_A  => 8,       -- byte-write granularity
    WRITE_DATA_WIDTH_A  => 32,
    READ_DATA_WIDTH_A   => 32,
    READ_LATENCY_A      => 2,
    MEMORY_PRIMITIVE    => "block"  -- use BRAM (not LUTRAM)
  )
  port map (
    clka   => clk,
    ena    => bram_en,
    wea    => wstrb,       -- 4-bit write strobe
    addra  => addr,
    dina   => wdata,
    douta  => rdata
  );
```

### Relevance to Your Project

Your project uses the AXI BRAM Controller IP (from the block design) to access BRAM — that IP is unaffected by the BMG deprecation. However, if you ever add a custom BRAM port on the PL side (e.g., a second port for PL-side DMA), use XPM_MEMORY_DPRAM instead of instantiating a Block Memory Generator IP, as the latter may be removed from the IP Catalog in a future Vivado release.
