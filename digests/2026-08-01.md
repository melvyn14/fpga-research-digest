# FPGA Research Digest - 2026-08-01

## Executive Summary

- **Vivado 2025.1/2025.2 breaking change**: Embedded Memory Generator (Block Memory Generator) and FIFO Generator IPs can no longer be instantiated directly from the IP Catalog — they must now be used exclusively inside IP Integrator block designs. This directly affects any standalone VHDL instantiation of BRAM in the KV260 project.
- **AXI-Lite BRESP pitfall**: Many Vivado-generated AXI-Lite slave templates have known bugs in the write-response channel; always verify BVALID is not asserted until WLAST (and the final WDATA beat) is accepted, and leave BRESP at 2'b00 (OKAY) unless you are implementing error signalling.
- **Vivado 2025.1 address-width bug**: An apparent address decoding bug in Vivado 2025.1 for custom AXI Full peripherals limits usable address space to 1 KB, even when `C_S_AXI_ADDR_WIDTH` is set to 16. The KV260 project uses AXI-Lite to BRAM which is unaffected, but this is worth knowing for future AXI Full expansions.
- **Kria KV260 bare-metal JTAG boot** requires four files: `fsbl.elf`, `pmufw.elf`, `<app>.elf`, and `<design>.bit`. XSCT/XSDB scripts can automate this — essential for iterating on PS-PL connectivity without reflashing QSPI.
- **Non-project mode TCL**: Block designs used in non-project Vivado flows must be pre-generated with OOC synthesis before being added via `read_bd`; otherwise `synth_design` will error. Export your BD as TCL (`write_bd_tcl`) and source it to reproduce builds reproducibly.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- **READY/VALID handshake invariants**: Once VALID is asserted by an initiator, it must not be de-asserted until the corresponding READY is received. Violating this causes protocol errors that are silent in RTL simulation but caught by the AXI VIP (Verification IP).
- **BRESP must follow WLAST**: A slave must issue BVALID only after the final data beat (WLAST for AXI4; for AXI-Lite every transaction is effectively single-beat, so BVALID must follow WVALID+WREADY). AXI VIP will fatal-error on premature BVALID.
- **AXI-Lite address-space Vivado 2025 bug**: Setting `C_S_AXI_ADDR_WIDTH` higher than 10 bits in a custom AXI Full peripheral does not actually decode addresses beyond 10 bits in Vivado 2025.1. Workaround: use IP Integrator's address editor and verify with the address map report rather than relying on parameter inference.
- **AXI-Stream TLAST/TKEEP rules**: TLAST marks the final byte of a packet; TKEEP can only be sparse (contain zeros) on the TLAST beat — any intermediate beat must have all TKEEP bits set. `axis_data_fifo` Packet Mode holds the entire packet in BRAM until TLAST before forwarding.
- **Formal verification**: Dan Gisselquist's (ZipCPU) open-source `axilite` formal property file (`faxil_slave.v`) is the most rigorous way to prove AXI-Lite compliance without a Cadence/Mentor license.

### Code Example

```vhdl
-- Minimal AXI-Lite write path: correct BVALID gating
-- BVALID must only go high after both AWREADY and WREADY handshakes complete
process(S_AXI_ACLK)
begin
  if rising_edge(S_AXI_ACLK) then
    if S_AXI_ARESETN = '0' then
      axi_bvalid <= '0';
      axi_bresp  <= "00";         -- OKAY
    else
      -- Gate on write-address AND write-data channels both completing
      if (axi_awready and S_AXI_AWVALID and
          axi_wready  and S_AXI_WVALID) = '1' then
        axi_bvalid <= '1';
        axi_bresp  <= "00";       -- never signal SLVERR unless intentional
      elsif S_AXI_BREADY = '1' then
        axi_bvalid <= '0';        -- deassert only after master accepts
      end if;
    end if;
  end if;
end process;
```

### Relevance to Your Project

Your `main.c` writes 32-bit patterns to BRAM0 (0xA0000000) and BRAM2 (0xA0010000) via AXI-Lite. The Cortex-A53's AXI master will assert BREADY immediately (bare-metal, no OS), so BVALID timing from the BRAM controller matters. If the controller's BRESP path has a latency bug, `memread` will return stale data. Add an `ila_0` in Vivado to probe AXI channels — set a trigger on `BVALID & ~BREADY` to catch response backpressure.

## Vivado Block Design / IP Integrator

### Key Findings

- **Breaking change in 2025.1+**: Embedded Memory Generator and Embedded FIFO Generator IPs are only usable inside IP Integrator. Direct `xpm_memory` or BMG instantiation in RTL still works, but the GUI IP Catalog entry is hidden.
- **Connection Automation**: `apply_bd_automation` in TCL (or the "Run Connection Automation" button) automatically inserts `proc_sys_reset`, `axi_interconnect`, and wires up `S_AXI`, `M_AXI_GP0`, and clock/reset. Always inspect what it created — it can add an unnecessary `AXI SmartConnect` that adds pipeline stages.
- **Address Editor is authoritative**: Manual edits to `C_BASEADDR` in IP properties are ignored by the address map; only the Address Editor (or `assign_bd_address`) determines the actual memory-map.
- **Regenerate layout**: After major changes, `regenerate_bd_layout` (TCL) or "Regenerate Layout" cleans up visual clutter — it does not change connectivity, only the canvas positions.
- **Upgrading IPs**: When opening a project in a new tool version, use `upgrade_ip [get_ips *]` in TCL before attempting synthesis to avoid stale IP containers causing errors.

### Code Example

```tcl
# Assign and lock BRAM addresses in block design via TCL
# Run after create_bd_cell calls and connections

# Assign BRAM0 to 0xA000_0000
set_property offset 0xA0000000 [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property range 64K          [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]

# Assign BRAM2 to 0xA001_0000
set_property offset 0xA0010000 [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_2_Mem0}]
set_property range 64K          [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_2_Mem0}]

# Validate and regenerate layout
validate_bd_design
regenerate_bd_layout
save_bd_design
```

### Relevance to Your Project

Your `create_bd.tcl` almost certainly uses `apply_bd_automation` and manual address assignments for BRAM0/BRAM2. Double-check that `assign_bd_address` is called (not just `set_property offset`) after any tool-version upgrade — a mismatch between the BD address map and the `0xA0000000`/`0xA0010000` constants in `main.c` is the #1 cause of FAIL results in this class of demo.

## Vivado TCL Scripting

### Key Findings

- **Export block design as TCL**: Use `File → Export → Export Block Design` (or `write_bd_tcl <output.tcl>`) to get a self-contained script that recreates the entire BD. This is the preferred source-control artifact — commit the TCL, not the `.bd` file.
- **Non-project mode BD requirement**: If using non-project mode (`synth_design` without `create_project`), block designs must be pre-synthesized OOC. Add `set_property synth_checkpoint_mode None [get_files <bd>.bd]` to force global synthesis of the BD within non-project flow.
- **UG994 2025.1 IP Integrator in Non-Project Mode**: AMD's official doc for 2025.1 (UG994 chapter "Using IP Integrator in Non-Project Mode") details the `open_bd_design` / `generate_target` / `read_bd` sequence.
- **Batch mode execution**: `vivado -mode batch -source create_bd.tcl` is the canonical CI invocation. Use `exit [expr {$rc != 0}]` at the end of your script to propagate failure codes.
- **Variable scoping**: Vivado TCL runs in a global namespace; prefix all helper procedures with a project-specific namespace (`namespace eval kv260 {}`) to avoid collisions when sourcing multiple scripts.

### Code Example

```tcl
# Non-project mode: synthesize, implement, and write bitstream
# Usage: vivado -mode batch -source build.tcl

# Read sources
read_vhdl   [glob src/*.vhd]
read_bd     bd/design_1.bd
read_xdc    constraints/timing.xdc

# Force global synth so BD is included without OOC checkpoint
set_property synth_checkpoint_mode None [get_files bd/design_1.bd]
generate_target all [get_files bd/design_1.bd]

synth_design   -top kv260_top -part xck26-sfvc784-2LV-c
opt_design
place_design
route_design

# Reports
report_timing_summary -file reports/timing.rpt
report_utilization    -file reports/util.rpt

# Bitstream
write_bitstream -force output/kv260_top.bit

exit 0
```

### Relevance to Your Project

Your `create_bd.tcl` can be extended with the snippet above to form a full non-project build pipeline. Running in batch mode in CI (e.g., GitHub Actions with a self-hosted Vivado runner) catches addressing and connectivity errors early without needing the GUI.

## Vitis Bare-Metal / Standalone

### Key Findings

- **xil_printf vs printf**: `xil_printf` is a lightweight format-string printer (no float support) that goes to the UART defined by the BSP's `stdin`/`stdout` peripheral. For the KV260, this is typically `psu_uart_1` (USB-UART). Ensure the BSP `system.mss` has `STDIN_PERIPHERAL` and `STDOUT_PERIPHERAL` set correctly or output will be silent.
- **Vitis 2025.2 xil_printf.h include**: A known issue in Vitis 2025.2 is that `xil_printf.h` is not found when using the new Vitis Unified IDE with certain platform configurations — workaround is to add `${EMBEDDEDSW_BSP_DIR}/include` explicitly to the compiler include path.
- **BSP regeneration after hardware change**: Every time you export a new XSA from Vivado, you must regenerate the BSP in Vitis (`vitis -s regenerate_bsp.py` or via the GUI "Update Hardware" flow). Stale BSPs with old address maps are a frequent source of FAIL on read-back.
- **Linker script heap/stack**: The default standalone linker script places heap and stack in DDR (`ps_ddr_low`). For bare-metal demos that only use PL memory (BRAM), this is fine — but verify `lscript.ld` does not place `.text` or `.data` sections at an address conflicting with your BRAM base addresses.
- **GIC interrupt controller**: `XScuGic` driver (in `xscugic.h`) manages the ARM GIC-400 on Zynq UltraScale+. For simple polling-based BRAM access (as in the KV260 demo), interrupts are not needed — but adding a PL-to-PS interrupt from the BRAM controller's `interrupt` port can replace busy-wait polling loops.

### Code Example

```c
#include "xil_printf.h"
#include "xparameters.h"   /* auto-generated; defines XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR */

#define BRAM0_BASE  XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR   /* 0xA0000000 */
#define BRAM2_BASE  XPAR_AXI_BRAM_CTRL_2_S_AXI_BASEADDR   /* 0xA0010000 */

static inline void bram_write32(u32 base, u32 offset, u32 val) {
    *(volatile u32 *)(base + offset) = val;
}

static inline u32 bram_read32(u32 base, u32 offset) {
    return *(volatile u32 *)(base + offset);
}

int main(void) {
    const u32 pattern = 0xDEADBEEF;
    u32 readback;

    xil_printf("KV260 AXI-BRAM Test\r\n");

    /* Write pattern to BRAM0 offset 0 */
    bram_write32(BRAM0_BASE, 0x00, pattern);
    /* Memory barrier: ensure write completes before read */
    __asm__ __volatile__("dsb sy" ::: "memory");

    readback = bram_read32(BRAM0_BASE, 0x00);
    if (readback == pattern)
        xil_printf("BRAM0: PASS (0x%08X)\r\n", readback);
    else
        xil_printf("BRAM0: FAIL (got 0x%08X, expected 0x%08X)\r\n",
                   readback, pattern);
    return 0;
}
```

### Relevance to Your Project

The `dsb sy` data synchronisation barrier (ARM ISB/DSB) is critical in bare-metal AXI write-then-read sequences — without it, the Cortex-A53 store buffer may not have flushed to the AXI bus before the load instruction executes, causing false FAILs on fast CPUs. Ensure your `main.c` has a barrier between every write and read-back.

## XDC Timing Constraints

### Key Findings

- **`set_input_delay` is clock-relative**: The value specifies the external path delay from the clock edge to the data arriving at the FPGA pin (in ns). A positive value means data arrives after the launch clock edge. The Timing Constraints Wizard (Vivado → Tools → Timing Constraints Wizard) auto-generates correct templates by analysing your netlist.
- **`set_output_delay` dual-edge pattern**: For DDR interfaces, use `-max` and `-min` variants on both rising and falling edges. For simple single-data-rate outputs to LEDs or test pins, a single `set_output_delay -clock <clk> -max <ns> [get_ports <port>]` is sufficient.
- **Clock groups for PS-PL clock domains**: Zynq UltraScale+ designs typically have `pl_clk0` from the PS and a separate free-running PL clock. Declare these as asynchronous: `set_clock_groups -asynchronous -group [get_clocks clk_pl_0] -group [get_clocks <pl_clk>]`. Without this, Vivado will attempt cross-domain timing analysis and produce false violations.
- **AXI-BRAM constraint scope**: For a pure AXI-BRAM design where all logic is synchronous to `pl_clk0`, no I/O timing constraints are needed beyond the PS-generated clock definition. The BRAM controller IP handles its own internal timing.
- **`create_clock` for PL clocks**: If your design uses a BUFG or MMCM output as a PL clock, you must define it with `create_clock`. PL clocks sourced from the PS (`pl_clk0`) are auto-constrained by the Zynq IP and do not need a manual `create_clock`.

### Code Example

```tcl
# timing.xdc for KV260 AXI-BRAM demo

# pl_clk0 is auto-constrained by the Zynq PS IP (100 MHz default)
# Only needed if you add external I/O ports:

# Example: constrain an LED output driven from pl_clk0
set_output_delay -clock [get_clocks clk_pl_0] -max 2.0 [get_ports led_o]
set_output_delay -clock [get_clocks clk_pl_0] -min 0.5 [get_ports led_o]

# Declare any additional free-running PL clock (e.g. from MMCM):
# create_clock -period 10.000 -name clk_pl_mmcm [get_pins mmcm_inst/CLKOUT0]

# If PS and a separate PL clock coexist, declare them asynchronous:
# set_clock_groups -asynchronous \
#   -group [get_clocks clk_pl_0] \
#   -group [get_clocks clk_pl_mmcm]

# False path on async reset (if used):
# set_false_path -from [get_ports aresetn]
```

### Relevance to Your Project

The KV260 bare-metal BRAM demo has no external I/O beyond USB-UART (handled by PS MIO, not PL). The XDC file needs only: (1) any pin assignments for PL GPIO if used in `kv260_top.vhd`, and (2) `set_clock_groups` if you ever add a second PL clock domain. If your current design passes timing with an empty XDC, that is expected and correct for an AXI-only PL design.

## Kria KV260 / K26 SoM Platform

### Key Findings

- **Boot mode defaults**: KV260 Starter Kits ship with QSPI32 boot mode (boot from onboard QSPI flash). The SD card is the secondary boot device. For bare-metal development, JTAG boot (via XSCT/XSDB) is the fastest iteration loop — no reflashing required.
- **JTAG bare-metal boot sequence (4 files)**: `fsbl.elf` (First Stage Boot Loader), `pmufw.elf` (PMU Firmware), `<design>.bit` (PL bitstream), `<app>.elf` (your application). XSDB loads them in this order.
- **MIO vs EMIO**: USB-UART on the KV260 is routed through PS MIO (specifically `psu_uart_1` on MIO 36/37). PL-side GPIOs on RPi/PMOD headers connect to the PL fabric, not to PS MIO — these require EMIO or direct PL I/O ports in your XDC.
- **Device tree overlay requirement**: When running under Linux, custom PL designs require a device tree overlay (`.dtbo`). For bare-metal, there is no OS and no device tree — the hardware is configured entirely by the bitstream and FSBL.
- **Kria SOM platform files in Vivado**: Vivado 2025.1 includes updated board files for K26 SOM and KV260 Starter Kit. Use `get_boards` in TCL or the Board Manager GUI to verify you have the latest files before creating a project.

### Code Example

```tcl
# xsdb_boot.tcl — JTAG bare-metal boot for KV260
# Run with: xsdb xsdb_boot.tcl

connect

# Target the APU (Cortex-A53 core 0)
targets -set -filter {name =~ "PSU"}

# Initialise PS (runs FSBL-equivalent PS init)
rst -system
after 3000

# Download and run PMU firmware
targets -set -filter {name =~ "MicroBlaze PMU"}
dow pmufw.elf
con
after 1000

# Program the PL bitstream
targets -set -filter {name =~ "PSU"}
fpga -f design_1_wrapper.bit

# Load and run FSBL
targets -set -filter {name =~ "A53*#0"}
dow fsbl.elf
con
after 5000
stop

# Load and run application
dow kv260_axi_bram.elf
con

puts "Application running — open /dev/ttyUSB1 at 115200 baud"
exit
```

### Relevance to Your Project

This XSDB script exactly matches the KV260 bare-metal boot flow for your AXI-BRAM demo. Replace `design_1_wrapper.bit` and `kv260_axi_bram.elf` with your actual filenames. Run `xsdb xsdb_boot.tcl` from the Vitis terminal (not a plain shell — it needs the Vitis environment sourced) to quickly iterate without touching the QSPI flash.

## AMD/Xilinx Tool Updates (Vivado/Vitis 2025.x)

### Key Findings

- **Vivado 2026.1 available**: AMD released Vivado/Vitis 2026.1 (downloads page updated as of mid-2026). It supersedes 2025.1/2025.2 and includes performance improvements for Versal and UltraScale+. KV260 users on 2025.1 are encouraged to evaluate 2026.1 for stability fixes.
- **BRAM/FIFO IP Catalog removal (2025.1+)**: The Block Memory Generator and FIFO Generator are no longer in the standalone IP Catalog. Use `xpm_memory_spram` / `xpm_memory_dpram` (Xilinx Parameterized Macros) for RTL instantiation, or use the IP Integrator BMG/BRAM generator.
- **Vitis 2025.1 release date**: Vitis 2025.1 (UG1742) was released 2025-07-08. Key changes include updates to the platform creation flow for Kria SOM (`Custom Kria SOM Platform Creation Example`, XD101 tutorial).
- **Vitis 2025.2 `xil_printf.h` include issue**: Some users report `xil_printf.h not found` in Vitis 2025.2 Unified IDE — confirmed bug with workaround of adding BSP include path manually.
- **`X_MODULE_SPEC` HDL attribute**: Vivado 2025.x introduces the `X_MODULE_SPEC` attribute, combining `X_INTERFACE_INFO` and `X_INTERFACE_PARAMETER` into a single HDL attribute. This simplifies custom IP creation in RTL.
- **IP Integrator 2025.2 tutorial**: The `Vivado-Design-Tutorials` GitHub repo has a 2025.2 branch with updated `Versal/IP_Integrator` examples demonstrating Block Design Container flows.

### Code Example

```vhdl
-- Using XPM macros instead of Block Memory Generator IP
-- Available in Vivado 2016.4+ without needing IP Catalog
-- No license required; synthesises on all Xilinx/AMD device families

library ieee;
use ieee.std_logic_1164.all;
library xpm;
use xpm.vcomponents.all;

entity bram_xpm is
  port (
    clka  : in  std_logic;
    ena   : in  std_logic;
    wea   : in  std_logic_vector(0 downto 0);
    addra : in  std_logic_vector(13 downto 0);  -- 16K x 32-bit
    dina  : in  std_logic_vector(31 downto 0);
    douta : out std_logic_vector(31 downto 0)
  );
end bram_xpm;

architecture rtl of bram_xpm is
begin
  xpm_memory_spram_inst : xpm_memory_spram
    generic map (
      ADDR_WIDTH_A        => 14,
      AUTO_SLEEP_TIME     => 0,
      BYTE_WRITE_WIDTH_A  => 32,   -- full-word writes only
      ECC_MODE            => "no_ecc",
      MEMORY_PRIMITIVE    => "block",
      MEMORY_SIZE         => 16384 * 32,  -- bits
      READ_DATA_WIDTH_A   => 32,
      READ_LATENCY_A      => 2,
      WRITE_DATA_WIDTH_A  => 32,
      WRITE_MODE_A        => "no_change"
    )
    port map (
      clka   => clka,
      ena    => ena,
      wea    => wea,
      addra  => addra,
      dina   => dina,
      douta  => douta,
      injectsbiterra => '0',
      injectdbiterra => '0',
      regcea => '1',
      rsta   => '0',
      sleep  => '0'
    );
end rtl;
```

### Relevance to Your Project

If you plan to upgrade from Vivado 2025.1 to 2026.1 (or were already seeing the BRAM IP Catalog issue in 2025.1/2025.2), the `xpm_memory_spram` instantiation above can replace a Block Memory Generator IP without requiring an IP Catalog entry. For your current project, the AXI BRAM Controller IP in IP Integrator is still the correct approach — but understanding XPM macros is valuable for custom BRAM wrappers in `kv260_top.vhd`.
