# FPGA Research Digest - 2026-09-12

## Executive Summary

- **AXI-Lite backpressure bug is widespread**: Once `BREADY` is de-asserted, a correct slave must propagate backpressure to `AWREADY`/`WREADY`; Xilinx's own example code (pre-2019) gets this wrong — verify your BRAM controller wrapper.
- **`apply_bd_automation` handles clock/reset wiring automatically**: Use it in TCL after adding IP so clock and reset pins on AXI slaves are wired without manual `connect_bd_net` calls — saves dozens of lines in `create_bd.tcl`.
- **KV260 bare-metal JTAG flow uses `psu_init.tcl` instead of FSBL**: For fast iteration without building a full `BOOT.BIN`, download `psufw.elf` to PMU, then load your application ELF directly over JTAG — no SD card or QSPI write needed.
- **Vivado 2026.1 introduces tiered licensing**: The free "WebPACK" model is gone from 2026.1 onwards; projects targeting KV260/K26 (Zynq UltraScale+) need the new **Core** or **Pro** tier. If staying on 2025.x, no change.
- **`set_input_delay -max` and `-min` must both be set for system-synchronous interfaces**: Omitting `-min` leaves hold timing unconstrained and can cause subtle intermittent data corruption at speed.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- The **VALID-before-READY** rule is asymmetric: a master **must not** wait for `READY` before asserting `VALID`, but a slave **may** wait for `VALID` before asserting `READY`. Violating the master side causes protocol deadlock.
- **Sticky VALID**: Once `AWVALID`/`WVALID`/`ARVALID` is asserted, it must stay asserted until the handshake completes (both VALID and READY sampled high on the same rising edge). This applies equally to AXI-Stream `TVALID`.
- **Backpressure propagation** is the most common Xilinx example-code bug: when `BREADY` is held low by the master, the slave must lower `AWREADY` and `WREADY` to prevent accepting new writes whose responses can't be queued. Vivado's auto-generated AXI-Lite slave template (pre-2019 vintage) has this bug — check your wrappers.
- **Combinatorial READY paths hurt Fmax**: Although legal, tying `ARREADY` combinatorially to `ARVALID` saves a cycle but reduces maximum frequency and complicates place-and-route. Prefer registered READY.
- **AXI-Stream TLAST**: Marks end of packet; the next `TVALID` after `TLAST` starts a new packet. If your design doesn't use packets, tie `TLAST = TVALID` for IP compatibility.
- For the KV260 AXI-BRAM demo, the AXI BRAM Controller IP can operate in either **AXI4** or **AXI4-Lite** mode; AXI4-Lite is simpler and sufficient for register-width single-beat accesses.

### Code Example

```c
/* Bare-metal AXI-Lite write + read back to BRAM0 at 0xA0000000 */
#include "xil_io.h"

#define BRAM0_BASE  0xA0000000U
#define BRAM2_BASE  0xA0010000U

static inline void bram_write32(u32 base, u32 offset, u32 val) {
    Xil_Out32(base + offset, val);
}

static inline u32 bram_read32(u32 base, u32 offset) {
    return Xil_In32(base + offset);
}

int bram_test(u32 base, const char *name) {
    const u32 patterns[] = {0xDEADBEEF, 0xCAFEBABE, 0xA5A5A5A5, 0x12345678};
    int pass = 1;
    for (u32 i = 0; i < 4; i++) {
        bram_write32(base, i * 4, patterns[i]);
        u32 rd = bram_read32(base, i * 4);
        if (rd != patterns[i]) {
            xil_printf("%s[%d]: FAIL wrote 0x%08X read 0x%08X\r\n",
                       name, i, patterns[i], rd);
            pass = 0;
        }
    }
    xil_printf("%s: %s\r\n", name, pass ? "PASS" : "FAIL");
    return pass;
}
```

### Relevance to Your Project

Your `main.c` drives AXI-Lite writes to `0xA0000000` (BRAM0) and `0xA0010000` (BRAM2). The `Xil_Out32`/`Xil_In32` wrappers issue single-beat AXI4-Lite transactions through the Zynq PS GP0 AXI master port. The backpressure bug note above applies if you have a custom wrapper around the AXI BRAM Controller — the AMD-supplied BMG IP itself handles backpressure correctly, but any hand-written AXI slave between the PS and BRAM must be verified.

## Vivado Block Design / IP Integrator

### Key Findings

- **`apply_bd_automation`** is the IP Integrator designer-assistance command. After adding an AXI slave IP (`create_bd_cell`), running `apply_bd_automation -rule xilinx.com:bd_rule:axi4` automatically adds an AXI Interconnect (if needed), wires `S_AXI_ACLK`, `S_AXI_ARESETN`, and connects the slave to the PS master — no manual `connect_bd_net` for clocks.
- **`write_bd_tcl`** exports a complete block design as a reproducible TCL script. Use `-include_layout` to also capture the canvas position of IP blocks (useful for readability in large designs).
- The **Address Editor** automatically assigns base addresses but ranges default to 4 KB; for BRAM deeper than 1K words you must explicitly set the range to 64 KB (`assign_bd_address` + `set_property range 64K`).
- **Version portability**: Block design TCL scripts are not guaranteed to work across major Vivado versions. The safe practice is to pin the `vlnv` of each IP core in `create_bd_cell -type ip -vlnv` calls rather than relying on the latest version being auto-selected.
- **Validate before generating**: Always call `validate_bd_design` in your TCL flow before `generate_target all`. It catches unconnected required ports and clock-domain mismatches early.

### Code Example

```tcl
# Minimal TCL snippet: add AXI BRAM Controller + BMG pair and automate connections
set bram_ctrl [create_bd_cell -type ip \
    -vlnv xilinx.com:ip:axi_bram_ctrl:4.1 axi_bram_ctrl_0]
set_property CONFIG.SINGLE_PORT_BRAM {1} $bram_ctrl

set bmg [create_bd_cell -type ip \
    -vlnv xilinx.com:ip:blk_mem_gen:8.4 blk_mem_gen_0]
set_property -dict {
    CONFIG.Memory_Type {True_Dual_Port_RAM}
    CONFIG.Enable_32bit_Address {true}
} $bmg

# Wire BRAM port B from controller to BMG port A
connect_bd_intf_net [get_bd_intf_pins $bram_ctrl/BRAM_PORTA] \
                    [get_bd_intf_pins $bmg/BRAM_PORTA]

# Let IP Integrator handle AXI clock/reset/interconnect wiring
apply_bd_automation -rule xilinx.com:bd_rule:axi4 \
    -config {Master "/zynq_ultra_ps_e_0/M_AXI_HPM0_FPD" Clk "Auto"} \
    [get_bd_intf_pins $bram_ctrl/S_AXI]

# Set 64 KB address range so a 16K-word BRAM is fully addressable
assign_bd_address [get_bd_addr_segs $bram_ctrl/S_AXI/Mem0]
set_property range 64K \
    [get_bd_addr_segs zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0]

validate_bd_design
save_bd_design
```

### Relevance to Your Project

Your `create_bd.tcl` builds BRAM0 at `0xA0000000` and BRAM2 at `0xA0010000`. The `assign_bd_address` + `set_property range 64K` pattern above is what you need if the default 4 KB range is too small for future deeper BRAMs. The `validate_bd_design` call before `generate_target` will catch any dangling AXI clock/reset pins before you spend time on synthesis.

## Vivado TCL Scripting

### Key Findings

- **Non-project mode** (`vivado -mode batch -source run.tcl`) is the recommended CI/CD flow: no `.xpr` file is created; read sources, synthesize, implement, and write bitstream in one script. Use `read_vhdl`, `read_xdc`, `synth_design`, `opt_design`, `place_design`, `route_design`, `write_bitstream`.
- **Project mode vs. non-project mode**: For reproducible builds, prefer non-project mode; for interactive development with incremental compile caching, project mode (`.xpr`) is more practical. Mixing both is possible via `open_project` / `close_project` in scripts.
- **Log everything**: In batch mode, `vivado -mode batch` outputs to stdout. Redirect with `vivado -mode batch -source run.tcl -log build.log -journal build.jou` to capture for CI artifact storage.
- **GUI action → TCL learning**: Every action in Vivado GUI is echoed to the TCL console. Use this to discover undocumented commands by doing the action once in the GUI, copying the command from the TCL console, then pasting into your script.
- **Checkpoints** (`write_checkpoint` / `read_checkpoint`) allow multi-pass optimization runs without re-running previous steps. Save after `synth_design` and `place_design` to enable fast re-runs of just route.
- **Timing closure helpers**: `phys_opt_design` (post-place physical optimization) often finds 10–20% timing improvement on congested designs with no code changes.

### Code Example

```tcl
#!/usr/bin/env tclsh
# Non-project mode: full flow from VHDL sources to bitstream
set part "xck26-sfvc784-2LV-c"   ;# K26 SoM

read_vhdl [glob ../vhdl/*.vhd]
read_xdc  ../constraints/kv260_top.xdc
read_ip   [glob ../ip/*.xci]

synth_design -top kv260_top -part $part -flatten_hierarchy rebuilt
write_checkpoint -force post_synth.dcp

opt_design
place_design
phys_opt_design
write_checkpoint -force post_place.dcp

route_design
write_checkpoint -force post_route.dcp

report_timing_summary -file timing_summary.rpt -warn_on_violation
report_utilization    -file utilization.rpt

write_bitstream -force output/kv260_top.bit
write_hw_platform -fixed -force output/kv260_top.xsa
```

### Relevance to Your Project

Your project uses `create_bd.tcl` inside Vivado's project mode GUI. The non-project snippet above shows how to wrap your existing TCL into a headless CI script. The `-part xck26-sfvc784-2LV-c` matches the K26 SoM device string — double-check this in **Tools → Settings → Project Settings → General** in Vivado and copy the exact part string to avoid synthesis targeting the wrong speed grade.

## Vitis Bare-Metal / Standalone

### Key Findings

- **BSP (Board Support Package)** is auto-generated from the XSA exported by Vivado. It contains `xparameters.h` (all base addresses, IRQ numbers) and the driver source. After re-exporting XSA, update the BSP platform in Vitis (`vitis -s update_platform.py`) before rebuilding.
- **`xil_printf` vs `printf`**: `xil_printf` is a lightweight implementation (no float support, no buffer) suitable for bare-metal. It writes directly to the UART. For float output, enable `STDOUT_BASEADDRESS` and use `printf` with newlib (adds ~150 KB to ELF). For your PASS/FAIL output, `xil_printf` is the right choice.
- **UART base address**: On KV260/K26, UART1 (`0xFF010000`) is connected to the USB-UART bridge. The BSP will set `STDIN_BASEADDRESS`/`STDOUT_BASEADDRESS` to this automatically if UART1 is enabled in the PS configuration.
- **Linker script pitfalls**: Default linker script places stack in DDR (`0x00000000`). For a minimal bare-metal demo, override to OCM (`0xFFFC0000`–`0xFFFFFFFF`) for faster access and to avoid DDR initialization dependency. Set in `lscript.ld`: `_stack_end = 0xFFFC0000; _stack = 0xFFFFFFFF;`.
- **Platform re-generation**: After changing the Vivado block design and exporting a new XSA, the Vitis platform must be rebuilt (`Build → Build Platform`) before the application project picks up new `xparameters.h` values.
- **Interrupt controller**: For AXI peripherals that assert interrupts, instantiate `XScuGic` (Zynq UltraScale+ GIC) rather than the legacy `XIntc` (MicroBlaze AXI interrupt controller). For polling-only BRAM access, no interrupt setup is needed.

### Code Example

```c
/* Minimal Vitis standalone startup with UART and memory init check */
#include "xil_printf.h"
#include "xil_cache.h"
#include "xparameters.h"

#define BRAM0_BASE  XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR
#define BRAM2_BASE  XPAR_AXI_BRAM_CTRL_2_S_AXI_BASEADDR

int main(void) {
    /* Disable D-cache so AXI-Lite writes hit the peripheral immediately */
    Xil_DCacheDisable();

    xil_printf("\r\n=== KV260 AXI-BRAM Demo ===\r\n");

    /* Write and read back */
    Xil_Out32(BRAM0_BASE + 0x00, 0xDEADBEEF);
    Xil_Out32(BRAM2_BASE + 0x00, 0xCAFEBABE);

    u32 r0 = Xil_In32(BRAM0_BASE + 0x00);
    u32 r2 = Xil_In32(BRAM2_BASE + 0x00);

    xil_printf("BRAM0: %s (0x%08X)\r\n",
               (r0 == 0xDEADBEEF) ? "PASS" : "FAIL", r0);
    xil_printf("BRAM2: %s (0x%08X)\r\n",
               (r2 == 0xCAFEBABE) ? "PASS" : "FAIL", r2);

    return 0;
}
```

### Relevance to Your Project

The `XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR` macro comes from the auto-generated `xparameters.h` and maps directly to your `0xA0000000` address assignment in the Address Editor. The `Xil_DCacheDisable()` call is critical for bare-metal AXI-Lite polling: without it, writes may be cached in L1/L2 and reads may return stale cache lines rather than actual PL register values, causing false PASS results.

## XDC Timing Constraints

### Key Findings

- **`set_input_delay` requires both `-max` and `-min`**: `-max` constrains setup (how late data arrives), `-min` constrains hold (how early data arrives). Omitting `-min` leaves hold timing unconstrained; Vivado will not flag this as an error but the design may fail in hardware at certain temperatures.
- **Virtual clocks** are needed when an external device shares a board oscillator with the FPGA but its clock does not physically enter the FPGA. Create with `create_clock -name virt_clk -period 10` (no `-waveform` source pin), then reference in `set_input_delay -clock virt_clk`.
- **Clock groups for asynchronous domains**: Use `set_clock_groups -asynchronous -group {clkA} -group {clkB}` to tell Vivado not to analyze timing between two unrelated clock domains. For the KV260 AXI-BRAM demo, the PS AXI clock and any PL user clock should be in separate clock groups if they come from different PLLs.
- **`set_false_path`** on resets crossing clock domains: A synchronizer for an async reset does not need to meet a setup/hold budget; use `set_false_path -to [get_pins */PRE]` for the async preset/reset pins of the synchronizer's first flop.
- **Constraint ordering matters**: Clocks must be defined before any delay constraint that references them. Use a single `clocks.xdc` sourced first in the constraints fileset.
- For Zynq UltraScale+, the PS-side clocks (`pl_clk0`–`pl_clk3`) are automatically defined by the Zynq PS IP during block design generation; you do not need to `create_clock` for them manually.

### Code Example

```tcl
# kv260_top.xdc — example constraints for KV260 AXI-BRAM demo

# PS delivers 100 MHz PL clock on pl_clk0 — defined by the PS IP, do not redefine
# Reference it for I/O constraints via get_clocks
set pl_clk [get_clocks -of_objects [get_pins zynq_ultra_ps_e_0/inst/PS8_i/PLCLK[0]]]

# If you have a secondary PL user clock from a BUFG/MMCM:
create_clock -name user_clk -period 8.0 [get_pins mmcm_inst/CLKOUT0]

# Asynchronous clock groups: PS AXI clock vs. user MMCM clock
set_clock_groups -asynchronous \
    -group [get_clocks $pl_clk] \
    -group [get_clocks user_clk]

# System-synchronous I/O example (not needed for pure PS-PL AXI, but for EMIO GPIOs):
# Data launched by external device on same 100 MHz board clock,
# 2 ns PCB trace delay, max clock-to-Q = 3 ns
set_input_delay -clock $pl_clk -max 5.0 [get_ports gpio_in[*]]
set_input_delay -clock $pl_clk -min 1.0 [get_ports gpio_in[*]]

# Async reset false path to synchronizer first flop
set_false_path -to [get_pins rst_sync_reg[0]/PRE]
```

### Relevance to Your Project

For a pure PS-to-PL AXI-BRAM design with no external I/O timing, the only required constraint is the PL clock (auto-defined by the PS IP) and an asynchronous clock group if you add a second PL clock from MMCM. The most important XDC action for your project is verifying that Vivado reports zero WNS violations on the `pl_clk0` domain in `report_timing_summary` — if you see negative WNS, it usually means the AXI interconnect datapath is failing to close at the configured PS clock frequency.

## Kria KV260 / K26 SoM

### Key Findings

- **Primary boot device** is QSPI flash on the SOM containing `BOOT.BIN` (FSBL + PMU firmware + ATF + U-Boot). For bare-metal demos, you bypass this by using JTAG mode: remove the SD card, and the KV260 falls through to JTAG boot.
- **JTAG bare-metal sequence** (no Linux, no SD card):
  1. Connect USB-JTAG, power on KV260
  2. In Vitis: target → connect; download `pmufw.elf` to MicroBlaze PMU (required by PMU ROM)
  3. Load `psu_init.tcl` (in BSP) to initialize DDR and PS peripherals
  4. Download application ELF to Cortex-A53 core 0; run
- **MIO pinout**: K26 SOM exposes 49 MIO pins. On KV260 carrier card, UART1 MIO[36:37] connects to the CP2108 USB-UART bridge (the `/dev/ttyUSB1` port at 115200 baud). UART0 MIO[38:39] is on a header.
- **EMIO GPIO path**: PS GPIO (EMIO) → PL fabric → ZynqMP package pin → SOM240_1 connector → KV260 carrier net → Pmod/expansion header. Any EMIO GPIO must be declared in the VHDL top-level port map and constrained in XDC to an actual package pin on the K26.
- **Power domains**: K26 has separate power domains for PS, PL, and transceivers. PL power (`VCCINT`) is supplied by the carrier card's VCC_INT rail. The PL is unpowered until you download a bitstream or configure via JTAG — do not assume PL registers retain state across power cycles without a stored bitstream.
- **Board files**: Install the KV260 board files from AMD's board store (`xhub:board_parts/xilinx.com/kria_kv260_som`) to get pre-configured PS settings, pinout, and IP defaults. Board files set PS MIO configuration, DDR4 timing parameters, and USB/Ethernet automatically.

### Code Example

```tcl
# JTAG bare-metal download sequence (run in Vitis XSCT or Vivado TCL console)
connect
targets -set -filter {name =~ "PSU"}

# Initialize PS (sets up DDR, MIO, clocks)
source $env(XILINX_VITIS)/scripts/vitis/util/zynqmp_utils.tcl
psu_init

# Load PMU firmware (required before A53 access)
targets -set -filter {name =~ "MicroBlaze PMU"}
dow pmufw.elf
con

# Switch to APU Cortex-A53 core 0
targets -set -filter {name =~ "Cortex-A53 #0"}
rst -processor

# Load and run bare-metal application
dow kv260_bram_demo.elf
con

# Monitor UART output at /dev/ttyUSB1, 115200 8N1
```

### Relevance to Your Project

Your demo targets exactly this flow: JTAG boot → bitstream loaded by Vitis hardware manager → application ELF runs on A53 core 0 → UART output on USB-UART bridge. The `psu_init.tcl` step is often missed when moving from Zynq-7000 tutorials (which use `ps7_init.tcl`) — without it, DDR initialization may not complete and your AXI transactions will hang waiting for the interconnect's DDR-backed response buffer to become ready.

## AMD/Xilinx Tool Updates

### Key Findings

- **Vivado / Vitis 2026.1** (current latest as of September 2026): Major licensing restructuring. The free "WebPACK" license tier is replaced by tiered subscriptions (Basic, Core, Pro) plus perpetual Enterprise/Gold. Zynq UltraScale+ devices (including K26) require at least the **Core** tier. If you are on 2025.1 or 2025.2, your existing license is unaffected.
- **Vivado 2025.2 highlights** (last stable before 2026.x licensing change): New device support for Versal RF Series; Power Design Manager standalone tool for UltraScale+ power estimation; improved incremental compile hit rates; `phys_opt_design` gets new directives for congestion-driven optimization.
- **Vitis 2026.1 new IDE backend**: Vitis Server replaces the Eclipse-based backend for the unified IDE. Classic command-line tools (`hw_server`, `bootgen`, `program_flash`) remain. The new backend improves project indexing speed significantly on large embedded projects.
- **Kria Vitis Platforms** (github.com/Xilinx/kria-vitis-platforms) main branch now targets **Vivado/Vitis 2026.1**. If you are on 2025.1, use the `2025.1` tag of that repo when following platform creation tutorials.
- **Known Vitis 2026.x issues** (AMD article 000040220): Some BSP regeneration sequences fail silently when the XSA platform version mismatches. Workaround: delete and re-import the platform rather than updating in place.
- **AXI BRAM Controller IP**: Version 4.1 (current in 2025.1+) supports AXI4 and AXI4-Lite modes, ECC, and up to 2 BRAM ports. No significant functional changes between 2025.1 and 2026.1 for this IP.

### Code Example

```tcl
# Check Vivado version in TCL and abort if below required minimum
set min_major 2025
set min_minor 1
set ver [split [version -short] "."]
set major [lindex $ver 0]
set minor [lindex $ver 1]

if {$major < $min_major || ($major == $min_major && $minor < $min_minor)} {
    error "Vivado $min_major.$min_minor or later required. Found: [version -short]"
}
puts "INFO: Vivado [version -short] — OK"

# Detect installed board files for KV260
set board_parts [get_board_parts -filter {VENDOR_NAME =~ "*xilinx*" && \
                                          DISPLAY_NAME =~ "*KV260*"}]
if {[llength $board_parts] == 0} {
    puts "WARNING: KV260 board files not found. Install via Tools > Vivado Store."
} else {
    puts "INFO: Found board: $board_parts"
    set_property BOARD_PART [lindex $board_parts 0] [current_project]
}
```

### Relevance to Your Project

If you plan to upgrade from Vivado/Vitis 2025.1 to 2026.1, budget time to: (1) verify your license tier covers K26/Zynq UltraScale+, (2) re-export the XSA and rebuild the Vitis platform from scratch (don't update-in-place due to the known BSP regeneration bug), and (3) update any `create_bd.tcl` scripts that reference IP VLNVs with hardcoded 2025.x version numbers. The 2025.1 toolchain your project currently uses is stable and has no blocking known issues for the AXI-BRAM use case.
