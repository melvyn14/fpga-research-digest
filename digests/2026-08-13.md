## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- **Five-channel handshake**: AXI-Lite uses five independent channels (AW, W, B, AR, R). Every channel is source-synchronous: a transfer completes on the rising edge where both `*VALID` and `*READY` are asserted simultaneously.
- **Write ordering constraint**: The AXI4 spec permits the write address and write data channels to complete in *either* order. A compliant slave must hold `BVALID` low until it has seen both `AWVALID`/`AWREADY` and `WVALID`/`WREADY` handshakes. Violating this is one of the most common causes of silent data corruption.
- **VALID must not depend on READY**: A master is forbidden from waiting for `READY` before asserting `VALID`. This prevents deadlocks but is often accidentally violated in hand-rolled state machines.
- **AXI Protocol Checker IP (PG101)**: Xilinx ships a free in-silicon protocol checker. Add it in simulation or even in hardware (with ILA attached) to catch protocol violations during bring-up.
- **Interconnect selection**: For AXI-Lite peripherals at low throughput (BRAM register access), use the AXI Interconnect v2.1 (PG059) — it is lighter-weight than SmartConnect and sufficient for 1 master / 2 slaves at low bandwidth.
- **XPM_FIFO_AXIL**: New macro in Vivado libraries (UG974) for adding a FIFO buffer on an AXI-Lite interface — useful if the PS and PL clock domains differ slightly.

### Code Example

```vhdl
-- Minimal AXI-Lite slave write FSM (state machine skeleton)
-- Correctly holds BVALID until BOTH AW and W channels complete

type axi_wr_state_t is (IDLE, WAIT_BOTH, SEND_RESP);
signal aw_done, w_done : std_logic := '0';
signal state : axi_wr_state_t := IDLE;

process(aclk)
begin
  if rising_edge(aclk) then
    if aresetn = '0' then
      aw_done <= '0'; w_done <= '0';
      s_axi_bvalid <= '0'; state <= IDLE;
    else
      case state is
        when IDLE =>
          -- Latch channels independently
          if s_axi_awvalid = '1' then aw_done <= '1'; end if;
          if s_axi_wvalid  = '1' then w_done  <= '1'; end if;
          if (s_axi_awvalid or aw_done) = '1' and
             (s_axi_wvalid  or w_done ) = '1' then
            state <= SEND_RESP;
          end if;
        when SEND_RESP =>
          s_axi_bvalid <= '1';
          s_axi_bresp  <= "00"; -- OKAY
          if s_axi_bready = '1' then
            s_axi_bvalid <= '0';
            aw_done <= '0'; w_done <= '0';
            state <= IDLE;
          end if;
        when others => state <= IDLE;
      end case;
    end if;
  end if;
end process;

s_axi_awready <= '1';  -- always ready (single-register slave)
s_axi_wready  <= '1';
```

### Relevance to Your Project

Your `kv260-axi-bram-demo` uses two AXI-BRAM controllers (BRAM0 at `0xA0000000`, BRAM2 at `0xA0010000`) driven by the Zynq PS AXI master. If you ever replace either BRAM controller with a custom VHDL slave, the state machine above is the correct template. The AXI Protocol Checker IP is also worth dropping into your simulation testbench to catch any issues before hardware bring-up.

## Vivado Block Design / IP Integrator

### Key Findings

- **Run Connection Automation**: After adding IP, click *Run Connection Automation* — it wires the PS reset to the reset IP, adds an AXI Interconnect, and maps slave ports into the PS memory space automatically. Always ensure the reset checkbox is selected in the dialog.
- **Address Editor**: Go to the *Address Editor* tab and click *Assign All* to auto-assign base addresses. For fixed-address hardware (like your `0xA0000000` / `0xA0010000`), manually enter the Offset Address and Range to match your software constants.
- **Non-Project Mode in IPI**: As of 2025.1 (UG994), IP Integrator is fully supported in non-project mode — you can call `create_bd_design`, add IPs, run connection automation, and generate outputs all from a TCL script without a `.xpr` file.
- **Save frequently**: Ctrl+S saves the block design (`*.bd`) incrementally. Unsaved BDs are not included in `write_checkpoint`.
- **Validate design**: Always run *Validate Design* (F6 or `validate_bd_design`) before generating a bitstream — it catches unconnected ports and address conflicts that synthesis misses.
- **Regenerate IP outputs**: If you change an IP parameter after synthesis, right-click the IP and *Reset Output Products* before regenerating, otherwise stale netlists persist.

### Code Example

```tcl
# IP Integrator automation in non-project mode (Vivado 2025.1+)
open_project  myproject.xpr
open_bd_design [get_bd_files]

# Fix BRAM addresses to match software constants
set_property offset 0xA0000000 [get_bd_addr_segs {ps/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property range  64K        [get_bd_addr_segs {ps/Data/SEG_axi_bram_ctrl_0_Mem0}]

set_property offset 0xA0010000 [get_bd_addr_segs {ps/Data/SEG_axi_bram_ctrl_1_Mem0}]
set_property range  64K        [get_bd_addr_segs {ps/Data/SEG_axi_bram_ctrl_1_Mem0}]

validate_bd_design
save_bd_design

# Generate all output products
generate_target all [get_bd_designs]
```

### Relevance to Your Project

Your `create_bd.tcl` script should use `set_property offset` to pin the BRAM base addresses to exactly `0xA0000000` and `0xA0010000`. If the Address Editor ever auto-assigns different offsets, your bare-metal C pointers will silently point at unmapped memory. Lock the addresses in TCL so the constraint is version-controlled.

## Vivado TCL Scripting

### Key Findings

- **Batch mode invocation**: `vivado -mode batch -source build.tcl -tclargs "PART=xck26-sfvc784-2LV-c"` — the `-tclargs` value is available inside the script as `$argv`.
- **Non-project mode advantages**: No `.xpr` file, no GUI dependency — the entire flow (read_vhdl → synth_design → opt_design → place_design → route_design → write_bitstream) is expressed as a linear script. Perfect for CI/CD.
- **Design checkpoints**: `write_checkpoint -force post_route.dcp` captures the full routed state. `read_checkpoint post_route.dcp` restores it in seconds — invaluable for iterating on XDC constraints without re-running P&R.
- **Explicit reports**: In non-project mode, no reports are generated automatically. Add `report_timing_summary`, `report_utilization`, `report_io`, and `report_clock_interaction` to your script.
- **Source file management**: Use `read_vhdl -vhdl2008` for VHDL-2008 features. Re-read sources explicitly if any file changes between runs.
- **IP snapshot**: Use `generate_target all` and `export_ip_user_files` to pre-generate IP netlists so synthesis does not need to regenerate them on every run.

### Code Example

```tcl
#!/usr/bin/env vivado -mode batch -source

# Non-project mode build script for kv260-axi-bram-demo
set PART "xck26-sfvc784-2LV-c"

# Read sources
read_vhdl -vhdl2008 {vhdl/kv260_top.vhd}
read_xdc  {xdc/kv260_top.xdc}

# Synthesis
synth_design -top kv260_top -part $PART -flatten_hierarchy rebuilt
write_checkpoint -force checkpoints/post_synth.dcp
report_utilization  -file reports/utilization_synth.rpt

# Implementation
opt_design
place_design
phys_opt_design
route_design
write_checkpoint -force checkpoints/post_route.dcp
report_timing_summary -max_paths 10 -file reports/timing.rpt
report_io             -file reports/io.rpt

# Bitstream
write_bitstream -force output/kv260_top.bit
```

### Relevance to Your Project

Converting your `create_bd.tcl` into a full non-project build script makes the demo entirely reproducible from `git clone` + one command. Add the `post_route.dcp` to `.gitignore` but commit the `reports/timing.rpt` so timing closure history is preserved.

## Vitis Bare-Metal / Standalone

### Key Findings

- **BSP generation flow**: After Vivado exports the XSA (`export_hardware -fixed -xsa`), Vitis creates a Platform project that generates the BSP with drivers for every peripheral in the block design. The BSP must be rebuilt whenever the XSA changes.
- **xil_printf vs printf**: `xil_printf` (from `xil_printf.h`) is a lightweight implementation that eliminates the heavy stdio library — saves ~50–100 KB of flash. It supports `%d`, `%x`, `%s`, `%c` but not floating-point.
- **UART assignment**: In BSP settings, `stdin` and `stdout` must point to the UART instance connected to USB-UART on KV260 — typically `psu_uart_1`. If you see no output, verify this is set correctly in `system.mss`.
- **Memory map in linker script**: The default linker script places code/data in DDR starting at `0x0`. For bare-metal on Cortex-A53, ensure the linker script's `psu_ddr_0` region starts at `0x00000000` and is large enough for stack and heap.
- **Cache coherency with BRAM**: The PS AXI master goes through the CPU cache. When writing to AXI-mapped BRAM from bare-metal C, call `Xil_DCacheFlush()` or `Xil_DCacheDisable()` before reading back — otherwise the CPU may return cached stale data rather than the PL-side value.
- **GIC interrupt controller**: UltraScale+ uses ARM GICv2. To use interrupts from PL to PS, configure them via `XScuGic_Connect()` in the BSP and set the trigger type (rising edge for most PL signals).

### Code Example

```c
/* Bare-metal AXI-BRAM read/write with cache flush - Vitis standalone */
#include "xil_printf.h"
#include "xil_cache.h"
#include "xparameters.h"

#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL
#define TEST_WORDS  16

static volatile u32 *bram0 = (volatile u32 *)BRAM0_BASE;
static volatile u32 *bram2 = (volatile u32 *)BRAM2_BASE;

int test_bram(volatile u32 *bram, u32 base, const char *name) {
    /* Write pattern */
    for (int i = 0; i < TEST_WORDS; i++)
        bram[i] = 0xDEAD0000 | (u32)i;

    /* Flush D-cache so PL sees the writes, not cached values on readback */
    Xil_DCacheFlushRange(base, TEST_WORDS * sizeof(u32));

    /* Readback check */
    for (int i = 0; i < TEST_WORDS; i++) {
        u32 rd = bram[i];
        if (rd != (0xDEAD0000 | (u32)i)) {
            xil_printf("%s FAIL @ [%d]: wrote 0x%08X, read 0x%08X\r\n",
                       name, i, 0xDEAD0000 | i, rd);
            return -1;
        }
    }
    xil_printf("%s PASS\r\n", name);
    return 0;
}

int main(void) {
    xil_printf("KV260 AXI-BRAM Demo\r\n");
    int r0 = test_bram(bram0, BRAM0_BASE, "BRAM0");
    int r1 = test_bram(bram2, BRAM2_BASE, "BRAM2");
    xil_printf(r0 == 0 && r1 == 0 ? "Overall: PASS\r\n" : "Overall: FAIL\r\n");
    while (1);
}
```

### Relevance to Your Project

The `Xil_DCacheFlushRange()` call is the most critical addition if your current `main.c` does not include it. Without it, the write-back D-cache can return CPU-cached values on readback, making the BRAM appear to work even if the AXI bus or BRAM controller has a problem. This is especially relevant because the A53 in the K26 has a 32 KB L1 + 1 MB L2 cache hierarchy.

## XDC Timing Constraints

### Key Findings

- **`set_input_delay` semantics**: Specifies the external system-level path delay (in ns) on a primary input port relative to a clock edge. A positive value means data arrives *after* the launching clock edge. The value is subtracted from the available setup time in the timing analysis.
- **`set_output_delay` semantics**: Specifies the delay budget consumed by the load downstream. The timing engine reserves this margin from the total clock period when checking paths driving the port.
- **Min/max pairs**: Both commands should be applied with `-min` (hold) and `-max` (setup) values separately. Omitting `-min` defaults to 0 — potentially masking hold violations.
- **False paths for asynchronous inputs**: UART RXD, button GPIOs, and async reset inputs should use `set_false_path -from [get_ports ...]` or `set_input_delay` with an appropriate `async_reg` FLOP chain.
- **Kria SOM XDC**: The K26 SOM ships with an official XDC file (in the Vivado board files) that captures all SOM-connector-to-package-pin mappings. Always start from this file — do not hand-write pin assignments for the MPSoC device.
- **Clock groups for PS clocks**: The PS-generated clocks (`pl_clk0`, `pl_clk1`) are automatically constrained by the processing system IP. Add `set_clock_groups -asynchronous -group [get_clocks clk_pl_0] -group [get_clocks clk_pl_1]` if you use two PS clocks to prevent false timing paths between them.

### Code Example

```tcl
# XDC snippet for KV260 AXI-BRAM demo
# PS pl_clk0 @ 100 MHz is auto-constrained by Zynq IP

# Example: external GPIO input with 2 ns board delay (max), 0.5 ns (min)
set_input_delay -clock [get_clocks clk_pl_0] -max 2.0 [get_ports gpio_i[*]]
set_input_delay -clock [get_clocks clk_pl_0] -min 0.5 [get_ports gpio_i[*]]

# Example: external GPIO output driving a 10 ns load
set_output_delay -clock [get_clocks clk_pl_0] -max 3.0 [get_ports gpio_o[*]]
set_output_delay -clock [get_clocks clk_pl_0] -min 0.5 [get_ports gpio_o[*]]

# Async UART RX input - false path (no timing analysis needed)
set_false_path -from [get_ports uart_rxd]

# If using two PS clocks: declare them asynchronous to each other
set_clock_groups -asynchronous \
  -group [get_clocks clk_pl_0] \
  -group [get_clocks clk_pl_1]
```

### Relevance to Your Project

The KV260 bare-metal demo is PS-master-only (no external I/O except USB-UART driven by MIO, not PL). For this project the critical XDC concern is confirming that the AXI-BRAM internal paths meet timing at your chosen `pl_clk0` frequency (typically 100 or 200 MHz). Run `report_timing_summary` and check the `Intra Clock Paths` section — WNS must be positive before testing in hardware.

## Kria KV260 / K26 SoM

### Key Findings

- **Boot mode selection**: The MODE[3:0] pins on the SOM connector are tied on the carrier card. KV260 Starter Kit ships with QSPI32 (`MODE = 0b0010`) as the default boot mode. The Boot ROM reads the FSBL from QSPI flash; to boot from SD card change the physical switches on the carrier.
- **MIO bank 500 (LVCMOS 1.8V)**: USB-UART (the FTDI on KV260) is connected to MIO 36/37 (psu_uart_1) in the 1.8V MIO bank. The BSP must reference `psu_uart_1` as stdout, not `psu_uart_0`.
- **EMIO**: EMIO pins route PL signals through the PS GPIO block (128 EMIO bits available on ZU5). This is how the KV260 default bitstream connects the carrier fan-control pin — a useful pattern for any PL-to-PS GPIO bridging in your design.
- **Power domains**: K26 has four power domains: PL (VCCINT), PS (VCC_PSINTLP/FP), GTR (VCCINT_GT), and I/O banks. VCCO for the PL I/O banks (HD banks on KV260) is carrier-card-supplied — KV260 provides 3.3V. Any custom PL I/O must use LVCMOS33 standard.
- **Vivado board files for K26**: In Vivado's *Create Project* wizard, search for "KV260" to load the official board files. These pre-configure PS DDR, UART, clock parameters — don't skip this step.
- **Bare-metal entry point on A53**: After FSBL loads, execution jumps to the bare-metal ELF at the linker-specified load address in DDR. The Cortex-A53 starts in EL3 (secure); FSBL drops to EL1 before handing off to the application.

### Code Example

```tcl
# Vivado TCL: Configure processing system for KV260 using board presets
# (run after create_bd_design; assumes KV260 board files loaded)

create_bd_cell -type ip -vlnv xilinx.com:ip:zynq_ultra_ps_e:3.5 zynq_ultra_ps_e_0
apply_board_preset zynq_ultra_ps_e_0

# Verify UART1 is enabled (MIO 36-37, pl_clk0 @ 100 MHz)
set_property CONFIG.PSU__UART1__PERIPHERAL__ENABLE  1 [get_bd_cells zynq_ultra_ps_e_0]
set_property CONFIG.PSU__UART1__PERIPHERAL__IO      {MIO 36 .. 37} \
             [get_bd_cells zynq_ultra_ps_e_0]
set_property CONFIG.PSU__CRL_APB__PL0_REF_CTRL__FREQMHZ 100 \
             [get_bd_cells zynq_ultra_ps_e_0]

# Enable two GP AXI master ports for two BRAM slaves
set_property CONFIG.PSU__USE__M_AXI_GP0 1 [get_bd_cells zynq_ultra_ps_e_0]
```

### Relevance to Your Project

The `apply_board_preset` call is critical — it configures DDR4 timing, MIO pin assignments, and clock sources for the K26 package automatically. Manually configuring the `zynq_ultra_ps_e` IP without a board preset leads to lengthy DDR training failures during boot. For your two-BRAM demo you need at least one AXI GP master port (`M_AXI_HPM0_FPD`) enabled.

## AMD/Xilinx Tool Updates (2025.x / 2026.x)

### Key Findings

- **Vivado 2026.1 — tiered licensing**: AMD restructured Vivado into five tiers: *Basic*, *Core*, *Pro* (annual subscriptions) and *Enterprise*, *Gold* (perpetual). Feature gates now include number of ILA probe cores, System ILA, IBERT, simulation support, incremental compile, DFX (Dynamic Function eXchange), and security features. Free/WebPACK tier is subsumed into *Basic*.
- **Verify your tier before upgrading**: If your CI uses the free tier for synthesis/bitstream generation, confirm *Basic* still covers your target device (KV260 / xck26) and that ILA debug insertion is not blocked.
- **Vitis 2025.1 released 2025-07-08**: Covers Vitis Unified Software Platform (UG1742). The key change for bare-metal users is the continued unification of the classic SDK workflow into the Vitis IDE — the standalone domain and BSP generation are now fully within Vitis.
- **2026.1 tools available**: The AMD downloads page lists 2026.1 as the current release as of mid-2026. If you are on 2025.1, upgrading to 2026.1 brings the new licensing model but also the latest device support and bug fixes.
- **Known AXI4-Lite issue (UG1483)**: A known issue exists in AXI4-Lite interface generation affecting model composer / system generator workflows — check the 2025.2 UG1483 errata if you generate AXI4-Lite interfaces from high-level tools.
- **IP Integrator in Non-Project Mode (UG994 2025.1)**: Explicitly documented as supported in 2025.1 — a green light to fully script your BD generation without a .xpr.

### Code Example

```tcl
# Check Vivado version at script start and warn if unexpected
set viv_ver [version -short]
if {![string match "2025.*" $viv_ver] && ![string match "2026.*" $viv_ver]} {
    puts "WARNING: Script tested on 2025.1/2026.1, running on $viv_ver"
}
puts "Vivado version: $viv_ver"

# Scripted bitstream flow with explicit checkpoint and report
synth_design  -top kv260_top -part xck26-sfvc784-2LV-c
write_checkpoint -force checkpoints/post_synth.dcp

opt_design
place_design
route_design
write_checkpoint -force checkpoints/post_route.dcp

# Timing must pass (WNS >= 0) before committing bitstream
set wns [get_property SLACK [get_timing_paths -max_paths 1]]
if {$wns < 0} {
    puts "ERROR: Timing not met (WNS = $wns ns). Aborting bitstream."
    exit 1
}
write_bitstream -force output/kv260_top.bit
puts "Bitstream written. WNS = $wns ns"
```

### Relevance to Your Project

The version guard script above is a clean addition to your `create_bd.tcl` or a wrapper build script — it prevents silent errors if the toolchain is upgraded mid-project. The WNS check before `write_bitstream` prevents shipping a timing-failing bitstream that may exhibit intermittent BRAM read/write errors in hardware (a notoriously hard-to-debug failure mode).
