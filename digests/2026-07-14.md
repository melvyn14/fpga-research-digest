# FPGA Research Digest - 2026-07-14

## Executive Summary

- **AXI-Lite backpressure bug in Xilinx-generated example slaves**: The Vivado-generated AXI-Lite slave template incorrectly handles `BREADY`/`RREADY` de-assertion backpressure; formal verification has confirmed multiple errors. Audit any generated slave logic before trusting it in the KV260 BRAM demo.
- **Raise `AWREADY` only when both `AWVALID` and `WVALID` are asserted**: This channel-synchronization rule is required by the AXI spec and often missing from beginner implementations. Without it, a write-address handshake can complete without a data handshake, silently corrupting BRAM writes.
- **Vivado 2025.1 adds an RTL-based AXI Switch IP and ultra-low-area mode**: The new `STRATEGY` parameter for AXI Switch and AXI SmartConnect can reduce LUT cost. New dedicated "Clocking and Reset" and "Interrupt and AXI-4 Lite" views in IP Integrator improve block design readability.
- **`write_project_tcl -force recreate.tcl`** exports a complete recreation script from any existing GUI project — the fastest way to version-control the KV260 block design with minimal manual TCL effort.
- **Vitis 2025.x linker scripts gained NOC Memory segments and separate Code/Data sections**: Bare-metal developers targeting the Cortex-A53 on the K26 SoM should regenerate their BSP and linker script when upgrading tool versions.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- All AXI4 signals are sampled on the **rising edge** of the clock; all signal changes must occur *after* the rising edge to satisfy setup/hold.
- The five-channel handshake completes only when both `VALID` and `READY` are simultaneously asserted on the rising edge — neither side needs memory of prior cycles, making it a **stateless** protocol per beat.
- **Critical slave-side rule**: `S_AXI_AWREADY` should only be raised when *both* `S_AXI_AWVALID` **and** `S_AXI_WVALID` are asserted, synchronizing the write-address and write-data channels.
- **Backpressure handling is the #1 mistake**: If the master holds `BREADY` low, the slave must lower `AWREADY`/`WREADY`; if the master holds `RREADY` low, the slave must lower `ARREADY`. Xilinx's own Vivado-generated AXI-Lite slave code has bugs in this path that have been confirmed by formal property checking (ZipCPU/Dan Gisselquist).
- AXI-Stream: `TKEEP` enables byte-granular transfers over wide buses; leaving it unconnected restricts FIFO to word-aligned boundaries only. `TLAST` must be buffered inside FIFOs — it carries frame/line metadata that is lost if the FIFO does not pass it through.
- AXI-Stream packet-mode FIFOs must be sized to hold **at least one full packet** before outputting, or a high-throughput source will stall or overflow.
- AXI DataMover does **not** support null/sparse `TKEEP` except at the `TLAST` beat.

### Code Example

```vhdl
-- Correct AXI-Lite write-channel synchronization in a VHDL slave
-- Raise AWREADY only when both address AND data are valid
process(S_AXI_ACLK)
begin
  if rising_edge(S_AXI_ACLK) then
    if S_AXI_ARESETN = '0' then
      axi_awready <= '0';
      aw_en       <= '1';
    else
      if aw_en = '1' and S_AXI_AWVALID = '1' and S_AXI_WVALID = '1' then
        axi_awready <= '1';
        aw_en       <= '0';
      elsif S_AXI_BREADY = '1' and axi_bvalid = '1' then
        aw_en       <= '1';
        axi_awready <= '0';
      else
        axi_awready <= '0';
      end if;
    end if;
  end if;
end process;
```

### Relevance to Your Project

The KV260 AXI-BRAM demo uses the Xilinx AXI BRAM Controller IP to bridge PS writes to BRAM0 (0xA0000000) and BRAM2 (0xA0010000). The Xilinx IP itself is well-tested, but **any custom AXI-Lite peripherals added later** — or the wrapper in `kv260_top.vhd` — must implement backpressure correctly. Run a quick simulation driving `BREADY = '0'` mid-transaction to verify your slave does not dead-lock.

## Vivado Block Design / IP Integrator

### Key Findings

- **Connection Automation**: Click "All Automation" in the Run Connection Automation dialog to connect AXI slaves, clocks, and resets in one step. Each AXI interface can have its clock source individually changed by selecting the entry in the list.
- **Address Editor**: The Address Editor appears automatically when an AXI master (e.g., Zynq PS HPM0) is present. You can set the range to `4K` minimum to conserve the 4 GB address space — critical when using multiple BRAM controllers.
- **IP Integrator 2025.1 adds dedicated views**: A "Clocking and Reset" view and an "Interrupt and AXI-4 Lite" view improve at-a-glance understanding of complex block designs.
- Regenerating output products after an IP upgrade is mandatory; stale `.xci` files can silently use an old IP version. Use **Upgrade IP** from the Reports menu after changing tool versions.
- For the Zynq/Kria PS, the HPM0 AXI master is a 32-bit master with 49-bit addressing. Set `C_M_AXI_HPM0_FPD_DATA_WIDTH` to match your slave data width (32-bit is typical for AXI-Lite BRAM controllers).

### Code Example

```tcl
# Automate all block-design connections via TCL (run after instantiating IP)
apply_bd_automation -rule xilinx.com:bd_rule:axi4 \
  -config { Clk_master {Auto} Clk_slave {Auto} Clk_xbar {Auto} \
            Master {/zynq_ultra_ps_e_0/M_AXI_HPM0_FPD} \
            Slave {/axi_bram_ctrl_0/S_AXI} \
            intc_ip {New AXI Interconnect} \
            master_apm {0} } \
  [get_bd_intf_pins axi_bram_ctrl_0/S_AXI]

# Set BRAM0 base address to match bare-metal code expectation
set_property offset 0xA0000000 \
  [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property range 64K \
  [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
```

### Relevance to Your Project

Your `create_bd.tcl` script likely mirrors exactly this pattern for the two BRAM controllers. Verifying that the `offset` values match your C bare-metal addresses (0xA0000000 and 0xA0010000) in the TCL script is the single most important consistency check. A mismatch here causes every read/write to fail silently or access wrong memory — the most common cause of `FAIL` printouts in AXI-BRAM demos.

## Vivado TCL Scripting

### Key Findings

- **`write_project_tcl -force recreate.tcl`**: Generates a complete TCL script to recreate your GUI project from scratch. This is the recommended way to version-control Vivado projects — commit the TCL, not the `.xpr`.
- Vivado logs every GUI command to a **journal file** (`.jou`) and a full history log (`.log`). These are invaluable for discovering the TCL equivalent of any GUI action.
- **Batch (non-project) mode**: `vivado -mode batch -source script.tcl` runs synthesis and implementation headlessly. In non-project mode, all design state lives in memory — use `write_checkpoint` after each major step to save design checkpoints (`.dcp`).
- Non-project mode implementation requires a synthesis DCP as input, and stages 1, 3, and 5 (place, route, write bitstream) must always be run in order.
- Scripts enable exact reproducibility across machines and CI environments — no GUI-locked settings.

### Code Example

```tcl
# Non-project mode: synthesize + implement + write bitstream
read_vhdl   ../vhdl/kv260_top.vhd
read_xdc    ../constraints/kv260.xdc
read_ip     ../ip/block_design_wrapper.v   ;# generated wrapper

synth_design -top kv260_top -part xck26-sfvc784-2LV-c
write_checkpoint -force post_synth.dcp

opt_design
place_design
route_design
write_checkpoint -force post_route.dcp

write_bitstream -force kv260_top.bit
write_hw_platform -fixed -force -file kv260_top.xsa
```

### Relevance to Your Project

Replacing a GUI-driven build with a single `vivado -mode batch -source build.tcl` command makes the KV260 AXI-BRAM demo fully reproducible and CI-friendly. Your `create_bd.tcl` already handles block design creation — wrap it with the synthesis and implementation commands above and you can regenerate the complete bitstream from a clean repo clone.

## Vitis Bare-Metal / Standalone

### Key Findings

- **`xil_printf` vs `printf`**: `xil_printf` (from `xil_printf.h`) is a lightweight formatted print that uses far less memory than the full `stdio` library. It does not support floating-point format specifiers (`%f`) — use `printf` only if you enable full libc in BSP settings.
- **BSP regeneration after hardware change**: Any XSA export from Vivado must be followed by a BSP regeneration in Vitis. Stale BSPs cause incorrect driver addresses and can silently pass with wrong UART baud rates.
- **Linker script 2025.x changes**: Code and Data segments are now explicitly separated. NOC Memory segments have been added to the memory section. If you see linker errors after upgrading to 2025.x, regenerate the linker script via Vitis → Application → Modify BSP Settings.
- **Vitis 2025.2 known issue**: `xil_printf.h` was reported as "not found" in some project configurations due to an include-path regression — workaround is to add `${BSP_DIR}/include` manually to the compiler include paths.
- For AXI-Lite register access in bare-metal, use `Xil_Out32(addr, data)` and `Xil_In32(addr)` from `xil_io.h` rather than raw pointer casts — these issue the correct memory barriers for Cortex-A53.

### Code Example

```c
#include "xil_io.h"
#include "xil_printf.h"

#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL

void bram_write_read_test(u32 base, const char *name) {
    const u32 pattern = 0xDEADBEEFUL;
    Xil_Out32(base, pattern);          /* AXI-Lite write */
    u32 readback = Xil_In32(base);     /* AXI-Lite read  */
    if (readback == pattern) {
        xil_printf("%s: PASS (0x%08X)\r\n", name, readback);
    } else {
        xil_printf("%s: FAIL — wrote 0x%08X, read 0x%08X\r\n",
                   name, pattern, readback);
    }
}

int main(void) {
    xil_printf("KV260 AXI-BRAM Test\r\n");
    bram_write_read_test(BRAM0_BASE, "BRAM0");
    bram_write_read_test(BRAM2_BASE, "BRAM2");
    return 0;
}
```

### Relevance to Your Project

This pattern matches the `main.c` intent (write patterns, read back, print PASS/FAIL). Using `Xil_Out32`/`Xil_In32` rather than `*(volatile u32*)` ensures the Cortex-A53 issues the required `dsb` data synchronization barriers before and after the AXI transaction, preventing out-of-order execution from producing false FAILs.

## XDC Timing Constraints

### Key Findings

- XDC is based on Synopsys Design Constraints (SDC) format; every command valid in SDC is valid in XDC.
- **Primary clock**: `create_clock -period 10.000 [get_ports sys_clk]` is the mandatory first line. For Kria/Zynq, the PS provides clocks to PL via `FCLK_CLK0` — reference it with `get_pins zynq_ultra_ps_e_0/inst/FCLK_CLK0`.
- **`set_input_delay` / `set_output_delay`**: Model board-level delays from external devices. A virtual clock (`create_clock -name virt_clk -period N`) is required as a reference when the external clock is not physically present on an FPGA pin.
- **`set_clock_groups -asynchronous`**: Tells Vivado to skip timing analysis between independent clock domains — essential for the PS-to-PL clock boundary on Kria. Without it, Vivado reports false timing violations across the clock-domain crossing.
- A minimal, complete XDC for a single-clock AXI-Lite design needs fewer than 20 lines: one `create_clock`, I/O delay pairs, false paths for async resets and JTAG.
- Constraint order matters: `create_clock` must precede any constraints that reference the clock.

### Code Example

```xdc
# KV260 bare-metal AXI-BRAM XDC (minimal template)

# PS fabric clock delivered to PL at 100 MHz
create_clock -period 10.000 -name pl_clk0 \
  [get_pins zynq_ultra_ps_e_0/inst/FCLK_CLK0]

# Prevent timing analysis across PS-PL async clock boundary
set_clock_groups -asynchronous \
  -group [get_clocks pl_clk0] \
  -group [get_clocks -of_objects \
    [get_pins zynq_ultra_ps_e_0/inst/PS8_i/PLCLK[0]]]

# False path on active-low reset (async, not data)
set_false_path -from [get_ports aresetn]

# UART TX/RX — no external timing reference needed for PS UART
set_false_path -to   [get_ports uart_txd]
set_false_path -from [get_ports uart_rxd]
```

### Relevance to Your Project

The KV260 bare-metal design uses `FCLK_CLK0` from the PS to clock all PL logic including both BRAM controllers. Adding the `set_clock_groups -asynchronous` constraint between the PS internal clock and `pl_clk0` eliminates phantom timing violations that can appear during implementation, especially if you later add any GPIO or status signals crossing from PL back to the PS.

## Kria KV260 / K26 SoM

### Key Findings

- **Boot modes** are selected by the `MODE[3:0]` pins on the SoM connector, allowing the carrier card to choose JTAG, SD, or QSPI boot. The KV260 carrier card exposes a MODE DIP switch. For bare-metal development, JTAG boot is the fastest iteration path.
- **MIO pins 0–25** are reserved for the PS peripherals on the K26 SoM (UART, I2C, SD card, eMMC). Custom designs should not re-map these MIO pins. EMIO gives access to PL-driven GPIO.
- **VCCO for sideband signals is 1.8V** on the K26 SoM. Carrier card designers must ensure all PL I/O banks match this voltage, or configure them for 3.3V only on banks that are not connected to the SoM sideband.
- **Power domains**: The K26 SoM contains PS, PL, and GT power rails. The PL must be powered even in PS-only bare-metal applications because the AXI interconnect between PS and PL resides in PL fabric.
- A community bare-metal 4K streaming tutorial for the KV260 (updated May 2026 for Vivado/Vitis 2025.2) covers: block design generation, HDL wrapper creation, BRAM address map verification, XSA export, platform creation, and Cortex-A53 application build — matching the exact workflow of the AXI-BRAM demo.
- A GitHub template (`miya4649/Vitis_KV260_KR260_Template`) provides a minimal bare-metal Vitis project for KV260 and KR260 as a starting point for new PL applications.

### Code Example

```tcl
# Vivado TCL: configure Zynq PS for KV260 (K26 SoM MIO assignment)
# Sets UART1 on MIO pins 8/9 (standard KV260 USB-UART path)
set_property -dict [list \
  CONFIG.PSU__UART1__PERIPHERAL__ENABLE {1} \
  CONFIG.PSU__UART1__PERIPHERAL__IO {MIO 8 .. 9} \
  CONFIG.PSU__UART1__BAUD_RATE {115200} \
  CONFIG.PSU__FPGA_PL0_ENABLE {1} \
  CONFIG.PSU__CRL_APB__PL0_REF_CTRL__FREQMHZ {100} \
] [get_bd_cells zynq_ultra_ps_e_0]
```

### Relevance to Your Project

The KV260 USB-UART goes through UART1 on MIO 8/9 at 115200 baud — this is the path your `xil_printf` PASS/FAIL output uses. If you see garbled output on the host terminal, verify this PS configuration in your block design. The `PSU__FPGA_PL0_ENABLE` and 100 MHz `PL0_REF_CTRL` settings are required to drive `FCLK_CLK0` to the AXI BRAM controllers.

## AMD/Xilinx Tool Updates: Vivado/Vitis 2025.x

### Key Findings

- **Vivado 2025.1 highlights**:
  - New **RTL-based AXI Switch IP**: Fully customizable bridge between AXI interface types/widths. Replaces the older AXI Interconnect IP in new designs.
  - **Ultra-low-area mode** for AXI Switch and AXI SmartConnect via `STRATEGY` parameter — reduces LUT utilization for resource-constrained designs.
  - New dedicated **"Clocking and Reset"** and **"Interrupt and AXI-4 Lite"** views in IP Integrator for improved design navigation.
  - **PS-first boot with dynamic PL load**: The PS can now boot independently and load the PL bitstream dynamically at runtime, enabling more flexible boot flows.
  - **New Pblock planner** for floorplanning.
  - Improved **HLS timing estimation accuracy**.

- **Vitis 2025.1 highlights**:
  - Enhanced **GEMV & FFT for AI Engine** using 2D parallel AIE+PL architecture.
  - Vectorized bitonic SIMD sorting, correlation, and convolution for AI Engine targets.
  - Improved BSP generation and linker script handling (NOC Memory segments, separated Code/Data).

- **Vitis 2025.2 known issue**: `xil_printf.h` not found in some configurations — manually add BSP include path as workaround.

- **Vivado 2025.2** release notes document additional known issues; always cross-check the `UG973` release notes PDF before starting a major upgrade.

### Code Example

```tcl
# Vivado 2025.1: use AXI Switch IP with ultra-low-area strategy
# (replaces older axi_interconnect in new designs)
create_bd_cell -type ip -vlnv xilinx.com:ip:axi_noc:1.0 axi_noc_0

# For resource-constrained Kria designs, set SmartConnect ultra-low-area mode
set_property CONFIG.STRATEGY {MinArea} \
  [get_bd_cells axi_smc]

# Verify IP versions after upgrade
report_ip_status -name ip_status
# Review output — upgrade any "Version Locked" or "Revision Change" IPs
upgrade_ip -vlnv xilinx.com:ip:axi_bram_ctrl:4.0 \
  [get_ips -all *axi_bram_ctrl*]
```

### Relevance to Your Project

The KV260 AXI-BRAM demo was built on Vivado/Vitis 2025.1. The new IP Integrator views make it easier to spot misconfigured clock or interrupt connections at a glance. If you upgrade to 2025.2, run `report_ip_status` immediately after opening the project — AXI BRAM Controller and SmartConnect IPs often get "Revision Change" flags that require an explicit upgrade step before re-synthesis.
