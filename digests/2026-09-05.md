## Executive Summary

- **AXI-Lite BRAM write-enable timing bug**: The Xilinx AXI BRAM Controller IP has a documented quirk where the BRAM write-enable asserts one clock early and holds one clock longer than expected; tying the `BRAM Enable` signal correctly is the fix — directly relevant if you see stale/extra data in reads from BRAM0 or BRAM2.
- **TVALID stickiness is a hard protocol rule**: Once your master drives `AWVALID`/`WVALID` high, it must stay high until the corresponding `READY` is observed — violating this causes silent deadlocks on AXI-Lite, especially at the PS-to-PL boundary of the K26.
- **KV260 bare-metal QSPI boot requires FSBL + PMUFW + app.elf + bitstream packed into boot.bin** — JTAG is for development, QSPI is for standalone power-on boot; the Vitis `bootgen` flow handles this.
- **Non-project Vivado TCL** (`read_vhdl` → `synth_design` → `opt_design` → `place_design` → `route_design` → `write_bitstream`) is reproducible and CI-friendly; avoids the `.xpr` lock-in pitfall of exported `write_bd_tcl` scripts that embed tool-version metadata.
- **Vitis 2025.1 release notes** (UG1742, published July 8 2025) and the companion IP change log (Answer Record 000037919) are the authoritative delta from 2024.2 — check these before upgrading an existing KV260 project.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- **VALID stickiness rule (hard)**: Once `xVALID` is asserted by a master (`AWVALID`, `WVALID`, `ARVALID`), it **must not deassert** until the corresponding `xREADY` is observed. Deasserting early causes the slave to miss the transaction; on the PS AXI-Lite interface this can look like a silent hang rather than an error.
- **READY may depend on VALID, but not vice-versa**: VALID must be asserted independently of READY. Designs that gate VALID on READY create a combinational deadlock.
- **BRAM Controller write-enable timing quirk**: The Xilinx AXI BRAM Controller IP (all versions up to at least 4.1) has a documented simulation/synthesis mismatch where WE asserts one clock before data and holds one extra clock. Fix: verify the `BRAM_EN` tie-off in your block design. If BRAM0 (0xA0000000) or BRAM2 (0xA0010000) returns stale values on the first read after write, this is the first place to look.
- **AXI-Stream abort/flush**: A slave may hold `TREADY` low indefinitely; any design that assumes a bounded TREADY latency must include a timeout/watchdog or accept head-of-line blocking.
- **Handshake check idiom**: The canonical simulation check is `if (VALID && READY)` — adding any extra conditions to this (e.g., state machine qualifiers) causes missed handshake detection in waveform analysis.

### Code Example

```vhdl
-- AXI-Lite write-channel handshake — minimal compliant master fragment
-- Drives AWVALID/WVALID simultaneously (legal per spec) and waits for both READYs
process(clk)
begin
  if rising_edge(clk) then
    if rst = '1' then
      awvalid <= '0'; wvalid <= '0'; state <= IDLE;
    else
      case state is
        when IDLE =>
          awaddr  <= TARGET_ADDR;
          wdata   <= WRITE_DATA;
          wstrb   <= "1111";
          awvalid <= '1';
          wvalid  <= '1';
          state   <= WAIT_ACK;
        when WAIT_ACK =>
          -- deassert only after BOTH channels handshake
          if awready = '1' then awvalid <= '0'; end if;
          if wready  = '1' then wvalid  <= '0'; end if;
          if awready = '1' and wready = '1' then
            state <= IDLE;
          end if;
        when others => state <= IDLE;
      end case;
    end if;
  end if;
end process;
```

### Relevance to Your Project

Your bare-metal C code drives the PS AXI-Lite master via `Xil_Out32`/`Xil_In32`, which ultimately produce AXI transactions to BRAM0 (`0xA0000000`) and BRAM2 (`0xA0010000`). The PS hardware handles the handshake automatically, but any custom PL-side IP that wraps or observes these buses must obey the VALID-stickiness rule. If you ever see a PASS turn into a FAIL intermittently, suspect the write-enable timing quirk in the AXI BRAM Controller.

## Vivado Block Design / IP Integrator

### Key Findings

- **Connection automation**: `apply_bd_automation` automates AXI interconnect and clock/reset wiring — invoke it after placing all IP cells, not incrementally, to get the best results.
- **Address editor**: Every AXI slave must have a unique, non-overlapping address range assigned in the Address Editor (or via TCL `assign_bd_address`). Vivado does not error at block design time for overlapping ranges — only at implementation.
- **Regeneration tip**: After adding a new IP or changing AXI data-width, run `validate_bd_design` before generating output products; it surfaces connectivity errors early and avoids cryptic synthesis failures downstream.
- **Version-locked TCL exports**: `write_bd_tcl` embeds the Vivado version that created the design; sourcing it in a different version may fail or produce warnings. Store the TCL in version control but test it on each tool upgrade.
- **IP catalog refresh**: If an IP shows a yellow exclamation mark after a tool version change, run `upgrade_ip [get_ips *]` in the TCL console rather than re-creating it.

### Code Example

```tcl
# Re-create block design headlessly from an exported TCL
# Run as: vivado -mode batch -source create_bd.tcl

create_project kv260_proj ./kv260_proj -part xck26-sfvc784-2LV-c
set_property board_part xilinx.com:kv260_som:part0:1.4 [current_project]

create_bd_design "kv260_bd"

# Place Zynq MPSoC
set zynq [create_bd_cell -type ip -vlnv xilinx.com:ip:zynq_ultra_ps_e:3.5 zynq_ultra_ps_e_0]
apply_board_preset $zynq

# Place two AXI BRAM Controllers
set bram_ctrl0 [create_bd_cell -type ip -vlnv xilinx.com:ip:axi_bram_ctrl:4.1 axi_bram_ctrl_0]
set bram_ctrl2 [create_bd_cell -type ip -vlnv xilinx.com:ip:axi_bram_ctrl:4.1 axi_bram_ctrl_1]

# Apply automation (wires AXI interconnect, clk, rst)
apply_bd_automation -rule xilinx.com:bd_rule:axi4 \
  -config {Master "/zynq_ultra_ps_e_0/M_AXI_HPM0_LPD" Clk "Auto"} \
  [get_bd_intf_pins axi_bram_ctrl_0/S_AXI]

# Assign addresses
assign_bd_address [get_bd_addr_segs {axi_bram_ctrl_0/S_AXI/Mem0}] -range 64K -offset 0xA0000000
assign_bd_address [get_bd_addr_segs {axi_bram_ctrl_1/S_AXI/Mem0}] -range 64K -offset 0xA0010000

validate_bd_design
save_bd_design
generate_target all [get_files *.bd]
```

### Relevance to Your Project

Your `create_bd.tcl` script builds the block design containing the two BRAM controllers at exactly these addresses. The `assign_bd_address` commands must produce non-overlapping 64 KB windows at `0xA0000000` and `0xA0010000` — verify with `get_bd_addr_segs` in the TCL console if read-back fails at runtime.

## Vivado TCL Scripting

### Key Findings

- **Non-project mode is CI-friendly**: Avoids `.xpr` file, `.cache`, and `.runs` directories; the entire flow is `read_*` → `synth_design` → `opt_design` → `place_design` → `route_design` → `write_bitstream`.
- **`write_bd_tcl` version lock**: Exported block-design TCL embeds tool version metadata — it should only be sourced in the version it was created with. Use it for version control + documentation, but test on tool upgrades.
- **IP VLNV identifiers**: Always pin the full VLNV string (`xilinx.com:ip:axi_bram_ctrl:4.1`) in scripts; using partial IDs can silently pick up a newer version after a tool upgrade.
- **Batch mode invocation**: `vivado -mode batch -source script.tcl` runs headlessly; exit codes propagate to the shell, enabling `Makefile` integration.
- **Tcl `proc` for reusable IP placement**: Wrapping repeated `create_bd_cell` + `set_property` patterns into a `proc` reduces duplication and makes the script maintainable.

### Code Example

```tcl
# Non-project mode build script skeleton for KV260 AXI-BRAM project
# Usage: vivado -mode batch -source build.tcl

set PART "xck26-sfvc784-2LV-c"
set TOP  "kv260_top"
set OUTDIR "./output"

file mkdir $OUTDIR

# Read sources
read_vhdl -vhdl2008 [glob ./vhdl/*.vhd]
read_xdc  [glob ./constraints/*.xdc]
read_ip   [glob ./ip/*.xci]

# Synthesize
synth_design -top $TOP -part $PART -flatten_hierarchy rebuilt
write_checkpoint -force $OUTDIR/post_synth.dcp

# Implement
opt_design
place_design
phys_opt_design
route_design
write_checkpoint -force $OUTDIR/post_route.dcp

# Reports & bitstream
report_timing_summary -file $OUTDIR/timing.rpt
report_utilization    -file $OUTDIR/util.rpt
write_bitstream -force $OUTDIR/$TOP.bit

puts "Build complete: $OUTDIR/$TOP.bit"
```

### Relevance to Your Project

Your existing `create_bd.tcl` handles the block design step. Wrapping it in a non-project `build.tcl` shell as above makes the full Vivado flow (`tcl/build.tcl`) runnable from a `Makefile` with a single `make bitstream` target — useful for a CI check on every push to `kv260-axi-bram-demo`.

## Vitis Bare-Metal / Standalone

### Key Findings

- **BSP UART port**: In Vitis Unified IDE, the standalone BSP defaults `stdin`/`stdout` to the first UART found in the hardware (`psu_uart_0`). For KV260 USB-UART (connected to `psu_uart_1`), you must set `stdin` and `stdout` to `psu_uart_1` in `vitis-comp.json` under BSP settings, or `xil_printf` will silently discard output.
- **`xil_printf` is not buffered**: It writes directly to UART; no `fflush()` needed. However, it does not support all format specifiers (`%f`, `%e` are absent in the lightweight version) — use `print()` for strings and manual hex formatting for floats.
- **Linker script (`lscript.ld`)**: The default linker script places `.text` in DDR (`ps_ddr_0`). For fastest execution on Cortex-A53, move time-critical functions to OCM (`psu_ocm_ram_0`, 256 KB) using the `__attribute__((section(".ocm")))` pragma and add the section to `lscript.ld`.
- **Interrupt controller**: The standalone BSP includes `XScuGic` for the GIC-400; for bare-metal AXI interrupt testing, register your PL interrupt on `IRQ_F2P[0]` (connected to `pl_ps_irq0` in the block design) and set the trigger type to level-high.
- **2025.1 Vitis release** (UG1742, July 2025): Vitis Unified IDE replaces the legacy Eclipse-based IDE; platform creation and domain configuration now use `vitis -s` (scripted) flows compatible with Makefile integration.

### Code Example

```c
/* Minimal AXI-Lite BRAM read/write test — bare-metal C for KV260 */
#include "xil_io.h"
#include "xil_printf.h"

#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL
#define TEST_PATTERN 0xDEADBEEFUL

static int test_bram(const char *name, uintptr_t base) {
    Xil_Out32(base, TEST_PATTERN);
    u32 val = Xil_In32(base);
    if (val == TEST_PATTERN) {
        xil_printf("%s PASS: read 0x%08X\r\n", name, val);
        return 0;
    }
    xil_printf("%s FAIL: expected 0x%08X got 0x%08X\r\n",
               name, (u32)TEST_PATTERN, val);
    return -1;
}

int main(void) {
    xil_printf("KV260 AXI-BRAM test starting...\r\n");
    int rc = 0;
    rc |= test_bram("BRAM0", BRAM0_BASE);
    rc |= test_bram("BRAM2", BRAM2_BASE);
    xil_printf(rc == 0 ? "ALL PASS\r\n" : "SOME FAIL\r\n");
    return rc;
}
```

### Relevance to Your Project

This matches your existing `main.c` architecture. The key actionable item: if USB-UART shows no output, check the BSP UART selection (`psu_uart_1` for the KV260 micro-USB debug port). Also note `Xil_Out32`/`Xil_In32` perform single 32-bit AXI-Lite transactions — they do not use write-combining or caches, so you won't need cache-flush calls for BRAM accesses from the PS.

## XDC Timing Constraints

### Key Findings

- **`set_input_delay` / `set_output_delay`**: Values are in nanoseconds relative to a clock edge at the device boundary. Positive delay means data arrives *after* the clock edge (setup margin shrinks); negative means data arrives *before* the edge.
- **Clock groups for Zynq/Kria**: The PS-generated clocks (`clk_out1` from `clk_wiz_0`, which derives from `pl_clk0` of `zynq_ultra_ps_e`) are synchronous to each other but asynchronous to any free-running board oscillator. Use `set_clock_groups -asynchronous` to tell Vivado not to time cross-domain paths.
- **PL clock from PS**: `pl_clk0` on the K26 SOM defaults to 100 MHz but is configurable in the Zynq MPSoC IP settings; always define it with `create_clock` in the XDC rather than relying on the auto-derived clock from the block design — the auto-clock is fragile across regenerations.
- **False paths for debug-only signals**: JTAG / ILA probe signals are timing-irrelevant — add `set_false_path -to [get_pins -hierarchical -filter {NAME =~ */D}]` scoped to the ILA cell to avoid spurious timing violations.
- **Constraint ordering**: `create_clock` must appear before any `set_input_delay` / `set_output_delay` that references it; Vivado processes XDC files sequentially.

### Code Example

```tcl
# kv260_top.xdc — timing constraints for KV260 AXI-BRAM demo

# PS-generated PL clock (100 MHz default from pl_clk0)
create_clock -period 10.000 -name pl_clk0 [get_ports pl_clk0]

# Clock wizard output (if you add one) — async to any board oscillator
# create_clock -period 8.000 -name clk_125 [get_pins clk_wiz_0/clk_out1]

# Isolate PS and PL clock domains so Vivado won't try to time between them
set_clock_groups -asynchronous \
  -group [get_clocks pl_clk0] \
  -group [get_clocks -include_generated_clocks clk_125]

# Example I/O constraints for GPIO to carrier card (if used)
# set_input_delay  -clock pl_clk0 -max 2.0 [get_ports {gpio_i[*]}]
# set_output_delay -clock pl_clk0 -max 2.0 [get_ports {gpio_o[*]}]

# Suppress ILA probe timing (optional, reduces noise in timing reports)
# set_false_path -to [get_cells -hierarchical -filter {NAME =~ *ila*}]
```

### Relevance to Your Project

For a pure PS-to-BRAM project with no external I/O, the minimum XDC is just the `create_clock` for `pl_clk0`. However, adding the `set_clock_groups` line future-proofs the design if you later add a second clock domain (e.g., a 125 MHz Ethernet or video clock). The timing report (`report_timing_summary`) should show zero unconstrained endpoints after adding these constraints.

## Kria KV260 / K26 SoM Platform Specifics

### Key Findings

- **Boot modes**: K26 MODE[3:0] pins are pulled on the carrier card. KV260 Starter Kit ships with QSPI32 boot mode; JTAG mode is selected by holding the JTAG boot-mode switch. For bare-metal development, JTAG is fastest (no `boot.bin` needed); for deployment, QSPI requires `bootgen` to pack `fsbl.elf + pmufw.elf + bitstream + app.elf` into `boot.bin`.
- **QSPI boot image components**: `boot.bin` = FSBL + PMUFW + bitstream (.bit) + application ELF. The Vitis `Create Boot Image` wizard or `bootgen -bif` CLI handles this. Missing PMUFW causes a hang before FSBL completes.
- **MIO allocation on K26**: Many MIO pins are consumed by the SOM itself (eMMC, QSPI, I2C, UART). The free MIO pins available to the carrier card are documented in the K26 SOM datasheet (DS987). `psu_uart_1` (MIO 36/37) is routed to the KV260 USB-UART chip — this is your `xil_printf` port.
- **Power domains**: The K26 has separate power rails for PL (`VCCINT`), PS (`VCC_PSINTLP`/`VCC_PSINTFP`), and I/O banks. PL clock and reset must not be released until PS DDR initialization completes — the Zynq MPSoC IP handles this via `pl_resetn0` (active-low, released by FSBL after DDR init).
- **KV260 rev2**: Adds auto-focus support for IAS camera sensors; no functional change for AXI-BRAM bare-metal designs.

### Code Example

```bash
# Create boot.bin for KV260 bare-metal deployment (run in Vitis TCL console or shell)
# Assumes: fsbl.elf, pmufw.elf, kv260_top.bit, app.elf are in ./output/

cat > kv260_boot.bif << 'EOF'
the_ROM_image:
{
  [bootloader, destination_cpu=a53-0] output/fsbl.elf
  [pmufw_image]                       output/pmufw.elf
  [destination_device=pl]             output/kv260_top.bit
  [destination_cpu=a53-0, exception_level=el-3, trustzone] output/app.elf
}
EOF

bootgen -image kv260_boot.bif -arch zynqmp -w on -o output/BOOT.bin
# Flash to QSPI:
# program_flash -f output/BOOT.bin -offset 0 -flash_type qspi-x4-single \
#   -fsbl output/fsbl.elf -cable type xilinx_tcf
```

### Relevance to Your Project

Your current JTAG-based development flow (`Run As → Launch on Hardware`) is correct for iteration. When you're ready to demo the board standalone (power-on without a laptop), this `bootgen` flow is the path. The critical gotcha: the bitstream in `boot.bin` must match the hardware platform the `app.elf` was built against — rebuild both together when the block design changes.

## AMD/Xilinx Tool Updates (Vivado/Vitis 2025.x)

### Key Findings

- **Vitis 2025.1 released July 8, 2025** (UG1742): The Vitis Unified IDE fully replaces the legacy Eclipse-based Vitis IDE. All platform, domain, and application management now uses the `vitis` CLI or YAML-based component files, enabling Makefile/CI integration without a GUI.
- **`vitis -s script.py`**: Scripted Vitis flows use Python (not TCL) for platform creation, domain configuration, and application build. Migration guide in UG1742.
- **IP change log (AR 000037919)**: AMD publishes a single consolidated IP change log article covering all IP version changes in 2025.1 — check this for AXI BRAM Controller, AXI Interconnect, and Zynq MPSoC IP updates before upgrading.
- **Vivado 2025.1 known issues**: Tracked in UG973. Common category for Zynq/Kria projects: block design IP upgrade warnings after tool version change; resolve with `upgrade_ip` in TCL console.
- **Hardware Design Fast Iteration (XD101)**: New AMD tutorial covering `vitis_export_to_vivado` for rapid hardware iteration without full platform rebuild — relevant if you want to iterate on the PL fabric without regenerating the entire Vitis platform.
- **Vitis 2026.1 release notes** are already available on docs.amd.com, indicating the 2025.x stream is stable/mature.

### Code Example

```python
# Vitis 2025.1 scripted platform creation (vitis -s create_platform.py)
# Replaces the GUI-based "Create Platform Project" wizard

import vitis

client = vitis.create_client()
client.set_workspace(path="./vitis_ws")

# Create platform from Vivado-exported XSA
platform = client.create_platform_component(
    name      = "kv260_platform",
    hw_design = "./output/kv260_top.xsa",
    os        = "standalone",
    cpu       = "psu_cortexa53_0",
    no_boot_bsp = False

bsp.set_config(option="stdin",  value="psu_uart_1")
bsp.set_config(option="stdout", value="psu_uart_1")

platform.build()
client.close()
```

### Relevance to Your Project

If you migrate from Vitis 2024.x to 2025.1, the platform creation step changes from GUI to this Python script. The `psu_uart_1` BSP configuration shown here is the programmatic equivalent of the GUI setting — this is the fix if `xil_printf` produces no output on a fresh 2025.1 platform build.
