# FPGA Research Digest - 2026-10-27

## Executive Summary

- **AXI write completion trap**: A write is NOT done when the data-channel handshake completes — you must wait for the write-response channel (BREADY/BVALID). Skipping this in bare-metal C is the #1 source of silent BRAM corruption on the KV260.
- **BRAM read latency must match controller setting**: The Block Memory Generator's read-latency setting must be reflected in your AXI BRAM controller logic; a mismatch causes off-by-one read errors that are hard to distinguish from address bugs.
- **Kria KV260 boot is QSPI-only, console is UART1**: There are no boot-mode DIP switches; the K26 SOM always boots from QSPI flash. UART console routes to UART1, not UART0 — wire your Vitis `xil_printf` to the right peripheral.
- **Vivado 2025.1 adds RTL AXI Switch IP**: The new IP can be instantiated directly in RTL (unlike SmartConnect, which is IPI-only), useful for custom gating logic between PS and your BRAM fabric.
- **Non-project TCL flow requires manual checkpoints**: There is no auto-save between stages; always write `.dcp` files after synthesis, implementation, and routing, or a failed run means starting over.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- **Handshake rule**: A transfer completes only when both `xVALID` and `xREADY` are high in the *same* clock cycle. Never add extra conditions to this check — missing even one handshake corrupts burst data.
- **Write-response channel is mandatory**: On AXI-Lite, a write is complete only when the B-channel (`BVALID`/`BREADY`) handshake occurs, not when the W-channel data is accepted. Bare-metal code that ignores BVALID can overwrite a BRAM word before it has settled.
- **AXI-Lite has no burst signals**: There is no `WLAST`/`RLAST` in AXI-Lite; every transaction is a single transfer. If you see these signals in a custom slave, it is likely AXI4 full, not AXI-Lite.
- **BRAM latency mismatch**: Increasing the Block Memory Generator's read latency beyond the default (1 cycle) requires updating the AXI BRAM controller's pipeline logic; otherwise read data arrives one cycle early or late, and the handshake deasserts before data is valid.
- **AXI-Stream TVALID must not wait for TREADY**: A master asserting `TVALID` only after `TREADY` is high is a protocol violation and can deadlock combinational paths. `TREADY` may depend on `TVALID`, but not vice versa.
- **Register TREADY (skid buffer pattern)**: Combinational `TREADY` paths create timing-closure risk. Use a registered ready with a 2-entry skid buffer to absorb one stall cycle without losing throughput.
- **TLAST is required for DMA transfers**: Even though TLAST is optional in AXI-Stream, Xilinx AXI DMA and CDMA IPs require it to frame packet boundaries. Missing TLAST causes the DMA to hang waiting for packet end.

### Code Example

```c
/* Bare-metal AXI-Lite write + wait for B-channel (Vitis, xil_io.h) */
#include "xil_io.h"

#define BRAM0_BASE  0xA0000000U
#define BRAM2_BASE  0xA0010000U

/* Volatile pointer write -- forces load/store, no compiler reordering */
static inline void axi_write32(u32 base, u32 offset, u32 val)
{
    Xil_Out32(base + offset, val);
    /* Drain write buffer: read back forces AXI B-channel completion */
    (void)Xil_In32(base + offset);
}

int main(void)
{
    const u32 PATTERN = 0xDEADBEEFU;

    axi_write32(BRAM0_BASE, 0x00, PATTERN);
    axi_write32(BRAM2_BASE, 0x00, PATTERN);

    u32 rb0 = Xil_In32(BRAM0_BASE + 0x00);
    u32 rb2 = Xil_In32(BRAM2_BASE + 0x00);

    xil_printf("BRAM0: %s  BRAM2: %s\r\n",
               (rb0 == PATTERN) ? "PASS" : "FAIL",
               (rb2 == PATTERN) ? "PASS" : "FAIL");
    return 0;
}
```

### Relevance to Your Project

Your `main.c` writes patterns to BRAM0 (`0xA0000000`) and BRAM2 (`0xA0010000`) and reads them back. The read-after-write in `axi_write32` above is the minimal idiom to ensure the AXI write response has propagated before reading — without it, read-back can race against BRAM write settling and produce intermittent FAIL results even on correct hardware.

## Vivado Block Design / IP Integrator

### Key Findings

- **Address Editor "Assign All"**: In Vivado 2025.1 IPI, use the **Assign All** toolbar button (or right-click) to auto-assign base addresses to all slave segments. This is faster and less error-prone than typing `0xA0000000` and `0xA0010000` by hand when adding a second BRAM.
- **Address Width column reveals truncation**: The Paths view in the Address Editor shows the address width at each interface hop. If your master's address width is smaller than the slave's required width, the column highlights the truncation point — the most common cause of "address out of range" synthesis warnings.
- **Excluded vs. unassigned paths**: In SmartConnect designs, *excluding* a path blocks a master from reaching a slave; *leaving it unassigned* does not add decode logic but also does not block access. Use exclusion deliberately to harden security boundaries.
- **Show Inactive Apertures checkbox**: Enables listing all available apertures at each interface, not just the active ones — helpful when diagnosing why a slave is unreachable after an IP regeneration.
- **2025.1: New "Clocking and Reset" and "Interrupt and AXI-4 Lite" views**: These dedicated tabs in IPI give quick overviews of clock and reset connections and interrupt wiring, reducing the need to trace individual nets manually.
- **Run Connection Automation re-check**: After adding a second BRAM controller, always re-run **Run Connection Automation** and then re-validate the design (`validate_bd_design` in TCL) before re-generating the bitstream.

### Code Example

```tcl
# TCL: Assign all addresses, then lock them to prevent accidental shifts
open_bd_design [get_bd_files]
assign_bd_address
validate_bd_design

# Manually pin BRAM0 base address after auto-assign (if auto picked wrong base)
set_property offset 0xA0000000 [get_bd_addr_segs \
    {ps_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property range 64K [get_bd_addr_segs \
    {ps_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
```

### Relevance to Your Project

Your `create_bd.tcl` script programmatically assigns addresses. After any IP version upgrade in Vivado 2025.1, call `assign_bd_address` followed by explicit `set_property offset` to ensure BRAM0 stays at `0xA0000000` and BRAM2 at `0xA0010000` — auto-assign can reorder segments if IDs change.

## Vivado TCL Scripting

### Key Findings

- **Batch mode invocation**: `vivado -mode batch -source build.tcl` runs a complete build without opening the GUI. Exit codes propagate correctly, making it CI-friendly.
- **Non-project mode sequence**: `read_vhdl` → `read_xdc` → `synth_design` → `opt_design` → `place_design` → `route_design` → `write_bitstream`. There is no automatic state tracking — Vivado does not know which stage you completed last.
- **Manual checkpoints are essential**: Use `write_checkpoint` after each major stage. Without them, a failed route means re-running synthesis. A typical pattern:
  ```tcl
  synth_design -top kv260_top -part xck26-sfvc784-2LV-c
  write_checkpoint -force synth.dcp
  ```
- **Source file ordering matters**: Files are compiled in the order their `read_vhdl` / `read_verilog` commands appear. Place component package files before entity files to avoid "undefined identifier" elaboration errors.
- **`config_flows` for strategies**: Use `config_flows` with synthesis and implementation strategy presets rather than setting every directive individually — this also ensures the strategy is applied consistently across rebuilds.
- **`report_timing_summary` before write_bitstream**: Always call this before writing the bitstream; a failed timing run that still produces a bitstream will silently ship a design that won't meet timing in silicon.

### Code Example

```tcl
# Minimal non-project batch build for KV260 AXI-BRAM demo
set part "xck26-sfvc784-2LV-c"
set top  "kv260_top"

read_vhdl  -library work [glob src/*.vhd]
read_xdc              constraints/timing.xdc

synth_design -top $top -part $part -flatten_hierarchy rebuilt
write_checkpoint -force out/post_synth.dcp
report_timing_summary -file out/post_synth_timing.rpt

opt_design
place_design
route_design
write_checkpoint -force out/post_route.dcp

# Fail loudly if timing is not met
set wns [get_property SLACK [get_timing_paths -max_paths 1 -nworst 1]]
if {$wns < 0} {
    puts "ERROR: Timing not met (WNS = $wns ns)"
    exit 1
}

write_bitstream -force out/kv260_top.bit
write_hw_platform -fixed -force -file out/kv260.xsa
```

### Relevance to Your Project

Your `create_bd.tcl` builds the block design. Wrapping it in the non-project flow above gives you a CI-reproducible build that will fail the pipeline on timing violations rather than silently shipping a broken bitstream to the KV260.

## Vitis Bare-Metal / Standalone

### Key Findings

- **xil_printf is a lite printf**: The standalone BSP ships `xil_printf`, a size-optimized subset of `printf` with no floating-point support and limited format specifiers. Use `%d`, `%x`, `%s` safely; use `%f` only if you have linked a full libc and enabled FPU in BSP settings.
- **Linker script pitfall on JTAG boot**: The auto-generated `lscript.ld` sometimes maps all sections to the first memory region in the XSA, which can be a PL BAR0 instead of DDR. If the application crashes immediately on JTAG load, open `lscript.ld` and confirm all `.text`, `.data`, and `.bss` sections point to `psu_ddr_0_MEM_0` (or the equivalent DDR symbol for your platform).
- **BSP HAL helpers**: `Xil_Out32(addr, val)` and `Xil_In32(addr)` in `xil_io.h` are the recommended bare-metal memory-mapped I/O idiom — they compile to inline `STR`/`LDR` with barriers on Cortex-A53.
- **Interrupt controllers**: The GIC (ARM Generic Interrupt Controller) is exposed via `xscugic.h` in the standalone BSP. For a simple AXI-Lite design without PL interrupts, you do not need the GIC at all — poll BRAM read-back directly.
- **2025.1 open-source components**: Linux kernel updated to 6.12, and early-access Zephyr RTOS driver support was added for ZynqMP devices (relevant for future KV260 development).
- **Toolchain caveat**: Building the standalone BSP with a Linux cross-compiler (e.g., `aarch64-linux-gnu-gcc`) instead of the Vitis-bundled `aarch64-none-elf-gcc` can cause `__ctype_ptr__` link errors. Always use the embedded-profile toolchain.

### Code Example

```c
/* Vitis standalone: verify linker script maps stack to DDR, not PL */
/* In lscript.ld, check this section exists and has sufficient size:  */
/*   psu_ddr_0_MEM_0 (RWXAI) : ORIGIN = 0x0, LENGTH = 0x7FF00000      */

#include "xil_printf.h"
#include "xil_io.h"
#include "xparameters.h"   /* Auto-generated from BSP; includes base addrs */

/* XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR is defined in xparameters.h     */
/* as 0xA0000000 for BRAM0 when set correctly in Address Editor.        */

void check_bram(const char *name, u32 base)
{
    const u32 PAT = 0xCAFEBABEU;
    Xil_Out32(base, PAT);
    u32 rb = Xil_In32(base);
    xil_printf("%s @ 0x%08X: %s\r\n", name, base,
               (rb == PAT) ? "PASS" : "FAIL");
}

int main(void)
{
    xil_printf("KV260 AXI-BRAM test\r\n");
    check_bram("BRAM0", XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR);
    check_bram("BRAM2", XPAR_AXI_BRAM_CTRL_1_S_AXI_BASEADDR);
    return 0;
}
```

### Relevance to Your Project

Using `XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR` from `xparameters.h` is safer than hardcoding `0xA0000000` — if you ever shift the address in the Address Editor and regenerate the XSA, the constant updates automatically and you catch mismatches at compile time rather than at runtime.

## XDC Timing Constraints

### Key Findings

- **`set_input_delay` / `set_output_delay` model board-level delays**: These commands tell the Vivado timing engine how long signals spend outside the FPGA on PCB traces. They are required for accurate setup/hold analysis on external I/O; without them, Vivado reports unconstrained paths.
- **Always use `-max` and `-min` together**: AMD recommends applying both options for complete setup and hold coverage:
  ```
  set_input_delay -clock clk -max 3.0 [get_ports DIN]
  set_input_delay -clock clk -min 1.0 [get_ports DIN]
  ```
- **Virtual clock for uncorrelated I/O**: When an input/output path is not synchronous to your primary clock (e.g., a static configuration register), create a virtual clock and reference it to avoid false timing paths.
- **`set_max_delay` interaction**: If a port has both `set_output_delay` and `set_max_delay`, the output delay is subtracted from the max-delay budget. Setting both for the same path is a common source of unintentional over-constraining.
- **Kria PS-side clocks**: The PS-side clock (`clk_wiz_0/clk_out1` from a Clock Wizard fed by `pl_clk0`) should be constrained with `create_clock`, not `set_input_delay`. Vivado's block-design export creates this constraint automatically in the wrapper XDC.
- **UG949 methodology**: The UltraFast Design Methodology guide (UG949) is the canonical reference for Zynq/Kria timing methodology — check it before writing I/O constraints for carrier-card-specific signals.

### Code Example

```xdc
# KV260 AXI-BRAM demo: timing constraints skeleton
# PS PL clock at 100 MHz (generated by block design wrapper)
create_clock -period 10.000 -name pl_clk0 [get_ports pl_clk0]

# If exposing PL GPIO to carrier card, constrain those ports:
# (Adjust board-level delay values from carrier card schematic)
set_input_delay  -clock pl_clk0 -max 2.0 -min 0.5 [get_ports {gpio_in[*]}]
set_output_delay -clock pl_clk0 -max 2.0 -min 0.5 [get_ports {gpio_out[*]}]

# Cross-clock groups: PS clock domain vs PL clock domain
# (Required if your design has two clock domains crossing)
set_clock_groups -asynchronous \
    -group [get_clocks pl_clk0] \
    -group [get_clocks {clk_wiz_0_clk_out1}]

# False path on async reset synchronizer inputs
set_false_path -from [get_ports sys_rst_n]
```

### Relevance to Your Project

Your `kv260_top.vhd` wrapper connects the PS AXI master to PL BRAM controllers. The BRAM paths are fully internal (PS → AXI Interconnect → BRAM), so no I/O delay constraints are needed for them. However, if you add PL-exposed pins to the KV260 carrier card (e.g., LED status outputs), the XDC skeleton above is the correct starting point for those constraints.

## Kria KV260 / K26 SoM

### Key Findings

- **Boot is QSPI-only — no DIP switches**: Unlike Zynq eval boards, the K26 SOM has no physical boot-mode pins. Boot mode is hard-configured for QSPI flash. To boot a bare-metal app, you load it over JTAG or write it to the flash partition using `program_flash` from Vitis.
- **UART console is UART1, not UART0**: On Kria SOMs, the USB-UART bridge connects to PS UART1. If `xil_printf` output is missing, verify that the BSP is configured for UART1 (`STDIN_BASEADDRESS` and `STDOUT_BASEADDRESS` in BSP settings point to `psu_uart_1`).
- **MIO banks**: K26 SOM exposes MIO banks 501 and 502 for PS peripherals, and bank 504 is dedicated to on-module DDR4. PL I/O uses HPIO and HDIO banks; their voltage levels are set by carrier card supply rails, not the SOM.
- **Carrier card overlays**: The SOM boots a minimal device tree from QSPI; additional carrier-card peripherals are activated via device-tree overlays. In bare-metal (no OS), this does not apply — you configure peripherals directly via register writes or BSP drivers.
- **240-pin connectors**: The two SOM connectors expose PS MIO, PS-GTR transceivers, PL HPIO/HDIO, PL GTH transceivers, and power/sequencing signals. The `+5V` carrier input is the only required supply to bring up the SOM.
- **PL clock source**: `pl_clk0` is sourced from the PS clock generator. For a 100 MHz PL design on Kria, set `pl_clk0_freq_hz` to `100000000` in the Zynq UltraScale+ IP configuration panel.

### Code Example

```tcl
# Vivado block design: configure PS for KV260 bare-metal UART1 console
set_property -dict [list \
    CONFIG.PSU__UART1__PERIPHERAL__ENABLE {1} \
    CONFIG.PSU__UART1__PERIPHERAL__IO     {MIO 36 .. 37} \
    CONFIG.PSU__UART0__PERIPHERAL__ENABLE {0} \
    CONFIG.PSU__CRL_APB__PL0_REF_CTRL__FREQMHZ {100} \
    CONFIG.PSU__USE__M_AXI_GP0            {1} \
] [get_bd_cells zynq_ultra_ps_e_0]
```

### Relevance to Your Project

If you are seeing blank serial output from your KV260 AXI-BRAM demo, the most likely cause is that Vitis is targeting UART0 while the hardware routes the USB-UART to UART1. The TCL snippet above corrects the PS configuration in the block design; remember to regenerate the XSA and rebuild the BSP after changing UART assignment.

## AMD/Xilinx Tool Updates (Vivado/Vitis 2025.1)

### Key Findings

- **New RTL-based AXI Switch IP**: Vivado 2025.1 ships a new `axi_switch` IP that is "fully customizable" and can be instantiated directly in RTL code, unlike SmartConnect which is restricted to the IP Integrator canvas. This is useful for designs that need AXI arbitration outside of a block design.
- **IP Integrator new views**: Two new dedicated views appear in the IPI canvas:
  - **"Clocking and Reset"** — shows all clock and reset connections at a glance.
  - **"Interrupt and AXI-4 Lite"** — shows interrupt wiring and AXI-Lite slave connections, reducing the manual net-tracing needed to verify interrupt routing.
- **New Pblock Planner**: A new floorplanning assistant helps place logic into Pblocks for partial reconfiguration and DFX flows.
- **New device support**: Versal AI Edge Gen 2, Versal Prime Gen 2, and Spartan UltraScale+ are newly supported. New Versal-specific addressing GUI.
- **`report_dfx_summary` GUI support**: Dynamic function exchange (partial reconfiguration) gets a dedicated GUI report panel.
- **Embedded open-source components (2025.1)**: Linux kernel version bumped to 6.12. Early-access Zephyr RTOS drivers added for ZynqMP (relevant for KV260 future work beyond bare-metal).
- **Vitis 2025.2** (next release): AMD's "What's New" page highlights enhanced GEMV/FFT for AI Engine combining AIE and PL; AI Core vectorized sorting, correlation, and convolution — not relevant to KV260 bare-metal but worth tracking for future acceleration work.
