# FPGA Research Digest - 2026-10-07

## Executive Summary

- **AXI VALID/READY rule violation is the #1 bare-metal bug**: Xilinx's own Vivado-generated AXI-Lite slave templates have historically asserted VALID conditionally on READY — illegal per spec and a silent data-corruption hazard in the KV260 BRAM read-back path.
- **SmartConnect replaces AXI Interconnect** in Vivado 2025.1+: the old `axi_interconnect` soft-IP is superseded by `smartconnect`; update `create_bd.tcl` IP names accordingly or synthesis will warn and fall back.
- **`Xil_In32` / `Xil_Out32` are the safe BRAM accessors**: direct C pointer dereferences to AXI-Lite BRAM addresses work on Cortex-A53 but can be reordered by the compiler; always use the Xilinx memory-barrier macros or declare pointers `volatile`.
- **Vivado 2025.1 adds per-address-space grouping GUI** in IP Integrator — the new "Interrupt and AXI-4 Lite" dedicated view simplifies assigning BRAM0 at 0xA0000000 and BRAM2 at 0xA0010000 without manual address-editor edits.
- **KV260 bare-metal BOOT.BIN requires FSBL + bitstream + app ELF** packaged via `bootgen`; skipping the bitstream causes the PL to remain unconfigured and all AXI-Lite reads return 0xDEADBEEF or bus-error.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- AXI spec (IHI0022) mandates: once VALID is asserted it **must not** be deasserted until the handshake occurs (both VALID and READY high on the same clock edge). Violating this causes silent data loss — no synthesis error is generated.
- Xilinx Vivado-generated AXI-Lite slave templates (confirmed through at least 2018.3, partially present in later versions) incorrectly gate state machine transitions on `AWVALID & AWREADY` instead of just `AWVALID`, creating a livelock if the master deasserts READY.
- READY **may** be deasserted at any time as long as the interface remains legal; the transmitter side (VALID) has no such freedom.
- Insert the Xilinx AXI Protocol Checker IP (`axi_protocol_checker`) in simulation to catch handshake violations early — it fires an assertion the moment VALID illegally drops before the handshake completes.
- For AXI-Stream: `TVALID`/`TREADY` follow the same handshake rules; `TLAST` must be asserted on the last beat of a packet regardless of `TREADY` state.

### Code Example

```vhdl
-- Correct AXI-Lite write-address channel acceptance: do NOT gate on axi_awready
process(S_AXI_ACLK)
begin
  if rising_edge(S_AXI_ACLK) then
    if S_AXI_ARESETN = '0' then
      axi_awready <= '0';
    else
      -- Accept as soon as VALID appears; no dependency on our own READY
      if axi_awready = '0' and S_AXI_AWVALID = '1' then
        axi_awready <= '1';
      else
        axi_awready <= '0';
      end if;
    end if;
  end if;
end process;
```

### Relevance to Your Project

The kv260-axi-bram-demo's PS writes 32-bit patterns to two BRAMs over AXI-Lite. If the auto-generated AXI-Lite slave wrapper (used inside `axi_bram_ctrl`) still carries the VALID/READY coupling bug, intermittent read-back mismatches could appear only under certain Cortex-A53 burst timing. Audit any custom VHDL slave or regenerate the template under Vivado 2025.1 and enable the Protocol Checker in the block diagram during simulation.

## Vivado Block Design / IP Integrator

### Key Findings

- **Connection Automation** (`Run Connection Automation`) wires AXI masters to slaves automatically and assigns a default address range; always verify the address map in the Address Editor tab afterwards — auto-assigned ranges sometimes overlap for multi-slave designs.
- **Editing Addresses (UG994, 2025.1)**: slave interfaces expose `address_segment` objects; master interfaces expose `address_space` objects. A slave's memory map is a container of segments, each representing a decode window. Use `assign_bd_address` in TCL to set specific base addresses instead of relying on auto-assignment.
- Vivado 2025.1 adds a dedicated **"AXI-4 Lite" view** in IP Integrator that groups all AXI-Lite slave address segments by master — far easier to audit than the classic flat address editor table.
- When regenerating a block design in batch mode, always call `validate_bd_design` before `generate_target`; the validate step catches unconnected required ports that `generate_target` silently ignores.
- The **Designer Assistance** banner (green bar at top of block diagram) must be cleared — dismiss each suggestion or run the automation — before synthesis or a `[BD 41-2146]` critical warning fires.

### Code Example

```tcl
# Assign specific base addresses to match your bare-metal defines
# (equivalent to manual Address Editor entry)
set_property offset 0xA0000000 [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property range  64K        [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]

set_property offset 0xA0010000 [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_1_Mem0}]
set_property range  64K        [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_1_Mem0}]

# Validate before generating
validate_bd_design
generate_target all [get_files *.bd]
```

### Relevance to Your Project

`create_bd.tcl` must explicitly call `assign_bd_address` (or `set_property offset`) to pin BRAM0 at `0xA0000000` and BRAM2 at `0xA0010000`; without this, auto-assigned addresses can shift between Vivado versions and silently break `main.c`'s hardcoded defines.

## Vivado TCL Scripting

### Key Findings

- **Non-Project Mode** (`vivado -mode batch -source script.tcl`) creates an in-memory project only — no `.xpr` written to disk, no managed sources folder. You must explicitly call `read_vhdl`, `read_xdc`, `synth_design`, `opt_design`, `place_design`, `route_design`, and `write_bitstream`.
- **Project Mode** (`create_project`) writes managed sources and is the default for `create_bd.tcl` style flows; it is easier to re-open in the GUI but harder to version-control cleanly.
- Use `write_checkpoint` after each major step (post-synth, post-route) to enable incremental flows and checkpoint-based debugging — critical for CI pipelines.
- `config_flows -synth_strategy Flow_PerfOptimized_high` applies a preset strategy without specifying individual directives — simpler in automation scripts.
- `export_ip_user_files -of_objects [get_files *.bd]` must be called before `launch_runs` in project mode or the BD generates incomplete output products.
- Always source scripts with absolute paths: `source [file dirname [info script]]/helpers.tcl` rather than relative paths that break when Vivado's CWD differs.

### Code Example

```tcl
#!/usr/bin/env tclsh
# Non-project mode minimal build script for kv260-axi-bram-demo
set PART "xck26-sfvc784-2LV-c"
set TOP  "kv260_top"
set OUTDIR "./output"

file mkdir $OUTDIR

# Read sources
read_vhdl  ../vhdl/kv260_top.vhd
read_xdc   ../xdc/kv260_top.xdc

# Synthesize
synth_design -top $TOP -part $PART -flatten_hierarchy rebuilt
write_checkpoint -force $OUTDIR/post_synth.dcp

# Implement
opt_design
place_design
phys_opt_design
route_design
write_checkpoint -force $OUTDIR/post_route.dcp

# Reports
report_timing_summary -file $OUTDIR/timing.rpt
report_utilization    -file $OUTDIR/util.rpt

# Bitstream
write_bitstream -force $OUTDIR/$TOP.bit
```

### Relevance to Your Project

`create_bd.tcl` in the kv260-axi-bram-demo is a Project Mode script. Consider extracting a thin non-project wrapper for CI so the bitstream can be regenerated without a GUI licence seat, by using `open_project` + `launch_runs impl_1 -to_step write_bitstream -wait` when project mode artifacts are already on disk.

## Vitis Bare-Metal / Standalone

### Key Findings

- **Standalone BSP** for Cortex-A53 (APU) lives under `<Vitis>/data/embedded/lib/bsp/standalone`; key files: `xparameters.h` (peripheral base addresses), `xil_io.h` (`Xil_In32`/`Xil_Out32`), `xil_printf.h`.
- `xil_printf` is a lightweight `printf` that writes to the UART configured as `stdout` in BSP settings; it does **not** support `%f` or `%e` floating-point by default — link `printf` from libc if floats are needed.
- **stdin/stdout UART selection**: in the Vitis BSP settings (`platform.spr`) set `stdin` and `stdout` to `psu_uart_1` for the KV260 USB-UART (UART1 is routed to USB-to-serial on the carrier card; UART0 is on MIO and not brought out on KV260).
- `Xil_DCacheFlushRange(addr, len)` must be called before reading BRAM if D-cache is enabled — AXI-Lite slaves are typically marked non-cacheable in the MPU table, but verify `xil_mpu.c` entries match BRAM addresses.
- The linker script (`lscript.ld`) default OCM section is only 256 KB; for larger data arrays, map them to DDR by adjusting the `ps_ddr_0` region in the linker script.

### Code Example

```c
#include "xil_io.h"
#include "xil_printf.h"

#define BRAM0_BASE  0xA0000000U
#define BRAM2_BASE  0xA0010000U
#define TEST_WORDS  16

int bram_test(u32 base, const char *name) {
    u32 pattern, readback;
    for (u32 i = 0; i < TEST_WORDS; i++) {
        pattern = 0xDEAD0000U | i;
        Xil_Out32(base + (i << 2), pattern);   /* 32-bit AXI-Lite write */
    }
    /* Barrier: ensure all writes retire before reads start */
    dsb();
    for (u32 i = 0; i < TEST_WORDS; i++) {
        readback = Xil_In32(base + (i << 2));
        pattern  = 0xDEAD0000U | i;
        if (readback != pattern) {
            xil_printf("%s FAIL @ offset 0x%04x: wrote 0x%08x read 0x%08x\r\n",
                       name, i<<2, pattern, readback);
            return -1;
        }
    }
    xil_printf("%s PASS\r\n", name);
    return 0;
}

int main(void) {
    xil_printf("KV260 AXI-BRAM Demo\r\n");
    bram_test(BRAM0_BASE, "BRAM0");
    bram_test(BRAM2_BASE, "BRAM2");
    return 0;
}
```

### Relevance to Your Project

The `main.c` pattern-write/read-back loop maps directly to this structure. The critical addition is the `dsb()` (Data Synchronization Barrier) between the write loop and the read loop — without it the Cortex-A53's out-of-order execution pipeline can issue reads before all writes have propagated through the AXI-Lite interconnect, producing spurious FAILs on the first few words.

## XDC Timing Constraints

### Key Findings

- **Recommended constraint ordering (UG903 2025.2)**: (1) primary clocks → (2) generated clocks → (3) virtual clocks → (4) clock groups → (5) input/output delays → (6) timing exceptions. Violations of this order cause Vivado to silently ignore some constraints at implementation.
- `set_input_delay` specifies the external system-level path delay on a primary input relative to a clock edge — the value is the setup time budget consumed *outside* the FPGA.
- `set_output_delay` specifies the external delay on a primary output; negative values indicate the clock arrives at the destination before the data and are legal.
- For **AXI-Lite designs with Zynq/Kria**, PL logic driven by the PS's `FCLK_CLK0` does not need external `set_input_delay`/`set_output_delay` on PS↔PL paths — the Zynq PS IP already constrains those paths internally. Only constrain external I/O ports (LEDs, GPIOs, etc.).
- `set_clock_groups -asynchronous -group [get_clocks clk_pl_0] -group [get_clocks clk_pl_1]` cuts timing between independent PL clocks; use `-physically_exclusive` only when clocks are truly mutually exclusive (MUXed sources).
- The **`create_clock`** constraint for `FCLK_CLK0` is auto-generated by the Zynq PS IP; do not re-declare it in your XDC or you'll get a duplicate-clock critical warning.

### Code Example

```tcl
# kv260_top.xdc - minimal constraints for KV260 AXI-BRAM demo

# FCLK_CLK0 is auto-constrained by PS IP — do NOT re-declare it.
# Only add constraints for external ports here.

# Example: GPIO output to status LED (10 MHz system clock period = 100 ns)
# Assume 5 ns board trace + receiving FF setup of 2 ns
set_output_delay -clock [get_clocks clk_pl_0] -max  7.0 [get_ports {led[*]}]
set_output_delay -clock [get_clocks clk_pl_0] -min -2.0 [get_ports {led[*]}]

# False path on async reset (active-low from PS)
set_false_path -from [get_ports sys_resetn]

# Cut timing between PL clocks if using multiple FCLK outputs
# (only needed if a second clock domain exists in the design)
# set_clock_groups -asynchronous \
#   -group [get_clocks clk_pl_0] \
#   -group [get_clocks clk_pl_1]
```

### Relevance to Your Project

The kv260-axi-bram-demo only uses `FCLK_CLK0` driving the AXI-Lite BRAM paths — all timing is internal PS-to-PL. The XDC file need only constrain external I/O (UART TX/RX are through PS MIO and need no PL XDC entries). Over-constraining by re-declaring `FCLK_CLK0` is the most common mistake and causes misleading timing failures in post-implementation reports.

## Kria KV260 / K26 SoM

### Key Findings

- **K26 SoM power**: all SoC power rails are derived from a single +5V input on the carrier card; PL I/O supply voltages are defined by the carrier card power rails — the KV260 carrier exposes 1.8 V VADJ for PL HPIO banks.
- **Boot modes**: SD-boot is the default for KV260 out-of-box; QSPI-boot loads a limited peripheral set (only SOM-defined MIO peripherals) and then applies a carrier-card DT overlay. For bare-metal development, SD-boot is preferred because `BOOT.BIN` on the FAT partition is simplest to update.
- **FSBL → bitstream → app ELF sequence**: The First Stage Boot Loader (FSBL) initialises the DDR, configures the PL with the bitstream, then hands off to the bare-metal ELF. Without the bitstream in `BOOT.BIN`, the PL remains in "Blanked" state and all AXI-Lite transactions to `0xA000xxxx` will return bus errors.
- **MIO pinout**: USB-UART uses UART1 (MIO 36/37 on K26). UART0 (MIO 18/19) is available but is not brought to a USB connector on the KV260 carrier — do not set it as stdout unless a separate 3.3 V UART adapter is attached to the PMOD header.
- **EMMC vs. QSPI versions**: the `sm-k26` has eMMC storage; the `smk-k26` (Starter Kit variant) has only QSPI — SD card is the only viable development boot target on `smk-k26`.
- **PL I/O banks**: PL HPIO bank 65 (1.8 V) and bank 66 are available via the KV260 carrier Raspberry Pi header and Pmod headers. Ensure XDC `set_property IOSTANDARD LVCMOS18` for any PL-facing GPIOs.

### Code Example

```tcl
# bootgen.bif - BOOT.BIN recipe for KV260 bare-metal
# Run: bootgen -image kv260_bram.bif -arch zynqmp -o BOOT.BIN -w on

the_ROM_image:
{
  [fsbl_config] a53_x64
  [bootloader, destination_cpu=a53-0] fsbl/fsbl.elf

  [destination_device=pl] kv260_top.bit         /* PL bitstream - MUST be present */

  [destination_cpu=a53-0, exception_level=el-3,
   trustzone] pmufw/pmufw.elf                   /* PMU firmware */

  [destination_cpu=a53-0, exception_level=el-2] bl31.elf   /* ATF (optional for bare-metal) */

  [destination_cpu=a53-0, exception_level=el-1] kv260_bram_app.elf
}
```

### Relevance to Your Project

A complete `BOOT.BIN` for the kv260-axi-bram-demo must include the FSBL ELF, the bitstream with the BRAM block design, and the application ELF. The most common failure mode — "program runs, all reads return 0" — is caused by packaging the `BOOT.BIN` without the `.bit` file, leaving the PL unconfigured.

## AMD/Xilinx Tool Updates (Vivado/Vitis 2025.x)

### Key Findings

- **Vivado 2025.1 released** (June 2025): key new items relevant to KV260 development:
  - **New AXI Switch IP**: bridges different AXI interface types and widths — useful for mixing AXI4-Full and AXI-Lite in a single block diagram without hand-writing an adapter.
  - **SmartConnect replaces AXI Interconnect**: `axi_interconnect` is now fully superseded; update TCL scripts to instantiate `smartconnect` instead.
  - **New IP Integrator views**: dedicated "Clocking and Reset" and "Interrupt and AXI-4 Lite" sub-views; new Pblock planner; new addressing GUI with automatic grouping of equivalent address spaces.
  - **Selective device installer**: dramatically reduces download size for Versal devices; no impact on Zynq UltraScale+ installs but useful if both device families are in use.
- **Vivado 2025.2** (available at time of digest): further refines the addressing GUI and adds more SmartConnect diagnostics in the IP Integrator reports.
- **Known community issues (Vivado 2025.1)**:
  - DocNav SSL handshake errors on some Linux distros — workaround: use browser to access docs.amd.com directly.
  - Vitis IDE startup failures on Ubuntu 22.04 with certain JDK versions — use the bundled JDK (`<Vitis>/tps/lnx64/jre`).
  - `axi_bram_ctrl` v4.0 IP requires explicit `upgrade_ip` call in TCL if project was originally created with Vivado < 2024.1.

### Code Example

```tcl
# Upgrading IPs in an existing project after Vivado version change
# Run in Vivado Tcl Console or batch mode

open_project ./kv260/kv260.xpr

# List IPs that need upgrade
set stale [get_ips -filter {UPGRADE_VERSIONS != ""}]
foreach ip $stale {
  puts "Upgrading: [get_property NAME $ip]"
}

# Upgrade all stale IPs in one call
upgrade_ip $stale

# Regenerate output products
generate_target all [get_ips]

# Re-validate the block design after IP upgrades
open_bd_design [get_files *.bd]
validate_bd_design
save_bd_design

puts "IP upgrade complete."
```

### Relevance to Your Project

If the kv260-axi-bram-demo was originally created with Vivado 2024.x, opening it in 2025.1 will flag `axi_bram_ctrl`, `zynq_ultra_ps_e`, and `smartconnect` as requiring upgrades. Running the above script before `generate_target` prevents the "IP is locked" errors that stall bitstream generation in CI.
