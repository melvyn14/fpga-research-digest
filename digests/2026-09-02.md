# FPGA Research Digest - 2026-09-02

## Executive Summary

- **AXI-Lite deadlock risk**: Never wait for READY before asserting VALID — it violates the AXI spec and can cause the bus to hang indefinitely; the KV260 project's bare-metal write loop should assert VALID unconditionally and wait for READY after.
- **BRAM ECC control port**: The AXI BRAM Controller v4.1 exposes a separate AXI4-Lite control interface (`S_AXI_CTRL`) for ECC status/correction — if you ever add ECC to BRAM0/BRAM2, you need a second address-mapped slave entry in the address editor (e.g., 0xA0001000 / 0xA0011000).
- **Vivado TCL re-creation**: `write_bd_tcl` exports a self-contained script to recreate the entire block design; running it under non-project mode (`vivado -mode batch -source create_bd.tcl`) is the cleanest CI-friendly flow for the kv260-axi-bram-demo repo.
- **KV260 boots QSPI32 by default** — bare-metal apps loaded over JTAG via `xsdb`/`xsct` do NOT persist across power cycles unless you reflash QSPI; use SD boot mode for iterative bare-metal development to preserve the factory image.
- **Vivado 2025.2 licensing change incoming**: Starting with the 2026.1 release AMD is moving Vivado to a new tiered licensing model; pin your CI toolchain to 2025.1 or 2025.2 now to avoid unexpected breakage.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- **VALID must never be withheld waiting for READY**: the AXI spec states the initiator must assert VALID as soon as data is available; stalling VALID until READY is seen risks deadlock when both master and slave wait on each other.
- **W and AW channels are independent**: the slave must accept whichever arrives first; responding on BVALID before both `aw_hs_done` and `w_hs_done` flags are set is a common RTL bug in custom AXI-Lite slaves.
- **WSTRB must be handled**: bare-metal C writes 32-bit words, so all four byte-enable strobes (WSTRB = 0xF) are set by the Zynq AXI interconnect automatically — but custom IP must honour individual byte lanes or data corruption results.
- **Drive RREADY/BREADY during reset**: during active-low reset, slaves should hold RVALID and BVALID low to avoid dropping a transfer if the master releases reset before the slave does.
- **AXI Protocol Checker (PG101)**: insert `axi_protocol_checker` in simulation to catch spec violations — it monitors all five channels and flags illegal transitions.

### Code Example

```c
/* Bare-metal AXI-Lite write + readback via direct memory access (main.c style) */
#include <stdint.h>
#include "xil_printf.h"

#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL

static inline void bram_write(uint32_t base, uint32_t offset, uint32_t val) {
    volatile uint32_t *p = (volatile uint32_t *)(base + offset);
    *p = val;
    /* AXI-Lite: Cortex-A53 issues AW+W; interconnect asserts BVALID when slave responds */
    __asm__ volatile("dsb sy" ::: "memory"); /* data sync barrier before readback */
}

static inline uint32_t bram_read(uint32_t base, uint32_t offset) {
    volatile uint32_t *p = (volatile uint32_t *)(base + offset);
    uint32_t val = *p;
    __asm__ volatile("dsb sy" ::: "memory");
    return val;
}

void bram_test(void) {
    const uint32_t pattern = 0xDEADBEEF;
    bram_write(BRAM0_BASE, 0x00, pattern);
    bram_write(BRAM2_BASE, 0x00, ~pattern);

    uint32_t r0 = bram_read(BRAM0_BASE, 0x00);
    uint32_t r2 = bram_read(BRAM2_BASE, 0x00);

    xil_printf("BRAM0: %s (0x%08X)\r\n", r0 == pattern  ? "PASS" : "FAIL", r0);
    xil_printf("BRAM2: %s (0x%08X)\r\n", r2 == ~pattern ? "PASS" : "FAIL", r2);
}
```

### Relevance to Your Project

Your `main.c` writes patterns to BRAM0 (`0xA0000000`) and BRAM2 (`0xA0010000`) and reads them back over AXI-Lite. The `dsb sy` barrier between write and readback is critical on Cortex-A53 — without it the store may still be in the write buffer when the load executes, producing a stale value that gives a false FAIL. The WSTRB note matters if you ever add partial-word writes (e.g., byte-granular logging into BRAM).

## Vivado Block Design / IP Integrator

### Key Findings

- **Connection Automation**: after adding the Zynq PS and BRAM Controller IPs, `Run Connection Automation` wires M_AXI_HPM0_LPD → S_AXI and generates the AXI SmartConnect/Interconnect and resets automatically.
- **Address Editor is mandatory**: after IP connections, assign BRAM0 at 0xA0000000 and BRAM2 at 0xA0010000 in the Address Editor; `assign_bd_address` in TCL handles this programmatically.
- **Regenerate Layout after adding IPs**: `regenerate_bd_layout` redraws the canvas without changing connections — run it after bulk TCL IP instantiation to keep the diagram legible.
- **Block Design Containers (BDC)**: Vivado supports hierarchical block designs via BDC; useful for partitioning the PS wrapper from custom PL logic to speed up incremental synthesis.
- **Export to TCL then version-control**: `write_bd_tcl -force output.tcl` after each design milestone; the generated script is the ground truth for reproducible builds.

### Code Example

```tcl
# Programmatically assign AXI BRAM addresses in block design (add to create_bd.tcl)
proc assign_bram_addresses {} {
    # BRAM0 at 0xA000_0000, 64KB range
    set bram0_seg [get_bd_addr_segs {axi_bram_ctrl_0/S_AXI/Mem0}]
    set_property offset 0xA0000000 $bram0_seg
    set_property range  64K        $bram0_seg

    # BRAM2 at 0xA001_0000, 64KB range
    set bram2_seg [get_bd_addr_segs {axi_bram_ctrl_1/S_AXI/Mem0}]
    set_property offset 0xA0010000 $bram2_seg
    set_property range  64K        $bram2_seg

    assign_bd_address
    validate_bd_design
    xil_printf "Address assignment complete\n"
}
```

### Relevance to Your Project

Your `create_bd.tcl` already builds the block design programmatically. Ensuring `assign_bd_address` is called after all IPs are connected prevents the "unmapped slave" DRC error that blocks bitstream generation. Double-check the `Mem0` segment names match your actual IP instance names if you see offset mismatches during implementation.

## Vivado TCL Scripting

### Key Findings

- **Non-project mode is CI-friendly**: `vivado -mode batch -source build.tcl` opens Vivado, runs the script, and exits — no `.xpr` required, no GUI, no manual intervention.
- **Project mode vs. non-project mode**: in non-project mode you are responsible for all file management; re-running synthesis after source changes requires re-calling `synth_design` explicitly.
- **Export block design to TCL**: in project mode, `File → Export → Export Block Design` generates a portable `.tcl`; edit out project-specific paths to make it portable.
- **Batch synthesis pattern**: `read_vhdl`, `read_xdc`, `synth_design`, `opt_design`, `place_design`, `route_design`, `write_bitstream` is the canonical non-project pipeline.
- **`get_bd_cells` + `set_property`**: use these to modify IP parameters in script rather than the GUI — avoids stale `.xci` files in version control.

### Code Example

```tcl
# Minimal non-project batch build script (non_project_build.tcl)
set outputDir ./output
file mkdir $outputDir

# Read sources
read_vhdl  [glob ./vhdl/*.vhd]
read_xdc   [glob ./xdc/*.xdc]

# Source the block design recreation script
source ./tcl/create_bd.tcl
create_root_design ""          ;# call the proc that create_bd.tcl defines

# Generate block design output products
generate_target all [get_files *.bd]
make_wrapper -files [get_files *.bd] -top
add_files -norecurse [glob $outputDir/hdl/*.v]

# Implement
synth_design  -top kv260_top -part xck26-sfvc784-2LV-c
opt_design
place_design
phys_opt_design
route_design
write_bitstream -force $outputDir/kv260_top.bit

# Export hardware (for Vitis XSA)
write_hw_platform -fixed -include_bit -force $outputDir/kv260_top.xsa
```

### Relevance to Your Project

Your repo has `create_bd.tcl` — wrapping it with this non-project driver script means `make bitstream` can run in CI without a Vivado GUI license seat. The `write_hw_platform` call at the end produces the `.xsa` that Vitis needs to generate the BSP, closing the full build loop in one script.

## Vitis Bare-Metal / Standalone

### Key Findings

- **BSP auto-generated from XSA**: Vitis reads the `.xsa` exported by Vivado and generates `xparameters.h` containing all peripheral base addresses — use `XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR` rather than hard-coded hex in production code.
- **`xil_printf` vs `printf`**: `xil_printf` is lightweight (no floating point, no malloc) and outputs over the PS UART; sufficient for PASS/FAIL reporting; link `printf` only if you need `%f` formatting (it adds ~40KB to the image).
- **UART0 mapped to MIO10/11 on K26**: the KV260 carrier routes PS UART0 to the USB-UART bridge (Silicon Labs CP2105); BSP UART base is `0xFF000000`; baud rate defaults to 115200 in standalone domain.
- **Vitis Unified IDE (2022.1+) vs. Classic**: the 2025.x toolchain uses Vitis Unified IDE by default; the `system.spr` workspace model replaces the old `.hdf` + application project flow.
- **Bare-metal template for KV260**: a community template (`Vitis_KV260_KR260_Template`) allows direct FPGA programming from a host PC over USB-JTAG without booting Linux or writing an FSBL — ideal for iterative BRAM testing.

### Code Example

```c
/* BSP-portable BRAM addressing using xparameters.h */
#include "xparameters.h"
#include "xil_io.h"
#include "xil_printf.h"

/* These symbols come from the Vitis-generated BSP */
#define BRAM0_BASE  XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR
#define BRAM2_BASE  XPAR_AXI_BRAM_CTRL_1_S_AXI_BASEADDR

int main(void) {
    xil_printf("KV260 AXI-BRAM Demo\r\n");

    /* Walking-ones pattern across both BRAMs */
    int errors = 0;
    for (int i = 0; i < 16; i++) {
        uint32_t pattern = 1U << i;
        Xil_Out32(BRAM0_BASE + i * 4, pattern);
        Xil_Out32(BRAM2_BASE + i * 4, ~pattern);

        uint32_t r0 = Xil_In32(BRAM0_BASE + i * 4);
        uint32_t r2 = Xil_In32(BRAM2_BASE + i * 4);

        if (r0 != pattern || r2 != ~pattern) {
            xil_printf("FAIL at word %d: BRAM0=0x%08X BRAM2=0x%08X\r\n", i, r0, r2);
            errors++;
        }
    }
    xil_printf(errors == 0 ? "ALL PASS\r\n" : "ERRORS DETECTED\r\n");
    return 0;
}
```

### Relevance to Your Project

Using `Xil_Out32`/`Xil_In32` (from `xil_io.h`) instead of raw pointer casts gives you proper memory barriers and is the AMD-recommended pattern for bare-metal peripheral access. The walking-ones pattern exercises all 16 data bits and is a stronger functional test than the single `0xDEADBEEF` write.

## XDC Timing Constraints

### Key Findings

- **`set_input_delay`/`set_output_delay` model board-level delays**: these commands specify the round-trip delay from the FPGA pin to external logic (PCB trace + component delay) so Vivado can compute actual setup/hold margins.
- **K26 SoM XDC includes package + PCB delays**: AMD provides signal delay XDC files that account for K26 SoM PCB trace lengths for MIO, HDIO, and HPIO interfaces — include them before your custom XDC for accurate timing.
- **AXI-Lite signals are internal (no `set_input_delay` needed)**: since both PS and PL are on the same die, the AXI connections between Zynq HP/HPM ports and BRAM are die-internal paths; Vivado knows their delays without user constraints.
- **`create_clock` on PL clock output from PS**: the PS generates `pl_clk0`; constrain it with `create_clock -period 10.000 [get_pins PSS_INST/PSS_ALTO/PSS_ALTO_CORE/pl_clk[0]]` to establish the timing reference.
- **False paths for CDC**: if you ever add clock-domain-crossing logic between PL clock domains, use `set_false_path -from [get_clocks clk_a] -to [get_clocks clk_b]` to suppress bogus timing violations.

### Code Example

```tcl
# kv260_timing.xdc — timing constraints for KV260 AXI-BRAM demo

# PL clock from PS (100 MHz default on HPM0)
# PS drives pl_clk0; constrain the net at the PS output pin
create_clock -period 10.000 -name pl_clk0 \
    [get_nets -hierarchical -filter {NAME =~ */pl_clk0}]

# External GPIO output on PMOD (example: if routing PL output to carrier GPIO)
# Assume 2 ns board trace delay, 2 ns setup margin needed by receiver
# set_output_delay -clock pl_clk0 -max  2.000 [get_ports {pmod_gpio[*]}]
# set_output_delay -clock pl_clk0 -min -1.000 [get_ports {pmod_gpio[*]}]

# If adding an external trigger input from PMOD header:
# set_input_delay  -clock pl_clk0 -max  3.000 [get_ports {ext_trigger}]
# set_input_delay  -clock pl_clk0 -min  1.000 [get_ports {ext_trigger}]

# Internal AXI-Lite paths (PS-to-PL BRAM) are inferred — no user constraints needed.
# Suppress timing check on async reset synchronizer if present:
# set_false_path -from [get_pins PSS_INST/*/por_b] -to [get_pins */PRE]
```

### Relevance to Your Project

For the current demo, the only PL clock is `pl_clk0` driven by the PS. You do not need `set_input_delay`/`set_output_delay` because there are no off-chip I/O paths in the AXI-BRAM design. Adding the `create_clock` constraint is still recommended to suppress the "No clocks found" critical warning that appears if no clock constraint is applied, and ensures Vivado optimises the AXI-Lite path timing correctly.

## Kria KV260 / K26 SoM

### Key Findings

- **Default boot mode is QSPI32**: the K26 SoM ships pre-programmed with QSPI32 boot mode; bare-metal apps loaded via JTAG (`xsdb target 2; dow app.elf`) run in SRAM/DDR but are lost after power cycle — switch to SD boot for iterative development.
- **MIO10/11 = UART0 (USB-UART)**: the KV260 carrier card routes PS MIO10 (TX) and MIO11 (RX) to the Silicon Labs CP2105 USB-UART bridge; this is the `xil_printf` UART — it appears as `/dev/ttyUSB1` on Linux hosts.
- **HPM0_LPD (128-bit AXI, 300 MHz)**: the Kria's PS exposes `M_AXI_HPM0_LPD` — this is the port connected to your AXI Interconnect in the block design; it supports up to 300 MHz but the BRAM controller IP typically runs at 100 MHz so clock the interconnect at `pl_clk0` (100 MHz).
- **No jumpers for boot mode on KV260**: unlike older Zynq-7000 boards, boot mode on KV260 is not set by jumpers; it is fixed by SOM hardware resistors; use `xsdb` with JTAG to download without changing boot mode.
- **EMIO for PL-controlled GPIOs**: if the application later needs to toggle carrier-card GPIOs from PL logic, route through EMIO (Extended MIO) by enabling EMIO in the PS IP and connecting the `emio_gpio` port in the block design.

### Code Example

```tcl
# XSDB script to program KV260 over JTAG and run bare-metal ELF (run_jtag.tcl)
# Usage: xsdb run_jtag.tcl

connect
# Target 1 = APU cluster, Target 2 = Cortex-A53 #0
targets -set -nocase -filter {name =~ "*A53*#0"}

# Load and initialise PS (clock PLL, DDR, etc.) via FSBL or ps_init
# Using pre-built ps_init from Vitis BSP:
source [lindex $argv 0]/ps7_init.tcl
ps7_post_config

# Download application ELF
dow  kv260_bram_demo.elf

# Optional: set breakpoint at main and run
# bpadd -addr &main
con
```

### Relevance to Your Project

The JTAG-download flow above is the fastest inner-loop cycle for the kv260-axi-bram-demo: edit `main.c` → rebuild in Vitis → `xsdb run_jtag.tcl` → observe PASS/FAIL on UART, all without touching the QSPI image. On success, program the SD card once for stand-alone demos.

## AMD/Xilinx Tool Updates

### Key Findings

- **Vivado 2025.2 released**: adds new Versal AI Edge Series Gen 2 and Versal Prime Series Gen 2 device support; also introduces a new `STRATEGY` parameter on AXI Switch and AXI SmartConnect IPs for ultra-low-area mode — useful for resource-constrained designs on the K26.
- **Vitis 2025.2**: AI Engine API gains new block floating-point types (MX6, MX4) and enhanced cfloat/cbfloat16 support; also adds C++ functional simulation and hardware-in-the-loop testing with MATLAB/Python testbenches (early access).
- **Vivado 2025.1 IP change log (AR 000037919)**: Sync LVDS mode support added in Advanced IO Wizard IP for Versal; check this answer record before upgrading from 2025.1 to 2025.2 for any IP version deltas.
- **Licensing change in 2026.1**: AMD is moving to a tiered licensing model starting with the 2026.1 release — pin your project toolchain to 2025.x now if you rely on the free WebPACK/Standard license tier.
- **Vitis 2026.x known issues (AR 000040220)**: active AR tracking 2026.x Vitis issues — worth bookmarking to check before any tool upgrade.
