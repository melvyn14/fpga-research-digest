## Executive Summary
- **Vivado/Vitis 2026.1 introduces a tiered licensing model that drops native Linux support from the free tier.** The free "Basic" tier is Windows-only; Linux users now need the paid "Core" tier (~$1,200-1,800/yr). Pre-2026.1 releases (including your current 2025.1) remain usable indefinitely under the existing free Standard/ML license, so there is no urgency to upgrade — but plan toolchain budget/OS choices before any future jump to 2026.1+.
- **AW/W channel ordering is the #1 mistake in hand-written AXI-Lite slaves**: a slave must NOT assume `AWVALID`+`AWREADY` completes before `WVALID` arrives — both can (and often do) arrive in the same cycle, and Xilinx's own example templates have had this bug. The AXI BRAM Controller handles this correctly, so `Xil_Out32()`/`Xil_In32()` calls from `main.c` to BRAM0/BRAM2 are safe; this only matters if you ever wrap the BRAM controllers with a custom AXI-Lite register block (e.g., for status/control registers).
- **`axi_bram_ctrl` + `blk_mem_gen` pairing requires matching `DATA_WIDTH`/`READ_WRITE_MODE`**, and connection automation auto-generates the BMG instance — if `create_bd.tcl` manually instantiates both IPs, a mismatch produces a `validate_bd_design` error that's easy to miss in batch-mode logs.
- **Vitis 2025.x Unified IDE removed `.mss`/`.mld`/`.bsp` files** in favor of `vitis-comp.json` + YAML platform-component config — if `create_bd.tcl`'s companion software flow (or any setup docs) still reference editing `system.mss`, that workflow is Vitis Classic-only and won't work in 2025.1's default Unified IDE.
- **KV260 boot-mode pins (`MODE[3:0]`) are irrelevant for JTAG-based bare-metal debug** — the carrier card ships strapped to QSPI32 for the certified Linux image, but downloading the AXI-BRAM-demo ELF via XSDB/JTAG bypasses boot mode entirely. Only relevant if the demo is ever flashed as a persistent boot image.

## AXI Protocol / AXI-Lite / AXI-Stream
### Key Findings
- The AXI4/AXI4-Lite VALID/READY handshake: a transfer occurs only when both VALID and READY are `1` on the same clock edge; once VALID is asserted it **cannot be withdrawn** until the handshake completes, while READY may be deasserted indefinitely by either side.
- **Most common custom-slave bug**: assuming the master must complete the AW handshake before presenting W-channel data. The AXI spec explicitly allows (and high-performance masters often do) AW and W to arrive together or W-before-AW-completion — a slave gated on "wait for AWREADY before sampling WDATA" can deadlock or drop data.
- `BVALID` may only assert **after** the `WVALID && WREADY` (and `WLAST` for AXI4) handshake completes — for AXI4-Lite that's just "data accepted, then respond," which `axi_bram_ctrl` does automatically.
- Output signals (e.g., `AWREADY`, `WREADY`) must not be purely combinational functions of the corresponding input VALID signals — registering them avoids long combinational paths and accidental protocol violations.
- AXI-Stream `TKEEP` may only be "sparse" (contain zero bits) on the beat where `TLAST` is asserted, or on the first beat if a Data Realignment Engine (DRE) is present — relevant only if a future DMA/streaming path is added to the BRAM demo.

### Code Example
```vhdl
-- Minimal correct AXI4-Lite write-channel FSM for a custom register slave
-- (relevant only if you ever add a custom control/status register block
-- alongside axi_bram_ctrl0/axi_bram_ctrl1 in kv260_top.vhd)
process(s_axi_aclk)
begin
  if rising_edge(s_axi_aclk) then
    if s_axi_aresetn = '0' then
      awready <= '0';
      wready  <= '0';
      bvalid  <= '0';
    else
      -- Accept AW and W independently/concurrently, not AW-then-W
      if s_axi_awvalid = '1' and awready = '0' and bvalid = '0' then
        awready <= '1';
        awaddr_reg <= s_axi_awaddr;
      else
        awready <= '0';
      end if;

      if s_axi_wvalid = '1' and wready = '0' and bvalid = '0' then
        wready <= '1';
      else
        wready <= '0';
      end if;

      -- BVALID only after the W handshake completes
      if s_axi_wvalid = '1' and wready = '1' and bvalid = '0' then
        bvalid <= '1';
        -- perform register write here using awaddr_reg / s_axi_wdata
      elsif s_axi_bready = '1' and bvalid = '1' then
        bvalid <= '0';
      end if;
    end if;
  end if;
end process;
```

### Relevance to Your Project
BRAM0/BRAM2 sit behind `axi_bram_ctrl` instances in AXI4-Lite mode (single outstanding transaction, no bursts). The PS's AXI master (`M_AXI_HPM0_FPD`/`LPD`) is a Xilinx-verified IP that respects all ordering rules, so `Xil_Out32(0xA0000000, ...)` / `Xil_In32(0xA0000000)` calls in `main.c` need no special handling. The AW/W ordering rule above only becomes relevant if the project grows to include a hand-rolled AXI-Lite peripheral (e.g., a status register exposing PASS/FAIL flags to the PS without UART) — in that case, use the FSM pattern above rather than a naive "wait for AWREADY first" implementation.

## Vivado Block Design / IP Integrator
### Key Findings
- When `axi_bram_ctrl` is added and Connection Automation is run, Vivado auto-generates a matching `blk_mem_gen` (Block Memory Generator) instance configured for the controller's native interface — if `create_bd.tcl` instead manually instantiates both IPs, their `DATA_WIDTH` and `READ_WRITE_MODE` parameters must match exactly or `validate_bd_design` throws an error.
- If ECC is enabled on `axi_bram_ctrl` (`C_ECC = 1`), the paired BMG must be configured with the corresponding ECC parity-bit memory map — this changes the BRAM's effective addressable depth and is a frequent source of "controller works in sim, fails on hardware" reports.
- `write_bd_tcl -force` captures the *current* state of a `.bd` (IP customizations, connections, address assignments) back into a Tcl script — useful for one-time "GUI drift capture" if someone manually tweaks the block design in the GUI and `create_bd.tcl` needs to be re-synced.
- Address Editor / `assign_bd_address` entries only populate after a master with an address space (the Zynq UltraScale+ PS `M_AXI_HPM0_FPD`/`LPD`) exists in the BD; any manually-assigned offset must be aligned to the slave's declared range (a 64KB-range slave needs an offset that's a multiple of `0x10000`, which `0xA0000000`/`0xA0010000` both satisfy).
- After any programmatic BD edit (manual `connect_bd_intf_net`, `assign_bd_address`, etc.), run `validate_bd_design` then `regenerate_bd_layout` before `save_bd_design` — skipping this is the most common reason a freshly Tcl-generated `.bd` produces a wrapper whose `xparameters.h` doesn't match the intended address map.

### Code Example
```tcl
# Idempotent axi_bram_ctrl + blk_mem_gen pairing with matched parameters,
# safe to re-source against an existing .bd (checks for existing cells)
foreach {idx base} {0 0xA0000000  1 0xA0010000} {
    set ctrl "axi_bram_ctrl_$idx"
    set bmg  "blk_mem_gen_$idx"

    if {[get_bd_cells $ctrl -quiet] eq ""} {
        create_bd_cell -type ip -vlnv [get_ipdefs -filter {NAME == "axi_bram_ctrl"}] $ctrl
        set_property -dict [list CONFIG.DATA_WIDTH {32} CONFIG.SINGLE_PORT_BRAM {1}] [get_bd_cells $ctrl]
    }
    if {[get_bd_cells $bmg -quiet] eq ""} {
        create_bd_cell -type ip -vlnv [get_ipdefs -filter {NAME == "blk_mem_gen"}] $bmg
        # Match axi_bram_ctrl's native interface so types/widths line up
        set_property -dict [list CONFIG.Memory_Type {Single_Port_RAM} \
            CONFIG.Use_Byte_Write_Enable {true} \
            CONFIG.Write_Width_A {32} CONFIG.Read_Width_A {32}] [get_bd_cells $bmg]
    }
    connect_bd_intf_net [get_bd_intf_pins $ctrl/BRAM_PORTA] [get_bd_intf_pins $bmg/BRAM_PORTA]

    assign_bd_address -offset $base -range 0x00010000 \
        -target_address_space [get_bd_addr_spaces zynq_ultra_ps_e_0/Data] \
        [get_bd_addr_segs $ctrl/S_AXI/Reg] -force
}
validate_bd_design
regenerate_bd_layout
```

### Relevance to Your Project
This is the explicit Tcl form of "drag axi_bram_ctrl onto the canvas, let Connection Automation create the BMG, then set the Address Editor offset" — the pattern your `create_bd.tcl` is presumably already following for BRAM0/BRAM2. If it instead instantiates `blk_mem_gen` separately, double-check `Write_Width_A`/`Read_Width_A` = 32 to match the controller's `DATA_WIDTH`, since a mismatch is silent in the GUI but fails `validate_bd_design` in batch mode with a non-obvious error message.

## Vivado TCL Scripting
### Key Findings
- Non-project mode is invoked as `vivado -mode batch -source <script.tcl>`; the tool reads sources and builds the design entirely in memory, with no automatic intermediate files — any reports must be explicitly generated via Tcl (`report_timing_summary`, etc.).
- In batch mode, unrecognized commands are **not** passed to the OS shell — use `exec` explicitly for any external program calls, so the script behaves identically in GUI Tcl console, `-mode tcl`, and `-mode batch`.
- Non-project flows should checkpoint state with `write_checkpoint` at key stages (post-synth, post-opt, post-place, post-route) rather than relying on `.dcp` auto-save, since nothing is persisted automatically.
- For version control, the recommendation is to keep only source Tcl scripts (BD-creation script, XDC, HDL) under git and treat the `.xpr`/`.bd`/generated output as disposable build artifacts — `write_bd_tcl -force <path>` regenerates the BD-creation script from a GUI-edited `.bd` when needed.
- `Tcl Batch Mode` (UG835, 2025.x) confirms `source` works identically across modes — a script developed interactively in `-mode tcl` can be dropped unmodified into a `-mode batch` build pipeline.

### Code Example
```tcl
# build.tcl - non-project mode skeleton for kv260_claude/kv260
set proj_dir   [file dirname [info script]]
set part       "xck26-sfvc784-2LV-c"   ;# K26 SOM part

create_project -in_memory -part $part

source $proj_dir/tcl/create_bd.tcl      ;# builds zynq_ultra_ps_e_0, axi_bram_ctrl_0/1, etc.

add_files -fileset constrs_1 $proj_dir/xdc/kv260_top.xdc
read_vhdl $proj_dir/vhdl/kv260_top.vhd
set_property top kv260_top [current_fileset]

synth_design -top kv260_top -part $part
write_checkpoint -force $proj_dir/build/post_synth.dcp

opt_design
place_design
route_design
write_checkpoint -force $proj_dir/build/post_route.dcp

report_timing_summary -file $proj_dir/build/timing_summary.rpt
write_bitstream -force $proj_dir/build/kv260_top.bit

# Capture XSA for Vitis
write_hw_platform -fixed -include_bit -force $proj_dir/build/kv260_top.xsa
```

### Relevance to Your Project
If `create_bd.tcl` is currently sourced inside a project-mode `.xpr` workflow, this skeleton shows how the same script slots into a fully scripted, non-project build — useful for CI or for regenerating the `.xsa` headlessly after any BD/XDC edit without opening the Vivado GUI. The final `write_hw_platform` step is what feeds the Vitis platform/BSP regeneration that produces `xparameters.h` with the `0xA0000000`/`0xA0010000` base addresses used in `main.c`.

## Vitis Bare-Metal / Standalone
### Key Findings
- Vitis 2025.x's Unified IDE replaced the legacy `.mss`/`.mld`/`.bsp` BSP-editor files with `vitis-comp.json` plus per-domain YAML config — any guide that says "open Board Support Package Settings → standalone → stdin/stdout" describes Vitis Classic; in 2025.1 Unified IDE the equivalent is the platform component's "Domain" configuration and `vitis-comp.json`.
- `xil_printf()` (from `xil_printf.h`) is the recommended print function for bare-metal apps — it's a minimal `printf` subset (no floating point by default) that avoids pulling in the full newlib `stdio`, keeping `.elf` size and startup time down, important for a "blink and report PASS/FAIL" demo.
- Standalone BSP `stdin`/`stdout` defaults to the UART specified by the hardware platform (PS UART0/UART1 on Zynq UltraScale+); if the BD wires USB-UART through PS UART1, the BSP must be regenerated after any BD change that alters which UART is connected, or `xil_printf` output silently goes to the wrong/no port.
- The GIC (Generic Interrupt Controller) standalone driver source ships with Vitis and is also in the `Xilinx/embeddedsw` GitHub repo under release-tagged branches — useful if the BRAM demo is later extended to use an AXI timer or GPIO interrupt instead of polling.
- Linker scripts (`lscript.ld`) generated by Vitis define memory regions (`.text`, `.bss`, heap/stack) based on the hardware platform's address map — after any address-map change (e.g., BRAM0/BRAM2 offsets), re-running "Update Hardware Specification" regenerates both `xparameters.h` and the linker script's memory regions.

### Code Example
```c
/* main.c excerpt - standalone bare-metal pattern for Cortex-A53 on KV260 */
#include "xil_printf.h"
#include "xil_io.h"
#include "xparameters.h"

#define BRAM0_BASEADDR  XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR  /* 0xA0000000 */
#define BRAM2_BASEADDR  XPAR_AXI_BRAM_CTRL_1_S_AXI_BASEADDR  /* 0xA0010000 */

int test_bram(UINTPTR base, const char *name) {
    int pass = 1;
    for (int i = 0; i < 16; i++) {
        u32 pattern = 0xA5A50000 | i;
        Xil_Out32(base + (i * 4), pattern);
    }
    for (int i = 0; i < 16; i++) {
        u32 expected = 0xA5A50000 | i;
        u32 actual = Xil_In32(base + (i * 4));
        if (actual != expected) {
            xil_printf("%s FAIL @0x%08lX: wrote 0x%08lX read 0x%08lX\r\n",
                       name, (UINTPTR)(base + i*4), expected, actual);
            pass = 0;
        }
    }
    xil_printf("%s: %s\r\n", name, pass ? "PASS" : "FAIL");
    return pass;
}

int main(void) {
    xil_printf("KV260 AXI-BRAM demo starting\r\n");
    int ok = test_bram(BRAM0_BASEADDR, "BRAM0");
    ok &= test_bram(BRAM2_BASEADDR, "BRAM2");
    xil_printf("Overall: %s\r\n", ok ? "PASS" : "FAIL");
    while (1) { /* idle */ }
    return 0;
}
```

### Relevance to Your Project
This mirrors the described pattern in `main.c`. The key actionable item: whenever `create_bd.tcl` changes BRAM0/BRAM2 base addresses or any IP is added/removed from the BD, re-export the `.xsa` (via `write_hw_platform`) and trigger "Update Hardware Specification" in the Vitis platform component — otherwise `xparameters.h` retains stale `XPAR_AXI_BRAM_CTRL_*_S_AXI_BASEADDR` macros and the demo will read/write the wrong addresses while still compiling cleanly.

## XDC Timing Constraints
### Key Findings
- `set_input_delay`/`set_output_delay` define external system-level path delays on primary I/O ports relative to a clock edge, specified in ns, e.g. `set_input_delay -clock clk -max 5.0 [get_ports data_in]`. These only matter for signals crossing the FPGA pin boundary to external devices.
- For Zynq UltraScale+ designs where the PL portion is purely AXI-Lite peripherals talking to the PS (no top-level I/O pins), `set_input_delay`/`set_output_delay` are typically **not needed** — the PS-PL AXI interfaces are internal, synchronous, and timed automatically against `FCLK_CLK0` (or whichever PL clock drives the AXI interconnect).
- `set_clock_groups -asynchronous` is required whenever two clock domains in the design have no defined phase relationship (e.g., a PL-generated clock vs. a PS `FCLK_CLKx`) — omitting it causes Vivado to attempt (and fail) timing analysis across unrelated clocks, producing spurious critical paths.
- The Kria-PYNQ reference `base.xdc` (Xilinx/Kria-PYNQ repo) is a good source of carrier-board-specific pin constraints (PMOD, RPi header, etc.) for KV260 if the design grows to include external GPIO/PMOD signals.
- Recommended practice: keep carrier-board pin-mapping XDC separate from reusable PL-IP timing XDC, so the BRAM-demo's internal-only constraints file stays portable if ported to a different K26 carrier.

### Relevance to Your Project
Since BRAM0/BRAM2 are accessed purely through PS-internal AXI4-Lite (no PL-side top-level ports beyond what the K26 SOM's fixed pinout requires), the project's `kv260_top.xdc` likely needs minimal or no `set_input_delay`/`set_output_delay` constraints today. The main thing to watch for is if a future revision adds any PL-generated clock (e.g., for a custom AXI-Stream block) — at that point `set_clock_groups -asynchronous` against the PS `pl_clk0` becomes mandatory to avoid false timing failures during implementation.

## Kria KV260 / K26 SoM
### Key Findings
- Primary boot device is selected via `MODE[3:0]` pins strapped on the carrier card; KV260 Starter Kits ship pre-configured for QSPI32 boot of the certified Linux image — these pins are physically fixed by the carrier and not something a bare-metal Vivado/Vitis project can or needs to change for JTAG-based development.
- Bare-metal ELF deployment via Vitis/XSDB over JTAG bypasses the QSPI boot chain entirely — the FSBL/PMU/U-Boot stack used for the Linux image is irrelevant to a "build .xsa, build .elf, `xsdb` download-and-run" bare-metal flow.
- The K26/K24 board files (used for "Apply Board Preset" during PS configuration) define a minimal MIO configuration sufficient to boot to Linux — for a bare-metal project, applying the board preset is still the right starting point for `zynq_ultra_ps_e_0` configuration (clocks, DDR, UART) even though the project never boots Linux.
- PMU reference pin mappings include MIO31 (HW-requested shutdown input) and MIO35 (external watchdog trigger output) — not relevant to the AXI-BRAM demo unless power-management features are added, but worth knowing if the board behaves unexpectedly on external power-good/shutdown signaling.
- The Kria SOM Carrier Card Design Guide (UG1091) and Zynq UltraScale+ TRM (UG1085) remain the canonical references for the full boot-mode and MIO/EMIO pin tables.

### Code Example
```tcl
# Applying the K26 board preset for PS configuration in create_bd.tcl
# (sets up DDR, UART, clocks per the SOM's fixed hardware design)
create_bd_cell -type ip -vlnv [get_ipdefs -filter {NAME == "zynq_ultra_ps_e"}] zynq_ultra_ps_e_0
apply_bd_automation -rule xilinx.com::bd_rule:zynq_ultra_ps_e \
    -config {apply_board_preset "1"}  [get_bd_cells zynq_ultra_ps_e_0]

# Enable the PL-PS AXI master interface used by axi_bram_ctrl_0/1
set_property -dict [list CONFIG.PSU__USE__M_AXI_GP0 {1} \
    CONFIG.PSU__MAXIGP0__DATA_WIDTH {32}] [get_bd_cells zynq_ultra_ps_e_0]
```

### Relevance to Your Project
For the AXI-BRAM demo's bare-metal JTAG workflow, boot-mode pins and PMU MIO configuration are non-issues — `apply_board_preset` for `zynq_ultra_ps_e_0` (likely already in `create_bd.tcl`) is the only K26-specific configuration that matters, ensuring DDR and the USB-UART path (typically PS UART1) are correctly initialized so `xil_printf` PASS/FAIL output reaches the host terminal.

## AMD/Xilinx Tool Updates
### Key Findings
- **Vivado/Vitis 2026.1 introduces tiered licensing** (BASIC, CORE, PRO annual subscriptions; ENTERPRISE/GOLD perpetual). The free BASIC tier is **Windows-only** — Linux users need at least the CORE tier (~$1,200-1,800/year) to run 2026.1+ natively on Linux. This has generated significant community pushback (Tom's Hardware, It's FOSS, EEVblog/Digilent forums).
- Pre-2026.1 versions (2025.1, 2025.2, etc.) continue to work under existing free Standard/ML licenses with no forced expiry tied to the 2026.1 change — there's no need to upgrade off 2025.1 for this project.
- Vivado 2025.2 changed the **AMD IP configuration file format from XML to JSON**, improving revision-control diffing and IP load times — relevant if `create_bd.tcl` or any script parses `.xci` files directly.
- Vivado 2025.2 has a known **XSIM double-compilation bug** requiring a workaround (re-run `xvlog`/`xelab` compile step twice) — only relevant if/when simulation is added to the project's verification flow.
- 2025.2 IP release notes (AR 000039903) catalog per-IP changelogs — useful to check before bumping `axi_bram_ctrl` or `zynq_ultra_ps_e` IP versions during a future Vivado upgrade.
