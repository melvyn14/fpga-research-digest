# FPGA Research Digest - 2026-11-08

## Executive Summary
- **AXI-Lite VALID persistence bug**: Once VALID is asserted it must stay asserted until READY responds — Xilinx's own generated slave templates have historically violated this; audit `kv260_top.vhd` and any custom IP against this rule using the AXI Protocol Checker IP or formal properties from ZipCPU's wb2axip.
- **BRAM read extra cycle**: The AXI BRAM Controller (PG078) adds one cycle of read latency for the BRAM primitive; AXI-Lite reads appear to stall briefly — this is expected and not a timing violation; confirm with the protocol checker in simulation.
- **write_bd_tcl version pinning**: Your `create_bd.tcl` exports IP VLNVs with version numbers by default; always regenerate the script in the same tool release and use `-no_ip_version` only intentionally, since major IP version changes can silently alter behaviour.
- **Vivado 2025.2 adds ultra-low-area AXI SmartConnect/Switch**: Not relevant to BRAM demo, but useful for future multi-master designs on the K26.
- **Vitis BSP STDOUT mapping is critical**: For USB-UART to work in a bare-metal application, the BSP platform setting `STDIN/STDOUT` must point to the correct PS UART; a misconfigured BSP produces silent output even when the UART IP is wired correctly.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings
- **VALID persistence rule**: The AXI specification requires that once `VALID` is asserted, it must remain asserted until the handshake completes (READY goes high on the same cycle). Deasserting VALID early is a protocol violation and can cause silent data loss or bus hang. This is the single most common bug in custom AXI-lite slave peripherals, including those generated by Vivado templates in releases through 2019.
- **AXI Protocol Checker IP**: Xilinx ships an inline protocol checker IP that can be inserted in simulation between master and slave. It flags handshake violations, out-of-spec burst parameters, and illegal response codes. Use it during RTL simulation before integrating hardware.
- **Register slices for timing closure**: Insert AXI Register Slice IP between long interconnect paths to break combinatorial timing chains at the cost of one added cycle of latency. Acceptable for BRAM-backed register maps with no real-time constraints.
- **AXI-Lite vs AXI-Full**: AXI-Lite has no burst support (single-beat transactions only) and no WSTRB masking beyond byte-level. For the KV260 AXI-BRAM demo, AXI-Lite is the correct choice since the PS Cortex-A53 drives single word-wide accesses to the BRAM via `M_AXI_HPM0_LPD`.
- **RVALID must not assert before RDATA is valid**: A common secondary bug is asserting RVALID one cycle before RDATA is loaded from BRAM. Formal verification catches this immediately; inspection of waveforms in simulation is the manual alternative.

### Code Example
```vhdl
-- Correct AXI-Lite slave read handshake skeleton (VHDL)
-- RVALID must not de-assert until RREADY is seen

process(clk)
begin
  if rising_edge(clk) then
    if rst = '1' then
      s_axi_rvalid <= '0';
      s_axi_rdata  <= (others => '0');
    elsif s_axi_arvalid = '1' and s_axi_arready = '1' then
      -- address accepted; latch BRAM output next cycle
      bram_rd_addr <= s_axi_araddr(ADDR_BITS-1 downto 2);
      read_pending <= '1';
    elsif read_pending = '1' then
      s_axi_rdata  <= bram_dout;   -- BRAM output ready after 1 cycle
      s_axi_rvalid <= '1';
      read_pending <= '0';
    elsif s_axi_rvalid = '1' and s_axi_rready = '1' then
      s_axi_rvalid <= '0';         -- de-assert only after handshake
    end if;
  end if;
end process;
```

### Relevance to Your Project
Your `kv260_top.vhd` wraps two Block Memory Generators behind AXI-Lite. Any custom glue logic between the PS master port and the BRAM controller must follow the VALID-persistence rule. If you are using Xilinx's AXI BRAM Controller IP directly (PG078), the IP handles handshaking correctly, but adding an intermediate VHDL wrapper reintroduces the risk. Simulate with the AXI Protocol Checker inserted on `S_AXI` of each BRAM controller before hardware bring-up.

## Vivado Block Design / IP Integrator

### Key Findings
- **`apply_bd_automation` is an IDE command**: AMD UG994 (2025.2) explicitly recommends running `apply_bd_automation` through the Vivado IDE's Designer Assistance GUI rather than from Tcl scripts. For a scriptable flow, the guidance is to use the GUI once, then export the resulting design with `write_bd_tcl`.
- **`write_bd_tcl` version-locks the design**: By default, IP VLNVs are written with their version numbers, which means the script will fail if sourced in a different tool release. Use `-no_ip_version` only if you are intentionally upgrading IPs.
- **Layout not saved by default**: Add `-include_layout` to `write_bd_tcl` to preserve canvas positions; otherwise IP blocks are repositioned on each re-source.
- **Custom IP repositories must be pre-added**: Before sourcing a `write_bd_tcl` output, add all custom IP repos with `set_property ip_repo_paths`; without this, the script fails with `BD_TCL-115 IPs not found in catalog`.
- **Connection automation for AXI masters**: The Designer Assistance auto-connects AXI slave ports, assigns addresses in the Address Editor, and enables ECC or BRAM options when prompted. For the KV260, the PS `M_AXI_HPM0_LPD` port is the typical source; run automation on it to let Vivado assign the base address.

### Code Example
```tcl
# Minimal Vivado block design TCL script skeleton for a KV260 AXI-BRAM design
# Run with: vivado -mode batch -source create_bd.tcl

create_project kv260_bram ./kv260_bram -part xck26-sfvc784-2LV-c
set_property board_part xilinx.com:kv260_som:part0:1.4 [current_project]

create_bd_design "design_1"

# Instantiate Zynq UltraScale+ MPSoC
set zynq [create_bd_cell -type ip -vlnv xilinx.com:ip:zynq_ultra_ps_e zynq_ultra_ps_e_0]
apply_board_preset $zynq

# Instantiate AXI BRAM Controller + Block Memory Generator pair
set bram_ctrl [create_bd_cell -type ip -vlnv xilinx.com:ip:axi_bram_ctrl axi_bram_ctrl_0]
set bram_mem  [create_bd_cell -type ip -vlnv xilinx.com:ip:blk_mem_gen  blk_mem_gen_0]
set_property CONFIG.Memory_Type {True_Dual_Port_RAM} [get_bd_cells blk_mem_gen_0]

# Wire BRAM controller to memory
connect_bd_intf_net [get_bd_intf_pins axi_bram_ctrl_0/BRAM_PORTA] \
                    [get_bd_intf_pins blk_mem_gen_0/BRAM_PORTA]

# Connect PS master to BRAM controller slave
connect_bd_intf_net [get_bd_intf_pins zynq_ultra_ps_e_0/M_AXI_HPM0_LPD] \
                    [get_bd_intf_pins axi_bram_ctrl_0/S_AXI]

# Assign address: 0xA000_0000, 64 KB
assign_bd_address -offset 0xA0000000 -range 0x00010000 \
    [get_bd_addr_segs axi_bram_ctrl_0/S_AXI/Mem0]

validate_bd_design
save_bd_design
```

### Relevance to Your Project
Your `create_bd.tcl` likely already mirrors this structure. The key addition is the explicit `assign_bd_address` for BRAM0 at `0xA0000000` and BRAM2 at `0xA0010000` — these must match the base addresses used in `main.c` (`0xA0000000` and `0xA0010000`). Any mismatch between the Address Editor and the C code produces silent reads of `0xDEADBEEF` or garbage without a bus error.

## Vivado TCL Scripting

### Key Findings
- **Non-project mode** is the CI-friendly approach: source files are managed explicitly, there is no `.xpr` file, and the build is fully reproducible from a single Tcl script. AMD UG895 documents the full non-project command set.
- **Checkpoint-based incremental compile**: Write checkpoints after synthesis and after implementation with `write_checkpoint`; this allows re-running only the changed stage without a full rebuild.
- **Bitstream generation command**: In non-project mode, use `write_bitstream -force -bin_file output.bit` after `route_design`. In project mode, use `launch_runs impl_1 -to_step write_bitstream`.
- **IP generation in scripts**: Call `generate_target all [get_files *.xci]` after adding IP XCI files; without this, synthesis fails because the IP output products (stub files, simulation models) are not present.
- **Block design wrapper**: After saving a BD, generate the VHDL wrapper with `make_wrapper -files [get_files design_1.bd] -top` and add the resulting file to the project before synthesis.

### Code Example
```tcl
# Non-project mode build script for KV260 AXI-BRAM
# Usage: vivado -mode batch -source build.tcl

set outputDir ./output
file mkdir $outputDir

# Read sources
read_vhdl [glob ./vhdl/*.vhd]
read_xdc  ./constraints/kv260_top.xdc

# Source the block design (re-creates it from scratch)
source ./tcl/create_bd.tcl

# Generate block design wrapper
set bd_file [get_files design_1.bd]
make_wrapper -files $bd_file -top
add_files -norecurse [glob ./kv260_bram.gen/sources_1/bd/design_1/hdl/*.vhd]

# Synthesis
synth_design -top kv260_top -part xck26-sfvc784-2LV-c
write_checkpoint -force $outputDir/post_synth.dcp

# Implementation
opt_design
place_design
route_design
write_checkpoint -force $outputDir/post_route.dcp

# Reports
report_timing_summary -file $outputDir/timing.rpt
report_utilization    -file $outputDir/utilization.rpt

# Bitstream
write_bitstream -force -bin_file $outputDir/kv260_top.bit

puts "Build complete."
```

### Relevance to Your Project
Using a non-project build script means your CI can reproduce the bitstream from `create_bd.tcl` and `kv260_top.vhd` without a persistent `.xpr`. This is especially valuable for a demo project: anyone who clones `kv260-axi-bram-demo` can regenerate the bitstream with a single Vivado invocation. The `write_checkpoint` calls give you checkpoints for examining timing failures without re-running the full flow.

## Vitis Bare-Metal / Standalone

### Key Findings
- **BSP STDOUT mapping is essential**: The Vitis BSP platform configuration must map `STDIN/STDOUT` to the correct PS UART (e.g., `psu_uart_1` on the KV260). A misconfigured BSP compiles and links successfully but produces no UART output at runtime — this is a frequent stumbling block for first-time KV260 bare-metal projects.
- **`xil_printf` vs full `printf`**: `xil_printf` is a minimal, non-floating-point implementation in the standalone BSP. It is significantly smaller (useful for resource-constrained bare-metal) but does not support `%f`, `%e`, or `%g`. Use the full `printf` from newlib only if floating-point formatting is required and the larger code size is acceptable.
- **Do not call `xil_printf` from an ISR**: Community consensus (backed by BSP source inspection) is that `xil_printf` uses a UART FIFO polling loop and is not interrupt-safe. Use a flag in the ISR and print in main loop context.
- **GIC interrupt wiring for PL-to-PS**: For a fabric interrupt to reach the Cortex-A53, wire `pl_ps_irq0[0:0]` on the Zynq PS IP in the block design to the PL interrupt source. In software, register the handler with `XScuGic_Connect`, then call `Xil_ExceptionEnable()` and `XScuGic_Enable()`.
- **Linker script memory regions**: The default Vitis linker script places code in DDR. For the KV260, DDR starts at `0x00000000` for Cortex-A53. Confirm the memory map matches the XSA export from Vivado; a wrong base address causes the application to load correctly over JTAG but hang on a cache-coherency access.

### Code Example
```c
/* Minimal KV260 bare-metal AXI-BRAM read/write test (Vitis standalone) */
#include "xil_printf.h"
#include "xil_io.h"

#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL
#define TEST_PATTERN 0xDEAD600DUL

static void test_bram(const char *name, uintptr_t base)
{
    Xil_Out32(base + 0x00, TEST_PATTERN);
    Xil_Out32(base + 0x04, ~TEST_PATTERN);

    u32 rd0 = Xil_In32(base + 0x00);
    u32 rd1 = Xil_In32(base + 0x04);

    if (rd0 == TEST_PATTERN && rd1 == (u32)(~TEST_PATTERN))
        xil_printf("%s: PASS (0x%08X / 0x%08X)\r\n", name, rd0, rd1);
    else
        xil_printf("%s: FAIL got 0x%08X / 0x%08X\r\n", name, rd0, rd1);
}

int main(void)
{
    xil_printf("KV260 AXI-BRAM demo starting\r\n");
    test_bram("BRAM0", BRAM0_BASE);
    test_bram("BRAM2", BRAM2_BASE);
    xil_printf("Done.\r\n");
    return 0;
}
```

### Relevance to Your Project
Your `main.c` performs essentially this pattern. The key practical improvement is using `Xil_Out32`/`Xil_In32` (from `xil_io.h`) rather than raw pointer casts; these macros handle data-cache coherency barriers on Cortex-A53 when caches are enabled. If you are running with MMU and data cache on, bare pointer writes may be held in cache and never reach the AXI fabric — `Xil_Out32` includes a `dmb` barrier.

## XDC Timing Constraints

### Key Findings
- **`set_input_delay` / `set_output_delay` scope**: These commands constrain the combinatorial path from an I/O pin to the first capture register. For the KV260 AXI-BRAM demo, all AXI signals are internal PS-to-PL and do not cross device I/O pads, so `set_input_delay` / `set_output_delay` are not needed for AXI paths. Focus XDC constraints on external I/O (clocks, LEDs, debug headers).
- **`set_clock_groups` cuts timing across clock domains**: Using `-asynchronous` or `-logically_exclusive` between independent clock groups suppresses inter-domain timing checks. This is correct when the clocks have no phase relationship, but it silences the timing report for those paths — the crossing must be handled in RTL (synchronizer FFs, FIFO) independently of Vivado's constraint.
- **Primary clock constraint is mandatory**: Every design must have a `create_clock` for every primary clock; without it, Vivado may auto-infer incorrect periods, or leave paths unconstrained and report false timing clean.
- **Zynq PS clocks**: For Zynq UltraScale+ (and K26), the PS supplies fabric clocks through `pl_clkX` pins. Vivado auto-creates timing constraints for `pl_clk0` etc. when the Zynq PS IP is instantiated in the block design; you should NOT add a conflicting `create_clock` for the same clock net in your XDC.
- **`-datapath_only` for false paths**: For paths that cross clock domains via handshaking (not synchronizers), use `set_max_delay -datapath_only` to give a realistic max delay budget instead of excluding the path entirely. This prevents the timing engine from complaining while still checking data arrival.

### Code Example
```tcl
# kv260_top.xdc – minimal constraint file for KV260 AXI-BRAM demo

# The PS-generated pl_clk0 is auto-constrained by Vivado when the
# Zynq UltraScale+ PS IP is in the block design.
# DO NOT add create_clock for pl_clk0 here; it creates a conflicting constraint.

# If you have a free-running oscillator on the carrier (e.g., 125 MHz on SOM GPIO):
# create_clock -period 8.000 -name clk_125 [get_ports clk_125_p]

# Example: cut timing between pl_clk0 and an independent async reference
# set_clock_groups -asynchronous \
#     -group [get_clocks -include_generated_clocks pl_clk0] \
#     -group [get_clocks -include_generated_clocks clk_125]

# Output delay example for a GPIO LED driven by pl_clk0 (illustrative)
# set_output_delay -clock [get_clocks pl_clk0] -max 2.0 [get_ports led_o]
# set_output_delay -clock [get_clocks pl_clk0] -min -1.0 [get_ports led_o]

# False path for async resets driven from PS logic
set_false_path -from [get_pins */rst_n_reg/C] -to [get_ports *]
```

### Relevance to Your Project
For the AXI-BRAM demo, the main timing risk is on the PL logic connecting the PS AXI master to the BRAM controllers. These paths are all driven by `pl_clk0`, so they are in the same clock domain and will be automatically checked. Run `report_timing_summary` after route and confirm **WNS ≥ 0** on `pl_clk0`; if negative, insert an AXI Register Slice IP to relax the path.

## Kria KV260 / K26 SoM

### Key Findings
- **MIO bank assignment**: The K26 SoM uses MIO bank 500 for onboard eMMC, QSPI, and I2C/TPM; bank 501 for PMU and user I/O; bank 502 for further user I/O. All three MIO banks are 1.8V. External peripherals requiring 3.3V must be connected to PL I/O banks through EMIO or dedicated carrier-board connectors.
- **Boot mode override via XSDB**: To JTAG-boot a bare-metal application during development, use the XSDB/XSCT `boot_jtag.tcl` script provided in AMD's Kria docs. The hardware default is QSPI32 primary boot; the script writes to PSU boot-mode registers to override this without physically changing jumpers.
- **Bare-metal BRAM flow uses M_AXI_HPM0_LPD**: The K26 PS exposes `M_AXI_HPM0_LPD` (Low-Power Domain, 32-bit, up to 1 GB mapped space) as the convenient AXI master for bare-metal demos. The AXI BRAM controller connects to this port in the block design.
- **FTDI FT4232HL provides JTAG + UART**: The KV260 Starter Kit's FT4232HL chip handles both the Vivado/Vitis JTAG interface and the USB-UART console. No additional USB-serial adapter is needed; just plug in the USB cable and confirm the `/dev/ttyUSBx` port is mapped to the UART interface (not the JTAG interface — typically ttyUSB1 for UART on KV260).
- **XSCT load sequence for Cortex-A53**: The correct debug sequence is `connect`, `targets -set -filter {name =~ "Cortex-A53 #0"}`, `rst -processor`, `dow <app.elf>`, `con`. Omitting `rst -processor` before download often leaves stale state from a previous run.

### Code Example
```tcl
# XSCT/XSDB script: load and run a bare-metal ELF on KV260 Cortex-A53 #0
# Usage: xsct load_bm.tcl

connect

# Target the A53 core 0
targets -set -filter {name =~ "Cortex-A53 #0"}

# Reset processor only (not the full PS, to avoid re-initialising DDR)
rst -processor

# Download the application ELF
dow ./kv260_bram_demo.elf

# Optional: set a breakpoint at main to inspect before run
# bpadd -addr &main

# Run
con

puts "Application loaded and running. Connect to /dev/ttyUSB1 at 115200 baud."
```

### Relevance to Your Project
Your bare-metal bring-up workflow maps exactly to this. The `rst -processor` step is especially important on the K26: without it, the A53 may be in an undefined state from the PMU firmware that ran during JTAG boot negotiation, and the ELF download succeeds but execution hangs before `main`. After `con`, open the serial terminal on the UART port at 115200 8N1 to see your PASS/FAIL output from `xil_printf`.

## AMD/Xilinx Tool Updates (Vivado/Vitis 2025.x)

### Key Findings
- **Vivado 2025.2 headline**: The release focuses on Versal QoR improvements (reduced PhysOpt compile time, retiming enhancements) and adds a new ultra-low-area mode for the **AXI Switch** and **AXI SmartConnect** IPs via a `STRATEGY` parameter. This mode reduces LUT count significantly for designs with few masters/slaves.
- **New AXI Switch IP**: Vivado 2025.2 adds a new AXI Switch IP to the catalog alongside the existing AXI Interconnect and AXI SmartConnect. The new IP is positioned as a lightweight alternative for simple routing topologies.
- **VHDL 2019 simulation constructs**: Vivado 2025.1 adds support for VHDL 2019 features including conditional expressions and conditional return statements in simulation. Synthesis support for VHDL 2019 is not yet complete; use `--std=vhdl2019` flag in simulation only.
- **Vitis 2025.2 platform/BSP**: Open-source component release notes list new BSP migrations for ZCU102/ZCU106 boards and a Linux kernel upgrade to 6.12. For bare-metal, the standalone BSP itself sees minor fixes; the most significant ongoing change is the split of `xil_printf` and `print` into separate compilation units to reduce dead-code inclusion.
- **UG1209 (Zynq UltraScale+ Embedded Design Tutorial) 2025.2**: Dated 2025-12-29, it reflects the 2025.2 tool flow and is the definitive starting point for a new KV260 Vitis project. Worth reviewing if you upgrade from 2025.1.
- **Vivado 2025.1 adds Spartan UltraScale+ production support**: XCSU10P, XCSU25P, XCSU35P are now production-qualified. Not relevant to K26, but signals active device portfolio work.

### Code Example
```tcl

# Available in Vivado 2025.2+

    [get_bd_intf_pins smartconnect_0/S00_AXI]

connect_bd_intf_net \
    [get_bd_intf_pins smartconnect_0/M00_AXI] \
    [get_bd_intf_pins axi_bram_ctrl_0/S_AXI]

    [get_bd_intf_pins smartconnect_0/M01_AXI] \
```

### Relevance to Your Project
You are using Vivado/Vitis 2025.1. If you upgrade to 2025.2, the AXI Switch/SmartConnect ultra-low-area mode and the DFX summary GUI are the most practically useful additions. For your two-BRAM demo, the most impactful change is the confirmed VHDL 2019 simulation support in 2025.1 — you can use conditional expressions in testbenches without workarounds. Verify your project's IP VLNVs if you upgrade tools: `write_bd_tcl` output from 2025.1 will not source cleanly in 2025.2 without updating the IP version numbers.
