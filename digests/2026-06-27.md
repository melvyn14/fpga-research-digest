- Confirmed once more: **`create_clock` must never be hand-applied to `pl_clk0`** or any other PS-/MMCM-derived clock output — Vivado auto-derives the constraint from the upstream clock generator the moment the block design clock network is connected, and a manual override silently replaces the accurate auto-derived waveform with a potentially wrong one rather than throwing an error.

## AXI Protocol / AXI-Lite / AXI-Stream
### Key Findings
- AXI4-Lite (as implemented in `axi_bram_ctrl` and equivalent IPIF-based slaves) is hard-limited to a 32-bit data bus and single-beat, aligned, non-burst transfers — no `WLAST`, no narrow transfers, no reordering; this is an architectural ceiling, not a configuration option, confirmed again across Xilinx product-guide and community sources this round.
- The AXI4 specification explicitly forbids `AWVALID` from waiting on `WREADY` (and vice versa) — a slave that only asserts `AWREADY` once both `AWVALID` and `WVALID` are true is a protocol violation that can stall the bus when an interconnect/SmartConnect decouples address and data phase arrival; this remains a documented recurring mistake in hand-rolled AXI-Lite slaves derived from Xilinx's own demo wizard template, even outside the long-standing WLAST/WVALID gating bug covered previously.
- For AXI-Stream interfaces (not used by this project today, but relevant if a future streaming peripheral is added alongside the BRAM controllers): `TLAST` semantics are IP-specific and inconsistent across Xilinx cores — some IP (e.g. AXI DataMover S2MM) terminates a transfer the moment `TLAST` is asserted, video-oriented IP treats `TLAST` as end-of-line rather than end-of-frame, and `TREADY` must be a registered (not combinational) signal per AMD's own AXI-Stream infrastructure guidance — a frequent root cause of streams that "work in simulation" but stall or truncate on hardware.
- Dual-port AXI BRAM Controller configurations do not give two fully independent read/write ports: enabling a second AXI port on one `axi_bram_ctrl` instance dedicates Port A to write traffic and Port B to read traffic (a throughput/pipelining optimization, not true dual-port semantics) — for genuine independent dual-master access to the same memory, AMD's documented guidance is to instantiate a second `axi_bram_ctrl` against the same `blk_mem_gen` core with a back-to-back address range, rather than relying on one controller's second port.
- ECC on the AXI BRAM Controller is available independent of single/dual-port configuration, but only at 32-, 64-, or 128-bit data widths — worth knowing if a future revision of this project ever needs error-protected BRAM storage, since enabling ECC changes the effective usable data width per beat.

### Code Example
```tcl
# Correct pattern for two independent AXI-accessible BRAM regions sharing one
# Block Memory Generator core, avoiding the "dual-port AXI BRAM Controller is
# not truly dual-port" pitfall -- use two controllers, not one dual-ported one.

# axi_bram_ctrl_0 (BRAM0) - independent controller, single AXI port
set bram_ctrl_0 [create_bd_cell -type ip -vlnv xilinx.com:ip:axi_bram_ctrl:4.1 axi_bram_ctrl_0]
set_property -dict [list CONFIG.SINGLE_PORT_BRAM {1}] $bram_ctrl_0

# axi_bram_ctrl_2 (BRAM2) - second independent controller, NOT a second port
# on axi_bram_ctrl_0, so each master gets genuinely independent timing.
set bram_ctrl_2 [create_bd_cell -type ip -vlnv xilinx.com:ip:axi_bram_ctrl:4.1 axi_bram_ctrl_2]
set_property -dict [list CONFIG.SINGLE_PORT_BRAM {1}] $bram_ctrl_2

# Each controller drives its own blk_mem_gen instance's PORTA -- this is the
# project's actual topology (two BRAM0/BRAM2 IP pairs), and it's the correct
# pattern per AMD's dual-port-is-not-independent guidance.
connect_bd_intf_net [get_bd_intf_pins axi_bram_ctrl_0/BRAM_PORTA] [get_bd_intf_pins blk_mem_gen_0/BRAM_PORTA]
connect_bd_intf_net [get_bd_intf_pins axi_bram_ctrl_2/BRAM_PORTA] [get_bd_intf_pins blk_mem_gen_2/BRAM_PORTA]
```

### Relevance to Your Project
This confirms the project's existing two-controller, two-BMG topology (BRAM0/BRAM2 as separate `axi_bram_ctrl` + `blk_mem_gen` pairs) is already the architecturally correct way to get independent address-mapped memory regions, rather than a riskier single-controller dual-port alternative. Since `main.c` issues sequential single-beat AXI-Lite writes/reads with no burst, no AXI-Stream, and one master, none of the AWVALID/WVALID ordering bug, the TLAST/TREADY stream pitfalls, or the dual-port-is-not-independent gotcha are live risks today — but they're the right things to check first if the demo is ever extended to concurrent dual-master BRAM access or a streaming peripheral.

## Vivado Block Design / IP Integrator
### Key Findings
- Address ranges assigned via the Address Editor (or `assign_bd_address`) for different segments cannot overlap by design — Vivado enforces this at `validate_bd_design` time, but only if the range was explicitly tightened; a default/oversized range is what creates the overlap risk in the first place, not the enforcement itself.
- Address alignment requirements are stricter than "doesn't overlap": a range of size N bytes must start on an N-byte-aligned boundary (e.g., a 64KB range requires the base address to have its low 16 bits all zero) — for BRAM0 at `0xA0000000` and BRAM2 at `0xA0010000` with 64KB ranges, both addresses already satisfy 64KB alignment, but this is worth re-verifying by hand if the address map is ever edited rather than regenerated wholesale.
- A real Vivado 2025-series forum report (Digilent forum, AXI-Lite-attached peripheral, not BRAM-specific) found an address decoder limited to 10 usable bits, capping the peripheral to 1KB of address space with silent wraparound past word address 255 — block design validation did not catch this; it only surfaced as runtime read/write corruption. This is a category of bug (decoder width mismatch vs. advertised IP address range) that `validate_bd_design` cannot detect, since it checks the BD's address map metadata, not the synthesized decoder logic.
- Connection Automation auto-inserts a Processing System Reset IP and an interconnect (AXI Interconnect or SmartConnect depending on Vivado version) when run against a new AXI-attached peripheral — useful default behavior, but it means re-running Connection Automation on an already-wired design can silently insert a redundant second interconnect/reset block rather than reusing the existing one, so it's safer to use targeted manual `connect_bd_intf_net`/`connect_bd_net` calls when editing an established topology like this project's rather than re-invoking automation broadly.
- `validate_bd_design`'s width/link-type negotiation (AXI4 vs AXI4-Lite propagation across connected IP) happens only during validation, not at connection time — a `connect_bd_intf_net` call that links an AXI4-Lite master to an AXI4-only-configured slave (or vice versa) will not error immediately; the mismatch surfaces only once `validate_bd_design` runs and parameter propagation resolves the conflict.

### Code Example
```tcl
# Defensive address-map sanity check to run after assign_bd_address, to catch
# the class of "decoder narrower than advertised range" bug reported against
# Vivado 2025-series AXI-Lite peripherals (silent wraparound, not caught by
# validate_bd_design alone).

set segs [get_bd_addr_segs -of_objects [get_bd_cells axi_bram_ctrl_0]]
foreach seg $segs {
    set range  [get_property RANGE  $seg]
    set offset [get_property OFFSET $seg]
    puts "Segment [get_property NAME $seg]: offset=$offset range=$range"

    # Confirm alignment: offset must be a multiple of range.
    if {[expr {$offset % $range}] != 0} {
        puts "WARNING: $seg offset $offset is not aligned to range $range"
    }
}

# validate_bd_design still required, but does not catch decoder-width bugs --
# a real hardware readback test sweeping the full advertised range (not just
# offset 0) is the only way to confirm the decoder matches the advertised range.
validate_bd_design
```

### Relevance to Your Project
BRAM0 (`0xA0000000`) and BRAM2 (`0xA0010000`) with 64KB ranges both satisfy alignment by construction, so the alignment risk is low today. The actionable new item is the decoder-width bug class: since this can pass `validate_bd_design` and only manifest as silent wraparound at runtime, it's worth having `main.c`'s test pattern sweep addresses near the top of each 64KB range (not just a handful of low offsets) at least once to positively confirm the full range is real and not silently aliased.

## Vivado TCL Scripting
### Key Findings
- Non-project (in-memory) mode has no implicit checkpointing — anything not explicitly written via `save_bd_design`, `write_checkpoint`, or similar is lost if the Tcl interpreter session ends, making `create_bd.tcl`'s discipline of validate-then-save checkpoints the correct pattern, not an optional nicety.
- `connect_bd_intf_net` is exclusively for bundled interface pins (AXI4/AXI4-Lite, `BRAM_PORTA`/`PORTB`); real-world example scripts (Digilent's `vivado-hierarchies` repo, Xilinx's own `revCtrl` repo) consistently use a `foreach` pattern like `foreach a {A B} { connect_bd_intf_net [get_bd_intf_pins $ctrl/BRAM_PORT$a] [get_bd_intf_pins $bmg/BRAM_PORT$a] }` when a controller exposes multiple BRAM-side ports — useful boilerplate if this project's BMG instances are ever reconfigured to expose both PORTA and PORTB.
- `write_project_tcl -force recreate.tcl` is a real, supported way to regenerate a full project-recreation script from an existing GUI-built project — useful as a cross-check: running this against a known-good `kv260_claude` Vivado project and diffing the output against the maintained `create_bd.tcl` would surface any drift between what's hand-scripted and what the GUI/IP defaults actually produce.
- Best-practice guidance (MicroZed Chronicles, multiple sources) continues to recommend sketching the block design topology before scripting it and simulating each module independently before wiring — process advice rather than a tooling gotcha, but relevant if a third peripheral is ever added to this project's two-BRAM topology, since debugging a TCL-scripted three-way address map from scratch is harder than verifying each piece first.
- Tcl Batch Mode (`vivado -mode batch -source script.tcl`) differs from interactive Tcl mode in that it exits automatically on script completion and is the correct mode for CI/headless regeneration of this project's block design — interactive/GUI-launched Tcl console sessions are for development/exploration of the script, not for the final repeatable build path.

### Code Example
```tcl
# foreach-based dual-port BRAM_PORT connection pattern (from Digilent/Xilinx
# reference scripts) -- only needed if a BMG instance is reconfigured to
# expose BRAM_PORTA and BRAM_PORTB rather than this project's current
# single-port-per-controller topology.

set axiCtrlName "axi_bram_ctrl_0"
set bmgName     "blk_mem_gen_0"

foreach a {A} {
    connect_bd_intf_net \
        [get_bd_intf_pins $axiCtrlName/BRAM_PORT$a] \
        [get_bd_intf_pins $bmgName/BRAM_PORT$a]
}

# Headless/CI-correct invocation for regenerating this project's block design:
#   vivado -mode batch -source create_bd.tcl -log create_bd.log -journal create_bd.jou
```

### Relevance to Your Project
`create_bd.tcl`'s existing single-port-per-controller, validate-then-save pattern already matches the documented best practice for non-project mode. The one concrete action worth taking: run `write_project_tcl -force recreate.tcl` against the project's current Vivado-GUI state (if one exists) and diff it against `create_bd.tcl` to catch any drift between the hand-maintained script and what Vivado's own defaults would generate — a cheap, mechanical way to catch silent IP-version or property drift before it causes a hard-to-debug regeneration failure.

## Vitis Bare-Metal / Standalone
### Key Findings
- Vitis Unified IDE's platform-then-application component model is strict about build order: if the platform component's initial build hasn't been run before an application component build is attempted, the application build fails with a non-descriptive error rather than a clear "platform not built" message — worth knowing if a future fresh-checkout build of this project's Vitis workspace fails mysteriously on first try.
- The standalone BSP's default stdin/stdout is UART0 — confirmed again this round; `xil_printf`'s PASS/FAIL output in `main.c` relies on this default holding, so if the platform/BSP is ever regenerated from a re-exported XSA, re-confirm UART0 is still the assigned stdout console rather than assuming it carries over automatically.
- Zynq UltraScale+'s GIC offsets interrupt IDs by 32 relative to the raw IRQ number space (the well-known "IRQ - 32" GIC-vs-SPI numbering offset) — not relevant to this project's current polled, interrupt-free BRAM read/write loop, but the first thing to get wrong if a timer or AXI interrupt controller is ever added to trigger PL-to-PS interrupts.
- Confirmed again: `XScuGic_Enable(&ScuGic, <interrupt_id>)` is the final step in standalone GIC bring-up, following `XScuGic_LookupConfig` → `XScuGic_CfgInitialize` → `XScuGic_SetPriorityTriggerType` → `XScuGic_Connect` → `XScuGic_Enable` — this project's current polled-PASS/FAIL design has no need for any of this sequence, since there are no PL-to-PS interrupt sources in the BRAM-only topology.
- Linker script base-address correctness is something that has to be manually verified, not assumed: Vitis documentation explicitly directs users to open the generated linker script in a text editor and confirm the memory region base address matches the actual hardware map — this is consistent with the previously-flagged `lscript.ld` vector-placement bug class and reinforces that the linker script should be spot-checked after every XSA re-import, not just trusted.

### Code Example
```c
#include "xil_printf.h"
#include "xparameters.h"
#include "xil_io.h"

/* Sweep test near the top of each BRAM's advertised 64KB range, not just
 * offset 0 -- defends against the address-decoder-width class of bug
 * (silent wraparound past the true usable range) flagged in the Vivado
 * IP Integrator section above. */
#define BRAM0_BASEADDR XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR /* 0xA0000000 */
#define BRAM_RANGE_BYTES 0x10000U /* 64KB advertised range */

int sweep_bram_range(u32 base, const char *name) {
    u32 offsets[] = {0x0, 0x4, 0x1000, 0x8000, BRAM_RANGE_BYTES - 0x4};
    int fail = 0;
    for (int i = 0; i < sizeof(offsets)/sizeof(offsets[0]); i++) {
        u32 pattern = 0xA5A50000U | (u32)i;
        Xil_Out32(base + offsets[i], pattern);
        u32 readback = Xil_In32(base + offsets[i]);
        if (readback != pattern) {
            xil_printf("%s @0x%08x: FAIL (wrote 0x%08x, read 0x%08x)\r\n",
                       name, offsets[i], pattern, readback);
            fail = 1;
        } else {
            xil_printf("%s @0x%08x: PASS\r\n", name, offsets[i]);
        }
    }
    return fail;
}
```

### Relevance to Your Project
This extends the existing write/readback/PASS-FAIL idiom in `main.c` to cover near-top-of-range offsets, directly testing the address-decoder-width bug class surfaced in this digest's Vivado IP Integrator section — a quick addition that would catch a silent address-decoder truncation that `validate_bd_design` cannot detect. The platform-build-order and stdout-console items are worth a one-time sanity check the next time the Vitis workspace is rebuilt from a fresh XSA export, since both fail silently/non-descriptively rather than with an obvious error pointing at the root cause.

## XDC Timing Constraints
### Key Findings
- Reconfirmed: `create_clock` must never be applied to MMCM/PLL or PS-generated clock output pins (including `pl_clk0`) — Vivado auto-derives the generated-clock constraint from the upstream clock source the moment the block design's clock network is connected; a manual `create_clock` override on such a pin doesn't error, it silently replaces the accurate auto-derived waveform with a user-specified one that may not match the actual configuration, corrupting timing analysis without any warning.
- `create_clock` should be reserved for primary clock inputs only — i.e., ports where a clock enters the FPGA from an external oscillator. For this project, that means the design has effectively zero need for a hand-written `create_clock` anywhere in its XDC, since `pl_clk0` (PS-derived) is auto-constrained and there's no other clock source in a PS-only AXI-to-BRAM design.
- The official Kria platform reference designs (e.g. the KD240 board's `pin_timing.xdc` in the `Xilinx/kria-vitis-platforms` repo) use `set_clock_groups -asynchronous` for genuinely independent clock domains (e.g. Ethernet RGMII TX clock vs. fabric clock) — a useful concrete reference pattern if this project's UART or any future PL peripheral is ever clocked from a domain independent of `pl_clk0`.
- `set_input_delay`/`set_output_delay` constraints in real Kria/Zynq reference XDC files are applied specifically to high-speed board-level interfaces like RGMII Ethernet, with explicit `-clock`, `-max`, `-min`, and `-add_delay` parameters referencing the interface's own clock — reinforcing that these constraints exist to describe external device timing relative to a board-level clock, not internal PS-to-PL AXI signal timing (which is already covered by the standard synchronous timing analysis once `pl_clk0` is correctly constrained via the PS IP).
- The Kria K26 SOM Carrier Card Design Guide (UG1091) is the canonical source for any board-level pin timing this project might eventually need (e.g. if a PMOD or RPi-header peripheral is added) — worth keeping on hand as a reference rather than guessing at I/O standard or delay values for any new board-level signal.

### Code Example
```tcl
# This project's complete XDC clock-constraint need, given a PS-only AXI/BRAM
# design with no PL-side oscillator: nothing. pl_clk0 is auto-constrained by
# the PS IP's own generated .xdc the moment "PL Fabric Clocks" is enabled.
#
# DO NOT do this -- it silently overrides the correct auto-derived constraint:
#   create_clock -period 10.000 -name pl_clk0 [get_pins zynq_ultra_ps_e_0/pl_clk0]
#
# If a future PL peripheral introduces an independent clock domain (e.g. a
# PMOD-driven external oscillator), follow the Kria reference pattern:
create_clock -period 8.000 -name pmod_clk [get_ports pmod_clk_p]
set_clock_groups -asynchronous \
    -group [get_clocks pl_clk0] \
    -group [get_clocks pmod_clk]

# Board-level I/O delay only applies to signals that actually leave the FPGA
# pin to an external device -- e.g. a future PMOD/RPi-header peripheral,
# referenced against UG1091's pin-timing guidance:
set_input_delay -clock pmod_clk -max 2.0 [get_ports pmod_data_in]
set_input_delay -clock pmod_clk -min 0.5 [get_ports pmod_data_in]
```

### Relevance to Your Project
Confirms, again, that `kv260_top.vhd`'s XDC needs are essentially limited to the USB-UART pins, with zero legitimate use for a hand-written `create_clock` anywhere in the design. The Kria reference XDC patterns (`set_clock_groups`, `set_input_delay`/`set_output_delay`) become relevant only the day a PL-side peripheral with its own clock or board-level I/O timing requirement (PMOD, RPi header, external oscillator) is added — not applicable to the current PS-only AXI-to-BRAM topology.

## Kria KV260 / K26 SoM
### Key Findings
- The Kria Starter Kit's prebuilt boot firmware maintains two user partitions ("A" and "B"), with an Image Selector application controlling which one is active at boot — bare-metal applications are loaded into one of these user partitions and booted via the default QSPI32 boot mode, which is a more structured mechanism than just "flash a raw BOOT.BIN," and worth understanding if this project's deployment path ever moves from JTAG-tethered iteration to a flashed, untethered boot.
- A documented, repeatable XSCT JTAG boot-mode override sequence exists: connect to the target via XSCT, use `ta` to enumerate available targets (PSU, RPU/Cortex-R5, APU/Cortex-A53), update the multiboot register to 0, switch boot mode to JTAG, then issue a system reset — this is the scripted equivalent of the manual `rst -processor`/`dow`/`con` loop covered previously, useful if the boot-mode override needs to be automated rather than done interactively each session.
- The K26/K24 board file's MIO configuration is fixed by the SOM hardware design itself, not freely reconfigurable per-project — `kv260_som` board file selection in `create_bd.tcl` locks in MIO assignments that match the physical SOM, and any attempt to reassign MIO pins inconsistent with the board file risks a PS configuration that doesn't match the actual silicon-to-carrier wiring.
- Newer Kria boot firmware (2026.1+) has a forward compatibility requirement: WIC (Wic disk image) images require boot firmware released with 2026.1 or later, and earlier boot firmware is explicitly incompatible — not directly relevant to this project's bare-metal-only (non-WIC, non-Linux-image) flow today, but worth tracking if the project's KV260 board firmware is ever updated for other reasons, since a firmware bump could have downstream compatibility implications for the boot flow.
- PMODs and the Raspberry Pi header on Kria carrier boards route through the K26's programmable logic (PL) fabric, not the PS MIO/EMIO pins that most other on-SOM peripherals use — relevant context if this project is ever extended with a carrier-board PMOD/RPi-header peripheral, since that would be a PL-side I/O addition (with its own XDC pin constraints) rather than a PS-side MIO/EMIO reconfiguration.

### Code Example
```tcl
# xsct - scripted JTAG boot-mode override (vs. interactive single-shot use),
# useful for automating repeated bare-metal iteration cycles on the KV260
# Starter Kit without touching the carrier card's physical boot-mode straps.
connect
set psu_target [lindex [ta -t {PSU}] 0]
targets -set $psu_target

# Update multiboot register to 0 (boot from the start of QSPI image).
mwr 0xFFCA0010 0x0

# Switch boot mode to JTAG (boot mode register), then reset.
mwr 0xFFCA0200 0x0800
rst -system
```

### Relevance to Your Project
The two-partition (A/B) Image Selector mechanism is the structured alternative to manually repackaging `BOOT.BIN` every iteration if this project's bare-metal app is ever flashed for untethered boot rather than JTAG-driven development — worth a look if cold-boot (non-JTAG-tethered) demoing becomes a goal. Otherwise, the project's existing JTAG/XSCT-tethered iteration loop remains the right approach for active development, and the board-file-locked MIO configuration confirms `create_bd.tcl`'s use of the official `kv260_som` board file (rather than hand-specified PS config) is the only correct way to keep the PS config consistent with the physical SOM.

## AMD/Xilinx Tool Updates
### Key Findings
- AMD has now directly, publicly confirmed (via its own adaptive support forum, in response to "Why is Vivado 2026.1 Dropping Linux Support for Free Tier?") that the free BASIC tier in 2026.1 requires Windows, and Linux support requires the paid CORE tier (~$1,200–$1,800/year) — this moves the story from "reported by Tom's Hardware/community" (as of the prior digest) to "confirmed directly by AMD," removing prior ambiguity.
- New, concrete detail this round: **existing Linux-licensed Vivado installations (e.g. 2025.2 Standard Edition) will continue to function past 2026.1, but official support — bug fixes and updates — for free Linux users is cut off after the 2026.3 release.** This gives this project's Linux-Vivado-2025.1 workflow a hard external deadline to plan around: either migrate to a paid CORE license, switch the build host to Windows, or accept running an unsupported/frozen toolchain version past 2026.3.
- AMD's stated rationale (per its own forum response) is that ~70% of Vivado's customer base is on Windows, and the company says it is not planning to drop Windows support — this framing has drawn significant community criticism (Slashdot, It's FOSS, Hacker News per secondary reporting) from academic/hobbyist/open-source users who are disproportionately Linux-based, but does not change the practical guidance: budget for either a CORE license or a Windows build host before the 2026.3 support cutoff if staying on AMD's officially supported toolchain matters.
- Vivado 2025.2 IP release notes (Answer Record 000039903) document the AXI Switch/SmartConnect ultra-low-area `STRATEGY` mode and the deprecated `axi_interconnect` → `smartconnect` IP swap in UltraScale example designs — reconfirms last round's finding; still not relevant to this project's existing topology, but the `axi_interconnect`-to-`smartconnect` deprecation is the thing to watch if a third differently-typed peripheral is ever added and an older example/template still references `axi_interconnect`.
- The 2025.2 IP configuration file format change (XML → JSON) is documented in the same release notes; reconfirms last round's caution that any hand-written TCL parsing `.xci`-adjacent config files via text/regex (rather than `get_property`/`report_property`) needs review before any future bump past 2025.1.
