# FPGA Research Digest - 2026-08-08

## Executive Summary

- **AXI-Lite deadlock risk**: A slave that waits for `WVALID` before asserting `AWREADY` creates a protocol deadlock; your BRAM controller must accept write-address independently of write-data to be spec-compliant.
- **Backpressure gap**: When the PS holds `BREADY` low to stall responses, the slave **must** also pull `AWREADY`/`WREADY` low — easy to miss in simulation-only testing and a known Xilinx demo-core bug.
- **KV260 UART BSP pitfall**: The default standalone BSP UART selection is often wrong for the USB-UART path; you must explicitly set `STDIN`/`STDOUT` to `psu_uart_1` (or whichever MIO UART the USB bridge connects to) or `xil_printf` output will be silently dropped.
- **Vivado 2025.2 AXI SmartConnect**: New `STRATEGY` parameter adds an ultra-low-area mode — useful if your block design grows beyond two BRAMs and fabric congestion becomes an issue.
- **XSA export TCL**: Use `write_hw_platform -include_bit -force -file <name>.xsa` after `generate_target all [get_files *.bd]`; missing the `generate_target` step is the most common reason Vitis can't find the correct AXI address map.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- A transfer completes when **both** VALID and READY are High on the **rising clock edge**; all AXI signals are sampled at the rising edge, and all changes must occur after it.
- **VALID must never depend on READY**: a source (master) must not wait for the destination to assert Ready before asserting Valid. Violating this creates a deadlock between master and slave.
- **READY may depend on VALID**: a slave is allowed to wait for Valid before asserting Ready, though asserting Ready unconditionally (early) improves throughput.
- **Backpressure propagation**: if the PS holds `BREADY` low (stalling write responses), a correct AXI-Lite slave must also deassert `AWREADY` and `WREADY`. This is the most commonly missed edge case and is what causes hard-to-reproduce FPGA hangs.
- **Write-channel deadlock**: a slave that waits for `WVALID` before asserting `AWREADY` (or vice-versa) can deadlock with a master that holds both valid signals simultaneously. The AXI-Lite BRAM controller must accept write-address and write-data independently.
- `WVALID`, `WREADY`, and `BVALID` can all be high in the same cycle, but only for **different** in-flight transactions, not the same one.
- AMD's `XPM_FIFO_AXIL` parameterized macro (UG974, 2025.2) provides a verified AXI-Lite FIFO for bridging between clock domains when extending the design beyond a single AXI-Lite slave.

### Code Example

```vhdl
-- Minimal AXI-Lite slave write handshake (safe: accepts AW and W independently)
process(s_axi_aclk)
begin
  if rising_edge(s_axi_aclk) then
    if s_axi_aresetn = '0' then
      aw_active <= '0';
      w_active  <= '0';
    else
      -- Accept address channel independently
      if s_axi_awvalid = '1' and aw_active = '0' then
        aw_addr  <= s_axi_awaddr;
        aw_active <= '1';
      end if;
      -- Accept write-data channel independently
      if s_axi_wvalid = '1' and w_active = '0' then
        w_data   <= s_axi_wdata;
        w_strb   <= s_axi_wstrb;
        w_active <= '1';
      end if;
      -- Commit to BRAM only when both captured
      if aw_active = '1' and w_active = '1' then
        bram_we   <= w_strb;
        bram_addr <= aw_addr(ADDR_BITS-1 downto 2);
        bram_din  <= w_data;
        aw_active <= '0';
        w_active  <= '0';
        b_pending <= '1';
      end if;
      -- Send write response
      if s_axi_bready = '1' and b_pending = '1' then
        b_pending <= '0';
      end if;
    end if;
  end if;
end process;

s_axi_awready <= not aw_active;   -- accept address any time we don't already have one
s_axi_wready  <= not w_active;    -- accept data any time we don't already have it
s_axi_bvalid  <= b_pending;
s_axi_bresp   <= "00";            -- OKAY
```

### Relevance to Your Project

Your design writes to BRAM0 (`0xA0000000`) and BRAM2 (`0xA0010000`) from the Cortex-A53. If the Xilinx AXI BRAM Controller IP is used (as generated by IP Integrator), it handles these rules correctly. However, if you ever replace or extend the controller with custom VHDL (e.g., in `kv260_top.vhd`), the independent accept pattern above is mandatory. The backpressure rule is particularly relevant: a PASS/FAIL test that relies on polling a response that was silently stalled will hang indefinitely.

## Vivado Block Design / IP Integrator

### Key Findings

- **`create_bd_design`** is the TCL equivalent of "Create Block Design" in the GUI; all subsequent `create_bd_cell` / `connect_bd_net` calls build the design in-memory.
- **Connection Automation**: after adding a Zynq PS IP, right-click → "Run Connection Automation" applies preset board-file pin assignments (DDR, fixed IO) and can auto-connect AXI GP ports to interconnects.
- **Address Editor**: the IP Integrator assigns AXI memory maps automatically; the Address Editor (or `assign_bd_address` / `set_property offset/range` TCL commands) lets you override the base address — critical for matching your C bare-metal `#define` addresses.
- **`regenerate_bd_layout`** (UG835, 2025.2): cleans up visual clutter after scripted modifications without altering connectivity — run it after any scripted `connect_bd_net` session.
- **`apply_board_connection`**: applies board-file-defined interface presets (e.g., UART, DDR) to an IP cell; saves manually wiring MIO constraints.
- **Version portability warning**: exported block-design TCL (`write_bd_tcl`) frequently breaks when re-imported into a different Vivado version; AMD continuously changes internal IP parameter names between releases.
- In **non-project mode**, you must call `open_bd_design` and `close_bd_design` explicitly, and manage output products (DCP, synthesis runs) yourself.

### Code Example

```tcl
# Minimal block design recreation script (non-project mode safe)
create_bd_design "design_1"
open_bd_design [get_bd_designs design_1]

# Add Zynq UltraScale+ MPSoC PS
create_bd_cell -type ip -vlnv xilinx.com:ip:zynq_ultra_ps_e:3.5 zynq_ultra_ps_e_0
apply_bd_automation -rule xilinx.com:bd_rule:zynq_ultra_ps_e \
  -config {apply_board_preset "1"} [get_bd_cells zynq_ultra_ps_e_0]

# Add AXI BRAM Controller
create_bd_cell -type ip -vlnv xilinx.com:ip:axi_bram_ctrl:4.1 axi_bram_ctrl_0
set_property -dict {CONFIG.SINGLE_PORT_BRAM {1}} [get_bd_cells axi_bram_ctrl_0]

# Add Block Memory Generator
create_bd_cell -type ip -vlnv xilinx.com:ip:blk_mem_gen:8.4 blk_mem_gen_0

# Connect BRAM controller to Block Memory Generator
apply_bd_automation -rule xilinx.com:bd_rule:bram_cntlr \
  -config {BRAM "Auto"} [get_bd_intf_pins axi_bram_ctrl_0/BRAM_PORTA]

# Connect AXI SmartConnect between PS and BRAM controllers
create_bd_cell -type ip -vlnv xilinx.com:ip:smartconnect:1.0 smartconnect_0
set_property CONFIG.NUM_SI {1} [get_bd_cells smartconnect_0]
connect_bd_intf_net [get_bd_intf_pins zynq_ultra_ps_e_0/M_AXI_HPM0_LPD] \
  [get_bd_intf_pins smartconnect_0/S00_AXI]
connect_bd_intf_net [get_bd_intf_pins smartconnect_0/M00_AXI] \
  [get_bd_intf_pins axi_bram_ctrl_0/S_AXI]

# Set addresses
assign_bd_address
set_property offset 0xA0000000 [get_bd_addr_segs \
  {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property range 64K [get_bd_addr_segs \
  {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]

validate_bd_design
regenerate_bd_layout
save_bd_design
```

### Relevance to Your Project

Your `create_bd.tcl` script directly maps to this pattern. The `assign_bd_address` → explicit `set_property offset` sequence is what sets BRAM0 to `0xA0000000` and BRAM2 to `0xA0010000`. If those addresses ever drift (e.g., after an IP upgrade regenerates the design), the C `#define` constants in `main.c` will point at unmapped memory and the test will silently fail or hang.

## Vivado TCL Scripting

### Key Findings

- **Non-project mode workflow**: read sources → synthesize → implement → write bitstream, all driven by TCL with no `.xpr` project file; you own checkpoints (`write_checkpoint`) and reports (`report_timing_summary`) explicitly.
- **Key XSA export sequence**: `generate_target all [get_files *.bd]` must precede `write_hw_platform`; skipping it is the #1 reason Vitis can't locate the correct AXI memory map in the exported platform.
- **Platform intent properties**: setting `platform.design_intent.embedded "true"` and `platform.default_output_type "sd_card"` on the project before `write_hw_platform` controls how Vitis surfaces the platform in the domain wizard.
- **IP Integrator TCL extension**: each IP can supply a TCL automation callback (`bd_rule`) that IP Integrator invokes for parameter propagation — this is how `apply_bd_automation` knows what clock to wire to which port.
- **`write_bd_tcl` portability**: exported block-design scripts often require manual editing when migrating between Vivado versions because AMD changes IP VLNV strings and parameter names frequently.
- **Batch mode**: invoke `vivado -mode batch -source script.tcl` for CI-friendly flows; use `-tclargs` to pass variables (board part, output directory) without modifying the script.

### Code Example

```tcl
#!/usr/bin/env tclsh
# Non-project mode: synthesize + implement + export XSA

# 1. Open project or read sources
open_project ./kv260_project/kv260_project.xpr
# OR in non-project mode:
# read_vhdl    [glob ./vhdl/*.vhd]
# read_xdc     [glob ./constraints/*.xdc]
# read_bd      ./bd/design_1/design_1.bd

# 2. Synthesis
launch_runs synth_1 -jobs 8
wait_on_run synth_1

# 3. Implementation
launch_runs impl_1 -to_step write_bitstream -jobs 8
wait_on_run impl_1

# 4. Generate output products for the block design
open_run impl_1
generate_target all [get_files *.bd]

# 5. Export XSA for Vitis
set_property platform.design_intent.embedded "true"      [current_project]
set_property platform.design_intent.server_managed "false" [current_project]
set_property platform.default_output_type "sd_card"      [current_project]

write_hw_platform \
  -include_bit \
  -force \
  -file ./output/kv260_design.xsa

puts "XSA written to ./output/kv260_design.xsa"
```

### Relevance to Your Project

Your TCL scripts automate the Vivado portion of the flow. The critical insight is that `generate_target all` must run before `write_hw_platform` — if your `create_bd.tcl` ends at `save_bd_design` without generating targets, a downstream Vitis run will import an XSA that has no address-map data and the BSP linker script will be incorrect.

## Vitis Bare-Metal / Standalone

### Key Findings

- **UART selection**: the standalone BSP `STDIN`/`STDOUT` default is often `psu_uart_0`, which maps to the MIO UART connected to the PS console, not the USB-UART bridge (typically `psu_uart_1` on KV260). If `xil_printf` produces no output, check BSP settings → `standalone` → `stdin`/`stdout` and flip to the correct UART instance.
- **`xil_printf` limitations**: does **not** interpret `\n` as a newline in ANSI C style (use `\r\n` for terminal line endings); does **not** support `%f` floating-point formatting. Use `printf` from the full C library if floating-point output is needed, at the cost of increased BSP code size.
- **Standalone domain first**: in Vitis 2025.1, a standalone domain (`standalone_domain`) must be created before the application project can be added; this changed from the older "application wizard creates domain implicitly" behavior.
- **BSP regeneration**: after any change to the XSA (e.g., re-synthesized design with different IP), you must regenerate the BSP (`vitis -s regenerate_bsp.py` or via GUI "Update Hardware") to pick up new peripheral base addresses.
- **Interrupt controller**: the AXI Interrupt Controller (axi_intc) IP is not required for simple polling-based AXI-BRAM access, but is needed for interrupt-driven operation; configure it via the `XScuGic` (GIC) driver in the BSP for Zynq UltraScale+ targets.
- **QSPI persistence**: bare-metal applications loaded over JTAG are lost on power cycle; boot from QSPI flash (pre-programmed via `program_flash` in XSCT) for persistent execution.

### Code Example

```c
#include "xil_printf.h"
#include "xparameters.h"

/* Base addresses match the Address Editor in IP Integrator */
#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL
#define BRAM_SIZE   0x10000UL   /* 64 KB each */

static inline void bram_write32(uintptr_t base, uint32_t offset, uint32_t val)
{
    *(volatile uint32_t *)(base + offset) = val;
    /* Memory barrier: ensure write completes before read-back */
    __asm__ volatile("dmb sy" ::: "memory");
}

static inline uint32_t bram_read32(uintptr_t base, uint32_t offset)
{
    return *(volatile uint32_t *)(base + offset);
}

int main(void)
{
    uint32_t pattern = 0xDEADBEEF;
    int pass = 1;

    /* Write pattern to BRAM0 */
    bram_write32(BRAM0_BASE, 0x00, pattern);
    bram_write32(BRAM0_BASE, 0x04, ~pattern);

    /* Read back and verify */
    if (bram_read32(BRAM0_BASE, 0x00) != pattern)  { pass = 0; }
    if (bram_read32(BRAM0_BASE, 0x04) != ~pattern) { pass = 0; }

    /* Use \r\n for correct terminal rendering with xil_printf */
    xil_printf("BRAM0 test: %s\r\n", pass ? "PASS" : "FAIL");
    return 0;
}
```

### Relevance to Your Project

This is the core of your `main.c` flow. Two practical notes: (1) the `dmb sy` barrier between write and read-back prevents the Cortex-A53 out-of-order store buffer from returning a stale cached value instead of the actual BRAM contents; (2) `\r\n` instead of `\n` is required for your USB-UART terminal to display correctly with `xil_printf`.

## XDC Timing Constraints

### Key Findings

- **Two-file Kria convention**: Kria designs use two XDC files — a carrier-card XDC that maps signal names to Kria SOM connector pins, and a device XDC that maps those connector pins to Zynq UltraScale+ package balls. Keep them separate to make carrier-board swaps easier.
- **`set_input_delay` syntax** (UG835 2025.1): specifies the external path delay on a primary input port relative to a clock edge at the interface; values are in nanoseconds and can be positive or negative depending on clock/data phase relationship.
- **`set_output_delay` syntax** (UG835 2025.1): analogous for output ports — sets the time after the capturing clock edge that data must be stable at the output pin.
- **Timing Constraints Wizard**: available in Vivado IDE under Constraints; provides timing diagrams and auto-generates `set_input_delay`/`set_output_delay` templates — preferable to hand-editing XDC for new peripheral interfaces.
- **AXI-BRAM is PS-internal**: for a pure PS-to-PL AXI connection via HP/GP ports, the timing between PS and PL is handled by the Zynq UltraScale+ PS IP's internal timing model; you typically do **not** need `set_input_delay`/`set_output_delay` on the AXI signals themselves.
- **`create_clock` is still required** for any user-defined PL clock (e.g., an external oscillator routed through the PL); PS-generated clocks (from `clk_wiz` driven by `pl_clk0`) are automatically constrained by the Zynq PS IP.
- **False paths**: use `set_false_path` for asynchronous resets crossing from PS to PL; a CDC reset that isn't false-pathed will generate spurious timing violations.

### Code Example

```tcl
# kv260_pl.xdc - PL-side constraints for KV260 AXI-BRAM design

# PS-generated PL clock is auto-constrained by Zynq PS IP;
# only needed if you have an external oscillator entering the PL directly.
# create_clock -period 10.000 -name pl_clk0 [get_ports pl_clk0_0]

# Async reset from PS: declare false path to avoid CDC timing violations
set_false_path -from [get_pins zynq_ultra_ps_e_0/pl_resetn0] \
               -to   [all_registers]

# Example: user LED output (if connected to PL GPIO)
# Assume 10 ns clock period (100 MHz pl_clk0)
# set_output_delay -clock [get_clocks pl_clk0] -max 2.0 [get_ports led_0]
# set_output_delay -clock [get_clocks pl_clk0] -min -0.5 [get_ports led_0]

# Example: external button input
# set_input_delay -clock [get_clocks pl_clk0] -max 3.0 [get_ports btn_0]
# set_input_delay -clock [get_clocks pl_clk0] -min 0.5 [get_ports btn_0]

# Clock groups: prevent timing analysis between unrelated clock domains
# (Only needed if design has multiple independent clocks)
# set_clock_groups -asynchronous \
#   -group [get_clocks pl_clk0] \
#   -group [get_clocks clk_100mhz_ext]
```

### Relevance to Your Project

For the current bare-metal AXI-BRAM demo (pure PS-to-PL over AXI GP/HP, single clock), the timing constraint burden is minimal: the Zynq PS IP handles all AXI timing, and the PS-generated `pl_clk0` is auto-constrained. The main XDC action items are: (1) declare `set_false_path` on the PS reset to suppress spurious CDC violations in the timing report, and (2) use two separate XDC files following the Kria two-file convention so future carrier-card changes don't require rewriting signal-to-ball assignments.

## Kria KV260 / K26 SoM

### Key Findings

- **Default boot mode**: Kria Starter Kits ship with QSPI32 boot mode pre-programmed in the boot-mode resistors. This boots the pre-installed Canonical Ubuntu image from QSPI flash automatically.
- **Bare-metal beyond JTAG**: JTAG/USB boot loads your ELF in RAM (volatile). For persistent power-on execution, program your bitstream + ELF into the on-board QSPI flash using `program_flash` in XSCT, then reboot.
- **Boot mode switching via XSCT**: you can override the boot mode at runtime via `connect; targets -set -nocase -filter {name =~ "PSU"}; mwr 0xFF5E0200 0x0100` to force JTAG mode for development without physically changing resistors.
- **Board files automate MIO**: the Vivado KV260 board files (installed via `xhub:install [get_xhub_objects -filter {name == "kv260-starterkit"}]`) pre-configure the Zynq PS IP MIO for DDR, QSPI, UART, and SD card — avoiding manual PS MIO configuration in the block design.
- **KV260 rev2 vs rev1**: KV260 revision 2 adds auto-focus support for IAS (Image Array Sensor) interfaces; for bare-metal AXI-BRAM work, both revisions are equivalent.
- **EMIO for PL GPIO**: MIO pins are allocated to PS peripherals; PL-accessible GPIO uses EMIO — routed through the Zynq PS IP `emio_gpio` port and constrained in XDC to physical package pins (typically on the Pmod/FMC connector on the KV260 carrier card).
- **Power domains**: the K26 SOM has two core power rails (VCCINT, VCCAUX) and PL I/O banks (VCCO) powered separately; the carrier card provides bank voltages. For the KV260 carrier, PL I/O banks default to 1.8 V (Bank 65/66) and 3.3 V (Bank 47) — set `IOSTANDARD` in XDC accordingly (e.g., `LVCMOS18` for FMC, `LVCMOS33` for Pmod).

### Code Example

```tcl
# XSCT script: connect, halt PS, load bitstream + ELF via JTAG, run
# (For development; for persistent boot, use program_flash instead)

connect

# Select the Cortex-A53 APU target
targets -set -nocase -filter {name =~ "APU*"}

# Reset the PS (does not reset PL)
rst -processor

# Load bitstream into PL
fpga -file ./output/kv260_wrapper.bit

# Now select CPU 0
targets -set -nocase -filter {name =~ "*A53*#0"}

# Load and run the bare-metal ELF
source ./scripts/ps_init.tcl    ;# Initialize DDR, PLL (generated by Vitis BSP)
dow ./output/kv260_bm.elf
con

# Monitor via UART terminal at 115200 8N1 on /dev/ttyUSB1 (USB-UART)
```

### Relevance to Your Project

This XSCT script mirrors the debug flow for your KV260 AXI-BRAM demo. The key note is `source ps_init.tcl` before `dow` — skipping PS initialization means DDR may not be configured, causing the ELF to crash before `main()` if the linker script places `.data` / `.bss` in DDR. For a BRAM-only design with a small ELF that fits in OCM (On-Chip Memory), PS init is less critical, but it is still required for DDR-based stack and heap.

## AMD/Xilinx Tool Updates (Vivado/Vitis 2025.x)

### Key Findings

- **Vivado 2025.2 highlights** (AMD What's New page):
  - Reduced physical optimization (PhysOpt) compile time — faster iteration on large designs.
  - Support for **adding RTL with NoC XPMs** directly in block designs (Versal-targeted, but signals direction for future UltraScale+ convergence).
  - Simplified AXI connections between SystemVerilog instances with **automatic wrapper creation** — reduces TCL boilerplate for mixed RTL/IP designs.
  - New **ultra-low-area mode** for AXI Switch and AXI SmartConnect IP via `STRATEGY` parameter — reduces fabric resource usage at the cost of bandwidth.
- **Vivado 2025.1 IP Change Log**: AMD Answer Record AR#000037919 lists every IP version change in 2025.1; check it before upgrading a project — IP VLNV mismatches are the #1 source of "IP is locked" errors after a tool upgrade.
- **Vitis 2025.1 BIST on KV260**: community tutorial (LogicTronix, Hackster.io) confirms the full Vivado 2025.1 → Vitis 2025.1 → KV260 bare-metal flow works; notable step is explicitly setting the platform's `design_intent` properties before XSA export.
- **Vivado for Spartan UltraScale+**: 2025.x adds Spartan UltraScale+ device support — not relevant to KV260 (Zynq UltraScale+) but signals continued investment in the UltraScale+ tool chain.
- **FPGA Developer AMI 1.18.0**: Rocky Linux 8.10 AWS AMI with Vivado/Vitis 2025.1 pre-installed — useful for cloud-based CI of the KV260 design without a local tool installation.
- **Vitis Export to Vivado Flow** (UG1701): in 2025.1, the extensible XSA format stabilised — the XSA now acts as a container linking Vivado hardware to Vitis software domains, replacing the older `.hdf` hand-off format entirely.

### Code Example

```tcl
# Vivado 2025.x: Set AXI SmartConnect to ultra-low-area mode
# (Useful if BRAM design grows and fabric LUT usage is a concern)

set_property CONFIG.STRATEGY {MinArea} \
  [get_bd_cells smartconnect_0]

# Verify the property was applied
report_property [get_bd_cells smartconnect_0] CONFIG.STRATEGY

# After any IP configuration change, regenerate output products
generate_target all [get_files *.bd]
export_ip_user_files -of_objects [get_files *.bd] -no_script -sync -force -quiet
```

```tcl
# Check for IP version mismatches after a tool upgrade (run in Tcl Console)
# Reports any IPs in the design that are out-of-date with the installed catalog
report_ip_status -name ip_status
# To upgrade all IPs to latest versions:
upgrade_ip [get_ips]
```

### Relevance to Your Project

Two immediate actions for your KV260 project if upgrading to 2025.1/2025.2: (1) run `report_ip_status` immediately after opening the project and resolve any "IP is locked" warnings before attempting synthesis; (2) verify the `write_hw_platform` includes `generate_target all` in your TCL flow — the 2025.1 extensible XSA format is stricter about requiring pre-generated output products than older tool versions.
