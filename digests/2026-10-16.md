# FPGA Research Digest - 2026-10-16

## Executive Summary

- **UART1 not UART0 on KV260**: The K26 SoM routes the console to UART1; bare-metal projects using the default UART0 will see no output — verify the `xparameters.h` value for `STDIN_BASEADDRESS`/`STDOUT_BASEADDRESS` after hardware export.
- **AXI BRAM reads must be 32-bit aligned**: Using `Xil_In32()` / `Xil_Out32()` to access the BRAM controller only works at 4-byte-aligned offsets (0, 4, 8 …); sub-word byte accesses require deliberate masking or a different driver call.
- **Vivado 2025.1 adds RTL-instantiable AXI Switch IP**: Unlike SmartConnect (block-design only), the new AXI Switch can appear directly in RTL, useful for projects that mix HDL and block design.
- **Two new IP Integrator views in 2025.1**: "Clocking and Reset" and "Interrupt and AXI-4 Lite" dedicated panels give at-a-glance wiring status for common connections, reducing the time to spot missing clock/reset hookups.
- **set_clock_groups catches silent timing failures**: Unrelated async clocks (e.g., the PS 100 MHz and any PL-generated clocks) produce false timing failures unless explicitly grouped; this is a frequent omission in bare-metal KV260 constraint files.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- **VALID must hold until READY**: Once a master or slave asserts `VALID`, it must not deassert until the receiver asserts `READY` on the same rising clock edge. Violating this causes dropped or double-sampled transactions and is the number-one bug in custom slave IP.
- **READY may be combinatorially dependent on VALID (with caution)**: The spec permits `READY` to depend on `VALID`, but creating a combinatorial loop between them can cause simulation races and synthesis warnings; drive `READY` from a register in custom slaves.
- **AXI-Lite write response (BRESP/BVALID) is mandatory**: A master must always accept `BVALID`; custom slaves that assert `BVALID` but never check whether the master has consumed it can stall the write channel permanently.
- **AXI-Lite word alignment**: `WSTRB` selects active byte lanes but the base address for each beat must be 32-bit word-aligned when the bus width is 32 bits; unaligned addresses return an error response from the BRAM controller.
- **AXI-Stream TKEEP byte qualifier**: Bit 0 of TKEEP corresponds to the LSB byte of TDATA; a deasserted bit marks a null byte that can be discarded by the receiver. For 32-bit streams TKEEP is 4 bits wide (TDATA_WIDTH / 8).

### Code Example

```c
/* Bare-metal AXI-Lite BRAM write + read-back (Vitis / standalone) */
#include "xil_io.h"
#include "xparameters.h"

#define BRAM0_BASE  XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR  /* 0xA0000000 */
#define BRAM2_BASE  XPAR_AXI_BRAM_CTRL_1_S_AXI_BASEADDR  /* 0xA0010000 */
#define PATTERN     0xDEADBEEFUL

void bram_test(u32 base, const char *name) {
    u32 i, rd;
    for (i = 0; i < 16; i++) {          /* 16 words = 64 bytes */
        Xil_Out32(base + (i * 4), PATTERN ^ i);
    }
    for (i = 0; i < 16; i++) {
        rd = Xil_In32(base + (i * 4));
        if (rd != (PATTERN ^ i)) {
            xil_printf("%s FAIL @ offset %lu: got 0x%08lX\r\n", name, i*4, rd);
            return;
        }
    }
    xil_printf("%s PASS\r\n", name);
}

int main(void) {
    bram_test(BRAM0_BASE, "BRAM0");
    bram_test(BRAM2_BASE, "BRAM2");
    return 0;
}
```

### Relevance to Your Project

The `kv260-axi-bram-demo` drives two BRAM controllers at `0xA0000000` and `0xA0010000` from the Cortex-A53. The example above mirrors that exact structure. Key guard: `Xil_Out32`/`Xil_In32` use `volatile` word stores — always 4-byte-aligned offsets, no byte arithmetic. If `XPAR_AXI_BRAM_CTRL_x_S_AXI_BASEADDR` macros are missing after hardware export, check that the AXI BRAM Controller was assigned addresses in IP Integrator's Address Editor before running `write_hw_platform`.

## Vivado Block Design / IP Integrator

### Key Findings

- **Address Editor tab only appears when a bus master is present**: If the tab is absent after opening a block design, confirm the Zynq PS (or MicroBlaze) block is present and its AXI master port is enabled.
- **Assign All vs. manual entry**: Use the "Assign All" toolbar button to auto-populate addresses, then override specific slaves by typing into the Offset Address column. Paths must be in "Assigned" state before the range field becomes editable.
- **CSV import/export for repeatable address maps**: The context menu exposes "Export Address Map" and "Import Address Map"; the Tcl equivalents are `assign_bd_address -export_to_file addr.csv` and `assign_bd_address -import_from_file addr.csv`. Useful for keeping `0xA0000000`/`0xA0010000` stable across design rebuilds.
- **2025.1 new views**: Two new side-panel views — "Clocking and Reset" and "Interrupt and AXI-4 Lite" — show wiring status at a glance. Missing clock or reset connections now surface without manually tracing wires.
- **Connection automation can mis-wire clocks**: After running "Run Connection Automation", always verify that PL IP clocks are sourced from the Zynq PS `pl_clk0` output and not left unconnected or connected to a wrong port.

### Code Example

```tcl
# Address assignment in a create_bd.tcl script
# Fix BRAM0 at 0xA0000000 and BRAM2 at 0xA0010000

assign_bd_address [get_bd_addr_segs {axi_bram_ctrl_0/S_AXI/Mem0}]
set_property offset 0xA0000000 [get_bd_addr_segs \
    {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property range 64K [get_bd_addr_segs \
    {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]

assign_bd_address [get_bd_addr_segs {axi_bram_ctrl_1/S_AXI/Mem0}]
set_property offset 0xA0010000 [get_bd_addr_segs \
    {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_1_Mem0}]
set_property range 64K [get_bd_addr_segs \
    {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_1_Mem0}]
```

### Relevance to Your Project

Your `create_bd.tcl` script maps BRAM0 at `0xA0000000` and BRAM2 at `0xA0010000`. The snippet above shows the canonical Tcl pattern to lock those addresses in script, eliminating manual re-entry whenever the block design is regenerated. Run after all IP is instantiated and before `validate_bd_design`.

## Vivado TCL Scripting

### Key Findings

- **Non-project mode = repeatable CI-friendly builds**: Run `vivado -mode tcl -source build.tcl` to execute RTL-to-bitstream in one shot without a persistent project file. All state lives in in-memory design objects; write checkpoints (`write_checkpoint`) after each stage to enable incremental restarts.
- **Implementation step order matters**: `opt_design → place_design → phys_opt_design → route_design → write_bitstream`. Skipping `phys_opt_design` is fine for timing-slack designs but disabling it without a reason leaves performance on the table.
- **Source file change after synthesis forces re-synthesis**: Non-project mode does not track dependencies; if you edit VHDL after `synth_design`, you must re-run synthesis explicitly — Vivado will not detect the staleness.
- **`get_bd_cells` / `get_bd_pins` for block design scripting**: In project mode (with an `.xpr`), open the block design with `open_bd_design` and use `get_bd_*` commands rather than hard-coding net names.
- **Strategies via `set_property`**: Apply synthesis or implementation strategies with `set_property STEPS.SYNTH_DESIGN.STRATEGY Flow_PerfOptimized_high [get_runs synth_1]` rather than editing GUI flow settings.

### Code Example

```tcl
# Minimal non-project mode build script skeleton
set output_dir ./build_output
file mkdir $output_dir

# Read design sources
read_vhdl [glob ./vhdl/*.vhd]
read_xdc ./constraints/timing.xdc

# Synthesis
synth_design -top kv260_top -part xck26-sfvc784-2LV-c
write_checkpoint -force $output_dir/post_synth.dcp
report_timing_summary -file $output_dir/post_synth_timing.rpt

# Implementation
opt_design
place_design
phys_opt_design
route_design
write_checkpoint -force $output_dir/post_route.dcp

# Reports + bitstream
report_timing_summary -file $output_dir/post_route_timing.rpt
report_utilization -file $output_dir/utilization.rpt
write_bitstream -force $output_dir/kv260_top.bit
```

### Relevance to Your Project

Your `create_bd.tcl` script currently targets project mode. Migrating the bitstream generation to non-project mode (keeping `create_bd.tcl` as a sourced block-design helper) would allow fully automated builds from CI with no Vivado GUI state to maintain.

## Vitis Bare-Metal / Standalone

### Key Findings

- **UART1 for KV260 serial console**: The K26 SoM routes the USB-UART bridge to UART1 (`MIO[40:41]`), not UART0. If `xil_printf` produces no output, check that the BSP's `stdin`/`stdout` are mapped to `psu_uart_1` in the platform component settings, not `psu_uart_0`.
- **Linker script (lscript.ld) heap default is small**: Vitis generates `lscript.ld` in the application `src/` folder. The default heap is often 256 KB; start with 1 MB (`_HEAP_SIZE = 0x100000`) and increase if `malloc` calls silently fail.
- **Standalone BSP is single-threaded, no MMU by default**: The A53 runs in EL3 (or EL1 depending on ATF), with caches and MMU disabled until explicitly enabled. For latency-sensitive AXI accesses, enable the D-cache after memory initialization to avoid slow uncached reads.
- **BSP `xparameters.h` is generated from hardware XSA**: Re-export hardware from Vivado (File → Export → Export Hardware) every time you change addresses or add IP, then update the Vitis platform to regenerate the BSP and updated `xparameters.h`.
- **`Xil_DCacheFlushRange` before DMA**: If you add DMA later, flush the D-cache range before starting a DMA transfer to ensure coherency between CPU writes and the DMA engine's view of DDR.

### Code Example

```c
/* Enable A53 D-cache for faster AXI-BRAM access pattern */
#include "xil_cache.h"
#include "xil_printf.h"

int main(void) {
    Xil_DCacheEnable();   /* Enable data cache */
    Xil_ICacheEnable();   /* Enable instruction cache */

    xil_printf("Caches enabled\r\n");

    /* ... BRAM test code ... */

    return 0;
}
```

### Relevance to Your Project

The bare-metal demo drives the AXI-BRAM controllers and prints PASS/FAIL over USB-UART. Enabling the D-cache (two lines above) can reduce the measured write→read latency for the pattern verification loop. Additionally, confirming UART1 is the BSP default explains any "no output" debug sessions.

## XDC Timing Constraints

### Key Findings

- **`set_clock_groups -asynchronous` is mandatory for multi-clock designs**: Any PL-generated clock unrelated to `pl_clk0` (e.g., a PLL-derived clock) must be placed in a separate clock group, or the timing engine reports false cross-domain failures that obscure real ones.
- **`set_input_delay` / `set_output_delay` relative to a known clock**: Reference both to a single source clock (typically `pl_clk0` for PL-side logic, or the appropriate bank reference clock for I/O). A negative input delay is valid when the data arrives before the clock edge.
- **Unconstrained ports = most common timing warning**: Ports without a `set_input_delay` or `set_output_delay` appear in the Timing Summary as "unconstrained". For the KV260 with only PS-to-PL internal AXI traffic, PL I/O pins that are NC (not connected) on the carrier board should be given `set_false_path` to suppress noise.
- **`create_clock` is required for any user-defined clock**: If a VHDL wrapper passes a clock pin, you must create a clock definition in the XDC; Vivado does not infer it from the port direction.
- **`-datapath_only` on `set_max_delay` disables hold analysis**: Use this when timing-closing an asynchronous CDC path where hold analysis is handled structurally (e.g., a synchronizer chain), not by the timing engine.

### Code Example

```xdc
# Example XDC for KV260 AXI-BRAM demo
# PS provides pl_clk0 at 100 MHz — no create_clock needed (auto-derived)

# Declare async clock groups if any secondary PL clock exists
# (e.g. if MMCM generates a 200 MHz PL clock alongside 100 MHz)
# create_clock -period 5.000 -name clk_200 [get_pins mmcm_inst/CLKOUT0]
# set_clock_groups -asynchronous \
#     -group [get_clocks -of_objects [get_pins zynq_ultra_ps_e_0/pl_clk0]] \
#     -group [get_clocks clk_200]

# Silence timing on unconnected PL I/O
set_false_path -from [get_ports *] -to [get_clocks *]
set_false_path -from [get_clocks *] -to [get_ports *]

# If external I/O is added later, replace false_path with:
# set_input_delay  -clock [get_clocks pl_clk0] -max 3.000 [get_ports ext_in]
# set_output_delay -clock [get_clocks pl_clk0] -max 3.000 [get_ports ext_out]
```

### Relevance to Your Project

The KV260 AXI-BRAM demo has no external I/O beyond what the PS provides, so `set_false_path` on unconnected ports cleans up the Timing Summary report. If you later add a second MMCM-derived clock, the `set_clock_groups` pattern above prevents spurious timing failures from masking real ones.

## Kria KV260 / K26 SoM

### Key Findings

- **No boot-mode switches**: Unlike the ZCU102 eval board, the KV260 has no physical boot-mode DIP switches. The K26 SoM is hard-wired to boot from QSPI flash. For bare-metal development, use JTAG (boot mode override via cable, or load ELF directly with `program_elf` in Vitis without writing flash).
- **UART1 is the hardware console**: The carrier board connects the FTDI USB-UART bridge to UART1 (`PS MIO[40]=TX, MIO[41]=RX`), not UART0. This is a documented difference from most Zynq UltraScale+ reference boards.
- **Two K26 SoM variants exist**: `sm-k26` (with eMMC) and `smk-k26` (without eMMC, QSPI-only firmware). Confirm which is populated before relying on eMMC boot paths.
- **MIO bank split**:
  - Bank 501: `MIO[26:30]` and `MIO[38:51]` (LVCMOS 1.8V)
  - Bank 502: `MIO[52:77]` (LVCMOS 1.8V)
  - PL I/O via HPA/HPB/HPC (1.2V/1.8V-capable) and HDA/HDB/HDC (3.3V-capable)
- **Power domain awareness**: The PL I/O banks on the KV260 carrier are split between 1.8V and 3.3V capable banks; driving 3.3V signals into an HPA bank configured for 1.2V will latch-up the device.

### Code Example

```c
/* Bare-metal UART init for KV260: target UART1, not UART0 */
/* In BSP settings: set stdio to psu_uart_1 (MIO 40/41)     */

/* After BSP regeneration, xparameters.h will contain:       */
/* #define STDIN_BASEADDRESS   0xFF010000  (UART1)           */
/* #define STDOUT_BASEADDRESS  0xFF010000  (UART1)           */

/* Verify in your main.c — if it shows 0xFF000000 (UART0),  */
/* re-export hardware and rebuild the platform.              */
#include "xil_printf.h"

int main(void) {
    xil_printf("KV260 UART1 OK\r\n");
    return 0;
}
```

### Relevance to Your Project

The USB-UART path in the `kv260-axi-bram-demo` (`PASS/FAIL` output) only works if the BSP targets UART1. If the demo generates a bitstream successfully but produces no serial output, this UART0 vs. UART1 mismatch is the first thing to check before re-examining the AXI wiring.

## AMD/Xilinx Tool Updates (2025.x)

### Key Findings

- **Vivado 2025.1: new RTL-instantiable AXI Switch IP**: A fully customizable RTL-based switch that bridges AXI interfaces of different types and widths. Crucially, unlike SmartConnect, it can be instantiated directly in RTL code, not only inside the IP Integrator block design. Useful for projects that mix RTL and block design.
- **Vivado 2025.1: two new IPI panel views**: The block design canvas gained "Clocking and Reset" and "Interrupt and AXI-4 Lite" side-panel views. These summarize clock/reset connectivity and show AXI-Lite interface hookups at a glance, reducing wiring errors on complex designs.
- **Vivado 2025.1: new device support**: Versal AI Edge Series Gen 2, Versal Prime Series Gen 2, and Spartan UltraScale+ are newly supported. No change to Zynq UltraScale+ (K26) part numbers.
- **Vivado 2025.2: ultra-low-area mode for AXI Switch and SmartConnect**: Both IPs now support a `STRATEGY` parameter selecting "ultra-low-area" mode, trading throughput for area savings. Useful for area-constrained designs where full crossbar bandwidth is not needed.
- **Open-source components 2025.1**: Linux kernel bumped to 6.12; early-access Zephyr RTOS driver support added.
- **Vitis AI 5.1 (on Vivado 2025.1.1)**: Adds multi-NPU support, mixed precision, DepthToSpace and PixelShuffle layers; Apptainer (rootless containers) replaces Docker as the preferred runtime.
- **Unified device installer**: The 2025.1 installer reduces download size through a unified package, eliminating redundant downloads of shared components across Vivado and Vitis.

### Code Example

```tcl
# Using the new AXI Switch IP in Vivado 2025.1 block design (IPI Tcl)
# Add AXI Switch with 1 master / 2 slave ports
create_bd_cell -type ip -vlnv xilinx.com:ip:axi_switch:* axi_switch_0
set_property -dict [list \
    CONFIG.NUM_MI {2} \
    CONFIG.NUM_SI {1} \
] [get_bd_cells axi_switch_0]

# Or in RTL instantiation (non-IPI flow):
# axi_switch #(
#   .NUM_SI(1), .NUM_MI(2),
#   .STRATEGY("area")        /* new in 2025.2: "area" or default */
# ) u_switch ( ... );
```

### Relevance to Your Project

The 2025.1 IPI "Clocking and Reset" view is immediately useful during initial block design setup: it surfaces unconnected `resetn` pins on the AXI BRAM Controllers, which cause the BRAM to hold reset and produce all-zero reads. This is a common first-boot failure mode. The new AXI Switch IP is relevant if you later need to fan out the PS AXI master to more than two BRAM slaves without adding a second SmartConnect instance.
