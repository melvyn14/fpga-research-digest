# FPGA Research Digest - 2026-11-20

## Executive Summary
- **AXI-Lite byte-to-word address mapping**: Drop the bottom two address bits when indexing BRAM words from AXI byte addresses. The KV260 project's main.c reads BRAM at 0xA0000000 and 0xA0010000 — confirm write addresses are word-aligned to avoid silently writing to the wrong location.
- **Vivado non-project mode requires explicit output products**: After calling `create_bd_design`, you must call `generate_target all` before adding the BD to synthesis. Skipping this step causes a hard error; the project's `create_bd.tcl` should include this call.
- **XDC constraints: always set both `-min` and `-max`**: Specifying only `-max` on `set_output_delay` leaves hold unconstrained and can let the tools shift the internal clock in a way that violates hold timing silently.
- **Vitis BSP stdout must match PS UART selection**: For the KV260, `standalone_stdin`/`standalone_stdout` in the BSP settings must both point to `psu_uart_1`; mismatches cause `xil_printf` to produce no output even when the hardware is correct.
- **Vivado 2025.2 known issues**: There is an install error where the data folder cannot be detected on some machines; also a NoC issue on Versal with partial PDI loads. Upgrade to the latest 2025.2 patch if affected.

## AXI Protocol / AXI-Lite / AXI-Stream
### Key Findings
- **VALID must stay asserted**: Once a master raises AWVALID or WVALID, it must not deassert until AWREADY/WREADY is received. Changing payload mid-handshake causes protocol violations that are hard to catch without a VIP.
- **AWREADY and WREADY can arrive in either order**: AXI-Lite slaves are allowed to accept the address before or after the write data. Designs that assume one order first will deadlock on slaves that implement the other.
- **BRAM output registers affect read latency**: Enabling the primitive output register in Block Memory Generator adds one cycle of read latency. The AXI BRAM Controller accounts for a fixed read latency; mismatching the BRAM IP setting versus the controller's expected latency causes read garbage or timeout.
- **Response channel must be consumed**: Custom slaves that drive RVALID/BVALID but don't check that the master has accepted (RREADY/BREADY) can lock up the AXI interconnect.
- **AXI-Lite does not support unaligned transfers**: The Xilinx AXI BRAM Controller explicitly drops support for unaligned AXI-Lite accesses.
- **AXI-Stream TLAST/TKEEP discipline**: TLAST must be held stable while stalled (TVALID high, TREADY low). TKEEP bits mark valid bytes in the last beat — tying TKEEP to all-ones for every beat is correct only when every beat is fully populated.

### Code Example
```c
/* Safe AXI-Lite write + read-back for 32-bit word at word address n */
#define BRAM0_BASE  0xA0000000UL
#define BRAM_WORD(n) (*((volatile uint32_t *)(BRAM0_BASE + ((n) << 2))))

static inline void bram_write(uint32_t word_idx, uint32_t val) {
    BRAM_WORD(word_idx) = val;
    /* dsb() ensures the write is flushed before the read-back */
    __asm__ volatile("dsb sy" ::: "memory");
}

static inline uint32_t bram_read(uint32_t word_idx) {
    return BRAM_WORD(word_idx);
}
```

### Relevance to Your Project
Your `main.c` writes patterns to BRAM0 at 0xA0000000 and BRAM2 at 0xA0010000. Using `(base + (index << 2))` keeps addresses word-aligned and avoids the unaligned-transfer limitation of the AXI BRAM Controller. The `dsb sy` barrier prevents out-of-order memory access on the Cortex-A53 — without it, a compiler or CPU reorder could read back stale cache data before the write reaches the PL.

## Vivado Block Design / IP Integrator
### Key Findings
- **Block design names must be ≤25 characters**: Longer names can cause issues during wrapper generation and certain TCL automation steps (from UG994 2025.1).
- **`generate_target all` is mandatory in non-project mode**: Adding a block design to a non-project flow without first generating output products causes an error at synthesis.
- **`make_wrapper` path**: After `generate_target all`, call `make_wrapper -files [get_files <bd>.bd] -top` to create a synthesizable HDL wrapper, then add the wrapper with `add_files`.
- **`write_hw_platform`** (formerly `write_dsa`): Export the XSA for Vitis with `write_hw_platform -fixed -force <name>.xsa` after `impl_design`.
- **Connection automation can mis-wire clocks**: `apply_bd_automation` is convenient but can connect clocks from the wrong source. Always inspect the generated connections in the Address Editor before running implementation.
- **`validate_bd_design`** catches unconnected ports and address conflicts before synthesis — run it in every TCL script after IP connections.

### Code Example
```tcl
# Minimal non-project block design flow for KV260 AXI-BRAM
create_project -in_memory -part xck26-sfvc784-2LV-c

# Source the block design creation script
source ./tcl/create_bd.tcl

# Generate output products (REQUIRED before synthesis)
generate_target all [get_files *.bd]

# Create HDL wrapper
set bd_files [get_files -filter {FILE_TYPE == "Block Designs"}]
make_wrapper -files $bd_files -top
add_files -norecurse [glob ./kv260.gen/sources_1/bd/*/hdl/*_wrapper.v]

# Validate before synthesis
open_bd_design [get_files *.bd]
validate_bd_design
close_bd_design [get_bd_designs]

# Synthesize
synth_design -top kv260_wrapper -part xck26-sfvc784-2LV-c
write_checkpoint -force post_synth.dcp
```

### Relevance to Your Project
Your `create_bd.tcl` should include `generate_target all` and `validate_bd_design` calls. Missing `generate_target` is the most common reason a scripted KV260 build fails at the first `synth_design` call with a cryptic "block design must be generated" error.

## Vivado TCL Scripting
### Key Findings
- **Batch mode**: Run scripts with `vivado -mode batch -source build.tcl` — interactive mode is not needed for CI/automated flows.
- **Source ordering matters**: In non-project mode, HDL files compile in the order `read_vhdl`/`read_verilog` commands appear; put packages and common files first.
- **Write checkpoints after each step**: `write_checkpoint -force post_synth.dcp` and `write_checkpoint -force post_route.dcp` let you re-open results without rerunning hours of implementation.
- **Strategy shortcuts**: `config_flows -synth_strategy "Flow_PerfOptimized_High"` applies a preset strategy rather than setting every directive individually.
- **IP checkpoints**: For IP cores with pre-synthesized `.dcp` files in their IP directory, Vivado uses those directly — this significantly speeds up iterative builds.
- **No default reports**: All reports (`report_timing_summary`, `report_utilization`, etc.) must be explicitly called; nothing is auto-generated in non-project mode.

### Code Example
```tcl
# Reusable non-project build skeleton
set part xck26-sfvc784-2LV-c
set top  kv260_wrapper

read_vhdl    [glob ./vhdl/*.vhd]
read_xdc     ./constraints/kv260.xdc
source       ./tcl/create_bd.tcl
generate_target all [get_files *.bd]
make_wrapper -files [get_files *.bd] -top
add_files -norecurse [glob ./kv260.gen/sources_1/bd/*/hdl/*.v]

synth_design -top $top -part $part
write_checkpoint -force ./checkpoints/post_synth.dcp
report_utilization -file ./reports/utilization.rpt

opt_design
place_design
route_design
write_checkpoint -force ./checkpoints/post_route.dcp
report_timing_summary -file ./reports/timing.rpt

write_hw_platform -fixed -force ./output/kv260.xsa
```

### Relevance to Your Project
Wrapping your existing `create_bd.tcl` with this skeleton gives you a reproducible one-command build: `vivado -mode batch -source build.tcl`. The checkpoint strategy means failed implementations can be resumed from `post_synth.dcp` without re-running synthesis.

## Vitis Bare-Metal / Standalone
### Key Findings
- **BSP stdout/stdin must point to `psu_uart_1`**: The KV260 routes the PS UART to the USB-UART bridge via UART1. If the BSP still shows the default `psu_uart_0`, xil_printf produces no output. Fix: in the BSP settings, change `standalone_stdin` and `standalone_stdout` to `psu_uart_1`, then click **Regenerate BSP**.
- **`xil_printf` does not support `%f`**: Floats must be split into integer and fractional parts before printing. Use `printf` from the newlib stdio library when floating-point formatting is needed, but be aware of the larger code size.
- **FSBL initialization conflict**: On some KV260 setups, leaving "Initialize using FSBL" enabled in a bare-metal application causes a hang or corrupted UART output. Disabling this option fixes the issue (confirmed on Vitis 2023.1; still relevant to 2025).
- **Linker script memory regions**: The default auto-generated `lscript.ld` maps the application to DDR. For latency-critical sections, place code or data in OCM (0xFFFC0000, 256 KB) by adding a custom memory region and assigning sections with `>ocm_ram`.
- **Interrupt controller**: To use the Zynq GIC in bare-metal, initialize with `XScuGic_CfgInitialize` and register handlers before enabling interrupts globally with `Xil_ExceptionEnable`.

### Code Example
```c
#include "xil_printf.h"
#include "xparameters.h"
#include "sleep.h"

/* Print integer + fractional parts since xil_printf has no %f */
static void print_fixed(int32_t val_milli) {
    int whole = val_milli / 1000;
    int frac  = (val_milli < 0 ? -val_milli : val_milli) % 1000;
    xil_printf("%d.%03d\r\n", whole, frac);
}

int main(void) {
    xil_printf("KV260 AXI-BRAM bare-metal test\r\n");

    volatile uint32_t *bram0 = (volatile uint32_t *)0xA0000000UL;
    volatile uint32_t *bram2 = (volatile uint32_t *)0xA0010000UL;

    for (uint32_t i = 0; i < 16; i++) {
        bram0[i] = 0xDEAD0000 | i;
        bram2[i] = 0xBEEF0000 | i;
    }

    uint32_t pass = 1;
    for (uint32_t i = 0; i < 16; i++) {
        if (bram0[i] != (0xDEAD0000 | i)) { pass = 0; }
        if (bram2[i] != (0xBEEF0000 | i)) { pass = 0; }
    }

    xil_printf("BRAM test: %s\r\n", pass ? "PASS" : "FAIL");
    return 0;
}
```

### Relevance to Your Project
This is a minimal but complete version of what your `main.c` likely implements. The key addition is the `__asm__ volatile("dsb sy")` barrier (or `Xil_DCacheFlush` if cache is enabled) between writes and reads to prevent the Cortex-A53 from reading cached values instead of BRAM contents.

## XDC Timing Constraints
### Key Findings
- **Always specify both `-min` and `-max`**: Using only `-max` on `set_output_delay` leaves hold time unconstrained. The tools may then shift the internal clock to satisfy setup while silently violating hold.
- **Account for trace/board delay**: `set_input_delay` and `set_output_delay` values should include board trace delay, not just the component datasheet values.
- **Negative `-min` output delay is correct**: The minimum output delay constraint uses a negative value because of the sign convention for hold-time analysis in SDC syntax.
- **Vendor IP can ship its own XDC**: AXI Ethernet and similar Xilinx IP cores include built-in XDC files. If you need to override these, add your constraint file with `PROCESSING_ORDER LATE` to ensure it takes precedence.
- **Clock groups prevent false paths**: Use `set_clock_groups -asynchronous` between independent clock domains (e.g., the PL design clock and an external RGMII clock) to prevent the router from trying to meet timing across unrelated domains.
- **Zynq PS clocks**: The PS generates clocks (FCLK_CLK0–3) that feed the PL. These are auto-constrained by Vivado from the block design; avoid manually re-constraining them in the XDC or you'll get duplicate constraint warnings.

### Code Example
```tcl
# kv260.xdc — timing constraints for KV260 AXI-BRAM demo

# PL design clock from PS (100 MHz from FCLK_CLK0, constrained by block design)
# Do NOT re-create this clock here — Vivado auto-generates it from the BD

# Example: external 125 MHz ref clock on PL pin (if added later)
# create_clock -period 8.000 -name clk_125 [get_ports clk_125_p]

# I/O delays for a hypothetical GPIO output with a 2 ns board trace
set_output_delay -clock [get_clocks clk_pl_0] -max  3.0 [get_ports {gpio_out[*]}]
set_output_delay -clock [get_clocks clk_pl_0] -min -1.0 [get_ports {gpio_out[*]}]

# False path to async reset (if present)
set_false_path -from [get_ports aresetn]

# Async clock group example (PL clock vs external ref)
# set_clock_groups -asynchronous \
#   -group [get_clocks clk_pl_0] \
#   -group [get_clocks clk_125]
```

### Relevance to Your Project
The KV260 AXI-BRAM demo runs entirely on the PS-generated `FCLK_CLK0`. Vivado auto-constrains this clock from the block design, so the XDC should contain primarily I/O constraints and false paths. Avoid adding a `create_clock` for the PS clock — it creates a duplicate that generates confusing critical warnings during implementation.

## Kria KV260 / K26 SoM
### Key Findings
- **Boot device is MIO-strapped**: The K26 SOM uses MODE[3:0] pins on the carrier card to select the boot source. QSPI (MIO[5:0]) holds the FSBL and U-Boot; eMMC (MIO[22:13]) holds the OS. For bare-metal JTAG development, boot mode does not matter — the debugger loads the ELF directly.
- **MIO bank voltage is 1.8V (fixed on SOM)**: All three MIO banks on the K26 run from 1.8V supplied by the SOM. External interfaces on carrier-card MIO pins must be level-shifted if driving 3.3V devices.
- **MIO[34:32] are reserved**: These pins are used by the SOM for power management. Never assign them in XDC or the board design.
- **MIO[31]/MIO[35] PMU signals**: MIO31 is a hardware-requested shutdown input to the SOM; MIO35 is an external watchdog trigger output. These must be treated as special-purpose in bare-metal designs.
- **UART1 is the USB-UART bridge**: The KV260 carrier routes PS UART1 (MIO[36:37]) through a USB-UART bridge. Bare-metal apps must configure psu_uart_1, not psu_uart_0.
- **Power domains**: The carrier card splits power into an always-on domain (5V main, management, clocking) and a PS domain (PS MIO/GTR rails). PL power is separate; ensure the PL power rail is stable before accessing PL peripherals.
- **Kria vitis-platforms targets 2026.1**: AMD's official `kria-vitis-platforms` repo now targets 2026.1 tools. If you are on 2025.1, check out the corresponding branch (`rel-v2025.1`) to get matching platform files.

### Code Example
```tcl
# XDC pin assignment snippet for KV260 (carrier card MIO-routed signals)
# UART1 — handled by PS block design, not XDC
# PL user LED example (adjust pin number for your carrier)
set_property PACKAGE_PIN  F11  [get_ports {pl_led[0]}]
set_property IOSTANDARD   LVCMOS18 [get_ports {pl_led[0]}]

# PL reset input (active low, from carrier card reset button)
set_property PACKAGE_PIN  G11  [get_ports pl_resetn]
set_property IOSTANDARD   LVCMOS18 [get_ports pl_resetn]
# DRIVE and SLEW for outputs
set_property DRIVE        4    [get_ports {pl_led[0]}]
set_property SLEW         SLOW [get_ports {pl_led[0]}]
```

### Relevance to Your Project
Your AXI-BRAM demo communicates over UART (xil_printf). Confirming `psu_uart_1` is used in both the BSP and the hardware design is the single most common fix when a KV260 bare-metal demo runs but produces no serial output. Also note that any future PL I/O additions must use LVCMOS18 on the KV260 carrier's PL pins.

## AMD/Xilinx Tool Updates (Vivado / Vitis 2025.x)
### Key Findings
- **Vivado 2025.2 IP changes**: The 100M/1G TSN Subsystem v3.0 Rev. 2 added Spartan UltraScale+ support and hardware support for multiple PTP domains, plus several bug fixes including an RTC timer fix.
- **Vitis HLS 2025.2**: Performance pragma now uses trip counts from C simulation for optimization. New features include fractional-rate SSR for FIR/FFT, ECC for dataflow buffers, multi-port M-AXI cache, and auto-restart in CSIM/CoSim.
- **Vitis 2025.2 platform**: New data types (block floating-point MX6/MX4, emulated cbfloat16), cumulative sum and Euclidean distance functions, and a new "Integration Project" component.
- **Known issues (2025.2)**:
  - Install error where the data folder cannot be detected on some machines.
  - Dynamic Function eXchange NoC issue: partial PDI loads fail when NPI Shutdown Fix is enabled (Versal only).
  - Versal HDIO IOBUFDS_DIFF_OUT placement error when TM and TS signals are connected.
  - Design advisory for Spartan UltraScale+ speed files requiring update.
- **Vivado 2026.1 is now current**: As of November 2026, AMD has released Vivado/Vitis 2026.1. If you stay on 2025.1 for stability, pin your environment and check that `kria-vitis-platforms` branch `rel-v2025.1` is used for platform files.
- **AXI BRAM Controller product guide**: Check AMD PG058 for the current IP version shipped with your tool; the BRAM output register latency setting changed between some tool releases.

### Code Example
```tcl
# Check Vivado version at build time and warn if not 2025.1
set vivado_ver [version -short]
if {[string compare $vivado_ver "2025.1"] != 0} {
    puts "WARNING: Expected Vivado 2025.1, got $vivado_ver"
    puts "         Check kria-vitis-platforms branch compatibility"
}

# Pin IP to known-good versions to avoid unexpected changes on upgrade
set_property ip_repo_paths [list ./ip_repo] [current_project]
update_ip_catalog -rebuild
```

### Relevance to Your Project
Your project is locked to Vivado/Vitis 2025.1. The version check above, added to the top of your build TCL, will catch accidental upgrades in a CI environment. Also check that the AXI BRAM Controller version in your block design matches PG058 for 2025.1 — the IP changelog may list fixes relevant to the write-then-read pattern your demo exercises.
