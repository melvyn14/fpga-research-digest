# FPGA Research Digest - 2026-10-18

## Executive Summary
- **AXI-Lite deadlock**: Never make VALID dependent on READY — this creates a circular stall. Once VALID is asserted, keep it high with stable payload until the handshake completes. The reverse (READY depending on VALID) is permitted.
- **AXI Interconnect deprecated**: Vivado 2025.1 confirms AXI Interconnect will be deprecated; migrate all new block designs to AXI SmartConnect. Connection automation now defaults to SmartConnect in example designs.
- **Vitis 2025.2 `xil_printf.h` path bug**: Scripted Vitis platform creation can lose BSP include paths, causing `xil_printf.h` not found. Workaround: re-open the project in the IDE and manually verify the domain's include directories after scripted generation.
- **AXI BRAM addressing is byte-based**: `Xil_Out32(BASE + 0x4, val)` writes the second 32-bit word. The BRAM port address bits do not map 1:1 to AXI byte addresses — the low 2 bits select the byte lane, not the BRAM word.
- **New AXI Switch IP in Vivado 2025.1**: A fully RTL-instantiable AXI Switch IP was added, filling the gap between AXI SmartConnect (IPI-only) and custom interconnect. Useful for RTL-first designs without a block diagram.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings
- **VALID must not depend on READY**: The rule is strict — a source asserting VALID only after seeing READY causes deadlock when the sink waits for VALID before asserting READY. The reverse (READY depending on VALID) is explicitly allowed by the spec.
- **VALID stability**: Once VALID is raised, it must remain asserted with the payload held constant until the handshake completes (VALID && READY both true for one clock).
- **AXI-Lite write sequence**: The write response (BVALID/BREADY) channel must only complete after *both* the address channel (AWVALID/AWREADY) and write data channel (WVALID/WREADY) have completed — not after just one of them.
- **WSTRB ignored leads to partial writes**: In AXI-Lite, WSTRB selects which byte lanes are active. Ignoring it results in silent partial writes that are hard to debug. The PS AXI master sets WSTRB = 4'hF for 32-bit aligned word writes.
- **Extra conditions break handshakes**: Adding any condition beyond `VALID & READY` to the transfer detection logic (e.g. `VALID & READY & some_enable`) can silently cause missed transactions.

### Code Example
```vhdl
-- AXI-Lite slave write channel — correct handshake
process(clk)
begin
  if rising_edge(clk) then
    if rst = '1' then
      awready <= '0';
      wready  <= '0';
    else
      -- Accept address once we're idle
      if awvalid = '1' and awready = '0' and wvalid = '1' then
        awready <= '1';
        bram_addr <= awaddr(ADDR_WIDTH-1 downto 2); -- strip byte offset
      else
        awready <= '0';
      end if;

      -- Accept data in same or next cycle
      if wvalid = '1' and wready = '0' and awvalid = '1' then
        wready <= '1';
        -- Honour WSTRB byte lanes
        for i in 0 to 3 loop
          if wstrb(i) = '1' then
            bram_din(i*8+7 downto i*8) <= wdata(i*8+7 downto i*8);
          end if;
        end loop;
      else
        wready <= '0';
      end if;
    end if;
  end if;
end process;
```

### Relevance to Your Project
Your project writes 32-bit patterns to BRAM0 (0xA0000000) and BRAM2 (0xA0010000) from the Cortex-A53. The PS AXI master issues AXI-Lite transactions; if your `kv260_top.vhd` wraps a BRAM controller, verifying WSTRB handling and the BVALID/BREADY sequencing will prevent silent write failures that show as FAIL in the UART readback loop.

## Vivado Block Design / IP Integrator

### Key Findings
- **Connection Automation for BRAM**: When you right-click an AXI BRAM controller's `S_AXI` port and run Connection Automation, Vivado adds a SmartConnect, a Processor System Reset, and wires the PS's HP or GP master port. The Address Editor then auto-populates with a 64K window.
- **Address Editor pitfall**: After automation, verify the base address in the Address Editor matches your software constants (0xA0000000 for BRAM0). A mismatch is the most common reason a bare-metal read returns 0xDEADBEEF or hangs.
- **Explicit Tcl over `apply_bd_automation`**: For reproducible builds, prefer explicit `connect_bd_intf_net` and `assign_bd_address` commands over relying on automation, then call `validate_bd_design` to propagate parameters and catch port-width mismatches before synthesis.
- **Regenerate output products**: After any block design change, always run `generate_target all` before synthesizing, or the generated wrapper VHDL will be stale.

### Code Example
```tcl
# Explicit AXI BRAM connection — more reproducible than apply_bd_automation
connect_bd_intf_net [get_bd_intf_pins axi_bram_ctrl_0/S_AXI] \
    [get_bd_intf_pins axi_smc/M00_AXI]

# Assign base address to match software constant
assign_bd_address [get_bd_addr_segs {axi_bram_ctrl_0/S_AXI/Mem0}]
set_property offset 0xA0000000 \
    [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property range 64K \
    [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]

validate_bd_design
generate_target all [get_files *.bd]
```

### Relevance to Your Project
Your `create_bd.tcl` sets up two BRAM controllers at 0xA0000000 and 0xA0010000. Using explicit address assignments (not automation) guarantees those constants stay synchronized between the block design and `main.c`. Adding `validate_bd_design` to the TCL script catches interface-width mismatches before the multi-hour synthesis run.

## Vivado TCL Scripting

### Key Findings
- **Non-project batch mode**: Invoke Vivado as `vivado -mode batch -source build.tcl` to run synthesis, implementation, and bitstream generation without a persistent project file. This is faster for CI and avoids stale run cache issues.
- **Argument passing**: Use `-tclargs arg1 arg2` to pass parameters to your script, accessible via `$argv` inside TCL. Useful for parameterizing part number or output directory.
- **Build sequence**: The canonical non-project flow is: `read_vhdl` → `read_xdc` → `synth_design` → `opt_design` → `place_design` → `route_design` → `write_bitstream`.
- **Project-mode alternative**: Use `launch_runs impl_1 -to_step write_bitstream` + `wait_on_run impl_1` for project-based automation; simpler but slightly slower due to project overhead.
- **Programming in batch**: `open_hw_manager` → `connect_hw_server` → `open_hw_target` → `program_hw_devices` — but an already-open GUI hardware manager on the same server will block the connection.

### Code Example
```tcl
#!/usr/bin/env tclsh
# Non-project batch build for KV260 AXI-BRAM demo
# Usage: vivado -mode batch -source build.tcl

set part "xck26-sfvc784-2LV-c"

read_vhdl   [glob ../vhdl/*.vhd]
read_xdc    [glob ../xdc/*.xdc]

synth_design -top kv260_top -part $part -flatten_hierarchy rebuilt
opt_design
place_design
route_design

report_timing_summary -file timing_summary.rpt
report_utilization    -file utilization.rpt

write_bitstream -force output/kv260_top.bit
puts "Build complete: output/kv260_top.bit"
```

### Relevance to Your Project
Wrapping your current `create_bd.tcl` in a non-project build script eliminates the need to open the Vivado GUI for each rebuild. Pair it with `generate_target all` (after recreating the block design) so the VHDL wrapper and stub files are always fresh before synthesis.

## Vitis Bare-Metal / Standalone

### Key Findings
- **`xil_printf.h` missing in 2025.2 scripted flows**: A confirmed AMD support issue (2025.2) shows that scripted platform/app creation can drop BSP include paths, causing `xil_printf.h` not found at compile time. Workaround: after running the creation script, open the Vitis IDE, navigate to the platform's standalone domain settings, and verify the include path points to `<bsp>/include`. Re-export and rebuild.
- **`xil_printf` vs `printf`**: `xil_printf` is a lightweight, format-limited substitute (no floats, limited width specifiers). It calls `outbyte()`, which in the Zynq UltraScale+ BSP routes to the PS UART. The full `printf` requires the C library and ~10× more code space.
- **Default linker script spans full DDR**: Vitis generates `lscript.ld` targeting the full DDR range. For a bare-metal demo that shares DDR with other software later, adjust the `DDR` memory origin and `LENGTH` to carve out a dedicated region.
- **BSP `sleep` functions**: `usleep(n)` and `sleep(n)` from `xil_sleep.h` use TTC0 internally. If TTC0 is routed to fan control (as it is on KV260), calling `sleep()` can interfere with the fan timer — use `for` loop delays or dedicate a different timer.

### Code Example
```c
/* Minimal AXI-BRAM read/write test — bare-metal Vitis */
#include "xil_io.h"
#include "xil_printf.h"

#define BRAM0_BASE  0xA0000000U
#define BRAM2_BASE  0xA0010000U
#define TEST_WORDS  16

int main(void) {
    xil_printf("KV260 AXI-BRAM test start\r\n");

    /* Write phase */
    for (int i = 0; i < TEST_WORDS; i++) {
        Xil_Out32(BRAM0_BASE + (i * 4), 0xDEAD0000 | i);
        Xil_Out32(BRAM2_BASE + (i * 4), 0xBEEF0000 | i);
    }

    /* Readback phase */
    int pass = 1;
    for (int i = 0; i < TEST_WORDS; i++) {
        u32 r0 = Xil_In32(BRAM0_BASE + (i * 4));
        u32 r2 = Xil_In32(BRAM2_BASE + (i * 4));
        if (r0 != (0xDEAD0000 | i) || r2 != (0xBEEF0000 | i)) {
            xil_printf("FAIL at word %d: BRAM0=0x%08X BRAM2=0x%08X\r\n", i, r0, r2);
            pass = 0;
        }
    }
    xil_printf(pass ? "PASS\r\n" : "FAIL\r\n");
    return 0;
}
```

### Relevance to Your Project
This is directly analogous to your `main.c` pattern. The key addition is byte-offset addressing `(i * 4)` and explicit readback comparison per word — helps pinpoint which BRAM and which offset fails, rather than a single PASS/FAIL at the end.

## XDC Timing Constraints

### Key Findings
- **Unconstrained I/O ports are invisible to timing**: Without `set_input_delay` / `set_output_delay`, Vivado simply skips I/O timing paths. For a PS-to-PL AXI design, all PL I/O that connects to the PS via AXI is internally constrained by the Zynq PS IP, so you typically only need explicit constraints for external I/O (e.g. LEDs, buttons, UART TX/RX at the PL level).
- **Virtual clock for MMCM paths**: When a clock source goes through an MMCM/PLL, use a virtual clock on the input pad and set `-clock` to the virtual clock in `set_input_delay`. Without this, timing violations can appear on legitimate fast paths.
- **Sign of output delay**: `set_output_delay` value can be negative (data arrives at the destination before the clock edge) — this is valid and common for source-synchronous protocols.
- **Max/min pair for full analysis**: Always pair `-max` (setup check) and `-min` (hold check) variants:
  ```
  set_input_delay  -clock clk -max 4.0 [get_ports data_in]
  set_input_delay  -clock clk -min 2.0 [get_ports data_in]
  set_output_delay -clock clk -max 8.0 [get_ports data_out]
  set_output_delay -clock clk -min -3.0 [get_ports data_out]
  ```
- **Clock groups for PS-PL boundary**: Use `set_clock_groups -asynchronous` for clocks that cross the PS/PL boundary from different sources to suppress false path reports.

### Code Example
```tcl
# KV260 typical XDC — PS-driven AXI design
# The ZYNQ PS clock is auto-constrained; only constrain PL-external I/O

# On-board 100 MHz PL reference (not used if relying on PS clocks)
# create_clock -period 10.000 -name pl_clk [get_ports pl_clk_ref]

# UART TX — output only, no strict timing needed for debug UART
set_output_delay -clock [get_clocks -of_objects \
    [get_pins -hierarchical -filter {NAME =~ */pl_clk0}]] \
    -max 2.0 [get_ports uart_txd]
set_output_delay -clock [get_clocks -of_objects \
    [get_pins -hierarchical -filter {NAME =~ */pl_clk0}]] \
    -min -1.0 [get_ports uart_txd]

# Mark PS-to-PL AXI clocks as not related to any external PL free-running clock
# (prevents spurious cross-domain timing errors)
# set_clock_groups -asynchronous \
#   -group [get_clocks -of_objects [get_pins */pl_clk0]] \
#   -group [get_clocks external_pl_clk]
```

### Relevance to Your Project
Your project routes UART through the PS (MIO-based UART1), so the UART path is entirely inside the PS and needs no PL XDC constraint. Focus your XDC on the PL clock definition (if any free-running PL clock is used) and any GPIO pins brought out through the KV260 expansion header.

## Kria KV260 / K26 SoM

### Key Findings
- **Boot mode**: The K26 SOM's boot source is selected via `PS_Mode[3:0]` pins on MIO[5:0]. For JTAG/bare-metal development, confirm the KV260 starter kit jumper is in JTAG mode or SD card mode (the starter kit defaults to SD card boot, which can interfere with JTAG downloads if no SD is present).
- **Power domains (three of them)**: Always-on domain, PS domain (MIO and PS-GTR peripherals), PL domain (HDIO and HPIO). The SOM's MIO banks operate at **1.8 V** — do not connect 3.3 V logic directly to MIO pins without a level shifter.
- **MIO31/MIO35 special functions**: MIO31 = hardware shutdown request input; MIO35 = external watchdog output. In bare-metal, if your design accidentally drives MIO31 low, the SOM may reset.
- **TTC0 / fan conflict**: The KV260 fan controller maps to TTC0 via EMIO. If your bare-metal app uses TTC0 (e.g. for `sleep()` calls or general timers), you will disrupt the fan — use TTC1 or TTC2 instead.
- **EMIO GPIO for PL-visible signals**: Signals that appear on the KV260 expansion connector (PMOD, Arduino) are routed through EMIO. Map them in the PS IP block as EMIO GPIO and assign MIO/EMIO numbers accordingly in the XDC.

### Code Example
```c
/* Bare-metal: read PS GPIO via EMIO (KV260 expansion header) */
#include "xgpiops.h"

#define GPIO_DEVICE_ID  XPAR_XGPIOPS_0_DEVICE_ID
/* EMIO pins start at offset 78 on ZynqMP (54 MIO + 24 reserved) */
#define EMIO_LED_PIN    78

XGpioPs GpioInst;

int init_gpio(void) {
    XGpioPs_Config *cfg = XGpioPs_LookupConfig(GPIO_DEVICE_ID);
    if (!cfg) return XST_FAILURE;
    XGpioPs_CfgInitialize(&GpioInst, cfg, cfg->BaseAddr);
    /* Set EMIO pin as output */
    XGpioPs_SetDirectionPin(&GpioInst, EMIO_LED_PIN, 1);
    XGpioPs_SetOutputEnablePin(&GpioInst, EMIO_LED_PIN, 1);
    return XST_SUCCESS;
}

void toggle_led(int state) {
    XGpioPs_WritePin(&GpioInst, EMIO_LED_PIN, state);
}
```

### Relevance to Your Project
Your AXI-BRAM demo currently avoids EMIO, but if you add status LEDs or a debug signal to confirm write completion, they will go through EMIO GPIO. The 1.8 V MIO constraint and the TTC0/fan conflict are the two most likely surprises in extending the demo to use physical I/O.

## AMD/Xilinx Tool Updates (Vivado/Vitis 2025.x)

### Key Findings
- **AXI Interconnect officially deprecated in 2025.1**: AMD's PG059 states the IP will be deprecated in a future release and strongly encourages migration to AXI SmartConnect (for IP Integrator designs). Example designs within Vivado 2025.1 have been updated to use SmartConnect.
- **New AXI Switch IP (2025.1)**: A new RTL-instantiable AXI Switch IP was added — unlike SmartConnect, it can be instantiated directly in HDL without requiring a block diagram. This fills a long-standing gap for RTL-first designers.
- **Versal/UltraScale+ scope**: AXI Interconnect support ends at UltraScale+. Versal designs must use SmartConnect or the NoC. The KV260/K26 SOM uses XCZU5EV (UltraScale+), so AXI Interconnect still works but migration to SmartConnect is advised now.
- **Vitis 2025.2 known issue — include paths dropped in scripted flows**: Scripted creation of Vitis platforms can lose `xil_printf.h` and other BSP headers from the include path (see Vitis section above). Affects automated CI pipelines using `xsct` scripts.
- **Vitis AI 5.1**: Quantization enhancements and vectorized SIMD sorting/correlation for Versal AI Core. Not directly relevant to KV260 bare-metal, but the AI Engine improvements are relevant if you later port to the KV260's ML accelerator capabilities.

### Code Example
```tcl
# Migration: replace AXI Interconnect with AXI SmartConnect in a Vivado BD
# Old (deprecated):
# create_bd_cell -type ip -vlnv xilinx.com:ip:axi_interconnect:2.1 axi_interconnect_0

# New (recommended):
create_bd_cell -type ip -vlnv xilinx.com:ip:smartconnect:1.0 axi_smc
set_property CONFIG.NUM_SI {1} [get_bd_cells axi_smc]
set_property CONFIG.NUM_MI {2} [get_bd_cells axi_smc]

# Connect PS GP0 master to SmartConnect
connect_bd_intf_net \
    [get_bd_intf_pins zynq_ultra_ps_e_0/M_AXI_HPM0_FPD] \
    [get_bd_intf_pins axi_smc/S00_AXI]

# Route to BRAM controllers
connect_bd_intf_net [get_bd_intf_pins axi_smc/M00_AXI] \
    [get_bd_intf_pins axi_bram_ctrl_0/S_AXI]
connect_bd_intf_net [get_bd_intf_pins axi_smc/M01_AXI] \
    [get_bd_intf_pins axi_bram_ctrl_1/S_AXI]
```

### Relevance to Your Project
Your `create_bd.tcl` likely uses `axi_interconnect` for routing the PS master to BRAM0 and BRAM2. Updating to `smartconnect` now prevents a forced migration later and removes a deprecation warning from every build log. SmartConnect also has lower resource utilization for simple 1-to-N routing topologies.
