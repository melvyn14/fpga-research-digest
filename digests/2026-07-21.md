# FPGA Research Digest - 2026-07-21

## Executive Summary

- **AXI-Lite deadlock prevention**: Never wait for READY before asserting VALID. Only raise AWREADY when both AWVALID *and* WVALID are high — synchronizing the write-address and write-data channels avoids the most common bare-metal hang on the KV260 BRAM demo.
- **Vivado 2025.x AXI BRAM address-space bug**: Vivado 2025 has a known issue where generated RTL may limit usable BRAM address space to 1 kB due to asynchronous read logic; confirm your BRAM Controller is set to synchronous read mode and verify the address width parameter matches your BRAM depth.
- **write_bd_tcl portability**: Block design TCL exports embed the Vivado version and cannot be used across releases; always regenerate `create_bd.tcl` after a Vivado upgrade and pin IP versions explicitly in TCL to avoid silent parameter drift.
- **Vitis 2025.1 BSP stdout**: If `xil_printf` is silent, the BSP stdout is likely pointed at the wrong UART. Set `stdout` to `psu_uart_1` (the KV260's USB-UART bridge) in BSP settings and regenerate before rebuilding.
- **KV260 bare-metal boot**: QSPI32 is the default boot mode on the Starter Kit; for JTAG-based bare-metal PS+PL development, use XSCT to download the bitstream and ELF in sequence — verify BRAM access at 0xA0000000 is blocked before the bitstream loads and passes afterward as the go/no-go test.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- AXI4-Lite uses five independent channels: AW (write address), W (write data), B (write response), AR (read address), R (read data). All use VALID/READY handshake; a transfer occurs on the rising clock edge when both are high.
- **Deadlock rule**: A source must assert VALID without waiting for READY. If the master waits for READY before asserting VALID, and the slave waits for VALID before asserting READY, the system deadlocks permanently.
- On writes, the slave should only raise AWREADY when *both* AWVALID and WVALID are asserted, ensuring the address and data channels are captured atomically.
- BRESP/RRESP should return `2'b00` (OKAY) for normal transactions. Slaves that drive `SLVERR` (`2'b10`) cause some masters to fault; prefer OKAY even for out-of-range addresses unless the master is known to handle errors.
- There must be no combinatorial path from a received VALID to the same-channel READY — register xREADY or use a skid buffer to break the loop and meet timing.
- The write response channel (B channel) is often overlooked in bare-metal code: if BREADY stays low permanently, the slave cannot accept new write-address transfers and the bus stalls after the first transaction.

### Code Example

```vhdl
-- Minimal AXI4-Lite write handshake (VHDL, synchronous)
-- Only accept address+data when both valid signals are present
process(S_AXI_ACLK)
begin
  if rising_edge(S_AXI_ACLK) then
    if S_AXI_ARESETN = '0' then
      axi_awready <= '0';
      axi_wready  <= '0';
      axi_bvalid  <= '0';
    else
      -- Accept write address and data only when both are valid
      if S_AXI_AWVALID = '1' and S_AXI_WVALID = '1' and
         axi_awready = '0' and axi_wready = '0' then
        axi_awready <= '1';
        axi_wready  <= '1';
      else
        axi_awready <= '0';
        axi_wready  <= '0';
      end if;

      -- Issue write response exactly one cycle after acceptance
      if axi_awready = '1' and axi_wready = '1' then
        axi_bvalid  <= '1';
        axi_bresp   <= "00"; -- OKAY
      elsif S_AXI_BREADY = '1' and axi_bvalid = '1' then
        axi_bvalid  <= '0'; -- de-assert once master accepts response
      end if;
    end if;
  end if;
end process;
```

### Relevance to Your Project

Your demo writes patterns to BRAM0 (0xA0000000) and BRAM2 (0xA0010000) over AXI-Lite from Cortex-A53 bare-metal C code. If `Xil_Out32` calls succeed but the subsequent `Xil_In32` reads back garbage, check BVALID/BREADY handling in the BRAM Controller — the controller may be stalling waiting for your software to "drain" the B channel. Also ensure BREADY is held high in your software (the Xilinx Memory Mapped I/O helpers do this, but a custom polling loop may not).

## Vivado Block Design / IP Integrator

### Key Findings

- IP Integrator's **Connection Automation** (Run Connection Automation) detects common topologies and wires clock, reset, and AXI ports automatically — always run it after adding each new IP to catch missed connections before validation.
- The **Address Editor** auto-assign (`assign_bd_address`) will lay out all slave segments; right-click → Auto Assign Address to resolve unmapped-slave errors without manual entry.
- **AXI SmartConnect** is preferred over the older AXI Interconnect for new designs; its topology is generated dynamically at Validate time, automatically inserting clock-crossing logic when master and slave clock domains differ.
- Vivado 2025.x has a regression where asynchronous BRAM read-port RTL cannot be inferred as synchronous block RAM, limiting the effective address space to 10 bits (1 kB). Force `Read Latency` to 1 cycle (synchronous) in the Block Memory Generator IP to work around this.
- `validate_bd_design` in TCL catches address conflicts and unconnected mandatory ports before synthesis — integrate it into your CI build script after `create_bd.tcl` runs.
- For version control, always store `create_bd.tcl` (written by `write_bd_tcl`) rather than the `.bd` XML file — the XML is binary-ish and produces huge, unreadable diffs.

### Code Example

```tcl
# Vivado IP Integrator: create block design and validate from TCL
open_project ./kv260.xpr
open_bd_design [get_files *.bd]

# Auto-assign all unassigned AXI slave addresses
assign_bd_address

# Set BRAM0 base address explicitly for documentation clarity
set_property offset 0xA0000000 [get_bd_addr_segs {bram_ctrl_0/S_AXI/Mem0}]
set_property range  64K         [get_bd_addr_segs {bram_ctrl_0/S_AXI/Mem0}]

# Validate before generating
validate_bd_design

# Generate output products (HDL wrapper + sim models)
generate_target all [get_files *.bd]
make_wrapper -files [get_files *.bd] -top
add_files -norecurse [glob ./kv260.gen/sources_1/bd/*/hdl/*.vhd]
```

### Relevance to Your Project

Your `create_bd.tcl` automates the PS + BRAM Controller + Block Memory Generator topology. Adding `assign_bd_address` and `validate_bd_design` calls at the end of that script ensures the address map is correct every time the design is regenerated — critical when moving between Vivado versions or workstations.

## Vivado TCL Scripting

### Key Findings

- `write_bd_tcl -force ./tcl/create_bd.tcl` exports the live block design to a reproducible script; the `-force` flag overwrites without prompting.
- **Version lock**: exported TCL embeds the Vivado version string and will warn (or fail) if sourced in a different release. Always regenerate after a tool upgrade.
- Only user-modified IP parameters are written; default parameters after propagation are implicit. This means the script is compact but also means adding a new IP version may silently change propagated values — re-run `validate_bd_design` after any IP catalog update.
- Non-project mode flow (`-nolog -nojournal`) is useful for headless CI: `vivado -mode batch -source create_bd.tcl` runs the entire design creation pipeline without spawning the GUI.
- `write_project_tcl` captures the entire Vivado project (constraints, sources, runs) while `write_bd_tcl` captures only the block design — use both for full reproducibility.
- Use `get_property` / `set_property` on `bd_cell` objects in TCL to parameterize IP cores without touching the GUI, enabling configuration-as-code workflows.

### Code Example

```tcl
# Non-project mode: create project, run BD script, synthesize, implement, write bitstream
# Usage: vivado -mode batch -source build_all.tcl

set part "xck26-sfvc784-2LV-c"
set bd_tcl "./tcl/create_bd.tcl"
set xdc    "./xdc/kv260_top.xdc"

create_project kv260 ./kv260_build -part $part -force
set_property board_part xilinx.com:kv260_som:part0:1.4 [current_project]

source $bd_tcl
validate_bd_design
generate_target all [get_files *.bd]
make_wrapper -files [get_files *.bd] -top
add_files -norecurse [glob ./kv260_build/kv260_build.gen/sources_1/bd/*/hdl/*.vhd]
add_files -fileset constrs_1 $xdc

launch_runs synth_1 -jobs 4
wait_on_run synth_1
launch_runs impl_1 -to_step write_bitstream -jobs 4
wait_on_run impl_1

# Export XSA for Vitis
write_hw_platform -fixed -include_bit -force ./kv260_top.xsa
```

### Relevance to Your Project

Your project already has a `create_bd.tcl` under `tcl/`. Wrapping it in a non-project-mode outer script (above) would let a CI job regenerate the bitstream and XSA from scratch on every commit, making the kv260-axi-bram-demo fully reproducible without checking in binary files.

## Vitis Bare-Metal / Standalone

### Key Findings

- **stdout misconfiguration** is the most common cause of silent `xil_printf` on KV260: the BSP must point `stdout` to `psu_uart_1` (connected to the USB-UART bridge on the KV260), not `psu_uart_0`.
- After changing BSP settings (UART selection, baud rate, memory sizes), always **Clean Project → Regenerate BSP → Rebuild Application** in that order; incremental rebuilds may silently miss BSP changes.
- Vitis 2025.1 uses the **System Device Tree (SDT)-based flow** by default for new platforms. Legacy Classic flow is still available but deprecated; migrate to SDT flow if starting a new project.
- The SDT flow changes how standalone libraries are packaged — `xil_printf.h` and peripheral drivers come from the `embeddedsw` library pulled in by the platform, not the BSP directly.
- For Cortex-A53 AArch64, default heap is 0x2000 and stack is 0x2000 bytes. AXI-BRAM demos are tiny, but if you add printf format strings or float arithmetic, increase heap in `lscript.ld`:
  ```
  _HEAP_SIZE = DEFINED(_HEAP_SIZE) ? _HEAP_SIZE : 0x10000;
  _STACK_SIZE = DEFINED(_STACK_SIZE) ? _STACK_SIZE : 0x8000;
  ```
- GIC (interrupt controller) initialization for bare-metal: use `XScuGic_Initialize`, register handlers with `XScuGic_Connect`, then `Xil_ExceptionEnable()` — do not skip the exception enable or interrupts fire but are never dispatched.
- `Xil_DCacheFlushRange` / `Xil_ICacheInvalidateRange` are critical before and after DMA or BRAM-based transactions if the D-cache is enabled; without them, the CPU may read stale cache lines instead of updated BRAM contents.

### Code Example

```c
/* Bare-metal AXI-BRAM read/write test for KV260
 * BRAM0 at 0xA0000000, BRAM2 at 0xA0010000 */
#include "xil_printf.h"
#include "xil_io.h"
#include "xil_cache.h"

#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL
#define TEST_WORDS  8

int main(void) {
    u32 i, rd;
    int pass = 1;

    xil_printf("KV260 AXI-BRAM Test\r\n");

    /* Write incrementing pattern */
    for (i = 0; i < TEST_WORDS; i++) {
        Xil_Out32(BRAM0_BASE + (i * 4), 0xDEAD0000 | i);
        Xil_Out32(BRAM2_BASE + (i * 4), 0xBEEF0000 | i);
    }

    /* Flush D-cache before readback if cache is enabled */
    Xil_DCacheFlushRange(BRAM0_BASE, TEST_WORDS * 4);
    Xil_DCacheFlushRange(BRAM2_BASE, TEST_WORDS * 4);

    /* Readback and verify */
    for (i = 0; i < TEST_WORDS; i++) {
        rd = Xil_In32(BRAM0_BASE + (i * 4));
        if (rd != (0xDEAD0000 | i)) {
            xil_printf("BRAM0[%d] FAIL: got 0x%08X\r\n", i, rd);
            pass = 0;
        }
        rd = Xil_In32(BRAM2_BASE + (i * 4));
        if (rd != (0xBEEF0000 | i)) {
            xil_printf("BRAM2[%d] FAIL: got 0x%08X\r\n", i, rd);
            pass = 0;
        }
    }

    xil_printf(pass ? "All tests PASS\r\n" : "FAIL\r\n");
    while (1); /* bare-metal spin */
    return 0;
}
```

### Relevance to Your Project

This pattern mirrors what your `main.c` likely implements. The key addition is the `Xil_DCacheFlushRange` calls — if the Cortex-A53 D-cache is enabled (it is by default in the standalone BSP for performance), omitting the flush will cause read-back to return stale cached values instead of BRAM contents, producing spurious FAIL results even when the hardware is correct.

## XDC Timing Constraints

### Key Findings

- `set_input_delay` and `set_output_delay` specify the external path delay relative to a clock edge at the design interface — they are mandatory for any real I/O but can be omitted for AXI-BRAM designs where all interfaces are internal (PS ↔ PL over the AXI fabric).
- For pure PS-to-PL AXI designs (no external I/O besides UART and JTAG), the minimum useful XDC contains: (1) the primary PL clock constraint, (2) `set_false_path` for asynchronous resets, and (3) `create_clock` for any generated clocks.
- The Zynq UltraScale+ PS generates the `pl_clk0` through the PS IP block; constrain it in XDC with:
  ```tcl
  create_clock -period 10.000 -name clk_pl_0 [get_pins -hierarchical -filter {NAME =~ *zynq_ultra_ps_e_0*/PL0_REF_CLK}]
  ```
- `set_clock_groups -asynchronous` should be used if your design has multiple clock domains (e.g., the PS FCLK at 100 MHz for AXI logic and a separate pixel clock). Without it, Vivado attempts cross-domain timing analysis across unrelated clocks, producing false violations.
- Vivado's timing summary after implementation (`report_timing_summary`) will report `No timing constraints` warnings if constraints are missing — treat any such warning as a blocker, as the router may make sub-optimal decisions.
- For UART (MIO-routed on KV260), no XDC is needed — MIO signals are entirely inside the PS and are constrained by the PS IP configuration, not by user XDC.

### Code Example

```tcl
# Minimal XDC for KV260 AXI-BRAM bare-metal demo
# (no external I/O beyond PS-MIO UART and JTAG)

# PL fabric clock from Zynq UltraScale+ PS (100 MHz)
create_clock -period 10.000 -name clk_pl_0 \
  [get_pins -hierarchical -filter {NAME =~ *zynq_ultra_ps_e_0*/PL0_REF_CLK}]

# Async reset false paths (PS-driven PL reset is asynchronous to PL clock)
set_false_path -from [get_pins -hierarchical -filter {NAME =~ *zynq_ultra_ps_e_0*/PL_RESETN0}]

# If design uses multiple clock domains, declare them asynchronous
# (uncomment if you add a second FCLK)
# set_clock_groups -asynchronous \
#   -group [get_clocks clk_pl_0] \
#   -group [get_clocks clk_pl_1]

# Optional: constrain BRAM output delay for timing closure sanity
# (not required for AXI-connected BRAMs, but helps meet hold margins)
# set_multicycle_path -setup 2 -from [get_cells *bram*] -to [get_cells *axi*]
```

### Relevance to Your Project

Your VHDL `kv260_top.vhd` wraps the PS and block design. The XDC above is the minimum needed to give Vivado a valid timing context — without the `create_clock` for `PL0_REF_CLK`, timing analysis is unconstrained and the implementation may not meet timing even for a simple BRAM demo at 100 MHz.

## Kria KV260 / K26 SoM

### Key Findings

- The **K26 SoM** is an XCK26 Zynq UltraScale+ MPSoC (quad-core Cortex-A53 + dual Cortex-R5F) on a tiny form-factor module with a 395-pin connector to the carrier card.
- **Boot modes**: KV260 ships with QSPI32 pre-selected via boot-mode pins on the carrier card. For bare-metal PS+PL development, switch to **JTAG mode** or load via XSCT over USB without changing physical jumpers.
- **MIO bank 501** carries PS MIO signals to the carrier — UART1 (MIO 36/37) is wired to the USB-UART bridge, which is why BSP stdout should be `psu_uart_1`.
- **PL power domain**: The PL fabric on K26 is powered by VCC_PL (0.85 V core) and VCC_PLIO (1.8 V I/O). The PL is not powered until the PS boot sequence enables it — always ensure the PS boots successfully before attempting PL operations.
- **AXI GP master ports**: The PS exposes `M_AXI_HPM0_FPD` (full-power domain, 128-bit, up to 333 MHz) and `M_AXI_HPM1_FPD` for PL communication. For simple BRAM demos, connect to `M_AXI_HPM0_FPD` and use the SmartConnect IP to bridge to your AXI-Lite BRAM controllers.
- Pre-verified address map for KV260 bare-metal: access to 0xA0000000 fails (bus error / hang) before the PL bitstream is loaded, and succeeds after — this is the standard go/no-go test to confirm PS-PL AXI connectivity.
- The Kria SOM board files for Vivado are available from the AMD board repository; pin `board_part` to `xilinx.com:kv260_som:part0:1.4` in your TCL to auto-configure the PS IP with correct DDR and MIO settings.

### Code Example

```bash
# XSCT commands for JTAG bare-metal load on KV260 (run in Vitis XSCT console)
# Step 1: Connect and select the APU Cortex-A53 core 0
connect
targets -set -nocase -filter {name =~ "*A53*#0"}

# Step 2: Initialize the PS (required before accessing PL)
source {/path/to/ps_init.tcl}
ps_init

# Step 3: Download the bitstream to configure the PL
fpga {/path/to/kv260_top.bit}

# Step 4: Download the bare-metal ELF to DDR and run
dow {/path/to/kv260_bram_test.elf}
con

# Verify UART output at 115200 baud on /dev/ttyUSB1 (Linux) or COMx (Windows)
```

### Relevance to Your Project

This XSCT sequence is the standard development loop for the kv260-axi-bram-demo. The `ps_init` step is mandatory — skipping it means the DDR and AXI fabric clocks may not be initialized, causing the `Xil_Out32` calls to hang the processor before reaching `xil_printf`. The bitstream load step configures the PL and activates the two BRAM address ranges your demo tests.

## AMD/Xilinx Tool Updates: Vivado/Vitis 2025.x

### Key Findings

- **Vivado 2025.1** introduces a hardware fast-iteration flow (`Vitis Export to Vivado`) that allows incremental PL changes without re-exporting the entire XSA — useful for iterating on BRAM address maps without full Vitis platform rebuild cycles.
- **Vitis 2025.1** defaults to the System Device Tree (SDT)-based flow for new standalone platforms; the Classic flow (Vitis Classic IDE) is still supported but is scheduled for deprecation. Migrate new projects to the SDT flow.
- IP Change Log (AMD Answer Record 000037919) documents all IP version bumps in 2025.1 — notably the AXI BRAM Controller v4.1 and Block Memory Generator v8.4 received functional updates; review the change log before upgrading an existing design.
- The SmartConnect IP received performance improvements in 2025.1 for burst transaction scheduling; no functional changes expected for AXI-Lite single-beat traffic.
- **Known issue**: Vivado 2025.1 may fail to generate the block design wrapper HDL when the project path contains spaces or non-ASCII characters — keep all project paths ASCII-only with no spaces.
- Vitis 2025.1 adds improved support for **MicroBlaze-V** (RISC-V soft processor) and extends the Unified IDE to support mixed PS/PL bare-metal projects more cleanly.
- The `write_hw_platform` command (used to generate `.xsa`) now supports `-include_bit` as a standard option without workarounds in 2025.1.

### Code Example

```tcl

# Captures bitstream + metadata for Vitis platform creation

# After write_bitstream completes:
write_hw_platform \
  -fixed \

  -force \
  ./output/kv260_top.xsa

# In Vitis (SDT flow), create platform from XSA:
# vitis -s create_platform.py  (Python-based platform creation in 2025.1+)

# Alternatively, classic xsct approach still works:
# xsct% platform create -name kv260_platform -hw ./output/kv260_top.xsa
# xsct% platform generate
```

### Relevance to Your Project

If you upgrade the kv260-axi-bram-demo from an earlier Vivado/Vitis version to 2025.1, the main migration steps are: (1) regenerate the XSA with `write_hw_platform -include_bit`, (2) recreate the Vitis platform using the SDT flow, and (3) re-run `validate_bd_design` to catch the BRAM address-width regression noted in the AXI section above. The IP change log for AXI BRAM Controller v4.1 should be reviewed before accepting automatic IP upgrades.
