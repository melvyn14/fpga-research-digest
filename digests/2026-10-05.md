# FPGA Research Digest - 2026-10-05

## Executive Summary
- **AXI-Lite handshaking bug in Xilinx example code**: A well-documented bug exists in Vivado-generated AXI-lite slave templates where combinational logic is exposed directly on RDATA outputs, causing timing violations and incorrect behavior under back-pressure conditions. Review your AXI BRAM read-response logic carefully.
- **Vivado 2025.1 new AXI Switch IP + IP Integrator views**: The 2025.1 release adds a fully customizable AXI Switch IP and dedicated "Clocking and Reset" and "Interrupt and AXI-4 Lite" views in IP Integrator — useful for navigating and verifying your block design connections more quickly.
- **Non-project TCL automation**: Using `vivado -mode batch -source your_script.tcl` with `create_bd.tcl` as a sourced sub-script is the recommended AMD workflow for reproducible builds — exactly the pattern your project already uses.
- **Kria K26 boot sequence**: The K26 SoM first boots from QSPI with a limited peripheral set, then detects the carrier card and applies a DT overlay. For bare-metal work, JTAG boot mode bypasses this entirely and is the most reliable path for iterative development.
- **AXI BRAM Controller read latency**: Output register configuration and ECC settings both affect read latency. With ECC disabled and output registers off (the fastest path), AXI BRAM reads complete in 2 clock cycles — important for verifying your PASS/FAIL timing assumptions.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings
- AXI4-Lite handshaking uses a VALID/READY pair on all 5 channels (AW, W, B, AR, R). A transfer occurs on any cycle where both VALID and READY are asserted simultaneously.
- **Critical rule**: Once TVALID (or any channel VALID) is asserted, it must NOT be de-asserted until the corresponding READY is seen. Violating this causes silent data loss or bus deadlock.
- A well-known bug in Vivado-generated AXI-lite slave templates exposes combinational logic directly on `S_AXI_RDATA`, producing timing violations on real hardware. The fix is to register RDATA through a flip-flop on the output path.
- For AXI-Stream: TVALID once asserted cannot be de-asserted before TREADY is seen; TLAST must be asserted on the last beat of a packet; TKEEP marks which byte lanes are valid in wide buses.
- AXI4-Lite does not support burst transfers; every transaction is a single beat. For burst access patterns to BRAM, use full AXI4 (the AXI BRAM Controller supports both protocols).

### Code Example
```vhdl
-- Safe registered RDATA path for AXI-Lite read channel
-- Avoids combinational path on S_AXI_RDATA
process(S_AXI_ACLK)
begin
  if rising_edge(S_AXI_ACLK) then
    if S_AXI_ARESETN = '0' then
      axi_rdata  <= (others => '0');
      axi_rvalid <= '0';
    elsif ar_active = '1' then
      -- Register data on the cycle the address is accepted
      axi_rdata  <= bram_dout;  -- already registered from BRAM
      axi_rvalid <= '1';
    elsif S_AXI_RREADY = '1' then
      axi_rvalid <= '0';
    end if;
  end if;
end process;
```

### Relevance to Your Project
Your AXI-Lite master (PS Cortex-A53) writes patterns to BRAM0 at `0xA0000000` and BRAM2 at `0xA0010000`, then reads them back. If the AXI BRAM Controller IP is using its default registered-output mode, your read latency is 2 cycles — but if you have added extra pipeline stages or your Vivado version generates a combinational RDATA path, you could see unreliable readback. Confirm read latency in the IP configuration dialog and verify against your C timing assumptions.

## Vivado Block Design / IP Integrator

### Key Findings
- **Connection Automation**: Right-click any unconnected interface port in the block design canvas → "Run Connection Automation" to let Vivado auto-wire standard interfaces like AXI, clock, and reset. This is faster than manual wiring for well-typed interfaces.
- **Address Editor**: After adding IP, always visit Window → Address Editor to confirm base addresses match your software (`0xA0000000`, `0xA0010000`). Automation assigns addresses that may not match your C code.
- **Regenerating IP**: After changing IP parameters, run "Generate Output Products" before synthesis; stale output products cause cryptic synthesis errors.
- Vivado 2025.1 adds dedicated "Clocking and Reset" and "Interrupt and AXI-4 Lite" views in IP Integrator, making it much easier to audit clock domains and AXI connections without scrolling across large block designs.
- **Validate Design**: Always run Validate Design (Tools → Validate Design, or Tcl: `validate_bd_design`) before synthesis to catch unconnected interfaces, address overlaps, and missing clocks early.

### Code Example
```tcl
# Validate block design and report issues before synthesis
open_bd_design [get_files *.bd]
validate_bd_design -verbose

# Check address segments programmatically
set segs [get_bd_addr_segs]
foreach seg $segs {
  set range  [get_property range  $seg]
  set offset [get_property offset $seg]
  puts "Segment: $seg  Offset: $offset  Range: $range"
}
```

### Relevance to Your Project
With two BRAM instances at `0xA0000000` and `0xA0010000` (64 KB apart), a 128 KB range segment for each is correct. Run the snippet above after `create_bd.tcl` to confirm the address map matches your `main.c` constants before committing a new bitstream.

## Vivado TCL Scripting

### Key Findings
- The standard reproducible build pattern is: `vivado -mode batch -source run_build.tcl`, where `run_build.tcl` sources your `create_bd.tcl` as a sub-script, then calls `synth_design`, `opt_design`, `place_design`, `route_design`, `write_bitstream`.
- `write_bd_tcl -force output.tcl` exports the current in-memory block design as a re-runnable Tcl script. Only user-modified parameters are written; IP defaults are omitted.
- Non-project mode is leaner for CI/automation; project mode is better for interactive development. You can mix both: author the design in project mode, export with `write_bd_tcl`, and build headlessly from the export.
- In non-project mode, add sources in the order they must be compiled: read constraints first, then read VHDL/Verilog, then call `synth_design`.
- Vivado 2025.1 UG994 documents the non-project block design flow under "Non-Project Script" — see `docs.amd.com/r/2025.1-English/ug994-vivado-ip-subsystems/Non-Project-Script`.

### Code Example
```tcl
# Minimal non-project batch build script
# Usage: vivado -mode batch -source build.tcl

set part "xck26-sfvc784-2LV-c"
set output_dir "./output"
file mkdir $output_dir

# Create in-memory project (non-project mode)
read_xdc ./constraints/kv260_top.xdc

# Re-create block design from exported script
source ./tcl/create_bd.tcl

# Make wrapper and set as top
make_wrapper -files [get_files *.bd] -top
read_vhdl ./vhdl/kv260_top.vhd

# Run implementation
synth_design  -top kv260_top -part $part
opt_design
place_design
route_design
write_bitstream -force "$output_dir/kv260_top.bit"
write_hw_platform -fixed -force "$output_dir/kv260_top.xsa"
puts "Build complete: $output_dir/kv260_top.bit"
```

### Relevance to Your Project
Your `create_bd.tcl` already follows this pattern. To add CI reproducibility, wrap it in the full non-project script above and add a `write_hw_platform` call — the resulting `.xsa` can be directly consumed by Vitis to regenerate the BSP without manual intervention.

## Vitis Bare-Metal / Standalone

### Key Findings
- The Vitis standalone BSP provides single-threaded bare-metal execution with `xil_printf` (lightweight, no `%f` support), interrupt support, cache APIs, and hardware abstraction for all Zynq peripherals.
- **Linker script pitfall**: For Zynq designs, the Vitis linker script generator may incorrectly assign all sections to BAR0 instead of DDR. The fix is to manually edit the generated `lscript.ld` and redirect `.text`, `.data`, `.bss` to the DDR region (`0x00000000` for Zynq UltraScale+ A53 in EL3/bare-metal).
- `xil_printf` uses less code space than standard `printf` but does not buffer output; every character goes directly to UART. For high-frequency debug output, consider batching messages.
- Interrupt controller setup for Zynq UltraScale+: use `XScuGic` (GIC-400) driver; call `XScuGic_Connect`, then `XScuGic_Enable`, then `Xil_ExceptionEnable()`. For PL interrupts connected over AXI, the IRQ must be routed through the block design to a `pl_ps_irq` port.
- BSP re-generation: after changing the block design or XSA, in Vitis right-click the platform project → "Update Hardware" → rebuild BSP to pick up new memory maps and driver instances.

### Code Example
```c
/* Minimal AXI-Lite BRAM read/write test pattern for Kria KV260 bare-metal */
#include "xil_io.h"
#include "xil_printf.h"

#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL
#define PATTERN     0xDEADBEEFUL

int bram_test(u32 base, const char *name) {
    Xil_Out32(base, PATTERN);
    /* Memory barrier: ensure write completes before read */
    Xil_DCacheFlushRange(base, 4);
    u32 readback = Xil_In32(base);
    if (readback == PATTERN) {
        xil_printf("%s PASS: wrote 0x%08X, read 0x%08X\r\n",
                   name, (unsigned)PATTERN, (unsigned)readback);
        return 0;
    } else {
        xil_printf("%s FAIL: wrote 0x%08X, read 0x%08X\r\n",
                   name, (unsigned)PATTERN, (unsigned)readback);
        return -1;
    }
}

int main(void) {
    xil_printf("--- KV260 AXI BRAM Test ---\r\n");
    int result = 0;
    result |= bram_test(BRAM0_BASE, "BRAM0");
    result |= bram_test(BRAM2_BASE, "BRAM2");
    xil_printf("Overall: %s\r\n", result == 0 ? "PASS" : "FAIL");
    while(1);
    return 0;
}
```

### Relevance to Your Project
The `Xil_DCacheFlushRange` call is critical on Cortex-A53 bare-metal: without it, the write may stay in the L1/L2 cache and the subsequent read may return the cached value rather than the actual BRAM contents (giving a false PASS). If your test is passing trivially, this cache coherence issue could mask a broken AXI connection. Add explicit cache flushes around each BRAM write.

## XDC Timing Constraints

### Key Findings
- For AXI interfaces internal to the Zynq PS-to-PL fabric, you generally do **not** need `set_input_delay`/`set_output_delay` — those apply to I/O paths crossing the device boundary (chip pins). AXI paths through the PS interconnect are constrained by the Zynq block's internal constraints.
- The AXI Clock Converter and AXI Data Width Converter IPs automatically generate `set_max_delay -datapath_only` constraints in their IP-level XDC files for asynchronous clock domain crossings. Review these in `<project>.ip_user_files/` to ensure they are picked up.
- **Clock groups**: If your design has multiple clock domains (e.g., a PL clock at 100 MHz and the PS clock domain), declare them as asynchronous with `set_clock_groups -asynchronous -group {clk_pl_0} -group {clk_ps_...}` to prevent false timing paths.
- Constraint ordering matters for runtime: I/O constraints before timing exceptions, primary clocks before generated clocks. Vivado 2026.1 UG903 documents recommended ordering at `docs.amd.com/r/en-US/ug903-vivado-using-constraints/Ordering-Constraints-for-Better-Runtime`.
- For BRAM-only PL designs (no external I/O), the minimal XDC is a clock definition + BITSTREAM properties.

### Code Example
```xdc
# kv260_top.xdc - Minimal constraints for KV260 AXI-BRAM demo
# The PL clock comes from the PS (pl_clk0) via the Zynq block.
# No I/O timing constraints needed for internal AXI paths.

# Async clock groups: separate PL fabric clock from any other domains
# (Add only if you have a second PL clock)
# set_clock_groups -asynchronous \
#     -group [get_clocks clk_pl_0] \
#     -group [get_clocks -of_objects [get_nets zynq_ultra_ps_e_0/..../clk_pl_1]]

# Bitstream settings for KV260
set_property BITSTREAM.CONFIG.UNUSEDPIN PULLNONE [current_design]
set_property CONFIG_VOLTAGE 1.8 [current_design]

# If adding PL-side UART or GPIO (external I/O), add I/O standards here:
# set_property IOSTANDARD LVCMOS18 [get_ports {some_output_port}]
# set_property PACKAGE_PIN <pin> [get_ports {some_output_port}]
```

### Relevance to Your Project
Since your AXI-BRAM demo has no external PL I/O (the UART goes through the PS MIO, not PL pins), your XDC file only needs bitstream configuration properties and possibly `set_clock_groups` if you ever add a second PL clock domain. Check that your current XDC is not accidentally applying input/output delays to AXI ports — those would be treated as I/O constraint errors.

## Kria KV260 / K26 SoM

### Key Findings
- The K26 SoM integrates a Zynq UltraScale+ MPSoC with 4× Cortex-A53 (APU) at up to 1.5 GHz, 2× Cortex-R5 (RPU), and a Mali-400 GPU, plus 4 GB LPDDR4 and 16 GB eMMC (on SM variant).
- **MIO bank layout**: MIO Bank 501 provides 19 user-definable PS MIO pins (MIO[30:26], MIO[51:38]); Bank 502 provides 26 more (MIO[77:52]). The UART0 used for USB-UART console is typically mapped to MIO[10:11] on the KV260 carrier.
- **Boot sequence**: K26 boots from QSPI (platform management firmware + U-Boot SPL), then detects carrier card and applies DT overlay. For bare-metal JTAG development, select JTAG boot mode (all boot mode pins low on KV260) to bypass the QSPI stage and load directly via Vivado Hardware Manager.
- **Power domains**: The KV260 has separate power rails for PS (VCC_PSINTLP, VCC_PSINTFP) and PL (VCCINT). The PL must be powered and the bitstream loaded before AXI-Lite transactions from PS to PL succeed.
- **Bare-metal 4K streaming example (2025.2)**: A recent Hackster.io tutorial demonstrates building a bare-metal application on KV260 with Vivado/Vitis 2025.2 targeting one A53 core — confirms the toolchain workflow for your project type.

### Code Example
```tcl
# Zynq UltraScale+ PS configuration for KV260 in Vivado IP Integrator
# Sets UART0 on MIO 10-11 (KV260 carrier board default) and pl_clk0 to 100 MHz

set_property -dict [list \
  CONFIG.PSU__UART0__PERIPHERAL__ENABLE {1} \
  CONFIG.PSU__UART0__PERIPHERAL__IO {MIO 10 .. 11} \
  CONFIG.PSU__FPGA_PL0_ENABLE {1} \
  CONFIG.PSU__CRL_APB__PL0_REF_CTRL__FREQMHZ {100} \
  CONFIG.PSU__USE__M_AXI_GP0 {1} \
  CONFIG.PSU__MAXIGP0__DATA_WIDTH {32} \
] [get_bd_cells zynq_ultra_ps_e_0]
```

### Relevance to Your Project
The `PSU__USE__M_AXI_GP0` and `PSU__MAXIGP0__DATA_WIDTH {32}` settings are what enable the HP0 AXI master port from the PS to reach your BRAM at `0xA0000000`. Confirm these are set in your `create_bd.tcl`. If `MAXIGP0` is not enabled, the PS AXI master has no path to the PL and all reads/writes will silently fail or hang.

## AMD/Xilinx Tool Updates (Vivado/Vitis 2025.x)

### Key Findings
- **Vivado 2025.1 new device support**: Versal AI Edge Series Gen 2, Versal Prime Series Gen 2, and Spartan UltraScale+ Family added.
- **New AXI Switch IP**: A fully customizable AXI Switch IP was added in 2025.1, serving as a bridge between different AXI interface types and widths. This supersedes workarounds using multiple AXI Interconnects for simple routing.
- **Unified Selective Device Installer**: Reduces download size by allowing selection of individual devices rather than entire Versal product lines.
- **IP Integrator UX improvements**: Dedicated "Clocking and Reset" and "Interrupt and AXI-4 Lite" views make auditing complex block designs much faster.
- **Vitis AI 5.1**: Uses Vitis + Vivado 2025.1.1, XRT, and PetaLinux 2025.1. The unified toolchain versioning makes combining embedded Linux + PL development easier.
- **write_bd_tcl in 2025.2**: Now supports additional export options; the exported script only contains user-modified parameters, keeping scripts clean and diff-friendly.

### Code Example
```tcl
# Export block design as clean, minimal Tcl script (Vivado 2025.1+)
# Only user-modified IP parameters are written — diffs stay readable
write_bd_tcl \
  -force \
  -include_layout \
  ./tcl/create_bd_exported.tcl

# Then rebuild headlessly using the exported script:
# vivado -mode batch -source build.tcl
# where build.tcl sources create_bd_exported.tcl

# Check current Vivado version programmatically

puts "Running Vivado $vivado_ver"
if {[package vcompare $vivado_ver "2025.1"] < 0} {
  puts "WARNING: This script was developed on 2025.1; results may differ"
}
```

### Relevance to Your Project
If you are on Vivado 2025.1, you have access to the new IP Integrator views that can quickly surface whether your BRAM Controller addresses, clock connections, and AXI widths are correctly configured — without scrolling across the block canvas. Running `write_bd_tcl` after any GUI change keeps your `create_bd.tcl` in sync and version-controllable.
