# FPGA Research Digest - 2026-11-27

## Executive Summary

- **AXI-Lite reset bug in Vivado-generated slaves**: Formal verification has found persistent VALID/READY handshake reset-handling bugs in Vivado-generated AXI-Lite slave templates; manually auditing your VHDL register logic against the ARM spec is recommended before tapeout.
- **`upgrade_ip [get_ips -all]` is dangerous**: AMD explicitly warns against using this in TCL scripts — it can silently delete sub-core IPs during a parent upgrade. Use targeted IP upgrades instead.
- **KV260 uses incremental PMU MIO config**: Unlike legacy Zynq designs, KV260 uses a PMU overlay at U-Boot stage to dynamically apply carrier-card-specific MIO configurations, so bare-metal FSBL generation can be skipped for Starter Kit targets.
- **VHDL 2019 constructs now synthesizable in Vivado 2025.1+**: Added support for VHDL 2019 simulation and synthesis constructs makes it safe to adopt modern VHDL in your `kv260_top.vhd`.
- **set_clock_groups overrides XPM CDC constraints**: If your block design uses XPM clock-domain-crossing macros, adding `set_clock_groups` will silently overwrite those constraints — apply with care in your XDC file.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- **Handshake rule**: A transfer on any AXI channel only occurs when both VALID and READY are simultaneously high. The spec forbids a master from gating VALID on READY (VALID must be held once asserted until READY responds).
- **Vivado-generated slave bugs**: ZipCPU's formal analysis of Vivado-generated AXI-Lite slaves found incorrect reset-time handling of BREADY/RVALID signals. These bugs were still present in 2020.2; their status in 2025.x is unconfirmed.
- **arready after reset**: AXI BRAM Controller documentation and community reports indicate that `arready` (read address ready) is held high immediately after reset, meaning your master can issue a read address without first checking `arready` state.
- **AXI-Stream sideband signals**: TKEEP and TSTRB are both `TDATA/8` bits wide. TKEEP marks bytes that are part of the stream; TSTRB distinguishes data bytes from position bytes. Both are optional — omit them in simple streaming designs where every byte is valid.
- **TLAST drives arbitration in AXI-Stream Interconnect**: The IP can be configured to relinquish bus grants on a TLAST transfer, which is critical for frame-based streaming pipelines.

### Code Example

```vhdl
-- Minimal AXI-Lite slave: safe reset-time behavior
-- Keep arready/awready low during reset, assert only on valid address
process(s_axi_aclk)
begin
  if rising_edge(s_axi_aclk) then
    if s_axi_aresetn = '0' then
      arready_r <= '0';  -- explicitly deassert during reset
      rvalid_r  <= '0';
      rdata_r   <= (others => '0');
    else
      -- assert arready one cycle after valid address seen
      if s_axi_arvalid = '1' and arready_r = '0' then
        arready_r <= '1';
        rdata_r   <= slv_reg(to_integer(unsigned(s_axi_araddr(5 downto 2))));
      else
        arready_r <= '0';
        if arready_r = '1' then
          rvalid_r <= '1';
        end if;
      end if;
      if rvalid_r = '1' and s_axi_rready = '1' then
        rvalid_r <= '0';
      end if;
    end if;
  end if;
end process;
```

### Relevance to Your Project

Your two AXI-Lite BRAM slaves (at `0xA0000000` and `0xA0010000`) are driven by Vivado-generated `axi_bram_ctrl` IPs. If you have added any custom AXI-Lite logic in `kv260_top.vhd`, audit the reset path using the pattern above. For the generated IPs, confirm in simulation that `arready` is not spuriously high before `aresetn` is deasserted. A failing PASS/FAIL read back from bare-metal C is often a symptom of a spurious handshake during reset.

## Vivado Block Design / IP Integrator

### Key Findings

- **Connection Automation for HPM port**: When adding an AXI BRAM controller, run Connection Automation to wire `S_AXI` to `M_AXI_HPM0_FPD` (or HPM LPD for the lower-latency path). Note the assigned base address from the Address Editor — this is the literal value your C code writes to.
- **apply_bd_automation from TCL**: AMD recommends running `apply_bd_automation` through the Vivado IDE rather than from scripts. It is recommended that you make use of this command in IP integrator through the Vivado IDE, rather than directly from Tcl scripts. If you must call it from TCL, capture the result with `write_bd_tcl` and commit the generated script.
- **IP regeneration**: After changing device targets or upgrading tools, run `validate_bd_design` and `generate_target` before exporting to XSA. Missing this step produces stale wrapper HDL.
- **Module Reference limitation**: Custom VHDL modules added via Module Reference to a block design cannot be encrypted, and have restrictions on interface inference — keep complex logic outside the BD wrapper when possible.

### Code Example

```tcl
# Recommended IP Integrator TCL pattern for adding BRAM to KV260 block design
# Run from Vivado Tcl console AFTER creating/opening a block design

# Add and configure AXI BRAM Controller
create_bd_cell -type ip -vlnv xilinx.com:ip:axi_bram_ctrl:4.1 axi_bram_ctrl_0
set_property -dict [list \
  CONFIG.DATA_WIDTH {32} \
  CONFIG.SINGLE_PORT_BRAM {1} \
] [get_bd_cells axi_bram_ctrl_0]

# Add Block Memory Generator
create_bd_cell -type ip -vlnv xilinx.com:ip:blk_mem_gen:8.4 blk_mem_gen_0
connect_bd_intf_net [get_bd_intf_pins axi_bram_ctrl_0/BRAM_PORTA] \
                    [get_bd_intf_pins blk_mem_gen_0/BRAM_PORTA]

# Run connection automation (best done in GUI, but scriptable)
apply_bd_automation -rule xilinx.com:bd_rule:axi4 \
  -config { Clk_master {Auto} Clk_slave {Auto} Clk_xbar {Auto} \
            Master {/zynq_ultra_ps_e_0/M_AXI_HPM0_FPD} \
            Slave {/axi_bram_ctrl_0/S_AXI} } \
  [get_bd_intf_pins axi_bram_ctrl_0/S_AXI]

# Save and validate
save_bd_design
validate_bd_design
```

### Relevance to Your Project

Your `create_bd.tcl` likely already does the above for `axi_bram_ctrl_0` (BRAM0 at `0xA0000000`) and `axi_bram_ctrl_2` (BRAM2 at `0xA0010000`). When migrating to Vivado 2025.x, regenerate the BD script with `write_bd_tcl` from the new tool version — do not reuse the script from an older release directly.

## Vivado TCL Scripting

### Key Findings

- **`write_bd_tcl` is version-locked**: The script it produces is tied to the Vivado release that generated it. Regenerate it whenever you change tool versions; do not cross-use scripts across major versions.
- **Never use `upgrade_ip [get_ips -all]`**: AMD explicitly warns: `CAUTION: Do not use upgrade_ip [get_ips -all]; this can cause issues with Vivado. The -all option returns sub-core IP. These IP might get removed during an upgrade of the parent and can lead to unreferenced Tcl objects.`
- **Non-Project Mode batch flow**: Headless builds use `vivado -mode batch -source build.tcl`. Key commands in sequence: `read_vhdl`, `read_xdc`, `synth_design`, `opt_design`, `place_design`, `route_design`, `write_bitstream`. You must save Design Checkpoints (DCPs) manually.
- **IP repository must precede sourcing**: When a BD script references custom or IP catalog entries, add the repository with `set_property ip_repo_paths` before calling `source create_bd.tcl`.
- **`-verbose` flag on automation commands**: Use `-verbose` on `apply_bd_automation` or `generate_target` to bypass message throttling and see all warnings during CI runs.

### Code Example

```tcl
#!/usr/bin/env tclsh
# Non-project mode batch build script for KV260 AXI-BRAM demo
# Usage: vivado -mode batch -source build_nonproject.tcl

set part "xck26-sfvc784-2LV-c"

# Read sources
read_vhdl -library work [glob ../vhdl/*.vhd]
read_xdc ../constraints/kv260_top.xdc

# Synthesis
synth_design -top kv260_top -part $part -flatten_hierarchy rebuilt
write_checkpoint -force ./checkpoints/post_synth.dcp
report_timing_summary -file ./reports/timing_synth.rpt

# Implementation
opt_design
place_design
phys_opt_design
route_design
write_checkpoint -force ./checkpoints/post_route.dcp
report_timing_summary -file ./reports/timing_route.rpt

# Bitstream
write_bitstream -force ./output/kv260_top.bit
```

### Relevance to Your Project

Your `create_bd.tcl` runs in project mode (via `open_project` / `open_bd_design`). Consider adding a companion `build_nonproject.tcl` for clean CI runs where no `.xpr` file should be checked in. This keeps your repository source-of-truth in the TCL scripts rather than binary project files.

## Vitis Bare-Metal / Standalone

### Key Findings

- **UART selection via BSP settings**: In the Vitis standalone BSP, `xil_printf()` routes to whichever UART is set as `standalone_stdin` / `standalone_stdout`. On KV260, PS UART1 (MIO-based, routed to USB-UART) is typically `UART1` at base address `0xFF010000`. Confirm in `vitis-comp.json` or the BSP configuration panel.
- **SDT-based BSP flow in 2025.1**: Vivado 2025.1 introduced System Device Tree (SDT) BSPs for new platforms. If you create a fresh KV260 platform in 2025.1, check whether the platform uses the SDT flow — it changes how drivers are auto-generated and how the BSP is configured.
- **`xil_printf` vs `printf`**: `xil_printf` is a lightweight, non-floating-point-capable print function from the standalone BSP. For bare-metal debug prints (hex addresses, integer values), `xil_printf` is sufficient and avoids pulling in the full libc `printf`.
- **Standalone BSP provides**: Timer drivers (TTC, GTC), interrupt controller (GIC) stubs, cache management (`Xil_DCacheFlush`), and memory-mapped I/O macros (`Xil_Out32`, `Xil_In32`).
- **Fixed Starter Kit boot images**: For the KV260 Starter Kit, AMD ships fixed FSBL and PMU firmware — you do not need to regenerate them. Your bare-metal app runs as the second-stage payload.

### Code Example

```c
/* Minimal AXI-Lite BRAM read/write pattern for KV260 bare-metal */
#include "xil_printf.h"
#include "xil_io.h"

#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL
#define TEST_OFFSET 0x00000000UL
#define TEST_PATTERN 0xDEADBEEFUL

static int bram_test(u32 base, const char *name)
{
    u32 readback;

    Xil_Out32(base + TEST_OFFSET, TEST_PATTERN);
    /* Memory barrier: ensure write completes before read */
    __asm__ volatile("dsb sy" ::: "memory");
    readback = Xil_In32(base + TEST_OFFSET);

    if (readback == TEST_PATTERN) {
        xil_printf("%s: PASS (wrote 0x%08X, read 0x%08X)\r\n",
                   name, TEST_PATTERN, readback);
        return 0;
    } else {
        xil_printf("%s: FAIL (wrote 0x%08X, read 0x%08X)\r\n",
                   name, TEST_PATTERN, readback);
        return -1;
    }
}

int main(void)
{
    int status = 0;
    xil_printf("KV260 AXI-BRAM Bare-Metal Test\r\n");
    status |= bram_test(BRAM0_BASE, "BRAM0");
    status |= bram_test(BRAM2_BASE, "BRAM2");
    xil_printf("Overall: %s\r\n", (status == 0) ? "PASS" : "FAIL");
    return status;
}
```

### Relevance to Your Project

The `dsb sy` data synchronization barrier after each `Xil_Out32` is critical on the Cortex-A53. Without it, the processor's out-of-order execution pipeline may issue the subsequent `Xil_In32` before the write has propagated through the AXI interconnect to the BRAM. This is the most common cause of spurious FAIL results in otherwise-correct AXI-BRAM demos.

## XDC Timing Constraints

### Key Findings

- **Ordering matters for runtime**: AMD's methodology guide recommends: (1) clock definitions, (2) generated clocks, (3) clock groups, (4) I/O delays (`set_input_delay`/`set_output_delay`), (5) timing exceptions, (6) physical constraints. Placing `set_clock_groups` before I/O delays reduces iteration.
- **`set_clock_groups` overrides XPM CDC**: If your block design uses `xpm_cdc_*` macros, their internal timing constraints are silently overridden by any `set_clock_groups` in your XDC. Be explicit about which clock pairs are async vs. synchronous.
- **`set_input_delay` skips clock ports**: When applying `set_input_delay -clock clk_pl [all_inputs]`, clock ports are automatically excluded — this is safe.
- **`set_input_delay` and `set_max_delay` interact**: Any `set_max_delay` applied to a path counts the input delay budget. If a path has both constraints, the effective max delay is `max_delay - input_delay`.
- **Timing Constraints Wizard**: Available in Vivado 2025.x, it guides you through generating XDC for all unconstrained I/O, which is useful for ensuring `kv260_top` doesn't have floating timing exceptions at the PL boundary.

### Code Example

```xdc
# KV260 XDC timing constraints skeleton for kv260_top
# Primary PL clock (100 MHz from PS clock output)
create_clock -period 10.000 -name clk_pl -waveform {0.000 5.000} [get_ports clk_pl_i]

# PS-driven generated clocks (created by IP Integrator automatically)
# set_clock_groups: mark PS and PL clocks as asynchronous where needed
# WARNING: this will override any xpm_cdc constraints in the BD
set_clock_groups -asynchronous \
  -group [get_clocks clk_pl] \
  -group [get_clocks clk_ps_*]

# I/O delays for PL-side GPIO (example, adjust to board layout)
set_input_delay  -clock clk_pl -max 2.000 [get_ports gpio_in[*]]
set_input_delay  -clock clk_pl -min 0.500 [get_ports gpio_in[*]]
set_output_delay -clock clk_pl -max 1.500 [get_ports gpio_out[*]]
set_output_delay -clock clk_pl -min 0.000 [get_ports gpio_out[*]]

# False path on asynchronous reset (active-low, board button)
set_false_path -from [get_ports aresetn_i]
```

### Relevance to Your Project

For a minimal PS-to-PL AXI-BRAM demo, most of the actual timing is internal to the AXI interconnect and is covered by the IP's own constraints. Your XDC primarily needs: (1) a `create_clock` for the PL clock input, (2) `set_false_path` for async reset, and (3) a `set_clock_groups -asynchronous` between the PS fabric clock and any external PL clock. Keep XDC constraints minimal to avoid masking real timing violations in the IP integration.

## Kria KV260 / K26 SoM

### Key Findings

- **Three MIO banks, all 1.8V on the SOM**: The K26 has three MIO banks. Bank 0 is consumed by on-SOM peripherals (eMMC, QSPI, etc.). Banks 1 and 2 are exposed through the SOM connector for carrier card use. All three banks are powered at 1.8V by the SOM itself — do not drive them at 3.3V.
- **Incremental PMU MIO config (not static like legacy Zynq)**: KV260 Starter Kit uses a PMU overlay applied by U-Boot to configure the carrier-card-specific MIO (instead of the legacy static FSBL configuration). This is what makes the same K26 SOM work on both KV260 and KR260 carrier cards.
- **Skip FSBL generation for Starter Kit targets**: Because the KV260 boot images are fixed, you do not need to generate or build FSBL. Your bare-metal project is the second payload loaded by the existing boot chain.
- **PL power domain control via PMU**: The K26 PL power domain can be managed by the PMU firmware. Refer to UG1137 for software-controlled power-down APIs. This matters for power-saving applications where you want to gate the PL fabric.
- **Boot mode**: KV260 Starter Kit defaults to SD card boot (SD1, MIO pins 46–51). For bare-metal development, use the same SD card slot — place your BOOT.BIN on a FAT32 partition. JTAG boot is also available via the JTAG header.
- **EMIO**: EMIO signals route PL logic to MPS SoC I/O infrastructure but are constrained by MIO bank voltages. For custom carrier card designs, EMIO-based GPIO at 1.8V is the safest option.

### Code Example

```tcl
# Vivado board part selection for KV260 Starter Kit
# Use this at the top of your create_bd.tcl or project creation script
set_property BOARD_PART xilinx.com:kv260_som:part0:1.4 [current_project]

# When creating the Zynq UltraScale+ PS block in the BD,
# apply the board preset to auto-configure MIO:
set_property -dict [list CONFIG.preset {KV260}] \
  [get_bd_cells zynq_ultra_ps_e_0]

# After apply_board_preset, MIO is configured for:
#   UART1  -> MIO 48/49 (USB-UART via USB bridge)
#   SD1    -> MIO 46-51 (boot SD card)
#   I2C1   -> MIO 24/25 (Starter Kit I2C bus)
# PL clock output: pl_clk0 at 100 MHz by default
```

### Relevance to Your Project

Always start your block design with `set_property BOARD_PART` and apply the KV260 preset to the Zynq PS block. This correctly configures the UART1 MIO (which is your `USB-UART` path for `xil_printf` output) and the PL clock. Without the preset, UART1 may not be active and you will see no output from your bare-metal application even when it runs successfully.
