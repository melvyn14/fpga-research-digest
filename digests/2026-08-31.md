# FPGA Research Digest - 2026-08-31

## Executive Summary

- **BRAM/FIFO IP catalog breaking change (Vivado 2025.1+):** `Block Memory Generator` and `FIFO Generator` IPs are no longer directly instantiable from the IP Catalog in Vivado 2025.1 and later — they must be used inside a block design or via XPM macros. This directly impacts the KV260 AXI-BRAM project's `create_bd.tcl` workflow.
- **AXI-Lite VALID/READY invariant:** A source must assert VALID and hold it until READY is seen — the reverse (waiting for READY before asserting VALID) is a protocol violation that passes simulation but fails in real hardware with slow or stalled masters.
- **Backpressure on READY signals is the #1 AXI-Lite bug:** If the master holds BREADY low, the slave must hold AWREADY/WREADY low too; this corner-case is rarely exercised in simple test benches and manifests as intermittent read-back corruption — exactly the kind of failure seen in PS-to-PL BRAM tests.
- **Kria KV260 bare-metal must use QSPI32 boot mode:** The K26 SOM ships with no FW in eMMC; QSPI32 is the preset boot mode. Any bare-metal `.elf` must be loaded via JTAG or packaged into a BOOT.BIN for QSPI flashing.
- **Non-project mode TCL in Vivado 2026.1:** AMD updated the UG892 non-project mode docs; `exec` is now required for all OS-level calls inside batch scripts — bare shell commands are silently dropped.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- **VALID must not wait for READY.** The AXI spec requires that a source assert VALID independently; creating a combinational dependency where VALID only goes high after READY is asserted forms a deadlock cycle. Xilinx's own early example AXI-Lite slave cores (Vivado ≤2018.3) contained this bug.
- **Backpressure is the silent killer.** When a master stalls (holds BREADY or RREADY low), the slave's AWREADY, WREADY, and ARREADY must also de-assert. Skipping this in slave RTL passes simulation (test benches rarely hold BREADY low) but corrupts data in real hardware.
- **Latched handshake flags must clear on the response beat.** Internal flags like `aw_hs_done` and `w_hs_done` — used to track when the address and data channels have both completed — must be cleared on the B-channel handshake (BVALID & BREADY), not on the next rising edge.
- **AXI4-Lite is 32-bit only, no bursts.** The AXI BRAM Controller configured in AXI4-Lite mode accepts only a 32-bit data bus, single-beat transfers. Attempting narrow or unaligned transfers is silently ignored by the IP core.
- **Dual-port BRAM controller:** Port A handles writes, Port B handles reads by default. In single-port mode, Port A handles both — important for timing analysis since both channels share the same BRAM port mux.

### Code Example

```vhdl
-- Correct AXI-Lite slave write handshake — clears aw_hs_done on B-channel
process(clk)
begin
  if rising_edge(clk) then
    if rst_n = '0' then
      aw_hs_done <= '0';
      w_hs_done  <= '0';
      S_AXI_BVALID <= '0';
    else
      -- Latch address handshake
      if S_AXI_AWVALID = '1' and S_AXI_AWREADY = '1' then
        aw_hs_done <= '1';
      end if;
      -- Latch data handshake
      if S_AXI_WVALID = '1' and S_AXI_WREADY = '1' then
        w_hs_done <= '1';
      end if;
      -- Issue write response only when both channels complete
      if aw_hs_done = '1' and w_hs_done = '1' then
        S_AXI_BVALID <= '1';
        S_AXI_BRESP  <= "00";
        -- CRITICAL: clear flags on response handshake, not before
        if S_AXI_BREADY = '1' then
          S_AXI_BVALID <= '0';
          aw_hs_done   <= '0';
          w_hs_done    <= '0';
        end if;
      end if;
    end if;
  end if;
end process;
```

### Relevance to Your Project

Your `kv260_top.vhd` top-level wires the PS AXI Master (HP0/GP0) through the AXI Interconnect to the BRAM controllers at `0xA0000000` and `0xA0010000`. The write-then-read pattern in `main.c` will pass simple bench tests even with broken backpressure handling, because the PS AXI master rarely stalls its BREADY line during single-word transfers. Adding a formal verification pass with ZipCPU's `faxil_slave.v` property set (open source) would catch these without needing a full SV environment.

## Vivado Block Design / IP Integrator

### Key Findings

- **BRAM/FIFO IPs removed from direct IP Catalog in 2025.1+.** `Block Memory Generator` and `FIFO Generator` can no longer be instantiated standalone from the catalog. Use them exclusively inside Block Design or switch to XPM (`xpm_memory_bram`, `xpm_fifo_sync`) in RTL. This is a silent breaking change for scripts that called `create_ip -name blk_mem_gen`.
- **Address Editor auto-assign is the fix for unmapped peripheral errors.** After connecting an AXI BRAM Controller via `Run Connection Automation`, the address editor sometimes leaves the slave unmapped. Right-click → `Auto-Assign Address` (or `assign_bd_address` in TCL) resolves the validation error.
- **AXI4 vs AXI4-Lite for BRAM:** Using AXI4 (full) with the BRAM Controller enables burst transactions and higher bandwidth. For the PS-to-PL test pattern, AXI4-Lite is sufficient and simplifies address decoding, but AXI4 mode allows future DMA-based burst fills with much higher throughput.
- **IP Integrator in Non-Project Mode requires `open_bd_design` before TCL edits.** When scripting block design changes in non-project mode (Vivado 2025.1 UG994), the BD must be explicitly opened before `create_bd_cell` or `connect_bd_net` calls, otherwise the commands silently no-op.
- **Regenerate Output Products after every IP change.** After any IP parameter change or BD modification, call `generate_target all [get_files *.bd]` before synthesis. Stale output products are a common source of "IP locked" errors.

### Code Example

```tcl
# Vivado 2025.1 compatible: use XPM instead of blk_mem_gen for RTL
# Inside a bd.tcl or as an RTL instantiation

# Option A: Block Design (preferred in 2025.1+)
create_bd_cell -type ip -vlnv xilinx.com:ip:axi_bram_ctrl:4.1 axi_bram_ctrl_0
set_property CONFIG.SINGLE_PORT_BRAM {1} [get_bd_cells axi_bram_ctrl_0]
set_property CONFIG.PROTOCOL {AXI4LITE}   [get_bd_cells axi_bram_ctrl_0]
create_bd_cell -type ip -vlnv xilinx.com:ip:emb_mem_gen:1.0 emb_mem_gen_0
connect_bd_intf_net [get_bd_intf_pins axi_bram_ctrl_0/BRAM_PORTA] \
                    [get_bd_intf_pins emb_mem_gen_0/BRAM_PORTA]
assign_bd_address [get_bd_addr_segs {axi_bram_ctrl_0/S_AXI/Mem0}]
set_property offset 0xA0000000 \
  [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property range 64K \
  [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
```

### Relevance to Your Project

Your `create_bd.tcl` likely calls `create_ip -name blk_mem_gen` to instantiate the Block Memory Generators for BRAM0 and BRAM2. Under Vivado 2025.1, this call will fail silently or produce an "IP not found" error. The fix is to switch to `emb_mem_gen` (the new Embedded Memory Generator IP name) or use `xpm_memory_bram` in your VHDL top. The address assignments at `0xA0000000` (BRAM0) and `0xA0010000` (BRAM2) remain valid — only the IP name changes.

## Vivado TCL Scripting

### Key Findings

- **Non-project mode: you own the flow.** Vivado does not create intermediate files, checkpoints, or reports automatically. Every `write_checkpoint`, `report_timing_summary`, and `write_bitstream` call must be explicit in the script. Missing a checkpoint means losing synthesis results on crash.
- **Batch mode drops unknown commands silently.** In `vivado -mode batch -source script.tcl`, any command that isn't a Vivado or Tcl built-in is silently discarded — unlike interactive mode where it falls through to the OS shell. Use `exec <cmd>` explicitly for any system calls (`exec mkdir -p output`, `exec cp ...`).
- **Vivado 2026.1 UG892 update:** AMD published updated non-project mode TCL guidance in 2026.1, clarifying that `read_vhdl -vhdl2008` is required for VHDL-2008 constructs and that `set_part` must precede any `read_*` calls in non-project mode.
- **IP Integrator in non-project mode:** After `create_project -in_memory`, call `open_bd_design` explicitly before modifying the block design. `generate_target` must be called before `synth_design` to produce wrapper HDL from the BD.
- **`write_bd_tcl` is your BD export tool.** To reproduce a block design from scratch, use `write_bd_tcl -force output/create_bd.tcl` from within Vivado — this exports a re-runnable script that correctly handles all IP connections and parameter settings.

### Code Example

```tcl
#!/usr/bin/env tclsh
# Non-project mode batch script for KV260 AXI-BRAM build
# Run: vivado -mode batch -source build.tcl

set outputDir ./output
exec mkdir -p $outputDir

# 1. Set target part first (required before read_* in non-project mode)
set_part xck26-sfvc784-2LV-c

# 2. Read sources
read_vhdl -vhdl2008 [glob ../vhdl/*.vhd]
read_xdc ../constraints/kv260_top.xdc

# 3. Open and generate block design
open_bd_design [get_files *.bd]
generate_target all [get_files *.bd]
make_wrapper -files [get_files *.bd] -top

# 4. Synthesize
synth_design -top kv260_top_wrapper -part xck26-sfvc784-2LV-c
write_checkpoint -force $outputDir/post_synth.dcp
report_timing_summary -file $outputDir/post_synth_timing.rpt

# 5. Implement
opt_design
place_design
route_design
write_checkpoint -force $outputDir/post_route.dcp
report_timing_summary -file $outputDir/post_route_timing.rpt

# 6. Generate bitstream
write_bitstream -force $outputDir/kv260_top.bit
write_hw_platform -fixed -force -file $outputDir/kv260_top.xsa
```

### Relevance to Your Project

Your `create_bd.tcl` is the canonical entry point for the block design. Wrapping it with the full non-project mode shell above gives a single `vivado -mode batch -source build.tcl` invocation that produces a `.bit` and `.xsa` — eliminating the need to open the Vivado GUI for routine rebuilds. The `write_hw_platform` output is what Vitis ingests to generate the BSP for your bare-metal `main.c`.

## Vitis Bare-Metal / Standalone

### Key Findings

- **Standalone BSP is a minimal, single-threaded HAL.** It provides startup (`_boot.S` → `main`), cache/MMU init for Cortex-A53, and the `xil_printf` formatted print — which routes to UART0 (PS UART, typically `/dev/ttyUSB1` at 115200 8N1 on KV260).
- **`xil_printf` is NOT `printf`.** It uses a reduced format string parser: `%d`, `%x`, `%s`, `%u` work; `%f` (float) does NOT work without enabling the full `libc` printf via BSP settings. Use `xil_printf("Val: 0x%08X\r\n", val)` for BRAM read-back diagnostics.
- **Linker script `lscript.ld` controls memory map.** The default Vitis linker script places `.text` in DDR at `0x00000000`. For bare-metal on KV260 with the PS, ensure the DDR base is `0x00000000` (the K26 maps 2 GB of DDR starting at 0x0). Accidentally linking to OCM (On-Chip Memory, 256 KB at `0xFFFC0000`) causes size overflows.
- **Cache coherency with AXI BRAM:** The Cortex-A53 data cache may buffer writes to the AXI-mapped BRAM range. For bare-metal AXI-Lite reads to be coherent, either use `Xil_DCacheFlushRange(BRAM_BASE, BRAM_SIZE)` after writes or mark the BRAM address range as Device/Strongly-Ordered in the MMU translation table (the standalone BSP does this by default for PL peripheral regions when the XSA MPU settings are correct).
- **BSP parameter: `stdin`/`stdout` must match the physical UART.** In Vitis BSP settings, set `stdin` and `stdout` to `psu_uart_0` (or `psu_uart_1` depending on which PS UART routes to the KV260 USB-UART bridge). Wrong selection means `xil_printf` output appears on no terminal.

### Code Example

```c
/* main.c — bare-metal AXI-BRAM write/read test for KV260
 * BRAM0 @ 0xA0000000, BRAM2 @ 0xA0010000 */
#include "xil_printf.h"
#include "xil_cache.h"
#include "xil_io.h"

#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL
#define BRAM_WORDS  16

static const u32 pattern[BRAM_WORDS] = {
    0xDEADBEEF, 0xCAFEBABE, 0x12345678, 0xABCDEF01,
    0x00FF00FF, 0xFF00FF00, 0xAAAA5555, 0x55555555,
    0xAAAAAAAA, 0x0F0F0F0F, 0xF0F0F0F0, 0x01234567,
    0x89ABCDEF, 0xFEDCBA98, 0x76543210, 0xC0FFEE00
};

static int bram_test(u32 base, const char *name) {
    int pass = 1;
    /* Write phase */
    for (int i = 0; i < BRAM_WORDS; i++)
        Xil_Out32(base + (i * 4), pattern[i]);

    /* Flush D-cache to ensure writes reach AXI fabric */
    Xil_DCacheFlushRange(base, BRAM_WORDS * 4);

    /* Read-back and verify */
    for (int i = 0; i < BRAM_WORDS; i++) {
        u32 rd = Xil_In32(base + (i * 4));
        if (rd != pattern[i]) {
            xil_printf("[%s] FAIL @ 0x%08X: wrote 0x%08X read 0x%08X\r\n",
                       name, base + (i*4), pattern[i], rd);
            pass = 0;
        }
    }
    return pass;
}

int main(void) {
    xil_printf("\r\n=== KV260 AXI-BRAM Test ===\r\n");
    xil_printf("BRAM0: %s\r\n", bram_test(BRAM0_BASE, "BRAM0") ? "PASS" : "FAIL");
    xil_printf("BRAM2: %s\r\n", bram_test(BRAM2_BASE, "BRAM2") ? "PASS" : "FAIL");
    xil_printf("=== Done ===\r\n");
    return 0;
}
```

### Relevance to Your Project

The `Xil_DCacheFlushRange` call is the key addition over a naive `*(volatile u32*)` approach. Without it, the Cortex-A53 L1/L2 cache may service the read from cache rather than the AXI fabric, making the test pass even if the BRAM write never reached the PL — a false PASS. The BSP's standalone platform also zero-initializes DDR and enables the D-cache before `main()`, so you get this behavior for free but must explicitly flush when crossing the coherency boundary to PL peripherals.

## XDC Timing Constraints

### Key Findings

- **`set_input_delay` / `set_output_delay` are I/O interface constraints, not internal path constraints.** They describe external path delays relative to a clock edge at the device boundary. For internal PS-to-PL AXI paths on Zynq, these constraints are NOT needed — the AXI clock is generated inside the PS and Vivado automatically constrains the PS-PL interface via the Zynq IP's built-in constraints.
- **`create_clock` on PL clocks only.** The PS generates clocks (`pl_clk0` through `pl_clk3`). In XDC, define `create_clock` only for clocks that originate from external pins (e.g., a differential clock input on an HP bank). Do NOT re-create the PS-generated PL clocks — the Zynq PS IP already defines them internally.
- **Use `set_clock_groups -asynchronous` for unrelated clock domains.** If your design has multiple clock domains (e.g., `pl_clk0` at 100 MHz for AXI and a separate `pl_clk1` at 200 MHz for a data path), declare them asynchronous to prevent Vivado from trying to time crossing paths that are handled by CDC logic.
- **False paths on configuration/reset signals.** Set `set_false_path -from [get_ports sys_resetn]` for your external reset input to exclude it from setup/hold analysis — synchronizer stages will handle the metastability, not the timing engine.
- **Kria KV260 I/O timing:** For external pins on HP banks (e.g., Pmod connectors on the carrier card), use a virtual clock as the reference for `set_input_delay`/`set_output_delay` when the external device doesn't share the FPGA's clock.

### Code Example

```xdc
## kv260_top.xdc — Timing constraints for KV260 AXI-BRAM demo

# PS-generated AXI clock — do NOT redefine here; Zynq IP defines it.
# Only uncomment below if using an external clock input on a PL pin:
# create_clock -period 10.000 -name pl_ext_clk [get_ports ext_clk_p]

# Declare PS PL clocks as the primary timing reference
# (Vivado picks up pl_clk0 from the PS IP automatically)

# Asynchronous clock groups — prevent cross-domain timing if using >1 PL clock
set_clock_groups -asynchronous \
  -group [get_clocks -of_objects [get_pins zynq_ultra_ps_e_0/inst/PS8_i/PLCLK[0]]] \
  -group [get_clocks -of_objects [get_pins zynq_ultra_ps_e_0/inst/PS8_i/PLCLK[1]]]

# False path on async reset from PS
set_false_path -from [get_pins zynq_ultra_ps_e_0/inst/PS8_i/PLRESET[0]]

# I/O timing for external signals on carrier card (example: PMOD)
# Virtual clock for off-chip interface that uses board trace + external device timing
create_clock -period 20.000 -name virt_pmod_clk
set_input_delay  -clock virt_pmod_clk -max 3.0 [get_ports {pmod_in[*]}]
set_input_delay  -clock virt_pmod_clk -min 1.0 [get_ports {pmod_in[*]}]
set_output_delay -clock virt_pmod_clk -max 4.0 [get_ports {pmod_out[*]}]
set_output_delay -clock virt_pmod_clk -min 1.5 [get_ports {pmod_out[*]}]
```

### Relevance to Your Project

For a pure PS-to-PL AXI-BRAM demo with no external I/O other than the USB-UART (which is PS MIO and needs no PL XDC constraints), your XDC file needs almost nothing. The Zynq PS IP handles all AXI clock and reset constraints internally. The most common mistake is adding duplicate `create_clock` constraints for `pl_clk0`, which creates a confusing "multiple clocks on the same source" warning that can be ignored but pollutes the timing report. Clean XDC = fast implementation.

## Kria KV260 / K26 SoM

### Key Findings

- **Boot mode is QSPI32 by default.** The K26 SOM ships with preset boot mode set to QSPI32 (mode pins are hardwired on the SOM240_1 connector). For bare-metal development, load your `.elf` via JTAG through Vitis/`xsdb` — no BOOT.BIN is needed for iterative debug. For deployment, package into BOOT.BIN with `bootgen`.
- **USB-UART is PS UART1 (MIO 38/39), not a PL pin.** The KV260 carrier card routes PS MIO 38 (TX) and MIO 39 (RX) to the USB-UART bridge. In Vitis BSP, set `stdout=psu_uart_1` to get `xil_printf` output. No XDC constraints needed for this path.
- **EMIO GPIO connects PS GPIO to PL fabric.** PS GPIO banks 2 and 3 (EMIO, 32 pins each) are available through the Zynq UltraScale+ PS GPIO block. In the block design, enabling GPIO EMIO and exporting it to a PL port lets you toggle PL-side logic from bare-metal C with `XGpioPs_WritePin()`.
- **Power domains:** The K26 SOM separates PS power (VCCINT_PS, VCCAUX_PS) from PL power (VCCINT, VCCAUX). The PL does not power on until the PS has completed its power sequence. In bare-metal, your `.elf` runs entirely in the PS domain; the PL is programmed separately via the bitstream loaded by the FSBL or `xsdb`.
- **SOM240_1 connector pin mapping:** PL I/O on the KV260 is accessible through the SOM240_1 connector rows. HP I/O bank 64, 65, and 66 pins route to the Pmod and Arduino headers on the carrier card. LVDS pairs in bank 64 are available for differential interfaces.

### Code Example

```c
/* Bare-metal EMIO GPIO toggle on KV260 — useful for debugging PL connectivity
 * Requires EMIO GPIO width >= 1 enabled in Zynq PS IP block design */
#include "xgpiops.h"
#include "xparameters.h"

#define GPIO_DEVICE_ID  XPAR_XGPIOPS_0_DEVICE_ID
#define EMIO_PIN_BASE   54   /* PS GPIO: MIO is 0-77, EMIO starts at 78 on ZynqMP */
                              /* But XGpioPs treats EMIO as offset 78+bank_offset */

static XGpioPs GpioInstance;

void emio_toggle_init(void) {
    XGpioPs_Config *cfg = XGpioPs_LookupConfig(GPIO_DEVICE_ID);
    XGpioPs_CfgInitialize(&GpioInstance, cfg, cfg->BaseAddr);
    /* Set EMIO pin 0 (absolute pin 78) as output */
    XGpioPs_SetDirectionPin(&GpioInstance, 78, 1);
    XGpioPs_SetOutputEnablePin(&GpioInstance, 78, 1);
}

void emio_heartbeat(void) {
    static int state = 0;
    XGpioPs_WritePin(&GpioInstance, 78, state);
    state ^= 1;
}
```

### Relevance to Your Project

Your project uses only PS-to-PL AXI (no EMIO GPIO), so the EMIO section is a future extension. The immediately relevant finding is the **UART assignment**: if `xil_printf` produces no output on your terminal, check that the Vitis BSP `stdout` parameter is set to `psu_uart_1` (the USB-visible UART) and that your terminal is connected at 115200 8N1. The boot flow detail (JTAG `.elf` load vs. BOOT.BIN) is also directly applicable for iterating on `main.c` without reflashing QSPI.

## AMD/Xilinx Tool Updates (2025.x / 2026.x)

### Key Findings

- **Vivado 2025.1/2025.2 — BRAM/FIFO IP catalog removal:** `Block Memory Generator` (blk_mem_gen) and `FIFO Generator` IPs are no longer available for standalone instantiation. Use `Embedded Memory Generator` (emb_mem_gen) inside block design, or use `xpm_memory_bram` / `xpm_fifo_sync` XPM macros in RTL. This is the single largest breaking change for existing TCL build scripts.
- **Vivado 2026.1 — Non-project mode TCL docs updated (UG892):** AMD published clearer guidance on the `exec` requirement in batch mode and updated the non-project mode TCL example scripts. Available at docs.amd.com.
- **Vitis 2025.1 — VEK280 AIE-ML support:** 20 new L1 APIs and 6 new L2 APIs for AIE-ML targets. Not directly relevant to KV260 bare-metal, but the underlying IDE infrastructure updates (Eclipse-based project handling) affect all platforms.
- **Vitis 2025.1 known issue — RHEL/CentOS LD_LIBRARY_PATH conflict:** On RHEL 8.3 and CentOS 8.2, Vitis GUI projects fail due to a `LD_LIBRARY_PATH` library conflict. Workaround: remove `${env_var:LD_LIBRARY_PATH}` from the project environment settings in the Vitis IDE.
- **Vivado 2025.2 — IP Catalog taxonomy update:** IP descriptions and catalog groupings were reorganized with no functional impact. However, TCL scripts that used `get_ipdefs -filter {VLNV =~ *blk_mem_gen*}` will return empty sets and must be updated to `*emb_mem_gen*`.
- **Vivado 2026.1 — Latest stable release as of August 2026.** Available from the AMD adaptive computing download portal.

### Code Example

```tcl
# Migration: blk_mem_gen → emb_mem_gen in create_bd.tcl for Vivado 2025.1+

# OLD (Vivado 2024.2 and earlier — no longer works in 2025.1+):
# create_bd_cell -type ip -vlnv xilinx.com:ip:blk_mem_gen:8.4 blk_mem_gen_0

# NEW (Vivado 2025.1+): Use Embedded Memory Generator inside block design
create_bd_cell -type ip -vlnv xilinx.com:ip:emb_mem_gen:1.0 emb_mem_gen_0
set_property CONFIG.MEMORY_TYPE {Simple_Dual_Port_RAM} [get_bd_cells emb_mem_gen_0]
set_property CONFIG.WRITE_WIDTH_A {32} [get_bd_cells emb_mem_gen_0]
set_property CONFIG.READ_WIDTH_B  {32} [get_bd_cells emb_mem_gen_0]
set_property CONFIG.WRITE_DEPTH_A {1024} [get_bd_cells emb_mem_gen_0]

# OR: Use XPM macro in VHDL RTL (no IP Catalog dependency)
# -- In VHDL source, add to library/use clauses:
# library xpm;
# use xpm.vcomponents.all;
#
# -- Then instantiate:
# xpm_memory_bram_inst : xpm_memory_bram
#   generic map (
#     MEMORY_SIZE        => 32768,  -- bits (1K x 32)
#     MEMORY_PRIMITIVE   => "block",
#     WRITE_DATA_WIDTH_A => 32,
#     READ_DATA_WIDTH_B  => 32,
#     BYTE_WRITE_WIDTH_A => 8,
#     ADDR_WIDTH_A       => 10,
#     ADDR_WIDTH_B       => 10
#   )
#   port map (
#     clka  => axi_clk, ena => '1', wea => bram_we,
#     addra => bram_addr_w, dina => bram_din,
#     clkb  => axi_clk, enb => '1',
#     addrb => bram_addr_r, doutb => bram_dout
#   );
```

### Relevance to Your Project

This is the most urgent update for your project. If you upgrade from Vivado 2024.x to 2025.1+ and run `create_bd.tcl` unchanged, the BRAM instantiation will fail silently or error out. The migration path is straightforward: replace `blk_mem_gen` with `emb_mem_gen` and update the VLNV string. All AXI BRAM Controller connections, address assignments, and port mappings remain identical — only the memory generator IP name changes.
