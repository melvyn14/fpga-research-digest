# FPGA Research Digest - 2026-09-11

## Executive Summary

- **AXI address 1K limit bug in Vivado 2025**: Reports confirm that Vivado 2025.x limits AXI full peripheral decoding to ~1 KB of usable address space; changing `C_S_AXI_ADDR_WIDTH` to 16 does not resolve it — directly relevant if you expand BRAM0/BRAM2 beyond current 4K ranges.
- **Silent BRAM address boundary overrun**: Reads past the configured BRAM controller address space return `0x00000000` and writes return OKAY — your PASS/FAIL logic could silently miss out-of-bounds accesses without explicit boundary checks in main.c.
- **BREADY/RREADY backpressure omission**: If the PS holds BREADY or RREADY low (can happen during interrupt preemption in bare-metal), the slave must deassert AWREADY/ARREADY — easy to miss in simulation-only validation.
- **xil_printf has no floating-point support**: Ensure all diagnostic prints in main.c use integer/hex format specifiers; passing a float to xil_printf silently produces garbage output.
- **Vivado 2025.1 IP update core dump**: After IP upgrades, a core dump may occur — save the block design and let Vivado restart before re-running synthesis, as documented in the 2025.1 IP release notes.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- All five AXI channels (AW, W, B, AR, R) use VALID/READY handshake; a transfer occurs only when both are asserted on the same rising clock edge.
- **Critical backpressure pitfall**: If the PS master de-asserts BREADY (write response ready) — which can happen during a bare-metal IRQ handler — the BRAM controller slave must hold its response. On the read side, if RREADY goes low the slave must hold ARREADY low. These corner cases are rarely exercised in simulation-only testing.
- **Simultaneous R/W burst loss**: If `AWVALID && AWREADY` and `ARVALID && ARREADY` are both true in the same cycle, both bursts can be silently lost in some AXI-Lite slave implementations. The PS AXI-Lite master serialises these, but custom PL slaves must guard against it.
- **AXI-Stream TKEEP vs TSTRB**: `TKEEP=1` means the byte lane is live (keep it); `TSTRB=1, TKEEP=1` means it is a data byte; `TSTRB=0, TKEEP=1` means it is a position byte. Most Xilinx IPs only inspect TKEEP — tie TSTRB to TKEEP unless the downstream IP explicitly requires otherwise.
- **TLAST obligation**: Every AXI-Stream packet must assert TLAST on the final beat; omitting it causes the sink IP (e.g. DMA) to stall waiting for end-of-packet.

### Code Example

```vhdl
-- Minimal AXI-Lite slave write path with correct BREADY backpressure handling
-- If bready_i is low, the slave must not accept a new write address
process(clk)
begin
  if rising_edge(clk) then
    if s_axi_bready = '1' and bvalid_r = '1' then
      bvalid_r  <= '0';   -- response consumed
      awready_r <= '1';   -- re-open address channel
    end if;
    if s_axi_awvalid = '1' and awready_r = '1' then
      awready_r <= '0';
      -- latch address, proceed to data phase
    end if;
  end if;
end process;
s_axi_awready <= awready_r;
s_axi_bvalid  <= bvalid_r;
s_axi_bresp   <= "00";  -- OKAY
```

### Relevance to Your Project

Your two BRAM controllers at `0xA0000000` (BRAM0) and `0xA0010000` (BRAM2) are AXI-Lite slaves. The PS Cortex-A53 is the master. Bare-metal C code performs blocking reads/writes, so BREADY de-assertion is unlikely in practice — but if you add interrupt-driven printing via UART, re-examine the write loop to confirm BREADY is never held low mid-transaction.

## Vivado Block Design / IP Integrator

### Key Findings

- **Connection Automation** auto-adds a `proc_sys_reset` and `axi_interconnect` IP when you run "Run Connection Automation" after dropping in `zynq_ultra_ps_e_0` and BRAM controllers — saves wiring all reset and clock signals manually.
- **Address Editor**: Each AXI slave's base address and range are set here. For 4 KB of BRAM, set Range = 4K and Offset = `0xA000_0000` (BRAM0) / `0xA001_0000` (BRAM2). Mismatches between the address editor and your C pointer arithmetic are the #1 source of FAIL results.
- **Regeneration tip**: After editing the block design TCL or upgrading IPs, use **File → Close Block Design → Reopen** before re-running synthesis; Vivado 2025 sometimes does not detect changes otherwise.
- **Validate Design (F6)** before generating the wrapper — it catches unconnected ports, clock-domain crossing warnings, and missing address assignments before synthesis wastes time.
- **Save frequently** with Ctrl+S; the block design journal (`*.jou`) records all changes, useful for reconstructing TCL if the project file gets corrupted.

### Code Example

```tcl
# Assign BRAM addresses in the address editor via TCL (from create_bd.tcl)
assign_bd_address [get_bd_addr_segs {axi_bram_ctrl_0/S_AXI/Mem0}] \
    -range 4K \
    -offset 0xA0000000

assign_bd_address [get_bd_addr_segs {axi_bram_ctrl_1/S_AXI/Mem0}] \
    -range 4K \
    -offset 0xA0010000
```

### Relevance to Your Project

Your `create_bd.tcl` drives the block design programmatically. The `assign_bd_address` calls above must match the literal pointer values used in main.c (`(volatile uint32_t *)0xA0000000` and `0xA0010000`). Any range mismatch silently wraps addresses, turning PASS into FAIL for patterns written near the top of the address window.

## Vivado TCL Scripting

### Key Findings

- **Batch mode invocation**: `vivado -mode batch -source create_bd.tcl` runs the script headless and exits with a non-zero code on error — ideal for CI/CD integration.
- **Non-project mode** (no `.xpr` file) is more portable: read sources → synthesize → implement → write_bitstream in one script. The block design itself must be created with IP Integrator TCL commands within this flow.
- **IP Integrator in non-project mode**: Call `open_bd_design` after `create_bd_design`; the design lives in memory and must be written to disk with `write_bd_tcl` before `close_bd_design`.
- **Critical**: In non-project mode, always call `update_compile_order -fileset sources_1` after adding sources; otherwise the synthesis run may not find all files.
- **Error propagation**: Wrap key steps in `if {[catch {synth_design -top ...} err]} { puts "ERROR: $err"; exit 1 }` to surface failures in CI logs.

### Code Example

```tcl
# Non-project mode flow skeleton for kv260-axi-bram-demo
set outputDir ./output
file mkdir $outputDir

# Read sources
read_vhdl    [glob ./vhdl/*.vhd]
read_xdc     ./constraints/kv260.xdc
read_ip      [glob ./ip/*.xci]

# Synthesize
synth_design -top kv260_top -part xck26-sfvc784-2LV-c

# Implement
opt_design
place_design
route_design

# Output
write_bitstream -force $outputDir/kv260_top.bit
write_hw_platform -fixed -include_bit -force $outputDir/kv260_top.xsa

puts "Build complete: $outputDir/kv260_top.bit"
```

### Relevance to Your Project

Your existing `create_bd.tcl` can be called from a non-project master script like the above, making the entire Vivado flow reproducible with a single command — no manual GUI steps needed. Add this to a Makefile or CI action triggered on pushes to `main`.

## Vitis Bare-Metal / Standalone

### Key Findings

- **xil_printf limitations**: `xil_printf` has no floating-point support and interprets `\n` as newline only (not `\r\n`). For terminals that require CR+LF, either use `\r\n` explicitly or switch to `printf` from the newlib C library (at the cost of larger code size).
- **stdout UART binding**: In the BSP settings, `stdout` must be explicitly bound to the UART peripheral (`psu_uart_1` on KV260) under **BSP Settings → standalone → stdin / stdout**. If left unset, `xil_printf` produces no output even with correct hardware.
- **Linker script memory regions**: Vitis auto-generates `lscript.ld` mapping `.text` to OCM or DDR. For the AXI-BRAM demo, all code should live in DDR (`ps_ddr_0`); ensure the linker script does not place `.data` in the same region as your BRAM test buffers.
- **Cache coherence**: On Cortex-A53, the AXI-Lite port bypasses the L1/L2 cache. Bare-metal C `*(volatile uint32_t*)addr` is correct for MMIO — the `volatile` keyword prevents the compiler from caching the load/store in a register.
- **Interrupt controller (GIC)**: For Zynq UltraScale+, use `XScuGic` driver. IRQ IDs for PL fabric interrupts start at 121 (IRQ_F2P[0]) — relevant when you add interrupt-driven BRAM completion signalling.

### Code Example

```c
/* Correct bare-metal AXI-Lite BRAM write/read with volatile pointer */
#include "xil_printf.h"
#include "xparameters.h"

#define BRAM0_BASE  0xA0000000UL
#define BRAM1_BASE  0xA0010000UL
#define TEST_WORDS  4

static volatile uint32_t * const bram0 = (volatile uint32_t *)BRAM0_BASE;
static volatile uint32_t * const bram1 = (volatile uint32_t *)BRAM1_BASE;

int test_bram(volatile uint32_t *base, uint32_t base_addr) {
    for (int i = 0; i < TEST_WORDS; i++) base[i] = 0xDEAD0000 + i;
    for (int i = 0; i < TEST_WORDS; i++) {
        if (base[i] != 0xDEAD0000 + i) {
            xil_printf("FAIL @ 0x%08X: expected 0x%08X got 0x%08X\r\n",
                       base_addr + i*4, 0xDEAD0000 + i, base[i]);
            return -1;
        }
    }
    xil_printf("PASS: BRAM @ 0x%08X\r\n", base_addr);
    return 0;
}
```

### Relevance to Your Project

The `volatile` qualifier on your BRAM pointers is essential — without it, GCC may fold back-to-back reads into a single load and the PASS/FAIL comparison never re-reads from hardware. Use `\r\n` in xil_printf format strings so PuTTY/minicom display correctly over USB-UART.

## XDC Timing Constraints

### Key Findings

- **set_input_delay / set_output_delay syntax**: Both take `–clock <clk_name>` and a delay value in nanoseconds relative to the specified clock edge. Positive input delay means data arrives *after* the clock edge; negative delay means it arrives before.
- **AXI-Lite internal paths**: For a pure PS-to-PL AXI-Lite design (no external I/O), you typically do **not** need `set_input/output_delay` — the PS-PL interface timing is handled by the Processing System IP constraints included automatically by Vivado.
- **Clock groups**: If your design has multiple unrelated clocks (e.g. `clk_fpga_0` from PL fabric and an external oscillator), declare them asynchronous with `set_clock_groups -asynchronous -group {clk_fpga_0} -group {ext_clk}` to prevent Vivado from reporting false timing violations.
- **False paths on resets**: Add `set_false_path -from [get_ports reset_n]` for asynchronous reset inputs to avoid pessimistic setup/hold analysis on the reset net.
- **KV260 reference XDC**: The official PYNQ KV260 XDC (`Kria-PYNQ/kv260/base/vivado/constraints/base.xdc`) is a good starting point for clock and I/O pin definitions.

### Code Example

```tcl
# kv260.xdc - minimal constraints for PS-to-PL AXI-Lite BRAM demo

# The PS provides the PL clock; no create_clock needed for pl_clk0
# Only external pins (LEDs, buttons on CC) need I/O constraints

# Example: constrain a PL LED output on the KV260 carrier card
set_property PACKAGE_PIN H12 [get_ports {led[0]}]
set_property IOSTANDARD  LVCMOS33 [get_ports {led[0]}]

# Async clock groups if a second clock is used
# set_clock_groups -asynchronous \
#     -group [get_clocks clk_fpga_0] \
#     -group [get_clocks clk_fpga_1]

# False path on active-low async reset from PL fabric
set_false_path -from [get_ports resetn]
```

### Relevance to Your Project

For the current BRAM demo (PS-to-PL only, no external I/O other than UART), your XDC needs only pin assignments for debug signals and IOSTANDARD declarations. The AXI-Lite timing is fully constrained by the Zynq UltraScale+ PS IP. Adding the `set_false_path` on any async reset prevents spurious timing errors during implementation.

## Kria KV260 / K26 SoM

### Key Findings

- **Default boot mode**: KV260 ships pre-loaded with boot firmware in QSPI and a **QSPI32** boot mode pin configuration. For bare-metal development, keep QSPI32 and load your ELF via Vitis/XSCT to RPU/APU over JTAG — no reflashing needed during development.
- **JTAG over USB**: The KV260 exposes a USB-JTAG bridge (FTDI); Vitis Hardware Manager auto-detects it as a Digilent/Xilinx cable. Ensure the USB-C cable is the **data** port, not the UART-only port.
- **MIO vs EMIO**: Most KV260 carrier-card peripherals (UART, USB, SD card) are connected through MIO (PS-internal multiplexed I/O). The RPi header and PMOD use **PL fabric pins**, accessible via EMIO or direct PL I/O constraints. Your BRAM demo is entirely PS↔PL internal, so no MIO/EMIO configuration is needed.
- **Power domains**: The K26 SoM has separate power rails for PS (`VCC_PSINT`), PL (`VCC_INT`), and I/O banks (`VCCO_*`). PL logic including BRAM runs on `VCC_INT` (0.72 V nominal); I/O banks on the carrier card run at 1.8 V or 3.3 V depending on bank.
- **Two KV260 revisions**: Rev1 and Rev2 differ mainly in IAS sensor auto-focus capability. For bare-metal AXI-BRAM work, both revisions are functionally identical.

### Code Example

```tcl
# XSCT (Xilinx Software Command-line Tool) script to load bare-metal ELF via JTAG
# Run: xsct load_elf.tcl

connect
targets -set -filter {name =~ "APU*"}
rst -system
after 3000

targets -set -filter {name =~ "*A53*#0"}
dow kv260_axi_bram.elf
con

puts "ELF loaded and running on APU core 0"
disconnect
```

### Relevance to Your Project

Use this XSCT snippet to replace manual "Run As → Launch on Hardware" clicks in Vitis. It lets you reload the bare-metal binary from a Makefile after each recompile, enabling a tight edit-compile-test loop entirely from the terminal without opening the Vitis GUI.

## AMD/Xilinx Tool Updates (2025.x)

### Key Findings

- **Vivado 2025.1 IP update core dump**: After upgrading IPs in the block design, Vivado may crash with a core dump. Workaround: save the block design before upgrading, let Vivado restart cleanly, then re-open.
- **Vivado 2025 AXI address space 1 KB limit bug**: Community reports confirm that in some Vivado 2025 versions, AXI full peripherals are limited to ~1 KB of decodable address space regardless of `C_S_AXI_ADDR_WIDTH` setting. Workaround: use AXI-Lite (not AXI4) for BRAM controllers, or downgrade to 2024.2 until a hotfix is issued. AXI-Lite with the BRAM controller is unaffected.
- **Vivado 2025 IP stale detection**: After modifying `create_bd.tcl` externally, Vivado may not detect that the block design is out of date. Fix: close and reopen the project (`File → Close Project → Open Project`).
- **KV260 BIST with Vivado 2025.1**: A community tutorial (LogicTronix on Hackster) successfully recreated KV260 BIST with Vivado/Vitis 2025.1, noting AXI bus interface property mismatch warnings that can be safely ignored.
- **Vitis 2025.2 xil_printf.h path change**: A support thread confirms `xil_printf.h` include path changed in Vitis 2025.2 — if you upgrade, update `#include "xil_printf.h"` to `#include "xil_printf.h"` (same name, but BSP include path requires explicit BSP include directory in compiler settings).
- **Vivado 2025.2 highlights**: Versal QoR enhancements, SystemVerilog interface support improvements, and ease-of-use enhancements to the IP Integrator connection automation UI.

### Code Example

```tcl
# Vivado TCL: detect and report IP version mismatches before synthesis
# Run after opening the block design to catch stale IP before wasting synthesis time

set ip_list [get_ips]
foreach ip $ip_list {
    set upgrade_avail [get_property UPGRADE_VERSIONS $ip]
    if {$upgrade_avail ne ""} {
        puts "WARNING: IP [get_property NAME $ip] has upgrade available: $upgrade_avail"
    }
    set stale [get_property IS_LOCKED $ip]
    if {$stale} {
        puts "WARNING: IP [get_property NAME $ip] is LOCKED (out of date)"
        upgrade_ip $ip
    }
}
report_ip_status
```

### Relevance to Your Project

Add this snippet at the top of your `create_bd.tcl` (or a separate `check_ips.tcl`) to automatically detect locked/stale IPs each time you open the project in Vivado 2025.1. The AXI BRAM Controller and Block Memory Generator are the most likely to have available upgrades between Vivado minor versions, and running on a locked IP silently degrades QoR.
