# FPGA Research Digest - 2026-10-21

## Executive Summary
- **AXI-Lite VALID/READY deadlock rule:** Once VALID is asserted it must never be de-asserted before the handshake completes, and VALID must never be gated on READY for the same channel — violating either rule causes silent deadlocks in your BRAM controllers.
- **Kria UART1 is the hardware console:** The on-board FTDI chip routes to UART1 (not UART0). Ensure your BSP stdout points to UART1; the Zephyr docs confirm this is shared with Linux, so keep them from contending at boot.
- **Vivado 2025.1 adds dedicated IP Integrator views:** Two new views — "Clocking and Reset" and "Interrupt and AXI-4 Lite" — streamline validation of the block diagram connections your AXI-BRAM design depends on.
- **`set_clock_groups -asynchronous` is essential for PS/PL clocking:** The Zynq PS FCLK and any Clocking Wizard output are unrelated domains; without this constraint Vivado may attempt timing closure across them and produce misleading violations.
- **Non-project mode TCL gives deterministic, CI-friendly builds:** Driving `synth_design → opt_design → place_design → route_design → write_bitstream` from a script avoids hidden GUI state and is the recommended approach for a bare-metal demo that must rebuild cleanly from TCL (`create_bd.tcl`).

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings
- **Handshake completes on the rising edge where both VALID and READY are high.** The source (master or slave) must keep VALID and its payload stable from assertion until that edge — it may not lower VALID mid-transaction.
- **VALID must never be combinationally gated on READY for the same channel.** A slave that waits for WVALID before asserting WREADY is legal; a master that waits for WREADY before raising WVALID on the same channel is a deadlock per AMBA spec section A3.3.1.
- **READY may be raised and lowered freely** — it carries no "promise" obligation and can be de-asserted between transactions.
- **Write-response channel (B channel) obeys the same rule:** BVALID must stay asserted until BREADY is seen; dropping it early causes the master to miss the response and hang.
- **Common Vivado-generated AXI-Lite slave bug (ZipCPU analysis):** The address and data channel handshake logic in some versions of the Vivado-generated AXI-Lite slave template assumed that both AWVALID and WVALID arrive together — if the master sends them on different cycles the slave can stall.

### Code Example

```vhdl
-- Correct AXI-Lite write-address handshake: latch address only on accepted beat
process(S_AXI_ACLK)
begin
  if rising_edge(S_AXI_ACLK) then
    if S_AXI_ARESETN = '0' then
      aw_en    <= '1';
      aw_addr  <= (others => '0');
    else
      -- Accept the address only when master says it is valid
      -- and we are ready.  aw_en prevents double-latching.
      if S_AXI_AWVALID = '1' and S_AXI_AWREADY = '1' and aw_en = '1' then
        aw_addr <= S_AXI_AWADDR;
        aw_en   <= '0';
      end if;
      -- Re-enable once the write-data beat also completes
      if S_AXI_WVALID = '1' and S_AXI_WREADY = '1' then
        aw_en <= '1';
      end if;
    end if;
  end if;
end process;

-- AWREADY: pulse for one cycle when both channels are ready and aw_en is set
S_AXI_AWREADY <= '1' when (aw_en = '1' and
                            S_AXI_AWVALID = '1' and
                            S_AXI_WVALID  = '1') else '0';
```

### Relevance to Your Project
Your design exposes two AXI-Lite BRAM controllers (BRAM0 @ 0xA000_0000, BRAM2 @ 0xA001_0000). If you ever swap the Vivado-generated slave template for hand-written VHDL, apply the `aw_en` guard shown above to prevent the address from being latched twice when the master issues back-to-back writes. Also verify that your C test loop does not rely on the write-response to be checked only after both BRAMs are written — a missed BRESP from BRAM0 could allow the A53 to issue a second write before the first completes, silently corrupting results.

## Vivado Block Design / IP Integrator

### Key Findings
- **`apply_bd_automation`** in TCL triggers Vivado's connection-automation rules for clocks, resets, and interconnect wiring; it can replace many manual `connect_bd_intf_net` calls when adding standard IP.
- **`assign_bd_address`** assigns AXI slave address segments; `-import_from_file <csv>` and `-export_to_file <csv>` allow address maps to be version-controlled and re-applied after IP regeneration.
- **Vivado 2025.1** added dedicated "Clocking and Reset" and "Interrupt and AXI-4 Lite" views in IP Integrator, making it easier to audit which IP has unconnected clock/reset or missing register-map connections without scrolling through the full canvas.
- **Address Editor in 2025.1/2025.2** supports per-path property view and shows address paths separately from the flat segment list, which is useful when multiple masters share the same interconnect.
- **Regenerate Output Products after any XCI or block-design change**; stale output products are a common cause of `synth_design` failing with "missing module" errors.

### Code Example

```tcl
# Automate clocking and reset connections for all IP in the block design
apply_bd_automation -rule xilinx.com:bd_rule:clkrst \
    -config {Master "/processing_system7_0/FCLK_CLK0" Clk "Auto"}  \
    [get_bd_cells axi_bram_ctrl_0]

# Assign addresses deterministically from a CSV (source-controlled)
assign_bd_address -import_from_file ./constraints/bd_address_map.csv

# Or assign a single slave segment manually
assign_bd_address \
    -target_address_space /processing_system7_0/Data \
    [get_bd_addr_segs axi_bram_ctrl_0/S_AXI/Mem0] \
    -range 8K -offset 0xA0000000
```

### Relevance to Your Project
Your `create_bd.tcl` script builds the block diagram that wires the Zynq PS to the two BRAM controllers. Using `assign_bd_address -import_from_file` for the 0xA0000000 and 0xA0010000 segments ensures addresses survive a `delete_bd_objs`/re-add cycle without manual re-entry. The new 2025.1 Interrupt and AXI-4 Lite view is particularly useful for auditing that both BRAM controller AXI slaves are properly mapped to the PS AXI-HP or AXI-GP master.

## Vivado TCL Scripting

### Key Findings
- **Non-project mode** runs entirely in memory; no `.xpr` file is created. You call `read_vhdl`, `read_xdc`, `synth_design`, `opt_design`, `place_design`, `route_design`, and `write_bitstream` in sequence from a single script.
- **Project mode** (`create_project` → GUI or `launch_runs`) auto-manages output products, IP caches, and incremental compilation — simpler for interactive work but harder to reproduce in CI.
- **Source files are read from their on-disk location** in non-project mode; a VCS checkout is naturally the source root with no copy step.
- **Design checkpoints (DCPs)** can be written at any stage (`write_checkpoint`) for incremental compilation or hand-off; reading one back with `read_checkpoint -incremental` allows Vivado to re-use previous placement.
- **`synth_design` is non-project-mode only** — calling it inside a project-mode script (after `create_project`) causes an error; use `launch_runs synth_1` instead.

### Code Example

```tcl
# Non-project mode batch build script for KV260 AXI-BRAM demo
set part "xck26-sfvc784-2LV-c"

read_vhdl   ./vhdl/kv260_top.vhd
read_bd     ./bd/design_1.bd       ;# exported from IP Integrator
read_xdc    ./constraints/kv260.xdc

# Synthesise targeting the K26 SoC part
synth_design -top kv260_top -part $part -flatten_hierarchy rebuilt

write_checkpoint ./checkpoints/post_synth.dcp

opt_design
place_design
phys_opt_design
route_design

write_checkpoint ./checkpoints/post_route.dcp

# Generate timing and utilisation reports
report_timing_summary -file ./reports/timing_summary.rpt
report_utilization    -file ./reports/utilization.rpt

write_bitstream -force ./output/kv260_top.bit
```

### Relevance to Your Project
Your repo already has `create_bd.tcl`. Pairing it with a wrapper script like the one above lets a CI job (`vivado -mode batch -source build.tcl`) reproduce the bitstream from scratch without any GUI interaction, which is the most robust way to ensure the demo works after any IP update.

## Vitis Bare-Metal / Standalone

### Key Findings
- **UART1 is the Kria KV260 hardware console**, routed through the on-board FTDI USB-to-UART chip. Both Linux and bare-metal firmware share this controller; a bare-metal A53 app that reconfigures UART1 will take over the console from Linux.
- **Host terminal settings:** 115200 baud, 8N1, no flow control — confirmed by QNX's KV260 BSP guide.
- **`xil_printf` is a lightweight subset** of `printf` (no float, no `%f`) that writes directly to the BSP-configured stdout UART; use `printf` from the Newlib BSP if floating-point formatting is needed, but it increases code size significantly.
- **BSP stdout:** In Vitis 2025.x the stdout device is set in the BSP MSS configuration (`xparameters.h` / `STDOUT_BASEADDRESS`); verify it matches the UART1 base address (`0xFF010000` on ZynqMP) rather than UART0 (`0xFF000000`).
- **Linker script pitfall:** The Vitis auto-generated linker script may assign all sections to the first listed memory region; on Zynq UltraScale+ this can be OCM instead of DDR. Manually set `.text`, `.data`, and `.bss` to `psu_ddr_0_MEM_0` for a bare-metal app that needs more than 256 KB.

### Code Example

```c
/* main.c — minimal AXI-BRAM write/read with xil_printf over UART1 */
#include "xil_printf.h"
#include "xparameters.h"

#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL
#define TEST_WORD   0xDEADBEEFUL

static inline void bram_write(uint32_t base, uint32_t offset, uint32_t val) {
    *(volatile uint32_t *)(base + offset) = val;
}
static inline uint32_t bram_read(uint32_t base, uint32_t offset) {
    return *(volatile uint32_t *)(base + offset);
}

int main(void) {
    xil_printf("AXI-BRAM demo starting\r\n");

    bram_write(BRAM0_BASE, 0, TEST_WORD);
    bram_write(BRAM2_BASE, 0, TEST_WORD ^ 0xFFFFFFFF);

    uint32_t r0 = bram_read(BRAM0_BASE, 0);
    uint32_t r2 = bram_read(BRAM2_BASE, 0);

    if (r0 == TEST_WORD && r2 == (TEST_WORD ^ 0xFFFFFFFF))
        xil_printf("PASS: BRAM0=0x%08X  BRAM2=0x%08X\r\n", r0, r2);
    else
        xil_printf("FAIL: BRAM0=0x%08X  BRAM2=0x%08X\r\n", r0, r2);

    return 0;
}
```

### Relevance to Your Project
Your project's `main.c` already follows this pattern. Confirm `STDOUT_BASEADDRESS` in `xparameters.h` is the UART1 base (`0xFF010000`), not UART0. Also check the linker script's memory map — if the `.text` section starts at OCM (e.g., `0xFFFC0000`) the program will silently fail once the code exceeds 256 KB.

## XDC Timing Constraints

### Key Findings
- **`set_clock_groups -asynchronous`** tells Vivado not to analyse timing between two unrelated clock domains. For Zynq UltraScale+, the PS FCLK (`pl_clk0`) and any downstream Clocking Wizard (`clk_wiz`) output are typically asynchronous unless you feed the wizard from FCLK and the tool can determine the relationship.
- **`set_input_delay` / `set_output_delay`** model external setup/hold at the device I/O boundary; values can be positive or negative depending on the clock-to-data phase relationship on the PCB.
- **`set_clock_groups` overrides `set_false_path` and `set_multicycle_path`** for affected paths — apply it before other exceptions to avoid confusion.
- **Generated clocks on MMCM/PLL outputs** must be named explicitly with `create_generated_clock` if you need to reference them in subsequent constraints; Vivado auto-names them but the auto-name is fragile across re-synthesis.
- **Zynq PS internal clocks** (PL clock outputs) appear as `clk_pl_0` (or `FCLK_CLK0` depending on IP) in the clock network report — run `report_clocks` after `synth_design` to confirm the actual names before writing constraints.

### Code Example

```tcl
# kv260.xdc — timing constraints for KV260 AXI-BRAM demo

# 1. Primary PS fabric clock at 100 MHz (verify name with report_clocks)
create_clock -period 10.000 -name pl_clk0 \
    [get_pins zynq_ultra_ps_e_0/inst/PS8_i/PLCLK[0]]

# 2. If a Clocking Wizard is present, declare its output as a generated clock
create_generated_clock -name clk100 \
    -source [get_pins clk_wiz_0/inst/mmcme4_adv_inst/CLKIN1] \
    -multiply_by 1 \
    [get_pins clk_wiz_0/inst/mmcme4_adv_inst/CLKOUT0]

# 3. Declare PS and PL clocks asynchronous so Vivado does not
#    attempt cross-domain timing closure across the PS boundary
set_clock_groups -asynchronous \
    -group [get_clocks pl_clk0] \
    -group [get_clocks clk100]

# 4. False path on async reset (active-low, from PS)
set_false_path -from [get_ports aresetn]
```

### Relevance to Your Project
Your KV260 block design feeds both BRAM controllers from the PS FCLK via the AXI Interconnect. Even without an external Clocking Wizard, applying `set_clock_groups -asynchronous` between the PS clock domain and any debug/JTAG clocks Vivado auto-creates prevents spurious setup violations from cluttering the timing report and masking real failures in the AXI paths.

## Kria KV260 / K26 SoM

### Key Findings
- **No boot-mode dip switches on Kria SOMs.** Boot mode is hard-wired: the KV260 carrier fixes the MPSoC to QSPI32 boot. The FSBL and PMU firmware live in QSPI flash; the OS/application image is on microSD.
- **UART1 is the console UART** (not UART0); the on-board FTDI maps to UART1. Buildroot and Zephyr both confirm this. Linux typically occupies UART1; bare-metal apps inherit the same hardware.
- **MIO banks 501, 502, 504** are the user-accessible PS I/O banks on the K26 SoM (bank 504 is dedicated to DDR4). PL I/O bank supplies (HPIO/HDIO) are set by carrier-card rails.
- **K26 SoM power input:** The SoC supplies all derive from a single +5V input on the SoM; PL I/O voltage is determined by carrier-board level shifters / power rails.
- **K26 SoM exposes PS MIO, PS-GTR (4 lanes), PL HPIO/HDIO, and GTH transceivers** on its two connectors (CC and SM edges); not all pins are accessible on the KV260 carrier.

### Code Example

```tcl
# Vivado XDC: constrain the KV260 status LED on the carrier (PL HDIO bank)
# PL pin location confirmed from KV260 carrier schematic (check UG1089 for exact pin)
set_property PACKAGE_PIN  A12        [get_ports {led[0]}]
set_property IOSTANDARD   LVCMOS33   [get_ports {led[0]}]

# UART1 TX/RX are MIO 48/49 on the K26 SoM — they do NOT appear in XDC
# because they are PS-side MIO, configured in the Zynq PS IP block design:
#   set_property CONFIG.PSU__UART1__PERIPHERAL__ENABLE {1} [get_bd_cells zynq_ultra_ps_e_0]
#   set_property CONFIG.PSU__UART1__PERIPHERAL__IO     {MIO 48 .. 49} [get_bd_cells zynq_ultra_ps_e_0]
```

### Relevance to Your Project
For your bare-metal AXI-BRAM demo you do not need to touch boot mode — the FSBL loaded from QSPI handles PS/PL power sequencing, and Vitis loads the ELF over JTAG/XSDB. Confirm in your block design that UART1 is enabled on MIO 48-49 (the KV260 carrier's FTDI connection); if the PS IP is configured for UART0 or wrong MIO pins, `xil_printf` output will be silent even though the code runs.

## AMD/Xilinx Tool Updates (Vivado/Vitis 2025.x)

### Key Findings
- **Vivado 2025.1 new IP:** A fully customisable **RTL-based AXI Switch IP** was added — it bridges different AXI interface types and widths and is a more flexible alternative to the standard AXI Interconnect for custom topologies.
- **IP Integrator 2025.1:** Two dedicated views added — *Clocking and Reset* and *Interrupt and AXI-4 Lite* — provide at-a-glance validation of clock/reset wiring and AXI-Lite control register connectivity without scrolling the main canvas.
- **Installer improvement (2025.1):** Vivado can now be installed scoped to specific Versal device families rather than entire product lines, significantly reducing download and disk footprint.
- **New device support (2025.1):** Versal AI Edge Gen 2, Versal Prime Gen 2, Spartan UltraScale+.
- **Vitis 2025.2 highlights:** Simplified AXI connections between SystemVerilog instances, automatic wrapper creation for AMD IP, and improved AI Engine mapper/router. A new PS Wizard block-diagram and swim-lane view was added.
- **Linux kernel upgraded to 6.12** in the 2025.1 open-source component release (PetaLinux).

### Code Example

```tcl
# Vivado 2025.1 — instantiate the new RTL-based AXI Switch IP
# Useful when you need to arbitrate between PS and a PL DMA master over shared BRAMs

create_bd_cell -type ip -vlnv xilinx.com:ip:axi_switch:1.0 axi_switch_0

set_property CONFIG.NUM_SI  {2} [get_bd_cells axi_switch_0]  ;# 2 slave interfaces
set_property CONFIG.NUM_MI  {2} [get_bd_cells axi_switch_0]  ;# 2 master interfaces
set_property CONFIG.ARB_ALGORITHM {0} [get_bd_cells axi_switch_0]  ;# Round-robin

# Connect PS AXI-GP0 to switch slave 0
connect_bd_intf_net [get_bd_intf_pins zynq_ultra_ps_e_0/M_AXI_HPM0_FPD] \
                    [get_bd_intf_pins axi_switch_0/S00_AXI]
```

### Relevance to Your Project
Your current design uses direct AXI-Lite connections from the PS to each BRAM controller. The new AXI Switch IP is relevant if you plan to add a second master (e.g., a PL-side DMA) that also needs access to the BRAMs — it provides arbitration without requiring a full AXI Interconnect. The new IP Integrator Clocking/Reset view is immediately useful to confirm that both BRAM controllers share the same clock domain as the PS AXI master in your current `create_bd.tcl`-generated design.
