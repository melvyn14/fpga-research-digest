# FPGA Research Digest - 2026-07-22

## Executive Summary

- **AXI-Lite VALID/READY pitfall**: A master must never make VALID conditional on READY — this creates a combinational deadlock. The Xilinx-generated AXI-Lite slave template from Vivado ≤2019 contained exactly this bug; audit your generated slave wrappers before use.
- **BRAM address alignment**: The AXI BRAM Controller maps with a 4-byte (word) stride; byte enables must be set correctly in WSTRB when doing sub-word writes. Using 32-bit aligned addresses (as in your 0xA000_0000 / 0xA001_0000 layout) avoids this class of bugs entirely.
- **TCL reproducibility**: Always run `write_bd_tcl -force bd_export.tcl` after any manual block-design edit in IP Integrator — this captures the ground-truth state including exact VLNV versions and property values that your checked-in `create_bd.tcl` may not match after a tool upgrade.
- **KV260 JTAG boot for bare-metal**: The on-board boot mode switches default to SD/QSPI. To download and run bare-metal ELFs directly from Vitis, you must switch to JTAG mode (remove SD card, use XSDB `mwr` to override the boot mode register) or program a BOOT.BIN to SD.
- **Vivado/Vitis 2025.1 upgrade**: The 2025.1 toolchain ships with updated IP core VLNV versions. If your `create_bd.tcl` hard-codes old `axi_bram_ctrl:4.1` or `blk_mem_gen:8.4` VLNVs, it will silently use a newer version or error out; prefer `-type ip -vlnv xilinx.com:ip:axi_bram_ctrl:*` (wildcard) or omit the version suffix in scripts.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- **Handshake rule #1 — VALID must not wait for READY**: A master is forbidden from asserting VALID only after seeing READY high. The spec allows a slave to wait for VALID before asserting READY, but not vice-versa. Violating this can cause deadlock that only manifests under backpressure in silicon, not in simple simulation testbenches.
- **Handshake rule #2 — signals must be stable once VALID is asserted**: Once a master drives VALID high, it must hold AWADDR, AWPROT, WDATA, WSTRB (or ARADDR, ARPROT for reads) stable until the handshake completes (both VALID and READY high on a rising clock edge).
- **Write-response channel (B channel) must be consumed**: The master must eventually assert BREADY; if it never does, the slave's response FIFO fills and AWREADY/WREADY de-asserts, stalling the bus. In tight bare-metal polling loops it is easy to accidentally issue a write without ever reading BRESP.
- **AXI-Lite has no burst mode**: Each transaction is single-beat. The AXI BRAM Controller in AXI-Lite mode (vs. AXI4) therefore issues one 32-bit transfer per address. This is acceptable for a debug/bringup demo but is the primary throughput bottleneck to be aware of.
- **Reset must be synchronous to ACLK**: The AXI spec requires ARESETn to be de-asserted synchronously. The Zynq PS drives `aresetn` from the Processing System Reset IP; never bypass this block or tie reset directly to a PL GPIO.

### Code Example

```c
/* Minimal AXI-Lite write + response poll for bare-metal on Zynq */
#include "xil_io.h"

#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL

/* Write 32-bit word, then read back to verify */
static int axi_bram_write_verify(u32 base, u32 offset, u32 data) {
    u32 addr = base + (offset << 2);   /* word-addressed: multiply by 4 */
    Xil_Out32(addr, data);
    dsb();                              /* data synchronization barrier */
    u32 readback = Xil_In32(addr);
    return (readback == data) ? 0 : -1;
}

int main(void) {
    xil_printf("AXI-BRAM test start\r\n");

    int fail = 0;
    for (u32 i = 0; i < 16; i++) {
        u32 pattern = 0xDEAD0000 | i;
        fail |= axi_bram_write_verify(BRAM0_BASE, i, pattern);
        fail |= axi_bram_write_verify(BRAM2_BASE, i, ~pattern);
    }

    xil_printf(fail ? "FAIL\r\n" : "PASS\r\n");
    return fail;
}
```

### Relevance to Your Project

Your `main.c` writes patterns to BRAM0 at `0xA0000000` and BRAM2 at `0xA0010000` and reads them back. The `dsb()` barrier is critical: without it the Cortex-A53 store buffer may reorder the write and the subsequent read, producing a false PASS even if the AXI slave never committed the data. `Xil_Out32`/`Xil_In32` from `xil_io.h` map directly to the AXI-Lite bus — no driver initialization is needed for simple memory-mapped access.

## Vivado Block Design / IP Integrator

### Key Findings

- **Run Connection Automation in two passes**: First run it for the `S_AXI` port of the AXI BRAM Controller (this instantiates an AXI SmartConnect/Interconnect), then run it again for `BRAM_PORTA` (this instantiates and wires the Block Memory Generator). Doing it in one pass sometimes misses the BRAM side.
- **Address Editor auto-assignment caveat**: After running connection automation, always open the Address Editor tab and verify the auto-assigned offsets. The tool defaults to sequential base addresses (0x4000_0000, 0x4001_0000 etc.) for Zynq-7000; for Zynq UltraScale+ (KV260) it uses the HP0 AXI slave, with range starting at 0xA000_0000 only if `HP0_SLAVE_BASEADDR` is set in the Zynq PS IP properties.
- **Validate Design before Generate Bitstream**: Always run `validate_bd_design` (or Validate Design from the toolbar) before generating the bitstream. Common errors: unconnected AXI clocks, mismatched data widths (BRAM data width vs AXI data width), and missing `ext_reset_in` on the Proc Sys Reset IP.
- **`regenerate_bd_layout`**: If the canvas looks scrambled after script replay, run `regenerate_bd_layout` in the Tcl console — it redraws the graphical layout without modifying connectivity.
- **IP version lock-in**: Block designs store the exact VLNV of each IP. After a tool upgrade (e.g., 2024.2 → 2025.1), opening the project may show "IP out of date" warnings. Run `upgrade_ip [get_ips *]` in Tcl to upgrade all IPs at once, then re-validate and regenerate.

### Code Example

```tcl
# Validate and generate block design in Tcl (batch-friendly)
open_bd_design [get_files *.bd]

# Upgrade any stale IP after tool version change
set stale [get_ips -filter {UPGRADE_NEEDED == 1}]
if {[llength $stale] > 0} {
    upgrade_ip $stale
    report_ip_status
}

validate_bd_design -force
generate_target all [get_files *.bd]
make_wrapper -files [get_files *.bd] -top
add_files -norecurse [glob ./*/hdl/*.v]
```

### Relevance to Your Project

Your `create_bd.tcl` script builds the block design from scratch. After any Vivado version upgrade, run the `upgrade_ip` snippet above before re-running the script to ensure BRAM Controller and Block Memory Generator versions stay current. The `validate_bd_design` call will surface mismatches between your two BRAM controllers (BRAM0/BRAM2) and the Zynq PS HP port data widths before synthesis wastes time.

## Vivado TCL Scripting

### Key Findings

- **Batch mode invocation**: `vivado -mode batch -source build.tcl -notrace` runs a Tcl script headlessly. `-notrace` suppresses per-command echo to keep logs clean; use `-log build.log -journal build.jou` to capture output.
- **Non-project mode for CI**: Non-project mode (`read_vhdl`, `read_xdc`, `synth_design`, `impl_design`, `write_bitstream`) avoids the `.xpr` file entirely and is preferred for CI pipelines. Exception: IP Integrator block designs **must be pre-generated** before adding them to a non-project flow (i.e., run `generate_target all` in a separate project-mode step first).
- **`write_bd_tcl` is the ground truth**: After any GUI edit, run `write_bd_tcl -force -no_ip_version scripts/create_bd.tcl` to regenerate the canonical script. The `-no_ip_version` flag makes the script version-agnostic, preventing hard-coded VLNV failures on tool upgrades.
- **`create_bd_cell` VLNV best practices**: Use `xilinx.com:ip:axi_bram_ctrl` (no version) and let Vivado pick the latest; or check `get_ipdefs -filter {NAME == axi_bram_ctrl}` to enumerate available versions before hard-coding.
- **Tcl error handling**: Wrap critical steps in `if {[catch {synth_design ...} err]} { puts "ERROR: $err"; exit 1 }` — otherwise Vivado Tcl continues past errors silently and produces corrupt outputs.

### Code Example

```tcl
# Minimal non-project mode build for KV260 AXI-BRAM demo
# Run as: vivado -mode batch -source build_nonproject.tcl

set PART "xck26-sfvc784-2LV-c"
set TOP  "kv260_top"

# 1. Read sources
read_vhdl    [glob ./vhdl/*.vhd]
read_xdc     [glob ./xdc/*.xdc]

# 2. Read pre-generated block design wrapper
read_verilog [glob ./bd/*/hdl/*.v]

# 3. Synthesize
if {[catch {
    synth_design -top $TOP -part $PART -flatten_hierarchy rebuilt
} err]} { puts "SYNTH FAILED: $err"; exit 1 }

# 4. Implement
opt_design
place_design
phys_opt_design
route_design

# 5. Reports + bitstream
report_timing_summary -file timing.rpt
report_utilization    -file util.rpt

if {[catch {write_bitstream -force ${TOP}.bit} err]} {
    puts "BITSTREAM FAILED: $err"; exit 1
}
puts "Build complete: ${TOP}.bit"
```

### Relevance to Your Project

Your `create_bd.tcl` is already the right approach for reproducibility. The key gap to close: add `write_bd_tcl -force` to the end of any interactive session so the script stays in sync with the GUI state. For CI runs, the non-project mode template above avoids the GUI entirely after the one-time BD generation step.

## Vitis Bare-Metal / Standalone

### Key Findings

- **BSP stdout/stdin must point to the correct UART**: In the BSP settings (`system.mss` or the Vitis platform configuration), set `stdin` and `stdout` to the UART instance connected to the USB-serial bridge. For KV260, this is typically `psu_uart_1` (the second UART, exposed via the microUSB port). If set to the wrong instance, `xil_printf` produces no output and the board appears hung.
- **`xil_printf` vs `printf`**: `xil_printf` is lightweight (no floating point, no heap) and goes directly to the UART FIFO. `printf` from newlib requires a full BSP with heap — it is slower, larger, and requires `_write()` syscall redirection. For bare-metal bringup, always use `xil_printf`.
- **Linker script memory regions**: The default linker script places code in DDR starting at `0x0`. For the KV260, the PS DDR base is `0x0000_0000` (low 2 GB). If your ELF is larger than expected or crashes at startup, check the linker script `lscript.ld` — the OCM (On-Chip Memory) region must match the actual address (`0xFFFC_0000` for the Zynq UltraScale+ OCM, not `0x0`).
- **Cache coherency with AXI**: The Cortex-A53 L1/L2 caches are enabled by default in the standalone BSP. For AXI-mapped peripheral registers (like BRAM at `0xA000_0000`), the PS marks those regions as "Device" (non-cached) in the MPU — so `Xil_Out32`/`Xil_In32` are already coherent. Do NOT call `Xil_DCacheFlush` on AXI peripheral addresses; it has no effect and wastes cycles.
- **Interrupt controller (GIC) for bare-metal**: If adding interrupts, use `XScuGic` (the GIC-400 driver). Initialize with `XScuGic_CfgInitialize`, connect your handler, then call `Xil_ExceptionEnable()`. The standalone BSP does not enable exceptions by default.

### Code Example

```c
/* BSP-correct UART printf and AXI BRAM test skeleton for KV260 */
#include "xparameters.h"
#include "xil_printf.h"
#include "xil_io.h"
#include "xil_cache.h"

/* These come from xparameters.h generated by Vitis from the hardware XSA */
#define BRAM0_BASE  XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR
#define BRAM2_BASE  XPAR_AXI_BRAM_CTRL_1_S_AXI_BASEADDR
#define BRAM_DEPTH  0x2000   /* 8 KB — match your Block Memory Generator config */

int main(void) {
    xil_printf("\r\n=== KV260 AXI-BRAM Demo ===\r\n");

    u32 errors = 0;

    /* Walking-ones pattern test */
    for (u32 i = 0; i < BRAM_DEPTH / 4; i++) {
        u32 pat = (1u << (i % 32));
        Xil_Out32(BRAM0_BASE + i * 4, pat);
        Xil_Out32(BRAM2_BASE + i * 4, ~pat);
    }

    for (u32 i = 0; i < BRAM_DEPTH / 4; i++) {
        u32 pat = (1u << (i % 32));
        if (Xil_In32(BRAM0_BASE + i * 4) != pat)   errors++;
        if (Xil_In32(BRAM2_BASE + i * 4) != ~pat)  errors++;
    }

    xil_printf("Result: %s (%lu errors)\r\n", errors ? "FAIL" : "PASS", errors);
    return (int)errors;
}
```

### Relevance to Your Project

Using `XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR` from `xparameters.h` (auto-generated from the XSA) instead of hard-coded `0xA0000000` makes your `main.c` portable across address-map changes. The walking-ones pattern catches stuck-at-0 and stuck-at-1 bit faults that a simple incrementing counter misses.

## XDC Timing Constraints

### Key Findings

- **AXI BRAM is internally timed — no I/O constraints needed**: The AXI-Lite interface between the PS and BRAM Controller lives entirely inside the PL (via the PS HP/GP AXI slave ports). You do NOT need `set_input_delay`/`set_output_delay` for this path. Only external I/O pins (UART TX/RX pads, LEDs, GPIOs) need I/O timing constraints.
- **Primary clock constraint**: The PS generates `pl_clk0` (typically 100 MHz). Declare it in XDC as:
  `create_clock -name pl_clk0 -period 10.000 [get_ports pl_clk0]`
  Without this, Vivado will create a virtual clock and timing may not close reliably.
- **False paths for asynchronous resets**: If you have any reset synchronizers, add:
  `set_false_path -from [get_ports aresetn]`
  to suppress spurious hold-time violations on the reset path.
- **`ASYNC_REG` for CDC synchronizers**: Any flip-flop pair used for clock-domain crossing must be marked with `set_property ASYNC_REG TRUE [get_cells ...]`. Without this, the placer may separate the two FFs and introduce metastability risk.
- **`set_clock_groups` for PS-PL boundary**: The PS internal clock and the PL `pl_clk0` are synchronous by design (the PS generates `pl_clk0`), so no `set_clock_groups -asynchronous` is needed for this path. Only add it if you add a second, independent PL clock source.

### Code Example

```xdc
# Minimal XDC for KV260 AXI-BRAM bare-metal demo
# The PS drives pl_clk0; declare it as the primary constraint

# Primary PL clock from PS (100 MHz)
create_clock -name pl_clk0 -period 10.000 [get_ports pl_clk0]

# False path on async reset input (the PS drives this after its own reset)
set_false_path -from [get_ports aresetn]

# If using an on-board LED for status (KV260 has 4 LEDs on CC)
# set_output_delay -clock pl_clk0 -max 2.0 [get_ports {led[*]}]
# set_output_delay -clock pl_clk0 -min 0.5 [get_ports {led[*]}]

# Prevent the tools from touching hold-fix flops (if any synchronizers added later)
# set_property ASYNC_REG TRUE [get_cells -hierarchical -filter {NAME =~ *sync_reg*}]
```

### Relevance to Your Project

For your current design (PS → AXI → BRAM, no external I/O other than UART which is PS-internal), the XDC file only needs the `create_clock` line for `pl_clk0`. Everything else is internal timing and is handled automatically. Keep the XDC minimal — unnecessary constraints are a common source of false timing violations that mask real issues.

## Kria KV260 / K26 SoM

### Key Findings

- **Boot mode for bare-metal development**: The KV260 Starter Kit defaults to SD card boot. For iterative bare-metal development without reprogramming SD, boot in JTAG mode: remove the SD card (or override boot mode via XSDB), then use `xsdb` to download FSBL + PMU firmware + your ELF. The AMD support forum confirms: PSU_INIT.TCL can substitute for FSBL in JTAG-only flows.
- **Two USB ports — JTAG is separate from UART**: The KV260 has a microUSB port that enumerates as **two COM ports**. COM port 1 (lower number) is JTAG; COM port 2 is UART. Connect PuTTY/minicom to the **second** COM port at 115200 8N1 to see `xil_printf` output.
- **MIO bank assignments**: PS MIO bank 500 carries I2C (MIO 2/3) and the SD interface (MIO 13-22). MIO bank 501 carries UART1 (MIO 36/37 — TX/RX). The PL GPIO uses EMIO, which starts at GPIO offset 78 for Zynq UltraScale+. Do not attempt to use bank 500/501 MIO as PL I/O — they are PS-only.
- **Power domains — VCCOEN sequencing**: The SOM asserts `VCCOEN_PL_M2C` to enable the carrier card's PL power rails. Bare-metal code that configures PL VCCO before this signal is asserted will see incorrect I/O voltage on the carrier card's PMOD/FMC connectors. For the AXI-BRAM demo this is not an issue since no external PL I/O is used.
- **K26 part number in Vivado**: The correct part string for the KV260's K26 SoM is `xck26-sfvc784-2LV-c`. The board file in Vivado exposes this as `xilinx.com:kv260_som:part0:1.3` (or later). Always select the board file rather than the bare part to get correct MIO and DDR pre-configuration.

### Code Example

```tcl
# XSDB script to boot bare-metal ELF on KV260 via JTAG
# Run from Vitis XSDB console: source jtag_boot.tcl

connect

# Target the A53 core 0
targets -set -nocase -filter {name =~ "*A53*#0"}

# Initialize PS (replaces FSBL in simple JTAG flows)
rst -system
after 1000
source psu_init.tcl
psu_init

# Optional: disable security gates
psu_post_config_01
psu_ps_pl_isolation_removal_01
psu_ps_pl_reset_config_01

# Download and run the application ELF
dow kv260_bram_demo.elf
con

puts "Application running. Connect UART COM port 2 at 115200."
```

### Relevance to Your Project

This XSDB flow lets you iterate on `main.c` changes in seconds (recompile → `dow` → `con`) without ever touching an SD card. The `psu_init.tcl` is auto-generated by Vitis when you create a hardware platform from your `.xsa` file — it lives in `<platform>/hw/psu_init.tcl`.

## AMD/Xilinx Tool Updates — Vivado/Vitis 2025.1

### Key Findings

- **Vitis 2025.1 released 2025-07-08**: The unified Vitis platform received a maintenance release. The Vitis release notes (UG1742) are the authoritative source; key bare-metal relevant changes include updated embeddedsw drivers and BSP library versions.
- **Vitis 2026.1 is now current**: As of July 2026, AMD has released Vitis/Vivado 2026.1. The download page lists 2025.1 as an archived version. If you are using 2025.1, check the 2026.1 migration guide for any `xparameters.h` API changes before upgrading.
- **IP core version bumps in 2025.1**: The `axi_bram_ctrl` and `blk_mem_gen` IPs received minor revision bumps in 2025.1. Existing `.xpr` files from 2024.2 will show "IP out of date" on first open — this is expected. Run `upgrade_ip` as described in the IP Integrator section above.
- **Known issue — RHEL 8.3 / CentOS 8.2 GUI crash**: Vitis 2025.1 GUI projects on RHEL8.3/CentOS8.2 may fail due to an `LD_LIBRARY_PATH` conflict. Workaround: remove `${env_var:LD_LIBRARY_PATH}` from the project environment settings in the Vitis workspace properties. This does not affect batch/headless flows.
- **Vitis Libraries 2025.1 new AIE-ML APIs**: The VEK280 AIE-ML device gained 20 new L1 and 6 new L2 APIs (float, int32, cint16). Not directly relevant to the KV260 bare-metal demo, but indicates AMD's continued investment in the AIE stack for future platform evolution.
- **UG835 (Vivado Tcl Command Reference) updated to 2025.2**: Several new `bd_*` commands were added. Notably `regenerate_bd_layout` is now documented to also recheck internal routing of the canvas, making it more useful after large script-driven design modifications.

### Code Example

```tcl
# Detect Vivado version at script start and warn if unexpected
set tool_ver [version -short]
puts "Vivado version: $tool_ver"

if {[string compare $tool_ver "2025.1"] != 0} {
    puts "WARNING: This script was tested on 2025.1. Running on $tool_ver."
    puts "         Run 'upgrade_ip \[get_ips *\]' if IP out-of-date warnings appear."
}

# Upgrade stale IPs (safe to run even if nothing needs upgrading)
set stale [get_ips -filter {UPGRADE_NEEDED == 1}]
if {[llength $stale] > 0} {
    puts "Upgrading [llength $stale] IP(s): [get_property NAME $stale]"
    upgrade_ip $stale
}

# Check for critical IP after upgrade
foreach ip_name {axi_bram_ctrl blk_mem_gen zynq_ultra_ps_e} {
    set found [get_ips -filter "IPDEF =~ *${ip_name}*"]
    if {$found eq ""} {
        puts "ERROR: Required IP $ip_name not found in project!"
    } else {
        puts "OK: $ip_name -> [get_property IPDEF $found]"
    }
}
```

### Relevance to Your Project

Running the version check at the top of `create_bd.tcl` protects against silent failures when the project is opened on a different tool version. The IP audit loop will catch if either `axi_bram_ctrl` (used twice — for BRAM0 and BRAM2) or `blk_mem_gen` is missing after an environment change.
