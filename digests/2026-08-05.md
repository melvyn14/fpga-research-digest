# FPGA Research Digest - 2026-08-05

## Executive Summary

- **AXI-Lite ARREADY deadlock risk**: Xilinx's reference AXI-Lite slave implementation does not gate `ARREADY` on `RVALID`/`RREADY`, creating potential backpressure deadlock when the read-return channel is stalled — any custom AXI-Lite slave in the KV260 project should guard against this.
- **AXI SmartConnect over Interconnect**: For Zynq UltraScale+ designs, AMD now recommends `AXI SmartConnect` for new block designs; it auto-adapts protocol widths and gives 20–30% better timing at high utilisation compared to the older `AXI Interconnect` IP.
- **`write_bd_tcl` is version-locked**: TCL scripts exported from Vivado 2025.1 with `write_bd_tcl` will not reproduce correctly in other versions — pin the Vivado version in the repo README.
- **Kria KV260 bare-metal JTAG flow**: Requires loading `fsbl.elf`, `pmufw.elf`, bitstream, and application ELF via XSDB in sequence after switching to JTAG boot mode — the PL bitstream must be included in the XSA export from Vivado.
- **Vivado 2025 AXI address-width bug**: A confirmed forum-reported issue in Vivado 2025 limits AXI full peripheral address decode to 10 bits (~1 KB usable), even when a wider address width is configured — test your BRAM address range assumptions explicitly.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- **Handshake invariant**: Once `VALID` is asserted by an initiator it must not be de-asserted until the corresponding `READY` is received. Violating this causes undefined behaviour and is a common source of intermittent BRAM read corruption.
- **ARREADY deadlock in Xilinx reference slave**: Xilinx's sample AXI-Lite slave VHDL does not make `ARREADY` conditional on `not RVALID or RREADY`. When the read-data channel is backpressured, a new read address can be accepted before the previous read data is consumed, leading to data loss or deadlock under load.
- **AXI4-Lite BRAM controller width constraint**: The `axi_bram_ctrl` IP in AXI4-Lite mode only supports a 32-bit AXI data bus. If you need 64-bit transfers to BRAM you must switch to the full AXI4 mode.
- **Read/write port collision not detected**: The AXI BRAM Controller does not detect simultaneous read/write collisions at the same BRAM address — the result is undefined. The Cortex-A53 firmware must ensure sequential, non-overlapping accesses when testing BRAM0 and BRAM2.
- **Vivado 2025 address-width bug**: Forum reports confirm AXI full peripherals in Vivado 2025 are limited to 10-bit address decoding (~1 KB), even with wider parameters. Workaround: verify effective decode in the Address Editor and use AXI-Lite mode (which side-steps this for simple register maps).

### Code Example

```vhdl
-- Correct AXI-Lite read-address handshake in VHDL slave
-- Gate ARREADY so it only accepts a new address when the read-data channel is free
process(S_AXI_ACLK)
begin
  if rising_edge(S_AXI_ACLK) then
    if S_AXI_ARESETN = '0' then
      axi_arready <= '0';
    else
      -- Only accept new AR beat when no read response is pending
      if axi_arready = '0' and S_AXI_ARVALID = '1'
         and (axi_rvalid = '0' or S_AXI_RREADY = '1') then
        axi_arready <= '1';
      else
        axi_arready <= '0';
      end if;
    end if;
  end if;
end process;
```

### Relevance to Your Project

The KV260 AXI-BRAM demo relies on back-to-back PS reads from `0xA0000000` and `0xA0010000`. If your `kv260_top.vhd` wrapper includes any custom AXI-Lite glue logic, the ARREADY fix above prevents the Cortex-A53 from stalling waiting for `RREADY` after a burst of reads. For the stock `axi_bram_ctrl` IP the handshake is handled internally, but it is worth adding a short inter-transaction delay in `main.c` when toggling between BRAM0 and BRAM2.

## Vivado Block Design / IP Integrator

### Key Findings

- **Connection Automation adds required infrastructure**: Running *Run Connection Automation* after adding `axi_bram_ctrl` IPs automatically inserts the `Processor System Reset` and either `AXI Interconnect` or `AXI SmartConnect`. Ensure the reset checkbox is checked in the automation dialog.
- **Address Editor — Assign All vs manual**: Click the *Address Editor* tab, then *Assign All* to let Vivado auto-assign base addresses. You can then override individual offset addresses (e.g. `0xA000_0000` for BRAM0, `0xA001_0000` for BRAM2) and set the range column to match your BRAM depth.
- **AXI SmartConnect preferred for UltraScale+**: The `AXI SmartConnect` IP is the current recommended interconnect for Zynq UltraScale+ MPSoC (including K26). It auto-adapts data-width mismatches and provides 20–30% better timing performance than the legacy `AXI Interconnect`. Caveat: for very small AXI-Lite-only designs, SmartConnect can use more LUTs.
- **Regenerate Output Products after XSA change**: Any time you modify IP parameters or re-run connection automation, right-click the block design and choose *Generate Output Products* before re-exporting the XSA to Vitis.

### Code Example

```tcl
# In IP Integrator TCL: manually fix addresses after Assign All
assign_bd_address
set_property offset 0xA0000000 [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property range  64K        [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property offset 0xA0010000 [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_1_Mem0}]
set_property range  64K        [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_1_Mem0}]
```

### Relevance to Your Project

Your `create_bd.tcl` drives the entire block design setup. The address snippet above matches the memory map your `main.c` uses (`0xA0000000` / `0xA0010000`). If addresses ever drift (e.g. after adding an IP and re-running automation), the `set_property offset` calls above restore them deterministically and can be appended to the end of `create_bd.tcl`.

## Vivado TCL Scripting

### Key Findings

- **`write_bd_tcl` is the source-control primitive**: Use `File → Export → Export Block Design` or the `write_bd_tcl` Tcl command to serialise the entire block design to a reproducible script. This is the file that belongs in version control (not the `.bd` binary).
- **Version lock**: The generated script is version-specific. A script created in 2025.1 will fail or misbehave in 2025.2 or 2024.x because Vivado tweaks IP parameter names between releases. Tag or comment the generating version at the top of the file.
- **`-include_layout` preserves visual arrangement**: Pass this flag to `write_bd_tcl` so the canvas block positions are stored — useful for readable diffs.
- **Non-project mode requires pre-generated BD**: In non-project (batch) mode, the block design must be fully generated (OOC synthesis complete) before calling `add_files` on it. If you drive synthesis from TCL, call `generate_target all` first.
- **IP Tcl commands are consistent across modes**: `create_ip`, `set_property`, `generate_target` behave identically in both project and non-project flows.

### Code Example

```tcl
#!/usr/bin/env tclsh
# Non-project batch flow for kv260-axi-bram-demo
# Usage: vivado -mode batch -source build.tcl

# 1. Set part
set_part xczu5ev-sfvc784-2-e

# 2. Read sources
read_vhdl [glob ./vhdl/*.vhd]
read_xdc  ./constraints/kv260_top.xdc

# 3. Source the BD creation script (outputs to ./bd/)
source ./tcl/create_bd.tcl

# 4. Generate block design outputs (OOC)
generate_target all [get_files *.bd]
export_ip_user_files -of_objects [get_files *.bd] -no_script -sync -force -quiet

# 5. Synthesise, implement, write bitstream
synth_design -top kv260_top -part xczu5ev-sfvc784-2-e
opt_design
place_design
route_design
write_bitstream -force ./output/kv260_top.bit
write_hw_platform -fixed -include_bit -force ./output/kv260_top.xsa
```

### Relevance to Your Project

Your repo already has a `create_bd.tcl`; wrapping it in the batch script above gives you a fully headless CI-friendly build. The `write_hw_platform` at the end produces the XSA that Vitis consumes, closing the full Vivado → Vitis automation loop.

## Vitis Bare-Metal / Standalone

### Key Findings

- **Vitis Unified IDE workflow (2025.x)**: `File → New Component → Platform` → select XSA → set OS = `standalone` → select processor `psu_cortexa53_0` → create Application component on top. This replaces the older SDK project wizard.
- **`xil_printf` limitations**: Outputs strings without format interpretation beyond `%d`, `%x`, `%s`. Does **not** support `%f` (floating point). Strings must be null-terminated. For floating point, link `printf` from newlib instead (increases BSP size significantly).
- **UART mux warning**: Some Kria BSP configurations default `stdin`/`stdout` to `psu_uart_0` (MIO) while the physical USB-UART on the KV260 carrier maps to `psu_uart_1`. Verify BSP MSS settings match your hardware and check `xparameters.h` for the correct `XPAR_PSU_UART_*` index.
- **Interrupt controller (GIC)**: Zynq UltraScale+ uses the ARM GIC-400. Private Peripheral Interrupts (PPI, IDs 16–31) are CPU-local; Shared Peripheral Interrupts (SPI, IDs 32+) are system-wide. AXI peripheral interrupts route as SPI. Use `XScuGic` driver from the BSP.
- **KV260 Vitis template**: A community template repo (`miya4649/Vitis_KV260_KR260_Template`) provides a ready-made bare-metal project structure targeting the KV260/KR260 in the Unified IDE.

### Code Example

```c
/* Bare-metal AXI-Lite BRAM write/read with explicit memory barriers */
#include "xil_io.h"
#include "xil_printf.h"

#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL
#define TEST_PATTERN 0xDEADBEEFUL

static int test_bram(u32 base, const char *name) {
    Xil_Out32(base, TEST_PATTERN);
    /* Data memory barrier — ensure write reaches AXI slave before read */
    __asm__ __volatile__("dmb sy" ::: "memory");
    u32 readback = Xil_In32(base);
    if (readback == TEST_PATTERN) {
        xil_printf("%s PASS (0x%08X)\r\n", name, readback);
        return 0;
    }
    xil_printf("%s FAIL: wrote 0x%08X, read 0x%08X\r\n",
               name, (unsigned)TEST_PATTERN, (unsigned)readback);
    return -1;
}

int main(void) {
    xil_printf("KV260 AXI-BRAM Demo\r\n");
    int rc = 0;
    rc |= test_bram(BRAM0_BASE, "BRAM0");
    rc |= test_bram(BRAM2_BASE, "BRAM2");
    return rc;
}
```

### Relevance to Your Project

The `dmb sy` instruction before each `Xil_In32` is the bare-metal equivalent of a memory fence — it prevents the Cortex-A53's out-of-order pipeline from issuing the read before the AXI write has propagated. Without it, intermittent PASS/FAIL results are possible even when the hardware is correct. Check whether this barrier is present in your `main.c`.

## XDC Timing Constraints

### Key Findings

- **`set_input_delay` syntax**: Specifies external path delay on a primary input relative to a clock edge. Value is in nanoseconds; can be positive or negative depending on clock/data phase. Use `-clock_fall` to reference the falling edge instead of the default rising edge.
- **Clock groups for Zynq PS/PL boundary**: The PS clock (`clk_pl_0`, 100 MHz by default) and any free-running PL clocks must be declared as `asynchronous` or `exclusive` clock groups to prevent Vivado timing from trying to analyse CDC paths across them.
- **Timing Constraint Wizard**: Vivado's built-in wizard (`Tools → Timing Constraint Wizard`) auto-detects unclocked ports and generates skeleton `set_input_delay` / `set_output_delay` constraints — a good starting point for new designs.
- **Kria KV260 XDC file**: AMD provides an official XDC pin assignment file for the K26 SoM. Always source it first before adding any custom constraints to avoid overriding the SoM's fixed MIO pin directions.

### Code Example

```tcl
# kv260_top.xdc — minimal timing constraints for PS-PL AXI-BRAM design

# 1. Source the official K26 SoM pin XDC (adjust path as needed)
# source kv260_som.xdc

# 2. The PS generates pl_clk0 at 100 MHz — constrain it
create_clock -name pl_clk0 -period 10.000 [get_ports pl_clk0]

# 3. If you have an external reset button on the carrier:
set_input_delay -clock pl_clk0 -max 2.0 [get_ports reset_n]
set_input_delay -clock pl_clk0 -min 0.5 [get_ports reset_n]

# 4. Mark PS and PL clocks as asynchronous to avoid false timing paths
# (PS-side clocks are generated internally; PL sees them via pl_clk0)
set_clock_groups -asynchronous \
    -group [get_clocks pl_clk0] \
    -group [get_clocks -of_objects [get_pins */PLLE4_ADV*/CLKOUT0]]

# 5. Relax CDC paths between PS AXI clock domain and any PL async logic
set_false_path -from [get_clocks pl_clk0] \
               -to   [get_clocks -filter {NAME =~ *async_clk*}]
```

### Relevance to Your Project

For a pure AXI-BRAM design where all logic runs on a single `pl_clk0` from the PS, only constraints 1–2 are strictly necessary. Constraint 4 prevents Vivado from attempting timing analysis across the PS boundary, which would otherwise generate misleading critical-path warnings that mask real issues in the PL.

## Kria KV260 / K26 SoM

### Key Findings

- **Boot modes**: The K26 SoM exposes `MODE[3:0]` pins at the SoM connector. The KV260 starter kit ships configured for `QSPI32` boot (pre-loaded FSBL + PMU firmware). For development, JTAG boot is easiest: connect via USB, configure XSDB to switch boot mode, then load bitstream and application ELF.
- **MIO vs EMIO pinout**: Most PS peripherals (UART, I2C, SD) use MIO bank 500 on the SoM. The carrier-specific expansion headers (RPi 40-pin, PMOD) are routed through the PL fabric via EMIO — they are not direct PS MIO.
- **Power domains**: The K26 SoM sideband signals use VCCO = 1.8 V. The PL I/O banks on the carrier can be 1.8 V or 3.3 V depending on the specific header — check the KV260 carrier schematic before assigning IOSTANDARD in XDC.
- **Custom PL overlays (2025.2)**: AMD EDF v2025.2 supports loading custom PL designs as runtime overlays using `xmutil loadapp`. The overlay consists of a `.bit` file, Device Tree Overlay (`.dtbo`), and a JSON descriptor placed in `/lib/firmware/xilinx/<app_name>/`. This is the Linux path; for bare-metal you still program the PL at boot via FSBL or XSDB.
- **PS UART for USB-UART**: On the KV260 carrier, the USB-UART adapter connects to `UART1` (MIO 36/37). The BSP `standalone` domain defaults to `UART0`. Set `stdin`/`stdout` to `psu_uart_1` in the BSP MSS settings to get `xil_printf` output on the USB connector.

### Code Example

```tcl
# XSDB script: JTAG boot flow for KV260 bare-metal AXI-BRAM demo
# Usage: xsdb jtag_boot.tcl

connect

# Switch to JTAG boot mode (overrides QSPI32 board setting temporarily)
targets -set -nocase -filter {name =~ "PSU"}
mwr 0xFF5E0200 0x0100   ;# BOOT_MODE_USER: JTAG

# Reset PS (needed after boot-mode change)
rst -system

# Program PL with bitstream
targets -set -nocase -filter {name =~ "PL*"}
fpga ./output/kv260_top.bit

# Load and run FSBL on Cortex-A53 #0
targets -set -nocase -filter {name =~ "Cortex-A53 #0"}
dow ./output/fsbl.elf
con
after 3000

# Load PMU firmware
targets -set -nocase -filter {name =~ "MicroBlaze PMU"}
dow ./output/pmufw.elf
con
after 1000

# Load and run bare-metal application
targets -set -nocase -filter {name =~ "Cortex-A53 #0"}
rst -processor
dow ./output/kv260_bram_demo.elf
con
```

### Relevance to Your Project

The XSDB script above is the direct script to load your bare-metal AXI-BRAM binary onto the KV260 via JTAG. Adapt `./output/` paths to match your Vitis workspace structure. The `after 3000` delay gives the FSBL time to complete DDR initialisation before the application is loaded.

## AMD/Xilinx Tool Updates

### Key Findings

- **Vivado 2025.1 IP change log**: AXI Ethernet Buffer received a bug fix for correct PTP 1588 frame handling at the Buffer→MAC interface. Sync LVDS mode support added for Versal devices via Advanced IO Wizard. IP Catalog taxonomy was restructured — some IP search paths have changed.
- **`AXI_ACLK_FREQ_MHZ` parameter removed from BD TCL**: Vivado 2025.1 IP release notes state that `AXI_ACLK_FREQ_MHZ` and `C_S_AXI_ID_WIDTH` are no longer initialised in BD TCL outputs. If your `create_bd.tcl` explicitly sets these parameters, they may cause warnings or errors in 2025.1.
- **Vivado 2025.2 available**: Released November 2025 with further improvements. Open source component release notes are published on the Xilinx Confluence wiki.
- **Vivado 2026.1 docs published**: AMD has already published UG973 and UG1742 for Vivado/Vitis 2026.1, indicating a 2026.1 tool release. If you plan to upgrade from 2025.1, review the migration guide first.
- **AXI4-Lite Interface Generation known issue (2025.2)**: Designs with Gateway In/Out configured as AXI4-Lite interfaces do not support testbench generation in Model Composer 2025.2 (UG1483). Does not affect standard `axi_bram_ctrl` IP.
- **Vitis Unified IDE 2025.x**: Platform creation workflow stable. The `standalone` BSP + Cortex-A53 selection path is unchanged between 2025.1 and 2025.2.

### Code Example

```tcl
# Check for deprecated parameter in existing create_bd.tcl
# Run in Vivado Tcl Console to find and report uses of removed params

set bd_file [get_files -filter {FILE_TYPE == "Block Designs"}]
set fh [open $bd_file r]
set content [read $fh]
close $fh

foreach deprecated_param {AXI_ACLK_FREQ_MHZ C_S_AXI_ID_WIDTH} {
    if {[string match "*$deprecated_param*" $content]} {
        puts "WARNING: Deprecated parameter '$deprecated_param' found in BD."
        puts "  Remove or update for Vivado 2025.1+ compatibility."
    }
}
puts "Parameter check complete."
```

### Relevance to Your Project

Your `create_bd.tcl` was generated with an earlier Vivado version. Running the snippet above in the Vivado 2025.1 Tcl Console identifies parameters that need to be removed before the script will cleanly re-run in 2025.1. This is especially relevant if you regenerate the block design from scratch (e.g. on a CI machine with a clean Vivado 2025.1 install).
