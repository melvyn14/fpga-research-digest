# FPGA Research Digest - 2026-07-09

## Executive Summary

- **AXI-Stream TVALID must never be de-asserted until TREADY is seen** — a master that drops TVALID while waiting for TREADY is a protocol violation that can cause silent data loss or deadlock in AXI-Lite/Stream-connected BRAM paths.
- **On the KV260 the PL has no independent clock source** — your block design must derive the PL fabric clock from the PS (`pl_clk0` from the Zynq MPSoC IP), and every IP including both BRAM controllers must be driven by that same domain; failing to connect pl_resetn0 causes the AXI BRAM controller to remain in reset after bitstream load.
- **Vivado 2025.1 ships with a new RTL-based AXI Switch IP and Pblock planner** — the AXI Switch is fully customisable and replaces workarounds involving AXI Interconnect for simple fan-out; the Pblock planner helps with PL resource assignment on the K26.
- **Vitis 2025.1 `xil_printf` drops `%f` support** — use `printf` (enable in BSP settings by linking newlib) or convert floats to fixed-point integers before printing; `xil_printf` with `%f` silently prints nothing.
- **KV260 bare-metal JTAG boot sequence requires FSBL + bitstream + ELF** — writing only the application ELF via XSDB without re-initialising the PL leaves stale bitstream state, causing false PASS results on address 0xA0000000 if the previous run left residual data in BRAM.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- **VALID/READY handshake invariant**: once a master asserts TVALID (or AWVALID/WVALID/ARVALID), it must hold it high until the corresponding READY is sampled high on the same rising edge. Dropping VALID early is a protocol violation that can desynchronise the AXI Interconnect's internal state machine.
- **AXI-Lite does not support bursts** — every transaction is a single 32-bit or 64-bit beat. The BRAM controller in AXI-Lite mode (`C_S_AXI_PROTOCOL = AXI4LITE`) takes one additional clock cycle of latency compared to AXI4 full-burst mode because it does not pipeline address and data phases.
- **BRESP/RRESP must be checked** — DECERR (`2'b11`) is returned by the AXI interconnect when an address has no mapped slave. Most bare-metal loops read/write by raw pointer without checking these; a missed DECERR silently leaves BRAM unwritten. Poll `RRESP[1:0]` after each read.
- **AXI-Stream TLAST and TKEEP** — most AXI-Stream consumer IPs expect both `tlast` and `tkeep` side-bands. Connecting a stream source that omits `tkeep` to a FIFO IP will cause a port-type mismatch in IP Integrator's connection automation.
- **TREADY registration pitfall**: registering TREADY through an extra flip-flop to break combinational paths adds one cycle of back-pressure latency. For the AXI BRAM controller at 100 MHz this is negligible, but the upstream AXI Interconnect must not assume zero-cycle TREADY.

### Code Example

```c
/* AXI-Lite write-and-check-response via Xil_In32/Xil_Out32 */
#include "xil_io.h"
#include "xil_printf.h"

#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL

/* Returns 1 on verified round-trip, 0 on mismatch */
int axi_bram_write_verify(u32 base, u32 offset, u32 pattern) {
    Xil_Out32(base + offset, pattern);
    /* Memory barrier: ensure AXI write completes before read */
    __asm__ volatile ("dsb sy" ::: "memory");
    u32 readback = Xil_In32(base + offset);
    if (readback != pattern) {
        xil_printf("FAIL: addr=0x%08X wrote=0x%08X read=0x%08X\r\n",
                   (unsigned)(base + offset), (unsigned)pattern, (unsigned)readback);
        return 0;
    }
    return 1;
}
```

### Relevance to Your Project

Your main.c tests BRAM0 at `0xA0000000` and BRAM2 at `0xA0010000`. Adding a DSB memory barrier between `Xil_Out32` and `Xil_In32` prevents the Cortex-A53 store buffer from returning stale data on the read before the AXI write reaches the BRAM controller — a subtle source of false PASS results on cache-coherent systems.

## Vivado Block Design / IP Integrator

### Key Findings

- **Connection Automation vs explicit `connect_bd_net`**: `apply_bd_automation` infers connections from interface rules and is convenient for standard PS-to-AXI-slave wiring, but it adds AXI Interconnect shim even when a direct AXI SmartConnect or direct connection would suffice. For exactly two BRAMs on a single AXI master, use explicit `connect_bd_intf_net` to wire HPM0 → SmartConnect → BRAM controllers directly.
- **Address Editor must be verified after every IP regeneration** — re-running `apply_bd_automation` can reset address offsets. Check that BRAM0 is at `0x0000_0000_A000_0000` and BRAM2 at `0x0000_0000_A001_0000` with 64 KB ranges after any automation step.
- **Vivado 2025.1 adds "Clocking and Reset" and "Interrupt and AXI4-Lite" views** in the IP Integrator toolbar — use these to audit unconnected reset pins on the BRAM controllers; an unconnected `s_axi_aresetn` pin will hold the controller in reset silently.
- **Block design DRC runs automatically before synthesis** — `validate_bd_design` in TCL catches unconnected mandatory ports before they cause cryptic downstream errors.
- **SmartConnect vs AXI Interconnect**: SmartConnect (`axi_smc`) is the preferred modern IP. It performs protocol conversion, data-width conversion, and clock conversion, and it is clocking-aware. AXI Interconnect (`axi_interconnect`) is the legacy IP — still functional but no longer receives optimisation improvements.

### Code Example

```tcl
# Explicit SmartConnect wiring for BRAM0 and BRAM2 in IP Integrator
# Run after create_bd_cell calls for zynq_ultra_ps_e_0, axi_smc,
# axi_bram_ctrl_0, blk_mem_gen_0, axi_bram_ctrl_2, blk_mem_gen_2

connect_bd_intf_net [get_bd_intf_pins zynq_ultra_ps_e_0/M_AXI_HPM0_FPD] \
    [get_bd_intf_pins axi_smc/S00_AXI]

connect_bd_intf_net [get_bd_intf_pins axi_smc/M00_AXI] \
    [get_bd_intf_pins axi_bram_ctrl_0/S_AXI]

connect_bd_intf_net [get_bd_intf_pins axi_smc/M01_AXI] \
    [get_bd_intf_pins axi_bram_ctrl_2/S_AXI]

# Wire pl_clk0 and pl_resetn0 to all clk/reset pins
connect_bd_net [get_bd_pins zynq_ultra_ps_e_0/pl_clk0] \
    [get_bd_pins axi_smc/aclk] \
    [get_bd_pins axi_bram_ctrl_0/s_axi_aclk] \
    [get_bd_pins axi_bram_ctrl_2/s_axi_aclk]

connect_bd_net [get_bd_pins zynq_ultra_ps_e_0/pl_resetn0] \
    [get_bd_pins axi_smc/aresetn] \
    [get_bd_pins axi_bram_ctrl_0/s_axi_aresetn] \
    [get_bd_pins axi_bram_ctrl_2/s_axi_aresetn]

# Assign addresses
assign_bd_address [get_bd_addr_segs axi_bram_ctrl_0/S_AXI/Mem0]
set_property offset 0xA0000000 [get_bd_addr_segs \
    {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property range 64K [get_bd_addr_segs \
    {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]

assign_bd_address [get_bd_addr_segs axi_bram_ctrl_2/S_AXI/Mem0]
set_property offset 0xA0010000 [get_bd_addr_segs \
    {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_2_Mem0}]
set_property range 64K [get_bd_addr_segs \
    {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_2_Mem0}]

validate_bd_design
```

### Relevance to Your Project

Using `axi_smc` (SmartConnect) instead of `axi_interconnect` in your `create_bd.tcl` reduces LUT usage and simplifies clock-domain management. The explicit address assignments guarantee the offsets match the `#define` values in your `main.c` and survive any future IP re-customisation or Vivado version upgrade.

## Vivado TCL Scripting

### Key Findings

- **Exporting a block design to TCL**: `File → Export → Export Block Design` (or `write_bd_tcl`) serialises the entire BD including IP configuration, connections, and address assignments. This is the correct starting point for a reproducible `create_bd.tcl`; however, the output may contain version-specific `CONFIG.*` property names that break under different Vivado releases.
- **Non-project mode** (`vivado -mode batch -source build.tcl`) never creates `.xpr`/`.cache` directories and is significantly faster for CI/CD builds. It requires explicitly calling `read_vhdl`, `read_bd`, `read_xdc` before any synthesis step.
- **`apply_bd_automation` in scripts**: parameterised automation can be scripted with `apply_bd_automation -rule xilinx.com:bd_rule:zynq_ultra_ps_e -config {...}`, but AMD's own documentation recommends replacing this with explicit `connect_bd_net` calls to avoid non-determinism across tool versions.
- **`open_bd_design` is required before `validate_bd_design`** in non-project mode; forgetting this produces a misleading "no open block design" error after a `read_bd` call.
- **Wrapper generation**: `make_wrapper -files [get_files *.bd] -top` generates the VHDL/Verilog wrapper around your block design; add `update_compile_order -fileset sources_1` afterward to keep the fileset consistent.

### Code Example

```tcl
# Non-project mode full build: BD + synthesis + implementation + bitstream
set outputDir ./output
file mkdir $outputDir

# Read sources
read_vhdl ./vhdl/kv260_top.vhd
read_bd   ./bd/design_1.bd
generate_target all [get_files design_1.bd]
make_wrapper -files [get_files design_1.bd] -top
read_vhdl [glob ./bd/hdl/*_wrapper.vhd]

# Constraints
read_xdc  ./constraints/kv260_top.xdc

# Synthesis
synth_design -top kv260_top_wrapper -part xck26-sfvc784-2LV-c

# Implementation
opt_design
place_design
route_design

# Reports (optional but recommended)
report_timing_summary -file $outputDir/timing.rpt
report_utilization    -file $outputDir/util.rpt

# Bitstream
write_bitstream -force $outputDir/kv260_top.bit

puts "Build complete: $outputDir/kv260_top.bit"
```

### Relevance to Your Project

Your existing `create_bd.tcl` handles BD creation. Wrapping it with the synthesis/implementation/bitstream commands shown above converts it into a single-command end-to-end build (`vivado -mode batch -source build.tcl`) — no GUI needed. This is the recommended pattern for version-controlled FPGA projects.

## Vitis Bare-Metal / Standalone

### Key Findings

- **`xil_printf` format string support is limited** — supported specifiers are `%d`, `%i`, `%u`, `%x`, `%X`, `%c`, `%s`, `%l` (long modifier). `%f`, `%e`, `%g` are silently ignored. To print floating-point, either link newlib (`printf`) or multiply by a power of 10 and print as integer.
- **BSP UART selection** (`standalone_stdin` / `standalone_stdout`): in Vitis 2025.1 these are configured under *Platform → BSP Settings → standalone → stdin/stdout*. For KV260 over USB, use `psu_uart_1` (connected to the USB-UART bridge on the KV260 carrier); `psu_uart_0` maps to the SOM UART exposed on the PS MIO.
- **Linker script memory regions**: the default Vitis standalone linker script places `.text` in DDR starting at `0x0` with a 2 GB span. For bare-metal AXI BRAM demos, add a custom section for your pattern buffer in the linker script to guarantee it lives in cached DDR rather than the BRAM address space.
- **BSP regeneration is required after platform changes** — if the Vivado block design is updated (e.g. address range changed), the XSA must be re-exported and the Vitis platform rebuilt before the BSP `xparameters.h` constants update.
- **`XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR`** in `xparameters.h` is auto-generated from the XSA and reflects the address editor assignment. Always use these macros in `main.c` rather than hard-coding `0xA0000000` to keep the software portable across address changes.

### Code Example

```c
/* BSP-portable BRAM access using xparameters.h macros */
#include "xparameters.h"
#include "xil_io.h"
#include "xil_printf.h"

/* These are generated from the XSA address editor */
#define BRAM0_BASE  XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR
#define BRAM2_BASE  XPAR_AXI_BRAM_CTRL_2_S_AXI_BASEADDR

static const u32 PATTERNS[] = {0xDEADBEEF, 0xCAFEBABE, 0xA5A5A5A5, 0x12345678};
#define N_PATTERNS (sizeof(PATTERNS) / sizeof(PATTERNS[0]))

int main(void) {
    xil_printf("KV260 AXI-BRAM Test\r\n");

    int pass = 1;
    for (u32 i = 0; i < N_PATTERNS; i++) {
        Xil_Out32(BRAM0_BASE + i * 4, PATTERNS[i]);
        Xil_Out32(BRAM2_BASE + i * 4, ~PATTERNS[i]);
    }
    __asm__ volatile ("dsb sy" ::: "memory");
    for (u32 i = 0; i < N_PATTERNS; i++) {
        u32 r0 = Xil_In32(BRAM0_BASE + i * 4);
        u32 r2 = Xil_In32(BRAM2_BASE + i * 4);
        if (r0 != PATTERNS[i] || r2 != ~PATTERNS[i]) {
            xil_printf("FAIL offset=%u BRAM0=0x%08X BRAM2=0x%08X\r\n",
                       (unsigned)(i*4), (unsigned)r0, (unsigned)r2);
            pass = 0;
        }
    }
    xil_printf(pass ? "PASS\r\n" : "OVERALL FAIL\r\n");
    return 0;
}
```

### Relevance to Your Project

Using `XPAR_*` macros rather than hard-coded addresses means your `main.c` automatically picks up address changes made in the Vivado address editor without a manual source edit — critical when debugging address conflicts or adding a third BRAM instance.

## XDC Timing Constraints

### Key Findings

- **Primary clock definition** for the KV260: the PL fabric clock comes from the PS (`pl_clk0`), not from an external pin, so there is no `create_clock` on an FPGA pin. Vivado automatically creates a virtual clock for `pl_clk0` when the Zynq MPSoC IP is in the design — verify this with `report_clocks` and confirm a 100 MHz (10 ns period) clock appears.
- **`set_input_delay` / `set_output_delay`**: these apply to signals crossing the FPGA I/O boundary. For a pure PS-to-PL AXI-BRAM design with no external IO, these commands are not needed — all timing paths are internal. Adding unnecessary I/O constraints can generate false violations.
- **Clock groups for PS/PL paths**: if your design uses both `pl_clk0` and an EMIO-derived clock, add `set_clock_groups -asynchronous` between them to suppress false paths across the domain boundary.
- **`set_false_path` vs `set_max_delay`**: for CDC (clock domain crossing) registers, use `set_false_path -datapath_only` to exclude the path from setup/hold analysis. Using `set_max_delay` without `-datapath_only` still runs hold checks and can produce unnecessary hold violations.
- **Timing closure tips**: if `route_design` reports negative WNS, try `-directive AggressiveExplore` or add Pblock constraints to cluster logic near the PS block; path delays through the AXI interconnect can be long if logic is spread across the device.

### Code Example

```tcl
# Minimal XDC for KV260 bare-metal AXI-BRAM demo (no external IOs)
# pl_clk0 is created automatically by the Zynq MPSoC IP at 100 MHz
# Verify with: report_clocks

# If EMIO GPIO is used for an external indicator LED on the carrier card:
set_property PACKAGE_PIN  A12  [get_ports {led[0]}]
set_property IOSTANDARD   LVCMOS33 [get_ports {led[0]}]

# EMIO is driven synchronously from pl_clk0, no IO delay constraint needed
# for a pure register-to-pad path with no external setup requirement.

# Suppress CDC paths if using a second clock domain (e.g. for AXI-Stream):
# set_clock_groups -asynchronous \
#     -group [get_clocks clk_out1_design_1_clk_wiz_0_0] \
#     -group [get_clocks clk_pl_0]

# Prohibit placement of logic in the PS hard-block region:
# create_pblock pblock_pl
# add_cells_to_pblock [get_pblocks pblock_pl] [get_cells -hierarchical -filter {NAME =~ design_1_i/*}]
# resize_pblock [get_pblocks pblock_pl] -add {CLOCKREGION_X0Y0:CLOCKREGION_X1Y1}
```

### Relevance to Your Project

For your current demo with no external FPGA I/O (PS UART is MIO, not PL), the XDC file needs only VCCAUX and bank voltage settings if required by the carrier card, plus any EMIO-mapped output pins. No `set_input_delay`/`set_output_delay` commands are needed — keeping the XDC minimal avoids false timing violations that waste debug time.

## Kria KV260 / K26 SoM

### Key Findings

- **Boot mode**: the KV260 ships with QSPI32 as the default boot mode (MODE[3:0] = `0110` via resistors on the carrier card). For bare-metal development, JTAG mode is strongly preferred — set via the Vivado Hardware Manager or XSDB without physically changing resistors; the boot mode register can be overridden in software.
- **PL clock requirement**: the K26 SoM has no dedicated PL oscillator on the carrier card. All PL clocks must come from the PS (`pl_clk0` … `pl_clk3`) configured through the Zynq MPSoC IP. Attempting to use an external clock pin that isn't populated results in an unconstrained clock and synthesis warnings.
- **MIO pin allocation**: MIO 0–25 are allocated to the SOM (eMMC, QSPI, I2C, JTAG). MIO 26–77 are available to the carrier card. The KV260 carrier uses MIO 38–39 for `psu_uart_1` (USB-UART bridge) — confirmed by the KV260 XDC reference design.
- **EMIO**: EMIO[0..95] are routed through the PL fabric and can be connected to PS GPIO registers from software (`XGpioPs_WritePin`). The KV260 carrier card exposes EMIO on the Raspberry Pi and PMOD connectors.
- **Bare-metal JTAG sequence with XSDB**:
  1. Connect: `connect`
  2. Target the A53 cluster: `targets -set -filter {name =~ "PSU"}`
  3. Run FSBL: `dow fsbl.elf && con`
  4. After FSBL completes, target core 0: `targets -set -filter {name =~ "Cortex-A53 #0"}`
  5. Program PL: `fpga kv260_top.bit`
  6. Load and run app: `dow kv260_bram_test.elf && con`

### Code Example

```tcl
# XSDB script for iterative JTAG bare-metal boot on KV260
# Usage: xsdb boot_jtag.tcl

connect

# Reset the entire SoC
targets -set -filter {name =~ "PSU"}
rst -system

# Download and run FSBL to initialise DDR, MIO, etc.
dow build/fsbl.elf
con

# Wait for FSBL to complete (watches for FSBL done magic word in memory)
after 3000

# Switch to Cortex-A53 #0
targets -set -filter {name =~ "Cortex-A53 #0"}
rst -processor

# Program the PL bitstream
fpga -f build/kv260_top.bit

# Load application ELF
dow build/kv260_bram_test.elf

# Set a breakpoint at exit so the target halts cleanly
bpadd -addr &exit

# Run
con

puts "Board running - connect terminal to /dev/ttyUSB1 at 115200 baud"
```

### Relevance to Your Project

The XSDB script above matches the two-BRAM bare-metal flow: FSBL initialises DDR and clock PLL, the bitstream loads your `kv260_top.vhd` wrapper with both BRAM controllers, and the ELF runs your PS-to-PL AXI read/write test. Running this script from the command line (`xsdb boot_jtag.tcl`) lets you iterate in seconds without touching the SD card or QSPI flash.

## AMD/Xilinx Tool Updates (Vivado / Vitis 2025.x)

### Key Findings

- **Vivado 2025.1 new features**:
  - **Pblock Planner**: interactive visual tool for placing logic into constrained regions — useful for isolating your AXI BRAM controllers to a specific clock region on the K26.
  - **PS-first boot / dynamic PL loading**: supports booting the Cortex-A53 before the PL is configured, then loading the bitstream at runtime. This enables faster boot times and matches the Kria Linux runtime platform model.
  - **Fully customisable RTL-based AXI Switch IP**: new IP replacing ad-hoc AXI Interconnect fan-outs. Supports 1–16 masters and slaves with configurable arbitration.
  - **Improved HLS timing estimation accuracy**: better correlation between HLS latency estimates and post-route timing.
- **Vitis 2025.1 new features**:
  - **Enhanced GEMV and FFT for AI Engine**: vectorised operations for the AI Engine array on devices that include it (not applicable to K26, which has no AI Engine).
  - **New Overview feature with Timeline Trace Viewer**: helps correlate software execution phases with hardware AXI transaction timing.
  - **Vitis Unified IDE** continues replacing Vitis Classic; both are present in 2025.1 but Classic is being deprecated.
- **Vivado 2025.2** is available as of mid-2026 and adds further improvements to incremental implementation and timing closure directives.
- **Known issue to watch**: some users report that `apply_bd_automation` in Vivado 2025.1 incorrectly assigns address ranges when two BRAM controllers share a SmartConnect master — manual `set_property offset/range` corrections are required after automation.

### Code Example

```tcl
# Vivado 2025.1: use the new RTL-based AXI Switch instead of legacy AXI Interconnect
# for a cleaner 1-master / 2-slave fan-out to BRAM0 and BRAM2

create_bd_cell -type ip -vlnv xilinx.com:ip:axi_switch:1.0 axi_switch_0
set_property -dict [list \
    CONFIG.NUM_SI {1} \
    CONFIG.NUM_MI {2} \
    CONFIG.ADDR_WIDTH {32} \
    CONFIG.DATA_WIDTH {32} \
    CONFIG.PROTOCOL {AXI4LITE} \
] [get_bd_cells axi_switch_0]

# Connect PS HPM0 FPD to AXI Switch slave port
connect_bd_intf_net \
    [get_bd_intf_pins zynq_ultra_ps_e_0/M_AXI_HPM0_FPD] \
    [get_bd_intf_pins axi_switch_0/S00_AXI]

# Connect AXI Switch master ports to BRAM controllers
connect_bd_intf_net \
    [get_bd_intf_pins axi_switch_0/M00_AXI] \
    [get_bd_intf_pins axi_bram_ctrl_0/S_AXI]

connect_bd_intf_net \
    [get_bd_intf_pins axi_switch_0/M01_AXI] \
    [get_bd_intf_pins axi_bram_ctrl_2/S_AXI]
```

### Relevance to Your Project

The RTL-based AXI Switch in Vivado 2025.1 is worth evaluating as a replacement for SmartConnect in your block design — it offers lower latency for simple 1-to-N fan-outs because it skips the protocol-conversion logic that SmartConnect always instantiates. For your two-BRAM design at AXI-Lite protocol, the AXI Switch may reduce resource usage and improve timing margin. The PS-first boot capability also aligns with iterative JTAG development: the PS can be started immediately while the PL bitstream is loaded separately.
