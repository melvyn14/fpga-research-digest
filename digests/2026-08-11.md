# FPGA Research Digest - 2026-08-11

## Executive Summary

- **AXI BRAM write-enable glitch**: The AXI BRAM Controller can assert write-enable one clock early, causing an extra spurious write. Tying the BRAM EN signal properly in the block design fixes this — directly relevant to your BRAM0/BRAM2 write paths.
- **VALID must never be de-asserted mid-handshake**: On all AXI channels, once an initiator drives VALID high it must hold it until READY arrives. Violating this in bare-metal C (e.g., a tight polling loop that re-initiates before a handshake completes) causes silent data corruption over AXI-Lite.
- **Kria bare-metal boot requires JTAG or QSPI** — there is no jumper to force JTAG mode; you must configure the boot mode via XSCT/XSDB scripts or use the SD-card-removal workaround to launch a debug session in Vitis 2025.1.
- **`write_bd_tcl` only serialises non-default parameters** — regenerating a block design from a saved TCL script will silently skip tool-propagated values. Always verify IP parameters after re-running `create_bd.tcl`.
- **Vivado 2025.2 adds an ultra-low-area mode for AXI SmartConnect**: the new `STRATEGY` parameter reduces LUT count significantly, useful if you later expand the KV260 PL fabric with more AXI peripherals.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- **VALID-must-not-de-assert rule**: Once a master asserts AWVALID/WVALID/ARVALID it cannot clear it until the corresponding READY arrives. Bare-metal code that polls a status bit and restarts a transaction mid-flight breaks this invariant and will cause slave state-machine corruption on the BRAM controller.
- **AXI BRAM Controller write-enable early assertion**: Xilinx's AXI BRAM Controller v4.x is documented to assert write-enable one clock before the last WVALID/WREADY handshake completes in certain burst configurations. Leaving the BRAM EN pin floating (rather than driven by the controller's `bram_en_a` output) can allow an extra stale word to be written.
- **AXI-Lite has no bursts**: AXI-Lite transfers are always single-beat. Each 32-bit word to BRAM requires a complete address + data + response handshake cycle. The BRAM Controller in AXI4-Lite mode acknowledges the write with BVALID after the operation; the master must wait for BREADY/BVALID to close before starting the next transaction — failure to do so causes silent drops.
- **AXI-Stream TVALID stickiness**: Unlike AXI-Lite, AXI-Stream TVALID is "sticky" — it cannot be de-asserted until TREADY arrives. TLAST must be properly terminated; several Xilinx FIFO and DMA IPs stall indefinitely if TLAST never asserts at the end of a packet.
- **AXI4 VIP timing in simulation**: Vivado's AXI VIP drives control signals with specific setup/hold relative to the rising clock edge. Mismatches in simulation testbench clocking against the VIP can produce false failing handshakes that do not reflect real hardware behaviour.

### Code Example

```c
/* Minimal AXI-Lite write + read-back with proper BVALID polling
   using Xilinx bare-metal xil_io macros (no HAL abstraction) */
#include "xil_io.h"
#include "xil_types.h"

#define BRAM0_BASE 0xA0000000UL

static void axi_lite_write32(u32 base, u32 offset, u32 val) {
    Xil_Out32(base + offset, val);
    /* Xil_Out32 is a single AXI-Lite write; the processor stalls
       on the AXI response channel automatically via the interconnect
       — no explicit BVALID poll needed in bare-metal cache-coherent mode */
}

static u32 axi_lite_read32(u32 base, u32 offset) {
    return Xil_In32(base + offset);
}

int main(void) {
    const u32 pattern = 0xDEADBEEF;
    axi_lite_write32(BRAM0_BASE, 0x00, pattern);
    u32 readback = axi_lite_read32(BRAM0_BASE, 0x00);
    xil_printf("BRAM0[0]: wrote 0x%08X, read 0x%08X -> %s\r\n",
               pattern, readback,
               (readback == pattern) ? "PASS" : "FAIL");
    return 0;
}
```

### Relevance to Your Project

Your `main.c` writes test patterns to BRAM0 (0xA0000000) and BRAM2 (0xA0010000) via `Xil_Out32` and reads them back with `Xil_In32`. The early write-enable glitch documented for the AXI BRAM Controller means your BRAM EN pins must be wired correctly in `create_bd.tcl`; if you see extra zeros or corrupted data at offset 0, suspect this. The BVALID handshake is handled transparently by the Cortex-A53's AXI master + AXI SmartConnect in your block design, so no explicit BVALID polling is required in bare-metal C — `Xil_Out32` blocks until the transaction completes.

## Vivado Block Design / IP Integrator

### Key Findings

- **Run Block Automation before Run Connection Automation**: When instantiating the Zynq UltraScale+ Processing System (PSU), always run "Block Automation" first — it applies the correct preset and wires `pl_clk0`/`pl_resetn0`. Running Connection Automation first leaves these undriven.
- **Address Editor auto-assign**: After connecting AXI peripherals click the "Auto Assign Address" button (or run `assign_bd_address` in TCL). Without it, AXI slaves have no offset address and synthesis will fail with a confusing "unmapped AXI slave" error.
- **AXI Interconnect vs AXI SmartConnect**: For new designs on Zynq UltraScale+, prefer AXI SmartConnect over the legacy AXI Interconnect IP. SmartConnect is clock-domain-crossing aware, uses less area per master/slave port, and supports the new ultra-low-area `STRATEGY` parameter in 2025.2.
- **Vivado 2025.2 adds a new ultra-low-area mode for AXI Switch and SmartConnect** via a `STRATEGY` property — reduces fabric LUT usage for simple point-to-point connections like your PS-to-BRAM path.
- **Regenerating a block design**: The exported TCL from File → Export → Export Block Design only writes parameters the user changed. Tool-propagated values (like AXI data width, clock frequency propagation) are inferred at re-open time and may differ between Vivado versions. Always force-regenerate IP output products (`reset_target all` + `generate_target all`) after running a recreate script.

### Code Example

```tcl
# After sourcing create_bd.tcl, regenerate all IP output products cleanly
set bd_file [get_files *.bd]
set_property generate_synth_checkpoint false $bd_file

# Re-assign addresses if they were lost
open_bd_design $bd_file
assign_bd_address
validate_bd_design
save_bd_design

# Export bitstream-ready output products
generate_target all $bd_file
export_ip_user_files -of_objects $bd_file -no_script -sync -force
```

### Relevance to Your Project

Your `create_bd.tcl` script recreates the block design for the KV260 AXI-BRAM demo. If you regenerate on a fresh Vivado 2025.1 install and find that BRAM0/BRAM2 addresses at 0xA0000000/0xA0010000 are missing, the `assign_bd_address` command above (or the Address Editor GUI button) restores them. The `reset_target` + `generate_target` sequence ensures IP output products match the current tool version rather than cached stale wrappers.

## Vivado TCL Scripting

### Key Findings

- **Batch mode invocation**: `vivado -mode batch -source create_bd.tcl` runs your script non-interactively. The tool exits after the last command. Use `-nojournal -nolog` to suppress verbose log files in CI, or redirect stdout: `vivado -mode batch -source script.tcl 2>&1 | tee build.log`.
- **Non-project mode for synthesis/implementation**: Non-project mode omits `.xpr` project files entirely — sources are directly `read_vhdl`/`read_xdc` and the flow is `synth_design` → `opt_design` → `place_design` → `route_design` → `write_bitstream`. This is significantly faster in CI and avoids stale cached runs.
- **`write_project_tcl` vs `write_bd_tcl`**: `write_project_tcl -force recreate.tcl` captures the full project including fileset assignments. `write_bd_tcl` captures only the block design. For reproducible builds of a complete KV260 project use `write_project_tcl` with the `-use_bd_files` switch.
- **TCL variable scoping in bd scripts**: Variables set outside a `proc` are in the global scope and can collide when Vivado sources multiple scripts. Namespace your helper procs (`namespace eval kv260 { proc create_bd {} {...} }`) to avoid conflicts.
- **`source -notrace`**: Suppress line-by-line TCL trace output (which can grow to MBs in verbose block design scripts) with `source -notrace script.tcl` in batch mode.

### Code Example

```tcl
# Non-project mode full build script skeleton for KV260 AXI-BRAM demo
# Run: vivado -mode batch -source build_all.tcl

# Read sources
read_vhdl -library work [glob ../vhdl/*.vhd]
read_xdc ../xdc/kv260_top.xdc

# Source block design recreation
source -notrace ../tcl/create_bd.tcl

# Make wrapper and add it
set bd_path [get_files *.bd]
make_wrapper -files $bd_path -top
add_files -norecurse [glob ./kv260_wrapper.vhd]

# Synthesis
synth_design -top kv260_wrapper -part xck26-sfvc784-2LV-c

# Implementation
opt_design
place_design
route_design

# Reports and bitstream
report_timing_summary -file timing_summary.rpt
write_bitstream -force kv260_top.bit
write_hw_platform -fixed -force kv260_top.xsa
```

### Relevance to Your Project

Your current `create_bd.tcl` is the Vivado-exported block design script. Wrapping it in the non-project mode skeleton above lets you build the full KV260 bitstream from a single CI command without a GUI, reproducibly. The `part xck26-sfvc784-2LV-c` is the correct part string for the K26 SoM on the KV260 carrier.

## Vitis Bare-Metal / Standalone

### Key Findings

- **BSP stdout assignment**: In the standalone BSP settings, `stdin` and `stdout` must point to the UART instance wired to the USB-UART bridge. On KV260 this is `psu_uart_1` (the one connected to the carrier card's USB bridge). If `xil_printf` produces no output, verify this setting in `system.mss` or via the BSP configuration dialog in Vitis.
- **`xil_printf` vs `printf`**: `xil_printf` is a lightweight, non-buffered printf that does not support floating-point. It is always safe for bare-metal. Standard `printf` requires the newlib heap and a larger stack — enable it only if you specifically need float formatting and have adjusted the linker script stack/heap regions.
- **Linker script heap/stack for KV260 bare-metal**: The default standalone BSP linker script places stack in DDR at a very high address with 32 KB stack / 64 KB heap. For simple BRAM test applications these defaults are fine, but if you add interrupt handlers ensure the IRQ stack (separate from the application stack) is also sized correctly via `_STACK_SIZE` in the linker script.
- **GIC interrupt enable sequence on Zynq UltraScale+**: To enable a PL interrupt in bare-metal, you must: (1) call `XScuGic_SetPriorityTriggerType`, (2) `XScuGic_Connect` to register the handler, (3) `XScuGic_Enable` for the specific IRQ ID, (4) `Xil_ExceptionEnable()` to unmask the processor IRQ line. Missing any step results in silent interrupt loss.
- **Cache coherency with AXI BRAM**: When writing from the Cortex-A53 to a PL BRAM over AXI, the data passes through the CCI (Cache Coherent Interconnect). For BRAM-backed memory regions not marked as device memory in the MMU, stale cache lines can cause read-back mismatches. Use `Xil_DCacheFlushRange` before reading back, or mark the BRAM address region as strongly-ordered in `xil_mmu.h`.

### Code Example

```c
/* Cache flush before BRAM read-back to avoid stale D-cache lines
   affecting the pass/fail comparison */
#include "xil_cache.h"
#include "xil_io.h"

#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL
#define TEST_WORDS  16

void bram_test(u32 base, const char *name) {
    /* Write phase */
    for (u32 i = 0; i < TEST_WORDS; i++)
        Xil_Out32(base + (i * 4), 0xA5A50000 | i);

    /* Flush D-cache for this region before reading back */
    Xil_DCacheFlushRange((UINTPTR)base, TEST_WORDS * 4);

    /* Read-back and verify */
    u32 errors = 0;
    for (u32 i = 0; i < TEST_WORDS; i++) {
        u32 expected = 0xA5A50000 | i;
        u32 got = Xil_In32(base + (i * 4));
        if (got != expected) errors++;
    }
    xil_printf("%s: %s (%u/%u words correct)\r\n",
               name, errors ? "FAIL" : "PASS",
               TEST_WORDS - errors, TEST_WORDS);
}

int main(void) {
    bram_test(BRAM0_BASE, "BRAM0");
    bram_test(BRAM2_BASE, "BRAM2");
    return 0;
}
```

### Relevance to Your Project

Your `main.c` writes patterns and reads them back, printing PASS/FAIL over USB-UART. The `Xil_DCacheFlushRange` call above is the most likely fix if you ever observe intermittent FAIL results that disappear when you add a `xil_printf` between write and read (since `xil_printf` itself has memory barriers). Confirm that `stdout` in the BSP points to `psu_uart_1` — on KV260, UART1 is the one accessible from the host via the USB-C debug connector.

## XDC Timing Constraints

### Key Findings

- **For AXI-BRAM bare-metal demo, minimal XDC is sufficient**: Since all PL logic operates synchronously on `pl_clk0` (100 MHz from the PSU), and there are no I/O paths to external pins, you only need `create_clock` on `pl_clk0` plus `set_clock_groups` to isolate the PS/PL clock domains.
- **`set_input_delay` / `set_output_delay` for external I/O**: These constrain the external system-level path on primary I/O ports. Values are in nanoseconds relative to a named clock edge. Both `-max` and `-min` variants should be provided for setup and hold analysis. They are not needed for internal AXI paths.
- **False path for PS-to-PL reset**: The `pl_resetn0` synchronisation path should be declared a false path — it is an asynchronous reset that the BSP's reset synchroniser manages. Add `set_false_path -from [get_pins */PSU/pl_resetn0] -to [get_pins */rst_sync_*]` or use Vivado's Constraint Wizard.
- **Clock domain crossing (CDC) for AXI SmartConnect**: AXI SmartConnect handles CDC internally, so you do not need `set_clock_groups` between the PS AXI clock and a PL clock when using SmartConnect. If you replace SmartConnect with the legacy AXI Interconnect, you may need explicit clock group constraints.
- **Timing constraint file ordering**: XDC constraints are applied in the order they appear. Place `create_clock` before `set_input_delay`/`set_output_delay` constraints; placing them after causes Vivado to warn "clock not found" and silently skip the constraint.

### Code Example

```xdc
# Minimal XDC for KV260 AXI-BRAM bare-metal demo
# pl_clk0 is generated by the Zynq PSU block; 100 MHz

# 1. Define the PL clock (sourced from PSU — virtual in XDC, real in block design)
create_clock -period 10.000 -name pl_clk0 \
    [get_pins -hierarchical -filter {NAME =~ */PSU/pl_clk0}]

# 2. Isolate PS and PL async clock domains (SmartConnect handles the AXI CDC;
#    this covers any other cross-domain paths you may add later)
set_clock_groups -asynchronous \
    -group [get_clocks -include_generated_clocks pl_clk0] \
    -group [get_clocks -include_generated_clocks clk_pl_0]

# 3. False path on PL reset synchroniser
set_false_path -from [get_ports pl_resetn0]

# 4. I/O standard for any GPIO you expose on the carrier card
# set_property IOSTANDARD LVCMOS18 [get_ports {gpio_out[*]}]
# set_property PACKAGE_PIN <pin> [get_ports {gpio_out[0]}]
```

### Relevance to Your Project

Your `kv260_top.vhd` wrapper exposes the PL block design to the Vivado implementation flow. The XDC above constrains `pl_clk0` for proper timing analysis. Without `create_clock`, Vivado treats the design as unconstrained and timing closure reports are meaningless. The `set_false_path` on `pl_resetn0` prevents spurious timing violations on the reset synchroniser output.

## Kria KV260 / K26 SoM

### Key Findings

- **No JTAG-mode jumper on KV260**: Unlike Zynq evaluation boards, the KV260 has no MODE pin jumpers exposed to the user. To enter JTAG boot mode for bare-metal debug, you must use XSCT/XSDB with a `psu_init.tcl` script instead of FSBL, or remove the SD card and configure boot mode programmatically. Vitis 2025.1 handles this transparently when you launch a debug session with a connected JTAG adapter.
- **QSPI is write-protected by default**: The KV260 ships with the QSPI boot sectors locked to protect the factory boot firmware. You can append a custom boot image to the user partition of QSPI, but overwriting the entire QSPI will brick the board. Use the Kria-provided `program_flash` flow with the correct offset.
- **K26 SoM clock domains**: The K26 SoM PS provides `pl_clk0`–`pl_clk3` to the PL. Frequencies are set in the PSU block design settings. `pl_clk0` defaults to 99.999 MHz (targeting 100 MHz) — use this for your AXI-BRAM fabric rather than creating an additional MMCM.
- **MIO vs EMIO GPIO**: The K26 SoM's MIO pins are mostly pre-allocated to PS peripherals (UART1 on MIO 36/37, I2C on MIO 10/11, etc.). User GPIO to the carrier card expansion headers is routed via EMIO — you instantiate GPIO in the PL block design and assign it to the carrier card connector pins in XDC.
- **Power domains**: The KV260 carrier provides VCCO_HP (1.8 V) to the K26 SoM's HP banks and VCCO_HR (3.3 V) to the HR banks. When assigning XDC IOSTANDARD, ensure you use LVCMOS18 for HP-bank pins and LVCMOS33 for HR-bank pins to avoid hardware damage.

### Code Example

```tcl
# XSCT script to boot a bare-metal ELF on KV260 via JTAG
# (No SD card needed; overrides QSPI boot mode)
# Run: xsct boot_jtag.tcl

connect
targets -set -filter {name =~ "PSU"}

# Initialise the PS (replaces FSBL for JTAG debug)
source [lindex [glob $env(XILINX_VITIS)/data/embeddedsw/lib/psufsdlinit/psu_init.tcl] 0]
psu_init

# Reset PL
targets -set -filter {name =~ "PSU"}
mwr 0xFFCA0010 0x0

# Download and run the bare-metal ELF on APU Core 0
targets -set -filter {name =~ "Cortex-A53 #0"}
dow kv260_bram_test.elf
con
```

### Relevance to Your Project

This XSCT script is the recommended way to download and run your BRAM test application on KV260 without flashing QSPI — directly applicable to your current bare-metal development workflow. The `psu_init` call initialises DDR, clocks, and MIO exactly as FSBL would, making the bare-metal ELF environment identical to what you'd get after a normal boot.

## AMD/Xilinx Tool Updates (Vivado/Vitis 2025.x)

### Key Findings

- **Vivado 2025.2 highlights** (most recent release as of this digest): Versal QoR improvements — reduced PhysOpt compile time, BUFG_FABRIC replication, and module-level retiming control. New **ultra-low-area mode** for AXI Switch and AXI SmartConnect via `STRATEGY` parameter. SystemVerilog Interface support for simplified AXI connections with automatic wrapper generation. New SLR crossing reporting and ECO legalizer in Hardware Manager.
- **Vitis 2025.1 (UG1742)**: Released 2025-07-08. Key changes include updated standalone BSP for Zynq UltraScale+ with improved cache management APIs, refresh of the Vitis Unified IDE, and improved platform management for Kria applications.
- **AXI SmartConnect ultra-low-area STRATEGY** (2025.2): Set the `STRATEGY` property on an `axi_smartconnect` instance in your block design TCL to `"STRATEGY_AREA"` for minimum LUT usage on simple point-to-point AXI paths. Benchmark against the default for your design.
- **Deprecation notice**: The legacy `AXI Interconnect` IP (non-Smart) is in maintenance mode as of 2025.x. AMD recommends migrating all new designs to `AXI SmartConnect`. For the KV260 demo this is already the default when using IP Integrator in 2025.1.
- **Known issue — 2025.1 Vitis Unified IDE project import**: Some users report that importing a `.xsa` hardware platform into Vitis 2025.1 from a Vivado 2024.x project requires re-running "Update Hardware Specification" in the platform project to refresh the BSP drivers. This is important if your `.xsa` was generated with an earlier Vivado version.

### Code Example

