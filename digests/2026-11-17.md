# FPGA Research Digest - 2026-11-17

## Executive Summary
- **Critical AXI-Lite bug in Xilinx template**: The Vivado-generated AXI-Lite slave (both Verilog and VHDL) has a confirmed bug where it can accept more read requests than it returns responses, violating the spec. Never use it unmodified for real designs.
- **Vivado 2025.1 adds AXI Switch IP and new IP Integrator views**: A new RTL-based AXI Switch IP was introduced in 2025.1 (bridges types/widths), plus dedicated clocking/reset and interrupt/AXI-Lite views in IPI—but the AXI Switch does NOT participate in connection automation and needs manual address configuration.
- **BRAM address range must be explicitly set to 64K**: In the Address Editor, set the AXI BRAM Controller segment range to 64K (0x10000) to match your 0xA0010000 spacing between BRAM0 and BRAM2.
- **Vitis Classic IDE deprecated in 2025.1**: Migrate to the Vitis Unified IDE. The BSP stdout/stdin must be explicitly pointed at `psu_uart_1` for xil_printf to appear on the USB-UART port.
- **KV260 boots from QSPI by default**: A custom bare-metal boot.bin must be loaded into Image A of the QSPI flash, then marked as the requested boot image, to override the default Linux-first boot sequence.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings
- **Xilinx's VHDL AXI-Lite slave template has a confirmed outstanding-transaction bug**: `ARREADY` is not gated on `RVALID`/`RREADY`, so the slave can accept multiple read requests while still holding pending responses. The root cause: Xilinx's AXI-Lite IPIF v2.0 explicitly lists "multiple outstanding transactions" as unsupported.
- **The correct fix**: Gate acceptance of new reads on the prior response being consumed—only raise `ARREADY` when no previous read response is pending (`RVALID=0` or the response is being accepted on this cycle).
- **xVALID must deassert after reset**: A common handshake bug in AXI masters is not deassserting `xVALID` following reset. Per the spec, all VALID signals must start deasserted after `ARESETn` is released.
- **For Xilinx BRAM controllers via AXI-Lite**: The PS uses single-beat (non-burst) transactions. The PS AXI-Lite master in the Zynq PS block inherently assumes no outstanding transactions, so the BRAM controller's limitation is acceptable for this use case.
- **AXI-Stream gotcha**: Unlike AXI-Lite, AXI-Stream has no handshake for addresses—only `TVALID`/`TREADY`. Adding an `TLAST` signal is optional but required if you want packet framing.

### Code Example
```vhdl
-- Correct AXI-Lite read-channel acceptance logic (no outstanding transactions)
-- Gate ARREADY so only one read is in flight at a time
process(S_AXI_ACLK)
begin
  if rising_edge(S_AXI_ACLK) then
    if S_AXI_ARESETN = '0' then
      axi_arready <= '0';
      axi_rvalid  <= '0';
    else
      -- Accept a read address only when no response is pending
      if axi_arready = '0' and S_AXI_ARVALID = '1' and axi_rvalid = '0' then
        axi_arready <= '1';
        axi_araddr  <= S_AXI_ARADDR;
      else
        axi_arready <= '0';
      end if;
      -- Hold RVALID until master accepts the response
      if axi_arready = '1' and S_AXI_ARVALID = '1' then
        axi_rvalid <= '1';
        axi_rdata  <= slv_reg(to_integer(unsigned(axi_araddr(ADDR_LSB+OPT_MEM_ADDR_BITS downto ADDR_LSB))));
      elsif S_AXI_RREADY = '1' then
        axi_rvalid <= '0';
      end if;
    end if;
  end if;
end process;
```

### Relevance to Your Project
Your project accesses BRAM0 (0xA0000000) and BRAM2 (0xA0010000) over AXI-Lite from the Cortex-A53 PS. The PS AXI-Lite master issues single-beat, non-pipelined transactions, so a slave that handles only one outstanding transaction at a time is correct here. The key risk is if you ever replace the BRAM controller with a custom AXI-Lite slave—use the gated `ARREADY` pattern above, not the Vivado template.

## Vivado Block Design / IP Integrator

### Key Findings
- **Vivado 2025.1 introduced two new IPI views**: A "Clocking and Reset" view and an "Interrupts and AXI-Lite" view, simplifying design navigation for complex block designs.
- **New AXI Switch IP (2025.1)**: A new RTL-based AXI Switch that bridges AXI interface types and widths. **Important caveat**: This IP does not participate in IP Integrator connection automation and does not inherit Address Editor information—decode ranges must be set manually.
- **Address Editor tips**: Right-click → "Assign All" first, then verify that the two BRAM controllers got non-overlapping 64K ranges (0xA0000000 and 0xA0010000). If automation assigns overlapping addresses, unassign one and manually set offset + range.
- **Range must match physical BRAM size**: Set each AXI BRAM Controller segment range to 64K (`0x10000`) in the Address Editor to match the 0x10000 spacing in your design.
- **Regenerating the block design**: After modifying IP, always run "Validate Design" (F6) before generating the bitstream. If you see "critical warnings" about unconnected ports on `axi_bram_ctrl`, check that `bram_porta` is fully wired.

### Code Example
```tcl
# TCL: Set BRAM addresses manually in a block design after adding IPs
# After running assign_bd_address, verify and correct offsets:
set_property offset 0xA0000000 [get_bd_addr_segs {mig_7series_0/S_AXI/reg0}]
# For the KV260 design with two BRAM controllers:
assign_bd_address [get_bd_addr_segs {axi_bram_ctrl_0/S_AXI/Mem0}]
assign_bd_address [get_bd_addr_segs {axi_bram_ctrl_1/S_AXI/Mem0}]
# Then lock addresses to prevent automation from reassigning:
set_property offset 0xA0000000 \
  [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property range  0x00010000 \
  [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property offset 0xA0010000 \
  [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_1_Mem0}]
set_property range  0x00010000 \
  [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_1_Mem0}]
```

### Relevance to Your Project
Your `create_bd.tcl` script builds a block design with two BRAM controllers. The address mapping to `0xA0000000` and `0xA0010000` must survive a full `generate_target`/`write_bitstream` cycle without automation resetting them. Using `assign_bd_address` followed by manual `set_property offset/range` (as above) locks the addresses. Run `validate_bd_design` before saving to catch routing errors early.

## Vivado TCL Scripting

### Key Findings
- **Non-project mode is best for CI/batch flows**: Run with `vivado -mode batch -source script.tcl`. No `.xpr` file is created; the in-memory state is not saved. Reports and DCPs must be generated explicitly with Tcl commands.
- **Non-project mode skips `create_project`**: Sources are read with `read_vhdl`, `read_xdc`, etc. Synthesis starts with `synth_design -top <top> -part <part>`. Then `opt_design`, `place_design`, `route_design`, `write_bitstream`.
- **Project mode is better for IP Integrator block designs**: IPI is not fully supported in non-project mode (IP generation, `generate_target`, etc., require a project context). Your `create_bd.tcl` should be run in project mode.
- **Source file order matters**: In non-project mode, files are compiled in the order `read_*` commands appear. Put packages and components before entities that use them.
- **`write_project_tcl` is your friend**: After building a design interactively in Vivado GUI, use `File → Write Project Tcl` to generate a reproducible script that recreates the entire project, including IPI block design. Useful for version control.

### Code Example
```tcl
# Non-project batch flow skeleton for a simple VHDL design
# Launch: vivado -mode batch -source build.tcl

set part "xck26-sfvc784-2LV-c"  ;# Kria K26 SoM part

# Read sources in dependency order
read_vhdl -library work [glob src/*.vhd]
read_xdc constraints/timing.xdc

# Synthesize
synth_design -top kv260_top -part $part -flatten_hierarchy rebuilt
write_checkpoint -force checkpoints/post_synth.dcp

# Implement
opt_design
place_design
route_design
write_checkpoint  -force checkpoints/post_route.dcp

# Reports
report_timing_summary -file reports/timing_summary.rpt
report_utilization    -file reports/utilization.rpt

# Output
write_bitstream -force output/kv260_top.bit
```

### Relevance to Your Project
Your `create_bd.tcl` runs in project mode (uses `create_project`, `create_bd_design`, IP Integrator commands). That is the correct choice for IPI. Consider adding a separate `build.tcl` that opens the existing project and drives synthesis through bitstream generation non-interactively: `open_project kv260.xpr; launch_runs impl_1 -to_step write_bitstream; wait_on_run impl_1`.

## Vitis Bare-Metal / Standalone

### Key Findings
- **Vitis Classic IDE deprecated in 2025.1**: The Vitis Unified IDE is now the default. Classic is still present but will be removed in a future release. Migrate your application project to Unified IDE.
- **stdout/stdin must be explicitly configured**: In the BSP settings, set `standalone_stdin` and `standalone_stdout` to `psu_uart_1` (the KV260 USB-UART). Navigate to: `psu_cortexa53_0 → standalone_psu_cortexa53_0 → Board Support Package → standalone`.
- **xil_printf vs printf**: `xil_printf` is a lightweight, non-floating-point printf backed by the UART BSP driver. It is always available. Standard `printf` requires a larger libc implementation; use `xil_printf` for bare-metal to save code size.
- **Linker script memory regions**: The auto-generated `lscript.ld` maps `.text`, `.data`, `.bss`, and stack/heap to the PS DDR. Increase stack/heap by double-clicking `lscript.ld` in Vitis IDE and adjusting `Stack_Size` and `Heap_Size` symbols.
- **Interrupt controller**: For bare-metal A53, use `XScuGic` (Generic Interrupt Controller). Initialize with `XScuGic_CfgInitialize`, then `XScuGic_Connect` for each IRQ, and `Xil_ExceptionEnable` to globally enable exceptions.

### Code Example
```c
/* Minimal AXI-BRAM bare-metal write/read with xil_printf */
#include "xil_printf.h"
#include "xil_io.h"

#define BRAM0_BASE  0xA0000000UL
#define BRAM1_BASE  0xA0010000UL
#define TEST_PATTERN 0xDEADBEEFUL

int main(void) {
    u32 readback;

    xil_printf("KV260 AXI-BRAM test start\r\n");

    /* Write test pattern to BRAM0 offset 0 */
    Xil_Out32(BRAM0_BASE, TEST_PATTERN);
    /* Read back */
    readback = Xil_In32(BRAM0_BASE);
    if (readback == TEST_PATTERN)
        xil_printf("BRAM0: PASS (0x%08X)\r\n", readback);
    else
        xil_printf("BRAM0: FAIL got 0x%08X\r\n", readback);

    /* Write to BRAM2 */
    Xil_Out32(BRAM1_BASE, ~TEST_PATTERN);
    readback = Xil_In32(BRAM1_BASE);
    if (readback == (~TEST_PATTERN & 0xFFFFFFFF))
        xil_printf("BRAM2: PASS (0x%08X)\r\n", readback);
    else
        xil_printf("BRAM2: FAIL got 0x%08X\r\n", readback);

    return 0;
}
```

### Relevance to Your Project
Your `main.c` writes patterns to BRAM0 and BRAM2 and prints PASS/FAIL over USB-UART. The key operations are `Xil_Out32`/`Xil_In32` (memory-mapped I/O) and `xil_printf`. Ensure the BSP stdout is set to `psu_uart_1` or you will see no output. The `Xil_DCacheFlush()` call before reads is good practice (though the AXI-Lite path bypasses the data cache for BRAM addresses by default if the address region is marked device/strongly-ordered in the MMU).

## XDC Timing Constraints

### Key Findings
- **PS-side clocks are automatically defined**: In Vivado, the PS block (`zynq_ultra_ps_e_0`) automatically creates clock objects for `pl_clk0` through `pl_clk3`. You do NOT need `create_clock` for these—they are sourced from the PS and Vivado infers them. Verify with `report_clock_networks` after synthesis.
- **set_input_delay / set_output_delay purpose**: These model board-level timing from the FPGA boundary to external devices. For pure PS-to-PL paths (PS AXI to BRAM in PL), you typically do NOT need these constraints—there is no board trace involved.
- **AXI-Lite PS-PL path**: The PS HP/GP AXI ports cross from PS to PL within the device. Vivado's timing engine knows about these paths. The constraint you do need is `create_clock` for any external clocks, plus `set_clock_groups -asynchronous` between unrelated clock domains if you have them.
- **For UART output pin**: The USB-UART typically goes through a PS MIO pin. PS MIO timing is handled internally by the PS block. No XDC `set_output_delay` is needed for PS MIO UART.
- **External I/O constraint template**:
  ```
  set_input_delay  -clock [get_clocks pl_clk0] -max 2.0 [get_ports <port>]
  set_input_delay  -clock [get_clocks pl_clk0] -min 0.5 [get_ports <port>]
  set_output_delay -clock [get_clocks pl_clk0] -max 1.5 [get_ports <port>]
  set_output_delay -clock [get_clocks pl_clk0] -min 0.0 [get_ports <port>]
  ```

### Code Example

The PS clock (`pl_clk0`) is auto-defined. If Vivado reports timing violations after implementation, check `report_timing_summary -delay_type max` and look at the PS GP0 AXI output paths.

## Kria KV260 / K26 SoM

### Key Findings
- **Default boot sequence is QSPI-first → SD card**: The KV260 ships with a BOOT.BIN in QSPI that starts PetaLinux. For bare-metal, you must replace Image A in QSPI with your custom BOOT.BIN (containing FSBL + bitstream + bare-metal ELF) and mark it as the requested boot image.
- **UART is at 115200 baud on USB**: Connect a terminal at 115200 8N1. UART output appears on the micro-USB debug port. The UART peripheral is `psu_uart_1` in the PS.
- **MIO banking**: K26 has MIO banks 500/501/502. On-module assignments include eMMC (MIO[13:22]), QSPI (MIO[1:12]), I2C (MIO[24:25]), and TPM SPI (MIO[18:23]). Banks 501/502 are user-defined and carrier-card-specific.
- **KV260 uses PMU incremental configuration**: The KV260 and KR260 share the same K26 SoM but differ in carrier-card MIO assignments. The firmware uses PMU incremental configuration to apply the carrier-specific MIO pinout at runtime.
- **EMIO for PL I/O**: If you need GPIO from the PS to the PL (e.g., reset signals, LEDs on PL), route them through EMIO (bank 2 of the PS GPIO, pins 78–173). These are AXI-accessible from bare-metal via the `XGpioPs` driver.
- **Boot image loading**: Use XSCT or Vitis to load a boot.bin directly into QSPI: `program_flash -f boot.bin -offset 0 -flash_type qspi-x4-single`.

### Code Example
```c
/* EMIO GPIO example: toggle an LED connected to EMIO[0] (PS GPIO bank 2, pin 78) */
#include "xgpiops.h"

#define GPIO_DEVICE_ID  XPAR_XGPIOPS_0_DEVICE_ID
#define EMIO_LED_PIN    78  /* EMIO[0] = PS GPIO pin 78 */

int gpio_led_blink(void) {
    XGpioPs Gpio;
    XGpioPs_Config *ConfigPtr;

    ConfigPtr = XGpioPs_LookupConfig(GPIO_DEVICE_ID);
    XGpioPs_CfgInitialize(&Gpio, ConfigPtr, ConfigPtr->BaseAddr);

    /* Set direction: 1 = output */
    XGpioPs_SetDirectionPin(&Gpio, EMIO_LED_PIN, 1);
    XGpioPs_SetOutputEnablePin(&Gpio, EMIO_LED_PIN, 1);

    /* Toggle */
    XGpioPs_WritePin(&Gpio, EMIO_LED_PIN, 1);
    /* ... delay ... */
    XGpioPs_WritePin(&Gpio, EMIO_LED_PIN, 0);
    return 0;
}
```

### Relevance to Your Project
Your bare-metal demo uses the PS AXI GP0 port to access BRAM via AXI-Lite. For this to work in bare-metal (without Linux), your BOOT.BIN must include an FSBL that initializes the PS (DDR, clocks, PL programming). Generate FSBL from your hardware XSA in Vitis, then package: `bootgen -image boot.bif -arch zynqmp -o boot.bin`. The KV260's default boot sequence will override your design unless you write your BOOT.BIN to the QSPI Image A slot.

  - Vitis AI 5.0 is validated against Vivado/Vitis/PetaLinux 2025.1
- **Known community concerns from Reddit (r/FPGA)**:

  - Migration from Vitis Classic to Unified IDE broke some existing project setups
- **Open-source components**: The 2025.1 release notes for open-source components (Xilinx Wiki) cover PetaLinux, embeddedsw, and U-Boot changes; check this page before upgrading BSP versions.
