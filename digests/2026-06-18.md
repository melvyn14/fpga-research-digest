# FPGA Research Digest - 2026-06-18

## Executive Summary

- **The Kria Apps "Baremetal Flow Example" is the closest published reference design to your project** — it describes exactly the same pattern as `kv260-axi-bram-demo`: connect an AXI BRAM Controller's `S_AXI` to the PS's `M_AXI_HPM0` port, wire `BRAM_PORTA`/`BRAM_PORTB` to a Block Memory Generator, and confirm `HPM0` is explicitly enabled on the PS cell. Worth diffing your `create_bd.tcl` against it if you haven't already.
- **`HPM0` (and `MAXIGP0__DATA_WIDTH`) must be explicitly enabled on the Zynq UltraScale+ PS cell** — `M_AXI_HPM0_FPD` does not exist as a connectable port until `CONFIG.PSU__USE__M_AXI_GP0` is set, which is a classic silent-failure point: the BD validates fine without it, but `S_AXI` on your BRAM controllers has nothing to attach to.
- **AXI BRAM Controller's write-enable can assert one clock early** when migrating between AXI Interconnect and AXI SmartConnect topologies — a documented AMD support case traced this to the BRAM "Enable" signal not being properly tied, causing extra words to be written. If you ever swap interconnect IP in your BD, re-run the read-back PASS/FAIL test immediately rather than assuming functional equivalence.
- **`apply_bd_automation -rule xilinx.com:bd_rule:axi4`** is the scripted one-call equivalent of manually running Connection Automation per AXI master/slave pair — useful if `create_bd.tcl` is ever extended to add a third BRAM or a GPIO/timer IP, since it handles clock/reset wiring and interconnect insertion automatically.
- **Vivado 2025.1 ships a fully customizable RTL-based AXI Switch IP** and improved Directive/Subdirective support for QoR — neither is required for a two-BRAM bring-up demo today, but the AXI Switch is a lighter-weight alternative to AXI Interconnect/SmartConnect worth knowing about if PL-side AXI fan-out ever grows beyond what a single interconnect handles cleanly.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- The READY/VALID handshake rule set is absolute: once VALID is asserted it must not be deasserted until the corresponding READY arrives, and none of the accompanying signals (ADDR, DATA, STRB, etc.) may change while VALID is high and READY is low.
- READY may be withheld indefinitely without violating the protocol; VALID must never be withheld indefinitely waiting on application logic, or the system can deadlock.
- Backpressure correctness is the most commonly missed case in hand-rolled or modified AXI logic: if the master holds BREADY low, the slave must also lower AWREADY/WREADY; if RREADY is held low, ARREADY must follow. Simple directed tests rarely exercise this path, so it survives basic simulation undetected.
- A documented AMD support case found the AXI BRAM Controller asserting write-enable one clock early after switching from AXI Interconnect to AXI SmartConnect in the same design — root cause was the controller's internal "Enable" signal not being correctly tied/gated, leading to extra words written to the underlying BRAM.
- The xREADY signal should be registered (with a skid buffer if needed) rather than combinationally derived from xVALID, to avoid creating a long combinational path that limits achievable clock frequency.

### Code Example

```tcl
# Sanity check after any interconnect swap (AXI Interconnect <-> SmartConnect):
# re-verify the BRAM controller's enable/we behavior didn't shift by a cycle.
# Run in hardware manager / ILA, or re-run the bare-metal PASS/FAIL test
# immediately after regenerating the BD with the new interconnect IP.

# Programmatic check of which interconnect IP is currently used:
foreach cell [get_bd_cells -filter {VLNV =~ "*axi_interconnect*" || VLNV =~ "*smartconnect*"}] {
    puts "[get_property NAME $cell]: [get_property VLNV $cell]"
}
```

### Relevance to Your Project

Your demo currently uses the AXI BRAM Controller IP, which implements the handshake correctly out of the box — this isn't a live bug. But if a future revision changes the interconnect topology (e.g., swapping AXI Interconnect for SmartConnect to reduce resource usage, a common KV260 optimization), re-run the existing PASS/FAIL UART test immediately rather than assuming the swap is behaviorally transparent — the AMD case above shows it isn't always.

## Vivado Block Design / IP Integrator

### Key Findings

- The Address Editor tab only appears once an AXI master interface exists in the design (e.g., the PS's `M_AXI_HPM0_FPD`) — if it's missing, the master port likely isn't connected yet, not a tool bug.
- After running Connection Automation or adding new IP, "Auto-Assign Address" (right-click in the Address Editor) resolves most "peripheral not mapped" validation errors in one click.
- Regenerate Layout only affects visual block/wire arrangement in the canvas — it has zero effect on the generated bitstream or functional behavior, so it's safe to run at any point for readability.
- "Optimize Routing" is a lighter alternative to full Regenerate Layout: it only reroutes wires without moving block positions, useful when you want to preserve your manual layout but clean up wire crossings.
- Validate Design (the checkmark button) propagates IP parameters across connections — including BRAM operation mode and AXI data-width negotiation — so it should be run after any manual IP reconfiguration, not just before bitstream generation.

### Code Example

```tcl
# Equivalent of clicking "Connection Automation" for a new AXI BRAM controller's
# S_AXI port, wired to the ZynqMP PS's enabled HPM0 master port
create_bd_cell -type ip -vlnv xilinx.com:ip:axi_bram_ctrl:4.1 axi_bram_ctrl_2
set_property -dict [list CONFIG.SINGLE_PORT_BRAM {1}] [get_bd_cells axi_bram_ctrl_2]

apply_bd_automation -rule xilinx.com:bd_rule:axi4 \
  -config { Master "/zynq_ultra_ps_e_0/M_AXI_HPM0_FPD" Clk "Auto" } \
  [get_bd_intf_pins axi_bram_ctrl_2/S_AXI]

validate_bd_design
save_bd_design
```

### Relevance to Your Project

If `create_bd.tcl` issues manual `connect_bd_intf_net` calls for BRAM0 and BRAM2 today (the more reproducible, diff-friendly choice for a two-peripheral design), adding a third peripheral is the point where `apply_bd_automation` starts paying off — it handles AXI Smart/Interconnect insertion and address-map registration in one call instead of several manual connections plus an Address Editor pass.

## Vivado TCL Scripting

### Key Findings

- Non-Project Mode runs the entire synth -> place -> route -> bitstream sequence in memory without writing `.xpr` project files to disk, making it the standard choice for CI and reproducible builds.
- BD (Block Design) Tcl commands — `create_bd_cell`, `connect_bd_intf_net`, `apply_bd_automation` — require an open, in-memory project with a live BD; they cannot run in a pure non-project synth/impl-only flow.
- A common two-phase pattern: open a project just to regenerate/validate the block design and its output products, close it, then switch to non-project mode for the deterministic synth/impl/bitstream stages.
- `write_bd_tcl` by default omits visual layout info (pass `-include_layout` to keep it) and only emits parameters explicitly changed from tool defaults — re-running an exported script in a different Vivado version can yield slightly different default values for unspecified parameters.
- Exported BD Tcl scripts embed version metadata; AMD explicitly documents that a script captured in one Vivado release isn't guaranteed to run unmodified in another — relevant since this project pins Vivado 2025.1.

### Code Example

```tcl
# Two-phase build: project-mode BD regeneration, then non-project synth/impl
set PART "xck26-sfvc784-2LV-c"

open_project ./kv260_claude/kv260/kv260.xpr
source ./kv260_claude/kv260/tcl/create_bd.tcl
validate_bd_design
generate_target all [get_files *.bd]
close_project

read_vhdl   [glob ./kv260_claude/kv260/vhdl/*.vhd]
read_xdc    ./kv260_claude/kv260/constraints/*.xdc
synth_design -top kv260_top -part $PART
opt_design
place_design
route_design
write_bitstream -force ./output/kv260_top.bit
```

### Relevance to Your Project

`create_bd.tcl` already lives under version control with the BD construction logic separated from synthesis — the right structure for this two-phase pattern. The key gotcha to remember: any future automated/CI build script must open a project for the `source create_bd.tcl` step even if everything downstream runs non-project, since the BD Tcl API has no non-project equivalent.

## Vitis Bare-Metal / Standalone

### Key Findings

- `xil_printf` supports a deliberately reduced format-specifier set (`%d`, `%l`, `%x`, `%c`, `%s` — no `%f`/floating point) to keep code size and stack usage far smaller than full `stdio printf`, which matters on tight bare-metal/OCM budgets.
- BSP stdout/stdin routing is controlled by `standalone_stdin`/`standalone_stdout` settings; on multi-UART platforms, BSPs sometimes default to the wrong UART instance (e.g., `psu_uart_0` instead of `psu_uart_1`) — symptom is total silence on the expected serial console with no error reported.
- In the newer Vitis Unified IDE flow, the UART default lives in the platform component's `vitis-comp.json` file under the `Settings` folder rather than purely in BSP GUI settings — worth checking there directly if BSP settings UI doesn't show the expected value.
- The GIC standalone driver (`scugic`) requires explicit `XScuGic_LookupConfig` -> `XScuGic_CfgInitialize` -> `Xil_ExceptionEnable` sequencing in application code; this is unnecessary for a polling-only PASS/FAIL demo with no interrupts, but is the standard reference if a future revision adds an interrupt-driven UART or DMA path.
- The linker script (`lscript.ld`) defaults to using DDR if it's present on the platform, falling back to OCM otherwise — and is editable to constrain an application to a memory sub-region, which matters once a project grows to span multiple A53 cores running independent bare-metal images.

### Code Example

```c
#include "xil_io.h"
#include "xil_printf.h"
#include "xparameters.h"

/* Prefer xparameters.h macros over hardcoded literals so the address
   assignment tracks the block design's actual address map */
#define BRAM0_BASE   XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR  /* expect 0xA0000000 */
#define BRAM2_BASE   XPAR_AXI_BRAM_CTRL_1_S_AXI_BASEADDR  /* expect 0xA0010000 */

int main(void) {
    xil_printf("BRAM0 base : 0x%08X\r\n", BRAM0_BASE);
    xil_printf("BRAM2 base : 0x%08X\r\n", BRAM2_BASE);

    /* Pattern write/read-back, no interrupts needed for this test */
    Xil_Out32(BRAM0_BASE, 0xDEADBEEF);
    u32 readback = Xil_In32(BRAM0_BASE);
    xil_printf("BRAM0 test: %s\r\n", (readback == 0xDEADBEEF) ? "PASS" : "FAIL");
    return 0;
}
```

### Relevance to Your Project

If `main.c` currently hardcodes `0xA0000000`/`0xA0010000`, switching to the `XPAR_AXI_BRAM_CTRL_*_S_AXI_BASEADDR` macros generated from the exported XSA makes the addresses self-correcting if the block design's address map ever shifts (e.g., after adding a third peripheral) — eliminates a class of "works until the BD changes" bugs. Since this project has no UART output without a correctly configured BSP, confirming `standalone_stdout` points at the actual USB-UART instance is worth a one-time check if console output is ever silent after a fresh BSP regeneration.

## XDC Timing Constraints

### Key Findings

- `set_input_delay -clock <clk> -max <ns> [get_ports ...]` and `set_output_delay -clock <clk> -max <ns> [get_ports ...]` remain the canonical syntax in 2025.1/2025.2 (UG835) — no breaking changes to this command pair for the current toolchain.
- Input delay budgeting: if a source clock period is 10 ns and the driving device's clock-to-Q is 2 ns, the valid setup window is 8 ns — specify `-max` 2 ns (not the period), since `-max` models the delay, not the remaining margin.
- `set_clock_groups -asynchronous` (or `-logically_exclusive`) disables timing analysis between clock domains with no fixed phase relationship — necessary because Vivado times all clocks together by default unless told otherwise, and trying to time genuinely asynchronous CDC paths produces meaningless (and possibly unclosable) slack numbers.
- Best practice for genuine CDC paths even after exclusion: still cap with `set_max_delay -datapath_only` and tag crossing registers with `ASYNC_REG` to prevent the synthesis tool from optimizing the double-flop synchronizer structure away.
- Vivado's Timing Constraint Wizard auto-detects ports/clocks likely needing constraints and emits a draft XDC as a starting point — a faster first pass than writing every input/output delay from scratch on a new design.

### Code Example

```xdc
# Declare the PL fabric clock sourced from PS8 -- mandatory even with no
# external I/O, otherwise Vivado has nothing to time internal AXI logic against
create_clock -period 10.000 -name clk_pl_0 [get_pins zynq_ultra_ps_e_0/inst/PS8_i/PLCLK[0]]

# Any asynchronous external reset should be excluded from setup/hold analysis
set_false_path -from [get_ports ext_rst_n]

# If a future revision adds a second, independently-clocked PL block:
# set_clock_groups -asynchronous -group [get_clocks clk_pl_0] -group [get_clocks clk_pl_1]
```

### Relevance to Your Project

Since the demo's only external interface is USB-UART (handled inside the PS, not via PL pins), the constraints that matter for `kv260_top.xdc` are internal: a `create_clock` on the PS8-sourced PL clock so Vivado actually times the AXI register paths inside `kv260_top.vhd`. Without it, Vivado silently reports "no clocks found" rather than erroring loudly, so it's worth explicitly confirming this line exists rather than assuming PS-generated clocks are auto-detected.

## Kria KV260 / K26 SoM

### Key Findings

- The official Kria Apps "Baremetal Flow Example" documents this exact pattern: AXI BRAM Controller's `S_AXI` wired to the PS's `M_AXI_HPM0` port, `BRAM_PORTA` (and optionally `BRAM_PORTB`) connected to a Block Memory Generator, with `HPM0` explicitly enabled in the PS configuration — effectively the canonical reference design for `kv260-axi-bram-demo`.
- `M_AXI_HPM0_FPD` does not exist as a connectable BD port until `CONFIG.PSU__USE__M_AXI_GP0` (and the associated data-width config) is set on the Zynq UltraScale+ PS cell — a common silent-failure point where the BD looks fine but the AXI master port simply isn't there to connect to.
- KV260 boot mode is selected via MODE[3:0] pins exposed at the SOM connector; Kria Starter Kits ship preconfigured for QSPI32 boot by default, configurable post-boot via XSDB/XSCT register writes if a different boot device is needed.
- K26 SOM's PS MIO bank assignment is fixed at the hardware level — carrier cards and PL designs only have access to EMIO-routed signals, not raw reconfigurable MIO, since the SOM itself bakes in the MIO allocation.
- KV260 specifically uses PS GEM3 for Ethernet (vs. GEM1 on KR260/KD240) — a board-specific detail worth knowing if the demo is ever ported to a different Kria carrier/SOM combination.
- A 2026-dated Hackster.io guide ("Bare-metal 4K Streaming on KV260") targets the 2025.2 toolchain specifically, confirming the bare-metal flow on KV260 is actively maintained and validated against the current AMD tool versions, not just legacy releases.

### Code Example

```tcl
# Confirm HPM0 is enabled and width-matched before connecting BRAM controllers --
# the single most common silent-failure point in PS-to-PL AXI bring-up on K26
set_property -dict [list \
  CONFIG.PSU__USE__M_AXI_GP0        {1} \
  CONFIG.PSU__MAXIGP0__DATA_WIDTH   {32} \
] [get_bd_cells zynq_ultra_ps_e_0]

# Verify after the fact:
puts "HPM0 enabled: [get_property CONFIG.PSU__USE__M_AXI_GP0 [get_bd_cells zynq_ultra_ps_e_0]]"
puts "HPM0 width  : [get_property CONFIG.PSU__MAXIGP0__DATA_WIDTH [get_bd_cells zynq_ultra_ps_e_0]]"
```

### Relevance to Your Project

Your project is essentially a from-scratch reimplementation of the documented Kria "Baremetal Flow Example" pattern, with two BRAM controllers instead of one. If `create_bd.tcl` ever needs debugging for an address-map or connectivity issue, diffing it against that reference design (and explicitly checking `PSU__USE__M_AXI_GP0` / `PSU__MAXIGP0__DATA_WIDTH`) is the fastest path to spotting a config mismatch versus AMD's known-working baseline.

## AMD/Xilinx Tool Updates (Vivado/Vitis 2025.x)

### Key Findings

- Vivado 2025.1 introduces a fully customizable RTL-based AXI Switch IP, an alternative to AXI Interconnect/SmartConnect for PL-side AXI fan-out — not needed for a two-BRAM demo today, but a lighter-weight option if the design grows additional AXI peripherals.
- 2025.1 also adds the ability to boot the processing system first and dynamically load the PL afterward, enabling faster OS bring-up sequences decoupled from PL configuration timing — relevant context if the demo is ever integrated into a larger Linux-booting platform rather than a standalone bare-metal image.
- The Vitis Embedded Software Development flow in 2025.1/2025.2 continues to ship both the new Vitis Unified IDE/Vitis Server and the classic command-line utilities (`hw_server`, `bootgen`, `program_flash`) — both interaction modes remain supported, so existing TCL-driven build scripts for bare-metal apps aren't forced onto the new IDE.
- AMD's IP changelog (000037919) lists per-IP fixes for 2025.1, including BRAM statistic register mismatches in certain controller modes — worth a quick scan if the demo ever reports unexpected BRAM utilization/statistics numbers, though it doesn't affect basic read/write functionality.
- No 2025.1-specific breaking changes surfaced in this round's search that would affect an already-working AXI-Lite/BRAM bare-metal design — the toolchain appears stable for this exact use case at the version your project targets.

### Relevance to Your Project

Nothing in this round's research indicates a need to change anything in a project already built and passing on 2025.1 — the main actionable item is awareness of the new AXI Switch IP as a future option if the demo's PL-side AXI fan-out grows, and the per-IP changelog (000037919) as a reference point if BRAM statistics/utilization numbers ever look unexpected after a tool upgrade.
