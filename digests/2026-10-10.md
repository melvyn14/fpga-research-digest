# FPGA Research Digest - 2026-10-10

## Executive Summary

- **AXI BRAM Controller v4.1 does not buffer AWADDR/WDATA** on the AXI-Lite write path by default — your back-to-back write loop in `main.c` must hold those signals stable until both address and data handshakes complete independently.
- **Vivado 2025.1 changed the installation directory structure** from `Vivado/<version>/` to `<version>/Vivado/`; any CI scripts or Docker images with hardcoded paths will silently break.
- **Vitis Unified IDE is now the default GUI** in 2025.1 (Classic IDE deprecated); the XSCT tool has a known hang on Windows during application builds — use CLI build scripts as a workaround.
- **The KV260 boots from QSPI by default** (read-only); bare-metal JTAG debugging works without modifying boot firmware, but a production SD-card app requires custom FSBL/boot.bin via bootgen.
- **PS-generated clocks are already constrained by the Zynq PS IP** — never add a duplicate `create_clock` on a PS clock output port, or Vivado will flag it as a clock redefinition and timing analysis will be wrong.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- The **AXI BRAM Controller v4.1** AXI-Lite write path has no AWADDR/WDATA buffering to save LUT resources; AWREADY and WREADY are driven combinatorially. This means the master must hold both address and data valid simultaneously if it cannot independently pipeline the two channels.
- Write transfers require both the **AW and W channel handshakes** to complete before the slave drives BRESP — never assume the response arrives after only the address handshake.
- A transfer is complete on the rising clock edge where both **VALID and READY are high** simultaneously. A master must assert VALID and hold it until the slave asserts READY; it cannot deassert VALID speculatively.
- **ECC mode** on the BRAM controller turns every write into a read-modify-write, adding latency and requiring extra cycles in the bare-metal loop.
- On **AXI-Stream**: TLAST marks packet boundaries and is required whenever the downstream consumer uses DMA scatter-gather or packet mode. PS is the stream master in PS-to-PL transfers; confusing roles (treating PS as a slave) is a frequent source of silent data loss.
- AXI-Stream handshake rule: data is consumed only when `TVALID && TREADY` on a rising clock edge. The sender must not change `TDATA` after asserting `TVALID` until `TREADY` is seen.

### Code Example

```c
/* AXI-Lite write to BRAM — ensure AW and W channels complete before reading back */
#define BRAM0_BASE 0xA0000000UL
#define WR_OFFSET  0x00000004UL

static inline void axi_write32(uintptr_t addr, uint32_t val)
{
    /* Volatile prevents the compiler from reordering or eliding the store */
    *(volatile uint32_t *)addr = val;
    /* Memory barrier: wait for AXI write response before next access */
    __asm__ volatile("dsb sy" ::: "memory");
}

static inline uint32_t axi_read32(uintptr_t addr)
{
    __asm__ volatile("dsb sy" ::: "memory");
    return *(volatile uint32_t *)addr;
}

/* Usage in main.c */
axi_write32(BRAM0_BASE + WR_OFFSET, 0xDEADBEEF);
uint32_t rd = axi_read32(BRAM0_BASE + WR_OFFSET);
if (rd != 0xDEADBEEF) xil_printf("BRAM0 FAIL: got 0x%08X\r\n", rd);
else                   xil_printf("BRAM0 PASS\r\n");
```

### Relevance to Your Project

Your `main.c` accesses BRAM0 at `0xA0000000` and BRAM2 at `0xA0010000`. The `dsb sy` barrier after each write is essential: without it, the Cortex-A53 out-of-order pipeline can retire the read before the AXI write response returns, giving a false stale-data FAIL. Add barriers between every write-then-read pair in your test loop.

## Vivado Block Design / IP Integrator

### Key Findings

- **Address Editor automation**: `assign_bd_address` in Vivado TCL accepts `-import_from_file <csv>` to load a pre-defined memory map, letting you guarantee BRAM0 lands at `0xA0000000` and BRAM2 at `0xA0010000` reproducibly across Vivado versions.
- **Automatic address assignment** can silently change offset values when you add or remove IP; always run `assign_bd_address` explicitly in your TCL script rather than relying on IP Integrator's auto-assign.
- **validate_bd_design** must be called after any address change before `generate_target`; skipping it produces silent mismatches between the block design and the XSA that Vitis reads.
- Connection Automation (`apply_bd_automation`) wires up AXI Interconnect and resets automatically, but it can insert an AXI SmartConnect between the PS and your BRAM controller; verify that the SmartConnect does not add an unexpected clock domain.
- For **out-of-context synthesis** in a scripted flow, generate the block design with `generate_target {synthesis implementation simulation} [get_files *.bd]` before calling `synth_design` at the top level.

### Code Example

```tcl
# create_bd.tcl — reproducible address assignment
proc assign_bram_addresses {} {
    # Assign BRAM0 at 0xA0000000, size 8K
    set bram0_seg [get_bd_addr_segs */S_AXI/Mem0]
    set_property offset 0xA0000000 $bram0_seg
    set_property range  8K         $bram0_seg

    # Assign BRAM2 at 0xA0010000, size 8K
    set bram2_seg [get_bd_addr_segs */S_AXI/Mem1]
    set_property offset 0xA0010000 $bram2_seg
    set_property range  8K         $bram2_seg

    validate_bd_design
    save_bd_design
}
```

### Relevance to Your Project

Your `create_bd.tcl` should explicitly set and validate BRAM addresses rather than accepting whatever auto-assign chooses. If you ever add a third AXI slave, auto-assign will happily move BRAM2 away from `0xA0010000`, causing silent mismatch with the hardcoded address in `main.c`.

## Vivado TCL Scripting

### Key Findings

- **Non-project mode** (2025.1 UG994) is the correct mode for CI/batch flows: Vivado reads all sources, implements in memory, and never writes a `.xpr`. Source changes require an explicit reload — there is no project-level tracking.
- **Exporting an existing block design** via "File → Export Block Design" generates a TCL script, but the output contains project-mode artefacts (absolute paths, `create_project` calls). Always strip these before using the script in a non-project flow.
- `create_bd_design "<name>"` is the entry point for building a block design programmatically; follow it with IP creation, connection, and address assignment before calling `generate_target`.
- **Report generation** must be driven explicitly in non-project mode — there are no run objects with auto-reporting. Use `report_timing_summary -file timing.rpt` and `report_utilization -file util.rpt` immediately after `impl_design`.
- The **UG835 TCL Command Reference** (updated for 2025.1) is the authoritative source for exact command syntax; the 2025.1 version added `set_input_delay -reference_pin` improvements.

### Code Example

```tcl
#!/usr/bin/env tclsh
# non_project_build.tcl — batch implementation for KV260 AXI-BRAM demo

# Source the block design creation script
source ./tcl/create_bd.tcl

# Read design sources
read_vhdl  [glob ./vhdl/*.vhd]
read_xdc   [glob ./xdc/*.xdc]

# Generate block design wrapper (out-of-context)
make_wrapper -files [get_files kv260_bd.bd] -top
add_files -norecurse ./kv260_bd.srcs/sources_1/bd/kv260_bd/hdl/kv260_bd_wrapper.vhd
set_property top kv260_bd_wrapper [current_fileset]

# Synthesise and implement
synth_design  -top kv260_bd_wrapper -part xck26-sfvc784-2LV-c
opt_design
place_design
route_design

# Reports
report_timing_summary  -file reports/timing.rpt   -warn_on_violation
report_utilization     -file reports/utilization.rpt
report_power           -file reports/power.rpt

# Write bitstream and XSA
write_bitstream -force output/kv260_top.bit
write_hw_platform -fixed -force -include_bit output/kv260_top.xsa
```

### Relevance to Your Project

Your existing `create_bd.tcl` can be sourced directly from this non-project driver script, enabling one-command CI builds without requiring a `.xpr` file to be checked in.

## Vitis Bare-Metal / Standalone

### Key Findings

- **Vitis 2025.1** ships `xil_printf` with a 2023–2025 AMD copyright notice and a bug fix (removed unused variables from `xil_printf.c`); the function signature and usage are unchanged. It remains ~1 KB and outputs to the first UART configured in the BSP.
- **SDTGen** is now a standalone tool in 2025.1 (extracted from XSCT), used to generate the System Device Tree from an XSA. For bare-metal/standalone projects that don't use SDT, the older XSA → platform flow still works.
- **Known 2025.1 issue**: XSCT hangs during application build on Windows. Mitigation: build with `xsct -eval "app build"` from a Unix shell or use the `vitis -s build.py` Python scripting flow.
- **Linker script pitfall**: Vitis's auto-generated linker script assigns all sections to the first memory region in the XSA. For Zynq UltraScale+, this is often `PSU_DDR_0` but can be `PSU_OCM` depending on BSP settings. Verify `lscript.ld` assigns `.text`, `.data`, `.bss`, and `.heap` to DDR (`PSU_DDR_0`, starting at `0x0`) not OCM.
- Interrupt controllers on the A53 use `XScuGic` (GIC v2); do not mix `XIntc` (for MicroBlaze) in your BSP configuration.

### Code Example

```c
/* standalone main.c — safe bare-metal AXI-BRAM pattern test */
#include "xil_printf.h"
#include "xparameters.h"
#include <stdint.h>

/* These come from xparameters.h if generated by Vitis BSP.
   Hardcode as fallback if BSP didn't capture them. */
#ifndef XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR
#define XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR 0xA0000000UL
#define XPAR_AXI_BRAM_CTRL_1_S_AXI_BASEADDR 0xA0010000UL
#endif

static int test_bram(const char *name, uintptr_t base, uint32_t pattern)
{
    volatile uint32_t *p = (volatile uint32_t *)base;
    __asm__ volatile("dsb sy" ::: "memory");
    p[0] = pattern;
    __asm__ volatile("dsb sy" ::: "memory");
    uint32_t got = p[0];
    if (got == pattern) {
        xil_printf("%s: PASS (0x%08X)\r\n", name, got);
        return 0;
    }
    xil_printf("%s: FAIL — wrote 0x%08X, read 0x%08X\r\n", name, pattern, got);
    return -1;
}

int main(void)
{
    xil_printf("--- KV260 AXI-BRAM demo ---\r\n");
    int rc = 0;
    rc |= test_bram("BRAM0", XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR, 0xA5A5A5A5);
    rc |= test_bram("BRAM2", XPAR_AXI_BRAM_CTRL_1_S_AXI_BASEADDR, 0x5A5A5A5A);
    xil_printf(rc ? "OVERALL: FAIL\r\n" : "OVERALL: PASS\r\n");
    for (;;) {}  /* spin — no OS to return to */
}
```

### Relevance to Your Project

The `xparameters.h` guard ensures the code compiles even if the BSP platform capture missed a peripheral. The `for(;;)` at the end is mandatory in standalone mode — returning from `main()` is undefined behavior with the default CRT stub.

## XDC Timing Constraints

### Key Findings

- **Never add a manual `create_clock` on PS-generated clock outputs** (e.g., `pl_clk0`). The Zynq UltraScale+ PS IP block emits its own `.xdc` constraints file that already defines these clocks. Duplicating the constraint causes a "clock redefinition" warning and corrupts skew analysis.
- **Primary clocks must be defined before any constraint that references them** in the XDC. Load order matters: if `set_clock_groups` precedes `create_clock`, the group silently applies to no clock.
- `PS_REF_CLK` electrical requirements (from DS925): **27–60 MHz**, **45–55% duty cycle**, **50 ps peak-to-peak jitter**. Violating jitter on the carrier card causes intermittent AXI bus errors that look like BRAM write failures.
- For AXI bus signals internal to the block design, **no `set_input_delay`/`set_output_delay` is needed** — these are internal registered paths analyzed by Vivado automatically.
- Only add `set_input_delay`/`set_output_delay` on **top-level package pins** that cross the FPGA boundary (e.g., external GPIO, PMOD, FMC signals). Applying them to AXI internal ports causes over-constraint.
- `BUFG_PS` is the correct primitive for distributing PS clock signals to PL logic at high fanout with low skew.

### Code Example

```xdc
## kv260_top.xdc — minimal constraints for KV260 AXI-BRAM demo

# pl_clk0 is already defined by the Zynq PS IP constraints — DO NOT redefine here.
# The line below is intentionally commented out to prevent redefinition:
# create_clock -period 10.000 -name pl_clk0 [get_ports pl_clk0]

# If you expose a free-running oscillator from the carrier card on a PL pin,
# define it here instead:
# create_clock -period 8.000 -name ext_osc [get_ports {ext_osc_i}]

# Clock groups: mark the PS clock and any async PL clock as unrelated
# to prevent false timing paths across domains
set_clock_groups -asynchronous \
    -group [get_clocks -of_objects [get_nets -hier -filter {NAME =~ *pl_clk0*}]] \
    -group [get_clocks -of_objects [get_nets -hier -filter {NAME =~ *pl_clk1*}]]

# I/O standard for UART (connected to PS MIO — typically no XDC needed,
# but include for custom carrier card GPIO):
# set_property PACKAGE_PIN  <pin>   [get_ports {uart_tx_o}]
# set_property IOSTANDARD   LVCMOS18 [get_ports {uart_tx_o}]
```

### Relevance to Your Project

Your design is entirely internal (PS AXI master → PL BRAM), so the only XDC entries you truly need are the I/O standard and package pin assignments for any external signals in `kv260_top.vhd`. The PS clock and AXI internal paths are constrained by the IP-generated XDC automatically.

## Kria KV260 / K26 SoM

### Key Findings

- **Default boot sequence**: KV260 boots from QSPI (read-only firmware). For bare-metal JTAG development you do **not** need to modify QSPI — Vitis downloads the ELF directly to DDR via JTAG and runs it.
- **Boot mode pins** (MIO[5:0] on the SOM): QSPI = `0010`, eMMC = `0110`. These are set by resistors on the carrier card (KV260 fixes them to QSPI by design).
- **Console UART**: MIO36/37 is the default PS UART1 console at **115200-8N1**. The USB-UART bridge on the KV260 connects to PS UART0 (MIO10/11) at the same baud — confirm which UART your BSP `stdin`/`stdout` targets in `xparameters.h` (`XPAR_XUARTPS_0_BASEADDR` vs `_1_`).
- **EMIO to PL path**: GPIO signals reach the PL fabric via the 240-pin SOM240_1 connector. EMIO GPIO does not require a package pin assignment in XDC because the signal path is entirely within the PS↔PL interface.
- **Recovery via FWUEN**: Hold the FWUEN button on power-up to enter the AMD Boot Image Recovery web UI (served over USB Ethernet), allowing QSPI reflash without JTAG hardware. Useful if a corrupt bitstream prevents boot.
- **Power domains**: PL is powered by VCCO banks on the KV260 carrier. Check bank 26 (1.8 V) and bank 44 (3.3 V) I/O voltage before assigning `IOSTANDARD` in XDC.

### Code Example

```tcl
## Vitis project TCL — explicitly target PS UART0 for xil_printf on KV260
# In the BSP configuration, set stdin/stdout to uart0 (MIO10/11 → USB-UART):
set_property -name {standalone_stdin}  -value {psu_uart_0} -objects [get_sw_comps standalone]
set_property -name {standalone_stdout} -value {psu_uart_0} -objects [get_sw_comps standalone]

## Equivalent in Vitis Unified IDE: edit platform.spr → standalone domain →
## set stdin/stdout to "psu_uart_0"
```

### Relevance to Your Project

Your `main.c` uses `xil_printf` for PASS/FAIL output. If the BSP targets `psu_uart_1` (MIO36/37, the Linux console) instead of `psu_uart_0` (MIO10/11, the USB-UART), output appears on the wrong physical port. The FWUEN recovery button is your safety net if a bad bitstream is ever programmed to QSPI.

## AMD/Xilinx Tool Updates (Vivado/Vitis 2025.1)

### Key Findings

- **Installation path changed**: Vivado 2025.1 installs to `<install_root>/<version>/Vivado/` instead of the previous `<install_root>/Vivado/<version>/`. Any PATH exports, Makefile variables, or Docker images using the old layout will silently fail to find `vivado`.
- **Vitis Unified IDE is now the default** GUI (Classic IDE deprecated). The Unified IDE uses a workspace concept; `.xpr`-based Classic projects must be migrated before opening in Unified.
- **Known issue — XSCT hang on Windows**: Application builds using XSCT can hang indefinitely. AMD workaround: use Linux or the `-eval` flag with a timeout.
- **Known issue — file dialog on AlmaLinux 9.5 / RHEL 9.5**: The file/directory picker does not open. Workaround: use TCL/Python scripting to pass paths instead of the GUI dialog.
- **SDTGen extracted from XSCT**: System Device Tree generation is now a separate tool invoked as `sdtgen` from the command line. For standalone (no-OS) projects, this change is invisible — the XSA → platform flow is unchanged.
- **Vitis HLS**: New Flow Navigator in HLS with `BIND_OP` and `BIND_STORAGE` directive sections in synthesis reports — useful if you later add a hardware accelerator PL kernel.
- **AXI IP versions in 2025.1**: AXI BRAM Controller, AXI Interconnect, and AXI SmartConnect are updated but maintain backward compatibility with prior block design TCL scripts.

### Code Example

```bash
#!/usr/bin/env bash
# Updated PATH for Vivado 2025.1 installation layout change
VIVADO_VERSION="2025.1"
VIVADO_ROOT="/tools/Xilinx"

# 2025.1+ layout: <root>/<version>/Vivado/bin
export PATH="${VIVADO_ROOT}/${VIVADO_VERSION}/Vivado/bin:${PATH}"
export PATH="${VIVADO_ROOT}/${VIVADO_VERSION}/Vitis/bin:${PATH}"

# Verify
vivado -version 2>/dev/null | head -1 || echo "ERROR: vivado not found — check VIVADO_ROOT and VIVADO_VERSION"
vitis  -version 2>/dev/null | head -1 || echo "ERROR: vitis not found"

# Non-interactive batch build (avoids XSCT hang on Windows):
vivado -mode batch -source ./tcl/non_project_build.tcl -tclargs ${VIVADO_VERSION}
```

### Relevance to Your Project

If your CI pipeline or Dockerfile hardcodes the old `Vivado/2025.1/` path style, it will silently fail on any 2025.1 install. Update the PATH export above and verify with `vivado -version` as a pipeline health check before invoking the synthesis script.
