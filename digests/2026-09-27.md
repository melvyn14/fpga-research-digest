# FPGA Research Digest - 2026-09-27

## Executive Summary

- **AXI-Lite combined handshake pitfall**: The `axi_bram_ctrl` IP waits for both `AWVALID` and `WVALID` simultaneously before asserting `AWREADY`/`WREADY`; a PS master that issues address and data on separate cycles is safe, but a custom VHDL slave must handle both orderings or risk deadlock
- **Cache coherency for bare-metal AXI reads**: The Cortex-A53's D-cache may serve stale data after a PL write; always call `Xil_DCacheInvalidateRange(BRAM0_BASEADDR, size)` before reading back pattern data, or mark the BRAM region as strongly-ordered in the MPU
- **BRAM ECC initialization requirement**: When ECC is enabled in Block Memory Generator, the parity bits are uninitialized at power-on; the driver's `InitializeECC()` must perform a full read-write pass across `MemBaseAddress` to `MemHighAddress` before enabling ECC correction to avoid spurious single-bit errors
- **TCL `assign_bd_address` must follow `create_bd_addr_seg`**: In non-project-mode scripts, omitting the explicit `assign_bd_address` call after connecting BRAM leaves the slave unmapped; the AXI address editor will show offset 0x0000 and PS reads return X's
- **Vivado 2025.1 branch tag policy**: All Xilinx design tutorials are now tagged per tool version; use the `2025.2` branch for the closest validated examples if starting a new project, but `2025.1` IPs are backward-compatible

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- **Combined vs. split handshake**: AXI-Lite does not mandate that `AWVALID` and `WVALID` arrive together, but many Xilinx slaves (including `axi_bram_ctrl` in single-port BRAM mode) implement a combined acceptance that only fires `AWREADY` when both channels are valid simultaneously. Your PS AXI master issues address then data, which is compliant; custom VHDL slaves must handle both orderings.
- **WSTRB byte-enable semantics**: `WSTRB[i]` enables byte lane `i` of `WDATA`. A 32-bit slave at word-aligned addresses always receives `WSTRB = 4'b1111`; if you see `WSTRB = 4'b0000` your master has a configuration issue (Vitis `Xil_Out32` always sets all four strobes).
- **BRESP/RRESP response codes**: `2'b00` = OKAY, `2'b10` = SLVERR, `2'b11` = DECERR. An unmapped address in the AXI Interconnect returns DECERR; check this with an ILA probe on `M_AXI_BRESP` if your bare-metal write appears to succeed but BRAM reads return 0.
- **AXI-Stream TKEEP vs TSTRB**: For AXI-Stream, `TKEEP[i]=0` marks a null byte (whole transaction may still be valid); `TLAST` asserts end-of-frame. AXI-Lite has no streaming channel; use AXI4-Stream only when you need burst data paths, not for register-style BRAM access.
- **Fixed 2-cycle read latency from `axi_bram_ctrl`**: `ARREADY` asserts in the same cycle as `ARVALID` (zero-wait address accept), but `RVALID` is asserted exactly 2 clock cycles later — one cycle for BRAM address pipelining, one for the output register. The A53 AXI master handles this automatically; a custom HDL master that assumes `RVALID` follows `ARREADY` by 1 cycle will silently read stale data.
- **Read-before-write for partial WSTRB on BRAM**: `WSTRB` maps directly to BRAM's `WEA[3:0]` — partial strobes perform genuine byte-masked writes. When ECC is enabled and `WSTRB != 4'b1111`, the controller performs an internal read-modify-write, adding one extra latency cycle visible as an extra AXI read on an ILA.

### Code Example

```vhdl
-- Minimal AXI-Lite slave state machine (write path)
-- Handles both orderings: addr-before-data and data-before-addr
type t_aw_state is (IDLE, ADDR_RCVD, DATA_RCVD, RESP);
signal aw_state : t_aw_state := IDLE;
signal latched_addr : std_logic_vector(31 downto 0);
signal latched_data : std_logic_vector(31 downto 0);
signal latched_strb : std_logic_vector(3  downto 0);

process(clk)
begin
  if rising_edge(clk) then
    s_axi_awready <= '0';
    s_axi_wready  <= '0';
    s_axi_bvalid  <= '0';
    s_axi_bresp   <= "00";  -- OKAY

    case aw_state is
      when IDLE =>
        if s_axi_awvalid = '1' and s_axi_wvalid = '1' then
          -- Both valid at once: accept immediately
          s_axi_awready <= '1';
          s_axi_wready  <= '1';
          latched_addr  <= s_axi_awaddr;
          latched_data  <= s_axi_wdata;
          latched_strb  <= s_axi_wstrb;
          aw_state      <= RESP;
        elsif s_axi_awvalid = '1' then
          s_axi_awready <= '1';
          latched_addr  <= s_axi_awaddr;
          aw_state      <= ADDR_RCVD;   -- wait for data
        elsif s_axi_wvalid = '1' then
          s_axi_wready  <= '1';
          latched_data  <= s_axi_wdata;
          latched_strb  <= s_axi_wstrb;
          aw_state      <= DATA_RCVD;   -- wait for address
        end if;

      when ADDR_RCVD =>
        if s_axi_wvalid = '1' then
          s_axi_wready <= '1';
          latched_data <= s_axi_wdata;
          latched_strb <= s_axi_wstrb;
          aw_state     <= RESP;
        end if;

      when DATA_RCVD =>
        if s_axi_awvalid = '1' then
          s_axi_awready <= '1';
          latched_addr  <= s_axi_awaddr;
          aw_state      <= RESP;
        end if;

      when RESP =>
        -- Perform write to internal register / memory here
        -- for byte k: if latched_strb(k) = '1' then write byte k
        s_axi_bvalid <= '1';
        if s_axi_bready = '1' then
          aw_state <= IDLE;
        end if;
    end case;
  end if;
end process;
```

### Relevance to Your Project

Your `kv260-axi-bram-demo` uses `Xil_Out32` / `Xil_In32` which map to `str`/`ldr` instructions that the Zynq PS AXI master issues with all four byte strobes. The BRESP/RRESP probe tip is immediately actionable: if you add an ILA to `M_AXI_GP0` and capture `BRESP != 2'b00` after a write, the address is not in the BRAM's assigned segment. Also, the read-modify-write note explains why BRAM single-port mode adds latency: the `axi_bram_ctrl` must arbitrate between AXI reads and the internal ECC read-modify-write.

## Vivado Block Design / IP Integrator

### Key Findings

- **Non-project mode cannot be used for Block Designs**: `create_project -in_memory` supports RTL-only flows. IP Integrator block designs require a persistent on-disk project (`create_project kv260 ./kv260 -part ...`) because `create_bd_design` stores state in the project database. Use `vivado -mode batch -source create_bd.tcl` (batch mode with a project file) for BD-based automation, not true non-project mode.
- **`validate_bd_design` before generating**: Always call `validate_bd_design` in TCL before `generate_target`; it catches unconnected ports, clock domain mismatches, and address overlap errors that only surface as cryptic messages during synthesis if skipped.
- **`apply_bd_automation` for AXI clock/reset**: The `apply_bd_automation -rule xilinx.com:bd_rule:axi4` TCL command automatically inserts `proc_sys_reset` and wires `M_AXI_GP*_ARESETN`/`ACLK` to the PS clocking; doing this manually is error-prone and is the most common cause of "AXI bus hangs at startup".
- **Address editor conflicts**: Two BRAMs at overlapping addresses (e.g., both defaulting to `0xA000_0000`) will cause `validate_bd_design` to throw `[BD 41-241]`; resolve by right-clicking each segment in the Address Editor and setting distinct offsets before generating.
- **Regenerate output products after any IP change**: Changing a BRAM depth or width requires right-clicking the IP → "Reset Output Products" → "Generate Output Products" before re-running synthesis; stale netlists cause "black box" errors in elaboration.
- **`save_bd_design` and `close_bd_design` in scripts**: A TCL script that modifies a block design without calling `save_bd_design` leaves the `.bd` file on disk unchanged; always save before `generate_target`.

### Code Example

```tcl
# Minimal non-project-mode block design for PS + 2x BRAM

# Instantiate Zynq UltraScale+ PS

         -vlnv xilinx.com:ip:zynq_ultra_ps_e:3.5 zynq_ultra_ps_e_0 ]
apply_bd_automation -rule xilinx.com:bd_rule:zynq_ultra_ps_e \
         -config { apply_board_preset "1" } $ps

# Enable HP0 AXI slave port at 100 MHz

set_property CONFIG.PSU__MAXIGP0__DATA_WIDTH {32} $ps

# BRAM 0
set bram_ctrl_0 [ create_bd_cell -type ip \
         -vlnv xilinx.com:ip:axi_bram_ctrl:4.1 axi_bram_ctrl_0 ]
set_property CONFIG.SINGLE_PORT_BRAM {1} $bram_ctrl_0
set bram_0 [ create_bd_cell -type ip \
         -vlnv xilinx.com:ip:blk_mem_gen:8.4 blk_mem_gen_0 ]
connect_bd_intf_net [get_bd_intf_pins axi_bram_ctrl_0/BRAM_PORTA] \
         [get_bd_intf_pins blk_mem_gen_0/BRAM_PORTA]

set bram_2 [ create_bd_cell -type ip \

connect_bd_intf_net [get_bd_intf_pins axi_bram_ctrl_2/BRAM_PORTA] \
         [get_bd_intf_pins blk_mem_gen_2/BRAM_PORTA]

# AXI Interconnect (1 master, 2 slaves)
set axi_ic [ create_bd_cell -type ip \
         -vlnv xilinx.com:ip:axi_interconnect:2.1 axi_interconnect_0 ]

# Wire PS -> Interconnect -> BRAMs
connect_bd_intf_net [get_bd_intf_pins zynq_ultra_ps_e_0/M_AXI_HPM0_FPD] \
         [get_bd_intf_pins axi_interconnect_0/S00_AXI]
connect_bd_intf_net [get_bd_intf_pins axi_interconnect_0/M00_AXI] \
         [get_bd_intf_pins axi_bram_ctrl_0/S_AXI]
connect_bd_intf_net [get_bd_intf_pins axi_interconnect_0/M01_AXI] \
         [get_bd_intf_pins axi_bram_ctrl_2/S_AXI]

# Clock + reset automation
apply_bd_automation -rule xilinx.com:bd_rule:axi4 \
         -config { Clk_master "/zynq_ultra_ps_e_0/pl_clk0 (100 MHz)" \
                   Clk_slave  "Auto" Clk_xbar "Auto" \
                   Master "/zynq_ultra_ps_e_0/M_AXI_HPM0_FPD" \
                   Slave "/axi_bram_ctrl_0/S_AXI" } \
         [get_bd_intf_pins axi_bram_ctrl_0/S_AXI]
apply_bd_automation -rule xilinx.com:bd_rule:axi4 \
         -config { Clk_master "/zynq_ultra_ps_e_0/pl_clk0 (100 MHz)" \
                   Clk_slave  "Auto" Clk_xbar "Auto" \
                   Master "/zynq_ultra_ps_e_0/M_AXI_HPM0_FPD" \
                   Slave "/axi_bram_ctrl_2/S_AXI" } \
         [get_bd_intf_pins axi_bram_ctrl_2/S_AXI]

# Assign addresses
assign_bd_address [get_bd_addr_segs {axi_bram_ctrl_0/S_AXI/Mem0}]
set_property offset 0xA0000000 \
         [get_bd_addr_segs zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0]
set_property range 8K \
         [get_bd_addr_segs zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0]

assign_bd_address [get_bd_addr_segs {axi_bram_ctrl_2/S_AXI/Mem0}]
set_property offset 0xA0010000 \
         [get_bd_addr_segs zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_2_Mem0]
set_property range 8K \
         [get_bd_addr_segs zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_2_Mem0]

validate_bd_design
save_bd_design
generate_target all [get_files system.bd]
```

### Relevance to Your Project

This script mirrors your `create_bd.tcl` workflow and sets BRAM0 at `0xA0000000` and BRAM2 at `0xA0010000` — exactly your project's addresses. The `apply_bd_automation` calls replace the manual clock/reset wiring that is a common source of "AXI bus never comes out of reset" bugs. The `assign_bd_address` + `set_property offset` sequence is what must be present to prevent `DECERR` responses.

## Vivado TCL Scripting

### Key Findings

- **Non-project mode (`-in_memory`)**: Using `create_project -in_memory` avoids writing `.xpr` and runs faster for CI pipelines; `write_bitstream` output still requires an explicit `-file` path.
- **`get_bd_cells` vs `get_bd_intf_pins`**: Use `get_bd_cells` to refer to IPs as objects, `get_bd_intf_pins` for connecting interfaces, and `get_bd_pins` for scalar signals. Mixing these types causes silent connection failures (no error, but the port is left unconnected).
- **`write_hw_platform -fixed`**: After `write_bitstream`, export the XSA with `write_hw_platform -fixed -include_bit -force output.xsa`; omitting `-include_bit` generates an XSA that Vitis cannot program.
- **`report_timing_summary -warn_on_violation`**: Add this after `route_design` in your TCL flow; a non-zero WNS is caught programmatically by checking `[get_timing_paths -setup -max_paths 1 -slack_less_than 0]`.
- **Vivado 2025.x uses SDT by default**: New projects created in 2025.1+ use the System Device Tree (SDT) flow; `write_hw_platform` generates an `.xsa` with embedded SDT. Legacy XSA flows (no SDT) still work but show deprecation warnings.

### Code Example

```tcl
# Complete non-project-mode build script skeleton
# Usage: vivado -mode batch -source build.tcl

set outputDir ./output
file mkdir $outputDir

# Open the pre-created block design project
open_project kv260.xpr

# Synthesize
launch_runs synth_1 -jobs 8
wait_on_run synth_1
if {[get_property PROGRESS [get_runs synth_1]] != "100%"} {
    error "Synthesis failed"
}

# Implement
launch_runs impl_1 -to_step write_bitstream -jobs 8
wait_on_run impl_1
if {[get_property PROGRESS [get_runs impl_1]] != "100%"} {
    error "Implementation failed"
}

# Check timing
open_run impl_1
set wns [get_property SLACK [get_timing_paths -setup -max_paths 1]]
if {$wns < 0} {
    puts "WARNING: Timing violation - WNS = ${wns} ns"
}

# Export hardware platform with bitstream
write_hw_platform -fixed -include_bit -force \
    $outputDir/kv260_system.xsa

puts "Build complete. XSA written to $outputDir/kv260_system.xsa"
close_project
```

### Relevance to Your Project

Adding the `write_hw_platform -fixed -include_bit` call at the end of your `create_bd.tcl` (or a separate build script) lets you run the entire Vivado flow non-interactively. The WNS check programmatically catches timing failures before you spend time debugging a flaky bitstream in Vitis. The `-jobs 8` flag cuts implementation time on multi-core machines.

## Vitis Bare-Metal / Standalone

### Key Findings

- **`xil_printf` vs `printf`**: `xil_printf` compiles to ~1 KB, is unbuffered (character-at-a-time, safe before interrupt setup), and supports `%d %l %x %c %s` only — no `%f`, `%e`, or `%lld`. `printf` from newlib adds ~20 KB plus heap (`malloc`). Use `xil_printf` for PASS/FAIL messages; ensure the BSP heap is sized if you ever switch to `printf`.
- **BSP stdout must be set correctly**: In Vitis BSP settings, `stdout` must point to `psu_uart_0` (base `0xFF000000`). On the KV260, the FT4232HL USB-UART bridge is wired to **UART0** on MIO18/MIO19 — not UART1. A wrong stdout assignment produces silent output (no PASS/FAIL visible). Regenerate the BSP after changing this setting. The boot ROM configures the port at 115200 baud 8N1; no `XUartPs_SetBaudRate()` call is needed.
- **Cache coherency with AXI-Lite BRAM**: PL BRAM addresses (`0xA000_0000`+) are mapped as Device memory (strongly-ordered, uncacheable) by default in the Vitis standalone MPU table — direct `Xil_Out32`/`Xil_In32` writes go straight to PL over AXI without being cached. The real risk is DDR→PL copies: if you first assemble a buffer in DDR and then a PL DMA reads it, call `Xil_DCacheFlushRange()` on the DDR source buffer. For the direct PS pointer write-back test in this demo, a memory barrier (`dmb()`) before the read loop is sufficient for ordering.
- **Linker script DDR region**: The default Vitis linker script places `bss`, `data`, and the stack in DDR. For a bare-metal demo that only accesses BRAM via AXI, you don't need to modify the linker script; however, ensure the BRAM addresses (`0xA000_0000`, `0xA001_0000`) are NOT in the DDR region (`0x0000_0000`–`0x7FFF_FFFF`).
- **`init_platform()` / `cleanup_platform()`**: The BSP-generated `platform.c` wraps cache enable and exception handler setup. Always call `init_platform()` first and `cleanup_platform()` before returning from `main()`; omitting these leaves the CPU in a default state where instruction fetches may fault.

### Code Example

```c
/* bare-metal AXI-BRAM read/write test for KV260
 * BRAM0 @ 0xA0000000, BRAM2 @ 0xA0010000
 */
#include "platform.h"
#include "xil_printf.h"
#include "xil_io.h"
#include "xil_cache.h"

#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL
#define TEST_WORDS  16

static int bram_rw_test(uintptr_t base, const char *name)
{
    u32 i, readback;
    int pass = 1;

    /* Flush any cached lines covering this range before writing */
    Xil_DCacheFlushRange(base, TEST_WORDS * 4);

    for (i = 0; i < TEST_WORDS; i++) {
        Xil_Out32(base + i * 4, 0xDEAD0000 | i);
    }

    /* Invalidate so next reads go to AXI, not cache */
    Xil_DCacheInvalidateRange(base, TEST_WORDS * 4);

    for (i = 0; i < TEST_WORDS; i++) {
        readback = Xil_In32(base + i * 4);
        if (readback != (0xDEAD0000 | i)) {
            xil_printf("FAIL %s[%d]: wrote 0x%08X, read 0x%08X\r\n",
                       name, i, 0xDEAD0000 | i, readback);
            pass = 0;
        }
    }
    if (pass)
        xil_printf("PASS %s: all %d words match\r\n", name, TEST_WORDS);
    return pass;
}

int main(void)
{
    init_platform();
    xil_printf("\r\n=== KV260 AXI-BRAM Test ===\r\n");

    bram_rw_test(BRAM0_BASE, "BRAM0");
    bram_rw_test(BRAM2_BASE, "BRAM2");

    xil_printf("=== Done ===\r\n");
    cleanup_platform();
    return 0;
}
```

### Relevance to Your Project

This is a drop-in replacement for your `main.c` that adds the critical `Xil_DCacheFlushRange` / `Xil_DCacheInvalidateRange` calls. Without these, your test may pass intermittently depending on whether the cache line happened to be dirty — the most common cause of "sometimes PASS, sometimes FAIL" in AXI bare-metal tests. The `xil_printf` pattern matches your existing UART output style.

## XDC Timing Constraints

### Key Findings

- **PS clock is auto-constrained**: Vivado automatically applies a `create_clock` on `pl_clk0` from the Zynq PS block; you do NOT need to add a manual `create_clock` for the AXI fabric clock in your `.xdc` if the block design is properly configured.
- **AXI-Lite is register-to-register; no I/O timing constraints needed**: All AXI signals in this demo live entirely inside PL fabric — no package pins are crossed. For a pure AXI-BRAM design, the only required XDC content is three bitstream config lines: `CONFIG_VOLTAGE 1.8`, `CFGBVS GND`, and `OVERTEMPSHUTDOWN ENABLE`.
- **`set_false_path` for reset synchronizer**: The `proc_sys_reset` output `peripheral_aresetn` is a multi-cycle reset; add `set_false_path -from [get_pins proc_sys_reset_0/U0/ACTIVE_LOW_PR_OUT_DFF*.FDRE/C] -to [get_cells -hierarchical *slr_sync*]` to silence the multi-cycle path warning if it appears.
- **`create_clock` for external differential clocks only**: The Zynq PS IP block automatically generates `create_generated_clock` for `pl_clk0` at elaboration — confirmed by direct inspection of the Kria-PYNQ `base.xdc`, which contains zero clock constraints. Only add `create_clock` for external oscillators coming in through PL I/O pins (e.g., a differential 300 MHz clock from the SOM240 connector).
- **`set_clock_groups -asynchronous`**: If you gate the PL clock independently from `pl_clk0`, add `set_clock_groups -asynchronous -group [get_clocks pl_clk0] -group [get_clocks clk_300]` to prevent Vivado from attempting to time cross-domain paths that you know are safe.

### Code Example

## Kria KV260 / K26 SoM

### Key Findings

- **K26 SoM = Zynq UltraScale+ xczu5ev**: The K26 SoM on the KV260 carries a `xck26-sfvc784-2LV-c` part (ZU5EV variant); Vivado board files for `kv260` resolve this automatically. Use `set_property board_part xilinx.com:kv260_som:part0:1.4` in TCL to target the correct device.
- **Boot mode is a volatile register, not a physical switch on KV260**: Unlike Zynq-7000 boards with DIP switches, the KV260 sets boot mode via MMIO register `0xFF5E0200` (JTAG = `0x0100`, SD = `0xE100`). The change is lost on power cycle. From XSCT: `mwr 0xFFCA0010 0x0`; `mwr 0xFF5E0200 0x0100`; `rst -system`. For a persistent bare-metal JTAG workflow, re-apply this every session. Also note: the KV260 uses the **SMK-K26** SOM variant (QSPI flash, no eMMC), so the eMMC boot path is unavailable.
- **`M_AXI_HPM0_FPD` is the correct PS AXI master for PL BRAM**: The K26's PS has four AXI master ports: `HPM0_FPD`, `HPM1_FPD`, `HPM0_LPD`. For bare-metal access to PL fabric from the APU (A53), use `HPM0_FPD`; it supports 32-bit data width at up to 333 MHz. Do NOT use `HPM0_LPD` (connected to RPU) for A53 bare-metal unless you're running on the R5.
- **UART0 on MIO18/MIO19 = the USB-UART bridge**: The KV260 carrier routes UART0 RX→MIO18 and TX→MIO19 to the FT4232HL USB bridge (Channel A). On the host this appears as `/dev/ttyUSB0` (first FTDI channel). Set `stdout = psu_uart_0` (base `0xFF000000`) in Vitis BSP settings. Vitis terminal settings: 115200 baud, 8N1, no flow control. UART1 (MIO20/21) is routed on the SOM but NOT connected to the USB bridge on the KV260 carrier — using it for stdout produces no output.
- **PL power domain must be enabled**: On the KV260 carrier, the PL power rail is controlled by a PMC register. In JTAG bare-metal mode, Vitis/XSCT calls `psu_init.tcl` which enables the PL power domain before programming the bitstream; if you skip the TCL init sequence, the FPGA fabric stays unpowered and BRAM reads return `0xFFFFFFFF`.

### Code Example

```tcl
# XSCT script to initialize KV260, program bitstream, and run bare-metal ELF
# Run from Vitis XSCT console: source program_kv260.tcl

connect

# Target the APU cluster (Cortex-A53 #0)
targets -set -nocase -filter {name =~ "*A53*#0"}

# Run PSU initialization (enables PL power, configures MIO/clocks)
source [lindex [glob -nocomplain ./psu_init.tcl] 0]
psu_init

# Program the bitstream
fpga -file ./system_wrapper.bit

# Reconfigure APU after bitstream load (resets the interconnect)
psu_ps_pl_reset_config

# Download and run the bare-metal ELF
dow ./kv260_bram_test.elf
con

puts "KV260 programmed and running. Connect terminal to /dev/ttyUSB1 at 115200."
```

### Relevance to Your Project

The `psu_init` + `fpga` + `psu_ps_pl_reset_config` sequence is the correct order for your demo. Skipping `psu_ps_pl_reset_config` after loading a new bitstream leaves the AXI interconnect in reset, causing every BRAM read to return `0`. The UART identification (`psu_uart_1` = `/dev/ttyUSB1`) confirms which port to open in your serial terminal to see the PASS/FAIL output.

## AMD/Xilinx Tool Updates (Vivado/Vitis 2025.x)

### Key Findings

- **Breaking change in 2025.1: Block Memory Generator removed from standalone RTL IP Catalog**: `blk_mem_gen` and FIFO Generator can no longer be added via the IP Catalog right-click menu for RTL instantiation. They must be used inside IP Integrator (Block Design), or replaced with **XPM macros** (`xpm_memory_spram`, `xpm_memory_dpram`, `xpm_fifo_sync`) for pure-RTL flows. Your IPI-based demo is unaffected — `create_bd_cell -vlnv xilinx.com:ip:blk_mem_gen:8.4` still works inside a block design.
- **Vivado 2025.1 → 2025.2 IP catalog**: The `axi_bram_ctrl` 4.1 and `blk_mem_gen` 8.4 used in 2025.1 are unchanged in 2025.2; bitstreams generated in 2025.1 do not need re-generation for IP version reasons.
- **Vitis classic IDE discontinued in 2024.1 — migration required**: The classic Vitis IDE workspace must be migrated via "File → Migrate Classic Workspace" before opening in 2025.1 Unified IDE. The Unified IDE runs a new "Vitis Server" process. `xsct` scripting is unchanged.
- **System Device Tree (SDT) flow**: Projects created in 2025.1 with `write_hw_platform` generate an XSA containing a System Device Tree; Lopper (`lopper.py`) extracts BSP metadata. If you're using the legacy flow (no SDT), you'll see `[Common 17-57] 'set_property' expects at least one object` warnings during BSP generation — these are benign.
- **Known issue — `axi_interconnect` vs `smartconnect`**: In 2025.x, AMD recommends `smartconnect` over `axi_interconnect` for new designs targeting Zynq UltraScale+; `smartconnect` has lower latency (1 cycle vs. 2 cycles for AXI-Lite pass-through) and handles clock crossing internally. Existing projects using `axi_interconnect` do not need to migrate.
- **Vivado 2025.1 `write_bitstream` multi-threading**: The `-jobs` parameter to `launch_runs` is now capped at the license tier's allowed core count for non-enterprise licenses; using `-jobs 16` on a free WebPACK license silently falls back to 4 threads.

### Code Example

```bash
# Checking installed Vivado/Vitis version from shell
source /tools/Xilinx/Vivado/2025.1/settings64.sh
vivado -version
# Expected output: Vivado v2025.1 (64-bit)
#   SW Build 4745030 on ...

source /tools/Xilinx/Vitis/2025.1/settings64.sh
vitis --version
# Expected: vitis v2025.1 (64-bit)

# Check which IP catalog version is active
vivado -mode tcl -nolog -nojournal << 'EOF'
set_param general.maxThreads 4
get_ipdefs -all -filter {VLNV =~ *axi_bram_ctrl*}
# Should show: xilinx.com:ip:axi_bram_ctrl:4.1
get_ipdefs -all -filter {VLNV =~ *smartconnect*}
# Should show: xilinx.com:ip:smartconnect:1.0
exit
EOF
```

### Relevance to Your Project

If you used `axi_interconnect` when creating the initial block design, there is no urgency to migrate to `smartconnect` — your AXI-Lite throughput for BRAM test patterns is well below the bandwidth limit. The SDT warning note means if you see BSP generation warnings in Vitis 2025.1, they are not causing your PASS/FAIL results. The version check script helps confirm your exact tool and IP versions match the expected `4.1` for `axi_bram_ctrl`.
