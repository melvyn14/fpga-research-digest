# FPGA Research Digest - 2026-07-07

## Executive Summary

- **AXI-Lite handshake bug in Xilinx generated code**: Xilinx's own AXI-Lite demo core raises `AWREADY` without checking `BREADY`, causing silent write-response loss and bus hang — your bare-metal PS→BRAM path is vulnerable if BREADY ever de-asserts. Use the ZipCPU-corrected pattern that gates `AWREADY` on `(!BVALID || BREADY)`.
- **Vivado 2025.2 introduces ultra-low-area AXI SmartConnect**: Set `STRATEGY=MinArea` on your SmartConnect IP to shrink fabric usage between the PS AXI-GP0 master and your two BRAM controllers. The deprecated `axi_interconnect` IP is being phased out — if your `create_bd.tcl` still uses it, migrate to SmartConnect.
- **TCL non-project batch mode is faster for CI**: Running `vivado -mode batch -source create_bd.tcl` skips project overhead and processes everything in-memory; use `write_checkpoint` and `write_bitstream` at the end to persist artifacts.
- **KV260 bare-metal JTAG boot sequence requires PMU firmware first**: Before loading your bare-metal ELF to Cortex-A53 Core 0, XSCT must first download `pmufw.elf` to the MicroBlaze PMU. Skipping this step causes the PS to stall before reaching `main()`.
- **XDC clock groups needed for PS-to-PL paths**: Without explicit `set_clock_groups -asynchronous` between the PS FCLK and any free-running PL clocks, Vivado may report false timing violations on your AXI paths. Add clock-group constraints after generating the bitstream to clean up the timing report.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- A transfer only completes when both `*VALID` and `*READY` are high in the same clock cycle — conditioning your slave response on anything else causes silent hangs.
- Xilinx's AXI-Lite demo core has a known read-channel bug (still unfixed as of 2025): `ARREADY` is raised without checking whether the response channel (`RVALID`/`RREADY`) is clear.
- The most critical write-path fix: `AWREADY` must not be raised when `BVALID` is asserted and `BREADY` is low. If your PS never de-asserts BREADY this is benign, but it is latent and will fire under bus congestion.
- Proper synchronization: set both `AWREADY` and `WREADY` to the same gating signal so both write-address and write-data channels are accepted atomically.
- AXI-Lite does not support bursts; every transaction is single-beat. Your BRAM writes at `0xA0000000`/`0xA0010000` use AXI-Lite semantics, so confirm your BRAM controller is configured in AXI4-Lite mode (not AXI4) when a single-beat controller is intended.

### Code Example

```vhdl
-- Corrected AXI-Lite AWREADY gating (ZipCPU pattern)
-- Raises AWREADY only when both channels valid AND response channel clear
process(S_AXI_ACLK)
begin
  if rising_edge(S_AXI_ACLK) then
    if S_AXI_ARESETN = '0' then
      axil_awready <= '0';
    else
      -- Gate on BVALID/BREADY to prevent response loss
      axil_awready <= not axil_awready
                      and (S_AXI_AWVALID and S_AXI_WVALID)
                      and (not S_AXI_BVALID or S_AXI_BREADY);
    end if;
  end if;
end process;

-- WREADY tracks AWREADY (atomic accept of addr+data)
S_AXI_AWREADY <= axil_awready;
S_AXI_WREADY  <= axil_awready;
```

### Relevance to Your Project

Your `main.c` hammers BRAM0/BRAM2 with sequential write-then-read patterns. If the generated AXI-Lite slave inside the BRAM controller (or any IP on your SmartConnect) has the BREADY gating bug, a single stalled response will permanently hang the AXI bus, causing your PASS/FAIL check to silently loop. Verify the AXI BRAM Controller version is ≥4.1 (Vivado 2022.1+) which includes AMD's partial fix.

## Vivado Block Design / IP Integrator

### Key Findings

- **Run Connection Automation** on `axi_bram_ctrl/S_AXI` automatically instantiates an AXI SmartConnect, connects it to `M_AXI_HPM0_FPD` (or GP0 on Zynq-7000), and wires a Processor System Reset. Accept the automation rather than hand-wiring to avoid missing the reset synchronizer.
- In the Address Editor, **Auto Assign Address** allocates non-overlapping base addresses; for the KV260 project the manual assignments are `0xA0000000` (BRAM0) and `0xA0010000` (BRAM2) — verify these do not collide with any GP0 exclusion zones in the MPSoC Address Map.
- After any IP parameter change (e.g., changing BRAM width/depth), click **Validate Design** (`validate_bd_design` in TCL) before generating the wrapper — parameter propagation (width negotiation, AXI protocol mode) only fires during validation.
- IP Integrator stores the block design as a `.bd` file; check this into source control rather than the generated HDL wrappers to keep diffs readable.
- Vivado 2025.2 added **automatic wrapper creation and management** for all AMD IP and block designs — the manual "Create HDL Wrapper" step may now be optional if your flow is fully scripted.

### Code Example

```tcl
# In IP Integrator / Vivado TCL console:
# Validate after parameter changes before generating wrapper
validate_bd_design
# Regenerate wrapper (Vivado 2025.1 and earlier)
make_wrapper -files [get_files design_1.bd] -top
add_files -norecurse ./kv260.gen/sources_1/bd/design_1/hdl/design_1_wrapper.vhd
set_property top design_1_wrapper [current_fileset]

# Address assignment for dual-BRAM layout
set_property offset 0xA0000000 [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property range  64K         [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property offset 0xA0010000 [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_1_Mem0}]
set_property range  64K         [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_1_Mem0}]
```

### Relevance to Your Project

Your `create_bd.tcl` drives the entire block design from script. Confirming `validate_bd_design` is called before `generate_target` prevents silent parameter-mismatch issues between your two BRAM controllers, and the explicit address assignments above match the `0xA0000000`/`0xA0010000` base addresses your `main.c` uses for direct memory-mapped writes.

## Vivado TCL Scripting

### Key Findings

- **Batch mode invocation**: `vivado -nolog -nojournal -mode batch -source create_bd.tcl` runs headless without creating `.jou`/`.log` clutter; useful in CI pipelines.
- **Non-project mode** skips `.xpr`/`.runs` directory overhead — synthesis, implementation, and bitstream are all in-memory. Use `write_checkpoint` after each major stage to enable restart without re-running.
- **BD scripting idiom**: `create_bd_cell -type ip -vlnv xilinx.com:ip:blk_mem_gen:8.4` and `connect_bd_intf_net` are the core commands; always use versioned VLNVs to avoid "IP upgrade required" dialogs on tool upgrades.
- **`assign_bd_address`** followed by `set_property offset/range` is the correct TCL path to set explicit BRAM addresses rather than relying on Auto Assign (which may shuffle addresses between Vivado versions).
- Export the BD as a self-contained TCL script with `write_bd_tcl` for portability — this is more stable than committing the `.bd` XML.

### Code Example

```tcl
#!/usr/bin/env tclsh
# Minimal non-project batch flow for KV260 AXI-BRAM

set part "xck26-sfvc784-2LV-c"

# Open in-memory project
create_project -in_memory -part $part

# Source block design
source [file join [file dirname [info script]] create_bd.tcl]

# Generate targets (HDL wrapper + IP sources)
generate_target all [get_files design_1.bd]
make_wrapper -files [get_files design_1.bd] -top

# Synthesis
read_vhdl ../vhdl/kv260_top.vhd
synth_design -top kv260_wrapper -part $part
write_checkpoint -force post_synth.dcp

# Implementation + bitstream
opt_design
place_design
route_design
write_checkpoint -force post_route.dcp
write_bitstream -force kv260_top.bit

puts "Build complete: kv260_top.bit"
```

### Relevance to Your Project

Your existing `create_bd.tcl` can be wrapped in the batch flow above, making the project fully reproducible from the command line — no Vivado GUI required. The versioned VLNV strings prevent silent IP upgrades when colleagues build on a newer Vivado patch release.

## Vitis Bare-Metal / Standalone

### Key Findings

- **BSP stdout/stdin routing**: In the BSP settings for `psu_cortexa53_0`, set both `standalone_stdin` and `standalone_stdout` to `psu_uart1` (or `psu_uart0` depending on your carrier card UART mux) to direct `xil_printf` to the USB-UART visible on your PC.
- **`xil_printf` vs `printf`**: `xil_printf` is a lightweight formatted-print that avoids pulling in the full newlib `printf` (saving ~40 KB code size); it does not support floating point by default. For your PASS/FAIL output it is the correct choice.
- **Linker script (`lscript.ld`)**: Vitis auto-generates this from the hardware design. Verify `.text` and `.data` are mapped to `ps_ddr_0` (DDR) not OCM; for tiny bare-metal demos you can fit everything in OCM (256 KB) but BRAM writes to PL addresses require cache-coherent DDR access.
- **Cache and MMU for AXI-mapped peripherals**: The Cortex-A53 MMU is enabled by the BSP startup code. PL peripheral regions (`0xA0000000`+) must be marked device-memory (non-cacheable) in the MMU table — the default Vitis BSP does this correctly via `Xil_SetTlbAttributes`.
- **XSCT JTAG boot sequence**: `connect → targets -set -filter {name =~ "PSU"} → mwr 0xFF5E0230 0x100 → targets -set -filter {name =~ "MicroBlaze PMU"} → dow pmufw.elf → targets -set -filter {name =~ "Cortex-A53 #0"} → dow your_app.elf → run`.

### Code Example

```c
/* main.c pattern for AXI-BRAM write/read verify */
#include "xil_printf.h"
#include "xil_io.h"

#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL
#define TEST_WORDS  16

int main(void) {
    xil_printf("KV260 AXI-BRAM test starting...\r\n");

    /* Write pattern */
    for (int i = 0; i < TEST_WORDS; i++) {
        Xil_Out32(BRAM0_BASE + (i * 4), 0xDEAD0000 | i);
        Xil_Out32(BRAM2_BASE + (i * 4), 0xBEEF0000 | i);
    }

    /* Read back and verify */
    int pass = 1;
    for (int i = 0; i < TEST_WORDS; i++) {
        u32 r0 = Xil_In32(BRAM0_BASE + (i * 4));
        u32 r2 = Xil_In32(BRAM2_BASE + (i * 4));
        if (r0 != (0xDEAD0000 | i) || r2 != (0xBEEF0000 | i)) {
            xil_printf("FAIL at word %d: BRAM0=0x%08X BRAM2=0x%08X\r\n", i, r0, r2);
            pass = 0;
        }
    }
    xil_printf(pass ? "ALL PASS\r\n" : "OVERALL FAIL\r\n");
    return 0;
}
```

### Relevance to Your Project

This pattern mirrors what your `main.c` does; the key additions are `Xil_SetTlbAttributes` (already called by the BSP init) and using `Xil_Out32`/`Xil_In32` rather than raw pointer casts — these emit proper 32-bit AXI transactions and include memory barriers on AArch64, preventing the compiler from reordering stores before the AXI write completes.

## XDC Timing Constraints

### Key Findings

- **KV260/K26 SoM provides `.xdc` templates**: The AMD Kria board files ship XDC files mapping SOM connector pins — use these as the starting point rather than writing from scratch. Only add constraints for signals you actually instantiate.
- **`set_clock_groups -asynchronous`**: When your PL design uses a clock derived from the PS FCLK alongside any free-running oscillator, Vivado will try to analyze paths between them as related. Add an async clock group to suppress false violations and speed up timing closure.
- **AXI bus paths are almost always register-to-register**: The SmartConnect/BRAM controller pipeline all AXI channels through registers; you should not need `set_multicycle_path` for any AXI-Lite interface running at ≤150 MHz.
- **`set_false_path` for JTAG/UART**: If you have any CDC (Clock Domain Crossing) for the debug UART, use `set_false_path` rather than `set_multicycle_path` — the UART samples asynchronously and timing analysis is meaningless on those paths.
- **Output delay for EMIO**: If you drive any EMIO pins (e.g., fan control as noted in KV260 docs), add `set_output_delay -clock [get_clocks fclk0] 1.0 [get_ports emio_*]` — without this Vivado leaves output timing unconstrained.

### Code Example

```xdc
# KV260 AXI-BRAM project — timing constraints

# PS FCLK0 is defined by the block design; constrain as source
# (Vivado auto-creates the clock from the PS IP, but explicit constraint helps reporting)
create_clock -name fclk0 -period 10.000 [get_pins zynq_ultra_ps_e_0/FCLKCLK[0]]

# Declare PS FCLK and any debug clocks asynchronous to each other
set_clock_groups -asynchronous \
  -group [get_clocks fclk0] \
  -group [get_clocks dbg_hub_clk]

# False path for UART CDC (PS UART goes through async bridge)
set_false_path -from [get_cells -hierarchical -filter {NAME =~ *uart*}]

# EMIO output delay if fan-control EMIO is used
# set_output_delay -clock fclk0 -max 1.0 [get_ports emio_fan_en_o]
# set_output_delay -clock fclk0 -min 0.5 [get_ports emio_fan_en_o]
```

### Relevance to Your Project

Your project uses a single PS-derived FCLK for all AXI logic; the primary timing risk is false violations between the PS FCLK and Vivado's internal debug hub clock. The `set_clock_groups` constraint above eliminates these cleanly without over-constraining the real AXI paths on BRAM0/BRAM2.

## Kria KV260 / K26 SoM

### Key Findings

- **Boot mode selection**: KV260 Starter Kits ship with `QSPI32` boot mode (MODE[3:0] strapped). For JTAG-based bare-metal development, the mode can be switched via the on-board boot-mode switch (SW1 on the KV260 CC) — consult UG1091 (Kria SOM Carrier Card Design Guide) for resistor values.
- **PS AXI-HP vs GP ports**: The K26 SoM MPSoC has both GP (general-purpose, 32-bit) and HP (high-performance, 128-bit) AXI master ports. For register-wide BRAM access at `0xA0000000`/`0xA0010000`, the GP0 (`M_AXI_HPM0_LPD`) port is correct — do not mix GP and HP in the same SmartConnect unless you need the bandwidth.
- **UART MUX**: On the KV260 CC, the USB-UART chip is connected to PS UART1 (`MIO[36:37]`) — ensure your BSP `stdin`/`stdout` points to `psu_uart1`, not `psu_uart0`.
- **EMIO fan control**: Since Kria Linux 2022.1, the default bitstream maps fan-control to an EMIO pin. In bare-metal you must drive this pin manually (or it may be high-Z causing a thermal warning); the pin is exposed via EMIO[0] in most reference designs.
- **Board files**: Add the KV260 board to Vivado via `xhub:board_connect` or the Vivado Board Repository Manager; the board VLNV is `xilinx.com:kv260_starter_kit:part0:1.4` in Vivado 2025.x — use this in `set_property board_part` in your project TCL.

### Code Example

```tcl
# Set KV260 board part in Vivado project (2025.x VLNV)
set_property board_part xilinx.com:kv260_starter_kit:part0:1.4 [current_project]

# After applying board part, re-run board automation in IP Integrator:
# Design > Board > Apply Board Preset → PS UART1 and DDR auto-populated

# XSCT bare-metal JTAG boot sequence (run in Vitis XSCT console)
# connect
# targets -set -filter {name =~ "PSU"}
# mwr 0xFF5E0230 0x100       ;# release PMU MB from reset
# targets -set -filter {name =~ "MicroBlaze PMU"}
# dow pmufw.elf
# con
# after 500
# targets -set -filter {name =~ "Cortex-A53 #0"}
# rst -processor
# dow kv260_axi_bram.elf
# con
```

### Relevance to Your Project

The UART1 vs UART0 distinction is critical for your USB-UART PASS/FAIL output — if your BSP is configured to UART0 but the KV260 CC routes UART1 to USB, you will see no output despite the application running correctly. The XSCT boot sequence above is the minimal flow to get your bare-metal ELF executing without a full boot image.

## AMD/Xilinx Tool Updates (Vivado/Vitis 2025.x)

### Key Findings

- **Vivado 2025.1 key additions**: PS-first boot ("boot the PS, load PL on the fly"), a new Pblock planner UI, improved directive/subdirective support for QoR, and a fully customizable RTL-based AXI Switch IP.
- **Vivado 2025.2 SmartConnect**: New `STRATEGY=MinArea` parameter on AXI SmartConnect and AXI Switch IPs for ultra-low-area mode; automatic wrapper creation and management for all AMD IP/BDs; `axi_interconnect` (deprecated) fully replaced by SmartConnect in Ultrascale example designs.
- **Vitis 2025.1**: Unified IDE is stable for embedded flows; `xil_printf` and standalone BSP unchanged from 2024.x for Zynq UltraScale+ targets. GEMV/FFT AI Engine library updates do not affect bare-metal PS flows.
- **Known issues (2025.x)**: See AMD Adaptive Support article `000037546` for the full Vivado 2025.x known-issues list. One confirmed issue: block design parameter propagation occasionally requires a second `validate_bd_design` call in scripted flows when IP have cross-dependent parameters.
- **IP change log**: AMD Adaptive Support article `000037919` (2025.1) and `000039903` (2025.2) list per-IP version bumps — check `axi_bram_ctrl` and `blk_mem_gen` changelog entries if you encounter unexpected behavior after upgrading tools.

### Code Example

```tcl
# Vivado 2025.2 — use SmartConnect with MinArea strategy
# (replaces deprecated axi_interconnect for low-resource designs)

set sc [create_bd_cell -type ip \
  -vlnv xilinx.com:ip:smartconnect:1.0 axi_smc]

# MinArea strategy — reduces LUT count for simple 1M→2S topologies
set_property CONFIG.STRATEGY {MinArea} [get_bd_cells axi_smc]
set_property CONFIG.NUM_SI   {1}       [get_bd_cells axi_smc]
set_property CONFIG.NUM_MI   {2}       [get_bd_cells axi_smc]

# Connect PS GP0 master → SmartConnect slave
connect_bd_intf_net \
  [get_bd_intf_pins zynq_ultra_ps_e_0/M_AXI_HPM0_LPD] \
  [get_bd_intf_pins axi_smc/S00_AXI]

# SmartConnect masters → BRAM controllers
connect_bd_intf_net \
  [get_bd_intf_pins axi_smc/M00_AXI] \
  [get_bd_intf_pins axi_bram_ctrl_0/S_AXI]
connect_bd_intf_net \
  [get_bd_intf_pins axi_smc/M01_AXI] \
  [get_bd_intf_pins axi_bram_ctrl_1/S_AXI]
```

### Relevance to Your Project

If your `create_bd.tcl` was initially generated in Vivado 2024.x or earlier, it likely uses `axi_interconnect`. Migrating to `smartconnect` with `STRATEGY=MinArea` will reduce LUT usage for your simple 1-master-to-2-BRAM topology and eliminates future deprecation warnings. The PS-first boot feature in 2025.1 is not needed for your current JTAG flow but becomes relevant if you move to SD-card boot with a dynamically-loaded bitstream.
