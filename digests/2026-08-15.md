# FPGA Research Digest - 2026-08-15

## Executive Summary

- **AXI-Lite VALID/READY deadlock bug**: Xilinx-generated AXI-Lite slave templates contain a subtle bug where slave logic checks *VALID and *READY with additional conditions — the interconnect advances state whenever both signals are simultaneously asserted, bypassing your extra guard. Audit any generated AXI slave in your BRAM wrapper.
- **Vivado 2025.1 AXI full slave address decoder bug**: A regression in Vivado 2025 limits auto-generated AXI full slave address decoders to only 10 bits (1 KB usable space). For `BRAM0 @ 0xA0000000` and `BRAM2 @ 0xA0010000` you are using AXI-Lite which is unaffected, but watch for this if you upgrade to AXI full bursts.
- **AXI BRAM Controller collision caveat**: Single-port AXI BRAM Controller mode (Port A for both read and write) does **not** detect read/write collisions. Use dual-port mode for concurrent access, or serialize accesses in your bare-metal C code.
- **KV260 bare-metal JTAG vs QSPI boot**: For development, JTAG download via XSDB is the fastest iteration loop. For deployment, pack the ELF into a BOOT.BIN with FSBL and write to QSPI to boot standalone at power-up — no host PC required.
- **TCL non-project mode tip**: Running `vivado -mode batch -source build.tcl` eliminates project file overhead and is 10–15% faster than GUI/project mode for CI pipelines — directly applicable to your `create_bd.tcl` automation workflow.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- **VALID must stay asserted**: Once a master asserts TVALID/AWVALID/WVALID, it must hold the signal high until the handshake completes (both VALID and READY are simultaneously high). Dropping VALID before READY is a protocol violation that Vivado's simulator may not catch but hardware will fail on.
- **Backpressure and READY deassertion**: If the master holds BREADY low (write response channel), the slave must hold AWREADY and WREADY low — these are often coded incorrectly in hand-written slaves. For your AXI-Lite BRAM write path, verify the write-response handshake is not stalling silently.
- **The generated-slave VALID/READY bug**: Xilinx's Vivado AXI-Lite slave template conditions the state machine transitions on `slv_reg_wren`, which is derived from `(axi_awready & S_AXI_AWVALID & axi_wready & S_AXI_WVALID)`. The interconnect moves on as soon as AWVALID & AWREADY go high, irrespective of `slv_reg_wren`. This causes mismatched state if your slave has additional conditions gating the write.
- **AXI-Lite read path pitfall**: Some bare-metal masters require ARVALID and RREADY to be tied high for reads to complete; if your C code polls the read-data register without properly sequencing ARVALID, reads may return stale data.

### Code Example

```vhdl
-- Minimal AXI-Lite write handshake (corrected pattern)
-- AWREADY and WREADY must assert simultaneously for single-cycle write
process(S_AXI_ACLK)
begin
  if rising_edge(S_AXI_ACLK) then
    if S_AXI_ARESETN = '0' then
      axi_awready <= '0';
      axi_wready  <= '0';
    else
      -- Accept address and data together to avoid deadlock
      if (axi_awready = '0' and S_AXI_AWVALID = '1' and
          axi_wready  = '0' and S_AXI_WVALID  = '1') then
        axi_awready <= '1';
        axi_wready  <= '1';
      else
        axi_awready <= '0';
        axi_wready  <= '0';
      end if;
    end if;
  end if;
end process;
```

### Relevance to Your Project

Your `kv260_top.vhd` wraps the Zynq PS AXI master driving two BRAM controllers at `0xA0000000` (BRAM0) and `0xA0010000` (BRAM2). The simultaneous AWREADY/WREADY pattern above is the correct form for any custom AXI-Lite slave glue logic. Use Vivado's ILA to probe AWVALID, AWREADY, WVALID, WREADY, BVALID, and BREADY in a four-channel group to catch handshake stalls before they become PASS/FAIL regressions.

## Vivado Block Design / IP Integrator

### Key Findings

- **Connection Automation saves wiring time**: In IP Integrator, after placing a BRAM Controller IP, right-click and select "Run Connection Automation" — Vivado auto-connects AXI signals, generates the interconnect, and assigns default clock/reset. For your two BRAM controllers, run automation once per controller then verify the address editor.
- **Address Editor is authoritative**: After connection automation, open the Address Editor tab and verify each BRAM segment has the exact base address and range you intend (`0xA0000000 / 64K` for BRAM0, `0xA0010000 / 64K` for BRAM2). Mismatches here are the most common source of silent FAIL in PS-to-PL AXI designs.
- **IP re-locking after upgrade**: After upgrading IPs (e.g., moving from 2024.2 to 2025.1), Vivado may not detect the update until you close and reopen the project. Force a re-lock with `upgrade_ip [get_ips *]` in the TCL console.
- **Vivado 2025.2 UG994 coverage**: The 2025.2 version of UG994 (released 2025-11-26) adds new sections on hierarchical block design addressing — relevant if you plan to encapsulate your BRAM logic into a hierarchy for reuse.

### Code Example

```tcl
# Address assignment in IP Integrator via TCL (after create_bd_addr_seg)
# Assigns 64KB at 0xA0000000 to BRAM0
assign_bd_address [get_bd_addr_segs {axi_bram_ctrl_0/S_AXI/Mem0}]
set_property offset 0xA0000000 [get_bd_addr_segs \
  {processing_system7_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property range 64K [get_bd_addr_segs \
  {processing_system7_0/Data/SEG_axi_bram_ctrl_0_Mem0}]

# BRAM2 at 0xA0010000
assign_bd_address [get_bd_addr_segs {axi_bram_ctrl_1/S_AXI/Mem0}]
set_property offset 0xA0010000 [get_bd_addr_segs \
  {processing_system7_0/Data/SEG_axi_bram_ctrl_1_Mem0}]
set_property range 64K [get_bd_addr_segs \
  {processing_system7_0/Data/SEG_axi_bram_ctrl_1_Mem0}]
```

## Vivado TCL Scripting

### Key Findings

- **Non-project mode is CI-friendly**: `vivado -mode batch -source build.tcl` runs synthesis, implementation, and bitstream without creating a `.xpr` project — faster and version-control-clean. Only reading source files and constraints is required before calling `synth_design`.
- **Project mode TCL is exportable**: From a working GUI project, use `File → Project → Write Tcl` to export a portable reconstruction script. Re-import to any machine with the same Vivado version to reproduce the exact block design.
- **Key non-project commands in order**: `read_vhdl`, `read_xdc`, `synth_design -top <top> -part <part>`, `opt_design`, `place_design`, `route_design`, `write_bitstream -force output.bit`.
- **Block design in batch mode**: Use `open_bd_design` or regenerate from script with `source create_bd.tcl` before `make_wrapper` and synthesis in non-project batch flows.

### Code Example

```tcl
# Minimal non-project batch build for KV260
set PART "xck26-sfvc784-2LV-c"

read_vhdl   [glob ./vhdl/*.vhd]
read_xdc    [glob ./xdc/*.xdc]

# Recreate block design from script
source ./tcl/create_bd.tcl

# Synthesize
synth_design -top kv260_top -part $PART -flatten_hierarchy rebuilt

# Implement
opt_design
place_design
route_design

# Write outputs
write_checkpoint -force ./output/post_route.dcp
write_bitstream   -force ./output/kv260_top.bit
write_hw_platform -fixed -force ./output/kv260_top.xsa

puts "Build complete."
```

### Relevance to Your Project

Your repo already has `create_bd.tcl`. Wrapping it in the non-project batch script above gives you a one-command CI build (`vivado -mode batch -source build.tcl`) that regenerates the block design, synthesizes, implements, and produces both the bitstream and the XSA platform file needed by Vitis for your bare-metal application.

## Vitis Bare-Metal / Standalone

### Key Findings

- **BSP stdout selection is critical**: In Vitis BSP configuration, set `stdin`/`stdout` to the correct UART instance (`psu_uart_1` on KV260 for the USB-UART). If mismatched, `xil_printf` output appears on the wrong physical UART and the terminal stays blank.
- **xil_printf vs printf**: `xil_printf` is a lightweight formatted-output function without floating-point support — it is safe and fast for PASS/FAIL messaging. Use `printf` (which requires the full newlib C library, increasing BSP size) only if you need `%f` or `%e`.
- **Linker script memory regions**: The Vitis-generated linker script places code in `ps7_ddr_0` (DDR) and stack/heap in the same region. For tight timing tests, relocate `.text` and `.rodata` to the Cortex-A53 TCM or OCM for deterministic latency. Edit `lscript.ld` `MEMORY` and `SECTIONS` blocks.
- **Interrupt controller (GIC) for bare-metal**: The Zynq UltraScale+ GIC-400 is initialized via `XScuGic_Initialize(&IntcInstance, &IntcConfig, XPAR_SCUGIC_0_DIST_BASEADDR)`. For your AXI BRAM polling demo, interrupts are not required, but adding a timer interrupt improves test repeatability.

### Code Example

```c
#include "xil_printf.h"
#include "xparameters.h"

/* AXI-Lite BRAM base addresses from xparameters.h */
#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL

static inline void bram_write32(uint32_t base, uint32_t offset, uint32_t val)
{
    /* Volatile write ensures no compiler reordering */
    *(volatile uint32_t *)(base + offset) = val;
}

static inline uint32_t bram_read32(uint32_t base, uint32_t offset)
{
    return *(volatile uint32_t *)(base + offset);
}

int main(void)
{
    const uint32_t pattern = 0xDEADBEEFUL;
    uint32_t readback;
    int pass = 1;

    xil_printf("KV260 AXI-BRAM demo\r\n");

    /* Write pattern to BRAM0 offset 0 */
    bram_write32(BRAM0_BASE, 0, pattern);
    readback = bram_read32(BRAM0_BASE, 0);
    if (readback != pattern) {
        xil_printf("FAIL BRAM0: wrote 0x%08X read 0x%08X\r\n", pattern, readback);
        pass = 0;
    }

    /* Write pattern to BRAM2 offset 0 */
    bram_write32(BRAM2_BASE, 0, ~pattern);
    readback = bram_read32(BRAM2_BASE, 0);
    if (readback != ~pattern) {
        xil_printf("FAIL BRAM2: wrote 0x%08X read 0x%08X\r\n", ~pattern, readback);
        pass = 0;
    }

    xil_printf(pass ? "PASS\r\n" : "OVERALL FAIL\r\n");
    return 0;
}
```

### Relevance to Your Project

This C snippet is a hardened version of your existing `main.c` pattern: it uses `volatile` pointer casts for all MMIO accesses (preventing compiler optimization from eliding the writes), matches your BRAM base addresses, and uses `xil_printf` for lightweight UART output. The `~pattern` second test verifies both data buses independently.

## XDC Timing Constraints

### Key Findings

- **`set_input_delay` syntax**: The value (in ns) is positive when data arrives *after* the clock edge at the device input, negative when it arrives *before*. For a 100 MHz external clock with 2 ns trace delay: `set_input_delay -clock clk_100 -max 2.0 [get_ports data_in]`.
- **`set_output_delay` for registered outputs**: Similarly, `set_output_delay -clock clk_100 -max 1.5 [get_ports data_out]` tells Vivado the downstream device needs data stable 1.5 ns before the next clock edge.
- **`set_clock_groups` for async domains**: Use `set_clock_groups -asynchronous -group [get_clocks clk_pl_0] -group [get_clocks clk_pl_1]` to tell the timing engine that paths crossing between PL clock domains are asynchronous and should not be constrained. This is critical for designs with multiple AXI clock domains.
- **KV260/Zynq primary clock**: The PS provides `clk_out1` from the ZYNQ PS IP to the PL fabric. Define your master PL clock constraint against this output to anchor all derived timing constraints.

### Code Example

```xdc
# KV260 bare-metal AXI-BRAM XDC timing constraints

# Primary PL clock from PS (100 MHz, period = 10.0 ns)
# The PS drives this via FCLK_CLK0 — define it here so Vivado can
# propagate it through the interconnect to BRAM controller registers.
create_clock -period 10.000 -name clk_pl_0 \
    [get_pins -hierarchical -filter {NAME =~ */FCLK_CLK0}]

# False paths on PS-to-PL reset (async reset synchronizer handles this)
set_false_path -from [get_pins -hierarchical -filter {NAME =~ */FCLK_RESET0_N}]

# If a second PL clock is used, mark it async relative to clk_pl_0
# set_clock_groups -asynchronous \
#     -group [get_clocks clk_pl_0] \
#     -group [get_clocks clk_pl_1]

# Constrain external GPIO output (if any)
# set_output_delay -clock clk_pl_0 -max 2.0 [get_ports {led[*]}]
# set_output_delay -clock clk_pl_0 -min 0.5 [get_ports {led[*]}]
```

### Relevance to Your Project

For a pure PS-to-PL AXI-Lite demo with no external I/O (only internal BRAM), timing is driven entirely by the internal PL clock from the PS. The `create_clock` on `FCLK_CLK0` is the most important constraint; without it, Vivado's timing engine runs unconstrained and the implementation cannot be validated for 100+ MHz operation.

## Kria KV260 / K26 SoM

### Key Findings

- **Boot mode selection**: Boot mode is set by `MODE[3:0]` pins on the SOM connector, controlled by your carrier card (KV260). JTAG mode (all zeros) is selected when a JTAG cable is connected and XSDB is used — this is the standard bare-metal development flow. QSPI boot (`MODE = 0b0010`) loads BOOT.BIN from the 512 MB QSPI flash for standalone deployment.
- **MIO vs EMIO**: PS peripherals connected to MIO pins (PS-side) don't require PL bitstream configuration — the PS can use UART0/UART1 on MIO even before the PL is programmed. USB-UART on the KV260 board routes to PS MIO UART1 (`psu_uart_1`). EMIO pins cross the PS/PL boundary and require a loaded bitstream.
- **Power domains on K26**: Three domains: Always-On (5V main, powers DDR and PS core), PL power (1V/1.8V, requires stable before PL configuration), and I/O banks. Loss of PL power mid-configuration causes partial configuration and bus errors — check your carrier card sequencing if BRAM reads return `0xFFFFFFFF`.
- **Vitis 2025.2 KV260 bare-metal guide (Hackster.io)**: An updated guide for 4K streaming on KV260 in bare-metal mode, targeting Vitis 2025.2, confirms the XSA import + platform creation + domain + application flow remains unchanged from 2024.x. The XSA from `write_hw_platform` is the key handoff artifact from Vivado to Vitis.

### Code Example

```tcl
# XSDB script to JTAG-boot a bare-metal ELF on KV260 (run in Vitis XSDB console)
connect
targets -set -filter {name =~ "PSU"}
mwr 0xffff0000 0x14000000  ;# disable security gates
after 1000

# Load and run the FSBL to initialize DDR
targets -set -filter {name =~ "PSU"}
rst -system
after 3000

# Switch to A53 core 0
targets -set -filter {name =~ "Cortex-A53 #0"}
# Load the bitstream
fpga -file ./output/kv260_top.bit

# Load the bare-metal ELF
dow ./output/kv260_axi_bram.elf
con
```

### Relevance to Your Project

This XSDB script is your fast development loop: load bitstream + ELF over JTAG in under 30 seconds without modifying QSPI. The `fpga -file` command programs the PL with your BRAM block design, then `dow` loads your `main.c` ELF to Cortex-A53 core 0. After `con`, watch the UART terminal for `PASS`.

## AMD/Xilinx Tool Updates (2025.x)

### Key Findings

- **Vivado 2025.1 IP release notes (AR 000037919)**: All IP change log information for 2025.1 is consolidated in AMD Adaptive Support AR 000037919. Notable fix: potential deadlock between peripheral and cache data AXI interfaces in frequency-optimized pipeline mode — relevant if your AXI interconnect is running near its timing closure limit.
- **Vivado 2026.1 downloads available**: AMD has posted Vivado/Vitis 2026.1 downloads on their main downloads page, suggesting a 2026.1 release cycle is underway. Stick with 2025.1 for project stability unless you need a specific 2026.1 fix.
- **Vitis AI v5.0 compatibility**: Vitis AI and DPU IP v5.0 are verified with Vivado/Vitis 2025.1. Not directly relevant to your bare-metal AXI-BRAM demo but useful if you extend the project to include an AI inference pipeline.
- **Vivado 2025 AXI full slave address decoder regression**: In Vivado 2025, auto-generated AXI full slave peripherals (from IP Packager wizard) have their address decoder limited to 1 KB (10-bit). Workaround: manually extend the `OPT_MEM_ADDR_BITS` parameter in the generated HDL. This does **not** affect the AXI BRAM Controller IP (pg078), which has its own address decoder.
- **Vitis Unified IDE**: Vitis 2025.x uses the Eclipse-based Unified IDE by default. The classic Vitis IDE workflow (platform → domain → application) remains supported. The new "component-based" flow changes how BSPs are managed — check migration notes if updating from 2024.1.
