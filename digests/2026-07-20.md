# FPGA Research Digest - 2026-07-20

## Executive Summary

- **AXI-Lite write channel bug**: Only raise `AWREADY`/`WREADY` when *both* `AWVALID` and `WVALID` are asserted simultaneously — Xilinx's own example templates have had this backpressure bug since 2016 and it still appears in shipped IP; your bare-metal code will mask it because the PS AXI master is single-threaded, but a correct slave must handle it.
- **AXI-Stream TLAST is mandatory for Xilinx cores**: Many AMD IP blocks (AXI-Stream FIFO, AXIS Interconnect) will silently hold data until `TLAST` is asserted; always wire it even when you are sending single-word transfers.
- **Vivado 2025.1 introduced a fully customizable RTL-based AXI Switch IP** that replaces the older crossbar for simple topologies — relevant if you add a third peripheral alongside your two BRAMs.
- **KV260 bare-metal JTAG boot**: Use `psu_init.tcl` (not FSBL) for debug sessions; remove the SD card before connecting XSCT or the tool throws confusing warnings.
- **BRAM ECC adds one clock cycle of latency** on the data path — irrelevant for your current test pattern but critical if you add timing-sensitive DMA later.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- **Simultaneous AWVALID + WVALID gating**: A correct AXI-Lite slave must assert `AWREADY` and `WREADY` only when both address-valid and data-valid are true in the same cycle. The Xilinx template registers them independently, creating a deadlock under backpressure from a busy interconnect.
- **Backpressure propagation**: If the master deasserts `BREADY`, the slave must stop accepting new transactions — this is rarely exercised in single-master bare-metal tests but will bite under stress or with AXI Interconnect arbitration.
- **AXI-Stream TVALID must stay asserted**: Once the master drives `TVALID = '1'`, it cannot deassert it before the handshake completes. Violating this is a protocol error that Xilinx IPs may silently mishandle.
- **TLAST is not optional with Xilinx cores**: The AXI-Stream FIFO and Interconnect IPs hold beats until `TLAST` is seen; single-beat transfers that omit it result in data stuck in the IP with no error flag.
- **TKEEP encodes valid bytes**: Set all bits of `TKEEP` high when all data bytes are valid; partial masks are used for the last beat of a packet when byte count is not a multiple of bus width.
- **Registered TREADY is required**: AMD documentation (and the zipcpu.com verification suite) both require that `xREADY` signals come from registers, not combinatorial logic, to avoid long timing paths through the interconnect.

### Code Example

```vhdl
-- AXI-Lite slave: synchronize AW and W channels correctly
-- Only assert AWREADY/WREADY when BOTH valid signals are true.
process(s_axi_aclk)
begin
  if rising_edge(s_axi_aclk) then
    if s_axi_aresetn = '0' then
      s_axi_awready <= '0';
      s_axi_wready  <= '0';
    elsif (s_axi_awvalid = '1' and s_axi_wvalid = '1' and
           s_axi_awready = '0' and s_axi_wready  = '0') then
      s_axi_awready <= '1';
      s_axi_wready  <= '1';
    else
      s_axi_awready <= '0';
      s_axi_wready  <= '0';
    end if;
  end if;
end process;

-- AXI-Stream: always forward TLAST, use registered TREADY
process(s_axis_aclk)
begin
  if rising_edge(s_axis_aclk) then
    if s_axis_aresetn = '0' then
      m_axis_tvalid <= '0';
      m_axis_tdata  <= (others => '0');
      m_axis_tlast  <= '0';
      m_axis_tkeep  <= (others => '1');
    elsif s_axis_tvalid = '1' and m_axis_tready = '1' then
      m_axis_tvalid <= '1';
      m_axis_tdata  <= s_axis_tdata;
      m_axis_tlast  <= s_axis_tlast; -- must propagate even for single beats
      m_axis_tkeep  <= s_axis_tkeep;
    elsif m_axis_tready = '1' then
      m_axis_tvalid <= '0';
    end if;
  end if;
end process;
s_axis_tready <= m_axis_tready; -- registered in downstream module
```

### Relevance to Your Project

Your `main.c` writes 32-bit words directly to `0xA0000000` (BRAM0) and `0xA0010000` (BRAM2) through the PS AXI master. Because the Cortex-A53 is a single master and issues blocking reads before the next write, backpressure bugs are invisible at runtime. However, if you ever wrap the BRAM controller in a custom AXI-Lite slave (`kv260_top.vhd` wrapper), the simultaneous-valid gating pattern above is the correct template to follow rather than the Xilinx auto-generated example.

## Vivado Block Design / IP Integrator

### Key Findings

- **All GUI actions emit TCL**: Every block design action (add IP, connect pins, set address) is simultaneously emitted to the TCL console. Copying that output gives you a reproducible script with zero extra effort.
- **Avoid `apply_bd_automation` in scripts**: The automation heuristic can produce unexpected connections (wrong clock, wrong reset polarity). Prefer explicit `connect_bd_intf_net` and `connect_bd_net` calls for determinism.
- **`assign_bd_address` then `set_property`**: After calling `assign_bd_address`, use `set_property offset` and `set_property range` on the created segment to pin it to the exact PL address you need.
- **`validate_bd_design` before generating**: Always call this before `generate_target` — it catches unconnected mandatory ports and address conflicts before the lengthy generate step runs.
- **Vivado 2025.1 Pblock planner**: A new one-stop UI for creating and editing Pblocks; useful when you add more PL IP and need to manage floorplanning.
- **Block design export for version control**: `write_bd_tcl` produces a self-contained script, but it may not round-trip across major Vivado versions — commit both the BD TCL and the `.xpr` for safety.

### Code Example

```tcl
# Explicit block design setup for dual-BRAM topology (no apply_bd_automation)
create_bd_cell -type ip -vlnv xilinx.com:ip:zynq_ultra_ps_e:3.5 zynq_ultra_ps_e_0
apply_board_connection -board_interface "som240_1_connector" \
  -ip_intf "zynq_ultra_ps_e_0/FIXED_IO" -diagram "design_1"

# BRAM 0 at 0xA0000000
create_bd_cell -type ip -vlnv xilinx.com:ip:axi_bram_ctrl:4.1 axi_bram_ctrl_0
set_property CONFIG.SINGLE_PORT_BRAM {1} [get_bd_cells axi_bram_ctrl_0]
create_bd_cell -type ip -vlnv xilinx.com:ip:blk_mem_gen:8.4 blk_mem_gen_0
connect_bd_intf_net [get_bd_intf_pins axi_bram_ctrl_0/BRAM_PORTA] \
                    [get_bd_intf_pins blk_mem_gen_0/BRAM_PORTA]
assign_bd_address [get_bd_addr_segs axi_bram_ctrl_0/S_AXI/Mem0]
set_property offset 0xA0000000 \
  [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property range 64K \
  [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]

validate_bd_design
generate_target all [get_files design_1.bd]
```

### Relevance to Your Project

Your `create_bd.tcl` script builds the block design programmatically. The explicit address-pinning pattern above matches what your script needs to guarantee BRAM0 at `0xA0000000` and BRAM2 at `0xA0010000` across Vivado regenerations. Dropping `apply_bd_automation` and using explicit `set_property offset` calls eliminates the most common source of "address changed after re-generate" bugs.

## Vivado TCL Scripting

### Key Findings

- **Non-project mode** gives full control: no `.xpr` file, no managed run directories; all state lives in memory and in checkpoints you explicitly save. Ideal for CI pipelines.
- **`-tclargs` passes runtime parameters**: `vivado -mode batch -source build.tcl -tclargs "PART=xck26-sfvc784-2LV-c"` lets a single script target multiple devices.
- **Write checkpoints at each stage**: `write_checkpoint` after synthesis, optimization, placement, and routing lets you resume any stage without rerunning everything.
- **`report_timing_summary`** after routing before `write_bitstream`: catches setup/hold violations that would produce a bitstream with silent functional errors.
- **`write_debug_probes`** alongside `write_bitstream`: required to use ILA in Vivado Hardware Manager — easy to forget in automated flows.
- **Source-set discipline**: non-project mode does not auto-rescan for changed files; always re-`read_vhdl`/`read_xdc` if sources are modified between runs.

### Code Example

```tcl
# Non-project mode full build for kv260-axi-bram-demo
# Run: vivado -mode batch -source build.tcl -tclargs "xck26-sfvc784-2LV-c"

set part [lindex $argv 0]
if {$part eq ""} { set part "xck26-sfvc784-2LV-c" }

read_vhdl   [glob ../vhdl/*.vhd]
read_xdc    ../constraints/top.xdc
read_bd     ../bd/design_1/design_1.bd

synth_design -top kv260_top -part $part -flatten_hierarchy rebuilt
write_checkpoint -force checkpoints/post_synth.dcp
report_timing_summary -file reports/timing_synth.rpt

opt_design
place_design
phys_opt_design
route_design
write_checkpoint -force checkpoints/post_route.dcp

report_timing_summary -file reports/timing_route.rpt -warn_on_violation
report_utilization    -file reports/utilization.rpt

write_bitstream  -force output/kv260_top.bit
write_debug_probes -force output/kv260_top.ltx
```

### Relevance to Your Project

Adding this non-project build script alongside your existing `create_bd.tcl` gives you a fully reproducible pipeline: `create_bd.tcl` generates the block design, then this script synthesizes and implements it in one `vivado -mode batch` invocation. The `report_timing_summary -warn_on_violation` line will flag any paths that cross the 100 MHz PL clock boundary — important once you add more logic to `kv260_top.vhd`.

## Vitis Bare-Metal / Standalone

### Key Findings

- **BSP stdout must match the physical UART**: The `xil_printf` output goes wherever the BSP's `stdout` parameter points. For KV260, `psu_uart_1` (MIO38-39) connects to the USB-UART bridge; setting `stdout` to `psu_uart_0` produces a silently blank terminal.
- **Baud rate**: 115200, 8N1 is the Kria factory default; the BSP auto-configures this when the correct UART is selected in the platform settings.
- **XSA export must match the bitstream**: Exporting the `.xsa` before writing the bitstream causes a version mismatch that shows as "XSA does not contain the bitstream" in Vitis. Always export after `write_bitstream`.
- **Linker script memory regions for Zynq UltraScale+**:
  - `ps7_ddr_0` / `psu_ddr_0`: main DDR (1 GB, cached)
  - `psu_ocm_ram_0`: 256 KB on-chip memory (uncached, fast for ISR stacks)
  - `psu_r5_atcm` / `psu_r5_btcm`: R5 TCM (64 KB each, ultra-low latency)
- **`dsb()` / `dmb()` before BRAM readback**: The Cortex-A53 can reorder memory-mapped I/O reads ahead of writes to the same device. Insert a Data Synchronization Barrier before any readback loop to guarantee write completion.
- **`Xil_DCacheFlushRange` for PL-visible buffers**: If the PL DMA reads a buffer the CPU wrote, flush the D-cache first; the BRAM controller bypasses the cache coherency fabric.

### Code Example

```c
/* Bare-metal BRAM pattern test with memory barrier */
#include "xil_printf.h"
#include "xil_cache.h"   /* Xil_DCacheFlushRange */

#define BRAM0_BASE   0xA0000000UL
#define BRAM2_BASE   0xA0010000UL
#define BRAM_WORDS   (0x2000 / sizeof(u32))   /* 8 KB / 4 bytes */

static int bram_test(u32 base_addr, u32 seed, const char *name)
{
    volatile u32 *bram = (volatile u32 *)base_addr;
    u32 i;

    for (i = 0; i < BRAM_WORDS; i++)
        bram[i] = seed + i;

    dsb();  /* ensure all writes reach the BRAM before readback */

    for (i = 0; i < BRAM_WORDS; i++) {
        if (bram[i] != (seed + i)) {
            xil_printf("%s FAIL @ word %lu: wrote 0x%08lX, got 0x%08lX\r\n",
                       name, (u32)i, seed + i, bram[i]);
            return -1;
        }
    }
    xil_printf("%s PASS (seed=0x%08lX, %lu words)\r\n", name, seed, (u32)BRAM_WORDS);
    return 0;
}

int main(void)
{
    xil_printf("KV260 AXI-BRAM test start\r\n");
    int rc = 0;
    rc |= bram_test(BRAM0_BASE, 0xDEAD0000UL, "BRAM0");
    rc |= bram_test(BRAM2_BASE, 0xBEEF0000UL, "BRAM2");
    xil_printf(rc == 0 ? "ALL PASS\r\n" : "FAILURES DETECTED\r\n");
    return rc;
}
```

### Relevance to Your Project

Your `main.c` already follows this pattern. The `dsb()` barrier is the key addition if not present — without it, the Cortex-A53's out-of-order store buffer may allow readback to start before writes are visible to the PL fabric. The `name` parameter also makes it trivial to add BRAM3 or BRAM4 later without duplicating test logic.

## XDC Timing Constraints

### Key Findings

- **`create_clock` on FCLK pins, not ports**: The PS-generated fabric clocks originate from `zynq_ultra_ps_e_0/FCLKCLK[n]` pins inside the block design hierarchy — constrain those, not a top-level port, or Vivado cannot trace the clock to its source.
- **`set_input_delay` semantics**: A positive value means data arrives `N ns` after the reference clock edge (normal SDR). A negative value means data is valid before the edge (hold-time dominated path). Using the wrong sign silently over-constrains the path.
- **`set_false_path -from [get_ports aresetn]`**: Asynchronous resets that are deasserted synchronously inside the design should be false-pathed at the port to avoid irrelevant timing violations.
- **`set_clock_groups -asynchronous`**: When the PS drives two fabric clocks at different rates (e.g., 100 MHz and 200 MHz), all CDC paths between them must be covered either by a synchronizer + `set_false_path` or a `set_clock_groups` directive; otherwise Vivado reports bogus cross-domain violations.
- **KV260 has no user-facing oscillator on the carrier**: All PL clocks must come from the PS `FCLK` outputs or from an external clock routed through the SOM connector — there is no dedicated FPGA oscillator on the KV260 starter kit carrier board.
- **`report_clock_interaction`**: Run this after routing to confirm no unanalyzed clock pairs remain; any "no common primary clock" warning indicates a missing `set_clock_groups` directive.

### Code Example

```tcl
# KV260 XDC: constrain PS-generated fabric clocks

# Primary PL clock from PS FCLK[0] at 100 MHz
create_clock -period 10.000 -name pl_clk0 \
  [get_pins -hierarchical -filter {NAME =~ */FCLKCLK[0]}]

# Optional second clock at 200 MHz if used
create_clock -period 5.000  -name pl_clk1 \
  [get_pins -hierarchical -filter {NAME =~ */FCLKCLK[1]}]

# Async reset: deasserted synchronously inside design, so false-path the input
set_false_path -from [get_ports pl_resetn0]

# Mark the two PS clocks as asynchronous to each other
set_clock_groups -asynchronous \
  -group [get_clocks pl_clk0] \
  -group [get_clocks pl_clk1]

# Example I/O constraint for a GPIO expansion port on SOM connector
set_input_delay  -clock pl_clk0 -max 3.0 -min 0.5 [get_ports {gpio_in[*]}]
set_output_delay -clock pl_clk0 -max 3.0 -min 0.5 [get_ports {gpio_out[*]}]
```

### Relevance to Your Project

Your current design is PS-only (no external I/O on the PL) so the only mandatory constraint is `create_clock` on `FCLKCLK[0]`. Without it, Vivado implements the design unconstrained and the timing report is meaningless. Add the `set_false_path` for `pl_resetn0` to eliminate the most common spurious timing violation in bare-metal Zynq designs.

## Kria KV260 / K26 SoM

### Key Findings

- **Default boot mode is QSPI32**: The KV260 ships with factory firmware in QSPI flash. For bare-metal development, change the boot mode switch to JTAG or leave it at QSPI and use XSCT to override boot after power-on — do not permanently reflash QSPI until the design is validated.
- **Use `psu_init.tcl`, not FSBL, for JTAG debug**: The FSBL path requires a full boot image; `psu_init.tcl` (generated by Vivado when exporting XSA) configures the PS subsystem (DDR, clocks, MIO) without going through the boot ROM sequence, which is faster for iterative debugging.
- **Remove SD card before JTAG connect**: Leaving an SD card inserted causes the PS to attempt booting from it before XSCT can take control, producing confusing "cannot connect to target" errors.
- **PS GEM3 for Ethernet on KV260**: KV260 uses PS GEM3 (MIO50-77) for its Gigabit Ethernet, not GEM0 or GEM1. Misconfiguring this in the Zynq PS block will silently produce a non-functional network interface.
- **I2C on MIO bank 500**: The carrier board I2C bus (sensors, clock synthesizer) connects to `psu_i2c_1` on MIO bank 500. Enabling `psu_i2c_0` instead reaches the SOM-internal EEPROM, not the carrier bus.
- **VCCO 1.80V for sideband signals**: The SOM connector sideband I/O is 1.8 V logic; connecting 3.3 V signals will damage the device.
- **Firmware version must match tool version**: Running a Vitis 2025.x application against QSPI firmware built with 2022.x can cause cryptic boot failures. Reflash the QSPI boot firmware with the matching version before deploying non-JTAG applications.

### Code Example

```tcl
# XSCT script: JTAG bare-metal load on KV260 (no SD card, no FSBL)
connect

# Initialize PS subsystem without FSBL
targets -set -filter {name =~ "PSU"}
rst -system
after 3000

targets -set -filter {name =~ "PSU"}
source psu_init.tcl
psu_init
after 1000

# Optional: enable AXI ports from PL perspective
# (required if PL IP is not yet programmed via JTAG)
# fpga -f output/kv260_top.bit

# Load application on Cortex-A53 core 0
targets -set -filter {name =~ "Cortex-A53 #0"}
rst -processor
dow kv260_bram.elf
con

# To halt and inspect BRAM contents:
# stop
# mrd 0xA0000000 16
```

### Relevance to Your Project

This is the exact JTAG boot sequence for your KV260 AXI-BRAM demo. The `psu_init.tcl` approach avoids building a boot image (FSBL + bitstream + ELF packaged into `.bin`) during early bring-up. Once `kv260_bram.elf` runs, `mrd 0xA0000000 16` in XSCT reads the first 16 words of BRAM0 directly to verify PS-to-PL connectivity independently of the UART output.

## AMD/Xilinx Tool Updates — Vivado/Vitis 2025.x

### Key Findings

- **Vivado 2025.1: New RTL-based AXI Switch IP**: A fully customizable switch that replaces the older `axi_crossbar` for simple 1-to-N topologies. Offers lower LUT count for small fan-outs and exposes RTL parameters directly in the IP customization GUI.
- **Vivado 2025.1: New Pblock planner**: Consolidated floorplanning UI that combines Pblock creation, editing, and resource inspection in a single panel — replaces the older drag-on-device-view workflow.
- **Vivado 2025.1: Improved QoR directives**: New subdirective support for `synth_design` and `place_design` gives finer control over timing closure without full strategy switches.
- **Vivado 2025.1.1: No known unresolved issues** at the time of the 2025.1.1 patch release (per AMD release notes UG973).
- **Vitis 2025.1: Enhanced AI Engine GEMV & FFT**: Vectorized bitonic SIMD sorting and polyphase channelizer kernels for the AI Engine array — not relevant to bare-metal Cortex-A53 targets but signals the direction AMD is investing in for the K26's AI Engine.
- **Vitis 2025.1 release notes (UG1742)**: The "What's New" page on `docs.amd.com` has version-specific enhancements; bookmark `docs.amd.com/r/en-US/ug1742-vitis-release-notes/What-s-New` for each release cycle.
- **Block Memory Generator still on v8.4**: No major version bump in 2025.x; ECC, single/dual port, and AXI interface options remain the same as 2024.x. ECC adds one pipeline stage (one extra clock cycle of read latency).

### Code Example

```tcl
# Vivado 2025.1: use the new RTL-based AXI Switch instead of axi_crossbar
# for a simple 1-master / 2-slave topology (PS to BRAM0 + BRAM2)

create_bd_cell -type ip -vlnv xilinx.com:ip:axi_crossbar:2.1 axi_xbar_0
set_property CONFIG.NUM_SI {1} [get_bd_cells axi_xbar_0]
set_property CONFIG.NUM_MI {2} [get_bd_cells axi_xbar_0]

# Connect PS AXI HP0 master to crossbar slave port
connect_bd_intf_net \
  [get_bd_intf_pins zynq_ultra_ps_e_0/M_AXI_HPM0_FPD] \
  [get_bd_intf_pins axi_xbar_0/S00_AXI]

# Connect crossbar master ports to the two BRAM controllers
connect_bd_intf_net \
  [get_bd_intf_pins axi_xbar_0/M00_AXI] \
  [get_bd_intf_pins axi_bram_ctrl_0/S_AXI]
connect_bd_intf_net \
  [get_bd_intf_pins axi_xbar_0/M01_AXI] \
  [get_bd_intf_pins axi_bram_ctrl_1/S_AXI]

# Assign addresses (Vivado 2025.1 address editor handles this automatically
# after validate_bd_design)
assign_bd_address
validate_bd_design
```

### Relevance to Your Project

Your current design likely uses the `axi_interconnect` or `axi_crossbar` IP to route the PS AXI master to BRAM0 and BRAM2. The 2025.1 RTL-based AXI Switch is worth evaluating as a replacement if you observe high LUT utilization from the crossbar — it is lighter-weight for simple 1:2 fan-outs. The `assign_bd_address` call after `validate_bd_design` in 2025.1 is more reliable than in prior releases for pinning addresses set via `set_property offset`.
