## Executive Summary

1. **AXI-Lite write-enable timing bug** — The AXI BRAM Controller v4.x has a
   documented simulation-visible defect where the write-enable signal asserts
   one clock cycle early, writing an extra word at the *previous* address.
   Tying the BRAM Enable signal properly gates this; using AXI SmartConnect
   instead of the older AXI Interconnect IP avoids it entirely.

2. **xparameters.h no longer carries GIC interrupt IDs in Vitis Unified** —
   Switching from Vitis Classic to Vitis Unified (2023.2+/2025.1) breaks any
   bare-metal interrupt code that hardcodes `#define XPAR_…_INTR_ID` from the
   old header. PL-to-PS interrupt IDs must now be looked up from the BSP
   metadata or read from the GIC pending register at runtime.

3. **Reproducible block-design rebuilds with `write_bd_tcl`** — `write_bd_tcl`
   only records *user-changed* parameters, not defaults. Always use
   **File → Project → Write Tcl** with "Recreate Block Designs using Tcl"
   checked to capture the full project state including the BD in a single
   portable script.

4. **KV260 requires explicit UART1 enable in the PS block** — By default the
   Zynq MPSoC PS on the Kria SOM does *not* expose UART1. You must enable it
   in the Zynq UltraScale+ PS IP GUI and map it to MIO 36–37 (the USB-UART
   path on the KV260 carrier) to get `xil_printf` output.

5. **`set_clock_groups -asynchronous` takes priority over `set_false_path`** —
   When the PS 100 MHz PL clock and any async reset or debug clock coexist in
   the same design, use `set_clock_groups` rather than individual false paths;
   the former has higher precedence in Vivado's constraint evaluation order
   (UG903 / UG949).

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- **Handshake rule**: once a master asserts AWVALID (or WVALID), it **must
  hold** that signal until the corresponding READY pulse is received. Dropping
  VALID early is a protocol violation and will silently corrupt AXI-Lite
  transactions against the BRAM controller.
- **Simultaneous assertion of AWVALID + WVALID**: AXI-Lite allows — and the
  Zynq PS GP port always does — asserting the address and data channels at the
  same time. Slave IP that only accepts AWVALID first then waits for WVALID
  is technically non-compliant but common in older IP.
- **BREADY must be asserted before BVALID**: The Zynq PS AXI master asserts
  BREADY continuously so write-response stalls are rare, but custom slave wrappers
  that delay BVALID without confirming BREADY is high can cause deadlock.
- **Write-enable one-cycle-early bug** (AMD AR forum): AXI BRAM Controller
  asserts its internal write-enable a cycle before the AXI handshake truly
  completes, writing one extra word at the *previous* address. Workaround:
  switch the interconnect IP from AXI Interconnect to **AXI SmartConnect** —
  the issue does not reproduce with SmartConnect.
- **AXI4 vs AXI4-Lite choice**: For single-beat register-style BRAM access
  (as in this project) AXI-Lite is correct. AXI4 full adds burst/beat IDs and
  is only worth the overhead when transferring >1 word per transaction.

### Code Example

```c
/* Bare-metal AXI-Lite write + read-back with explicit barrier */
#include "xil_io.h"

#define BRAM0_BASE 0xA0000000UL
#define BRAM2_BASE 0xA0010000UL

static inline void bram_write32(u32 base, u32 offset, u32 val) {
    Xil_Out32(base + offset, val);
    /* dsb() ensures the AXI write retires before the read-back */
    __asm__ volatile("dsb sy" ::: "memory");
}

static inline u32 bram_read32(u32 base, u32 offset) {
    return Xil_In32(base + offset);
}

int axi_bram_selftest(void) {
    const u32 pattern = 0xDEADBEEFUL;
    bram_write32(BRAM0_BASE, 0x00, pattern);
    bram_write32(BRAM2_BASE, 0x00, ~pattern);

    u32 r0 = bram_read32(BRAM0_BASE, 0x00);
    u32 r2 = bram_read32(BRAM2_BASE, 0x00);

    return (r0 == pattern && r2 == ~pattern) ? 0 : -1;
}
```

### Relevance to Your Project

Your `main.c` writes patterns to BRAM0 at `0xA0000000` and BRAM2 at
`0xA0010000` over AXI-Lite, then reads them back for PASS/FAIL. The `dsb sy`
barrier above prevents the A53 store buffer from reordering the write before
the read-back, which can silently give false PASSes on a cache-enabled system.
If the demo fails intermittently, check whether the cache-disable / strongly-ordered
memory attributes are applied correctly to the BRAM address region in
`xil_mmu.c` / `lscript.ld`.

## Vivado Block Design / IP Integrator

### Key Findings

- **Connection Automation** respects board-file presets for the Kria KV260;
  always run it after adding each IP rather than at the end, as later additions
  can leave previously auto-connected nets with incorrect widths if AXI address
  maps have shifted.
- **Address Editor**: The AXI BRAM Controller address must be manually locked
  after auto-assignment if you have hard-coded base addresses in software. Use
  the lock icon or `assign_bd_address -offset 0xA0000000 -range 64K` in TCL.
- **AXI SmartConnect vs AXI Interconnect**: AMD recommends SmartConnect for all
  new designs on Zynq UltraScale+. SmartConnect eliminates the extra-write-enable
  timing issue and has lower area in 1×1 coupling mode.
- **Regenerate Layout after IP upgrade**: Upgrading IP mid-project can leave
  stale bd.tcl ports. Always run **Validate Design (F6)** then **Regenerate
  Layout** before re-exporting the XSA.

### Code Example

```tcl
# Vivado TCL: force a specific AXI BRAM address and lock it
open_bd_design [get_files *.bd]
set bram0 [get_bd_addr_segs -of [get_bd_cells axi_bram_ctrl_0]]
assign_bd_address -offset 0xA0000000 -range 0x00010000 $bram0
set_property offset_lock true $bram0

set bram2 [get_bd_addr_segs -of [get_bd_cells axi_bram_ctrl_1]]
assign_bd_address -offset 0xA0010000 -range 0x00010000 $bram2
set_property offset_lock true $bram2

validate_bd_design
save_bd_design
```

### Relevance to Your Project

Your `create_bd.tcl` script sets up two BRAM controllers at the fixed addresses
`0xA0000000` and `0xA0010000`. Locking offsets in TCL prevents Vivado from
silently re-assigning them if you add another AXI peripheral later — a silent
offset shift that compiles without error but fails at runtime.

## Vivado TCL Scripting

### Key Findings

- **`write_bd_tcl` only captures user-overridden parameters** — default
  parameter values and tool-propagated values are omitted. This means two
  engineers running the same script on different Vivado versions can get
  different default values silently. Prefer **File → Project → Write Tcl** with
  "Recreate Block Designs using Tcl" to capture the full project.
- **`-include_layout` switch** adds block-diagram placement coordinates to the
  exported TCL, making the regenerated BD visually identical to the original.
- **Non-project mode**: IP Integrator fully supports non-project mode (UG994
  2025.1). Call `create_bd_design`, `set_property`, `connect_bd_intf_net`, and
  `write_bd_tcl` without ever opening a `.xpr`. CI pipelines should prefer this
  mode for reproducibility.
- **Version lock warning**: `write_bd_tcl` embeds the Vivado version in which
  it was created; sourcing the script in a different version may issue warnings
  or fail silently on newer IP versions. Add a version check at the top of the
  script.

### Code Example

```tcl
# Non-project mode BD creation skeleton for KV260 AXI-BRAM demo
# Run with: vivado -mode batch -source create_bd_nonproj.tcl

set vivado_ver [version -short]
if {[string compare $vivado_ver "2025.1"] < 0} {
    error "Requires Vivado >= 2025.1, got $vivado_ver"
}

create_project -in_memory -part xck26-sfvc784-2LV-c

# Load board files for KV260
set_property board_part xilinx.com:kv260_som:part0:1.4 [current_project]

create_bd_design "kv260_bd"
open_bd_design [get_bd_designs kv260_bd]

# Instantiate Zynq PS
set ps [create_bd_cell -type ip -vlnv xilinx.com:ip:zynq_ultra_ps_e:3.5 zynq_ultra_ps_e_0]
apply_bd_automation -rule xilinx.com:bd_rule:zynq_ultra_ps_e \
    -config {apply_board_preset 1} [get_bd_cells $ps]

# Add BRAM controllers
set bram0 [create_bd_cell -type ip -vlnv xilinx.com:ip:axi_bram_ctrl:4.1 axi_bram_ctrl_0]
set bram2 [create_bd_cell -type ip -vlnv xilinx.com:ip:axi_bram_ctrl:4.1 axi_bram_ctrl_1]

apply_bd_automation -rule xilinx.com:bd_rule:axi4 \
    -config {Clk_master "/zynq_ultra_ps_e_0/pl_clk0" \
             Clk_slave "Auto" Master "/zynq_ultra_ps_e_0/M_AXI_HPM0_LPD"} \
    [get_bd_intf_pins $bram0/S_AXI]

validate_bd_design
write_bd_tcl -include_layout ./tcl/create_bd_generated.tcl
```

### Relevance to Your Project

Your existing `create_bd.tcl` is already a good TCL-first approach. Adding a
version guard at the top (`if { [version -short] < "2025.1" }`) prevents
silent failures when running on older Vivado installs in a CI pipeline.

## Vitis Bare-Metal / Standalone

### Key Findings

- **`xparameters.h` regression in Vitis Unified (2023.2+)**: PL-to-PS
  interrupt IDs (`XPAR_FABRIC_…_INTR`) are no longer emitted into
  `xparameters.h` for IP created with the IP Packager. You must read the
  interrupt ID from the BSP's `xscugic` driver metadata, or hard-code the GIC
  SPI offset (IRQ 61 = SPI 29 in UltraScale+) directly.
- **xil_printf vs printf**: `xil_printf` is a lightweight format-string
  implementation that does *not* support floats. It goes to the UART configured
  as `stdin`/`stdout` in the BSP settings. If you see no UART output on the
  KV260, verify that UART1 is enabled in the Zynq PS IP and that the BSP
  `stdin`/`stdout` peripheral is set to `psu_uart_1` in `system.mss`.
- **Linker script heap/stack**: The default standalone BSP places stack at the
  top of OCM (0xFFFEFFFF down). For larger programs add `_HEAP_SIZE = 0x200000`
  to `lscript.ld` and map it to the DDR region (`0x10000000+`).
- **BRAM standalone driver**: `XBram_Initialize()` and `XBram_WriteReg()` /
  `XBram_ReadReg()` are the official bare-metal BRAM driver API. For a
  simple AXI-Lite test, `Xil_Out32` / `Xil_In32` are lower overhead and
  sufficient.

### Code Example

```c
/* BSP check: confirm UART1 is correctly mapped before any xil_printf */
#include "xparameters.h"
#include "xuartps.h"
#include "xil_printf.h"

#define UART1_BASEADDR  XPAR_PSU_UART_1_BASEADDR  /* 0xFF010000 */

void uart_selftest(void) {
    /* Simple loopback check using the UART status register */
    u32 status = Xil_In32(UART1_BASEADDR + XUARTPS_SR_OFFSET);
    if (status & XUARTPS_SR_TXEMPTY) {
        xil_printf("UART1 TX FIFO empty — ready\r\n");
    } else {
        /* TX FIFO not empty: MIO not routed, check PS IP settings */
        xil_printf("UART1 TX FIFO busy — check MIO 36/37 config\r\n");
    }
}
```

### Relevance to Your Project

The KV260 USB-UART is wired to MIO 36 (TX) and 37 (RX) → UART1 on the PS.
If `xil_printf` produces no output over USB, the most common cause is UART1
not being enabled in the Zynq PS block in Vivado, leading to the BSP generating
no UART1 peripheral definition and silently using a null UART.

## XDC Timing Constraints

### Key Findings

- **Clock priority**: `set_clock_groups` has **higher precedence** than
  `set_false_path`. Defining both for the same clock pair causes `set_false_path`
  to be silently ignored. Use one or the other, not both.
- **PS PL clock**: The `pl_clk0` (typically 100 MHz) derived from the Zynq PS
  is an **automatically created clock** — do not call `create_clock` on it.
  Vivado creates it internally; you only need to reference it as
  `[get_clocks -of_objects [get_pins zynq_ultra_ps_e_0/pl_clk0]]`.
- **AXI-Lite input delays**: For purely internal PS→PL paths over AXI-Lite
  (no off-chip I/O), `set_input_delay` / `set_output_delay` are *not required*.
  These constraints apply to chip-boundary I/O only. Applying them to AXI bus
  signals creates confusing over-constraint warnings.
- **Async reset false path**: If you derive a synchronous reset from an async
  pin, constrain it explicitly: `set_false_path -from [get_ports aresetn]`.
- **`-datapath_only` vs `-asynchronous`**: For deliberately unrelated clocks
  (e.g., an external SPI clock and pl_clk0), use
  `set_clock_groups -asynchronous`. For paths that will never have data
  transfers, use `set_false_path` — the latter also suppresses CDC warnings.

### Code Example

```xdc
# KV260 XDC snippet for AXI-BRAM demo

# pl_clk0 is auto-defined by Vivado from the PS — do NOT create_clock it.
# Reference it for constraints:
set pl_clk [get_clocks -of_objects [get_pins zynq_ultra_ps_e_0/pl_clk0]]

# If you add a second clock (e.g., external oscillator on PMOD):
# create_clock -period 10.000 -name ext_clk [get_ports ext_clk_p]
# set_clock_groups -asynchronous \
#     -group [get_clocks $pl_clk] \
#     -group [get_clocks ext_clk]

# Async reset from active-low PS reset
set_false_path -from [get_pins zynq_ultra_ps_e_0/pl_resetn0]

# UART output timing — MIO path, usually covered by PS IO constraints
# set_output_delay -clock $pl_clk -max 2.0 [get_ports uart_txd]
# set_output_delay -clock $pl_clk -min -1.0 [get_ports uart_txd]
```

### Relevance to Your Project

A pure PS→PL AXI-Lite to BRAM design with no off-chip PL I/O needs only the
`pl_resetn0` false path and the auto-generated PS clocks. Over-constraining
with unnecessary `set_input_delay` on AXI buses will produce confusing timing
failures that do not reflect real hardware problems.

## Kria KV260 / K26 SoM

### Key Findings

- **UART1 not enabled by default**: The K26 MPSoC PS configuration in the
  board preset does *not* enable UART1. You must manually enable it in the
  Zynq UltraScale+ PS IP and select MIO 36–37 for the KV260 carrier card's
  USB-UART bridge.
- **Boot modes**: The KV260 supports SD card, QSPI, eMMC, and JTAG boot modes,
  selected via `MODE[3:0]` pins on the SOM240 connector (set on the carrier
  card). JTAG mode is the fastest iteration path during bare-metal development:
  use XSDB / XSCT to download the bitstream + ELF without reflashing QSPI.
- **JTAG bare-metal flow**:
  1. Set boot mode switches to JTAG on the KV260 carrier.
  2. In Vitis/XSDB: `program_hw_devices`, `dow <elf>`, `con`.
  3. No SD card or boot image needed.
- **EMIO GPIO**: PL-side GPIO exposed via EMIO is a useful debug path (toggle
  a GPIO from bare-metal C, probe with a logic analyzer) without needing a
  full PL peripheral.
- **Power domains**: KV260 sideband I/O (SOM240 connector) runs at 1.8 V.
  PL VCCO banks are configured via the carrier card. Check bank voltage
  assignment in Vivado's I/O Planning before targeting any PL pins.
- **Vivado 2025.1 board file**: Use board part
  `xilinx.com:kv260_som:part0:1.4` — this auto-populates the Zynq PS
  subsystem with correct DDR, MIO, and PL clock settings for the K26.

### Code Example

```tcl
# XSDB/XSCT script: JTAG boot and run bare-metal ELF on KV260
# Run from: xsct boot_jtag.tcl

connect
targets -set -filter {name =~ "PSU"}

# Disable security gates for JTAG access
rst -system
after 1000

# Load the bitstream (optional: skip if PL already configured)
targets -set -filter {name =~ "xck26*"}
fpga -file ./impl/kv260_top.bit

# Switch to A53 core 0 and load the bare-metal ELF
targets -set -filter {name =~ "Cortex-A53 #0"}
rst -processor
dow ./vitis_ws/kv260_app/Debug/kv260_app.elf
con

puts "Application running — open serial terminal at 115200 baud"
```

### Relevance to Your Project

This JTAG flow eliminates the QSPI flash-program loop entirely during
iteration. For the AXI-BRAM demo, the typical debug cycle becomes:
modify `main.c` → rebuild ELF → run `xsct boot_jtag.tcl` → read UART output.
No SD card swaps or boot-image packaging needed.

## AMD/Xilinx Tool Updates (Vivado / Vitis 2025.x)

### Key Findings

- **Vivado 2025.1**: Added full device support for the **Spartan UltraScale+**
  family. AXI SmartConnect IP gained a new ultra-low-area mode
  (`STRATEGY=low_area`) beneficial for 1×1 Master→Slave configurations like
  the PS→BRAM path.
- **AXI Interconnect → SmartConnect migration**: AMD officially recommends
  replacing all AXI Interconnect instances with SmartConnect for UltraScale+
  designs. AXI Interconnect is still supported but receives no new feature
  development in 2025.x.
- **Vitis 2025.1 known issue**: `xparameters.h` does not auto-populate
  `#define` entries for custom IP created with the Vivado IP Packager. Users
  must manually add interrupt IDs or read them from the BSP's
  `psu_cortexa53_0/standalone_domain/bsp/…/xparameters.h` path after
  platform regeneration (AMD AR: 0D5Pd00000kXRWBKA4).
- **`write_bd_tcl` version embedding**: Scripts generated in 2025.1 contain
  a version header. Sourcing them in 2024.x triggers a warning and may use
  stale IP versions; always regenerate when upgrading tools.
- **Vitis Export to Vivado** (new in 2025.1, tutorial XD101): Allows hardware
  iteration — modifying the Vivado block design — without exiting the Vitis IDE
  and re-importing the full XSA. Reduces the inner-loop iteration time for
  hardware/software co-debug.
- **2026.1 tools are now available**: AMD has released Vivado/Vitis 2026.1.
  If you are locked to 2025.1 for board-file reasons, check that `kv260_som`
  board part version 1.4 is still shipped with 2026.1.

### Code Example

```tcl
# Vivado 2025.1 TCL: replace AXI Interconnect with SmartConnect
# Run inside an open project with block design loaded

open_bd_design [get_files *.bd]

# Delete old AXI Interconnect
delete_bd_objs [get_bd_cells axi_interconnect_0]

# Create SmartConnect with 1 master, 2 slaves (BRAM0 + BRAM2)
set sc [create_bd_cell -type ip \
    -vlnv xilinx.com:ip:smartconnect:1.0 axi_smc]
set_property CONFIG.NUM_SI {1} [get_bd_cells $sc]
set_property CONFIG.NUM_MI {2} [get_bd_cells $sc]

# Re-connect PS to SmartConnect
connect_bd_intf_net \
    [get_bd_intf_pins zynq_ultra_ps_e_0/M_AXI_HPM0_LPD] \
    [get_bd_intf_pins $sc/S00_AXI]
connect_bd_intf_net \
    [get_bd_intf_pins $sc/M00_AXI] \
    [get_bd_intf_pins axi_bram_ctrl_0/S_AXI]
connect_bd_intf_net \
    [get_bd_intf_pins $sc/M01_AXI] \
    [get_bd_intf_pins axi_bram_ctrl_1/S_AXI]

validate_bd_design
save_bd_design
```

### Relevance to Your Project

If your current design uses the older AXI Interconnect IP between the Zynq PS
and the two BRAM controllers, upgrading to SmartConnect in Vivado 2025.1 can
eliminate the write-enable timing bug and reduce PL resource usage. This is a
low-risk change because it only affects the AXI bus fabric, not the BRAM
controllers or PS configuration.
