# FPGA Research Digest - 2026-10-20

## Executive Summary

- **Word-aligned BRAM access is mandatory**: The AXI BRAM Controller maps 32-bit words, not bytes. Software writes at non-multiples of 4 (e.g. `0xA0000001`) will cause a CPU alignment trap or stall silently—always use offsets `0x0, 0x4, 0x8, …` on your KV260 bare-metal reads/writes to BRAM0 and BRAM2.
- **VALID must stay asserted until handshake completes**: AXI4-Lite requires the initiator to hold VALID high until READY is also seen; deasserting VALID early causes a deadlock that simulation may not catch unless you add an AXI Protocol Checker IP.
- **Vivado 2025.1 ships a new RTL-based AXI Switch IP** with configurable protocol bridging and width conversion—potentially useful for future expansion of the KV260 demo to add streaming peripherals alongside BRAM.
- **`apply_bd_automation` in TCL automates clock/reset wiring** on your block design's AXI interconnect, saving manual connection steps every time you regenerate.
- **JTAG boot PLL caveat**: Community reports indicate that when loading over JTAG instead of SD card, the PS PLL may not be fully initialized unless `psu_init` is explicitly called—relevant if you debug your KV260 demo via Hardware Manager and find AXI transactions timing out.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- **Handshake invariant**: A transaction completes only when both VALID and READY are high on the same rising clock edge. The initiator must hold VALID asserted once raised; the responder may raise/lower READY freely.
- **Deadlock risk**: If your RTL deasserts VALID before READY is seen (e.g. a combinational path that clears VALID in response to an upstream stall), you get a permanent hang—hard to catch without a protocol checker.
- **AXI Register Slice IP** inserts a one-cycle pipeline register that breaks long combinational paths without changing protocol behavior—the recommended fix for timing closure failures on AXI buses.
- **AXI Protocol Checker IP**: Insert during simulation to flag VALID/READY violations; the synthesizer will not report them.
- **BRAM address alignment**: The AXI BRAM Controller addresses 32-bit words. Software must use word-aligned byte offsets (`base + 0`, `base + 4`, etc.); unaligned accesses cause the Cortex-A53 to trap.
- **AXI-Lite vs AXI4**: AXI-Lite has no burst support and only 32-bit data width—suitable for control registers and small BRAMs, but switch to AXI4 if you need full-width DMA bursts in future work.

### Code Example

```c
/* Write pattern to BRAM0 over AXI-Lite (Cortex-A53 bare-metal) */
#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL

static inline void bram_write(uint32_t base, uint32_t word_offset, uint32_t value) {
    /* word_offset is in words (0, 1, 2, ...); multiply by 4 for byte address */
    volatile uint32_t *ptr = (volatile uint32_t *)(base + (word_offset << 2));
    *ptr = value;
    dsb();  /* data synchronization barrier before readback */
}

static inline uint32_t bram_read(uint32_t base, uint32_t word_offset) {
    volatile uint32_t *ptr = (volatile uint32_t *)(base + (word_offset << 2));
    return *ptr;
}
```

### Relevance to Your Project

Your `main.c` writes patterns to BRAM0 (`0xA0000000`) and BRAM2 (`0xA0010000`). Using `volatile uint32_t *` pointers and only word-aligned offsets ensures the AXI-Lite handshake completes correctly and avoids silent data corruption. Add the AXI Protocol Checker to your block design in simulation mode to verify no handshake violations occur during rapid back-to-back accesses.

## Vivado Block Design / IP Integrator

### Key Findings

- **Address Editor auto-assignment**: IP Integrator can auto-assign addresses to all AXI slaves via "Assign All." This is the fastest way to confirm your BRAM0/BRAM2 base addresses and ensure they don't collide.
- **Address Editor TCL export**: `assign_bd_address` supports CSV import/export, letting you version-control the address map separately from the block design.
- **Connection automation**: `apply_bd_automation` wires clock and reset pins and optionally creates interconnects; it is the TCL equivalent of the GUI's "Run Connection Automation" button.
- **New in 2025.1**: IP Integrator gained dedicated "Clocking and Reset" and "Interrupt and AXI-4 Lite" views, making it easier to verify PS-to-PL clock domains and interrupt routing.
- **Address tab visibility**: The Address Editor tab only appears if at least one IP block is acting as a bus master—ensure the Zynq PS block is enabled.

### Code Example

```tcl
# In your create_bd.tcl - auto-assign all slave addresses then pin specific ones
assign_bd_address

# Override BRAM0 base address to 0xA000_0000
set_property offset 0xA0000000 [get_bd_addr_segs {mig_7series_0/S_AXI/Mem0}]

# Or for the BRAM controller directly:
set bram0_seg [get_bd_addr_segs {axi_bram_ctrl_0/S_AXI/Mem0}]
set_property offset 0xA0000000 $bram0_seg
set_property range  0x10000    $bram0_seg

set bram2_seg [get_bd_addr_segs {axi_bram_ctrl_1/S_AXI/Mem0}]
set_property offset 0xA0010000 $bram2_seg
set_property range  0x10000    $bram2_seg

# Run connection automation for clocks and resets
apply_bd_automation -rule xilinx.com:bd_rule:clkrst \
    -config {Clk "/zynq_ultra_ps_e_0/pl_clk0 (100 MHz)" {}} \
    [get_bd_pins axi_bram_ctrl_0/s_axi_aclk]
```

### Relevance to Your Project

Your `create_bd.tcl` script rebuilds the block design non-interactively. Pinning the address assignments with explicit TCL commands (as above) prevents Vivado from reassigning addresses on regeneration, which would break the hardcoded base addresses in `main.c`.

## Vivado TCL Scripting

### Key Findings

- **Non-Project Mode**: In this mode, Vivado works in-memory; you must explicitly write checkpoints (`write_checkpoint`) and reports. There is no automatic regeneration on source changes—you must rerun synthesis manually.
- **Batch invocation**: `vivado -mode batch -source my_script.tcl` runs headless; `-mode tcl` drops you to an interactive Tcl shell without a GUI.
- **In-project checkpoint for IP**: Vivado uses the `.dcp` file inside the IP directory to skip re-synthesis of unchanged IP in implementation—keep the IP output products in source control.
- **Flow commands**: `synth_design`, `opt_design`, `place_design`, `route_design`, `write_bitstream` each accept `-directive` for strategy selection.
- **`open_project` vs `open_bd_design`**: After `open_project`, call `open_bd_design [get_bd_designs]` before accessing block design objects.

### Code Example

```tcl
#!/usr/bin/env tclsh
# Non-project mode: read sources, synthesize, implement, write bitstream

read_vhdl  kv260_top.vhd
read_xdc   kv260_constraints.xdc
read_ip    [glob ip/*.xci]

synth_design -top kv260_top -part xck26-sfvc784-2LV-c
write_checkpoint -force checkpoints/post_synth.dcp

opt_design
place_design   -directive Explore
route_design   -directive Explore
write_checkpoint -force checkpoints/post_route.dcp

report_timing_summary -file reports/timing.rpt
report_utilization    -file reports/util.rpt

write_bitstream -force output/kv260_top.bit
```

### Relevance to Your Project

Your project already uses `create_bd.tcl` for block design generation. Extending it with the synthesis and implementation commands above enables a fully automated CI-style build from TCL without opening the Vivado GUI, useful for reproducible builds and regression testing.

## Vitis Bare-Metal / Standalone

### Key Findings

- **BSP generation**: Vitis generates the BSP from the exported XSA hardware file. The standalone BSP includes `xil_printf`, `xuartps` drivers, and interrupt support.
- **`xil_printf` routing**: In BSP settings, `stdin`/`stdout` must be mapped to the correct PS UART (usually `psu_uart_1` on KV260 for the USB-UART port). Misconfigured BSP settings produce silent output—verify the BSP STDOUT property.
- **Linker script pitfalls**: Vitis can place `.text`/`.data` sections in the wrong memory region. Verify `lscript.ld` maps sections to DDR (`psu_ddr_0_MEM_0` at `0x0`) rather than a PL BAR or TCM.
- **xscugic interrupt init**: For PS interrupts, `XScuGic_CfgInitialize` must be called before enabling interrupts; the GIC distributor and CPU interface initialization order matters.
- **Embeddedsw changelog**: The `uartps` driver changelog for 2025.1 is at `xlnx_rel_v2025.1` on GitHub embeddedsw—check it for any behavioral changes.

### Code Example

```c
#include "xil_printf.h"
#include "xuartps.h"

/* Minimal UART init for KV260 bare-metal (PS UART1 → USB-UART) */
int main(void) {
    /* xil_printf routes to the STDOUT UART configured in BSP settings */
    xil_printf("KV260 AXI-BRAM Demo starting...\r\n");

    /* Write and read back BRAM0 */
    volatile uint32_t *bram0 = (volatile uint32_t *)0xA0000000UL;
    bram0[0] = 0xDEADBEEF;
    __asm__ volatile("dsb sy");
    uint32_t rd = bram0[0];

    if (rd == 0xDEADBEEF)
        xil_printf("BRAM0[0] PASS: 0x%08X\r\n", rd);
    else
        xil_printf("BRAM0[0] FAIL: expected 0xDEADBEEF, got 0x%08X\r\n", rd);

    return 0;
}
```

### Relevance to Your Project

Your `main.c` uses `xil_printf` for PASS/FAIL output over USB-UART. If output is missing, first check the BSP STDOUT setting in `system.mss`—it must point to `psu_uart_1`. Add a `dsb sy` barrier between write and read to ensure the AXI write completes before the read is issued.

## XDC Timing Constraints

### Key Findings

- **`set_input_delay` / `set_output_delay`**: Constrain external path delays relative to a clock edge. Values can be negative depending on clock/data phase relationship. These tell the timing engine how much of the clock period budget is consumed outside the FPGA.
- **`set_clock_groups -asynchronous`**: Use for clocks with no timing relationship (e.g. independent PL clock vs. PS clock). Without this, Vivado reports false path violations between unrelated domains.
- **PS-PL interface constraints**: The Zynq PS AXI interfaces run at `pl_clk0`—ensure this clock is properly defined in the XDC. The auto-generated XDC from Vivado's Zynq PS block usually handles this, but verify after export.
- **Timing-driven P&R**: Always run `report_timing_summary` post-route. Negative WNS (Worst Negative Slack) means a failed constraint—increase clock period or add register stages.
- **False paths**: AXI resets crossing clock domains should be declared as false paths or multicycle paths to suppress spurious violations.

### Code Example

```xdc
# kv260_constraints.xdc

# PS provides pl_clk0 at 100 MHz to PL fabric
# (auto-created by Vivado Zynq PS block — included here for clarity)
create_clock -period 10.000 -name pl_clk0 [get_pins zynq_ultra_ps_e_0/pl_clk0]

# Treat PS and PL resets as asynchronous to PL clock
set_false_path -from [get_ports {pl_resetn0}]

# Async clock groups: if a second PL clock domain is added later
# set_clock_groups -asynchronous \
#     -group [get_clocks pl_clk0] \
#     -group [get_clocks pl_clk1]

# For bare-metal AXI-Lite demo with no external I/O timing requirements,
# only the internal PS-to-PL AXI interface timing is critical.
# Vivado auto-handles PS-PL AXI timing via Zynq IP constraints.
```

### Relevance to Your Project

Your KV260 demo only uses PS-to-PL AXI-Lite with no off-chip I/O timing. The critical constraint is that `pl_clk0` is properly defined—Vivado's Zynq PS IP generates this automatically. Focus on ensuring post-route WNS is positive at your target frequency (100 MHz is typical for the K26 AXI interfaces).

## Kria KV260 / K26 SoM

### Key Findings

- **SOM variants**: The K26 exists in two variants—`sm-k26` (with eMMC) and `smk-k26` (Starter Kit, no eMMC, QSPI firmware). The KV260 uses the `smk-k26` variant.
- **Boot sequence**: At QSPI boot, a limited set of peripherals is initialized; a carrier-card detection step then applies a device tree overlay. For bare-metal JTAG debug, this overlay step is bypassed.
- **JTAG access**: The KV260 uses an FTDI chip for JTAG; the `LS_OE_B` pin must be asserted (driven by the carrier board) for on-board JTAG to work. Install Digilent cable drivers first.
- **MIO banks**: Bank 501 covers MIO[38:51] and MIO[26:30]; Bank 502 covers MIO[52:77]; Bank 504 is the DDR controller bank. UART1 uses MIO[36:37] (TX/RX) by default on the KV260.
- **PLL init over JTAG**: Community reports indicate PS PLL initialization may be incomplete when loading bitstreams via JTAG without the full boot flow—call `psu_init` from XSCT before downloading your application if you see AXI timeouts.
- **FSBL + JTAG**: Build FSBL and PMU firmware in Vitis, load FSBL to APU core 0 via XSCT, then download your application ELF—this fully initializes DDR and PS peripherals before your code runs.

### Code Example

```tcl
# XSCT script: download and run bare-metal ELF on KV260 over JTAG
# Run from: xsct kv260_jtag_run.tcl

connect -url TCP:localhost:3121
targets -set -nocase -filter {name =~ "PSU"}

# Initialize the PS (clocks, DDR, MIO)
mwr  0xFFCA0038 0x1FF
after 500
targets -set -nocase -filter {name =~ "MicroBlaze PMU"}
catch {dow pmufw.elf}
con
after 500

targets -set -nocase -filter {name =~ "*A53*#0"}
rst -processor
dow fsbl.elf
con
after 5000

stop
dow kv260_axibram_demo.elf
con
```

### Relevance to Your Project

When debugging your KV260 AXI-BRAM demo via JTAG, this XSCT flow ensures the full PS initialization happens (DDR training, PLL lock, MIO setup) before your code runs. Without it, the Cortex-A53 may access the AXI-Lite slaves before the interconnect is clocked, causing silent failures that look like hardware bugs.

## AMD/Xilinx Tool Updates (Vivado/Vitis 2025.x)

### Key Findings

- **Vivado 2025.1** (released ~October 2025):
  - New **RTL-based AXI Switch IP**: bridges AXI interfaces of different protocol types (AXI4/AXI-Lite/AXI-Stream) and widths—replaces the older SmartConnect for some use cases.
  - IP Integrator new **"Clocking and Reset"** and **"Interrupt and AXI-4 Lite"** dedicated views.
  - New device support: Versal AI Edge Gen 2, Versal Prime Gen 2, Spartan UltraScale+.
  - Selective device installer for Versal reduces download size.
- **Vivado 2025.2** (later release):
  - AXI Switch and AXI SmartConnect gain an **ultra-low-area mode** via a `STRATEGY` parameter.
  - Block design supports adding RTL with NoC XPMs via module referencing.
  - Simplified AXI connections between SystemVerilog instances with automatic wrapper creation.
- **Vitis AI 5.1** (on 2025.1 toolchain): Multi-NPU support, mixed-precision, BF16 YOLO variants, Apptainer as Docker alternative.
- **Open Source 2025.1**: Linux kernel updated to 6.12; early-access Zephyr driver support for several Zynq peripherals.

### Code Example

```tcl
# Using the new AXI Switch IP in a 2025.1 block design (TCL)
# Instantiate an AXI Switch to bridge an AXI4-Lite master to AXI4 slaves

create_bd_cell -type ip -vlnv xilinx.com:ip:axi_switch:1.0 axi_switch_0

set_property -dict [list \
    CONFIG.NUM_SI {1} \
    CONFIG.NUM_MI {2} \
    CONFIG.PROTOCOL  {AXI4LITE} \
] [get_bd_cells axi_switch_0]

# Connect PS AXI-Lite master port to switch input
connect_bd_intf_net \
    [get_bd_intf_pins zynq_ultra_ps_e_0/M_AXI_HPM0_LPD] \
    [get_bd_intf_pins axi_switch_0/S00_AXI]

# Connect switch outputs to two BRAM controllers
connect_bd_intf_net \
    [get_bd_intf_pins axi_switch_0/M00_AXI] \
    [get_bd_intf_pins axi_bram_ctrl_0/S_AXI]

connect_bd_intf_net \
    [get_bd_intf_pins axi_switch_0/M01_AXI] \
    [get_bd_intf_pins axi_bram_ctrl_1/S_AXI]
```

### Relevance to Your Project

Currently your design likely uses the AXI SmartConnect IP to fan out from the PS to two BRAM controllers. The new AXI Switch IP in 2025.1 is a lighter-weight alternative with explicit protocol bridging—worth evaluating if you expand the design to mixed AXI-Lite and AXI-Stream peripherals in future iterations.
