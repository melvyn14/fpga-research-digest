# FPGA Research Digest - 2026-11-03

## Executive Summary
- **AXI-Lite address alignment is critical**: The AXI BRAM Controller requires word-aligned addresses (bottom 2 bits zero). Unaligned writes land at the wrong BRAM word — always generate addresses as `base + 4*n` in your `main.c` writes to BRAM0 (0xA0000000) and BRAM2 (0xA0010000).
- **AWREADY/WREADY are unregistered in AXI-Lite BRAM controller**: AMD's PG078 notes these outputs are combinational, which can cause timing closure issues at higher frequencies. Add pipeline registers or reduce clock speed if timing fails post-route.
- **Non-project Tcl mode is ideal for CI/batch flows**: Your `create_bd.tcl` can be extended into a full non-project run (`read_vhdl` → `synth_design` → `opt_design` → `place_design` → `route_design` → `write_bitstream`) without ever opening the Vivado GUI.
- **Vitis 2025.1 makes the Unified IDE default**: The Classic IDE is now deprecated; migrate your Vitis application project to the Unified IDE to stay on the supported path for future Vivado/Vitis updates.
- **XPM_FIFO_AXIS operates in FWFT mode only**: Any future AXI-Stream addition to this project must account for first-word fall-through behavior and sticky TVALID semantics.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings
- **Handshake rule**: A transfer completes only on the rising clock edge where both VALID and READY are high on the same channel (AWVALID+AWREADY for address, WVALID+WREADY for write data, BVALID+BREADY for write response).
- **Unregistered readys**: PG078 (AXI BRAM Controller v4.1) states AWREADY and WREADY are not registered in AXI4-Lite mode, creating combinational paths. At 100 MHz on KV260 these usually meet timing, but verify with timing report post-route.
- **ECC write penalty**: When ECC is enabled, every write becomes a read-modify-write (adds ~2–4 cycles). Your project uses raw BRAM without ECC, so this isn't a current concern, but remember it if you enable ECC later.
- **Address alignment**: The bottom 2 bits of an AXI-Lite address must be zero (word-aligned). Misaligned accesses may appear to succeed but write to the wrong word. Always use `0xA0000000 + (offset * 4)`.
- **AXI-Stream TVALID stickiness**: Once asserted, TVALID must not de-assert until TREADY responds. A slave's TREADY may depend on TVALID, but TVALID must never depend on TREADY (deadlock).

### Code Example
```c
/* Correct word-aligned AXI-Lite write to BRAM0 */
#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL

static inline void bram_write(uint32_t base, uint32_t word_offset, uint32_t val) {
    volatile uint32_t *ptr = (volatile uint32_t *)(base + (word_offset << 2));
    *ptr = val;
}

static inline uint32_t bram_read(uint32_t base, uint32_t word_offset) {
    volatile uint32_t *ptr = (volatile uint32_t *)(base + (word_offset << 2));
    return *ptr;
}

/* Walking-ones pattern test */
int test_bram(uint32_t base, uint32_t depth_words) {
    for (uint32_t i = 0; i < depth_words; i++)
        bram_write(base, i, 1u << (i % 32));
    for (uint32_t i = 0; i < depth_words; i++) {
        if (bram_read(base, i) != (1u << (i % 32))) return -1;
    }
    return 0;
}
```

### Relevance to Your Project
Your `main.c` writes patterns to BRAM0 and BRAM2. The helpers above enforce word-aligned access and make a walking-ones test easy to layer on top of the existing pass/fail check. If you see unexpected FAIL results, check first that the write address has bits[1:0] = 0.

## Vivado Block Design / IP Integrator

### Key Findings
- **Address Editor auto-assign**: If validation reports "unmapped peripheral", right-click the Address Editor canvas and choose **Assign All** (or Auto-Assign Address). For the KV260 project, BRAM0 and BRAM2 should be mapped to `0xA000_0000` and `0xA001_0000` respectively.
- **Block Automation vs Connection Automation**: Block Automation configures the Zynq PS (apply board preset); Connection Automation wires up AXI interfaces and clocks. Always run Block Automation first, then Connection Automation.
- **Regenerate Layout vs Optimize Routing**: Regenerate Layout moves blocks and reroutes; Optimize Routing only reroutes. Use Regenerate Layout after structural changes.
- **Out-of-context synthesis**: Compiling each IP separately means changing one IP (e.g., the BRAM width) doesn't force re-synthesis of the entire block design.
- **Address Editor tab visibility**: Only visible when the design has a bus master. If missing, open it via **Window → Address Editor**.

### Code Example
```tcl
# Verify BRAM address segments in Tcl console / create_bd.tcl
set bram0 [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
set bram2 [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_2_Mem0}]
puts "BRAM0 range: [get_property OFFSET $bram0] size [get_property RANGE $bram0]"
puts "BRAM2 range: [get_property OFFSET $bram2] size [get_property RANGE $bram2]"

# Force address assignments if not already set
assign_bd_address [get_bd_addr_segs {axi_bram_ctrl_0/S_AXI/Mem0}]
assign_bd_address [get_bd_addr_segs {axi_bram_ctrl_2/S_AXI/Mem0}]
```

### Relevance to Your Project

## Vivado TCL Scripting

### Key Findings
- **Non-project mode sequence**: `read_vhdl` / `read_ip` / `read_xdc` → `synth_design -top <top> -part <part>` → `opt_design` → `place_design` → `route_design` → `write_bitstream`.
- **Write checkpoints after each step**: `write_checkpoint -force post_route.dcp` lets you reopen at any stage without re-running. Checkpoints are not intended as restart points except for bitstream regeneration (per AMD UG892 2025.2).
- **Incremental synthesis**: Pass `-incremental` to `read_checkpoint` before `synth_design` to reuse unchanged synthesis results and speed up iterative builds.
- **Batch invocation**: `vivado -mode tcl -source run.tcl` runs fully headless; exit with `quit` at the end of the script.
- **Monitor source changes manually**: Non-project mode has no auto-refresh — you must re-read changed source files and re-run the relevant steps.

### Code Example
```tcl
# Minimal non-project batch flow for kv260-axi-bram-demo
set part "xck26-sfvc784-2LV-c"

read_vhdl  ../vhdl/kv260_top.vhd
read_ip    ../ip/blk_mem_gen_0/blk_mem_gen_0.xci
read_ip    ../ip/blk_mem_gen_2/blk_mem_gen_2.xci
read_xdc   ../constraints/kv260_top.xdc

synth_design -top kv260_top -part $part
write_checkpoint -force post_synth.dcp

opt_design
place_design
write_checkpoint -force post_place.dcp

route_design
write_checkpoint -force post_route.dcp

report_timing_summary -file timing_summary.rpt
write_bitstream -force kv260_top.bit
quit
```

### Relevance to Your Project
Your existing `create_bd.tcl` builds the block design interactively. Wrapping it in a non-project flow (or extending it with the snippet above) enables a full headless build — useful for automated daily regression or rebuilding the bitstream after VHDL changes without opening Vivado.

## Vitis Bare-Metal / Standalone

### Key Findings
- **Vitis 2025.1 default IDE**: The Unified IDE is now the default; the Classic IDE is deprecated. New projects should use Unified IDE to get the Vitis Server backend and ongoing support.
- **Linker script generation**: In the Unified IDE, the linker script generator reads memory nodes from the System Device Tree (SDT). For KV260 bare-metal the default DDR region is `ps_ddr_0`, typically starting at 0x00000000. If the app is large or you add a second ELF, split the DDR regions in `lscript.ld`.
- **xil_printf limitations**: ~1 KB footprint, no floating-point, no 64-bit integers. Use `%d` for uint32_t pattern values; use a custom hex printer if you need 64-bit display.
- **Multi-ELF memory collision**: If running both a FSBL and an application, ensure their linker scripts assign non-overlapping DDR regions (FSBL default is 0x00000000–0x0FFFFFFF; move your app above that, e.g., 0x10000000).
- **BSP standalone library**: Provides `Xil_Out32`/`Xil_In32` for raw memory-mapped I/O — a lighter-weight alternative to pointer casts for AXI peripheral access.

### Code Example
```c
#include "xil_io.h"
#include "xil_printf.h"

#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL
#define TEST_WORDS  16

int main(void) {
    xil_printf("KV260 AXI-BRAM test start\r\n");

    /* Write phase */
    for (uint32_t i = 0; i < TEST_WORDS; i++) {
        Xil_Out32(BRAM0_BASE + i * 4, 0xDEAD0000 | i);
        Xil_Out32(BRAM2_BASE + i * 4, 0xBEEF0000 | i);
    }

    /* Verify phase */
    int pass = 1;
    for (uint32_t i = 0; i < TEST_WORDS; i++) {
        uint32_t b0 = Xil_In32(BRAM0_BASE + i * 4);
        uint32_t b2 = Xil_In32(BRAM2_BASE + i * 4);
        if (b0 != (0xDEAD0000 | i) || b2 != (0xBEEF0000 | i)) {
            xil_printf("FAIL word %u: b0=0x%08X b2=0x%08X\r\n", i, b0, b2);
            pass = 0;
        }
    }
    xil_printf(pass ? "PASS\r\n" : "OVERALL FAIL\r\n");
    return 0;
}
```

### Relevance to Your Project
`Xil_Out32`/`Xil_In32` are the idiomatic Xilinx standalone way to do what your `main.c` does with raw pointer casts. They add `dsb()` memory barriers internally on Cortex-A53, preventing out-of-order speculative reads — important when verifying writes to AXI peripherals.

## XDC Timing Constraints

### Key Findings
- **Constraint ordering matters**: AMD recommends applying clocks first, then generated clocks and clock groups, then I/O delay constraints. Violating this order can cause constraints to be silently ignored.
- **Virtual clock for MMCM input**: When the PS-generated PL clock goes through an MMCM before reaching your logic, define a virtual clock and use it as the reference in `set_input_delay`/`set_output_delay`.
- **Clock groups for async CDC**: Use `set_clock_groups -asynchronous -group {clk_a} -group {clk_b}` to cut timing between unrelated clocks. If you ever add a second clock domain to the KV260 PL fabric, this is mandatory.
- **Hold vs setup**: `set_input_delay -min` constrains hold (minimum delay path); `set_input_delay -max` constrains setup. Always specify both.
- **False paths on static signals**: Configuration/status registers written once at startup can be declared with `set_false_path -from [get_cells config_reg*]` to reduce pessimism in the timing report.

### Code Example
```tcl
# kv260_top.xdc — timing constraints for KV260 AXI-BRAM demo

# PL fabric clock from Zynq PS (pl_clk0, nominally 100 MHz)
# create_clock is auto-generated in block design; include it here if using non-project flow:
# create_clock -period 10.000 -name pl_clk0 [get_pins zynq_ultra_ps_e_0/inst/PS8_i/PLCLK[0]]

# Clock domain crossing: async reset synchronizer (if added later)
# set_false_path -from [get_ports sys_rst_n] -to [get_cells rst_sync_reg*]

# I/O delays for any future external interface on KV260 PMOD/FMC
# (not needed for PS-to-PL AXI — all paths are internal)
# set_input_delay  -clock pl_clk0 -max 2.0 [get_ports {pmod_in[*]}]
# set_input_delay  -clock pl_clk0 -min 0.5 [get_ports {pmod_in[*]}]
# set_output_delay -clock pl_clk0 -max 2.0 [get_ports {pmod_out[*]}]
# set_output_delay -clock pl_clk0 -min 0.5 [get_ports {pmod_out[*]}]

# Mark async clock groups if a second PL clock is added:
# set_clock_groups -asynchronous \
#   -group [get_clocks pl_clk0] \
#   -group [get_clocks pl_clk1]
```

### Relevance to Your Project
The current project uses only `pl_clk0` for AXI and BRAM, so all paths are synchronous and I/O constraints aren't needed for existing ports. The template above is ready to uncomment if you add PMOD I/O, a second clock, or an async reset synchronizer — common next steps for this demo board.

## Kria KV260 / K26 SoM

### Key Findings
- **Boot mode via MODE[3:0]**: Quad-SPI (32-bit) uses MIO[5:0]; eMMC uses MIO[22:13]. The boot device is selected by the carrier board pin state at power-on.
- **Special MIO pins**: MIO12 = firmware update enable; MIO31 = PMU hardware shutdown input; MIO35 = external watchdog; MIO36/MIO37 = default Linux UART console.
- **MIO banks**: Banks 501 (MIO[51:26]) and 502 (MIO[77:52]) route through the SOM240_1 connector on the KV260 carrier board.
- **Bare-metal UART**: For your USB-UART output over `xil_printf`, the PS UART1 is wired to the KV260's USB-to-UART bridge on MIO36/MIO37. BSP auto-configures STDOUT to UART1 when the hardware platform is exported from Vivado.
- **PL clock domains**: The Zynq PS can output up to 4 independent PL clocks (pl_clk0–pl_clk3). For this demo only pl_clk0 is used; the others are gated off by default.

### Code Example
```tcl
# In create_bd.tcl: set pl_clk0 to 100 MHz for AXI BRAM operation
set_property -dict [list \
  CONFIG.PSU__CRL_APB__PL0_REF_CTRL__FREQMHZ {100} \
  CONFIG.PSU__USE__M_AXI_GP0 {1} \
  CONFIG.PSU__MAXIGP0__DATA_WIDTH {32} \
] [get_bd_cells zynq_ultra_ps_e_0]

# Enable UART1 on MIO36/MIO37 (default for KV260 console)
set_property -dict [list \
  CONFIG.PSU__UART1__PERIPHERAL__ENABLE {1} \
  CONFIG.PSU__UART1__PERIPHERAL__IO {MIO 36 .. 37} \
] [get_bd_cells zynq_ultra_ps_e_0]
```

### Relevance to Your Project
Confirming that UART1 is mapped to MIO36/37 in the PS configuration ensures `xil_printf` output appears on the KV260's USB console port. If the PS configuration accidentally maps UART0 or disables UART1, you'll see nothing on the terminal even when the AXI-BRAM test passes.

## AMD/Xilinx Tool Updates (Vivado/Vitis 2025.x)

### Key Findings
- **Vitis 2025.1**: Unified IDE is now the **default**; Classic IDE is deprecated. The backend Vitis Server replaces the older Eclipse-based process manager. Legacy CLI tools (`hw_server`, `bootgen`, `program_flash`) are retained.
- **Vivado 2025.1 known issues (resolved)**: As of the `.1` release, AMD reports no unresolved known issues for Vivado 2025.1. Documented fixed issues include GUI instability on the Elaborated Design NoC view and a spurious DRC HDPR-6 error during `place_design`.
- **Vivado 2025.1 known issues (active)**: MIPI C-PHY/D-PHY hold violations on routed designs and ECO-flow clock routing problems are listed but are unlikely to affect an AXI-BRAM project.
- **Vitis 2025.1 known issues**: File/directory selection dialog fails on AlmaLinux 9.5 and RHEL 9.5 (workaround: use file path text input directly). R52-core Dhrystone ELF regression on Versal AI Edge Gen 2 (does not affect KV260/A53).
- **Vitis AI 5.1** (ships on 2025.1.1): Adds mixed-precision support, YOLO acceleration on AIE, and new ops (DepthToSpace, PixelShuffle, Deconvolution) — not relevant to bare-metal AXI-BRAM but useful context if you add NPU inference later.

### Code Example
```bash
# Check installed Vivado/Vitis version headlessly
vivado -version 2>&1 | head -3
vitis -version 2>&1 | head -3

# Patch update check (run from shell with tools sourced)
updatemem --version   # also verifies environment is sourced correctly

# Non-interactive bitstream programming via hw_server
program_hw_devices [get_hw_devices xcku*] -bitfile kv260_top.bit
```

### Relevance to Your Project
If you're on Vivado/Vitis 2025.1 and see DRC HDPR-6 errors during implementation, this is a known tool bug (fixed in 2025.1.1). Upgrade to the `.1` patch release before assuming a constraint or design problem. Also: migrate your Vitis application project to Unified IDE now to avoid a forced migration when Classic is removed in a future release.
