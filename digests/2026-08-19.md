## Executive Summary

- **AXI-Lite backpressure is the #1 handshake bug**: When `BREADY`/`RREADY` is held low by the master, the slave must deassert its ready signals — easy to miss in basic simulation but critical for your two-BRAM design under write pressure.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- The VALID/READY handshake governs all five AXI channels (AW, W, B, AR, R). All signals are sampled on the rising clock edge and must change after that edge.
- **Backpressure is the most commonly broken rule**: If the master holds `BREADY` low, the slave must lower `AWREADY` and `WREADY`. Likewise for `RREADY` → `ARREADY`. This is frequently correct in simulation but breaks on real hardware with varying latencies.
- For AXI-Lite specifically, the master may not issue a write address and write data simultaneously — the slave may accept them in any order; your logic must handle both orderings.
- Vivado 2025 has a known issue where AXI4 full peripherals can be limited to a 1 KB effective address space unless the address decode logic is properly parameterized (Digilent Forum AR #33038).
- AXI read data path latency in the BRAM Controller is configurable (`C_READ_LATENCY`, max 128); leaving it at default can cause the PS read to sample before data is valid if your pipeline assumes single-cycle response.

### Code Example

```c
/* Bare-metal AXI-Lite write/read with explicit polling for BRAM readback */
#define BRAM0_BASE 0xA0000000UL
#define BRAM1_BASE 0xA0010000UL

static inline void axi_write32(u32 addr, u32 data) {
    *(volatile u32 *)addr = data;
    /* Ensure write completes before subsequent reads */
    __asm__ volatile("dsb sy" ::: "memory");
}

static inline u32 axi_read32(u32 addr) {
    __asm__ volatile("dsb sy" ::: "memory");
    return *(volatile u32 *)addr;
}

/* Pattern test with explicit data barrier between write and readback */
u32 pattern = 0xDEADBEEF;
axi_write32(BRAM0_BASE + 0x00, pattern);
__asm__ volatile("dsb sy; isb" ::: "memory");   /* full barrier before read */
u32 rb = axi_read32(BRAM0_BASE + 0x00);
if (rb != pattern) xil_printf("BRAM0 FAIL: wrote 0x%08X read 0x%08X\r\n", pattern, rb);
```

### Relevance to Your Project

Your `main.c` writes patterns to BRAM0 (`0xA0000000`) and BRAM2 (`0xA0010000`) and reads back. The full memory barrier (`dsb sy; isb`) between the AXI-Lite write and the subsequent read is critical on Cortex-A53 — without it, the CPU's store buffer may cause the read to return stale data even if the BRAM is correctly wired.

## Vivado Block Design / IP Integrator

### Key Findings

- **Capture-then-edit workflow**: The recommended AMD approach is to build the block design interactively in the Vivado GUI, then use *File → Export Block Design as Tcl* to capture a `.tcl` script. Edit that script to parameterize it rather than hand-writing from scratch.
- The IP Integrator TCL console echoes every GUI action as a Tcl command — watching it while making connections gives you the exact commands to use in automation scripts.
- **Version locking**: Block design Tcl scripts are fragile across Vivado versions. A script generated in 2025.1 may fail in 2025.2 due to IP version bumps. Pin IP versions explicitly: `set_property CONFIG.IP_VERSION {4.1} [get_bd_cells axi_bram_ctrl_0]`.
- Address Editor must be manually validated after any IP addition — run `assign_bd_address` in Tcl or use *Tools → Assign All* to avoid silent address overlap.
- Connection automation (`apply_bd_automation`) can incorrectly wire the BRAM's native port instead of the AXI slave port — always verify port bindings after automation.

### Code Example

```tcl
# Targeted block design validation and address assignment in Tcl
open_project ./kv260.xpr
open_bd_design [get_files *.bd]

# Force address reassignment after adding a new BRAM controller
delete_bd_objs [get_bd_addr_segs]
assign_bd_address

# Validate design and capture warnings
set validation_result [validate_bd_design -quiet]
if {$validation_result != 0} {
    puts "ERROR: Block design validation failed"
    exit 1
}

# Export hardware for Vitis after generation
generate_target all [get_files *.bd]
write_hw_platform -fixed -include_bit -force ./kv260_wrapper.xsa
```

### Relevance to Your Project

Your `create_bd.tcl` drives the block design non-interactively. Adding `-quiet` to `validate_bd_design` and checking the return code lets the script self-diagnose misconnections between the Zynq PS AXI master and your two BRAM controllers without requiring a GUI round-trip.

## Vivado TCL Scripting

### Key Findings

- **Non-project mode** is preferred for CI/CD pipelines: the developer controls every step explicitly (`read_vhdl`, `synth_design`, `opt_design`, `place_design`, `route_design`, `write_bitstream`). No `.xpr` is created; design checkpoints (`.dcp`) serve as intermediate artifacts.
- In **project mode**, `launch_runs impl_1 -to_step write_bitstream` followed by `wait_on_run impl_1` handles the full flow asynchronously — useful for GUI-initiated batch builds.
- Design checkpoints are the key artifact for resumability: `write_checkpoint -force post_route.dcp` lets you reload and generate reports without rerunning routing.
- Use `report_timing_summary -file timing.rpt` and `report_utilization -file util.rpt` at the end of every batch run — these are the primary signals a CI system should parse.
- The `Xilinx/Vivado-Design-Tutorials` GitHub repo has a 2025.2 branch with updated IP Integrator examples.

### Code Example

```tcl
#!/usr/bin/env tclsh
# non_project_build.tcl - Non-project mode full build for KV260 AXI-BRAM demo

set part "xck26-sfvc784-2LV-c"
set top  "kv260_top"

# Read sources
read_vhdl   [glob ./vhdl/*.vhd]
read_xdc    [glob ./xdc/*.xdc]
read_ip     [glob ./ip/**/*.xci]
generate_target all [get_ips]

# Synthesis
synth_design -top $top -part $part -flatten_hierarchy rebuilt
write_checkpoint -force ./checkpoints/post_synth.dcp
report_utilization -file ./reports/utilization_synth.rpt

# Implementation
opt_design
place_design
phys_opt_design
route_design
write_checkpoint -force ./checkpoints/post_route.dcp
report_timing_summary -file ./reports/timing_summary.rpt -warn_on_violation

# Bitstream
write_bitstream -force ./output/kv260_top.bit
write_hw_platform -fixed -include_bit -force ./output/kv260_wrapper.xsa
puts "Build complete."
```

### Relevance to Your Project

Converting `create_bd.tcl` to feed into a non-project mode flow lets you run the entire Vivado build from one shell command: `vivado -mode batch -source non_project_build.tcl`. This is particularly useful for iterating on the AXI address map without opening the GUI.

## Vitis Bare-Metal / Standalone

### Key Findings

- **BSP UART configuration**: In Vitis Unified IDE 2025.1, the `vitis-comp.json` under the platform component's `Setting` folder contains `standalone_stdin` and `standalone_stdout` parameters. For KV260 these must be set to `psu_uart_1` (the USB-UART) — default may point to `psu_uart_0`.
- **`xil_printf` is not re-entrant** and has no floating-point support. For PASS/FAIL output it is ideal; for debugging numeric patterns use `%08X` formatting rather than attempting `%f`.
- **Known interrupt issue (2024.2/2025.x)**: PL-to-PS interrupt IDs from custom RTL IP cores do not appear in `xparameters.h`. Workaround: define the interrupt ID manually as a `#define` in your application code and use `XScuGic_Connect()` directly.
- The Vitis 2025.1 template from `miya4649/Vitis_KV260_KR260_Template` (GitHub) provides a minimal working BSP for KV260 with correct UART routing and memory map — a useful baseline to diff against.
- For bare-metal, the linker script (`lscript.ld`) must place code in DDR (`ps_ddr_0` at `0x00000000`) and stack/heap sized appropriately — default 4 KB heap is too small if you add FreeRTOS later.

### Code Example

```c
/* xparameters.h manual workaround for missing PL interrupt IDs */
#include "xparameters.h"
#include "xscugic.h"

/* Workaround: PL→PS interrupt ID not generated in xparameters.h (Vitis 2025.x bug) */
#ifndef XPAR_FABRIC_AXI_BRAM_CTRL_0_VEC_ID
#define XPAR_FABRIC_AXI_BRAM_CTRL_0_VEC_ID  (61U)  /* SPI[29] = 32+29 = 61 */
#endif

static XScuGic gic;

int setup_bram_interrupt(void) {
    XScuGic_Config *cfg = XScuGic_LookupConfig(XPAR_SCUGIC_SINGLE_DEVICE_ID);
    XScuGic_CfgInitialize(&gic, cfg, cfg->CpuBaseAddress);
    Xil_ExceptionRegisterHandler(XIL_EXCEPTION_ID_INT,
        (Xil_ExceptionHandler)XScuGic_InterruptHandler, &gic);
    XScuGic_Connect(&gic, XPAR_FABRIC_AXI_BRAM_CTRL_0_VEC_ID,
        (Xil_InterruptHandler)bram_irq_handler, NULL);
    XScuGic_Enable(&gic, XPAR_FABRIC_AXI_BRAM_CTRL_0_VEC_ID);
    Xil_ExceptionEnable();
    return XST_SUCCESS;
}
```

### Relevance to Your Project

Your bare-metal app uses `xil_printf` for PASS/FAIL output over USB-UART. Confirming `standalone_stdout = psu_uart_1` in the BSP is the first check if output is absent. The interrupt workaround above is relevant if you add interrupt-driven BRAM completion signaling in a future iteration.

## XDC Timing Constraints

### Key Findings

- `set_input_delay` specifies external path delay on a primary input port relative to a clock edge, in nanoseconds. It can be positive or negative depending on clock/data relative phase.
- `set_clock_groups -asynchronous` disables timing analysis between named clock groups. **Do not lump all clocks into one command** — splitting into per-pair commands avoids false paths being ignored.
- For Zynq/Kria: the PS provides `pl_clk0` (default 100 MHz); do not add a `create_clock` for it — use `create_generated_clock` referencing the Zynq PS clock output port.
- Constraints that affect synthesis: `create_clock`, `create_generated_clock`, `set_input_delay`, `set_output_delay`, `set_clock_groups`, `set_false_path`, `set_max_delay`, `set_multicycle_path`.
- The Vivado Constraint Wizard (*Tools → Timing → Constraints Wizard*) can auto-generate `set_input_delay`/`set_output_delay` templates from the synthesized netlist — run it after synthesis to catch unconstrained paths.
- AMD UG835 (2025.1) and UG903 (2025.2) are the authoritative references for constraint syntax.

### Code Example

```xdc
# kv260_top.xdc - Minimal timing constraints for KV260 AXI-BRAM demo

# Primary PL clock sourced from Zynq PS (do NOT use create_clock on pl_clk0)
# The MMCM/PLL in the PS drives this; reference it as generated
create_generated_clock -name clk_100mhz \
    -source [get_pins -hierarchical -filter {NAME =~ */PSU/U0/psu_pl_clk0}] \
    -divide_by 1 \
    [get_nets clk_100mhz]

# Async CDC between any future PL-generated clock and PS clock domain
set_clock_groups -asynchronous \
    -group [get_clocks clk_100mhz] \
    -group [get_clocks clk_200mhz]

# False path on reset (asserted asynchronously, released synchronously)
set_false_path -from [get_ports sys_rst_n]

# I/O constraints for debug signals on PMOD (example)
set_input_delay  -clock clk_100mhz -max 3.0 [get_ports {pmod_in[*]}]
set_input_delay  -clock clk_100mhz -min 0.5 [get_ports {pmod_in[*]}]
set_output_delay -clock clk_100mhz -max 3.0 [get_ports {pmod_out[*]}]
set_output_delay -clock clk_100mhz -min 0.5 [get_ports {pmod_out[*]}]
```

### Relevance to Your Project

The KV260 AXI-BRAM demo's PL clock comes from the Zynq PS (`pl_clk0`). Using `create_generated_clock` rather than `create_clock` ensures Vivado correctly models the PS clock tree and avoids false timing violations on the AXI-Lite paths to your two BRAM controllers.

## Kria KV260 / K26 SoM

### Key Findings

- **Boot modes**: Determined by `MODE[3:0]` pins on the SOM connector (set by carrier card). KV260 Starter Kit ships in **QSPI32** mode. For bare-metal development, **JTAG** mode (MODE = 0000) is recommended — avoids overwriting the QSPI boot image and allows direct Vitis debug attachment.
- **PS MIO pins**: PS MIO bank 501 is on the K26 SOM. `MIO[52:53]` are routed to UART1 (USB-UART via USB-to-serial on the KV260 carrier), which is why `psu_uart_1` is the correct BSP selection.
- **Power domains**: The K26 SOM design guide recommends splitting carrier board power into: *Always On* (5V main), *PL power domain*, and *PS power domain*. PL power must be stable before programming the PL bitstream.
- **EMIO**: GPIO through EMIO (bank 0) is available from the PS to PL without consuming MIO pins. For the AXI-BRAM demo, EMIO is unused but useful for adding a hardware status LED without extra PL GPIO IP.
- MIO/EMIO pinout reference: K26 SOM XDC file and UG1085 (K26 SOM Data Sheet, Mouser: DS987).

### Code Example

```tcl
# Tcl snippet: configure Zynq PS for KV260 in block design
# UART1 on MIO52/53, PL clock at 100 MHz, no QSPI in bare-metal test mode

set_property -dict [list \
    CONFIG.PSU__UART1__PERIPHERAL__ENABLE {1} \
    CONFIG.PSU__UART1__PERIPHERAL__IO    {MIO 52 .. 53} \
    CONFIG.PSU__CRL_APB__PL0_REF_CTRL__FREQMHZ {100} \
    CONFIG.PSU__USE__M_AXI_GP0           {1} \
    CONFIG.PSU__SAXIGP2__DATA_WIDTH      {32} \
] [get_bd_cells zynq_ultra_ps_e_0]

# Enable EMIO GPIO for status LED (32 bits, bank 0)
set_property CONFIG.PSU__GPIO_EMIO__PERIPHERAL__ENABLE {1} \
    [get_bd_cells zynq_ultra_ps_e_0]
set_property CONFIG.PSU__GPIO_EMIO__PERIPHERAL__IO {32} \
    [get_bd_cells zynq_ultra_ps_e_0]
```

### Relevance to Your Project

Confirming `PSU__UART1__PERIPHERAL__IO = MIO 52 .. 53` in your `create_bd.tcl` Zynq PS configuration is the single most common fix for "no UART output" in bare-metal KV260 projects. If your PASS/FAIL output is absent, this and the BSP `standalone_stdout` setting are the first two checks.

## AMD/Xilinx Tool Updates (Vivado/Vitis 2025.x)

### Key Findings

- **Vivado 2026.1 is now available** (August 2026 per AMD downloads page). The 2025.1 → 2025.2 transition resolved several IP bugs; 2026.1 is the current release and may contain additional fixes relevant to Kria.
- **IP Change Log for 2025.1** is consolidated in AMD Answer Record 000037919 — check this before upgrading to confirm whether AXI BRAM Controller v4.1 has errata fixed in newer versions.
- **Vitis AI v5.0** (DPU IP) is certified compatible with Vitis/Vivado/PetaLinux 2025.1.
- **KV260 BIST recreation on 2025.1** is documented on Hackster.io (LogicTronix) — confirms the full Vivado + Vitis 2025.1 flow for KV260 works for MIPI/VCU designs; the same flow applies to simpler AXI-BRAM demos.
- The Vivado Design Tutorials repo has a `2025.2` branch with updated IP Integrator examples for Versal and Zynq targets.
- Vitis Unified IDE 2025.x uses a component-based project model (`vitis-comp.json`) that replaces the classic workspace/project model — migration required if using scripts from Vitis Classic.

### Code Example

```bash
#!/bin/bash
# check_tool_version.sh - Verify Vivado/Vitis version before build

VIVADO_VER=$(vivado -version 2>/dev/null | grep -oP 'v\K[0-9]+\.[0-9]+')
VITIS_VER=$(vitis -version 2>/dev/null | grep -oP 'v\K[0-9]+\.[0-9]+')

echo "Vivado: $VIVADO_VER"
echo "Vitis:  $VITIS_VER"

# Warn if not on supported version for KV260 AXI-BRAM project
if [[ "$VIVADO_VER" != "2025.1" && "$VIVADO_VER" != "2025.2" ]]; then
    echo "WARNING: This project was validated on 2025.1/2025.2. Current: $VIVADO_VER"
fi

# Check AXI BRAM Controller IP version in project
grep -r "axi_bram_ctrl" ./ip/ --include="*.xci" | \
    grep -oP '"component_version":\s*"\K[^"]+' | sort -u | \
    xargs -I{} echo "AXI BRAM Ctrl IP version: {}"
```

### Relevance to Your Project

If you encounter unexplained synthesis or simulation failures in the kv260-axi-bram-demo, the first step is confirming the AXI BRAM Controller IP version in the `.xci` files matches what Vivado 2025.1 ships. The 2025.1 IP Change Log (AR 000037919) documents all changes to this IP; reviewing it takes less than 5 minutes and can save hours of debugging.
