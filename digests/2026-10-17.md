# FPGA Research Digest - 2026-10-17

## Executive Summary
- **BRAM byte-vs-word addressing** is the #1 AXI BRAM pitfall: the AXI-Lite bus is byte-addressed, so consecutive 32-bit words in BRAM must be accessed at address offsets of 4, not 1. Confirms why `BRAM0 @ 0xA0000000` and `BRAM2 @ 0xA0010000` require `addr += 4` in bare-metal C loops.
- **BSP stdout must be explicitly set** to the correct PS UART (psu_uart_0 on KV260) for `xil_printf` to appear on USB-UART; the Vitis BSP generator can silently pick the wrong peripheral.
- **Non-project mode `create_bd.tcl`** flow in Vivado 2025.1 sources the block-design script, calls `make_wrapper` / `generate_target all`, then `write_hw_platform` to produce the XSA — the exact pattern used by this project.
- **Vivado 2025.1 adds new "Clocking and Reset" and "Interrupt and AXI-4 Lite" views** in IP Integrator, making it faster to audit the KV260's AXI clock and reset wiring without opening individual IP dialogs.
- **set_clock_groups -asynchronous** between the PS-derived clock (pl_clk0) and any free-running PL clock is required once CDC paths exist; omitting it causes Vivado to insert false timing violations across the clock boundary.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings
- AXI4-Lite uses a five-channel VALID/READY handshake (AW, W, B, AR, R). A transfer completes only when **both** VALID and READY are high on the same rising clock edge; releasing VALID before READY is asserted is a protocol violation.
- A common slave-side bug: skipping the RESPONSE state when an internal acknowledge arrives in the same cycle as stall de-assertion, causing the AXI-Lite handshake to be incomplete. This hangs the CPU on the next access.
- AXI4-Lite is strictly single-beat (no bursts); AXI4-Stream carries a continuous flow with no address channel — use the right protocol for the job.
- The AXI-Stream FIFO (PG080) bridges a memory-mapped master to a streaming slave; its 2 KB internal TX/RX FIFOs and AXI4-Lite control port make it the lowest-complexity way to add streaming DMA-like behaviour to a bare-metal design.
- Byte addressing: on a 32-bit-wide AXI-Lite bus, address bits [1:0] select a byte lane. Reads at `base + 0`, `base + 4`, `base + 8`, … return consecutive 32-bit words; reads at `base + 1` do not advance to the next word.

### Code Example
```c
/* Correct 32-bit word iteration over AXI-BRAM at base 0xA0000000 */
#define BRAM0_BASE 0xA0000000UL
#define BRAM_DEPTH 1024          /* words */

volatile uint32_t *bram = (volatile uint32_t *)BRAM0_BASE;

for (int i = 0; i < BRAM_DEPTH; i++) {
    bram[i] = (uint32_t)(0xDEAD0000 | i);  /* pointer arithmetic: +4 bytes per step */
}

for (int i = 0; i < BRAM_DEPTH; i++) {
    uint32_t rd = bram[i];
    if (rd != (uint32_t)(0xDEAD0000 | i)) {
        xil_printf("FAIL @ word %d: got 0x%08X\r\n", i, rd);
    }
}
xil_printf("BRAM0 test PASS\r\n");
```

### Relevance to Your Project
`main.c` writes patterns to `BRAM0 @ 0xA0000000` and `BRAM2 @ 0xA0010000`. The pointer-cast pattern above matches typical bare-metal AXI BRAM access. If a test returns all-zeros for every other word, the likely cause is a word-offset bug (using byte index instead of array index).

## Vivado Block Design / IP Integrator

### Key Findings
- Vivado 2025.1 adds **"Clocking and Reset"** and **"Interrupt and AXI-4 Lite"** dedicated views in IP Integrator, letting you audit all clock and interrupt connections without manually tracing nets.
- The **AXI Switch** is a new RTL-based IP in 2025.1 (a fully customizable bridge between AXI interface types and widths), complementing the existing SmartConnect.
- Vivado 2025.2 adds an ultra-low-area mode for both AXI Switch and SmartConnect via a `STRATEGY` parameter — check whether this benefits the AXI Interconnect on the KV260 block design when area is tight.
- The Address Editor auto-assigns addresses; you must manually set the **Range** column to match actual BRAM depth (e.g., 64 KB for a 16 K × 32-bit BRAM) or the interconnect will silently cap accesses to the auto-assigned smaller window.
- Connection Automation (`apply_bd_automation`) wires clock and reset correctly for most IP; always **review the automation report** before accepting — it occasionally assigns the wrong clock when multiple `pl_clk*` sources exist.

### Code Example
```tcl
# Vivado IP Integrator: set address range for AXI BRAM Controller
# After running connect_bd_intf_net / apply_bd_automation:
set_property range 64K \
  [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]

# Validate and save
validate_bd_design
save_bd_design
```

### Relevance to Your Project
The `create_bd.tcl` script builds the block design with BRAM0 at `0xA0000000` (64 KB range) and BRAM2 at `0xA0010000`. After any IP Integrator regeneration, re-run `validate_bd_design` and confirm segment ranges in the Address Editor — range resets to 4 KB on some IP upgrades.

## Vivado TCL Scripting

### Key Findings
- The recommended non-project flow for block designs (UG994, 2025.1): source the `create_bd.tcl`, call `make_wrapper -files [get_files *.bd] -top`, add the wrapper to sources, then `generate_target all [get_files *.bd]`, followed by `synth_design`, `impl_design`, and `write_bitstream`.
- `read_bd` + `open_bd_design` can reload an existing `.bd` file without re-running the full creation script — useful for incremental IP configuration changes.
- Vivado's batch mode (`vivado -mode batch -source script.tcl`) differs subtly from interactive mode; relative paths in IP references can break portability. Always use `[file normalize [file dirname [info script]]]` to derive absolute paths.
- For CI pipelines, keep `set_property SEVERITY {Warning} [get_drc_violations ...]` out of automated flows — it can mask real errors. Use `report_drc -file drc.rpt` and parse the report instead.

### Code Example
```tcl
# Minimal non-project build script for kv260-axi-bram-demo
set script_dir [file normalize [file dirname [info script]]]
set proj_dir   [file normalize "$script_dir/.."]

# 1. Create in-memory project targeting KV260
create_project -in_memory -part xck26-sfvc784-2LV-c

# 2. Source the block design creator
source "$script_dir/create_bd.tcl"

# 3. Wrap and generate targets
make_wrapper -files [get_files *.bd] -top
add_files "$proj_dir/kv260_top_wrapper.v"
generate_target all [get_files *.bd]

# 4. Synthesise → implement → bitstream
synth_design  -top kv260_top_wrapper -part xck26-sfvc784-2LV-c
opt_design
place_design
route_design
write_bitstream -force "$proj_dir/kv260_top.bit"
write_hw_platform -fixed -include_bit -force "$proj_dir/kv260.xsa"
```

### Relevance to Your Project
The `tcl/create_bd.tcl` file in the repo is invoked from this style of wrapper script. The `write_hw_platform` step produces the `.xsa` consumed by Vitis when creating a bare-metal platform for the KV260.

## Vitis Bare-Metal / Standalone

### Key Findings
- **stdout must match the board UART**: on KV260, set both `stdin` and `stdout` to `psu_uart_1` (KV260 uses UART1 for its USB-UART bridge) in the standalone BSP settings; `xil_printf` silently drops output otherwise.
- **Linker script auto-generation pitfall**: Vitis's generator can assign `.text`/`.data`/`.bss` to the AXI BRAM address space instead of DDR when BRAM address segments appear in the address map. Always verify `lscript.ld` places all code sections in `psu_ddr_0_MEM_0` (DDR).
- The standalone BSP changelog for 2025.2 is available on the Xilinx Wiki; review it for the `xiltimer`, `xilpm`, and `xilstandalone` library changes before upgrading from 2025.1.
- For interrupt-driven designs, configure `xscugic` in the BSP and enable the IRQ output on the Zynq UltraScale+ PS in the block design before exporting the XSA.
- Build the platform **after every hardware change** (new XSA export from Vivado); stale platforms silently use old memory maps.

### Code Example
```c
/* Minimal bare-metal BRAM read-back test with xil_printf */
#include "xil_printf.h"
#include "xil_io.h"

#define BRAM0_BASE 0xA0000000UL
#define BRAM2_BASE 0xA0010000UL
#define TEST_WORDS 8

int main(void) {
    xil_printf("KV260 AXI-BRAM bare-metal test\r\n");

    /* Write phase */
    for (int i = 0; i < TEST_WORDS; i++) {
        Xil_Out32(BRAM0_BASE + i * 4, 0xA0000000 + i);
        Xil_Out32(BRAM2_BASE + i * 4, 0xB0000000 + i);
    }

    /* Verify phase */
    int pass = 1;
    for (int i = 0; i < TEST_WORDS; i++) {
        if (Xil_In32(BRAM0_BASE + i * 4) != (0xA0000000 + i)) pass = 0;
        if (Xil_In32(BRAM2_BASE + i * 4) != (0xB0000000 + i)) pass = 0;
    }
    xil_printf("BRAM test: %s\r\n", pass ? "PASS" : "FAIL");
    return 0;
}
```

### Relevance to Your Project
`main.c` follows this exact `Xil_Out32` / `Xil_In32` pattern via the AXI-Lite bus. Using `Xil_Out32`/`Xil_In32` (from `xil_io.h`) is preferred over raw pointer casts in Vitis because they include cache-line invalidation barriers on Cortex-A53.

## XDC Timing Constraints

### Key Findings
- For AXI-BRAM designs running entirely on PS-generated `pl_clk0`, **only `create_clock` for `pl_clk0` is strictly required** — all AXI paths will be timed against it automatically.
- If the design introduces a second clock domain (e.g., a free-running 200 MHz oscillator), add `set_clock_groups -asynchronous -group [get_clocks pl_clk0] -group [get_clocks clk_200]` to prevent Vivado from attempting cross-domain timing analysis.
- The Timing Constraints wizard in Vivado 2025.x auto-recommends `set_input_delay` / `set_output_delay` for all I/O ports; for internal AXI-BRAM paths with no off-chip I/O these are optional, but the tool emits `"There are N input/output ports with no input/output delay specified"` warnings — suppress them with false paths on the unconstrained ports.
- AMD UG835 (2025.2) clarifies: `set_input_delay` consumed at a port reduces the remaining budget for subsequent paths — keep I/O delay values realistic to avoid tightening internal slack unnecessarily.

### Code Example
```tcl
# KV260 minimal XDC for a single-clock AXI-BRAM design
# pl_clk0 is generated by the Zynq PS block (no external oscillator needed)

# Constrain PS-generated PL clock (100 MHz example; match your block design setting)
create_clock -period 10.000 -name pl_clk0 \
  [get_pins zynq_ultra_ps_e_0/inst/PS8_i/PLCLK[0]]

# Suppress I/O timing warnings for ports driven purely through PS
set_false_path -from [get_ports *] -to [get_clocks pl_clk0]
set_false_path -from [get_clocks pl_clk0] -to [get_ports *]

# If a second async clock exists (e.g., external 200 MHz):
# set_clock_groups -asynchronous \
#   -group [get_clocks pl_clk0] \
#   -group [get_clocks clk_200mhz]
```

### Relevance to Your Project
The KV260 block design uses `pl_clk0` from the Zynq PS for both AXI-Lite master and BRAM clock. The above XDC satisfies Vivado's analysis without over-constraining the design, and the commented block is a ready template for future multi-clock expansions.

## Kria KV260 / K26 SoM

### Key Findings
- The K26 SoM provides **user-accessible MIO banks 501 and 502**: bank 501 covers MIO[30:26] and MIO[51:38]; bank 502 covers MIO[77:52]. MIO bank 504 is reserved for the on-module DDR4. EMIO connects PS peripherals (e.g., GPIO, I2C, SPI) to the PL fabric for routing to carrier-board connectors.
- Two SoM variants exist: the standard K26 (with eMMC) and the starter-kit K26i (QSPI-only, no eMMC). The KV260 ships with the starter variant; boot from SD card maps to MIO 39–51 on the carrier.
- For **bare-metal JTAG boot**: the KV260's on-board FT4232H USB chip exposes both UART and JTAG; JTAG cable-driver udev rules must be installed on the host PC for Vitis Hardware Manager to recognise it.
- The USB-UART interface on KV260 uses **UART1** (psu_uart_1) at 115200 baud 8N1 — set this in both the Zynq PS block design and the standalone BSP configuration.
- Vitis 2025.x debug tutorial (XD260) covers step-by-step bare-metal FSBL and application debug on A53 cores; the KV260 bare-metal debug path is identical to the generic Zynq UltraScale+ flow.

### Code Example
```tcl
# Block design: configure PS for KV260 UART1 and pl_clk0
# Inside create_bd.tcl after creating the zynq_ultra_ps_e_0 IP:

set_property -dict [list \
  CONFIG.PSU__UART1__PERIPHERAL__ENABLE {1} \
  CONFIG.PSU__UART1__PERIPHERAL__IO    {MIO 36 .. 37} \
  CONFIG.PSU__CRL_APB__PL0_REF_CTRL__FREQMHZ {100} \
  CONFIG.PSU__USE__M_AXI_GP0           {1} \
] [get_bd_cells zynq_ultra_ps_e_0]
```

### Relevance to Your Project
The Zynq PS configuration in `create_bd.tcl` must enable UART1 on MIO 36–37 for `xil_printf` output to reach the USB-UART. If the PASS/FAIL messages are absent on the terminal, this PS peripheral configuration is the first thing to verify.

## AMD/Xilinx Tool Updates (2025.1 / 2025.2)

### Key Findings
- **Vivado 2025.1 highlights** (from community-posted release notes): new device support for Versal AI Edge Gen 2, Versal Prime Gen 2, and Spartan UltraScale+; selective device installer to reduce download size; new **AXI Switch RTL IP**; new "Clocking and Reset" and "Interrupt and AXI-4 Lite" views in IP Integrator.
- **Vivado 2025.2 highlights** (official AMD page): ultra-low-area mode for AXI Switch and SmartConnect via `STRATEGY` parameter; additional incremental implementation improvements.
- **Vitis 2025.1 open-source components**: Linux kernel upgraded to 6.12; early-access Zephyr support for several peripherals; `SDTGen` available as a standalone tool for System Device Tree generation.
- **Vitis 2025.2 embedded debug (XD260)**: updated step-by-step bare-metal debugging tutorial targeting Vitis 2025.2 / 2026.1; covers Cortex-A53 FSBL debug on Zynq UltraScale+.
- The standalone BSP 2025.2 changelog is published on the Xilinx Wiki; review `xilstandalone`, `xiltimer`, and `xilpm` library changes before migrating a 2025.1 project.

### Code Example
```tcl
# Vivado 2025.x: apply ultra-low-area strategy on SmartConnect (2025.2+)
# Set before generate_target:
set_property CONFIG.STRATEGY {MinArea} \
  [get_bd_cells axi_smc]   ;# axi_smc is the SmartConnect instance name

# Check IP Integrator Clocking view (new in 2025.1):
# GUI: IP Integrator → Window → Board / Clocking and Reset
# Programmatically list clock nets in a block design:
get_bd_nets -of_objects [get_bd_pins -filter {TYPE == clk}]
```

### Relevance to Your Project
The new "Clocking and Reset" view in 2025.1 lets you instantly verify that both AXI BRAM controllers share the same `pl_clk0` source — a common misconfiguration that causes intermittent BRAM read failures. Upgrade to 2025.1 if still on an older version for this diagnostic improvement.
