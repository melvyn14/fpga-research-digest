# FPGA Research Digest - 2026-11-16

## Executive Summary
- **AXI-Lite write-strobe handling** is the most common source of silent data corruption in BRAM-mapped registers; Vivado's generated slave template has had verified bugs — always test with partial-strobe writes.
- **RVALID must stay asserted until RREADY goes high** — your BRAM read path must hold `rvalid`/`rdata` stable or the master may mis-capture data.
- **Connection Automation can silently mis-assign address ranges** when multiple HP ports cover overlapping ranges; always verify BRAM0/BRAM2 base addresses (0xA0000000 / 0xA0010000) in the Address Editor after automation runs.
- **Vivado 2025.1 introduced a new AXI Switch IP** that is explicitly *not* intended for use in block diagram designs — do not use it as a workaround interconnect in your PS-to-PL path.
- **Non-project (batch) TCL mode** is the recommended path for reproducible builds; `synth_design` / `opt_design` / `place_design` / `route_design` / `write_bitstream` is the full pipeline and is well-documented for 2025.x.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings
- **Valid-before-ready rule is strictly enforced by Zynq's AXI master:** VALID must not be deasserted before the corresponding READY is seen. Xilinx IP has historically violated this rule internally, but your slave must never violate it.
- **ARREADY/RVALID interaction bug in Vivado templates:** Formal verification (ZipCPU) found that the Vivado-generated AXI-Lite slave's `ARREADY` logic does not correctly depend on `RVALID`/`RREADY` state, causing startup hangs in some designs.
- **Write-strobe support is error-prone:** The strobe `wstrb[3:0]` selects which byte lanes are written; a common mistake is applying data to all bytes and masking only in software. The correct approach applies the strobe per byte lane in the register logic.
- **Read latency must be absorbed:** BRAM has 1–2 cycle read latency. `RDATA`/`RVALID` must not be driven combinatorially from `ARVALID`; a registered pipeline stage is required.
- **Combinatorial READY paths hurt Fmax:** Any path where READY depends combinatorially on VALID adds a round-trip penalty through the AXI interconnect.

### Code Example
```vhdl
-- VHDL AXI-Lite read channel with 1-cycle BRAM latency
process(s_axi_aclk)
begin
  if rising_edge(s_axi_aclk) then
    if s_axi_aresetn = '0' then
      ar_pending  <= '0';
      s_axi_rvalid <= '0';
    else
      -- Accept AR once prior read response is drained
      if s_axi_arvalid = '1' and ar_pending = '0' then
        ar_pending    <= '1';
        bram_addr_reg <= s_axi_araddr(ADDR_WIDTH-1 downto 2);
      end if;
      -- One cycle after AR, BRAM data is valid
      if ar_pending = '1' and s_axi_rvalid = '0' then
        s_axi_rdata  <= bram_dout;   -- registered BRAM output
        s_axi_rvalid <= '1';
        s_axi_rresp  <= "00";
        ar_pending   <= '0';
      end if;
      -- Hold RVALID until master accepts
      if s_axi_rvalid = '1' and s_axi_rready = '1' then
        s_axi_rvalid <= '0';
      end if;
    end if;
  end if;
end process;
```

### Relevance to Your Project
Your `kv260-axi-bram-demo` drives `BRAM0` at `0xA0000000` and `BRAM2` at `0xA0010000` through AXI-Lite. The registered read pipeline above prevents the BRAM latency from causing RDATA/RVALID misalignment. Verify that the AXI BRAM Controller IP's read latency setting matches your BRAM generator's output-register configuration (1 extra cycle if output registers are enabled).

## Vivado Block Design / IP Integrator

### Key Findings
- **Connection Automation can mis-map addresses** when multiple HP ports cover overlapping ranges. The KV260 demo's HP0/HP2 scenario is documented: Vivado may assign the same range to both BRAMs. Always manually verify 0xA0000000 (BRAM0) and 0xA0010000 (BRAM2) in the Address Editor after automation.
- **Right-click → Assign All** in the Address Editor auto-assigns unassigned slave segments to master address spaces; use this as a starting point, then verify offset/range.
- **`apply_bd_automation` in TCL is discouraged in automated scripts** (AMD UG835 2025.2 notes it is better used interactively from the IDE); for batch scripts, explicitly create nets with `connect_bd_net` / `connect_bd_intf_net` instead.
- **Designer Assistance banner** appears at the top of the canvas when IP is added; clicking it and accepting suggestions is the fastest way to handle clock/reset wiring, but the results must be reviewed.
- **System ILA for in-circuit debug:** IP Integrator can insert a System ILA core directly onto AXI interfaces through the debug wrenches in the block diagram; no separate ILA instantiation is required.

### Code Example
```tcl
# Explicit address assignment in TCL (preferred over apply_bd_automation for batch)
assign_bd_address [get_bd_addr_segs {axi_bram_ctrl_0/S_AXI/Mem0}]
set_property offset 0xA0000000 \
  [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property range 64K \
  [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]

assign_bd_address [get_bd_addr_segs {axi_bram_ctrl_1/S_AXI/Mem0}]
set_property offset 0xA0010000 \
  [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_1_Mem0}]
set_property range 64K \
  [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_1_Mem0}]
```

### Relevance to Your Project
Your `create_bd.tcl` likely uses `apply_bd_automation`; augment it with explicit `set_property offset` calls for BRAM0/BRAM2 so the script is deterministic across Vivado version reinstalls and does not rely on automation heuristics to get the addresses right.

## Vivado TCL Scripting

### Key Findings
- **Non-project (batch) mode is the recommended reproducible-build approach:** `vivado -mode batch -source build.tcl` runs the full flow without a `.xpr` file on disk.
- **Source files are read with explicit commands:** `read_vhdl`, `read_xdc`, `read_bd` load design sources; `read_ip` loads pre-synthesized IP.
- **`launch_runs` does NOT exist in non-project mode** — use the direct commands `synth_design`, `opt_design`, `place_design`, `route_design`, `write_bitstream` instead.
- **IP must be generated explicitly:** `generate_target all [get_files *.bd]` after `read_bd` regenerates BD wrappers and IP outputs.
- **Write XDC from project mode:** `write_xdc -force constraints/top.xdc` from a working project-mode design captures all constraint assignments for use in a batch script.

### Code Example
```tcl
#!/usr/bin/env tclsh
# Non-project mode batch build for KV260 AXI-BRAM demo
set part "xck26-sfvc784-2LV-c"

read_vhdl    [glob ../vhdl/*.vhd]
read_xdc     [glob ../constraints/*.xdc]
read_bd      [glob ../bd/*.bd]
generate_target all [get_files *.bd]

synth_design  -top kv260_top -part $part -flatten_hierarchy rebuilt
opt_design
place_design
phys_opt_design
route_design

report_timing_summary -file reports/timing_summary.rpt
report_utilization    -file reports/utilization.rpt
write_bitstream       -force outputs/kv260_top.bit
write_hw_platform     -fixed -force outputs/kv260_top.xsa
```

### Relevance to Your Project
Wrapping `create_bd.tcl` with the script above gives you a fully reproducible, CI-friendly build that produces both the bitstream and the `.xsa` platform file for Vitis in one `vivado -mode batch` call.

## Vitis Bare-Metal / Standalone

### Key Findings
- **Vitis 2025.1 has deprecated the Classic IDE** — the Unified IDE is now default. Bare-metal platform/application project creation workflows differ between the two; AMD's UG1209 (2025.2) covers the Unified IDE flow.
- **Standalone BSP provides:** interrupt/exception handling, `xil_printf` (lightweight printf over UART), and register-level memory access macros (`Xil_Out32` / `Xil_In32`).
- **GIC driver for interrupts:** `XScuGic` (`xscugic.h`) is the correct driver for Zynq UltraScale+ PS interrupts; use `xil_exception.h` for enabling processor-level exceptions.
- **`xil_printf` does not support all format specifiers** (no `%f` for floating point); use `printf` from newlib for full format support (at higher code-size cost).
- **BSP linker script memory map** must reflect your XSA's memory layout; Vitis auto-generates `lscript.ld` but you may need to adjust `DDR_LOW` size for the Kria's 4GB map.

### Code Example
```c
#include "xil_printf.h"
#include "xil_io.h"

#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL

/* Write a 32-bit test pattern and verify readback */
static int bram_selftest(u32 base, const char *name) {
    const u32 PATTERN = 0xDEADBEEFU;
    Xil_Out32(base, PATTERN);
    u32 readback = Xil_In32(base);
    if (readback == PATTERN) {
        xil_printf("%s PASS (0x%08X)\r\n", name, readback);
        return 0;
    }
    xil_printf("%s FAIL: wrote 0x%08X, read 0x%08X\r\n",
               name, PATTERN, readback);
    return -1;
}

int main(void) {
    int rc = 0;
    rc |= bram_selftest(BRAM0_BASE, "BRAM0");
    rc |= bram_selftest(BRAM2_BASE, "BRAM2");
    xil_printf("Overall: %s\r\n", rc == 0 ? "PASS" : "FAIL");
    return rc;
}
```

### Relevance to Your Project
This mirrors your project's PASS/FAIL test pattern. `Xil_Out32`/`Xil_In32` are the correct bare-metal MMIO accessors — they emit `str`/`ldr` instructions with the memory ordering barriers needed for device memory on Cortex-A53.

## XDC Timing Constraints

### Key Findings
- **AXI-to-BRAM paths are entirely on-chip** — `set_input_delay` / `set_output_delay` are only needed for signals that cross the FPGA boundary (physical I/O pins). Do not add them to your AXI slave ports.
- **Clock definition is the critical constraint:** `create_clock -period 10.000 [get_ports pl_clk0]` (or via PS clock output) is the foundation all timing analysis depends on.
- **For PS-sourced clocks use `create_generated_clock`:** The Zynq PS generates `pl_clk0`; Vivado may auto-create this constraint from the Zynq block, but verify it in the timing report.
- **Clock groups for unrelated PS domains:** If you use multiple PS clocks (e.g., `pl_clk0` for logic and `pl_clk1` for a different domain), declare them as asynchronous: `set_clock_groups -asynchronous -group [get_clocks pl_clk0] -group [get_clocks pl_clk1]`.
- **Virtual clocks for I/O delay:** For any real I/O pins on expansion connectors, define a virtual clock referencing your board's external timing, then apply `set_input_delay`/`set_output_delay` relative to it.

### Code Example
```tcl
# Minimal XDC for KV260 AXI-BRAM demo (PS clock + GPIO button)

# PS supplies pl_clk0 at 100 MHz — Vivado usually auto-creates this
# Uncomment if it doesn't appear in timing reports:
# create_clock -name pl_clk0 -period 10.000 \
#   [get_pins zynq_ultra_ps_e_0/inst/PS8_i/PLCLK[0]]

# Asynchronous reset false-path (reset is multi-cycle by design)
set_false_path -from [get_ports resetn]

# Example: external button on PMOD — needs I/O delay relative to virtual clk
create_clock -name virt_clk -period 10.000
set_input_delay -clock virt_clk -max 2.0 [get_ports btn_in]
set_input_delay -clock virt_clk -min 0.5 [get_ports btn_in]

# Asynchronous clock groups (if pl_clk1 drives a separate logic domain)
# set_clock_groups -asynchronous \
#   -group [get_clocks pl_clk0] \
#   -group [get_clocks pl_clk1]
```

### Relevance to Your Project
For the AXI-BRAM demo, the minimum viable XDC is a `create_clock` for `pl_clk0` plus a false-path on the reset input. The AXI interconnect and BRAM paths are purely internal and constrained automatically once the master clock is defined.

## Kria KV260 / K26 SoM

### Key Findings
- **MIO bank layout:** MIO 500 carries QSPI, eMMC/SD, I2C, and TPM SPI (all 1.8V). MIO 501 and 502 are the user-available MIO banks at 1.8V supplied by the SOM.
- **Primary boot device is on-module QSPI flash;** microSD on the KV260 carrier card is the secondary boot device. The boot image is `BOOT.BIN` in Zynq UltraScale+ format.
- **For bare-metal with custom PL:** the standard Kria boot firmware (U-Boot + PMU FW) configures the PS but does NOT program the PL. For bare-metal + bitstream, build an FSBL that programs the PL, then package everything into a `BOOT.BIN` with `bootgen`.
- **Power domains:** VCC_SOM (5V from carrier) supplies PS logic; PL I/O rails are carrier-card-defined. For the KV260, HP bank voltages are set by the carrier — verify against the KV260 schematic before connecting 3.3V-tolerant peripherals to PL I/O.
- **K26 vs. KR260 differences:** KR260 adds GEM1/GEM0 Ethernet MIO assignments that KV260 lacks; device-tree and PMU overlays differ between the two boards.

### Code Example
```tcl
# Vivado XDC: pin assignment for KV260 PL LEDs (PMOD J2)
# Verify against the KV260 schematic (pg 7-8) before use
set_property PACKAGE_PIN H12 [get_ports {pl_led[0]}]
set_property IOSTANDARD  LVCMOS33 [get_ports {pl_led[0]}]
set_property PACKAGE_PIN E10 [get_ports {pl_led[1]}]
set_property IOSTANDARD  LVCMOS33 [get_ports {pl_led[1]}]

# KV260 USB-UART is routed through the PS MIO — no PL pin assignment needed.
# Access it in bare-metal via the UART1 register at 0xFF010000 (or Xuartps driver).
```

### Relevance to Your Project
Your PS-to-PL AXI-BRAM demo uses the PS UART for `xil_printf` output. The KV260 carrier routes UART1 through MIO pins 36/37 to a USB-UART bridge — no XDC pin assignments are needed for UART, but `uart1` must be enabled in the PS configuration in your block design.

## AMD/Xilinx Tool Updates (Vivado/Vitis 2025.1)

### Key Findings
- **Vivado 2025.1 adds new device support:** Versal AI Edge Gen 2, Versal Prime Gen 2, and Spartan UltraScale+ families. Zynq UltraScale+ (K26 SoM) support continues unchanged.
- **New AXI Switch IP:** A new fully customizable RTL-based AXI Switch IP was introduced. **Explicitly not intended for IP Integrator block diagram use** — it does not participate in connection automation or metadata propagation. Do not substitute it for `axi_interconnect` or `smartconnect` in your design.
- **Vitis Classic IDE deprecated:** The Vitis Unified IDE is now default in 2025.1. The Classic IDE is still launchable but is not the supported path going forward. AMD's UG1209 (2025.2) documents the Unified IDE platform/application project flow.
- **Third-party toolchain support:** Vitis 2025.1 adds support for GCC and ARMClang as alternative toolchains for embedded (bare-metal/RTOS) applications.
- **Ubuntu 24.04 Vitis launch issue:** Community reports of Vitis failing to start on Ubuntu 24.04; some users rolled back to 2024.2.2. If you encounter this, check for missing `libtinfo5` / `libncurses5` dependencies or use the AMD-provided Docker container.
- **Inline HDL for utility IP:** Vivado 2025.1 includes inline HDL for certain utility IP cores, reducing IP generation time.

### Code Example
```tcl
# Check tool version in a Vivado/Vitis TCL script
# and warn if below expected minimum
set vivado_ver [version -short]
if {[package vcompare $vivado_ver "2025.1"] < 0} {
    puts "WARNING: Vivado $vivado_ver detected; 2025.1+ recommended."
    puts "         Inline HDL and AXI Switch IP require 2025.1."
}
puts "Using Vivado $vivado_ver"

# When creating a Vitis workspace in batch (Unified IDE CLI):
# xsct -eval "setws ./vitis_ws; \
#             platform create -name kv260_platform -hw ./outputs/kv260_top.xsa; \
#             platform generate"
```

### Relevance to Your Project
You are targeting Vivado/Vitis 2025.1, which is the current recommended version. The Vitis Classic → Unified IDE migration is the most likely workflow disruption: if you have `.launch` / platform project files from an older install, they will need to be recreated in the Unified IDE. The AXI BRAM Controller IP itself has no documented breaking changes in 2025.1.
