# FPGA Research Digest - 2026-07-18

## Executive Summary

- **AXI-Lite deadlock risk**: The AW (address write) and W (write data) channels are independent — a master must NOT wait for AWREADY before placing data on the W channel, or a deadlock occurs. On the KV260 AXI-BRAM demo this is the most likely silent failure mode when the PS writes to 0xA0000000/0xA0010000.
- **BRESP/RRESP must be driven**: Slaves must assert BVALID and hold it until both BVALID and BREADY are high; the response code should be 2'b00 (OKAY). Omitting this stalls the PS AXI master.
- **write_bd_tcl for reproducible builds**: Use `write_bd_tcl` (or File → Export → Export Block Design) to generate a portable TCL that recreates your block design from scratch — essential for CI/CD and teammate handoffs. Combined with `write_project_tcl -force`, you can recreate the full Vivado project programmatically.
- **KV260 PL clock must come from PS**: The PL has no independent clock source — the PS Zynq block must be configured to output a fabric clock (pl_clk0). Failing to connect this is a common cause of "design has no clock" DRC errors on bare-metal bringup.
- **Vitis Platform Project is mandatory**: On Vitis 2025.1, you must create a Platform Project (importing the XSA from Vivado) before creating the Application Project. Skipping this step means no BSP, no xil_printf UART assignment, and no linker script generation.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- **VALID must not depend on READY**: Per the AXI spec, a source must assert VALID without waiting for the recipient to assert READY. Once VALID is asserted it must stay asserted until the handshake completes (both VALID and READY high on the same rising clock edge).
- **AW and W channels are independent**: The AXI protocol does NOT require that a master wait for AWREADY before presenting write data on the W channel. Slaves that enforce this ordering can deadlock with well-formed masters. This is a documented pitfall in Xilinx's own AXI implementations (per ZipCPU analysis).
- **BVALID hold requirement**: After a write, the slave must assert BVALID and hold it asserted until BREADY is seen high. If BREADY is held low by the master, the slave must lower AWREADY/WREADY to apply backpressure rather than silently dropping the response.
- **RRESP/BRESP default to 2'b00**: For a simple BRAM slave, both response signals should be hardwired to `"00"` (OKAY). Using `"10"` (SLVERR) or `"11"` (DECERR) will cause the PS to report AXI errors visible in debug.
- **SmartConnect vs AXI Interconnect**: SmartConnect (pg247) is the recommended replacement for AXI Interconnect. A historical bug caused AXI Interconnect to assert write-enable one clock early compared to SmartConnect; if mixing IP versions, verify BRAM write behavior in simulation.

### Code Example

```vhdl
-- Minimal AXI-Lite slave write-response FSM
-- Key: BVALID is held until master asserts BREADY
process(S_AXI_ACLK)
begin
  if rising_edge(S_AXI_ACLK) then
    if S_AXI_ARESETN = '0' then
      axi_bvalid <= '0';
      axi_bresp  <= "00";
    else
      -- Set BVALID on a completed write (aw & w handshakes both done)
      if (axi_awready = '1' and S_AXI_AWVALID = '1' and
          axi_wready  = '1' and S_AXI_WVALID  = '1' and
          axi_bvalid  = '0') then
        axi_bvalid <= '1';
        axi_bresp  <= "00";   -- OKAY
      -- Clear BVALID only after master accepts the response
      elsif (S_AXI_BREADY = '1' and axi_bvalid = '1') then
        axi_bvalid <= '0';
      end if;
    end if;
  end if;
end process;
S_AXI_BVALID <= axi_bvalid;
S_AXI_BRESP  <= axi_bresp;
```

### Relevance to Your Project

Your `main.c` writes patterns to BRAM0 (0xA0000000) and BRAM2 (0xA0010000) via AXI-Lite. If the write response channel (BVALID/BREADY) is not handled correctly in the BRAM controller, the PS may hang waiting for an acknowledgement, causing silent failures that look like a UART timeout rather than an AXI issue. Always verify with an ILA or simulation trace that BVALID pulses after every write.

## Vivado Block Design / IP Integrator

### Key Findings

- **Board Awareness automates pin constraints**: When using the KV260 board file, Block Automation can automatically assign FPGA pins, configure the Zynq PS with board-specific settings (UART, DDR), and create I/O constraints — saving significant manual XDC editing.
- **Connection Automation for AXI**: After adding a BRAM Controller, clicking "Run Connection Automation" handles AXI SmartConnect insertion, clock/reset wiring, and address assignment. Use "All Automation" to ensure no connections are missed.
- **Address Editor gotcha**: The default 4K range (0x1000) assigned to each BRAM slave is usually sufficient, but if you have multiple BRAMs you must ensure the base addresses don't overlap. The editor shows conflicts with red highlighting. Your addresses (0xA0000000 and 0xA0010000) are 64KB apart — well within the safe zone for 4K slaves.
- **Regenerate Output Products**: After any IP parameter change, right-click the IP in the block design and select "Generate Output Products" to ensure synthesis netlists are up to date. Stale output products are a common source of confusing implementation errors.
- **Validate Design before generating bitstream**: Use Tools → Validate Design (or `validate_bd_design` in TCL) to catch unconnected ports, clock domain crossings, and address conflicts before running implementation.

### Code Example

```tcl
# IP Integrator connection automation via TCL (equivalent to GUI "Run Connection Automation")
# Add BRAM controller and connect to PS
create_bd_cell -type ip -vlnv xilinx.com:ip:axi_bram_ctrl:4.1 axi_bram_ctrl_0
apply_bd_automation -rule xilinx.com:bd_rule:axi4 \
  -config {Master "/zynq_ultra_ps_e_0/M_AXI_HPM0_FPD" Clk "Auto"} \
  [get_bd_intf_pins axi_bram_ctrl_0/S_AXI]

# Set address in address editor
set_property offset 0xA0000000 [get_bd_addr_segs \
  {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property range 4K [get_bd_addr_segs \
  {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]

# Validate before generating wrapper
validate_bd_design
make_wrapper -files [get_files *.bd] -top
```

### Relevance to Your Project

Your `create_bd.tcl` script builds the block design programmatically. The `apply_bd_automation` approach above mirrors what the GUI does and is the most robust way to handle SmartConnect insertion. Explicitly setting the slave address offset in TCL avoids the address being auto-assigned differently across Vivado versions, which would break your hardcoded `0xA0000000`/`0xA0010000` accesses in `main.c`.

## Vivado TCL Scripting

### Key Findings

- **Journal file is your best teacher**: Every GUI action is logged to `vivado.jou` in the project directory. Open it after performing an action in the GUI to see the exact TCL equivalent — the fastest way to learn the TCL API.
- **write_bd_tcl for block design portability**: `write_bd_tcl -force ./tcl/create_bd.tcl` exports the block design as a self-contained script. It creates all IPs, sets parameters, makes connections, and assigns addresses. Pair with `write_project_tcl` (File → Project → Write Tcl) to capture the whole project.
- **Version compatibility caveat**: Exported TCL scripts are generally version-specific. IP parameter names and default values change between releases. When upgrading from e.g. 2024.2 to 2025.1, test the script on a clean checkout and expect some `upgrade_ip` calls to be needed.
- **Non-project mode for CI**: In non-project mode (`read_vhdl`, `synth_design`, `opt_design`, etc.) there is no `.xpr` — compilation lives in memory. Use `write_checkpoint` to save state between stages. This is ideal for server/CI builds where disk space or GUI access is unavailable.
- **Batch mode invocation**: `vivado -mode batch -source script.tcl` runs headlessly. Exit code reflects success/failure. Redirect stdout/stderr for CI log capture: `vivado -mode batch -source build.tcl 2>&1 | tee build.log`.

### Code Example

```tcl
# Non-project mode synthesis + implementation skeleton
# Run with: vivado -mode batch -source build.tcl

# Read sources
read_vhdl -library work [glob ./vhdl/*.vhd]
read_xdc ./constraints/timing.xdc

# Synthesize
synth_design -top kv260_top -part xck26-sfvc784-2LV-c
write_checkpoint -force ./checkpoints/post_synth.dcp

# Implement
opt_design
place_design
route_design
write_checkpoint -force ./checkpoints/post_route.dcp

# Reports
report_timing_summary -file ./reports/timing.rpt
report_utilization   -file ./reports/utilization.rpt

# Bitstream
write_bitstream -force ./output/kv260_top.bit
```

### Relevance to Your Project

Your project already has a `create_bd.tcl` — the natural next step is a wrapper `build.tcl` that calls `create_bd.tcl`, generates the wrapper, runs synthesis and implementation, and exports the XSA, all in one `vivado -mode batch` invocation. This enables fully reproducible builds from a clean git clone with zero GUI interaction.

## Vitis Bare-Metal / Standalone

### Key Findings

- **Platform Project must be created first**: Vitis 2025.1 requires importing the XSA (exported from Vivado via File → Export → Export Hardware) as a Platform Project before creating an Application Project. The Platform generates the BSP, linker script, and hardware abstraction layer.
- **stdout/stdin must match your UART**: In the BSP settings, `stdin` and `stdout` must point to the UART peripheral connected to your USB-UART bridge. On the KV260, this is typically `psu_uart_1`. Incorrect assignment results in `xil_printf` producing no output even though the application runs successfully.
- **xil_printf vs printf**: `xil_printf` is a lightweight, format-limited alternative that avoids pulling in `newlib`. It does not support floating-point format specifiers (`%f`, `%e`) by default. Use `printf` (with floating-point support enabled in BSP settings) only if needed, as it significantly increases code size.
- **Linker script OCM addresses**: The OCM (On-Chip Memory) base address in the default linker script may be incorrect for the ZU+ variant used on the K26. Verify `OCM_RAM_0_baseaddr` in the generated linker script against the actual hardware address map (typically `0xFFFC0000` for 256KB OCM). Mismatches cause hard-to-debug crashes at startup.
- **Match Vivado and Vitis versions exactly**: Use Vivado 2025.1 with Vitis 2025.1. Mixing major versions (e.g. XSA from 2024.2 imported into Vitis 2025.1) is unsupported and causes BSP generation failures.

### Code Example

```c
/* Minimal bare-metal AXI-Lite read/write pattern for Vitis standalone BSP */
#include "xil_printf.h"
#include "xil_io.h"

#define BRAM0_BASE  0xA0000000U
#define BRAM2_BASE  0xA0010000U
#define TEST_PATTERN 0xDEADBEEFU

int main(void) {
    xil_printf("AXI-BRAM test start\r\n");

    /* Write test pattern */
    Xil_Out32(BRAM0_BASE, TEST_PATTERN);
    Xil_Out32(BRAM2_BASE, ~TEST_PATTERN);

    /* Mandatory data memory barrier before read-back */
    Xil_DCacheFlush();

    /* Read back and verify */
    u32 rd0 = Xil_In32(BRAM0_BASE);
    u32 rd2 = Xil_In32(BRAM2_BASE);

    if (rd0 == TEST_PATTERN && rd2 == ~TEST_PATTERN)
        xil_printf("PASS: BRAM0=0x%08X BRAM2=0x%08X\r\n", rd0, rd2);
    else
        xil_printf("FAIL: BRAM0=0x%08X (exp 0x%08X), BRAM2=0x%08X (exp 0x%08X)\r\n",
                   rd0, TEST_PATTERN, rd2, ~TEST_PATTERN);
    return 0;
}
```

### Relevance to Your Project

`Xil_Out32`/`Xil_In32` are the correct bare-metal accessors for memory-mapped AXI peripherals — they compile to single `str`/`ldr` instructions on Cortex-A53. The `Xil_DCacheFlush()` call is critical: without it, a subsequent `Xil_In32` may return a cached value from before the write, giving a false PASS. If your current `main.c` is seeing intermittent failures, this is the first thing to check.

## XDC Timing Constraints

### Key Findings

- **KV260 PL has no independent clock**: The PL fabric must receive its clock from the PS (via `pl_clk0` through `pl_clk3` outputs of the Zynq UltraScale+ block). There is no user-accessible oscillator directly driving PL clock pins on the K26 SOM. This must be enabled in the Zynq PS IP configuration under "Clock Configuration → PL Fabric Clocks".
- **Primary clock constraint is automatic for PS clocks**: When using `pl_clk0` from the PS block, Vivado automatically creates a clock constraint for it. Do NOT add a redundant `create_clock` on this net — it will create a second clock object and cause conflicting constraint warnings.
- **set_input_delay / set_output_delay for external I/O**: These constraints define the external board-level timing budget for I/O pins relative to a clock. For AXI-BRAM designs with no external I/O (purely internal PS-PL fabric paths), these constraints are not needed.
- **set_clock_groups for asynchronous domains**: If you later add a second clock domain (e.g., a video clock from an external pin), use `set_clock_groups -asynchronous -group {clk_a} -group {clk_b}` to tell the timing engine not to analyze cross-domain paths. Do NOT use `set_false_path` as a blanket CDC workaround — it hides real timing problems.
- **KV260 XDC file**: The board XDC (`kv260_cc_master.xdc`) contains pad-to-signal mappings for the carrier card connectors. Load it via `read_xdc` in TCL or add via the Vivado GUI source manager.

### Code Example

```xdc
# KV260 minimal XDC for AXI-BRAM bare-metal project
# PS provides pl_clk0 — DO NOT add create_clock here for PS-sourced clocks
# Vivado infers the clock from the Zynq PS IP automatically

# Example: constrain an optional external differential clock on PMOD (if used)
# create_clock -period 10.000 -name sys_clk [get_ports sys_clk_p]

# False path for PS-to-PL reset synchronizer crossing (reset is async by design)
set_false_path -from [get_pins {zynq_ultra_ps_e_0/pl_resetn0}] \
               -to   [get_pins {reset_sync_reg/D}]

# If you add a second async clock domain later:
# set_clock_groups -asynchronous \
#   -group [get_clocks -of_objects [get_pins zynq_ultra_ps_e_0/pl_clk0]] \
#   -group [get_clocks ext_clk]
```

### Relevance to Your Project

For a purely internal PS-PL AXI-BRAM design on KV260, your XDC file's main job is confirming the PS fabric clock is the timing reference. The most important constraint to add is the `set_false_path` on the reset synchronizer path (the PS `pl_resetn0` is asynchronous to the PL clock domain by definition). Without it, Vivado may flag a false timing violation on the reset path.

## Kria KV260 / K26 SoM Platform Specifics

### Key Findings

- **No preloaded firmware**: K26 SOM ships with blank QSPI and eMMC. For bare-metal development, JTAG boot is the standard flow — download the bitstream and ELF directly via JTAG without writing to non-volatile storage.
- **Boot mode selection via MODE[3:0]**: The boot mode is set by the `MODE[3:0]` pins on the carrier card. For JTAG-only boot (typical during development): `MODE[3:0] = 0000`. For QSPI boot: consult UG1091 (Carrier Card Design Guide) for the correct encoding.
- **MIO/EMIO connectivity via SOM240 connector**: The SOM240_1 connector provides two MIO banks (MIO501, MIO502), HPIO bank 66, HDIO bank 45, and PS-GTR transceivers. All KV260 baseboard peripherals (UART, I2C, Ethernet, SD) connect to the K26 via these MIO/EMIO signals — no PL routing is needed for the UART console.
- **USB-UART is on MIO UART1**: The KV260 USB-UART bridge is wired to MIO UART1 (`psu_uart_1`). In Vitis BSP settings, set `stdout = psu_uart_1`. In the PS block design configuration, enable UART1 and set its I/O to MIO 36-37.
- **Power domains**: The K26 has separate VCC_PSPLL, VCC_PSINTFP, VCC_PSINTLP, and VCCO_PL power rails. The KV260 baseboard provides all of these; no special power sequencing is required for bare-metal bringup.

### Code Example

```tcl
# Vivado TCL: Configure Zynq PS for KV260 UART1 on MIO 36-37
# Set within create_bd.tcl after creating the zynq_ultra_ps_e_0 instance

set_property -dict [list \
  CONFIG.PSU__UART1__PERIPHERAL__ENABLE {1} \
  CONFIG.PSU__UART1__PERIPHERAL__IO    {MIO 36 .. 37} \
  CONFIG.PSU__UART1__BAUD_RATE         {115200} \
  CONFIG.PSU__CRL_APB__UART1_REF_CTRL__SRCSEL  {IOPLL} \
  CONFIG.PSU__CRL_APB__UART1_REF_CTRL__FREQMHZ {100} \
  CONFIG.PSU__FPGA_PL0_ENABLE          {1} \
  CONFIG.PSU__CL_APB__PL0_REF_CTRL__FREQMHZ    {100} \
] [get_bd_cells zynq_ultra_ps_e_0]
```

### Relevance to Your Project

If `xil_printf` output isn't appearing on the USB-UART, the most common causes are: (1) UART1 not enabled in the PS block, (2) MIO pins not set to 36-37, or (3) BSP stdout set to `psu_uart_0` instead of `psu_uart_1`. The TCL snippet above sets all three correctly. The PL0 fabric clock at 100 MHz is also enabled, which drives your AXI-BRAM clock domain.

## AMD/Xilinx Tool Updates — Vivado/Vitis 2025.1

### Key Findings

- **PS-first boot (Vivado 2025.1 new feature)**: Vivado now supports booting the PS first and dynamically loading the PL bitstream afterward, enabling OS bring-up without waiting for FPGA configuration. For bare-metal flows this is not directly relevant, but it simplifies hybrid Linux+bare-metal development workflows.
- **RTL-based AXI Switch IP**: A new fully customizable AXI Switch IP was introduced in 2025.1, acting as a bridge between different AXI interface types and widths. This is more flexible than the SmartConnect for designs requiring custom arbitration policies.
- **Pblock Planner (new UI tool)**: A new interactive Pblock planner allows graphical floor-planning of IP regions, useful for timing closure on larger KV260 designs. Not needed for a minimal AXI-BRAM demo but valuable as the design grows.
- **Vitis 2025.1 — no known unresolved issues for AXI-BRAM flow**: The AMD support portal confirms no open known issues for Vivado 2025.1.1 affecting AXI BRAM Controller or SmartConnect in the Zynq UltraScale+ MPSoC flow.
- **Vitis 2026.1 is current**: Note that as of July 2026, Vivado/Vitis 2026.1 is the latest release. If you are still on 2025.1, consider evaluating 2026.1 release notes for any AXI-BRAM or K26 flow improvements before a future upgrade.

### Code Example

```tcl
# Vivado 2025.1+ TCL: Upgrade all IPs in a project to current catalog versions
# Run this after opening a project created with an older Vivado version

report_ip_status -name ip_status
upgrade_ip [get_ips *] -log ip_upgrade.log
generate_target all [get_ips *]

# After upgrade, validate the block design to catch any interface changes
open_bd_design [glob ./*.srcs/sources_1/bd/*/*.bd]
validate_bd_design
save_bd_design

# Regenerate the wrapper with updated IP
make_wrapper -files [get_files [glob ./*.srcs/sources_1/bd/*/*.bd]] -top
```

### Relevance to Your Project

If you cloned `kv260-axi-bram-demo` on a machine with Vivado 2025.1 or newer and opened the project, Vivado will report IP version mismatches for the Block Memory Generator, BRAM Controller, and SmartConnect. Running `upgrade_ip` and `validate_bd_design` as above avoids manual "Upgrade Available" dialogs and ensures all output products match the installed catalog — required before synthesis will succeed cleanly.
