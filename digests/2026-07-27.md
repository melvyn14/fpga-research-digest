# FPGA Research Digest - 2026-07-27

## Executive Summary

- **AXI BRAM Controller early-write bug**: Using `AXI Interconnect` instead of `AXI SmartConnect` can cause write-enable assertion one clock cycle early, writing extra words — switch to SmartConnect in your block design to eliminate this.
- **Kria UART pitfall — xil_printf silent**: On Kria boards the BSP defaults stdout to `psu_uart_0`, but the JTAG/USB-UART port is `psu_uart_1`; your PASS/FAIL prints will be silent until the BSP is corrected.
- **Vivado 2025 AXI address-width regression**: AXI full peripherals are reported to decode only 10 address bits (1 KB usable space) in Vivado 2025.x; verify your BRAM ranges are within this window or apply the parameter workaround.
- **XDC clock for bare-metal AXI**: You must add a `create_clock` constraint targeting the PS-sourced `pl_clk0` net; without it Vivado cannot derive AXI path timing and implementation timing closure is unreliable.
- **Non-project-mode TCL portability**: Block design TCL scripts exported by Vivado are version-specific; pinning the Vivado version in CI and regenerating the script on upgrade is the only safe strategy.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- AXI handshake rule: once `VALID` is asserted by an initiator it **must not be de-asserted** until `READY` is received. Violating this causes protocol deadlocks that are difficult to debug without an ILA or AXI VIP.
- `READY` may be withheld indefinitely by the slave; do not assume a fixed latency in bare-metal polling loops.
- **AXI SmartConnect vs AXI Interconnect**: Community reports confirm that using the older `AXI Interconnect` IP causes the BRAM Controller's write-enable to assert one clock early, writing N+1 words instead of N. `AXI SmartConnect` does not exhibit this behavior. Always prefer SmartConnect for new designs.
- Write response channel (B channel) must be consumed — if `BREADY` is never asserted, the slave stalls. Many bare-metal drivers assert `BREADY` permanently; confirm yours does the same.
- AXI-Lite has no burst support; each transaction is a single beat. For the KV260 BRAM demo the throughput ceiling is one 32-bit word per ~10 ns at 100 MHz — sufficient for register-map style access.

### Code Example

```c
/* Bare-metal AXI-Lite write with explicit B-channel drain */
#define AXI_WRITE(base, offset, val) \
    do { \
        Xil_Out32((base) + (offset), (val)); \
        /* Drain write response — Xil_Out32 handles AW+W channels;
           standalone BSP keeps BREADY permanently asserted */ \
        dsb(); \
    } while (0)

/* Read-back verify pattern */
uint32_t readback = Xil_In32(XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR + 0x00);
if (readback != expected) {
    xil_printf("FAIL: got 0x%08X expected 0x%08X\r\n", readback, expected);
}
```

### Relevance to Your Project

Your `main.c` pattern-writes to BRAM0 (`0xA0000000`) and BRAM2 (`0xA0010000`) and reads back for PASS/FAIL. The `dsb()` (data synchronisation barrier) is critical on Cortex-A53 between the write and the read-back to prevent the store buffer from masking a true AXI fault. Confirm `Xil_Out32` / `Xil_In32` issue full AXI transactions and are not cached by the MMU — for bare-metal, ensure the BRAM address regions are marked as Device memory (strongly-ordered) in the MMU table.

## Vivado Block Design / IP Integrator

### Key Findings

- **Run Connection Automation** auto-inserts an `AXI Interconnect` or `AXI SmartConnect` and a `Proc System Reset` between the Zynq PS master and your AXI slaves. In Vivado 2021.1+ the dialog prefers SmartConnect — verify this in your `create_bd.tcl`.
- **Address Editor**: after adding BRAM Controllers, you must assign non-overlapping base addresses. Vivado can auto-assign with `assign_bd_address` in TCL. For two BRAMs with 4 KB each, typical assignments are `0xA000_0000` (BRAM0) and `0xA001_0000` (BRAM2) — matching your project layout.
- Block Memory Generator in **BRAM Controller mode** vs **AXI BRAM Controller**: the IP Integrator flow uses `axi_bram_ctrl` connected to a `blk_mem_gen`; the controller handles AXI protocol translation. Ensure the BRAM depth matches the address range assigned in the address editor.
- After modifying IP parameters, always click **Validate Design** (F6) before generating the bitstream; silent mismatches in clock/reset connectivity will fail at implementation otherwise.

### Code Example

```tcl
# In create_bd.tcl — assign addresses after creating BRAM controllers
assign_bd_address [get_bd_addr_segs {axi_bram_ctrl_0/S_AXI/Mem0}] \
    -offset 0xA0000000 -range 4K
assign_bd_address [get_bd_addr_segs {axi_bram_ctrl_1/S_AXI/Mem0}] \
    -offset 0xA0010000 -range 4K

# Validate and save
validate_bd_design
save_bd_design
```

### Relevance to Your Project

Your two BRAM controllers at `0xA0000000` and `0xA0010000` need exactly these assignments in the address editor. If you ever regenerate the block design from TCL, the `assign_bd_address` calls must come **after** `connect_bd_intf_net` calls for the AXI interfaces, or the segment won't exist yet and the command will silently fail.

## Vivado TCL Scripting

### Key Findings

- **Non-project mode** (`vivado -mode batch -source script.tcl`) reads sources and runs implementation entirely in-memory — no `.xpr` file. It's the cleanest approach for CI/CD but requires you to manage checkpoints manually with `write_checkpoint`.
- **Export block design as TCL**: In the GUI, use `File → Export → Export Block Design` to generate a `.tcl` that reproduces the IP Integrator canvas. This script is **Vivado version-specific** — IP versions are embedded and will fail on a different tool release.
- **IP Integrator in non-project mode** (UG994, 2025.1): you must call `create_bd_design` before any `create_bd_cell` calls, and call `generate_target all` after `validate_bd_design` to produce the synthesis netlist.
- Use `set_param ips.includeClockLocationConstraints true` before out-of-context IP synthesis to ensure correct hold-timing closure with HD.CLK_SRC properties.
- `exec` is preferred over `catch {exec ...}` for calling external programs from TCL — it raises a Tcl error on non-zero exit codes, enabling proper CI failure propagation.

### Code Example

```tcl
# Non-project mode bare-minimum flow for KV260 AXI-BRAM design
set_param ips.includeClockLocationConstraints true

# Create in-memory project targeting K26 (xczu5eg-sfvc784-2-e)
create_project -in_memory -part xczu5eg-sfvc784-2-e

# Source the exported block design script
source ./tcl/create_bd.tcl

# Generate HDL wrapper
make_wrapper -files [get_files kv260_top.bd] -top
add_files -norecurse ./kv260_claude/kv260/vhdl/kv260_top_wrapper.vhd

# Add XDC constraints
add_files -fileset constrs_1 -norecurse ./kv260_claude/kv260/xdc/kv260_top.xdc

# Synthesise, implement, and write bitstream
launch_runs synth_1 impl_1 -to_step write_bitstream -jobs 4
wait_on_run impl_1

# Export XSA for Vitis
write_hw_platform -fixed -include_bit ./output/kv260_top.xsa
```

### Relevance to Your Project

Your `create_bd.tcl` is the heart of the reproducible build. Running it with `vivado -mode batch` lets you rebuild the entire design without the GUI, which is essential for remote CI (e.g. GitHub Actions runners). Pin the Vivado version in your workflow YAML to prevent silent block-design TCL breakage on tool upgrades.

## Vitis Bare-Metal / Standalone

### Key Findings

- **UART stdout assignment critical**: On Kria KV260, the BSP generator defaults `stdin`/`stdout` to `psu_uart_0` (MIO bank), but the physical JTAG/USB-UART on the carrier card connects to `psu_uart_1`. This means all `xil_printf` output is silently discarded. **Set `stdout` to `psu_uart_1` in BSP settings.**
- `xil_printf` is a lightweight formatted print with no heap dependency; prefer it over `printf` in bare-metal to avoid pulling in the full C library. It lacks `%f` (float) support.
- **Linker script memory regions**: The default standalone linker script maps `.text`, `.data`, and `.bss` to DDR. For Cortex-A53, the default DDR region starts at `0x0` and extends to physical RAM size. If your BRAM address space (`0xA000_0000`) appears in the linker script as a memory region with wrong attributes, AXI accesses may be treated as cached — force device-memory attributes instead.
- **Interrupt controller (GIC)**: the standalone BSP includes `XScuGic` for the ARM GIC-400. For a simple BRAM read/write demo, polling is sufficient, but if you later add interrupt-driven DMA, initialise the GIC before enabling any PL interrupt lines.
- BSP drivers are auto-generated from the XSA; always regenerate the BSP after updating the block design and exporting a new XSA, or the `XPAR_` address macros will be stale.

### Code Example

```c
/* BSP system.mss snippet — set in Vitis BSP settings or edit directly */
/*
  BEGIN driver
    PARAMETER DRIVER_NAME = standalone
    PARAMETER DRIVER_VER = 8.0
    PARAMETER HW_INSTANCE = psu_cortexa53_0
    PARAMETER stdin = psu_uart_1      # <-- must be uart_1 on KV260
    PARAMETER stdout = psu_uart_1     # <-- must be uart_1 on KV260
  END driver
*/

/* In main.c — initialise UART explicitly for robustness */
#include "xuartps.h"
XUartPs_Config *uart_cfg = XUartPs_LookupConfig(XPAR_XUARTPS_1_DEVICE_ID);
XUartPs uart_inst;
XUartPs_CfgInitialize(&uart_inst, uart_cfg, uart_cfg->BaseAddress);
XUartPs_SetBaudRate(&uart_inst, 115200);

xil_printf("BRAM demo starting...\r\n");
```

### Relevance to Your Project

The silent UART bug is the most likely culprit if your PASS/FAIL output never appears over USB-UART — check the BSP `system.mss` or the Vitis platform component settings and confirm `psu_uart_1` is selected for stdout on KV260.

## XDC Timing Constraints

### Key Findings

- For Zynq UltraScale+ bare-metal designs, the AXI clock originates from the PS (`pl_clk0`). Vivado **cannot auto-derive** this clock unless you declare it explicitly with `create_clock` on the output net of `zynq_ultra_ps_e_0`.
- Without the `create_clock` for `pl_clk0`, Vivado reports all AXI paths as unconstrained; timing closure is indeterminate and the design may work at low speed but fail after temperature/voltage variation.
- `set_input_delay` / `set_output_delay` are needed only if signals cross the FPGA boundary. For a pure PS→PL AXI design with no off-chip peripherals, these are not required — only the `create_clock` matters.
- `set_clock_groups -asynchronous` should be applied between any clock domains that are unrelated (e.g. a 100 MHz AXI clock and a 200 MHz DDR clock if both appear in the PL). For a single-clock BRAM design this is not needed.
- **Auto-derived clocks**: rely on Vivado's auto-derivation for all generated clocks downstream of `pl_clk0` (MMCM outputs, etc.) rather than manually declaring them — manual declarations can over-constrain and cause false failures.

### Code Example

```xdc
# kv260_top.xdc — minimum constraints for a 100 MHz AXI-Lite / BRAM design

# Declare the PS-sourced PL clock (100 MHz = 10 ns period)
# The net name matches the Zynq PS block output in the block design
create_clock -period 10.000 -name clk_pl_0 \
    [get_pins zynq_ultra_ps_e_0/inst/PS8_i/PLCLK[0]]

# If using an MMCM downstream, let Vivado auto-derive its output clocks.
# Do NOT manually create_clock on MMCM outputs — use create_generated_clock
# only if you need to rename them for set_clock_groups.

# Active-low reset is asynchronous from the PS; false-path it to avoid
# pessimistic timing on reset tree paths
set_false_path -from [get_pins zynq_ultra_ps_e_0/inst/PS8_i/PLRESET[0]]
```

### Relevance to Your Project

Your bare-metal AXI-BRAM design is single-clock (PS `pl_clk0` feeds both BRAM controllers). The XDC file needs at minimum the `create_clock` above to get a green timing report. Without it, Vivado will implement the design but the timing report will show all paths as "No clock" — a yellow/orange warning that masks real setup/hold violations.

## Kria KV260 / K26 SoM

### Key Findings

- **Boot modes**: KV260 ships with QSPI32 boot mode (factory default). For bare-metal development, use **JTAG boot** — no SD card needed, load directly via XSDB. JTAG boot avoids having to pack a BOOT.BIN each iteration.
- **XSDB bare-metal load sequence**: (1) load PMU firmware, (2) load FSBL or use `psu_init.tcl` to initialise DDR/clocks, (3) load bitstream via `fpga`, (4) load `.elf` application on `psu_cortexa53_0`.
- **MIO assignment on K26**: UARTs, I2C, QSPI, and eMMC are on MIO bank 500 (PS-side). The PL logic connects to the carrier card via the SOM connector — EMIO pins from the PS can reach the PL but are not needed for AXI-BRAM (which is purely PS→PL AXI).
- The K26 SoM part is `xczu5eg-sfvc784-2-e` (production speed grade). Always target this exact part in Vivado; using `-1` speed grade will produce overly pessimistic timing results.
- **Power domains**: The KV260 carrier supplies the SOM with multiple VCCINT rails. PL fabric powers up with the PS. No special sequencing is needed for a bare-metal AXI demo — the PL is accessible as soon as the bitstream is loaded via JTAG.

### Code Example

```tcl
# xsdb_boot.tcl — JTAG bare-metal boot for KV260
connect
targets -set -filter {name =~ "PSU"}

# Switch to JTAG boot mode and reset PS
mwr 0xff5e0200 0x0100
rst -system

# Load PMU firmware
targets -set -filter {name =~ "MicroBlaze PMU"}
dow ./pmufw.elf
con

# Initialise PS (DDR, clocks) without FSBL
targets -set -filter {name =~ "Cortex-A53 #0"}
source ./psu_init.tcl
psu_init

# Load bitstream into PL
fpga -file ./kv260_top.bit

# Load and run application
dow ./kv260_axi_bram.elf
con
```

### Relevance to Your Project

This XSDB script is the fastest inner loop for iterating on your bare-metal AXI-BRAM demo. Whenever you change `main.c` or rebuild the bitstream, this sequence reloads everything over JTAG in ~30 seconds without reprogramming QSPI. Keep `psu_init.tcl` in sync with your XSA — Vitis generates a fresh one each time you export the platform.

## AMD/Xilinx Tool Updates (2025.x)

### Key Findings

- **Vivado 2025.2** (latest as of this digest) added **SystemVerilog Interface support** in IP Integrator — AXI connections can now be expressed as SV interface bundles, with automatic wrapper creation. This simplifies custom AXI IP development for users on SV-capable flows, but VHDL projects are unaffected.
- **AXI Switch / AXI SmartConnect** gained an **ultra-low-area mode** in 2025.2, reducing LUT consumption for simple point-to-point connections — relevant if you ever expand your BRAM demo to more slaves on resource-constrained fabric.
- **NoC XPM support in block design**: Versal-targeting designs can now add RTL modules that instantiate NoC XPMs directly in IP Integrator via module referencing. Not applicable to KV260 (ZynqMP), but worth tracking for future platform migration.
- **Vivado 2025.1 known issues** (AR #000037546): IP updates sometimes go unrecognised after closing/reopening a project; workaround is to close and reopen once more, or run `upgrade_ip` in TCL. Core dumps on IP upgrade are resolved by restarting Vivado.
- **Vitis 2025.1** (UG1742, released July 8 2025): release notes cover improved BSP generation for standalone targets, Vitis Unified IDE stability fixes, and updated embedded software library versions.
- **Vivado 2026.1** release notes are already appearing on AMD docs (UG973), suggesting the tool cadence continues at roughly 6-month intervals.

### Code Example

```tcl
# Upgrade all IP cores in a project to latest version (safe to run after tool update)
# Run in Vivado TCL console or in batch mode
set ip_list [get_ips]
foreach ip $ip_list {
    set upgrade_result [upgrade_ip $ip]
    if {$upgrade_result ne ""} {
        puts "Upgraded: [get_property NAME $ip] -> $upgrade_result"
    }
}

# Re-validate after upgrading
validate_bd_design
save_bd_design

# Regenerate all targets to pick up new IP netlists
generate_target all [get_files *.bd]
```

### Relevance to Your Project

If you open your KV260 project in Vivado 2025.1 or later, run `upgrade_ip` in the TCL console before rebuilding. The AXI BRAM Controller, AXI SmartConnect, and Zynq UltraScale+ PS IPs all receive periodic updates. Skipping the upgrade leaves you on older IP with known bugs fixed in newer versions.
