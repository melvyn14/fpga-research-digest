## Executive Summary
- **AMD is replacing free/WebPACK-style Vivado access with a tiered licensing model starting Vivado 2026.1 (~June 2026)**: the free BASIC tier is being restricted to Windows-only and loses partial reconfiguration (DFX) plus full debug/xsim features; native Linux use of Vivado/Vitis will require a paid CORE tier (~$1,200-$1,800/year). If your KV260 build host is Linux and you plan to stay on free tooling, confirm the exact terms on AMD's licensing page before any 2026.1 upgrade — this is a real risk to the current 2025.1-pinned workflow's long-term cost, even though the bare-metal-only (no embedded Linux) flow may be less exposed than full PetaLinux users.
- **Xilinx's own AXI-Lite reference/demo slave template has a documented handshake bug** (checks write data without gating on `WVALID`/`WREADY`) that persisted for years — if `kv260_top.vhd` or any future hand-rolled register logic is ever derived from the "Create and Package IP" wizard template rather than pure `axi_bram_ctrl` passthrough, audit it against this known issue rather than trusting it as a reference.
- **Block Memory Generator/FIFO Generator are reportedly no longer directly instantiable standalone from the IP Catalog in 2025.1/2025.2** (steered toward block-design-integrated use only) — since `create_bd.tcl` creates BMG instances via `create_bd_cell`, this should still work fine inside a block design, but it's worth confirming the VLNV/version resolves cleanly and running `upgrade_bd_cells` if not.
- **`connect_bd_net` vs `connect_bd_intf_net` remains the most common TCL copy-paste error** for exactly this project's pattern (AXI4-Lite + BRAM_PORTA interfaces vs scalar clock/reset nets) — using the wrong one throws an explicit `[BD 5-106]`-class error immediately rather than failing silently, so it's a fast thing to grep for if `create_bd.tcl` errors during `validate_bd_design`.
- **PS-generated PL clocks (`pl_clk0`) are auto-constrained by the Zynq UltraScale+ PS IP's own generated `.xdc`** the moment "PL Fabric Clocks" is enabled in the block design — a hand-written `create_clock` on `pl_clk0` in a top-level XDC is redundant and risks a duplicate/conflicting clock definition; this project's only real board-level constraint need is the USB-UART pins themselves.

## AXI Protocol / AXI-Lite / AXI-Stream
### Key Findings
- Xilinx's own AXI-Lite reference/demo slave code (from the "Create and Package New IP" wizard) inspects write-data/`WLAST` conditions even when `!WVALID || !WREADY`, meaning a hand-rolled slave copy-pasted from that template can latch garbage or commit an un-handshaked write; this bug was reported in 2017/2018 and was still present as late as Vivado 2020.2.
- Backpressure must propagate upstream on the response channels: if the master holds `BREADY` low, a slave must deassert `AWREADY`/`WREADY` until the write response is accepted (and similarly `ARREADY` vs `RREADY`); asserting address-channel readys unconditionally every cycle works in simple direct testing but can lock up once any interconnect/SmartConnect with non-zero latency sits between the PS HPM master and the slave.
- Xilinx's AXI-Lite IPIF-based slaves are architecturally capped at ~25% throughput because they serialize to one outstanding transaction at a time; fine for a low-traffic PASS/FAIL register/BRAM-bridge use case, but a hand-rolled high-throughput AXI-Lite slave needs a skid buffer to align `AW*`/`W*` arrival since AXI-Lite gives no guarantee they land on the same cycle.
- Vivado 2025.2's IP release notes document a fix making `s_axi_awready`/`s_axi_wready`/`s_axi_arready` stay low until reset completion (`rst_busy`) deasserts — confirming earlier IP versions (including what 2025.1 ships) could glitch-assert ready signals during/just after reset, exactly the kind of race that can bite a bare-metal app issuing AXI-Lite transactions immediately after PS reset deassertion.
- The AXI BRAM Controller correctly implements WRAP-burst address generation internally, but real forum-reported cases describe "wrong address at burst transaction" with this exact IP — if this project ever moves from single-beat AXI-Lite access to AXI4 burst/DMA access into BRAM, validate the address sequence with an ILA rather than trusting it across IP version upgrades.
- A real-world AXI BRAM Controller bug report found the controller asserting BRAM write-enable one clock early and corrupting the previous address when the native BRAM-side `EN` signal wasn't tied/driven correctly — since this project uses AXI BRAM Controller + Block Memory Generator as discrete IP, double-check enable polarity/timing in simulation, not just synthesis, since this class of bug often passes timing closure while silently corrupting data.

### Code Example
```vhdl
-- Correct AXI-Lite write-channel backpressure (avoids the Xilinx-demo-IP bug
-- of accepting AWVALID/WVALID while a previous BVALID hasn't been accepted).
-- Reference for a future hand-rolled register file alongside BRAM0/BRAM2,
-- since the stock axi_bram_ctrl already implements this correctly.
process(s_axi_aclk)
begin
  if rising_edge(s_axi_aclk) then
    if s_axi_aresetn = '0' then
      s_axi_awready <= '0';
      s_axi_wready  <= '0';
      s_axi_bvalid  <= '0';
    else
      -- Only ready for a new address/data phase if no response is pending
      if s_axi_bvalid = '0' or s_axi_bready = '1' then
        s_axi_awready <= not s_axi_awready and s_axi_awvalid;
        s_axi_wready  <= not s_axi_wready  and s_axi_wvalid;
      else
        s_axi_awready <= '0';
        s_axi_wready  <= '0';
      end if;

      if s_axi_awready = '1' and s_axi_awvalid = '1' and
         s_axi_wready  = '1' and s_axi_wvalid  = '1' then
        -- commit write here (bram_we <= '1'; bram_addr <= s_axi_awaddr; ...)
        s_axi_bvalid <= '1';
      elsif s_axi_bready = '1' then
        s_axi_bvalid <= '0';
      end if;
    end if;
  end if;
end process;
```

### Relevance to Your Project
BRAM0 and BRAM2 sit entirely behind the stock `axi_bram_ctrl`, which already handles AW/W ordering and response backpressure correctly, so the demo isn't exposed to the wizard-template bug or the naive-backpressure mistake today. The real action item is the reset-race finding: if `main.c` issues its first BRAM write/read immediately after PS reset deassertion with no settle delay or readiness poll, that's the one scenario in this list actually worth testing on real hardware across a few cold boots.

## Vivado Block Design / IP Integrator
### Key Findings
- Block Memory Generator and FIFO Generator are reportedly no longer directly instantiable standalone from the IP Catalog in Vivado 2025.1/2025.2 — steered toward block-design-integrated usage only; since `create_bd.tcl` creates BMG via `create_bd_cell` inside a block design (not standalone), this should be unaffected, but worth confirming the VLNV/version resolves cleanly and that `upgrade_bd_cells` isn't silently needed.
- `validate_bd_design` only flags address/connectivity problems, it never auto-fixes them — always call it immediately after `assign_bd_address` and before `generate_target`/`make_wrapper`, since a BRAM controller's default address range (often 64K) can silently overlap between BRAM0 (`0xA0000000`) and BRAM2 (`0xA0010000`) if the range isn't explicitly tightened with `set_property range`.
- Vivado 2025.1 added two new dedicated IP Integrator canvas views, "Clocking and Reset" and "Interrupt and AXI-4 Lite," specifically for visualizing AXI-Lite connectivity across a design — useful for visually confirming both BRAM controllers' `S_AXI` are actually fanned out from the same `M_AXI_HPM0_FPD` rather than accidentally left dangling after a manual edit.
- The KV260/K26 board files are not bundled as a selectable Vivado part — XCK26-SFVC784 isn't directly supported as a raw part select, so a board-file-driven `create_bd.tcl` needs `set_param board.repoPaths` pointed at the installed board file repo plus `set_property board_part xilinx.com:kv260_som:part0:<rev>` (verify the exact revision string with `get_board_parts` for the installed 2025.1 board file package).
- `regenerate_bd_layout` is purely cosmetic redraw and performs no validation or re-synthesis — relying on it as a stand-in for `validate_bd_design` after a TCL-driven topology change (e.g. adding the second BRAM controller) is a common scripting mistake that lets a bad connection slip through undetected.

### Code Example
```tcl
# Explicit address assignment for two AXI BRAM Controllers off one HPM master.
# Avoids relying on auto-assigned ranges, which can silently overlap if the
# BRAM controller's default address range (often 64K) isn't tightened.

assign_bd_address -offset 0xA0000000 -range 64K \
  [get_bd_addr_segs {axi_bram_ctrl_0/S_AXI/Mem0}]

assign_bd_address -offset 0xA0010000 -range 64K \
  [get_bd_addr_segs {axi_bram_ctrl_2/S_AXI/Mem0}]

# Catch overlap / unassigned-segment errors before generating the wrapper.
# validate_bd_design returns non-zero and prints ERRORs to stdout on failure;
# don't just check the Tcl return value, grep the log for "ERROR:" too.
if {[catch {validate_bd_design} result]} {
    puts "ERROR: block design validation failed: $result"
    exit 1
}

# Cosmetic only -- run after validation, never as a substitute for it.
regenerate_bd_layout
```

### Relevance to Your Project
This mirrors the exact BRAM0/BRAM2 address layout in `create_bd.tcl`. The most actionable item: confirm each `axi_bram_ctrl` instance's address range is explicitly set to a tight value (e.g. 64K) via `set_property range` rather than left at an IP default, since BRAM0 at `0xA0000000` and BRAM2 at only 64KB apart at `0xA0010000` is exactly the spacing where a default-sized range would silently overlap and only `validate_bd_design` (not synthesis) would catch it.

## Vivado TCL Scripting
### Key Findings
- `connect_bd_net` is only for scalar/discrete signal pins (clocks, resets, individual GPIO bits); `connect_bd_intf_net` is required for bundled interface pins (AXI4/AXI4-Lite, BRAM_PORTA/PORTB). Using the wrong one produces an explicit `[BD 5-106] Arguments to the connect_bd_intf_net command cannot be empty`-class error rather than a silent no-op — for this project's two AXI BRAM controllers, `S_AXI` and `BRAM_PORTA` must use `connect_bd_intf_net`, while `ACLK`/`ARESETN` fan-out uses `connect_bd_net`.
- Non-project (in-memory) mode discards everything not explicitly written to disk — there's no autosave safety net like project mode, so a hand-maintained `create_bd.tcl` needs disciplined `validate_bd_design`/`save_bd_design` calls at known checkpoints rather than assuming state persists implicitly.
- Block-design TCL scripts are version-locked: a script exported via `write_bd_tcl` (or hand-written against one Vivado release) isn't guaranteed to replay cleanly on a different release — after any future toolchain bump, regenerate/re-validate via "Report IP Status" rather than assuming the existing `create_bd.tcl` still works unchanged.
- A documented AMD support case showed Vivado crashing in batch mode (but not the GUI) when calling `generate_target all` immediately after project creation without first explicitly opening the block design — the workaround is `open_bd_design -quiet [get_files <bd>.bd]` before any generate/validate call, since the GUI silently opens the BD context but headless mode does not.
- `apply_bd_automation` for the Zynq UltraScale+ PS is rule-driven and version-fragile — it silently no-ops or partially applies if cell/HPM port names (`M_AXI_HPM0_FPD`, `M_AXI_HPM1_FPD`) don't exactly match what that Vivado version's PS IP exposes, so always `validate_bd_design` immediately after automation rather than trusting it succeeded silently.

### Code Example
```tcl
# Correct intf vs net connections for an AXI BRAM Controller in non-project
# mode, plus the validate/save checkpoint discipline this project's
# create_bd.tcl should follow per BRAM instance.

set bram_ctrl [create_bd_cell -type ip -vlnv xilinx.com:ip:axi_bram_ctrl:4.1 axi_bram_ctrl_0]
set blk_mem   [create_bd_cell -type ip -vlnv xilinx.com:ip:blk_mem_gen:8.4 blk_mem_gen_0]

# Interface connections -> MUST use connect_bd_intf_net
connect_bd_intf_net [get_bd_intf_pins axi_bram_ctrl_0/BRAM_PORTA] \
                     [get_bd_intf_pins blk_mem_gen_0/BRAM_PORTA]
connect_bd_intf_net [get_bd_intf_pins zynq_ultra_ps_e_0/M_AXI_HPM0_FPD] \
                     [get_bd_intf_pins axi_bram_ctrl_0/S_AXI]

# Scalar clock/reset fan-out -> MUST use connect_bd_net (not intf_net)
connect_bd_net [get_bd_pins zynq_ultra_ps_e_0/pl_clk0] [get_bd_pins axi_bram_ctrl_0/s_axi_aclk]
connect_bd_net [get_bd_pins rst_ps_0/peripheral_aresetn] [get_bd_pins axi_bram_ctrl_0/s_axi_aresetn]

# Always validate before save in headless mode -- catches automation/connection
# mistakes that the GUI would otherwise flag interactively.
validate_bd_design
save_bd_design
```

### Relevance to Your Project
`create_bd.tcl` almost certainly already follows the intf-vs-net split correctly for both BRAM controllers given the project's working state, but this is the first thing to check if a future edit (e.g. adding a third peripheral) throws a `[BD 5-106]`-class error during a fresh non-project rebuild. The batch-mode-crash workaround (`open_bd_design -quiet` before `generate_target`) is worth keeping in mind if the script is ever extended to call `generate_target`/`make_wrapper` directly rather than stopping after `save_bd_design`.

## Vitis Bare-Metal / Standalone
### Key Findings
- Vitis 2025.1 defaults to the Unified IDE; the old Classic IDE MSS/MDD/MLD/BSP-settings.xml flow is gone, replaced by a CMake/YAML/JSON-driven flow where each platform/application component is configured through `vitis-comp.json` — expect import-XSA → create platform component (`os=standalone`, `cpu=psu_cortexa53_0`) → create application component referencing that platform, rather than the old "BSP project" step.
- There is an active 2025.1-specific bug/annoyance where "Create Platform" doesn't appear or hangs after importing a custom XSA (multiple AMD support threads plus a related Xilinx-Tutorials GitHub issue about the Unified IDE hanging at "Select Operating System and Processor"); the reported workaround is closing/reopening the workspace or re-exporting the XSA with the hardware platform left enabled, since a stale/incomplete XSA silently breaks platform creation.
- `xil_printf` supports only `%d`, `%l` (long), `%u`, `%x`, `%c`, `%s` — no floating point (`%f`) at all. PASS/FAIL/pattern-mismatch logging in `main.c` should keep formatting addresses/data as hex and avoid trying to print floats without a custom conversion routine.
- Zynq UltraScale+ uses an ARM GIC-400 (GICv2), not GICv3 — bare-metal interrupt setup on the A53 is `XScuGic_LookupConfig()` → `XScuGic_CfgInitialize()` → `XScuGic_SetPriorityTriggerType()` → `XScuGic_Connect()` → `XScuGic_Enable()`; for a simple polled BRAM read/write demo with no PL interrupts, this whole sequence can be skipped entirely, but it's needed the moment a timer or AXI interrupt controller IP is added.
- The standalone BSP's auto-generated `lscript.ld` has a documented bug class around custom memory layouts: a Xilinx support thread shows the `.vectors` section can get mis-placed at address 0 instead of the configured `CBaseVectors` address when memory IP (like an AXI BRAM controller) is mapped into the address space the linker considers for vector placement — worth manually inspecting `lscript.ld`'s `MEMORY` and vector placement after each XSA re-import rather than trusting the auto-generated layout.

### Code Example
```c
#include "xil_printf.h"
#include "xparameters.h"
#include "xil_io.h"

#define BRAM0_BASEADDR XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR /* 0xA0000000 */
#define BRAM2_BASEADDR XPAR_AXI_BRAM_CTRL_1_S_AXI_BASEADDR /* 0xA0010000 */

int test_bram_word(u32 base, u32 offset, const char *name) {
    u32 pattern = 0xDEADBEEF;
    Xil_Out32(base + offset, pattern);
    u32 readback = Xil_In32(base + offset);

    /* xil_printf has no %f -- hex/decimal/string only */
    if (readback != pattern) {
        xil_printf("%s @0x%08x: FAIL (wrote 0x%08x, read 0x%08x)\r\n",
                   name, offset, pattern, readback);
        return 1;
    }
    xil_printf("%s @0x%08x: PASS\r\n", name, offset);
    return 0;
}
```

### Relevance to Your Project
This mirrors the write/readback/PASS-FAIL idiom in `main.c` directly. Two concrete checks worth doing on real hardware: (1) inspect the generated `lscript.ld` after the current XSA import to confirm vector placement landed where expected, since BRAM0/BRAM2 sit far outside the normal OCM/DDR vector base; and (2) if the toolchain is ever bumped past 2025.1, budget time for the Classic-to-Unified-IDE migration and watch for the "Create Platform" hang when re-importing the XSA.

## XDC Timing Constraints
### Key Findings
- PS-generated PL clocks (`pl_clk0`, etc.) do not need a manual `create_clock` in the top-level XDC — once the Zynq UltraScale+ PS IP has "PL Fabric Clocks" enabled in the block design, Vivado auto-generates the clock constraint into a per-IP `.xdc` during block-design synthesis/implementation; adding a redundant `create_clock` on `pl_clk0` risks a duplicate/conflicting clock definition.
- `set_max_delay -datapath_only` is increasingly preferred over a blanket `set_false_path`/`set_clock_groups -asynchronous` for genuine CDC paths — a false path disables all analysis on that path (including hold), whereas `-datapath_only` still bounds propagation delay (commonly ~2x the faster clock period) while only relaxing the setup relationship; AMD's UG949 methodology guide flags this distinction explicitly.
- Constraint precedence matters when mixing styles: `set_clock_groups -asynchronous` supersedes `set_max_delay -datapath_only` in priority, so declaring two clocks asynchronous via `set_clock_groups` and also trying to bound the same pair with `set_max_delay` on top doesn't compose — pick one approach per clock pair.
- Tag CDC synchronizer registers with the `ASYNC_REG` attribute (a placement directive, not a timing exception) so the placer keeps the two flip-flops physically adjacent, minimizing the path length any `set_max_delay -datapath_only` constraint has to cover — omitting this is a common cause of marginal CDC timing on UltraScale+ parts.
- `set_input_delay`/`set_output_delay` describe the external device's timing window referenced to the clock edge at the FPGA pin — for an AXI-Lite/BRAM-only design with no PL-side I/O beyond the USB-UART bridge, there's no need to fabricate input/output delay constraints for internal PS-to-BRAM-controller AXI signals, since that path never leaves the fabric and is already covered by standard `create_clock`-derived setup/hold analysis.

### Code Example
```tcl
# XDC fragment for this Zynq UltraScale+ bare-metal BRAM/AXI-Lite design.
# pl_clk0 needs NO create_clock here -- it's auto-constrained by the PS IP's
# generated .xdc once "PL Fabric Clocks" is enabled in the block design.

# The USB-UART pins are the only real board-level I/O in this design --
# this is where set_input_delay/set_output_delay would actually matter.
set_property PACKAGE_PIN <uart_rx_pin> [get_ports uart_rxd]
set_property PACKAGE_PIN <uart_tx_pin> [get_ports uart_txd]
set_property IOSTANDARD LVCMOS33 [get_ports {uart_rxd uart_txd}]

# If an independent second clock domain is ever added (e.g. a debug/ILA
# clock), prefer a bounded datapath constraint over a blanket false path:
set_max_delay -datapath_only -from [get_clocks pl_clk0] -to [get_clocks dbg_clk] 4.0
set_max_delay -datapath_only -from [get_clocks dbg_clk] -to [get_clocks pl_clk0] 4.0

# Tag any hand-coded CDC synchronizer flops so placement keeps them adjacent
# (in VHDL: attribute ASYNC_REG of sync_reg : signal is "TRUE";)
```

### Relevance to Your Project
The design is purely PS-driven AXI on the single PS-generated `pl_clk0` domain feeding both BRAM controllers through `kv260_top.vhd`, so none of the CDC or board-I/O-delay guidance applies to the AXI-Lite path today — `kv260_top.vhd`'s only legitimate XDC need is the USB-UART pins. The CDC/`ASYNC_REG` guidance becomes directly relevant the moment a PL-side clock independent of `pl_clk0` (a free-running oscillator, an MMCM-derived clock for new logic) is introduced.

## Kria KV260 / K26 SoM
### Key Findings
- The K26 SOM has no split power rails between LPD and FPD — `PWRGD_LPD_M2C` and `PWRGD_FPD_M2C` are tied together on the SOM itself, and PS VCCO rails are gated by `VCCOEV_PS_M2C` driven from the carrier card; there's no way to selectively power down FPD-only or LPD-only domains the way one might on a discrete UltraScale+ design — the KV260 carrier card's power sequencing is fixed and out of the PL/PS design's control.
- JTAG boot-mode override on the Kria SOM Starter Kit is done via XSCT register writes against the live target, not a physical DIP switch — the carrier card ships fixed for QSPI32 boot by default, so switching to JTAG for bare-metal iteration is a software/JTAG operation against boot-mode registers from Vivado Hardware Manager or the XSCT console, not a hardware strap change.
- A working XSCT bring-up pattern for Zynq UltraScale+ over JTAG: `connect` → select the A53 target → `rst -processor` → `dow <app>.elf` → `con`, provided FSBL/PMUFW are already resident (e.g. booted once from QSPI then halted) — community reports flag a "Memory write error" if you skip FSBL/PMUFW bring-up and try to `dow` directly into DDR before MMU/DDR controller init has run.
- For deployed (non-JTAG-tethered) bare-metal boot, the standard path is repackaging the `.elf` into a new `BOOT.BIN` via `bootgen` alongside the existing FSBL/PMUFW, then reprogramming QSPI (the KV260's default boot device); SD-card bare-metal boot without PetaLinux is a frequently-asked but non-default configuration requiring manually building `BOOT.BIN` onto a FAT32 SD card rather than the stock Kria Linux/Ubuntu boot flow.
- The official KV260 board file pre-populates Zynq UltraScale+ PS configuration (DDR, clocking, MIO) and predefined connectivity for onboard PL IP — using it in `create_bd.tcl` instead of a fully hand-specified PS config means most DDR/MIO/clocking decisions are already locked in by the board file, and re-specifying them manually is a common source of subtle bring-up divergence/bugs.

### Code Example
```tcl
# Use the AMD-provided KV260 board file so DDR/clocking/MIO match the
# carrier card defaults instead of hand-specifying PS config from scratch.
set_property board_part xilinx.com:kv260_som:part0:1.4 [current_project]
create_bd_design "kv260_top_bd"
startgroup
create_bd_cell -type ip -vlnv xilinx.com:ip:zynq_ultra_ps_e:3.5 zynq_ultra_ps_e_0
apply_bd_automation -rule xilinx.com:bd_rule:zynq_ultra_ps_e \
    -config {apply_board_preset "1"} [get_bd_cells zynq_ultra_ps_e_0]
endgroup
```

```tcl
# xsct console - bring up a bare-metal app on Cortex-A53 #0 over JTAG once
# FSBL/PMUFW are already resident (board booted once from QSPI, then halted
# for iterative bare-metal development without a full power cycle).
connect
after 2000
targets -set -nocase -filter {name =~ "*A53*#0"}
rst -processor
dow kv260_bram_demo.elf
con
```

### Relevance to Your Project
Both BRAM0/BRAM2 feeding off a single HPM master matches the official Kria baremetal AXI-BRAM reference pattern. The most actionable items here: (1) confirm `create_bd.tcl` uses the official `kv260_som` board file/`board_part` rather than hand-specifying PS config, to avoid silently fighting carrier-card-locked DDR/MIO defaults; and (2) for fast bare-metal iteration without rebuilding `BOOT.BIN`/reflashing QSPI every time, the `rst -processor` / `dow` / `con` XSCT loop over JTAG (after one initial QSPI boot to bring up FSBL/PMUFW) is the practical fast-iteration path this project should already be using.

## AMD/Xilinx Tool Updates
### Key Findings
- Starting with Vivado 2026.1 (expected ~June 2026), AMD is replacing WebPACK-style free access with a tiered model (BASIC/CORE/PRO annual, ENTERPRISE/GOLD perpetual): the free BASIC tier is restricted to Windows only, drops partial reconfiguration (DFX), and ships a crippled debug/simulator (xsim) experience — native Linux use requires the paid CORE tier (~$1,200-$1,800/year). AMD's official social response says Linux support continues for all tiers including free BASIC, but community reporting (Tom's Hardware, Digilent forum) says the exact embedded-Linux-workflow implications are still unconfirmed; this project's pure bare-metal (no embedded Linux) flow is likely less exposed, but the licensing page should be re-checked before any 2026.1 upgrade.
- AMD PetaLinux is being phased out in favor of the Embedded Development Framework (EDF), a Yocto Project-based toolchain first released alongside Vivado 2025.1 (EDF release `25.05`); PetaLinux BSPs are on a path to end-of-life. EDF drops classic MicroBlaze support but Zynq UltraScale+ (the KV260's K26) remains supported — not an immediate concern for a bare-metal-only flow with no PetaLinux image in the loop, but worth tracking if a Linux-capable variant is ever added.
- Vivado 2025.1 introduces a new RTL-based AXI Switch IP that bridges between AXI master/slave endpoints of differing interface types and widths, and both AXI Switch and AXI SmartConnect gained a new ultra-low-area mode selectable via the `STRATEGY` parameter — not needed for the current single-HPM-master, two-BRAM layout, but useful for trimming LUT/FF usage on the K26's PL fabric if a third differently-typed peripheral is ever added.
- Vivado 2025.2 changes the AMD IP configuration file format from XML to JSON specifically to improve revision-control diffing and IP catalog load times — any hand-written TCL that greps/parses `.xci`-adjacent IP config files (rather than using proper `get_property`/`report_property` commands) should be re-checked after a future bump past 2025.1.
- Known Vitis 2025.1 issue: a GUI/build failure on RHEL83/CentOS82 caused by a library conflict via `LD_LIBRARY_PATH` (workaround: remove `${env_var:LD_LIBRARY_PATH}` from the project environment settings) — worth checking if the build host is RPM-based rather than Ubuntu/Windows.
- A new Pblock Planner lands in Vivado 2025.1 as a consolidated GUI for floorplanning/pblock creation, alongside a TCL script that auto-maps legacy "directive" syntax to new directive/subdirective names in the Advanced Flow — not needed for a design this small today, but relevant if floorplanning or strategy-directive TCL becomes necessary as the design grows.

### Code Example
```tcl
# Defensive version guard for hand-rolled build scripts, useful when
# comparing this 2025.1-pinned environment against a future toolchain bump.
set required_major_minor "2025.1"
set current_version [version -short]

if {[string compare $current_version $required_major_minor] != 0} {
    puts "WARNING: script tuned for Vivado $required_major_minor, running on $current_version"
    if {[regexp {^2025\.2} $current_version]} {
        puts "NOTE: 2025.2+ stores IP config as JSON, not XML --"
        puts "      any TCL that greps .xci/.xml IP config files may need updating."
    }
}

if {[llength [get_parts -quiet -filter {PART_NAME =~ "*xck26*"}]] == 0} {
    puts "WARNING: K26/KV260 part files not found - check installed device support"
}
```

### Relevance to Your Project
2025.1 remains current and stable for this design, and none of the 2025.1/2025.2 IP-level changes directly touch `axi_bram_ctrl` or the Zynq UltraScale+ PS block. The one item worth real attention regardless of toolchain version is the 2026.1 licensing change — even a bare-metal-only Linux-host workflow should confirm free-tier terms before upgrading past 2025.1/2025.2, since the cost/feature delta (DFX, full xsim, Linux support) is a real planning input for this project's toolchain roadmap.
