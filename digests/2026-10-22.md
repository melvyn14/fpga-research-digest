## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- **Handshake law — VALID ≠ f(READY):** AMBA spec section A3.2.1 forbids a sender from gating VALID on READY. Violating this creates deadlock that is invisible in most testbenches unless both sides assert simultaneously. This is the single most-reported AXI-Lite bug on community forums.
- **VALID must be held until accepted:** Once asserted, VALID cannot be de-asserted until the handshake completes (VALID ∧ READY = 1).
- **READY may toggle freely:** The slave/receiver can raise and lower READY at any time without violating the spec; this is legitimate backpressure.
- **Register your outputs:** A design rule of thumb: no combinational path from an incoming VALID to an outgoing READY. All I/O registered → timing closure is simpler and protocol violations become impossible.
- **AXI Register Slice IP** inserts one pipeline stage, cuts long combinational paths, and costs only one cycle of latency — use it freely on your interconnect to help timing closure.
- **AXI Protocol Checker IP** (available in Vivado IP catalog) catches spec violations in simulation without touching production logic.
- **AXI-Lite vs AXI-Stream distinction:** AXI-Lite = memory-mapped register access (control/status), low bandwidth. AXI-Stream = unidirectional data pipeline (video, DSP), no address channel. For your PS→BRAM path AXI-Lite is correct; AXI-Stream would be appropriate only for streaming data between PL blocks.

### Code Example

```vhdl
-- AXI-Lite slave read channel: VALID must not depend on ARREADY
-- BAD (deadlock risk):
-- s_axi_arready <= not s_axi_arvalid;  -- combinational from VALID

-- GOOD: registered READY, VALID held until accepted
process(clk)
begin
  if rising_edge(clk) then
    if s_axi_arvalid = '1' and s_axi_arready = '1' then
      -- handshake done: latch address
      read_addr_reg <= s_axi_araddr;
      s_axi_arready <= '0';
    elsif s_axi_arvalid = '0' then
      -- ready to accept next transaction
      s_axi_arready <= '1';
    end if;
  end if;
end process;
```

### Relevance to Your Project

Your PS accesses BRAM0 at `0xA000_0000` and BRAM2 at `0xA001_0000` over AXI-Lite. The Zynq PS AXI master is spec-compliant, but your `kv260_top.vhd` wrapper or any custom logic between the PS and BRAM controllers must follow the VALID/READY rules above. Add the AXI Protocol Checker IP in simulation to confirm your `create_bd.tcl` block design is clean before moving to hardware.

## Vivado Block Design / IP Integrator

### Key Findings

- **`write_bd_tcl`** exports a block design as a reproducible script. Only user-modified parameters are written; defaults are omitted. Add `-include_layout` to preserve GUI canvas positions.
- **Version portability:** The exported script is intended for the same Vivado release; cross-version use may fail on IP port or parameter mismatches.
- **Methodology workflow:** Build interactively first, then `write_bd_tcl` to capture; store the script in version control and use it as the canonical design source.
- **Address Editor:** The address map for your two BRAM controllers must be set explicitly. Each controller needs a unique base address (0xA000_0000, 0xA001_0000) with a matching range (e.g., 64 KB each). Mismatched ranges cause silent address aliasing.
- **Vivado 2025.1 IP Integrator new views:** "Clocking and Reset" and "Interrupt and AXI-4 Lite" dedicated views make it easier to audit clock/reset connections and AXI-Lite register maps at a glance.
- **Connection automation:** `apply_bd_automation` in TCL handles most AXI interconnect and clock routing; manually verify any automation result that touches the address editor.

### Code Example

```tcl
# Export block design to TCL from the Vivado console
write_bd_tcl -force -include_layout ./tcl/create_bd.tcl

# Recreate the block design in a new project (non-project or project mode)
source ./tcl/create_bd.tcl

# Verify address assignments after recreation
open_bd_design [get_bd_files]
assign_bd_address
validate_bd_design
```

### Relevance to Your Project

Your `create_bd.tcl` is the source of truth for the block design. If the BRAM base addresses (0xA000_0000 / 0xA001_0000) ever shift after a re-run, check that `assign_bd_address` is called before `validate_bd_design`. Use `write_bd_tcl -include_layout` after any manual edit so the script stays current.

## Vivado TCL Scripting

### Key Findings

- **Non-project mode** (no `.xpr`) is the gold standard for reproducible builds: `vivado -mode batch -source run.tcl` produces a bitstream from pure TCL without GUI state.
- **Key commands in order:** `read_vhdl`, `read_xdc`, `synth_design -top <top> -part <part>`, `write_checkpoint`, `opt_design`, `place_design`, `phys_opt_design`, `route_design`, `write_bitstream`.
- **Save DCPs at each step** with `write_checkpoint -force` — these are your incremental reuse points and allow resuming from any stage without re-running earlier steps.
- **Config strategies** via `config_flows -synth_strategy` / `-impl_strategy` apply AMD's preset directives (e.g., `AreaOptimized_high`, `Performance_ExplorePostRoutePhysOpt`).
- **For block-design-based projects:** source `create_bd.tcl`, call `generate_target all [get_files *.bd]`, then `export_ip_user_files` before synthesis so generated wrapper HDL is available.

### Code Example

```tcl
# Minimal non-project batch script for kv260 AXI-BRAM demo
set PART "xck26-sfvc784-2LV-c"   ;# K26 SoM part number

# Read sources
read_vhdl [glob ./vhdl/*.vhd]
read_xdc  [glob ./constraints/*.xdc]

# Synthesize
synth_design -top kv260_top -part $PART
write_checkpoint -force ./checkpoints/post_synth.dcp

# Implement
opt_design
place_design
phys_opt_design
route_design
write_checkpoint -force ./checkpoints/post_route.dcp

# Reports
report_timing_summary -file ./reports/timing.rpt
report_utilization   -file ./reports/utilization.rpt

# Bitstream
write_bitstream -force ./output/kv260_top.bit
```

### Relevance to Your Project

This script pattern maps directly to your repo layout (`vhdl/kv260_top.vhd`, `tcl/create_bd.tcl`). Add a `source ./tcl/create_bd.tcl` block before the `read_vhdl` calls when block-design-generated wrapper HDL is needed.

## Vitis Bare-Metal / Standalone

### Key Findings

- **Classic IDE removed in 2025.1** — if you have a pre-2025.1 workspace, it cannot be opened; you must regenerate the XSA from Vivado 2025.1 and create a new platform project in Vitis Unified IDE.
- **New methodology:** Hardware metadata now passes from Vivado to Vitis via a changed path, but existing bare-metal drivers, standalone BSP, and libraries are fully ported and unaffected at source level.
- **BSP-level access to BRAM:** `xparameters.h` (generated from XSA) provides `XPAR_AXI_BRAM_CTRL_0_BASEADDR` etc. Use `Xil_Out32` / `Xil_In32` for direct AXI-Lite word-level access without instantiating the full BRAM driver.
- **`xil_printf` UART:** Routes through the PS UART (UART1 on KV260 — not UART0). Verify the standalone BSP's `stdin`/`stdout` peripheral setting matches `psu_uart_1` in the platform configuration.
- **2025.1 additions to standalone BSP:** IAR compiler support, armcc/armclang support, and bare-metal Xen Hypervisor guest support — none of these affect a simple standalone AXI-BRAM test.
- **BRAM Standalone driver** (`xbram.h`) provides `XBram_Initialize`, `XBram_ReadReg`, `XBram_WriteReg` for ECC-enabled configurations; for simple BRAM access without ECC, direct `Xil_Out32`/`Xil_In32` calls are simpler and need no driver init.

### Code Example

```c
#include "xil_io.h"
#include "xil_printf.h"
#include "xparameters.h"

/* Base addresses from xparameters.h */
#define BRAM0_BASE  XPAR_AXI_BRAM_CTRL_0_BASEADDR   /* 0xA0000000 */
#define BRAM2_BASE  XPAR_AXI_BRAM_CTRL_1_BASEADDR   /* 0xA0010000 */

void test_bram(u32 base, const char *name) {
    u32 pattern = 0xDEADBEEF;
    Xil_Out32(base + 0x00, pattern);
    Xil_Out32(base + 0x04, ~pattern);

    u32 r0 = Xil_In32(base + 0x00);
    u32 r1 = Xil_In32(base + 0x04);

    if (r0 == pattern && r1 == ~pattern)
        xil_printf("%s: PASS (0x%08X, 0x%08X)\r\n", name, r0, r1);
    else
        xil_printf("%s: FAIL got 0x%08X, 0x%08X\r\n", name, r0, r1);
}

int main(void) {
    xil_printf("AXI-BRAM test start\r\n");
    test_bram(BRAM0_BASE, "BRAM0");
    test_bram(BRAM2_BASE, "BRAM2");
    return 0;
}
```

### Relevance to Your Project

This matches your `main.c` pattern. Ensure `XPAR_AXI_BRAM_CTRL_0_BASEADDR` aligns with your block design's address editor (0xA0000000) and `XPAR_AXI_BRAM_CTRL_1_BASEADDR` with 0xA0010000. If the macro names differ (e.g., `_CTRL_2_`), check the generated `xparameters.h` in the BSP.

## XDC Timing Constraints

### Key Findings

- **`set_input_delay`** models board-level propagation delay from an external clock edge to a data pin arriving at the FPGA. Applied to input ports: `set_input_delay -clock <clk> <ns> [get_ports <port>]`.
- **`set_output_delay`** models the timing requirement of downstream logic outside the FPGA. Output delay consumes part of any `set_max_delay` budget on the same path — watch for over-constraining.
- **`-clock_fall`** selects the falling edge as the reference for DDR interfaces; default is rising edge.
- **`-reference_pin`** ties delay to a pin/port rather than a clock net — useful for clock forwarding interfaces.
- **`set_clock_groups -asynchronous`** is the correct way to tell Vivado that two clocks (e.g., FCLK_CLK0 and a free-running oscillator) have no timing relationship; without it, Vivado may try to meet a multi-cycle path between them and over-constrain.
- **Zynq FCLK:** The PS fabric clock (FCLK_CLK0) is synthesized from PL_CLK and is fully constrained automatically by the Vivado IP Integrator when the Zynq PS IP is in the block design — you normally do not need a `create_clock` for it.
- **UG903** (Vivado Using Constraints, 2025.2 edition) is the definitive reference for constraint priority, interaction rules, and the recommended workflow.

### Code Example

```xdc
# Example XDC for KV260 AXI-BRAM demo
# FCLK_CLK0 is auto-constrained by the PS IP; add overrides only if needed.

# Constrain an external single-ended oscillator input (example only)
# create_clock -period 10.000 -name sys_clk [get_ports sys_clk_p]

# Declare the PS-derived fabric clock as a group to avoid false paths
# to any free-running PL debug clocks
set_clock_groups -asynchronous \
    -group [get_clocks -include_generated_clocks clk_pl_0] \
    -group [get_clocks -include_generated_clocks clk_dbg]

# False-path the BRAM reset synchroniser path if crossing domains
set_false_path -from [get_pins */rst_reg/C] -to [get_pins */bram_rst_reg/D]
```

### Relevance to Your Project

For your bare-metal AXI-BRAM demo the PS fabric clock is the only clock, so `create_clock` is not needed in your XDC. Add `set_clock_groups -asynchronous` only if you introduce a second clock domain. The key XDC requirement is confirming timing closure on the AXI-Lite paths between the PS and both BRAM controllers — check `report_timing_summary` for any failing WNS paths after place-and-route.

## Kria KV260 / K26 SoM

### Key Findings

- **Boot mode is hardware-fixed to QSPI32** — no DIP switches exist on the KV260 carrier or K26 SoM for changing boot mode. The carrier card electrically sets BOOT_MODE pins to QSPI32.
- **Two-stage boot:** Primary boot = QSPI flash (FSBL + U-Boot). Secondary boot = SD card (OS/application). For bare-metal, your ELF is loaded either over JTAG or packaged into a BOOT.bin written to QSPI/SD.
- **UART1, not UART0:** KV260 routes the PS UART console to UART1 (`psu_uart_1`). If `xil_printf` output is silent, check that the BSP `stdout` peripheral is set to `psu_uart_1` and the USB-UART (J4 Micro-USB) is connected.
- **JTAG boot for development:** For iterative bare-metal development (without SD/QSPI reflash), use the JTAG interface via Vitis debugger — load the ELF directly to DDR and run without touching QSPI. This is the fastest workflow for your write/readback test loop.
- **SoM variants:** `sm-k26` has eMMC; `smk-k26` (Starter Kit variant) uses QSPI-only with no eMMC. The KV260 uses the `smk-k26` variant.
- **K26 SoM MIO banks:** Bank 501 covers MIO[26:30] and MIO[38:51]; Bank 502 covers MIO[52:77]. EMIO extends PS I/O into the PL fabric. Your AXI-BRAM demo uses no EMIO — all PS-to-PL traffic goes through the AXI interconnect.
- **PL power domains:** The KV260 PL is powered by VCCINT/VCCBRAM; these come up automatically with the carrier board. No explicit PL power sequencing is needed for bare-metal demos.

### Code Example

```tcl
# Vitis TCL: load ELF over JTAG for bare-metal development iteration
# Run from Vitis TCL console or script

connect
targets -set -filter {name =~ "Cortex-A53 #0"}
rst -system
fpga -file ./output/kv260_top.bit
loadhw -hw ./hw/kv260.xsa -mem-ranges [list {0x80000000 0xbfffffff}]
configparams force-mem-access 1
source ./ps7_init.tcl; ps7_init; ps7_post_config
elf ./Debug/kv260_bram_test.elf
con
```

### Relevance to Your Project

Use JTAG-based ELF loading for all iterative development on your AXI-BRAM demo — it avoids QSPI reflashing and gives you full debug access (breakpoints, memory inspection). Ensure the BSP `stdout` is `psu_uart_1` so `xil_printf` PASS/FAIL output appears on the USB-UART terminal.

## AMD/Xilinx Tool Updates (Vivado/Vitis 2025.x)

### Key Findings

- **Vivado 2025.1 new device support:** Versal AI Edge Gen 2, Versal Prime Gen 2, Spartan UltraScale+ family added. KV260 (K26/Zynq UltraScale+ MPSoC) continues to be supported with no device-support changes.
- **New IP: RTL-based AXI Switch** — bridges AXI interfaces of different types and widths at the RTL level (not just IP Integrator level). Useful for future heterogeneous interconnect designs.
- **IP Integrator UI improvements:** Dedicated "Clocking and Reset" view and "Interrupt and AXI-4 Lite" view for faster auditing of block designs.
- **Pblock planner:** New interactive placement tool for floorplanning.
- **x86-only install:** Vivado/Vitis 2025.1 installers are x86_64 only; no ARM-native host support.
- **Single File Download being deprecated in 2025.2** — switch to the web installer or selective package installer now.
- **Vitis Classic IDE permanently removed in 2025.1** — no migration utility; recreate workspaces manually (see Vitis section above).
- **Open-source BSP 2025.1 changes:** Added IAR, armcc, armclang compiler support; added Xen Hypervisor bare-metal guest support.
- **Known install issue (community-reported, unconfirmed):** The `installer_0008_2025.1_0530_0145_strip.xz` archive reportedly fails to extract on some Linux setups; workaround is to download via the web installer instead.
