# FPGA Research Digest - 2026-11-02

## Executive Summary
- **AXI-Lite handshake rule**: VALID once asserted must remain asserted until READY completes the handshake — violating this is a common custom-slave bug that AMD's AXI Protocol Checker IP can catch in simulation.
- **BRAM address boundary**: Ensure every byte address used in C falls within the configured controller window (e.g., if axi_bram_ctrl is configured for 64 KB at 0xA0000000, addresses must stay below 0xA0010000); one off-by-one puts you outside the slave's decode range.
- **KV260 bare-metal UART**: The default KV260 board file does not enable UART — you must manually enable UART1 on MIO36/MIO37 in the Zynq UltraScale+ block to get USB-UART output from xil_printf.
- **Vivado 2025 possible AXI regression**: A Digilent forum thread reports AXI peripheral address space capped at 1 KB in Vivado 2025 on Zynq-7000; if your custom AXI IP exhibits unexpected address truncation, check that the `C_S_AXI_ADDR_WIDTH` parameter propagates correctly.
- **Vitis 2025.1 IDE change**: The classic Vitis IDE is deprecated in 2025.1; the new Unified IDE is the default. Verify your project/BSP scripts are compatible with the new flow.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings
- **VALID must stay asserted**: Once a master or slave asserts VALID on any AXI channel, it must hold VALID high until the corresponding READY is seen. Dropping VALID early is a protocol violation and can cause the remote agent to miss the transaction.
- **Dropped handshake in bridges**: A bug in an OHWR Wishbone-to-AXI-Lite bridge was traced to `wb.ack` arriving in the same cycle that `wb.stall` cleared; the "RESPONSE_READ" state was skipped, leaving the AXI-Lite handshake incomplete. The same race can occur in any custom slave that acknowledges requests before it is ready for a response.
- **BRAM read latency adds one cycle to RVALID**: For AXI-Lite reads routed through BRAM, RVALID appears one clock after the address handshake completes (BRAM registered output). Account for this in simulation and when checking read-response timing.
- **Use AXI Protocol Checker IP**: AMD ships an AXI Protocol Checker IP that flags handshake violations, out-of-order responses, and VALID/READY mismatches during simulation. Add it between the PS master port and your BRAM controller during debug.
- **AXI-Lite vs AXI4**: For simple BRAM access, AXI-Lite (no bursts, no AWLEN, AWSIZE fixed to data-bus width) is simpler and sufficient. The AXI BRAM Controller PG078 supports both AXI4 and AXI4-Lite modes.

### Code Example
```c
/* AXI-Lite write followed by read-back with explicit barriers */
#include "xil_io.h"

#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL

static inline void axi_write32(u32 addr, u32 data) {
    Xil_Out32(addr, data);
    /* dsb ensures the store completes before the next load */
    __asm volatile("dsb sy" ::: "memory");
}

static inline u32 axi_read32(u32 addr) {
    __asm volatile("dsb sy" ::: "memory");
    return Xil_In32(addr);
}

int verify_bram(u32 base, u32 pattern) {
    axi_write32(base + 0x00, pattern);
    axi_write32(base + 0x04, ~pattern);
    u32 rd0 = axi_read32(base + 0x00);
    u32 rd1 = axi_read32(base + 0x04);
    return (rd0 == pattern) && (rd1 == ~pattern);
}
```

### Relevance to Your Project
Your `main.c` writes patterns to BRAM0 (0xA0000000) and BRAM2 (0xA0010000). Using `dsb sy` memory barriers before each read ensures the Cortex-A53's store buffer is drained and the AXI write has actually completed before the read is issued — critical for correctness on an out-of-order CPU talking to a memory-mapped peripheral.

## Vivado Block Design / IP Integrator

### Key Findings
- **Auto address assignment**: IP Integrator can assign addresses for all slaves automatically via **Assign All** in the Address Editor. Addresses can also be set manually or imported from a CSV file using `assign_bd_address -import_from_file`.
- **Tcl finishing sequence**: After making connections, always run `validate_bd_design`, `regenerate_bd_layout`, and `save_bd_design` before exiting to keep the block design consistent and avoid stale connection warnings.
- **Avoid over-reliance on `apply_bd_automation`**: Community experience suggests spelling out connections explicitly in Tcl (`connect_bd_intf_net`, `connect_bd_net`) rather than relying on automation, which can wire unexpected nets if IPs have multiple compatible ports.
- **Address Editor columns**: The 2025.2 UG994 documents a **Path Property View** with columns for Master, Slave, Base Address, High Address, and Range — useful for auditing your BRAM address map in a script.
- **Export address map**: Use `assign_bd_address -export_to_file constraints/addr_map.csv` in your build TCL to snapshot the address map alongside the bitstream for reproducibility.

### Code Example
```tcl
# Explicitly assign BRAM addresses in create_bd.tcl
create_bd_addr_seg -range 0x00010000 -offset 0xA0000000 \
    [get_bd_addr_spaces ps/Data] \
    [get_bd_addr_segs axi_bram_ctrl_0/S_AXI/Mem0] SEG_bram0

create_bd_addr_seg -range 0x00010000 -offset 0xA0010000 \
    [get_bd_addr_spaces ps/Data] \
    [get_bd_addr_segs axi_bram_ctrl_1/S_AXI/Mem0] SEG_bram2

validate_bd_design
save_bd_design
```

### Relevance to Your Project
Your `create_bd.tcl` sets up two BRAM controllers at the exact offsets above. Making these assignments explicit in TCL (rather than relying on the GUI auto-assign) ensures reproducible builds and prevents the addresses from shifting between Vivado runs.

## Vivado TCL Scripting

### Key Findings
- **Non-project mode** runs the full Vivado flow (synthesis → implementation → bitstream) from a single TCL script, producing only the files you explicitly write. It reduces disk usage by avoiding project-related metadata files.
- **Manage source files manually**: In non-project mode, your script is the manifest. Keep an explicit list of VHDL/XDC sources and pass them all to `read_vhdl` / `read_xdc` before calling `synth_design`.
- **Save checkpoints (DCPs)**: Call `write_checkpoint` after synthesis and after routing to enable incremental flows and to resume after a failure without re-running everything.
- **Batch mode invocation**: Run Vivado headlessly with `vivado -mode batch -source build.tcl -notrace`; the `-notrace` flag suppresses verbose echo of every command, making log files easier to scan.
- **Non-project mode reduces memory footprint**: Skips design project files and some intermediate processes, useful when running inside CI containers with tight RAM limits.

### Code Example
```tcl
# Minimal non-project mode build for KV260 AXI-BRAM demo
set part "xck26-sfvc784-2LV-c"

read_vhdl   [glob ../vhdl/*.vhd]
read_xdc    [glob ../xdc/*.xdc]

synth_design -top kv260_top -part $part -flatten_hierarchy rebuilt
write_checkpoint -force ./checkpoints/post_synth.dcp
opt_design
place_design
route_design
write_checkpoint -force ./checkpoints/post_route.dcp
write_bitstream -force ./output/kv260_top.bit
```

### Relevance to Your Project
Your existing `create_bd.tcl` handles block design assembly. Wrapping it inside a non-project flow like the snippet above gives you a single `vivado -mode batch` command that produces a bitstream from scratch, suitable for CI or headless builds in the CCR environment.

## Vitis Bare-Metal / Standalone

### Key Findings
- **Classic IDE deprecated in 2025.1**: The classic Vitis IDE is deprecated; the Vitis Unified IDE is now the default. Update any scripted project-creation flows that use legacy `xsct` project commands.
- **xil_printf vs printf**: `xil_printf` is a lightweight, standalone-safe implementation with no floating-point support and no heap allocation. Use `printf` (which links against `newlib`) only if you explicitly configure the BSP and accept the larger binary size.
- **Linker script DDR placement**: Vitis auto-generates a linker script that can place `.data`, `.bss`, and `.stack` in the wrong memory region (e.g., in a PCIe BAR instead of DDR). Verify the generated `lscript.ld` assigns `.text` and `.data` to the correct DDR region (e.g., `ps_ddr_0` on the K26).
- **KV260 UART1 requires explicit BSP config**: The KV260 board file omits UART1 in the default PS configuration. You must add UART1 on MIO36/37 in the Zynq UltraScale+ block, then regenerate the BSP, before `xil_printf` output reaches the USB-UART bridge.
- **BSP source on GitHub**: The standalone BSP is open-source at `Xilinx/embeddedsw`; browsing it lets you understand exactly what `Xil_In32`/`Xil_Out32` do (they compile to direct memory-mapped load/store instructions on ARM).

### Code Example
```c
/* Minimal KV260 bare-metal entry point */
#include "xparameters.h"
#include "xil_printf.h"
#include "xil_io.h"

#define BRAM0_BASE  XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR
#define BRAM2_BASE  XPAR_AXI_BRAM_CTRL_1_S_AXI_BASEADDR

int main(void) {
    xil_printf("KV260 AXI-BRAM test starting\r\n");

    Xil_Out32(BRAM0_BASE, 0xDEADBEEF);
    u32 readback = Xil_In32(BRAM0_BASE);

    if (readback == 0xDEADBEEF) {
        xil_printf("BRAM0: PASS (0x%08X)\r\n", readback);
    } else {
        xil_printf("BRAM0: FAIL (got 0x%08X)\r\n", readback);
    }
    return 0;
}
```

### Relevance to Your Project
Using `XPAR_AXI_BRAM_CTRL_x_S_AXI_BASEADDR` from `xparameters.h` instead of hard-coded addresses means your software automatically tracks any address changes made in the block design without requiring manual C-code edits.

## XDC Timing Constraints

### Key Findings
- **Core constraint commands for synthesis impact**: Only `create_clock`, `create_generated_clock`, `set_input_delay`, `set_output_delay`, `set_clock_groups`, `set_false_path`, `set_max_delay`, and `set_multicycle_path` affect synthesis and implementation timing closure. All others are placement/I/O hints.
- **set_clock_groups for async domains**: Use `set_clock_groups -asynchronous -group {clk_A} -group {clk_B}` to tell the tools that two clocks are unrelated. This is needed between the PS clock (from the Zynq PS) and any PL-generated clocks.
- **set_false_path for BRAM-only designs**: If your BRAM0 and BRAM2 are purely PS-side (AXI master in the PS, BRAM controller in PL, no custom RTL with I/O pads), you may have no external I/O delays to constrain. A `set_false_path` on any board-level I/Os you don't use prevents unnecessary timing failures.
- **Constraint ordering matters**: XDC files are read in order; create_clock must appear before any constraint that references that clock object.
- **Vivado 2025.2 UG903 is current**: The valid-commands table in UG903 was updated 2025-11-20; verify your constraint syntax against that edition if you see unexpected tool warnings.

### Code Example
```tcl
# kv260_top.xdc — minimal timing constraints for PS+PL AXI-BRAM demo

# PS provides 100 MHz PL fabric clock via FCLK_CLK0
create_clock -period 10.000 -name clk_pl_0 [get_ports clk]

# If a second clock exists (e.g. FCLK_CLK1 at 200 MHz):
# create_clock -period 5.000 -name clk_pl_1 [get_ports clk_fast]
# set_clock_groups -asynchronous -group {clk_pl_0} -group {clk_pl_1}

# Loosen I/O timing for any debug GPIO (not performance-critical)
set_input_delay  -clock clk_pl_0 -max 2.0 [get_ports {gpio_in[*]}]
set_output_delay -clock clk_pl_0 -max 2.0 [get_ports {gpio_out[*]}]
```

### Relevance to Your Project
For the KV260 AXI-BRAM demo the critical timing path is entirely internal (PS AXI master → PL BRAM controller → BRAM → response back). The XDC above is minimal and correct: one `create_clock` for the PL fabric clock is sufficient for Vivado to close timing on the AXI interconnect paths.

## Kria KV260 / K26 SoM

### Key Findings
- **Default boot mode is QSPI+SD**: The K26 SoM ships configured to boot from QSPI with SD as the secondary device. For bare-metal JTAG debugging, switch the boot mode via XSDB (`targets`, `mwr 0xFF5E0200 <boot_mode>`), not by physical jumpers (there are none accessible on the KV260 carrier).
- **MIO banks**: The K26 MPSoC has three MIO banks. Bank 500 is used for SOM peripherals (QSPI, eMMC, I2C, SPI/TPM). Banks 501 and 502 route to the carrier via the board-to-board connectors and are user-configurable. All MIO banks are powered at 1.8 V by the SOM.
- **UART1 on MIO36/MIO37**: The USB-UART bridge on the KV260 carrier connects to UART1 of the MPSoC at MIO36 (TX) and MIO37 (RX). This must be explicitly enabled in the Zynq UltraScale+ PS configuration; the default board file omits it.
- **PMODs and RPi header go to PL, not MIO**: The KV260's PMOD and Raspberry Pi 40-pin headers connect to PL I/O, not to MIO/EMIO. Driving them requires VHDL/HDL output assignments in the XDC, not PS GPIO registers.
- **Board schematic note**: The KV260 base-board schematic is not public; the KR260 schematic package includes a master XDC constraints file that is a useful reference for pin mapping.

### Code Example
```tcl
# Switch KV260 to JTAG boot mode via XSDB (run from Vitis/XSCT console)
# Connect to hw_server first: connect

targets -set -filter {name =~ "APU*"}
# Read current boot mode register
set bm [mrd -force 0xFF5E0200]
puts "Current boot mode: $bm"

# Force JTAG boot mode (value 0x00000000) for next reset
mwr -force 0xFF5E0200 0x00000000
rst -system
```

### Relevance to Your Project
When iterating on the AXI-BRAM demo, switching to JTAG boot mode via the snippet above lets you load and run your bare-metal ELF over JTAG without re-flashing QSPI each time. After a successful run, restore QSPI boot mode and program the bitstream + ELF to QSPI/SD for standalone operation.

## AMD/Xilinx Tool Updates (Vivado/Vitis 2025.x)

### Key Findings
- **Vivado 2025.1 new device support**: Added Versal AI Edge Series Gen 2, Versal Prime Series Gen 2, and Spartan UltraScale+. A Unified Selective Device Installer reduces download size when only certain device families are needed.
- **Vitis 2025.1 — classic IDE deprecated**: The Vitis Unified IDE (new GUI) is the default as of 2025.1. Scripts and project-creation flows that rely on the classic IDE's XSCT API should be migrated.
- **Vivado 2025 possible AXI peripheral regression**: A Digilent forum user on a Zynq-7000 board reported that a custom AXI peripheral's address space was capped at 1 KB in Vivado 2025, with changing `C_S_AXI_ADDR_WIDTH` having no effect. This is a single report, but worth monitoring if your BRAM controllers ever show address-decode anomalies.
- **RHEL/CentOS LD_LIBRARY_PATH issue**: Vitis 2025.1 GUI projects on RHEL 8.3 / CentOS 8.2 may fail due to a library conflict; workaround is to unset `LD_LIBRARY_PATH` before launching Vitis.
- **UG903 2025.2 updated**: The Vivado timing constraints reference (UG903) was revised for 2025.2 (dated 2025-11-20). Always check the version-specific docs at docs.amd.com, as constraint command syntax and defaults do change between major versions.

### Code Example
```tcl
# Vivado 2026.1 / 2025.x non-project mode with report_dfx_summary
# (new 2025.1 feature — prints DFX partition summary to console)
open_checkpoint ./checkpoints/post_route.dcp
report_dfx_summary -file ./reports/dfx_summary.rpt

report_utilization -file ./reports/utilization.rpt
write_bitstream -force ./output/kv260_top.bit

```

### Relevance to Your Project
The `report_dfx_summary` addition in 2025.1 is irrelevant if you are not using Dynamic Function eXchange, but the pattern above (open checkpoint → report → bitstream) is useful for adding post-implementation reporting to your build TCL. If you move to the new Vitis Unified IDE, verify that the XSCT `app create` / `app build` commands still work as expected, since the unified flow changed some project-file locations.
