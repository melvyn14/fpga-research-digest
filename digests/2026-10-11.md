# FPGA Research Digest - 2026-10-11

## Executive Summary
- **AXI-Lite VALID/READY deadlock**: once VALID is asserted it must stay high until READY responds; violations are silent in simulation unless an AXI Protocol Checker IP is inserted.
- **BRAM read latency is 1 cycle by default** (PG058); if you change the latency setting in Block Memory Generator you must update your AXI BRAM Controller configuration to match.
- **KV260 PL fabric clock**: the KV260 has no standalone PL clock on the board — use `pl_clk0` from the PS block in your block design as the clock source for all PL IP.
- **AXI Switch IP in Vivado 2025.1 is RTL-only**: it cannot be dropped into IP Integrator block designs; use SmartConnect or AXI Interconnect for IPI flows.
- **PS UART on KV260 is UART1** (`xuartps`, MIO-routed); when configuring your bare-metal BSP console, select `psu_uart_1` — using UART0 produces no output.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings
- The AXI spec requires that once `TVALID`/`VALID` is asserted it remains asserted until the corresponding `READY` handshake occurs. Dropping VALID prematurely causes a deadlock that simulation may not catch without exhaustive stimulus coverage.
- Insert the **AXI Protocol Checker** IP (Vivado IP catalog) in simulation-only configurations to flag VALID/READY violations at run time rather than hunting waveforms manually.
- BRAM read data appears one cycle after the address is presented by default. If you configure the Block Memory Generator for two-cycle latency (registered output), you must change the AXI BRAM Controller's `C_S_AXI_RD_PIPELINE_STAGES` parameter accordingly.
- Use **AXI Register Slice** IP at interconnect boundaries (PS ↔ Interconnect, Interconnect ↔ BRAM Controller) to pipeline long combinatorial paths without changing protocol semantics.
- AXI-Stream: a missing `TLAST` on the final beat is the most common cause of DMA engine stalls. `TKEEP`/`TSTRB` should be asserted to all-ones on non-last beats; partial assertion is only legal on the final beat (when `TLAST` is high).

### Code Example
```vhdl
-- Minimal AXI4-Lite slave read path (skeleton)
process(S_AXI_ACLK)
begin
  if rising_edge(S_AXI_ACLK) then
    if S_AXI_ARESETN = '0' then
      axi_arready <= '0';
      axi_rvalid  <= '0';
    else
      -- Accept address only when we are ready to service it
      if S_AXI_ARVALID = '1' and axi_arready = '0' then
        axi_arready <= '1';
        axi_araddr  <= S_AXI_ARADDR;
      else
        axi_arready <= '0';
      end if;

      -- Hold RVALID until master asserts RREADY (never drop early)
      if axi_arready = '1' then
        axi_rvalid <= '1';
        axi_rdata  <= slv_reg(to_integer(unsigned(axi_araddr(ADDR_LSB+OPT_MEM_ADDR_BITS downto ADDR_LSB))));
      elsif S_AXI_RREADY = '1' then
        axi_rvalid <= '0';   -- only clear AFTER master acknowledges
      end if;
    end if;
  end if;
end process;
```

### Relevance to Your Project
Your project writes patterns to BRAM0 (`0xA0000000`) and BRAM2 (`0xA0010000`) over AXI-Lite from the Cortex-A53. The register-slice recommendation directly helps timing closure on the paths between Zynq PS, AXI Interconnect, and each BRAM Controller. The RVALID hold rule is critical for your bare-metal C driver: `Xil_In32()` relies on the controller following this rule; a buggy custom slave that drops RVALID early would return stale data without a bus error.

## Vivado Block Design / IP Integrator

### Key Findings
- **Export to Tcl**: `write_bd_tcl -force <output.tcl>` from the Tcl Console captures the entire block design as a reproducible script — commit this instead of the `.bd` binary for clean version control diffs.
- **New in Vivado 2025.1**: dedicated **Clocking and Reset**, **Interrupt**, and **AXI4-Lite** views in IP Integrator let you filter the canvas to just those connectivity concerns — useful for checking your PS clock routing and AXI address map without visual clutter.
- **Address Editor**: always explicitly assign base addresses for each AXI slave in the Address Editor tab rather than relying on `assign_bd_address` auto-assignment — auto-assignment can shift addresses between tool versions and silently break bare-metal base-address constants.
- **Connection Automation**: use `apply_bd_automation` in Tcl scripts to automatically route AXI connections and clock/reset after adding IP; it is idempotent and faster than manual port wiring.
- **Avoid `upgrade_ip [get_ips -all]`**: the `-all` flag includes sub-core IPs that get removed when a parent IP is upgraded, which orphans Tcl objects and causes errors. Use `upgrade_ip [get_ips {<explicit_list>}]` instead.

### Code Example
```tcl
# Recreate block design from Tcl (project mode)
open_project my_project/my_project.xpr
open_bd_design [get_files *.bd]

# Export the current BD to a script for version control
write_bd_tcl -force ./tcl/create_bd.tcl

# Add AXI BRAM Controller and connect to existing AXI Interconnect
create_bd_cell -type ip -vlnv xilinx.com:ip:axi_bram_ctrl:4.1 axi_bram_ctrl_0
apply_bd_automation -rule xilinx.com:bd_rule:axi4 \
  -config { Clk_master {/zynq_ultra_ps_e_0/pl_clk0} \
            Clk_slave  {Auto} \
            Master     {/zynq_ultra_ps_e_0/M_AXI_HPM0_FPD} } \
  [get_bd_intf_pins axi_bram_ctrl_0/S_AXI]

# Explicitly set and lock the base address
set_property offset 0xA0000000 [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property range  64K        [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
```

### Relevance to Your Project
Your `create_bd.tcl` script drives the entire PS–BRAM connectivity. The explicit address assignment snippet above mirrors exactly how BRAM0 at `0xA0000000` and BRAM2 at `0xA0010000` should be locked — if these are left to auto-assignment they can silently shift on a project rebuild, causing your C `#define` base addresses to become stale.

## Vivado TCL Scripting

### Key Findings
- **Batch mode invocation**: `vivado -mode batch -source create_bd.tcl -tclargs arg1 arg2` runs a script headlessly; the return value of `[lindex $argv 0]` gives the first argument so scripts stay parameterised.
- **Non-project mode flow**: `read_vhdl`, `read_xdc`, then `synth_design -part <PART> -top <top>` without a persistent project file. Fast for CI — no `.xpr` overhead. Set the part with `set_part` before synthesising.
- **Block design in non-project mode**: use `read_bd` to load the BD source; generated products must already exist (`generate_target all [get_files *.bd]` must have run in a prior project-mode step). Alternatively run the BD creation Tcl inline: `source create_bd.tcl; generate_target all [get_files *.bd]`.
- **Namespace isolation**: wrap all BD-creation procedures in a Tcl namespace (`namespace eval myproject { ... }`) to avoid collisions when the script is sourced multiple times or composed with other scripts.
- **Defensive `get_*` checks**: always guard against empty results — `[llength [get_cells foo]]` before operating on `foo`; the tool will silently pass an empty string to downstream commands otherwise.

### Code Example
```tcl
#!/usr/bin/env tclsh
# Non-project batch build: synth + impl + bitstream
# Usage: vivado -mode batch -source build_all.tcl -tclargs xck26-sfvc784-2LV-c

set PART [lindex $argv 0]

# Read sources
read_vhdl -library work [glob ./vhdl/*.vhd]
read_xdc  ./constraints/kv260_top.xdc

# Synthesize (in-memory project created automatically)
synth_design -part $PART -top kv260_top -flatten_hierarchy rebuilt

# Optimise and implement
opt_design
place_design
route_design

# Reports and bitstream
report_timing_summary -file ./reports/timing.rpt
report_utilization     -file ./reports/util.rpt
write_bitstream -force ./output/kv260_top.bit
```

### Relevance to Your Project
Your `create_bd.tcl` is already in place. Wrapping it in the batch invocation above lets CI regenerate the full bitstream without opening the GUI — useful once the PS–BRAM demo is stable and you want reproducible artifact generation from a GitHub Action.

## Vitis Bare-Metal / Standalone

### Key Findings
- **xil_printf vs printf**: `xil_printf` is a lightweight formatted-output function that ships in the standalone BSP. It does not support floating-point format specifiers (`%f`, `%e`) — use plain `printf` from `stdio.h` if floats are needed (requires enabling `stdio` in BSP settings and consumes significantly more code space).
- **BSP domain creation (Vitis unified IDE)**: `File → New Component → Platform`, select `Standalone` as OS, processor `psu_cortexa53_0`, then Build Platform. The generated `lscript.ld` in `src/` controls heap and stack.
- **Linker script heap/stack**: edit `lscript.ld` and change `_HEAP_SIZE` and `_STACK_SIZE` symbols. The Vitis-generated default stack for Cortex-A53 is typically 0x2000 (8 KB) — increase to at least 0x10000 (64 KB) if you observe stack corruption during printf-heavy tests.
- **Console UART on KV260**: the board routes `psu_uart_1` (UART1) to the USB-UART bridge. In BSP settings set `stdin`/`stdout` to `psu_uart_1`; selecting `psu_uart_0` produces no output on the USB port.
- **Platform re-import**: after a hardware export (`.xsa`) is updated in Vivado, you must right-click the Platform component in Vitis and select **Update Hardware** to regenerate BSP drivers — stale BSP headers will silently use wrong register offsets.

### Code Example
```c
#include "xil_printf.h"
#include "xparameters.h"

#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL
#define TEST_WORDS  16

static inline void bram_write32(uintptr_t base, uint32_t offset, uint32_t val) {
    *(volatile uint32_t *)(base + offset) = val;
}
static inline uint32_t bram_read32(uintptr_t base, uint32_t offset) {
    return *(volatile uint32_t *)(base + offset);
}

int main(void) {
    int pass = 1;

    /* Write pattern */
    for (uint32_t i = 0; i < TEST_WORDS; i++)
        bram_write32(BRAM0_BASE, i * 4, 0xDEAD0000 | i);

    /* Read back and verify */
    for (uint32_t i = 0; i < TEST_WORDS; i++) {
        uint32_t rd = bram_read32(BRAM0_BASE, i * 4);
        if (rd != (0xDEAD0000 | i)) {
            xil_printf("FAIL: addr=0x%08X exp=0x%08X got=0x%08X\r\n",
                       (unsigned)(BRAM0_BASE + i*4),
                       (unsigned)(0xDEAD0000 | i), (unsigned)rd);
            pass = 0;
        }
    }
    xil_printf(pass ? "BRAM0: PASS\r\n" : "BRAM0: FAIL\r\n");
    return 0;
}
```

### Relevance to Your Project
This is a direct expansion of your existing `main.c` pattern-test loop. The `volatile` qualifier on the pointer casts is essential — without it the compiler may cache the read result in a register and skip the actual memory-mapped read, giving a false PASS on a broken AXI path.

## XDC Timing Constraints

### Key Findings
- **`set_input_delay` / `set_output_delay`**: both commands model off-chip timing onto the FPGA's I/O ports. Specify both `-max` and `-min` values to cover setup and hold analysis simultaneously; omitting `-min` leaves the hold path unconstrained.
- **Clock reference**: always anchor I/O delay constraints to a named clock with `-clock <clk_name>`; using a port directly works but makes constraints harder to read and maintain.
- **Falling-edge capture**: use `-clock_fall` when data is launched or captured on the falling edge of the reference clock.
- **Interaction with `set_max_delay`**: the value in `set_input_delay` is additive to `set_max_delay` — do not double-count external delay by applying both a tight `set_max_delay` and a large `set_input_delay` on the same path.
- **AXI-only internal paths**: for AXI signals entirely inside the FPGA (PS–PL interconnect), no I/O constraints are needed — those paths are covered by Vivado's internal timing model for the PS interface.
- **`set_clock_groups -asynchronous`**: use this to declare the PL clock (`pl_clk0`) and any fabric-generated clocks as unrelated, preventing false multi-cycle paths across clock-domain crossings.

### Code Example
```tcl
# kv260_top.xdc - timing constraints for KV260 bare-metal demo

# Primary PL clock (100 MHz from PS pl_clk0)
create_clock -period 10.000 -name pl_clk0 [get_pins zynq_ultra_ps_e_0/inst/PS8_i/PLCLK[0]]

# If a secondary async clock is present (e.g. external ref), declare it unrelated
# create_clock -period 20.000 -name ext_clk [get_ports ext_clk_i]
# set_clock_groups -asynchronous -group [get_clocks pl_clk0] \
#                                -group [get_clocks ext_clk]

# Example: external UART RX input captured on rising edge of pl_clk0
# Max external delay = 3 ns before clock edge, min = 0.5 ns
set_input_delay -clock pl_clk0 -max 3.0 [get_ports uart_rxd_i]
set_input_delay -clock pl_clk0 -min 0.5 [get_ports uart_rxd_i]

# Example: GPIO output launched from pl_clk0
set_output_delay -clock pl_clk0 -max 2.5 [get_ports gpio_out_o]
set_output_delay -clock pl_clk0 -min 0.0 [get_ports gpio_out_o]
```

### Relevance to Your Project
Your `kv260_top.vhd` likely exposes few external ports (primarily the UART pins). The AXI BRAM paths are internal and don't need I/O constraints. However, declaring `pl_clk0` as the primary clock and adding `set_clock_groups -asynchronous` for any secondary clocks prevents Vivado from reporting spurious timing violations on CDC paths and keeps your timing reports clean.

## Kria KV260 / K26 SoM Platform Specifics

### Key Findings
- **No standalone PL clock**: the KV260 carrier board does not supply an independent clock to the PL fabric. You must use `pl_clk0` (or `pl_clk1–3`) from the Zynq UltraScale+ PS block. In your block design, connect every IP's clock input to `pl_clk0` and assert PL reset from `pl_resetn0`.
- **MIO-routed interfaces**: PS MIO exposes 2×USB 2.0, 2×SD/SDIO, 2×UART (UART0 on MIO10–11, UART1 on MIO36–37), 2×CAN 2.0B, 2×I2C, 2×SPI, and 4×32-bit GPIO, all at 1.8 V.
- **Boot order (bare-metal)**: the K26 SOM boots from QSPI Flash by default; for development, switch Boot Mode pins to JTAG or SD boot on the KV260 carrier to load your `.bit` + `.elf` directly from Vitis.
- **HPM0 port for PS→PL AXI**: connect your AXI Interconnect to `M_AXI_HPM0_FPD` (the high-performance master port on the FPD side). Use 32-bit data width to match AXI-Lite BRAM Controller defaults; enabling 64-bit requires controller re-configuration.
- **PL-to-PS interrupts**: route PL interrupt signals to `pl_ps_irq0[0:7]` on the PS block in IP Integrator; bare-metal interrupt handlers must be registered via `XScuGic_Connect()`.

### Code Example
```tcl
# In create_bd.tcl: configure PS for KV260 bare-metal AXI BRAM demo
set_property -dict [list \
  CONFIG.PSU__UART1__PERIPHERAL__ENABLE {1} \
  CONFIG.PSU__UART1__PERIPHERAL__IO    {MIO 36 .. 37} \
  CONFIG.PSU__FPGA_PL0_ENABLE          {1} \
  CONFIG.PSU__CRL_APB__PL0_REF_CTRL__FREQMHZ {100} \
  CONFIG.PSU__USE__M_AXI_GP0           {1} \
  CONFIG.PSU__MAXIGP0__DATA_WIDTH      {32} \
] [get_bd_cells zynq_ultra_ps_e_0]

# Connect pl_clk0 and pl_resetn0 to all PL IP
connect_bd_net [get_bd_pins zynq_ultra_ps_e_0/pl_clk0] \
               [get_bd_pins axi_bram_ctrl_0/s_axi_aclk] \
               [get_bd_pins axi_interconnect_0/ACLK]

connect_bd_net [get_bd_pins zynq_ultra_ps_e_0/pl_resetn0] \
               [get_bd_pins proc_sys_reset_0/ext_reset_in]
```

### Relevance to Your Project
The `PSU__UART1` and `PSU__MAXIGP0__DATA_WIDTH` settings directly match your project's UART-over-USB output path and AXI-Lite 32-bit data bus. If your existing `create_bd.tcl` omits `PSU__FPGA_PL0_ENABLE` or uses the wrong HPM port, AXI transactions will time out silently and you'll see all reads return `0xFFFFFFFF`.

## AMD/Xilinx Tool Updates (Vivado/Vitis 2025.1)

### Key Findings
- **New AXI Switch IP**: 2025.1 introduces an RTL-instantiable AXI Switch IP for bridging AXI interfaces of different types and widths. **Critical caveat**: it is not supported in IP Integrator block designs and does not participate in IPI Connection Automation or Address Editor propagation. Use SmartConnect for IPI flows.
- **New IP Integrator views**: dedicated **Clocking and Reset**, **Interrupt**, and **AXI4-Lite** canvas-filter views make it easier to audit connectivity in complex block designs without scrolling.
- **New device support**: Versal AI Edge Series Gen 2, Versal Prime Series Gen 2, and Spartan UltraScale+ family added in 2025.1. No changes to Zynq UltraScale+ (K26/KV260) device support.
- **Unified selective installer**: new per-device selective installer for Versal reduces download size significantly; Zynq UltraScale+ install footprint unchanged.
- **Upgrade IP caution**: avoid `upgrade_ip [get_ips -all]` — the `-all` flag includes sub-core IPs that are removed when their parent is upgraded, producing orphaned Tcl objects and non-deterministic errors. Target specific IP names instead.
- **AXI Interconnect legacy**: community reports persist that the legacy **AXI Interconnect** IP (not SmartConnect) generates bogus transactions in some data-width-conversion scenarios. For new designs always use **SmartConnect**.

### Code Example
```tcl
# Vivado 2025.1: safe IP upgrade targeting only top-level IPs
# Collect only top-level (non-sub-core) IPs in the project
set top_ips [get_ips -filter {IS_LOCKED == 0}]

# Upgrade and lock each sequentially to avoid orphan sub-core issues
foreach ip $top_ips {
  if {[llength [get_ips $ip]] > 0} {
    upgrade_ip [get_ips $ip]
    generate_target all [get_ips $ip]
  }
}

# Verify no IP is still in needs-upgrade state
foreach ip [get_ips] {
  set status [get_property UPGRADE_VERSIONS [get_ips $ip]]
  if {$status ne ""} {
    puts "WARNING: $ip still has pending upgrade to $status"
  }
}
```

### Relevance to Your Project
If you upgrade your Vivado project from 2024.x to 2025.1, run the safe upgrade snippet above rather than bulk `upgrade_ip -all`. The new IPI views are immediately useful for auditing your PS HPM0 → AXI Interconnect → BRAM Controller address routing in the new AXI4-Lite canvas filter.
