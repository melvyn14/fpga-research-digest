# FPGA Research Digest - 2026-09-08

## Executive Summary

- **AXI-Lite deadlock risk**: Requiring both `AWVALID` and `WVALID` simultaneously before asserting `AWREADY`/`WREADY` is a common fatal flaw in custom AXI-Lite slaves — your BRAM controller must handle the channels independently to avoid PS lockup.
- **Kria bare-metal boot**: The K26 SOM boots Linux from QSPI by default; bare-metal ELF images must be loaded via JTAG or by replacing the BOOT.BIN payload — understanding this is critical before any PS-to-PL AXI test.
- **apply_bd_automation TCL**: The `apply_bd_automation` command (updated in 2025.2 docs) auto-connects clocks, resets, and AXI interconnects — use it in your `create_bd.tcl` to reduce manual wiring mistakes.
- **Vivado 2025.2 SystemVerilog interfaces**: Native SV Interface support for AXI bundles simplifies port lists; if you ever migrate from VHDL records, this is the Vivado-native path.
- **AXI-Stream TLAST abort hazard**: Setting `TLAST` while the channel is stalled (`TVALID=1`, `TREADY=0`) corrupts packet framing — relevant if you later add a streaming DMA path to the KV260 design.

## 1. AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- **VALID/READY independence rule**: Once a master asserts `AXVALID`, it must hold all channel signals stable until the handshake completes (`READY` is sampled high). `VALID` **cannot** be de-asserted before `READY` goes high — violating this causes silent data corruption.
- **AWREADY/WREADY deadlock pattern**: A slave that gates `AWREADY` on `WVALID` (or vice-versa) creates a deadly embrace when a master issues the write address and write data in separate cycles. This is the #1 cause of AXI-Lite slaves that hang permanently under Zynq PS masters.
- **Reset must drive READY low**: During reset, all slave-driven READY outputs must be deasserted. A master recovering from reset mid-transfer will otherwise complete a phantom transaction.
- **AXI-Stream TLAST stall violation**: Setting `TLAST=1` on a beat while the downstream is not ready (`TREADY=0`) can cause the receiving IP to count the wrong number of beats per packet — always ensure TLAST is only "committed" when the handshake completes.
- **TKEEP sparsity restriction**: AXI DataMover does not support sparse `TKEEP` bytes in the middle of a packet; partial bytes are only valid on the TLAST beat (or first beat when DRE unaligned mode is enabled).
- **AXI Protocol Checker IP (PG101)**: The AMD AXI Protocol Checker is a free debug IP — insert it in simulation to flag rule violations automatically, far faster than manual waveform inspection.

### Code Example

```vhdl
-- AXI-Lite write channel: handle AWREADY and WREADY independently
-- Both channels must accept independently to avoid deadlock

process(S_AXI_ACLK)
begin
  if rising_edge(S_AXI_ACLK) then
    if S_AXI_ARESETN = '0' then
      axi_awready <= '0';
      axi_wready  <= '0';
    else
      -- Accept write address whenever master presents it
      if S_AXI_AWVALID = '1' and axi_awready = '0' then
        axi_awready <= '1';
        aw_addr_reg <= S_AXI_AWADDR;
      else
        axi_awready <= '0';
      end if;

      -- Accept write data independently of address channel
      if S_AXI_WVALID = '1' and axi_wready = '0' then
        axi_wready  <= '1';
        w_data_reg  <= S_AXI_WDATA;
        w_strb_reg  <= S_AXI_WSTRB;
      else
        axi_wready  <= '0';
      end if;
    end if;
  end if;
end process;

-- Commit write only when both address and data have been captured
write_enable <= aw_addr_valid and w_data_valid;
```

### Relevance to Your Project

Your `kv260_top.vhd` wraps two AXI-Lite BRAM controllers (BRAM0 @ `0xA0000000`, BRAM2 @ `0xA0010000`). If you ever write a custom slave shim, use the independent-channel pattern above. Even with the AMD BRAM controller IP, verifying that neither `AWREADY` nor `WREADY` is gated on the other channel's `VALID` in simulation prevents the most common bare-metal hang where `Xil_Out32` never returns.

## 2. Vivado Block Design / IP Integrator

### Key Findings

- **`apply_bd_automation` is your first call**: After instantiating the Zynq PS and any AXI slave IP, `apply_bd_automation -rule xilinx.com:bd_rule:axi4` auto-adds the AXI Interconnect, connects clocks/resets, and populates the address editor. Missing this step is the most common cause of "clock not connected" DRC errors.
- **Address Editor auto-assign**: After all IPs are connected, right-click the Address Editor and choose "Auto-Assign Address." For custom addresses (like your `0xA0000000` / `0xA0010000` offsets) use `assign_bd_address` + `set_property offset` in TCL to override the auto-assigned values.
- **BD_ADDR_SEG property**: Use `set_property range 64K [get_bd_addr_segs ...]` in TCL to explicitly set the slave address range — prevents accidentally too-small windows that cause AXI decode errors at run time.
- **Regenerate Layout**: Call `regenerate_bd_layout` after major IP additions to clean up the canvas. Running `validate_bd_design` before export catches connectivity/address errors before synthesis.
- **Export hardware (XSA)**: After bitstream, `write_hw_platform -fixed -force $xsa_file` (Vivado 2021+) replaces the old `export_hardware` — required for Vitis to see the PS+PL address map.

### Code Example

```tcl
# Minimal block design creation with correct AXI automation order

create_bd_design "system"

# 1. Add and configure Zynq MPSoC PS
set ps [create_bd_cell -type ip -vlnv xilinx.com:ip:zynq_ultra_ps_e:3.5 zynq_ultra_ps_e_0]
apply_bd_automation -rule xilinx.com:bd_rule:zynq_ultra_ps_e \
  -config {apply_board_preset "1"} [get_bd_cells zynq_ultra_ps_e_0]

# 2. Add AXI BRAM Controller + Block Memory Generator
set bram_ctrl [create_bd_cell -type ip -vlnv xilinx.com:ip:axi_bram_ctrl:4.1 axi_bram_ctrl_0]
set_property CONFIG.DATA_WIDTH {32} [get_bd_cells axi_bram_ctrl_0]
set_property CONFIG.SINGLE_PORT_BRAM {1} [get_bd_cells axi_bram_ctrl_0]

create_bd_cell -type ip -vlnv xilinx.com:ip:blk_mem_gen:8.4 blk_mem_gen_0
connect_bd_intf_net [get_bd_intf_pins axi_bram_ctrl_0/BRAM_PORTA] \
                    [get_bd_intf_pins blk_mem_gen_0/BRAM_PORTA]

# 3. Apply AXI automation — this adds interconnect, clock, reset
apply_bd_automation -rule xilinx.com:bd_rule:axi4 \
  -config {Master "/zynq_ultra_ps_e_0/M_AXI_HPM0_FPD" Clk "Auto"} \
  [get_bd_intf_pins axi_bram_ctrl_0/S_AXI]

# 4. Fix address to match bare-metal map
set_property offset 0xA0000000 \
  [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property range  64K \
  [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]

validate_bd_design
save_bd_design
```

### Relevance to Your Project

Your `create_bd.tcl` builds the two-BRAM block design. The pattern above mirrors what your script should do, with the key discipline of calling `apply_bd_automation` before manual connections, then using `set_property offset` to lock in the `0xA0000000` / `0xA0010000` addresses that your bare-metal `main.c` hard-codes.

## 3. Vivado TCL Scripting

### Key Findings

- **Non-project mode keeps only in-memory state**: In non-project mode (`-mode tcl`), no `.xpr` is created; you must write design checkpoints (`write_checkpoint`) and reports (`report_timing_summary`) explicitly — they are not auto-saved.
- **Batch invocation**: `vivado -mode batch -source build.tcl` runs headlessly and exits with non-zero status on any Tcl error, making it CI-friendly. Use `exit [expr {[get_msg_config -count {ERROR}] > 0}]` at the end to propagate errors.
- **`write_bitstream -force`**: Without `-force`, Vivado refuses to overwrite an existing bitstream file and the script stalls. Always include `-force` in automated flows.
- **`get_bd_cells` glob patterns**: `get_bd_cells *bram*` lets you reference IP by partial name — useful in parametrized scripts that loop over multiple BRAM instances.
- **`open_hw_manager` / `program_device`**: Can be scripted to program the device at the end of the batch flow without opening the GUI — useful for quick hardware-in-loop test loops.

### Code Example

```tcl
# Non-project mode: RTL-to-bitstream batch script skeleton
# Usage: vivado -mode batch -source build_kv260.tcl

set outputDir ./output
file mkdir $outputDir

# Read sources
read_vhdl [glob ./vhdl/*.vhd]
read_xdc  ./constraints/kv260_timing.xdc

# Synth
synth_design -top kv260_top -part xck26-sfvc784-2LV-c
write_checkpoint -force $outputDir/post_synth.dcp
report_timing_summary -file $outputDir/synth_timing.rpt

# Implement
opt_design
place_design
route_design
write_checkpoint -force $outputDir/post_route.dcp
report_timing_summary -file $outputDir/route_timing.rpt

# Bitstream
write_bitstream -force $outputDir/kv260_top.bit

# Propagate errors to shell
set errcount [llength [get_msg_config -count {ERROR}]]
if {$errcount > 0} {
    puts "ERROR: $errcount errors found — see reports above"
    exit 1
}
exit 0
```

### Relevance to Your Project

Converting your `create_bd.tcl` to a full non-project batch script lets CI/CD pipelines (GitHub Actions, Jenkins) rebuild bitstreams without a GUI license seat. The error-propagation pattern at the bottom ensures the pipeline correctly fails on synthesis or routing errors, rather than silently producing a corrupt bitstream.

## 4. Vitis Bare-Metal / Standalone

### Key Findings

- **KV260 2025.2 bare-metal guide exists**: Hackster.io published a 2025.2-specific guide for bare-metal 4K streaming on KV260, confirming the flow still works with Vitis unified IDE in the latest toolchain.
- **BSP `standalone` domain**: When creating the Vitis platform from your XSA, select the `standalone` OS (not Linux) and `psu_cortexa53_0` processor. The BSP auto-generates `xparameters.h` with all AXI peripheral base addresses from the XSA address map.
- **`xil_printf` vs `printf`**: `xil_printf` is a lightweight formatted-output function that does not pull in libc's full `printf` implementation — avoids ~50 KB of BSP bloat. It does not support `%f` (floating point); use `xil_printf("%d.%d", int_part, frac_part)` workarounds for fixed-point display.
- **`Xil_Out32` / `Xil_In32`**: These inline memory-mapped I/O macros map directly to `*(volatile uint32_t *)addr` with a data memory barrier (`dsb()`). Prefer them over raw pointer casts to ensure the compiler does not reorder AXI transactions.
- **Linker script `lscript.ld`**: Default BSP places all code+data in OCM (On-Chip Memory, 256 KB). For larger programs, edit the linker script to place `.text` in DDR (`psu_ddr_0_MEM_0`, starting at `0x00000000`).
- **Interrupt controller**: The `XScuGic` (GIC-400) driver handles all PL interrupts. Initialize with `XScuGic_CfgInitialize`, then `XScuGic_Connect` to register per-IRQ handlers. PL interrupts map to GIC SPI IDs starting at 121 (`XPAR_FABRIC_*_INTR`).

### Code Example

```c
#include "xil_printf.h"
#include "xil_io.h"
#include "xparameters.h"

#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL
#define TEST_OFFSET 0x00000000UL

/* Write a pattern and verify read-back */
static int bram_loopback_test(uintptr_t base, const char *name) {
    const uint32_t pattern = 0xDEADBEEFUL;

    Xil_Out32(base + TEST_OFFSET, pattern);
    /* dsb() is implicit inside Xil_Out32 — no explicit barrier needed */
    uint32_t readback = Xil_In32(base + TEST_OFFSET);

    if (readback == pattern) {
        xil_printf("[PASS] %s: wrote 0x%08X, read 0x%08X\r\n",
                   name, (unsigned)pattern, (unsigned)readback);
        return 0;
    } else {
        xil_printf("[FAIL] %s: wrote 0x%08X, read 0x%08X\r\n",
                   name, (unsigned)pattern, (unsigned)readback);
        return -1;
    }
}

int main(void) {
    xil_printf("KV260 AXI-BRAM test starting...\r\n");
    int rc = 0;
    rc |= bram_loopback_test(BRAM0_BASE, "BRAM0");
    rc |= bram_loopback_test(BRAM2_BASE, "BRAM2");
    xil_printf(rc == 0 ? "All tests PASSED\r\n" : "One or more tests FAILED\r\n");
    return rc;
}
```

### Relevance to Your Project

This is essentially the pattern your `main.c` implements. Key improvements to verify: (1) `Xil_Out32` not raw pointer casts (ensures memory barriers), (2) `xil_printf` not `printf` (avoids libc overhead in bare-metal), (3) base addresses match `xparameters.h` — if you hard-code `0xA0000000`, double-check it matches the XSA address map to avoid silent mismatches after block design regeneration.

## 5. XDC Timing Constraints

### Key Findings

- **Primary clock only needed for BRAM designs**: For a pure PS-to-PL AXI-BRAM design, you typically only need `create_clock` on the PL fabric clock pin (`pl_clk0`). AXI-Lite to BRAM paths are fully synchronous and do not need `set_input_delay`/`set_output_delay` unless you have external I/O.
- **`set_clock_groups -asynchronous`**: Use this to declare independent clock domains (e.g., PS `pl_clk0` and any secondary PL clock) as asynchronous, suppressing false timing paths between them. Without it, Vivado may report spurious inter-clock timing violations.
- **`set_false_path` for reset**: Asynchronous resets sourced from the PS (e.g., `pl_resetn0`) should be constrained with `set_false_path -from [get_pins .../pl_resetn0]` — the reset assertion path is not timing-critical.
- **`set_input_delay` syntax**: Requires an explicit `-clock` reference. For AXI signals entering from external pins (not applicable to PS-PL), `set_input_delay -clock [get_clocks clk_pl_0] -max 2.0 [get_ports {your_port}]`.
- **Constraint Wizard**: Vivado's Edit > Constraints Wizard interactively generates `set_input_delay`/`set_output_delay` from the timing analysis database — faster and less error-prone than manual entry for I/O-heavy designs.
- **AMD UG835 (2025.1)**: The `set_input_delay` command reference is fully documented in UG835 2025.1 — verify syntax if upgrading from an older Vivado version as parameter names occasionally shift.

### Code Example

```xdc

# does not infer it from the block design.

# Declare PS reset as a false path (asynchronous, not timing-critical)
set_false_path -from [get_pins zynq_ultra_ps_e_0/pl_resetn0]

# If a second PL clock domain exists, make it asynchronous to clk_pl_0
# set_clock_groups -asynchronous \
#   -group [get_clocks clk_pl_0] \
#   -group [get_clocks clk_pl_1]

# Input delay example for external signals (not needed for pure PS-PL designs)
# set_input_delay  -clock [get_clocks clk_pl_0] -max 2.0 [get_ports {ext_in[*]}]
# set_input_delay  -clock [get_clocks clk_pl_0] -min 0.5 [get_ports {ext_in[*]}]
# set_output_delay -clock [get_clocks clk_pl_0] -max 2.0 [get_ports {ext_out[*]}]
# set_output_delay -clock [get_clocks clk_pl_0] -min 0.5 [get_ports {ext_out[*]}]

If `report_timing_summary` shows no unconstrained paths, your XDC is sufficient. The `set_clock_groups` lines are commented stubs for future expansion (e.g., adding a second AXI clock domain).

## 6. Kria KV260 / K26 SoM Platform

### Key Findings

- **Boot lock**: The K26 SoM QSPI boot ROM is **read-only** — you cannot replace the FSBL or ATF. Bare-metal bare-ELF runs must be loaded via JTAG (`program_hw_devices` + `dow`), or packaged into a BOOT.BIN with a custom First Stage Boot Loader (FSBL) written to SD card.
- **SOM240 connector**: The PS-PL boundary crosses the SOM240_1 240-pin connector. MIO 0–25 are available on the SOM; the carrier card exposes additional IOs via EMIO through the PL. Your AXI BRAM design uses the HP0 (High Performance) AXI port — it does **not** cross MIO/EMIO, so no carrier-specific pin constraints are needed.
- **HP vs HPC AXI ports**: The K26 uses `M_AXI_HPM0_FPD` (or `M_AXI_HPM0_LPD`) for master AXI traffic to PL. HP ports support 128-bit wide bursts; AXI-Lite is typically 32-bit. The AXI Interconnect IP down-converts from 64/128-bit HP to 32-bit AXI-Lite slaves automatically.
- **USB-UART (ttyUSB1)**: On KV260, the UART used by `pl_uart` is typically `/dev/ttyUSB1` (not ttyUSB0, which is JTAG). Set terminal to **115200 8N1**. The PS UART (`psu_uart_1`) maps to MIO 36/37 by default.
- **Power domains**: The KV260 has separate PL (VCCINT/VCCAUX) and PS (VCC_PSINTFP/VCC_PSINTLP) power rails. The SOM manages sequencing; no manual rail ordering is needed in bare-metal.
- **Custom Kria Platform (XD101 2025.1)**: AMD published a 2025.1 tutorial (XD101) covering custom Kria SOM platform creation — useful when you need to build a Vitis platform from scratch rather than using the pre-built KV260 platform.

### Code Example

```tcl

### Relevance to Your Project

The `con` (continue) command in XSDB starts execution after `dow` loads the ELF — `xil_printf` output then appears on `/dev/ttyUSB1` at 115200 baud. The JTAG flow is the fastest iteration loop for your bare-metal PASS/FAIL test: change C code → rebuild ELF → `dow` + `con` in XSDB — no SD card re-flash needed.

## 7. AMD/Xilinx Tool Updates (Vivado/Vitis 2025.x)

### Key Findings

- **Vivado 2025.2 highlights**:
  - **SystemVerilog Interface support**: Native SV Interface support for AXI bundles with automatic wrapper creation — simplifies port lists for complex multi-channel AXI designs.
  - **Versal QoR improvements**: Reduced physical optimization compile time; BUFG_FABRIC replication per-SLR for high-fanout nets.
  - **New SLR crossing reports**: `report_design_analysis -slr_crossings` gives per-crossing timing summaries on multi-die devices.
  - **New device support**: Versal AI Edge Series Gen 2 (XC2VE3504/3558/3804/3858) and Versal Prime Series Gen 2 (XC2VM3558/3858).
- **Vitis 2025.2 highlights**:
  - **Enhanced DSP library**: New Cumulative Sum, Euclidean Distance, and Function Approximation functions.
  - **Enhanced TDM FIR** with Packet Switching (relevant for AXI-Stream-based signal processing pipelines).
  - **1D FFT using AIE + PL** co-design.
- **2026.1 downloads visible**: The AMD download page now lists 2026.1 tools — if you are planning long-term maintenance, check compatibility of KV260 platform targets in the next major release.
- **KV260 BIST Tutorial (2025.1)**: LogicTronix published a 2025.1-specific tutorial recreating the KV260 Built-In Self Test design in Vivado/Vitis 2025.1 — a good reference for confirming your toolchain flow against a known-good design.
- **UG835 2025.1/2025.2 TCL reference**: Updated `set_input_delay`, `apply_bd_automation`, `assign_bd_address` command pages are available at docs.amd.com — bookmark the 2025.1 version to match your installed tools.
