# FPGA Research Digest - 2026-11-10

## Executive Summary
- **AXI-Lite deadlock risk**: Both `AWVALID`/`WVALID` must be asserted together (or sequentially) before Xilinx slaves raise `AWREADY`/`WREADY` — do not wait for READY before driving VALID (Answer Record 63381). This directly affects your PS-to-BRAM write path.
- **BRAM controller throughput**: The AXI BRAM Controller (PG078) uses AXI-Lite single-beat transactions by default; burst AXI-Full mode gives significantly higher throughput if your design grows beyond read/write pattern tests.
- **BSP UART misconfiguration**: Vitis bare-metal BSPs on Kria often default stdin/stdout to `psu_uart_0` instead of `psu_uart_1` (the USB-UART path). If `xil_printf` output is silent, verify the BSP's `standalone_stdin`/`standalone_stdout` parameters match your hardware UART instance.
- **KV260 AXI clock source**: The PL has no independent clock on KV260 — the PS must supply it via `pl_clk0`. Confirm this is routed and enabled in your Zynq UltraScale+ IP block design settings.
- **Vivado 2025.1 Vitis Classic IDE deprecated**: The Vitis Unified IDE is now the default and Classic is fully deprecated; migration to the new IDE is required for 2025.1+ projects.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings
- **Valid-before-Ready rule**: The AMBA AXI spec requires that a source driving VALID must hold it asserted until the handshake completes; it must never de-assert VALID before READY arrives. Violating this causes bus lockups in the write-address or write-data channel.
- **Xilinx slave behavior (Answer Record 63381)**: Xilinx embedded AXI slaves wait for *both* `AWVALID` and `WVALID` to be simultaneously high before they assert `AWREADY`/`WREADY`. Masters that issue write-address before write-data (or vice versa) can deadlock if they then wait for READY before asserting the second channel.
- **BVALID timing**: `BVALID` on the write-response channel may only be driven high after the final write-data handshake completes — never before.
- **XPM_FIFO_AXIL (UG974 2025.2)**: Xilinx now ships a parameterized AXI-Lite FIFO macro; it runs exclusively in First-Word Fall-Through mode and is a clean building block for buffering AXI traffic.
- **Deadlock prevention at custom IP boundaries**: ZipCPU's AXI rules article summarizes: a transfer occurs *only* when both VALID and READY are high; never gate that check on additional state.

### Code Example
```c
/* Minimal AXI-Lite write from bare-metal C (Vitis, Cortex-A53)        */
/* Both AWADDR and WDATA are issued; slave latches on handshake.        */
#define BRAM0_BASE  0xA0000000UL
#define XPAR_BRAM0  BRAM0_BASE

static inline void axi_write32(uintptr_t addr, uint32_t data) {
    /* Single volatile write — the AXI interconnect handles handshaking */
    *((volatile uint32_t *)addr) = data;
    /* Issue a read-back barrier to ensure write completed              */
    __asm__ volatile("dsb sy" ::: "memory");
}

static inline uint32_t axi_read32(uintptr_t addr) {
    return *((volatile uint32_t *)addr);
}
```

### Relevance to Your Project
Your `main.c` writes patterns to BRAM0 at `0xA0000000` and BRAM2 at `0xA0010000`. The critical risk is the Cortex-A53 write buffer: without a `dsb` barrier between write and read-back, the read can return a cached value rather than the BRAM response. Add a `dsb sy` after each write in your PASS/FAIL loop.

## Vivado Block Design / IP Integrator

### Key Findings
- **Connection Automation for BRAM**: After adding both the Zynq UltraScale+ IP and the AXI BRAM Controller, clicking *Run Connection Automation* wires `M_AXI_HPM0_LPD` → AXI interconnect → `S_AXI` of the BRAM controller, sets the clock, and connects resets automatically. This is faster and less error-prone than manual wiring.
- **LPD vs. FPD master ports**: For bare-metal AXI-Lite to PL, prefer the LPD (Low-Power Domain) master port `AXI_HPM0_LPD`. The FPD ports (`HPM0_FPD`, `HPM1_FPD`) require the full-power domain to be powered and are over-provisioned for simple BRAM access.
- **Address Editor**: After adding the BRAM controller, open *Address Editor* and assign the slave's offset address (`0xA0000000`) and range (64K default). Mismatches here are a common cause of bus timeouts at runtime.
- **IP upgrade on re-open**: Vivado warns about IP version mismatches when a project is opened with a newer tool version. Run *Reports → Report IP Status* and use *Upgrade Selected* before regenerating targets.
- **Block design wrapper**: Vivado auto-generates an HDL wrapper for the block design. Right-click the `.bd` file → *Create HDL Wrapper* → *Let Vivado manage*. This wrapper must be the top-level design source for synthesis.

### Code Example
```tcl
# Vivado IP Integrator Tcl — create and connect BRAM via LPD master
create_bd_cell -type ip -vlnv xilinx.com:ip:zynq_ultra_ps_e:3.5 zynq_ultra_ps_e_0
apply_board_preset zynq_ultra_ps_e_0

create_bd_cell -type ip -vlnv xilinx.com:ip:axi_bram_ctrl:4.1 axi_bram_ctrl_0
set_property CONFIG.SINGLE_PORT_BRAM {1} [get_bd_cells axi_bram_ctrl_0]

create_bd_cell -type ip -vlnv xilinx.com:ip:blk_mem_gen:8.4 blk_mem_gen_0

# Wire BRAM controller to memory
connect_bd_intf_net [get_bd_intf_pins axi_bram_ctrl_0/BRAM_PORTA] \
                    [get_bd_intf_pins blk_mem_gen_0/BRAM_PORTA]

# Run connection automation (connects PS LPD master → BRAM ctrl)
apply_bd_automation -rule xilinx.com:bd_rule:axi4 \
  -config { Master "/zynq_ultra_ps_e_0/M_AXI_HPM0_LPD" Clk "Auto" } \
  [get_bd_intf_pins axi_bram_ctrl_0/S_AXI]

# Assign address
assign_bd_address [get_bd_addr_segs axi_bram_ctrl_0/S_AXI/Mem0]
set_property offset 0xA0000000 [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property range  64K        [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
```

### Relevance to Your Project
Your `create_bd.tcl` follows exactly this pattern. If you are adding a second BRAM (BRAM2 at `0xA0010000`), duplicate the `axi_bram_ctrl` and `blk_mem_gen` cells, run connection automation again, and assign the second offset in the Address Editor.

## Vivado TCL Scripting

### Key Findings
- **Project-mode vs. non-project mode**: Non-project mode skips the `.xpr` project file and runs entirely in-memory, which is better for CI pipelines. The tradeoff: no out-of-context (OOC) synthesis, no cross-probing, and you must manually call `generate_target` for block designs before synthesis.
- **`write_project_tcl`**: From an open Vivado project, run `write_project_tcl rebuild.tcl` to export a fully self-contained Tcl script that re-creates the project from scratch. Essential for version control.
- **`-force` on `create_project`**: Re-running a project-mode script without `-force` fails if the `.xpr` already exists. Always use `create_project -force`.
- **Batch invocation**: `vivado -mode batch -source build.tcl` is the preferred non-interactive form. Use `-tclargs` to pass runtime arguments (e.g., part number, output directory).
- **Block design upgrade in non-project mode (UG994 2025.2)**: The sequence is `create_project -in_memory` → `read_bd` → `current_bd_design` → `upgrade_ip` → `reset_target` → `generate_target` → `make_wrapper`.

### Code Example
```tcl
# Minimal non-project-mode build script for Kria KV260
# Run: vivado -mode batch -source build_np.tcl

set outputDir ./output
file mkdir $outputDir

# Part for K26 SoM
set part xck26-sfvc784-2LV-c

# Read sources
read_vhdl  [glob ./vhdl/*.vhd]
read_xdc   [glob ./xdc/*.xdc]

# Generate block design wrapper (must be pre-generated in project mode first)
read_bd    ./bd/kv260_bd/kv260_bd.bd
generate_target all [get_files ./bd/kv260_bd/kv260_bd.bd]
make_wrapper -files [get_files ./bd/kv260_bd/kv260_bd.bd] -top
read_vhdl [glob ./bd/kv260_bd/hdl/*.vhd]
set_property top kv260_bd_wrapper [current_fileset]

# Synthesize
synth_design -top kv260_bd_wrapper -part $part -directive PerformanceOptimized
write_checkpoint -force $outputDir/post_synth.dcp

# Implement
opt_design
place_design
route_design
write_checkpoint -force $outputDir/post_route.dcp

# Reports
report_timing_summary -file $outputDir/timing.rpt
report_utilization    -file $outputDir/util.rpt

# Bitstream
write_bitstream -force $outputDir/kv260_top.bit
```

### Relevance to Your Project
Your `create_bd.tcl` is a project-mode script. Add `write_project_tcl rebuild.tcl` at the end of a successful run to produce a portable re-creation script for CI. For a CI pipeline that tests BRAM connectivity, wrap the above non-project pattern and check the timing report's WNS for failures.

## Vitis Bare-Metal / Standalone

### Key Findings
- **Vitis Unified IDE is default in 2025.1**: The Classic IDE is deprecated. Projects targeting 2025.1+ must use the Unified IDE. Existing Classic projects require migration via *File → Migrate Classic to Unified*.
- **BSP UART configuration**: In the Vitis Unified IDE, navigate to the platform component → *Board Support Package* → *Standalone* settings. Confirm `standalone_stdin` and `standalone_stdout` are set to `psu_uart_1` (the USB-UART path on KV260). If set to `psu_uart_0` (the default), `xil_printf` output is silently discarded.
- **`xil_printf` limitation**: `xil_printf` does not support `%f` (floating-point). For floats, use `printf` from the newlib C library (enabled in BSP settings → *Use printf float/scanf float*), which increases code size.
- **Linker script memory regions**: The auto-generated linker script places code in DDR (`ps_ddr_0` / `psu_ddr_0`). For standalone apps that run from OCM for fast startup, manually edit the `.ld` to map `.text` to `psu_ocm_ram_0`.
- **GIC interrupt setup (Cortex-A53)**: The `XScuGic` driver (`xscugic.h`) manages the GIC-400. Call `XScuGic_Initialize`, `XScuGic_Connect`, `XScuGic_Enable`, then `Xil_ExceptionEnable()` to wire PS interrupts to A53 IRQ line.

### Code Example
```c
/* Vitis 2025.1 bare-metal: GIC interrupt setup for PL-to-PS IRQ      */
#include "xscugic.h"
#include "xil_exception.h"

#define INTC_DEVICE_ID   XPAR_SCUGIC_0_DEVICE_ID
#define PL_IRQ_ID        121   /* PL-to-PS IRQ[0] = SPI ID 121 on MPSoC */

static XScuGic IntcInstance;

static void PlIrqHandler(void *CallbackRef) {
    /* Handle PL interrupt — clear PL-side flag before returning        */
    xil_printf("PL interrupt received\r\n");
}

int setup_interrupts(void) {
    XScuGic_Config *cfg = XScuGic_LookupConfig(INTC_DEVICE_ID);
    if (!cfg) return XST_FAILURE;

    XScuGic_CfgInitialize(&IntcInstance, cfg, cfg->CpuBaseAddress);
    Xil_ExceptionInit();
    Xil_ExceptionRegisterHandler(XIL_EXCEPTION_ID_INT,
        (Xil_ExceptionHandler)XScuGic_InterruptHandler, &IntcInstance);
    Xil_ExceptionEnable();

    XScuGic_Connect(&IntcInstance, PL_IRQ_ID,
        (Xil_InterruptHandler)PlIrqHandler, NULL);
    XScuGic_SetPriorityTriggerType(&IntcInstance, PL_IRQ_ID, 0xA0, 0x3);
    XScuGic_Enable(&IntcInstance, PL_IRQ_ID);
    return XST_SUCCESS;
}
```

### Relevance to Your Project
Your current demo polls BRAM read-back for PASS/FAIL over `xil_printf`. Verify `psu_uart_1` is set in the BSP before debugging silent output. If you later add a DMA or interrupt-driven data path, the GIC setup above is the starting point.

## XDC Timing Constraints

### Key Findings
- **Always constrain I/O ports**: Vivado reports unconstrained I/O as a high-severity methodology violation. For AXI-to-BRAM demos, the main ports to constrain are the PL clock input (driven by PS `pl_clk0`) and any EMIO-routed signals.
- **`set_input_delay` and `set_output_delay` require both `-max` and `-min`**: Specifying only `-max` leaves minimum-path (hold) analysis unconstrained. The XDC pattern is two lines per port — one for each.
- **Falling-edge and DDR**: For DDR-style I/O, pair `-max`/`-min` with `-clock_fall` and `-add_delay` flags on the second constraint (applies to DDR peripherals, not plain BRAM).
- **PS-driven clock constraint**: The PS clock exported to PL (`pl_clk0`) must be declared with `create_clock` or matched via `create_generated_clock`. If you use `apply_board_preset` in IP Integrator, the preset may add this automatically; always verify in the Timing Constraints Wizard.
- **Clock groups for unrelated clocks**: If your design has multiple independent clocks (e.g., `pl_clk0` and a free-running oscillator), add `set_clock_groups -asynchronous` to suppress false-path CDC timing violations.

### Code Example
```tcl
# XDC constraints for KV260 AXI-BRAM bare-metal design

# PS-supplied PL clock (100 MHz — adjust to match Vivado block design setting)
create_clock -period 10.000 -name pl_clk0 [get_ports pl_clk0]

# Example: constrain a GPIO output driven from PL (EMIO)
set_output_delay -clock pl_clk0 -max  2.000 [get_ports {gpio_out[*]}]
set_output_delay -clock pl_clk0 -min -1.000 [get_ports {gpio_out[*]}] -add_delay

# Example: constrain a GPIO input from carrier card
set_input_delay  -clock pl_clk0 -max  3.000 [get_ports {gpio_in[*]}]
set_input_delay  -clock pl_clk0 -min  0.500 [get_ports {gpio_in[*]}] -add_delay

# False path for async resets (PS reset to PL logic)
set_false_path -from [get_ports pl_resetn0]
```

### Relevance to Your Project
In a PS-driven AXI-BRAM design, timing is dominated by the PS-generated clock and internal routing — the AXI interconnect and BRAM paths are typically well within budget at 100 MHz. The main XDC requirement is `create_clock` for `pl_clk0`; without it, Vivado's timing analysis is undefined and reports may be misleading.

## Kria KV260 / K26 SoM

### Key Findings
- **USB-UART path**: The KV260 uses a quad FTDI FT4232HL for both JTAG and UART over a single USB-B Micro connector (J4). The UART TX/RX connect to MIO36/MIO37, mapping to `psu_uart_1` in the PS configuration. If the terminal is silent, confirm you're connected to the correct COM port (the FTDI enumerates as 4 serial ports; the UART is typically the second or third).
- **JTAG fallback (J3)**: Header J3 is a direct JTAG interface that bypasses the FTDI chip. If the FTDI path is unreliable or unrecognized, a Digilent JTAG cable on J3 is confirmed to work for hardware debugging.
- **PL clock dependency**: The KV260 PL has no on-board oscillator routed to the PL fabric. All PL clocks must come from the PS (`pl_clk0`–`pl_clk3`). Forgetting to enable `pl_clk0` in the Zynq UltraScale+ IP means the PL logic has no clock and all simulation/hardware tests fail silently.
- **Boot modes**: Quad-SPI uses MIO[5:0]; eMMC uses MIO[22:13]. The `PS_Mode[3:0]` pins select boot mode on power-up. For bare-metal JTAG development, boot from JTAG mode (all PS_Mode pins low) or use SD card mode.
- **Power domains (UG1091)**: The carrier card exposes three domains — Always On, PS (MIO peripherals), and PL (HDIO). The PL domain is off until a bitstream loads. PWRGD signals on the SOM240 connector (`PWRGD_FPD_M2C`, `PWRGD_LPD_M2C`, `PWRGD_PL_M2C`) indicate rail readiness.
- **MIO bank mapping**: Bank 500 covers MIO[25:0]; bank 501 covers MIO[51:26]. MIO32–34 are reserved for SOM power management (do not drive these from user logic).

### Code Example
```c
/* KV260 bare-metal: confirm UART1 is active and print startup banner  */
#include "xuartps.h"
#include "xil_printf.h"
#include "xparameters.h"

/* In BSP, ensure standalone_stdout = psu_uart_1 (MIO36/37, 115200 8N1) */
int platform_init(void) {
    /* xil_printf routes to BSP-configured UART — no explicit init needed
     * if BSP stdout is set correctly. This call confirms UART is alive. */
    xil_printf("\r\n=== KV260 AXI-BRAM Demo (Vitis 2025.1) ===\r\n");
    xil_printf("PS clock: 100 MHz  BRAM0: 0xA0000000  BRAM2: 0xA0010000\r\n");
    return 0;
}
```

### Relevance to Your Project
Your demo outputs PASS/FAIL over USB-UART. The most common silent-output bug on KV260 is BSP stdout pointing to `psu_uart_0` instead of `psu_uart_1`. The second most common is not loading a bitstream before running (PL powers off at boot). Confirm both before interpreting any PASS/FAIL result.

## AMD/Xilinx Tool Updates (Vivado/Vitis 2025.x)

### Key Findings
- **Vitis Classic IDE deprecated in 2025.1**: The Unified IDE is now the default. The classic Vitis IDE (pre-2022.1 style) is deprecated; AMD will not ship further updates for it. Projects must migrate to the Unified IDE.
- **Vivado 2025.1 new device support**: Added Versal AI Edge Gen 2, Versal Prime Gen 2, and Spartan UltraScale+ family devices. For KV260 (K26 / XCZU5EV), no major device support change — the existing UltraScale+ MPSoC support is unchanged.
- **New AXI Switch IP in 2025.1**: A new AXI Switch IP core was introduced for AXI interconnect topologies. This complements the existing AXI Interconnect and AXI SmartConnect IPs.
- **Rebuilt Pblock Planner**: Vivado 2025.1 ships a new Pblock planner GUI that consolidates all pblock-related operations into a single panel. Useful for partitioned designs.
- **Known issues in 2025.1**:
  - GUI instability after opening Elaborated Design NoC view
  - Hardware Manager flash programming failure for Winbond W25Q12PW
  - ECO flow clock routing problem
  - Vitis: file dialog fails to open on AlmaLinux 9.5 / RHEL 9.5
  - Vitis: XSCT hangs during application builds on Windows
- **Vivado 2025.2 also released**: Adds further Versal Gen 2 features and an address-grouping GUI. If you are on 2025.1 and encounter the ECO routing bug, check if 2025.1.1 or 2025.2 resolves it.

### Code Example
```tcl
# Vitis 2025.1 Unified IDE: create platform and application from Tcl
# (run from Vitis Unified IDE Tcl console or vitis -source script.tcl)

setws ./workspace

# Create platform from exported XSA (from Vivado)
platform create -name kv260_platform \
    -hw ./kv260_top.xsa \
    -proc psu_cortexa53_0 \
    -os standalone

# Configure BSP: set UART1 as stdout
bsp setlib -name standalone \
    -config {stdin psu_uart_1 stdout psu_uart_1}

platform generate

# Create bare-metal application
app create -name axi_bram_demo \
    -platform kv260_platform \
    -domain standalone_psu_cortexa53_0 \
    -template "Empty Application"

# Add source files
importsources -name axi_bram_demo -path ./src

# Build
app build -name axi_bram_demo
```

### Relevance to Your Project
If you are building with Vitis 2025.1, the script above replaces the older `xsct` BSP/app creation flow. The key line is the `bsp setlib` call setting `stdout psu_uart_1` — this ensures `xil_printf` output reaches the USB-UART port on KV260 and your PASS/FAIL messages appear on the terminal.
