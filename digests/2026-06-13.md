## Executive Summary
- **AXI-Stream "abort" semantics matter even for an AXI-Lite-only design** if you ever add a DMA/streaming path later: per the ZipCPU "AXI Stream is broken" analysis, `TVALID` must never depend on `TREADY`, and once asserted it is "sticky" until accepted — a rule that's easy to violate when bridging AXI-Lite control registers into a stream FIFO.
- **`apply_bd_automation` + the Address Editor remain the two load-bearing TCL calls** in `create_bd.tcl`; a community example explicitly mapped multiple `axi_bram_ctrl` instances at `0xA0000000`, `0xA0002000`, `0xA0004000` off `M_AXI_HPM0_FPD`/`M_AXI_HPM0_LPD` — confirms your `0xA0000000`/`0xA0010000` BRAM0/BRAM2 split is a standard, well-trodden address layout for this exact PS master port.
- **`validate_bd_design` → `regenerate_bd_layout` → `save_bd_design`** is the canonical post-edit TCL sequence (per UG835 2025.2) — if `create_bd.tcl` is re-run against a newer Vivado, missing `validate_bd_design` before `make_wrapper` is the most common cause of a wrapper that silently doesn't reflect your latest BRAM/address changes.
- **Vitis 2025.1 standalone BSPs on Kria boards default `stdin`/`stdout` to `psu_uart_0`**, but the USB-UART bridge on KV260/KR260 carriers is wired to PS UART **1** — if `xil_printf` output from `main.c` never appears on the USB-UART terminal, check `vitis-comp.json` / BSP `stdout` settings for `psu_uart_1` before suspecting a hardware fault.
- **The K26 SOM has no split power rails for LPD/FPD** (`PWRGD_LPD_M2C`/`PWRGD_FPD_M2C` are tied together) — for a bare-metal-only design this simplifies your boot story (no separate LPD-only low-power mode to worry about), but `PWRGD_PL_M2C` still gates whether the PL fabric (and thus your AXI BRAM controllers) is powered before `main()` runs.

## AXI Protocol / AXI-Lite / AXI-Stream
### Key Findings
- Every AXI channel (AW/W/B/AR/R for AXI4/AXI4-Lite, plus the single TDATA/TVALID/TREADY/TLAST channel for AXI-Stream) follows the same rule: a transfer occurs only when `VALID && READY` are both `1` on the same edge; `VALID` may never be deasserted before that handshake completes, but `READY` can be withheld arbitrarily long.
- For AXI-Stream specifically, ZipCPU's "AXI Stream is broken" post highlights that **`TREADY` must never be combinationally derived from `TVALID` of the same source** — doing so creates a false combinational dependency that can deadlock when chained through multiple cores (e.g., FIFO → DMA → FIFO).
- `TLAST` is required for FIFO "packet mode": data is not released to the consumer until `TLAST` is seen on a complete packet — if a custom AXI-Stream producer never asserts `TLAST` (common bug when adapting a continuous-data source), an AXI4-Stream FIFO configured in packet mode will appear to "swallow" all data.
- For the AXI BRAM Controller (AXI4-Lite mode, as used for BRAM0/BRAM2): it deasserts `WREADY` when its internal write pipeline to the BRAM is full. Any hand-rolled AXI-Lite-to-BRAM bridge that doesn't replicate this backpressure can silently drop write beats under back-to-back `Xil_Out32()` calls.
- The AXI BRAM Controller's address range is bounded by its configured `C_S_AXI_ID_WIDTH`/memory depth — addresses issued beyond the configured BRAM depth (e.g., reading word offset 8192 from an 8K-deep BRAM) are out of range and the controller's response is implementation-defined (often a `SLVERR` on the `R`/`B` channel), so bounds-check loop indices against the actual BMG depth, not just the AXI address-map "range" field.

### Code Example
```c
/* AXI-Lite read with explicit memory barrier + range check pattern,
   relevant when porting BRAM test loops to a cached A53 core */
#include "xil_io.h"
#include "xil_cache.h"

#define BRAM0_BASE   0xA0000000U
#define BRAM0_DEPTH_WORDS  2048   /* match the BMG depth, not just the 64K AXI range */

int bram_word_inbounds(u32 word_offset) {
    return word_offset < BRAM0_DEPTH_WORDS;
}

void axi_write_word(u32 base, u32 word_offset, u32 value) {
    Xil_Out32(base + (word_offset * 4U), value);
    /* AXI-Lite to PL is non-cacheable on the default memory map, so no
       Xil_DCacheFlush is strictly required here -- but if BRAM0 is ever
       remapped into a cacheable region, add Xil_DCacheFlushRange(). */
}
```

### Relevance to Your Project
BRAM0/BRAM2 sit behind `axi_bram_ctrl` instances configured AXI4-Lite, which is the simplest and most forgiving AXI mode (no burst, no `TLAST`, single outstanding transaction). The AXI-Stream pitfalls above aren't directly exercised today, but if a future iteration adds a streaming DMA path (e.g., to move test patterns faster than per-word `Xil_Out32`), the `TVALID`/`TREADY` independence rule and `TLAST` packet-mode behavior become load-bearing. For the current design, the most actionable item is the **BRAM depth bounds check**: confirm your `main.c` test-pattern loop count doesn't exceed the Block Memory Generator's configured depth for BRAM0/BRAM2, independent of the 64KB address-range entries in the address editor.

## Vivado Block Design / IP Integrator
### Key Findings
- `apply_bd_automation -rule xilinx.com:bd_rule:axi4` is the standard call that wires a Zynq UltraScale+ PS master (`M_AXI_HPM0_FPD` or `M_AXI_HPM0_LPD`) through an AXI Interconnect/SmartConnect to a slave's `S_AXI` interface, including clock (`*_ACLK`) and reset (`*_ARESETN`) connections in one shot.
- A community-documented design mapped several `axi_bram_ctrl` instances at `0xA0000000`, `0xA0002000`, and `0xA0004000` off the PS's HPM ports — this confirms `0xA0...` is a conventional, collision-free region for PL-side BRAM peripherals on Zynq UltraScale+ (default HPM0 aperture is the 1GB window `0x80000000`-`0xBFFFFFFF`).
- To enable the PS-PL AXI master path at all, **AXI HPM0 LPD** (or FPD) must be explicitly checked in the PS Configuration → "PS-PL Configuration" → "AXI HPM0 LPD"/"AXI HPM0 FPD" pane, with the data width set (commonly 32-bit for control-plane traffic like BRAM test access).
- "Regenerate Layout" (`regenerate_bd_layout`) only redraws the canvas — it does not propagate parameters. The actual parameter-propagation/width-negotiation step is `validate_bd_design`, which must run after any TCL-driven edit and before `make_wrapper`/`generate_target`.
- A frequent IPI error when pairing `axi_bram_ctrl` with a Block Memory Generator is a data-width or `READ_WRITE_MODE` mismatch between the two IPs — both must agree, and if ECC is enabled on the controller, the BMG must be set to the matching "wrapper" memory-map mode (extra ECC bits per word).

### Code Example
```tcl
# Re-run-safe BD construction snippet (idempotent against re-running
# create_bd.tcl on an existing project)
if {[get_bd_cells -quiet /axi_bram_ctrl_0] eq ""} {
    set axi_bram_ctrl_0 [create_bd_cell -type ip -vlnv xilinx.com:ip:axi_bram_ctrl:4.1 axi_bram_ctrl_0]
    set_property -dict [list CONFIG.SINGLE_PORT_BRAM {0} CONFIG.DATA_WIDTH {32}] $axi_bram_ctrl_0
}
if {[get_bd_cells -quiet /blk_mem_gen_0] eq ""} {
    set blk_mem_gen_0 [create_bd_cell -type ip -vlnv xilinx.com:ip:blk_mem_gen:8.4 blk_mem_gen_0]
    set_property -dict [list CONFIG.Memory_Type {True_Dual_Port_RAM}] $blk_mem_gen_0
}
connect_bd_intf_net [get_bd_intf_pins axi_bram_ctrl_0/BRAM_PORTA] \
                     [get_bd_intf_pins blk_mem_gen_0/BRAM_PORTA]
connect_bd_intf_net [get_bd_intf_pins axi_bram_ctrl_0/BRAM_PORTB] \
                     [get_bd_intf_pins blk_mem_gen_0/BRAM_PORTB]

apply_bd_automation -rule xilinx.com:bd_rule:axi4 \
  -config { Clk_master {Auto} Clk_slave {Auto} Clk_xbar {Auto} \
            Master {/zynq_ultra_ps_e_0/M_AXI_HPM0_FPD} \
            Slave {/axi_bram_ctrl_0/S_AXI} \
            intc_ip {New AXI SmartConnect} master_apm {0} } \
  [get_bd_intf_pins axi_bram_ctrl_0/S_AXI]

validate_bd_design
regenerate_bd_layout
save_bd_design
```

### Relevance to Your Project
The `0xA0000000`/`0xA0010000` split for BRAM0/BRAM2 follows exactly the same convention seen in the community HPM0 example above, just with 64KB spacing instead of 8KB — both are valid as long as ranges don't overlap and stay inside the 1GB HPM0 aperture. The most useful guard to add to `create_bd.tcl` is the `get_bd_cells -quiet` idempotency check above: it lets the script be safely re-sourced against an existing `.bd` (e.g., during a Vivado 2025.1 re-validation pass) without `ERROR: [BD 41-737] ... already exists`.

## Vivado TCL Scripting
### Key Findings
- Vivado has three execution modes: **GUI**, **Tcl mode** (`vivado -mode tcl`, interactive console — best for developing scripts incrementally), and **Batch mode** (`vivado -mode batch -source script.tcl`, non-interactive, exits on completion — best for CI/regeneration).
- In **non-project mode** (no `.xpr`; everything driven via `read_vhdl`/`read_xdc`/`synth_design`/`opt_design`/`place_design`/`route_design`/`write_bitstream`), the developer owns all source management — each time a source file changes on disk, the design must be reloaded, and there are no default intermediate reports unless the script writes them explicitly.
- A documented best practice for batch-mode scripts: **explicitly use `exec`** for any external OS command, since unknown Tcl commands are not auto-forwarded to the shell in batch mode the way they sometimes are interactively.
- `write_bd_tcl` will regenerate a faithful Tcl recreation of an existing block design (IP customizations, connections, BD properties) — useful as a one-time "export current GUI state to script" step if `create_bd.tcl` ever drifts from the actual `.bd` due to manual GUI edits.
- For reproducibility across Vivado releases, pin the exact part (`xck26-sfvc784-2LV-c` for the K26 SoM) in `create_project` rather than relying solely on a board file — board file definitions occasionally change between Vivado versions and can shift default pin/IO assignments.

### Code Example
```tcl
#!/usr/bin/env -S vivado -mode batch -source
# build.tcl - non-project-mode regeneration entry point
set part    "xck26-sfvc784-2LV-c"
set bd_name "kv260_bd"
set top     "${bd_name}_wrapper"

create_project -in_memory -part $part

create_bd_design $bd_name
source ./tcl/create_bd.tcl
validate_bd_design
regenerate_bd_layout
save_bd_design

make_wrapper -files [get_files ${bd_name}.bd] -top
add_files -norecurse [get_files -of_objects [get_filesets sources_1] *${top}.vhd]
add_files -fileset constrs_1 -norecurse ./xdc/kv260_axi_bram.xdc

synth_design -top $top -part $part
opt_design
place_design
route_design
write_bitstream -force ./build/${top}.bit

puts "Done: ./build/${top}.bit"
```

### Relevance to Your Project
A single `build.tcl` of this shape gives a one-command, version-pinned (`xck26-sfvc784-2LV-c`) rebuild of the KV260 AXI-BRAM hardware from `tcl/create_bd.tcl` + `vhdl/kv260_top.vhd`, independent of any `.xpr` checked into git. Running it under `vivado -mode batch` is also the cleanest way to regression-test that a Vivado 2025.1 install still produces the same `0xA0000000`/`0xA0010000` address map after `validate_bd_design` — any address-editor drift will surface as a synthesis/`assign_bd_address` warning in the batch log.

## Vitis Bare-Metal / Standalone
### Key Findings
- On Kria carrier boards (KV260/KR260), the **USB-UART bridge is connected to PS UART 1**, but the standalone BSP's `stdin`/`stdout` often defaults to `psu_uart_0`. In the Vitis Unified IDE flow, this is fixed by editing `vitis-comp.json` for the platform component and setting both `standalone_stdin` and `standalone_stdout` to `psu_uart_1`, then regenerating the BSP.
- `xil_printf` is a minimal printf substitute with **no floating-point support** (`%f` is not implemented) — its supported specifiers are essentially `%d`, `%u`, `%x`, `%c`, `%s`, and the `l`/`ll` length modifiers for 32/64-bit integers. Any diagnostic that tries to print a computed ratio or percentage as a float will print garbage or nothing.
- The standalone BSP for Cortex-A53 (APU) links the GIC driver (`xscugic`) by default even for purely polling bare-metal apps — this is harmless for functionality but adds to binary size; it's not something you need to fight for a small BRAM test app.
- Linker scripts (`lscript.ld`) generated by the BSP place `.text`/`.data`/`.bss`/heap/stack according to the memory region chosen in "Edit BSP Settings" (commonly OCM or DDR for A53 bare-metal). If PASS/FAIL output is truncated or the app hangs after several test iterations, check `STACK_SIZE`/`HEAP_SIZE` in `lscript.ld` before suspecting AXI bus issues.
- For Vitis 2025.1's Unified IDE, "Update Hardware Specification" on the platform component is the step that re-imports a regenerated `.xsa` — skipping it after any `create_bd.tcl`/address-map change leaves `xparameters.h` stale, so `XPAR_AXI_BRAM_CTRL_*_S_AXI_BASEADDR` may not match the actual `0xA0000000`/`0xA0010000` addresses in the new bitstream.

### Code Example
```c
#include "xil_printf.h"
#include "xil_io.h"
#include "xparameters.h"

#define BRAM0_BASE  XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR  /* expect 0xA0000000 */
#define BRAM2_BASE  XPAR_AXI_BRAM_CTRL_1_S_AXI_BASEADDR  /* expect 0xA0010000 */
#define NUM_WORDS   16U

static int test_bram(u32 base, const char *name) {
    int errors = 0;
    for (u32 i = 0; i < NUM_WORDS; i++) {
        Xil_Out32(base + (i * 4U), 0xA5A50000U | i);
    }
    for (u32 i = 0; i < NUM_WORDS; i++) {
        u32 expect = 0xA5A50000U | i;
        u32 got    = Xil_In32(base + (i * 4U));
        if (got != expect) {
            /* xil_printf has no %f -- use integer fields only */
            xil_printf("%s[%lu]: wrote 0x%08lx read 0x%08lx FAIL\r\n",
                       name, (unsigned long)i, (unsigned long)expect, (unsigned long)got);
            errors++;
        }
    }
    xil_printf("%s: %s (%d errors)\r\n", name, errors ? "FAIL" : "PASS", errors);
    return errors;
}

int main(void) {
    xil_printf("\r\n--- KV260 AXI BRAM Demo ---\r\n");
    int e = test_bram(BRAM0_BASE, "BRAM0") + test_bram(BRAM2_BASE, "BRAM2");
    xil_printf("Overall: %s\r\n", e ? "FAIL" : "PASS");
    return e;
}
```

### Relevance to Your Project
If PASS/FAIL output never appears on the USB-UART terminal but the board otherwise seems to run (LED activity, JTAG connection succeeds), the `psu_uart_0` vs `psu_uart_1` default mismatch above is the single most likely culprit on KV260/KR260 — check `vitis-comp.json`/BSP `stdout` before debugging the AXI path itself. Separately, after any `create_bd.tcl` edit to the BRAM address map, re-run "Update Hardware Specification" in Vitis so `xparameters.h` reflects the current `0xA0000000`/`0xA0010000` mapping — otherwise `main.c` can compile fine but target the wrong (stale) addresses.

## XDC Timing Constraints
### Key Findings
- `set_input_delay -clock <clk> [-max|-min] <value> [get_ports ...]` and `set_output_delay -clock <clk> [-max|-min] <value> [get_ports ...]` describe the **external system's** timing relative to a clock at a port boundary — input delay represents the driving device's clock-to-output, output delay represents the receiving device's setup requirement. Neither directly encodes the FPGA's own internal setup/hold (STA computes that separately once the external delay is known).
- The `-clock` argument on both commands ties the delay to a specific clock domain — this is what lets Vivado's timing engine associate an I/O delay with the correct clock group when multiple clocks are present.
- `set_clock_groups -asynchronous -group [get_clocks A] -group [get_clocks B]` is required whenever two clocks are genuinely unrelated (e.g., a free-running reference oscillator vs. `pl_clk0`) — without it, Vivado will try to perform (and fail or over-constrain) cross-domain timing analysis between clocks that have no defined phase relationship.
- For Zynq UltraScale+/Kria designs where **all PL logic is driven by a PS-generated `pl_clk0`** and the only I/O is routed through PS MIO (UART, JTAG), the Zynq PS IP's auto-generated constraints (clock definitions for `pl_clkN`) plus IP-Integrator default `false_path`/`clock_groups` are typically sufficient — a project-level `.xdc` may be nearly empty by design, not by omission.
- If reusing a `.xdc` from a different Kria carrier (e.g., KR260 vs KV260) for an LED/PMOD signal, `PACKAGE_PIN`/`IOSTANDARD` assignments are carrier-specific — a stale pin name silently leaves a port unconstrained rather than throwing a hard error in some flows, so always check the implemented design's I/O Planning report after porting constraints.

### Code Example
```tcl
# kv260_axi_bram.xdc - representative minimal constraints when the only
# PL-side I/O is an optional status LED; PS-routed UART needs no XDC entry.

set_property PACKAGE_PIN H12 [get_ports led_status]
set_property IOSTANDARD LVCMOS33 [get_ports led_status]

# Treat the LED as a slow, non-critical output relative to pl_clk0
create_clock -period 10.000 -name virtual_pl_clk0 -waveform {0 5} \
  [get_pins -hier -filter {NAME =~ *pl_clk0*}]
set_output_delay -clock virtual_pl_clk0 -max 2.000 [get_ports led_status]
set_output_delay -clock virtual_pl_clk0 -min 0.500 [get_ports led_status]

# Example asynchronous clock group declaration, only needed if a second
# free-running clock is introduced (e.g., an LED PWM generator):
# set_clock_groups -asynchronous \
#   -group [get_clocks -of_objects [get_pins -hier -filter {NAME =~ *pl_clk0*}]] \
#   -group [get_clocks -of_objects [get_pins -hier -filter {NAME =~ *pwm_clk*}]]
```

### Relevance to Your Project
Since `kv260_top.vhd` is described as exposing AXI-BRAM connectivity driven entirely from the PS over `M_AXI_HPM0_*`, and UART runs over PS MIO, the project's `.xdc` likely needs **no `set_input_delay`/`set_output_delay` entries at all** for correct timing closure — these only become relevant if/when the top level adds a directly PL-driven I/O pin (status LED, PMOD). Treat a near-empty XDC as expected, but if you do add such a pin, use the pattern above and double check `PACKAGE_PIN` against the actual KV260 carrier schematic (not a KR260 or generic UltraZed pinout).

## Kria KV260 / K26 SoM
### Key Findings
- The K26 SOM's Zynq UltraScale+ boot mode is selected via `PS_MODE[3:0]` pins routed through the SOM connector to the carrier; all mode pins are pulled high to 1.8V on the SOM, and the carrier must pull specific pins low to select a valid boot mode (per the ZU+ TRM boot mode table). KV260 starter-kit carriers ship pre-configured for **QSPI32** boot of the certified firmware/Linux image.
- The K26 SOM does **not** have split power rails for LPD and FPD — `PWRGD_LPD_M2C` and `PWRGD_FPD_M2C` are tied together on the SOM. `PWRGD_PL_M2C` is a separate active-high signal indicating PL power-rail status; PL (and thus the AXI fabric/BRAM controllers) must be powered and the PL fabric clock/reset released before AXI transactions to BRAM0/BRAM2 will succeed.
- In PS-PL Configuration, **AXI HPM FPD/LPD** are the PS master interfaces into the PL (used by your `main.c` to reach the BRAM controllers), while **AXI HP FPD/LPD** are PS slave interfaces (used by PL masters to reach DDR) — for a pure "CPU writes to PL BRAM" demo, only an HPM master interface needs to be enabled.
- The KV260's I2C signals (`I2C_SCK`/`I2C_SDA`) connect to an I2C master on MIO bank 500 of the SOM's Zynq UltraScale+, and the default carrier bitstream provides an EMIO mapping for fan control — useful context if your block design inherited MIO/EMIO assignments from the official Kria starter-kit reference BD rather than a from-scratch PS configuration.
- For "PS can't see PL peripherals at all" symptoms on KV260, the most common root cause remains a stale `.xsa`: any BD change requires re-export and "Update Hardware Specification" in Vitis, or `xparameters.h` addresses won't match the actual bitstream's BRAM controller addresses.

### Code Example
```tcl
# XSCT/JTAG live-debug snippet: confirm PL fabric clock/reset are
# released and BRAM0 is reachable before trusting main.c's own test
connect
targets -set -filter {name =~ "*A53*0*"}

# CRL_APB.PL0_REF_CTRL - confirm PL fabric clock (FCLK0) is enabled/sourced
mrd 0xFF5E0080

# Manual peek/poke sanity check of BRAM0 over the AXI-Lite path
mwr 0xA0000000 0xCAFEF00D
mrd 0xA0000000 1

# And BRAM2
mwr 0xA0010000 0x600DF00D
mrd 0xA0010000 1
```

### Relevance to Your Project
If the BRAM PASS/FAIL test hangs or bus-errors only on a cold boot (but works after a JTAG re-download), suspect PL power/clock sequencing (`PWRGD_PL_M2C`, `FCLK0` release) rather than the AXI-Lite logic itself — the standard Vitis bare-metal template's generated `psu_init()` call (which must run before any BRAM access) handles this in the normal flow. The XSCT snippet above is a fast way to isolate "PS/PL link problem" from "test-pattern logic problem" by manually poking `0xA0000000`/`0xA0010000` independent of `main.c`.

## AMD/Xilinx Tool Updates (Vivado/Vitis 2025.x)
### Key Findings
- The **Vitis Unified IDE is the default flow** as of 2025.x (Classic Vitis IDE is deprecated) — platform component creation, "Update Hardware Specification," and BSP editing have moved into the unified flow's "Create Platform Component"/"Create Application Project" wizards; older Kria bare-metal tutorials written against Vitis Classic (pre-2023.2) will have different menu paths but the same underlying concepts (BSP, `xparameters.h`, `lscript.ld`).
- Vivado 2025.x's **Tcl Batch Mode** documentation (UG835) continues to recommend `vivado -mode batch -source <script>.tcl` for unattended runs, with the standard post-BD-edit sequence `validate_bd_design` → `regenerate_bd_layout` → `save_bd_design` explicitly called out as the canonical cleanup/commit sequence.
- "Using IP Integrator in Non-Project Mode" is documented as a first-class flow in UG994 (2025.1) — non-project-mode IPI (build the BD entirely via Tcl, no `.xpr` checked into git) remains fully supported and is the natural fit for a repo that already separates `tcl/create_bd.tcl` from VHDL sources.
- 2025.1/2025.2 Vitis embedded tutorials (per `Xilinx/Vitis-Tutorials` on GitHub) continue to ship Kria-targeted bare-metal examples (e.g., KD240/KV260 "BIST" platform recreations), confirming the bare-metal + Unified IDE + Kria combination remains an actively maintained reference path for 2025.x toolchains.
- When moving an existing project between Vivado releases, `report_ip_status` followed by `upgrade_ip [get_ips -all]` on the block design — then re-running `validate_bd_design`/`save_bd_design` — is the standard way to bring `axi_bram_ctrl`/Block Memory Generator IP up to the new release's versions before regenerating the wrapper and re-exporting the `.xsa`.

### Code Example

open_bd_design [get_files kv260_bd.bd]

### Relevance to Your Project
Before relying on a from-scratch `xck26-sfvc784-2LV-c` rebuild under a fresh 2025.1 install, run `report_ip_status`/`upgrade_ip` against any existing checked-in `.bd`/`.xpr` first — IP version drift between `axi_bram_ctrl`/Block Memory Generator versions and the `xparameters.h` the BSP was generated against is the most common "worked on old Vivado, FAILs on new Vivado" failure mode for this kind of project. Since the project already keeps `tcl/create_bd.tcl` separate from the VHDL top level, the non-project-mode IPI flow documented in UG994 (2025.1) is a good fit if you want to drop the `.xpr` from git entirely.
