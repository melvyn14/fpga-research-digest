## Executive Summary

1. **AXI-Lite handshake deadlock is the #1 bare-metal integration bug**: if
   your PS master or custom IP ever gates `AWVALID`/`WVALID` behind seeing
   the corresponding `READY`, the bus hangs forever. The ZipCPU "easy AXI-
   Lite" reference design (cited below) is the canonical VHDL fix.
2. **AXI BRAM Controller write-enable fires one cycle early** in some
   configurations (PG078 errata): you may see an extra spurious write at the
   base address. Confirm with ILA before trusting PASS results.
3. **Address alignment is mandatory**: a 4 KB slave (range `0x1000`) must
   have three trailing zeros in its base address. Mis-aligned addresses
   silently pass DRC in some Vivado versions but fail at runtime.
4. **`write_bd_tcl` scripts are version-locked**: the TCL exported by Vivado
   2025.1 is not portable to 2025.2 or 2026.x. Commit the script *and* tag
   the Vivado version alongside it.
5. **Vivado 2025.1 changed the default GT Wizard type** to GT Wizard
   Subsystem; any design importing an older GT Wizard IP block will trigger
   an upgrade prompt on first open.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- **Handshake deadlock (most common bug)**: The AXI spec forbids a source
  from asserting VALID only after it has seen READY. A slave that gates
  `AWREADY` behind `AWVALID`, combined with a master that gates `AWVALID`
  behind `AWREADY`, produces a permanent stall. This affects custom VHDL
  slaves and any wrapper that "optimises" the ready path.
- **VALID must never be de-asserted once raised**: once the master drives
  `WVALID = '1'`, it must hold `WVALID` high *and* keep `WDATA`/`WSTRB`
  stable until the handshake completes (`WREADY = '1'` on a rising edge).
  Relaxing this silently corrupts the transfer.
- **AXI BRAM Controller (PG078) write-enable early-assertion**: the
  controller has been observed asserting BRAM write-enable one clock cycle
  before the AXI write handshake completes in certain pipelined modes,
  writing stale data to word 0. Workaround: insert a one-cycle pipeline
  register on the BRAM data/EN path, or use the AXI4 (non-Lite) mode with
  burst length = 1.
- **AXI4-Lite vs AXI4**: AXI4-Lite has no burst, no narrow transfers, fixed
  32-bit data width. For your two-BRAM design the Lite mode is correct and
  simpler, but be aware the BRAM Controller IP defaults to AXI4 mode; switch
  it explicitly.

### Code Example

```vhdl
-- Correct AXI-Lite slave write-address handshake (no deadlock)
-- AWREADY goes high combinatorially when the slave is idle;
-- it does NOT wait for AWVALID.
process(s_axi_aclk)
begin
  if rising_edge(s_axi_aclk) then
    if s_axi_aresetn = '0' then
      aw_active <= '0';
      aw_addr_r <= (others => '0');
    elsif s_axi_awvalid = '1' and aw_active = '0' then
      -- Latch address on handshake, not before
      aw_addr_r <= s_axi_awaddr;
      aw_active <= '1';
    elsif w_done = '1' then
      aw_active <= '0';
    end if;
  end if;
end process;

-- AWREADY: held high when idle (combinatorial, no gating on AWVALID)
s_axi_awready <= not aw_active;
```

### Relevance to Your Project

Your bare-metal test drives `AWVALID`/`WVALID` via the Zynq PS AXI master
(HPM0), which is a fully spec-compliant initiator, so deadlock is unlikely
*from the PS side*. However, if `kv260_top.vhd` wraps or re-drives any AXI
signal before it reaches the BRAM Controller, inspect that path for VALID
de-assertion or gating. The write-enable early-assertion issue (above) is
worth checking with an ILA capture on `BRAM_WEN` vs `WVALID`/`WREADY` to
confirm your PASS results reflect actual BRAM contents.

## Vivado Block Design / IP Integrator

### Key Findings

- **Connection Automation** adds two IPs automatically when triggered: an
  AXI Interconnect (SmartConnect in 2024+) and a Processor System Reset.
  If you re-run automation after adding a second BRAM Controller, it may
  insert a *second* reset block; delete the duplicate or the bitstream DRC
  will warn about multiple resets on the same `ext_reset_in` net.
- **Address alignment rule**: a peripheral with 4 KB range occupies
  `0x1000` bytes, so its base address must end in `000` hex. Your BRAM0 at
  `0xA000_0000` and BRAM2 at `0xA001_0000` are correctly aligned and
  non-overlapping (64 KB apart, 4 KB ranges).
- **Overlapping address ranges**: Vivado reports a DRC warning
  (`ADRV-34`) but *does not* block bitstream generation in all cases. The
  overlap causes silent aliasing at runtime — both slaves respond to the
  same addresses, producing incorrect read-back.
- **Validate Design** (`validate_bd_design` in TCL) must be run after every
  address edit; errors here are much cheaper to fix than post-implementation
  routing failures.
- **Regenerate Layout** button re-arranges the canvas without changing
  connectivity — safe to use at any time.

### Code Example

```tcl
# TCL: validate and report the address map after any change
validate_bd_design
assign_bd_address
# Show address segments for all AXI slaves
report_bd_address_space
# Example output you want to see:
#   SEG_axi_bram_ctrl_0_Mem0  0xA0000000  0xA0000FFF
#   SEG_axi_bram_ctrl_1_Mem0  0xA0010000  0xA0010FFF
```

### Relevance to Your Project

Your `create_bd.tcl` script should call `assign_bd_address` before
`validate_bd_design` — if the address auto-assignment differs from your
intended `0xA0000000`/`0xA0010000`, the bare-metal `main.c` offsets will be
wrong. Pin the addresses explicitly with `set_property offset` after
`assign_bd_address` rather than relying on auto-assignment order.

## Vivado TCL Scripting

### Key Findings

- **`write_bd_tcl` is version-locked**: AMD explicitly states the exported
  script is intended for use only in the release that created it. Commit
  the Vivado version string (e.g. `# Generated by Vivado 2025.1`) in the
  header comment and tag the git commit.
- **Only user-changed parameters are written**: IP default values are
  omitted. If a downstream user opens the script on a fresh install with
  different IP defaults, regenerated IPs may silently differ. Use
  `-include_layout` and `-no_ip_version` flags to maximise reproducibility.
- **Non-project mode** (`vivado -mode batch`) is ideal for CI: it reads
  sources, runs synthesis/implementation, writes bitstream, and exits.
  Block designs generated in project mode can be used in non-project mode
  if the OOC (Out-of-Context) DCP is pre-built.
- **Batch invocation pattern**: `vivado -mode batch -source script.tcl
  -tclargs arg1 arg2` passes arguments accessible via `$argv` in the script.

### Code Example

```tcl
# Non-project mode: synthesise + implement + write bitstream in one script
# Usage: vivado -mode batch -source build.tcl

read_vhdl -library work [glob ../vhdl/*.vhd]
read_bd   ../bd/design_1.bd
read_xdc  ../constrs/kv260_top.xdc

# Regenerate BD wrapper
generate_target all [get_files ../bd/design_1.bd]
make_wrapper -files [get_files ../bd/design_1.bd] -top
add_files -norecurse ../bd/design_1/hdl/design_1_wrapper.vhd

# Full compile
synth_design  -top design_1_wrapper -part xck26-sfvc784-2LV-c
opt_design
place_design
route_design
write_bitstream -force ../output/kv260_top.bit
write_hw_platform -fixed -force -file ../output/kv260_top.xsa

puts "Build complete."
```

### Relevance to Your Project

Your `create_bd.tcl` is already in the right shape for this flow. Add
`assign_bd_address` and explicit offset `set_property` calls for your two
BRAM Controllers so the script is fully deterministic regardless of the
order IPs are instantiated. Running the full build in batch mode lets you
catch address-map regressions in CI without opening the GUI.

## Vitis Bare-Metal / Standalone

### Key Findings

- **BSP must match the exported XSA**: after any Vivado change (even a
  re-layout with no logical change) the XSA must be re-exported and the
  Vitis platform re-generated. A stale BSP silently uses wrong base
  addresses from the previous hardware map.
- **`xil_printf` is UART-backed**: it uses the PS UART0 (MIO 18/19 on K26)
  by default. It does *not* buffer — each character is polled out. For
  timing-sensitive tests, call `xil_printf` only after the AXI R/W sequence
  is complete, not interleaved.
- **Driver path**: BRAM Controller driver headers live at
  `<Vitis>/<ver>/data/embeddedsw/XilinxProcessorIPLib/drivers/bram_v4_0/src/`
  — use `XBram_WriteReg` / `XBram_ReadReg` macros for typed access instead
  of raw `Xil_Out32` / `Xil_In32`.
- **Linker script DDR range for K26**: the Cortex-A53 DDR starts at
  `0x0000_0000` (PS DDR low) and extends to 4 GB. The default linker script
  places `.text` and `.data` in `ps_ddr_0`; leave this unchanged for bare-
  metal AXI-BRAM tests (BRAM is in PL address space, not DDR).
- **Kria KV260 BIST tutorial** (Hackster, LogicTronix, 2025.1) is the
  closest publicly documented bare-metal reference for this exact platform.

### Code Example

```c
#include "xil_printf.h"
#include "xil_io.h"
#include "xparameters.h"

/* Use driver macros instead of raw Xil_Out32 for type safety */
#define BRAM0_BASE  XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR
#define BRAM2_BASE  XPAR_AXI_BRAM_CTRL_1_S_AXI_BASEADDR
#define TEST_WORD   0xDEADBEEFU

static int bram_rw_test(u32 base, const char *name) {
    Xil_Out32(base, TEST_WORD);
    /* Insert memory barrier so write completes before read */
    dsb();
    u32 rb = Xil_In32(base);
    if (rb == TEST_WORD) {
        xil_printf("%s PASS (0x%08X)\r\n", name, rb);
        return 0;
    }
    xil_printf("%s FAIL: wrote 0x%08X, read 0x%08X\r\n",
               name, TEST_WORD, rb);
    return -1;
}

int main(void) {
    xil_printf("KV260 AXI-BRAM test start\r\n");
    int rc = 0;
    rc |= bram_rw_test(BRAM0_BASE, "BRAM0");
    rc |= bram_rw_test(BRAM2_BASE, "BRAM2");
    xil_printf(rc == 0 ? "ALL PASS\r\n" : "SOME FAIL\r\n");
    return rc;
}
```

### Relevance to Your Project

The `dsb()` (Data Synchronisation Barrier) between write and read is
critical on Cortex-A53: without it the compiler or out-of-order pipeline
may reorder the accesses, producing a read-before-write at the AXI bus
level. If your current `main.c` uses raw `Xil_Out32`/`Xil_In32` without a
barrier, add `dsb()` (or `__asm__ volatile("dsb sy" ::: "memory")`) between
write and read-back to prevent false PASSes.

## XDC Timing Constraints

### Key Findings

- **`create_clock` is mandatory for PL clocks from PS**: even though the
  MMCM/PLL inside the PS feeds the PL clocks, Vivado needs a `create_clock`
  on the `PL_CLK0` output port so timing analysis has a reference. Without
  it, all AXI paths are unconstrained and Vivado optimises for speed with no
  timing guarantee.
- **AXI-Lite pure-FPGA path**: if all your logic (BRAM, interconnect,
  wrappers) is clocked by the same PS-derived clock, you only need
  `create_clock` — no `set_input_delay`/`set_output_delay` are required
  unless signals cross to board I/O.
- **KV260 nominal clock allocation**: 100 MHz for AXI-Lite control fabric,
  200 MHz and 400 MHz reserved for accelerator AXI and DPU core. Your BRAM
  demo running at 100 MHz is well-matched to AXI-Lite throughput.
- **`set_clock_groups -asynchronous`**: if the PL design has a second clock
  domain (e.g. a free-running oscillator), declare it asynchronous to the
  PS-derived clock or Vivado will attempt cross-domain timing analysis and
  report false violations.
- **Constraint Wizard** (`Tools > Constraints Wizard` in Vivado) auto-
  generates I/O constraints for UART, I2C, and other board interfaces; run
  it after adding any MIO-connected peripheral.

### Code Example

```xdc
# kv260_top.xdc — minimal constraints for AXI-BRAM demo

# PS provides PL_CLK0 at 100 MHz (10 ns period)
# This port name appears on the block design wrapper
create_clock -period 10.000 -name pl_clk0 \
    [get_ports pl_clk0]

# If a second oscillator is used on the carrier card
# (e.g. 25 MHz Ethernet ref), mark it asynchronous to pl_clk0
# create_clock -period 40.000 -name eth_clk [get_ports eth_ref_clk]
# set_clock_groups -asynchronous \
#     -group [get_clocks pl_clk0] \
#     -group [get_clocks eth_clk]

# PS UART TX — no output delay needed for bare-metal UART polling
# but add this if Vivado warns about unconstrained output
# set_output_delay -clock pl_clk0 -max 2.0 [get_ports uart_txd]
# set_output_delay -clock pl_clk0 -min 0.5 [get_ports uart_txd]
```

### Relevance to Your Project

For a pure PS→PL AXI-BRAM design with no external I/O from the PL fabric,
the single `create_clock` above is all you need. Confirm the port name
matches the wrapper generated by Vivado (check the Tcl console after
`generate_target all`). The most common symptom of missing constraints is
timing summary showing `0 clocks analysed` — treat this as a red flag even
if implementation "succeeds".

## Kria KV260 / K26 SoM

### Key Findings

- **Boot mode is set by `MODE[3:0]` pins on the carrier card**, not in
  software. The KV260 Starter Kit ships in `QSPI32` mode. For bare-metal
  development, JTAG boot is the fastest iteration cycle: set MODE to JTAG
  (all pins low) and use XSCT `dow` / `con` to load ELF directly.
- **AXI High-Performance Master port**: connect the BRAM Controllers to
  `M_AXI_HPM0_FPD` (Full-Power Domain, 128-bit wide internally but
  downscaled to 32-bit by the AXI Interconnect for Lite slaves). Disable
  `M_AXI_HPM1_FPD` in PS-PL Configuration if unused to reduce resource
  consumption.
- **MIO 18/19 → UART0**: PS UART0 is wired to MIO 18 (TX) and MIO 19 (RX)
  on the K26 SoM, routed to USB-UART on the KV260 carrier. Confirm the BSP
  `xparameters.h` maps `XPAR_XUARTPS_0_BASEADDR` to `0xFF000000`.
- **Power domains**: PL fabric is powered by the `VCCINT`/`VCCBRAM` rails
  (internal). BRAM content is retained while `VCCBRAM` is powered; PL
  configuration is lost on full power cycle. For production, use `QSPI +
  fallback` boot mode to reload the bitstream automatically.
- **Bare-metal 4K Streaming guide** (Hackster, fredo2, Vivado/Vitis 2025.2)
  is the most recent comprehensive bare-metal reference for KV260 as of
  this run.

### Code Example

```tcl
# XSCT session: JTAG boot + load bare-metal ELF on KV260
# Run from Vitis XSCT console or: xsct boot_jtag.tcl

connect
targets -set -nocase -filter {name =~ "APU*"}
rst -system
after 3000

# Download and run ELF
targets -set -nocase -filter {name =~ "ARM*#0"}
dow kv260_bram_test.elf
con

# Monitor UART output separately (e.g. minicom /dev/ttyUSB1 115200)
```

### Relevance to Your Project

Switching to JTAG boot eliminates the QSPI flash-program step during
development, cutting the iteration loop from ~3 minutes (flash + reboot) to
~15 seconds (ELF download + run). Once your PASS/FAIL test is stable, burn
to QSPI for standalone demo use. Note that `boot.bin` for QSPI must embed
both the FSBL and the bitstream; the Vitis `bootgen` utility wraps them with
your ELF.

## AMD/Xilinx Tool Updates (Vivado/Vitis 2025.x)

### Key Findings

- **Vivado 2025.1**: GT Wizard IP type default changed to *GT Wizard
  Subsystem*. Designs opened from 2024.x or earlier that contain the
  classic GT Wizard will receive an upgrade prompt; accept it and re-
  validate the block design.
- **AXI Ethernet Buffer (2025.1 fix)**: PTP 1588 frames were not handled
  correctly in prior releases — patched in 2025.1 IP change log
  (AR #000037919). Not relevant to BRAM-only designs but notable for
  future Ethernet additions.
- **Vitis AI v5.0** (released with 2025.1) is verified against Vivado/
  Vitis/PetaLinux 2025.1 and the Kria KV260. The DPU IP bundle now ships
  as a separate download from the main Vitis installer.
- **Vitis Unified IDE (2025.1)**: embedded platform creation now uses a
  single "component" workflow replacing the legacy Domain/Platform wizard.
  The new flow reduces the number of steps to export a standalone platform
  from ~8 to ~4 GUI clicks.
- **Vivado 2026.1** release notes are already published (AMD docs site),
  indicating the tool is in active development. If upgrading, the Kria board
  files and IP repos target 2026.1 per the `Xilinx/kria-vitis-platforms`
  `main` branch.
- **Known issue (2025.x)**: `write_hw_platform` can silently omit
  processor-specific metadata if called before `impl_design` completes. Always
  call `write_hw_platform` only after `write_bitstream` succeeds.

### Code Example

```tcl
# Vivado 2025.1 correct XSA export sequence (non-project mode)
# Do NOT call write_hw_platform before write_bitstream

route_design
write_bitstream -force output/kv260_top.bit

# Only export XSA after bitstream is confirmed written
if {[file exists output/kv260_top.bit]} {
    write_hw_platform -fixed -force \
        -include_bit \
        -file output/kv260_top.xsa
    puts "XSA exported successfully"
} else {
    error "Bitstream not found — aborting XSA export"
}
```

### Relevance to Your Project

If you upgrade from Vivado 2024.x to 2025.1, re-open the block design and
accept the GT Wizard upgrade if prompted (even if you don't use GT/SerDes —
the prompt may appear due to indirect IP dependencies). Re-run
`validate_bd_design` immediately after; any new DRCs indicate IP
incompatibilities introduced by the upgrade. For Vitis, the new Unified IDE
component flow means your existing `.vitis` workspace may need to be
recreated from the new XSA — keep the old workspace on a branch until the
new one is confirmed working.
