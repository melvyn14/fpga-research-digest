# FPGA Research Digest - 2026-10-29

## Executive Summary
- **BRAM read latency is 1 cycle** on the RAMB36E2 primitive; extra output FFs configured in the Block Memory Generator add latency beyond that. For your AXI-BRAM demo, account for this 1-cycle delay when checking read-back data in the C test loop.
- **Stack default in Vitis bare-metal is only 400 bytes; heap default is zero** — `xil_printf` (and standard `printf`) uses heap internally. Always allocate at least 4–8 KB heap in `lscript.ld` or your demo may crash silently without stack/heap overflow detection.
- **Vitis 2025.2 deprecates Classic Vitis IDE** — the Unified IDE is now the default. Plan migration now if you are on 2025.1 Classic workflows to avoid being forced into the change unexpectedly.
- **The 0xA0000000 BRAM base address is confirmed** for HPM0-attached BRAM controllers on the KV260; BRAM1 at 0xA0010000 matches standard address-editor spacing. The address editor in Vivado is the authoritative source — verify yours matches your `main.c` constants.
- **`assign_bd_address` TCL command** fully automates AXI address assignment in batch mode and is the safest way to re-generate the block design without manual GUI clicks. Prefer explicit TCL over automation in `create_bd.tcl` to avoid the known conflict when two address segments share a range.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings
- A transfer completes when **both `VALID` and `READY` are asserted on the same clock edge**. A common mistake is de-asserting `VALID` before `READY` goes high; per the AXI spec, once `VALID` is asserted it must remain high until the handshake completes.
- **Vivado's generated AXI-Lite slave example core has known protocol bugs.** ZipCPU's formal verification flow found multiple errors when its properties were applied to Xilinx's example slave — treat auto-generated slaves as starting points, not references.
- The **AXI Register Slice IP** inserts a 1-cycle pipeline stage that cuts long combinational paths on AXI buses without changing protocol semantics. Useful if timing fails on the path between your Zynq MPSoC HP master and the BRAM controller.
- **Protocol errors are invisible to synthesis.** Insert `sim_axi_protocol_checker` or use the built-in AXI Protocol Checker during simulation to catch handshake violations early.
- BRAM **read latency is 1 clock cycle** for the output register stage in the RAMB36E2 primitive. If you configure the Block Memory Generator with "Register" output or add pipeline stages, read latency increases accordingly.

### Code Example
```vhdl
-- Minimal AXI-Lite read handshake (slave side)
process(clk)
begin
  if rising_edge(clk) then
    if rst = '1' then
      s_axi_arready <= '0';
      s_axi_rvalid  <= '0';
    else
      -- Accept the address in one cycle
      if s_axi_arvalid = '1' and s_axi_arready = '0' then
        s_axi_arready <= '1';
        read_addr_r   <= s_axi_araddr(ADDR_BITS-1 downto 2);
      else
        s_axi_arready <= '0';
      end if;
      -- Return data one cycle after address accepted
      if s_axi_arready = '1' then
        s_axi_rdata  <= reg_file(to_integer(unsigned(read_addr_r)));
        s_axi_rvalid <= '1';
        s_axi_rresp  <= "00"; -- OKAY
      elsif s_axi_rvalid = '1' and s_axi_rready = '1' then
        s_axi_rvalid <= '0'; -- de-assert once master accepts
      end if;
    end if;
  end if;
end process;
```

### Relevance to Your Project
Your `kv260_top.vhd` wraps the Block Memory Generators exposed via AXI-Lite. Ensuring the slave follows the handshake rules above (never de-asserting `ARVALID` early, properly gating `RVALID`) prevents silent read failures that could cause spurious FAIL prints even when data was written correctly to BRAM0 (0xA0000000) and BRAM2 (0xA0010000).

## Vivado Block Design / IP Integrator

### Key Findings
- The **Address Editor tab** only appears when the block design contains a bus master (e.g., the Zynq PS). Without a master present, the tab is hidden.
- **Automation can assign conflicting ranges.** When two address segments share an overlapping range, the automator fails silently or assigns incorrect values. Always verify the address map after running automation.
- The recommended address range for an AXI BRAM Controller targeting a single BRAM is **64 K** (0x10000). Set this explicitly in the Range column of the Address Editor.
- Running **`validate_bd_design`** in TCL after every structural change catches unconnected mandatory ports (e.g., missing clock/reset on BRAM controllers) before synthesis.
- **Re-generating IP output products** is required after any IP parameter change; otherwise synthesis uses stale DCP files and changes silently disappear.

### Code Example
```tcl
# Assign a specific base address + range to a BRAM controller slave
set_property offset 0xA0000000 [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property range  0x10000    [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]

# Or use the auto-assigner for unmapped segments (works in batch):
assign_bd_address

# Always validate before generating the wrapper
validate_bd_design
```

### Relevance to Your Project
Your `create_bd.tcl` likely uses `assign_bd_address`. Confirming that BRAM0 lands at `0xA0000000` and BRAM2 at `0xA0010000` in the generated `xsa` is essential — a mis-assigned slave causes every read and write in `main.c` to hit unmapped space and return bus errors instead of data.

## Vivado TCL Scripting

### Key Findings
- **Batch mode** is the recommended way to run non-project scripts: `vivado -mode batch -source create_bd.tcl`. This avoids the GUI license overhead and is CI-friendly.
- **Non-project mode discards the in-memory state** at session end unless you call `write_checkpoint`. Add a `write_checkpoint` step after synthesis and implementation to preserve results.
- **Source file order matters.** In non-project mode, files are compiled in the order `read_vhdl` / `read_xdc` commands appear in the script. Put constraint files after all RTL reads.
- One benchmark (Vivado 2024.2, single design) found non-project TCL mode to be no faster than the GUI — sometimes slower. Use batch mode for repeatability, not raw speed.
- `get_bd_addr_segs` with explicit segment names is more reliable than relying on automation when you have a fixed address map — it fails loudly if the segment name changes rather than silently assigning the wrong address.

### Code Example
```tcl
# Minimal non-project batch flow for KV260 synthesis + implementation
read_vhdl   ../vhdl/kv260_top.vhd
read_xdc    ../xdc/kv260_top.xdc

# Synthesize
synth_design -top kv260_top -part xck26-sfvc784-2LV-c
write_checkpoint -force ./checkpoints/post_synth.dcp

# Implement
opt_design
place_design
route_design
write_checkpoint -force ./checkpoints/post_route.dcp

# Outputs
write_bitstream -force ./outputs/kv260_top.bit
write_debug_probes -force ./outputs/kv260_top.ltx
```

### Relevance to Your Project
Your `create_bd.tcl` automates the block design. Wrapping it in a top-level batch script that calls `create_bd.tcl` → `generate_target all` → `make_wrapper` → `synth_design` gives you a fully reproducible one-command build that can run in CI without any GUI interaction.

## Vitis Bare-Metal / Standalone

### Key Findings
- **Default stack: 400 bytes; default heap: 0 bytes.** This is the Vitis standalone BSP default. `xil_printf` is a lightweight printf that avoids floating-point, but even it uses the heap internally for format buffering. Allocate at least 4–8 KB heap in `lscript.ld`.
- **Stack grows downward** and can silently overwrite heap. No guard page exists in bare-metal — an overflow corrupts data without any exception. Size generously and check the `.map` file for actual usage.
- `xil_printf` does **not** support `%f` or floating-point formats. Use integer conversions and scale manually if you need to print decimal fractions.
- The Vitis BSP for Cortex-A53 bare-metal sets up the **MMU with a flat 1:1 physical-to-virtual map** by default. The PL AXI address region (0xA0000000+) is device memory in this map; read/write barriers (`dsb()` / `dmb()`) are important after MMIO writes if you check read-back data immediately.
- **Linker script heap/stack section** lives in `lscript.ld` under the `src/` folder. Edit `_HEAP_SIZE` and `_STACK_SIZE` there, not in the BSP settings GUI (which only affects new project generation, not rebuilds).

### Code Example
```c
/* Recommended minimum bare-metal I/O write + read-back pattern for AXI-BRAM */
#include "xil_io.h"
#include "xil_printf.h"

#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL
#define TEST_OFFSET 0x00000000UL
#define TEST_PATTERN 0xDEADBEEFUL

int test_bram(u32 base) {
    Xil_Out32(base + TEST_OFFSET, TEST_PATTERN);
    /* Ensure write completes before read-back */
    dsb();
    u32 val = Xil_In32(base + TEST_OFFSET);
    if (val == TEST_PATTERN) {
        xil_printf("BRAM @ 0x%08X: PASS\r\n", base);
        return 0;
    }
    xil_printf("BRAM @ 0x%08X: FAIL (got 0x%08X)\r\n", base, val);
    return -1;
}
```

### Relevance to Your Project
Your `main.c` writes patterns and reads them back. Adding `dsb()` between the write and read-back call ensures the AXI transaction completes before you sample the result. Without the barrier, the Cortex-A53's store buffer might return a cached value, masking real bus errors.

## XDC Timing Constraints

### Key Findings
- **Recommended XDC constraint order (UG903):** Clock definitions → I/O delays → Clock groups → Timing exceptions. Clock groups (`set_clock_groups`) have **higher precedence** than `set_false_path`, even when a false path is added later.
- `set_clock_groups -asynchronous` silences cross-domain timing reports but does **not** make the crossing safe; you still need proper synchronizers in RTL.
- **I/O delay constraints** (`set_input_delay`, `set_output_delay`) have minimal impact on runtime and their order within the I/O section is flexible.
- For a bare-metal AXI-BRAM design with only the PS clock driving PL logic, you typically need just a `create_clock` for any PL-only clocks (PS clocks are auto-constrained by the PS IP) and `set_clock_groups -asynchronous` between the PS-derived and any external oscillator clocks.
- **`USE_EMBEDDED_CONSTRAINT = 0`** on BRAM primitives may trigger Vivado Timing-6 or Timing-7 warnings. Leave the BRAM constraint attribute at its default value.

### Code Example
```tcl
# Minimal KV260 XDC for a PL design clocked from PS (no external PL clock)
# PS-derived clocks (pl_clk0) are auto-constrained by the Zynq PS IP.
# Only add this if you have a separate PL oscillator input:

# create_clock -period 10.000 -name pl_osc_clk [get_ports pl_clk_in]

# Mark PS internal clocks as asynchronous to any free-running PL clock
# set_clock_groups -asynchronous \
#     -group [get_clocks -include_generated_clocks clk_pl_0] \
#     -group [get_clocks -include_generated_clocks pl_osc_clk]

# I/O constraints for UART TX (example - adjust for actual pin)
# set_output_delay -clock [get_clocks clk_pl_0] -max 2.0 [get_ports uart_txd]
# set_output_delay -clock [get_clocks clk_pl_0] -min 0.5 [get_ports uart_txd]

# False path on async reset input (if used)
# set_false_path -from [get_ports sys_resetn]
```

### Relevance to Your Project
For a PS-only-clocked design like the KV260 AXI-BRAM demo, the XDC typically only needs I/O constraints for any external pins (UART, LEDs). The AXI clock comes from `pl_clk0` generated by the Zynq PS IP, which is auto-constrained — no `create_clock` needed for it.

## Kria KV260 / K26 SoM

### Key Findings
- **MIO bank layout:** MIO500 = QSPI, SPI, I2C, eMMC (onboard SOM peripherals); MIO501 = PMU power management + user I/O; MIO502 = user-defined I/O. The I2C lines for power management and the EEPROM are on MIO[25:24] in bank 500.
- **BRAM is confirmed at 0xA0000000** when the AXI BRAM Controller is attached to the HPM0 LPD AXI port. Multiple community examples and AMD tutorials place it there. Your two-BRAM layout (0xA0000000 / 0xA0010000) is consistent with 64 K spacing.
- **Bare-metal targets Cortex-A53 #0.** The Vitis debugger and Vitis platform both target `Cortex-A53 #0` for bare-metal standalone applications.
- **KV260 vs. KR260 carrier differences:** The PMU overlay configuration separates base-SOM MIO from carrier-specific MIO. GEM1 RGMII and GEM0 SGMII Ethernet are enabled on KR260 but not KV260. Don't copy KR260 pin assignments to a KV260 project.
- **Boot slot:** For bare-metal, mark the boot image as bootable in the SOM boot flow. The SOM boots from the marked Image A slot on every power cycle. This differs from SD-card boot used in PetaLinux flows.

### Code Example
```tcl
# Vivado XDC: Constrain the KV260 onboard LED (example, verify against schematic)
# The KV260 exposes 4 user LEDs via the carrier board MIO or PL I/O.
# Check the KV260 schematic (PG-02098) for exact net names and bank voltages.

# Example: PL LED on bank 45 (1.8V) - adjust pin and bank to match your design
set_property PACKAGE_PIN  H12          [get_ports {led[0]}]
set_property IOSTANDARD   LVCMOS18     [get_ports {led[0]}]
set_false_path -to [get_ports {led[0]}]   ;# LEDs are async outputs
```

### Relevance to Your Project
Confirming the address space and target core in your Vitis platform matches the Vivado XSA's address map is the single most common source of FAIL prints in a KV260 bare-metal AXI-BRAM demo. If the platform was generated from an older XSA after a block-design change, regenerate and re-export the XSA before rebuilding.

## AMD/Xilinx Tool Updates

### Key Findings
- **Vitis 2025.1.1 patch** released September 17, 2025 — addresses known regressions from the 2025.1 base release. Install 2025.1.1 if you are on 2025.1 base.
- **Vitis Unified IDE is now the default as of 2025.2; Classic Vitis IDE is deprecated.** If you are targeting 2025.1, plan your migration to the Unified IDE now before Classic is removed.
- **Known issue in Vivado 2025.1:** ILA insertion triggers an incorrect LUT connection error in `axi_dbg_hub`. Workaround: avoid ILA-based `axi_dbg_hub` insertion in 2025.1; upgrade to 2025.1.1 or later.
- **Windows installer issue (2025.1):** The cable driver installation option is missing from the Windows installer. Manually install cable drivers from the Vivado install directory (`<install>/data/xicom/cable_drivers/`).
- **GUI instability after opening the Elaborated Design NoC view** is a known Vivado 2025.x issue. Save your work before opening the NoC view.

### Code Example
```bash
# Check your installed Vivado/Vitis version from the terminal
# (run from a sourced Vivado environment)
vivado -version
# Expected for latest patched release: Vivado v2025.1.1

# Verify the cable driver is loaded on Linux:
lsmod | grep xillybus
# or for older Digilent/Xilinx drivers:
lsmod | grep ftdi_sio

# Install cable drivers manually on Linux if missing

```

### Relevance to Your Project
The `axi_dbg_hub` ILA insertion bug directly affects AXI debug in Vivado 2025.1. If you are adding ILA probes to monitor AXI transactions on your BRAM paths (useful for debugging FAIL conditions), upgrade to 2025.1.1 first or use ChipScope manually without the automated ILA flow.
