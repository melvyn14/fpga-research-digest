# FPGA Research Digest - 2026-09-24

## Executive Summary
- **AXI-Lite BRAM timing pitfall**: The AXI BRAM Controller v4.x asserts write-enable one extra clock early due to BRAM-enable signal gating; always tie `BRAM_EN` high or gate it properly — directly applicable to your BRAM0/BRAM2 write path.
- **JTAG boot is the fastest debug loop on KV260**: Use `PSU_INIT.TCL` + XSDB to load your bitstream + ELF over JTAG without a full FSBL, drastically shortening the edit-build-test cycle on bare-metal.
- **`apply_bd_automation` in TCL reduces wiring errors**: Use this Vivado command after `connect_bd_intf_net` to let the tool wire clocks, resets, and AXI interconnects automatically; manual `connect_bd_net` for clk/rst is a common source of missed connections.
- **Vitis 2025.2+ xil_printf requires explicit BSP include path**: `xil_printf.h` is no longer implicitly on the include path; you must reference it via `#include "xil_printf.h"` and confirm BSP `standalone` version ≥ 8.1 in your platform settings.
- **Vivado 2026.1 introduces tiered licensing**: Starting 2026.1 the tool moves to a new tiered model — standard/enterprise splits may affect which devices and features are available; verify your license covers Zynq UltraScale+ (K26).

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings
- AXI handshake rule: once `VALID` is asserted by an initiator, it **must not be de-asserted** until the corresponding `READY` is seen — violating this can cause permanent bus stall.
- All AXI signals must be registered; combinatorial paths between AXI input/output violate the protocol and cause timing failures.
- The AXI BRAM Controller raises `BRAM_ARREADY` one clock after it receives `ARVALID`, then takes two more cycles before asserting `RVALID`/`RDATA` — plan your read-latency polling loop accordingly.
- A documented silicon-level bug: the AXI BRAM Controller v4.x asserts write-enable one clock **early** (duration becomes N+1 instead of N clocks); root cause is `BRAM_EN` not being used to gate the write enable. Fix: connect `BRAM_EN` properly or rely on ECC to guard stale writes.
- AXI-Lite is a simplified single-beat-only subset of AXI4 — there are no burst transactions, no AWLEN/ARLEN signals, and address/data channels have no dependency ordering, making it ideal for control registers and BRAM controllers in this demo.

### Code Example
```c
/* Bare-metal AXI-Lite BRAM read with explicit latency handling */
#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL

static inline void bram_write32(uint32_t base, uint32_t offset, uint32_t val) {
    *(volatile uint32_t *)(base + offset) = val;
    /* AXI-Lite write: no burst, address and data presented simultaneously */
    __asm__ volatile("dsb sy"); /* data sync barrier ensures write committed */
}

static inline uint32_t bram_read32(uint32_t base, uint32_t offset) {
    __asm__ volatile("dsb sy");
    return *(volatile uint32_t *)(base + offset);
    /* BRAM controller latency: ARVALID→RVALID is ~3 clock cycles; Cortex-A53
       load instruction stalls naturally — no explicit delay needed for single reads */
}
```

### Relevance to Your Project
Your `main.c` writes patterns to BRAM0 (0xA0000000) and BRAM2 (0xA0010000) over AXI-Lite. The extra-clock write-enable bug means a single 32-bit write at offset 0 may corrupt offset -4 (underflow) or write a stale zero to offset +4 unless `BRAM_EN` is handled correctly in your block design. Verify the write-enable waveforms in simulation with an ILA before trusting PASS results.

## Vivado Block Design / IP Integrator

### Key Findings
- Use **File → Export → Export Block Design** to generate a reproducible `.tcl` that recreates the entire block diagram; commit this instead of the `.bd` binary for clean git diffs.
- `apply_bd_automation` after placing IP resolves most clock/reset wiring automatically; manually wiring `ACLK`/`ARESETN` is the #1 source of forgotten connections.
- The **Address Editor** in IP Integrator must assign a base address to each AXI slave; unassigned slaves produce `[BD 41-237]` warnings at validation and the address space is left unmapped — causing hard faults at runtime.
- Vivado 2025.2 adds **SystemVerilog Interface support** in block design with automatic AXI wrapper generation — useful if you later want to instantiate a custom VHDL IP with an AXI SV interface.
- Always run `validate_bd_design` in your TCL script before synthesis; it catches unconnected pins and clock-domain issues before they become cryptic timing errors.

### Code Example
```tcl
# After placing zynq_ultra_ps_e and axi_bram_ctrl IPs:
apply_bd_automation -rule xilinx.com:bd_rule:axi4 \
  -config { Clk_master {Auto} Clk_slave {Auto} Clk_xbar {Auto} \
            Master {/zynq_ultra_ps_e_0/M_AXI_HPM0_FPD} \
            Slave {/axi_bram_ctrl_0/S_AXI} \
            ddr_seg {Auto} intc_ip {New AXI Interconnect} \
            master_apm {0} } [get_bd_intf_pins axi_bram_ctrl_0/S_AXI]

# Explicitly set BRAM address to match your bare-metal base address:
set_property offset 0xA0000000 [get_bd_addr_segs \
  {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property range 64K [get_bd_addr_segs \
  {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]

validate_bd_design
```

### Relevance to Your Project
Your `create_bd.tcl` should include `validate_bd_design` and explicit address assignments for both BRAM0 (0xA0000000) and BRAM2 (0xA0010000). The 64K range is adequate for a single BRAM but verify it matches the `depth × width / 8` of your Block Memory Generator configuration.

## Vivado TCL Scripting

### Key Findings
- **Non-project mode** avoids the `.xpr` project overhead: use `read_vhdl`, `read_xdc`, `synth_design`, `opt_design`, `place_design`, `route_design`, `write_bitstream` directly in sequence — faster in CI, produces identical results.
- `create_bd_cell -type ip -vlnv xilinx.com:ip:<name>:<ver>` is the primitive for placing IP; omitting the version picks the latest installed, which can break reproducibility across tool versions — always pin the version.
- `connect_bd_intf_net` connects AXI interface buses (master↔slave bus objects), while `connect_bd_net` connects individual signals (clock, reset, GPIO pins) — mixing these is a common TCL scripting error that produces silent failures.
- Exporting a block design TCL and then stripping `create_project`/`open_project` calls gives a clean non-project BD script; wrap it with `create_bd_design "design_1"` and `make_wrapper -files [get_files design_1.bd] -top`.
- Use `set_msg_config -id {BD 41-1306} -new_severity ERROR` to escalate BD warnings to errors in automated flows — prevents silent misconfigurations from reaching bitstream.

### Code Example
```tcl
# Minimal non-project batch synthesis + implementation flow
read_vhdl   ../vhdl/kv260_top.vhd
read_bd     ../bd/design_1.bd
read_xdc    ../xdc/kv260_timing.xdc

synth_design  -top kv260_top -part xck26-sfvc784-2LV-c
opt_design
place_design
phys_opt_design
route_design

write_bitstream -force ../output/kv260_top.bit
write_debug_probes -force ../output/kv260_top.ltx

# Report critical warnings to stdout for CI log parsing
report_timing_summary -warn_on_violation -file ../output/timing_summary.rpt
```

### Relevance to Your Project
Your existing `create_bd.tcl` can be extended with the lines above to create a fully headless build pipeline. Running `vivado -mode batch -source build.tcl` from a Makefile means your entire bitstream is reproducible from a single command — essential for the KV260 demo's CI story.

## Vitis Bare-Metal / Standalone

### Key Findings
- In Vitis 2025.2, `xil_printf.h` is **not** automatically included via a legacy transitive header — add `#include "xil_printf.h"` explicitly; missing this causes `implicit declaration` warnings that silently use the wrong printf variant.
- The Standalone BSP does **not** initialize the GIC (interrupt controller) by default; if you add interrupts later, call `XScuGic_CfgInitialize` explicitly and register your handler before enabling IRQs on the CPU.
- For KV260 UART: the hardware BSP defaults `standalone_stdin`/`standalone_stdout` to `psu_uart_0`, but the KV260 carrier routes the USB-UART to **UART1** (MIO 26/27). Change BSP settings to `psu_uart_1` or your `xil_printf` output will appear on the wrong port.
- `Xil_DCacheFlushRange` / `Xil_DCacheInvalidateRange` are mandatory before DMA or PL-accessible memory regions to prevent cache coherency issues when the PL reads memory the PS has written.
- Linker script `lscript.ld` places `.text` in DDR by default; for ultra-low latency access (e.g. tight polling loops), move hot code sections to OCM (0xFFFC0000, 256 KB) via a custom memory region.

### Code Example
```c
#include "xparameters.h"
#include "xil_printf.h"   /* Must be explicit in Vitis 2025.2+ */
#include "xil_cache.h"

#define BRAM0_BASE  0xA0000000UL
#define TEST_WORDS  16

int main(void) {
    volatile uint32_t *bram0 = (volatile uint32_t *)BRAM0_BASE;
    uint32_t errors = 0;

    /* Flush D-cache so PL sees PS writes immediately */
    Xil_DCacheFlushRange((UINTPTR)BRAM0_BASE, TEST_WORDS * 4);

    for (uint32_t i = 0; i < TEST_WORDS; i++)
        bram0[i] = 0xDEAD0000 | i;

    Xil_DCacheInvalidateRange((UINTPTR)BRAM0_BASE, TEST_WORDS * 4);

    for (uint32_t i = 0; i < TEST_WORDS; i++) {
        uint32_t expected = 0xDEAD0000 | i;
        if (bram0[i] != expected) {
            xil_printf("FAIL @ [%02u]: expected 0x%08X got 0x%08X\r\n",
                       i, expected, bram0[i]);
            errors++;
        }
    }
    xil_printf(errors ? "BRAM0 FAIL (%u errors)\r\n"
                      : "BRAM0 PASS\r\n", errors);
    return 0;
}
```

### Relevance to Your Project
If your PASS/FAIL output isn't appearing on the USB-UART terminal, verify the BSP `stdout` setting points to `psu_uart_1`. The `Xil_DCacheFlushRange` calls are likely **missing** in your current `main.c` — without them, a write might sit in the Cortex-A53 L1/L2 cache and never reach the PL BRAM, causing a spurious PASS (reads hit cache) or unpredictable FAIL.

## XDC Timing Constraints

### Key Findings
- `set_input_delay` and `set_output_delay` specify the **external path delay** relative to a clock edge at the FPGA interface, in nanoseconds; values can be negative when data arrives before the clock edge.
- For AXI-only internal designs (like your KV260 demo) where all I/O is through the PS, you often only need `create_clock` for external differential clocks; `set_input/output_delay` applies to the PL I/O pins, not to AXI ports routed through the PS.
- Use `set_clock_groups -asynchronous -group {clk_pl_0} -group {clk_pl_1}` to tell the timing engine not to analyze paths between unrelated clock domains — critical when running the AXI clock and a second PL clock at different rates.
- The Constraint Wizard (`Tools → Timing → Constraint Wizard`) in Vivado auto-detects unconstrained clocks and suggests `set_input/output_delay` commands — run it after initial synthesis to catch missing constraints.
- For the Kria KV260, the PL reference clock (300 MHz via `pl_clk0` from the PS block) is created automatically from the block design; no manual `create_clock` is needed for it in the XDC.

### Code Example
```tcl
# kv260_timing.xdc — minimal constraints for KV260 AXI-BRAM demo

# PL system clock from PS block (auto-created in BD, but explicit for documentation):
# create_clock -period 3.333 -name clk_pl_0 [get_pins zynq_ultra_ps_e_0/pl_clk0]

# If using an external PL clock input from the carrier (e.g. differential 200 MHz):
create_clock -period 5.000 -name clk_ext \
  [get_ports clk_p]
set_input_jitter clk_ext 0.050

# Prevent timing analysis across unrelated clocks (if using multiple PL clocks):
set_clock_groups -asynchronous \
  -group [get_clocks clk_pl_0] \
  -group [get_clocks clk_ext]

# False path on async reset (assert path not timing-critical):
set_false_path -from [get_ports rst_n]
```

### Relevance to Your Project
Since your KV260 demo uses only `pl_clk0` from the PS as the AXI clock and has no external PL I/O other than reset, your XDC can be minimal. The most important constraint to add is `set_false_path` on your reset input to prevent the timing engine from flagging the asynchronous reset assertion path as a violation.

## Kria KV260 / K26 SoM

### Key Findings
- KV260 ships with QSPI32 as the default boot mode; the SOM's onboard QSPI holds the pre-loaded boot firmware — you can overwrite user partitions with your own bare-metal BOOT.BIN.
- **Fastest bare-metal debug loop**: set boot mode to JTAG (remove SD card, no eMMC boot image), then use XSDB to load `psu_init.tcl` + bitstream + ELF without going through FSBL; this avoids a 20-30 second FSBL/Linux boot on every iteration.
- The KV260 carrier routes USB-UART to **MIO 26/27** (UART1), not MIO 18/19 (UART0) — a common misconfiguration that causes blank serial terminals on bare-metal.
- AXI HPM0_FPD (High Performance Master) is the recommended PS-to-PL AXI port for non-cache-coherent BRAM access; HPM0_LPD is available but has lower bandwidth.
- The K26 SoM MIO is partially locked by the SOM hardware design (QSPI, eMMC, I2C PMICs) — only the carrier-exposed MIO/EMIO signals are freely usable for custom PL peripherals.

### Code Example
```tcl
# XSDB script for JTAG-based KV260 bare-metal load (no FSBL needed)
# Run: xsdb load_baremetal.tcl

connect
target 1
# Initialize PS (replaces FSBL for JTAG debug)
source [lindex $argv 0]  ;# psu_init.tcl generated by Vitis platform

target 1
dow [lindex $argv 1]     ;# path to kv260_top.bit (bitstream)

target 2                  ;# Cortex-A53 Core 0
rst -processor
dow [lindex $argv 2]     ;# path to kv260_axi_bram.elf
con
```

```bash
# Invoke with:
xsdb load_baremetal.tcl psu_init.tcl kv260_top.bit kv260_axi_bram.elf
```

### Relevance to Your Project
Using XSDB JTAG boot means you iterate your bare-metal C without burning QSPI each time. Pair this with a `Makefile` target that rebuilds the ELF and re-runs the XSDB script — your full edit→build→flash→observe loop can drop from minutes to under 30 seconds.

## AMD/Xilinx Tool Updates

### Key Findings
- **Vivado 2025.2**: Added SystemVerilog Interface support in block design (automatic AXI wrapper generation), reduced PhysOpt compile time, BUFG_FABRIC replication per-SLR for high-fanout nets, and module referencing for RTL with NoC XPMs in block design.
- **Vitis 2025.2**: Enhanced DSP Library (Cumulative Sum, Euclidean Distance, Function Approximation), C++ Functional Simulation (early access), and Hardware-in-the-Loop via MATLAB/Python testbench (early access).
- **Vivado 2026.1**: New device support (Versal RF, AI Edge Gen 2, Prime Gen 2, Spartan UltraScale+), and a new **tiered licensing model** — standard vs. enterprise tiers; verify K26/Zynq UltraScale+ is in your tier before upgrading.
- **Vitis 2026.1**: Production Hardware-in-the-Loop, Cholesky & QRD DSP library additions, AI Engine API new data types for Versal AI Edge Gen 2, improved AIE Compiler with Code Coverage.
- **Known issue (Vitis 2026.x)**: AMD's support portal lists open known issues for 2026.x — check article `000040220` before upgrading if your project is stable on 2025.1/2025.2.

### Code Example
```tcl
# Vivado 2025.2+ non-project batch build with PhysOpt enabled
# (PhysOpt compile time is reduced in 2025.2)
synth_design  -top kv260_top -part xck26-sfvc784-2LV-c \
              -flatten_hierarchy rebuilt
opt_design    -directive Explore
place_design  -directive AggressiveExplore
phys_opt_design -directive AggressiveFanoutOpt  ;# faster in 2025.2
route_design  -directive AggressiveExplore
write_bitstream -force ../output/kv260_top.bit

# Check timing closure
set wns [get_property SLACK [get_timing_paths -max_paths 1 -nworst 1 \
         -setup -significant_digits 3]]
if {$wns < 0} {
    puts "ERROR: Timing not met, WNS = $wns ns"
    exit 1
}
puts "Timing PASSED, WNS = $wns ns"
```

### Relevance to Your Project
You are currently on **Vivado/Vitis 2025.1**. The 2025.2 PhysOpt speedup is meaningful for iterative builds. However, before upgrading, check the Vitis 2025.2 known issues for Zynq UltraScale+ bare-metal flows — particularly the `xil_printf.h` include path change noted in this digest. Your `main.c` may need a header addition after upgrading.
