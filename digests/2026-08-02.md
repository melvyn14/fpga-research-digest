# FPGA Research Digest - 2026-08-02

## Executive Summary

- **AXI-Lite deadlock hazard**: Never make a slave's `RVALID` conditional on `RREADY` — this creates the "too polite master" deadlock. Xilinx's own AXI Ethernet-lite core shipped with this bug. Your BRAM read path must drive `RVALID` solely from `ARVALID && ARREADY`.
- **Block Memory Generator deprecated in 2025.1/2025.2**: AMD has moved away from the Block Memory Generator IP for standalone RTL use; use XPM macros (`XPM_MEMORY_SPRAM`, etc.) in new designs, or keep BMG inside block designs where it still works reliably.
- **AXI full peripheral address bug in Vivado 2025.x**: A confirmed forum bug masks address bits above bit 9 on AXI full peripherals — BRAM0 at `0xA0000000` and BRAM2 at `0xA0010000` may both map correctly since the AXI-Lite controller only uses the low 12-16 bits, but watch for address aliasing if you expand the address space.
- **Kria bare-metal boot**: Use the `zynq_ultra_ps_e_0` HPM0_FPD AXI master (32-bit GP port) for AXI-Lite BRAM access at `0xA000_xxxx`; enable only HPM0 in the PS configuration to keep the design minimal.
- **Vivado 2025.2 AXI SmartConnect**: New ultra-low-area mode available via `STRATEGY` parameter — useful if your block design grows beyond the current two-BRAM demo.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- **The VALID-before-READY rule**: A master may never wait for `READY` before asserting `VALID`. Violating this creates a deadlock where the slave waits for `VALID` to raise `READY`, and the master waits for `READY` to assert `VALID`. Neither proceeds.
- **Independent write channels**: `AWVALID`/`AWREADY` (write address) and `WVALID`/`WREADY` (write data) are independent channels. The AXI4 spec forbids `AWVALID` from being gated by `WREADY` or vice versa. Both handshakes must complete before the slave can issue `BVALID`.
- **RVALID implementation rule**: `RVALID` must be set based only on `ARVALID && ARREADY` — never conditioned on `RREADY`. Xilinx shipped a violating implementation in their AXI Ethernet-lite controller.
- **Backpressure propagation**: If a master holds `BREADY` or `RREADY` low, the slave must hold its `READY` signals low. These are the signals most commonly forgotten in simulation-only testing.
- **Latch flag hygiene**: In pipelined slave implementations, clear handshake-done flags (`aw_hs_done`, `w_hs_done`) on the response handshake (`BVALID && BREADY`), not prematurely.

### Code Example

```vhdl
-- AXI-Lite read response: RVALID must NOT depend on RREADY
process(clk)
begin
  if rising_edge(clk) then
    if rst = '1' then
      s_axi_rvalid <= '0';
      s_axi_rdata  <= (others => '0');
    elsif s_axi_arvalid = '1' and s_axi_arready = '1' then
      -- Latch address and assert RVALID immediately on address handshake
      s_axi_rdata  <= bram_rd_data;  -- combinational read from BRAM
      s_axi_rvalid <= '1';
    elsif s_axi_rready = '1' then
      -- Deassert only after master accepts (RREADY high while RVALID high)
      s_axi_rvalid <= '0';
    end if;
  end if;
end process;
```

### Relevance to Your Project

Your AXI-Lite slave wrapper driving BRAM0 (`0xA0000000`) and BRAM2 (`0xA0010000`) must follow this pattern for read responses. If using Xilinx's generated AXI-Lite slave template from Vivado 2018–2022, verify that `RVALID` is not incorrectly gated by `RREADY` — older Xilinx-generated templates have shipped with this exact bug.

## Vivado Block Design / IP Integrator

### Key Findings

- **Validate design propagates parameters**: Always run *Validate Design* (F6) after adding/configuring IPs. This propagates bus-width and link-type negotiation between IPs (e.g., AXI4 vs AXI4-Lite mode selection on BRAM Controller, BRAM operation mode).
- **Avoid spaces in block design names and paths**: Vivado fails silently or errors unpredictably when the block design name or project path contains spaces. Use underscores or CamelCase.
- **Explicit TCL connections preferred**: When scripting block designs in TCL, use explicit `connect_bd_intf_net` commands rather than relying on `apply_bd_automation`. Automation reduces surprises in interactive use but can produce unintended connections in scripts.
- **BRAM controller port B**: To expose BRAM Port B externally (for custom logic), configure Port B as an external port on the Block Memory Generator. `BRAM_PORTA` goes to the AXI BRAM Controller; `BRAM_PORTB` becomes an external port.
- **Minimum BRAM Controller depth**: The AXI BRAM Controller IP requires a minimum BRAM depth of 512 bytes. Do not configure Block Memory Generator below this.
- **Block Memory Generator deprecated for standalone RTL** (2025.1/2025.2): AMD recommends `XPM_MEMORY_SPRAM` / `XPM_MEMORY_TDPRAM` for new RTL-level instantiations. BMG is still fully supported inside block designs.

### Code Example

```tcl
# Add and configure AXI BRAM Controller + Block Memory Generator pair
set axi_bram_ctrl_0 [create_bd_cell -type ip \
    -vlnv xilinx.com:ip:axi_bram_ctrl:4.1 axi_bram_ctrl_0]
set_property -dict [list \
    CONFIG.SINGLE_PORT_BRAM {1} \
    CONFIG.ECC_TYPE {0} \
] $axi_bram_ctrl_0

set blk_mem_gen_0 [create_bd_cell -type ip \
    -vlnv xilinx.com:ip:blk_mem_gen:8.4 blk_mem_gen_0]
set_property -dict [list \
    CONFIG.Memory_Type {True_Dual_Port_RAM} \
    CONFIG.Write_Depth_A {1024} \
] $blk_mem_gen_0

# Connect BRAM interface (use connect_bd_intf_net for interfaces, not connect_bd_net)
connect_bd_intf_net [get_bd_intf_pins axi_bram_ctrl_0/BRAM_PORTA] \
                    [get_bd_intf_pins blk_mem_gen_0/BRAM_PORTA]
```

### Relevance to Your Project

Your `create_bd.tcl` likely uses `apply_bd_automation` to wire the AXI-Lite master from `zynq_ultra_ps_e_0` to the two BRAM controllers. Replacing automation with explicit `connect_bd_intf_net` calls prevents unexpected clock or reset connections and makes the script fully reproducible across Vivado versions.

## Vivado TCL Scripting

### Key Findings

- **Non-project mode**: In non-project mode, Vivado does not maintain source file lists or run directories automatically. You must call `write_checkpoint` after each synthesis/implementation step and `open_checkpoint` to resume. This is ideal for CI pipelines where the project file is generated from TCL.
- **Batch mode invocation**: `vivado -mode batch -source script.tcl` runs the script headlessly; `-mode tcl` drops into an interactive TCL shell. Use `-nojournal -nolog` flags in CI to suppress journal files.
- **`apply_bd_automation` vs explicit connections**: `apply_bd_automation` is convenient for clock/reset routing but non-deterministic across tool versions. For reproducible scripted builds, call explicit `connect_bd_net`/`connect_bd_intf_net`.
- **Address assignment TCL**: Use `assign_bd_address` and `set_property offset/range` to pin AXI slave addresses deterministically in TCL rather than relying on auto-assign.
- **UG894 (2025.1)**: Updated guide covers querying and modifying in-memory designs using TCL for custom flows.

### Code Example

```tcl
# Non-project mode: read sources, synthesize, implement, write bitstream
read_vhdl    [glob ./vhdl/*.vhd]
read_xdc     [glob ./constraints/*.xdc]
read_ip      [glob ./ip/*.xci]
upgrade_ip   [get_ips]

synth_design -top kv260_top -part xck26-sfvc784-2LV-c
write_checkpoint -force ./checkpoints/post_synth.dcp

opt_design
place_design
route_design
write_checkpoint -force ./checkpoints/post_route.dcp
write_bitstream  -force ./output/kv260_top.bit

# Pin BRAM addresses after block design creation
set seg [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property offset 0xA0000000 $seg
set_property range  64K        $seg
```

### Relevance to Your Project

Your `create_bd.tcl` can be extended with explicit address pinning using `set_property offset` to guarantee `BRAM0` always maps to `0xA0000000` and `BRAM2` to `0xA0010000`, regardless of tool version. Add `write_checkpoint` calls to enable incremental synthesis during iterative development.

## Vitis Bare-Metal / Standalone

### Key Findings

- **`xil_printf` limitations**: `xil_printf` does not support floating-point format specifiers (`%f`, `%e`, `%g`). It interprets `\n` as newline only (not CR+LF). For full `printf` with floats, enable `stdin`/`stdout` in BSP and link against the full newlib `printf` (increases code size significantly).
- **AXI INTC (Interrupt Controller)**: The AXI INTC IP receives multiple PL interrupt inputs and merges them via an AXI4-Lite register interface. The GIC on Zynq UltraScale+ handles both Private Peripheral Interrupts (PPI) and Shared Peripheral Interrupts (SPI). PL interrupts connect via `pl_ps_irq` lines.
- **Linker script regions**: Vitis auto-generates `lscript.ld` with `.text`, `.data`, `.bss`, heap, and stack sections mapped to DDR. Manually edit the script to place `.text` in OCM for faster boot or to enforce strict memory budgets.
- **BSP `sleep` functions**: Use `usleep()` (microseconds) or `sleep()` (seconds) from `xil_io.h` for polling delays in bare-metal. These are busy-wait loops on Cortex-A53 — factor this into your BRAM write/readback timing.
- **Standalone BSP v9.x (2025.x)**: Updated sleep and cache APIs in the 2025.1 standalone BSP. Check release notes for your exact version in the BSP settings.

### Code Example

```c
#include "xil_printf.h"
#include "xil_io.h"

#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL
#define TEST_PATTERN 0xDEADBEEFUL

int verify_bram(u32 base, const char *name) {
    Xil_Out32(base, TEST_PATTERN);
    /* Small delay to ensure write completion through AXI fabric */
    __asm__ volatile("dsb sy" ::: "memory");

    u32 readback = Xil_In32(base);
    if (readback == TEST_PATTERN) {
        xil_printf("[PASS] %s @ 0x%08X: wrote 0x%08X, read 0x%08X\r\n",
                   name, base, TEST_PATTERN, readback);
        return 0;
    } else {
        xil_printf("[FAIL] %s @ 0x%08X: wrote 0x%08X, read 0x%08X\r\n",
                   name, base, TEST_PATTERN, readback);
        return -1;
    }
}

int main(void) {
    int result = 0;
    xil_printf("=== KV260 AXI-BRAM Demo ===\r\n");
    result |= verify_bram(BRAM0_BASE, "BRAM0");
    result |= verify_bram(BRAM2_BASE, "BRAM2");
    xil_printf("Overall: %s\r\n", result == 0 ? "PASS" : "FAIL");
    return result;
}
```

### Relevance to Your Project

Your `main.c` should use `dsb sy` (data synchronization barrier) after each `Xil_Out32` call to guarantee the AXI write has completed before reading back. Without the barrier, the Cortex-A53 write buffer may cause the subsequent `Xil_In32` to return stale data if the BRAM controller pipeline hasn't flushed yet. Also use `\r\n` not `\n` for USB-UART terminals that expect CR+LF.

## XDC Timing Constraints

### Key Findings

- **`set_input_delay` semantics**: Specifies the external path delay from a clock edge to data arriving at the FPGA input pin. Value is in nanoseconds and can be negative (data arrives before the reference clock edge). Format: `set_input_delay -clock <clk> [-max|-min] <ns> [get_ports <port>]`.
- **`set_output_delay` semantics**: Specifies the external setup/hold requirement at the load device after the FPGA output changes. Must be set for both `-max` (setup) and `-min` (hold) for complete coverage.
- **Clock groups**: Use `set_clock_groups -asynchronous` to tell the timing engine that two clocks are unrelated and not to perform cross-clock path analysis between them (e.g., PS internal clocks vs PL fabric clocks).
- **Zynq UltraScale+ internal clocks**: The PS generates `pl_clk0`–`pl_clk3`. Constrain these in XDC using `create_clock` only if they appear as primary clock sources. If routing through BUFG, constrain after the BUFG output.
- **Constraint Wizard**: Vivado's Edit Timing Constraints wizard can generate boilerplate `set_input_delay`/`set_output_delay` commands interactively, which you can then export to XDC.
- **AXI-Lite pure-register designs**: For an AXI-Lite slave that is purely register-based (no external I/O beyond BRAM), you typically only need `create_clock` for `pl_clk0` — `set_input_delay`/`set_output_delay` are only needed for external I/O pins.

### Code Example

```xdc
# Constrain the PL clock sourced from PS (100 MHz example)
create_clock -period 10.000 -name pl_clk0 [get_ports pl_clk0]

# False path for asynchronous PS reset (active-low from PS)
set_false_path -from [get_ports pl_resetn0]

# Example I/O constraints for an external GPIO (not needed for BRAM-only design)
set_input_delay  -clock pl_clk0 -max 2.0 [get_ports {gpio_in[*]}]
set_input_delay  -clock pl_clk0 -min 0.5 [get_ports {gpio_in[*]}]
set_output_delay -clock pl_clk0 -max 3.0 [get_ports {gpio_out[*]}]
set_output_delay -clock pl_clk0 -min 0.5 [get_ports {gpio_out[*]}]

# Async clock groups: isolate PS internal clock from PL fabric
set_clock_groups -asynchronous \
    -group [get_clocks pl_clk0] \
    -group [get_clocks -of_objects [get_pins zynq_ultra_ps_e_0/pl_clk0]]
```

### Relevance to Your Project

Your `kv260_top.vhd` wrapper likely only has `pl_clk0` and `pl_resetn0` as primary ports from the PS. For a pure PS-to-BRAM AXI-Lite design with no external I/O pins beyond UART (which is a PS MIO pin, not a PL port), you only need `create_clock` and `set_false_path` for the reset. This keeps your XDC minimal and avoids spurious timing violations.

## Kria KV260 / K26 SoM

### Key Findings

- **HPM0_FPD AXI master**: The Zynq UltraScale+ PS exposes `M_AXI_HPM0_FPD` (High Performance Master 0, Full Power Domain) — this is the 32-bit GP AXI master used to access PL peripherals at addresses in the `0xA000_0000`–`0xBFFF_FFFF` range. Enable only HPM0 for a minimal BRAM demo.
- **MIO pin allocation on K26**: PS MIO bank 500/501 is present on the SoM. UART0 (USB-UART bridge) is typically routed through MIO pins by the carrier card (KV260 uses UART0 on MIO38/39 via the Digilent onboard USB-UART). These are PS-side MIO pins — no XDC constraints needed.
- **Boot mode**: The KV260 bare-metal flow loads the bitstream and ELF via JTAG (Vitis Debug) or programs them into QSPI/SD. For development, use JTAG boot mode (SW1 on the carrier card) so Vitis can program both PL bitstream and PS ELF directly.
- **`preset.xml` board files**: The KV260 board files in Vivado automatically configure PS clock, DDR, and MIO settings when you run Block Automation on `zynq_ultra_ps_e_0`. Always apply the board preset before customizing PS settings manually.
- **Power domains**: The K26 SoM uses separate power rails for PS (1.0V core, 1.8V I/O) and PL (0.85V core). Sideband signals (VCCO bank 501) are 1.8V. Do not drive these from 3.3V logic directly.
- **2025.1 Custom Platform Tutorial**: AMD published a Kria SOM custom platform creation tutorial (XD101) for Vitis 2025.1 covering platform creation for bare-metal and Vitis AI flows.

### Code Example

```tcl
# Vivado TCL: configure PS for KV260 bare-metal AXI BRAM access
# Apply board preset first, then override for minimal design
set ps [get_bd_cells zynq_ultra_ps_e_0]
apply_bd_automation -rule xilinx.com:bd_rule:zynq_ultra_ps_e_0 \
    -config {apply_board_preset "1"} $ps

# Enable only HPM0_FPD (32-bit AXI master for PL access), disable others
set_property CONFIG.PSU__USE__M_AXI_GP0 {1} $ps   ;# HPM0_FPD = enable
set_property CONFIG.PSU__USE__M_AXI_GP1 {0} $ps   ;# HPM1_FPD = disable
set_property CONFIG.PSU__USE__M_AXI_GP2 {0} $ps   ;# HPM0_LPD = disable
# Set HPM0 data width to 32-bit (sufficient for AXI-Lite BRAM)
set_property CONFIG.PSU__MAXIGP0__DATA_WIDTH {32}  $ps
```

### Relevance to Your Project

Your block design targets HPM0_FPD as the AXI master driving the two BRAM controllers. Confirming that only HPM0 is enabled (GP1 and GP2 disabled) reduces resource usage and eliminates potential address decode conflicts. The USB-UART requires no PL involvement — it routes directly through PS MIO to the onboard FTDI chip on the KV260 carrier card.

## AMD/Xilinx Tool Updates (Vivado/Vitis 2025.x)

### Key Findings

- **Block Memory Generator deprecated (2025.1/2025.2)**: The Block Memory Generator and FIFO Generator IPs are no longer available for direct instantiation from the IP catalog in standalone RTL flows in 2025.1/2025.2. AMD recommends `XPM_MEMORY_SPRAM`, `XPM_MEMORY_TDPRAM`, and `XPM_FIFO_SYNC`/`XPM_FIFO_ASYNC` macros for new RTL designs. BMG still works inside IP Integrator block designs.
- **AXI SmartConnect ultra-low-area mode (2025.2)**: New `STRATEGY` parameter on AXI Switch and AXI SmartConnect enables an ultra-low-area implementation mode — useful when routing multiple AXI-Lite slaves and LUT count matters.
- **AXI full peripheral 1KB address space bug (Vivado 2025.x forum)**: An unresolved community-reported bug in Vivado 2025.x causes AXI full peripheral address bits above bit 9 to be forced to zero, limiting effective address space to 1KB and causing aliasing for larger peripherals. AXI-Lite-only designs (like BRAM controllers) appear unaffected by this specific bug but should be monitored.
- **Vivado 2025.2 release highlights**: Ultra-low-area mode for interconnect, bug fix for AXI Ethernet Buffer PTP 1588 frame handling, and a fix for a potential deadlock between peripheral and cache AXI interfaces in frequency-optimized pipeline mode.
- **Vitis Model Composer 2025.2 known issue**: AXI4-Lite interface generation for Gateway In/Out does not support testbench generation — affects simulation flows.
- **Vivado 2026.1 available**: AMD has released Vivado/Vitis 2026.1 as of mid-2026. Migration from 2025.1 projects requires re-running IP upgrade and re-generating block design outputs.

### Code Example

```vhdl
-- XPM replacement for Block Memory Generator (single-port RAM)
-- Use this pattern in RTL instead of instantiating blk_mem_gen
library xpm;
use xpm.vcomponents.all;

xpm_memory_spram_inst : xpm_memory_spram
  generic map (
    ADDR_WIDTH_A        => 10,      -- 2^10 = 1024 locations
    BYTE_WRITE_WIDTH_A  => 32,      -- 32-bit byte enables
    MEMORY_SIZE         => 32768,   -- bits: 1024 * 32
    MEMORY_PRIMITIVE    => "block", -- force BRAM inference
    READ_LATENCY_A      => 2,
    WRITE_MODE_A        => "read_first"
  )
  port map (
    clka    => clk,
    ena     => '1',
    wea     => wea,
    addra   => addra,
    dina    => dina,
    douta   => douta,
    rsta    => rst,
    regcea  => '1',
    injectdbiterra => '0',
    injectsbiterra => '0',
    sbiterra => open,
    dbiterra => open
  );
```

### Relevance to Your Project

If you migrate from Vivado 2025.1 to 2025.2 or 2026.1, your block design's Block Memory Generator instances will continue to work inside the block design (no immediate action required). However, if you ever instantiate BRAM directly in `kv260_top.vhd` outside the block design boundary, switch to XPM macros to stay on AMD's supported path. Monitor the AXI full peripheral address-space bug if you expand BRAM size beyond 1KB in future revisions.
