# FPGA Research Digest - 2026-07-17

## Executive Summary

- **AXI-Lite write deadlock risk**: Xilinx reference designs historically failed to check BREADY before asserting AWREADY/WREADY; the correct guard `(!S_AXI_BVALID || S_AXI_BREADY)` prevents a hung bus — directly relevant to any AXI-Lite BRAM write loop.
- **Vivado 2025.1 PS-first boot**: New capability allows the Zynq PS to boot before PL is configured, enabling faster bring-up; pair with dynamic bitstream loading for iterative KV260 bare-metal development.
- **AXI BRAM Controller v4.1**: AWREADY is held high until the pipeline-full condition; WREADY is withheld until BRAM is ready — mismatching these in a custom AXI slave will cause stalls at addresses 0xA0000000 and 0xA0010000.
- **Kria bare-metal via JTAG/XSDB**: The simplest path to booting a bare-metal `.elf` on the KV260 without touching QSPI is `xsdb` + `fpga -f bitstream.bit && dow app.elf && con`.
- **Vivado 2025.2 AXI Switch ultra-low-area mode**: New `STRATEGY` parameter on AXI Switch / SmartConnect slashes LUT usage for simple point-to-point topologies like the dual-BRAM design.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- AXI4-Lite has five independent channels (AW, W, B, AR, R). Write address (AW) and write data (W) channels are independent — both must complete before the slave can assert BVALID on the response channel.
- The canonical backpressure bug: if the master holds BREADY low, the slave **must** deassert AWREADY/WREADY, or it will silently drop the response and hang the bus indefinitely.
- Xilinx's own pre-2016.3 AXI-Lite demo core contained this exact bug on the read path; the fix was never applied to the read side at that time (source: ZipCPU blog).
- AXI-Lite does not support bursts; each transaction is exactly 1 beat. AXI4-Full adds ARLEN/ARSIZE burst fields — unnecessary for the KV260 BRAM demo but useful to know when upgrading to higher-bandwidth designs.
- Correct AWREADY logic must guard on the B-channel: only accept a new address when the prior response has been consumed.

### Code Example

```vhdl
-- Correct AXI-Lite AWREADY logic: accept new address only when
-- prior write response is consumed (BREADY or no pending BVALID)
process(S_AXI_ACLK)
begin
  if rising_edge(S_AXI_ACLK) then
    if S_AXI_ARESETN = '0' then
      axil_awready <= '0';
    else
      -- Accept address only when BOTH AW and W valid, AND B-channel clear
      axil_awready <= (not axil_awready)
                    and (S_AXI_AWVALID and S_AXI_WVALID)
                    and (not S_AXI_BVALID or S_AXI_BREADY);
    end if;
  end if;
end process;
```

### Relevance to Your Project

Your `main.c` writes a pattern to BRAM0 (0xA0000000) and BRAM2 (0xA0010000) then reads back. If the Xilinx AXI BRAM Controller or any intermediate AXI Interconnect IP has the backpressure bug, back-to-back writes in a tight loop can silently drop a transaction, causing a false FAIL even though the logic is otherwise correct. Test by adding a deliberate `BREADY` deassertion cycle in simulation.

## Vivado Block Design / IP Integrator

### Key Findings

- **Connection Automation** (Run Connection Automation): after dropping in a new IP, Vivado auto-wires AXI slave ports to the existing AXI Interconnect and connects resets through the Processor System Reset IP. Always verify the clock source selected for each `S_AXI` connection — it defaults to the first available clock, which may not match your design's PL clock.
- **Address Editor**: Vivado auto-assigns a 64 KB offset block (`0x4000_0000` default range). For bare-metal drivers using a hardcoded base address (e.g., `0xA000_0000`), you **must** open the Address Editor and manually set the master base address to match your C `#define`.
- After regenerating the block design (`.bd` file changes), always re-run **Validate Design** (F6) before synthesizing; unconnected pins and address conflicts are caught here, not during synthesis.
- IP Integrator in 2025.1 supports a fully customizable RTL-based AXI Switch that replaces the older fixed-topology AXI Crossbar in simple fan-out scenarios.
- Saving a block design to a `.tcl` via `write_bd_tcl` produces a reproducible script that re-creates the entire block design from scratch — essential for CI/CD and version control.

### Code Example

```tcl
# Force-assign base address for BRAM0 and BRAM2 after connection automation
# Run in Vivado Tcl Console after block design is open
open_bd_design [get_files *.bd]

# Assign BRAM0 at 0xA000_0000, 64KB
assign_bd_address [get_bd_addr_segs {axi_bram_ctrl_0/S_AXI/Mem0}]
set_property offset 0xA0000000 \
  [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property range 64K \
  [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]

# Assign BRAM2 at 0xA001_0000, 64KB
assign_bd_address [get_bd_addr_segs {axi_bram_ctrl_1/S_AXI/Mem0}]
set_property offset 0xA0010000 \
  [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_1_Mem0}]
set_property range 64K \
  [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_1_Mem0}]

validate_bd_design
save_bd_design
```

### Relevance to Your Project

Your `create_bd.tcl` script builds the block design programmatically. The address assignments above match the hardcoded base addresses `0xA0000000` and `0xA0010000` used in `main.c`. Keeping these in the TCL script (rather than relying on auto-assignment) ensures the addresses remain stable across IP upgrades and tool version changes.

## Vivado TCL Scripting

### Key Findings

- **Batch mode**: `vivado -mode batch -source create_bd.tcl` runs a script non-interactively and exits. Add `-nojournal -nolog` to suppress `.jou`/`.log` clutter in CI.
- **Non-Project Mode**: use `read_vhdl`, `read_xdc`, `synth_design`, `opt_design`, `place_design`, `route_design`, `write_bitstream` in sequence — no `.xpr` project file needed. Faster for automated builds and avoids stale IP caches.
- `write_bd_tcl -force output.tcl` exports the entire block design as a reproducible script. Commit this instead of the binary `.bd` file.
- Use `get_property` / `set_property` to inspect and override IP parameters in script — avoids the GUI for batch IP configuration changes.
- `report_timing_summary -file timing.rpt` at the end of a batch run captures timing closure status without opening the GUI.

### Code Example

```tcl
# Non-project mode full build: synthesize, implement, write bitstream
# Usage: vivado -mode batch -source build.tcl

read_vhdl  [glob ../vhdl/*.vhd]
read_xdc   [glob ../xdc/*.xdc]

# Recreate block design from exported TCL
source ../tcl/create_bd.tcl
make_wrapper -files [get_files *.bd] -top
read_vhdl  [get_files *_wrapper.v]

synth_design  -top kv260_top -part xck26-sfvc784-2LV-c
opt_design
place_design
phys_opt_design
route_design

report_timing_summary -file timing_summary.rpt
report_utilization    -file utilization.rpt

write_bitstream -force output/kv260_top.bit
write_hw_platform -fixed -force output/kv260_top.xsa
```

### Relevance to Your Project

Adding a `build.tcl` alongside your existing `create_bd.tcl` enables a one-command build from the repo without ever opening the Vivado GUI. This is especially valuable in the remote cloud session environment where GUI sessions are impractical.

## Vitis Bare-Metal / Standalone

### Key Findings

- **BSP `stdin`/`stdout` assignment**: In the Vitis standalone BSP, `stdout` must be explicitly set to the UART connected to the board's USB-serial bridge. For KV260 this is typically `psu_uart_1` (connected to the USB-UART bridge on the carrier card). A wrong assignment silently discards all `xil_printf` output.
- **`xil_printf` vs `printf`**: `xil_printf` is a lightweight formatted print in the standalone BSP that avoids pulling in the full libc `printf` — it lacks floating-point support but saves ~60 KB of code size. For PASS/FAIL messaging it is the correct choice.
- **Linker script memory regions**: The default linker script places `.text` in DDR starting at `0x0`. On Zynq UltraScale+ at EL3, OCM is at `0xFFFC0000` (256 KB). If your `main.c` global arrays are large, the linker may silently place them in DDR before the MMU is configured, causing alignment faults. Explicitly size your stack/heap in the BSP settings.
- **Vitis 2025.1 Unified IDE**: The new unified IDE replaces the Eclipse-based Classic IDE. `xsct` scripting for headless build/deploy still works unchanged.
- **Minimizing bare-metal binary size**: Compiling with `-Os`, disabling unused BSP features (cache, interrupts), and stripping debug symbols can reduce a KV260 bare-metal ELF from ~800 KB to under 100 KB — important for QSPI boot where partition size matters.

### Code Example

```c
/* Correct AXI-Lite BRAM read-back pattern with explicit cache flush.
   Call Xil_DCacheFlush() before reading if D-cache is enabled,
   otherwise the CPU may read a cached (stale) value after the
   AXI-Lite write completes on the PL side. */
#include "xil_io.h"
#include "xil_printf.h"
#include "xil_cache.h"

#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL
#define TEST_PATTERN 0xDEADBEEFUL

int main(void) {
    Xil_Out32(BRAM0_BASE, TEST_PATTERN);
    Xil_Out32(BRAM2_BASE, ~TEST_PATTERN);

    /* Flush D-cache so subsequent reads go to AXI bus, not cache */
    Xil_DCacheFlush();

    u32 r0 = Xil_In32(BRAM0_BASE);
    u32 r2 = Xil_In32(BRAM2_BASE);

    if (r0 == TEST_PATTERN && r2 == ~TEST_PATTERN) {
        xil_printf("PASS: BRAM0=0x%08X BRAM2=0x%08X\r\n", r0, r2);
    } else {
        xil_printf("FAIL: BRAM0=0x%08X (exp 0x%08X) BRAM2=0x%08X (exp 0x%08X)\r\n",
                   r0, TEST_PATTERN, r2, ~TEST_PATTERN);
    }
    return 0;
}
```

### Relevance to Your Project

The D-cache flush is the single most common cause of false FAIL results in AXI-Lite bare-metal tests. The Cortex-A53 runs with D-cache enabled by default in the Vitis BSP. Without `Xil_DCacheFlush()`, the CPU will read back its own cached write rather than the value that traversed the AXI bus to the BRAM and returned — producing a spurious PASS that hides a broken AXI path.

## XDC Timing Constraints

### Key Findings

- **KV260 board files**: The Kria SOM board file ships with a `.xdc` capturing all SOM-to-carrier-card connector pin mappings. For bare-metal AXI-BRAM designs using only PS peripherals (no PL I/O), you may need only the clock constraint — Vivado will warn about unconstrained I/O only if PL ports exist.
- **`create_clock` for PL clock**: The Zynq UltraScale+ PS generates PL clocks via the FCLK outputs. In XDC, these are already defined by the PS IP block — you should NOT add a duplicate `create_clock` on `FCLK_CLK0`. Instead, constrain any PL-side logic by referencing the auto-generated clock object.
- **`set_clock_groups -asynchronous`**: Use when the PS clock domain and PL clock domain are asynchronous (different FCLK frequencies). This suppresses false cross-domain timing paths without false-path exceptions.
- **`set_false_path`**: For purely combinational paths that span unrelated clock domains (e.g., a GPIO reset from PS to PL), `set_false_path -from [get_clocks clk_pl_0] -to [get_clocks clk_pl_1]` is cleaner than a full clock-group exception.
- For the KV260, timing constraints come from the board `.xdc` provided in the Kria board files package; always update to the version matching your Vivado release.

### Code Example

```tcl
# kv260_top.xdc — minimal constraints for PS-to-PL AXI-Lite BRAM design
# The PS generates FCLK_CLK0; its clock is auto-defined by the Zynq PS IP.
# Only add constraints here for PL-external signals.

# Example: if a PL-side LED or GPIO exists on the carrier card
# set_property PACKAGE_PIN <pin> [get_ports led_0]
# set_property IOSTANDARD LVCMOS18 [get_ports led_0]

# Suppress timing warnings on PS-PL reset crossing
# (PS reset is asynchronous to PL clock by design)
set_false_path -from [get_pins \
  {zynq_ultra_ps_e_0/inst/PS8_i/PLCLK[0]}] \
  -to [get_cells -hierarchical -filter {NAME =~ *reset_sync*}]

# If two FCLK frequencies are used, declare them asynchronous
# set_clock_groups -name async_pl_clks -asynchronous \
#   -group [get_clocks clk_pl_0] \
#   -group [get_clocks clk_pl_1]
```

### Relevance to Your Project

For a pure PS-to-PL AXI-Lite BRAM design with a single clock, your timing closure is straightforward. The key constraint to watch is the reset synchronizer path — Vivado often flags `PLRESET` → PL flop crossings as unconstrained. The `set_false_path` above eliminates this warning without masking any real timing violations.

## Kria KV260 / K26 SoM

### Key Findings

- **Boot modes**: K26 supports JTAG, SD card, and QSPI32 boot. The Kria Starter Kit ships pre-loaded with QSPI32 boot firmware. For bare-metal development, JTAG (`sw_mio[3:0] = 0000`) is the fastest iteration path — no QSPI programming needed.
- **JTAG bare-metal workflow**: Use `xsdb` → `connect` → `targets -set -filter {name =~ "APU*"}` → `fpga -f bitstream.bit` → `dow app.elf` → `con`. This bypasses the full BOOT.BIN flow entirely.
- **MIO vs EMIO**: PS peripherals (UART, I2C, SPI) use MIO pins on the SOM. The USB-UART bridge on the KV260 carrier card is connected to MIO pins routed through the SOM connector — these are fixed by the K26 hardware and cannot be remapped without a custom carrier. EMIO routes PS peripherals through the PL fabric to the carrier card's I/O pins.
- **UART for `xil_printf`**: On KV260, the USB-serial bridge maps to `psu_uart_1` (not `psu_uart_0`). Configuring BSP `stdout` to `psu_uart_0` is a common mistake that silences all console output.
- **Power domains**: The K26 SOM has separate power rails for PS (VCCINT_PS), PL (VCCINT), and I/O (VCCO_PSIO). PL clocks are gated when the PL is not configured; this is transparent to bare-metal code once the bitstream is loaded.

### Code Example

```bash
# XSDB bare-metal deployment script for KV260 over JTAG
# Run with: xsdb deploy_baremetal.tcl

connect

# Target the APU (Cortex-A53 cluster)
targets -set -filter {name =~ "APU*"}

# Load PL bitstream first
fpga -f ../output/kv260_top.bit

# Switch to A53 core 0 for ELF download
targets -set -filter {name =~ "Cortex-A53 #0"}

# Initialize PS (configures clocks, DDR, MIO from the XSA)
loadhw -hw ../output/kv260_top.xsa -mem-ranges [list {0x80000000 0xBFFFFFFF}]
configparams force-mem-access 1

# Download and run the bare-metal ELF
dow ../vitis/kv260_app/Debug/kv260_app.elf
con

# Monitor console output in your serial terminal (115200 8N1, psu_uart_1)
```

### Relevance to Your Project

The JTAG workflow above is the recommended fast iteration loop for the KV260 AXI-BRAM demo — no SD card, no QSPI flash, no BOOT.BIN. Change `main.c`, rebuild the ELF, re-run `xsdb deploy_baremetal.tcl`, and see PASS/FAIL output on the USB-UART terminal in under 30 seconds.

## AMD/Xilinx Tool Updates (Vivado/Vitis 2025.x)

### Key Findings

- **Vivado 2025.1 PS-first boot**: New feature allowing the Zynq/Kria PS to boot and run Linux before the PL is programmed. Enables faster OS bring-up and dynamic PL overlay loading via Device Tree Overlays (DTO) + `xmutil loadapp`.
- **Vivado 2025.1 Pblock Planner**: New interactive placement tool for defining Pblocks — useful for partitioning AXI IP from user logic to improve timing closure.
- **Vivado 2025.1 RTL-based AXI Switch IP**: A fully customizable replacement for the older AXI Crossbar, with improved timing and lower resource utilization for custom topologies.
- **Vivado 2025.2 AXI Switch/SmartConnect ultra-low-area mode**: New `STRATEGY` parameter enables a minimal-LUT mode — ideal for simple point-to-point AXI topologies (e.g., one PS master to two BRAM slaves via a 1x2 interconnect).
- **Vitis 2025.1 Unified IDE**: Eclipse-based Classic IDE is deprecated. The new Unified IDE (based on VS Code) is the primary Vitis front-end. All `xsct`/`xsdb` scripting APIs are unchanged — headless workflows are unaffected.
- **2025.1 known issues**: AR#000037546 tracks Vivado 2025.x known issues. Check this answer record before reporting a bug — common issues include incorrect timing report generation for certain UltraScale+ configurations and IP regeneration warnings after tool upgrades.

### Code Example

```tcl
# Vivado 2025.x: Set AXI SmartConnect to ultra-low-area mode
# (Vivado 2025.2+, STRATEGY parameter)
# This halves LUT usage for a 1-master, 2-slave topology.

set_property CONFIG.STRATEGY {1} \
  [get_bd_cells axi_smc]

# Verify the parameter was applied
report_property [get_bd_cells axi_smc]

# For Vivado 2025.1 PS-first boot: generate XSA with PS-only flag
# then load PL overlay separately via xmutil on Linux, or via
# xsdb fpga command in bare-metal JTAG flow.
write_hw_platform -fixed -force -include_bit output/kv260_ps_only.xsa
```

### Relevance to Your Project

The 2025.2 AXI SmartConnect `STRATEGY` parameter is directly applicable: your 1-PS-master to 2-BRAM-slave topology is the textbook use case for ultra-low-area mode. Enabling it can save 200–400 LUTs on the K26's relatively small PL fabric. Upgrade the project's Vivado version to 2025.2 to gain this benefit with a one-line TCL change.
