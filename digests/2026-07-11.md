## Executive Summary

- **AXI BRAM Controller write-enable timing bug**: The IP can assert BREN one clock early, writing a spurious word to the previously-accessed address — confirm the BRAM `ENA`/`ENB` enable port is properly driven, not left unconnected or tied high without a gate.
- **AXI-Lite AWVALID/WVALID ordering**: The AXI4 spec permits either signal to arrive first, but Xilinx's Zynq PS implementation internally enforces AWVALID before WVALID — custom PL slaves should be tolerant of either order; masters need not guarantee simultaneous assertion.
- **Vivado 2025.1 AXI Switch IP + PS-first boot**: A new fully RTL-customizable AXI Switch IP and dynamic PS-first PL loading are the headline 2025.1 additions — the AXI Switch is an option for expanding beyond two BRAM slaves; PS-first boot eases KV260 bring-up sequence.
- **Vitis 2025.1 BSP UART pitfall**: If `xil_printf` produces no output, check that BSP `stdout`/`stdin` is set to `psu_uart_1` (not `psu_uart_0`) and regenerate BSP sources before rebuilding.
- **AXI SmartConnect recommended over AXI Interconnect**: For all new UltraScale+ designs (including KV260), SmartConnect delivers 20–30% higher throughput at lower area/power and auto-bridges AXI3/AXI4/Lite type mismatches.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- **VALID must never be de-asserted**: Once any channel's VALID is raised it must stay high until the corresponding READY completes the handshake — de-asserting early is a protocol violation that causes deadlock with compliant slaves.
- **AWVALID/WVALID ordering flexibility**: AXI4 permits write address and write data to arrive in any order; the subordinate must not issue BVALID until both complete. However, Xilinx Zynq PS enforces AWVALID first internally.
- **AXI-Lite is single-transfer only**: No burst capability — each write or read consumes a full handshake on AW/W/B (write) or AR/R (read) channels. For repeated BRAM fills use AXI4 full or DMA.
- **AXI BRAM Controller write-enable timing hazard**: A documented issue shows the `axi_bram_ctrl` asserting write enable one clock cycle early, causing an extra write to the *previous* BRAM address. The fix is ensuring the BRAM `ENA` enable signal is properly gated by the controller output, not left undriven.
- **AXI-Stream sideband signals**: `TKEEP` marks which bytes in `TDATA` are valid (byte enables); `TSTRB` distinguishes position bytes from data bytes; `TLAST` signals end of packet. Width of `TKEEP`/`TSTRB` must match `TDATA` width ÷ 8 in any IP instantiation.
- **AXI4 full vs AXI-Lite**: AXI4 full adds burst transfers (ARBURST, ARLEN, ARSIZE) critical for bulk BRAM fills; AXI-Lite is sufficient for register-like single-word PS→PL accesses as used in the kv260-axi-bram-demo.

### Code Example

```vhdl
-- AXI-Lite write handshake: accepts AW and W in any order,
-- issues B response only after both channels complete.

architecture rtl of axilite_slave is
  signal aw_active : std_logic := '0';
  signal w_active  : std_logic := '0';
  signal aw_addr   : std_logic_vector(31 downto 0);
  signal w_data    : std_logic_vector(31 downto 0);
begin

  process(clk) begin
    if rising_edge(clk) then
      if rst = '1' then
        aw_active     <= '0';
        w_active      <= '0';
        S_AXI_AWREADY <= '0';
        S_AXI_WREADY  <= '0';
        S_AXI_BVALID  <= '0';
        S_AXI_BRESP   <= "00";
      else
        -- Capture write address
        S_AXI_AWREADY <= '0';
        if S_AXI_AWVALID = '1' and aw_active = '0' then
          aw_addr       <= S_AXI_AWADDR;
          aw_active     <= '1';
          S_AXI_AWREADY <= '1';
        end if;

        -- Capture write data
        S_AXI_WREADY <= '0';
        if S_AXI_WVALID = '1' and w_active = '0' then
          w_data       <= S_AXI_WDATA;
          w_active     <= '1';
          S_AXI_WREADY <= '1';
        end if;

        -- Issue response only after both AW and W complete
        if aw_active = '1' and w_active = '1' and S_AXI_BVALID = '0' then
          -- perform write to internal register / BRAM here
          S_AXI_BVALID  <= '1';
          S_AXI_BRESP   <= "00";   -- OKAY
          aw_active     <= '0';
          w_active      <= '0';
        elsif S_AXI_BREADY = '1' then
          S_AXI_BVALID <= '0';
        end if;
      end if;
    end if;
  end process;

end rtl;
```

### Relevance to Your Project

The kv260-axi-bram-demo relies on AXI-Lite reads and writes to `0xA0000000` (BRAM0) and `0xA0010000` (BRAM2). The early write-enable timing bug in `axi_bram_ctrl` is a live risk: a phantom write to the previous address would corrupt the readback comparison and produce a spurious FAIL. Checking `bram_en_a`/`bram_en_b` connectivity in the block design (they must connect to the controller's output, not be left open) is a quick validation step.

## Vivado Block Design / IP Integrator

### Key Findings

- **SmartConnect is the modern interconnect**: AXI SmartConnect (`xilinx.com:ip:smartconnect`) supersedes AXI Interconnect for UltraScale+ — auto-configures AXI3/AXI4/Lite bridging, delivers 20–30% better throughput, and reduces resource utilization vs. the legacy core.
- **Connection Automation shortcut**: After adding a slave IP, right-click its `S_AXI` port and select *Run Connection Automation* — Vivado auto-wires the port to the PS AXI master and assigns a clock, avoiding manual net drawing.
- **Address Editor auto-assign**: Validation errors about unmapped peripherals resolve with right-click → *Auto-Assign Address* in the Address Editor; manually override the offset afterward (e.g., set BRAM0 to `0xA0000000`).
- **Address Editor availability**: The tab only appears when a bus master (Zynq PS or MicroBlaze) is present with an exposed AXI master port — if missing, ensure the Zynq PS `M_AXI_HPM0_FPD` port is enabled and exposed.
- **Vivado 2025.1 new IP Integrator panels**: Dedicated *Clocking and Reset* and *Interrupt and AXI-4 Lite* side panels in the block diagram canvas reduce the need to scroll to find connection points.
- **Pblock Planner (2025.1)**: New integrated floorplanning UI useful when explicitly placing BRAM primitives in specific column/row regions.

## Vivado TCL Scripting

### Key Findings

- **`write_bd_tcl` for export**: Exports the current block design to a self-contained TCL script via `write_bd_tcl -force ./tcl/create_bd.tcl` or *File → Export → Export Block Design* in the GUI.
- **Version string fragility**: Exported TCL embeds IP version strings (e.g., `xilinx.com:ip:axi_bram_ctrl:4.0`) — these break when the target Vivado version ships a newer IP revision. Use `get_ipdefs -filter "VLNV =~ *axi_bram_ctrl*" -latest_only` to query the correct VLNV at runtime.
- **Non-project mode advantages**: Faster clean builds with no `.xpr` state corruption; design checkpoints (`write_checkpoint`) are the save units; outputs (bitstream, XSA) are explicitly scripted, making CI pipelines reproducible.
- **`$obj` variable lifetime**: Vivado's exported TCL uses `$obj`, `$file`, `$file_obj` as immediate temporaries — do not move these lines or wrap them in procedures without re-binding the variable.
- **Custom IP path**: Custom IP repos must be on `ip_repo_path` before `create_ip` calls: `set_property ip_repo_paths [list ./ip] [current_project]` then `update_ip_catalog`.
- **Batch launch**: `vivado -mode batch -source build.tcl -nolog -nojournal` suppresses `.log`/`.jou` files; `-notrace` suppresses the Tcl echo for cleaner CI output.

### Code Example

```tcl
# Reproducible non-project batch build for KV260 AXI-BRAM demo
# Usage: vivado -mode batch -source build.tcl

set part "xck26-sfvc784-2LV-c"
set bd_name "kv260_bd"

# Query latest BRAM ctrl VLNV so the script works across Vivado versions
proc get_latest_vlnv {name} {
  set hits [get_ipdefs -filter "NAME == $name" -latest_only]
  if {[llength $hits] == 0} { error "IP not found: $name" }
  return [get_property VLNV [lindex $hits 0]]
}

create_project -in_memory -part $part

# Add RTL and constraints
read_vhdl [glob ./vhdl/*.vhd]
read_xdc  ./xdc/kv260_top.xdc

# Source the block design creation script
source ./tcl/create_bd.tcl

# Generate HDL wrapper
set bd_file [get_files ${bd_name}.bd]
make_wrapper -files $bd_file -top
read_vhdl [glob ./kv260.gen/sources_1/bd/${bd_name}/hdl/*.vhd]
set_property top kv260_top [current_fileset]

# Implement
synth_design  -top kv260_top -part $part
opt_design
place_design
route_design

# Check timing
set wns [get_property SLACK [get_timing_paths -max_paths 1 -nworst 1]]
if {$wns < 0} { puts "WARNING: Timing not closed, WNS = $wns ns" }

# Output artifacts
file mkdir ./output
write_checkpoint  -force ./output/routed.dcp
write_bitstream   -force ./output/kv260_top.bit
write_hw_platform -fixed -include_bit -force ./output/kv260.xsa

puts "Build complete. XSA at ./output/kv260.xsa"
```

### Relevance to Your Project

Your `create_bd.tcl` is sourced inside this flow. The `write_hw_platform` line at the end generates the `.xsa` consumed by Vitis to create the bare-metal platform — this is the handoff point between Vivado and Vitis in the kv260-axi-bram-demo build chain. ## Vitis Bare-Metal / Standalone

### Key Findings

- **Vitis 2025.1 Unified IDE workflow**: Import XSA → *Create Platform Component* (standalone OS, psu_cortexa53_0) → *Create Application Component* — the legacy *Launch SDK* / *Export Hardware* flow is deprecated.
- **UART BSP misconfiguration is the #1 `xil_printf` failure cause**: BSP `stdout` defaults vary by board; on KV260 set `standalone_stdout = psu_uart_1`, then click *Regenerate BSP Sources* before rebuilding.
- **`vitis-comp.json` location**: Platform Settings folder — the authoritative source for BSP parameter values in a Vitis 2025.1 workspace; check here before regenerating if UART output is silent.
- **`volatile` is mandatory for MMIO**: The C compiler is free to optimize away stores/loads to non-volatile pointers — all AXI-mapped addresses must be accessed via `volatile uint32_t *`.
- **Linker script `lscript.ld`**: Default maps `.text` to DDR (`ps7_ddr_0`). If using Vitis template for Kria, confirm DDR region covers your ELF size; BRAM-based execution requires explicit `.text` relocation to the BRAM address range.
- **Community template**: `miya4649/Vitis_KV260_KR260_Template` provides a pre-configured Vitis 2025.1 bare-metal workspace for KV260 — reduces first-project setup from hours to minutes.

### Code Example

```c
/*
 * AXI-Lite BRAM read/write test for KV260 bare-metal
 * volatile keyword prevents compiler from optimizing MMIO accesses
 */
#include "xil_printf.h"
#include <stdint.h>

#define BRAM0_BASE   0xA0000000UL
#define BRAM1_BASE   0xA0010000UL
#define TEST_WORDS   16u

static void bram_fill(uintptr_t base, uint32_t seed) {
    volatile uint32_t *mem = (volatile uint32_t *)base;
    for (uint32_t i = 0; i < TEST_WORDS; i++)
        mem[i] = seed ^ i;
}

static int bram_check(uintptr_t base, uint32_t seed) {
    volatile uint32_t *mem = (volatile uint32_t *)base;
    int errors = 0;
    for (uint32_t i = 0; i < TEST_WORDS; i++) {
        uint32_t exp = seed ^ i;
        uint32_t got = mem[i];
        if (got != exp) {
            xil_printf("  MISMATCH @0x%08X: exp=0x%08X got=0x%08X\r\n",
                       (unsigned)(base + i * 4u), exp, got);
            errors++;
        }
    }
    return errors;
}

int main(void) {
    xil_printf("\r\nKV260 AXI-BRAM connectivity test\r\n");

    bram_fill(BRAM0_BASE, 0xDEAD0000u);
    bram_fill(BRAM1_BASE, 0xBEEF0000u);

    int e0 = bram_check(BRAM0_BASE, 0xDEAD0000u);
    int e1 = bram_check(BRAM1_BASE, 0xBEEF0000u);

    xil_printf("BRAM0 (0xA0000000): %s  (%d errors)\r\n",
               e0 == 0 ? "PASS" : "FAIL", e0);
    xil_printf("BRAM1 (0xA0010000): %s  (%d errors)\r\n",
               e1 == 0 ? "PASS" : "FAIL", e1);
    return (e0 | e1) ? 1 : 0;
}
```

### Relevance to Your Project

This is an enhanced version of the pattern in your `main.c`. The error count per BRAM and per-address mismatch printout make it much easier to diagnose whether a failure is from the write-enable timing bug (off-by-one address) vs. a connectivity issue (all words fail) vs. a wiring error (one BRAM all-zeros). The `volatile` cast is the single most important correctness requirement for your MMIO test loop.

## XDC Timing Constraints

### Key Findings

- **PS block constraints are auto-generated**: Do not add manual `set_input_delay` or `set_output_delay` on PS-PL AXI interface ports — Vivado loads these automatically from the processing system model and manual additions cause over-constraint errors.
- **Primary PL clock constraint**: Create a clock on the PS output clock pin (not the port): `create_clock -period 10.000 [get_pins -hier -filter {NAME =~ */PS8_i/PLCLK[0]}]` — this drives the timing engine for all AXI paths in the fabric.
- **SOM240 pin names**: Use the KV260 board `.xdc` file from AMD (not the KR260 version) to find correct `PACKAGE_PIN` assignments for SOM240_1/SOM240_2 connectors — schematic net names differ from XDC constraint names, a known source of confusion.
- **Bank voltage**: Most KV260 carrier card PL banks run at 1.8V LVCMOS — use `IOSTANDARD LVCMOS18` for user-defined SOM240 I/O; mismatches trigger DRC BIVC errors.
- **`set_false_path` for reset**: The PS PL reset (`pl_resetn0`) crosses from the PS clock domain into fabric — a `set_false_path -from [get_pins .../PS8_i/PLRESET[0]]` suppresses spurious timing violations on the reset synchronizer.
- **Timing closure on AXI at 100 MHz**: For the kv260-axi-bram-demo at 100 MHz `pl_clk0`, timing should close easily — violations at this frequency usually indicate a missing clock definition or a long combinatorial path in custom RTL wrapped around the BRAM.

### Code Example

## Kria KV260 / K26 SoM

### Key Findings

- **Two-stage boot architecture**: Factory QSPI holds the primary boot firmware (PMU FW + FSBL stub); secondary boot comes from SD card FAT partition (`BOOT.BIN`) containing your FSBL, bitstream, and application ELF.
- **Bare-metal BOOT.BIN composition**: Pack FSBL (A53 EL3) + `.bit` bitstream + bare-metal `.elf` into `BOOT.BIN` using `bootgen -arch zynqmp`; place on SD card FAT partition labeled `BOOT`.
- **Boot mode switch SW1**: KV260 boots from SD when `SW1 = 1110` (boot mode pins); JTAG mode is `SW1 = 0000`. Incorrect switch position is the most common reason a custom `BOOT.BIN` is silently ignored.
- **UART is on MIO (PS), not PL**: KV260 USB-UART uses PS MIO[36:37] → `psu_uart_1` at 115200 baud. This appears as `/dev/ttyUSB1` on Linux hosts (or `COMx` on Windows). The PL does not need to connect to UART.
- **PL clock default**: `pl_clk0` from the Zynq PS defaults to 100 MHz in bare-metal designs when no clock wizard is used; configure clock frequency in the Zynq PS IP GUI under *Clock Configuration → PL Fabric Clocks*.
- **SOM240 connector power domains**: KV260 carrier card Bank 45 = 1.8V, Bank 44 = 1.8V — use `LVCMOS18` for these banks; check UG1091 Carrier Card Design Guide for full bank-to-voltage mapping before adding custom I/O.

### Code Example

```bash
#!/usr/bin/env bash
# Generate BOOT.BIN for KV260 bare-metal AXI-BRAM demo
# Prerequisites: Vitis 2025.1 in PATH, fsbl.elf built, bitstream and app ready

set -e

FSBL=./vitis/fsbl/Debug/fsbl.elf
BIT=./vivado/output/kv260_top.bit
APP=./vitis/kv260_app/Debug/kv260_app.elf

# Boot Image Format descriptor
cat > boot.bif << 'EOF'
the_ROM_image:
{
  [bootloader, destination_cpu=a53-0]              fsbl.elf
  [destination_device=pl]                          kv260_top.bit
  [destination_cpu=a53-0, exception_level=el-3,
   authentication=none]                            kv260_app.elf
}
EOF

# Substitute real paths into BIF (bootgen does not expand shell vars)
sed -i "s|fsbl.elf|$FSBL|g"   boot.bif
sed -i "s|kv260_top.bit|$BIT|g" boot.bif
sed -i "s|kv260_app.elf|$APP|g" boot.bif

bootgen -image boot.bif -arch zynqmp -output BOOT.BIN -w on
echo "BOOT.BIN generated: $(du -h BOOT.BIN | cut -f1)"

# Copy to SD card (adjust mount point as needed)
# cp BOOT.BIN /media/$USER/BOOT/
# sync
echo "Copy BOOT.BIN to SD card BOOT partition, set SW1=1110, power cycle KV260"
echo "Connect serial: minicom -D /dev/ttyUSB1 -b 115200"
```

### Relevance to Your Project

This script is the final step connecting your Vivado + Vitis build outputs to running hardware. The `exception_level=el-3` flag lets your bare-metal app run in EL3 without TF-A (suitable for simple demos). For a production flow, add TF-A before the application ELF. The `SW1=1110` reminder is critical — it is a hardware configuration step that cannot be debugged in software.

## AMD/Xilinx Tool Updates (Vivado/Vitis 2025.1)

### Key Findings

- **New RTL-based AXI Switch IP**: Fully customizable multi-master/multi-slave AXI routing fabric available in 2025.1 — more flexible than SmartConnect for designs requiring dynamic or asymmetric routing between heterogeneous AXI master/slave widths.
- **PS-first / Dynamic PL loading** (Versal-focused): The PS can now boot and run code before the PL bitstream is loaded — enables faster OS bring-up and deferred PL initialization; applicable to KV260 in principle for streaming bitstream after PS boot.
- **Unified Vitis IDE**: Vitis HLS, Vitis IDE, and Vitis Analyzer are fully merged into a single tool in 2025.1; the classic Vitis Classic IDE is no longer the default and will eventually be removed.
- **Vivado 2025.1 Known Issues (AR#000037546)**: AMD publishes a living known-issues article at `adaptivesupport.amd.com` — check before filing support tickets; covers post-route DRC regressions, IP catalog version mismatches, and implementation corner cases.
- **New Pblock Planner**: Integrated floorplanning UI in 2025.1 simplifies BRAM column placement for designs with strict BRAM-to-logic proximity requirements.
- **Dedicated IPI panels (2025.1)**: *Clocking and Reset* and *Interrupt and AXI-4 Lite* panels in IP Integrator provide filtered views of clock/reset/interrupt connections without scrolling the full block diagram.
