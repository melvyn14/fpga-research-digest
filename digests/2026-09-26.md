# FPGA Research Digest - 2026-09-26

## Executive Summary
- **AXI-Lite VALID/READY deadlock risk**: Once VALID is asserted by the initiator, it must not be deasserted until READY is received — violating this can cause permanent deadlocks in the PS→BRAM write path.
- **Vitis 2025.2 Unified IDE is now default**: Classic Vitis IDE is deprecated; the new Unified IDE changes how platform projects and BSP generation are configured — adapt your workflow if upgrading from earlier versions.
- **KV260 bare-metal JTAG boot**: Remove the SD card and use JTAG boot mode for iterative debug. Use `psu_init.tcl` to bypass the FSBL and boot directly into your bare-metal application via Vitis debugger.
- **write_bd_tcl is the canonical reproducibility tool**: Export your block design to TCL via `write_bd_tcl` after every significant change — this is the only reliable way to reproduce a Vivado block design across machines and versions.
- **AXI DataMover TKEEP constraint**: Null bytes (TKEEP fully deasserted) are not supported between packet boundaries — only at TLAST beat. This affects any future AXI-Stream work hanging off your PL fabric.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings
- **VALID must never be deasserted prematurely**: Per the AXI spec, once the initiator asserts VALID, it cannot deassert until READY is seen. Violating this causes silent data corruption or deadlock. This applies to all five AXI channels (AW, W, AR, R, B).
- **Write response ordering**: The AXI4 spec requires both the Write Address (AW) and Write Data (W) channel handshakes to complete before the slave can respond with BRESP. Your PS AXI-Lite master handles this correctly, but custom AXI slaves must implement this ordering explicitly.
- **AXI BRAM Controller ECC port**: The AXI BRAM Controller v4.1+ supports ECC via a second AXI4-Lite control port. If unused, leave it disconnected — it does not need to be driven.
- **Out-of-Context (OOC) synthesis**: The BRAM controller IP uses `HD.CLK_SRC` constraints in OOC mode for correct hold-time closure. These are automatically generated by Vivado — do not manually remove them from your XDC.
- **AXI-Stream TDATA stability**: When TVALID is asserted but TREADY is not yet asserted, all data signals (TDATA, TLAST, TUSER, TKEEP, TSTRB) must remain stable. Toggling them violates the spec and is a common simulation-to-hardware bug.
- **Xilinx DMA requires TLAST**: TLAST is optional per the standard but required by Xilinx DMA IP. Always drive it in designs that include DMA engines, even if your immediate design does not use DMA.

### Code Example
```vhdl
-- Minimal AXI-Lite slave write channel (correct VALID/READY handling)
process(S_AXI_ACLK)
begin
  if rising_edge(S_AXI_ACLK) then
    if S_AXI_ARESETN = '0' then
      aw_en     <= '1';
      axi_awready <= '0';
    else
      if aw_en = '1' and S_AXI_AWVALID = '1' and S_AXI_WVALID = '1' then
        axi_awready <= '1';
        aw_en       <= '0';   -- only accept one address at a time
      elsif S_AXI_BREADY = '1' and axi_bvalid = '1' then
        aw_en <= '1';         -- re-arm after write response accepted
        axi_awready <= '0';
      else
        axi_awready <= '0';
      end if;
    end if;
  end if;
end process;
```

### Relevance to Your Project
Your `kv260_top.vhd` wraps the Zynq PS AXI-Lite master driving BRAM0 at `0xA0000000` and BRAM2 at `0xA0010000`. The PS AXI-Lite master enforces the VALID/READY protocol automatically, but if you ever extend the design with a custom AXI slave peripheral, the pattern above shows the correct aw_en gate that prevents address-channel re-arming before the write response is consumed. The OOC BRAM controller constraint note explains why you should never delete auto-generated `HD.CLK_SRC` lines from your XDC.

## Vivado Block Design / IP Integrator

### Key Findings
- **`apply_bd_automation` is convenient but opaque**: It works well for simple connections but generates implicit net names that are hard to trace in TCL exports. For reproducible, reviewable designs prefer explicit `connect_bd_net` / `connect_bd_intf_net` calls.
- **Connection Automation for AXI address assignment**: After adding a BRAM controller, run `assign_bd_address` or use the Address Editor to set the base address. If addresses shift unexpectedly after re-running TCL, ensure you call `assign_bd_address` before saving to lock assignments.
- **`validate_bd_design` before generating**: Always call `validate_bd_design` in your TCL script before `generate_target all [get_files *.bd]`. It catches unconnected mandatory ports and clock domain issues early.
- **IP version locking**: Vivado TCL scripts capture specific IP versions. When moving between Vivado releases, re-run `upgrade_ip [get_ips *]` and check the upgrade report for behavioral changes before re-running synthesis.
- **Block design canvas layout**: `write_bd_tcl` accepts `-include_layout` to preserve the visual arrangement on the canvas — useful when sharing designs with colleagues.

### Code Example
```tcl
# Reproducible block design creation snippet
create_bd_cell -type ip -vlnv xilinx.com:ip:axi_bram_ctrl:4.1 axi_bram_ctrl_0
set_property -dict [list \
  CONFIG.SINGLE_PORT_BRAM {1} \
  CONFIG.DATA_WIDTH        {32} \
] [get_bd_cells axi_bram_ctrl_0]

create_bd_cell -type ip -vlnv xilinx.com:ip:blk_mem_gen:8.4 blk_mem_gen_0
connect_bd_intf_net \
  [get_bd_intf_pins axi_bram_ctrl_0/BRAM_PORTA] \
  [get_bd_intf_pins blk_mem_gen_0/BRAM_PORTA]

# Assign address
assign_bd_address [get_bd_addr_segs {axi_bram_ctrl_0/S_AXI/Mem0}]
set_property range 8K \
  [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]

validate_bd_design
```

### Relevance to Your Project
Your `create_bd.tcl` script likely uses similar IP instantiation patterns for BRAM0 and BRAM2. The `assign_bd_address` / `set_property range` pattern ensures addresses stay at `0xA0000000` and `0xA0010000` across regenerations. Adding `validate_bd_design` before `generate_target` catches missing connections before a long synthesis run wastes time.

## Vivado TCL Scripting

### Key Findings
- **Non-project mode is more reproducible**: Use `read_vhdl`, `read_xdc`, `synth_design`, `opt_design`, `place_design`, `route_design`, `write_bitstream` as a linear pipeline — no `.xpr` file, easier to version-control.
- **Checkpoint-driven flow**: Write design checkpoints (`write_checkpoint`) after each major step so you can reopen (`open_checkpoint`) at any phase without re-running the full flow.
- **Journal capture for block design**: When building a block design interactively, Vivado records every GUI action to `vivado.jou`. Copy these commands into your `create_bd.tcl` and clean up verbose/redundant entries.
- **`write_bd_tcl` is the authoritative export**: Run it from the Tcl console after any block design edit: `write_bd_tcl -force -include_layout ./tcl/create_bd.tcl` — this is what should be committed to version control.
- **Batch execution**: `vivado -mode batch -source build.tcl` runs fully headless. Add `-log build.log -journal build.jou` for clean log capture in CI environments.

### Code Example
```tcl
# Non-project mode batch build (build.tcl)
set outputDir ./output
file mkdir $outputDir

# Read sources
read_vhdl [glob ./vhdl/*.vhd]
read_xdc  ./constraints/kv260_top.xdc

# Synthesis
synth_design -top kv260_top -part xck26-sfvc784-2LV-c
write_checkpoint -force $outputDir/post_synth.dcp
report_timing_summary -file $outputDir/post_synth_timing.rpt

# Implementation
opt_design
place_design
phys_opt_design
route_design
write_checkpoint -force $outputDir/post_route.dcp
report_timing_summary -no_header -file $outputDir/post_route_timing.rpt

# Bitstream
write_bitstream -force $outputDir/kv260_top.bit
```

### Relevance to Your Project
Adopting the non-project batch flow lets you run `vivado -mode batch -source build.tcl` from CI or a Makefile without opening the GUI. Combining this with `create_bd.tcl` (regenerating the block design) and your existing `kv260_top.vhd` gives a fully reproducible build chain: TCL → bitstream, no GUI interaction required.

## Vitis Bare-Metal / Standalone

### Key Findings
- **Vitis Unified IDE is now default in 2025.2**: Classic Vitis IDE is deprecated. Platform projects replace the old hardware project flow — export `.xsa` from Vivado, create Platform in Vitis, then create Application project on top.
- **BSP stdout configuration**: In the platform settings, `stdin` / `stdout` must be set to `psu_uart_1` (the UART connected to the KV260's USB-UART bridge). Wrong UART assignment causes `xil_printf` output to silently go nowhere.
- **`xil_printf` vs `printf`**: `xil_printf` is lighter (no floating-point, no heap) and preferred for bare-metal. `printf` requires `_write` stub or newlib configuration — use `xil_printf` unless you need `%f`.
- **GIC interrupt setup for custom IPs**: Use `XScuGic` driver. Register your ISR with `XScuGic_Connect`, set priority, and enable with `XScuGic_Enable`. The interrupt ID for PL peripherals starts at 121 for SPI[0] on Zynq UltraScale+.
- **Third-party toolchains in 2025.2**: Vitis 2025.2 adds explicit support for GCC and ARMClang as alternative toolchains, configurable per application project.
- **Linker script**: The default linker script places code/data in DDR (`ps_ddr_low`). For latency-sensitive bare-metal code, consider placing hot functions in OCM (on-chip memory, 256 KB at `0xFFFC0000`).

### Code Example
```c
/* main.c — AXI-Lite BRAM write/read/verify pattern */
#include "xil_printf.h"
#include "xil_io.h"

#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL
#define PATTERN     0xDEADBEEFUL

int main(void) {
    xil_printf("KV260 AXI-BRAM Test\r\n");

    /* Write */
    Xil_Out32(BRAM0_BASE + 0x00, PATTERN);
    Xil_Out32(BRAM2_BASE + 0x00, ~PATTERN);

    /* Read back and verify */
    uint32_t r0 = Xil_In32(BRAM0_BASE + 0x00);
    uint32_t r2 = Xil_In32(BRAM2_BASE + 0x00);

    if (r0 == PATTERN && r2 == ~PATTERN) {
        xil_printf("PASS: BRAM0=0x%08X BRAM2=0x%08X\r\n", r0, r2);
    } else {
        xil_printf("FAIL: BRAM0=0x%08X (exp 0x%08X) "
                   "BRAM2=0x%08X (exp 0x%08X)\r\n",
                   r0, PATTERN, r2, ~PATTERN);
    }
    return 0;
}
```

### Relevance to Your Project
This matches the structure your `main.c` uses. Key check: confirm that `stdout` in the BSP platform settings is `psu_uart_1` (not `psu_uart_0`) — on the KV260, the FTDI USB-UART bridge is wired to UART1. If PASS/FAIL output is missing on the terminal, wrong UART assignment is the most common culprit.

## XDC Timing Constraints

### Key Findings
- **KV260 XDC files**: AMD provides official SOM XDC (XTP685) and carrier card XDC (XTP686) with pre-defined `set_property PACKAGE_PIN` and `IOSTANDARD` constraints. Always start from these — do not derive pin assignments from the schematic by hand.
- **`set_input_delay` / `set_output_delay` for external IO**: For any signal crossing the PS/PL boundary to external pins, add `set_input_delay -clock <clk> <value> [get_ports <port>]`. Use `set_clock_groups -asynchronous` to cut paths between unrelated clock domains.
- **PL fabric clock from PS**: The `pl_clk0` output of the Zynq UltraScale+ PS block is the primary fabric clock. Constrain it with `create_clock -period <ns> [get_pins zynq_ultra_ps_e_0/pl_clk0]` in your XDC — Vivado will not automatically create this constraint.
- **`HD.CLK_SRC` in OOC synthesis**: These auto-generated properties ensure hold-timing closure for BRAM controller IP synthesized out of context. Never delete them from generated XDC files.
- **Clock domain crossing reporting**: In 2025.2, Vivado adds new SLR crossing reporting that surfaces CDC paths — run `report_cdc` after route to catch any unguarded crossings.

### Code Example
```tcl
# kv260_top.xdc — essential timing constraints

# PL fabric clock (100 MHz from PS pl_clk0)
create_clock -period 10.000 -name pl_clk0 \
  [get_pins zynq_ultra_ps_e_0/inst/PS8_i/PLCLK[0]]

# Asynchronous clock group: PL fabric vs PS internal clocks
set_clock_groups -asynchronous \
  -group [get_clocks pl_clk0] \
  -group [get_clocks clk_pl_0]

# Example: external PMOD output delay (assuming 2 ns board trace)
set_output_delay -clock pl_clk0 -max 2.0 [get_ports pmod_*]
set_output_delay -clock pl_clk0 -min -0.5 [get_ports pmod_*]
```

### Relevance to Your Project
For the pure PS-to-BRAM AXI-Lite demo, timing constraints are minimal — but the `create_clock` on `pl_clk0` is required for Vivado to close timing on the AXI interconnect paths. Without it, timing analysis is unconstrained and implementation results are non-deterministic. Add this constraint to `kv260_top.xdc` if it's not already present.

## Kria KV260 / K26 SoM Platform Specifics

### Key Findings
- **Boot mode for bare-metal development**: Remove the SD card and set DIP switches to JTAG mode. Use `psu_init.tcl` in the Vitis XSCT console to initialize the PS without going through the FSBL — this gives the fastest edit-compile-flash cycle.
- **USB-UART is UART1**: The FTDI bridge on the KV260 is connected to `psu_uart_1` (MIO 36/37), not UART0. Set BSP stdout to `psu_uart_1` in Vitis platform settings.
- **PL power domain**: The PL fabric is always powered on the KV260 Starter Kit — no separate PL power sequencing required for bare-metal demos. The PS powers up and the bitstream can be loaded immediately after `psu_init.tcl`.
- **AXI HP ports vs AXI GP ports**: For low-bandwidth control like AXI-Lite BRAM access, AXI GP (General Purpose) ports are correct. AXI HP (High Performance) ports are for bulk DMA traffic and have separate FIFOs — do not use HP ports for simple memory-mapped register access.
- **Known UART issue with default KV260 board file**: The default Kria board definition in older Vitis versions does not enable UART in the PS configuration, so `xil_printf` output silently disappears. Verify in the Zynq PS IP configuration that `UART1` is enabled with MIO 36/37 assigned.
- **QSPI for deployment**: Once the design is stable, `program_flash` in Vitis XSCT can write the bitstream + FSBL + application ELF to QSPI for standalone boot without JTAG.

### Code Example
```tcl
# XSCT console: bare-metal JTAG boot sequence (no SD card required)
connect
targets -set -nocase -filter {name =~ "PSU"}
mwr  0xffff0000 0x14000000  ;# disable security
rst -system
after 3000

# Run psu_init to configure PS clocks and DDR
source <vitis_platform>/hw/psu_init.tcl
psu_init

# Load bitstream into PL
fpga <path_to>/kv260_top.bit

# Load and run bare-metal ELF on Cortex-A53 core 0
targets -set -nocase -filter {name =~ "Cortex-A53 #0"}
rst -processor
dow <path_to>/kv260_bram.elf
con
```

### Relevance to Your Project
This XSCT sequence is the exact workflow for iterative development on your kv260-axi-bram-demo. The JTAG flow bypasses the FSBL entirely, loads your bitstream and ELF in under 30 seconds, and lets you iterate on PASS/FAIL output over USB-UART without reflashing SD/QSPI. The `psu_init.tcl` file is auto-generated by Vitis when you export the hardware platform from Vivado.

## AMD/Xilinx Tool Updates (2025.2)

### Key Findings
- **Vivado 2025.2 new devices**: Added Versal AI Edge Series Gen 2 and Versal Prime Series Gen 2. K26/KV260 support is unchanged but benefits from QoR improvements.
- **Reduced physical optimization compile time**: Vivado 2025.2 reduces `phys_opt_design` runtime for Versal targets; Zynq UltraScale+ also benefits from general placer improvements.
- **SystemVerilog Interfaces support**: Added in 2025.2 — now you can use `interface` constructs in mixed-language designs. No direct impact on your VHDL design, but relevant if collaborating on SV-based IP.
- **New SLR crossing reporting**: `report_cdc` and timing summary now include SLR (Super Logic Region) crossing detail — relevant if you ever move to multi-die Zynq devices.
- **Vitis 2025.2 Unified IDE is default**: Classic Vitis IDE deprecated. Workflow impact: Platform Projects replace old Hardware Projects. The XSA import → Platform → Application chain is now mandatory.
- **Vitis HLS integration**: From 2025.2, Vitis integrates HLS natively — the separate HLS IDE is gone. HLS IP can be generated from within the unified Vitis IDE.
- **Vitis 2026.x known issues tracker**: AMD now publishes a rolling 2026.x known issues article (article 000040220 on adaptivesupport.amd.com) — check it when upgrading.
- **IP change log for 2025.2**: Article 000039903 on adaptivesupport.amd.com lists all IP version bumps in 2025.2 — relevant to check if AXI BRAM Controller or Block Memory Generator versions changed.

### Code Example
```tcl
# Vitis 2025.2 Unified IDE: create platform from XSA (XSCT equivalent)
# Run in Vitis XSCT console
setws ./workspace
platform create -name kv260_platform \
  -hw ./kv260_top_wrapper.xsa \
  -proc psu_cortexa53_0 \
  -os standalone
platform generate

app create -name kv260_bram \
  -platform kv260_platform \
  -domain standalone_domain \
  -template "Empty Application(C)"
importsources -name kv260_bram -path ./src
app build -name kv260_bram
```

### Relevance to Your Project
If you are on Vitis 2025.1 today, this is the flow you'll migrate to in 2025.2. The `platform create` / `app create` XSCT commands replace the old `hsi` domain-creation commands. The key change: always pass `-proc psu_cortexa53_0` explicitly (not `psu_cortexa53_1` through `_3`) for single-core bare-metal targeting A53 Core 0.
