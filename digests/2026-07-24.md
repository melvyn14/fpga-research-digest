# FPGA Research Digest - 2026-07-24

## Executive Summary

- **AXI-Lite WSTRB pitfall**: bare-metal writes to BRAM via AXI-Lite require correct byte-strobe (`WSTRB`) values; a common bug is leaving all four strobe bits high on a 32-bit bus when intending a sub-word write, which silently overwrites adjacent bytes.
- **Block design TCL export**: avoid `apply_bd_automation` in scripts — it introduces version-specific side effects. Use explicit `connect_bd_net` / `connect_bd_intf_net` calls to keep the `create_bd.tcl` reproducible across Vivado versions.
- **Kria KV260 JTAG boot flow**: for iterative bare-metal development you can bypass SD/QSPI entirely: put the board into JTAG mode, use an XSDB script to download `fsbl.elf`, `pmufw.elf`, the bitstream, and your application ELF — no `BOOT.BIN` required.
- **Timing constraints for AXI-Lite on Kria**: the PS-side `pl_clk0` is auto-constrained by Vivado when you use a Zynq MPSoC IP; you only need `set_clock_groups -asynchronous` if you add a second PL clock domain — leaving it out causes Vivado to pessimistically time async paths.
- **Vivado 2025.1 known-issues page** (`AR #000037546`) tracks active ML Edition bugs; check before spending time debugging what may already be a confirmed tool defect.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- Once `VALID` is asserted on any AXI channel it **must not be de-asserted** until `READY` is received (rule from ARM IHI0022). Violating this on the write-data channel with the BRAM controller causes the controller to latch stale data — a silent corruption, not a hang.
- The AXI BRAM Controller v4.1 calculates BRAM write-enables from `WSTRB`, burst type, and address offset. For AXI-Lite (always single beat), `WSTRB` == `4'b1111` (all bytes) is the safe default for 32-bit word writes; partial-word writes need exact strobe bits.
- A documented timing bug exists where the BRAM controller's write-enable is asserted one clock too early when the BRAM Enable (`EN`) pin is not properly gated — ensure `EN` is tied to the global enable and not left floating.
- `RVALID` must only be asserted **after** data is ready; do not pipeline read responses ahead of BRAM output latency (typically 1–2 cycles for registered-output mode).
- For debugging, enable `AXI Protocol Checker` IP alongside your BRAM controller in simulation — it catches handshake violations that are invisible in waveforms without explicit assertions.

### Code Example

```c
/* Bare-metal AXI-Lite write to BRAM0 at 0xA0000000 */
#define BRAM0_BASE  0xA0000000UL

static inline void bram_write32(uint32_t offset, uint32_t val) {
    /* volatile prevents compiler from optimizing away the store */
    *(volatile uint32_t *)(BRAM0_BASE + offset) = val;
    /* Memory barrier: ensure store completes before next AXI transaction */
    __asm__ volatile("dsb sy" ::: "memory");
}

static inline uint32_t bram_read32(uint32_t offset) {
    uint32_t val = *(volatile uint32_t *)(BRAM0_BASE + offset);
    __asm__ volatile("dsb sy" ::: "memory");
    return val;
}
```

### Relevance to Your Project

Your `main.c` writes patterns to `BRAM0` (0xA0000000) and `BRAM2` (0xA0010000) and reads them back. The `dsb sy` barrier is critical — without it the Cortex-A53 store buffer may not have flushed to the AXI fabric before the subsequent read, causing false FAILs even when the hardware is correct. If you see intermittent FAIL results, add the barrier after every write.

## Vivado Block Design / IP Integrator

### Key Findings

- **Export → edit → replay** is the canonical workflow: create the design interactively in the GUI, then use `File → Export Block Design → Tcl` to capture the script. Edit the Tcl to remove GUI-only fluff and keep only `create_bd_cell`, `set_property`, `connect_bd_*` calls.
- `apply_bd_automation` is version-sensitive and can produce different connections between Vivado minor versions. Prefer explicit wiring in scripts used for CI or reproducible builds.
- IP Integrator validates addresses automatically when you click **Validate Design (F6)**; check the Address Editor view (`Window → Address Editor`) to confirm BRAM0 is at 0xA0000000 and BRAM2 at 0xA0010000 after running `assign_bd_address`.
- Regenerating output products (`generate_target all [get_files *.bd]`) is required after any block design change before export to Vitis — skipping this step is a common cause of stale wrappers.
- Block design wrapper auto-generation: `make_wrapper -files [get_files *.bd] -top` creates the HDL wrapper. If your `kv260_top.vhd` instantiates this wrapper, rerun the command after any IP update.

### Code Example

```tcl
# Explicit BRAM controller connection (no apply_bd_automation)
create_bd_cell -type ip -vlnv xilinx.com:ip:axi_bram_ctrl:4.1 axi_bram_ctrl_0
set_property -dict [list \
    CONFIG.DATA_WIDTH {32} \
    CONFIG.SINGLE_PORT_BRAM {1} \
    CONFIG.ECC_TYPE {0} \
] [get_bd_cells axi_bram_ctrl_0]

# Connect AXI slave port to PS master port
connect_bd_intf_net [get_bd_intf_pins zynq_ultra_ps_e_0/M_AXI_HPM0_FPD] \
                    [get_bd_intf_pins axi_bram_ctrl_0/S_AXI]

# Assign address
assign_bd_address [get_bd_addr_segs axi_bram_ctrl_0/S_AXI/Mem0]
set_property offset 0xA0000000 \
    [get_bd_addr_segs zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0]
set_property range 64K \
    [get_bd_addr_segs zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0]
```

### Relevance to Your Project

Your `create_bd.tcl` script should follow this explicit-connection pattern for both BRAM controllers. Any `apply_bd_automation` calls that were auto-generated may behave differently under Vivado 2025.x compared to when the design was first created.

## Vivado TCL Scripting

### Key Findings

- **Non-project mode** is ideal for CI: no `.xpr` file, no managed IP cache — just source files, XDC, and a driver script. Vivado runs as a pure Tcl interpreter: `vivado -mode batch -source build.tcl`.
- The canonical non-project flow is: `read_vhdl` → `read_xdc` → `synth_design` → `write_checkpoint` → `opt_design` → `place_design` → `route_design` → `write_bitstream`.
- Always `write_checkpoint` after `place_design` and `route_design` — this enables incremental compilation on subsequent runs, dramatically cutting runtime when only C code (not the bitstream) changes.
- For Zynq block designs in non-project mode, open the DCP exported from `write_block_design` then proceed — the BD must still be compiled to a DCP first (project mode or IPI Tcl API, then export).
- `report_timing_summary -file timing.rpt` after `route_design` is the definitive check; a positive Worst Negative Slack (WNS) means timing is met.

### Code Example

```tcl
# Minimal non-project batch flow for KV260 bitstream
set part "xck26-sfvc784-2LV-c"
set top  "kv260_top"

read_vhdl    [glob ./vhdl/*.vhd]
read_xdc     ./constraints/kv260_top.xdc

synth_design -top $top -part $part -flatten_hierarchy rebuilt
write_checkpoint -force ./checkpoints/post_synth.dcp
report_utilization -file ./reports/utilization_synth.rpt

opt_design
place_design
write_checkpoint -force ./checkpoints/post_place.dcp

route_design
write_checkpoint -force ./checkpoints/post_route.dcp
report_timing_summary -max_paths 10 -file ./reports/timing.rpt

# Fail loudly if timing not met
set wns [get_property SLACK [get_timing_paths -max_paths 1 -nworst 1 -setup]]
if { $wns < 0 } { error "Timing not met: WNS = $wns ns" }

write_bitstream -force ./output/kv260_top.bit
```

### Relevance to Your Project

Wrapping your build in a non-project Tcl script means the bitstream can be regenerated with a single command. Since your block design is already captured in `create_bd.tcl`, add a preamble that sources it and exports a DCP before the `synth_design` call.

## Vitis Bare-Metal / Standalone

### Key Findings

- **Vitis 2025.1 Unified IDE** (VS Code-based) replaced the Eclipse IDE. The workflow is: export XSA from Vivado → create platform in Vitis → create application project targeting `standalone` domain.
- For Kria KV260 bare-metal, choose the **A53 core 0** as the CPU target in the standalone domain. Core 0 is where the FSBL runs; your application replaces it post-boot.
- `xil_printf` is routed to **UART1** on the KV260 by default (MIO 48/49). Verify the BSP `standalone` settings set `stdin`/`stdout` to `psu_uart_1`. If output is garbled or absent, check the BSP configuration YAML.
- **Linker script gotcha**: the default linker script places all sections in DDR. If your BRAM addresses (0xA0000000, 0xA0010000) show up in the linker map as allocated memory regions, the linker script has mis-classified PL address space — add explicit `MEMORY` regions excluding PL peripherals.
- The BIST tutorial for KV260 with Vivado/Vitis 2025.1 is available on Hackster.io and covers the full XSA → BSP → application workflow for this exact board.

### Code Example

```c
#include "xil_printf.h"
#include "xparameters.h"
#include "sleep.h"

/* xparameters.h defines XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR = 0xA0000000
   XPAR_AXI_BRAM_CTRL_1_S_AXI_BASEADDR = 0xA0010000 */

#define TEST_PATTERN  0xDEADBEEFUL
#define BRAM_DEPTH    (16 * 1024 / 4)   /* 16 KB / 4 bytes per word */

int main(void) {
    xil_printf("\r\n=== KV260 AXI-BRAM Test ===\r\n");

    volatile uint32_t *bram0 = (uint32_t *)XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR;
    volatile uint32_t *bram2 = (uint32_t *)XPAR_AXI_BRAM_CTRL_1_S_AXI_BASEADDR;

    for (int i = 0; i < 16; i++) {
        bram0[i] = TEST_PATTERN + i;
        bram2[i] = ~(TEST_PATTERN + i);
    }
    __asm__ volatile("dsb sy" ::: "memory");

    int pass = 1;
    for (int i = 0; i < 16; i++) {
        if (bram0[i] != TEST_PATTERN + i)       { pass = 0; break; }
        if (bram2[i] != ~(TEST_PATTERN + i))    { pass = 0; break; }
    }

    xil_printf("BRAM test: %s\r\n", pass ? "PASS" : "FAIL");
    return 0;
}
```

### Relevance to Your Project

The `xparameters.h` approach is cleaner than hardcoding `0xA0000000` — once the XSA is exported, Vitis generates these defines automatically from your Address Editor assignments. Replace your raw address literals with `XPAR_*` macros to make the code portable across address remappings.

## XDC Timing Constraints

### Key Findings

- The Zynq MPSoC IP auto-creates `pl_clk0` with a `create_clock` constraint baked into the IP's XDC; **do not duplicate it** in your top-level XDC or Vivado reports a clock definition conflict.
- `set_input_delay` and `set_output_delay` are only needed for **external I/O ports** (pins going off-chip). Internal AXI connections between PS and BRAM do not need them.
- If you add a second PL clock (e.g., for a video pipeline): `set_clock_groups -asynchronous -group [get_clocks pl_clk0] -group [get_clocks pl_clk1]`. Without this, Vivado attempts to time cross-domain paths and may fail or generate misleading WNS numbers.
- `set_false_path -from [get_ports reset_n]` is a common constraint for async reset inputs — prevents Vivado from trying to time a path that will never be critical.
- The 2025.1 AMD TCL reference (UG835) documents the full syntax for `set_input_delay -clock_fall -add_delay` for DDR-style interfaces.

### Code Example

```xdc
# KV260 top-level XDC — minimal constraints for AXI-BRAM demo
# pl_clk0 is defined by the Zynq MPSoC IP XDC; do NOT redefine it here.

# Async reset from push-button (active-low) — no timing requirement
set_false_path -from [get_ports {reset_n}]

# If a second PL clock is added for a peripheral:
# set_clock_groups -asynchronous \
#   -group [get_clocks -of_objects [get_pins zynq_ultra_ps_e_0/inst/PS8_i/PLCLK[0]]] \
#   -group [get_clocks -of_objects [get_pins clk_wiz_0/inst/mmcme4_adv_inst/CLKOUT0]]

# Physical location: LED on KV260 carrier (PMOD header J2 pin 1)
set_property PACKAGE_PIN H12      [get_ports {led[0]}]
set_property IOSTANDARD  LVCMOS33 [get_ports {led[0]}]
```

### Relevance to Your Project

Your AXI-BRAM demo is single-clock-domain, so XDC constraints are minimal. The main constraint you need is `set_false_path` on any async reset tied to a push-button. Everything else is handled by the Zynq MPSoC IP's built-in constraints.

## Kria KV260 / K26 SoM

### Key Findings

- **Boot mode selection**: MODE[3:0] pins are set by the carrier card. KV260 ships in **QSPI32** mode. For bare-metal development, set SW1 to **JTAG** mode (all MODE pins low) — this lets you download FSBL + bitstream + ELF directly over the debug cable without touching QSPI.
- **JTAG bare-metal sequence**: (1) power on in JTAG mode, (2) use XSDB or Vitis debug to download `fsbl.elf` to DDR, (3) run FSBL (it programs the PL), (4) download and run your application ELF — no `BOOT.BIN` packaging needed during development.
- **PS MIO bank voltages**: Bank 501 (MIO 0-25) runs at 1.8V; Bank 502 (MIO 26-51) runs at 1.8V on the K26 SoM. The UART1 TX/RX (MIO 48/49) is in Bank 502 — ensure your USB-UART adapter handles 1.8V levels (the KV260 carrier does this via a level shifter).
- **PL power rail**: `VCCO_PL` on the KV260 carrier is 3.3V for most banks. Ensure your XDC `IOSTANDARD` matches (use `LVCMOS33` for 3.3V I/O on PL pins).
- The K26 SoM has **4 PS-PL clock outputs** (`pl_clk0`–`pl_clk3`) configurable in the Zynq MPSoC IP. For a bare AXI demo, only `pl_clk0` is needed — leave others disabled to save power.

### Code Example

```tcl
# XSDB script: download and run bare-metal app via JTAG (no BOOT.BIN)
# Run from Vitis XSDB console: xsdb run_bare.tcl

connect
targets -set -nocase -filter {name =~ "*PSU*"}

# Bring PS out of reset
rst -system

# Download FSBL (programs PL with your bitstream)
targets -set -nocase -filter {name =~ "*A53*#0*"}
dow fsbl/fsbl.elf
con
after 5000

# Download and run your application
stop
dow application/Release/kv260_axi_bram_demo.elf
con
```

### Relevance to Your Project

This XSDB flow eliminates the need to package `BOOT.BIN` during every iteration. With the KV260 in JTAG mode you can rebuild in Vitis and re-download in seconds, making the PASS/FAIL loop much tighter. Once the design is stable, switch to SD-card `BOOT.BIN` packaging for standalone operation.

## AMD/Xilinx Tool Updates (Vivado/Vitis 2025.x)

### Key Findings

- **Vivado 2025.1** (UG973) and **Vitis 2025.1** (UG1742) were released in 2025; Vitis UG1742 for 2025.1 was published July 8, 2025.
- **Known issues** for Vivado ML Edition 2025.x are tracked in AMD Adaptive Support article **AR #000037546** — check this before filing a support case.
- **Vitis Unified IDE** (VS Code shell) is now the default; the classic Eclipse-based Vitis IDE is available via a compatibility flag but scheduled for deprecation.
- **Vitis AI 5.0** is verified compatible with Vivado/Vitis/PetaLinux 2025.1, relevant if you later add ML inference to the KV260 design.
- **AXI BRAM Controller v4.1** ships with 2025.1 unchanged from recent releases; the ECC datapath adds one clock of latency — leave ECC disabled (`ECC_TYPE=0`) for bare-metal demos where latency matters more than error correction.
- **RapidWright 2025.2.1-beta** supports a pre-implemented module flow that can accelerate incremental bitstream generation — useful if your block design grows larger.
- **UG835** (Vivado Tcl Commands Reference) was updated for 2025.1 with revised `set_output_delay` and `set_input_delay` docs; `set_param ips.includeClockLocationConstraints true` is documented for ensuring correct hold timing on Out-of-Context IP.

### Code Example

```tcl
# Vivado 2025.1: enable clock location constraints for OOC IP
# Run once at the start of your build script
set_param ips.includeClockLocationConstraints true

# Upgrade all IP to latest versions before generating output products
upgrade_ip [get_ips]
report_ip_status

# Generate all output products (replaces stale wrappers)
generate_target all [get_files *.bd]
export_ip_user_files -of_objects [get_files *.bd] -no_script -sync -force -quiet

# Quick check for unresolved references before synthesis
check_syntax
```

### Relevance to Your Project

If you started your KV260 project in an earlier Vivado version and opened it in 2025.1, the `upgrade_ip` call is important — IP version mismatches are the most common cause of "IP is locked" errors in regenerated block designs. Run this at the top of your `create_bd.tcl` to keep IP versions pinned to what 2025.1 ships.
