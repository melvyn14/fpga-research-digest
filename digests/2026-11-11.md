# FPGA Research Digest - 2026-11-11

## Executive Summary
- **AXI-Lite handshake rule #1:** VALID must never be gated on READY — violating this causes deadlock; Vivado's own example slave cores have been formally verified to contain this bug (ZipCPU, 2019).
- **BRAM address range:** The AXI BRAM Controller's address range must be set large enough in the Vivado Address Editor to cover all BRAM offsets; writes beyond the mapped range are silently dropped — directly relevant to 0xA0010000 (BRAM2) placement.
- **Vitis 2025.1 breaking change:** AMD deprecated all Kria XSCT BSPs in 2025.1; bare-metal Kria projects should regenerate BSPs from hardware XSA in the Vitis Unified IDE (classic IDE also deprecated in 2025.2).
- **TCL reproducibility:** `write_bd_tcl` is the correct command to export a block design as a reproducible TCL script; `write_project_tcl` calls it automatically per BD but requires the working directory to match where the script was created.
- **Kria boot mode:** The KV260 uses QSPI+eMMC as the production boot mode; bare-metal flows replace `BOOT.bin` in the QSPI/SD sector — MIO bank 500 is reserved for SOM peripherals (QSPI, eMMC, I2C, TPM).

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings
- **VALID must not depend on READY.** The AXI spec explicitly forbids making AWVALID, WVALID, ARVALID, or RVALID conditional on the corresponding READY signal. Setting VALID combinationally from READY creates a deadlock potential. ZipCPU's formal verification of Vivado-generated slave example code confirmed this bug is present in Vivado 2018.3 example designs.
- **Formal property checkers catch hidden bugs.** ZipCPU's AXI-Lite property set (available on GitHub) can be instantiated in simulation or SymbiYosys formal flows. Running it against your own AXI slave catches protocol violations before hardware bring-up.
- **AXI-Lite in-order only.** The AXI BRAM Controller executes all transactions in-order regardless of thread ID; no read/write reordering is implemented. This simplifies software but means no pipelining across outstanding transactions.
- **BRAM controller supports both AXI4 and AXI4-Lite.** The core can be configured for a single or dual BRAM port; AXI4-Lite mode is correct for 32-bit register-mapped access as used in the KV260 demo.
- **AXI-Stream sideband pitfalls.** TKEEP may only partially deassert on the last beat (TLAST=1); asserting it mid-packet violates the spec. TUSER width of 0 omits the signal entirely — mismatches between IP configuration and HDL logic silently drop the port connection in Vivado.

### Code Example
```vhdl
-- AXI-Lite read channel: correct RVALID handshake
-- RVALID must be set by the slave and held until RREADY is asserted
process(clk)
begin
  if rising_edge(clk) then
    if rst = '1' then
      s_axi_rvalid <= '0';
      s_axi_rdata  <= (others => '0');
    else
      -- Only assert RVALID when data is ready; never gate on RREADY
      if read_data_ready = '1' and s_axi_rvalid = '0' then
        s_axi_rdata  <= bram_read_data;
        s_axi_rvalid <= '1';
      elsif s_axi_rvalid = '1' and s_axi_rready = '1' then
        -- Transfer complete; deassert only after master acknowledges
        s_axi_rvalid <= '0';
      end if;
    end if;
  end if;
end process;
```

### Relevance to Your Project
Your `main.c` reads back from BRAM0 (0xA0000000) and BRAM2 (0xA0010000) over AXI-Lite. If the AXI slave in your block design gates RVALID on RREADY, the read-back will silently stall. Run a quick formal or simulation check using ZipCPU's `faxil_slave.v` properties against `kv260_top.vhd` to verify protocol compliance before blaming BRAM content errors on data bugs.

## Vivado Block Design / IP Integrator

### Key Findings
- **Address Editor is mandatory for multi-BRAM layouts.** Each BRAM controller must have its address segment explicitly sized to cover the full depth of the BRAM. For a 64KB BRAM, set the range to 64K in the Address Editor; leaving it at the default 4K means accesses above offset 0xFFF are out-of-range.
- **Connection Automation does not set addresses.** Running `apply_bd_automation` wires up AXI ports but leaves address assignment incomplete; always follow with a manual check in the Address Editor or use `assign_bd_address` in TCL.
- **Regenerate output products after any IP parameter change.** In Vivado, changing a BRAM depth or AXI data width does not automatically regenerate synthesis output products; run `generate_target all [get_files *.bd]` or use the GUI "Generate Block Design" button.
- **Block design wrapper must be re-generated after modifications.** After editing the BD, right-click the BD in Sources and choose "Create HDL Wrapper" (Allow Vivado to automatically manage), or use `make_wrapper -files [get_files *.bd] -top`.
- **IP Integrator in Non-Project Mode (2025.2 UG994).** You must run `generate_target all` before top-level synthesis; Vivado does not auto-generate output products in non-project mode.

### Code Example
```tcl
# Assign addresses for two BRAM controllers in a block design
# Run after create_bd_cell and connect_bd steps

# Assign BRAM0 at 0xA0000000, 64KB range
assign_bd_address [get_bd_addr_segs {axi_bram_ctrl_0/S_AXI/Mem0}]
set_property offset 0xA0000000 [get_bd_addr_segs \
    {processing_system7_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property range 64K [get_bd_addr_segs \
    {processing_system7_0/Data/SEG_axi_bram_ctrl_0_Mem0}]

# Assign BRAM2 at 0xA0010000, 64KB range
assign_bd_address [get_bd_addr_segs {axi_bram_ctrl_1/S_AXI/Mem0}]
set_property offset 0xA0010000 [get_bd_addr_segs \
    {processing_system7_0/Data/SEG_axi_bram_ctrl_1_Mem0}]
set_property range 64K [get_bd_addr_segs \
    {processing_system7_0/Data/SEG_axi_bram_ctrl_1_Mem0}]

# Regenerate output products
generate_target all [get_files *.bd]
```

### Relevance to Your Project
Your `create_bd.tcl` likely uses `assign_bd_address` for both BRAM controllers. The snippet above matches your project's address map (BRAM0=0xA0000000, BRAM2=0xA0010000). Confirm the range is ≥64K to avoid silent out-of-range drops on higher-offset writes.

## Vivado TCL Scripting

### Key Findings
- **`write_project_tcl` vs `write_bd_tcl`:** `write_project_tcl` generates a script that recreates the entire project, calling `write_bd_tcl` automatically for each block design. `write_bd_tcl` alone exports only the BD — preferred for version-controlled projects where only the BD changes.
- **Working directory matters.** The script generated by `write_project_tcl` must be sourced from the same directory it was created in; the new project is created in the current working directory. Set `cd` explicitly at the top of your CI/automation scripts.
- **Batch mode exits after script completion.** Use `vivado -mode batch -source create_bd.tcl`; the tool exits on completion and does not need an explicit `quit`. Reports requiring GUI interactivity should be commented out for batch runs.
- **Non-project mode skips XPR.** No `.xpr` file is written; the design is held in-memory. Useful for CI pipelines but requires all steps (read_vhdl, read_bd, generate_target, synth_design, opt_design, place_design, route_design, write_bitstream) to be explicit in the script.
- **`-use_bd_files` flag:** Passing `-use_bd_files 1` to `write_project_tcl` stores block designs as `.bd` source files rather than regenerating them from TCL, which is faster but less portable across Vivado versions.

### Code Example
```tcl
# Minimal non-project mode build script for KV260 AXI-BRAM demo
# Usage: vivado -mode batch -source build.tcl

# Target device: Kria K26 SoM on KV260 (xczu5ev-sfvc784-2-e or xck26 part)
set device "xck26-sfvc784-2LV-c"

# Read sources
read_vhdl  ../vhdl/kv260_top.vhd
read_bd    ../bd/kv260_bd.bd
read_xdc   ../xdc/kv260_timing.xdc

# Generate BD output products before synthesis
generate_target all [get_files *.bd]
make_wrapper -files [get_files *.bd] -top

# Synthesize
synth_design -top kv260_top -part $device -flatten_hierarchy rebuilt

# Implement
opt_design
place_design
route_design

# Check timing
report_timing_summary -file timing_summary.rpt

# Write bitstream
write_bitstream -force kv260_demo.bit
```

### Relevance to Your Project
Your `create_bd.tcl` is a BD-creation script. Adding the full non-project build flow above lets CI regenerate the bitstream from scratch without a GUI, which is useful for validating changes to the block design or VHDL top-level without opening Vivado interactively.

## Vitis Bare-Metal / Standalone

### Key Findings
- **Kria XSCT BSPs deprecated in 2025.1.** AMD's 2025.1 open-source release notes explicitly list all Kria XSCT BSPs as deprecated. The recommended path is to generate a new BSP from the exported hardware XSA in the Vitis Unified IDE (File → New → Platform Project).
- **STDIN/STDOUT routing is BSP-controlled.** The `standalone_stdin` and `standalone_stdout` settings in the BSP configuration (`vitis-comp.json`) determine which UART `xil_printf()` outputs to. For KV260/KD240, UART 1 (MIO38/39) routes to the JTAG/USB-UART console.
- **Classic Vitis IDE deprecated in 2025.2.** AMD moved all Kria bare-metal workflows to the Vitis Unified IDE. The classic IDE (`vitis -classic`) still works but will not receive new feature support.
- **BSP must be regenerated after XSA update.** Changing the Vivado block design (e.g., adding a new AXI peripheral) and re-exporting the XSA does not automatically update the BSP; you must right-click the platform and "Update Hardware."
- **Interrupt controller startup order.** For bare-metal interrupt-driven designs, initialize `XScuGic` before enabling interrupts on individual peripherals; failing to do so causes the interrupt controller to silently drop the first interrupt.

### Code Example
```c
/* Minimal AXI-BRAM read-write test for Kria KV260 bare-metal
 * BRAM0 base: 0xA0000000, BRAM2 base: 0xA0010000
 * Uses Xilinx standalone xil_io.h for 32-bit MMIO
 */
#include "xil_printf.h"
#include "xil_io.h"
#include "sleep.h"

#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL
#define TEST_PATTERN 0xDEADBEEFUL

static int test_bram(u32 base, const char *name) {
    Xil_Out32(base, TEST_PATTERN);
    /* Small delay to ensure AXI write completes before read */
    usleep(1);
    u32 val = Xil_In32(base);
    if (val == TEST_PATTERN) {
        xil_printf("%s: PASS (0x%08X)\r\n", name, val);
        return 0;
    } else {
        xil_printf("%s: FAIL (expected 0x%08X, got 0x%08X)\r\n",
                   name, TEST_PATTERN, val);
        return -1;
    }
}

int main(void) {
    xil_printf("KV260 AXI-BRAM demo starting\r\n");
    int result = 0;
    result |= test_bram(BRAM0_BASE, "BRAM0");
    result |= test_bram(BRAM2_BASE, "BRAM2");
    xil_printf("Overall: %s\r\n", result == 0 ? "PASS" : "FAIL");
    return result;
}
```

### Relevance to Your Project
This is essentially what your `main.c` implements. The `usleep(1)` guard after `Xil_Out32` prevents a rare race where the AXI write transaction has not yet committed before the subsequent read on fast processors. If you observe intermittent FAIL results only at high optimization levels, add this guard.

## XDC Timing Constraints

### Key Findings
- **Avoid `set_max_delay` for general I/O constraints.** AMD's UG903 2026.1 edition explicitly advises against routinely using `set_max_delay` for input/output logic. Use `set_input_delay` and `set_output_delay` instead, which correctly associates a clock with the port.
- **Clock latency included unless you specify otherwise.** The 2025.1 UG835 notes that the Vivado timing engine includes clock network latency in I/O delay analysis unless `set_input_delay -source_latency_included` is used. For PS-generated clocks on Zynq UltraScale+, the tool models the PLL and routing latency automatically.
- **Output delay can be negative.** If the external device samples data launched by the same clock as the FPGA output, and data arrival is early relative to capture, the output delay value may be negative — this is valid and correct.
- **`set_max_delay -datapath_only` for async paths.** For CDC (clock domain crossing) paths or paths between the PS and PL clocks, use `-datapath_only` to remove the skew component and constrain only the combinational delay. Without `-datapath_only`, Vivado includes clock skew in the analysis and can give misleading hold violations.
- **Clock groups for PS-to-PL.** On Zynq/Kria, the PS generates PL clocks via the FCLKCLK ports. These share a common PLL source but Vivado may treat them as logically independent; use `set_clock_groups -asynchronous` between fclk_clk0 and any other independent clock to suppress false CDC paths.

### Code Example
```tcl
# XDC constraints for KV260 bare-metal AXI-BRAM demo
# PS generates PL clock at 100 MHz via FCLK_CLK0

# Primary PL clock (PS-generated, Vivado auto-derives from PS block)
# If not auto-created, declare it explicitly:
# create_clock -period 10.000 -name clk_pl_0 [get_pins ps_0/FCLKCLK[0]]

# If the design has a secondary free-running clock (e.g. oscillator):
# create_clock -period 20.000 -name clk_osc [get_ports CLK_OSC]
# set_clock_groups -asynchronous \
#   -group [get_clocks clk_pl_0] \
#   -group [get_clocks clk_osc]

# External GPIO input from expansion connector (assume 2ns board delay)
set_input_delay -clock [get_clocks clk_pl_0] -max  3.0 [get_ports {GPIO_IN[*]}]
set_input_delay -clock [get_clocks clk_pl_0] -min  0.5 [get_ports {GPIO_IN[*]}]

# External GPIO output to expansion connector (assume 2ns board delay)
set_output_delay -clock [get_clocks clk_pl_0] -max  3.0 [get_ports {GPIO_OUT[*]}]
set_output_delay -clock [get_clocks clk_pl_0] -min -1.0 [get_ports {GPIO_OUT[*]}]

# Suppress timing on JTAG/debug paths (not in production timing path)
set_false_path -from [get_ports {JTAG_*}]
```

### Relevance to Your Project
The KV260 AXI-BRAM demo drives no off-chip timing-critical signals (all AXI traffic is PS-internal), so the most important XDC work is ensuring Vivado correctly models `FCLK_CLK0` and that no unintended async paths exist between the PS clock domain and any PL-side logic in `kv260_top.vhd`.

## Kria KV260 / K26 SoM

### Key Findings
- **MIO bank allocation is fixed by the SoM.** Bank 500 (MIO 0–25) is entirely reserved for onboard SoM peripherals: QSPI Flash (MIO0–5), eMMC (MIO13–22), UART1 console (MIO38–39), I2C (MIO24–25), TPM SPI. These cannot be reassigned to PL via EMIO.
- **Boot mode on KV260 is QSPI+eMMC.** The KV260 carrier card boots from QSPI, loading a first-stage image that bootstraps from eMMC. For bare-metal development, the typical approach is to program your `BOOT.bin` via JTAG (`program_hw_devices`) or write it to the SD card/eMMC partition.
- **EMIO for PL-to-PS GPIO.** Additional GPIO between PS and PL must use EMIO (Extended MIO). MIO pins are physical package pins; EMIO signals are routed through the PL fabric and must be mapped in XDC.
- **Dynamic MIO configuration via PMU.** AMD's KV260/KR260 reference designs use the Platform Management Unit (PMU) to dynamically configure carrier-card-specific MIO, allowing the same SoM firmware to support multiple carrier cards.
- **UG1091 2025-09-18 revision.** The latest carrier card design guide was updated September 2025. It includes the SOM240_1 connector pinout and power domain specifications for K26-based designs.

### Code Example
```c
/* Access EMIO GPIO from bare-metal (PS GPIO bank 2 = EMIO[0..31])
 * Assumes EMIO GPIO is connected in the block design
 */
#include "xgpiops.h"
#include "xparameters.h"

#define GPIO_DEVICE_ID  XPAR_XGPIOPS_0_DEVICE_ID
/* EMIO GPIO starts at pin 54 (MIO pins 0-53, EMIO starts at 54) */
#define EMIO_PIN_BASE   54
#define PL_LED_PIN      (EMIO_PIN_BASE + 0)   /* EMIO[0] -> PL LED */

static XGpioPs GpioInstance;

int init_emio_gpio(void) {
    XGpioPs_Config *cfg = XGpioPs_LookupConfig(GPIO_DEVICE_ID);
    if (!cfg) return -1;
    if (XGpioPs_CfgInitialize(&GpioInstance, cfg, cfg->BaseAddr) != XST_SUCCESS)
        return -1;
    /* Set EMIO[0] as output */
    XGpioPs_SetDirectionPin(&GpioInstance, PL_LED_PIN, 1);
    XGpioPs_SetOutputEnablePin(&GpioInstance, PL_LED_PIN, 1);
    return 0;
}

void set_pl_led(int on) {
    XGpioPs_WritePin(&GpioInstance, PL_LED_PIN, on ? 1 : 0);
}
```

### Relevance to Your Project
The KV260 AXI-BRAM demo's pass/fail result currently goes to UART. If you want a hardware indicator (LED blink on PASS), EMIO GPIO is the correct path — add it to the PS block in the BD, connect to a PL output port, and use the XGpioPs driver above.

## AMD/Xilinx Tool Updates (2025.x)

### Key Findings
- **Vitis Unified IDE is now the default (2025.1/2025.2).** The classic Vitis IDE (`vitis -classic`) is deprecated as of 2025.2 and will not receive new features. Bare-metal workflows must migrate to the Unified IDE's platform/domain/application project structure.
- **Kria XSCT BSPs deprecated in 2025.1.** All Kria-specific XSCT board support packages are listed as deprecated. Use the Vitis Unified IDE to generate BSPs from the XSA exported from Vivado.
- **Vitis AI 5.0 targets 2025.1.** The DPU IP and Vitis AI library were updated for 2025.1 compatibility; this is relevant if adding ML inference to the KV260 (which has DPU IP in the production platform).
- **Vivado 2026.1 documentation in production.** AMD docs now refer to 2026.1 for several reference guides (UG892, UG903, UG835, UG953), suggesting a 2026.1 Vivado release is active or imminent. Features in 2026.1 include updated XPM_FIFO_AXIL_SV macros.
- **OS support changes in next release.** UG1742 (Vitis 2025.1 release notes) warns that Ubuntu 22.04.2 LTS and Red Hat 9.2/9.3 will drop from the supported OS list in a forthcoming release.
- **AWS F2 / HBM timing issue in 2025.1.** A known Vivado 2025.1 issue inserts `DONT_TOUCH` on HBM models, making timing closure harder on HBM-equipped devices. AMD has committed to a fix in a future release (does not affect Kria/K26).

### Code Example
```tcl
# Migrate a 2024.x Vivado project to 2025.1 non-project mode
# Step 1: Open the old project in 2025.1 to trigger IP version upgrades
open_project ./kv260_legacy/kv260_legacy.xpr

# Step 2: Check for IP version reports
report_ip_status -file ip_status.rpt

# Step 3: Upgrade stale IPs (run interactively or in batch)
upgrade_ip [get_ips *]

# Step 4: Export updated block design as TCL (for version control)
write_bd_tcl -force ./tcl/create_bd_2025.tcl [get_files *.bd]

# Step 5: Export hardware for Vitis Unified IDE
write_hw_platform -fixed -force -file ./kv260_top.xsa

# In Vitis Unified IDE CLI:
# xsct
#   platform create -name kv260_platform -hw kv260_top.xsa
#   platform generate
#   app create -name bram_test -platform kv260_platform \
#              -domain standalone_domain -template {Empty Application}
```

### Relevance to Your Project
If your Vivado 2025.1 project was originally created on an earlier version, running `upgrade_ip` after opening it ensures the AXI BRAM Controller and AXI Interconnect IPs are on their latest compatible versions. The `write_hw_platform` / `xsct` sequence above replaces the old `write_sysdef` + classic Vitis flow for generating your bare-metal BSP.
