# FPGA Research Digest - 2026-09-06

## Executive Summary

- **AXI BRAM Controller timing bug**: The AXI BRAM Controller IP can assert write-enable one clock cycle early, writing extra words; tying the BRAM Enable signal correctly gates this off. Relevant directly to BRAM0 and BRAM2 accesses in the KV260 demo.
- **Vitis BSP UART misconfiguration on Kria**: The standalone BSP defaults to `psu_uart_0` for stdin/stdout, but the physical JTAG/UART on Kria starter kits is `psu_uart_1`. Missing this setting silently swallows all `xil_printf` output—change both `standalone_stdin` and `standalone_stdout` in `vitis-comp.json`.
- **AXI address alignment pitfall on UltraScale+**: Only word-aligned (4-byte) addresses return valid data via AXI-Lite; reads to holes return `0x00000000` with OKAY response, making silent misreads easy to miss in PASS/FAIL logic.
- **Non-project TCL automation**: `vivado -mode batch -source build.tcl` is the cleanest way to drive synthesis, implementation, and bitstream generation without GUI overhead—directly applicable to CI/CD for the KV260 project.
- **Vivado 2026.1 licensing change**: AMD's new tiered model changes which device families and features are included at each price point; verify your license covers Kria/ZU5EV before upgrading from 2025.1.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- **AXI-Lite transfers are always 32-bit wide**; reads to unmapped address holes return `0x00000000` with an OKAY response—no bus error—making silent misreads easy to confuse with a successful "all-zeros" write test.
- **Write-enable duration bug in AXI BRAM Controller**: The IP can assert write-enable one clock cycle early and hold it one cycle too long when the BRAM Enable pin is left floating or tied incorrectly. Gating BRAM Enable with the AXI active period fixes it.
- **TVALID is "sticky"** in AXI-Stream: once asserted by the master it cannot be de-asserted until the slave raises TREADY. Violating this causes protocol deadlocks that are hard to catch without an AXI VIP or ILA.
- **Backpressure via TREADY**: the slave drives TREADY to zero to stall the source; TLAST marks the end of a packet (first TVALID after a TLAST begins the next packet).
- **AXI4-Lite vs AXI4**: AXI-Lite has no burst support and enforces single-beat transactions; the AXI BRAM Controller supports both AXI4 (burst) and AXI4-Lite modes—use AXI4 for higher throughput if your PS master supports it.

### Code Example

```c
/* Bare-metal AXI-Lite write-then-readback with explicit address alignment check */
#include "xil_io.h"
#include "xil_printf.h"

#define BRAM0_BASE 0xA0000000UL
#define BRAM2_BASE 0xA0010000UL
#define WORD_STEP  4           /* AXI-Lite is 32-bit; always step by 4 bytes */

void axi_bram_test(u32 base, u32 num_words) {
    u32 i, readback, errors = 0;
    /* Write phase */
    for (i = 0; i < num_words; i++)
        Xil_Out32(base + i * WORD_STEP, 0xDEAD0000 | i);
    /* Read-back phase */
    for (i = 0; i < num_words; i++) {
        readback = Xil_In32(base + i * WORD_STEP);
        if (readback != (0xDEAD0000 | i)) {
            xil_printf("FAIL @ 0x%08X: wrote 0x%08X read 0x%08X\r\n",
                       base + i * WORD_STEP, 0xDEAD0000 | i, readback);
            errors++;
        }
    }
    xil_printf(errors ? "BRAM @ 0x%08X: FAIL (%u errors)\r\n"
                      : "BRAM @ 0x%08X: PASS\r\n", base, errors);
}
```

### Relevance to Your Project

Your `main.c` writes patterns to BRAM0 at `0xA0000000` and BRAM2 at `0xA0010000`. The word-step loop above matches your layout exactly. The write-enable bug is worth checking in simulation (ILA or behavioral sim): add a BRAM Enable assertion in your block design to ensure the BRAM Enable from the controller is only high during an active AXI transaction.

## Vivado Block Design / IP Integrator

### Key Findings

- **Auto-Assign Address**: right-click anywhere in the Address Editor pane → "Auto-Assign Address" resolves "unmapped peripheral" validation errors instantly.
- **Connection Automation**: when you run connection automation, Vivado automatically inserts a `proc_sys_reset` IP and an AXI Interconnect to route the PS master(s) to all AXI slaves—don't wire these manually.
- **AXI Interconnect outside the block design**: if you need an AXI master external to the BD, connect it to a board-level AXI port and then to an AXI Interconnect inside the BD; the address editor becomes active after those external port connections are made.
- **Regenerating IP**: after changing a Vivado version or IP version, always run "Generate Block Design" (not just "Validate") before synthesis to pick up updated IP netlists.
- **Address ranges**: the AXI BRAM Controller default range is 8 KB (`0x2000`); increase it in the address editor if you use more BRAM depth to avoid address wrap-around reads.

### Code Example

```tcl
# Vivado TCL: set address segments for two BRAM controllers
assign_bd_address
set_property offset 0xA0000000 [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property range  8K          [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property offset 0xA0010000 [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_1_Mem0}]
set_property range  8K          [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_1_Mem0}]
validate_bd_design
save_bd_design
```

### Relevance to Your Project

Your `create_bd.tcl` script likely already calls `assign_bd_address`. The snippet above shows the explicit property-setting form that survives TCL round-trips better than relying on GUI state. Confirm both BRAM controllers have at least 8 KB ranges matching your BRAM generator depth.

## Vivado TCL Scripting

### Key Findings

- **Batch mode invocation**: `vivado -mode batch -source build.tcl` opens Vivado, runs the script, and exits—no GUI required; ideal for CI pipelines.
- **Non-project flow** (no `.xpr` file): `read_vhdl`, `read_xdc`, then `synth_design -top <top> -part <part>`, `opt_design`, `place_design`, `route_design`, `write_bitstream` entirely in memory—faster than project mode.
- **Project mode alternative**: `create_project`, `add_files`, `launch_runs synth_1`, `wait_on_run synth_1` is easier to reproduce GUI behavior and integrates better with incremental compilation.
- **Checkpoint workflow**: `write_checkpoint` after each major step lets you resume from mid-flow without re-running earlier steps.
- **`write_hw_platform`**: after generating the bitstream, call this to produce the `.xsa` for Vitis—automates the handoff between tools.

### Code Example

```tcl
# Non-project batch build for KV260 AXI-BRAM demo
set PART "xck26-sfvc784-2LV-c"   ;# K26 SoM part number

read_vhdl  [glob ../vhdl/*.vhd]
read_xdc   [glob ../xdc/*.xdc]

synth_design -top kv260_top -part $PART -flatten_hierarchy rebuilt
write_checkpoint -force ./checkpoints/post_synth.dcp

opt_design
place_design
phys_opt_design
route_design
write_checkpoint -force ./checkpoints/post_route.dcp

write_bitstream -force ./output/kv260_top.bit
write_hw_platform -fixed -include_bit -force ./output/kv260.xsa

puts "Build complete."
```

### Relevance to Your Project

Replacing manual GUI builds with this script ensures reproducible bitstreams across machines. The `xck26-sfvc784-2LV-c` part string matches the K26 SoM; confirm it matches your Vivado target by running `get_parts *k26*` in the Tcl Console.

## Vitis Bare-Metal / Standalone

### Key Findings

- **UART selection is the most common Kria bare-metal trap**: Vitis standalone BSP defaults to `psu_uart_0`, but the Kria KV260 physical JTAG/UART connector is wired to `psu_uart_1`. Change `standalone_stdin` and `standalone_stdout` in `vitis-comp.json` (Settings folder of the platform component) to `psu_uart_1`.
- **`xil_printf` limitations**: does not support floating-point format specifiers (`%f`, `%e`, `%g`). Use integer math for status values, or link in the full `printf` from the newlib libc at the cost of code size.
- **Vitis 2025.2 include path regression**: a reported issue where `xil_printf.h` is not found after project generation; workaround is to add `${SYSROOT}/usr/include` explicitly to the BSP include paths or use `#include <xil_printf.h>` (angle brackets vs quotes).
- **Linker script (`lscript.ld`)**: the default places `.text` and `.data` in `psu_ddr_0_MEM_0`; for very tight bare-metal workloads you can place `.text` in OCM (`psu_ocm_ram_0`) for deterministic latency.
- **Standalone BSP is single-threaded**: no RTOS, no interrupt preemption by default—interrupts must be explicitly enabled via `XScuGic` or `XIntc`.

### Code Example

```c
/* Correct include and UART init for Kria KV260 bare-metal */
#include "xparameters.h"
#include "xuartps.h"
#include "xil_printf.h"

/* In BSP settings: standalone_stdin/stdout = psu_uart_1 */
/* In lscript.ld: stack/heap sized for your use case     */

int main(void) {
    /* xil_printf goes to psu_uart_1 after BSP is configured correctly */
    xil_printf("KV260 AXI-BRAM Demo starting...\r\n");

    /* Always use \r\n — bare-metal UART does not add CR automatically */
    xil_printf("BRAM0 base: 0x%08X\r\n", (u32)0xA0000000);
    xil_printf("BRAM2 base: 0x%08X\r\n", (u32)0xA0010000);

    /* Run tests, then loop forever */
    while (1) { /* poll or interrupt-driven */ }
    return 0;
}
```

### Relevance to Your Project

If your demo prints PASS/FAIL over USB-UART but you see nothing on the terminal, check the BSP UART selection first—it's the single most common culprit on Kria. Confirm with a known-good `xil_printf("hello\r\n")` immediately after `main()` opens.

## XDC Timing Constraints

### Key Findings

- **`set_input_delay` and `set_output_delay`**: both specify external path delays in nanoseconds relative to a clock edge; positive values mean the data arrives/must leave after the clock edge. Always provide both `-max` and `-min` variants for setup and hold analysis.
- **`-clock_fall`**: use when the external device latches/drives on the falling clock edge (DDR-style).
- **Clock groups pitfall**: putting all clocks in one `set_clock_groups -asynchronous` creates timing exceptions between clocks that actually do communicate, masking real violations. Use separate commands per independent domain pair.
- **On Zynq/Kria**: the PS PLL clocks (`pl_clk0`, etc.) are automatically constrained by the Zynq PS IP; you only need XDC constraints for custom PL clocks and I/O.
- **AXI-Lite paths are generally short**: for an internal AXI-Lite bus running at the PS clock frequency, timing usually closes without manual I/O constraints, but adding `set_false_path -through [get_nets *axi_bram*]` for paths that cross async boundaries prevents false negatives.

### Code Example

```xdc
# KV260 XDC: constrain an external sync signal on PL I/O
# Assumes pl_clk0 is 100 MHz (10 ns period) from PS

# Create clock on PL (if using external clock pin, not PS-generated)
# create_clock -period 10.000 -name pl_clk0 [get_ports pl_clk0_pin]

# Example: external data valid after rising edge, hold for 2 ns
set_input_delay -clock [get_clocks clk_pl_0] -max 3.0 [get_ports ext_data_in]
set_input_delay -clock [get_clocks clk_pl_0] -min 1.0 [get_ports ext_data_in]

set_output_delay -clock [get_clocks clk_pl_0] -max 2.5 [get_ports ext_data_out]
set_output_delay -clock [get_clocks clk_pl_0] -min 0.5 [get_ports ext_data_out]

# Mark PS <-> PL AXI clock crossing as asynchronous if separate PLLs used
# set_clock_groups -asynchronous -group [get_clocks clk_pl_0] \
#                                -group [get_clocks clk_pl_1]
```

### Relevance to Your Project

The KV260 AXI-BRAM demo runs entirely on `pl_clk0` generated by the PS, so I/O timing constraints for the AXI bus itself are not needed. If you add external PL I/O (LEDs, buttons, external memory), use the template above. Run `report_timing_summary` after route to confirm no setup/hold violations on the AXI paths.

## Kria KV260 / K26 SoM

### Key Findings

- **Default boot mode is QSPI32**: the `MODE[3:0]` pins are set on the carrier card; on the KV260 starter kit they default to QSPI32 boot. For bare-metal JTAG boot, configure the MODE pins or use the Vitis hardware server to download directly over JTAG without changing flash.
- **Two hardware revisions**: KV260 rev1 and rev2 differ primarily in autofocus support for IAS sensors; for bare-metal AXI demos there is no functional difference.
- **VCCO for sideband signals is 1.80 V**: ensure any carrier-card I/O connected to the SoM sideband pins is 1.8 V tolerant.
- **EMIO for PL GPIO**: the default starter-kit bitstream uses EMIO to route a fan control PWM signal from PS to PL; if you override the bitstream with your own, you must account for this or the thermal management may be affected.
- **K26 SoM XDC**: AMD provides a pre-made XDC with pin assignments for the SoM connector; always start from this file rather than the Vivado board files to avoid mismatches.

### Code Example

```tcl
# TCL snippet: read the official K26 SoM XDC in non-project mode
# Download from AMD: https://www.amd.com/en/products/system-on-modules/kria/k26.html

read_xdc ./constraints/k26-som.xdc    ;# Official SoM pin assignments
read_xdc ./constraints/kv260-top.xdc  ;# Your board-level constraints

# Confirm the PL clock from PS is constrained (Vivado auto-constrains it
# from the PS IP, but verify with:)
# report_clocks
```

### Relevance to Your Project

Download AMD's official K26 XDC and layer your own `kv260_top.xdc` on top. For a bare-metal AXI-BRAM demo, you only need the UART and clock pins; the AXI interface is internal. If you ever see bitstream download failures over JTAG, check the boot mode pins—QSPI32 boot may try to re-load firmware from flash after JTAG download.

## AMD/Xilinx Tool Updates

### Key Findings

- **Vivado 2026.1 released** (as of mid-2026): introduces a new tiered licensing model—"pay for the device families you need." This replaces the prior WebPACK/Standard/Enterprise tiers. If you rely on the free WebPACK license, verify Kria/ZU5EV is still covered before upgrading.
- **2026.1 DSP IP additions**: expanded LogicCore PL DSP (FIR, FFT, Complex MAC) and new AIE-based GEMM/GEMV functions—primarily Versal-focused but the PL DSP cores apply to Zynq UltraScale+ too.
- **Vitis 2025.1 (released 2025-07-08)**: unified installer bundles Vivado + Vitis + Model Composer + Vitis HLS; supports Versal, Zynq MPSoC, Zynq 7000, MicroBlaze. No separate Vivado install needed.
- **Vitis 2025.2 known issue**: `xil_printf.h` not found after project generation—workaround is to add the sysroot include path manually to BSP settings.
- **Vitis Unified IDE**: the new backend (Vitis Server) replaces the Eclipse-based XSCT for most workflows; the classic command-line utilities (`xsct`, `xsdb`) still work for scripting and debugging.

### Code Example

```bash
# Verify tool version compatibility in a TCL script
# Run in Vivado Tcl Console or batch mode
set vivado_version [version -short]
puts "Vivado version: $vivado_version"

# Check available parts for K26
set k26_parts [get_parts *k26*]
puts "K26 parts available: $k26_parts"

# Confirm AXI BRAM Controller IP version
set bram_ctrl_ip [get_ipdefs *axi_bram_ctrl*]
puts "AXI BRAM Controller IP: $bram_ctrl_ip"
```

```tcl

# (run in xsct or Vitis batch mode)

    -platform kv260_platform \
    -domain a53_standalone \
    -template "Empty Application (C)"
importsources -name bram_test -path ../src
app build -name bram_test
```

### Relevance to Your Project

Stay on **Vitis 2025.1** for stability unless 2026.1 has a specific fix you need. The xsct-based platform and app creation above automates the Vitis side of your build—pair it with the non-project Vivado TCL from the scripting section for a fully headless pipeline from VHDL to `.elf`.
