# FPGA Research Digest - 2026-11-06

## Executive Summary

- **AXI-Lite unregistered READY**: The AXI BRAM Controller v4.1 does not register its write-side READY outputs; this directly affects timing margins at the BRAM0/BRAM2 interfaces in the KV260 AXI-BRAM demo and may require output timing constraints or pipeline stages.
- **BSP stdout routing is the #1 silent-output culprit**: Vitis standalone BSPs default to `psu_uart_0`; the KV260 routes the console to `psu_uart_1`. Confirm and regenerate the BSP if `xil_printf` produces no output.
- **Linker script memory sections must match the XSA address map**: Vitis can place code sections in an unexpected memory space (e.g., PCIe BAR instead of DDR). Verify BRAM and DDR origins in `lscript.ld` match the Vivado Address Editor after every hardware export.
- **Vivado 2025.1 Unified IDE is the new default**: Classic Vitis IDE is deprecated; the unified flow uses a new project structure. The KV260 Base Platform deprecation is coming in 2025.2—validate your platform version now.
- **Non-project TCL flow requires explicit output product generation**: `generate_target all` must be called before synthesis in a non-project Vivado script; otherwise IP output products are missing and synthesis fails silently.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- **Unregistered READY outputs**: The AXI BRAM Controller (PG078 v4.1) does not register its write-side READY signals, reducing combinational slack and potentially causing setup violations at higher clock frequencies.
- **Byte-address vs. word-address mismatch**: The BRAM controller exposes word addresses while AXI operates on byte addresses. Unaligned AXI4-Lite transfers are unsupported; misaligned simulation testbenches may pass while hardware fails.
- **Master must assert VALID before READY**: An AXI master must not wait for the slave to assert READY before driving VALID. Doing so creates a deadlock. Cortex-A53 AXI masters generally comply, but custom PL masters must be checked.
- **AXI-Stream sticky VALID rule**: Once TVALID is asserted it cannot be de-asserted until TREADY is high. Additionally, TVALID must not depend combinationally on TREADY—this rule prevents circular timing paths that break static timing analysis.
- **TLAST payload stability**: A known bug in some Xilinx AXI-Stream master templates is that TLAST changes while TREADY is low (stall cycle). Check any custom streaming IP for this—payload signals including TDATA, TUSER, and TLAST must be stable while TVALID is high and TREADY is low.
- **AXI Protocol Checker IP**: AMD ships a free Protocol Checker that can be inserted inline in simulation to flag handshake violations automatically. Insert it at the BRAM0/BRAM2 interfaces during bring-up.

### Code Example

```vhdl
-- AXI4-Lite read state machine skeleton (safe handshake)
type t_axi_rd_state is (IDLE, ADDR_PHASE, DATA_PHASE);
signal rd_state : t_axi_rd_state := IDLE;

process(clk)
begin
  if rising_edge(clk) then
    case rd_state is
      when IDLE =>
        s_axi_arready <= '1';           -- accept addresses
        if s_axi_arvalid = '1' then
          bram_addr    <= s_axi_araddr(ADDR_W-1 downto 2); -- word addr
          rd_state     <= DATA_PHASE;
          s_axi_arready <= '0';
        end if;
      when DATA_PHASE =>
        s_axi_rvalid <= '1';
        s_axi_rdata  <= bram_dout;
        s_axi_rresp  <= "00";
        if s_axi_rready = '1' then      -- handshake completes
          s_axi_rvalid <= '0';
          rd_state     <= IDLE;
        end if;
      when others => rd_state <= IDLE;
    end case;
  end if;
end process;
```

### Relevance to Your Project

BRAM0 at `0xA0000000` and BRAM2 at `0xA0010000` are accessed via AXI-Lite. The byte-to-word address conversion (`araddr >> 2`) is critical—if the C code writes `*(volatile uint32_t*)0xA0000004` and the BRAM controller receives address `0x1` rather than `0x4`, reads will return stale data, producing false FAILs without any bus error.

## Vivado Block Design / IP Integrator

### Key Findings

- **Connection Automation**: After adding IP cores, right-click the block design canvas and select **Run Connection Automation**. This wires AXI master/slave ports, connects clocks, and assigns resets. Skipping this step leaves the design with unconnected ports that pass validation but fail during simulation.
- **Validate Design is mandatory**: `validate_bd_design` runs DRCs and catches unconnected mandatory ports, mismatched clock frequencies, and address conflicts. Run it explicitly in TCL scripts before exporting the XSA.
- **Address Editor**: After adding an AXI slave, it may be assigned an arbitrary base address. Use the Address Editor to set `BRAM0` → `0xA0000000` (64 KB) and `BRAM2` → `0xA0010000` (64 KB). Mismatched addresses are the most common cause of read-back failures.
- **OOC synthesis**: Block designs default to Out-of-Context (OOC) synthesis, which generates an IP-level checkpoint independently. This speeds up top-level synthesis but means IP changes require re-running `generate_target all` before they propagate.
- **Regenerate output products after IP upgrade**: Upgrading any IP version without regenerating output products causes a stale `.dcp` to be used. Always call `upgrade_ip` followed by `generate_target all`.

### Code Example

```tcl
# Automate AXI connections and validate block design
connect_bd_intf_net [get_bd_intf_pins zynq_ultra_ps_e_0/M_AXI_HPM0_FPD] \
                    [get_bd_intf_pins axi_interconnect_0/S00_AXI]

apply_bd_automation -rule xilinx.com:bd_rule:axi4 \
  -config { Clk_master {Auto} Clk_slave {Auto} Clk_xbar {Auto} \
            Master {/zynq_ultra_ps_e_0/M_AXI_HPM0_FPD} \
            Slave  {/axi_bram_ctrl_0/S_AXI} } \
  [get_bd_intf_pins axi_bram_ctrl_0/S_AXI]

# Assign addresses
set_property offset 0xA0000000 [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property range  64K        [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]

validate_bd_design
save_bd_design
```

### Relevance to Your Project

The `create_bd.tcl` script in the demo drives address assignment programmatically. After any IP version bump in Vivado 2025.1, verify that `set_property offset` commands still match the hardware addresses your C code uses (`0xA0000000` and `0xA0010000`), since automated re-addressing can silently shift a slave.

## Vivado TCL Scripting

### Key Findings

- **Non-project batch flow sequence**: `read_vhdl` / `read_xdc` → `synth_design` → `opt_design` → `place_design` → `phys_opt_design` → `route_design` → `write_bitstream`. Skipping `phys_opt_design` often leaves ~5–10% timing slack improvement on the table for AXI-heavy designs.
- **Write checkpoints between stages**: `write_checkpoint -force post_route.dcp` after `route_design` lets you reload the routed netlist without re-running the entire flow on subsequent debug iterations.
- **Project-mode bitstream command**: `launch_runs impl_1 -to_step write_bitstream` followed by `wait_on_run impl_1`. Never call `open_run` and `write_bitstream` on a stale run without first confirming the run is current.
- **Source file ordering matters**: In non-project mode, files compile in the order the `read_*` commands appear. VHDL packages and component declarations must be read before the entities that use them.
- **Export XSA after bitstream**: `write_hw_platform -fixed -force -file kv260.xsa` exports the hardware hand-off file for Vitis. Forgetting this step means Vitis uses a stale XSA and the linker script contains wrong memory regions.

### Code Example

```tcl
#!/usr/bin/env tclsh
# Non-project batch flow for KV260 AXI-BRAM demo

set part "xck26-sfvc784-2LV-c"
set top  "kv260_top"

read_vhdl   [glob ../vhdl/*.vhd]
read_xdc    [glob ../xdc/*.xdc]

synth_design       -top $top -part $part -flatten_hierarchy rebuilt
write_checkpoint   -force post_synth.dcp

opt_design
place_design
phys_opt_design
route_design
write_checkpoint   -force post_route.dcp

write_bitstream    -force kv260_top.bit
write_hw_platform  -fixed -force -file kv260.xsa

report_timing_summary -file timing_summary.rpt
report_utilization    -file utilization.rpt
```

### Relevance to Your Project

The existing `create_bd.tcl` handles block design creation. Wrapping the entire flow—including `synth_design` and `write_hw_platform`—in a single script enables fully reproducible CI-style builds. Add `report_timing_summary` to catch any new setup violations introduced by changes to the AXI interconnect or BRAM controller configuration.

## Vitis Bare-Metal / Standalone

### Key Findings

- **UART stdout assignment**: The Vitis BSP generator defaults `stdout`/`stdin` to `psu_uart_0`. The KV260 carrier board routes its USB-UART to `psu_uart_1`. Navigate to **Board Support Package → Modify BSP Settings → standalone** and change `standalone_stdout` and `standalone_stdin` to `psu_uart_1`, then click **Regenerate BSP**.
- **xil_printf does not support %f**: Floating-point format specifiers are unsupported. Use integer math and print mantissa/exponent separately, or link `printf` from newlib (increases code size by ~30 KB).
- **A53 core selection**: Target `psu_cortexa53_0` for single-core bare-metal. Using `psu_cortexa53_1` works but requires the FSBL to bring up core 1, adding complexity.
- **Platform deprecation warning**: AMD announced that pre-built KV260 Vitis base platforms will not be provided from the **2025.2 release** onward. If you plan to upgrade tools, build your own platform XSA from Vivado and use `xsct` to generate the platform.
- **Linker script verification**: After every hardware export, open `lscript.ld` and confirm that `psu_ddr_0_MEM_0` origin and length match the Address Editor. A mismatch places the application stack in an unmapped region, causing a silent hang after the FSBL.

### Code Example

```c
/* Minimal AXI-BRAM read-write test on KV260 (bare-metal) */
#include "xil_printf.h"
#include "xil_io.h"

#define BRAM0_BASE 0xA0000000UL
#define BRAM2_BASE 0xA0010000UL
#define TEST_WORDS 16

int main(void)
{
    int failures = 0;

    /* Write phase */
    for (int i = 0; i < TEST_WORDS; i++) {
        Xil_Out32(BRAM0_BASE + (i * 4), 0xDEAD0000 | i);
        Xil_Out32(BRAM2_BASE + (i * 4), 0xBEEF0000 | i);
    }

    /* Read-back and verify */
    for (int i = 0; i < TEST_WORDS; i++) {
        u32 v0 = Xil_In32(BRAM0_BASE + (i * 4));
        u32 v2 = Xil_In32(BRAM2_BASE + (i * 4));
        if (v0 != (0xDEAD0000 | i) || v2 != (0xBEEF0000 | i)) {
            xil_printf("FAIL word %d: BRAM0=0x%08X BRAM2=0x%08X\r\n", i, v0, v2);
            failures++;
        }
    }

    xil_printf(failures == 0 ? "PASS\r\n" : "FAIL: %d errors\r\n", failures);
    return failures;
}
```

### Relevance to Your Project

This is functionally equivalent to the existing `main.c` test but adds per-word reporting, making it easier to pinpoint whether BRAM0 or BRAM2 is at fault. If UART output is silent, the first debug step is BSP stdout reassignment—not hardware changes.

## XDC Timing Constraints

### Key Findings

- **AXI slave I/O constraints**: For the AXI-Lite interface at the PL boundary, `set_input_delay` and `set_output_delay` define the external timing budget. `set_input_delay` is silently skipped on clock ports even when `all_inputs` is used—this is expected behavior per UG835.
- **Use -max and -min**: Both `set_input_delay` and `set_output_delay` should be specified with `-max` and `-min` to cover setup and hold margins separately. Using only `-max` leaves hold paths unconstrained.
- **set_clock_groups suppresses cross-domain reports**: Declaring two clocks as asynchronous via `set_clock_groups -asynchronous` cuts timing analysis between them. This is correct for truly async clocks but will hide dangerous CDC paths if misapplied. Use `set_false_path` instead for specific one-directional exception paths.
- **Internal AXI clocks don't need I/O constraints**: The AXI-Lite connection between the Zynq PS hard block and PL logic is entirely on-chip. No `set_input_delay`/`set_output_delay` are needed for `M_AXI_HPM0_FPD`—only for ports that cross the device boundary.
- **STARTUPE3 and similar primitives**: On UltraScale+ devices, `set_output_delay` can target internal data pins such as `STARTUPE3/DATA_OUT`. Consult UG903 2025.2 for the full list of valid pin targets.

### Code Example

```tcl
# KV260 XDC timing constraints skeleton

# Primary PL clock (from PS clock output or SYZYGY)
create_clock -period 10.000 -name clk_pl_0 [get_ports clk_pl_0]

# For external GPIO or PMOD signals crossing PL boundary:
set_input_delay  -clock clk_pl_0 -max 2.000 [get_ports {gpio_in[*]}]
set_input_delay  -clock clk_pl_0 -min 0.500 [get_ports {gpio_in[*]}]
set_output_delay -clock clk_pl_0 -max 2.000 [get_ports {gpio_out[*]}]
set_output_delay -clock clk_pl_0 -min 0.500 [get_ports {gpio_out[*]}]

# Asynchronous clocks (e.g., external ref vs PL fabric clock)
# WARNING: this suppresses cross-domain timing reports entirely
# set_clock_groups -asynchronous -group [get_clocks clk_pl_0] \
#                                -group [get_clocks ext_ref_clk]

# False path for async reset (synchronised in fabric)
set_false_path -from [get_ports rst_n] -to [all_registers]
```

### Relevance to Your Project

The KV260 AXI-BRAM demo's AXI connections are all internal (PS hard AXI master → PL AXI slave). No external I/O timing constraints are needed for the BRAM interfaces. However, once UART or GPIO signals cross the package boundary, `set_output_delay` constraints become mandatory to close timing to the carrier board's trace impedances.

## Kria KV260 / K26 SoM

### Key Findings

- **Boot mode pins**: PS_Mode[3:0] pins select the boot device. Quad-SPI (MIO[5:0]) is the default for the K26 SOM. Alternative boot devices can be added on a carrier through MIO banks 501 (MIO[51:26]) and 502 (MIO[77:52]).
- **UART default MIO**: The UART console defaults to MIO36/MIO37 in FSBL and PetaLinux BSP. The KV260 carrier routes this to its USB-UART bridge. Confirm the BSP `psu_uart_1` mapping matches your hardware before debugging silent output.
- **Power domains**: Three independent domains: (1) always-on 5 V supply, (2) PS domain (MIO and PS-GTR), (3) PL domain (PL HDIO). All MIO banks run at 1.8 V from the SOM. Power-good signals (`PS_FPD_PWR_GOOD`, `PS_LPD_PWR_GOOD`, `PL_PWR_GOOD`) must be stable before the application runs.
- **MIO34:32 reserved for PMU**: Avoid using MIO[34:32] for general I/O—they are assigned to power-management functions. MIO31 is a hardware shutdown request; asserting it unexpectedly will reset the system.
- **KV260 Base Platform deprecation**: AMD will stop shipping pre-built KV260 Vitis base platforms from 2025.2. For flows beyond 2025.1, generate the XSA directly from Vivado and create the Vitis platform from scratch using `xsct`.
- **EMIO routing**: EMIO signals route PL logic through the PS to external pins. Useful for debugging PL state via PS-controlled GPIOs without consuming PL I/O banks.

### Code Example

```c
/* Read Zynq PS power-good status via SLCR (bare-metal) */
#include "xil_io.h"

#define SLCR_BASE        0xFF180000UL
#define SLCR_BOOT_MODE   (SLCR_BASE + 0x0004)

static inline u32 kv260_read_boot_mode(void)
{
    /* PS_MODE[3:0] captured at power-on reset */
    return Xil_In32(SLCR_BOOT_MODE) & 0xF;
}

/*
 * Boot mode encoding (K26 SOM):
 *   0x0 = JTAG
 *   0x2 = Quad-SPI (default)
 *   0x5 = eMMC
 *   0xE = SD card (carrier-dependent)
 */
```

### Relevance to Your Project

Understanding the power-domain sequence explains why the AXI-BRAM demo occasionally passes JTAG boot but fails SD-card boot: if the PL domain is not yet stable when `main()` starts executing, the first AXI write to BRAM0 arrives before the interconnect is ready, returning a bus error that the bare-metal stub may silently swallow. Adding a small PL power-good poll or a microsecond delay after PL configuration can mitigate this.

## AMD/Xilinx Tool Updates (Vivado/Vitis 2025.x)

### Key Findings

- **Vitis Unified IDE is now the default in 2025.1**: The classic Vitis IDE (pre-2022.x style) is deprecated. Project structure, CMakeLists.txt-based builds, and the new system project concept replace the legacy workspace model. Existing projects should be migrated using the import wizard.
- **KV260 Base Platform end-of-life in 2025.2**: AMD's deprecation notice states the platform will not ship from 2025.2 onward. Projects relying on the pre-built platform must transition to custom XSA-based platforms before upgrading.
- **Vivado 2025.1 known issues**: Spartan UltraScale+ bitstream issues, an ECO flow clock routing bug, and a DRC `HDPR-6` error during `place_design`. Workarounds are listed in AMD article 000037546.
- **Vitis Unified IDE 2025.1 known issues**: File/directory dialog does not open on AlmaLinux 9.5 / RHEL 9.5. XSCT can hang during application build due to a `which.exe` lookup on Linux. Workaround: ensure `which` is on the PATH.
- **Vitis 2025.1.1 patch**: AMD's known-issues page reports zero unresolved issues for the 2025.1.1 patch release—upgrade from base 2025.1 if any of the above issues affect your flow.
- **AI Engine and HLS updates**: AIE-ML tiling parameters and faster pipelining added. HLS IP export and Vivado implementation run widgets redesigned with direct settings and constraint file pass-through—useful for parameterized IP like custom AXI peripherals.

### Code Example

```tcl
# Vitis 2025.x: create a bare-metal application from XSA (xsct script)
# Run with: xsct create_vitis_app.tcl

set xsa_path "../vivado_output/kv260.xsa"
set ws_path  "./vitis_ws"
set app_name "kv260_bram_test"

setws $ws_path

# Create hardware platform from exported XSA
platform create -name kv260_platform \
                -hw $xsa_path \
                -os standalone \
                -proc psu_cortexa53_0

# Configure UART stdout
bsp config stdin  psu_uart_1
bsp config stdout psu_uart_1
platform generate

# Create application
app create -name $app_name \
           -platform kv260_platform \
           -domain standalone_domain \
           -template "Empty Application"

# Import source files
importsources -name $app_name -path ../src

app build -name $app_name
puts "Build complete: $ws_path/$app_name/Debug/$app_name.elf"
```

### Relevance to Your Project

If you upgrade to Vivado/Vitis 2025.1 or later, the XSCT script above replaces manual GUI-driven BSP setup and application creation. The critical line is `bsp config stdout psu_uart_1`—without it, `xil_printf` output goes to the wrong UART and the KV260's USB-UART bridge shows nothing.
