## Executive Summary

- **AXI BRAM Controller write-enable bug**: The Xilinx AXI BRAM Controller IP has a documented timing
  issue where the write-enable fires one clock cycle early, causing writes to land at the *previous*
  address. If your PASS/FAIL tests ever show off-by-one writes, verify the BRAM EN signal gating (PG078).
- **AXI-Lite deadlock rule**: `VALID` must never be withheld waiting for `READY`. Any custom logic that
  gates your AXI master's VALID on a slave's READY will deadlock the bus under certain ordering conditions.
- **Non-project TCL mode + `write_bd_tcl`**: Exporting your block design via `write_bd_tcl` gives a
  single reproducible script for CI/CD, but the output is Vivado-version-specific — tag it with `2025.1`.
- **Vitis 2025 BSP UART stdout**: In the new component-based Vitis flow, `xil_printf` requires explicitly
  setting `stdout` to your UART in the BSP settings; if the UART is disabled in the PS IP the linker will
  succeed but nothing prints.
- **Vivado 2025.2 SystemVerilog AXI wrappers**: Auto-generated SV wrappers for AMD IP now simplify AXI
  connections between RTL instances — useful if you ever add RTL-level AXI peripherals alongside the BRAM.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- **Handshake invariants (AXI spec)**: Once `VALID` is asserted by the initiator, it must stay asserted
  until the corresponding `READY` is received. Withdrawing `VALID` mid-handshake is a protocol violation.
- **Deadlock condition**: `READY` of one component must *never* be made dependent on the `VALID` of
  another component. Circular dependency between READY and VALID is the classic AXI deadlock.
- **AXI BRAM Controller write-enable timing bug** (documented in AMD support AR): The controller asserts
  its write-enable one clock cycle early, writing an extra word at the *previous* address. The BRAM `EN`
  signal was not properly gating this extra clock. Affects designs that write back-to-back to consecutive
  addresses. Workaround: add a one-cycle pipeline stage, or update to a fixed IP revision.
- **AXI-Lite vs AXI-Full for BRAM**: AXI-Full supports burst transfers (higher throughput); AXI-Lite is
  simpler and sufficient for register-like single-word accesses. For sequential BRAM fill loops, AXI-Full
  bursts can be 4–8× faster.
- **Simulation pitfall**: The AXI BRAM Controller IP behaves differently in simulation vs. hardware
  when `BCLK` (BRAM clock) and `ACLK` (AXI clock) are asynchronous; always tie them to the same clock
  in bare-metal single-clock designs to avoid metastability.

### Code Example

```c
/* AXI-Lite bare-metal write + readback with explicit VALID ordering.
   0xA0000000 = BRAM0, 0xA0010000 = BRAM2 (4 KB each, word-addressable) */
#include "xil_io.h"
#include "xil_printf.h"

#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL
#define TEST_WORDS  16

int axi_bram_test(u32 base, u32 pattern) {
    int errors = 0;
    /* Write phase */
    for (u32 i = 0; i < TEST_WORDS; i++) {
        Xil_Out32(base + (i * 4), pattern ^ i);
    }
    /* Memory barrier: ensure all AXI writes are committed before reads */
    __asm__ volatile("dsb sy" ::: "memory");
    /* Readback phase */
    for (u32 i = 0; i < TEST_WORDS; i++) {
        u32 rd = Xil_In32(base + (i * 4));
        if (rd != (pattern ^ i)) {
            xil_printf("FAIL @0x%08X: wrote 0x%08X read 0x%08X\r\n",
                       base + (i*4), pattern^i, rd);
            errors++;
        }
    }
    return errors;
}
```

### Relevance to Your Project

Your `main.c` writes patterns to BRAM0 (`0xA0000000`) and BRAM2 (`0xA0010000`) and checks PASS/FAIL.
The `dsb sy` barrier is critical between the write loop and readback loop — without it the Cortex-A53
store buffer may not have flushed all AXI-Lite write transactions before the first read issues. The
write-enable timing bug documented above is most visible when writing sequential addresses rapidly;
inserting a small delay or using single-word writes (as AXI-Lite naturally does) usually avoids it,
but verify your IP version matches a fixed revision in PG078.

## Vivado Block Design / IP Integrator

### Key Findings

- **Connection Automation** automatically wires AXI interfaces, clocks, and resets between IPs. Run it
  after adding the Zynq UltraScale+ PS and each AXI BRAM Controller; the tool will offer to connect
  `M_AXI_HPM0_FPD` → AXI Interconnect → BRAM controllers in one click.
- **Address Editor** must be visited after running Connection Automation — auto-assigned addresses can
  overlap. Each BRAM Controller slave must have a non-overlapping 64 KB (or larger) range. Manually
  verify `0xA000_0000` and `0xA001_0000` are each assigned the correct IP.
- **Validate Design** (`Tools → Validate Design` or `validate_bd_design` in TCL) catches undriven ports,
  address overlaps, and clock-domain mismatches before you waste time synthesizing a broken design.
- **Output Products**: Only the `.bd` file needs to be in version control; `.xci` files under the BD
  directory are regenerated automatically during `generate_target`. Committing `.xci` causes merge
  conflicts with no benefit.
- **IP Integrator in Non-Project Mode** (UG994 2025.1): You can use `open_bd_design`, `validate_bd_design`,
  `generate_target`, and `write_bitstream` entirely from TCL without a `.xpr` project file.

### Code Example

```tcl
# Regenerate all output products for a block design (run after git pull)
open_project myproject.xpr
open_bd_design [get_files *.bd]
validate_bd_design
generate_target all [get_files *.bd]
make_wrapper -files [get_files *.bd] -top
add_files -norecurse \
    ./myproject.gen/sources_1/bd/design_1/hdl/design_1_wrapper.vhd
set_property top design_1_wrapper [current_fileset]
launch_runs synth_1 -jobs 4
wait_on_run synth_1
launch_runs impl_1 -to_step write_bitstream -jobs 4
wait_on_run impl_1
```

### Relevance to Your Project

Your `create_bd.tcl` script recreates the block design from scratch — this is the correct approach for
version control. After cloning on a new machine, source `create_bd.tcl`, then run the snippet above to
regenerate products and build the bitstream. Ensure your Address Editor assigns BRAM0 to `0xA0000000`
(64 KB range) and BRAM2 to `0xA0010000` (64 KB range) to match the hard-coded addresses in `main.c`.

## Vivado TCL Scripting

### Key Findings

- **`write_bd_tcl`** exports a complete TCL script that recreates your block design; use it to keep the
  block design reproducible across machines: `write_bd_tcl -force ./tcl/create_bd.tcl`
- **Version lock**: `write_bd_tcl` output embeds the Vivado version string. The generated script will
  print a warning (and may partially fail) if sourced in a different major version. Tag your repo with
  the tool version.
- **Non-project mode** separates source management from Vivado's project bookkeeping, enabling cleaner
  CI pipelines. The flow: `read_vhdl` → `read_bd` / `open_bd_design` → `synth_design` →
  `opt_design` → `place_design` → `route_design` → `write_bitstream`.
- **Batch mode difference**: In `vivado -mode batch -source script.tcl`, unknown commands are *not*
  forwarded to the OS shell. Use `exec` explicitly for any system calls (e.g., `exec mkdir -p output`).
- **`generate_target all`** must be called before synthesis when using a `.bd` file in non-project mode —
  this step creates the HDL wrappers and simulation models. Missing it causes "top-level not found" errors.
- **`-include_layout`** flag on `write_bd_tcl`: adds graphical canvas coordinates to the export;
  useful for readability of the regenerated BD, not required for functionality.

### Code Example

```tcl
# Non-project mode build script (batch-safe, no .xpr)
# Usage: vivado -mode batch -source build.tcl

set outputDir ./output
exec mkdir -p $outputDir

# Read design sources
read_vhdl [glob ./vhdl/*.vhd]

# Open and validate block design
open_bd_design ./bd/design_1/design_1.bd
validate_bd_design
generate_target all [get_files design_1.bd]
make_wrapper -files [get_files design_1.bd] -top
read_vhdl [glob ./bd/design_1/hdl/*.vhd]

# Synthesis
synth_design -top design_1_wrapper -part xck26-sfvc784-2LV-c
write_checkpoint -force $outputDir/post_synth.dcp

# Implementation
opt_design
place_design
route_design
write_checkpoint -force $outputDir/post_route.dcp

# Reports
report_timing_summary -file $outputDir/timing.rpt
report_utilization    -file $outputDir/util.rpt

# Bitstream
write_bitstream -force $outputDir/top.bit
```

### Relevance to Your Project

Your `create_bd.tcl` follows the export pattern from `write_bd_tcl`. The non-project mode script above
is a drop-in build system for CI — replace the `.vhd` glob with `kv260_top.vhd` and point the BD path
at your KV260 block design. The part string `xck26-sfvc784-2LV-c` is the K26 SoM die identifier used
in Vivado 2025.1 for the KV260.

## Vitis Bare-Metal / Standalone

### Key Findings

- **Vitis 2025 unified IDE uses a component-based flow**: You create a *Platform Component* from the
  exported `.xsa`, then an *Application Component* targeting that platform. The old "New Application
  Project" wizard is replaced.
- **`xil_printf` requires UART enabled in BSP**: In BSP settings (or the platform YAML), set `stdin`/
  `stdout` to `psu_uart_1` (or whichever UART the KV260 USB bridge connects to). If UART is disabled in
  the Zynq PS IP, `xil_printf` will silently drop all output.
- **`SDTgen` tool** (new in Vitis 2024.x/2025.x): reads the XSA and generates a System Device Tree (SDT).
  `Lopper` then parses the SDT to generate BSP files. This replaces the older `hsi` flow.
- **Tool version matching is mandatory**: Mixing a 2025.1 XSA with a 2024.2 Vitis installation is not
  supported; BSP driver versions, memory map offsets, and include paths must all match.
- **Linker script (`lscript.ld`) memory regions**: The auto-generated linker script places `.text` in
  OCM or DDR depending on your processor configuration. For the KV260 Cortex-A53 in bare-metal, DDR
  starts at `0x0` (first 2 GB accessible). Verify `psu_ddr_0` base = `0x00000000`, size = `0x80000000`.
- **Interrupt controllers**: For bare-metal on Zynq UltraScale+, use the GIC-400 (`XScuGic`) to handle
  PL interrupts. Connect `pl_ps_irq0[0]` in the block design → `IRQ0_F2P` → GIC. Don't use the older
  `XIntc` which targets MicroBlaze.

### Code Example

```c
/* BSP: standalone v8.x, stdout = psu_uart_1
   Add to lscript.ld if auto-generated sizes are wrong:
   psu_ddr_0_MEM_0 : ORIGIN = 0x00000000, LENGTH = 0x80000000 */

#include "xparameters.h"
#include "xil_printf.h"
#include "xil_io.h"
#include "sleep.h"

/* xparameters.h defines from XSA export:
   XPAR_PSU_UART_1_BASEADDR  -- verify matches your BSP
   XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR  = 0xA0000000
   XPAR_AXI_BRAM_CTRL_1_S_AXI_BASEADDR  = 0xA0010000  */

int main(void) {
    xil_printf("\r\n=== KV260 AXI-BRAM Bare-Metal Test ===\r\n");

    const u32 BRAM0 = XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR;
    const u32 BRAM2 = XPAR_AXI_BRAM_CTRL_1_S_AXI_BASEADDR;
    int fail = 0;

    /* Write pattern */
    for (int i = 0; i < 16; i++) {
        Xil_Out32(BRAM0 + i*4, 0xDEAD0000 | i);
        Xil_Out32(BRAM2 + i*4, 0xBEEF0000 | i);
    }
    __asm__ volatile("dsb sy" ::: "memory");

    /* Readback */
    for (int i = 0; i < 16; i++) {
        if (Xil_In32(BRAM0 + i*4) != (0xDEAD0000 | i)) fail++;
        if (Xil_In32(BRAM2 + i*4) != (0xBEEF0000 | i)) fail++;
    }

    xil_printf(fail ? "FAIL (%d errors)\r\n" : "PASS\r\n", fail);
    return fail;
}
```

### Relevance to Your Project

This mirrors the core logic of your `main.c`. The key additions are: using `XPAR_*` constants from
`xparameters.h` (generated by Vitis from the XSA) instead of hard-coded addresses, and the `dsb sy`
barrier. If `xil_printf` produces no output on the USB serial port, the first thing to check is BSP
settings → `stdout` peripheral assignment, followed by verifying `psu_uart_1` is enabled and its MIO
pins are configured in the Zynq PS IP block.

## XDC Timing Constraints

### Key Findings

- **PS-PL AXI clock**: On the KV260, the AXI clock (`pl_clk0`) is generated by the Zynq UltraScale+ PS.
  Vivado automatically defines this as a clock via the PS IP — you do *not* need a `create_clock` for it.
  Only add constraints for clocks driven by PL logic (e.g., a `BUFG` or MMCM in your own VHDL).
- **`set_input_delay` / `set_output_delay`**: These apply to *external* I/O pins (GPIO, UART, SPI on
  external connectors). For PS-to-PL AXI paths, no I/O constraints are needed — the paths are internal
  to the device.
- **Virtual clock for external I/O**: When constraining an external signal clocked by an off-chip source,
  create a virtual clock with the same period, then reference it in `set_input_delay`.
- **`set_clock_groups -asynchronous`**: Use this to cut false timing paths between unrelated clock
  domains (e.g., a free-running 100 MHz PL clock and `pl_clk0`). Without it, Vivado may report false
  timing violations across these domains.
- **Timing Constraints Wizard**: Available in Vivado IDE under `Tools → Timing Constraints Wizard`,
  it auto-detects clock domains and suggests constraints interactively — good starting point for KV260
  projects with multiple PS clocks.
- **UG835 (2025.1)** is the definitive Vivado TCL command reference; the `set_output_delay` entry
  clarifies the sign convention (positive = data arrives after clock edge at receiver).

### Code Example

```xdc
# kv260_top.xdc — representative constraints for KV260 AXI-BRAM bare-metal demo

# pl_clk0 is automatically defined by the Zynq UltraScale+ PS IP (do not redefine)
# If you add a second free-running clock from PL logic, declare it:
# create_clock -period 10.000 -name clk_pl_100 [get_ports clk_pl_100_i]

# Cut false paths between PS-generated clock and any PL-generated clock
# (adjust clock names to match your design)
# set_clock_groups -asynchronous \
#     -group [get_clocks clk_pl_0] \
#     -group [get_clocks clk_pl_100]

# False path for BRAM output registers going to PS via AXI interconnect
# (usually not needed — IPI-generated constraints cover this)

# External LED output: treat as an unconstrained output
# set_output_delay -clock [get_clocks clk_pl_0] -max 2.0 [get_ports led_o]
# set_output_delay -clock [get_clocks clk_pl_0] -min -1.0 [get_ports led_o]

# If using virtual clock for off-chip peripheral (e.g., SPI sensor):
# create_clock -period 20.000 -name vclk_spi [get_ports spi_clk_o]
# set_input_delay  -clock vclk_spi -max 5.0 [get_ports spi_miso_i]
# set_input_delay  -clock vclk_spi -min 1.0 [get_ports spi_miso_i]
```

### Relevance to Your Project

For the current AXI-BRAM demo (all paths internal between PS and PL fabric), the XDC file needs
minimal constraints. The most common beginner mistake is adding redundant `create_clock` for `pl_clk0`
(which conflicts with the PS IP's auto-generated constraint). If Vivado reports `CRITICAL WARNING:
create_clock already defined`, that's the cause. Your `kv260_top.vhd` wrapper likely only passes
through the PS clock — confirm there is no `create_clock` in your XDC for the PS-generated clock.

## Kria KV260 / K26 SoM

### Key Findings

- **Boot modes**: The KV260 Starter Kit ships with QSPI32 boot mode pre-configured and a boot FW in
  QSPI. The bare K26 SoM (as used by custom carrier designs) ships *without* any preloaded FW.
  Boot mode pins (`MODE[3:0]`) are exposed on the SOM240_1 connector — on the KV260 baseboard they
  are hard-tied to QSPI32.
- **MIO banking**: The K26 provides two MIO banks (`MIO501`, `MIO502`) and one HPIO bank (`bank 66` /
  `HPA`) and one HDIO bank (`bank 45` / `HDA`) on the SOM240_1 connector. USB-UART (CDP CDC) is routed
  via MIO to `psu_uart_1` on the KV260 board.
- **VCCO sideband**: The KV260 sideband signals run at 1.80 V. HPIO bank 66 I/O voltage follows the
  `VCCO_HPA` supply from the carrier board — verify your XDC `set_property IOSTANDARD` matches.
- **All baseboard peripherals via MIO/EMIO**: On the KV260, every on-board peripheral (UART, Ethernet,
  SD card, USB, DisplayPort) is routed through MIO/EMIO in the Zynq PS — there is no PL-attached
  peripherals except what you add via the `HPA`/`HDA` connectors or RPi header.
- **Bare-metal PL custom IP 2025.2**: A recent Hackster article (`Custom PL Designs on Kria KV260
  with AMD EDF v2025.2`) demonstrates the current workflow using the Extension Design Framework.
- **UART on KV260**: Enable `psu_uart_1` in the Zynq PS IP → I/O Configuration → Low Speed → UART 1.
  MIO 36/37 are the TX/RX lines to the USB-UART bridge on the KV260 board.

### Code Example

```tcl
# In create_bd.tcl: correctly configure Zynq UltraScale+ PS for KV260
# Apply the KV260 board preset first, then override UART1 explicitly.

set_property CONFIG.PSU__UART1__PERIPHERAL__ENABLE {1} [get_bd_cells zynq_ultra_ps_e_0]
set_property CONFIG.PSU__UART1__PERIPHERAL__IO     {MIO 36 .. 37} \
    [get_bd_cells zynq_ultra_ps_e_0]
set_property CONFIG.PSU__UART1__BAUD_RATE          {115200} \
    [get_bd_cells zynq_ultra_ps_e_0]

# Confirm pl_clk0 is enabled (AXI fabric clock)
set_property CONFIG.PSU__FPGA_PL0_ENABLE {1} [get_bd_cells zynq_ultra_ps_e_0]
set_property CONFIG.PSU__CRL_APB__PL0_REF_CTRL__FREQMHZ {100} \
    [get_bd_cells zynq_ultra_ps_e_0]

# Enable AXI HP master (M_AXI_HPM0_FPD) for PS→PL transactions
set_property CONFIG.PSU__USE__M_AXI_GP0 {1} [get_bd_cells zynq_ultra_ps_e_0]
set_property CONFIG.PSU__USE__M_AXI_GP1 {0} [get_bd_cells zynq_ultra_ps_e_0]
```

### Relevance to Your Project

Your `create_bd.tcl` should contain exactly this PS configuration. If UART1 is not enabled or its MIO
assignment does not match MIO 36/37, `xil_printf` output will not appear over the USB cable. The
`pl_clk0` at 100 MHz is what clocks both BRAM controllers; setting it here ensures the constraint tools
know the frequency for timing analysis. The `M_AXI_GP0` master port is the AXI-Lite path from the
Cortex-A53 to your BRAM controllers.

## AMD/Xilinx Tool Updates (Vivado/Vitis 2025.x)

### Key Findings

- **Vivado 2025.1** (your current tool): Released and available for download. No breaking changes for
  Zynq UltraScale+/KV260 bare-metal AXI designs relative to 2024.2. Use AMD Answer Record 000037919
  for the full IP change log.
- **Vivado 2025.2** (available now): Key highlights for AXI/PS-PL designs:
  - **SystemVerilog interface auto-wrappers**: Simplified AXI connections between SV RTL instances and
    auto-generated wrapper creation for all AMD IP and block designs — reduces boilerplate AXI port mapping.
  - **IP Integrator**: Support for adding RTL modules containing NoC XPMs inside block designs via
    module referencing.
  - **PhysOpt compile time reduction** and improved SLR crossing reports for timing closure.
  - New device support: Versal AI Edge Gen 2, Versal Prime Gen 2.
- **Vitis 2025.x unified IDE**: The `SDTgen + Lopper` flow for BSP generation is now the default for
  all Zynq UltraScale+ projects. The legacy `hsi`-based BSP generation is deprecated (still available
  but not recommended for new projects).
- **AXI IP bug fixes (2025.1 IP Change Log, AR 000037919)**:
  - Fixed potential deadlock between peripheral and cache data AXI interfaces in certain pipeline
    frequency-optimization configurations.
  - Fixed incorrect AXI interface sizing with 64-bit peripheral data width and wide cache data widths.
  - PTP 1588 frame handling fix in AXI Ethernet Buffer.
- **IP Catalog taxonomy update (2025.1)**: IP categorization structure was reorganized — if you can't
  find an IP under the old path, use the search bar.
- **Vitis 2025 "Classic" vs "Unified" IDE**: If you see references to "Vitis Classic" in tutorials,
  that refers to the pre-2023 UI. Vitis 2025 uses the Unified IDE exclusively. The `xsct` TCL shell
  still works for scripted BSP/platform creation.

### Code Example

```tcl
# Vitis 2025 XSCT: create platform + application from XSA (scripted, CI-friendly)
# Run with: xsct create_vitis_app.tcl

setws ./workspace

# Create platform component from Vivado-exported XSA
platform create -name kv260_platform \
    -hw ./output/kv260_top_wrapper.xsa \
    -proc psu_cortexa53_0 \
    -os standalone \
    -out ./workspace

# Set UART stdout in BSP
bsp setlib -name xilfpga
bsp config stdout psu_uart_1

platform generate

# Create application component
app create -name kv260_bram_test \
    -platform kv260_platform \
    -domain standalone_domain \
    -template "Empty Application (C)"

# Add source
importsources -name kv260_bram_test -path ./src

app build -name kv260_bram_test
```

### Relevance to Your Project

If you upgrade from Vivado/Vitis 2025.1 to 2025.2, re-export the XSA and recreate the platform
component — the SystemVerilog wrapper improvements and IP updates require regeneration of output products.
The `xsct` script above is a drop-in CI script; replace the XSA path with your export location and the
source path with `kv260_claude/kv260/src/`. The BSP `stdout psu_uart_1` line ensures `xil_printf`
routes to the USB-UART bridge without requiring manual GUI intervention.
