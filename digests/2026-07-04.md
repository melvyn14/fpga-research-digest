# FPGA Research Digest - 2026-07-04

## Executive Summary

- **AXI-Lite deadlock from VALID mis-assertion**: The VALID signal (AWVALID, WVALID, ARVALID) must never be withheld indefinitely once a transaction is started — the BRAM controller will stall permanently if a master deasserts VALID before seeing READY, violating the AXI spec. This is the most common cause of bare-metal PS-to-BRAM hangs.
- **SmartConnect is now the recommended AXI bus for all new designs**: AMD/Xilinx officially deprecated AXI Interconnect v2 for new work — SmartConnect delivers 20–30% better Fmax on UltraScale+/Zynq and handles AXI-Lite endpoints with less LUT overhead. If your block design still uses AXI Interconnect, migrate to SmartConnect.
- **AXI BRAM Controller write pipeline backpressure**: When the write-data pipeline to BRAM is full, the controller asserts backpressure by deasserting WREADY. Your bare-metal C driver must never assume WREADY is always high — burst writes without polling the response channel can overrun the pipeline.
- **Vivado 2025.1 `write_project_tcl` reliably recreates block designs**: Checking "Recreate Block Designs using Tcl" on export produces a single script that rebuilds the entire BD including PS configuration and address assignments. This supersedes the older manual `export_bd_as_tcl` flow for full-project reproducibility.
- **KV260 JTAG boot requires PSU_INIT sequence before application load**: For bare-metal debug on KV260, the XSDB/XSCT flow must download `pmufw.elf` to the MicroBlaze PMU and run `psu_init` on the A53 before loading your application ELF — skipping this leaves DDR, PL power rails, and clocks unconfigured, causing silent failures at the UART or memory stage.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- **VALID-hold rule is absolute**: Once a master asserts AWVALID, WVALID, or ARVALID, it must hold that signal until the corresponding READY is seen. Deasserting early is an AXI protocol violation that the BRAM controller will not recover from — it stalls the write-response channel (BVALID), permanently blocking subsequent transactions. This is the #1 source of bare-metal PS-to-PL hangs on Zynq.
- **Write address and write data channels are independent**: The AXI4 spec does not require AWVALID and WVALID to be asserted simultaneously. The BRAM controller must receive both before it can issue BVALID. Your C driver's write sequence (write address, write data, then read BRESP) is correct only if you wait for both AWREADY and WREADY before deasserting their respective VALID lines.
- **AXI-Lite has no burst, no ID fields**: For the PS-to-BRAM connection at 0xA0000000/0xA0010000, AXI-Lite is the right choice — single 32-bit word transfers, no out-of-order transactions, and simple handshake. AXI-Stream is unidirectional and address-free, used for DMA or video pipelines, not register-mapped BRAM access.
- **BRAM controller WREADY backpressure**: When the internal write-data pipeline is full, the AXI BRAM Controller deasserts WREADY. A master that ignores WREADY and over-drives writes will lose data silently. Always verify WREADY is asserted before sampling WDATA in bare-metal drivers.
- **SmartConnect for deadlock avoidance**: SmartConnect uses the "Single Slave per ID" method to prevent AXI deadlock when multiple masters share a slave. For the KV260 PS (which generates multiple outstanding transactions via AXI HP/HPC ports), SmartConnect is safer than raw AXI Interconnect.

### Code Example

```c
/* Bare-metal AXI-Lite write to BRAM with BRESP polling
   Assumes memory-mapped I/O at base address BASE_ADDR (e.g., 0xA0000000).
   Xil_Out32/Xil_In32 are Xilinx BSP macros for 32-bit MMIO. */
#include "xil_io.h"

#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL

static inline void bram_write(u32 base, u32 offset, u32 data) {
    Xil_Out32(base + offset, data);
    /* AXI-Lite: Vitis BSP generates AWVALID+WVALID atomically via
       store instruction; BRESP is absorbed by the AXI interconnect.
       For custom AXI slaves, poll a status register here. */
}

static inline u32 bram_read(u32 base, u32 offset) {
    return Xil_In32(base + offset);
}

void bram_test(void) {
    const u32 pattern = 0xDEADBEEF;
    bram_write(BRAM0_BASE, 0x00, pattern);
    bram_write(BRAM2_BASE, 0x00, pattern ^ 0xFFFFFFFF);

    u32 r0 = bram_read(BRAM0_BASE, 0x00);
    u32 r2 = bram_read(BRAM2_BASE, 0x00);

    if (r0 == pattern && r2 == (pattern ^ 0xFFFFFFFF))
        xil_printf("PASS: BRAM0=0x%08X BRAM2=0x%08X\r\n", r0, r2);
    else
        xil_printf("FAIL: BRAM0=0x%08X BRAM2=0x%08X\r\n", r0, r2);
}
```

### Relevance to Your Project

Your demo reads and writes patterns to BRAM0 (0xA0000000) and BRAM2 (0xA0010000) over AXI-Lite. The most important finding here is the VALID-hold rule: your bare-metal C code uses `Xil_Out32`/`Xil_In32` which generate single-cycle store/load instructions — the AXI-Lite master inside the Zynq PS handles handshaking correctly at the hardware level, so you don't need to manually poll READY. However, if you ever add a custom VHDL AXI-Lite slave (e.g., a control register block), you must implement proper READY management or your PS will deadlock.

## Vivado Block Design / IP Integrator

### Key Findings

- **SmartConnect is the recommended replacement for AXI Interconnect**: AMD/Xilinx's IP Integrator UG994 now recommends SmartConnect for all new designs. It integrates more tightly with Vivado to remove redundant pipeline stages, supports better timing closure at higher frequencies, and handles AXI-Lite endpoints with lower LUT overhead for small configurations.
- **Address Editor auto-assign**: The `assign_bd_address` TCL command (or right-click → Auto-Assign Address in the GUI) maps slave segments into master address spaces. Unmapped peripherals cause validation errors — always run `validate_bd_design` after `assign_bd_address` to confirm all segments are correctly mapped.
- **`run_connection_automation` clock source pitfall**: After running `run_connection_automation` in IP Integrator, verify clock sources for every AXI slave port manually. The tool occasionally assigns a mismatched clock when multiple clocks are present (e.g., 100 MHz PS clock vs. 150 MHz PL clock), producing a design that compiles but fails at runtime.
- **Block Memory Generator v8.4 modes**: For your two BRAM instances, BMG supports Simple Dual-Port (SDP) and True Dual-Port (TDP). When connected to the AXI BRAM Controller in single-port mode, only Port A is used by the AXI interface — Port B is available for direct PL-side access.
- **AXI BRAM Controller ECC**: ECC is available for 32/64/128-bit data widths (C_ECC=1). Hamming or HSIAO algorithms available for 32/64-bit. For a bare-metal demo, ECC adds complexity without benefit — leave C_ECC=0 unless you need fault tolerance.

### Code Example

```tcl
# IP Integrator: add two AXI BRAM controllers and assign addresses
# Run inside Vivado TCL console after create_bd is complete

# Add SmartConnect (1 master, 2 slaves)
set sc [create_bd_cell -type ip -vlnv xilinx.com:ip:smartconnect:1.0 axi_smc]
set_property -dict [list CONFIG.NUM_SI {1} CONFIG.NUM_MI {2}] $sc

# Connect PS AXI master to SmartConnect
connect_bd_intf_net [get_bd_intf_pins zynq_ultra_ps_e_0/M_AXI_HPM0_FPD] \
                    [get_bd_intf_pins axi_smc/S00_AXI]

# Assign addresses for both BRAM controllers
set_property offset 0xA0000000 [get_bd_addr_segs \
    {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property range 64K [get_bd_addr_segs \
    {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]

set_property offset 0xA0010000 [get_bd_addr_segs \
    {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_1_Mem0}]
set_property range 64K [get_bd_addr_segs \
    {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_1_Mem0}]

validate_bd_design
save_bd_design
```

### Relevance to Your Project

Your `create_bd.tcl` builds the block design programmatically, which is the right approach. If you're still using `axi_interconnect` as the bus IP, this is a good time to migrate to `smartconnect` — the swap is a one-line change in the `create_bd_cell` call and will improve timing closure. Confirm your two BRAM base addresses (0xA0000000, 0xA0010000) match what `assign_bd_address` generates, or hardcode them via `set_property offset` as shown above.

## Vivado TCL Scripting

### Key Findings

- **`write_project_tcl` is the gold standard for reproducibility**: File → Project → Write Tcl with "Recreate Block Designs using Tcl" checked generates a single script that reconstructs the entire project — sources, block design, IP configuration, and address map — from scratch. This is more reliable than `export_bd_as_tcl` alone, which only exports the BD without the project wrapper.
- **Non-project mode for CI pipelines**: In non-project mode (`vivado -mode batch -source build.tcl`), you are responsible for managing sources, running synthesis (`synth_design`), implementation (`opt_design`, `place_design`, `route_design`), and writing the bitstream (`write_bitstream`). Design checkpoints (`.dcp` files) via `write_checkpoint` are the only way to save intermediate state.
- **Version guard in exported scripts**: Vivado's exported TCL scripts include a version check that aborts if the script is run under a different Vivado version. For 2025.1 scripts on 2026.x tools, remove or comment out this guard after verifying compatibility.
- **`-tclargs` for parameterized builds**: Pass build parameters to batch scripts via `vivado -mode batch -source build.tcl -tclargs part=xczu5ev-sfvc784-2-e`. Inside the script, access with `lindex $argv 0` or `set_param general.tcl_cmd_args`.
- **`generate_target` vs `export_ip_user_files`**: After modifying a block design, run `generate_target all` to regenerate HDL wrappers and simulation files, then `export_ip_user_files` to copy IP sources to the project directory. Skipping either step causes stale wrapper errors during synthesis.

### Code Example

```tcl
#!/usr/bin/env tclsh
# Non-project mode build script for KV260 AXI-BRAM demo
# Usage: vivado -mode batch -source build_nonproject.tcl

set part "xczu5ev-sfvc784-2-e"
set bd_script "tcl/create_bd.tcl"
set xdc_file  "xdc/kv260_top.xdc"
set top       "kv260_top"

# Create in-memory design
create_project -in_memory -part $part

# Source the block design creation script
source $bd_script
make_wrapper -files [get_files *.bd] -top
add_files -norecurse [glob ./kv260.gen/sources_1/bd/*/hdl/*_wrapper.v]

# Add VHDL sources and XDC
add_files -norecurse [glob ./vhdl/*.vhd]
add_files -fileset constrs_1 $xdc_file

# Synthesize, implement, bitstream
synth_design -top ${top}_wrapper -part $part
write_checkpoint -force post_synth.dcp
opt_design
place_design
route_design
write_checkpoint -force post_route.dcp
write_bitstream -force output/${top}.bit
write_hw_platform -fixed -force -include_bit output/${top}.xsa

puts "Build complete: output/${top}.bit and output/${top}.xsa"
```

### Relevance to Your Project

Your `create_bd.tcl` is the core of your reproducible build. To make the full project CI-friendly, wrap it in a non-project mode script like the one above — this eliminates the `.xpr` project file from your repo and lets any developer (or CI job) rebuild the bitstream with a single `vivado -mode batch -source build.tcl` command. The `write_hw_platform` at the end produces the `.xsa` that Vitis uses to generate the BSP.

## Vitis Bare-Metal / Standalone

### Key Findings

- **`xil_printf` vs `printf`**: `xil_printf` is a lightweight UART-only printf that supports `%d`, `%x`, `%s`, `%c` but NOT floating point. It outputs `\n` as a newline only (not CRLF) — your terminal emulator may need "Add CR on LF" enabled to display output correctly. For floating point, use the full `printf` from the newlib-based BSP, which requires linking against `-lm`.
- **Vitis 2025.2 `xil_printf.h` include path change**: A community report confirms that in Vitis 2025.2, `xil_printf.h` moved to a new BSP include path under the unified platform flow. If you see "xil_printf.h not known" after upgrading, add `${workspace_loc}/platform/psu_cortexa53_0/standalone_psu_cortexa53_0/bsp/include` to your include paths.
- **BSP `stdin`/`stdout` routing**: In the standalone BSP settings (system.mss or Vitis platform configuration), the `stdin` and `stdout` parameters must point to the correct UART instance. For KV260, this is `psu_uart_1` (connected to the USB-UART on the carrier card). Setting the wrong UART means `xil_printf` silently sends data nowhere.
- **SDT-based flow in 2025.x**: Vitis 2025.1+ supports a System Device Tree (SDT) based flow as an alternative to the classic XSA flow. The SDT flow uses `lopper` to generate drivers. For bare-metal projects, stick with the classic XSA → platform → application flow — the SDT flow is not yet the default and has rough edges for simple bare-metal demos.
- **Linker script `lscript.ld` memory regions**: The generated linker script places `.text` in DDR (ps_ddr_0) by default. For fast, cache-independent execution, consider placing `.text` in OCM (on-chip memory at 0xFFFC0000, 256 KB) via `set_property offset 0xFFFC0000` in the linker script. OCM is not subject to DDR controller initialization timing issues.

### Code Example

```c
/* Minimal bare-metal entry point for KV260 AXI-BRAM demo
   BSP: standalone, psu_cortexa53_0, stdout = psu_uart_1 */
#include "xil_printf.h"
#include "xil_io.h"
#include "xparameters.h"
#include "sleep.h"

/* These come from xparameters.h generated by Vitis BSP */
#define BRAM0_BASEADDR  XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR  /* 0xA0000000 */
#define BRAM2_BASEADDR  XPAR_AXI_BRAM_CTRL_1_S_AXI_BASEADDR  /* 0xA0010000 */

int main(void) {
    xil_printf("\r\n=== KV260 AXI-BRAM Demo ===\r\n");

    /* Write test patterns */
    Xil_Out32(BRAM0_BASEADDR + 0x00, 0xA5A5A5A5U);
    Xil_Out32(BRAM0_BASEADDR + 0x04, 0x5A5A5A5AU);
    Xil_Out32(BRAM2_BASEADDR + 0x00, 0xDEADBEEFU);
    Xil_Out32(BRAM2_BASEADDR + 0x04, 0xCAFEBABEU);

    /* Readback verification */
    u32 fail = 0;
    if (Xil_In32(BRAM0_BASEADDR + 0x00) != 0xA5A5A5A5U) fail++;
    if (Xil_In32(BRAM0_BASEADDR + 0x04) != 0x5A5A5A5AU) fail++;
    if (Xil_In32(BRAM2_BASEADDR + 0x00) != 0xDEADBEEFU) fail++;
    if (Xil_In32(BRAM2_BASEADDR + 0x04) != 0xCAFEBABEU) fail++;

    xil_printf("%s: %d errors\r\n", fail == 0 ? "PASS" : "FAIL", (int)fail);
    return 0;
}
```

### Relevance to Your Project

Your bare-metal C driver already uses `xil_printf` and `Xil_Out32`/`Xil_In32` — this is exactly right for the KV260 AXI-BRAM demo. The most actionable finding is the UART stdout routing: if you see no output over USB-UART, confirm the BSP `stdout` parameter is `psu_uart_1` (not `psu_uart_0`). Also verify your `xparameters.h` defines `XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR` as `0xA0000000` and `XPAR_AXI_BRAM_CTRL_1_S_AXI_BASEADDR` as `0xA0010000` — a mismatch here means your C code writes to the wrong physical address silently.

## XDC Timing Constraints

### Key Findings

- **`set_clock_groups -asynchronous` for unrelated clock domains**: Vivado times all clocks together by default. For the KV260, the PS generates multiple clocks (fclk_clk0 at 100 MHz, fclk_clk1 at 150/200 MHz) that may be unrelated to each other. Without `set_clock_groups -asynchronous`, Vivado will attempt to time paths between these domains and may produce false timing violations.
- **KV260 carrier-card external clocks are via MIO, not MRCC/SRCC pins**: Unlike FPGA boards with dedicated clock input pins, the KV260 carrier card routes its reference clock through the K26 SoM. For custom PL clocking, you must derive clocks from the PS fclk outputs or use the SoM's PL clock pins (available on the SOM240 connectors).
- **`set_input_delay`/`set_output_delay` are I/O constraints**: For a pure PS-to-PL design (no external I/O in the PL fabric), you do not need `set_input_delay` or `set_output_delay` — these only apply to ports connecting to physical pins. For the AXI-BRAM demo with no PL I/O, your XDC only needs the master clock definition and possibly clock group exceptions.
- **I/O timing constraint formula**: `set_input_delay -max = T_co_max + T_pcb_max - T_clk_skew_min`. For Zynq/Kria platforms with PS-driven clocks, clock skew between source and destination is typically very small (< 200 ps), so `set_input_delay` values are dominated by the external device's clock-to-output specification.
- **`DONT_TOUCH` on BRAM enables**: If timing closure is difficult near BRAM, `set_property DONT_TOUCH true [get_cells bram_inst]` prevents the optimizer from moving or merging BRAM primitives during optimization, which can help isolate timing-critical paths.

### Code Example

```xdc
# KV260 AXI-BRAM Demo XDC constraints
# The PS provides fclk_clk0 to the PL fabric; no external clock pins needed.

# Define PS-generated clock (100 MHz from fclk_clk0)
# The actual clock net name depends on your block design hierarchy.
create_clock -period 10.000 -name clk_100mhz \
    [get_pins zynq_ultra_ps_e_0/inst/PS8_i/PLCLK[0]]

# If a second PS clock is used (e.g., 150 MHz for AXI HP)
create_clock -period 6.667 -name clk_150mhz \
    [get_pins zynq_ultra_ps_e_0/inst/PS8_i/PLCLK[1]]

# Declare the two PS clocks as asynchronous to each other
# (no timing paths should cross between them)
set_clock_groups -asynchronous \
    -group [get_clocks clk_100mhz] \
    -group [get_clocks clk_150mhz]

# For AXI-BRAM demo with no external PL I/O:
# No set_input_delay / set_output_delay needed.
# Vivado will constrain all internal paths automatically.

# Optional: false path on asynchronous resets if used
# set_false_path -from [get_ports aresetn]
```

### Relevance to Your Project

Since your KV260 AXI-BRAM demo has no external PL I/O (all connectivity is PS↔PL over AXI), your XDC file should be minimal: one `create_clock` for `fclk_clk0` and a `set_clock_groups -asynchronous` if you use multiple PS clocks. If you're seeing timing violations, the most likely culprit is the AXI interconnect crossing from the PS clock domain into a different PL clock domain — adding the clock group exception resolves these without over-constraining the design.

## Kria KV260 / K26 SoM

### Key Findings

- **JTAG boot requires the full PSU initialization sequence**: For bare-metal KV260 debug via JTAG, the XSDB flow must: (1) connect to the hardware server, (2) download `pmufw.elf` to the PMU MicroBlaze, (3) run `psu_init.tcl` on the A53 (initializes PS peripherals, PLL, DDR controller), (4) set the A53 to supervisor mode, then (5) load and run your application ELF. Skipping step 3 causes DDR to be uninitialized — your application runs from OCM until it tries to access DDR and hangs.
- **KV260 boot mode pins**: Boot mode is set by the MODE[3:0] pins on the K26 SoM, exposed at the SOM240 connector to allow the carrier card to control boot source. KV260 carrier card defaults to SD card boot (MODE=1110). For JTAG-only development, use the JTAG boot mode switch on the carrier.
- **MIO bank assignments on K26**: The K26 SoM exposes two MIO banks (MIO501, MIO502) to the carrier card via the SOM240 connector. USB-UART is connected via MIO on the KV260 carrier (psu_uart_1, MIO pins 36/37). PS-GTR transceivers (MIO505) are used for USB3 and DisplayPort — do not remap these for custom designs.
- **PS-PL power sequencing**: The K26 SoM manages its own power sequencing via the PMIC. The PL VCC is brought up automatically after the PS VCC stabilizes. For bare-metal designs, you do not need to manually manage PL power rails — the SoM handles this. However, the PL is not powered until the FSBL (or your JTAG init script) releases the PL reset.
- **2026.1 WIC boot firmware incompatibility**: A 2026.1 release note confirms that WIC images require boot firmware (bootfw) from 2026.1 or later — earlier boot firmware is not compatible. If you're using a pre-2026.1 boot image on KV260, update the boot firmware before trying 2026.1-generated bitstreams.

### Code Example

```tcl
# XSDB script: Load and run bare-metal ELF on KV260 via JTAG
# Usage: xsdb jtag_boot.tcl

connect
targets -set -nocase -filter {name =~ "PSU"}

# Download PMU firmware
mwr 0xFFCA0038 0x1FF
after 100
targets -set -nocase -filter {name =~ "MicroBlaze PMU"}
dow pmufw.elf
con
after 200

# Initialize PS (DDR, PLLs, peripherals)
targets -set -nocase -filter {name =~ "Cortex-A53 #0"}
rst -processor -clear-registers
source psu_init.tcl
psu_init

# Optionally release PL reset
psu_ps_pl_isolation_removal
psu_ps_pl_reset_config

# Load and run application
dow kv260_axi_bram.elf
con

puts "Application running. Check UART output."
```

### Relevance to Your Project

This is directly applicable to your daily development workflow. If you're loading your bare-metal AXI-BRAM demo via JTAG in Vitis, the IDE automates most of this — but knowing the manual XSDB flow lets you script headless testing. The psu_init step is the most commonly missed one: if your application prints nothing over USB-UART and you're confident the stdout UART is correct, missing psu_init (and thus uninitialized DDR) is the next thing to check.

## AMD/Xilinx Tool Updates (Vivado/Vitis 2025.x)

### Key Findings

- **Vivado 2025.1 new Pblock Planner**: A new graphical Pblock planner was introduced in 2025.1 for creating floorplan constraints. For designs where BRAM placement is critical (e.g., when PL-side BRAM access timing is tight), the Pblock planner lets you constrain BRAM instances to specific clock regions.
- **RTL-based AXI Switch IP in 2025.1**: A fully customizable RTL-based AXI Switch IP was added in 2025.1 as a bridge between different AXI interface types and widths. This is distinct from SmartConnect and AXI Interconnect — it's intended for cases where you need fine-grained control over routing and arbitration logic.
- **PS-first dynamic PL boot in 2025.1**: Vivado 2025.1 enables PS-first boot with PL loaded dynamically. This is a significant architectural change: the PS boots to Linux or bare-metal, then loads the PL bitstream via FPGA manager or PCAP. For bare-metal AXI-BRAM demos using JTAG, this doesn't affect your flow, but it matters for QSPI/SD deployment.
- **Vitis AI 5.0 verified with 2025.1**: Vitis AI v5.0 (DPU IP) is verified with Vivado/Vitis/PetaLinux 2025.1. Not directly relevant to bare-metal BRAM demos, but worth noting if you plan to add ML inference on the KV260.
- **Vitis 2025.2 `xil_printf.h` path regression**: Community reports confirm a BSP include path regression in 2025.2 where `xil_printf.h` is not found by default in the unified platform flow. Workaround: manually add the BSP include path in project settings. Recommend staying on 2025.1 until this is resolved upstream.
- **Vivado 2026.1 tools available**: The Xilinx downloads page shows 2026.1 as the current release. KV260 WIC images require 2026.1 boot firmware — if you upgrade Vivado to 2026.1, update your boot firmware accordingly.

### Relevance to Your Project

The most actionable 2025.1 update for your project is the ability to preload BRAM with a `.coe` initialization file in the Block Memory Generator configuration. This lets you verify AXI readback without needing the PS to write first — useful for isolating whether a PASS/FAIL is a write-path or read-path issue. The PS-first dynamic PL boot is worth understanding as you think about deployment: transitioning from JTAG-load to a proper SD/QSPI boot image will require generating an FSBL and boot image (BOOT.bin) with `bootgen`.
