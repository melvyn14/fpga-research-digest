## Executive Summary

- **AXI write-response race:** Both Write Address (AW) and Write Data (W) channels must complete their handshakes *before* the slave can assert BVALID. Your bare-metal write loop must consume BREADY before issuing the next write or you risk stalling the AXI-Lite bus silently — check that `Xil_Out32` calls aren't bursting faster than the BRAM controller can respond.
- **AXI SmartConnect is the preferred interconnect** in Vivado 2025.x; the legacy AXI Interconnect is deprecated for new UltraScale+/Kria designs. If your block design uses `axi_interconnect`, migrating to `smartconnect` reduces resource use and simplifies clock connections.
- **Vitis 2025.1 linker script editor has a known bug** — the GUI editor can corrupt heap/stack section definitions. Edit the generated `.ld` file directly to control memory layout for your A53 bare-metal app.
- **QSPI boot for the KV260 requires XSCT, not the Vivado GUI**, once the QSPI already contains bootloaders. The GUI flashing path silently fails on pre-loaded QSPI memory.
- **Vivado non-project-mode TCL scripts** give fully reproducible one-command builds; adding `-tclargs` lets you pass parameters (board target, BRAM size) without modifying the script body — important for keeping `create_bd.tcl` reusable.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- The five AXI channels (AW, W, B, AR, R) each use an independent VALID/READY handshake; a transaction completes only when both signals are high on the same rising clock edge.
- **Critical write-ordering rule:** The AXI4 spec requires the slave to receive *both* AW (address) and W (data) handshakes before asserting BVALID on the B (write response) channel. These two channels may complete in any order relative to each other.
- **RVALID assertion timing:** The Xilinx AXI BRAM Controller does not assert RVALID until ARVALID *and* ARREADY have both been seen — there is always at least one clock of read latency. Bare-metal code polling a memory address must account for this pipeline depth (typically 2 cycles for AXI-Lite BRAM path).
- A common pitfall: using `axi_interconnect` instead of `smartconnect` for newer Zynq UltraScale+/Kria designs adds unnecessary register stages and can mask handshake timing issues during simulation.
- AXI-Lite does not support bursts; each read or write is a single-beat transaction. The BRAM controller's `ECC_MODE` parameter affects latency — disable ECC for the simplest timing model.
- For AXI-Stream (not used in the AXI-Lite BRAM path but relevant for future DMA work): `TREADY` de-assertion by the slave must be handled gracefully by the master — the AXI-Stream spec allows the slave to hold `TREADY` low indefinitely.

### Code Example

```c
/* Bare-metal AXI-Lite BRAM write + read-back with explicit ordering */
#include "xil_io.h"
#include "xil_printf.h"

#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL
#define PATTERN     0xDEADBEEFUL

static void bram_write_verify(u32 base, u32 offset, u32 val) {
    /* Write: Xil_Out32 issues AW+W on AXI-Lite; BVALID follows */
    Xil_Out32(base + offset, val);
    /* Insert a dsb() barrier so the A53 does not speculate the read
       before the write transaction completes on the AXI bus */
    dsb();
    u32 rd = Xil_In32(base + offset);
    if (rd == val) {
        xil_printf("PASS @ 0x%08X: wrote 0x%08X, read 0x%08X\r\n",
                   base + offset, val, rd);
    } else {
        xil_printf("FAIL @ 0x%08X: wrote 0x%08X, read 0x%08X\r\n",
                   base + offset, val, rd);
    }
}

int main(void) {
    xil_printf("AXI-BRAM test start\r\n");
    for (u32 i = 0; i < 16; i++) {
        bram_write_verify(BRAM0_BASE, i * 4, PATTERN + i);
        bram_write_verify(BRAM2_BASE, i * 4, ~(PATTERN + i));
    }
    xil_printf("Done\r\n");
    return 0;
}
```

### Relevance to Your Project

Your `main.c` writes patterns to BRAM0 at `0xA0000000` and BRAM2 at `0xA0010000`. The `dsb()` (Data Synchronization Barrier) between the `Xil_Out32` and `Xil_In32` calls is essential on the Cortex-A53 to prevent the out-of-order processor from forwarding a stale cached value before the AXI write response arrives. Without it, the PASS/FAIL check may compare against a cached write buffer value rather than actual BRAM contents.

## Vivado Block Design / IP Integrator

### Key Findings

- **Connection Automation** in IP Integrator auto-connects AXI master/slave ports and assigns clock/reset when you right-click → "Run Connection Automation." It also populates the Address Editor automatically for standard Zynq PS GP0/GP1 masters.
- The **Address Editor** tab in IP Integrator shows the memory map for each AXI master. For a PS-GP0 master connecting to two BRAM controllers, typical auto-assigned addresses are `0xA000_0000` (64KB range) and `0xA001_0000` (64KB range) — matching your project's `BRAM0_BASE` and `BRAM2_BASE`.
- **AXI SmartConnect (v1.0)** replaces the older AXI Interconnect for Zynq UltraScale+/Kria; it supports up to 16 SI and 16 MI, auto-handles clock-domain crossing, and uses less LUT/FF area. It is the default in Vivado 2025.x block design automation.
- Regenerating a block design output after parameter changes requires running `generate_target all [get_files *.bd]` in TCL, or right-clicking the BD in the Sources panel → "Generate Output Products." Forgetting this step after changing BRAM depth is a common source of synthesis errors.
- When exporting hardware (`.xsa`) to Vitis, use **"Include bitstream"** only if the bitstream is finalized; otherwise export without bitstream and load the `.bit` separately via XSCT for faster iteration.

## Vivado TCL Scripting

### Key Findings

- **Batch mode invocation:** `vivado -mode batch -source create_bd.tcl -tclargs arg1 arg2` runs a script headlessly and exits on completion. Use `-log build.log -journal build.jou` to capture all output.
- **Non-project mode** skips writing `.xpr`/`.runs` directories; the entire flow lives in memory and is faster. It's ideal for CI pipelines but requires manually sequencing: `read_vhdl` → `read_xdc` → `synth_design` → `opt_design` → `place_design` → `route_design` → `write_bitstream`.
- **Project mode** (what Vivado GUI uses) is better for iterative work with block designs because it tracks IP output products, synthesis runs, and implementation runs as named "runs" you can relaunch individually.
- A hybrid approach works well: use a TCL script to create and populate the block design (project mode under the hood via `create_project`), then export to non-project mode for the implementation/bitstream steps.
- `write_project_tcl` in Vivado exports the current project state as a re-runnable TCL script — a quick way to capture a block design you built interactively.
- For parameterized scripts: use `lindex $argv 0` to read `tclargs` values, enabling board-specific runs from the same script.

### Code Example

```tcl
# Reproducible non-project-mode build for KV260 BRAM demo
# Usage: vivado -mode batch -source build.tcl -tclargs kv260

set board_target [lindex $argv 0]
if {$board_target eq ""} { set board_target "kv260" }

puts "INFO: Building for target: $board_target"

# Read sources
read_vhdl -library work [glob ./vhdl/*.vhd]
read_xdc  ./constraints/kv260_top.xdc

# Synthesis
synth_design -top kv260_top -part xck26-sfvc784-2LV-c \
             -flatten_hierarchy rebuilt \
             -directive PerformanceOptimized

# Implementation
opt_design
place_design   -directive Explore
phys_opt_design
route_design   -directive AggressiveExplore

# Timing check — fail the script if timing is not met
if {[get_property SLACK [get_timing_paths -max_paths 1 -nworst 1]] < 0} {
    puts "ERROR: Timing NOT met"
    exit 1
}

# Bitstream
write_bitstream -force ./output/${board_target}_top.bit
write_hw_platform -fixed -force ./output/${board_target}.xsa

puts "INFO: Build complete"
```

### Relevance to Your Project

Your `create_bd.tcl` handles block design creation. Wrapping it in a non-project-mode outer script like the above gives you a single command (`vivado -mode batch -source build.tcl`) that rebuilds everything from sources — valuable for catching regressions when you adjust BRAM depth or AXI address ranges.

## Vitis Bare-Metal / Standalone

### Key Findings

- **Vitis 2025.1 Unified IDE** (Eclipse-based successor) fully supports bare-metal standalone applications for Cortex-A53; the classic Vitis IDE is still available but is being phased out.
- **Linker script bug in 2025.1:** The GUI linker script editor has a reported bug that can corrupt heap and stack section sizes. Workaround: close the GUI editor and edit `lscript.ld` directly in a text editor. Key sections to verify: `.heap` (default 0x2000 = 8KB) and `.stack` (default 0x2000 per core).
- **`xil_printf` vs `printf`:** `xil_printf` is a lightweight implementation that does NOT support floating-point format specifiers (`%f`, `%g`). Use `printf` (which links the full newlib) only when you need floats — it adds ~30KB to binary size.
- **BSP configuration:** In Vitis, the standalone BSP `Makefile` sets `STDIN_BASEADDRESS` and `STDOUT_BASEADDRESS` to the UART1 base (`0xFF010000` for PS UART1 on KV260's USB-UART path). Verify this in `system.mss` or `xparameters.h` if UART output is missing.
- **Cache coherency:** Cortex-A53 data caches are enabled by the BSP startup code. Writes to non-cached AXI peripheral space (mapped as Device memory in the MMU) are ordered by hardware, but you still need `dsb()` before a read-back to flush the store buffer.
- **Interrupt controller:** For bare-metal interrupt-driven BRAM access, use the GIC (Generic Interrupt Controller) via `XScuGic` driver. For polling-only AXI-Lite BRAM access (as in this project), no interrupt setup is needed.

### Code Example

```c
/* xparameters.h cross-check — confirm BRAM addresses match Vivado block design */
/* These values are generated by Vitis from the exported .xsa */
#ifndef XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR
#error "BSP missing BRAM0 address — re-export .xsa and re-generate BSP"
#endif

#include "xparameters.h"
#include "xil_io.h"
#include "xil_printf.h"
#include "xil_cache.h"

/* Validate at compile time that Vivado addresses match your constants */
#if XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR != 0xA0000000UL
#error "BRAM0 base address mismatch between BSP and application code"
#endif
#if XPAR_AXI_BRAM_CTRL_1_S_AXI_BASEADDR != 0xA0010000UL
#error "BRAM2 base address mismatch between BSP and application code"
#endif

int main(void) {
    /* Disable D-cache for BRAM regions to simplify write-ordering
       (optional — dsb() is sufficient if cache is kept enabled) */
    Xil_SetTlbAttributes(0xA0000000UL, 0x14de2);  /* strongly-ordered */
    Xil_SetTlbAttributes(0xA0010000UL, 0x14de2);

    xil_printf("-- KV260 AXI-BRAM bare-metal test --\r\n");

    const u32 test_patterns[] = {0xDEADBEEF, 0xCAFEBABE, 0x12345678, 0xA5A5A5A5};
    u32 pass = 0, fail = 0;

    for (u32 i = 0; i < 4; i++) {
        Xil_Out32(XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR + i*4, test_patterns[i]);
        Xil_Out32(XPAR_AXI_BRAM_CTRL_1_S_AXI_BASEADDR + i*4, ~test_patterns[i]);
        dsb();
        u32 r0 = Xil_In32(XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR + i*4);
        u32 r1 = Xil_In32(XPAR_AXI_BRAM_CTRL_1_S_AXI_BASEADDR + i*4);
        if (r0 == test_patterns[i] && r1 == ~test_patterns[i]) {
            pass++;
        } else {
            fail++;
            xil_printf("FAIL [%u]: BRAM0=0x%08X BRAM2=0x%08X\r\n", i, r0, r1);
        }
    }
    xil_printf("%s: %u pass, %u fail\r\n", fail ? "FAIL" : "PASS", pass, fail);
    return fail ? 1 : 0;
}
```

### Relevance to Your Project

The `XPAR_*_BASEADDR` compile-time checks ensure that if the Vivado block design address assignment ever drifts from your `main.c` constants (0xA0000000 / 0xA0010000), you get a build error rather than a silent FAIL at runtime. This is a zero-cost guard for your PS-to-PL connectivity demo.

## XDC Timing Constraints

### Key Findings

- For AXI-Lite BRAM paths on the KV260, the critical timing paths are internal to the PL (PS AXI master → SmartConnect/Interconnect → BRAM controller → Block RAM). These paths are constrained by the PS clock (`pl_clk0`, typically 100 MHz) and do not need `set_input_delay`/`set_output_delay` — those commands apply only to I/O ports connecting off-chip.
- **`set_input_delay`** syntax (UG835, 2025.1): specifies the worst-case external delay from a source clock edge to when valid data arrives at an FPGA input port. Values are in nanoseconds; `-max` sets the setup constraint, `-min` the hold constraint.
- **`set_output_delay`** syntax: specifies how long after the FPGA output clock edge the downstream device requires data to be valid. For source-synchronous interfaces, you typically set both `-max` and `-min`.
- **Clock groups:** For the KV260's PS clock driving PL logic, the clock is defined in the block design and Vivado auto-creates the `create_clock` constraint via the `.xdc` output of the BD. You should NOT manually add `create_clock` for `pl_clk0` — it will conflict.
- **Timing closure tips for Kria:** If the AXI path from PS → BRAM fails timing at 100 MHz, reduce `pl_clk0` to 50 MHz in the Zynq PS IP configuration rather than adding `set_multicycle_path` — simpler and less error-prone.
- For bare-metal projects with no off-chip I/O on the PL side (all signals go through PS), a minimal XDC file may contain only `set_property BITSTREAM.GENERAL.COMPRESS TRUE [current_design]` plus any debug hub constraints.

### Code Example

```tcl
# kv260_top.xdc — minimal constraints for PS-only AXI-BRAM demo
# Note: pl_clk0 create_clock is auto-generated by Vivado from the block design
# DO NOT duplicate it here — that causes "multiple clocks on the same source" errors

# CFGBVS and CONFIG_VOLTAGE for K26 SoM (required to avoid DRC errors)
set_property CFGBVS GND [current_design]
set_property CONFIG_VOLTAGE 1.8 [current_design]

# Bitstream options
set_property BITSTREAM.GENERAL.COMPRESS TRUE [current_design]

# False path: PS reset to PL reset tree (async reset, properly synchronized in BD)
set_false_path -from [get_pins zynq_ultra_ps_e_0/pl_resetn0] \
               -to   [get_cells -hierarchical -filter {NAME =~ *proc_sys_reset*}]

# If any GPIO debug outputs exist on PL I/O (uncomment and adjust as needed):
# set_output_delay -clock [get_clocks pl_clk0] -max 2.0 [get_ports {debug_gpio[*]}]
# set_output_delay -clock [get_clocks pl_clk0] -min 0.5 [get_ports {debug_gpio[*]}]

# Optional: relax non-critical paths to improve QoR
# set_multicycle_path 2 -setup -from [get_clocks pl_clk0] -to [get_clocks pl_clk0] \
#   -through [get_cells -hierarchical -filter {NAME =~ *bram_ctrl*}]
```

### Relevance to Your Project

Your `kv260_top.vhd` wraps the block design. The most common DRC errors on KV260 are missing `CFGBVS`/`CONFIG_VOLTAGE` properties — the XDC above includes those. Since your design is PS-internal (no PL-side I/O pins used for BRAM access), you need no I/O timing constraints, keeping the XDC minimal.

## Kria KV260 / K26 SoM

### Key Findings

- **Default boot mode:** KV260 ships with QSPI32 boot mode, loading AMD-provided boot firmware from QSPI flash. For bare-metal development, the fastest iteration path is JTAG boot (load bitstream and ELF directly via XSCT) — no reflashing required.
- **JTAG boot procedure:** Remove the SD card, power on. The board enters JTAG boot mode. Use XSCT: `connect`, `targets`, `fpga -file top.bit`, `source psu_init.tcl`, `dow main.elf`, `run`. No FSBL is needed for simple BRAM demos.
- **QSPI flashing via XSCT (not GUI):** Once QSPI has any bootloaders, the Vivado Hardware Manager flash GUI fails silently. Use XSCT script to call `program_flash` with explicit `-offset` parameters for reliable reflashing.
- **MIO pin allocation on K26:** UART1 (PS UART for USB-UART path on KV260 carrier) is on MIO[36:37]. This is pre-configured in the AMD-provided Zynq PS preset — do not change MIO assignments in your PS IP configuration or you lose UART output.
- **PL power domain:** The KV260's PL fabric is powered by the `VCC_PSINTLP` and `VCC_PSINTFP` rails from the K26 SoM PMIC. These are always-on when the board is powered; no explicit power-sequencing is needed for bare-metal PL designs.
- **Board files:** In Vivado 2025.1, use `set_property board_part xilinx.com:kv260_som:part0:1.4 [current_project]` when creating the project to get automatic PS configuration presets.
- **K26 part number for Vivado:** `xck26-sfvc784-2LV-c` (speed grade -2LV, commercial temperature). The `-2LV` designator means low-voltage core at the speed grade 2 level — do not substitute `-2` or `-1` without checking your actual part marking.

### Code Example

```tcl
# XSCT script: load bitstream + bare-metal ELF onto KV260 via JTAG (no SD/QSPI needed)
# Run from XSCT console or: xsct load_kv260.tcl

connect

# Select APU (Cortex-A53 core 0)
targets -set -nocase -filter {name =~ "*APU*"}

# Initialize PS (replaces FSBL for simple bare-metal)
source [file join $env(XILINX_VITIS) \
    data/embeddedsw/lib/sw_apps/freertos_lwip_tcp_perf_server/src \
    psu_init.tcl 2>/dev/null] \
    || source ./psu_init.tcl

psu_init

# Load PL bitstream
fpga -file ./output/kv260_top.bit

# Target A53 core 0 for ELF download
targets -set -nocase -filter {name =~ "*A53*#0"}
rst -processor

# Load and run ELF
dow ./output/main.elf
con

puts "Application running — check USB-UART for PASS/FAIL output"
```

### Relevance to Your Project

The XSCT flow above matches your bare-metal project exactly: load the bitstream that configures the PS-PL AXI-Lite BRAM path, then download and run your `main.elf` which writes/reads BRAM0 and BRAM2. No SD card, no Linux, no FSBL needed — just JTAG and XSCT for rapid iteration.

## AMD/Xilinx Tool Updates (Vivado/Vitis 2025.x)

### Key Findings

- **Vitis 2025.1 (released ~July 2025):** The Unified IDE is now the default entry point; the classic IDE is deprecated but still accessible. Bare-metal standalone workflows are fully supported. The 2025.1 UG1742 covers installation and new features.
- **Vitis 2025.2 (later in 2025):** The Revision History in UG1742 confirms ongoing updates including DSP library and platform support improvements.
- **Vitis 2026.1 (released 2026):** A new major version is now available with additional features; check AMD docs for upgrade notes before moving from 2025.1.
- **Vivado 2025.1 IP Change Log (AR #000037919):** All IP version changes for 2025.1 are documented in this AMD support article — includes AXI BRAM Controller, SmartConnect, Zynq UltraScale+ PS IP updates. Check this before upgrading an existing project to confirm IP compatibility.
- **AXI BRAM Controller v4.1:** The current shipping version; supports ECC, single/dual port configurations, and AXI4 or AXI4-Lite slave interface. The AXI4-Lite mode is simpler for bare-metal demos (no burst support, lower LUT cost).
- **Known Vivado 2025.1 issue — AXI Full peripheral address space:** A Digilent forum report notes a 2025 Vivado issue where AXI Full peripherals appear limited to 1K of usable address space in some configurations. Workaround: verify `set_property range` in the Address Editor explicitly rather than relying on auto-assignment defaults.
- **Vitis Unified IDE linker script editor bug (2025.1):** Confirmed user report on AMD Adaptive Support — the GUI editor can reset heap/stack to 0. Always verify `.lld` or `lscript.ld` sizes after any GUI edit.

### Code Example

```tcl
# Vivado 2025.1 TCL: check IP versions in a block design and flag outdated IP
# Useful after a tool upgrade to identify what needs refreshing

open_project ./kv260_bram_demo.xpr
open_bd_design [get_files *.bd]

set ip_cells [get_bd_cells -hierarchical -filter {TYPE == ip}]
puts "INFO: Checking IP versions in block design..."

foreach cell $ip_cells {
    set vlnv [get_property VLNV $cell]
    set upgrade_needed [get_property UPGRADE_NEEDED $cell]
    if {$upgrade_needed} {
        puts "WARNING: $cell ($vlnv) has upgrade available"
    } else {
        puts "OK: $cell ($vlnv)"
    }
}

# Upgrade all outdated IP at once
upgrade_ip [get_ips -all]
generate_target all [get_files *.bd]
puts "INFO: IP upgrade complete"
```

### Relevance to Your Project

When you upgrade from Vivado 2024.x to 2025.1 (or to 2025.2/2026.1), run the TCL snippet above to find any IP that needs refreshing — the AXI BRAM Controller and SmartConnect in your block design are common candidates. The address-space 1K limitation bug is worth verifying: your 64KB BRAM ranges should be safe, but confirm with `get_property range` on both BRAM address segments after implementation.
