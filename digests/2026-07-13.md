# FPGA Research Digest - 2026-07-13

## Executive Summary

- **AXI write-channel synchronization**: Both `AWVALID` and `WVALID` must be observed simultaneously before accepting a write — Xilinx's own auto-generated AXI-Lite slave templates have historically failed this check, causing silent data corruption at high write rates.
- **Vivado 2025 AXI full peripheral 1 kB address-space bug**: Custom AXI-full peripherals created with the IP wizard in Vivado 2025.x are silently limited to 1 kB (10-bit decoder); verify the generated `user_logic` address decode width and widen it manually if needed.
- **AXI-Lite BRESP acknowledgement in bare-metal C**: A plain `Xil_Out32` stores to the AXI write-address channel but never waits for `BRESP`; back-to-back writes without a read-back fence can outpace the interconnect on some versions of the SmartConnect IP.
- **BSP linker-script memory regions must match XSA**: After exporting a new `.xsa` and regenerating the BSP, confirm that `lscript.ld` `MEMORY` regions reflect the correct BRAM base (`0xA0000000`) and size — an outdated script silently maps the application over the wrong address range.
- **K26 boot-mode note for JTAG bare-metal**: The Kria SOM boots Linux from QSPI by default; for JTAG-based bare-metal development, remove the SD card, set boot pins to JTAG mode, and use `psu_init.tcl` directly via XSDB without an FSBL — this avoids the normal Linux-first boot sequence.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- **Write-channel synchronization pitfall**: The AXI-Lite spec requires an address-write handshake (`AW`) and a data-write handshake (`W`) to complete independently, but most slave implementations need both before they can commit the write. Raising `AWREADY` and `WREADY` independently (i.e., accepting AW before W arrives) requires an internal holding register; forgetting this causes data from a subsequent transaction to be written to the previous address.
- **READY must never depend on VALID (master side)**: `AWVALID` must not wait for `AWREADY` to be asserted first — this is an AXI deadlock. Conversely, `AWREADY` (slave) may depend on `AWVALID` (master), so slaves can choose to deassert `AWREADY` at reset.
- **BREADY low-holds downstream channels**: If the master drives `BREADY` low (i.e., is not ready to accept the write-response), the slave must stall its `AWREADY` and `WREADY` too, otherwise it accepts new addresses while the response channel is full. This backpressure path is the most commonly omitted piece in hand-written AXI-Lite slaves.
- **AXI-Stream `TKEEP` and `TSTRB`**: `TKEEP` marks byte lanes that carry data; `TSTRB` marks position bytes vs. null bytes. Null bytes (TKEEP=0) are only legal on the `TLAST` beat. Driving sparse `TKEEP` mid-packet violates the spec and produces undefined behaviour in Xilinx DMA and FIFO IPs.
- **AXI-Stream reset duration**: The AXI specification requires `ARESETn` to be held low for at least 16 cycles of the slowest clock in the system to guarantee all `TVALID`/`TREADY` outputs are deasserted before reset release.

### Code Example

```vhdl
-- AXI-Lite slave: synchronized AW+W acceptance with BREADY backpressure
process(clk)
begin
  if rising_edge(clk) then
    if rst_n = '0' then
      s_axi_awready <= '0';
      s_axi_wready  <= '0';
      s_axi_bvalid  <= '0';
    else
      -- Accept AW and W only when both are presented AND response channel is clear
      if s_axi_awvalid = '1' and s_axi_wvalid = '1'
         and s_axi_awready = '0' and s_axi_bvalid = '0' then
        s_axi_awready <= '1';
        s_axi_wready  <= '1';
        wr_addr       <= s_axi_awaddr;
        wr_data       <= s_axi_wdata;
      else
        s_axi_awready <= '0';
        s_axi_wready  <= '0';
      end if;
      -- Assert BVALID one cycle after acceptance
      if s_axi_awready = '1' then
        s_axi_bvalid <= '1';
        s_axi_bresp  <= "00";  -- OKAY
      elsif s_axi_bready = '1' then
        s_axi_bvalid <= '0';   -- clear after master acknowledges
      end if;
    end if;
  end if;
end process;
```

### Relevance to Your Project

Your `kv260_top.vhd` wraps two AXI-Lite BRAM controllers (`0xA0000000`, `0xA0010000`). The Xilinx `axi_bram_ctrl` IP handles the AW/W synchronization internally, but your bare-metal `main.c` never explicitly waits for `BRESP`. Insert a `Xil_In32` readback after each `Xil_Out32` burst to act as an implicit response fence and avoid outpacing the SmartConnect.

## Vivado Block Design / IP Integrator

### Key Findings

- **Vivado 2025.1 new addressing GUI**: A new GUI automatically groups equivalent address spaces; still verify with the manual Address Editor tab after running `assign_bd_address` — auto-grouping can reassign offsets.
- **Two new IP Integrator views in 2025.1**: "Clocking and Reset" and "Interrupt and AXI-4 Lite" pane views let you audit connectivity for those subsystems without scrolling the full diagram — useful when verifying that `axi_interconnect` is wired to all BRAM controllers.
- **`validate_bd_design` catches missing mandatory ports**: Run it explicitly before `generate_target all`; missing connections on `EXT_RESET_IN`, `ARESETN`, or unconnected slave AXI ports all surface here rather than at bitstream.
- **`upgrade_ip` after Vivado version change**: Calling `upgrade_ip [get_ips *]` in the Tcl console (or `update_ip_catalog -rebuild`) before synthesis prevents stale wrapper stubs — a common cause of `[Synth 8-3330] Module not found` errors after upgrading to 2025.1.
- **SmartConnect vs AXI Interconnect**: Starting in Vivado 2019.2, AMD recommends `axi_smartconnect` over `axi_interconnect` for new designs; SmartConnect auto-inserts clock crossing and width conversion, reducing manual steps.

### Code Example

```tcl
# Validate BD and assign addresses in non-interactive TCL
open_project myproject/myproject.xpr
open_bd_design [get_files *.bd]

validate_bd_design
if {[get_property NEEDS_REFRESH [current_bd_design]] != 0} {
  error "Block design validation failed — check messages above"
}

# Auto-assign then pin the two BRAMs at expected PS-PL addresses
assign_bd_address
set_property offset 0xA0000000 \
  [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property range 64K \
  [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property offset 0xA0010000 \
  [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_1_Mem0}]
set_property range 64K \
  [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_1_Mem0}]

generate_target all [get_files *.bd]
```

### Relevance to Your Project

Your `create_bd.tcl` drives the full block-design rebuild. Adding `validate_bd_design` before `generate_target all` will surface any connectivity gaps introduced by IP version upgrades before you waste synthesis time.

## Vivado TCL Scripting

### Key Findings

- **Non-project mode keeps no `.xpr`**: Use `read_vhdl`, `read_xdc`, `synth_design`, `opt_design`, `place_design`, `route_design`, `write_bitstream` as a linear pipeline — no project state is persisted to disk. This is ideal for CI builds.
- **Export block design to TCL**: In the IDE, use File → Export → Export Block Design; in batch mode, `write_bd_tcl -force my_bd.tcl`. The exported script is self-contained but includes `set_property board_part` lines that pin the Vivado version — strip those for portability.
- **Source guards for idempotent scripts**: Wrap IP creation in `if {[llength [get_bd_cells my_ip]] == 0}` guards so scripts can be re-sourced without error after partial runs.
- **UG892 / UG894 / UG994**: The canonical references are UG892 (Design Flows Overview, including non-project mode), UG894 (TCL Scripting), and UG994 (IP Integrator / Block Design) — all updated for 2025.2.
- **`report_timing_summary` in batch**: Call `report_timing_summary -delay_type min_max -report_unconstrained -warn_on_violation -file timing.rpt` at the end of a non-project run so timing violations block CI.

### Code Example

```tcl
# Non-project mode batch build skeleton for kv260-axi-bram-demo
set part "xck26-sfvc784-2LV-c"

read_vhdl   [glob ../vhdl/*.vhd]
read_xdc    [glob ../xdc/*.xdc]
read_ip     [glob ../ip/*.xci]

synth_design  -top kv260_top -part $part -flatten_hierarchy rebuilt
opt_design
place_design
phys_opt_design
route_design

report_timing_summary -delay_type min_max \
  -report_unconstrained -warn_on_violation \
  -file ./reports/timing_summary.rpt

write_bitstream -force ./output/kv260_top.bit
write_hw_platform -fixed -include_bit -force ./output/kv260.xsa
```

### Relevance to Your Project

Your existing `create_bd.tcl` uses project mode. Wrapping it in a non-project shell script allows headless CI runs (e.g., GitHub Actions with Vivado Docker) to produce reproducible bitstreams and XSA files without a GUI.

## Vitis Bare-Metal / Standalone

### Key Findings

- **`stdout` BSP setting must match physical UART**: In the BSP configuration, `stdin`/`stdout` should point to `psu_uart_1` for the KV260 (which routes to the USB-UART bridge) — assigning to `psu_uart_0` produces no serial output without error.
- **`xil_printf` vs `printf`**: `xil_printf` is lighter (no floating-point, no `%f` support) and links against the standalone libc stub. For PASS/FAIL messages without float, prefer `xil_printf`; for hex dump use `xil_printf("0x%08X\n\r", val)`.
- **Linker script `MEMORY` region for AXI BRAM**: If your application reads back BRAM at `0xA0000000`, ensure that address is NOT listed in `lscript.ld` as a loadable region — only OCM and DDR should appear there. AXI BRAM is accessed purely as a memory-mapped peripheral, not a program-load target.
- **BSP regeneration after XSA update**: After re-exporting the XSA from Vivado, right-click the platform in Vitis → Update Hardware; this regenerates BSP headers (`xparameters.h`) with correct `XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR` values.
- **Match tool versions**: Mixing Vivado 2025.1 XSA with Vitis 2024.2 is unsupported; the exported XSA schema changed between versions. Always use same-version pairs.

### Code Example

```c
/* Bare-metal AXI-BRAM write + verified readback with response fence */
#include "xil_io.h"
#include "xil_printf.h"

#define BRAM0_BASE  0xA0000000UL
#define BRAM1_BASE  0xA0010000UL
#define TEST_WORDS  16

int main(void)
{
    u32 i, val, err = 0;

    /* Write phase */
    for (i = 0; i < TEST_WORDS; i++) {
        Xil_Out32(BRAM0_BASE + (i * 4), 0xDEAD0000 | i);
        /* Implicit AXI BRESP fence: read-back stalls until write drains */
        val = Xil_In32(BRAM0_BASE + (i * 4));
        if (val != (0xDEAD0000 | i)) {
            xil_printf("BRAM0[%u] MISMATCH: wrote 0x%08X read 0x%08X\r\n",
                       i, 0xDEAD0000 | i, val);
            err++;
        }
    }

    xil_printf(err ? "FAIL (%u errors)\r\n" : "PASS\r\n", err);
    return (int)err;
}
```

### Relevance to Your Project

Your `main.c` pattern-writes to both BRAMs and checks PASS/FAIL over UART. The explicit readback after every write (as shown above) serves as a BRESP fence. Check that `xparameters.h` defines `XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR` as `0xA0000000` and `XPAR_AXI_BRAM_CTRL_1_S_AXI_BASEADDR` as `0xA0010000` — a mismatched BSP after XSA re-export is the most common "FAIL" root cause.

## XDC Timing Constraints

### Key Findings

- **AXI-Lite internal paths need no I/O delays**: All signals between the Zynq PS AXI master and the PL BRAM controller are internal to the device — no `set_input_delay`/`set_output_delay` are needed for those paths. I/O timing constraints only apply to signals crossing the package pins.
- **Create clock from PL fabric clock**: The PL clock from the PS (`pl_clk0`) is already defined in the Zynq PS IP; add `create_generated_clock` only if you derive additional clocks from it via MMCM/PLL.
- **`set_false_path` for CDC reset**: If your design uses an asynchronous reset tree with a synchronizer, mark the reset path: `set_false_path -from [get_ports sys_reset_n]` to prevent timing closure from trying to time an asynchronous signal.
- **`set_clock_groups` for unrelated clocks**: If you add a second clock domain (e.g., a video pixel clock), use `set_clock_groups -asynchronous -group [get_clocks clk_pl_0] -group [get_clocks pix_clk]` rather than `set_false_path` — it's more explicit and catches newly-added paths automatically.
- **`report_cdc` for cross-domain safety**: Run `report_cdc -details -severity {Critical High}` after route to identify unconstrained clock-domain crossings before tapeout.

### Code Example

```tcl
# XDC for kv260-axi-bram-demo — minimal constraints for PS-PL AXI design
# pl_clk0 is defined automatically by the Zynq UltraScale+ PS IP (100 MHz default)

# False-path on asynchronous reset input if using one
set_false_path -from [get_ports {sys_resetn}]

# If an external LED or GPIO crosses to a slow domain, relax timing
set_output_delay -clock [get_clocks clk_pl_0] -max 2.0 [get_ports {led[*]}]
set_output_delay -clock [get_clocks clk_pl_0] -min -1.0 [get_ports {led[*]}]

# Multicycle path for wide registers updated infrequently (e.g., status regs)
set_multicycle_path 2 -setup \
  -from [get_cells {status_reg_reg[*]}] \
  -to   [get_cells {s_axi_rdata_reg[*]}]
set_multicycle_path 1 -hold \
  -from [get_cells {status_reg_reg[*]}] \
  -to   [get_cells {s_axi_rdata_reg[*]}]
```

### Relevance to Your Project

Your current design routes all paths through the PS-to-PL AXI interface — no external data ports, so only the LED/GPIO outputs need I/O constraints. The primary timing risk is the `pl_clk0` frequency requested in the PS configurator; if you push it above the default 100 MHz, add a `create_generated_clock` and verify `report_timing_summary` shows positive slack on the BRAM controller read-data path.

## Kria KV260 / K26 SoM

### Key Findings

- **Default boot sequence**: The K26 SOM always boots its PMU/FSBLv2 from QSPI flash; the normal flow then hands off to Linux from the SD card. Bare-metal debugging intercepts this by setting the mode pins to JTAG (`SW1` on the KV260 carrier: all switches to 0) and powering on without SD/QSPI boot.
- **MIO / EMIO mapping on SOM240_1**: The SOM240_1 connector exposes MIO bank 501 (MIO0–25), MIO bank 502 (MIO26–51), HPIO bank 66 (HPA), and HDIO bank 45 (HDA). The RPi and PMOD headers on the KV260 carrier are wired to PL HPIO/HDIO pins — they are **not** PS MIO.
- **Power domains**: The K26 SOM has separate power rails for PS (VCC_PSINTFP, VCC_PSINTLP) and PL (VCCINT). PL must be powered for AXI-Lite to route PS→PL; a bitstream load failure over JTAG often indicates the PL power rail failed to sequence correctly.
- **USB-UART**: The KV260 carrier routes `psu_uart_1` (MIO38/39) through a Silicon Labs CP2108 USB-UART bridge — confirm `/dev/ttyUSB0` or `/dev/ttyUSB1` (interface 1) at 115200 8N1 is the correct port when using `minicom`/`picocom` on the host.
- **Bare-metal JTAG flow**: Load the bitstream first (`program_hw_devices`), then download the ELF (`dow app.elf`), then `con` — the PS must be initialized via `psu_init.tcl` sourced in XSDB before the ELF executes; otherwise the DDR and clocks are unconfigured.

### Code Example

```tcl
# XSDB bare-metal debug session for KV260 (run after connecting JTAG)
connect
targets -set -filter {name =~ "PSU"}
source psu_init.tcl
psu_init

# Program the PL with the bitstream
fpga -file kv260_top.bit

# Switch to A53 core 0 and load the ELF
targets -set -filter {name =~ "Cortex-A53 #0"}
dow main.elf

# Optional: set a breakpoint at main before running
bpadd -addr &main
con
```

### Relevance to Your Project

Your PS-to-PL connectivity demo depends on PL receiving a valid clock and reset from the PS. If BRAM reads return `0xFFFFFFFF` or `0x00000000`, verify that:
1. The bitstream loaded successfully (`program_hw_devices` returned no errors).
2. `psu_init.tcl` ran before `dow` (DDR must be up for the ELF stack).
3. `pl_clk0` is enabled in the PS configurator (default 100 MHz) — an unchecked PL fabric clock leaves the BRAM controller in reset.

## AMD/Xilinx Tool Updates (Vivado/Vitis 2025.x)

### Key Findings

- **Vivado 2025.1 AXI full peripheral 1 kB address decoder bug**: Custom AXI-full peripherals generated by the "Create and Package New IP" wizard in Vivado 2025.x emit a 10-bit address decoder (`addr_bits = 10`), silently limiting usable address space to 1 kB and wrapping addresses ≥ 256 words back to zero. Workaround: manually widen the `ADDR_LSB` and local address slice in the generated `_S00_AXI.vhd` template. This does **not** affect the Xilinx-provided `axi_bram_ctrl` IP, only hand-generated IP wizard output.
- **Vivado 2025.1 Pblock planner**: A new GUI one-stop-shop for creating, editing, and visualizing Pblocks — useful when constraining PL accelerators to specific clock regions on the K26 SOM to avoid routing congestion.
- **PS-first boot in 2025.1**: New capability to boot the PS (Linux) first and dynamically load PL bitstreams at runtime via `fpgautil` or `xmutil` — a shift from the traditional "PL static, then boot PS" flow. Not relevant for bare-metal demos but useful context for future Linux migration.
- **`write_hw_platform` is canonical**: `export_hardware`/`write_sysdef` (older docs) are deprecated as of 2022.x; use `write_hw_platform -fixed -include_bit -force output.xsa`. Using deprecated commands with 2025.1 can produce XSA files missing the `hardware_handoff` section.
- **Vitis 2025.1 Known Issues**: As of the 2025.1.1 patch, AMD reports no unresolved critical known issues for the embedded software development flow — the clean-sheet Vitis unified IDE (replacing Classic IDE) is now the primary interface.

### Code Example

```tcl
# Vivado 2025.1: export XSA with bitstream included (canonical command)
open_project ./myproject/myproject.xpr
open_run impl_1

# Confirm timing closure before export
set wns [get_property STATS.WNS [get_runs impl_1]]
if {$wns < 0} {
  puts "WARNING: Timing not met (WNS = $wns ns) — XSA may be unreliable"
}

write_hw_platform \
  -fixed \
  -include_bit \
  -force \
  ./output/kv260_platform.xsa

puts "XSA written: [file normalize ./output/kv260_platform.xsa]"
```

### Relevance to Your Project

If you are using Vivado 2025.1 to recreate the block design via `create_bd.tcl`, check the generated AXI BRAM controller IP version — `axi_bram_ctrl:4.1` is current in 2025.1. The 1 kB wizard bug only applies if you created a custom AXI peripheral with the IP wizard; the Xilinx-provided BRAM controller is unaffected. Always use `write_hw_platform` (not `write_sysdef`) at the end of your TCL build script to produce the XSA consumed by Vitis 2025.1.
