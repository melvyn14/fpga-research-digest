## Executive Summary

- **AXI VALID must never be gated on READY** — asserting `AWVALID`/`WVALID` only when the slave asserts `AWREADY` is an illegal deadlock-inducing pattern in AXI-Lite; the Zynq PS's AXI master already conforms, but any custom HDL wrapper on the PL side must not.
- **AXI SmartConnect is the preferred interconnect in 2025.x** — AXI Interconnect is deprecated for new designs; migrate BRAM connections to SmartConnect for better address decode and no re-mapping overhead.
- **KV260 bare-metal JTAG debug**: Boot with SD removed, supply `psu_init.tcl` instead of an FSBL in the Vitis debug config — this shaves minutes off every iteration cycle on the KV260 BRAM demo.
- **Vivado 2025.1 TCL non-project mode**: `open_bd_design` followed by `validate_bd_design` before `write_bitstream` catches address-segment errors that silent block-design saves miss in GUI mode.
- **XDC false-path the AXI-BRAM paths**: Internal BRAM read latency is one clock cycle; without `set_multicycle_path` you will see marginal WNS on high-speed implementations — safe to apply `-from [get_cells *bram*] -to [get_cells *bram*]`.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- **VALID must be held** — once a master asserts `AWVALID`, `WVALID`, or `ARVALID`, it must keep the signal high until the corresponding `READY` is seen. Deasserting early is a protocol violation that silently corrupts transactions.
- **Do not gate VALID on READY** — a master that waits for `READY` before asserting `VALID` creates a potential deadlock if the slave waits for `VALID` before asserting `READY` (which AXI explicitly permits).
- **AXI-Lite response channel** — many bare-metal drivers ignore `BVALID`/`BREADY` (the write-response channel). The PS AXI master still drives `BREADY` correctly, but if you ever insert a custom RTL master, you must complete the B-channel handshake or the slave stalls.
- **Address alignment** — AXI-Lite requires word-aligned addresses (4-byte for 32-bit bus). Misaligned accesses return a SLVERR; the Xilinx AXI BRAM controller logs this only if you check the response in your C driver.
- **AXI4 vs AXI-Lite**: BRAM2 at `0xA0010000` using AXI-Lite is limited to single-beat (non-burst) transfers; this is fine for register-style BRAM access but limits throughput compared to AXI4 with burst support.

### Code Example

```c
/* AXI-Lite read with response check — bare-metal C */
#define BRAM0_BASE 0xA0000000UL
#define BRAM1_BASE 0xA0010000UL

static inline uint32_t axi_read(uint32_t base, uint32_t offset) {
    return *(volatile uint32_t *)(base + offset);
}

static inline void axi_write(uint32_t base, uint32_t offset, uint32_t val) {
    *(volatile uint32_t *)(base + offset) = val;
    /* Memory barrier: ensure the write completes before the read-back */
    __asm__ volatile ("dsb sy" ::: "memory");
}

void bram_pattern_test(void) {
    const uint32_t PATTERN = 0xDEADBEEFUL;
    axi_write(BRAM0_BASE, 0x00, PATTERN);
    uint32_t rd = axi_read(BRAM0_BASE, 0x00);
    xil_printf("BRAM0: %s (0x%08X)\r\n",
               rd == PATTERN ? "PASS" : "FAIL", rd);
}
```

### Relevance to Your Project

The KV260 AXI-BRAM demo writes patterns from the Cortex-A53 over AXI-Lite. The `dsb sy` barrier is essential between the write and read-back: without it the Cortex-A53 store buffer may return the cached write value rather than the actual BRAM contents, masking a broken AXI connection. Also confirm that `BVALID` is connected in the block design — leaving it open may cause silent write hangs.

## Vivado Block Design / IP Integrator

### Key Findings

- **Run Connection Automation after every IP add** — Vivado auto-connects reset, clock, and AXI buses when you click "Run Connection Automation" after each IP insertion. Missing this step leaves dangling ports and causes DRC failures at validate time.
- **Address Editor — Assign All** — after adding BRAM controllers, use `Assign All` in the Address Editor to auto-populate base addresses. Then override manually: BRAM0 → `0xA0000000`, BRAM1 → `0xA0010000`, with 64 KB range each.
- **SmartConnect over AXI Interconnect** — Vivado 2025.x emits a deprecation warning when you instantiate `axi_interconnect`; migrate to `smartconnect` for new masters/slaves.
- **Validate before generating** — `validate_bd_design` (TCL) or Tools → Validate Design (GUI) catches address overlaps, unconnected required ports, and clock-domain mismatches before a long synthesis run.
- **Save the BD periodically** — BD edits are in-memory; Ctrl+S writes the `.bd` file and prevents losing half an hour of work on a tool crash.

### Code Example

```tcl
# Re-assign BRAM address segments after adding SmartConnect
set_property offset 0xA0000000 [get_bd_addr_segs {ps/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property range  64K        [get_bd_addr_segs {ps/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property offset 0xA0010000 [get_bd_addr_segs {ps/Data/SEG_axi_bram_ctrl_1_Mem0}]
set_property range  64K        [get_bd_addr_segs {ps/Data/SEG_axi_bram_ctrl_1_Mem0}]
validate_bd_design
```

### Relevance to Your Project

The KV260 demo targets BRAM0 at `0xA0000000` and BRAM2 at `0xA0010000`; the TCL snippet above locks those addresses in a reproducible script and validates immediately. If you ever regenerate the block design, running this snippet as part of `create_bd.tcl` prevents address-editor drift.

## Vivado TCL Scripting

### Key Findings

- **Non-project mode flow**: `read_vhdl` → `read_xdc` → `synth_design` → `opt_design` → `place_design` → `route_design` → `write_bitstream`. Each command is explicit; no project database is written unless you call `write_checkpoint`.
- **IP Integrator in non-project mode**: Use `create_bd_design`, `add_files`, `open_bd_design`, then `generate_target all [get_files *.bd]` to produce synthesis netlists without a project file.
- **`validate_bd_design` is your friend** — call it at the end of every block-design TCL script before `generate_target`; it surfaces address-segment gaps and disconnected interfaces before synthesis.
- **Checkpoints for incremental runs** — `write_checkpoint post_synth.dcp` after synthesis lets you restart from synthesis rather than re-running the full flow after a routing tweak.
- **`source` inside Vivado batch** — run `vivado -mode batch -source create_bd.tcl` to execute scripts headlessly; useful in CI pipelines.

### Code Example

```tcl
# Non-project mode: synthesize and write bitstream
read_vhdl   [glob ../vhdl/*.vhd]
read_xdc    ../xdc/kv260_top.xdc
read_ip     [glob ../ip/**/*.xci]

synth_design  -top kv260_top -part xck26-sfvc784-2LV-c
write_checkpoint post_synth.dcp -force

opt_design
place_design
phys_opt_design
route_design
write_checkpoint post_route.dcp -force

write_bitstream -force ../bitstream/kv260_top.bit
write_debug_probes -force ../bitstream/kv260_top.ltx
```

### Relevance to Your Project

Your `create_bd.tcl` runs inside Vivado's project mode today. Consider adding a companion `run_impl.tcl` in non-project mode for CI: it lets you regenerate the bitstream on any machine without the GUI and produces deterministic checkpoints for bisecting routing failures.

## Vitis Bare-Metal / Standalone

### Key Findings

- **BSP regeneration after XSA change** — whenever you export a new XSA from Vivado (after address changes, new IP, or constraint updates), you must regenerate the BSP in Vitis; stale BSPs silently use wrong base addresses from `xparameters.h`.
- **`xil_printf` vs `printf`** — `xil_printf` is a lightweight formatted-print that uses the UART from the standalone BSP without pulling in full `newlib`; it does NOT support floating-point format specifiers (`%f`, `%g`). Use `printf` (with `newlib` enabled) only if you need floats.
- **Linker script heap/stack** — the default standalone linker script places stack at the top of OCM (on-chip memory). For a BRAM demo that only writes to PL BRAM, you can keep everything in DDR and tighten the heap to 0x1000 to speed up link time.
- **`Xil_DCacheFlushRange`** — if D-cache is enabled (it is by default for Cortex-A53), flush the cache range before reading back AXI-written values: `Xil_DCacheFlushRange(BRAM0_BASE, 0x1000)`. The BRAM AXI port is not cache-coherent.
- **`psu_init.tcl` for JTAG debug** — use this file (generated by Vivado alongside the XSA) as the initialization script in the Vitis debug configuration instead of an FSBL. This eliminates the FSBL build step during rapid development iterations.

### Code Example

```c
#include "xil_printf.h"
#include "xil_cache.h"
#include "xparameters.h"

#define BRAM0_BASE XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR
#define BRAM1_BASE XPAR_AXI_BRAM_CTRL_1_S_AXI_BASEADDR

int main(void) {
    Xil_DCacheDisable();   /* simplest approach: disable cache for AXI-mapped regions */

    volatile uint32_t *bram0 = (volatile uint32_t *)BRAM0_BASE;
    volatile uint32_t *bram1 = (volatile uint32_t *)BRAM1_BASE;

    bram0[0] = 0xCAFEBABEUL;
    bram1[0] = 0xDEADBEEFUL;

    xil_printf("BRAM0[0] = 0x%08X  %s\r\n", bram0[0],
               bram0[0] == 0xCAFEBABEUL ? "PASS" : "FAIL");
    xil_printf("BRAM1[0] = 0x%08X  %s\r\n", bram1[0],
               bram1[0] == 0xDEADBEEFUL ? "PASS" : "FAIL");
    return 0;
}
```

### Relevance to Your Project

Using `XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR` from `xparameters.h` instead of hardcoded `0xA0000000` makes your `main.c` survive an address-editor change without a source edit. Also — `Xil_DCacheDisable()` at startup is the fastest way to prove the AXI path works; you can re-enable the cache and add proper flush/invalidate once correctness is confirmed.

## XDC Timing Constraints

### Key Findings

- **`set_input_delay` / `set_output_delay` syntax** — both take `-clock <clk_name>` and a nanosecond value; positive delay means the data arrives that many ns *after* the clock edge at the FPGA pin, negative means it arrives *before*.
- **Internal BRAM has no I/O delay** — `set_input_delay` / `set_output_delay` apply only to FPGA I/O pins (physical ports). The AXI-BRAM path is entirely internal; use `set_multicycle_path` if BRAM read latency causes timing closure issues.
- **Clock groups for Zynq PS clocks** — the Zynq PS emits `pl_clk0` through `pl_clk3`; these are internally generated so Vivado knows them. However, if you derive a divided clock from `pl_clk0` in HDL, declare it with `create_generated_clock` so the timing engine tracks it.
- **`set_false_path` for reset** — PS-generated resets crossing to the PL are asynchronous; `set_false_path -from [get_pins */PS8_0/PORB]` prevents erroneous cross-domain timing analysis.
- **UART TX pin** — if your XDC drives the USB-UART TX pin, add: `set_output_delay -clock pl_clk0 0.0 [get_ports uart_txd]` to keep Vivado from treating it as an unconstrained path (which triggers a warning but not an error).

### Code Example

```xdc
# kv260_top.xdc — timing constraints for KV260 AXI-BRAM demo

# Primary PL clock from Zynq PS (100 MHz)
# pl_clk0 is already created by Vivado from the PS8 IP — no create_clock needed.

# UART TX output: no external timing requirement, just silence the warning
set_output_delay -clock [get_clocks -of_objects [get_pins */PS8_0/PLCLK[0]]] \
    0.0 [get_ports uart_txd]

# Multi-cycle path for BRAM read (1 extra cycle read latency)
set_multicycle_path -setup 2 \
    -from [get_cells -hierarchical -filter {NAME =~ *blk_mem_gen*}] \
    -to   [get_cells -hierarchical -filter {NAME =~ *bram_ctrl*}]
set_multicycle_path -hold  1 \
    -from [get_cells -hierarchical -filter {NAME =~ *blk_mem_gen*}] \
    -to   [get_cells -hierarchical -filter {NAME =~ *bram_ctrl*}]
```

### Relevance to Your Project

At 100 MHz (10 ns period), the AXI BRAM controller's registered read path is comfortable, but at 150–200 MHz you will see WNS violations. The multicycle path exception above buys you an extra cycle safely. Add it to your XDC now so it's in place when you push the clock higher.

## Kria KV260 / K26 SoM

### Key Findings

- **Boot modes**: K26 ships with QSPI32 as the default boot mode; for development, boot from SD (set SW1 on the carrier card), which loads the U-Boot / Linux stack. For bare-metal JTAG, remove the SD card so the PS drops to JTAG boot, then use Vitis/XSDB to download your ELF.
- **MIO allocation**: The K26 SoM pre-assigns MIO to UART0 (MIO 18/19), GEM (Ethernet), USB, I2C, and QSPI. The carrier card exposes UART1 on MIO 36/37 (Raspberry Pi header). Stick to MIO 18/19 for your USB-UART `xil_printf` output — that's what the KV260 USB-UART bridge routes.
- **EMIO for PL GPIO**: Any GPIO not listed in MIO (fan control, LEDs) is routed through the PL via EMIO. In the bare-metal BRAM demo you don't need EMIO, but it's the mechanism for carrier-card LEDs if you want visual pass/fail indicators.
- **PL power domain**: The KV260's PL runs at 1.8 V I/O on the PMODs and 3.3 V on the Raspberry Pi connector. Ensure your XDC `set_property IOSTANDARD` matches the carrier voltage for any physical I/O you add.
- **Fan control**: The cooling fan on the KV260 starter kit is controlled via an EMIO GPIO pin in the default bitstream. In a bare-metal design you must either replicate this or accept the fan running at max speed.

### Code Example

```tcl
# In create_bd.tcl: configure UART0 (MIO 18/19) for xil_printf output
set_property -dict [list \
    CONFIG.PSU__UART0__PERIPHERAL__ENABLE  1 \
    CONFIG.PSU__UART0__PERIPHERAL__IO      {MIO 18 .. 19} \
    CONFIG.PSU__UART0__BAUD_RATE           115200 \
] [get_bd_cells zynq_ultra_ps_e_0]
```

### Relevance to Your Project

Your demo uses USB-UART for `xil_printf` PASS/FAIL output. Confirming UART0 maps to MIO 18/19 in the PS configurator ensures the output reaches the USB bridge chip on the KV260 carrier. If you ever see blank terminal output at the right baud rate, check the MIO assignment first — a regenerated PS block sometimes resets it.

## AMD/Xilinx Tool Updates (2025.x)

### Key Findings

- **Vivado 2025.1 IP Release Notes** (AR 000037919): Covers all IP core changes without requiring a tool install. Key changes for AXI IP: the AXI BRAM Controller (v4.1) received timing closure improvements for UltraScale+ at >200 MHz.
- **AXI Interconnect deprecated** — in Vivado 2025.x example designs, `axi_interconnect` is replaced by `smartconnect` everywhere. The IP Catalog still creates it but emits a deprecation warning. New projects should use SmartConnect.
- **Vitis 2025.1 Unified IDE**: The IDE moved to an Eclipse Theia-based (web technology) shell; some keyboard shortcuts changed. The underlying BSP and platform concepts are unchanged from 2024.x.
- **Vivado 2025.2 highlights**: Updated AI-assisted DRC and constraint recommendations; improved incremental implementation that preserves more placed cells across netlist changes — useful for iterating on the BRAM address without full reimplementation.
- **Known issue — BD regeneration in 2025.1**: There is a known issue where `generate_target` on a BD with multiple AXI BRAM controllers can produce duplicate port names in the generated wrapper if ports are left unnamed. Workaround: explicitly name all ports in the BD script with `set_property name`.

### Code Example

```tcl
# Vivado 2025.x: explicitly name BRAM controller ports to avoid wrapper collision
# (workaround for known BD generation issue with multiple BRAM controllers)
set bram0 [get_bd_cells axi_bram_ctrl_0]
set bram1 [get_bd_cells axi_bram_ctrl_1]

set_property name bram0_ctrl $bram0
set_property name bram1_ctrl $bram1

# Rename the BRAM memory IPs too
set_property name blk_mem_bram0 [get_bd_cells blk_mem_gen_0]
set_property name blk_mem_bram1 [get_bd_cells blk_mem_gen_1]
```

### Relevance to Your Project

Your project uses two BRAM controllers (BRAM0 and BRAM2/BRAM1). The known naming-collision workaround directly applies — if you have seen mysterious "duplicate symbol" linker errors or strange `xparameters.h` values, regenerating the BD after applying explicit names should resolve it. Also consider migrating from `axi_interconnect` to `smartconnect` in `create_bd.tcl` now, before AMD removes the old IP entirely.
