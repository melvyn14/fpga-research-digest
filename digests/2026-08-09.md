# FPGA Research Digest - 2026-08-09

## Executive Summary

- **AXI-Lite AWREADY timing bug**: Xilinx's stock AXI-Lite slave template historically gates `AWREADY` on both `AWVALID` and `WVALID` simultaneously, which can stall the write address channel if data arrives first — verify your generated IP against PG078 v4.0+ which fixes this
- **Vivado 2025 AXI address-space limit**: Vivado 2025 introduced a regression where custom AXI peripheral address space is capped at 1 kB in the Address Editor — work around by setting `range` explicitly in TCL with `assign_bd_address -range 4K`
- **AXI SmartConnect deprecates AXI Interconnect**: The legacy AXI Interconnect IP is officially discontinued and will be removed in the next major Vivado release; migrate block designs to AXI SmartConnect now — it requires only one clock/reset pair and auto-negotiates AXI/AXI-Lite widths
- **Bare-metal runs at EL3**: Vitis standalone BSP executes at Exception Level 3 on Cortex-A53; non-secure AXI transactions (NS bit=0) are required for PL peripheral access in bare-metal, which is the default — no TrustZone configuration needed for your BRAM demo
- **Vivado 2025.1 IP change log** (Answer Record 000037919) lists AXI BRAM Controller, AXI SmartConnect, and Zynq UltraScale+ PS IP updates — review before regenerating output products to catch interface changes

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- All five AXI channels (AW, W, B, AR, R) use VALID/READY handshake; a transfer completes only when **both** are high on a rising clock edge — never combinatorially derive READY from VALID on the same channel (violates AXI spec)
- **Write ordering requirement**: both the Write Address channel (`AWVALID`/`AWREADY`) and Write Data channel (`WVALID`/`WREADY`) must complete handshakes before the slave sends the Write Response (`BVALID`) — they may complete in any order
- Xilinx's early AXI-Lite slave template gated `AWREADY` on `AWVALID & WVALID` together, effectively merging two independent channels — the fix is to accept them independently with separate state machines (see zipcpu.com "Easy AXI-Lite" article)
- For AXI-Lite (no bursts, no IDs): write response `BRESP` and read response `RRESP` should always be `2'b00` (OKAY) for well-behaved slaves; `2'b10` (SLVERR) signals an error the PS can optionally trap
- `RDATA` on holes in BRAM address space returns `0x00000000`; writes to holes are silently accepted with OKAY — useful for debugging: unexpected zeros in readback often indicate address misalignment, not bus errors

### Code Example

```vhdl
-- Minimal AXI-Lite write handshake accepting AW and W independently
process(S_AXI_ACLK)
begin
  if rising_edge(S_AXI_ACLK) then
    if S_AXI_ARESETN = '0' then
      aw_active <= '0';
      w_active  <= '0';
    else
      -- Accept write address independently
      if S_AXI_AWVALID = '1' and aw_active = '0' then
        aw_addr  <= S_AXI_AWADDR;
        aw_active <= '1';
      end if;
      -- Accept write data independently
      if S_AXI_WVALID = '1' and w_active = '0' then
        w_data   <= S_AXI_WDATA;
        w_strb   <= S_AXI_WSTRB;
        w_active <= '1';
      end if;
      -- Commit write only when both channels have completed
      if aw_active = '1' and w_active = '1' then
        mem(to_integer(unsigned(aw_addr(ADDR_BITS-1 downto 2)))) <= w_data;
        aw_active <= '0';
        w_active  <= '0';
      end if;
    end if;
  end if;
end process;

S_AXI_AWREADY <= not aw_active;
S_AXI_WREADY  <= not w_active;
S_AXI_BVALID  <= aw_active and w_active;  -- assert after both accepted
S_AXI_BRESP   <= "00";
```

### Relevance to Your Project

Your kv260-axi-bram-demo uses Xilinx Block Memory Generator (BMG) IP connected through AXI BRAM Controller at `0xA0000000` and `0xA0010000`. The AXI BRAM Controller (PG078) handles these handshake details internally, but understanding the protocol helps interpret ILA waveforms when your PS write patterns don't read back correctly. The independent AW/W acceptance pattern above is exactly what PG078 v4.0+ implements inside the BRAM controller.

## Vivado Block Design / IP Integrator

### Key Findings

- **Connection Automation** (`run_connection_automation`) connects clock, reset, and AXI interfaces based on IP metadata — always run it after adding each IP rather than after adding all IPs to catch interface mismatches early
- **Address Editor**: after `assign_bd_address`, verify each segment's offset and range match your expected PS memory map; in Vivado 2025 a known issue caps custom peripheral address range at 1 kB — use the TCL workaround below
- **Regenerate vs. Re-export**: modifying block design parameters requires "Validate Design" (`validate_bd_design`) then "Generate Output Products" before re-launching synthesis — skipping generate causes stale wrappers
- AXI SmartConnect replaces AXI Interconnect: SmartConnect requires only `aclk` + `aresetn` (one pair total) vs. per-port clocks in the legacy IP; it auto-adapts AXI4 ↔ AXI4-Lite at each port
- Use `get_bd_intf_nets` and `get_bd_intf_pins` in TCL to audit connections programmatically before running synthesis — catches dangling or wrongly routed AXI buses before a long synthesis run

### Code Example

```tcl
# Fix Vivado 2025 1kB address-range cap for custom AXI peripheral
# After running assign_bd_address, override the range:
set seg [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property range 4K    $seg
set_property offset 0xA0000000 $seg

set seg2 [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_1_Mem0}]
set_property range 4K    $seg2
set_property offset 0xA0010000 $seg2

# Validate and regenerate
validate_bd_design
generate_target all [get_files *.bd]
```

### Relevance to Your Project

Your `create_bd.tcl` sets BRAM0 at `0xA0000000` and BRAM1 at `0xA0010000`. The 2025 address-range regression could silently cap your accessible range to 1 kB — only 256 words — while your `main.c` write loop may target higher offsets. Run `get_property range $seg` after `assign_bd_address` to confirm the range is `4K` (0x1000) or larger, not `1K`.

## Vivado TCL Scripting

### Key Findings

- **Non-project mode** is faster for CI/automation: use `read_vhdl`, `read_xdc`, `synth_design`, `opt_design`, `place_design`, `route_design`, `write_bitstream` in sequence — no `.xpr` file created, no managed runs
- **Project mode export**: `File → Export → Export Block Design` generates a self-contained TCL that recreates the full BD — use this as a baseline then strip GUI-only commands for headless use
- In non-project mode, **output products must be generated manually** before synthesis: `generate_target all [get_files *.bd]` — forgetting this causes "no sources found" errors on first run
- `launch_runs impl_1 -to_step write_bitstream` is the project-mode equivalent of the non-project `write_bitstream` command — use `-jobs 8` to parallelize across CPU cores
- `wait_on_run synth_1` blocks the TCL interpreter until the run completes — essential for scripted flows where implementation depends on synthesis artifacts

### Code Example

```tcl
#!/usr/bin/env tclsh
# Non-project mode: full synthesis → bitstream for KV260 AXI-BRAM demo
# Usage: vivado -mode batch -source build.tcl

set part "xck26-sfvc784-2LV-c"   ;# K26 SoM part number

# Read sources
read_vhdl  [glob ../vhdl/*.vhd]
read_xdc   [glob ../xdc/*.xdc]

# Open and generate block design
open_bd_design  [glob ../bd/*.bd]
generate_target all [get_files *.bd]
make_wrapper -files [get_files *.bd] -top

read_vhdl [glob .srcs/sources_1/bd/*/hdl/*_wrapper.vhd]

# Synthesize
synth_design -top kv260_top -part $part -flatten_hierarchy rebuilt

# Implement
opt_design
place_design
phys_opt_design
route_design

# Write outputs
write_checkpoint  -force  output/post_route.dcp
write_bitstream   -force  output/kv260_top.bit
write_debug_probes -force output/kv260_top.ltx

puts "Build complete."
```

### Relevance to Your Project

Your repo's `create_bd.tcl` is the block-design creation script. Pairing it with a non-project build script like the one above means you can reproduce the full bitstream from a clean checkout with a single `vivado -mode batch -source build.tcl` — no GUI interaction required, and suitable for automated nightly builds or CI.

## Vitis Bare-Metal / Standalone

### Key Findings

- **Standalone BSP runs at EL3** on Cortex-A53; this means all memory is accessible (no MMU restrictions) and AXI transactions to PL are non-secure by default — exactly what `Xil_Out32`/`Xil_In32` need to write to `0xA0000000`
- **xil_printf** goes to UART0 or UART1 depending on the BSP `stdin`/`stdout` settings in `system.mss`; for KV260 UART1 (MIO36/MIO37) is the USB-UART path — confirm `STDOUT` is set to `psu_uart_1` in the standalone domain
- **Linker script** (`lscript.ld`) places `.text` and `.data` in DDR by default; if you want a fully BRAM-resident app (no DDR) you must manually reassign regions to your BRAM address range — but for the KV260 demo DDR is available and the default is fine
- The `BRAM Standalone driver` (from AMD Wiki) provides `XBram_WriteReg` / `XBram_ReadReg` wrappers as an alternative to raw `Xil_Out32` — useful if you need ECC error injection/correction later
- Vitis 2025.1 scripting tutorials (GitHub `Xilinx/Vitis-Tutorials` branch `2025.2`) cover `xsct` TCL scripting to automate application build and JTAG download without opening the GUI

### Code Example

```c
#include "xil_io.h"
#include "xil_printf.h"
#include "sleep.h"

#define BRAM0_BASE  0xA0000000UL
#define BRAM1_BASE  0xA0010000UL
#define BRAM_SIZE   0x1000U       /* 4 KB = 1024 x 32-bit words */

static int bram_test(u32 base, const char *name) {
    u32 pattern = 0xDEADBEEFUL;
    u32 errors  = 0;

    /* Write phase */
    for (u32 off = 0; off < BRAM_SIZE; off += 4) {
        Xil_Out32(base + off, pattern ^ off);
    }
    /* Memory barrier before readback */
    dsb();

    /* Read-back phase */
    for (u32 off = 0; off < BRAM_SIZE; off += 4) {
        u32 rd = Xil_In32(base + off);
        if (rd != (pattern ^ off)) {
            xil_printf("%s @ 0x%08X: expected 0x%08X got 0x%08X\r\n",
                       name, base + off, pattern ^ off, rd);
            errors++;
        }
    }
    return errors;
}

int main(void) {
    xil_printf("KV260 AXI-BRAM test starting\r\n");
    int e0 = bram_test(BRAM0_BASE, "BRAM0");
    int e1 = bram_test(BRAM1_BASE, "BRAM1");
    xil_printf("%s\r\n", (e0 + e1 == 0) ? "PASS" : "FAIL");
    return 0;
}
```

### Relevance to Your Project

This is a drop-in enhancement for your `main.c`. The `dsb()` data synchronization barrier between write and read phases ensures Cortex-A53's store buffer is flushed before readback — without it, you may read cached values rather than confirming the AXI transaction reached the BRAM. The varying pattern (`pattern ^ off`) catches address aliasing bugs that a fixed pattern would miss.

## XDC Timing Constraints

### Key Findings

- The K26 SoM ships with a pre-packaged XDC file mapping SoM connector pins to MPSoC ball assignments — always use the official SoM XDC as your base and add carrier-card-specific constraints on top, never start from scratch
- **PS-derived clocks** (`pl_clk0` etc.) are automatically constrained by the Zynq UltraScale+ PS IP — you do not need `create_clock` for them; adding a duplicate `create_clock` on `pl_clk0` causes a `set_clock_groups` conflict
- `set_clock_groups -asynchronous` is the correct constraint when your design has multiple unrelated clock domains (e.g., PL fabric clock vs. a free-running oscillator on the carrier card) — using `-logically_exclusive` when clocks share no path causes DRC warnings but not errors
- `set_input_delay` and `set_output_delay` are required for any external IOs (PMOD, GPIO) but are **not** needed for PS↔PL AXI connections — the PS IP handles its own interface timing internally
- For a minimal AXI-BRAM demo with no external IOs, your only required XDC content is the pin location constraints and I/O standard assignments for any board-specific signals (UART, LEDs)

### Code Example

```tcl
# kv260_demo.xdc - Minimal constraints for AXI-BRAM bare-metal demo
# PS clocks are auto-constrained by the Zynq UltraScale+ PS IP block
# No create_clock needed for pl_clk0

# Status LED on KV260 carrier card (example - verify pin against KV260 schematic)
set_property PACKAGE_PIN   A12     [get_ports {led[0]}]
set_property IOSTANDARD    LVCMOS33 [get_ports {led[0]}]

# Asynchronous clock group example (only needed if you add a second fabric clock)
# set_clock_groups -asynchronous \
#   -group [get_clocks clk_pl_0] \
#   -group [get_clocks your_second_clock]

# False path on reset synchronizer (if using a PL reset synchronizer)
set_false_path -from [get_ports sys_rst_n] -to [all_registers]
```

### Relevance to Your Project

Your kv260-axi-bram-demo is purely PS↔PL AXI with no external timing interfaces, so timing constraints are minimal. The most common issue in this type of project is accidentally adding a `create_clock` on `pl_clk0` (which the PS IP already declares), causing a "clock defined multiple times" critical warning that prevents bitstream generation. Use `report_clocks` after `synth_design` to verify the clock topology before adding any `set_clock_groups` calls.

## Kria KV260 / K26 SoM

### Key Findings

- **Boot modes**: KV260 ships with QSPI32 boot mode (MODE[3:0] = 0010); for bare-metal JTAG debug change to JTAG mode by grounding MODE[1:0] or using the SW4 dip switch on the carrier card — no QSPI erase needed for JTAG-only boot
- **MIO allocation**: USB-UART is on UART1 (MIO36/MIO37) at 115200 baud by default; MIO26-MIO51 are reserved for SD card, UART, I2C — do not reassign these in the PS configuration or you lose the debug console
- **EMIO fan control**: the default K26 starter-kit bitstream exposes a fan PWM signal over EMIO; your custom bitstream must implement the same EMIO or the carrier card fan may stall — check `ps_fan_en` in the PS IP EMIO configuration tab
- **Power domains**: VCCO for sideband signals is 1.8 V; PL HP banks can be configured for 1.8 V or 3.3 V — KV260 carrier card uses 3.3 V on the PMOD header (HP bank 45), so set `IOSTANDARD LVCMOS33` for those pins
- Bare-metal JTAG download: use `Xilinx hw_server` + `xsct` or Vivado Hardware Manager; connect to the K26 JTAG TAP via the micro-USB JTAG port on the KV260 carrier card (separate from the USB-UART port)

### Code Example

```tcl
# xsct script: download and run bare-metal ELF over JTAG on KV260 Cortex-A53 core 0
connect
targets -set -filter {name =~ "APU*"}
source $::env(XILINX_VITIS)/scripts/vitis/util/zynqmp_utils.tcl
psu_init            ;# Initialize PS (clocks, DDR, MIO)

targets -set -filter {name =~ "APU Core 0"}
rst -processor
dow  build/kv260_axi_bram.elf
con

# Monitor UART1 output separately with:
#   screen /dev/ttyUSB1 115200
puts "ELF loaded and running. Check UART1 at 115200 baud."
```

### Relevance to Your Project

Your project writes to BRAM over AXI and prints PASS/FAIL over USB-UART. The `psu_init` call in the xsct script is critical — without PS initialization, `pl_clk0` is not running and your AXI fabric is unclocked, meaning every `Xil_Out32` call will hang indefinitely waiting for `BREADY`/`RVALID`. Always run `psu_init` before downloading your ELF when using JTAG without a prior bootloader.

## AMD/Xilinx Tool Updates (Vivado/Vitis 2025.x)

### Key Findings

- **Vivado 2025.1 IP change log** (Answer Record 000037919) available on AMD Adaptive Support — covers AXI BRAM Controller, AXI SmartConnect, Zynq UltraScale+ PS, and all other IPs; review before upgrading existing block designs
- **Vitis 2025.1 release notes** (UG1742, released 2025-07-08) document new standalone BSP features and updated `xsct` scripting capabilities for embedded flows
- **"Hardware Design Fast Iteration"** (XD101): a Vitis 2025.1 tutorial demonstrating the new "Export to Vivado" round-trip workflow — allows iterating on PL hardware from Vitis without re-running the full Vivado IP Integrator flow
- **AXI Interconnect removal warning**: AMD has officially announced the legacy AXI Interconnect IP will be removed in an upcoming major release — any block design using it should be migrated to AXI SmartConnect; IP Integrator shows a warning banner in 2025.1 for designs still using the old IP
- **Vivado 2025 address-space regression**: reported on Digilent forums — custom AXI peripheral `range` field resets to 1K in the Address Editor after certain BD operations; workaround is to always set range explicitly via TCL after `assign_bd_address`

### Code Example

```tcl
# Migrate legacy AXI Interconnect to AXI SmartConnect in an existing BD
# Run in Vivado TCL console with the BD open

# Step 1: identify old interconnect instances
set old_ics [get_bd_cells -filter {VLNV =~ *axi_interconnect*}]
puts "Found [llength $old_ics] AXI Interconnect instance(s): $old_ics"

# Step 2: For each, note connected masters/slaves then replace
# (Manual reconnection required - there is no automated migration script)
# AMD recommendation: delete and re-add as SmartConnect, then re-run
# run_connection_automation to restore connections.

# Step 3: Add replacement SmartConnect
create_bd_cell -type ip -vlnv xilinx.com:ip:smartconnect:1.0 smartconnect_0
set_property CONFIG.NUM_SI {1} [get_bd_cells smartconnect_0]
set_property CONFIG.NUM_MI {2} [get_bd_cells smartconnect_0]

# Step 4: Connect PS AXI HP port → SmartConnect → BRAM controllers
connect_bd_intf_net \
  [get_bd_intf_pins zynq_ultra_ps_e_0/M_AXI_HPM0_FPD] \
  [get_bd_intf_pins smartconnect_0/S00_AXI]

puts "SmartConnect added. Reconnect slave ports manually."
```

### Relevance to Your Project

If your `create_bd.tcl` uses the legacy AXI Interconnect, you will receive deprecation warnings in Vivado 2025.1 and the IP may be absent entirely in the next major release. Migrating to AXI SmartConnect now simplifies your block design (one clock connection instead of per-port clocks) and ensures forward compatibility. The address-space regression is also directly relevant — test with `get_property range` on each BRAM segment after running your TCL script.
