## Executive Summary

- **AXI BRAM Controller collision detection is absent** — back-to-back `Xil_Out32()` / `Xil_In32()` calls to the same BRAM address in `main.c` are not serialized by the PG078 controller; always insert a memory barrier (`__asm__ volatile("dsb sy" ::: "memory")`) between the final write and the first readback to prevent the Cortex-A53 store buffer from racing the AXI-Lite bus.
- **`apply_bd_automation` is the idiomatic TCL call for BRAM address assignment** — running it without the subsequent `assign_bd_address` to fix the offset to `0xA0000000` / `0xA0010000` leaves the address auto-assigned and may differ across Vivado patch releases; always lock addresses explicitly after automation in `create_bd.tcl`.
- **Vivado 2025.2 is the newest stable release** (released 2025-11-20 per AMD release notes) — if you are still on 2025.1 it is worth checking the UG973 delta for BRAM/block-design fixes before upgrading, as selective IP upgrade is not supported for Zynq UltraScale+ MPSoC blocks (full block regeneration required).
- **Vitis 2025.1 added VHDL 2019 simulation support** — if `kv260_top.vhd` uses any VHDL-2008/2019 constructs, verify the simulation set uses `--2019` and that the same standard is selected in Vivado's simulation settings to avoid false elaboration errors.
- **KV260 USB-UART is wired to PS UART 1 (`psu_uart_1`)** — the default BSP `stdout` in Vitis is `psu_uart_0`; if `xil_printf` PASS/FAIL messages never appear, verifying the BSP stdout setting is the fastest first debug step.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- **VALID must never depend on READY** — this is the most cited AXI bug in formal-verification literature. A source that ties `AWVALID` to `WREADY` (or vice versa) can deadlock. For the KV260 project, the Zynq PS AXI master is the initiator, so this rule applies to any custom VHDL slave you add downstream.
- **Vivado's generated AXI-Lite slave example contained reset-handling and RVALID/RREADY ordering bugs** in releases up to 2020.2 (ZipCPU analysis). If `kv260_top.vhd` includes a hand-written or Vivado-template-derived AXI-Lite slave wrapper, compare its `RVALID`/`RREADY` sequencing against the corrected `demoaxilite.v` reference at zipcpu.com.
- **AXI-Lite write requires three channel completions** (AW+W in any relative order, then B acknowledged) — a bare-metal write that never checks the write-response channel leaves the AXI slave in an undefined state if `BVALID` is never consumed. The `XBRAM` driver from Xilinx handles this internally, but hand-rolled pointer writes bypass it.
- **`RVALID` must not go high until `ARVALID && ARREADY` has completed** — a subtle timing rule that Vivado's older template violated; check with ILA or formal if you see sporadic read mismatches.
- **AXI-Stream `TLAST`**: even if your project is AXI-Lite only today, any DMA engine added later (e.g., AXI DMA IP) uses AXI-Stream channels internally; a producer that never asserts `TLAST` will silently stall an AXI-Stream FIFO configured in packet mode.

### Code Example

```c
/* Correct write-then-readback pattern on Cortex-A53 bare-metal */
#include "xil_io.h"
#include <stdint.h>

#define BRAM0_BASE 0xA0000000UL
#define BRAM_WORD_OFFSET(n) ((n) * 4U)

static void bram_write_verify(uint32_t base, uint32_t offset_words,
                               uint32_t pattern)
{
    Xil_Out32(base + BRAM_WORD_OFFSET(offset_words), pattern);
    /* DSB: drain Cortex-A53 store buffer before AXI read-back */
    __asm__ volatile("dsb sy" ::: "memory");
    uint32_t rb = Xil_In32(base + BRAM_WORD_OFFSET(offset_words));
    if (rb != pattern)
        xil_printf("FAIL @ 0x%08lX: wrote 0x%08lX, read 0x%08lX\r\n",
                   base + BRAM_WORD_OFFSET(offset_words), pattern, rb);
    else
        xil_printf("PASS @ 0x%08lX = 0x%08lX\r\n",
                   base + BRAM_WORD_OFFSET(offset_words), pattern);
}
```

### Relevance to Your Project

The `main.c` write loop for BRAM0 and BRAM2 almost certainly uses `Xil_Out32`/`Xil_In32`. Adding the `dsb sy` barrier between write and readback is the single highest-impact correctness fix for bare-metal AXI-Lite BRAM demos on Cortex-A53. Without it the CPU store buffer can deliver the write to the BRAM over AXI while the subsequent `Xil_In32` is already in-flight from cache, causing a race that shows up as random FAIL results at high optimization levels.

## Vivado Block Design / IP Integrator

### Key Findings

- **Connection Automation (2025.2 UG994)** — the "Run Connection Automation" banner auto-wires AXI master ports to slaves and can assign board constraints when a target board (KV260) is set. It calls `apply_bd_automation` internally and is recommended over manual wiring for BRAM controller connections.
- **Address Editor appears only when a bus-master IP is present** — if the Zynq UltraScale+ PS block is not yet configured as a bus master (`M_AXI_HPM0_LPD` or `M_AXI_HPM0_FPD` enabled), the Address Editor tab stays hidden and addresses cannot be assigned; this is a common confusion for first-time block designs.
- **`Assign All` auto-assigns addresses but may overlap** — the 2025.2 UG1165 tutorial notes that two ports with overlapping auto-assigned ranges need manual correction in the Address Editor. For BRAM0/BRAM2 at fixed offsets, explicit `assign_bd_address` in TCL is safer.
- **Selective IP upgrade is NOT supported** for `zynq_ultra_ps_e` and `axi_interconnect` blocks — when upgrading from 2025.1 → 2025.2 (or any major version), the block design must be fully regenerated, not selectively updated.
- **`validate_bd_design` before `make_wrapper`** — skipping validation can produce a wrapper that is out of sync with the block design; Vivado will not always raise an error at wrapper generation time but will fail silently at synthesis.

### Code Example

```tcl
# Explicit address assignment after apply_bd_automation
# (safer than relying on auto-assign in create_bd.tcl)
apply_bd_automation -rule xilinx.com:bd_rule:axi4 \
    -config {Master "/zynq_ultra_ps_e_0/M_AXI_HPM0_LPD"} \
    [get_bd_intf_pins axi_bram_ctrl_0/S_AXI]

apply_bd_automation -rule xilinx.com:bd_rule:axi4 \
    -config {Master "/zynq_ultra_ps_e_0/M_AXI_HPM0_LPD"} \
    [get_bd_intf_pins axi_bram_ctrl_1/S_AXI]

# Lock addresses to known offsets after automation
set_property offset 0xA0000000 \
    [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property range  64K \
    [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]

set_property offset 0xA0010000 \
    [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_1_Mem0}]
set_property range  64K \
    [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_1_Mem0}]

validate_bd_design
save_bd_design
```

### Relevance to Your Project

`create_bd.tcl` drives the block design that maps BRAM0 to `0xA0000000` and BRAM2 to `0xA0010000`. The pattern above ensures those addresses are pinned after each re-run, preventing Vivado from auto-assigning a different base on a tool upgrade or when the design is opened on a machine with a different Vivado patch version.

## Vivado TCL Scripting

### Key Findings

- **Non-project mode** (`vivado -mode batch -source script.tcl`) creates no on-disk project — it is entirely in-memory and exits when the script completes. This is the recommended CI/batch flow for reproducible builds.
- **Explicit sequence required** — in non-project mode nothing happens by default; you must call `read_vhdl`, `read_xdc`, `synth_design`, `opt_design`, `place_design`, `route_design`, `write_bitstream` explicitly.
- **Checkpoints are the only persistence** — `write_checkpoint` after each major step (post-synth, post-place, post-route) is the only way to resume a failed non-project run without restarting; `read_checkpoint` loads a prior checkpoint.
- **`open_project` / `open_bd_design` differ between modes** — in non-project mode use `open_checkpoint` on a post-synthesis DCP or `read_bd` on a `.bd` file, not `open_project`.
- **`apply_bd_automation` caveat** — AMD recommends running `apply_bd_automation` from the Vivado IDE rather than from pure Tcl scripts when possible, because the rule engine relies on board-awareness metadata that is richer in an interactive session.

### Code Example

```tcl
#!/usr/bin/env tclsh
# Non-project mode batch build: RTL to bitstream
# Run: vivado -mode batch -source build_kv260.tcl

read_vhdl  ../vhdl/kv260_top.vhd
read_xdc   ../xdc/kv260_top.xdc

# Synthesize targeting K26 (xck26)
synth_design -top kv260_top -part xck26-sfvc784-2LV-c
write_checkpoint -force post_synth.dcp
report_timing_summary -file reports/timing_synth.rpt

opt_design
place_design
write_checkpoint -force post_place.dcp

route_design
write_checkpoint -force post_route.dcp
report_timing_summary -file reports/timing_route.rpt

write_bitstream -force output/kv260_top.bit
```

### Relevance to Your Project

The existing `create_bd.tcl` runs in project mode (via `open_project`). For CI use — automating bitstream generation from a clean checkout — a thin non-project wrapper that calls `create_bd.tcl` for block design creation then proceeds to `synth_design` / `write_bitstream` avoids stale `.xpr` state and makes the build fully reproducible without committing Vivado project files.

## Vitis Bare-Metal / Standalone

### Key Findings

- **`xil_printf` is a lightweight, no-heap printf** — it supports `%d`, `%x`, `%s`, `%c`, `%l`, `%u` but not floating-point; using `%f` silently outputs garbage. For PASS/FAIL status messages this is not an issue, but be aware if adding percentage or float diagnostics later.
- **Vitis 2025.1 introduced the System Device Tree (SDT) flow** for new BSP generation — the SDT flow changes how `lscript.ld` is generated and may require re-exporting the XSA from Vivado if upgrading a 2024.x project.
- **Default `stdout` is `psu_uart_0`** — the KV260 carrier's USB-UART (Silabs CP2102N) is wired to PS UART **1** (`psu_uart_1`, MIO 36/37); verify BSP `stdin`/`stdout` is set to `psu_uart_1` in `vitis-comp.json` before debugging a "no output" symptom.
- **`Xil_DCacheFlushRange` before DMA or AXI reads** — if data cache is enabled (non-default for bare-metal but enabled by some BSP presets), a cache flush is required before reading BRAM data back via AXI to avoid seeing stale cache lines instead of AXI bus data.
- **Interrupt controller (GIC) for Zynq UltraScale+** uses `XScuGic` driver — if expanding the demo to handle BRAM-write-complete interrupts from PL, `XScuGic_Connect` and `XScuGic_Enable` are the two non-obvious calls; GIC distributor must be enabled before per-interrupt enable calls.

### Code Example

```c
/* BSP stdout check and minimal UART init for KV260 USB-UART (UART1) */
#include "xparameters.h"
#include "xuartps.h"
#include "xil_printf.h"

/* In Vitis, verify vitis-comp.json has:
 *   "stdin":  "psu_uart_1",
 *   "stdout": "psu_uart_1"
 * OR configure UART1 manually: */
static void init_uart1(void)
{
    XUartPs_Config *cfg = XUartPs_LookupConfig(XPAR_PSU_UART_1_DEVICE_ID);
    XUartPs uart1;
    XUartPs_CfgInitialize(&uart1, cfg, cfg->BaseAddress);
    XUartPs_SetBaudRate(&uart1, 115200);
}

int main(void)
{
    init_uart1();
    xil_printf("KV260 AXI-BRAM demo starting...\r\n");
    /* ... write/readback loop ... */
    return 0;
}
```

### Relevance to Your Project

The PASS/FAIL output in `main.c` relies on `xil_printf` reaching the USB-UART terminal. The most common failure mode — no output despite correct hardware — is the UART0 vs UART1 mismatch. The SDT note is relevant if you plan to upgrade from 2025.1 to 2025.2 Vitis, as BSP regeneration may be required.

## XDC Timing Constraints

### Key Findings

- **`set_input_delay` / `set_output_delay` model delays outside the FPGA** — Vivado's timing engine only sees logic inside the device; these commands tell it what delay is present on the PCB/connector so the tool can compute setup/hold slack correctly.
- **For AXI-only designs (PS master, no PL I/O ports)**, `set_input_delay` / `set_output_delay` are not required at the top-level design I/O because the AXI interface between the PS and PL is an internal path, not an external pin. The XDC file for `kv260_top.vhd` mainly needs a `create_clock` for any free-running PL clock and `set_clock_groups` for async clock domains.
- **Kria KV260 reference XDC** — AMD provides a board-specific XDC in the board files installed with Vivado (under `<Vivado_install>/data/boards/board_files/kv260`); these include the `pl_clk0` definition and the UART/status-LED pin assignments.
- **`-add_delay` stacks multiple I/O constraints** on one port (e.g., DDR data with both setup and hold at different clock edges) — not needed for a simple AXI-BRAM design but required if you add external memory or high-speed I/O.
- **`set_clock_groups -async`** is mandatory when the PS `pl_clk0` and any other PL clocks are not related — omitting it causes false timing paths between unrelated clock domains that inflate hold-violation counts.

### Code Example

```tcl
# Minimal XDC for KV260 AXI-BRAM demo (kv260_top.xdc)
# No external I/O delay constraints needed for a PS-only AXI design.

# 1) PL clock from PS (100 MHz typical for HPM0_LPD on K26)
#    The board-files XDC already defines this; include it only if
#    using a bare project without board-files.
# create_clock -period 10.000 -name pl_clk0 [get_ports pl_clk0]

# 2) Async clock group: prevent false timing paths between pl_clk0
#    and any secondary PL clock (e.g., pl_clk1 at 200 MHz)
set_clock_groups -asynchronous \
    -group [get_clocks pl_clk0] \
    -group [get_clocks pl_clk1]

# 3) Status LED output (no PCB delay model needed; relax to false path)
set_false_path -to [get_ports led_*]

# 4) False path on async reset (if used)
set_false_path -from [get_ports aresetn]
```

### Relevance to Your Project

For the current AXI-BRAM demo there are no external high-speed I/O ports, so `set_input_delay` / `set_output_delay` are not needed. The critical constraints are the clock definition (from PS board files or manual `create_clock`) and `set_clock_groups -async` if more than one PL clock is used. Missing the clock-groups constraint is the most common cause of inflated timing-violation reports on otherwise clean designs.

## Kria KV260 / K26 SoM

### Key Findings

- **K26 MIO banks** — three MIO banks (0–2). Bank 0 is used by the SOM for onboard peripherals (QSPI, eMMC, etc.); banks 1 and 2 are exposed through the SOM connector and can be assigned by the carrier. All MIO banks are powered at 1.8 V from the SOM.
- **Default boot mode is QSPI32** — the KV260 ships with boot firmware in QSPI NOR flash. For a bare-metal demo, the simplest path is to boot from SD card (set via the board DIP switch to SD boot mode) or JTAG-download via Vitis debugger without touching the QSPI image.
- **`PWRGD_PL_M2C`** gates PL power — the PL fabric (and therefore both AXI BRAM controllers) is not powered until `PWRGD_PL_M2C` is asserted by the carrier card. In bare-metal, the PS startup sequence waits for this automatically, but it is worth knowing when debugging very early-boot hangs.
- **SOM connector `som_240_1` vs `som_240_2`** — `som_240_1` is shared with K24 (control/status, MIO, PS-GTR, subset of HPIO/HDIO + SOM power); `som_240_2` is K26-only (additional HPIO/HDIO, GTH transceivers). The KV260 carrier routes HDMI, MIPI, and PCIe through `som_240_2`.
- **UART1 ↔ USB-UART bridge** — the KV260 carrier uses a CP2102N USB-UART bridge wired to PS UART1 (MIO 36/37). UART0 (MIO 18/19) is exposed as an RS232-level header, not USB.

### Code Example

```tcl
# KV260 platform boot mode check via JTAG / Vitis system debugger
# (Tcl console in Vitis or XSCT)

# Connect to KV260 target
connect
targets -set -filter {name =~ "PSU"}

# Read BOOT_MODE register (CRL_APB.BOOT_MODE_USER at 0xFF5E0200)
set boot_mode [mrd -value 0xFF5E0200]
switch [expr {$boot_mode & 0xF}] {
    0 { puts "JTAG boot" }
    1 { puts "QSPI32 boot (default KV260)" }
    5 { puts "SD0/eMMC boot" }
    6 { puts "SD1 (microSD) boot" }
    default { puts "Other boot mode: $boot_mode" }
}
```

### Relevance to Your Project

For the AXI-BRAM demo, the most practical KV260-specific detail is the JTAG/SD boot path and the UART1 wiring. When iterating on `main.c`, the fastest workflow is JTAG boot (no SD card flashing) with the Vitis debugger, which also gives you the XSCT console for direct BRAM memory inspection (`mrd 0xA0000000`) without running application code.

## AMD/Xilinx Tool Updates (Vivado/Vitis 2025.x)

### Key Findings

- **Vivado 2025.2 released 2025-11-20** — the newest stable release at the time of this digest. Delta from 2025.1 includes block design fixes; check UG973 2025.2 release notes and AMD Answer Records before upgrading a working 2025.1 project.
- **Vivado 2025.1 highlights**: added VHDL 2019 simulation constructs; Spartan UltraScale+ XCSU10/25/35P moved to production; `report_dfx_summary` GUI support added; a 2025.1.1 point release also exists.
- **Vitis 2025.1 highlights**: new Vitis Server backend for the IDE; expanded DSP library and AI Engine APIs; initial C++17 support (Clang 16) in Vitis HLS; System Device Tree (SDT) flow for BSP generation replaces the older `hsi` flow for new projects.
- **`zynq_ultra_ps_e` and `axi_interconnect` selective upgrade not supported** — when migrating a block design from 2025.1 to 2025.2, these two IP blocks require full regeneration; running "Upgrade All" on the IP catalog will trigger a full block design re-export.
- **Red Hat 9.2/9.3 and Ubuntu 22.04.2 LTS support ending after 2025.1** — if your build host runs one of these, plan the OS upgrade alongside the Vivado upgrade.
- **AMD Answer Record search** — the definitive source for version-specific bugs is `adaptivesupport.amd.com`; filter by "Vivado" and "2025.1" or "2025.2" with keyword "BRAM" or "block design" for the most relevant issues.

### Code Example

```vhdl
-- VHDL 2019 feature now supported in Vivado 2025.1 simulation:
-- Conditional expressions in concurrent signal assignments
-- (synthesizable subset; check tool support for specific constructs)

library ieee;
use ieee.std_logic_1164.all;

entity mux2 is
    port (
        sel  : in  std_logic;
        a, b : in  std_logic_vector(31 downto 0);
        y    : out std_logic_vector(31 downto 0)
    );
end entity;

architecture rtl of mux2 is
begin
    -- VHDL 2008+ conditional signal assignment (supported in Vivado synthesis)
    y <= a when sel = '1' else b;
end architecture;

-- To enable VHDL 2019 in simulation, set in Vivado:
--   Simulation Settings > Simulator Language > VHDL 2019
-- Or in TCL:
--   set_property VHDL_VERSION vhdl_2k19 [get_filesets sim_1]
```

### Relevance to Your Project

If `kv260_top.vhd` uses any VHDL-2008 constructs (generics with unconstrained types, `protected` types, or `std_logic_vector` aggregate returns), upgrading to Vivado 2025.1+ will enable VHDL-2019 simulation mode — set the file property explicitly to avoid ambiguous version detection. The 2025.2 release is now available; for a 2025.1 project, the main question before upgrading is whether the block design containing `axi_bram_ctrl` and `zynq_ultra_ps_e` needs to be regenerated (answer: yes, run "Upgrade All IP" and re-export XSA to Vitis).
