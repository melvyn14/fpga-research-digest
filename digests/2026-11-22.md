# FPGA Research Digest - 2026-11-22

## Executive Summary

- **AXI-Lite handshake bug**: Vivado's example AXI-Lite slave has a known flaw where it can accept multiple write requests while only returning a single response — always simulate or formally verify custom slaves before integrating with the KV260 PS master.
- **BRAM address shift**: The AXI BRAM Controller outputs byte addresses; the Block Memory Generator expects word addresses. Bits [1:0] must be stripped and the address right-shifted by 2 on the BRAM side — a silent mismatch that causes pattern reads to return wrong data.
- **Non-project TCL flow**: For the `create_bd.tcl` automation script, use `open_bd_design` / `validate_bd_design` / `generate_target all` after each structural change; non-project mode skips all auto-regen, so missing this step leaves stale netlists.
- **Vivado/Vitis 2025.2 is now current**: 2025.1 is no longer the latest release (2025.2 released 2025-11-20). Key 2025.1 → 2025.2 migration consideration: standalone BSP projects must migrate through 2024.2 before upgrading.
- **Kria boot firmware is QSPI-locked**: The KV260 boot mode is factory-set to QSPI32 and the QSPI firmware is read-only; for bare-metal AXI-BRAM demos you load your bitstream+elf through the fixed Linux boot path or JTAG — not by modifying QSPI.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- **Handshake invariant**: Once `xVALID` is asserted, the sender must hold `xVALID` and all payload signals stable until `xREADY` is seen; dropping `xVALID` early is a protocol violation.
- **Xilinx example slave bug**: Formal verification (ZipCPU) revealed that the Vivado-bundled AXI-Lite slave demo (through at least 2018.3) could accept up to 7 pending transactions while only sending a single response — still worth auditing in later versions.
- **Write response stall**: The most common crash mode is a slave that doesn't deassert `WREADY`/`AWREADY` when its write-response (`BVALID`/`BREADY`) channel is backpressured, causing invisible dropped transactions.
- **Read/write mutual exclusion**: AXI-Lite slaves that share internal state between read and write paths must explicitly gate the two channels; simultaneous read + write to overlapping registers is undefined in AXI-Lite.
- **AXI4-Stream TLAST**: Never update `TLAST` while the channel is stalled (`TVALID=1`, `TREADY=0`); the fix is to gate output-register writes on `!TVALID || TREADY`.
- **TREADY pre-assertion**: Drive `TREADY` combinationally high by default (or pre-assert it one cycle early) to cut pipeline latency to zero on the happy path.

### Code Example

```vhdl
-- Minimal AXI-Lite slave: safe BREADY/RVALID decoupling pattern
-- Prevents simultaneous read+write corruption in single-port registers

process(clk)
begin
  if rising_edge(clk) then
    if rst = '1' then
      s_axi_bvalid <= '0';
      s_axi_rvalid <= '0';
      s_axi_awready <= '0';
      s_axi_wready  <= '0';
      s_axi_arready <= '0';
    else
      -- Write address accept: only when write-response channel is clear
      s_axi_awready <= not s_axi_bvalid;
      s_axi_wready  <= not s_axi_bvalid;

      if s_axi_awvalid and s_axi_wvalid and not s_axi_bvalid then
        -- latch address and data, issue response next cycle
        reg_array(to_integer(unsigned(s_axi_awaddr(ADDR_WIDTH-1 downto 2))))
            <= s_axi_wdata;
        s_axi_bvalid <= '1';
        s_axi_bresp  <= "00";
      end if;

      if s_axi_bready and s_axi_bvalid then
        s_axi_bvalid <= '0';        -- clear only after master acks
      end if;

      -- Read: separate from write path entirely
      s_axi_arready <= '1';
      if s_axi_arvalid then
        s_axi_rdata  <= reg_array(
            to_integer(unsigned(s_axi_araddr(ADDR_WIDTH-1 downto 2))));
        s_axi_rvalid <= '1';
        s_axi_rresp  <= "00";
      end if;
      if s_axi_rready and s_axi_rvalid then
        s_axi_rvalid <= '0';
      end if;
    end if;
  end if;
end process;
```

### Relevance to Your Project

Your `kv260_top.vhd` connects the Zynq PS M_AXI_HPM0 master to two BRAM controllers at `0xA0000000` and `0xA0010000`. The write-response stall pattern above is exactly what happens when `main.c` issues back-to-back writes faster than the BRAM controller acknowledges — the second write silently drops. Add a `Xil_Out32` read-back after each write (or use the `BRESP` polling pattern) to detect dropped writes early.

## Vivado Block Design / IP Integrator

### Key Findings

- **Connection Automation**: Right-clicking the M_AXI_HPM0 port and selecting "Run Connection Automation" auto-wires AXI Interconnect, SmartConnect, and address segments — but it also sets default clock/reset connections that may not match your design; always inspect the generated connections in the Address Editor.
- **Address Editor segment sizes**: The default segment size for an AXI BRAM Controller is 4 KB; for a 2 KB BRAM the range must match exactly. Mismatch causes bus errors that are silent at synthesis — the PS just gets an AXI slave error response.
- **Re-generate targets after any IP change**: In both project and non-project mode, changing any IP property (data width, depth, latency) requires `generate_target all [get_files *.bd]` before synthesis or stale netlist artifacts will be used.
- **BD upgrade in non-project mode**: Use `upgrade_ip [get_ips *]` after opening a `.bd` from an older tool version; skipping this step causes "IP is locked" synthesis errors.
- **validate_bd_design**: Always call this before `generate_target`; it catches unconnected ports, address overlaps, and clock-domain mismatches as errors rather than silent warnings.

### Code Example

```tcl
# Non-project mode: safe BD regeneration sequence
read_bd ./bd/kv260_bd.bd
set_property target_language VHDL [current_project]

# Upgrade any stale IP first
upgrade_ip [get_ips *]

# Validate catches address conflicts, unconnected ports, CDC issues
set validate_result [validate_bd_design]
if {$validate_result != 0} {
    puts "ERROR: BD validation failed"
    exit 1
}

# Generate HDL wrapper and all output products
generate_target all [get_files kv260_bd.bd]
make_wrapper -files [get_files kv260_bd.bd] -top
read_vhdl -library xil_defaultlib \
    ./kv260_bd.gen/sources_1/bd/kv260_bd/hdl/kv260_bd_wrapper.vhd
```

### Relevance to Your Project

The `create_bd.tcl` script in your repo creates the block design programmatically. If the BRAM depth or width is ever changed (e.g., expanding BRAM0 for larger test patterns), the `generate_target all` sequence above must run before `synth_design`; otherwise Vivado synthesizes against the old BRAM stub.

## Vivado TCL Scripting

### Key Findings

- **Batch mode invocation**: `vivado -mode batch -source script.tcl` runs and exits; `-mode tcl` drops into an interactive prompt after the script finishes — use `batch` for CI/automation.
- **Non-project flow commands**: The full non-project pipeline is `read_vhdl` → `read_xdc` → `synth_design` → `opt_design` → `place_design` → `route_design` → `write_bitstream`. There is no `impl_design` command; `opt_design + place_design + route_design` replaces it.
- **Project mode export**: After GUI-driven changes, use `File → Project → Write Tcl` (or `write_project_tcl`) to export a reproducible script. This captures all source file additions, IP customizations, and run settings.
- **IP Tcl scripting**: `write_ip_tcl` exports individual RTL IP customizations as a standalone script; use this to version-control IP settings without committing large `.xci` files.
- **Error handling**: Wrap critical commands in `catch` blocks; `synth_design` returns non-zero on critical warnings that become errors — a bare call with no error check will silently produce a corrupted netlist.

### Code Example

```tcl
# Full non-project batch build for kv260 AXI-BRAM demo
set part "xck26-sfvc784-2LV-c"
set outputDir "./output"
file mkdir $outputDir

read_vhdl -library xil_defaultlib [glob ./vhdl/*.vhd]
read_vhdl -library xil_defaultlib \
    ./kv260_bd.gen/sources_1/bd/kv260_bd/hdl/kv260_bd_wrapper.vhd
read_xdc ./constraints/kv260_top.xdc

# Synthesis
set rc [catch {
    synth_design -top kv260_top -part $part -flatten_hierarchy rebuilt
} err]
if {$rc} { puts "SYNTH FAILED: $err"; exit 1 }
write_checkpoint -force $outputDir/post_synth.dcp

# Implementation
opt_design
place_design
phys_opt_design
route_design
write_checkpoint -force $outputDir/post_route.dcp

# Reports
report_timing_summary -file $outputDir/timing.rpt
report_utilization    -file $outputDir/util.rpt

# Bitstream
write_bitstream -force $outputDir/kv260_top.bit
```

### Relevance to Your Project

The `create_bd.tcl` in your repo handles block-design creation; wrapping it in the non-project flow above lets you rebuild the full bitstream from a clean checkout in one command (`vivado -mode batch -source build.tcl`), which is essential for reproducible CI and prevents "works on my machine" bitstream issues.

## Vitis Bare-Metal / Standalone

### Key Findings

- **xil_printf vs printf**: `xil_printf` is a lightweight subset — no floating-point, no `%u` in older versions, no buffer flush; for PASS/FAIL messages it is sufficient but `printf` requires the full `libc` via BSP linker settings, which significantly increases code size.
- **BSP regeneration**: Any hardware change (new XSA export from Vivado) requires regenerating the BSP in Vitis; stale BSPs use old base addresses and will silently read/write wrong AXI addresses.
- **2025.1 BSP migration note**: Classic Vitis IDE projects (pre-2024.2) must be migrated to 2024.2 first before opening in 2025.1 — skipping this step corrupts BSP settings.
- **System Device Tree (SDT) flow**: Vitis 2025.1 begins transitioning several reference boards (ZCU102, VCK190) to the SDT-based BSP flow; for the KV260 on 2025.1 the traditional XSA→BSP flow still applies but future releases may require SDT.
- **Interrupt controller**: Use `XScuGic` (Generic Interrupt Controller driver, `xscugic.h`) for Cortex-A53 interrupt handling; pair with `Xil_ExceptionEnable()` from `xil_exception.h`. Never call `XScuGic_Connect` before `XScuGic_CfgInitialize`.
- **UART baud rate**: The USB-UART on KV260 uses MIO-based UART0 at 115200 baud by default; BSP `xparameters.h` defines `XUARTPS_BAUDRATE` — verify it matches your terminal settings before concluding a print is missing.

### Code Example

```c
/* Minimal AXI-BRAM read/write test with result reporting */
#include "xparameters.h"
#include "xil_io.h"
#include "xil_printf.h"

#define BRAM0_BASE  0xA0000000UL
#define BRAM1_BASE  0xA0010000UL
#define TEST_WORDS  16U

static int bram_test(u32 base, const char *name)
{
    u32 i, readback;
    int pass = 1;

    /* Write phase */
    for (i = 0; i < TEST_WORDS; i++)
        Xil_Out32(base + (i * 4), 0xDEAD0000 | i);

    /* Fence: ensure writes complete before reads on weakly-ordered AXI */
    Xil_DCacheFlushRange(base, TEST_WORDS * 4);

    /* Read-back phase */
    for (i = 0; i < TEST_WORDS; i++) {
        readback = Xil_In32(base + (i * 4));
        if (readback != (0xDEAD0000 | i)) {
            xil_printf("%s[%u]: FAIL got 0x%08x\r\n", name, i, readback);
            pass = 0;
        }
    }
    return pass;
}

int main(void)
{
    xil_printf("AXI-BRAM demo starting\r\n");
    int ok = bram_test(BRAM0_BASE, "BRAM0")
           & bram_test(BRAM1_BASE, "BRAM1");
    xil_printf(ok ? "ALL PASS\r\n" : "FAIL\r\n");
    return ok ? 0 : 1;
}
```

### Relevance to Your Project

The `Xil_DCacheFlushRange` call above is critical on Cortex-A53 — without it, cached writes may never reach the AXI fabric, making BRAM reads return stale zeros. This is a common "works in simulation, fails on hardware" bug in bare-metal AXI demos.

## XDC Timing Constraints

### Key Findings

- **Purpose of I/O delays**: Vivado's timing engine only analyzes paths inside the FPGA boundary; `set_input_delay` and `set_output_delay` extend timing analysis to the PCB traces and register outside the device.
- **Virtual clock pattern**: For pure combinational or asynchronous I/O paths without an external clock reference, define a virtual clock and reference both delays against it; without this Vivado reports "unconstrained" paths that pass by accident.
- **set_input_delay reference**: The delay is measured from the source clock edge at the board connector to the data valid window at the FPGA input. Use `-max` for setup analysis and `-min` for hold.
- **Clock ports excluded from all_inputs**: `set_input_delay -clock clk -max 2.0 [all_inputs]` silently skips clock ports — this is by design but can leave STARTUPE3 or JTAG pins unconstrained if you rely on `all_inputs` alone.
- **PS-side I/O**: AXI signals between PS and PL cross inside the Zynq fabric; they do not need I/O delay constraints. Only PL-side external pins (GPIO, UART, PMOD) need explicit constraints.
- **set_clock_groups for async domains**: If your design has the PS 100 MHz reference and an independent PL-generated clock, declare them as `set_clock_groups -asynchronous -group [get_clocks clk_pl_0] -group [get_clocks clk_out1]` to suppress false cross-domain paths.

### Code Example

```tcl
# KV260 XDC: PS-PL clock + async PL clock group
# The PS supplies pl_clk0 at 100 MHz to the PL fabric

# Primary PL clock (PS-sourced, 100 MHz)
create_clock -period 10.000 -name pl_clk0 [get_pins */PS8_i/PLCLK[0]]

# If a PL MMCM generates a second clock domain:
create_clock -period 8.000 -name clk_fast [get_pins mmcm_inst/CLKOUT0]

# Declare the two as asynchronous to suppress false cross-domain warnings
set_clock_groups -asynchronous \
    -group [get_clocks pl_clk0] \
    -group [get_clocks clk_fast]

# PL-side GPIO (e.g., status LEDs on PMOD connector)
set_output_delay -clock pl_clk0 -max  2.0 [get_ports {led[*]}]
set_output_delay -clock pl_clk0 -min -1.0 [get_ports {led[*]}]

# False path for async reset (PS reset is not synchronous to PL clk)
set_false_path -from [get_pins */PS8_i/FCLKRESETN[0]]
```

### Relevance to Your Project

The KV260 AXI-BRAM demo uses only the PS-sourced `pl_clk0` with no external PL I/O other than the UART (which is MIO, not PL-constrained). The minimum required XDC is the `create_clock` on `PLCLK[0]` and a `set_false_path` on the PS reset; the `set_clock_groups` pattern above becomes critical the moment a second PL clock (e.g., for a future AXI-Stream data path) is added.

## Kria KV260 / K26 SoM

### Key Findings

- **Boot mode is QSPI32, read-only**: The K26 SoM ships with QSPI-based boot firmware that is factory-locked and read-only; it boots a minimal Linux from which you load your bitstream and application via JTAG or the `fpgautil` / Vitis debugger workflow.
- **MIO bank layout**: The K26 has three MIO banks. Bank 500 is reserved for SOM-internal peripherals (QSPI, SPI, I2C, eMMC). Banks 501 and 502 are user-accessible via the carrier board connector; on the KV260 carrier, UART0 (MIO 42/43) is routed to the USB-UART bridge.
- **EMIO vs MIO**: AXI peripherals in the PL are accessed over the PS AXI master (M_AXI_HPM0 / M_AXI_HPM1) — not EMIO. EMIO is only used to expose PS peripherals (I2C, SPI, GPIO, etc.) to PL pins; it is not involved in AXI-BRAM connectivity.
- **Kria bare-metal platform**: AMD's 2025.1 Kria platform creation tutorial builds a custom XSA from Vivado and links it to a Vitis standalone domain — the BRAM base addresses from the Address Editor flow directly into `xparameters.h`.
- **PMU overlay for carrier differences**: KV260 and KR260 differ in MIO bank 501/502 assignments (Ethernet is MIO on KR260, absent on KV260); a PMU configuration overlay object handles carrier-specific pin differences at boot time without reflashing the SOM.
- **JTAG debug flow**: The recommended bare-metal debug path is Vivado Hardware Manager → program bitstream → Vitis debugger → download ELF. The KV260 carrier exposes a Digilent JTAG USB interface on the carrier board.

### Code Example

```tcl
# Vivado: set part for K26 SoM on KV260 carrier
# The SoM part is xck26-sfvc784-2LV-c
# (xczu5ev inside a carrier-agnostic SOM package)
set_property PART xck26-sfvc784-2LV-c [current_project]

# UART0 on KV260 carrier: MIO 42 (TX) and MIO 43 (RX)
# These are pre-configured by the FSBL; no XDC constraints needed
# for MIO pins - they are PS-side and not part of the PL XDC

# Confirm PS UART config in block design TCL:
set_property -dict [list \
    CONFIG.PSU__UART0__PERIPHERAL__ENABLE {1} \
    CONFIG.PSU__UART0__PERIPHERAL__IO {MIO 42 .. 43} \
    CONFIG.PSU__CRL_APB__UART0_REF_CTRL__FREQMHZ {100} \
] [get_bd_cells zynq_ultra_ps_e_0]
```

### Relevance to Your Project

The PS TCL above is exactly the UART configuration needed in `create_bd.tcl` to ensure `xil_printf` output reaches the USB-UART bridge on the KV260 carrier at 115200 baud. If the `PSU__UART0__PERIPHERAL__IO` property is missing from the block design, the BSP will generate a stub UART driver with no physical connection, producing silent output.

## AMD/Xilinx Tool Updates (Vivado / Vitis 2025.x)

### Key Findings

- **2025.2 is now the latest release** (released ~2025-11-20, per UG973 revision date); if still on 2025.1, assess whether to upgrade before the next project milestone.
- **Vitis 2025.1 highlights**: Enhanced Versal AI Engine flow (new DSP library functions, C++17 via Clang 16 in HLS); Vitis Classic IDE projects from before 2024.2 must be migrated to 2024.2 first.
- **SDT BSP flow expansion**: Vitis 2025.1 extends the System Device Tree BSP flow to ZCU102 and VCK190; the KV260 still uses the traditional XSA-based flow in 2025.1 but migration is likely in a coming release.
- **Standalone BSP 2025.1 bug fixes**: Cortex-R5 fixes for secure/non-secure address space and an infinite loop in `Xil_MemMap`; no reported A53-side BSP regressions.
- **Vivado 2025.2**: New features listed in UG973 include production-ready Spartan UltraScale+ parts (XCSU10P/25P/35P) and continued Versal improvements; no KV260/Zynq UltraScale+ breaking changes identified in public release notes as of this digest.
- **Known-issues source**: AMD tracks known issues via "Answer Records" linked from UG973; for 2025.1-specific bugs search `https://support.xilinx.com/s/article/` with the tool version and symptom.

### Code Example

```tcl
# Vivado 2025.x: check tool version at script start and warn on mismatch
set required_version "2025.1"
set current_version  [version -short]

if {[string compare $current_version $required_version] < 0} {
    puts "WARNING: Script developed on $required_version, \
          running on $current_version — results may differ"
}

# 2025.x: upgrade_ip now reports a structured dict; parse it safely
set upgrade_log [upgrade_ip -quiet [get_ips *]]
foreach entry $upgrade_log {
    set ip_name  [dict get $entry name]
    set ip_state [dict get $entry upgrade_status]
    if {$ip_state ne "SUCCESS"} {
        puts "IP upgrade warning: $ip_name -> $ip_state"
    }
}
```

### Relevance to Your Project

If you open your `kv260_claude/kv260/` Vivado project in 2025.2, the IP cores (AXI BRAM Controller, Block Memory Generator, Zynq UltraScale+ PS) will be flagged for upgrade. The version-check and `upgrade_ip` snippet above is a safe way to handle this in `create_bd.tcl` without silently upgrading IPs that may have behavioral changes.
