## Executive Summary
- **`assign_bd_address` is the precise Tcl primitive behind the Address Editor** — `assign_bd_address -offset 0xA0000000 -range 0x10000 -target_address_space [get_bd_addr_spaces .../Data] [get_bd_addr_segs axi_bram_ctrl_0/S_AXI/Reg] -force` is the exact form that pins BRAM0/BRAM2 to fixed addresses; if `create_bd.tcl` ever needs to be re-sourced cleanly, this command (not manual GUI dragging) is what should be scripted.
- **AXI-Lite write backpressure**: per the AXI handshake rules, the slave (axi_bram_ctrl) must deassert `AWREADY`/`WREADY` while busy, and `BVALID` can only assert after the `WLAST`/`WVALID`/`WREADY` handshake completes — for a single-beat AXI-Lite write this collapses to "wait for `BVALID` before issuing the next `Xil_Out32`," which the PS automatically does, but it's the reason back-to-back unaligned writes from a tight C loop never get reordered.
- **`validate_bd_design` + `regenerate_bd_layout` + `save_bd_design`** remains the canonical post-`apply_bd_automation` sequence (UG835/UG994, 2025.x) — if `create_bd.tcl` builds the BD purely via Tcl in non-project mode, missing this sequence is the most common reason a freshly-generated `.bd` produces a wrapper whose `xparameters.h` doesn't match the intended `0xA0000000`/`0xA0010000` map.
- **Vitis Unified IDE (2025.x) removed MSS/MDD/MLD files** in favor of CMake + YAML-based BSP configuration — any tutorial that says "edit `system.mss`" or "open Board Support Package settings in the old dialog" is for Vitis Classic; on 2025.1 the equivalent is editing `vitis-comp.json` / the platform component's YAML and re-running "Update Hardware Specification."
- **K26 SOM boot mode is set via `PS_MODE[3:0]`**, pulled to specific levels by the carrier card (KV260 ships configured for QSPI32 boot of the certified image) — for a from-scratch bare-metal `.xsa`/ELF deployed via JTAG, boot-mode pins are irrelevant at debug time, but matter if you ever flash the BRAM-demo ELF as the persistent boot image.

## AXI Protocol / AXI-Lite / AXI-Stream
### Key Findings
- All five AXI4/AXI4-Lite channels (AW, W, B, AR, R) use the identical VALID/READY handshake: a transfer completes only on a clock edge where both VALID and READY are `1`; once VALID is asserted it must stay asserted until the handshake occurs (it cannot be withdrawn), while READY may be held low indefinitely by either side.
- **Backpressure propagation is the most commonly mis-implemented part of a hand-written AXI-Lite slave**: if a master holds `BREADY` low, the slave must eventually lower `AWREADY`/`WREADY` (it can't keep accepting writes it can't acknowledge); the symmetric rule applies to `RREADY` vs `ARREADY`. Simulation-only testing often misses this because most testbenches keep `BREADY`/`RREADY` high.
- `BVALID` may only be asserted by the slave **after** the corresponding `WVALID && WREADY` handshake (and `WLAST` for AXI4) has completed — for AXI4-Lite this just means "write data must be accepted before the write response is issued," which is automatically satisfied by the AXI BRAM Controller.
- For AXI-Stream (relevant only if a future DMA path is added), `TKEEP` may only be "sparse" (have zero bits) on the final beat of a packet (when `TLAST` is asserted) or, if Data Realignment Engine (DRE) is enabled, on the first beat — sparse `TKEEP` in the middle of a transfer is illegal and many cores will misbehave silently rather than flag an error.
- AXI DMA raises an interrupt on every beat where `TLAST` is asserted; a custom AXI-Stream producer that (incorrectly) asserts `TLAST` on every single-word transfer will cause an "interrupt flood" on the S2MM/MM2S channel — a known gotcha if BRAM-demo-style register pokes are ever replaced with a streaming interface.

### Code Example
```tcl
# Tcl form of the Address Editor entry for BRAM0/BRAM2 - the exact command
# that backs "type address into Offset column, click Regenerate Layout"
assign_bd_address -offset 0xA0000000 -range 0x00010000 \
    -target_address_space [get_bd_addr_spaces zynq_ultra_ps_e_0/Data] \
    [get_bd_addr_segs axi_bram_ctrl_0/S_AXI/Reg] -force

assign_bd_address -offset 0xA0010000 -range 0x00010000 \
    -target_address_space [get_bd_addr_spaces zynq_ultra_ps_e_0/Data] \
    [get_bd_addr_segs axi_bram_ctrl_1/S_AXI/Reg] -force

validate_bd_design
```

### Relevance to Your Project
BRAM0/BRAM2 sit behind `axi_bram_ctrl` in AXI4-Lite mode, which is the simplest AXI profile (single outstanding transaction, no bursts, no `TLAST`). The PS's AXI master automatically respects the `BVALID`-after-`WREADY` ordering rule, so `main.c`'s `Xil_Out32`/`Xil_In32` calls are safe without manual barriers. The most directly useful finding for `create_bd.tcl` is the `assign_bd_address` form above — if the script currently relies on `apply_bd_automation` to auto-pick addresses, pinning `0xA0000000`/`0xA0010000` explicitly via `assign_bd_address -force` makes the address map deterministic across Vivado re-generations.

## Vivado Block Design / IP Integrator
### Key Findings
- The Address Editor becomes active only once a master with an address space (e.g., the Zynq UltraScale+ PS's `M_AXI_HPM0_FPD`/`LPD`) is present in the BD; `apply_bd_automation`/connection automation auto-populates an entry in the Address Editor for every newly-connected slave, which you can then override.
- For the AXI BRAM Controller specifically: open its Address Editor entry, click "Expand All," and set the **Range** column (e.g., 64KB) per segment — then click **Regenerate Layout** to redraw the canvas after any manual address or connection edit.
- Manually-typed addresses must be aligned to their range: a peripheral with a 64KB (`0x10000`) range must have an offset with at least 16 trailing zero bits (i.e., a multiple of `0x10000`) — `0xA0000000` and `0xA0010000` both satisfy this for 64KB ranges.
- `write_bd_tcl -force` exports the *current* state of a `.bd` (IP customizations, connections, address assignments) back to a Tcl script — useful as a one-time "GUI drift capture" if someone hand-edits the block design and `create_bd.tcl` needs to be brought back in sync.
- A common IPI error pairing `axi_bram_ctrl` with `blk_mem_gen`: a `DATA_WIDTH` or `READ_WRITE_MODE` mismatch between the two IPs produces a `validate_bd_design` error; if ECC is enabled on the controller, the BMG must be configured in the matching ECC "wrapper" memory map (extra parity bits per word), which changes the BRAM's effective addressable depth.

### Code Example
```tcl
# Idempotent BRAM controller + BMG pairing, safe to re-source against
# an existing .bd (guards against "cell already exists" errors)
foreach {ctrl_name bmg_name base range} {
    axi_bram_ctrl_0 blk_mem_gen_0 0xA0000000 0x00010000
    axi_bram_ctrl_1 blk_mem_gen_1 0xA0010000 0x00010000
} {
    if {[get_bd_cells -quiet /$ctrl_name] eq ""} {
        set ctrl [create_bd_cell -type ip -vlnv xilinx.com:ip:axi_bram_ctrl:4.1 $ctrl_name]
        set_property -dict [list CONFIG.SINGLE_PORT_BRAM {0} CONFIG.DATA_WIDTH {32}] $ctrl
    }
    if {[get_bd_cells -quiet /$bmg_name] eq ""} {
        set bmg [create_bd_cell -type ip -vlnv xilinx.com:ip:blk_mem_gen:8.4 $bmg_name]
        set_property -dict [list CONFIG.Memory_Type {True_Dual_Port_RAM}] $bmg
    }
    connect_bd_intf_net [get_bd_intf_pins $ctrl_name/BRAM_PORTA] [get_bd_intf_pins $bmg_name/BRAM_PORTA]
    connect_bd_intf_net [get_bd_intf_pins $ctrl_name/BRAM_PORTB] [get_bd_intf_pins $bmg_name/BRAM_PORTB]

    apply_bd_automation -rule xilinx.com:bd_rule:axi4 \
        -config {Clk_master {Auto} Clk_slave {Auto} Clk_xbar {Auto} \
                 Master {/zynq_ultra_ps_e_0/M_AXI_HPM0_FPD} \
                 Slave {/${ctrl_name}/S_AXI} intc_ip {New AXI SmartConnect} master_apm {0}} \
        [get_bd_intf_pins $ctrl_name/S_AXI]
}
validate_bd_design
regenerate_bd_layout
save_bd_design
```

### Relevance to Your Project
This pattern matches the two-BRAM topology described for `kv260_axi_bram_demo` and is written so `create_bd.tcl` can be re-sourced against an existing `.bd` without `ERROR: [BD 41-737] ... already exists`. After the loop, the explicit `assign_bd_address` calls from the AXI section above can be inserted to lock `0xA0000000`/`0xA0010000` rather than relying on whatever `apply_bd_automation` picks by default (it tends to pick the next free aligned block, which is usually but not always `0xA0000000`-based).

## Vivado TCL Scripting
### Key Findings
- Vivado has three run modes: **GUI**, **Tcl mode** (`vivado -mode tcl`, interactive — best for iterative script development), and **Batch mode** (`vivado -mode batch -source script.tcl`, non-interactive, exits when the script finishes — best for CI/regeneration of `create_bd.tcl`).
- In **non-project mode**, there's no `.xpr`; the developer manages all sources explicitly (`read_vhdl`, `read_xdc`, `synth_design`, `opt_design`, `place_design`, `route_design`, `write_bitstream`). UG994 (2025.1) documents IP Integrator in non-project mode as a fully supported, first-class flow — a BD can be built, validated, and wrapped entirely from Tcl without ever creating a project file.
- A documented constraint: if a block design is not generated (synthesized) ahead of time, adding it to a non-project-mode flow errors with "block design must be generated prior to adding it to the non-project flow" — unless global synthesis (`synth_design` with the BD's `.bd` as a source and out-of-context synthesis enabled) is used, in which case the BD can be generated inline.
- `write_bd_tcl` supports `-force` (overwrite), `-no_mig_contents` (skip MIG PRJ data), and `-ignore_minor_versions` (target latest minor IP versions) — the latter is useful when re-running an older `create_bd.tcl` against a newer Vivado where IP minor versions have bumped (e.g., `axi_bram_ctrl:4.1` → `4.2`).
- Pin the exact part (`xck26-sfvc784-2LV-c` for the K26 SoM) via `create_project -part` rather than relying only on a board file — board-file definitions can change defaults (pin assignments, PS configuration presets) between Vivado releases even when the silicon part stays the same.

### Code Example
```tcl
#!/usr/bin/env -S vivado -mode batch -source
# build.tcl - non-project-mode rebuild entry point for kv260-axi-bram-demo
set part    "xck26-sfvc784-2LV-c"
set bd_name "kv260_bd"

create_project -in_memory -part $part

create_bd_design $bd_name
source ./kv260_claude/kv260/tcl/create_bd.tcl
validate_bd_design
regenerate_bd_layout
save_bd_design

make_wrapper -files [get_files ${bd_name}.bd] -top -force
add_files -norecurse [get_files -of_objects [get_filesets sources_1] *${bd_name}_wrapper.vhd]
add_files -fileset constrs_1 -norecurse ./kv260_claude/kv260/xdc/kv260_axi_bram.xdc

synth_design -top ${bd_name}_wrapper -part $part
opt_design
place_design
route_design
write_bitstream -force ./build/${bd_name}_wrapper.bit

# Snapshot the BD back to Tcl for drift-checking against create_bd.tcl
write_bd_tcl -force -ignore_minor_versions ./build/${bd_name}_export.tcl

puts "Done: ./build/${bd_name}_wrapper.bit"
```

### Relevance to Your Project
A single `build.tcl` of this shape, run via `vivado -mode batch -source build.tcl`, gives a one-command, version-pinned rebuild of the KV260 AXI-BRAM hardware directly from `kv260_claude/kv260/tcl/create_bd.tcl` and `vhdl/kv260_top.vhd`, with no `.xpr` checked into git. The trailing `write_bd_tcl -force -ignore_minor_versions` step is a cheap "did the regenerated BD still match what `create_bd.tcl` describes" sanity check — diffing the exported Tcl against `create_bd.tcl` after a Vivado version bump will surface IP version drift or address-map changes immediately.

## Vitis Bare-Metal / Standalone
### Key Findings
- **Vitis 2025.x's Unified IDE removed MSS/MDD/MLD files** and replaced the BSP configuration model with CMake + YAML — tutorials referencing "Board Support Package Settings" dialogs or `system.mss` are for Vitis Classic; on 2025.1 the equivalent edits happen in the platform component's YAML/`vitis-comp.json` plus "Update Hardware Specification."
- The Unified IDE's project-creation flow is conceptually the same as Classic but with different menu paths: create a workspace (pick a directory) → create a **platform component** from an `.xsa` → create an **application component** targeting that platform → build. Classic workspaces cannot be opened directly; "Export Workspace to Unified IDE" in Classic is the supported migration path.
- `xil_printf` (declared in `xil_printf.h`) is a minimal, no-floating-point `printf` substitute (`%d`, `%u`, `%x`, `%c`, `%s`, plus `l`/`ll` length modifiers) that's smaller than full `stdio` — appropriate for the PASS/FAIL UART output in this project, but any future diagnostic that wants a computed percentage/ratio needs to be done in fixed-point/integer math, not `%f`.
- The standalone BSP for the A53 (APU) links the GIC driver (`xscugic`) by default even for a purely polling app — harmless for a register-poke BRAM test, but worth knowing if binary size ever becomes a concern for OCM-resident code.
- Linker script (`lscript.ld`) placement of `.text`/`.data`/`.bss`/heap/stack follows the memory region chosen for the domain (commonly DDR or OCM for A53 bare-metal); if the BRAM PASS/FAIL test hangs partway through a larger test pattern, check `STACK_SIZE`/`HEAP_SIZE` in `lscript.ld` before suspecting the AXI path.

### Code Example
```c
#include "xil_printf.h"
#include "xil_io.h"
#include "xparameters.h"

#define BRAM0_BASE  XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR  /* expect 0xA0000000 */
#define BRAM2_BASE  XPAR_AXI_BRAM_CTRL_1_S_AXI_BASEADDR  /* expect 0xA0010000 */
#define NUM_WORDS   16U

static int test_bram(u32 base, const char *name) {
    int errors = 0;
    for (u32 i = 0; i < NUM_WORDS; i++) {
        Xil_Out32(base + (i * 4U), 0x5A5A0000U | i);
    }
    for (u32 i = 0; i < NUM_WORDS; i++) {
        u32 expect = 0x5A5A0000U | i;
        u32 got    = Xil_In32(base + (i * 4U));
        if (got != expect) {
            xil_printf("%s[%lu]: wrote 0x%08lx read 0x%08lx FAIL\r\n",
                       name, (unsigned long)i, (unsigned long)expect, (unsigned long)got);
            errors++;
        }
    }
    xil_printf("%s: %s (%d errors)\r\n", name, errors ? "FAIL" : "PASS", errors);
    return errors;
}

int main(void) {
    xil_printf("\r\n--- KV260 AXI BRAM Demo ---\r\n");
    int e = test_bram(BRAM0_BASE, "BRAM0") + test_bram(BRAM2_BASE, "BRAM2");
    xil_printf("Overall: %s\r\n", e ? "FAIL" : "PASS");
    return e;
}
```

### Relevance to Your Project
The most actionable item for this project's Vitis side: after any change to `create_bd.tcl` that alters the BRAM address map, the platform component's "Update Hardware Specification" step (not just re-importing the `.xsa` file into a fixed-name directory) must be re-run, or `XPAR_AXI_BRAM_CTRL_*_S_AXI_BASEADDR` in `xparameters.h` will silently still point at the old `0xA0000000`/`0xA0010000` values even though the bitstream's address decoders moved. Since Vitis 2025.1 no longer exposes the old BSP-settings dialog, this step now lives under the platform component's right-click menu / YAML regeneration in the Unified IDE.

## XDC Timing Constraints
### Key Findings
- `set_input_delay -clock <clk> [-max|-min] <value> [get_ports ...]` and `set_output_delay -clock <clk> [-max|-min] <value> [get_ports ...]` describe the **external** timing relationship at a port relative to a named clock — they do not by themselves encode the FPGA's internal setup/hold; Vivado's STA computes internal margins once the external delay is known. Both commands require `-clock` to associate the I/O delay with the correct clock domain when multiple clocks exist.
- `set_clock_groups -asynchronous -group [get_clocks A] -group [get_clocks B]` is the standard way to tell Vivado two clocks have no defined phase relationship and to **disable timing analysis between them** — paths crossing the boundary then need explicit handling (multi-flop synchronizers), since Vivado will not time them at all.
- Vivado times **all clocks together by default** unless clock groups or other exceptions are defined — for a PS-generated `pl_clk0` driving all PL logic and a separate free-running reference clock (if ever added), an explicit `set_clock_groups -asynchronous` is required, otherwise STA may report spurious cross-domain violations (or, worse, silently pass without flagging a real CDC issue, since default timing ≠ CDC verification).
- A practical pattern for Clock-Wizard-based asynchronous groups: `set_clock_groups -asynchronous -group [get_clocks -include_generated_clocks -of_objects [get_pins -hier -filter {name=~*clk_gen_ins/clk_in1}]] -group [get_clocks -include_generated_clocks -of_objects [get_pins -hier -filter {name=~*clk_gen_ins/clk_out1}]]` — generalizes directly to PL-vs-PS clock domain pairs.
- For Zynq UltraScale+/Kria designs where all PL logic runs from PS-generated `pl_clk0` and the only external I/O is routed through PS MIO (UART, JTAG), the PS IP's auto-generated clock constraints plus IP-Integrator default exceptions are typically sufficient — a project-level `.xdc` being nearly empty is expected, not a sign of missing constraints.

# set_clock_groups -asynchronous \
#   -group [get_clocks -of_objects [get_pins -hier -filter {NAME =~ *pl_clk0*}]] \

### Relevance to Your Project
Since `kv260_top.vhd` connects entirely to PS AXI master ports (`M_AXI_HPM0_*`) and UART runs over PS MIO, the project's `.xdc` likely needs **no `set_input_delay`/`set_output_delay`/`set_clock_groups` entries at all** for correct timing closure today — the PS IP and IP Integrator handle `pl_clk0` constraints automatically. Keep this in mind if a future revision adds any direct PL pin (debug LED, external trigger): only then do the `set_output_delay`/`set_clock_groups` patterns above become load-bearing, and the pin location must be verified against the KV260 carrier schematic specifically (not KR260/KD240, which differ).

## Kria KV260 / K26 SoM
### Key Findings
- The K26 SOM's Zynq UltraScale+ boot mode is selected via `PS_MODE[3:0]` pins routed through the SOM connector to the carrier. Kria Starter Kits ship with boot firmware pre-loaded in QSPI non-volatile memory and a default **QSPI32** boot configuration; boot mode can be changed afterward via XSDB/XSCT Tcl scripts (e.g., to switch to USB/JTAG boot for development).
- **KV260 uses PS GEM3** for its Ethernet/PS networking, while KR260 and KD240 use **GEM1** — a reminder that MIO assignments inherited from a reference block design are carrier-specific, and a `create_bd.tcl` adapted from a KR260/KD240 example may carry over the wrong GEM/MIO mapping if PS configuration wasn't re-checked for KV260.
- The default KV260 starter-kit bitstream includes an **EMIO mapping to the carrier's fan-control pin** — if a from-scratch `create_bd.tcl` for the AXI-BRAM demo was bootstrapped from the official Kria reference design rather than built from a blank PS configuration, check for and remove unused EMIO/fan-related PS configuration that has no corresponding logic in `kv260_top.vhd`.
- In PS-PL Configuration, **AXI HPM0/1 FPD/LPD** are PS *master* interfaces into the PL (what `main.c` uses to reach `axi_bram_ctrl` over AXI-Lite), while **AXI HP0-3 FPD** are PS *slave* interfaces (used by PL masters to reach DDR) — for a pure "CPU writes to PL BRAM" demo, only one HPM master interface needs to be enabled, simplifying the PS configuration page.
- The Baremetal Flow for Kria SOMs explicitly documents connecting the `S_AXI` port of an AXI BRAM Controller to `M_AXI_HPM0_FPD`/`LPD` of the PS as the reference topology — i.e., the exact pattern this project already follows is the one AMD documents for bare-metal BRAM access on Kria.

### Relevance to Your Project
If the PASS/FAIL test hangs or returns a bus error only on a cold boot (but succeeds after a JTAG re-download), suspect PL power/clock sequencing rather than the AXI-Lite read/write logic — the standard `psu_init()` call generated alongside the BSP must run before any BRAM access and handles `PWRGD_PL_M2C`/`FCLK0` release in the normal flow. The XSCT snippet above isolates "PS/PL link not up yet" from "test-pattern logic bug" by manually poking `0xA0000000`/`0xA0010000`. Separately, since the project's `axi_bram_ctrl` → `M_AXI_HPM0_*` topology matches AMD's documented Kria Baremetal Flow exactly, any debugging of the *block design* itself can lean directly on that reference doc rather than starting from scratch.

## AMD/Xilinx Tool Updates (Vivado/Vitis 2025.x)
### Key Findings
- **Starting with 2025.1, AMD restructured the tools' install folder layout** to `<Version>/Vivado` (and presumably `<Version>/Vitis`) — if any local build scripts or CI hardcode older install paths (e.g., `/opt/Xilinx/Vivado/2025.1/...` vs a new `<Version>/Vivado/...` layout), verify the actual install path on the 2025.1/2025.2 machine before assuming path compatibility with older automation.
- Vivado 2025.2's release notes (UG973) point to **Answer Record 000037546** for the current Known Issues list and **Answer Record 000039903** for a consolidated IP-by-IP change log — both are the right first stop when an `axi_bram_ctrl`/`blk_mem_gen`/`zynq_ultra_ps_e` IP behaves differently after upgrading from 2025.1 to 2025.2.
- The **Vitis Unified IDE is the default and only supported flow for new projects in 2025.x** (Classic Vitis IDE is deprecated for new work); "Migrating Projects from Classic IDE" (UG1700, 2025.1) documents the `Vitis > Export Workspace to Unified IDE` path for bringing forward older bare-metal workspaces.
- "Using IP Integrator in Non-Project Mode" remains documented as first-class in UG994 (2025.1) — a Tcl-only BD flow (no `.xpr`) continues to be fully supported, which fits a repo layout that already separates `tcl/create_bd.tcl` from VHDL sources and BSP/app code.
- When moving a project between Vivado releases, the standard upgrade sequence is `report_ip_status` (lists out-of-date IP) → `upgrade_ip [get_ips -all]` → `validate_bd_design` → `regenerate_bd_layout` → `save_bd_design` → `make_wrapper -force` — this is the documented way to bring `axi_bram_ctrl`/`blk_mem_gen`/PS IP up to a new release's versions before re-synthesizing and re-exporting the `.xsa`.

### Relevance to Your Project
Before relying on a from-scratch `xck26-sfvc784-2LV-c` rebuild under a fresh 2025.x install, run `report_ip_status`/`upgrade_ip` against any checked-in `.bd`/`.xpr` first — IP version drift between `axi_bram_ctrl`/`blk_mem_gen` and the `xparameters.h` the BSP was generated against is the most common "worked on old Vivado, fails on new Vivado" failure mode for projects like this. Given the Unified IDE is now the only forward-compatible Vitis flow, any setup notes or README steps describing Vitis Classic's BSP-settings dialog should be updated to reference the platform component's YAML/`vitis-comp.json` and "Update Hardware Specification" instead.
