# FPGA Research Digest - 2026-10-03

## Executive Summary

- **AXI-Lite handshake bug (critical):** Xilinx example slave code commonly conditions the bus response on signals beyond `*VALID & *READY`, causing missed transactions — always drive BREADY/RREADY combinatorially from the master side and never gate on side-conditions in the slave state machine.
- **BRAM at 0xA0000000 confirmed for KV260:** The HPM0 master port on the K26 SoM maps PL AXI slaves starting at 0xA0000000 by default; the bare-metal BRAM read/write pattern is the canonical connectivity proof for this platform.
- **Block Memory Generator cannot be selectively upgraded** in Vivado 2025.x block designs — upgrading any design that uses BRAM IP requires a full project IP upgrade cycle, not the selective one.
- **Vivado 2025.2 adds ultra-low-area mode** for AXI Switch and AXI SmartConnect via a `STRATEGY` parameter — useful for trimming resource usage when the project scales beyond two BRAMs.
- **Non-project mode TCL is the recommended CI/CD path:** `vivado -mode batch -source build.tcl` plus `write_bitstream -force` gives a fully reproducible build with no GUI dependency.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- All five AXI channels (AW, W, B, AR, R) use the same VALID/READY handshake; a transaction completes on the rising clock edge where **both** signals are high — no exceptions.
- The most common AXI-Lite slave bug: conditioning the response state machine on anything other than `*VALID & *READY`. Both the master and interconnect advance on those two signals alone; extra guards cause missed or corrupted transactions. ([Source: ZipCPU](https://zipcpu.com/formal/2019/04/16/axi-mistakes.html))
- **Address truncation pitfall (Vivado 2025):** If the IP's internal address space is smaller than what the Address Editor assigns, the interconnect silently truncates the upper address bits — any address with matching lower bits resolves to the same slave register. Ensure IP address range exactly matches the assigned segment. ([Source: Digilent Forum](https://forum.digilent.com/topic/33038-vivado-2025-axi-full-peripheral-limited-to-1k-usable-address-space/))
- **AXI BRAM Controller `C_READ_LATENCY`:** Default is 1 clock cycle (BRAM primitive latency). If timing closure at BRAM output fails, increase to 2 to allow the controller to pipeline the handshake correctly.
- AXI-Stream (`TVALID`/`TREADY`/`TDATA`/`TLAST`) is unidirectional and has no address phase — use it for streaming data paths; AXI-Lite is the right choice for slow, register-mapped control interfaces like BRAM controllers.

### Code Example

```vhdl
-- AXI-Lite slave: correct BREADY combinatorial response
-- NEVER gate on anything other than S_AXI_AWVALID / S_AXI_WVALID
process(S_AXI_ACLK)
begin
  if rising_edge(S_AXI_ACLK) then
    if S_AXI_ARESETN = '0' then
      axi_wready <= '0';
    elsif (axi_wready = '0' and S_AXI_WVALID = '1' and S_AXI_AWVALID = '1') then
      -- Accept write only when both address and data channels are valid
      axi_wready <= '1';
    else
      axi_wready <= '0';
    end if;
  end if;
end process;

-- Write response: assert BVALID one cycle after WREADY
process(S_AXI_ACLK)
begin
  if rising_edge(S_AXI_ACLK) then
    if S_AXI_ARESETN = '0' then
      axi_bvalid <= '0';
      axi_bresp  <= "00";
    elsif (axi_wready = '1' and S_AXI_WVALID = '1' and axi_bvalid = '0') then
      axi_bvalid <= '1';
      axi_bresp  <= "00"; -- OKAY
    elsif (S_AXI_BREADY = '1' and axi_bvalid = '1') then
      axi_bvalid <= '0';
    end if;
  end if;
end process;
```

### Relevance to Your Project

Your `kv260_top.vhd` wraps the PS and connects it to two AXI BRAM controllers (BRAM0 @ 0xA0000000, BRAM2 @ 0xA0010000). If you ever extend `kv260_top` with a custom AXI-Lite slave, the BREADY/WREADY logic above is the pattern to follow. The address truncation pitfall is worth checking in your Address Editor — the 64 KB spacing (0x10000) between BRAM0 and BRAM2 is correct only if each controller's address range is set to exactly 64 KB (or smaller).

## Vivado Block Design / IP Integrator

### Key Findings

- `write_bd_tcl -include_layout my_bd.tcl` exports the full block design including canvas layout — this is the version to commit to source control, not the `.bd` file directly.
- `regenerate_bd_layout` rebuilds the canvas auto-layout. Use `-hierarchy` to apply it recursively to hierarchical modules.
- To regenerate IP output products after changing a parameter: `reset_target all [get_ips *]` then `generate_target all [get_ips *]`. Do this before synthesis to avoid stale netlists.
- **Block Memory Generator cannot be selectively upgraded** in 2025.x — when migrating Vivado versions, every IP in the BD must be upgraded together. ([Source: AMD docs](https://docs.amd.com/r/en-US/ug994-vivado-ip-subsystems/Limitations-of-Selectively-Upgrading-IP-in-Block-Designs))
- Connection Automation (`apply_bd_automation`) will auto-wire S_AXI of a BRAM controller to the nearest AXI master port and add an AXI SmartConnect if needed.

### Code Example

```tcl
# Regenerate IP output products after parameter change
open_project my_project/my_project.xpr
open_bd_design [get_bd_files]

# Reconfigure BRAM controller read latency
set_property CONFIG.C_READ_LATENCY {2} [get_bd_cells axi_bram_ctrl_0]

# Regenerate output products
reset_target all  [get_ips *]
generate_target all [get_ips *]

# Re-run connection automation if needed
apply_bd_automation -rule xilinx.com:bd_rule:axi4 \
  -config { Clk_master {Auto} Clk_slave {Auto} } \
  [get_bd_intf_pins axi_bram_ctrl_0/S_AXI]

# Save and validate
validate_bd_design
save_bd_design
```

### Relevance to Your Project

Your `create_bd.tcl` script creates the block design programmatically. Adding `reset_target` / `generate_target` before the `launch_runs impl_1` call ensures the BRAM IP output products are always fresh — this prevents the known Vivado 2025.1 issue where an updated IP isn't recognized until the project is closed and re-opened.

## Vivado TCL Scripting

### Key Findings

- **Non-project mode** is the recommended approach for CI/CD: `vivado -mode batch -source build.tcl`. Source files are explicitly listed with `read_vhdl`, `read_xdc`, `read_bd`; no `.xpr` project file is needed.
- The canonical non-project flow: `read_*` → `synth_design` → `opt_design` → `place_design` → `route_design` → `write_checkpoint` → `write_bitstream -force output.bit`.
- `write_checkpoint -force post_route.dcp` after route gives a snapshot you can reopen for timing analysis without re-running the full flow.
- AMD documentation for 2026.1 (latest) confirms non-project mode TCL API is unchanged from 2025.x — scripts written for 2025.1 are forward-compatible. ([Source: AMD UG892](https://docs.amd.com/r/en-US/ug892-vivado-design-flows-overview/Non-Project-Mode-Tcl-Script-Example))
- `report_timing_summary -file timing.rpt` and `report_utilization -file util.rpt` should always follow `route_design` before bitstream generation.

### Code Example

```tcl
# Minimal non-project batch build for kv260-axi-bram-demo
# Usage: vivado -mode batch -source build_nonproject.tcl

set outputDir ./output
file mkdir $outputDir

# Read design sources
read_vhdl -library work ./vhdl/kv260_top.vhd
read_xdc  ./xdc/kv260_top.xdc

# Read the block design wrapper (generated from create_bd.tcl)
read_bd   ./bd/kv260_bd/kv260_bd.bd
generate_target all [get_ips *]

# Synthesis
synth_design -top kv260_top -part xck26-sfvc784-2LV-c
write_checkpoint -force $outputDir/post_synth.dcp

# Implementation
opt_design
place_design
route_design
write_checkpoint  -force $outputDir/post_route.dcp

# Reports
report_timing_summary -file $outputDir/timing.rpt
report_utilization    -file $outputDir/util.rpt

# Bitstream
write_bitstream -force $outputDir/kv260_top.bit
```

### Relevance to Your Project

Your `create_bd.tcl` creates the block design. Wrapping it in the non-project flow above gives you a single `vivado -mode batch` invocation that goes from source to `.bit` without any GUI interaction — ideal for automation or re-running after hardware changes.

## Vitis Bare-Metal / Standalone

### Key Findings

- The **Standalone BSP** ships with Vivado/Vitis and provides Cortex-A53 (ARMv8) support including `xil_printf`, `Xil_In32`/`Xil_Out32` memory-mapped I/O helpers, and `XTime_GetTime` for cycle-accurate delays.
- `xil_printf` is a lightweight formatted print that routes to the UART. It **does not support `%f` (float)** — use `printf` from the stdlib (`print_flag = 1` in BSP settings) if floating-point output is needed.
- The linker script `lscript.ld` is auto-generated by Vitis from the hardware platform XSA file; the default places code and data in DDR at 0x00000000 with a 512 MB heap. For bare-metal BRAM demos you rarely need to touch it.
- `Xil_DCacheFlushRange(addr, size)` is required before any coherency-sensitive PL access when the D-cache is enabled. For simple bare-metal BRAM read/write tests, the simplest fix is `Xil_DCacheDisable()` at startup.
- BSP driver for GPIO, UART, and timers lives at `$VITIS_INSTALL/data/embeddedsw/XilinxProcessorIPLib/drivers`. ([Source: AMD Wiki](https://xilinx-wiki.atlassian.net/wiki/spaces/A/pages/18842276/Standalone+Board+Support+Package+BSP))

### Code Example

```c
#include "xil_printf.h"
#include "xil_io.h"
#include "xil_cache.h"

#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL
#define TEST_OFFSET 0x00000000UL
#define TEST_PATTERN 0xDEADBEEFUL

int main(void)
{
    /* Disable D-cache to avoid coherency issues with PL BRAM */
    Xil_DCacheDisable();

    xil_printf("=== KV260 AXI BRAM Test ===\r\n");

    /* Write pattern to BRAM0 */
    Xil_Out32(BRAM0_BASE + TEST_OFFSET, TEST_PATTERN);

    /* Read back and verify */
    u32 readback = Xil_In32(BRAM0_BASE + TEST_OFFSET);
    if (readback == TEST_PATTERN) {
        xil_printf("BRAM0 PASS: wrote 0x%08X, read 0x%08X\r\n",
                   (unsigned)TEST_PATTERN, (unsigned)readback);
    } else {
        xil_printf("BRAM0 FAIL: wrote 0x%08X, read 0x%08X\r\n",
                   (unsigned)TEST_PATTERN, (unsigned)readback);
    }

    /* Repeat for BRAM2 */
    Xil_Out32(BRAM2_BASE + TEST_OFFSET, ~TEST_PATTERN);
    readback = Xil_In32(BRAM2_BASE + TEST_OFFSET);
    xil_printf("BRAM2 %s\r\n", (readback == ~TEST_PATTERN) ? "PASS" : "FAIL");

    return 0;
}
```

### Relevance to Your Project

This is effectively the same pattern your `main.c` implements. The key additions are `Xil_DCacheDisable()` at the top (prevents coherency surprises) and using `Xil_Out32`/`Xil_In32` (the Xilinx-canonical memory-mapped I/O wrappers) rather than raw pointer casts, which avoids compiler optimization issues on volatile addresses.

## XDC Timing Constraints

### Key Findings

- **Recommended XDC constraint order** (per UG903): primary clocks → generated clocks → clock groups → I/O delays → timing exceptions (false paths, max delay, multicycle paths). ([Source: AMD UG903](https://docs.amd.com/r/2025.2-English/ug903-vivado-using-constraints/Recommended-Constraints-Sequence))
- For Zynq/Kria designs, the PS clock (`pl_clk0`) is a generated clock; always define it with `create_generated_clock` referencing the PS's internal oscillator if you need Vivado to track it through the clock network.
- `set_clock_groups -asynchronous -group {clk_A} -group {clk_B}` tells Vivado that two clock domains are unrelated — required when your PL has clocks sourced independently from the PS's AXI clock. ([Source: AMD UG835 set_clock_groups](https://docs.amd.com/r/en-US/ug835-vivado-tcl-commands/set_clock_groups))
- For AXI Clock Converter IP (CDC crossing), Vivado auto-generates `set_max_delay` constraints in the IP's XDC — **do not override these** or you risk metastability.
- `set_input_delay` and `set_output_delay` apply to I/O pins only (physical package pins), not to internal PS↔PL interfaces which are already fully constrained by Zynq IP XDC files.

### Code Example

```tcl
# kv260_top.xdc — minimal constraints for single-clock AXI-BRAM design

# PS generates pl_clk0 at 100 MHz — declare it so Vivado tracks it
# (The Zynq IP already creates this; only add if not auto-created)
# create_generated_clock -name pl_clk0 -source [get_pins zynq_ultra_ps_e_0/inst/PS8_i/PLCLK[0]] \
#   -divide_by 1 [get_nets pl_clk0]

# If you add an external oscillator input (e.g. for standalone PL clock):
# create_clock -period 10.000 -name sys_clk [get_ports sys_clk_p]

# False path for async reset synchronizer (if present in kv260_top.vhd)
set_false_path -from [get_ports sys_rst_n]

# Relax I/O constraints for debug UART pin (not timing critical)
# set_output_delay -clock pl_clk0 -max 4.0 [get_ports uart_txd]
# set_output_delay -clock pl_clk0 -min -1.0 [get_ports uart_txd]

# Example: mark LED output as false path (async, not timing critical)
# set_false_path -to [get_ports {led[*]}]
```

### Relevance to Your Project

For a single-clock AXI-BRAM demo with the PS providing `pl_clk0`, you likely need only the false path on the reset synchronizer (if you have one) and nothing else — the Zynq UltraScale+ PS8 IP XDC already constrains all PS↔PL interfaces. If your BRAM controllers run off `pl_clk0`, no additional `set_clock_groups` is needed since there is only one PL clock domain.

## Kria KV260 / K26 SoM

### Key Findings

- The K26 SoM uses a **Zynq UltraScale+ MPSoC** (XCZU5EV or XCK26); the KV260 starter kit carrier provides UART via USB, JTAG, and Ethernet. ([Source: AMD Wiki](https://xilinx-wiki.atlassian.net/wiki/pages/viewpage.action?pageId=2689728513))
- For bare-metal PL access: the PS HPM0_FPD master port is the standard AXI master connecting to PL slaves. AXI BRAM slaves connected to HPM0 are mapped starting at **0xA0000000** by the Vivado Address Editor — this matches your project's addresses exactly. ([Source: Kria Baremetal Flow](https://xilinx.github.io/kria-apps-docs/creating_applications/2022.1/build/html/docs/baremetal.html))
- **Boot mode for bare-metal JTAG debug:** ensure the boot mode pins are set to JTAG (SW1 on KV260 = all 0s). The default KV260 boot loads Linux from SD/eMMC — JTAG mode bypasses this and lets Vitis download directly to DDR+PL.
- `xmutil axiqos` utility (Linux userspace) can tune PS↔PL AXI quality-of-service settings (read/write priority). Not applicable to bare-metal but useful if you later move to Linux coexistence.
- EMIO GPIO: GPIOs not physically connected to MIO pins can be routed to PL through EMIO. The default KV260 bitstream uses EMIO for fan control; your custom bitstream replaces this.
- **Power domains:** PL is powered by VCCINT (0.85 V) and VCCO banks from the carrier. The K26 SoM handles power sequencing — no user action needed for bare-metal bring-up. ([Source: K26 SOM Data Sheet](https://www.mouser.com/datasheet/2/903/ds987_k26_som-2329045.pdf))

### Code Example

```tcl
# Vivado Address Editor: assign BRAM0 and BRAM2 in create_bd.tcl
# After create_bd_cell and connect_bd_intf_net calls:

# Assign address ranges for both BRAM controllers
assign_bd_address [get_bd_addr_segs {axi_bram_ctrl_0/S_AXI/Mem0}]
assign_bd_address [get_bd_addr_segs {axi_bram_ctrl_1/S_AXI/Mem0}]

# Set BRAM0 base address to 0xA000_0000, range 64 KB
set_property offset 0xA0000000 \
  [get_bd_addr_segs zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0]
set_property range  64K \
  [get_bd_addr_segs zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0]

# Set BRAM2 base address to 0xA001_0000, range 64 KB
set_property offset 0xA0010000 \
  [get_bd_addr_segs zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_1_Mem0]
set_property range  64K \
  [get_bd_addr_segs zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_1_Mem0]
```

### Relevance to Your Project

This TCL snippet is the canonical way to set BRAM0 @ 0xA0000000 and BRAM2 @ 0xA0010000 in your `create_bd.tcl`. The address assignment pattern matches your project's memory map exactly and avoids the silent address truncation pitfall described in the AXI section.

## AMD/Xilinx Tool Updates

### Key Findings

- **Vivado 2025.1 released 2025-07-08** with UG973 v2025.1 release notes. Known community-reported issue: after upgrading IP, Vivado sometimes doesn't register the update until the project is closed and reopened. Workaround: close/reopen project after any IP upgrade. ([Source: r/FPGA](https://redlib.ssps.io/r/FPGA/comments/1l3v39b/amd_vivado_20251_released/))
- **Vivado 2025.2** (latest stable) adds: ultra-low-area mode for AXI Switch and AXI SmartConnect via `STRATEGY` parameter; new SLR-crossing reports; ECO legalizer for DRC. ([Source: AMD Vivado 2025.2 What's New](https://www.amd.com/en/products/software/adaptive-socs-and-fpgas/vivado/vivado-whats-new.html))
- **Block Memory Generator** is explicitly listed as **not supporting selective IP upgrade** in 2025.x — any design migration must upgrade all IPs together via the standard IP upgrade dialog. ([Source: AMD UG994](https://docs.amd.com/r/en-US/ug994-vivado-ip-subsystems/Limitations-of-Selectively-Upgrading-IP-in-Block-Designs))
- **Vitis 2025.1** (UG1742) is the current release; the unified IDE flow (replacing Classic Vitis) is now the default. Platform creation from XSA is mandatory before creating application projects.
- For **2026.1** (pre-release docs available): non-project mode TCL API unchanged; boot firmware for Kria SOM is now delivered as fixed flat images tied to specific starter kit SKUs — important if you plan to update boot firmware.

### Code Example

```tcl
# Vivado 2025.2: Enable ultra-low-area mode on AXI SmartConnect
# (reduces LUT usage when the SmartConnect has only 1 master and 1 slave)
set_property CONFIG.STRATEGY {1} [get_bd_cells axi_smc]

# Verify IP versions in block design (useful before committing)
foreach cell [get_bd_cells] {
    set vlnv [get_property VLNV $cell]
    puts "$cell : $vlnv"
}

# After Vivado version upgrade: force-upgrade all IPs
# (workaround for the "IP not recognized as updated" bug)
upgrade_ip [get_ips *]
close_project
open_project my_project/my_project.xpr
```

### Relevance to Your Project

Since your project targets Vivado 2025.1, be aware of the IP-not-updated-after-upgrade bug when migrating to 2025.2. The Block Memory Generator selective-upgrade limitation means you'll need to run a full `upgrade_ip [get_ips *]` when moving between tool versions — do not attempt selective upgrade on the BRAM IP. The AXI SmartConnect `STRATEGY` parameter is worth setting in `create_bd.tcl` if you add more AXI slaves later.
