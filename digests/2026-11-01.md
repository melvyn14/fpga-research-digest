# FPGA Research Digest - 2026-11-01

## Executive Summary

- **AXI-Lite deadlock risk**: Never gate VALID on READY — a slave waiting for VALID before raising READY
  combined with a master waiting for READY before raising VALID causes a permanent stall. Both sides
  must raise their signal unconditionally.
- **Vivado 2025.1 ships VHDL-2019 simulation** and makes the Vitis Unified IDE the default (Classic IDE
  deprecated). If you're on 2025.1, VHDL-2019 `protected` types and enhanced generics are now
  simulation-legal.
- **Address 0x0 in the AXI address map is unsafe** for KV260 peripherals — Vivado's auto-assign avoids
  it for good reason: some BSP drivers assert-fail when the base address is zero.
- **Kria boot is QSPI-primary, SD-secondary**, controlled by a PMU overlay rather than static MIO
  configuration at bitstream time. For bare-metal JTAG bring-up the JTAG boot mode pins bypass
  QSPI entirely.
- **write_checkpoint** after each implementation stage is the safest TCL-based batch flow pattern —
  it lets you resume from any stage without rerunning synthesis, critical for long Kria builds.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- **Handshake rule (immutable):** A transfer completes on the rising clock edge where both VALID and
  READY are high on the same channel. Adding any other condition to this check causes missed
  transfers.
- **Never gate VALID on READY:** A master that waits for `awready` before asserting `awvalid`
  deadlocks against a slave that waits for `awvalid` before asserting `awready`. VALID must be
  raised without checking READY first.
- **Registered READY required:** The AXI spec wants `xREADY` signals to be registered (not
  combinational). A purely combinational READY that reacts to VALID in the same cycle is
  technically non-compliant. Use a skid buffer to absorb the registered-READY throughput penalty.
- **Vivado-generated AXI-Lite peripheral bug (historical):** As of ~2020, ZipCPU formal verification
  found that Vivado's AXI-Lite template core failed to de-assert READY fast enough when the outgoing
  acknowledge channel was stalled. The write path was fixed in a later release; the read path bug
  persisted. Always run formal or behavioral simulation on any Vivado-generated AXI peripheral
  before trusting it.
- **Throughput ceiling without skid buffers:** A simple AXI-Lite slave achieves at most one transfer
  every two clocks. Skid buffers restore full throughput (one transfer per clock).
- **Five-channel structure:** AXI4-Lite uses five independent channels: AW (write address), W (write
  data), B (write response), AR (read address), R (read data). Each channel has its own independent
  VALID/READY handshake. The B-channel response (`bresp`) must be accepted by the master for the
  transaction to fully complete.

### Code Example

```vhdl
-- Minimal AXI-Lite slave write-address channel (VHDL)
-- VALID raised unconditionally; READY is registered
process(aclk)
begin
  if rising_edge(aclk) then
    if aresetn = '0' then
      awready_r <= '0';
    else
      -- Accept when we are idle; de-assert after one cycle
      if awready_r = '0' and s_axi_awvalid = '1' then
        awready_r <= '1';
        awaddr_r  <= s_axi_awaddr;
      else
        awready_r <= '0';
      end if;
    end if;
  end if;
end process;
s_axi_awready <= awready_r;
```

### Relevance to Your Project

Your project drives two BRAM controllers at `0xA0000000` (BRAM0) and `0xA0010000` (BRAM2) via
AXI-Lite. The write path from the Cortex-A53 goes through the AXI SmartConnect in the block design.
The key risk: if `main.c` writes to both BRAMs back-to-back without waiting for `bresp`, the PS AXI
master may pipeline transactions. Ensure your bare-metal driver either polls the write-response
register or uses `Xil_Out32` (which the Xilinx HAL does complete before returning) rather than
direct pointer writes, which may reorder past a write barrier.

## Vivado Block Design / IP Integrator

### Key Findings

- **Never assign a peripheral to address 0x0:** Some Xilinx BSP drivers assert at startup when the
  base address is zero. Vivado's auto-assign correctly starts peripherals above 0x40000000 for GP0.
  Your BRAM0 at `0xA0000000` and BRAM2 at `0xA0010000` are in the correct HP/GP AXI range.
- **Manual address edits require re-validation:** After typing values in the Address Editor, run
  `validate_bd_design` or click *Validate Design* — overlapping or unaligned segments will be
  reported as critical warnings.
- **Address alignment:** Each segment's base address must be a multiple of the segment's size. A 64 KB
  BRAM window starting at `0xA0010000` is valid (0x10000 aligned to 0x10000).
- **DFX designs — top-level Address Editor only:** If you ever add partial reconfiguration, address
  edits must be made in the top-level block design's Address Editor, not in a Block Design Container.
- **Regeneration order:** After modifying the block design, always re-run in this order:
  1. Validate design (`validate_bd_design`)
  2. Generate bitstream wrapper (`make_wrapper`)
  3. Regenerate IP output products (`generate_target all`)
  4. Re-export hardware (`.xsa`) before updating the Vitis platform

### Code Example

```tcl
# Address assignment in TCL (block design context)
# Assign BRAM0 at 0xA0000000, 64KB
assign_bd_address \
    -target_address_space /zynq_ultra_ps_e_0/Data \
    [get_bd_addr_segs bram_ctrl_0/S_AXI/Mem0] \
    -range 64K \
    -offset 0xA0000000

# Assign BRAM2 at 0xA0010000, 64KB
assign_bd_address \
    -target_address_space /zynq_ultra_ps_e_0/Data \
    [get_bd_addr_segs bram_ctrl_2/S_AXI/Mem0] \
    -range 64K \
    -offset 0xA0010000

validate_bd_design
```

### Relevance to Your Project

Your `create_bd.tcl` defines both BRAM controllers and their address assignments. If the TCL script is
replayed on a fresh project, verifying the assigned addresses match the hard-coded `0xA0000000` /
`0xA0010000` values in `main.c` is the first thing to check before synthesis. A mismatch here is the
single most common cause of test failures that look like AXI timeouts.

## Vivado TCL Scripting

### Key Findings

- **Non-project mode is ideal for CI/batch flows:** No `.xpr` file is written; everything is driven
  by Tcl. Vivado holds design state in memory only. Invocation: `vivado -mode batch -source top.tcl`
  (exits after the script) or `vivado -mode tcl -source top.tcl` (stays interactive after).
- **Source order matters:** In non-project mode, `read_vhdl`, `read_xdc`, and `read_bd` commands
  compile files in the order listed. No automatic dependency resolution; you must sequence them.
- **Checkpoint saves are essential:** Use `write_checkpoint` after synthesis, after `opt_design`,
  after `place_design`, and after `route_design`. This allows resuming from any stage without
  re-running expensive earlier steps.
- **Timing reports in batch:** Use `report_timing_summary -file timing.rpt` to persist timing results
  to disk — Vivado will not retain them across sessions in non-project mode.
- **Project mode vs non-project:** Project mode stores runs in a directory tree and manages
  incremental rebuilds automatically. Non-project mode gives explicit control but requires manual
  management of every step. For a KV260 bare-metal demo, project mode is usually easier; non-project
  shines in headless CI.

### Code Example

```tcl
# Minimal non-project batch flow for KV260 AXI-BRAM demo
set PART "xck26-sfvc784-2LV-c"

read_vhdl  ./vhdl/kv260_top.vhd
read_bd    ./bd/design_1.bd
read_xdc   ./xdc/kv260_top.xdc

synth_design -top kv260_top -part $PART -mode out_of_context
write_checkpoint -force ./checkpoints/post_synth.dcp
report_timing_summary -file ./reports/post_synth_timing.rpt

opt_design
place_design
write_checkpoint -force ./checkpoints/post_place.dcp

route_design
write_checkpoint -force ./checkpoints/post_route.dcp
report_timing_summary -file ./reports/post_route_timing.rpt

write_bitstream -force ./output/kv260_top.bit
```

### Relevance to Your Project

Your `create_bd.tcl` script automates block design creation. A complementary implementation script
using the above pattern would let you rebuild the entire project from scratch in headless CI
(e.g., a GitHub Actions runner) without Vivado GUI. The `$PART` string for the K26 SoM is
`xck26-sfvc784-2LV-c` — confirm this with `get_parts *k26*` in the Vivado Tcl console.

## Vitis Bare-Metal / Standalone

### Key Findings

- **BSP provides the foundation:** The standalone BSP handles processor bring-up (cache init,
  exception vectors, stack setup) before `main()` is called. The `xil_printf` it exports is
  intentionally lightweight — it lacks full `printf` floating-point support. Use `printf` from
  `libc` (set in BSP settings) when you need `%f`.
- **STDIN/STDOUT UART selection:** In the BSP domain settings, `STDIN/STDOUT` selects which UART
  feeds `xil_printf`. For KV260, this is typically `psu_uart_1` (the USB-UART bridge on MIO).
  Mismatching UART IDs is a common reason the terminal is silent despite a passing waveform.
- **Nested interrupt support:** Include `xil_exception.h` and call
  `Xil_ExceptionInit()` / `Xil_ExceptionRegisterHandler()` before enabling interrupts. The GIC
  (`XScuGic` on Zynq UltraScale+) handles IRQ routing; `XScuGic_Connect` links an interrupt ID to
  your ISR.
- **BSP source reset:** After modifying hardware and re-exporting the `.xsa`, right-click the
  platform in the Vitis Explorer and choose *Update Hardware Specification*, then rebuild the
  platform. Skipping this step leaves stale `xparameters.h` addresses.
- **Linker script address:** The default linker script places `.text` in DDR at `0x0`. For KV260
  bare-metal, ensure the DDR region matches the Zynq MPSoC DDR map (starting at `0x00000000`,
  2 GB). Overriding to SRAM (OCM at `0xFFFC0000`, 256 KB) is possible for ultra-fast boot tests.

### Code Example

```c
/* Minimal AXI-BRAM write/read test — bare-metal, standalone BSP */
#include "xil_io.h"
#include "xil_printf.h"

#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL
#define TEST_PATTERN 0xDEADBEEFUL

static int test_bram(u32 base, const char *name)
{
    Xil_Out32(base, TEST_PATTERN);
    u32 rd = Xil_In32(base);
    if (rd == TEST_PATTERN) {
        xil_printf("%s PASS (read 0x%08X)\r\n", name, rd);
        return 0;
    }
    xil_printf("%s FAIL (expected 0x%08X, got 0x%08X)\r\n",
               name, TEST_PATTERN, rd);
    return -1;
}

int main(void)
{
    xil_printf("KV260 AXI-BRAM test start\r\n");
    int rc = 0;
    rc |= test_bram(BRAM0_BASE, "BRAM0");
    rc |= test_bram(BRAM2_BASE, "BRAM2");
    xil_printf("Overall: %s\r\n", rc == 0 ? "PASS" : "FAIL");
    return rc;
}
```

### Relevance to Your Project

This code is the functional core of your `main.c`. The `Xil_Out32` / `Xil_In32` accessors issue
`dmb` (Data Memory Barrier) instructions around each access, ensuring the Cortex-A53 does not
reorder the write past the read. Bare pointer writes (`*(volatile u32*)addr = val`) skip this
barrier and can cause intermittent test failures on multi-core or cache-enabled builds.

## XDC Timing Constraints

### Key Findings

- **set_input_delay / set_output_delay syntax (Vivado 2025.1):**
  `set_input_delay -clock clk_out1 -max 3.0 [get_ports {data_in[*]}]`
  Both max and min values should be provided for full hold/setup analysis.
- **set_clock_groups for unrelated clocks:** When the PS and PL clocks are asynchronous (e.g., your
  100 MHz PL clock from `clk_wiz_0` and the PS internal `pl_clk0`), use:
  `set_clock_groups -asynchronous -group {clk_pl} -group {clk_wiz_out}`
  This tells Vivado not to analyze timing across the clock-domain boundary, preventing false
  violations.
- **Unconstrained ports generate high-severity warnings:** Vivado flags any port not covered by an
  input/output delay constraint as a critical warning. For a pure AXI-BRAM demo with no external
  I/O, this mainly affects the USB-UART TX/RX pins and any debug LEDs on the KV260 carrier.
- **AXI bus timing is internal:** AXI interfaces between PS and BRAM controllers in the PL are
  entirely internal (point-to-point in the block design). They require no user-written timing
  constraints — the block design synthesis handles them. Only board-level I/O (UART, GPIO, etc.)
  needs explicit `set_input/output_delay`.
- **Primary reference:** UG903 (Vivado Design Suite User Guide: Using Constraints) and UG835
  (Vivado Design Suite Tcl Command Reference) are the authoritative AMD sources for 2025.1.

### Code Example

```tcl
# kv260_top.xdc — representative constraints for KV260 AXI-BRAM demo

# Primary 100 MHz PL clock from PS
create_clock -period 10.000 -name pl_clk0 [get_ports pl_clk0]

# USB-UART (board-level I/O only; no setup/hold data for async UART)
set_input_delay  -clock pl_clk0 -max 2.0 [get_ports uart_rxd]
set_input_delay  -clock pl_clk0 -min 0.5 [get_ports uart_rxd]
set_output_delay -clock pl_clk0 -max 2.0 [get_ports uart_txd]
set_output_delay -clock pl_clk0 -min 0.0 [get_ports uart_txd]

# If clk_wiz generates a derived clock, declare it asynchronous from the source
# set_clock_groups -asynchronous \
#     -group [get_clocks pl_clk0] \
#     -group [get_clocks clk_wiz_0_clk_out1]
```

### Relevance to Your Project

Your `kv260_top.vhd` likely exposes the PS clock on a port and routes it to the block design. The
single most important constraint is `create_clock` for that pin — without it, Vivado cannot perform
any meaningful timing analysis. Run *Report Clock Interaction* after synthesis to identify any
unexpected CDC (clock-domain crossing) warnings that might indicate a wiring error in the block
design.

## Kria KV260 / K26 SoM

### Key Findings

- **MIO bank layout:**
  - Bank 500 (PS-side SOM): QSPI flash, SD/eMMC, I2C (×2), TPM SPI — fixed at SOM level
  - Bank 501 (PS-side PMU): PMU power-management pins + user I/O routed to carrier
  - Bank 502 (PS-side user): User-defined I/O via SOM-to-carrier connector
  - All MIO banks operate at 1.8 V on the K26
- **Boot sequence (QSPI primary, SD secondary):** The FSBL loads from QSPI. U-Boot then applies a
  carrier-specific PMU power overlay (different for KV260 vs KR260). For JTAG bare-metal bring-up,
  set the boot mode to JTAG via the SW1 dip switch on the KV260 carrier (pins 1-4 = 0000 for JTAG).
- **Dynamic MIO reconfiguration:** Unlike older Zynq-7000 designs that locked MIO at bitstream time,
  the Kria architecture reconfigures carrier-specific MIO at runtime via PMU incremental
  configuration. This is relevant if you add GPIO or SPI peripherals to a future project revision.
- **KV260 vs KR260 differences:** The KR260 adds dual GEM Ethernet (RGMII on GEM1, SGMII via GTR
  on GEM0) through the carrier board. The KV260 does not. Your AXI-BRAM demo is independent of
  this difference.
- **Boot mode reference:** UG1085 (Zynq UltraScale+ MPSoC Technical Reference Manual) Section 11
  documents the boot mode pin encoding. For JTAG: MODE[3:0] = 0000.

### Code Example

```tcl
# TCL snippet: confirm part and device in Vivado for KV260
# Run in Vivado Tcl console to verify target device
puts "Part: [get_property PART [current_project]]"
# Expected: xck26-sfvc784-2LV-c

# List available PS UART interfaces for BSP configuration
get_bd_cells -hierarchical -filter {VLNV =~ *axi_uart*}
# PS UART (MIO-based) does not appear here — it is configured
# in the Zynq UltraScale+ PS IP under I/O Configuration > UART

# Set PS UART to MIO 36-37 (KV260 USB-UART bridge)
# In create_bd.tcl:
set_property -dict [list \
    CONFIG.PSU__UART__PERIPHERAL__ENABLE {1} \
    CONFIG.PSU__UART__PERIPHERAL__IO    {MIO 36 .. 37} \
] [get_bd_cells zynq_ultra_ps_e_0]
```

### Relevance to Your Project

UART output over USB requires `PSU__UART__PERIPHERAL__IO` to be set to `MIO 36..37` in the PS IP
configuration — this is the path to the USB-UART bridge on the KV260 carrier. If the block design
TCL script omits this property, `xil_printf` output will be silent even with a valid bitstream and
application. Verify this in your `create_bd.tcl`.

## AMD/Xilinx Tool Updates (2025.x)

### Key Findings

- **Vitis Unified IDE is now default in 2025.1; Classic IDE deprecated:** The Vitis Classic IDE
  (Eclipse-based) is deprecated as of 2025.1. New projects should target the Vitis Unified IDE.
  The IP example designs in the IP catalog have been updated to support the Unified IDE flow.
- **VHDL-2019 simulation support added in Vivado 2025.1:** You can now simulate VHDL-2019 constructs
  (protected types, enhanced generics, `integer_vector`, etc.) in Vivado's simulator (xsim). This
  is a significant enabler for modern VHDL testbenches.
- **Vivado 2025.1 known issue — ECO flow clock routing:** There is a reported issue with the ECO
  (Engineering Change Order) flow causing incorrect clock routing in certain conditions. Avoid the
  ECO flow for production builds until a patch is confirmed.
- **Vivado 2025.1 known issue — W25Q12PW flash programming failure:** Flash programming fails for
  W25Q12PW devices. If your KV260 carrier uses this QSPI part, check the AMD adaptive support
  pages for the patch workaround.
- **Vitis 2025.1 known issue — file dialog on AlmaLinux/RHEL 9.5:** The file/directory selection
  dialog does not open on AlmaLinux 9.5 and Red Hat Enterprise Linux 9.5. Workaround: use the
  manual path entry field or upgrade to 2025.1.1 which resolves this.
- **2025.2 is available:** AMD has released Vivado/Vitis 2025.2 (UG973 updated November 2025).
  Notable: GTR wizard updates and CDC fixes in IP catalog. If you started on 2025.1, an upgrade to
  2025.1.1 (patch release) is lower risk than jumping to 2025.2 mid-project.

### Code Example

```vhdl
-- VHDL-2019 feature now simulatable in Vivado 2025.1: enhanced generics
-- This was compile-only in earlier Vivado releases; xsim now supports it
entity bram_ctrl_wrapper is
  generic (
    type DATA_TYPE is (<>);          -- VHDL-2019 unconstrained type generic
    DATA_WIDTH : positive := 32;
    ADDR_WIDTH : positive := 10
  );
  port (
    clk   : in  std_logic;
    we    : in  std_logic;
    addr  : in  std_logic_vector(ADDR_WIDTH-1 downto 0);
    din   : in  std_logic_vector(DATA_WIDTH-1 downto 0);
    dout  : out std_logic_vector(DATA_WIDTH-1 downto 0)
  );
end entity;
-- Note: instantiation with type generic requires VHDL-2019 mode in xsim
-- Compile flags: --2019 (xvhdl --2019 bram_ctrl_wrapper.vhd)
```

### Relevance to Your Project

If you are running Vivado/Vitis 2025.1 (as your project targets), the ECO flow issue is worth noting
if you need to patch the design post-synthesis. The VHDL-2019 simulation support means your
testbenches can adopt modern VHDL features without switching simulators. For the UART dialog issue
on Linux, use the Vitis command-line flow (`xsct`) as a workaround — it is also better for
scripted/CI flows.
