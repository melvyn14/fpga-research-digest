# FPGA Research Digest - 2026-07-01

## Executive Summary

- **AXI-Lite backpressure is the #1 source of silent bugs**: when the PS holds BREADY low, the slave must lower both AWREADY and WREADY — easy to miss in simulation if BREADY is tied high, but critical once the demo's C loop runs without stalls.
- **Use AXI SmartConnect (not legacy AXI Interconnect)** for all new Zynq UltraScale+ block designs; it requires only a single clock/reset pair and auto-inserts protocol converters between AXI4 and AXI4-Lite slaves (like the BRAM controllers at 0xA0000000 / 0xA0010000).
- **Vivado 2025.1 introduced a new "Clocking and Reset" view in IP Integrator** — use it to verify FCLK_CLK0 actually reaches both BRAM controllers after regenerating the block design.
- **Kria KV260 bare-metal has two boot paths**: JTAG (xsct script, ideal for iterative development) and QSPI (standalone deployment); the board ships in QSPI32 mode so JTAG requires no hardware switch change.
- **Vivado 2025.x reports no unresolved BRAM/AXI known issues** as of this digest, but a community-reported Vivado 2025 bug limits custom AXI-full peripherals to a 1 KB address decode — does not affect the Xilinx AXI BRAM Controller IP used in this project.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- All five AXI channels (AW, W, B, AR, R) use the same VALID/READY two-way handshake. A transfer completes only when **both** VALID and READY are asserted on the same rising clock edge.
- **Critical pitfall — backpressure propagation**: if the master holds BREADY low (write response channel), the slave **must** de-assert AWREADY and WREADY to avoid accepting new transactions it cannot yet complete. Designs that tie BREADY high in bench testing silently mask this bug.
- **VALID must not wait for READY**: the AXI spec forbids a master from polling READY before asserting VALID. The source asserts VALID whenever it has data; the sink asserts READY whenever it can accept — the pair are independent.
- Xilinx's own AXI-Lite reference core shipped with a read-path bug that was only fixed after Vivado 2016.3; always verify with a waveform or formal check, not just functional simulation.
- AXI4-Stream signals: TVALID / TREADY govern flow; **TDATA must remain stable** while TVALID is asserted and TREADY has not yet responded; TLAST marks the last beat of a packet — omitting it in streaming IPs causes downstream FIFOs to never flush.

### Code Example

```vhdl
-- Minimal AXI-Lite slave write response, correct backpressure handling
process(S_AXI_ACLK)
begin
  if rising_edge(S_AXI_ACLK) then
    if S_AXI_ARESETN = '0' then
      axi_bvalid  <= '0';
      axi_bresp   <= "00";
      axi_awready <= '0';
      axi_wready  <= '0';
    else
      -- Only accept address+data when we can also issue the response
      if (axi_awready = '0' and S_AXI_AWVALID = '1'
          and S_AXI_WVALID = '1' and axi_bvalid = '0') then
        axi_awready <= '1';
        axi_wready  <= '1';
      else
        axi_awready <= '0';
        axi_wready  <= '0';
      end if;

      -- Hold BVALID until master asserts BREADY
      if (axi_awready = '1') then
        axi_bvalid <= '1';
        axi_bresp  <= "00";  -- OKAY
      elsif S_AXI_BREADY = '1' then
        axi_bvalid <= '0';   -- clear only after master accepts
      end if;
    end if;
  end if;
end process;
```

### Relevance to Your Project

The KV260 PS (Cortex-A53) is the AXI master. The bare-metal C loop in `main.c` issues writes then immediately reads back — if `BREADY` is not handled correctly in a custom slave, you could get stale data or a hung bus. For the Xilinx BRAM Controller IP used at 0xA0000000 / 0xA0010000 this is handled for you, but understanding this is essential before adding any custom AXI slave registers.

## Vivado Block Design / IP Integrator

### Key Findings

- **SmartConnect is the current standard** (successor to AXI Interconnect v2). Key advantages: single `aclk`/`aresetn` pair instead of per-port clock connections; automatic protocol bridging between AXI4 and AXI4-Lite slaves; reduced resource usage on UltraScale+ vs. the old interconnect.
- **Connection Automation** in IP Integrator can instantiate the SmartConnect, Block Memory Generator, and Proc Sys Reset automatically when you add an AXI BRAM Controller — but always verify the generated address assignments in the Address Editor afterward.
- **Address Editor workflow**: select the Address Editor tab → right-click a master interface → "Auto Assign Address". For multiple BRAM slaves (BRAM0 at 0xA000_0000, BRAM2 at 0xA001_0000) manually verify that the generated offset and range match your bare-metal constants.
- **Vivado 2025.1 new "Clocking and Reset" view** in IP Integrator provides a dedicated panel showing which clock/reset domains each IP belongs to — invaluable for verifying that both BRAM controllers share the same `FCLK_CLK0`.
- After any IP upgrade or parameter change, always click **Validate Design (F6)** before regenerating output products; skipping this step can produce silent mismatches between the block design and the generated HDL wrappers.

### Code Example

```tcl
# TCL snippet: verify address assignments match bare-metal constants
set bram0_seg [get_bd_addr_segs -of [get_bd_intf_pins axi_bram_ctrl_0/S_AXI]]
set bram2_seg [get_bd_addr_segs -of [get_bd_intf_pins axi_bram_ctrl_1/S_AXI]]

set bram0_offset [get_property OFFSET [get_bd_addr_segs $bram0_seg]]
set bram2_offset [get_property OFFSET [get_bd_addr_segs $bram2_seg]]

if {$bram0_offset ne "0xA0000000"} {
  error "BRAM0 offset mismatch: $bram0_offset (expected 0xA0000000)"
}
if {$bram2_offset ne "0xA0010000"} {
  error "BRAM2 offset mismatch: $bram2_offset (expected 0xA0010000)"
}
puts "Address assignments verified OK"
```

### Relevance to Your Project

Your `create_bd.tcl` script creates BRAM0 at 0xA0000000 and BRAM2 at 0xA0010000. Adding the address-verification snippet above as a post-block-design sanity check prevents silent failures where auto-assignment shifts addresses, causing PASS/FAIL reads in `main.c` to hit the wrong slave.

## Vivado TCL Scripting

### Key Findings

- **Export Block Design** (`File → Export → Export Block Design`) generates a self-contained `.tcl` script that recreates the entire IPI diagram — this is the canonical way to put your block design under version control.
- **Non-project mode** (memory-only flow) lets you build bitstreams in CI without a `.xpr` file: `read_vhdl`, `read_xdc`, `synth_design`, `opt_design`, `place_design`, `route_design`, `write_bitstream`. No GUI required; suitable for automated nightly builds.
- **Batch mode invocation**: `vivado -mode batch -source script.tcl` runs a script and exits. Use `-notrace` to suppress Tcl command echo for cleaner CI logs.
- In project mode, use `open_project` / `update_compile_order` / `launch_runs impl_1 -to_step write_bitstream` for incremental flows that preserve implementation results.
- The `write_hw_platform -fixed -include_bit -force` command (replaces `write_sysdef`) generates the XSA consumed by Vitis — always run this after a successful `write_bitstream`.

### Code Example

```tcl
# Non-project batch build: synth + impl + XSA in one script
# Usage: vivado -mode batch -source build.tcl

set PART "xck26-sfvc784-2LV-c"
set TOP  "kv260_top"
set OUTDIR "./output"

file mkdir $OUTDIR

# Read sources
read_vhdl  [glob ./vhdl/*.vhd]
read_xdc   [glob ./xdc/*.xdc]

# Source the block-design recreation script
source ./tcl/create_bd.tcl
make_wrapper -files [get_files *.bd] -top
read_vhdl [glob ./kv260.gen/sources_1/bd/*/hdl/*_wrapper.vhd]

# Synthesize
synth_design -top ${TOP}_wrapper -part $PART -flatten_hierarchy rebuilt
write_checkpoint -force $OUTDIR/post_synth.dcp

# Implement
opt_design
place_design
route_design
write_checkpoint -force $OUTDIR/post_route.dcp

# Outputs
write_bitstream  -force $OUTDIR/${TOP}.bit
write_hw_platform -fixed -include_bit -force $OUTDIR/${TOP}.xsa
puts "Build complete: $OUTDIR/${TOP}.xsa"
```

### Relevance to Your Project

Your repo already has `create_bd.tcl`. Wrapping it in the non-project batch script above lets you rebuild the full bitstream + XSA from scratch in a CI environment without requiring a pre-existing `.xpr`, making the repo self-contained and reproducible.

## Vitis Bare-Metal / Standalone

### Key Findings

- **BSP stdout configuration**: in the Vitis BSP settings, `stdout` must point to the PS UART (`psuart1` on KV260 routed to the USB-UART bridge) for `xil_printf` to produce output. If the wrong UART is selected, the board appears silent even when the application runs correctly.
- **XSA → Platform → Domain → Application** is the Vitis 2025 unified flow. Create a `standalone` domain targeting `psu_cortexa53_0` (APU core 0) and ensure BSP libraries include `xilmem` / `xiltimer` only if you need them — unused drivers bloat BSP compile time.
- **Linker script memory regions**: for a bare-metal demo without DDR init, place all sections in `psu_r5_0_atcm_MEM_0` or `ps_ddr_0` (DDR requires `psu_ddr_0` init by FSBL or your startup code). The default Vitis linker puts `.text` and `.data` in DDR, which is fine if the bitstream is loaded by JTAG (FSBL initialises DDR first).
- `xil_printf` is lighter than `printf` (no floating-point format support) — use it throughout bare-metal firmware to keep code-size small and avoid pulling in the full newlib.
- Matching tool versions is mandatory: a Vivado 2025.1 XSA fed into a Vitis 2024.2 workspace produces BSP mismatches. Always use the same major.minor release.

### Code Example

```c
/* main.c snippet — robust AXI-BRAM write/read with explicit cache management */
#include "xil_printf.h"
#include "xil_cache.h"
#include "xil_io.h"

#define BRAM0_BASE  0xA0000000U
#define BRAM2_BASE  0xA0010000U
#define PATTERN0    0xDEADBEEFU
#define PATTERN2    0xCAFEBABEU

static int verify_bram(u32 base, u32 pattern, const char *name) {
    Xil_Out32(base, pattern);
    /* Flush D-cache line if caches enabled; PS AXI-Lite bypasses L1 but not L2 */
    Xil_DCacheFlushRange(base, 4);
    u32 readback = Xil_In32(base);
    if (readback == pattern) {
        xil_printf("%s PASS: wrote 0x%08X, read 0x%08X\r\n", name, pattern, readback);
        return 0;
    }
    xil_printf("%s FAIL: wrote 0x%08X, read 0x%08X\r\n", name, pattern, readback);
    return -1;
}

int main(void) {
    xil_printf("KV260 AXI-BRAM Demo\r\n");
    int rc = 0;
    rc |= verify_bram(BRAM0_BASE, PATTERN0, "BRAM0");
    rc |= verify_bram(BRAM2_BASE, PATTERN2, "BRAM2");
    xil_printf(rc == 0 ? "All tests PASSED\r\n" : "One or more tests FAILED\r\n");
    return rc;
}
```

### Relevance to Your Project

Adding `Xil_DCacheFlushRange` after each write guards against a subtle class of failures where the D-cache returns a locally-cached value instead of reading back over AXI. For AXI-Lite peripherals below 4 GB this is usually not an issue when caches are disabled (the Vitis standalone BSP disables caches by default on reset), but explicitly flushing is defensive and documents intent.

## XDC Timing Constraints

### Key Findings

- For Zynq UltraScale+ (K26 SoM), `FCLK_CLK0` is generated by the PS PLL — **do not add a `create_clock` for it in the XDC**; it is already defined as a generated clock by the PS7/MPSoC IP. Adding a second definition creates a duplicate-clock error.
- Use `create_generated_clock` only if you derive additional clocks from `FCLK_CLK0` using a BUFGCE or MMCM in PL fabric.
- **`set_clock_groups -asynchronous`** is required whenever two clock domains in the PL do not have a deterministic phase relationship. For the AXI-BRAM demo (single-clock design), this is not needed, but add it the moment a second PL clock (e.g., from an external oscillator on the carrier card) is introduced.
- **`set_input_delay` / `set_output_delay`** apply to signals crossing the chip boundary (IOs). For PS↔PL AXI signals that stay on-chip, these constraints are unnecessary and should be omitted to avoid false timing failures.
- The AMD-provided KV260 `.xdc` from the board support files (CCDR package) covers all carrier card IOs; for a pure PS-to-PL AXI design with no external IOs, the XDC can be minimal — just a clock constraint if needed.

### Code Example

```xdc
## kv260_axi_bram.xdc
## Minimal constraint file for pure PS-to-PL AXI design on KV260

## FCLK_CLK0 is auto-defined by the MPSoC IP — no create_clock needed here.
## If you add a PL-side oscillator (e.g., 125 MHz from carrier card SI5332):
# create_clock -name clk_pl_125 -period 8.000 [get_ports clk_pl_125_p]

## Mark PL clock and FCLK_CLK0 as asynchronous if both present
# set_clock_groups -asynchronous \
#   -group [get_clocks clk_pl_125] \
#   -group [get_clocks -include_generated_clocks clk_out1_kv260_top]

## False path on asynchronous reset crossing (if used)
# set_false_path -from [get_ports sys_reset_n] -to [all_registers]

## For JTAG-only debug builds with no PL IOs, no constraints are strictly required.
## Vivado will warn but will not error on an unconstrained internal-only design.
set_property BITSTREAM.GENERAL.COMPRESS TRUE [current_design]
set_property BITSTREAM.CONFIG.SPI_BUSWIDTH 4 [current_design]
```

### Relevance to Your Project

The KV260 AXI-BRAM demo has no external PL IOs, so timing constraints are minimal. The `BITSTREAM.CONFIG.SPI_BUSWIDTH 4` property matches the KV260's QSPI32 boot mode and reduces configuration time when loading via JTAG over SPI. Add `set_clock_groups` only when you extend the design with a second clock domain.

## Kria KV260 / K26 SoM

### Key Findings

- **Boot mode**: KV260 ships with QSPI32 as the primary boot device (on-SOM QSPI, factory-programmed). The SD card is the secondary boot device. For bare-metal development, **JTAG is the recommended path** — no hardware switch change is needed; connect via USB and use `xsct` or the Vitis debugger.
- **JTAG boot script**: using `xsct`, load the FSBL, bitstream, and ELF sequentially. Alternatively, Vitis's "Launch on Hardware" does this automatically from the Run Configuration dialog.
- **MIO pinout**: the K26 SOM exposes USB-UART via MIO[38:39] (PS UART1) routed to the FTDI chip on the KV260 carrier card — this is why `psuart1` must be selected in the BSP for `xil_printf` output.
- **PL-to-PS AXI addressing**: the PS High-Performance (HP) ports on the K26 give the PL access to DDR; the PS General Purpose (GP) master ports give the PS access to PL slaves (which is what the AXI-BRAM demo uses). Do not confuse HP ports (PL master → PS slave → DDR) with GP ports (PS master → PL slave → BRAM).
- Vivado board files for the KV260 are available in the board repository and automate the PS configuration (DDR, MIO, PLL) when using board presets in IP Integrator.

### Code Example

```tcl
## xsct script: load bitstream + bare-metal ELF via JTAG (no SD/QSPI required)
## Run with: xsct load_baremetal.tcl

connect
targets -set -filter {name =~ "APU*"}

# Reset the entire SoC cleanly
rst -system

# Program PL bitstream
fpga -file ./output/kv260_top.bit

# Load FSBL to initialise DDR and clocks, then jump to our app
target -set -filter {name =~ "Cortex-A53 #0"}
dow ./fsbl/fsbl.elf
con
after 3000   ;# wait for FSBL to complete DDR init

# Stop FSBL, load application
stop
dow ./output/kv260_axi_bram.elf
con

puts "Application running — open a terminal at 115200 baud on the USB-UART port"
```

### Relevance to Your Project

This `xsct` script replaces the multi-step manual process of loading files through the Vitis GUI. Running it from CI or a Makefile gives a reproducible, one-command hardware test cycle: build (Vivado + Vitis) → load → observe PASS/FAIL on UART.

## AMD/Xilinx Tool Updates — Vivado/Vitis 2025.1

### Key Findings

- **New AXI Switch IP** (Vivado 2025.1): a fully customizable RTL-based interconnect supporting multiple AXI master/slave endpoints with mixed interface types and widths. Relevant if you extend the demo to route multiple PS GP ports to different PL regions.
- **New IP Integrator views**: dedicated "Clocking and Reset" and "Interrupt and AXI4-Lite" panels make it easier to spot missing clock connections and unconnected interrupt ports during block design development.
- **New Pblock Planner**: a single GUI pane for all floorplanning tasks — useful when constraining the BRAM locations to specific PL columns for timing closure.
- **Segmented configuration** (2025.1): allows the PS to boot and start Linux before the PL bitstream is loaded — useful if you ever migrate from bare-metal to a Linux + PL co-design flow.
- **Vivado 2025.1.1 known issues**: no unresolved issues affecting AXI BRAM Controller or Block Memory Generator as of this digest. A Digilent community report documents a 1 KB address-decode cap on *custom* AXI-full peripherals created via the IP wizard — this does **not** affect Xilinx's own AXI BRAM Controller v4.x IP.
- **Vitis 2025.1** release notes document improvements to the embedded software development flow; the XSA → Platform → Application creation sequence is unchanged from 2024.2.

### Code Example

```tcl
## Vivado 2025.1: use the new report_dfx_summary (GUI support added)
## and verify no critical warnings after block design regeneration

open_project ./kv260.xpr
open_bd_design [get_files *.bd]

## Validate the block design programmatically before generating outputs

## Regenerate output products

## Export XSA for Vitis

## Optional: check for timing violations after implementation

set wns [get_property STATS.WNS [get_runs impl_1]]

  puts "WARNING: Timing not met, WNS = ${wns} ns"
} else {
  puts "Timing met, WNS = ${wns} ns"
}
```

### Relevance to Your Project

The `validate_bd_design` + WNS check snippet can be added to the end of `create_bd.tcl` as a built-in gate on every build, catching block design errors and timing regressions before they silently produce a broken XSA that fails in Vitis.
