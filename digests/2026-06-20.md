## Executive Summary
- **AXI handshake backpressure** is the most common bug class in custom AXI-Lite/BRAM designs: VALID must never wait on READY, and READY must be allowed to deassert independently — relevant if you ever swap the stock `axi_bram_ctrl` for a custom slave in front of your two BRAMs.
- **Address Editor offset/range alignment**: your two BRAMs at `0xA0000000` (BRAM0) and `0xA0010000` (BRAM2) must have Range set to a power-of-2 size matching (or exceeding) the actual BRAM depth, and the Offset must be aligned to that Range — misalignment is a frequent silent cause of address-decode bugs after regenerating the block design.
- **`xil_printf` has no `%f`** and limited format support (`%d`, `%l`, `%x`, `%c`, `%s`) — if your PASS/FAIL reporting in `main.c` ever needs floating-point or richer formatting, you'll need `printf` from libc (larger footprint) instead.
- **Non-project-mode TCL batch builds** (`vivado -mode batch -source create_bd.tcl`) are the right pattern for reproducible CI-style rebuilds of your block design — make sure `regenerate_bd_layout` and `validate_bd_design`/F6-equivalent checks are scripted before `generate_target`.
- **KV260 boot-mode and HPM port** notes: AXI BRAM Controller should attach to `M_AXI_HPM0_FPD`, with unused HPM1 deselected in the PS configuration to avoid leaving an unconnected master port that can trip block-design validation.

## AXI Protocol / AXI-Lite / AXI-Stream
### Key Findings
- All AXI4/AXI4-Lite signals are sampled on the clock's rising edge; all driven signals must change only after that edge — violating this in custom logic (e.g., a hand-rolled register-bank wrapper) causes intermittent timing closure failures that don't show up in functional sim.
- AWVALID and WVALID are explicitly independent — a master is never required (and a slave must never assume) that AW is accepted before W data arrives, or vice versa. Assuming AW-then-W ordering is a classic deadlock-inducing bug.
- Backpressure handling is the most-missed case: if BREADY is held low by the master, the slave must lower AWREADY/WREADY; if RREADY is held low, the slave must lower ARREADY. Pure functional simulation without backpressure stress-testing won't catch this.
- AXI-Stream specific: don't leave stream output ports floating — IP like the AXI4-Stream Broadcaster has no default `tready`, so a floating/unconnected downstream port will stall the whole pipeline.
- Output signals (on any AXI channel) must not be combinationally derived straight from inputs — register your handshake logic.

### Code Example
```vhdl
-- Minimal AXI4-Lite write-channel handshake skeleton (single-cycle accept),
-- illustrating correct independent AW/W handling and registered outputs.
process(s_axi_aclk)
begin
  if rising_edge(s_axi_aclk) then
    if s_axi_aresetn = '0' then
      awready_r <= '0';
      wready_r  <= '0';
      bvalid_r  <= '0';
    else
      -- AW and W are accepted independently, never gated on each other
      awready_r <= not awready_r and s_axi_awvalid;
      wready_r  <= not wready_r  and s_axi_wvalid;

      if awready_r = '1' and wready_r = '1' and s_axi_bready = '1' then
        bvalid_r <= '1';   -- only assert once both channels have completed
      elsif s_axi_bready = '1' then
        bvalid_r <= '0';   -- respect backpressure: don't force BVALID low early
      end if;
    end if;
  end if;
end process;

s_axi_awready <= awready_r;
s_axi_wready  <= wready_r;
s_axi_bvalid  <= bvalid_r;
```

### Relevance to Your Project
Your project currently relies on the stock `axi_bram_ctrl` IP, which already implements correct AXI4-Lite handshake semantics, so you're insulated from these bugs today. The risk surface opens up if you later add a custom AXI-Lite peripheral (e.g., a status/control register block) between the PS and your BRAMs — backpressure and independent-channel handling are exactly where hand-written AXI slaves break under load, even if the simple A53 read/write loop in `main.c` never exercises backpressure (single in-flight transaction, no burst).

## Vivado Block Design / IP Integrator
### Key Findings
- Connection Automation auto-creates the AXI Interconnect and Processing System Reset IP, and auto-populates the Address Editor — but offset/range fields are interdependent and must stay aligned; manual edits after automation are a common source of overlap errors.
- `validate_bd_design` (F6 in GUI) runs DRCs including clock-frequency-on-pin checks, but does NOT catch every issue at creation time — re-validate after any manual port/clock rewiring.
- `regenerate_bd_layout` only redraws the graphical layout; it does not re-run connectivity checks, so always follow it with validation before `generate_target`.
- Memory-mapped offset address and range fields must be power-of-2 aligned in the Address Editor; for two adjacent BRAM controllers like yours (BRAM0 at `0xA000_0000`, BRAM2 at `0xA001_0000`), confirm the assigned Range (typically 64KB per default AXI BRAM Controller config) doesn't overlap and matches your actual BRAM depth, or address decode will silently fold addresses.

### Code Example
```tcl
# Re-validate and regenerate a block design non-interactively before export
open_bd_design [get_files kv260_bd.bd]
regenerate_bd_layout
validate_bd_design
if {[get_msg_config -count -severity "Critical Warning"] > 0 || \
    [get_msg_config -count -severity "Error"] > 0} {
    puts "ERROR: block design validation failed, aborting build"
    exit 1
}
generate_target all [get_files kv260_bd.bd]
```

### Relevance to Your Project
Your `create_bd.tcl` builds the block design containing the Zynq UltraScale+ PS, AXI Interconnect, and two AXI BRAM Controllers feeding BRAM0/BRAM2. Anytime you regenerate the block design (e.g., after a Vivado version bump to 2025.1), add an explicit `validate_bd_design` + address-editor sanity check step to your script — silent address range overlap between BRAM0 and BRAM2 would manifest as your `main.c` PASS/FAIL test reading back BRAM0 data from what it thinks is BRAM2 (or vice versa) without any build-time error.

## Vivado TCL Scripting
### Key Findings
- Non-Project Mode (pure Tcl, no `.xpr`) puts the developer in full control of sources and ordering, but the script author is responsible for explicitly re-running synthesis/implementation stages after every source edit — there's no incremental "stale" detection like Project Mode provides.
- Batch execution: `vivado -mode batch -source script.tcl -tclargs <args>` opens Vivado, runs the script, and exits — the standard pattern for CI/headless builds of your KV260 design.
- `apply_bd_automation` is the scripted equivalent of the GUI's "Run Connection/Block Automation" — e.g. `apply_bd_automation -rule xilinx.com:bd_rule:axi4 -config {Slave ... Clk Auto} [get_bd_intf_pins axi_bram_ctrl_0/S_AXI]` wires clock/reset/interconnect automatically and is far less brittle across Vivado versions than manually instantiating and wiring every interconnect cell.
- For non-project implementation flows, the documented stage sequence is `opt_design` → `place_design` → `phys_opt_design` (optional) → `route_design` → `write_bitstream`, each invoked as a discrete Tcl command with checkpoints (`write_checkpoint`) saved between stages for resumability.

### Code Example
```tcl
# Pattern for building two AXI BRAM controllers with automation, matching
# the BRAM0/BRAM2 layout in this project
create_bd_cell -type ip -vlnv xilinx.com:ip:axi_bram_ctrl:4.1 axi_bram_ctrl_0
create_bd_cell -type ip -vlnv xilinx.com:ip:axi_bram_ctrl:4.1 axi_bram_ctrl_2

foreach {ctrl base} {axi_bram_ctrl_0 0xA0000000 axi_bram_ctrl_2 0xA0010000} {
    apply_bd_automation -rule xilinx.com:bd_rule:axi4 \
        -config { Master "/zynq_ultra_ps_e_0/M_AXI_HPM0_FPD" Clk "Auto" } \
        [get_bd_intf_pins ${ctrl}/S_AXI]
    set_property offset $base [get_bd_addr_segs "zynq_ultra_ps_e_0/Data/SEG_${ctrl}_Mem0"]
}

validate_bd_design
save_bd_design
```

### Relevance to Your Project
Your `create_bd.tcl` is exactly this non-project-mode pattern. Wrapping address assignment in a `foreach` keyed on controller name and target base address (as above) is more maintainable than hardcoding two near-duplicate blocks, and makes it trivial to add a third BRAM controller later without copy-paste address bugs.

## Vitis Bare-Metal / Standalone
### Key Findings
- `xil_printf` (from `xil_printf.h`) is the lightweight standalone-BSP print function — it has a much smaller code/stack footprint than libc `printf` but only supports `%d`, `%l`, `%x`, `%c`, `%s` (no `%f`).
- The standalone BSP defaults stdout/stdin to UART 0; this is configurable in BSP settings if your carrier card wires the USB-UART to a different PS UART instance.
- For Zynq UltraScale+ (KV260 is APU/Cortex-A53), enabling GIC-driven interrupts requires both registering the handler via `XScuGic_Connect`/`XScuGic_SetPriorityTriggerType` and explicitly enabling the corresponding bit in `GICD_ISENABLER#` (`XScuGic_Enable`) — a commonly missed second step that leaves an ISR "registered but silent."
- The linker script (`lscript.ld`) defines memory region placement (OCM, DDR, etc.); double-check the base address/size of each region matches your actual platform's DDR/OCM map, especially after switching hardware platforms (XSA) — a stale linker script silently truncates or mis-locates `.bss`/`.heap`.

### Code Example
```c
#include "xil_printf.h"
#include "xparameters.h"

#define BRAM0_BASEADDR XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR /* 0xA0000000 */
#define BRAM2_BASEADDR XPAR_AXI_BRAM_CTRL_1_S_AXI_BASEADDR /* 0xA0010000 */

int test_bram(u32 base, const char *name) {
    u32 pattern = 0xDEADBEEF;
    Xil_Out32(base, pattern);
    u32 readback = Xil_In32(base);
    if (readback == pattern) {
        xil_printf("%s: PASS (wrote 0x%x, read 0x%x)\r\n", name, pattern, readback);
        return 0;
    }
    xil_printf("%s: FAIL (wrote 0x%x, read 0x%x)\r\n", name, pattern, readback);
    return 1;
}
```

### Relevance to Your Project
This mirrors the read-back/PASS-FAIL pattern your `main.c` already implements for BRAM0/BRAM2. If you ever extend the demo to react to a hardware event (e.g., a BRAM-controller interrupt or an AXI GPIO "done" pin) rather than pure polling, remember the two-step GIC enable above — registering the handler alone is not sufficient on Zynq UltraScale+.

## XDC Timing Constraints
### Key Findings
- All clocks must be defined with `create_clock`, and every clock-domain crossing must be covered by `set_clock_groups` — undeclared CDCs default to being timed as synchronous, which can produce false timing failures or, worse, false passes that mask real metastability risk.
- `set_input_delay`/`set_output_delay` model the external system-level path delay at a primary I/O relative to a clock edge; values can be negative depending on the data/clock phase relationship at the board level.
- `set_clock_groups -asynchronous -group {...} -group {...}` is the standard way to tell the tool not to time paths between unrelated clock domains — but bundling too many unrelated clocks into one multi-group command can produce "non-existent path" warnings; prefer separate `set_clock_groups` calls per logically distinct pair of domains.
- For any registers that genuinely cross clock domains (not your case today, since BRAM access is fully within the PS-driven AXI clock domain), tag synchronizer flops with the `ASYNC_REG` attribute so the placer keeps them physically adjacent.

### Code Example
```tcl
# Typical Zynq UltraScale+ board-level XDC additions for a KV260 carrier
# (example for an external interface; not required for the pure PS<->PL
# AXI-only BRAM design, but needed if you add any board-level I/O)
create_clock -period 8.000 -name pl_clk0 [get_ports pl_clk0_p]

set_input_delay  -clock pl_clk0 -max 1.5 [get_ports {ext_data[*]}]
set_input_delay  -clock pl_clk0 -min 0.3 [get_ports {ext_data[*]}]
set_output_delay -clock pl_clk0 -max 1.2 [get_ports {ext_ctrl[*]}]
set_output_delay -clock pl_clk0 -min -0.5 [get_ports {ext_ctrl[*]}]

# Declare the PS-generated AXI clock and the PL user clock as asynchronous
set_clock_groups -asynchronous \
    -group [get_clocks -include_generated_clocks clk_fpga_0] \
    -group [get_clocks -include_generated_clocks pl_clk0]
```

### Relevance to Your Project
Your current design is purely PS-driven AXI (single clock domain feeding both BRAM controllers), so you likely don't need board-level `set_input_delay`/`set_output_delay` constraints today — those only matter once you add an external I/O port toggled at the board boundary. Worth keeping in mind if a future revision of `kv260_top.vhd` adds any direct PL I/O (e.g., driving an LED or reading a button via EMIO/PMOD) — that's the point you'll need real I/O timing constraints, not just the implicit AXI clock relationship Vivado infers from the block design.

## Kria KV260 / K26 SoM
### Key Findings
- The K26 SOM's primary boot device is selected via the MODE[3:0] pins, broken out at the SOM connector for the carrier card to tie off (JTAG, SD, QSPI, etc.); the KV260 starter-kit carrier exposes these as a boot-mode switch.
- MIO/EMIO: most KV260 carrier peripherals route through PS MIO, but the carrier's PMOD/RPi-header-style connectors (where present) connect to PL-side EMIO/PL I/O instead — relevant if you extend `kv260_top.vhd` to drive any carrier connector pins directly.
- Sideband/config signal bank (PS MIO bank 501) runs at 1.8V VCCO — useful to know if you're cross-referencing the K26 SOM datasheet (ds987) for any future PL-side I/O voltage planning.
- For AXI BRAM PS↔PL connectivity specifically, the established pattern (matching your project) is: AXI BRAM Controller's S_AXI connects to the Zynq UltraScale+ PS's `M_AXI_HPM0_FPD` master port, with `BRAM_PORTA` (or both ports if dual-port) wired to a Block Memory Generator instance; unused HPM master ports (e.g., HPM1_FPD) should be explicitly deselected in the PS configuration rather than left dangling.
- A 2025.2-era community guide ("Bare-metal 4K Streaming on KV260") confirms the bare-metal + Vivado/Vitis 2025.x toolchain combination is actively used and documented in the community for this exact board, suggesting your stack choice (2025.1) is well-trodden ground with available recent references once you hit edge cases.

### Code Example
```tcl
# PS configuration matching the BRAM0/BRAM2 HPM0-only pattern
set_property -dict [list \
    CONFIG.PSU__USE__M_AXI_GP0 {1} \
    CONFIG.PSU__USE__M_AXI_GP1 {0} \
    CONFIG.PSU__MAXIGP0__DATA_WIDTH {32} \
] [get_bd_cells zynq_ultra_ps_e_0]
```

### Relevance to Your Project
Your `kv260_top.vhd`/`create_bd.tcl` combo already follows the documented single-HPM-port pattern (S_AXI of each BRAM controller fed from `M_AXI_HPM0_FPD`). Double-check in the PS configuration that the unused HPM1 master is explicitly disabled (`PSU__USE__M_AXI_GP1 = 0`) rather than just unconnected in the diagram — an enabled-but-unconnected master port is a frequent source of `validate_bd_design` critical warnings that get incorrectly dismissed as "ignorable."
