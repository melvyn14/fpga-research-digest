# FPGA Research Digest - 2026-09-07

## Executive Summary

- **AXI-Lite deadlock risk**: The Xilinx AXI BRAM Controller v4.1 does not support full-duplex simultaneous read/write; AWREADY is gated by the write-address pipeline — ensure the PS AXI master never holds BREADY low during a burst without also monitoring AWREADY to avoid stalling the bus indefinitely.
- **TCL non-project mode in 2025.1**: AMD's UG994 (2025.1) now documents `using IP Integrator in Non-Project Mode`, making it possible to reconstruct your entire block design headlessly — critical for CI/CD reproducibility of the AXI-BRAM demo.
- **BOOT.BIN for bare-metal KV260**: The recommended boot flow embeds FSBL + bitstream + application ELF in a single BOOT.BIN written to QSPI/SD; a 2025.2-era Hackster guide confirms this still works with `bootgen` and a BIF file generated from Vitis.
- **Vitis 2025.1 release (UG1742, published 8 Jul 2025)**: New unified flow merges platform/application projects; standalone BSP settings (stdout UART selection, cache enable/disable) moved under platform configuration in the new UI.
- **Kria PYNQ XDC reference**: `Xilinx/Kria-PYNQ` repo ships a `base.xdc` with verified pin/clock constraints for KV260 — a ready-made starting point to derive your own timing constraints without guessing bank voltages.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings
- **VALID must never be de-asserted** once raised without a READY handshake; the master violating this rule causes protocol errors that the AXI Protocol Checker IP (PG101) will flag.
- **AWREADY pipeline gating**: The AXI BRAM Controller negates AWREADY when its write-address pipeline is full and WREADY when the data pipeline is full — these are independent back-pressure signals. Driving both simultaneously low stalls the interconnect; release happens only when the current phase completes.
- **Reset discipline**: Xilinx recommends slaves drive all READY outputs low during reset; neglecting this causes a transfer to be silently dropped if the master de-asserts reset before the slave does.
- **No simultaneous read/write** on AXI BRAM Controller — the IP serialises read and write channels internally; issuing overlapping AR and AW transactions from the same master produces correct but potentially slower throughput than expected.
- **AXI Protocol Checker** (PG101) is the fastest way to diagnose handshake bugs in simulation: instantiate it on your AXI-Lite bus in Vivado block design to get verbose assertion messages.

### Code Example
```c
/* Bare-metal AXI-Lite write to BRAM0, then safe read-back */
#define BRAM0_BASE 0xA0000000UL

static inline void axi_write32(uintptr_t addr, uint32_t val) {
    *(volatile uint32_t *)addr = val;
    /* Memory barrier: ensure write completes before next instruction */
    __asm__ volatile("dsb sy" ::: "memory");
}

static inline uint32_t axi_read32(uintptr_t addr) {
    __asm__ volatile("dsb sy" ::: "memory");
    return *(volatile uint32_t *)addr;
}

int main(void) {
    uint32_t pattern = 0xDEADBEEF;
    axi_write32(BRAM0_BASE + 0x00, pattern);
    uint32_t readback = axi_read32(BRAM0_BASE + 0x00);
    xil_printf("BRAM0: %s\r\n", (readback == pattern) ? "PASS" : "FAIL");
    return 0;
}
```

### Relevance to Your Project
Your `main.c` writes patterns to BRAM0 (0xA0000000) and BRAM2 (0xA0010000). The `dsb sy` barrier after every write is critical on Cortex-A53 because the write buffer can reorder stores; without it, the subsequent read may see stale data even though the AXI transaction nominally completed. Add the barrier pair around every BRAM access.

## Vivado Block Design / IP Integrator

### Key Findings
- **Run Connection Automation** (green banner) handles AXI Interconnect insertion, ARESETN wiring, and clock selection automatically — always run it after adding new IP before manual wiring.
- **Processor System Reset block** (`proc_sys_reset`) is mandatory for synchronising the `pl_resetn0` signal from the Zynq PS to the PL clock domain; missing this causes intermittent reset glitches.
- **Address Editor**: After connection automation, verify each BRAM's address offset in the Address Editor tab; Vivado may assign colliding addresses when multiple BRAMs are added in sequence.
- **Validate Design** (F6) runs DRC checks on all AXI connections; treat all Critical Warnings as errors before generating bitstream.
- **Hierarchical IP** (UG994 2023.1+): wrap related IP in a sub-block container to keep the top-level diagram readable when you add more peripherals later.

### Code Example
```tcl
# Add and wire a second BRAM in an existing block design
open_bd_design [get_files *.bd]
create_bd_cell -type ip -vlnv xilinx.com:ip:blk_mem_gen:8.4 blk_mem_gen_1
create_bd_cell -type ip -vlnv xilinx.com:ip:axi_bram_ctrl:4.1 axi_bram_ctrl_1

# Connect BRAM controller to AXI interconnect slave port
connect_bd_intf_net [get_bd_intf_pins axi_bram_ctrl_1/BRAM_PORTA] \
                    [get_bd_intf_pins blk_mem_gen_1/BRAM_PORTA]

# Let Vivado assign address and wire clocks/resets
apply_bd_automation -rule xilinx.com:bd_rule:axi4 \
    -config { Master "/zynq_ultra_ps_e_0/M_AXI_HPM0_FPD" Clk "Auto" } \
    [get_bd_intf_pins axi_bram_ctrl_1/S_AXI]

assign_bd_address
validate_bd_design
save_bd_design
```

### Relevance to Your Project
Your `create_bd.tcl` builds the block design programmatically. Adding this pattern for BRAM2 alongside BRAM0 ensures correct AXI Interconnect port expansion and automatic address assignment — avoiding the manual address-collision bug that can silently map both BRAMs to the same offset.

## Vivado TCL Scripting

### Key Findings
- **Non-project mode** (UG892): `read_vhdl`, `read_xdc`, `synth_design`, `opt_design`, `place_design`, `route_design`, `write_bitstream` — each called explicitly; no `.xpr` file on disk. Faster in CI because Vivado skips project-database overhead.
- **IP Integrator in non-project mode** (UG994 2025.1): `create_bd_design`, `make_wrapper`, and `update_compile_order` now work reliably outside project mode as of 2025.1.
- **Batch invocation**: `vivado -mode batch -source build.tcl -tclargs arg1 arg2` — use `$argv` inside the script to parse arguments, enabling parameterised builds (e.g., different BRAM depths).
- **`write_project_tcl`**: Open any GUI-built project and run this command to export a complete reconstruction script — the fastest way to convert an existing `.xpr` to a reproducible TCL flow.
- **Error handling**: Wrap synthesis/implementation steps in `catch {}` and check `[current_run -implementation]` status; batch mode returns exit code 1 on failure only if you call `exit [expr {$rc != 0}]` explicitly.

### Code Example
```tcl
#!/usr/bin/env tclsh
# build.tcl - Non-project mode build for kv260-axi-bram-demo
set part "xck26-sfvc784-2LV-c"  ;# K26 SoM part number

# Source files
read_vhdl   [glob ../vhdl/*.vhd]
read_xdc    [glob ../constraints/*.xdc]

# Synthesise
synth_design -top kv260_top -part $part -flatten_hierarchy rebuilt
write_checkpoint -force synth.dcp

# Implement
opt_design
place_design
phys_opt_design
route_design
write_checkpoint -force routed.dcp

# Reports
report_timing_summary -file timing_summary.rpt
report_utilization    -file util.rpt

# Bitstream
write_bitstream -force kv260_top.bit
puts "Build complete."
```

### Relevance to Your Project
Using this non-project pattern in a GitHub Actions workflow would let you reproduce your `kv260_top` bitstream on every commit without maintaining a GUI-built `.xpr`, and the `-tclargs` mechanism lets you parameterise the BRAM depth for regression testing.

## Vitis Bare-Metal / Standalone

### Key Findings
- **Vitis 2025.1 unified flow**: Platform and application projects are now merged; BSP configuration (stdout, cache, sleep timer) lives under **Platform → Board Support Package → standalone** in the new UI rather than a separate BSP project.
- **xil_printf limitations**: Does not support `%f` (floating point) or `%lld` (64-bit integers); use `printf` from `libc` (enable in BSP settings: `set_sw_proc_prop stdout ps7_uart_1`) only when stack space and ELF size allow.
- **Linker script**: Default DDR load address is 0x00000000; for bare-metal AXI tests that run from BRAM, adjust `.text` section in the linker script to 0xFFFC0000 (OCM) or confirm DDR is initialised by FSBL before your ELF runs.
- **GIC interrupt controller**: `XScuGic_Connect()` registers a handler for a PL interrupt; PL-to-PS interrupts must be routed through `pl_ps_irq0[0:7]` in the Zynq PS block design configuration, not left disconnected.
- **Cache coherency**: Cortex-A53 data cache is enabled by default in standalone; AXI BRAM mapped in the `0xA000_0000` range is typically marked as device memory (non-cacheable) in the MMU config generated by the BSP — verify `xil_SetTlbAttributes()` if you see stale reads.

### Code Example
```c
#include "xil_printf.h"
#include "xil_cache.h"
#include "sleep.h"

#define BRAM0_BASE 0xA0000000UL
#define BRAM2_BASE 0xA0010000UL
#define TEST_WORDS 16

int main(void) {
    /* Ensure AXI region is non-cacheable (device memory) */
    Xil_SetTlbAttributes(BRAM0_BASE, NORM_NONCACHE);
    Xil_SetTlbAttributes(BRAM2_BASE, NORM_NONCACHE);

    xil_printf("KV260 AXI-BRAM test starting\r\n");

    for (uint32_t i = 0; i < TEST_WORDS; i++) {
        Xil_Out32(BRAM0_BASE + i * 4, 0xA0000000 + i);
        Xil_Out32(BRAM2_BASE + i * 4, 0xA0010000 + i);
    }

    int pass = 1;
    for (uint32_t i = 0; i < TEST_WORDS; i++) {
        if (Xil_In32(BRAM0_BASE + i * 4) != 0xA0000000 + i) pass = 0;
        if (Xil_In32(BRAM2_BASE + i * 4) != 0xA0010000 + i) pass = 0;
    }
    xil_printf("Result: %s\r\n", pass ? "PASS" : "FAIL");
    return 0;
}
```

### Relevance to Your Project
`Xil_SetTlbAttributes()` with `NORM_NONCACHE` should be called once at startup for both BRAM base addresses; it prevents the Cortex-A53 D-cache from serving stale hits on your AXI-mapped BRAM and is the most common silent failure in bare-metal read-back tests.

## XDC Timing Constraints

### Key Findings
- **set_input_delay syntax (UG835 2025.1)**: Value is in nanoseconds, can be negative (data arrives before clock edge). Use both `-max` and `-min` variants for hold/setup coverage: `set_input_delay -clock clk -max 5.0 [get_ports din]` and `set_input_delay -clock clk -min 1.0 [get_ports din]`.
- **set_output_delay**: Similarly requires `-max` (setup) and `-min` (hold) variants; forgetting `-min` leaves hold paths unconstrained and timing closure may be optimistic.
- **Kria-PYNQ reference XDC**: `Xilinx/Kria-PYNQ` repo at `kv260/base/vivado/constraints/base.xdc` contains verified MMCM, clock, and I/O constraints for KV260 — use as a starting point.
- **Clock groups**: For gated clocks or CDC paths between PS and PL clocks, use `set_clock_groups -asynchronous` to tell the timing engine not to analyse cross-domain paths that are handled by proper synchronisers.
- **False paths on reset**: `set_false_path -from [get_ports pl_resetn0]` prevents the timing engine from flagging asynchronous reset distribution as a timing violation.

### Code Example
```tcl
# kv260_top.xdc — minimal timing constraints for KV260 AXI-BRAM demo
# PL clock from PS (100 MHz)
create_clock -period 10.000 -name pl_clk0 [get_pins zynq_ultra_ps_e_0/pl_clk0]

# Internal clocks generated by MMCM (if used)
# create_generated_clock ...

# Async reset: don't time the reset tree
set_false_path -from [get_pins zynq_ultra_ps_e_0/pl_resetn0]

# If you have PMOD/GPIO outputs registered to pl_clk0:
# set_output_delay -clock pl_clk0 -max 2.0 [get_ports {pmod_out[*]}]
# set_output_delay -clock pl_clk0 -min 0.5 [get_ports {pmod_out[*]}]

# Suppress CDC warnings for PS-managed signals
set_clock_groups -asynchronous \
    -group [get_clocks pl_clk0] \
    -group [get_clocks -of_objects [get_pins zynq_ultra_ps_e_0/pl_clk1]]
```

### Relevance to Your Project
Your design uses `pl_clk0` from the Zynq PS as the sole PL clock feeding both AXI BRAM controllers. The `set_false_path` on `pl_resetn0` and `set_clock_groups` for any secondary clocks are the two constraints most often missing in minimal demos, leading to spurious timing violations that block bitstream generation.

## Kria KV260 / K26 SoM

### Key Findings
- **No pre-loaded firmware**: K26 SOM ships with blank QSPI and eMMC; the first custom boot requires writing a BOOT.BIN (FSBL + bitstream + ELF) to an SD card or QSPI via JTAG.
- **Boot mode selection**: Boot mode is set by the carrier card's boot-mode pins (SW1 on KV260); SD card is mode 0xE, JTAG is 0x0. Confirm with `xsct` `mrd 0xFF5E0200` to read BOOT_MODE_POR.
- **MIO banks**: The K26 SOM exposes MIO bank 501 (3.3 V) and bank 502 (1.8 V) through the SOM240_1 connector, plus HPIO bank 66 and HDIO bank 45. UART0 is on MIO10/MIO11 (bank 501, KV260 routes to USB-UART chip).
- **Power domains**: Always-On domain (5 V main), Battery-Backed domain (for RTC/BBRAM), Full-Power domain (PS+PL). The PL does not power on until `PROG_B` is released by the PS after bitstream load — crucial for AXI initialisation ordering in bare-metal.
- **FSBL vs PSU_INIT.TCL**: For JTAG debugging without FSBL overhead, use `psu_init.tcl` to initialise DDR and clocks, then download your ELF directly; this avoids the 2–3 s FSBL boot time during rapid iteration.

### Code Example
```tcl
# Vitis XSCT script: JTAG boot without FSBL for rapid bare-metal debug
connect
targets -set -nocase -filter {name =~ "*PSU*"}

# Run PSU initialisation (generated by Vivado from block design)
source psu_init.tcl
psu_init

# Enable APU (Cortex-A53 core 0)
targets -set -nocase -filter {name =~ "*A53*#0*"}
rst -processor -clear-registers

# Load and run ELF
dow kv260_axi_bram.elf
con

puts "Running bare-metal app via JTAG — check UART for PASS/FAIL"
```

### Relevance to Your Project
Using `psu_init.tcl` + `dow` in XSCT cuts your debug iteration cycle from ~30 s (BOOT.BIN write → board reset → FSBL → app) to ~5 s (JTAG download → run), which is highly practical when tuning AXI base addresses or pattern logic in `main.c`.

## AMD/Xilinx Tool Updates (2025.x)

### Key Findings
- **Vitis 2025.1 (released 8 Jul 2025, UG1742)**: Unified platform/application workflow replaces classic SDK-style separate BSP project; standalone domain configuration now done via `xsct` script or the unified IDE's platform settings panel.
- **Vivado 2025.1 IP changelog (Answer Record 37919)**: AXI BRAM Controller updated to v4.1; Block Memory Generator updated — check for parameter compatibility if importing IP from older `.xpr` files.
- **Vitis Export to Vivado** (XD101 tutorial, 2025.1): New hardware fast-iteration flow lets you modify the Vivado block design from within Vitis and re-export without closing either tool — speeds up the hardware/software co-development loop.
- **IP Integrator in non-project mode** (UG994 2025.1): Officially documented and supported for the first time in this release.
- **Vitis 2026.1 release notes** already published (UG1742 latest): 2026.1 focuses on AI Engine improvements and Versal; for KV260/Zynq Ultrascale+, 2025.1/2025.2 remain the recommended stable versions.

### Code Example
```tcl
# Vitis XSCT: create platform + standalone domain for KV260 (2025.1 unified flow)
setws ./vitis_workspace

# Create platform from exported XSA
platform create -name kv260_platform \
    -hw ../vivado_output/kv260_top.xsa \
    -proc psu_cortexa53_0 \
    -os standalone \
    -out ./vitis_workspace

# Configure standalone domain: stdout → UART0, enable caches
domain active {standalone on psu_cortexa53_0}
bsp setproc psu_cortexa53_0
bsp config stdout psu_uart_0
bsp config extra_compiler_flags "-O2 -DUSE_BRAM_DEMO"

platform generate
puts "Platform with standalone BSP generated."

# Create application project
app create -name kv260_axi_bram \
    -platform kv260_platform \
    -domain {standalone on psu_cortexa53_0} \
    -template {Empty Application}
app build -name kv260_axi_bram
```

### Relevance to Your Project
Migrating from classic Vitis SDK to the 2025.1 unified flow requires replacing the old `hsi` BSP generation commands with the `bsp` commands shown above. The `bsp config stdout psu_uart_0` line is the equivalent of the old "System Configuration → stdout" GUI setting — getting this wrong is the most common reason xil_printf produces no output on a fresh KV260 bringup.
