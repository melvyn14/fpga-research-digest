# FPGA Research Digest - 2026-10-08

## Executive Summary
- **AXI BRAM address stepping**: The Block Memory Generator in "BRAM Controller" mode increments the address by 4, not 1 — mixing this up with "Stand-alone" mode causes silent off-by-4x read/write errors in main.c pointer arithmetic (PG058/PG078).
- **VALID must not drop**: Once `AWVALID`/`WVALID`/`ARVALID` is raised on AXI-Lite, the master cannot lower it until the corresponding READY is received — a rule synthesis tools do not check, making it easy to miss in RTL but lethal for PS-to-PL transactions.
- **write_bd_tcl caveat**: The exported TCL only records user-changed parameters; propagated IP defaults are omitted and must be re-derived by running `validate_bd_design` after sourcing the script — keep this in mind for the create_bd.tcl in the project.
- **Vivado 2025.1 new block design views**: IP Integrator gained dedicated "Clocking and Reset" and "Interrupt and AXI-4 Lite" canvas views, helping debug PS-to-PL connectivity issues without hunting in the standard BD diagram.
- **ZynqMP M_AXI_HPM0_FPD is the right PS-to-PL path**: For bare-metal writes to PL slaves like BRAM at 0xA000_0000, connect the PS through M_AXI_HPM0_FPD (GP master) — HP ports are only for PL-to-DDR/OCM data paths, not for PS register-style access.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings
- **VALID is sticky**: A master that raises VALID cannot withdraw it until the corresponding READY arrives. Synthesis does not flag violations; they manifest as deadlocks that intermittent simulation won't catch.
- **BVALID and RVALID are often mishandled**: A common hand-written slave bug ties `AWREADY` permanently high, accepting addresses regardless of internal state. Another is forgetting to gate `BVALID` on prior write completion.
- **Generated example cores can be wrong**: ZipCPU formal analysis of Xilinx's AXI-Lite slave example from Vivado found protocol bugs where the address and data channels conflicted on the same handshake cycle — don't copy example code without review.
- **AXI Register Slice breaks long combinational paths**: For timing closure on wide or fast AXI buses, inserting a Register Slice IP adds one cycle of latency but absorbs that stall via handshake.
- **Protocol Checker IP**: Add Xilinx's AXI Protocol Checker IP to simulation testbenches — it flags handshake violations automatically, replacing manual waveform inspection.

### Code Example
```vhdl
-- AXI-Lite slave write acceptance: hold AWREADY high for ONE cycle only
-- when both AWVALID and WVALID are present simultaneously (simplified)
process(S_AXI_ACLK)
begin
  if rising_edge(S_AXI_ACLK) then
    if S_AXI_ARESETN = '0' then
      axi_awready <= '0';
      aw_en       <= '1';
    else
      if aw_en = '1' and S_AXI_AWVALID = '1' and S_AXI_WVALID = '1' then
        axi_awready <= '1';
        aw_en       <= '0';   -- block further acceptance until B-channel clears
      elsif S_AXI_BREADY = '1' and axi_bvalid = '1' then
        aw_en <= '1';         -- re-enable only after write response accepted
        axi_awready <= '0';
      else
        axi_awready <= '0';
      end if;
    end if;
  end if;
end process;
```

### Relevance to Your Project
Your PS writes to BRAM0 (0xA000_0000) and BRAM2 (0xA001_0000) using Cortex-A53 bare-metal stores. The A53 AXI master must see AWREADY and WREADY in time; if custom wrapper logic (kv260_top.vhd) sits between the interconnect and BRAM controllers, any `aw_en` mismanagement will cause the PS store to silently stall. Inserting the AXI Protocol Checker IP in simulation will surface this before hardware.

## Vivado Block Design / IP Integrator

### Key Findings
- **Vivado 2025.1 added dedicated BD views**: "Clocking and Reset" and "Interrupt and AXI-4 Lite" views are now available in IP Integrator, making it easier to audit PS-PL clock connectivity and AXI-Lite slave maps.
- **Address Editor is authoritative**: The base addresses in Vivado's Address Editor (e.g., 0xA000_0000 for BRAM0) become the physical addresses your C code must use — any mismatch between the editor and main.c causes PASS to become FAIL silently.
- **Regenerating output products**: After re-importing or upgrading IP, always run `generate_target all [get_files *.bd]` before synthesis — stale output products cause cryptic elaboration errors.
- **Connection automation pitfall**: `apply_bd_automation` is convenient but can assign wrong clock domains for IP with multiple clock ports. Always inspect the result in the Clocking view.

### Code Example
```tcl
# Vivado TCL: regenerate all IP output products after IP upgrade
open_project ./kv260.xpr
update_ip_catalog -rebuild
upgrade_ip [get_ips *]
generate_target all [get_files *.bd]
export_ip_user_files -of_objects [get_files *.bd] -no_script -force
launch_runs impl_1 -to_step write_bitstream -jobs 4
wait_on_run impl_1
```

### Relevance to Your Project
The create_bd.tcl script drives the entire block design — after any Vivado version bump from 2025.1 to a future release, run `upgrade_ip` before generating targets, otherwise the AXI BRAM Controller and SmartConnect IPs may silently use stale parameters. The new "AXI-4 Lite" view in 2025.1 lets you visually confirm both BRAM controller slave segments are properly connected to the PS master.

## Vivado TCL Scripting

### Key Findings
- **write_bd_tcl only records changed parameters**: Default and propagated IP values are omitted. After sourcing a recreate script, always run `validate_bd_design` to propagate parameters before synthesis.
- **`-no_ip_version` flag is dangerous across major releases**: It makes the script pull the latest catalog version of each IP, which can introduce incompatible parameter sets. Use `-ignore_minor_versions` for safe point-release upgrades.
- **Version-pin the script**: The exported TCL embeds the Vivado release it came from. AMD recommends rebuilding the design in the same release, then migrating, rather than sourcing the script in a different version.
- **Non-project mode tip**: In non-project mode, call `read_bd` for an existing block design or `source create_bd.tcl` to build it, then `make_wrapper -files [get_files *.bd] -top` and `read_vhdl` the wrapper before synthesis.

### Code Example
```tcl
# Export block design to TCL for version control (run from Vivado Tcl console)
write_bd_tcl \
  -force \
  -bd_name kv260 \
  -ignore_minor_versions \
  ./tcl/create_bd.tcl

# After sourcing a recreate script, always validate:
# source ./tcl/create_bd.tcl
# validate_bd_design
# generate_target all [get_files kv260.bd]
```

### Relevance to Your Project
Your create_bd.tcl is the single source of truth for the block design. Adding `-ignore_minor_versions` to the `write_bd_tcl` invocation that generated it makes the script tolerate Vivado patch updates. After any `git pull` that modifies create_bd.tcl, running `validate_bd_design` is mandatory before proceeding to bitstream generation.

## Vitis Bare-Metal / Standalone

### Key Findings
- **xil_printf routes to BSP-configured UART**: The stdout peripheral is set in BSP settings (typically `psu_uart_1` on KV260's KV260's PS UART connected to the USB-UART bridge) — a wrong BSP UART selection produces a silent board with no PASS/FAIL output.
- **AXI INTC driver supports cascading**: For future interrupt expansion beyond 32 sources, the AXI INTC IP supports cascade mode — the driver exposes `XIntc_ConnectFastHandler` for direct vector dispatch.
- **Standalone BSP 2025.1 driver changes are minimal**: The AXI GPIO and AXI INTC driver changelogs for 2025.1 show "None" (no driver changes), so existing code targeting 2024.x should compile without modification.
- **embeddedsw GitHub tag**: The BSP sources for 2025.1 are at tag `xlnx_rel_v2025.1` in `github.com/Xilinx/embeddedsw` — useful for diffing BSP headers if a mysterious build error appears.

### Code Example
```c
/* Bare-metal AXI-Lite read/write using Xilinx helpers */
#include "xil_io.h"

#define BRAM0_BASE  0xA0000000U
#define BRAM2_BASE  0xA0010000U
#define BRAM_DEPTH  0x2000U      /* match address range in Address Editor */

void bram_write_pattern(u32 base, u32 pattern) {
    for (u32 offset = 0; offset < BRAM_DEPTH; offset += 4) {
        Xil_Out32(base + offset, pattern ^ offset);
    }
    /* data barrier: ensure stores are visible before readback */
    dsb();
}

int bram_verify_pattern(u32 base, u32 pattern) {
    for (u32 offset = 0; offset < BRAM_DEPTH; offset += 4) {
        u32 rd = Xil_In32(base + offset);
        if (rd != (pattern ^ offset)) return -1;
    }
    return 0;
}
```

### Relevance to Your Project
The `dsb()` (Data Synchronization Barrier) between write loop and readback loop is critical on the Cortex-A53 — without it the processor's out-of-order store buffer may not have flushed to the AXI bus before the read begins, causing intermittent FAIL even when the hardware is correct. Add this if it's not already in main.c.

## XDC Timing Constraints

### Key Findings
- **set_input_delay / set_output_delay model board-level paths**: These commands tell Vivado about the clock-to-data relationship at the FPGA pins, enabling the tool to compute real setup/hold margins for external interfaces.
- **Positive vs. negative delay**: The value can be positive (data arrives after clock edge — typical) or negative (data arrives before clock edge — source-synchronous with early-launch). The sign is set by the board-level timing diagram, not convention.
- **`-add_delay` preserves existing constraints**: When a port needs both a min and max specification (for hold and setup), use `-add_delay` on the second call to accumulate rather than replace.
- **PS/PL internal paths don't need input/output delays**: Clock domain crossings inside the FPGA (PS clock to PL clock) are handled by `set_clock_groups -asynchronous`, not by set_input/output_delay.
- **UltraFast Methodology (UG949)**: The canonical reference for constraining I/O ports on Zynq UltraScale+ — contains worked examples for source-synchronous and system-synchronous interfaces.

### Code Example
```tcl
# XDC example: constrain a 125 MHz reference clock and a registered output
# (replace CLK_P/N and DOUT with actual port names from your KV260 top)
create_clock -name clk_pl -period 8.000 [get_ports CLK_P]

# System-synchronous output: data must be stable 2 ns before next clock edge
# at the receiving device, and held 1 ns after.
set_output_delay -clock clk_pl -max  2.000 [get_ports DOUT]
set_output_delay -clock clk_pl -min -1.000 [get_ports DOUT] -add_delay

# Isolate PS and PL clocks — no timing path crosses PS/PL boundary
set_clock_groups -asynchronous \
  -group [get_clocks clk_pl_i] \
  -group [get_clocks clk_fpd_i]
```

### Relevance to Your Project
The KV260 AXI-BRAM demo is mostly internal-only timing (PS clock drives PL through BUFG), so `set_clock_groups -asynchronous` between `clk_pl` and the PS internal clocks is the primary constraint to add. Without it Vivado may attempt to analyze false cross-clock paths and either over-constrain or under-constrain the design.

## Kria KV260 / K26 SoM

### Key Findings
- **Two 240-pin connectors expose all PS/PL I/O**: MIO, PS-GTR transceivers, PL HPIO, PL HDIO, PL GTH, and sideband/power signals all route through the SOM connectors to the KV260 carrier card.
- **SMK vs SM variants**: The Starter-Kit SOM (SMK-K26) ships with no eMMC and QSPI pre-programmed with firmware. The full SM-K26 has eMMC. Boot mode pins on the carrier card determine whether JTAG, QSPI, or SD-card is tried.
- **QSPI boot runs a limited peripheral set**: On QSPI boot, only peripherals defined in the QSPI-resident FSBL are available. Carrier-card detection then applies device-tree overlays (Linux) or a second XSA configuration (bare-metal) to add further IP.
- **M_AXI_HPM0_FPD for PS→PL control traffic**: On ZynqMP, the PS routes AXI-Lite/AXI transactions to PL slaves through the FPD GP master ports (`M_AXI_HPM0_FPD`, `M_AXI_HPM1_FPD`). HP ports (`S_AXI_HP0_FPD`…) are PL→PS DDR paths only.
- **USB-UART bridge is PS UART1 (MIO 36/37)**: On KV260, the USB-to-UART chip connects to PS UART1. The BSP stdout must be set to `psu_uart_1` or xil_printf output will be silent.

### Code Example
```tcl
# Vivado BD TCL: enable HPM0 FPD AXI master on Zynq UltraScale+ PS for PL access
set_property -dict [list \
  CONFIG.PSU__USE__M_AXI_GP0 {1} \
  CONFIG.PSU__MAXIGP0__DATA_WIDTH {32} \
] [get_bd_cells zynq_ultra_ps_e_0]

# Connect PS M_AXI_HPM0_FPD to SmartConnect, then to BRAM controllers
connect_bd_intf_net \
  [get_bd_intf_pins zynq_ultra_ps_e_0/M_AXI_HPM0_FPD] \
  [get_bd_intf_pins smartconnect_0/S00_AXI]
```

### Relevance to Your Project
Your BRAM addresses (0xA000_0000 and 0xA001_0000) fall in the ZynqMP HPM0 FPD window. If the block design accidentally uses `S_AXI_HP0_FPD` instead of `M_AXI_HPM0_FPD` as the PS-to-PL path, the PS writes will never reach the BRAM controllers and you will see all-zero readbacks (FAIL) with no AXI error. Verify the port name in create_bd.tcl.

## AMD/Xilinx Tool Updates (Vivado/Vitis 2025.x)

### Key Findings
- **Vivado 2025.1 adds RTL-based AXI Switch IP**: New core bridges different AXI interface types and widths; it is an RTL-instantiated IP (not a BD automation block), intended for designs where AXI Interconnect or SmartConnect is oversized.
- **IP Integrator now has "Clocking and Reset" and "Interrupt and AXI-4 Lite" views**: These dedicated canvas perspectives reduce navigation effort for complex block designs with many clock domains or interrupt trees.
- **Selective installer reduces download size**: Vivado 2025.1 lets you install only specific Versal device families instead of the full catalog, cutting install size significantly.
- **New device support**: Versal AI Edge Series Gen 2, Versal Prime Series Gen 2, and Spartan UltraScale+ are now supported.
- **Vitis AI 5.1 aligns with 2025.1.1**: Vitis AI 5.1 requires Vivado/Vitis 2025.1.1 (not the base 2025.1) — important if adding AI acceleration later on the KV260.
- **Vivado 2025.2 ultra-low-area mode**: `STRATEGY` parameter for AXI Switch and AXI SmartConnect adds a resource-optimized mode (this is 2025.2, not 2025.1).
- **AXI full peripheral 1K address space bug (Vivado 2025)**: A Digilent forum report notes that AXI full peripherals may be limited to 1K of usable address space in Vivado 2025; workaround: use AXI4-Lite for control registers, or verify the Address Editor range matches the IP's address decode width.

### Code Example
```tcl
# Vivado 2025.1: use the new dedicated BD views from the Tcl console
# Open the Clocking and Reset view
open_bd_design [get_files *.bd]
start_gui
# In the GUI: Window > Block Design > Clocking and Reset
# Alternatively, check clock connections programmatically:
foreach cell [get_bd_cells -hierarchical -filter {VLNV =~ *bram_ctrl*}] {
  set clk_pin [get_bd_intf_pins -of_objects $cell -filter {MODE == Slave && VLNV =~ *aximm*}]
  puts "$cell -> [get_bd_nets -of_objects $clk_pin]"
}
```

### Relevance to Your Project
The AXI full peripheral 1K address space bug reported for Vivado 2025 is directly relevant: if your BRAM depth exceeds 1K bytes and you used AXI4 (not AXI4-Lite) for the BRAM controller, you may be able to write but only the first 1K is addressable. Since BRAM0 and BRAM2 are accessed at offsets up to `BRAM_DEPTH`, verify the Address Editor shows the full expected range (e.g., 8K), and check whether the BRAM Controller is in AXI4 or AXI4-Lite mode.
