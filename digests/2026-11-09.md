# FPGA Research Digest - 2026-11-09

## Executive Summary
- **AXI-Lite BRAM read latency is configurable** via `C_READ_LATENCY` (default 1 cycle); RVALID is not asserted until both ARVALID and ARREADY have been seen — a common source of testbench vs. hardware discrepancies.
- **AXI Interconnect IP has been officially discontinued** by AMD; migrate to AXI SmartConnect (or the new RTL-based AXI Switch for non-IPI flows) — SmartConnect remains the correct choice for IP Integrator block designs.
- **Connection Automation in Vivado 2025.2/2026.1 does NOT auto-connect BRAM ports** — after running Designer Assistance for the BRAM Controller, you must run a second Designer Assistance pass to wire the Block Memory Generator.
- **UART MIO mapping for Kria KV260 must stay on MIO36/MIO37** to match the boot firmware and PetaLinux BSP — deviating breaks UART output at boot.
- **Vivado 2025.2 adds an ultra-low-area mode** to AXI Switch and SmartConnect via a STRATEGY parameter — worth evaluating if LUT count is a concern for the BRAM arbitration path.

---

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings
- AXI-Lite handshake completes only when both VALID and READY are high **on the same clock edge** — simulators sometimes miss off-by-one timing issues that show up on hardware.
- RVALID must not be asserted until ARVALID+ARREADY have been seen; with a 1-cycle BRAM read latency the controller inserts one pipeline stage before asserting RVALID.
- Driving RDATA directly from a combinational mux works in simulation but can cause setup-time violations on-device; register the output stage.
- The AXI Protocol Checker IP (from Vivado IP catalog) can be inserted in simulation to flag handshake violations, illegal burst parameters, and bad response codes.
- AXI Interconnect is deprecated; AXI SmartConnect is the replacement and handles width/clock conversion automatically.
- Register slices at interconnect boundaries are the primary fix when post-route timing fails on AXI paths above ~150 MHz.

### Code Example
```vhdl
-- AXI-Lite read register process with proper RVALID pipelining
-- C_READ_LATENCY = 1 assumed (one clock cycle to output BRAM data)
process(S_AXI_ACLK)
begin
  if rising_edge(S_AXI_ACLK) then
    if S_AXI_ARESETN = '0' then
      axi_rvalid <= '0';
      axi_rresp  <= "00";
    else
      -- Assert RVALID one cycle after AR handshake (BRAM latency = 1)
      if (axi_arready = '1' and S_AXI_ARVALID = '1' and
          axi_rvalid = '0') then
        axi_rvalid <= '1';
        axi_rresp  <= "00";
      elsif (S_AXI_RREADY = '1') then
        axi_rvalid <= '0';  -- deassert after master accepts
      end if;
    end if;
  end if;
end process;
```

### Relevance to Your Project
Your project reads back patterns written to BRAM0 (0xA0000000) and BRAM2 (0xA0010000). If the AXI BRAM Controller's `C_READ_LATENCY` does not match the actual Block Memory Generator latency setting, reads will return stale or zero data. Verify these match in your block design. The PASS/FAIL print path depends entirely on correct read-back — a latency mismatch would produce silent failures.

## Vivado Block Design / IP Integrator

### Key Findings
- Running **Connection Automation** after adding an AXI BRAM Controller does NOT automatically wire the Block Memory Generator. A second Designer Assistance pass is required: "The AXI Block RAM Controller is not connected to a Block Memory Generator. You can also use the Designer Assistance feature to connect a Block Memory Generator to the Block RAM Controller."
- In Vivado 2026.1, **Start Connection Mode** auto-suggests compatible clock pins on other IPs after you wire `s_axi_aclk` — useful for multi-IP designs.
- Running **All Automation** auto-inserts a Clocking Wizard, Processor System Reset, and AXI SmartConnect — be aware of this when scripting, as extra IPs appear in the design.
- For **two BRAM controllers** (like your BRAM0 and BRAM2), you may need to run Connection Automation twice: once per controller.
- AXI SmartConnect now has an **ultra-low-area mode** (STRATEGY parameter) in Vivado 2025.2.

### Code Example
```tcl
# After adding both BRAM controllers, run automation for each
# In TCL this corresponds to:
apply_bd_automation \
  -rule xilinx.com:bd_rule:bram_cntlr \
  -config {BRAM "New Blk_Mem_Gen"} \
  [get_bd_intf_pins axi_bram_ctrl_0/BRAM_PORTA]

apply_bd_automation \
  -rule xilinx.com:bd_rule:bram_cntlr \
  -config {BRAM "New Blk_Mem_Gen"} \
  [get_bd_intf_pins axi_bram_ctrl_1/BRAM_PORTA]

# Regenerate all output products
generate_target all [get_files *.bd]
```

### Relevance to Your Project
Your `create_bd.tcl` likely uses `apply_bd_automation` to wire both BRAM controllers. The two-pass requirement means if you scripted this in one pass, the BRAMs may not be connected — confirm by checking the block design after regeneration. Use `validate_bd_design` in TCL to catch disconnected interfaces before synthesis.

## Vivado TCL Scripting

### Key Findings
- Non-project mode is fully Tcl-driven: no `.xpr` file is created; all state lives in memory. You must write explicit `report_timing_summary`, `write_checkpoint`, and `write_bitstream` commands.
- Batch invocation: `vivado -mode batch -source create_bd.tcl` — add `-nojournal -nolog` to suppress verbose output during CI.
- File read order matters: `read_vhdl`, `read_xdc`, and `read_bd` are compiled in the order listed. Dependencies must come before dependents.
- For block designs in non-project mode: (1) source the BD TCL, (2) call `generate_target`, (3) call `make_wrapper`, (4) `read_vhdl` the wrapper, (5) `update_compile_order`.
- Use `get_bd_intf_nets -hierarchical` and `get_bd_cells -hierarchical` for robust path-independent queries.
- Vivado's `write_project_tcl` can export a project-mode design to a reproducible script — a good starting point if your current `create_bd.tcl` was hand-written.

### Code Example
```tcl
# Minimal non-project-mode build script skeleton
read_vhdl -library xil_defaultlib [glob ./vhdl/*.vhd]
source ./tcl/create_bd.tcl
generate_target all [get_files *.bd]
make_wrapper -files [get_files *.bd] -top
read_vhdl -library xil_defaultlib ./kv260_top_wrapper.vhd
update_compile_order -fileset sources_1

read_xdc ./constraints/kv260_top.xdc

synth_design -top kv260_top_wrapper -part xck26-sfvc784-2LV-c
write_checkpoint -force ./checkpoints/post_synth.dcp

opt_design
place_design
route_design
write_checkpoint -force ./checkpoints/post_route.dcp

report_timing_summary -file ./reports/timing_summary.rpt
write_bitstream -force ./output/kv260_top.bit
```

### Relevance to Your Project
Your `create_bd.tcl` is the core reproducibility mechanism for the KV260 AXI-BRAM demo. Wrapping it in this non-project-mode shell gives you a CI-compatible one-shot build. The `validate_bd_design` call before `generate_target` will surface wiring errors before synthesis time.

## Vitis Bare-Metal / Standalone

### Key Findings
- The BSP's **STDIN/STDOUT** setting in `vitis-comp.json` (under the standalone OS settings) determines which UART `xil_printf` writes to — if prints don't appear over USB-UART, this is the first thing to check.
- The Standalone BSP supports nested interrupts and provides vectored exception handlers for Cortex-A53 (Zynq UltraScale+) — no OS needed for simple interrupt-driven AXI polling.
- For PL-to-PS interrupts: the interrupt must be enabled on the PS side (Zynq MPSoC IP), AND the exception handler must be registered via `Xil_ExceptionRegisterHandler` and enabled with `Xil_ExceptionEnable()`.
- A missing interrupt entry in `xparameters.h` after BSP generation usually means the interrupt was not enabled in the Zynq PS IP configuration in the block design.
- The 2025.2 Vitis **Unified IDE** is now default; the Classic IDE is deprecated. If you're on Vitis 2025.1 this is worth noting for future migration.

### Code Example
```c
#include "xil_printf.h"
#include "xil_io.h"
#include "xparameters.h"

/* AXI-Lite register write/read macros for BRAM via AXI */
#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL

static inline void bram_write(uintptr_t base, u32 offset, u32 val) {
    Xil_Out32(base + offset, val);
}

static inline u32 bram_read(uintptr_t base, u32 offset) {
    return Xil_In32(base + offset);
}

int verify_bram(uintptr_t base, const char *name) {
    const u32 PATTERN = 0xDEADBEEFU;
    bram_write(base, 0x00, PATTERN);
    u32 readback = bram_read(base, 0x00);
    if (readback == PATTERN) {
        xil_printf("%s: PASS (0x%08X)\r\n", name, readback);
        return 0;
    }
    xil_printf("%s: FAIL (wrote 0x%08X, read 0x%08X)\r\n",
               name, PATTERN, readback);
    return -1;
}

int main(void) {
    xil_printf("KV260 AXI-BRAM Test\r\n");
    int result = 0;
    result |= verify_bram(BRAM0_BASE, "BRAM0");
    result |= verify_bram(BRAM2_BASE, "BRAM2");
    xil_printf("Overall: %s\r\n", result == 0 ? "PASS" : "FAIL");
    return result;
}
```

### Relevance to Your Project
This mirrors your project's PS write-then-readback pattern. Using `Xil_Out32`/`Xil_In32` (from `xil_io.h`) is the canonical bare-metal approach and handles cache coherency correctly for Zynq UltraScale+. The `\r\n` termination is important — USB-UART terminals on Windows require CR+LF.

## XDC Timing Constraints

### Key Findings
- AMD UG903 (2025.2 edition, Nov 2025) recommends this constraint ordering: (1) clocks, (2) clock groups, (3) I/O delays, (4) timing exceptions. Clock groups and false paths should come last.
- `set_clock_groups -asynchronous` suppresses timing analysis between groups but does NOT make the crossing safe — synchronizers are still required for any real async crossing.
- `set_input_delay` measured from the capture-clock edge after clock latency, unless the value already includes source/network latency.
- If a port has both `set_input_delay` and `set_max_delay`, the input delay counts toward the max-delay computation.
- For the KV260 (Zynq UltraScale+), the PL clock typically comes from the PS (`pl_clk0`) — constrain it with `create_clock` on the PL clock port, not on a pad pin.

### Code Example
```tcl
# KV260 XDC timing constraints skeleton
# PL clock from PS - typically 100 MHz from pl_clk0
create_clock -period 10.000 -name pl_clk0 \
    [get_pins -hierarchical -filter {NAME =~ */zynq_ultra_ps_e_0/inst/PS8_i/PLCLK[0]}]

# If you have a separate free-running clock on a package pin:
# create_clock -period 10.000 -name sys_clk [get_ports sys_clk_p]

# Declare PL clock and PS internal clocks as asynchronous groups
# (PS fabric clocks are independent from each other)
set_clock_groups -asynchronous \
    -group [get_clocks pl_clk0] \
    -group [get_clocks -of_objects \
        [get_pins -hierarchical -filter {NAME =~ */PS8_i/PLCLK*}]]

# Example I/O delay if you have external signals (AXI over EMIO, etc.)
# set_input_delay -clock pl_clk0 -max 2.0 [get_ports {some_input_port}]
# set_output_delay -clock pl_clk0 -max 2.0 [get_ports {some_output_port}]
```

### Relevance to Your Project
For a pure PS→PL AXI-Lite demo where all logic is clocked from `pl_clk0`, you need very few XDC constraints — just the `create_clock` on the PL clock. The main timing risk is if you add external I/O later (EMIO signals, board-level interfaces on the KV260 carrier). The constraint skeleton above is a safe starting point.

## Kria KV260 / K26 SoM

### Key Findings
- **Boot mode**: KV260 starter kits ship with QSPI32 preset boot mode and pre-loaded boot firmware in QSPI. For bare-metal, you write `boot.bin` to the SD card (Image A slot) and the boot firmware loads it via FSBL.
- **UART MIO**: Boot firmware and PetaLinux BSP default to **MIO36/MIO37** for UART1. Bare-metal designs should use the same mapping to match the existing software stack.
- **MIO banks**: SOM uses MIO bank 500 for onboard peripherals; banks 501 and 502 are exposed via the SOM connector to the carrier card (KV260). Dynamic MIO configuration via the PMU handles carrier-specific differences between KV260 and KR260.
- **AXI connectivity**: The recommended bare-metal path is PS M_AXI_HPM0_FPD → AXI SmartConnect → AXI BRAM Controller, mirroring the official Kria bare-metal app note (2022.1).
- **Kria 2026.1 release**: AMD noted a Kria 2026.1 boot firmware update in their wiki but release details were not available at time of this digest.
- **Power domains**: The K26 SOM has a PMIC (TPS65086A) that sequences power rails. Bare-metal code that accesses PL clocks before the PL is powered will hang — the FSBL handles this sequencing.

### Code Example
```tcl
# Block design snippet: connect PS to AXI BRAM via HPM0
# This mirrors the recommended Kria bare-metal connectivity

# PS AXI Master port settings (in Zynq MPSoC IP)
set_property -dict [list \
    CONFIG.PSU__USE__M_AXI_GP0 {1} \
    CONFIG.PSU__MAXIGP0__DATA_WIDTH {32} \
] [get_bd_cells zynq_ultra_ps_e_0]

# Address assignment for BRAM controllers
# BRAM0 at 0xA000_0000, size 64K
assign_bd_address -offset 0xA0000000 -range 0x00010000 \
    [get_bd_addr_segs axi_bram_ctrl_0/S_AXI/Mem0]

# BRAM2 at 0xA001_0000, size 64K  
assign_bd_address -offset 0xA0010000 -range 0x00010000 \
    [get_bd_addr_segs axi_bram_ctrl_1/S_AXI/Mem0]
```

### Relevance to Your Project
The two BRAM addresses your project uses (0xA0000000 and 0xA0010000) match this assignment. If you see bus timeouts or hard faults on the A53, verify these address assignments are correct in the block design's Address Editor. A mismatch between the address in C (`#define BRAM0_BASE 0xA0000000`) and the XSA address map will cause a hard fault on first access.

## AMD/Xilinx Tool Updates (Vivado/Vitis 2025.x)

### Key Findings
- **Vivado 2025.1**: Added device support for Versal AI Edge Series Gen 2, Versal Prime Series Gen 2, and Spartan UltraScale+. Unified device installer reduces download size. GUI for `report_dfx_summary` added.
- **Vivado 2025.2**: New **ultra-low-area mode** for AXI Switch and SmartConnect (STRATEGY parameter). UG994 updated with utility IP migration to inline HDL guidance.
- **AXI Interconnect deprecated**: The legacy AXI Interconnect IP has been officially discontinued and will be removed in the next major Vivado release. Migrate to SmartConnect.
- **Vitis 2025.1/2025.2**: Vitis Unified IDE is now the default GUI; Classic IDE is deprecated. 2025.1 added a third-party tools marketplace utility.
- **Vitis Libraries 2025.1**: New PWM IP (IP_PWM_V2) added to the DSP library; VEK280 AIE-ML device support added.
- **Known issue (Vitis GUI / RHEL 8.3 / CentOS 8.2)**: An `LD_LIBRARY_PATH` conflict can break Vitis GUI projects — workaround is to remove that variable from the project environment.

### Code Example
```tcl
# Migrate from AXI Interconnect to SmartConnect in a block design
# Delete old interconnect and replace with SmartConnect
delete_bd_objs [get_bd_cells axi_interconnect_0]

create_bd_cell -type ip \
    -vlnv xilinx.com:ip:smartconnect:1.0 \
    axi_smc

set_property CONFIG.NUM_SI {1} [get_bd_cells axi_smc]
set_property CONFIG.NUM_MI {2} [get_bd_cells axi_smc]

# Reconnect master (PS) to SmartConnect
connect_bd_intf_net \
    [get_bd_intf_pins zynq_ultra_ps_e_0/M_AXI_HPM0_FPD] \
    [get_bd_intf_pins axi_smc/S00_AXI]

# Reconnect BRAM controllers
connect_bd_intf_net \
    [get_bd_intf_pins axi_smc/M00_AXI] \
    [get_bd_intf_pins axi_bram_ctrl_0/S_AXI]

connect_bd_intf_net \
    [get_bd_intf_pins axi_smc/M01_AXI] \
    [get_bd_intf_pins axi_bram_ctrl_1/S_AXI]
```

### Relevance to Your Project
If your existing `create_bd.tcl` was created before Vivado 2025.x, verify it does not use AXI Interconnect. If it does, replace it with SmartConnect now before the former is removed. For a simple 1-master, 2-slave topology (PS → 2× BRAM), SmartConnect with `NUM_SI=1, NUM_MI=2` is the correct configuration.
