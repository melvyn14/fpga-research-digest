# FPGA Research Digest - 2026-08-17

## Executive Summary

- **AXI BRAM write-enable early assertion**: The Xilinx AXI BRAM Controller IP (v4.x) can assert `WEN` one clock cycle early, potentially corrupting an extra address location. Workaround: ensure `ENA`/`ENB` is tied to the AXI BRAM controller's enable port rather than static-high, which gates the extra cycle.
- **AXI-Lite handshake deadlock**: Only raise `AWREADY` when *both* `AWVALID` and `WVALID` are high; never gate `VALID` on `READY` from a master (violates AXI spec and creates deadlock). Critical for any custom slave logic added to the BRAM demo.
- **TCL non-project mode for CI/CD**: Using `vivado -mode batch -source build.tcl` with explicit `read_vhdl`, `synth_design`, `place_design`, `route_design`, `write_bitstream` removes GUI dependency and makes the KV260 project fully scriptable and reproducible.
- **Kria KV260 bare-metal Vitis 2025.1 workflow**: A detailed tutorial (LogicTronix) documents recreating the BIST firmware for KV260 in Vivado/Vitis 2025.1—directly applicable to the AXI-BRAM demo's development flow.
- **Vivado 2025.2 SmartConnect ultra-low-area mode**: New `STRATEGY` parameter on AXI SmartConnect IP can reduce fabric area significantly—useful when the BRAM demo grows to add more AXI masters or slaves.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- **VALID must never depend on READY**: The AXI spec prohibits a master from gating `AWVALID` or `WVALID` on seeing the corresponding `READY` first. If both sides wait for the other, the channel deadlocks permanently.
- **Synchronizing write address and data channels**: A correct AXI-Lite slave should only assert `AWREADY` when *both* `AWVALID` and `WVALID` are simultaneously high, ensuring the address and data are captured together. Dan Gisselquist's "Easy AXI-Lite" blog post (zipcpu.com) is the canonical implementation reference.
- **`BREADY` backpressure propagates upstream**: If the write-response consumer holds `BREADY` low, the slave must propagate backpressure by de-asserting `AWREADY` and `WREADY` to avoid overwriting an un-acknowledged response register.
- **AXI BRAM Controller early write-enable bug**: When using `AXI Interconnect` (not `AXI SmartConnect`) the BRAM Controller can assert `WEN` one cycle early and write an extra word. Mitigation: switch to AXI SmartConnect, or tie the BRAM `ENA` port to the controller's enable output rather than VCC.
- **AXI-Lite has no burst, ID, or QoS fields**: For the KV260 AXI-BRAM demo, AXI-Lite is the correct choice—it has exactly the signals needed (AWADDR, AWVALID, AWREADY, WDATA, WSTRB, WVALID, WREADY, BRESP, BVALID, BREADY, and the read equivalents) with no burst-length or ordering complexity.

### Code Example

```vhdl
-- Minimal correct AXI-Lite write handshake in a custom BRAM slave
-- Key: only capture write when both address and data channels are valid
process(S_AXI_ACLK)
begin
  if rising_edge(S_AXI_ACLK) then
    if S_AXI_ARESETN = '0' then
      aw_active  <= '0';
      w_active   <= '0';
      bvalid_reg <= '0';
    else
      -- Accept address when both AWVALID and WVALID are present
      if S_AXI_AWVALID = '1' and S_AXI_WVALID = '1' and aw_active = '0' then
        aw_active  <= '1';
        addr_reg   <= S_AXI_AWADDR;
        data_reg   <= S_AXI_WDATA;
        strb_reg   <= S_AXI_WSTRB;
      end if;

      -- Issue write response after capturing address+data
      if aw_active = '1' then
        aw_active  <= '0';
        bvalid_reg <= '1';
        -- perform actual BRAM write here using addr_reg/data_reg
      end if;

      -- Deassert BVALID once master accepts the response
      if bvalid_reg = '1' and S_AXI_BREADY = '1' then
        bvalid_reg <= '0';
      end if;
    end if;
  end if;
end process;

S_AXI_AWREADY <= '1' when (S_AXI_AWVALID = '1' and S_AXI_WVALID = '1' and aw_active = '0') else '0';
S_AXI_WREADY  <= S_AXI_AWREADY;  -- accept data same cycle as address
S_AXI_BVALID  <= bvalid_reg;
S_AXI_BRESP   <= "00";           -- OKAY response
```

### Relevance to Your Project

The KV260 AXI-BRAM demo writes from the Cortex-A53 PS over AXI-Lite to BRAM0 (0xA0000000) and BRAM2 (0xA0010000). The write-enable early-assertion bug is a known hazard when using the Xilinx AXI BRAM Controller IP—if you observe write corruption at the address *before* your intended target, enabling the BRAM's `ENA` via the controller's dedicated enable output (not a static tie to '1') is the fix. Additionally, if you ever replace or augment the Xilinx IP with a custom VHDL slave, the synchronized AWREADY/WREADY pattern above is the correct starting point.

## Vivado Block Design / IP Integrator

### Key Findings

- **Run Connection Automation after every new IP drop**: Vivado's "Run Connection Automation" button wires clocks, resets, and AXI ports to the Zynq PS. If you add a second BRAM controller and forget to re-run it, the interconnect may be left unconnected without an obvious error until elaboration.
- **Address Editor: Assign All vs. manual**: Click "Assign All" in the Address Editor tab to let Vivado auto-assign slave offset and range. For the demo's two BRAMs, manually confirming BRAM0 at 0xA0000000 (64K range) and BRAM2 at 0xA0010000 (64K range) in the editor ensures the firmware addresses match the hardware.
- **AXI SmartConnect preferred over AXI Interconnect**: SmartConnect is the current-generation IP (lower latency, fewer dead-cycles on the write response path) and avoids the BRAM early write-enable bug seen with the older AXI Interconnect. Use SmartConnect for new designs.
- **Save the block design frequently (Ctrl+S)**: BD state is not auto-saved; an unsaved BD that crashes Vivado loses all manual wiring. Save before running synthesis or implementation.
- **Validate Design (F6) before generating output products**: "Validate Design" catches AXI width mismatches, unconnected required ports, and address-space collisions before you spend 20 minutes in synthesis only to see a critical warning.

### Code Example

```tcl
# TCL to add and connect a second AXI BRAM Controller in an existing BD
# Run from the Vivado TCL console after the first BRAM is already present

open_bd_design [get_bd_designs kv260_bd]

# Add second BRAM controller
create_bd_cell -type ip -vlnv xilinx.com:ip:axi_bram_ctrl:4.1 axi_bram_ctrl_1

# Add second Block Memory Generator
create_bd_cell -type ip -vlnv xilinx.com:ip:blk_mem_gen:8.4 blk_mem_gen_1
set_property -dict [list \
  CONFIG.Memory_Type {True_Dual_Port_RAM} \
  CONFIG.Use_Byte_Write_Enable {true} \
  CONFIG.Byte_Size {8} \
  CONFIG.Write_Width_A {32} \
  CONFIG.Read_Width_A {32} \
] [get_bd_cells blk_mem_gen_1]

# Connect BRAM controller to BRAM
connect_bd_intf_net [get_bd_intf_pins axi_bram_ctrl_1/BRAM_PORTA] \
                    [get_bd_intf_pins blk_mem_gen_1/BRAM_PORTA]

# Let IP Integrator wire clocks/resets and connect to SmartConnect
apply_bd_automation -rule xilinx.com:bd_rule:axi4 \
  -config { Clk_master {Auto} Clk_slave {Auto} Clk_xbar {Auto} \
            Master {/zynq_ultra_ps_e_0/M_AXI_HPM0_FPD} \
            Slave {/axi_bram_ctrl_1/S_AXI} \
            intc_ip {/axi_smartconnect_0} \
            master_apm {0} } \
  [get_bd_intf_pins axi_bram_ctrl_1/S_AXI]

# Assign addresses
assign_bd_address
set_property offset 0xA0010000 [get_bd_addr_segs \
  {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_1_Mem0}]
set_property range 64K [get_bd_addr_segs \
  {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_1_Mem0}]

save_bd_design
validate_bd_design
```

### Relevance to Your Project

The demo uses two BRAM controllers (BRAM0 + BRAM2) connected via the Zynq PS `M_AXI_HPM0_FPD` port. The TCL snippet above is directly applicable for scripted recreation of the block design's second BRAM connection, ensuring addresses 0xA0010000 is correctly set without touching the GUI. Running `validate_bd_design` before `generate_target` catches any wiring mistakes early.

## Vivado TCL Scripting

### Key Findings

- **Non-project mode is ideal for CI**: `vivado -mode batch -source build.tcl` runs the entire flow (read sources → synth → impl → bitstream) in-memory with no `.xpr` project file; the only outputs are reports, checkpoints, and the bitstream. This is reproducible and git-friendly.
- **Project mode `write_project_tcl` for migration**: If you start in GUI project mode, use `File > Write Project Tcl` (or `write_project_tcl rebuild.tcl`) to export a complete rebuild script. This is how most Kria demos distribute their designs.
- **Reference guide**: UG835 covers every Tcl command; UG892 covers non-project vs project flow architecture. Both are on docs.amd.com.
- **Use `set_msg_config` to elevate critical warnings**: In batch mode, routing/timing critical warnings don't fail the script by default. Add `set_msg_config -id "Route 35-5" -new_severity "ERROR"` to promote specific messages to errors that abort the build.
- **`write_hw_platform` (formerly `write_sysdef`) exports the XSA**: After bitstream generation, `write_hw_platform -fixed -force kv260.xsa` creates the hardware platform archive imported into Vitis to create the BSP.

### Code Example

```tcl
# Non-project mode build script for KV260 AXI-BRAM demo
# Usage: vivado -mode batch -source build.tcl

set PART "xck26-sfvc784-2LV-c"
set TOP  "kv260_top"

# Read sources
read_vhdl  ../vhdl/kv260_top.vhd
read_xdc   ../constraints/kv260_top.xdc

# Synthesis
synth_design -top $TOP -part $PART -flatten_hierarchy rebuilt
write_checkpoint -force post_synth.dcp
report_timing_summary -file post_synth_timing.rpt

# Implementation
opt_design
place_design
phys_opt_design
route_design
write_checkpoint -force post_route.dcp
report_timing_summary -file post_route_timing.rpt
report_utilization    -file utilization.rpt

# Promote any unresolved timing paths to errors before writing bitstream
set_msg_config -id "Timing 38-282" -new_severity "ERROR"

# Write outputs
write_bitstream -force $TOP.bit
write_hw_platform -fixed -force kv260_demo.xsa

puts "Build complete: $TOP.bit + kv260_demo.xsa"
```

### Relevance to Your Project

The TCL `create_bd.tcl` in your project's `tcl/` directory creates the Vivado block design. Wrapping it with the non-project-mode build script above gives a single-command CI path: `vivado -mode batch -source build.tcl` produces both the bitstream and the `.xsa` for Vitis without any GUI interaction. Using `write_hw_platform` replaces the manual XSA export step in the Vivado GUI.

## Vitis Bare-Metal / Standalone

### Key Findings

- **`xil_printf` vs `printf`**: `xil_printf` uses ~3KB less flash/SRAM than newlib `printf` because it lacks floating-point support and locale handling. For the PASS/FAIL UART output in this project, always prefer `xil_printf`.
- **BSP `stdout` must match your UART instance**: In the Vitis BSP settings, `stdin`/`stdout` must be set to the UartPS instance wired to the KV260's USB-UART (typically `psu_uart_1` for the KV260 carrier). A mismatch produces silent output.
- **Interrupt controller (GIC) on Zynq UltraScale+**: The Cortex-A53 uses an ARM GIC-400 (`XScuGic`). For bare-metal, use `XScuGic_Connect()` + `XScuGic_Enable()`. The KV260 does not need GIC initialization for simple polled AXI-BRAM reads/writes, but any future IRQ from PL logic requires it.
- **Linker script heap/stack**: The default standalone linker script places stack at the top of DDR; for bare-metal BRAM demos running from OCM or with tight timing, verify `_stack_end` and `_heap_size` in `lscript.ld` are not colliding with your data segment.
- **`Xil_Out32` / `Xil_In32` for direct MMIO**: These inline functions in `xil_io.h` write/read a 32-bit word to/from an absolute address with a memory barrier. They are the correct way to access the AXI-BRAM windows at 0xA0000000 and 0xA0010000 from bare-metal C.

### Code Example

```c
/* Bare-metal AXI-BRAM write/read/verify using Xil_Out32/Xil_In32
 * BRAM0 base: 0xA0000000, BRAM2 base: 0xA0010000
 * Assumes Vitis standalone BSP with xil_io.h included via xparameters.h */

#include "xil_printf.h"
#include "xil_io.h"
#include "xparameters.h"

#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL
#define TEST_WORDS  16

int bram_test(u32 base_addr, const char *name) {
    u32 pattern, readback;
    int errors = 0;

    /* Write phase */
    for (u32 i = 0; i < TEST_WORDS; i++) {
        pattern = 0xDEAD0000UL | (base_addr >> 16) | i;
        Xil_Out32(base_addr + (i * 4), pattern);
    }

    /* Barrier: ensure all writes committed before reads */
    dsb();

    /* Read and verify phase */
    for (u32 i = 0; i < TEST_WORDS; i++) {
        pattern  = 0xDEAD0000UL | (base_addr >> 16) | i;
        readback = Xil_In32(base_addr + (i * 4));
        if (readback != pattern) {
            xil_printf("[FAIL] %s addr 0x%08X: wrote 0x%08X read 0x%08X\r\n",
                       name, base_addr + (i * 4), pattern, readback);
            errors++;
        }
    }

    if (errors == 0)
        xil_printf("[PASS] %s: all %d words verified\r\n", name, TEST_WORDS);

    return errors;
}

int main(void) {
    int total_errors = 0;
    xil_printf("=== KV260 AXI-BRAM Demo ===\r\n");
    total_errors += bram_test(BRAM0_BASE, "BRAM0");
    total_errors += bram_test(BRAM2_BASE, "BRAM2");
    xil_printf("Result: %s\r\n", total_errors == 0 ? "PASS" : "FAIL");
    return total_errors;
}
```

### Relevance to Your Project

This is the core pattern for `main.c` in the KV260 AXI-BRAM demo. The `dsb()` barrier between the write loop and read loop is critical: without it, the Cortex-A53's out-of-order pipeline may reorder memory accesses and produce false PASS results in simulation but real failures on hardware. `Xil_Out32`/`Xil_In32` already include the necessary barriers internally, but an explicit `dsb()` between the loops adds safety when the compiler optimizes the loops.

## XDC Timing Constraints

### Key Findings

- **`create_clock` on `pl_clk0` is the foundation**: For the KV260's Zynq PS-generated clock to PL, define `create_clock -period 10.000 -name pl_clk0 [get_ports pl_clk0]` (or use the BD-generated wrapper name). All `set_input_delay`/`set_output_delay` constraints for PL I/O must reference this clock.
- **`set_input_delay -max` and `-min` both required**: For each external input, provide both `-max` (setup) and `-min` (hold) values. Omitting `-min` causes the tools to assume zero hold slack and can generate spurious hold-time violations.
- **`set_clock_groups -asynchronous`**: If you have a second clock domain (e.g., a dedicated BRAM clock or JTAG clock), use `set_clock_groups -asynchronous -group {clk_a} -group {clk_b}` to cut false timing paths across unrelated domains. Without this, Vivado tries to time across them and may report impossible paths.
- **False path on reset**: Add `set_false_path -from [get_ports rst_n]` if your external reset is asynchronous. The synchronizer flip-flops inside the design handle metastability; constraining the external reset as a timing path is meaningless and generates noise.
- **`report_clock_interaction` is your first check**: After routing, run `report_clock_interaction` to see all crossing paths and confirm CDC (clock domain crossing) paths are properly constrained before checking `report_timing_summary`.

### Code Example

```tcl
# kv260_top.xdc - Timing constraints for KV260 AXI-BRAM bare-metal demo

# Primary PL clock from Zynq PS (100 MHz example)
# The actual port name comes from the BD wrapper; adjust if different
create_clock -period 10.000 -name pl_clk0 [get_ports pl_clk0]

# If using a dedicated BRAM clock (e.g. from a MMCM):
# create_clock -period 5.000 -name bram_clk [get_pins mmcm_inst/CLKOUT0]

# Treat PS-to-PL reset as false path (async assert, sync deassert inside design)
set_false_path -from [get_ports pl_resetn0]

# Example I/O timing for any external GPIO (not needed for pure PS-to-BRAM)
# Assuming board-level setup/hold of 2 ns max / 0.5 ns min:
# set_input_delay -clock pl_clk0 -max 2.0 [get_ports gpio_in[*]]
# set_input_delay -clock pl_clk0 -min 0.5 [get_ports gpio_in[*]]
# set_output_delay -clock pl_clk0 -max 2.0 [get_ports gpio_out[*]]
# set_output_delay -clock pl_clk0 -min 0.5 [get_ports gpio_out[*]]

# Cut paths between PS and any async PL clocks (if present)
# set_clock_groups -asynchronous \
#   -group [get_clocks pl_clk0] \
#   -group [get_clocks bram_clk]

# Promote timing violations to errors in batch flows
set_msg_config -id "Timing 38-282" -new_severity "ERROR"
```

### Relevance to Your Project

For the bare-metal AXI-BRAM demo where all logic runs on the single Zynq PS-generated `pl_clk0`, the constraints are minimal—primarily the `create_clock` and a false path on the reset. The commented-out I/O delay and clock-group constraints are placeholders for when you add external GPIO or a second clock. The `set_msg_config` line is critical for CI: it prevents the build script from completing with unresolved timing violations.

## Kria KV260 / K26 SoM

### Key Findings

- **Boot mode is set by MODE[3:0] resistors on the carrier card**: The KV260 ships in QSPI32 boot mode (all four MODE pins tied per the QSPI32 pattern). Bare-metal development typically uses JTAG boot mode—this requires pulling MODE[3:0] to the JTAG strapping value **or** using Vitis/XSCT to download directly over JTAG without changing the physical straps.
- **MIO vs EMIO**: USB-UART (the PS UART at `/dev/ttyUSB1` when connected via the micro-USB on the KV260 carrier) is wired to MIO bank 500 pins—it is a PS peripheral directly connected without going through the PL. No VHDL wrapper or XDC pin assignment is needed for UART in the AXI-BRAM demo.
- **`M_AXI_HPM0_FPD` is the recommended PS-to-PL AXI port**: On the K26, use `M_AXI_HPM0_FPD` (High Performance Master port to Full Power Domain) for custom PL IP like BRAM controllers. `M_AXI_HPM1_FPD` is a second available port. Avoid `M_AXI_LPD` for PL IP unless specifically needed for the low-power domain.
- **Power domains**: The K26 has three power domains—Full Power Domain (FPD, includes Cortex-A53 + DDR), Low Power Domain (LPD, includes Cortex-R5 + OCM), and the PL domain. The AXI-BRAM demo runs entirely in FPD + PL; no power-domain crossing isolation is required for this configuration.
- **Platform prerequisites for Vitis 2025.1**: For the KV260, you need to export the XSA from Vivado, then create a Vitis platform (or use `xsct` scripting) to generate the standalone BSP targeting the `psu_cortexa53_0` processor.

### Code Example

```tcl
# XSCT (Xilinx Software Command-line Tool) script to:
# 1. Connect to KV260 via JTAG
# 2. Program the bitstream
# 3. Download and run the bare-metal ELF
# Usage: xsct program_kv260.tcl

connect

# Select the Cortex-A53 core #0
targets -set -filter {name =~ "Cortex-A53 #0"}

# Initialize the PS (runs FSBL-equivalent initialization)
rst -system
after 3000

# Program the PL bitstream
fpga -file kv260_top.bit

# Download the bare-metal application ELF
dow kv260_axi_bram_demo.elf

# Run the application
con

puts "KV260 programmed and running. Check USB-UART for PASS/FAIL output."
disconnect
```

### Relevance to Your Project

This XSCT script replaces the manual "Run" button workflow in Vitis and is directly usable with the KV260 AXI-BRAM demo. The `rst -system` followed by a delay is necessary because the Zynq UltraScale+ PS needs time after reset before the PL can be programmed. The `fpga -file` command programs the `.bit` file over JTAG—no boot mode resistor change needed. After `con`, the demo's PASS/FAIL output appears on the USB-UART terminal.

## AMD/Xilinx Tool Updates (Vivado/Vitis 2025.x)

### Key Findings

- **Vivado 2025.2 release highlights**: A new ultra-low-area strategy for AXI SmartConnect and AXI Switch IPs via the `STRATEGY` parameter reduces LUT consumption by up to 30% for designs with many peripheral connections.
- **Vitis 2025.1 release date**: The Vitis 2025.1 unified platform was released 2025-07-08 per UG1742. This is the version documented in current KV260 tutorials (LogicTronix BIST tutorial on Hackster).
- **Hardware Design Fast Iteration (XD101)**: A new Vitis 2025.1 tutorial "Hardware Design Fast Iteration with Vitis Export to Vivado" documents the recommended round-trip workflow: design in Vivado → export XSA → create Vitis platform → iterate on software, then export hardware changes back. This is the correct flow for the AXI-BRAM demo.
- **IP Release Notes (AR 000037919)**: AMD publishes per-release IP change logs. For 2025.1, notable fixes include AXI Ethernet buffer deadlock prevention and pause-acknowledge handling in frequency-optimized pipelines. Not directly applicable to the BRAM demo but worth bookmarking for future IP additions.
- **Non-project mode TCL now covers 2026.1**: AMD's UG892 "Using Non-Project Mode Tcl Commands" was updated for 2026.1 in early 2026, adding guidance on new device families. The KV260/K26 workflow documented therein is stable across 2025.1–2026.1.

### Code Example

```tcl
# Vitis XSCT: Scriptable platform + application creation for KV260 bare-metal demo
# Replaces all GUI clicks in Vitis 2025.1+
# Usage: xsct create_vitis_project.tcl

setws ./vitis_workspace

# Create platform from XSA generated by Vivado
platform create -name kv260_platform \
  -hw ./kv260_demo.xsa \
  -proc psu_cortexa53_0 \
  -os standalone

# Configure BSP: set stdout to the PS UART wired to USB-UART on KV260
bsp config stdout psu_uart_1

# Build the platform (generates BSP libraries)
platform build

# Create the bare-metal application project
app create -name kv260_axi_bram_demo \
  -platform kv260_platform \
  -domain standalone_domain \
  -template "Empty Application (C)"

# Copy main.c into the application source directory
file copy -force ../src/main.c ./vitis_workspace/kv260_axi_bram_demo/src/

# Build the application
app build -name kv260_axi_bram_demo

puts "Build complete: vitis_workspace/kv260_axi_bram_demo/Debug/kv260_axi_bram_demo.elf"
```

### Relevance to Your Project

This XSCT script automates the Vitis side of the build pipeline. Combined with the Vivado non-project-mode TCL from the Vivado TCL Scripting section above, you now have a fully scripted end-to-end flow: `vivado -mode batch -source build.tcl` → `xsct create_vitis_project.tcl` → `xsct program_kv260.tcl`. No GUI required. This is CI-ready and can run unattended, for example on every commit to the kv260-axi-bram-demo repository.
