## Executive Summary
- Xilinx's own AXI-Lite example/demo slave cores have had long-standing handshake bugs (write-address handshake before ~2016.3, read-channel backpressure issues persisting later) — worth keeping in mind if you ever swap the AXI BRAM Controller for a custom AXI-Lite slave; verify your own logic doesn't drop AWREADY/ARREADY independent of downstream backpressure.
- Two BRAM controllers mapped at 0xA0000000/0xA0010000 should show up as two distinct segments in the Vivado Address Editor under the Cortex-A53 (`psu_cortexa53_0`) address space — if `create_bd.tcl` sets these with `assign_bd_address`/`set_property offset`, a regenerate/validate after any future BD edit can silently move them unless you re-pin the offsets.
- `xil_printf` (used for your PASS/FAIL UART output) only supports `%d`, `%ld`, `%x`, `%c`, `%s` — no `%f` — and pulls in far less code than full `stdio`, which matters for a minimal bare-metal demo with no heap/MMU setup.
- AXI BRAM Controller in this kind of design typically runs as full AXI4 (not AXI4-Lite) between the interconnect and BRAM to get burst support, even though the PS-side master interface seen from Cortex-A53 looks like simple AXI-Lite register access — double check which protocol `create_bd.tcl` actually configures on the S_AXI port of each `axi_bram_ctrl`.
- Vivado/Vitis 2025.1 defaults to the Unified IDE for Vitis (Classic IDE deprecated) — if your build scripts or docs still reference Vitis Classic project structure, they may need updating for reproducibility on a fresh 2025.1 install.

## AXI Protocol / AXI-Lite / AXI-Stream
### Key Findings
- A long-documented bug in Xilinx's example AXI-Lite slave template ties state transitions purely to `*VALID && *READY` without correctly gating on downstream backpressure — e.g., ARREADY should depend on the read-return channel (RVALID/RREADY) being able to accept the response, not just on ARVALID. This was reportedly still present in some "fixed" cores even after the write-side bug was patched post-2016.3.
- If a master holds `BREADY` low, the slave must hold `AWREADY`/`WREADY` low for new transactions; if it holds `RREADY` low, the slave must hold `ARREADY` low. These corner cases are easy to miss in simulation-only testing because most testbenches keep `READY` signals high.
- Per the AXI4 spec, `WVALID`, `WREADY`, and `BVALID` can legally assert in the same cycle, but never for the *same* transaction in the same cycle — ordering still matters.
- If `AWVALID && AWREADY` and `ARVALID && ARREADY` both fire in the same cycle on a slave that doesn't arbitrate read/write properly, one of the two bursts can be silently dropped.
- The AXI BRAM Controller (`axi_bram_ctrl`, used for BRAM0/BRAM2) is documented (DS777/PG078) to support both AXI4 and AXI4-Lite protocol modes on its S_AXI; for two simple memory-mapped regions like this project, AXI4-Lite is the simpler/safer choice since it avoids burst-handling edge cases entirely.

### Code Example
```tcl
# Verify AXI protocol mode actually configured on each BRAM controller's S_AXI
foreach bram_ctrl {axi_bram_ctrl_0 axi_bram_ctrl_1} {
    set proto [get_property CONFIG.PROTOCOL [get_bd_cells $bram_ctrl]]
    puts "INFO: $bram_ctrl S_AXI protocol = $proto"
    if {$proto ne "AXI4LITE"} {
        puts "WARNING: $bram_ctrl is not AXI4LITE - burst support is on, verify this is intended"
    }
}
```
### Relevance to Your Project
Since this demo issues simple word-at-a-time writes/reads from bare-metal C (no burst transfers), confirm both `axi_bram_ctrl` instances for BRAM0 (0xA0000000) and BRAM2 (0xA0010000) are configured as AXI4-Lite in `create_bd.tcl` rather than full AXI4 — it simplifies the interconnect and removes an entire class of burst/backpressure bugs from your PASS/FAIL test path.

## Vivado Block Design / IP Integrator
### Key Findings
- Connection Automation auto-inserts a Processing System Reset IP and an AXI Interconnect when you wire a master like `psu_cortexa53`/Zynq PS to AXI peripherals, and it auto-populates the Address Editor — but auto-assignment can change offsets on *regeneration* if the BD is edited and "Auto Assign Address" is re-run.
- The Address Editor becomes available only once a bus master with an address space (e.g., the PS7/PSU AXI master) exists in the canvas; right-click → "Auto Assign Address" resolves "unmapped peripheral" validation errors, but will pick its own offsets unless you've explicitly locked yours with `Lock` in the Address Editor or via `set_property offset` in TCL.
- "Regenerate Layout" only affects visual block placement, not address mapping or connections — safe to run anytime for readability.
- Two AXI BRAM Controller instances on a shared interconnect should each show as separate `SEG_axi_bram_ctrl_*_Mem0` segments under the Cortex-A53 (or PS) address space; if a segment is missing, it's almost always a missed Connection Automation step on `S_AXI` for that specific controller.

### Code Example
```tcl
# After running connection automation, explicitly lock the two BRAM offsets so a later
# "Auto Assign Address" pass during BD edits can't silently relocate them.
set_property offset 0xA0000000 [get_bd_addr_segs {psu_cortexa53_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property range  64K        [get_bd_addr_segs {psu_cortexa53_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property offset 0xA0010000 [get_bd_addr_segs {psu_cortexa53_0/Data/SEG_axi_bram_ctrl_1_Mem0}]
set_property range  64K        [get_bd_addr_segs {psu_cortexa53_0/Data/SEG_axi_bram_ctrl_1_Mem0}]
validate_bd_design
```
### Relevance to Your Project
Your two BRAM controllers at fixed offsets (0xA0000000, 0xA0010000) are exactly the kind of mapping that "Auto Assign Address" can silently reshuffle if you ever add a third peripheral and re-run connection automation. Explicitly locking/asserting these two offsets in `create_bd.tcl` after BD creation protects `main.c`'s hardcoded addresses from drifting on a regenerate.

## Vivado TCL Scripting
### Key Findings
- Vivado has two flows: Project Mode and Non-Project Mode, both drivable via TCL; Non-Project Mode batch scripts (`vivado -mode batch -source script.tcl`) give full reproducibility since no `.xpr` project state is implicitly relied upon — good fit for a from-scratch `create_bd.tcl`-driven build.
- In Non-Project Mode you own all source/IP management yourself (no auto project file); you must explicitly write checkpoints/reports if you want artifacts preserved between script runs.
- `create_bd_cell` creates a block-design cell of any IP type; `set_property` is then used for IP customization (e.g., BRAM size, AXI protocol mode); `assign_bd_address` auto-assigns addresses to any still-unmapped block as a one-shot convenience, separate from manually pinning offsets.
- Scripting the whole flow (sources, constraints, IP config) in text files makes the entire hardware build diffable and trackable in git — directly applicable to a repo like this one that already version-controls TCL.

### Code Example
```tcl
# Minimal non-project-mode batch skeleton matching this project's two-BRAM topology
create_project -in_memory -part xczu5eg-sfvc784-2-e
add_files -norecurse {vhdl/kv260_top.vhd}
source tcl/create_bd.tcl
assign_bd_address [get_bd_addr_segs -of_objects [get_bd_cells axi_bram_ctrl_0]]
assign_bd_address [get_bd_addr_segs -of_objects [get_bd_cells axi_bram_ctrl_1]]
validate_bd_design
make_wrapper -files [get_files kv260_bd.bd] -top
add_files -norecurse [make_wrapper -files [get_files kv260_bd.bd] -top]
launch_runs synth_1 -jobs 4
wait_on_run synth_1
```
### Relevance to Your Project
Given `create_bd.tcl` already drives this build, structuring the full flow (project creation → BD source → address assignment → synthesis) as one batch-mode script makes the hardware build reproducible from a clean checkout with no manual Vivado GUI steps — useful for CI or for regenerating the bitstream after any VHDL change to `kv260_top.vhd`.

## Vitis Bare-Metal / Standalone
### Key Findings
- `xil_printf` supports only `%d`, `%ld`, `%x`, `%c`, `%s` format specifiers (no `%f`) and has a much smaller code/stack footprint than full `printf` from `stdio.h` — the right choice for a minimal bare-metal PASS/FAIL reporter over UART.
- The standalone BSP is auto-generated per processor (e.g. `psu_cortexa53_0`) from the hardware platform/XSA; UART driver instance and baud rate come from the BSP's board support settings, not from your application code, so a mismatch between the XSA's UART config and what `main.c` expects is a common source of garbled UART output.
- The bare-metal linker script (`lscript.ld`) controls where `.text`/`.data`/`.bss` get placed in DDR (or OCM) and how much space is reserved — for a Cortex-A53 standalone app this defaults to a generated memory map matching the BSP, but should be checked manually whenever memory regions change.
- Cache: Cortex-A53 standalone apps have D-cache/I-cache enabled by default in many BSP configs; if you ever map shared memory not covered by MMU table entries as cacheable, AXI BRAM reads/writes will appear stale even though they completed at the AXI level — `Xil_DCacheFlush()`/`Xil_DCacheInvalidateRange()` are the relevant standalone APIs to bracket BRAM accesses if cache effects appear.

### Code Example
```c
#include "xil_printf.h"
#include "xil_io.h"
#include "xil_cache.h"

#define BRAM0_BASE 0xA0000000U
#define BRAM2_BASE 0xA0010000U

int test_bram(u32 base, const char *label) {
    u32 pattern = 0xDEADBEEF;
    Xil_Out32(base, pattern);
    Xil_DCacheFlushRange(base, 4);          /* ensure write is visible if region is cacheable */
    u32 readback = Xil_In32(base);
    if (readback == pattern) {
        xil_printf("%s: PASS (wrote 0x%x, read 0x%x)\r\n", label, pattern, readback);
        return 0;
    }
    xil_printf("%s: FAIL (wrote 0x%x, read 0x%x)\r\n", label, pattern, readback);
    return -1;
}
```
### Relevance to Your Project
This mirrors the exact pattern described for `main.c`: writing a known value to BRAM0/BRAM2 over AXI and reading it back with PASS/FAIL over UART. If the BRAM address range is ever marked cacheable in the MMU table (uncommon for AXI peripherals but worth verifying in the BSP-generated `xparameters.h`/translation table), an explicit `Xil_DCacheFlushRange`/`Xil_DCacheInvalidateRange` pair around each access prevents false FAILs from stale cache data rather than actual AXI failures.

## XDC Timing Constraints
### Key Findings
- `set_input_delay`/`set_output_delay` define external system-level path delay on primary I/O ports relative to a clock edge; AMD's UG835 (2025.1) documents both as fundamental SDC-derived commands still central to Vivado timing closure.
- `set_clock_groups` marks clocks as exclusive or asynchronous, disabling timing analysis between domains; this is the standard way to tell Vivado not to time-analyze paths between, e.g., the AXI/PL clock domain and an unrelated free-running clock.
- For genuine clock-domain-crossing (CDC) logic (FIFOs, async resets), current best practice favors `set_max_delay -datapath_only` over blanket `set_false_path`, since false paths fully disable analysis (including for setup hold metastability awareness) — `set_max_delay` at ~2x the faster clock period is now recommended to retain better timing coverage while still suppressing unrealistic delay aggregation.
- Kria K26 SOM XDC files define the SOM240 connector pin-name mapping and Zynq UltraScale+ MPSoC-side constraints already; carrier-card-side I/O constraints (set_input_delay/set_output_delay for any external interface) are still the project's responsibility per UG1091.

### Code Example
```tcl
# Example XDC for a hypothetical external IO crossing into the AXI/PL clock domain,
# plus marking the PS<->PL AXI clock and an unrelated external clock as asynchronous.
create_clock -period 10.000 -name pl_clk0 [get_pins kv260_top_i/clk_wiz/clk_out1]

set_input_delay  -clock pl_clk0 -max 2.000 [get_ports ext_in]
set_input_delay  -clock pl_clk0 -min 0.500 [get_ports ext_in]
set_output_delay -clock pl_clk0 -max 2.000 [get_ports ext_out]
set_output_delay -clock pl_clk0 -min 0.500 [get_ports ext_out]

set_clock_groups -asynchronous \
    -group [get_clocks pl_clk0] \
    -group [get_clocks -of_objects [get_pins ps_e_clk_pin]]
```
### Relevance to Your Project
Since `kv260_top.vhd` only exposes AXI-Lite from the PS to two BRAM controllers (no external I/O pins beyond UART/boot pins handled by the SOM), `set_input_delay`/`set_output_delay` aren't currently exercised — but the moment you add any PMOD/external signal off the carrier card, this is the pattern to use, and `set_clock_groups -asynchronous` is the right call if you ever add a second PL clock domain that isn't meant to be timed against the AXI clock.

## Kria KV260 / K26 SoM
### Key Findings
- The K26 SOM's primary boot device is selected via MODE[3:0] pins tied at the carrier-card level; Kria Starter Kits ship preset to QSPI32 boot mode, with JTAG/SD/QSPI as the other supported options — relevant if this project is ever loaded via SD card instead of JTAG/Vitis download.
- Starting with 2022.1+ Kria Linux images, an EMIO mapping exists for carrier-card fan control; the K26 board file (not the carrier card) defines the base MIO configuration, meaning custom PL/bare-metal designs inherit MIO assignments from the SOM, not something you configure freely in `kv260_top.vhd`.
- Released base `.xsa` designs for Kria deliberately contain no PL logic — "PS is configured and PL is ready for you to add your own designs" — confirming that a from-scratch bare-metal AXI-BRAM PL design like this project is exactly the expected/intended customization path, not a hack around a pre-built image.
- VCCO for sideband signals on the K26/KV260 is 1.8V; full pinout and power-domain detail lives in the K26 SOM Data Sheet and carrier card design guide (UG1091) if any external interfacing is added later.

### Code Example
```tcl
# Confirm the project is building against the correct Kria K26 SOM part/board file
puts [get_property PART [current_project]]
# Expected for KV260: xck26-sfvc784-2LV-c (or similar K26 SOM part marking)
puts [get_property BOARD_PART [current_project]]
```
### Relevance to Your Project
Confirms `create_bd.tcl`/the Vivado project should target the K26 SOM board part (not a generic ZU5EG part) so that the MIO/board-level defaults (boot mode pins, fan EMIO, etc.) are inherited correctly even though this bare-metal demo's logic itself (BRAM0/BRAM2 over AXI-Lite) doesn't touch MIO/EMIO directly.
