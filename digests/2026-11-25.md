# FPGA Research Digest - 2026-11-25

## Executive Summary
- AXI-Lite slave timing bugs found in Vivado-generated example cores via formal verification: write-address channel resets/conditionals are error-prone — always verify with waveform capture or formal tools before trusting generated slave code.
- In Vivado 2025.1, Block Memory Generator (BMG) cannot be selectively upgraded in block designs — full BD upgrade is required when migrating Vivado versions; BD 41-235 width-mismatch warnings occur when BRAM controller's 14-bit address port connects to a 32-bit BMG port.
- For reproducible block designs, use `write_bd_tcl` to export TCL, avoid running `apply_bd_automation` from scripts (use GUI Designer Assistance banners instead), and never run `upgrade_ip [get_ips -all]` — it removes sub-cores mid-upgrade.
- Kria KV260 ships with QSPI32 as the default boot mode; JTAG and SD alternatives require explicit strap changes on the carrier card. MIO Bank 500 (1.8V) is SOM-reserved (QSPI/eMMC/I2C), while Banks 501/502 route to the carrier via 240-pin connectors.
- Cortex-A53 data cache can produce false FAIL results in AXI-BRAM tests — always call `Xil_DCacheFlushRange`/`Xil_DCacheInvalidateRange` around peripheral MMIO accesses or mark the address region as strongly-ordered in the MPU.

Findings are based on web research and known project context. Code examples are written to match the described project architecture.

## AXI Protocol / AXI-Lite / AXI-Stream
### Key Findings
- **Valid/Ready deadlock rule:** `AWVALID`, `ARVALID`, `WVALID`, `TVALID` must NEVER be gated on the corresponding `READY` signal — this creates a combinational loop and can deadlock. `READY` can depend on `VALID` (but the reverse is forbidden).
- **Vivado-generated slave bugs (ZipCPU formal analysis):** Multiple errors found in Xilinx's AXI-Lite example core via formal property checking — specifically in the reset-and-conditional logic on the write-address channel where the handshake state can be skipped when `AWVALID` and `AWREADY` coincide on the same clock edge.
- **ARREADY independence gap:** The standard Xilinx AXI-Lite slave does not gate `ARREADY` on `RVALID` or `RREADY`, meaning it can accept more read requests than it can answer — a silent backpressure gap that causes data corruption on burst-like access patterns.
- **Skipped response state:** An open-source AXI bridge showed a case where the acknowledge became active in the same cycle the stall de-asserted, causing the response-read state to be bypassed — a valid AXI-Lite handshake was not guaranteed.
- **AXI-Stream stability rule:** `TDATA`, `TKEEP`, and `TLAST` must all remain stable while `TVALID` is asserted but `TREADY` is LOW (the stall condition).
- **AXI Firewall trips:** AMD Vitis 2025.1 guidance highlights AXI Firewall trips as a first-line debug for PS→PL access hangs; check the AXI firewall status register in your debugger before assuming a logic error.

### Code Example
```vhdl
-- Correct AXI-Lite write-address/write-data channel separation (VHDL)
-- Key rule: latch address only when BOTH awvalid AND awready are high
-- Do NOT gate awready on wvalid — handle channels independently

architecture rtl of axil_slave is
  signal aw_active : std_logic := '0';
  signal aw_addr_r : std_logic_vector(31 downto 0);
  signal w_done    : std_logic := '0';
begin

  -- Write Address channel
  p_aw : process(clk)
  begin
    if rising_edge(clk) then
      if rst = '1' then
        aw_active <= '0';
      elsif s_axil_awvalid = '1' and s_axil_awready = '1' then
        aw_active <= '1';
        aw_addr_r <= s_axil_awaddr;
      elsif w_done = '1' then
        aw_active <= '0';
      end if;
    end if;
  end process;

  -- AWREADY: accept new address only when not already holding one
  s_axil_awready <= not aw_active;

  -- Write Data channel: accept data when address is latched
  s_axil_wready <= aw_active;

  -- Write response: send BRESP=OKAY after write completes
  p_b : process(clk)
  begin
    if rising_edge(clk) then
      if rst = '1' then
        s_axil_bvalid <= '0';
        w_done        <= '0';
      elsif aw_active = '1' and s_axil_wvalid = '1' then
        -- perform write to register at aw_addr_r here
        s_axil_bvalid <= '1';
        s_axil_bresp  <= "00";  -- OKAY
        w_done        <= '1';
      elsif s_axil_bready = '1' then
        s_axil_bvalid <= '0';
        w_done        <= '0';
      end if;
    end if;
  end process;

end architecture rtl;
```
### Relevance to Your Project
Your bare-metal `main.c` writes patterns to BRAM0 (0xA0000000) and BRAM2 (0xA0010000) over AXI-Lite through the AXI BRAM Controller. If you ever replace the AMD IP with a custom slave (or modify `kv260_top.vhd` to add an AXI slave), the channel-independence rule above is the most common source of silent data corruption. Use Vivado's built-in ILA or add a simple waveform simulation to verify that `AWREADY` does not oscillate unexpectedly during back-to-back writes.

## Vivado Block Design / IP Integrator
### Key Findings
- **Export with `write_bd_tcl`:** Regenerate a reproducible script from your in-memory block design. The script is version-stamped, so it may not run across major Vivado releases without manual fixup.
- **Build in GUI first, then capture:** AMD recommends creating the BD interactively, then capturing the TCL script for automation — not driving the entire build from TCL from the start.
- **`apply_bd_automation` caveat:** Use this from GUI Designer Assistance banners, not from raw TCL scripts. AMD's UG835 warns that `apply_bd_automation` is intended for IDE use; if you must script it, run `write_bd_tcl` afterward to capture the result cleanly.
- **IP upgrade pitfall:** Never run `upgrade_ip [get_ips -all]` — the `-all` flag includes sub-cores that can be removed during a parent IP upgrade, leaving dangling Tcl references and a broken BD.
- **BD 41-235 width mismatch:** AXI BRAM Controller uses a 14-bit address port internally; connecting it to a 32-bit Block Memory Generator port produces BD 41-235 — only the lower address bits are wired. Fix this by aligning the BRAM controller's address width to the BMG's configuration.
- **Block Memory Generator migration:** In Versal (and future Vivado versions), BMG is replaced by Embedded Memory Generator — migration is NOT automatic when upgrading.

### Code Example
```tcl
# Recommended workflow: export then re-source block design

# --- In Vivado IDE (or after GUI changes) ---
# File > Export > Export Block Design
write_bd_tcl -force ./tcl/create_bd.tcl

# --- In batch/CI mode: recreate project from scratch ---
create_project my_kv260 ./my_kv260 -part xck26-sfvc784-2LV-c
set_property target_language VHDL [current_project]

# Add IP repository if using custom IP
# set_property ip_repo_paths {./ip_repo} [current_project]
# update_ip_catalog -rebuild

source ./tcl/create_bd.tcl
make_wrapper -files [get_files *.bd] -top
add_files -norecurse ./my_kv260/my_kv260.gen/sources_1/bd/*/hdl/*_wrapper.vhd

# Generate all IP output products
generate_target all [get_files *.bd]

# Upgrade individual IPs (never -all):
# upgrade_ip [get_ips axi_bram_ctrl_0]
# upgrade_ip [get_ips blk_mem_gen_0]
```
### Relevance to Your Project
Your `create_bd.tcl` creates the AXI Interconnect, AXI BRAM Controller, and Block Memory Generator connections. Run `write_bd_tcl -force` after any BD change in the IDE to keep the script in sync. Watch for BD 41-235 on the BRAM address port — this warning is benign for small BRAMs but becomes an issue if you increase depth and need more address bits.

## Vivado TCL Scripting
### Key Findings
- **Non-project (batch) mode:** AMD UG894 covers writing Tcl scripts that drive the full flow (`read_vhdl` → `synth_design` → `opt_design` → `place_design` → `route_design` → `write_bitstream`) without an `.xpr` file — ideal for CI pipelines.
- **IP repository must be set first:** If `create_bd.tcl` fails on IP instantiation, check that `set_property ip_repo_paths` is called before `update_ip_catalog` and before `source create_bd.tcl`.
- **Runtime improvement:** Avoid unnecessary `report_*` calls inside the main synthesis/implementation flow; defer all reports to post-implementation to minimize memory and wall-clock overhead.
- **`write_ip_tcl` for custom IP:** Generates a reproducible script for RTL IP with parameter customizations — useful for documenting your BRAM and AXI Interconnect parameter choices.
- **Script versioning:** Always call `version` or `get_property VIVADO_VERSION [current_design]` at the top of batch scripts to log the tool version for reproducibility and troubleshooting.
- **`set_msg_config` to control noise:** Suppress known informational messages (e.g., `[BD 41-235]` if already acknowledged) with `set_msg_config -suppress -id "BD 41-235"` to keep CI logs readable.

### Code Example
```tcl
# Non-project (batch) mode full flow for KV260 AXI-BRAM design
# Usage: vivado -mode batch -source ./tcl/build_all.tcl

set part   "xck26-sfvc784-2LV-c"
set outdir "./output"

file mkdir $outdir

# Log tool version
puts "Vivado version: [version -short]"

# Recreate block design and generate wrapper
source ./tcl/create_bd.tcl
make_wrapper -files [get_files *.bd] -top

# Read wrapper and constraints
read_vhdl [glob ./my_kv260/my_kv260.gen/sources_1/bd/*/hdl/*_wrapper.vhd]
read_xdc  ./xdc/kv260_top.xdc

# Synthesis
synth_design -top kv260_bd_wrapper -part $part -flatten_hierarchy rebuilt
write_checkpoint -force $outdir/post_synth.dcp

# Implementation
opt_design
place_design
phys_opt_design
route_design
write_checkpoint -force $outdir/post_route.dcp

# Reports (post-implementation only)
report_timing_summary -file $outdir/timing_summary.rpt
report_utilization    -file $outdir/utilization.rpt
report_drc            -file $outdir/drc.rpt

# Bitstream
write_bitstream -force $outdir/kv260_top.bit
puts "Build complete: $outdir/kv260_top.bit"
```
### Relevance to Your Project
Wrapping your existing `create_bd.tcl` with a non-project driver script like this enables fully headless CI builds (GitHub Actions, Jenkins, etc.). The `report_timing_summary` gating on negative WNS catches timing failures before you try to load the bitstream on hardware.

## Vitis Bare-Metal / Standalone
### Key Findings
- **`xil_printf` vs standard `printf`:** Use `xil_printf` (from `xil_printf.h`) for bare-metal — it is a lightweight implementation without full libc floating-point overhead. Standard `printf` with `%f` pulls in large formatter machinery that balloons bare-metal image size.
- **Linker script location and reset:** The auto-generated linker script lives at `<app>/sources/src/lscript.ld`. Right-click the application → Reset Linker Script to regenerate from the updated BSP memory map after any platform hardware change.
- **Cache coherency (critical for AXI BRAM):** Cortex-A53 L1/L2 data cache can serve stale data if the AXI peripheral region is marked cacheable. Always call `Xil_DCacheFlushRange()` after writes and `Xil_DCacheInvalidateRange()` before reads to peripheral-mapped addresses.
- **MPU for peripheral regions:** Mark the AXI peripheral address regions (e.g., `0xA0000000`) as strongly-ordered or device memory in the MPU configuration — the BSP's `xil_mmu.h` / `Xil_SetTlbAttributes()` can do this.
- **Standalone interrupt setup (GIC on A53):** Use `XScuGic` driver from `xscugic.h`. Call `XScuGic_CfgInitialize()`, register handler with `XScuGic_Connect()`, enable the interrupt with `XScuGic_Enable()`, then `Xil_ExceptionEnable()`. For bare-metal with no OS, also call `Xil_ExceptionRegisterHandler(XIL_EXCEPTION_ID_IRQ_INT, ...)`.
- **Vitis 2025.1 (released 2025-07-08):** Adds Clang 16 / initial C++17 support, Vitis HLS GUI improvements. OS support ending after 2025.1: RHEL 9.2/9.3 and Ubuntu 22.04.2 LTS.

### Code Example
```c
#include "xil_printf.h"
#include "xparameters.h"
#include "xil_cache.h"
#include "xil_mmu.h"

#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL
#define BRAM_SIZE   0x00010000UL   /* 64 KB each */

/* Mark AXI peripheral regions as strongly-ordered (non-cacheable) */
static void configure_mpu(void)
{
    /* Device memory, non-shareable, non-cacheable, non-bufferable */
    Xil_SetTlbAttributes(BRAM0_BASE, NORM_NONCACHE | STRONG_ORDERED);
    Xil_SetTlbAttributes(BRAM2_BASE, NORM_NONCACHE | STRONG_ORDERED);
}

static void bram_write32(uint32_t base, uint32_t offset, uint32_t val)
{
    *(volatile uint32_t *)(base + offset) = val;
    /* Flush if MPU is not configured as device memory */
    /* Xil_DCacheFlushRange(base + offset, 4); */
}

static uint32_t bram_read32(uint32_t base, uint32_t offset)
{
    /* Invalidate if MPU is not configured as device memory */
    /* Xil_DCacheInvalidateRange(base + offset, 4); */
    return *(volatile uint32_t *)(base + offset);
}

int main(void)
{
    configure_mpu();
    xil_printf("AXI-BRAM bare-metal test\r\n");

    const uint32_t patterns[] = {0xDEADBEEF, 0xCAFEBABE, 0x12345678, 0xA5A5A5A5};
    int pass = 1;

    for (int i = 0; i < 4; i++) {
        bram_write32(BRAM0_BASE, i * 4, patterns[i]);
        bram_write32(BRAM2_BASE, i * 4, ~patterns[i]);
    }

    for (int i = 0; i < 4; i++) {
        uint32_t v0 = bram_read32(BRAM0_BASE, i * 4);
        uint32_t v2 = bram_read32(BRAM2_BASE, i * 4);
        if (v0 != patterns[i] || v2 != ~patterns[i]) {
            xil_printf("FAIL @ index %d: BRAM0=0x%08X BRAM2=0x%08X\r\n", i, v0, v2);
            pass = 0;
        }
    }
    xil_printf("Result: %s\r\n", pass ? "PASS" : "FAIL");
    return 0;
}
```
### Relevance to Your Project
This directly extends your existing `main.c` PASS/FAIL test pattern. The `configure_mpu()` call is the most likely fix if your test returns intermittent FAILs — the A53 D-cache will serve a cached copy of the write buffer rather than the actual BRAM read-back unless the region is marked non-cacheable. Add this before any MMIO access.

## XDC Timing Constraints
### Key Findings
- **Constraint ordering (UG903):** AMD recommends: (1) `create_clock` / `create_generated_clock`, (2) `set_input_delay` / `set_output_delay`, (3) timing exceptions (`set_false_path`, `set_multicycle_path`). I/O delay commands have minimal runtime impact and should not be deferred.
- **`set_input_delay` and `all_inputs`:** When using `all_inputs`, Vivado automatically skips clock ports — but always use an explicit targeted port list for clarity.
- **`set_output_delay -add_delay`:** The default behavior REPLACES existing delay values. Use `-add_delay` to accumulate min and max pairs for the same port (required for source-synchronous interfaces).
- **Clock groups for PS/PL:** The PS-generated clock (`FCLK_CLK0`) and any independent PL-only clocks should be separated with `set_clock_groups -asynchronous` to prevent Vivado from attempting to analyze timing across them when no synchronizer exists.
- **Kria / Zynq PS clock source:** The PS block generates `FCLK_CLK0` via an internal MMCM. Constrain the output at `[get_pins ps_i/inst/PS8_i/PLCLK[0]]` — do NOT apply `set_input_delay` to `FCLK_CLK0` itself; it is a generated clock, not a port.
- **Pure PS→PL AXI designs:** If there are no external I/O ports (no GPIOs brought out through PL), the XDC file for a bare-metal AXI-BRAM design needs only the `create_clock` constraint — Vivado analyzes the internal AXI paths automatically.

### Code Example
```tcl
# kv260_top.xdc — Minimal timing constraints for KV260 AXI-BRAM bare-metal design

# 1. Define the PS-generated PL clock (100 MHz = 10 ns period)
#    Pin path matches the Zynq UltraScale+ MPSoC PS8 instance name in your wrapper
create_clock -period 10.000 -name clk_pl_0 \
    [get_pins design_1_i/zynq_ultra_ps_e_0/inst/PS8_i/PLCLK[0]]

# 2. No external I/O ports in a pure PS-to-PL AXI-Lite design
#    Add these when you bring PL signals to the carrier card:
#
# set_input_delay  -clock clk_pl_0 -max 2.000 [get_ports {some_input_port}]
# set_input_delay  -clock clk_pl_0 -min 0.500 [get_ports {some_input_port}]
# set_output_delay -clock clk_pl_0 -max 2.000 [get_ports {some_output_port}]
# set_output_delay -clock clk_pl_0 -min 0.500 [get_ports {some_output_port}]

# 3. If a second PL clock (e.g. FCLK_CLK1) is used, cut analysis between them:
# create_clock -period 20.000 -name clk_pl_1 \
#     [get_pins design_1_i/zynq_ultra_ps_e_0/inst/PS8_i/PLCLK[1]]
# set_clock_groups -asynchronous \
#     -group [get_clocks clk_pl_0] \
#     -group [get_clocks clk_pl_1]

# 4. UART TX/RX are handled by PS MIO — no XDC needed for USB-UART on KV260
```
### Relevance to Your Project
In your pure PS→PL AXI-Lite demo with USB-UART handled by PS MIO (not PL I/O), the only required constraint is the `create_clock` on `FCLK_CLK0`. Copy the `get_pins` path above and verify it matches the exact instance name in your generated wrapper. If Vivado reports a "no clocks" critical warning during implementation, the pin path is wrong — use `get_pins -hierarchical -filter {NAME =~ *PLCLK*}` in the Tcl console to find the correct path.

## Kria KV260 / K26 SoM
### Key Findings
- **Default boot mode: QSPI32.** The KV260 ships with firmware pre-loaded in QSPI flash. To boot from SD card or enter JTAG mode for direct Vivado hardware manager programming, the boot-mode SW straps on the KV260 carrier card must be changed before power-on.
- **MIO bank assignments (all 1.8V):**
  - **Bank 500:** SOM-reserved — QSPI (`MIO[5:0]`), eMMC (`MIO[23:13]`), I2C, SPI, PMU signals (`MIO[34:32]`, `MIO[31]`). Do NOT reassign these in custom PetaLinux/Vitis platforms.
  - **Banks 501 & 502:** User-definable, exposed via the two 240-pin SOM connectors to the carrier card.
- **SOM connectors:**
  - `som_240_1` (K26 and K24 common): MIO, PS-GTR, HPIO/HDIO subset, SOM power rails.
  - `som_240_2` (K26 only): Additional HPIO, HDIO, GTH transceivers.
- **PMU overlay API:** KV260 vs KR260 differ in MIO — GEM1 RGMII is enabled only on KR260 via a PMU overlay configuration object, not in the base SOM firmware. Do not assume GEM1 is active on KV260.
- **Power sequencing:** `PS_POR_L` is held asserted (low) by a voltage monitor on the SOM until all power rails stabilize. The PL design should not assume FCLK is stable until after POR completes — the PS boot sequence handles this, but custom bare-metal startup code must not race it.
- **Target part:** Use `xck26-sfvc784-2LV-c` in Vivado (commercial: `xczu5ev-sfvc784-2-e`). The `-2LV` speed grade is the standard production device; `-c` suffix indicates commercial temperature range.

### Code Example
```tcl
# Minimum PS block configuration for KV260 AXI-BRAM bare-metal design
# in Vivado IP Integrator (create_bd.tcl fragment)

# Target part
set_property PART xck26-sfvc784-2LV-c [current_project]

# Instantiate PS block
create_bd_cell -type ip -vlnv xilinx.com:ip:zynq_ultra_ps_e:3.5 zynq_ultra_ps_e_0
apply_bd_automation -rule xilinx.com:bd_rule:zynq_ultra_ps_e \
    -config {apply_board_preset "1"} [get_bd_cells zynq_ultra_ps_e_0]

# Enable AXI GP0 master (PS → PL, used for BRAM0 and BRAM2 access)
set_property CONFIG.PSU__USE__M_AXI_GP0 {1} [get_bd_cells zynq_ultra_ps_e_0]

# Disable unused AXI master ports to reduce area
set_property CONFIG.PSU__USE__M_AXI_GP2 {0} [get_bd_cells zynq_ultra_ps_e_0]

# FCLK_CLK0 at 100 MHz
set_property CONFIG.PSU__FPGA_PL0_ENABLE {1} [get_bd_cells zynq_ultra_ps_e_0]
set_property CONFIG.PSU__CRL_APB__PL0_REF_CTRL__FREQMHZ {100} \
    [get_bd_cells zynq_ultra_ps_e_0]

# UART0 on MIO (PS-side USB-UART, no PL XDC needed)
set_property CONFIG.PSU__UART0__PERIPHERAL__ENABLE {1} [get_bd_cells zynq_ultra_ps_e_0]
set_property CONFIG.PSU__UART0__PERIPHERAL__IO {MIO 18 .. 19}  \
    [get_bd_cells zynq_ultra_ps_e_0]
```
### Relevance to Your Project
Your bare-metal demo uses the PS AXI GP0 master to reach the BRAM controllers. The TCL above is the minimum PS block configuration needed in `create_bd.tcl` for a 100 MHz bare-metal AXI-Lite design on KV260. For iterative development, switch boot mode to JTAG on the carrier card straps — this lets Vivado hardware manager program the PL directly without reflashing QSPI, which is significantly faster during debug cycles.

## AMD/Xilinx Tool Updates
### Key Findings
- **Vivado 2025.1 (~May 2025, UG973):** Contains a full known-issues list with Answer Record links at `docs.amd.com/r/2025.1-English/ug973-vivado-release-notes-install-license`. Check this list before filing a bug report on unexpected behavior.
- **Vitis 2025.1 (released 2025-07-08, UG1742):** Key additions: Clang 16 / initial C++17 support, Vitis HLS GUI improvements, new DSP library functions and AI Engine APIs for Versal. OS support ending after 2025.1: RHEL 9.2/9.3 and Ubuntu 22.04.2 LTS.
- **Known AXI4-Lite issue (UG1483):** A known issue exists in AXI4-Lite interface generation in Model Composer / System Generator. If you generate AXI4-Lite interfaces from Model Composer, check the Known Issues section in UG1483 before trusting the generated RTL.
- **BMG → Embedded Memory Generator (EMG):** Versal targets require the new EMG IP; migration from Block Memory Generator is NOT automatic in IP integrator. For Zynq/Kria targets BMG still works in 2025.1.
- **Selective upgrade limitation:** BMG (and several other IPs) cannot be selectively upgraded in block designs — full BD upgrade is required when moving to a new Vivado version. Upgrade individual IPs by name, never `upgrade_ip [get_ips -all]`.
- **2025.2 and 2026.1 available:** For stability on KV260 bare-metal, 2025.1 is a solid current choice. 2025.2 adds further AI Engine enhancements; 2026.1 is the latest at time of research.

### Code Example
```tcl
# Post-open IP status check — run this after opening project in a new Vivado version
# Identify locked or outdated IPs before attempting synthesis

open_project ./my_kv260/my_kv260.xpr

# Generate IP status report
report_ip_status -file ./output/ip_status.rpt
puts "IP status written to ./output/ip_status.rpt"

# Check for locked or needs-upgrade IPs
set locked_ips [get_ips -filter {UPGRADE_VERSIONS != ""}]
if {[llength $locked_ips] > 0} {
    puts "WARNING: The following IPs need upgrade:"
    foreach ip $locked_ips {
        puts "  $ip -> [get_property UPGRADE_VERSIONS $ip]"
    }
    # Upgrade individually (NEVER use [get_ips -all]):
    foreach ip $locked_ips {
        puts "Upgrading: $ip"
        upgrade_ip $ip
    }
    report_ip_status -file ./output/ip_status_post_upgrade.rpt
} else {
    puts "All IPs are up to date."
}

# Verify specific IPs used in the AXI-BRAM design
foreach cell_name {axi_bram_ctrl_0 blk_mem_gen_0} {
    set cell [get_bd_cells $cell_name]
    if {$cell ne ""} {
        puts "$cell_name version: [get_property IPDEF $cell]"
    }
}
```
### Relevance to Your Project
Running `report_ip_status` immediately after opening your project in a new Vivado version is the first step to prevent cryptic synthesis/implementation errors caused by version-drifted IPs. The BMG selective-upgrade limitation means if you open your project in Vivado 2026.x, you'll need to upgrade the full BD, not just the AXI BRAM Controller.
