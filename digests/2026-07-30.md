## Executive Summary
- **AXI BRAM write-enable glitch (critical):** The AXI BRAM Controller v4.x has a documented simulation bug where `ena` is asserted one clock early, causing an extra spurious write. Switching from AXI Interconnect to SmartConnect eliminates the issue on Zynq UltraScale+ designs.
- **Vivado 2025.1 address decoder limitation:** Vivado 2025 AXI Full peripherals may have address decoding limited to 10 bits (1 KB) when using certain AXI Interconnect configurations — verify your BRAM base addresses (0xA0000000 / 0xA0010000) in the Address Editor.
- **Non-project TCL flow is the gold standard for reproducibility:** Your `create_bd.tcl` approach is the right call. In batch mode, `exec` must be used explicitly for OS commands, and all reports must be manually triggered — there are no implicit intermediate files.
- **Kria KV260 bare-metal QSPI deployment:** XSCT (deprecated in 2026.1+) or XSDB can program QSPI for standalone boot. For development, JTAG download via `xsct` is fastest. For deployment, use `program_flash` from XSCT after building a boot image.
- **Vitis 2025.1 SDT flow:** The System Device Tree (SDT) flow is replacing XSCT-based BSP generation. For bare-metal apps on the KV260, still use the classic platform flow in 2025.1 — SDT is primarily for 2026.x onward.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings
- **AXI-Lite handshake rules:** Both VALID and READY must be held high until the handshake occurs (rising clock edge). VALID must never depend combinatorially on READY — this is a protocol violation that Xilinx IPs exploit but custom slaves must not implement.
- **Write-enable glitch in simulation:** AXI BRAM Controller v4.1 asserts `bram_we_a` one clock cycle before the AXI write completes in simulation. Root cause: the `BRAM_EN` port not being properly tied causes the write enable to bleed an extra cycle. Fix: ensure `bram_en_a` is properly driven and consider switching to SmartConnect instead of AXI Interconnect.
- **AXI-Lite does not support burst transfers:** Each transaction is a single data beat. For your BRAM read/write loop in C, this means N words = N separate AXI transactions — no burst optimization possible on the AXI-Lite side.
- **Vivado 2025 1KB address space limit:** Reports on Digilent forums indicate that Vivado 2025 AXI Full peripherals may decode only 10 bits of the address bus, limiting visible space to 1 KB. Verify your AXI BRAM ports are set to the correct data width and address range in the IP customization dialog.
- **SmartConnect vs AXI Interconnect:** SmartConnect (the newer replacement) handles clock domain crossing and protocol conversion more reliably. It also avoids the write-enable simulation glitch seen with the classic AXI Interconnect.

### Code Example
```vhdl
-- AXI-Lite slave register write process (correct VALID/READY usage)
-- READY may be registered; VALID must NOT depend on READY
process(s_axi_aclk)
begin
  if rising_edge(s_axi_aclk) then
    if s_axi_aresetn = '0' then
      axi_awready <= '0';
      axi_wready  <= '0';
    else
      -- Assert AWREADY for one cycle when AWVALID arrives
      if axi_awready = '0' and s_axi_awvalid = '1' and s_axi_wvalid = '1' then
        axi_awready <= '1';
      else
        axi_awready <= '0';
      end if;
      -- Assert WREADY simultaneously
      if axi_wready = '0' and s_axi_wvalid = '1' and s_axi_awvalid = '1' then
        axi_wready <= '1';
      else
        axi_wready <= '0';
      end if;
    end if;
  end if;
end process;
```

### Relevance to Your Project
Your BRAM0 at `0xA0000000` and BRAM2 at `0xA0010000` are accessed via AXI-Lite through the Block Memory Generator. The write-enable glitch is a real risk in simulation — if your C test reads back unexpected values in Vivado simulation (not on hardware), suspect the `bram_en_a` connection on the AXI BRAM Controller. Also double-check in the Address Editor that both BRAMs show their full intended range (e.g., 8 KB or 64 KB) and not a capped 1 KB range.

## Vivado Block Design / IP Integrator

### Key Findings
- **Connection Automation is order-sensitive:** Always run "Run Connection Automation" in one pass after adding all IP blocks. Running it incrementally after each IP add can create redundant AXI Interconnects or leave unresolved interfaces.
- **Address Editor must be visited explicitly:** After Connection Automation, open the Address Editor tab and verify the offset and range of each BRAM segment. Vivado may auto-assign overlapping or incorrect ranges.
- **Regenerate Output Products before exporting:** Always run "Generate Output Products" (right-click the BD) and then "Create HDL Wrapper" before exporting to Vitis. Stale wrappers cause mysterious port mismatch errors.
- **Upgrading IP between tool versions:** When opening a 2024.x BD in 2025.x, Vivado will prompt to upgrade IP. Always inspect the IP changelog (AR 000037919) before upgrading — some IPs (GT Wizard subsystem type change) alter behavior, not just version numbers.
- **Validate Design (F6) reveals critical errors:** The built-in design validator catches unconnected AXI clocks, wrong address segments, and missing resets before synthesis. Run it after every significant change.

### Code Example
```tcl
# Vivado TCL: assign address segments for dual BRAM design
# Run after connection automation, before generate output products

# Assign BRAM0 at 0xA000_0000, 64KB range
assign_bd_address [get_bd_addr_segs {axi_bram_ctrl_0/S_AXI/Mem0}]
set_property offset 0xA0000000 [get_bd_addr_segs \
  {processing_system7_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property range 64K [get_bd_addr_segs \
  {processing_system7_0/Data/SEG_axi_bram_ctrl_0_Mem0}]

# Assign BRAM2 at 0xA001_0000, 64KB range
assign_bd_address [get_bd_addr_segs {axi_bram_ctrl_2/S_AXI/Mem0}]
set_property offset 0xA0010000 [get_bd_addr_segs \
  {processing_system7_0/Data/SEG_axi_bram_ctrl_2_Mem0}]
set_property range 64K [get_bd_addr_segs \
  {processing_system7_0/Data/SEG_axi_bram_ctrl_2_Mem0}]

# Validate the design
validate_bd_design
```

### Relevance to Your Project
Your `create_bd.tcl` script should include explicit `set_property offset` and `set_property range` calls for both BRAM controllers to guarantee the 0xA0000000 / 0xA0010000 address map is preserved across tool upgrades. Relying on auto-assignment risks address changes when opening the project in a new Vivado version.

## Vivado TCL Scripting

### Key Findings
- **Non-project mode advantages:** No `.xpr` file, no in-memory project state — everything is explicit. Ideal for CI/CD and version-controlled flows. Your `create_bd.tcl` script is already following best practice.
- **Batch mode `exec` requirement:** In `vivado -mode batch`, unknown commands are NOT forwarded to the OS shell. Use `exec` explicitly: `exec make` or `exec cp file1 file2`. This is a common source of silent failures.
- **Checkpoint-driven flows:** In non-project mode, save design checkpoints (`write_checkpoint`) after each major stage (synth, impl, route). This allows resuming from any stage without re-running synthesis: `open_checkpoint post_synth.dcp`.
- **`source` for modularity:** Break large TCL scripts into `source constraints.tcl`, `source create_bd.tcl`, `source run_impl.tcl`. The top-level script calls each in order — enables testing individual stages.
- **`get_bd_cells -hierarchical`:** When scripting IP property changes in a block design, use `-hierarchical` to match cells regardless of hierarchy depth. Avoids brittle hard-coded paths.
- **IP Integrator in non-project mode (2025.1):** `create_bd_design`, `add_bd_ip`, `connect_bd_intf_net` are all available without an `.xpr` project. Call `open_bd_design` on the `.bd` file to reopen it later.

### Code Example
```tcl
# Non-project mode: full synthesis + implementation in one script
# Usage: vivado -mode batch -source build.tcl

# Read sources
read_vhdl [glob ./vhdl/*.vhd]
read_ip   ./ip/block_design/block_design.xci

# Read constraints
read_xdc  ./constraints/kv260_top.xdc

# Synthesize (out-of-context by default for IP, top-level normal)
synth_design -top kv260_top -part xck26-sfvc784-2LV-c

# Save checkpoint and report
write_checkpoint -force ./checkpoints/post_synth.dcp
report_timing_summary -file ./reports/post_synth_timing.rpt
report_utilization   -file ./reports/post_synth_util.rpt

# Implement
opt_design
place_design
route_design

# Final reports and bitstream
write_checkpoint -force ./checkpoints/post_route.dcp
report_timing_summary -file ./reports/post_route_timing.rpt -warn_on_violation
write_bitstream  -force ./output/kv260_top.bit

puts "Build complete."
```

### Relevance to Your Project
The `create_bd.tcl` in your repo already demonstrates this pattern. Adding explicit `write_checkpoint` calls after synthesis would let you re-run only implementation when you tweak constraints — important when iteration cycles are long on the K26's UltraScale+ fabric.

## Vitis Bare-Metal / Standalone

### Key Findings
- **BSP must be regenerated after every Vivado hardware export:** Changing the block design (adding an interrupt, resizing BRAM) requires re-exporting the XSA, updating the platform in Vitis, and rebuilding the BSP. Stale BSPs cause linker errors or wrong peripheral base addresses in `xparameters.h`.
- **`xil_printf` is UART0 by default:** On Zynq UltraScale+ (K26), `xil_printf` targets `psu_uart0` (MIO 18-19). If your KV260 USB-UART is on UART1 (MIO 36-37, the typical KV260 configuration), you must set `stdin`/`stdout` to `psu_uart1` in the BSP settings or set the STDIN_BASEADDRESS in `platform_config.h`.
- **Cortex-A53 cache coherency:** When writing to PL memory-mapped peripherals (AXI-BRAM), ensure data cache is either disabled or explicitly flushed/invalidated before reads. `Xil_DCacheDisable()` is the safest approach for bare-metal demos; for production use `Xil_DCacheFlushRange()`.
- **`Xil_Out32` / `Xil_In32`:** These are the correct bare-metal register access functions for memory-mapped I/O. They compile to direct load/store instructions — no AXI protocol complexity visible at the C layer.
- **Standalone BSP v7.x (2025.1):** The standalone library in 2025.1 adds SDT (System Device Tree) support for platform description, but the classic BSP flow still works. SDT-based bare-metal will become mandatory in future releases.

### Code Example
```c
/* Bare-metal AXI-BRAM read/write test for KV260 */
#include "xil_printf.h"
#include "xil_io.h"
#include "xil_cache.h"

#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL
#define TEST_WORDS  16

int main(void) {
    /* Disable D-cache to avoid stale reads from PL memory-mapped space */
    Xil_DCacheDisable();

    xil_printf("KV260 AXI-BRAM Test\r\n");

    /* Write phase */
    for (int i = 0; i < TEST_WORDS; i++) {
        Xil_Out32(BRAM0_BASE + (i * 4), 0xDEAD0000 | i);
        Xil_Out32(BRAM2_BASE + (i * 4), 0xBEEF0000 | i);
    }

    /* Read-back and verify phase */
    int pass = 1;
    for (int i = 0; i < TEST_WORDS; i++) {
        u32 v0 = Xil_In32(BRAM0_BASE + (i * 4));
        u32 v2 = Xil_In32(BRAM2_BASE + (i * 4));
        if (v0 != (0xDEAD0000 | i) || v2 != (0xBEEF0000 | i)) {
            xil_printf("FAIL @ word %d: BRAM0=0x%08X BRAM2=0x%08X\r\n", i, v0, v2);
            pass = 0;
        }
    }

    xil_printf(pass ? "PASS\r\n" : "OVERALL FAIL\r\n");
    return 0;
}
```

### Relevance to Your Project
This is essentially what your `main.c` implements. The critical addition here is `Xil_DCacheDisable()` — if you are seeing intermittent FAIL results on hardware that pass in simulation, a stale D-cache line is the most likely culprit. Also verify your `xil_printf` UART selection matches the KV260 physical USB-UART connection.

## XDC Timing Constraints

### Key Findings
- **`set_input_delay` / `set_output_delay` semantics:** These commands model the system-level delay on I/O paths relative to a clock edge at the device boundary. Positive `set_input_delay` means the data arrives late (after the reference clock edge); the tool must close this path. For AXI signals internal to the PS-PL interface, these constraints are typically NOT needed — the PS handles its own timing.
- **PS-PL AXI clock is already constrained:** The `pl_clk0` generated by the Zynq PS is automatically constrained by Vivado. Do not add a manual `create_clock` for it — this creates a duplicate clock definition and invalid timing paths.
- **`set_clock_groups -asynchronous`:** Use this for clocks that are genuinely asynchronous (e.g., an external reference vs. `pl_clk0`). Grouping all clocks together in one `set_clock_groups` command can create phantom false paths.
- **False path for reset synchronizers:** Asynchronous resets crossing clock domains should be false-pathed: `set_false_path -from [get_pins */PRE] -to [get_pins */D]` to prevent the tool from trying to time an asynchronous path.
- **Vivado 2025.1 OOC constraints:** Out-of-Context IP synthesis now includes `HD.CLK_SRC` properties. Enable them with: `set_param ips.includeClockLocationConstraints true` before synthesis to improve timing closure for IPs at specific floorplan locations.

### Code Example
```tcl
# kv260_top.xdc - Minimal constraints for KV260 AXI-BRAM design
# pl_clk0 is auto-constrained by the Zynq PS block — do NOT create_clock here

# Constrain external GPIO/PMOD outputs (if any) to 10ns setup, 2ns hold
# relative to pl_clk0 (Vivado infers the clock name from the PS block)
# set_output_delay -clock [get_clocks -of_objects [get_ports pl_clk0]] \
#                  -max  2.0 [get_ports {pmod_io[*]}]
# set_output_delay -clock [get_clocks -of_objects [get_ports pl_clk0]] \
#                  -min -1.0 [get_ports {pmod_io[*]}]

# False-path the async reset path (reset is synchronised in PL fabric)
set_false_path -from [get_ports sys_resetn]

# Async clock groups: if you add a secondary PL clock domain later
# set_clock_groups -asynchronous \
#   -group [get_clocks clk_pl_0] \
#   -group [get_clocks clk_out1_clk_wiz_0]

# Enable OOC IP clock location constraints (2025.1+)
set_param ips.includeClockLocationConstraints true
```

### Relevance to Your Project
For the current AXI-BRAM demo (single clock domain, no external I/O besides UART), the XDC file is minimal. The most important constraint is the false path on `sys_resetn` if it comes in asynchronously. As you add PMOD outputs or a secondary clock (e.g., for a video pipeline), use `set_clock_groups -asynchronous` correctly — grouping only the clocks that are truly unrelated.

## Kria KV260 / K26 SoM

### Key Findings
- **Boot mode selection:** The K26 SoM ships with QSPI32 boot mode pre-configured (MODE[3:0] pins on the carrier card). For bare-metal development, switch to JTAG mode using XSCT/XSDB: `targets -set -filter {jtag_device_name =~ "xck26*"}; rst -system`.
- **Boot mode switching via TCL (XSCT):**
  ```
  connect; targets 1; stop
  mwr 0xff5e0200 0x0100  ;# Switch to JTAG boot mode
  ```
- **UART mapping on KV260:** The KV260 carrier card connects the USB-UART bridge (CP2108 or similar) to **MIO 36-37 (UART1)**. `xil_printf` in the default BSP targets UART0 (MIO 18-19), which is NOT connected to the KV260 USB-UART — this is the #1 cause of "no output" reports from new KV260 users.
- **Power domains:** The K26 SoM has three primary power rails relevant to PL design: VCCO_HP (high-performance I/O banks, 1.2V/1.8V), VCCO_HR (high-range I/O banks, 1.2V–3.3V), and VCCINT (core, 0.85V). The KV260 carrier sets PMOD VCCO to 3.3V (HR banks) and the MIPI/CSI connectors to 1.8V (HP banks).
- **PL bitstream loading:** For bare-metal without Linux, the bitstream must be loaded before the application runs. In JTAG flow: `fpga -f kv260_top.bit` in XSCT, then download the ELF.
- **eMMC vs QSPI:** The K26 has both 256 MB QSPI flash and 4/8 GB eMMC. For bare-metal BOOT.BIN, QSPI is simpler. eMMC is typically used for PetaLinux images.

### Code Example
```tcl
# XSCT script: load bitstream + bare-metal ELF via JTAG on KV260
# Run from: xsct kv260_jtag_boot.tcl

connect

# Identify Kria target
set targets [targets -filter {jtag_device_name =~ "xck26*"}]
if {[llength $targets] == 0} {
    puts "ERROR: KV260 not found on JTAG. Check cable and power."
    exit 1
}

# Reset and hold
targets -set -filter {jtag_device_name =~ "xck26*"}
rst -system

# Load PL bitstream
fpga -f ./output/kv260_top.bit
after 1000

# Select APU Cortex-A53 core 0
targets -set -filter {name =~ "Cortex-A53 #0"}

# Initialize processor (sets up PS clock, DDR, MIO)
source ./scripts/psu_init.tcl
psu_init

# Download and run ELF
dow ./output/kv260_axi_bram.elf
con

puts "Application running. Check USB-UART (UART1 / ttyUSB1)."
```

### Relevance to Your Project
This XSCT script matches exactly what your project needs for iterative development. The critical line is targeting UART1 for output — if you haven't already, set the BSP `stdin`/`stdout` to `psu_uart1` in Vitis platform settings. The `psu_init.tcl` file is exported alongside the XSA from Vivado and sets up DDR and MIO routing before your ELF runs.

## AMD/Xilinx Tool Updates (Vivado/Vitis 2025.x)

### Key Findings
- **Vivado 2025.1 codename "Styx":** Confirmed release with Zynq UltraScale+ support. IP Release Notes (AR 000037919) document all IP version changes — the GT Wizard Subsystem is now the default type in the GT Wizard IP dialog (behavioral change, not just version bump).
- **Vitis 2025.1 SDT transition:** The System Device Tree (SDT) is the new hardware description format replacing HSI-based `xparameters.h` generation. In 2025.1 both flows coexist; SDT is opt-in. From 2026.x, SDT becomes mandatory. Start planning the migration now if your project spans multiple tool versions.
- **XSCT deprecation in 2026.1:** The XSCT scripting tool is deprecated starting in 2026.1; only the SDT flow via `vitis` CLI is supported going forward. For 2025.1 projects, XSCT still works fine.
- **Vivado 2025.2 / 2026.1 already available:** AMD released 2025.2 and 2026.1 in quick succession. Key 2026.1 addition: Spartan UltraScale+ support. For Kria KV260 (K26 / xck26), 2025.1 and 2025.2 are both stable.
- **New IP in 2025.1:** The kria-vitis-platforms targeting 2026.1 suggests active platform development. Check for updated Kria-specific platform files for 2025.1 at the Xilinx GitHub before starting a new project.
- **Known issues to watch:** AXI BRAM Controller address decoding (1 KB limit in some configurations) and SmartConnect vs AXI Interconnect behavior differences are active community pain points in 2025.x.
