# FPGA Research Digest - 2026-07-06

## Executive Summary

- **Vivado 2025.x AXI address-width regression**: Custom AXI-full peripherals built in Vivado 2025 are silently limited to a 1 KB usable address space because bits above bit 10 are zeroed by the generated decoder. Workaround: manually set the memory array bounds in the generated RTL and ensure synchronous reads. Your BRAM0/BRAM2 targets at 0xA0000000 / 0xA0010000 are fine with the Xilinx IP (axi_bram_ctrl), but any custom AXI slave you add will hit this bug.
- **New RTL AXI Switch IP in Vivado 2025.1** supports 16 SI × 16 MI with per-port protocol, width, and clock-domain conversion plus a new ultra-low-area mode — a direct replacement for the aging AXI Interconnect and a leaner alternative to SmartConnect when you do not need traffic shaping.
- **Vivado-generated AXI-Lite slave template has well-known handshake bugs**: the `axi_arready` signal is held high an extra cycle, creating a phantom second read transaction. Always verify your custom AXI-Lite slave with a formal tool (SymbiYosys) or ILA before trusting PASS/FAIL output from the ARM side.
- **Kria bare-metal JTAG boot requires four files**: `fsbl.elf`, `pmufw.elf`, `<app>.elf`, and `<wrapper>.bit`. The QSPI preset boot mode on a factory KV260 must be overridden via `xsdb` before JTAG download will work.
- **Linker script pitfall in Vitis for Zynq**: the auto-generated `lscript.ld` often assigns all sections to the BAR0 region instead of DDR, causing silent crashes when booting from SD or JTAG. Always open the script and verify `.text`/`.data`/`.bss` map to `psu_ddr_0`.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- **VALID/READY handshake rules**: Once `VALID` is asserted by the initiator, it must stay asserted until the corresponding `READY` is received. `READY` may be deasserted freely. Violating the first rule is the single most common cause of intermittent BRAM read corruption in PS-to-PL AXI-Lite designs.
- **Response codes**: `BRESP`/`RRESP` follow a priority order — `DECERR (0b11)` > `SLVERR (0b10)` > `OKAY (0b00)`. An AXI Interconnect returns `DECERR` (`BRESP = 3`) when the target slave is absent from the address map. If your BRAM reads all return 0xDEADBEEF-style garbage, check for DECERR first.
- **Vivado-generated AXI-Lite slave bug** (from ZipCPU): the template holds `axi_arready` high for an extra clock after the address is latched, allowing a second address to be captured before the first read completes. This is widely replicated across student/hobby designs.
- **AXI BRAM controller single-port mode**: `axi_bram_ctrl` in single-port (AXI-Lite) mode does not support simultaneous read and write to the same address cycle. The controller serialises them internally; bandwidth is roughly half the raw BRAM throughput.
- **AXI-Stream TREADY back-pressure**: For any future streaming addition (video pipeline, DMA), ensure `TREADY` is properly gated — asserting `TVALID` without checking `TREADY` causes dropped data that manifests as off-by-one frame errors.

### Code Example

```vhdl
-- Correct AXI-Lite read-address channel: arready pulses for exactly ONE cycle
-- when arvalid is seen; prevents double-latching the address.
process(s_axi_aclk)
begin
  if rising_edge(s_axi_aclk) then
    if s_axi_aresetn = '0' then
      axi_arready <= '0';
      axi_araddr  <= (others => '0');
    else
      if axi_arready = '0' and s_axi_arvalid = '1' then
        axi_arready <= '1';
        axi_araddr  <= s_axi_araddr;
      else
        axi_arready <= '0';   -- pulse only; Vivado template OMITS this line
      end if;
    end if;
  end if;
end process;
```

### Relevance to Your Project

Your `kv260_top.vhd` wraps two `axi_bram_ctrl` instances. The Xilinx IP handles the handshake correctly internally, but if you ever add a custom register interface alongside the BRAMs, apply the one-cycle `arready` fix above. Also confirm in your `main.c` that you poll the BRAM read-back address only after the full AXI round-trip by reading a dummy word first to flush any pipeline latency.

## Vivado Block Design / IP Integrator

### Key Findings

- **Connection Automation** instantiates an `axi_smartconnect`, a `proc_sys_reset`, and wires clocks/resets automatically when you click *Run Connection Automation* on an `axi_bram_ctrl` slave port. This is the fastest way to regenerate a clean block design from scratch.
- **Address Editor auto-assign**: click the *Auto Assign Address* button (bottom-left of the Address Editor tab) after adding new IPs. Manual offsets (e.g., 0xA0000000, 0xA0010000) override auto-assignment — enter them in the *Offset Address* column, then set *Range* to match the BRAM depth.
- **Validate Design is mandatory before export**: IP Integrator uses validation to propagate parameters (AXI data width, BRAM operating mode, burst type) across connected IPs. Running *Validate Design* (`validate_bd_design` in Tcl) before exporting the wrapper catches width mismatches silently ignored by synthesis.
- **New in 2025.1**: Two dedicated IP Integrator views — *Clocking and Reset* and *Interrupt and AXI-4 Lite* — provide a filtered view of the design, making it easier to audit clock domains and interrupt wiring without scrolling through a large block diagram.
- **SmartConnect vs AXI Switch (2025.1)**: Use `axi_smartconnect` when you need QoS/traffic shaping; use the new RTL `axi_switch` when you want minimal area and predictable timing on a simple crossbar.

### Code Example

```tcl
# Regenerate address assignment after adding a second BRAM controller
open_bd_design [get_files *.bd]
validate_bd_design
assign_bd_address
# Manually pin BRAM0 at 0xA000_0000, 64 KB range
set_property offset 0xA0000000 [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property range  64K         [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
# Pin BRAM2 at 0xA001_0000, 64 KB range
set_property offset 0xA0010000 [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_1_Mem0}]
set_property range  64K         [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_1_Mem0}]
save_bd_design
```

### Relevance to Your Project

Your `create_bd.tcl` script builds the block design non-interactively. The `assign_bd_address` + `set_property offset/range` pattern above is the correct way to pin BRAM0 at `0xA0000000` and BRAM2 at `0xA0010000` without relying on GUI auto-assignment that may shift addresses on IP upgrades.

## Vivado TCL Scripting

### Key Findings

- **Non-project mode vs project mode**: Non-project mode (`read_vhdl`, `synth_design`, `opt_design`, `place_design`, `route_design`) gives finer control and cleaner CI integration but requires you to manage checkpoints manually. Project mode (`create_project`, `launch_runs`) is simpler but less portable.
- **Exporting block design to Tcl**: *File → Export → Export Block Design* generates a self-contained `.tcl` that recreates the entire IP configuration. Edit out the `create_project` preamble and you have a reusable `create_bd.tcl` that works in any project.
- **`validate_bd_design` before `make_wrapper`**: Always call `validate_bd_design -quiet` before `make_wrapper -files [get_files *.bd] -top`. Skipping it causes the generated wrapper HDL to miss port declarations for late-bound IP parameters.
- **Batch synthesis tip**: Pass `-jobs [llength [get_property CONFIG.JOBS [current_run]]]` to `launch_runs` to utilise all available cores without hardcoding a thread count.
- **`write_checkpoint` after each phase**: In non-project mode, write a DCP after synthesis, optimisation, and placement. This allows resumption without re-running expensive earlier stages.

### Code Example

```tcl
# Minimal non-project batch flow for KV260 bare-metal bitfile
set PART "xck26-sfvc784-2LV-c"

read_vhdl  -library work [glob ../vhdl/*.vhd]
read_bd    [glob ../bd/*.bd]
generate_target all [get_files *.bd]
make_wrapper -files [get_files *.bd] -top
read_vhdl  [glob ./*/hdl/wrapper/*.vhd]
read_xdc   [glob ../constraints/*.xdc]

synth_design  -top kv260_top -part $PART -flatten_hierarchy rebuilt
write_checkpoint post_synth.dcp -force

opt_design
place_design
phys_opt_design
route_design
write_checkpoint post_route.dcp -force
write_bitstream  -force output.bit
```

### Relevance to Your Project

Your existing `create_bd.tcl` handles block-design creation. Wrapping it with the non-project synthesis flow above gives you a single command (`vivado -mode batch -source run.tcl`) that rebuilds the entire bitfile from clean sources — ideal for CI and reproducible builds.

## Vitis Bare-Metal / Standalone

### Key Findings

- **BSP `stdout` setting**: In `system.mss`, set `stdin`/`stdout` to the UART connected to your USB-UART bridge (`psu_uart_1` on KV260 by default). Baud rate for `xil_printf` is 115200. If the UART peripheral is wrong, `xil_printf` silently discards output.
- **`xil_printf` vs `printf`**: `xil_printf` is a lightweight implementation with no floating-point support. For PASS/FAIL pattern testing use `xil_printf("%08X\r\n", val)` — it is safe, has no heap dependency, and is ~10× smaller than `printf`.
- **Linker script (`lscript.ld`) DDR pitfall**: Vitis auto-generates `lscript.ld` with all sections mapped to the first available memory region, which is sometimes `psu_ocm_ram_0` (on-chip memory) instead of `psu_ddr_0`. OCM is only 256 KB; large applications silently corrupt adjacent memory. Always verify `.text` maps to `psu_ddr_0_MEM_0` (`0x00000000`, 2 GB).
- **Interrupt controller not required for polling**: Your bare-metal write-read-verify loop does not need `XScuGic` or any interrupt controller. Polling `Xil_In32`/`Xil_Out32` is sufficient and avoids BSP complexity. Add the GIC only when you need DMA done-interrupts or timer callbacks.
- **Tool version pairing**: Always use matching Vivado and Vitis versions. Mixing Vivado 2025.1 hardware export with Vitis 2024.2 BSP generation causes `xparameters.h` mismatches that manifest as incorrect base-address macros.

### Code Example

```c
#include "xil_io.h"
#include "xil_printf.h"

#define BRAM0_BASE 0xA0000000UL
#define BRAM2_BASE 0xA0010000UL

static int bram_verify(u32 base, const char *name) {
    const u32 PATTERN = 0xDEADBEEFUL;
    Xil_Out32(base, PATTERN);
    /* Memory barrier: ensure AXI write completes before read */
    dsb();
    u32 readback = Xil_In32(base);
    if (readback == PATTERN) {
        xil_printf("%s PASS (0x%08X)\r\n", name, readback);
        return 0;
    }
    xil_printf("%s FAIL: wrote 0x%08X read 0x%08X\r\n", name, PATTERN, readback);
    return -1;
}

int main(void) {
    xil_printf("KV260 AXI-BRAM demo\r\n");
    int rc = 0;
    rc |= bram_verify(BRAM0_BASE, "BRAM0");
    rc |= bram_verify(BRAM2_BASE, "BRAM2");
    xil_printf(rc == 0 ? "ALL PASS\r\n" : "SOME FAILURES\r\n");
    return rc;
}
```

### Relevance to Your Project

The `dsb()` (data synchronisation barrier) between `Xil_Out32` and `Xil_In32` is critical on Cortex-A53. Without it the compiler or CPU may reorder the stores and load, causing a read of stale cache data rather than the BRAM value — producing a false PASS when the AXI transaction actually failed.

## XDC Timing Constraints

### Key Findings

- **Two-layer constraint files for Kria**: AMD separates SoM constraints (XTP685 — K26 XDC) from carrier-card constraints (XTP686 — KV260 XDC). Your project should `read_xdc` both: the SoM file defines the MPSoC package-level timing; the carrier-card file maps SOM240 connector pins to physical board signals.
- **Trace-delay file XTP688**: The K26 SoM trace delay values file provides per-pin propagation delays from the MPSoC die to the SOM240 connector. Use these with `set_input_delay -max/-min` when constraining signals that cross from the carrier card into the SoM.
- **`set_false_path` for PS-PL AXI clock relationship**: The AXI interconnect between PS and PL is internally synchronised. If your PL AXI clock (`pl_clk0`) is derived from `zynq_ultra_ps_e_0`, declare it with `create_generated_clock` referencing the PS source. Without this, Vivado may report phantom setup violations on the AXI paths.
- **Clock group for independent PL clocks**: If you add a secondary PL clock (e.g., 200 MHz for DDR calibration), declare it asynchronous to `pl_clk0` with `set_clock_groups -asynchronous`.
- **`report_clock_interaction`** after routing: run this to catch any unintentionally unconstrained clock crossings before generating the bitstream.

### Code Example

```tcl
# constraints/kv260_timing.xdc  — minimal timing constraints for AXI-BRAM demo

# Primary PL clock from PS (100 MHz, adjust to your block design setting)
create_clock -period 10.000 -name pl_clk0 [get_ports pl_clk0]

# PS-PL AXI clock is the same as pl_clk0 — generated from the same source
# No crossing constraints needed when a single clock drives both BRAM controllers.

# If you expose any PL I/O (e.g., LEDs on the KV260 carrier card):
# Reference XTP686 for the correct pin names, e.g. som240_1_a17 -> LED0
# set_property PACKAGE_PIN <pin> [get_ports led[0]]
# set_property IOSTANDARD LVCMOS33 [get_ports led[0]]

# Prevent bitstream from being generated when timing is not met
set_property BITSTREAM.GENERAL.COMPRESS TRUE [current_design]

# Report unconstrained paths to catch missing constraints early
# (run interactively: report_clock_interaction -delay_type min_max)
```

### Relevance to Your Project

Your bare-metal AXI-BRAM demo is a single-clock design (all PL logic driven from `pl_clk0`). The constraints above are minimal and sufficient. When you later add an AXI-Stream pipeline with a second clock domain, revisit the `set_clock_groups` directive to prevent Vivado from optimising across the domain boundary.

## Kria KV260 / K26 SoM

### Key Findings

- **Factory boot mode is QSPI32**: The KV260 ships with boot FW in QSPI and a QSPI32 boot mode fuse. To boot a bare-metal application via JTAG you must override the boot mode at runtime using XSDB — you do **not** need to reflash QSPI fuses.
- **Four-file JTAG boot sequence**: FSBL (`fsbl.elf`), PMU firmware (`pmufw.elf`), application ELF, and bitfile. These are loaded in order via an XSDB script. FSBL initialises DDR and the PS clocks; omitting it causes the application to fault immediately.
- **PS-first boot in Vivado 2025.1**: A new 2025.1 feature allows the PS to boot and run Linux/bare-metal code before the PL bitstream is loaded. This is useful for fast OS bring-up but requires the bare-metal application to poll a handshake register before accessing PL peripherals.
- **MIO/EMIO assignments**: The KV260 routes UART1 (`MIO48/MIO49`) to the USB-UART bridge. Ensure your Zynq PS IP configuration in the block design has UART1 enabled on MIO, not EMIO. The PS also drives `pl_clk0` from the PS PLL — confirm the frequency matches your XDC constraint.
- **Power domains**: The K26 SoM has separate power domains for PS, PL, and the SOM240 I/O banks. PL I/O bank voltage is set by the carrier card; the KV260 carrier uses 3.3 V for the fan-out PMOD/GPIO headers.

### Code Example

```tcl
# xsdb_boot.tcl — JTAG bare-metal boot script for KV260
# Run with: xsdb xsdb_boot.tcl

connect

# Override factory QSPI boot mode to JTAG
targets -set -filter {name =~ "PSU"}
mwr  0xff5e0200 0x0100   ;# BOOT_MODE_USER: force JTAG
mwr  0xff5e0230 0x1      ;# BOOT_MODE_POR: latch override

# Load PMU firmware
targets -set -filter {name =~ "MicroBlaze PMU"}
dow  pmufw.elf
con

# Load and run FSBL on APU
targets -set -filter {name =~ "Cortex-A53 #0"}
rst -processor
dow  fsbl.elf
con
after 5000    ;# wait for FSBL to complete DDR init

# Program PL bitstream
targets -set -filter {name =~ "PSU"}
fpga -f kv260_wrapper.bit

# Load and run bare-metal application
targets -set -filter {name =~ "Cortex-A53 #0"}
rst -processor
dow  kv260_bram_demo.elf
con
```

### Relevance to Your Project

This script is the exact launch sequence for your `kv260-axi-bram-demo`. The `fpga -f` step programs the bitfile that instantiates your two BRAM controllers before the application ELF starts, ensuring `BRAM0` and `BRAM2` are live at `0xA0000000` and `0xA0010000` when `main()` executes. Without the `after 5000` DDR-init wait, the FSBL may not have finished setting up the PS before the application starts.

## AMD/Xilinx Tool Updates (Vivado/Vitis 2025.x)

### Key Findings

- **Vivado 2025.1 headline features**: PS-first boot support; new Pblock planner UI; improved QoR from enhanced Directive/Subdirective support; new fully-customisable RTL AXI Switch IP; calibrated skew compensation for Versal SSIT; NoC QoS time-slicing.
- **Vitis 2025.2 is current** (released since 2025.1): Key additions include enhanced GEMV/FFT for AI Engine with 2D parallel AIE+PL and vectorised bitonic SIMD sorting. For embedded bare-metal work the relevant change is updated `embeddedsw` standalone drivers in the BSP repository.
- **Vivado 2025.x Known Issues (AR 000037546)**: A live known-issues article is maintained at AMD Adaptive Support. Check it before beginning a new tapeout. Common 2025.x issues include: IP upgrade dialogs failing silently on locked netlists; AXI-full custom peripheral address-width truncation (see Executive Summary); and occasional IPI connection-automation crashes on large block designs.
- **AXI Switch IP (new in 2025.1)**: `axi_switch` supports up to 16 SI × 16 MI, per-port AXI3/AXI4/AXI4-Lite, automatic protocol and width conversion, three area/performance modes (area-optimized, balanced, performance), and a new `ultra-low-area` mode via `STRATEGY` parameter. It replaces `axi_interconnect` for new designs.
- **Vivado 2025.2 IP Change Log (AR 000039903)**: AMD maintains a per-IP change log with every release. Worth scanning before upgrading IP in an existing project to avoid breaking changes in `axi_bram_ctrl`, `zynq_ultra_ps_e`, or `axi_smartconnect`.

### Code Example

```tcl
# Add new AXI Switch IP (Vivado 2025.1+) to a block design
# instead of the legacy AXI Interconnect

create_bd_cell -type ip -vlnv xilinx.com:ip:axi_switch:1.0 axi_switch_0

# Configure: 1 master (PS HP0) → 2 slaves (BRAM0, BRAM2), ultra-low-area mode
set_property -dict {
  CONFIG.NUM_SI 1
  CONFIG.NUM_MI 2
  CONFIG.STRATEGY ultra_low_area
  CONFIG.ADDR_WIDTH 32
  CONFIG.DATA_WIDTH 32
} [get_bd_cells axi_switch_0]

# Connect PS HPC0 master to the switch input
connect_bd_intf_net [get_bd_intf_pins zynq_ultra_ps_e_0/M_AXI_HPM0_FPD] \
                    [get_bd_intf_pins axi_switch_0/S00_AXI]

# Connect switch outputs to the two BRAM controllers
connect_bd_intf_net [get_bd_intf_pins axi_switch_0/M00_AXI] \
                    [get_bd_intf_pins axi_bram_ctrl_0/S_AXI]
connect_bd_intf_net [get_bd_intf_pins axi_switch_0/M01_AXI] \
                    [get_bd_intf_pins axi_bram_ctrl_1/S_AXI]
```

### Relevance to Your Project

Your current design likely uses `axi_smartconnect` (auto-inserted by Connection Automation). If you rebuild the block design in Vivado 2025.1+, consider switching to `axi_switch` with `ultra_low_area` — for a two-slave AXI-Lite-only design like yours it will use measurably fewer LUTs than SmartConnect without any functional trade-off.
