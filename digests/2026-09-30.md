# FPGA Research Digest - 2026-09-30

## Executive Summary

- **AXI-Lite VALID must never depend on READY** — the most commonly violated AXI handshake rule in custom slave IP; once VALID is asserted it must remain stable until the handshake completes. Verify this in your BRAM write/read path.
- **Kria KV260 uses UART1 (not UART0) for the console** — a common gotcha when setting up the USB-UART path in bare-metal Vitis projects; the BSP must select `psu_uart_1` as stdout/stdin.
- **Prefer AXI SmartConnect over AXI Interconnect** for new Zynq UltraScale+ designs; SmartConnect gives 20–30% better PPA and is the only supported interconnect for Versal and beyond.
- **Vivado 2025.1 introduced a new AXI Switch IP** (fully customizable RTL-based) and **2025.2 adds a new ultra-low-area mode** for AXI SmartConnect via a `STRATEGY` parameter — worth evaluating for resource-constrained KV260 builds.
- **Non-project TCL mode gives reproducible builds** — Vivado reads sources, synthesizes, implements and writes bitstreams entirely from script with no `.xpr` state; critical for CI/CD pipelines and ensures clean regeneration.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- The AXI spec requires that once a `VALID` signal is asserted it **must remain stable** until the corresponding `READY` is seen. Asserting `VALID` conditionally on `READY` of the same channel is a protocol violation that causes deadlocks. This is the #1 bug in hand-written AXI slave IP.
- Backpressure in AXI-Lite implementations has caused latent bugs even in Xilinx example designs — treat Xilinx example AXI master/slave templates as starting points, not verified reference code.
- For BRAM timing safety, register (pipeline) external signals with a flip-flop stage before passing them into block RAM; if timing closure fails, an extra register stage on the BRAM output resolves most setup violations.
- AXI-Lite only supports one outstanding transaction per channel (no burst, no out-of-order) — simpler to implement but means every read or write is a separate address + data phase.
- The **AXI SmartConnect** IP (not AXI Interconnect) is recommended for all UltraScale+ designs. Vivado's Connection Automation will instantiate SmartConnect by default.

### Code Example

```vhdl
-- AXI-Lite slave handshake: correct VALID/READY pattern
-- ARREADY can be combinatorial; RVALID must be registered
process(s_axi_aclk)
begin
  if rising_edge(s_axi_aclk) then
    if s_axi_aresetn = '0' then
      rvalid <= '0';
    elsif s_axi_arvalid = '1' and s_axi_arready = '1' then
      -- address accepted; latch and assert RVALID
      read_addr_reg <= s_axi_araddr;
      rvalid <= '1';
    elsif s_axi_rready = '1' then
      rvalid <= '0';  -- handshake complete
    end if;
  end if;
end process;

s_axi_rvalid <= rvalid;
s_axi_rdata  <= bram_dout when rvalid = '1' else (others => '0');
s_axi_rresp  <= "00";  -- OKAY
```

### Relevance to Your Project

Your project uses two AXI-Lite BRAM controllers at `0xA0000000` (BRAM0) and `0xA0010000` (BRAM2). Verifying that read-back never stalls requires that `ARREADY` and `RVALID` handshakes complete correctly. If you ever see a read returning stale data or hanging, trace `RVALID` — it must not be held low while `RREADY` is high from the PS.

## Vivado Block Design / IP Integrator

### Key Findings

- **Connection Automation** in IP Integrator automatically wires AXI masters to SmartConnect and then to slaves; run it after instantiating every IP before touching the Address Editor.
- **Address Editor**: after running connection automation, each AXI slave gets an auto-assigned base address. You must verify (or manually override) these to match your intended memory map. Addresses must be naturally aligned — a 4 KB slave range needs a base address ending in `000` hex.
- Avoid assigning base address `0x0` — some driver code asserts on a null-pointer-equivalent base and will fault at runtime.
- The Address Editor tab only appears when the design contains at least one AXI master (e.g., Zynq PS `M_AXI_HPM0_FPD`).
- Vivado 2025.2 introduces **SystemVerilog Interface support** in IPI — SV `interface` types now connect directly between IP instances with auto-generated wrappers, reducing manual port connections for complex AXI fan-outs.

### Code Example

```tcl
# TCL: assign addresses for two BRAM controllers in a block design
# Run after create_bd_cell and connect_bd_intf_net calls

assign_bd_address [get_bd_addr_segs {axi_bram_ctrl_0/S_AXI/Mem0}] \
    -range 64K -offset 0xA0000000

assign_bd_address [get_bd_addr_segs {axi_bram_ctrl_1/S_AXI/Mem0}] \
    -range 64K -offset 0xA0010000

validate_bd_design
save_bd_design
```

### Relevance to Your Project

Your two BRAMs at `0xA0000000` and `0xA0010000` each need their address segment locked to those exact offsets in `create_bd.tcl`. The TCL snippet above is the idiomatic way to do this programmatically rather than relying on GUI auto-assignment, which can silently shift addresses on a block design regeneration.

## Vivado TCL Scripting

### Key Findings

- **Non-project mode** runs entirely from TCL: `read_vhdl`, `read_xdc`, `synth_design`, `opt_design`, `place_design`, `route_design`, `write_bitstream`. No `.xpr` file is created; state is in memory or design checkpoints (`.dcp`).
- Use `write_checkpoint` / `read_checkpoint` at key stages (post-synthesis, post-route) to allow resuming a long implementation run without restarting from scratch.
- `config_flows -impl_strategy` applies a preset implementation strategy (e.g. `Performance_ExplorePostRoutePhysOpt`) without manually listing individual directives.
- In batch mode (`vivado -mode batch -source script.tcl`), Vivado runs in Tcl script mode — stderr/stdout are fully captured, suitable for CI.
- Source file compile order matters: `read_vhdl` commands are processed in listing order — ensure packages/entities are listed before their instantiating architectures.

### Code Example

```tcl
# Non-project mode full build flow
create_project -in_memory -part xck26-sfvc784-2LV-c

read_vhdl  [glob ../vhdl/*.vhd]
read_xdc   ../constraints/kv260.xdc
read_bd    ../bd/design_1.bd

synth_design -top kv260_top -part xck26-sfvc784-2LV-c
write_checkpoint -force post_synth.dcp

opt_design
place_design
phys_opt_design
route_design
write_checkpoint -force post_route.dcp

write_bitstream -force kv260_top.bit
write_hw_platform -fixed -include_bit -force kv260_top.xsa
```

### Relevance to Your Project

Your `create_bd.tcl` script is already on the non-project TCL path. Wrapping it in the full flow above (with `synth_design` / `write_bitstream`) gives a single-command reproducible build: `vivado -mode batch -source build.tcl`. This is ideal for the KV260 AXI-BRAM demo since the design is small enough to build in a few minutes.

## Vitis Bare-Metal / Standalone

### Key Findings

- **UART1 for Kria KV260**: Unlike other ZynqMP evaluation boards that use UART0, the Kria SOM routes its USB-UART bridge to UART1 (`psu_uart_1`). In the BSP settings, `stdin`/`stdout` must be set to `psu_uart_1` or `xil_printf` output will be silent.
- The standalone BSP provides `xil_printf` (a lightweight, no-heap printf) for early bring-up output; full `printf` with floating-point support requires `-lm` and larger stack/heap settings in the linker script.
- **Linker script pitfall**: The auto-generated linker script can assign all sections to BAR0 instead of DDR. Verify that `.text`, `.data`, `.bss`, and the stack/heap are in `DDR_lowocm` (typically starting at `0x00000000` with 2 GB) for the KV260.
- Interrupt setup on ZynqMP requires: `XScuGic_LookupConfig()` → `XScuGic_CfgInitialize()` → `XScuGic_Connect()` → `XScuGic_Enable()` → `Xil_ExceptionEnable()`. The GIC base address is provided by the BSP device tree / `xparameters.h`.
- Vitis 2025.1 introduced a new **Vitis Server** backend for the IDE, improving build performance; classic command-line flows (`xsct`, `vitis -s`) remain fully functional.

### Code Example

```c
/* Bare-metal AXI-BRAM write/read with xil_printf on KV260 */
#include "xil_printf.h"
#include "xil_io.h"
#include "sleep.h"

#define BRAM0_BASE 0xA0000000UL
#define BRAM1_BASE 0xA0010000UL
#define TEST_PATTERN 0xDEADBEEFUL

int main(void) {
    u32 readback;

    xil_printf("KV260 AXI-BRAM test start\r\n");

    /* Write pattern */
    Xil_Out32(BRAM0_BASE, TEST_PATTERN);
    Xil_Out32(BRAM1_BASE, TEST_PATTERN ^ 0xFFFFFFFFUL);

    /* Ensure write completes before read (memory barrier) */
    dsb();

    /* Read back and verify */
    readback = Xil_In32(BRAM0_BASE);
    if (readback == TEST_PATTERN)
        xil_printf("BRAM0 PASS: 0x%08X\r\n", readback);
    else
        xil_printf("BRAM0 FAIL: expected 0x%08X got 0x%08X\r\n",
                   TEST_PATTERN, readback);

    readback = Xil_In32(BRAM1_BASE);
    if (readback == (TEST_PATTERN ^ 0xFFFFFFFFUL))
        xil_printf("BRAM1 PASS\r\n");
    else
        xil_printf("BRAM1 FAIL: 0x%08X\r\n", readback);

    return 0;
}
```

### Relevance to Your Project

The `dsb()` (Data Synchronization Barrier) before the read-back is critical on Cortex-A53 — without it the processor's out-of-order engine can reorder the AXI write/read pair and produce a false PASS. Your existing `main.c` should include this or use `Xil_Out32`/`Xil_In32` (which are `volatile`-safe) rather than raw pointer dereferences.

## XDC Timing Constraints

### Key Findings

- The recommended XDC constraint ordering is: (1) clock definitions, (2) clock groups / `set_false_path`, (3) I/O timing (`set_input_delay` / `set_output_delay`), (4) exceptions. Correct ordering improves solver runtime.
- `set_input_delay` and `set_output_delay` model external board-level delays relative to a clock edge. For a pure internal BRAM design with no off-chip I/O, these constraints are not needed on data paths — only on GPIO/UART pins.
- For the PS–PL clock crossing (e.g., `pl_clk0` used as AXI clock), use:
  ```tcl
  create_clock -period 10.000 [get_pins path/to/zynq_ps/inst/PS8_i/PLCLK[0]]
  ```
  Vivado normally auto-creates this clock from the Zynq IP, but explicitly defining it prevents surprises after IP regeneration.
- `set_clock_groups -asynchronous` is used when two clocks have no timing relationship. For the KV260's single `pl_clk0` driving both the AXI fabric and BRAM, all paths share the same clock — no clock groups needed.
- **Ordering constraints saves runtime (UG903 2026.1)**: placing timing exceptions before clock-domain constraints forces the solver to re-analyze; always follow the recommended order.

### Code Example

```xdc
# kv260.xdc - minimal timing constraints for AXI-BRAM demo

# PL clock from Zynq PS (100 MHz default)
# Vivado auto-creates this; explicit definition for safety
# create_clock -period 10.000 -name pl_clk0 \
#   [get_pins design_1_i/zynq_ultra_ps_e_0/inst/PS8_i/PLCLK[0]]

# UART TX/RX I/O timing (external board trace ~1 ns)
set_output_delay -clock [get_clocks pl_clk0] -max  2.0 [get_ports uart_txd]
set_output_delay -clock [get_clocks pl_clk0] -min -0.5 [get_ports uart_txd]
set_input_delay  -clock [get_clocks pl_clk0] -max  2.0 [get_ports uart_rxd]
set_input_delay  -clock [get_clocks pl_clk0] -min -0.5 [get_ports uart_rxd]

# Mark all BRAM paths as false path to PS clock
# (PS internal clocking; Vivado handles AXI clock relationship automatically)
set_false_path -from [get_clocks clk_pl_0] -to [get_clocks clk_pl_0]
```

### Relevance to Your Project

For the current AXI-BRAM demo, the main timing risk is the `pl_clk0` → BRAM → AXI read-data path. Vivado's implementation usually closes this easily at 100 MHz on the K26. If you expand to higher frequencies or add pipeline stages in `kv260_top.vhd`, add `set_multicycle_path` constraints for any multi-cycle registered paths to avoid overly tight timing analysis.

## Kria KV260 / K26 SoM Platform Specifics

### Key Findings

- **UART1 for console** (see also Vitis section): `psu_uart_1` maps to the USB-UART bridge on the KV260 carrier. The baud rate must be 115200. Connecting to UART0 produces no output.
- **Boot modes**: KV260 supports JTAG (SW6 switch), SD card, and QSPI. For bare-metal development, JTAG boot is fastest — connect USB-JTAG on J2, set SW6, power on, then use Vitis `xsct` → `connect` → `dow` → `run`.
- The K26 SoM has two 240-pin board-to-board connectors exposing: PS MIO pins, PS-GTR transceivers, PL HPIO, PL HDIO, PL GTH transceivers, and power rails. PL I/O supply voltages are set by the carrier card (KV260) — default 1.8V for HPIO.
- Two SOM variants: `sm-k26` (with eMMC) and `smk-k26` (without eMMC, used on KV260 Starter Kit). Starter kits have pre-programmed QSPI firmware; bare-metal overrides this with JTAG.
- Power: all PS supplies derived from a single +5V input on the SOM. PL I/O bank voltages are carrier-card defined — do not drive 3.3V signals into KV260 HPIO banks without checking the carrier card schematic.
- A community bare-metal bringup guide (hackster.io, 2025) covers 4K video streaming on KV260 with Vivado 2025.2 — useful reference for adding PL peripherals beyond BRAM.

### Code Example

```tcl
# XSCT bare-metal JTAG download and run sequence (run in Vitis XSCT console)
connect

# Target the A53 core 0
targets -set -filter {name =~ "Cortex-A53 #0"}

# Disable MMU/cache for bare-metal (optional but avoids cache coherency issues)
rst -processor

# Download ELF
dow /path/to/kv260_axi_bram.elf

# Run
con

# View UART output in a serial terminal at 115200 baud on /dev/ttyUSB1
```

### Relevance to Your Project

The JTAG download sequence above is the fastest iteration loop for the KV260 AXI-BRAM demo. After each Vitis rebuild, `dow` re-flashes the ELF without touching the bitstream — useful when only C code changes. For bitstream + ELF updates, run `fpga -file kv260_top.bit` before `dow`.

## AMD/Xilinx Tool Updates (Vivado/Vitis 2025.x)

### Key Findings

- **Vivado 2025.1**: Introduced a new **AXI Switch IP** — a fully customizable RTL-based bridge between different AXI interface types and widths. Complements (but does not replace) SmartConnect for point-to-point bridging.
- **Vivado 2025.2**: 
  - New **ultra-low-area mode** for AXI SmartConnect and AXI Switch via `STRATEGY` parameter — reduces logic utilization when bandwidth is not the bottleneck.
  - **SystemVerilog Interface support** in IPI: SV `interface` types connect directly in block design with auto-generated wrappers.
  - Reduced PhysOpt compile time.
  - BUFG_FABRIC replication improvements per-SLR for high-fanout nets.
  - New Versal AI Edge Gen 2 and Versal Prime Gen 2 device support.
- **Vitis 2025.1**: New Vitis IDE with **Vitis Server** backend (faster builds); classic XSCT command-line workflow unchanged. Supports Versal, Zynq MPSoC, Zynq 7000, MicroBlaze.
- **Vivado 2026.1** (current docs): UG892 and UG903 are already published for 2026.1 — documentation ahead of release is a sign AMD is on a faster release cadence. Non-project mode docs in UG892 now include updated TCL script examples.
- The community response to Vivado 2025.1 (r/FPGA, June 2025) is generally positive on stability; no major blocking issues for Zynq MPSoC bare-metal flows reported.

### Code Example

```tcl
# Vivado 2025.2: AXI SmartConnect with ultra-low-area strategy
# Set STRATEGY to "MinArea" to reduce LUT utilization

set_property CONFIG.STRATEGY {MinArea} \
    [get_bd_cells smartconnect_0]

# Or at creation time:
create_bd_cell -type ip -vlnv xilinx.com:ip:smartconnect:1.0 smartconnect_0
set_property CONFIG.NUM_SI {1}      [get_bd_cells smartconnect_0]
set_property CONFIG.NUM_MI {2}      [get_bd_cells smartconnect_0]
set_property CONFIG.STRATEGY {MinArea} [get_bd_cells smartconnect_0]
```

### Relevance to Your Project

If you upgrade to Vivado 2025.2 (or already use it), setting `STRATEGY MinArea` on the SmartConnect in `create_bd.tcl` is a free resource win for the KV260 AXI-BRAM demo — the design is throughput-limited by the PS, not by SmartConnect bandwidth. The new AXI Switch IP is worth evaluating if you later add a PL DMA master that also needs access to the BRAMs.
