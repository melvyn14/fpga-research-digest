# FPGA Research Digest - 2026-11-04

## Executive Summary
- **AXI-Lite handshake bug risk**: ZipCPU's formal analysis confirmed multiple errors in Vivado-generated AXI-Lite slave templates; always simulate with the AXI Protocol Checker IP before hardware bring-up on the KV260.
- **BSP UART selection**: The `standalone_stdin`/`standalone_stdout` keys in `vitis-comp.json` control which UART `xil_printf` uses; for the KV260 carrier, verify this maps to UART1 (the USB-JTAG path) rather than UART0.
- **Kria bare-metal boot image**: The default SOM BOOT.bin targets Linux — a custom boot image with `fsbl.elf`, `pmufw.elf`, the application ELF, and the bitstream is required for standalone bare-metal runs over JTAG.
- **Clock domain crossing constraints**: For PS-to-PL AXI-Lite paths, use `set_clock_groups -asynchronous -include_generated_clocks` and verify clock names with `get_clocks` in the Tcl console before trusting timing closure.
- **Non-project TCL flow**: Writing intermediate checkpoints after each design step (`write_checkpoint`) enables faster iterative debugging by resuming from `open_checkpoint` without rerunning synthesis.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings
- **xVALID must deassert after reset**: Any AXI channel's xVALID signal must be held low during and immediately following reset. Failure to do so is the most common reset-domain bug in custom AXI-Lite masters.
- **Vivado slave template bugs**: ZipCPU's formal verification of Vivado-generated AXI-Lite slave cores (as late as 2018.3) confirmed protocol violations in handshake logic, particularly around simultaneous read/write requests and conditional handshake gating. Treat generated templates as a starting point, not production-ready code.
- **Read/write arbitration pitfall**: Vivado-generated AXI-Lite slaves that can only handle one direction at a time silently buffer the other request; the buffering behavior is implementation-defined and may cause unexpected latency.
- **Protocol Checker IP**: The AMD AXI Protocol Checker IP (`axi_protocol_checker_v2_0`) flags handshake violations, illegal burst parameters, and response errors in simulation and in hardware with ILA integration.
- **AXI-Stream TVALID/TREADY rule**: The sender must never make `TVALID` conditional on `TREADY` — this creates a combinational loop. `TREADY` may depend on `TVALID`, but not the reverse. `TLAST` is only meaningful when both `TVALID` and `TREADY` are asserted simultaneously.
- **Register slices for timing**: When post-route timing shows setup violations on an AXI interconnect path, insert a register slice (`AXI Register Slice` IP) in the offending segment rather than relaxing constraints.

### Code Example
```vhdl
-- Minimal AXI-Lite slave: safe reset deassert + handshake pattern
-- Ensures AWREADY/WREADY/ARREADY deassert during reset
process(S_AXI_ACLK)
begin
  if rising_edge(S_AXI_ACLK) then
    if S_AXI_ARESETN = '0' then
      -- Critical: all xVALID/xREADY driven low during reset
      axi_awready <= '0';
      axi_wready  <= '0';
      axi_bvalid  <= '0';
      axi_arready <= '0';
      axi_rvalid  <= '0';
    else
      -- Write address handshake
      if axi_awready = '0' and S_AXI_AWVALID = '1' and S_AXI_WVALID = '1' then
        axi_awready <= '1';
      else
        axi_awready <= '0';
      end if;
    end if;
  end if;
end process;
```

### Relevance to Your Project
Your `main.c` writes patterns to BRAM0 (`0xA0000000`) and BRAM2 (`0xA0010000`) via memory-mapped AXI-Lite. If `kv260_top.vhd` or the block design's AXI Interconnect IP has reset-domain issues, writes may silently succeed (no bus error) but data integrity fails at the BRAM side. Run the AXI Protocol Checker in simulation against your block design before taping out.

## Vivado Block Design / IP Integrator

### Key Findings
- **Export with `write_bd_tcl`**: Use `write_bd_tcl -force -include_layout output.tcl` to generate a reproducible script from an existing block design. The `-no_ip_version` flag reduces version-mismatch failures when regenerating on a different Vivado install.
- **Avoid `apply_bd_automation` in scripts**: Automation works interactively but can produce non-reproducible connections in batch TCL scripts. Use explicit `connect_bd_net` and `connect_bd_intf_net` calls instead.
- **Required finalization sequence**: Always call `validate_bd_design`, then `regenerate_bd_layout`, then `save_bd_design` at the end of any programmatic block design construction.
- **Absolute paths required**: AMD's UG896 (2025.1) states that file paths in Tcl IP commands must be absolute — relative paths produce silent failures or incorrect file associations.
- **Avoid `upgrade_ip [get_ips -all]`**: This command can delete sub-core IPs during a parent IP upgrade, breaking the design. Upgrade IPs individually or by explicit list.
- **Address Editor after connections**: After connecting AXI master/slave ports, run `assign_bd_address` and verify the address map in the Address Editor — missing or overlapping segments are a common root cause of bus errors at runtime.

### Code Example
```tcl
# Reproducible block design creation pattern
create_bd_design "system"

# Create and configure Zynq UltraScale+ MPSoC IP
set zynq_ultra [create_bd_cell -type ip \
  -vlnv xilinx.com:ip:zynq_ultra_ps_e:3.5 zynq_ultra_ps_e_0]
set_property -dict [list \
  CONFIG.PSU__USE__M_AXI_GP0 {1} \
  CONFIG.PSU__UART1__PERIPHERAL__ENABLE {1} \
  CONFIG.PSU__UART1__PERIPHERAL__IO {MIO 36 .. 37} \
] $zynq_ultra

# Add AXI BRAM Controller
set bram_ctrl [create_bd_cell -type ip \
  -vlnv xilinx.com:ip:axi_bram_ctrl:4.1 axi_bram_ctrl_0]
set_property CONFIG.SINGLE_PORT_BRAM {1} $bram_ctrl

# Explicit connection (not apply_bd_automation)
connect_bd_intf_net \
  [get_bd_intf_pins zynq_ultra_ps_e_0/M_AXI_HPM0_FPD] \
  [get_bd_intf_pins axi_bram_ctrl_0/S_AXI]

# Assign addresses and validate
assign_bd_address
validate_bd_design
save_bd_design
```

### Relevance to Your Project
Your `create_bd.tcl` script builds the block design with two BRAM controllers (at `0xA0000000` and `0xA0010000`). Using explicit `connect_bd_intf_net` calls and always calling `assign_bd_address` before `validate_bd_design` ensures the address map is deterministic across Vivado versions — critical when the script is rerun on a CI machine or a different workstation.

## Vivado TCL Scripting

### Key Findings
- **Non-project batch flow structure**: The canonical AMD non-project script (UG892) follows: read sources → `synth_design` → `write_checkpoint` → `opt_design` → `write_checkpoint` → `place_design` → `phys_opt_design` → `route_design` → `write_checkpoint` → `write_bitstream`.
- **Checkpoint-driven iteration**: Opening a post-synthesis checkpoint with `open_checkpoint` lets you re-run place and route without redoing synthesis — saves 10-20 minutes per iteration on typical KV260 designs.
- **`write_ip_tcl` for IP capture**: Generates a standalone Tcl script reproducing all IP customizations. Useful for archiving IP settings separate from the block design.
- **Non-project has no auto-rerun**: Unlike project mode, non-project mode has no dependency tracking — after changing a source file, the entire flow from synthesis onwards must be rerun manually.
- **Strategy options**: `config_flows -synth_strategy "Flow_PerfOptimized_high" -impl_strategy "Performance_ExplorePostRoutePhysOpt"` applies named strategies to the non-project flow.

### Code Example
```tcl
#!/usr/bin/env tclsh
# Non-project batch flow for kv260-axi-bram-demo
set OUTPUT_DIR "./output_products"
file mkdir $OUTPUT_DIR

# Read sources
read_vhdl -library work [glob ./vhdl/*.vhd]
read_xdc ./constrs/kv260_top.xdc

# Synthesis with checkpoint
synth_design -top kv260_top -part xck26-sfvc784-2LV-c
write_checkpoint -force $OUTPUT_DIR/post_synth.dcp
report_timing_summary -file $OUTPUT_DIR/post_synth_timing.rpt

# Implementation with intermediate checkpoints
opt_design
place_design
phys_opt_design
write_checkpoint -force $OUTPUT_DIR/post_place.dcp

route_design
write_checkpoint -force $OUTPUT_DIR/post_route.dcp
report_timing_summary -file $OUTPUT_DIR/post_route_timing.rpt
report_utilization  -file $OUTPUT_DIR/utilization.rpt

# Generate bitstream
write_bitstream -force $OUTPUT_DIR/kv260_top.bit
```

### Relevance to Your Project
Wrapping `create_bd.tcl` in a non-project batch script lets the entire Vivado flow (block design generation → synthesis → implementation → bitstream) run from a single `vivado -mode batch -source build.tcl` command. This eliminates manual GUI steps and enables reproducible builds in CI.

## Vitis Bare-Metal / Standalone

### Key Findings
- **UART selection via `vitis-comp.json`**: The `standalone_stdin` and `standalone_stdout` keys in `vitis-comp.json` (the BSP component configuration) determine which UART `xil_printf` writes to. For KV260 (like KD240), UART1 is the JTAG/USB-UART interface; set both keys to `psuart1` to route console output there.
- **xil_printf vs printf**: `xil_printf` is a lightweight printf that handles `%d`, `%s`, `%x`, and `%u` only — it does not support `%f`, `%e`, or width specifiers. Use the full `printf` (enabled in BSP settings) only when floating-point or format width is needed.
- **Bare-metal Kria boot sequence**: JTAG boot requires `fsbl.elf` (First Stage Bootloader), `pmufw.elf` (PMU Firmware), the application ELF, and the bitstream. The default SOM BOOT.bin is Linux-oriented and cannot run a standalone ELF directly.
- **Linker script memory regions**: The Vitis standalone linker script maps `ps_pl_mem` to the AXI address space. If BRAM addresses (`0xA0000000`, `0xA0010000`) are not in the XSA's address map, the linker will not generate the correct section — verify the address map exports from Vivado match the XSA.
- **Cache coherency on Cortex-A53**: The A53 has hardware-managed coherency for inner shareable domains, but bare-metal AXI-Lite MMIO transactions to PL targets require `Xil_DCacheFlushRange` after writes if any caching layer is active on that memory region.

### Code Example
```c
/* Bare-metal AXI-Lite BRAM write-readback pattern */
#include "xil_printf.h"
#include "xil_io.h"
#include "xil_cache.h"

#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL
#define TEST_DEPTH  16

int bram_test(u32 base_addr, const char *name) {
    u32 wr_val, rd_val;
    int pass = 1;

    for (int i = 0; i < TEST_DEPTH; i++) {
        wr_val = 0xDEAD0000 | (u32)i;
        Xil_Out32(base_addr + (i * 4), wr_val);
    }

    /* Flush D-cache for the BRAM region (required if caching enabled) */
    Xil_DCacheFlushRange(base_addr, TEST_DEPTH * 4);

    for (int i = 0; i < TEST_DEPTH; i++) {
        rd_val = Xil_In32(base_addr + (i * 4));
        if (rd_val != (0xDEAD0000 | (u32)i)) {
            xil_printf("FAIL %s[%d]: wrote 0x%08X, read 0x%08X\r\n",
                       name, i, 0xDEAD0000 | i, rd_val);
            pass = 0;
        }
    }
    if (pass) xil_printf("PASS %s\r\n", name);
    return pass;
}

int main(void) {
    xil_printf("KV260 AXI-BRAM Test\r\n");
    bram_test(BRAM0_BASE, "BRAM0");
    bram_test(BRAM2_BASE, "BRAM2");
    return 0;
}
```

### Relevance to Your Project
This directly matches your `main.c` pattern. The `Xil_DCacheFlushRange` call is a defensive addition for when D-cache is enabled — on a default bare-metal KV260 BSP the A53 starts with caches enabled, and omitting the flush can cause reads to return stale cache lines rather than BRAM contents, producing false FAIL results.

## XDC Timing Constraints

### Key Findings
- **PS clock as source**: When using the Zynq UltraScale+ PS-generated clock (e.g., `pl_clk0`) as the PL fabric clock, Vivado automatically recognizes it as a primary clock once `create_clock` is applied to the PS clock output pin. The insertion delay before the named source point is not included in timing analysis — be aware of this when reasoning about inter-clock skew.
- **`set_clock_groups` for async clocks**: For AXI-Lite interfaces where PS and PL clocks are asynchronous, use `set_clock_groups -asynchronous -group [get_clocks clk_ps] -group [get_clocks clk_pl] -include_generated_clocks`. The `-include_generated_clocks` switch automatically pulls in PLL-derived clocks, avoiding missed CDC paths.
- **Bidirectional false path**: A single `set_false_path -from A -to B` only excludes paths in one direction. To exclude both directions, either use `set_false_path -from A -to B` AND `set_false_path -from B -to A`, or use `set_clock_groups` which is bidirectional by definition.
- **Clock name verification**: Always run `get_clocks` in the Vivado Tcl console after opening the synthesized design or a checkpoint to confirm the actual clock names before writing XDC constraints. Vivado reports `[Vivado 12-4739] No valid object(s) found` when a clock name is wrong — a silent constraint miss.
- **AXI Interconnect timing**: When the PS drives AXI-Lite at 100 MHz and PL logic runs at the same clock, they share one clock domain — no CDC constraint needed. Problems arise if `pl_clk1` or a different divisor is used for the BRAM controller.

### Code Example
```tcl
# kv260_top.xdc — timing constraints for KV260 AXI-BRAM demo

# PS-generated PL clock (100 MHz from pl_clk0)
# Vivado typically auto-derives this; include explicitly for clarity
create_clock -period 10.000 -name clk_pl \
  [get_pins zynq_ultra_ps_e_0/inst/PS8_i/PLCLK[0]]

# If using a secondary async clock (e.g., EMIO-driven external clock):
# set_clock_groups -asynchronous \
#   -group [get_clocks clk_pl -include_generated_clocks] \
#   -group [get_clocks clk_ext -include_generated_clocks]

# Output delay for signals going out of PL (adjust for board trace)
set_output_delay -clock clk_pl -max 2.000 [get_ports {led[*]}]
set_output_delay -clock clk_pl -min -1.000 [get_ports {led[*]}]

# False paths for asynchronous resets (if used)
# set_false_path -from [get_pins rst_gen/reset_out] -to [get_pins bram_ctrl/rstn]
```

### Relevance to Your Project
Your KV260 AXI-BRAM design runs the PL fabric from `pl_clk0` at 100 MHz, which also drives the AXI-Lite interconnect to both BRAM controllers. Since both PS and PL run from the same `pl_clk0` source, there is no AXI clock domain crossing — timing analysis should pass without `set_clock_groups`. The XDC risk area is false paths on any external reset or LED outputs you add.

## Kria KV260 / K26 SoM

### Key Findings
- **MIO bank assignment**: The K26 SoM partitions MIO into three banks: MIO500 (QSPI, eMMC, SOM I2C, SPI/TPM — reserved for onboard SOM peripherals), MIO501 (PMU power management + user I/O via SOM connector), MIO502 (user I/O via SOM connector). Avoid MIO500 in custom designs.
- **Dynamic MIO (Kria innovation)**: Unlike traditional Zynq boards with static MIO assignment at boot, the Kria platform uses PMU-driven incremental MIO configuration. This allows different carrier cards (KV260, KR260) to configure carrier-specific MIO at runtime without changing the SOM bitstream.
- **UART routing on KV260**: UART1 (MIO 36/37) is routed to the USB-JTAG chip on the KV260 carrier card, making it the console UART. UART0 is routed to the expansion connector. Verify by checking the KV260 carrier card schematic pinout.
- **Bare-metal BOOT.bin**: The default AMD BOOT.bin for the K26 SoM is targeted at Linux boot (Petalinux). For bare-metal, build a custom BOOT.bin from Vitis with FSBL + PMUFW + application ELF + bitstream via the `Create Boot Image` wizard or `bootgen` CLI.
- **Board files**: Vivado board support files for the KV260 (`xilinx.com:kv260_som:part0:1.3`) must be installed before `create_project` can target the board. Install via `Vivado > Tools > Vivado Store` or by copying board files to `$VIVADO_INSTALL/data/boards/board_files/`.

### Code Example
```tcl
# Vivado project creation targeting KV260 with correct board part
create_project kv260_axi_bram ./kv260_project -part xck26-sfvc784-2LV-c
set_property BOARD_PART xilinx.com:kv260_som:part0:1.3 [current_project]

# Verify board files are installed
if {[llength [get_board_parts xilinx.com:kv260*]] == 0} {
    error "KV260 board files not installed. Run: install_board_files kv260"
}
```

```bash
# Build BOOT.bin for bare-metal (run after Vitis generates ELF)
bootgen -image boot.bif -arch zynqmp -o BOOT.bin -w on
```

```
# boot.bif template for bare-metal KV260
the_ROM_image: {
    [bootloader, destination_cpu=a53-0] fsbl.elf
    [pmufw_image] pmufw.elf
    [destination_device=pl] kv260_top.bit
    [destination_cpu=a53-0, exception_level=el-3, trustzone] bl31.elf
    [destination_cpu=a53-0, exception_level=el-2] u-boot.elf

```

### Relevance to Your Project
The KV260's dynamic MIO means your bare-metal design should avoid assuming a fixed UART pinout — always cross-reference the KV260 carrier card schematic against `ug1092-kv260-starter-kit.pdf`. The `xck26-sfvc784-2LV-c` part string is the correct speed grade for the production KV260 KIT (note: `-2LV-c` = commercial temperature, `-2LV-i` = industrial). Using the wrong part string will cause DRC errors during bitstream generation.

## AMD/Xilinx Tool Updates (Vivado/Vitis 2025.x)

### Key Findings
- **Vivado 2025.1 new device support**: Added Versal AI Edge Series Gen 2, Versal Prime Series Gen 2, and Spartan UltraScale+ family. No changes were reported for existing Zynq UltraScale+ (K26) device support in the community notes reviewed.
- **Unified Selective Device Installer**: Vivado 2025.1 introduced a Unified Selective Device Installer that reduces the download footprint for Versal-only workflows. Zynq UltraScale+ remains in the standard installer.
- **Vitis AI 5.1 and 2025.1.1**: Vitis AI 5.1 targets the `2025.1.1` point release of Vivado/Vitis (a maintenance update beyond the initial 2025.1 drop). If running inference on the KV260, ensure the tool chain version matches exactly.
- **Vitis Libraries 2025.1**: 20 new L1 APIs and 6 new L2 APIs added for the VEK280 AIE-ML device. PWM IP has a new version (`IP_PWM_V2`).
- **Known issue — RHEL8/CentOS8 Vitis GUI**: Vitis GUI on RHEL 8.3 and CentOS 8.2 may fail due to a library conflict in `LD_LIBRARY_PATH`. Workaround: remove `${env_var:LD_LIBRARY_PATH}` from the project settings.
- **UG896 2025.2 update**: The Designing with IP guide has a 2025.2 edition (released 2025-11-20), covering updated `write_ip_tcl` behavior and warnings about `upgrade_ip` removing sub-core IP.

### Code Example
```tcl
# Verify Vivado version at script start (guards against tool mismatch)
set vivado_version [version -short]
if {[string compare -nocase $vivado_version "2025.1"] < 0} {
    puts "WARNING: Script developed for Vivado 2025.1, running on $vivado_version"

}

# Check installed board parts after tool update

    puts "ERROR: KV260 board files missing. Install via Vivado Store."

}
puts "Found KV260 board parts: $kv260_parts"
```

### Relevance to Your Project
Vivado 2025.1 is the target toolchain for your project. Since no breaking changes to Zynq UltraScale+ or AXI BRAM IP were reported for 2025.1, your existing `create_bd.tcl` and `kv260_top.vhd` should be forward-compatible with 2025.2 when that becomes available. Add the version check snippet above to `create_bd.tcl` to catch accidental regressions when the tool is upgraded.
