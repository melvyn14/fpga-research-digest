## Executive Summary

- **AXI-Lite backpressure pitfall:** If the PS holds `BREADY` low, your slave must de-assert
  `AWREADY`/`WREADY` — most reference cores get this wrong; verify with simulation before
  trusting a passing JTAG test.
- **BRAM controller limitation:** The `axi_bram_ctrl` in AXI4-Lite mode is fixed at 32-bit data
  width and single-beat transfers only — this matches your demo pattern-write loop but rules out
  wide/burst access.
- **JTAG boot scripting:** On the KV260 you must explicitly switch the SoM into JTAG boot mode
  via XSCT register writes before loading `.elf` and bitstream — the hardware default is QSPI32.
- **TCL non-project trap:** `write_bd_tcl` omits default parameters and propagated values; the
  exported script is Vivado-version-locked and will silently fail on any other release.
- **Vivado 2025.1 known issue:** IP updates may not be detected by the tool (requiring a full
  project close/reopen); a separate crash-on-update defect can require a host machine restart.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- AXI4-Lite uses five independent channels: **Write Address (AW)**, **Write Data (W)**,
  **Write Response (B)**, **Read Address (AR)**, **Read Data (R)**. Each uses its own
  `VALID`/`READY` handshake independently.
- **Backpressure is the top pitfall.** When the master de-asserts `BREADY` (not ready to accept
  a write response), a compliant slave must also de-assert `AWREADY` and `WREADY`. This is
  routinely missed in hand-rolled slaves and in Xilinx's own demo core (the write-channel bug
  was fixed after Vivado 2016.3; the read-channel bug remained as of recent documentation).
- `WSTRB` (write strobe) is a per-byte enable — for 32-bit AXI-Lite it is 4 bits wide. Your
  BRAM writes should check this if partial-word writes are ever needed.
- For the `axi_bram_ctrl` IP in AXI4-Lite mode: **data width is fixed at 32 bits**, only
  single-beat transfers are supported, and burst length is always 1. This is the correct
  configuration for your pattern write-readback test.
- A valid transfer completes only when **both** `VALID` and `READY` are high on the **same**
  rising clock edge. Driving `VALID` speculatively without verifying `READY` on the same edge
  is not a transfer — it is a potential deadlock if the slave is also waiting.

### Code Example

```vhdl
-- Minimal AXI4-Lite slave write channel with correct BREADY backpressure
process(s_axi_aclk)
begin
  if rising_edge(s_axi_aclk) then
    if s_axi_aresetn = '0' then
      s_axi_awready <= '0';
      s_axi_wready  <= '0';
      s_axi_bvalid  <= '0';
      s_axi_bresp   <= "00";
    else
      -- Accept AW+W only when B response channel is not backpressured
      if s_axi_awvalid = '1' and s_axi_wvalid = '1'
         and s_axi_awready = '0' and s_axi_wready = '0'
         and (s_axi_bvalid = '0' or s_axi_bready = '1') then
        s_axi_awready <= '1';
        s_axi_wready  <= '1';
      else
        s_axi_awready <= '0';
        s_axi_wready  <= '0';
      end if;

      -- Issue write response when both address and data were accepted
      if s_axi_awready = '1' and s_axi_awvalid = '1'
         and s_axi_wready = '1' and s_axi_wvalid = '1' then
        s_axi_bvalid <= '1';
        s_axi_bresp  <= "00"; -- OKAY
      elsif s_axi_bready = '1' then
        s_axi_bvalid <= '0';
      end if;
    end if;
  end if;
end process;
```

### Relevance to Your Project

Your demo writes 32-bit patterns from the Cortex-A53 (PS) through AXI-Lite to two BRAM
controllers at `0xA0000000` (BRAM0) and `0xA0010000` (BRAM2). Confirming your
`kv260_top.vhd` wrapper passes the `BREADY` signal correctly to the `axi_bram_ctrl` IP — and
doesn't permanently tie it high — is critical to avoiding silent write-response stalls that
would cause your bare-metal readback to hang or return stale data.

## Vivado Block Design / IP Integrator

### Key Findings

- **Export command:** `write_bd_tcl` (IDE: File → Export → Export Block Design) produces a
  portable TCL recreation script. Add `-include_layout` to preserve block-diagram positions.
- **Version lock:** The exported TCL embeds the Vivado version. Running it under a different
  release will either silently skip settings or produce errors — keep your `create_bd.tcl`
  versioned alongside your tool version.
- **Parameter propagation gotcha:** `write_bd_tcl` only records user-changed parameters.
  After import, always run `validate_bd_design` to re-trigger propagation; missing this step
  can leave downstream IP with wrong widths or clock frequencies.
- **Connection Automation:** `apply_bd_automation` handles standard connections (AXI
  interconnect insertion, reset polarity adaptation). Always review what it inserts — it may
  add an AXI SmartConnect that is unnecessary for a single-master, single-slave topology like
  yours.
- **Address Editor:** After adding a BRAM controller, the address must be manually assigned in
  the Address Editor or via TCL. Failing to do so causes synthesis to succeed but hardware to
  silently ignore writes.

### Code Example

```tcl
# Validate the block design (triggers parameter propagation)
validate_bd_design

# Export block design TCL with layout info (run after every significant change)
write_bd_tcl -force -include_layout ./tcl/create_bd.tcl

# Assign address segment for axi_bram_ctrl_0 connected to HPM0_LPD
assign_bd_address [get_bd_addr_segs {axi_bram_ctrl_0/S_AXI/Mem0}]
set_property offset 0xA0000000 \
  [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property range 8K \
  [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
```

### Relevance to Your Project

Your `create_bd.tcl` script sets up two `axi_bram_ctrl` instances. The Address Editor snippet
above matches the 0xA0000000 base used in your C firmware. If you regenerate the block design
on a different workstation, running `validate_bd_design` immediately after sourcing the TCL is
mandatory before synthesis.

## Vivado TCL Scripting

### Key Findings

- **Non-project mode** (`vivado -mode batch`) reads sources in-memory and never writes a
  `.xpr` file. It loses source-file management, out-of-context synthesis, and cross-probing,
  but is ideal for CI pipelines and headless servers.
- **`create_bd_cell` syntax:** Creating the AXI BRAM controller IP cell uses the full VLNV
  string: `xilinx.com:ip:axi_bram_ctrl:4.1`. Omitting the version (`:4.1`) causes Vivado to
  silently pick the latest compatible version, which may differ between tool releases.
- **IP Integrator in non-project mode:** As of 2025.1 (UG994), you can call all `create_bd_*`
  commands in non-project mode, but you must call `open_bd_design` on the generated `.bd` file
  before synthesis begins.
- **Best practice for team repos:** Store the `write_bd_tcl`-exported script, not the `.bd`
  binary. The TCL is diff-friendly and version-control-safe; `.bd` files are binary and do not
  merge cleanly.
- **`set_property` ordering:** Set IP properties before connecting ports. Setting properties
  after `connect_bd_net` can silently override connection widths.

### Code Example

```tcl
# Non-project mode block design creation skeleton for kv260-axi-bram-demo
# Run with: vivado -mode batch -source create_bd.tcl

create_project -in_memory -part xck26-sfvc784-2LV-c

# Create and open block design
create_bd_design "kv260_bd"
open_bd_design [get_bd_designs kv260_bd]

# Add Zynq UltraScale+ PS
set ps [create_bd_cell -type ip \
  -vlnv xilinx.com:ip:zynq_ultra_ps_e:3.5 zynq_ultra_ps_e_0]
apply_bd_automation -rule xilinx.com:bd_rule:zynq_ultra_ps_e \
  -config { apply_board_preset "1" } $ps

# Enable HPM0 LPD master port (for PL access at low address space)
set_property CONFIG.PSU__USE__M_AXI_GP2 {1} $ps
set_property CONFIG.PSU__USE__M_AXI_GP0 {0} $ps

# Add BRAM controller #0
set bram_ctrl_0 [create_bd_cell -type ip \
  -vlnv xilinx.com:ip:axi_bram_ctrl:4.1 axi_bram_ctrl_0]
set_property CONFIG.PROTOCOL {AXI4LITE} $bram_ctrl_0

# Add Block Memory Generator
set bram_0 [create_bd_cell -type ip \
  -vlnv xilinx.com:ip:blk_mem_gen:8.4 blk_mem_gen_0]
set_property CONFIG.Memory_Type {True_Dual_Port_RAM} $bram_0

# Connect BRAM to controller
connect_bd_intf_net [get_bd_intf_pins axi_bram_ctrl_0/BRAM_PORTA] \
                    [get_bd_intf_pins blk_mem_gen_0/BRAM_PORTA]

validate_bd_design
write_bd_tcl -force ./tcl/create_bd.tcl
```

### Relevance to Your Project

Your existing `create_bd.tcl` follows this pattern. The explicit `-vlnv` pinning for
`axi_bram_ctrl:4.1` and `blk_mem_gen:8.4` prevents silent IP version drift between
Vivado 2025.1 upgrades. Confirm the VLNV versions currently in the script match those
installed in your local Vivado instance with `get_ipdefs -all *axi_bram_ctrl*`.

## Vitis Bare-Metal / Standalone

### Key Findings

- **BSP generation:** After exporting the XSA from Vivado, Vitis generates a standalone BSP
  that includes `xil_printf` (lightweight UART formatter), `xparameters.h` (all peripheral
  base addresses), and driver stubs for every IP in the block design.
- **`xil_printf` vs `printf`:** `xil_printf` is the correct choice for bare-metal; it omits
  floating-point support and dramatically reduces BSS/stack usage. For your PASS/FAIL output
  it is sufficient and keeps the binary under typical BRAM capacity.
- **Linker script (`lscript.ld`):** The default standalone linker script places code in DDR
  at `0x0`. For a minimal AXI-BRAM demo that fits in on-chip SRAM, change the `.text` region
  to `0xFFFC0000` (OCM). This eliminates the need for DDR initialization at boot.
- **GIC / XScuGic for interrupts:** If you add interrupt-driven readback, use `XScuGic_Enable`
  to enable the specific interrupt ID and register a handler via `XScuGic_Connect`. The GIC
  base address for Zynq UltraScale+ (K26) is `0xF9010000`.
- **JTAG debug workflow:** For development without a boot image, Vitis Debug → Debug
  Configurations → use `psu_init.tcl` (not FSBL) to initialize the PS before loading the ELF.
  This skips secure boot and is faster for iterative testing.

### Code Example

```c
/* Minimal bare-metal AXI-BRAM write/readback using xil_printf */
#include "xil_printf.h"
#include "xil_io.h"

#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL
#define TEST_WORDS  8

static const u32 pattern[TEST_WORDS] = {
    0xDEADBEEFUL, 0xCAFEBABEUL, 0xA5A5A5A5UL, 0x5A5A5A5AUL,
    0x12345678UL, 0x87654321UL, 0xFFFFFFFFUL, 0x00000000UL
};

static int bram_test(u32 base, const char *name) {
    /* Write phase */
    for (int i = 0; i < TEST_WORDS; i++)
        Xil_Out32(base + (i * 4), pattern[i]);

    /* Readback phase */
    for (int i = 0; i < TEST_WORDS; i++) {
        u32 rd = Xil_In32(base + (i * 4));
        if (rd != pattern[i]) {
            xil_printf("%s FAIL @ offset %d: wrote 0x%08X read 0x%08X\r\n",
                       name, i * 4, pattern[i], rd);
            return -1;
        }
    }
    xil_printf("%s PASS (%d words verified)\r\n", name, TEST_WORDS);
    return 0;
}

int main(void) {
    xil_printf("KV260 AXI-BRAM Test\r\n");
    int rc = 0;
    rc |= bram_test(BRAM0_BASE, "BRAM0");
    rc |= bram_test(BRAM2_BASE, "BRAM2");
    xil_printf("Overall: %s\r\n", rc == 0 ? "PASS" : "FAIL");
    return rc;
}
```

### Relevance to Your Project

This mirrors your existing `main.c` pattern. Key additions: (1) the test covers 8 distinct
patterns including edge cases (all-zeros, all-ones, alternating bits) which exercise more BRAM
address/data lines than a simple incrementing pattern; (2) `Xil_Out32`/`Xil_In32` are the
correct BSP-provided I/O accessors — they handle cache and memory-ordering on the A53.

## XDC Timing Constraints

### Key Findings

- **`set_input_delay` / `set_output_delay`:** These constrain external PCB-level path delays
  relative to a clock edge at the device I/O. Values are in nanoseconds; positive means data
  arrives after the clock edge, negative means before. Both `-max` and `-min` variants should
  be specified for setup and hold coverage.
- **Clock groups for AXI:** The PS clock (`pl_clk0` from the Zynq PS block) and any
  free-running PL clocks are asynchronous to each other. Use `set_clock_groups -asynchronous`
  rather than individual false paths — it applies globally and cannot accidentally be missed on
  a new timing path.
- **Critical CDC rule:** Constraints hide timing violations; they do not fix metastability.
  A two-flip-flop synchronizer must exist in RTL for every CDC signal. The `XPM_CDC_SINGLE`
  and `XPM_CDC_GRAY` Xilinx parameterized macros (UG974) are the recommended primitives.
- **AXI IP internal synchronizers:** The `axi_bram_ctrl` and `zynq_ultra_ps_e` IPs contain
  internal CDC synchronizers. Do **not** override their internal `set_false_path` or
  `set_clock_groups` constraints with your own — doing so will silence real violations inside
  the IP and cause unpredictable behavior.
- **Constraint ordering:** In XDC, `create_clock` must appear before any `set_clock_groups`
  that reference it. Vivado processes XDC sequentially; out-of-order constraints are silently
  skipped.

### Code Example

```tcl
# kv260_top.xdc - Timing constraints for KV260 AXI-BRAM demo

# The PS provides pl_clk0 (typically 100 MHz); declare it as the primary clock
# Note: for Zynq PS, the clock is created automatically — this is for custom PL clocks only
# create_clock -period 10.000 -name pl_clk0 [get_ports pl_clk0]

# Mark PS clock and any independent PL clock as asynchronous clock groups
# Replace 'clk_100MHz' with your actual clock net name if you have a PL clock generator
set_clock_groups -asynchronous \
  -group [get_clocks -include_generated_clocks clk_pl_0] \
  -group [get_clocks -include_generated_clocks clk_out1_clk_wiz_0]

# I/O constraints for UART TX (output)
# Assumes 100 MHz clock; adjust max/min for your PCB trace delay
set_output_delay -clock [get_clocks clk_pl_0] -max 2.0 [get_ports uart_txd]
set_output_delay -clock [get_clocks clk_pl_0] -min -0.5 [get_ports uart_txd]

# False path for status LEDs (purely combinatorial, no timing requirement)
set_false_path -to [get_ports {led[*]}]
```

### Relevance to Your Project

For a minimal AXI-Lite/BRAM demo running entirely at `pl_clk0` from the PS, you likely need
only the `set_clock_groups` line if you have no secondary PL clocks. The false path on LEDs
and UART TX prevents spurious timing failures on the demo board outputs. If you are using a
clock wizard to derive a different PL frequency, add its output to the asynchronous group.

## Kria KV260 / K26 SoM

### Key Findings

- **Boot mode default is QSPI32.** The KV260 Starter Kit ships with boot firmware in QSPI NOR
  flash. For bare-metal development, you switch to JTAG mode programmatically via XSCT — not
  by hardware jumpers (the KV260 has no MODE pin headers exposed to the user).
- **JTAG boot switch via XSCT:**
  - Write `0x0` to `0xFFCA0010` (Boot Mode User register) to override hardware MODE pins.
  - Write `0x0100` to `0xFF5E0200` (CRL_APB.BOOT_MODE_USER) to select JTAG.
  - Perform a system reset. After reset, the PS comes up in JTAG boot mode and waits for XSCT
    to load FSBL/pmufw/bitstream/elf.
- **PS-PL AXI address mapping:** HPM0 LPD master (low-performance master port 0) maps to
  address space starting at `0xA0000000` by convention. Your two BRAMs at `0xA0000000` and
  `0xA0010000` are correctly placed within the 256 MB HPM0 LPD window
  (`0xA0000000`–`0xAFFFFFFF`).
- **MIO/EMIO:** All KV260 carrier-board peripherals (USB-UART at PL340 device, fan GPIO, etc.)
  are routed through MIO pins on the K26 SoM. USB-UART uses MIO38/39 at 3.3 V VCCO. No EMIO
  configuration is needed for UART — the PS UART1 is connected directly via MIO to the on-board
  USB-UART bridge.
- **Power domains:** The SoM sideband VCCO is 1.8 V. PL I/O banks on the K26 are at 1.8 V
  unless the carrier card supplies a different VCCO to the bank connector. Verify IOSTANDARD
  constraints in XDC match the carrier's actual VCCO.

### Code Example

```tcl
# XSCT script to switch KV260 to JTAG boot mode and load bare-metal ELF
# Run from Vitis XSCT console or: xsct boot_jtag.tcl

connect

# Switch boot mode to JTAG (override QSPI32 hardware default)
targets -set -filter {name =~ "PSU"}
mwr 0xFFCA0010 0x0          ;# Boot Mode User: select JTAG
mwr 0xFF5E0200 0x0100       ;# CRL_APB: apply boot mode override
rst -system                  ;# System reset — PS comes up in JTAG mode

after 3000                   ;# Wait for PS to complete reset sequence

# Initialize PS (use psu_init.tcl exported from Vivado hardware manager)
targets -set -filter {name =~ "PSU"}
source psu_init.tcl
psu_init

# Download bitstream
targets -set -filter {name =~ "PL"}
fpga kv260_top.bit

# Load and run the bare-metal ELF on APU core 0
targets -set -filter {name =~ "Cortex-A53 #0"}
dow kv260_bram_test.elf
con

disconnect
```

### Relevance to Your Project

This is the exact XSCT flow for loading your compiled ELF and bitstream without programming
QSPI. Replace `psu_init.tcl` with the file exported from your Vivado Hardware Manager run, and
substitute your `.bit` and `.elf` filenames. The `after 3000` delay is critical — skipping it
causes the `fpga` command to time out because the PS has not finished its reset sequence.

## AMD/Xilinx Tool Updates — Vivado/Vitis 2025.x

### Key Findings

- **Vivado 2025.1 new device support:** Added Versal AI Edge Series Gen 2, Versal Prime Series
  Gen 2, and Spartan UltraScale+ family targets. Zynq UltraScale+ (K26) support is unchanged
  and stable.
- **Known issue — IP update detection:** After updating an IP to a newer version, Vivado 2025.1
  may not recognize the update in the current session. Workaround: close and fully reopen the
  project. A separate defect causes a host-level crash (core dump) when updating certain IPs;
  workaround is a machine restart and re-opening Vivado.
- **Vitis 2025.1 release date:** UG1742 release notes published July 8, 2025. The unified Vitis
  IDE (replacing the classic Vitis IDE) is the primary workflow for new projects. Classic IDE
  features are deprecated but still functional in 2025.1.
- **AMD 2026.1 toolchain:** Documentation for Vivado/Vitis 2026.1 is now live on docs.amd.com.
  The Vitis Release Notes (UG1742 2026.1) and Vivado Release Notes (UG973 2026.1) are available.
  2026.1 is the newest release as of this digest date (2026-07-25). Consider evaluating an
  upgrade if you encounter the 2025.1 IP update crash.
- **KV260 BIST Tutorial for 2025.1:** A LogicTronix tutorial on Hackster.io recreates the KV260
  Board Integration Self-Test (BIST) design under Vivado/Vitis 2025.1, covering IP setup,
  block design, and Vitis standalone app — useful reference for AXI-BRAM troubleshooting steps.
- **`axi_bram_ctrl` IP version in 2025.1:** The VLNV string `xilinx.com:ip:axi_bram_ctrl:4.1`
  remains valid in 2025.1. If you open a project created in an earlier Vivado version, run
  **Tools → Report → Report IP Status** to see if a version upgrade is offered before
  regenerating output products.

### Code Example

```tcl
# Check IP status and upgrade if available — run in Vivado TCL console
# Useful after updating from e.g. Vivado 2024.x to 2025.1

# Report all IPs that need upgrading
report_ip_status -name ip_status
```

### Relevance to Your Project

If you are building on Vivado 2025.1, pin your `axi_bram_ctrl` and `blk_mem_gen` VLNV strings
explicitly in `create_bd.tcl` to avoid silent version drift between machines. The known IP-update
crash means you should avoid updating IPs mid-session — schedule upgrades as a standalone step
with a project backup beforehand.
