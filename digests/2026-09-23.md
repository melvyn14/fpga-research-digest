# FPGA Research Digest - 2026-09-23

## Executive Summary
- **WSTRB pitfall**: AXI-Lite BRAM writes that ignore the 4-bit WSTRB signal risk corrupting non-targeted bytes; the Xilinx BRAM controller uses WSTRB directly as per-byte write enables (WEA), so your bare-metal `Xil_Out32` must ensure all four strobe bits are set unless doing sub-word writes.
- **BRAM Enable race**: A documented silicon/IP bug in AXI BRAM Controller causes the write-enable to assert one clock early if the BRAM `EN` signal is not tied correctly, writing an extra word to the previous address; verify the `bram_en_a` signal stays low when no transaction is active.
- **Non-project TCL flow** keeps your build fully reproducible: `vivado -mode batch -source build.tcl` is the recommended method for CI/CD and version-controlled rebuilds of the KV260 block design.
- **Vitis 2025 BSP note**: AMD baremetal drivers do NOT auto-initialize the GIC interrupt controller — you must call `XScuGic_Initialize()` and `XScuGic_Connect()` explicitly; forgetting this is the #1 bare-metal bring-up error on A53-based SoMs.
- **Vivado 2025.2** (latest stable as of late 2026) adds `regenerate_bd_layout` TCL command for automating canvas redraw after IP changes, useful when scripting iterative block-design modifications.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings
- AXI handshake law: once VALID is asserted it **must not be de-asserted** until the corresponding READY is seen; violating this causes silent data loss or deadlock, not a bus error.
- WSTRB (write strobes) map 1:1 to byte lanes; setting WSTRB=0 is the protocol-defined way for a master to abort a transaction — slaves must not treat it as a normal write.
- The Xilinx AXI BRAM Controller v4.x passes WSTRB directly to BRAM port A `wea[3:0]`, so sub-word writes from bare-metal C require careful mask construction.
- Documented AXI BRAM Controller bug: write-enable asserts one cycle early when BRAM `EN` is not gated correctly, corrupting the previously-accessed address.
- AXI-Lite does not support burst transfers; every transaction is exactly one beat — appropriate for your BRAM register-map-style access pattern.

### Code Example
```c
/* Safe 32-bit AXI-Lite write to BRAM — all byte strobes asserted */
#define BRAM0_BASE 0xA0000000UL
#define BRAM2_BASE 0xA0010000UL

static inline void bram_write32(u32 base, u32 offset, u32 data)
{
    /* Xil_Out32 issues a single 32-bit store; AXI-Lite sets WSTRB=0xF */
    Xil_Out32(base + offset, data);
    /* Memory barrier: ensure write completes before readback */
    dsb();
}

static inline u32 bram_read32(u32 base, u32 offset)
{
    u32 val = Xil_In32(base + offset);
    dsb();
    return val;
}
```

### Relevance to Your Project
Your `main.c` writes patterns to BRAM0 (0xA0000000) and BRAM2 (0xA0010000) using `Xil_Out32`/`Xil_In32`. Adding explicit `dsb()` (Data Synchronization Barrier) after each AXI-Lite transaction prevents the A53's out-of-order store buffer from making a read appear to succeed before the AXI write has propagated through the interconnect to the BRAM controller.

## Vivado Block Design / IP Integrator

### Key Findings
- **Connection Automation** (`apply_bd_automation`) wires AXI slaves to the Zynq PS master automatically and sets correct clock/reset connections — always run it after adding a new IP.
- **Address Editor** must assign a non-overlapping range to each AXI slave; the default auto-assignment for a second BRAM controller often collides if run without first removing stale assignments.
- `validate_bd_design` propagates parameters between IPs (width negotiation, clock frequency) and must be called before `generate_target` — skipping it causes out-of-date wrapper warnings.
- `regenerate_bd_layout` (added in 2025.2) redraws the canvas without changing connectivity, useful in automated scripts after bulk IP additions.
- IP Output Products must be regenerated (Out-of-Context synthesis) whenever you change an IP parameter; stale OOC netlists cause silent timing-model mismatches.

### Code Example
```tcl
# Minimal block-design snippet: add second BRAM controller and automate
open_bd_design [get_bd_files]

# Add BRAM controller for BRAM2
create_bd_cell -type ip -vlnv xilinx.com:ip:axi_bram_ctrl:4.1 axi_bram_ctrl_1

# Wire to Zynq AXI GP0 master via SmartConnect
apply_bd_automation -rule xilinx.com:bd_rule:axi4 \
    -config {Master "/zynq_ultra_ps_e_0/M_AXI_HPM0_FPD" Clk "Auto"} \
    [get_bd_intf_pins axi_bram_ctrl_1/S_AXI]

# Assign address (must not overlap BRAM0 at 0xA000_0000, size 64K)
set_property offset 0xA0010000 \
    [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_1_Mem0}]
set_property range 64K \
    [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_1_Mem0}]

validate_bd_design
regenerate_bd_layout
save_bd_design
```

### Relevance to Your Project
Your `create_bd.tcl` script sets up both BRAM controllers. If you ever re-run it on an existing project, address segments from the prior run persist and cause the `apply_bd_automation` address assignment to fail silently. Add `delete_bd_objs [get_bd_addr_segs]` before re-applying automation in a rebuild scenario.

## Vivado TCL Scripting

### Key Findings
- **Non-project mode** (`vivado -mode batch -source build.tcl`) keeps no `.xpr` project file on disk — every rebuild starts clean from source, ideal for version-controlled flows.
- Key non-project command sequence: `read_vhdl` → `read_xdc` → `synth_design` → `opt_design` → `place_design` → `route_design` → `write_bitstream -force out.bit`.
- `write_hw_platform -fixed -include_bit` exports the XSA file Vitis needs, including the embedded bitstream.
- `report_timing_summary -warn_on_violation` in the batch script catches timing failures without requiring the GUI; use its exit code in CI.
- Sourcing `create_bd.tcl` inside a non-project flow requires wrapping IP Integrator commands with `open_bd_design` / `close_bd_design` explicitly.

### Code Example
```tcl
#!/usr/bin/env tclsh
# build.tcl — non-project RTL-to-XSA for kv260-axi-bram-demo
set PART "xck26-sfvc784-2LV-c"

read_vhdl -vhdl2008 ../vhdl/kv260_top.vhd
source               ../tcl/create_bd.tcl
read_xdc             ../xdc/kv260_top.xdc

synth_design  -top kv260_top -part $PART -mode out_of_context
opt_design
place_design
route_design

report_timing_summary -warn_on_violation -file timing_summary.rpt
if {[get_property SLACK [get_timing_paths -max_paths 1]] < 0} {
    puts "ERROR: Timing violation detected"
    exit 1
}

write_bitstream -force output/kv260_top.bit
write_hw_platform -fixed -include_bit -output output/kv260_top.xsa
puts "Build complete."
```

### Relevance to Your Project
Converting your current project-mode flow to this non-project script means a single `vivado -mode batch -source build.tcl` command reproducibly rebuilds the BRAM demo from scratch. The timing check before bitstream generation prevents deploying a design with setup-time violations that would manifest as intermittent BRAM read errors.

## Vitis Bare-Metal / Standalone

### Key Findings
- **GIC must be initialized manually** — AMD baremetal drivers (including `xgpiops`, `xuartps`) do not call `XScuGic_Initialize()`; you must do it explicitly before enabling any interrupts.
- The Standalone BSP `xil_printf` is a lightweight formatted print that writes to `stdout` (mapped to UART0 by default in the linker script's `STDOUT` BSP parameter); `printf` from libc is also available but adds ~20KB to code size.
- `lscript.ld` partitions memory into `psu_ddr_0_MEM_0` (DDR, default 2GB), `psu_ocm_ram_0_MEM_0` (OCM, 256KB), and PL-mapped regions; BRAM at 0xA0000000 is accessed via the AXI GP0 window — no special linker entry needed.
- For Kria KV260 in Vitis 2025, create a **Standalone platform** from the exported XSA; the "Classic IDE" and "Unified IDE" flows both work but have different project directory structures.
- BSP parameter `stdin`/`stdout` must point to `psu_uart_1` (the USB-UART on KV260 carrier card) not `psu_uart_0`.

### Code Example
```c
#include "xparameters.h"
#include "xil_printf.h"
#include "xil_io.h"
#include "xil_cache.h"

#define BRAM0_BASE  XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR
#define BRAM2_BASE  XPAR_AXI_BRAM_CTRL_1_S_AXI_BASEADDR
#define TEST_PATTERN 0xDEADBEEFU

int main(void)
{
    Xil_DCacheDisable();   /* simplify: no cache coherency with PL AXI */

    xil_printf("KV260 AXI-BRAM test starting...\r\n");

    /* Write */
    Xil_Out32(BRAM0_BASE, TEST_PATTERN);
    Xil_Out32(BRAM2_BASE, ~TEST_PATTERN);

    /* Read back */
    u32 r0 = Xil_In32(BRAM0_BASE);
    u32 r2 = Xil_In32(BRAM2_BASE);

    xil_printf("BRAM0: %s (got 0x%08X)\r\n",
               r0 == TEST_PATTERN  ? "PASS" : "FAIL", r0);
    xil_printf("BRAM2: %s (got 0x%08X)\r\n",
               r2 == ~TEST_PATTERN ? "PASS" : "FAIL", r2);
    return 0;
}
```

### Relevance to Your Project
Your current `main.c` uses hardcoded base addresses. Switching to `XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR` from `xparameters.h` (auto-generated from the XSA) means address changes in the block design propagate automatically without editing C source. Also: disabling D-cache before bare-metal BRAM tests avoids the most common "writes succeed but reads return stale data" failure mode on Cortex-A53.

## XDC Timing Constraints

### Key Findings
- For AXI-Lite interfaces driven by the PS internal clock (`pl_clk0`), **no `set_input_delay`/`set_output_delay` is needed** — the path is internal to the device; constrain only the clock itself.
- `set_input_delay` / `set_output_delay` are for **package pins** (board-level paths); misapplying them to internal AXI interfaces causes false-path analysis errors and wastes router margin.
- Use `set_clock_groups -asynchronous` to declare independent clock domains (e.g., a free-running PL clock vs. the PS clock); without it, Vivado attempts cross-domain timing analysis that reports impossible violations.
- Virtual clocks (`create_clock -name vclk_ext`) let you reference external interfaces in `set_input_delay` without a physical pin being the source.
- `set_max_delay -datapath_only` disables hold analysis on deliberately asynchronous CDC paths; always pair it with a synchronizer (two-FF) in RTL.

### Code Example
```tcl
# kv260_top.xdc — minimal constraints for KV260 AXI-BRAM demo

# PL clock from PS (100 MHz via pl_clk0)
# The Zynq PS block auto-constrains pl_clk0; just declare the clock group.
create_clock -period 10.000 -name clk_pl_0 [get_ports pl_clk0]

# Isolate the PS and PL clocks from unrelated free-running clocks (if any)
# set_clock_groups -asynchronous \
#     -group [get_clocks clk_pl_0] \
#     -group [get_clocks clk_user]

# I/O delay for a hypothetical external GPIO output (board-level path)
# set_output_delay -clock clk_pl_0 -max 2.0 [get_ports {gpio_out[*]}]
# set_output_delay -clock clk_pl_0 -min -1.0 [get_ports {gpio_out[*]}]

# Disable timing on JTAG-only debug paths
set_false_path -from [get_ports jtag_tdi] -to [get_ports jtag_tdo]
```

### Relevance to Your Project
Your AXI-BRAM demo has no off-chip AXI signals, so timing constraints are minimal. The most important constraint is declaring `pl_clk0` (which Vivado may auto-derive from the Zynq PS block) and ensuring no `set_input_delay` is applied to internal AXI nets — a common mistake when copy-pasting XDC templates.

## Kria KV260 / K26 SoM

### Key Findings
- The K26 SoM connects to the KV260 carrier card via the **SOM240_1 240-pin connector** — PL I/O routes through this connector, so EMIO GPIO paths go: PS GPIO → PL logic → ZynqMP package pin → SOM240 → carrier net → Pmod.
- **USB-UART** on KV260 maps to `psu_uart_1` (MIO 36/37), not UART0; set BSP `stdout`/`stdin` accordingly or `xil_printf` output will be silent.
- Boot mode is set by `MODE[3:0]` on the carrier card; for bare-metal JTAG debug use MODE=0000 (JTAG boot) to prevent the boot ROM from timing out looking for SD/eMMC images.
- The KV260's **secondary boot device** is a Micron QSPI flash; loading bare-metal directly via JTAG bypasses it and is the fastest bring-up path.
- Power domains: PL fabric runs at 0.72V core (VCCINT) supplied by the carrier card; PS MIO bank 501 runs at 1.8V (LVCMOS18) — always set `IOSTANDARD = LVCMOS18` for any MIO-connected I/O in XDC.

### Code Example
```tcl
# XDC snippet for KV260 PMOD GPIO via EMIO
# EMIO GPIO[0] routes through PL to PMOD connector JA pin 1
# Check KV260 board schematic for actual package pin (e.g. H12)
set_property PACKAGE_PIN  H12         [get_ports {emio_gpio_tri_o[0]}]
set_property IOSTANDARD   LVCMOS33    [get_ports {emio_gpio_tri_o[0]}]
# Note: SOM240 I/O bank voltage may be 3.3V on some PMOD rails;
# confirm from KV260 carrier card schematic before setting LVCMOS33.
```

### Relevance to Your Project
For your bare-metal BRAM demo, the most critical KV260-specific detail is the **UART mapping**: if `xil_printf` output is silent on the USB-UART terminal, check that the Vitis BSP `stdout` parameter is `psu_uart_1` and that your terminal is connected to the correct COM port (the KV260 USB-UART appears as the second of the two COM ports exposed by the CP2108 USB-UART bridge).

## AMD/Xilinx Tool Updates (2025.x)

### Key Findings
- **Vivado 2025.2** (latest as of late 2026) highlights: enhanced GEMV & FFT for AI Engine using 2D parallel AIE + PL, vectorized bitonic SIMD sorting, and new `regenerate_bd_layout` TCL command.
- **Vitis 2025.1** DSP Library additions: Cumulative Sum, Euclidean Distance, Function Approximation; Enhanced TDM FIR with Packet Switching; these are HLS library updates, not relevant to bare-metal C but useful context.
- **Vitis 2026.1** (future version per download page listing) — AMD has now moved to a semi-annual release cadence; check `adaptivesupport.amd.com` for 2025.1 known-issues answer records.
- The 2025.x Unified IDE migrated from Eclipse to a VS Code–based shell; if you're on Classic IDE (still shipped), project import and BSP configuration UX differs.
- `write_hw_platform` (replacing the deprecated `write_dsa`) is the correct Vitis 2025 command to export XSA from Vivado.

### Code Example
```tcl
# Vivado 2025.x: export XSA for Vitis after bitstream generation
# Replaces deprecated write_dsa from older flows
write_hw_platform \
    -fixed \
    -include_bit \
    -force \
    -file "output/kv260_axi_bram.xsa"

# Verify the exported file exists
if {![file exists "output/kv260_axi_bram.xsa"]} {
    error "XSA export failed"
}
puts "XSA exported successfully for Vitis import"

# In Vitis 2025 Unified IDE (CLI):
# vitis -s create_platform.py  (Python-based platform creation)
# or via GUI: File > New > Platform Project > browse XSA
```

### Relevance to Your Project
If you upgrade from Vivado/Vitis 2025.1 to 2025.2, re-run `write_hw_platform` to regenerate the XSA — Vitis platforms built against a 2025.1 XSA are not guaranteed to link correctly against 2025.2 BSP libraries. Also verify `XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR` in `xparameters.h` still maps to `0xA0000000` after regeneration.
