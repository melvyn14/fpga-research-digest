## Executive Summary
- **AW/W channel ordering is a real deadlock risk in hand-written AXI-Lite logic**: a master must never be required to wait for AW acceptance before presenting W data — both channels can and do arrive independently, and slave logic that implicitly assumes "AW always lands first" can hang. The stock `axi_bram_ctrl` handles this correctly, but it's the first thing to audit if either BRAM ever gains a hand-rolled control/status register instead of pure passthrough memory.
- **`connect_bd_net` vs `connect_bd_intf_net` is the most common TCL copy-paste error** when hand-maintaining a `create_bd.tcl` like this project's — using the wrong one against an AXI/BRAM_PORT interface produces an "incompatible interface" error, not a silent failure, so it surfaces immediately on `validate_bd_design` rather than at synthesis.
- **`xil_printf` silently drops `%f`** — only `%d`, `%l`, `%x`, `%c`, `%s` are supported. If the PASS/FAIL reporting in `main.c` is ever extended to print timing or throughput numbers, this will need integer/fixed-point formatting, not a float format specifier.
- **Kria SOMs boot from read-only QSPI firmware by design** (anti-brick measure) — JTAG remains the supported fast-iteration boot path for a pure bare-metal app with no PetaLinux image in the loop; direct QSPI reprogramming during active development is the wrong workflow.
- **Vivado 2025.1 introduces a fully customizable RTL-based AXI Switch IP** — not needed for the current single-HPM-master, two-BRAM layout, but the natural IP to reach for if a third AXI-Lite peripheral with a different interface width is ever added alongside BRAM0/BRAM2.

## AXI Protocol / AXI-Lite / AXI-Stream
### Key Findings
- A master is never permitted to wait for `AWREADY` before driving `WVALID`/`WDATA` — the AW and W channels are independent and may be presented in either order or simultaneously; slave logic that internally serializes "wait for AW, then accept W" is a latent deadlock, not just a performance bug.
- Once a channel's VALID is asserted, it must remain asserted until the corresponding READY arrives, and the payload on that channel must not change while waiting — this applies symmetrically to AW, W, AR, and the response channels.
- READY may legally be withheld indefinitely by either side; VALID may never be withheld once a transfer is intended — getting this backwards (gating VALID on the other side's READY) is the single most common cause of AXI deadlocks in hand-written interconnect logic.
- The Xilinx AXI BRAM Controller IP performs the AXI4/AXI4-Lite-to-BRAM-port protocol conversion entirely inside the IP; the BRAM side (BRAM_PORTA/B) is a simple synchronous memory interface with no AXI handshake of its own, which is why pairing it with a Block Memory Generator is "drop-in" rather than requiring custom glue logic.
- For burst-capable AXI4 (not used by this AXI-Lite-only project, but relevant if BRAM0/BRAM2 are ever upgraded to full AXI4 for burst access), `TLAST` must not be asserted on a stalled beat — i.e., if `VALID && !READY` on the would-be last beat, the core must not lock `TLAST` in early, or the receiver ends up with the wrong burst length.

### Code Example
```vhdl
-- AW/W channel independence: do not gate W acceptance on AW having
-- already been accepted in a prior cycle. Both can arrive together.
process(s_axi_aclk)
begin
  if rising_edge(s_axi_aclk) then
    if s_axi_aresetn = '0' then
      aw_latched <= '0';
      w_latched  <= '0';
    else
      -- Latch AW independently of W's arrival time
      if s_axi_awvalid = '1' and aw_latched = '0' then
        aw_addr_r  <= s_axi_awaddr;
        aw_latched <= '1';
      end if;

      -- Latch W independently of AW's arrival time
      if s_axi_wvalid = '1' and w_latched = '0' then
        w_data_r  <= s_axi_wdata;
        w_latched <= '1';
      end if;

      -- Only fire the actual write once BOTH have latched, in whichever
      -- order they arrived
      if aw_latched = '1' and w_latched = '1' then
        -- perform write, then clear both latches
        aw_latched <= '0';
        w_latched  <= '0';
      end if;
    end if;
  end if;
end process;
```

### Relevance to Your Project
Both BRAM0 and BRAM2 sit entirely behind the stock `axi_bram_ctrl`, which already implements this correctly, so the current design isn't exposed. This pattern is the reference to follow if `kv260_top.vhd` ever needs a hand-written AXI-Lite control register (e.g., a "start test" / "test mode select" register) sitting alongside the two BRAM controllers instead of relying purely on the PS writing/reading BRAM directly.

## Vivado Block Design / IP Integrator
### Key Findings
- Connection Automation and Block Automation are distinct: Block Automation configures a freshly-dropped Zynq/Zynq UltraScale+ PS (DDR, FIXED_IO, board preset), while Connection Automation wires a peripheral's AXI interface to an available PS master port and auto-inserts any needed AXI Interconnect/SmartConnect plus a Processor System Reset IP.
- "Check All Automation" when the automation dialog opens ensures every available connection gets made in one pass — running automation per-port one at a time is more error-prone for a two-BRAM design like this one, since it's easy to forget the second instance.
- The Address Editor only becomes active once a bus-master IP (Zynq UltraScale+ PS, MicroBlaze, etc.) is present in the diagram, and its "Auto Assign Address" button is the safe default for non-overlapping ranges — manual edits are validated for alignment immediately, not deferred to synthesis.
- `Tools → Validate Design` (i.e., `validate_bd_design` from script) is the step that actually catches connectivity, AXI4-vs-AXI4-Lite mismatches, and BRAM operating-mode propagation between `axi_bram_ctrl` and its Block Memory Generator — saving the design without validating first is a common way to ship a broken `.bd`.
- A frequent source of address-overlap or "unaligned base" errors when manually adjusting a block design's addresses (rather than relying on Auto Assign): a memory range's base address must have enough trailing zero bits to satisfy its range size, so resizing a range without re-checking its base is the most common cause of Address Editor failures.

### Code Example
```tcl
# Headless validate -> regenerate -> save sequence safe to run right
# before generate_target in a CI/non-interactive build.
open_bd_design [get_files kv260_bd.bd]
validate_bd_design
regenerate_bd_layout
save_bd_design

set crit_warnings [get_msg_config -severity {CRITICAL WARNING} -count]
if {$crit_warnings > 0} {
    puts "ERROR: block design has $crit_warnings unresolved critical warnings"
    exit 1
}
```

### Relevance to Your Project
Since `create_bd.tcl` is hand-maintained rather than a frozen GUI export, the safest pattern is to call `validate_bd_design` immediately after the last `connect_bd_intf_net` for each BRAM controller (not only once at the end of the whole script) so a broken connection on BRAM0 doesn't get masked by a correct one on BRAM2 in the same validation pass.

## Vivado TCL Scripting
### Key Findings
- `connect_bd_net` is for simple single-bit/bus nets (clocks, resets, GPIO); `connect_bd_intf_net` is specifically for bundled interface pins (AXI4, AXI4-Lite, BRAM_PORT) — using the wrong one against an interface pin produces an explicit "incompatible interface" error rather than a silent no-op, so the mistake surfaces immediately rather than at synthesis or simulation time.
- Non-Project Mode keeps the entire design in memory with no `.xpr` on disk; the script is solely responsible for source ordering and there's no Vivado-managed staleness detection, so every run re-reads sources from scratch unless `write_checkpoint`/`read_checkpoint` are added explicitly between stages.
- Standard headless invocation is `vivado -mode batch -source script.tcl -tclargs <args>`, which runs to completion and exits non-interactively; `-mode tcl` opens an interactive console intended only for script development, not CI.
- A fully scripted, non-project build is the only way to guarantee reproducible output across machines, since project settings, IP configuration, and constraints all live in version-controlled text rather than a binary `.xpr`/IP-cache state that can silently drift between checkouts.
- Table-driven `create_bd_cell`/`connect_bd_intf_net` loops over a list of {name, base-address} pairs scale cleanly to N peripherals and centralize address assignment, avoiding the classic copy-paste bug where a second instance's address typo differs only in the low bits from the first (exactly the BRAM0 `0xA0000000` / BRAM2 `0xA0010000` pattern in this project).

### Code Example
```tcl
# Table-driven instantiation for the two AXI BRAM controllers, keeping
# address assignment centralized rather than hand-copied per instance.
foreach {ctrl base} {axi_bram_ctrl_0 0xA0000000 axi_bram_ctrl_2 0xA0010000} {
    create_bd_cell -type ip -vlnv xilinx.com:ip:axi_bram_ctrl:4.1 $ctrl
    set bmg "${ctrl}_bmg"
    create_bd_cell -type ip -vlnv xilinx.com:ip:blk_mem_gen:8.4 $bmg

    connect_bd_intf_net [get_bd_intf_pins zynq_ultra_ps_e_0/M_AXI_HPM0_FPD] \
                         [get_bd_intf_pins ${ctrl}/S_AXI]
    connect_bd_intf_net [get_bd_intf_pins ${ctrl}/BRAM_PORTA] \
                         [get_bd_intf_pins ${bmg}/BRAM_PORTA]
    connect_bd_net [get_bd_pins zynq_ultra_ps_e_0/pl_clk0] \
                    [get_bd_pins ${ctrl}/s_axi_aclk]

    set_property offset $base [get_bd_addr_segs "zynq_ultra_ps_e_0/Data/SEG_${ctrl}_Mem0"]
    validate_bd_design
}

save_bd_design
```

### Relevance to Your Project
This mirrors the documented two-BRAM layout directly. If a third BRAM or AXI-Lite peripheral is ever added, extending the `foreach` table is safer than copy-pasting another `create_bd_cell`/`connect_bd_intf_net` block by hand, and calling `validate_bd_design` inside the loop (rather than only once at the end) catches a bad connection on the new instance before it's masked by the two working ones.

## Vitis Bare-Metal / Standalone
### Key Findings
- `xil_printf` deliberately trades format richness for footprint: it supports `%d`, `%l` (long), `%x`, `%c`, `%s` but has no `%f`/floating-point support at all — a hard constraint if PASS/FAIL reporting is ever extended to print computed metrics rather than just integers and addresses.
- The standalone BSP's stdin/stdout UART instance is a platform-component configuration choice (set in `vitis-comp.json` under the platform's Settings, via `standalone_stdin`/`standalone_stdout`), not auto-detected from the hardware — picking the wrong UART instance relative to the board's actual USB-UART bridge is a common failure mode where the application runs correctly but no PASS/FAIL text ever appears on the terminal.
- Vitis auto-generates a default `lscript.ld` from the hardware platform's memory map; after re-exporting hardware (a new XSA from an updated `create_bd.tcl`) for an existing application, the linker script's region base/size should be re-checked, since a stale region inherited from an older XSA can silently place sections outside valid DDR/OCM without a build error.
- GIC interrupt setup on Cortex-A53/Zynq UltraScale+ standalone BSP is multi-step — `XScuGic_CfgInitialize` → `Xil_ExceptionRegisterHandler` → `XScuGic_Connect` → a separate `XScuGic_Enable(&GicInst, <intr_id>)` call — and omitting the final enable call leaves a correctly registered handler that simply never fires, with no error reported anywhere.
- The standalone BSP is processor-architecture-aware (separate code paths for Cortex-A53/A9/R5/MicroBlaze) but otherwise carrier-card/board-agnostic — bring-up issues on a new KV260 build are far more often a hardware platform (XSA) mismatch than a BSP defect.

### Code Example
```c
#include "xil_printf.h"
#include "xparameters.h"
#include "xil_io.h"

#define BRAM0_BASEADDR XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR /* 0xA0000000 */
#define BRAM2_BASEADDR XPAR_AXI_BRAM_CTRL_1_S_AXI_BASEADDR /* 0xA0010000 */

int test_bram_word(u32 base, u32 offset, const char *name) {
    u32 pattern = 0xDEADBEEF;
    Xil_Out32(base + offset, pattern);
    u32 readback = Xil_In32(base + offset);
    if (readback != pattern) {
        /* %f is NOT supported by xil_printf - integers/hex only */
        xil_printf("%s @0x%x: FAIL (wrote 0x%x, read 0x%x)\r\n",
                   name, offset, pattern, readback);
        return 1;
    }
    xil_printf("%s @0x%x: PASS\r\n", name, offset);
    return 0;
}
```

### Relevance to Your Project
This mirrors the write/readback/PASS-FAIL idiom described for `main.c`. If output ever silently stops appearing over USB-UART, check the BSP's stdout UART selection in the platform component first, and re-verify `lscript.ld` after any hardware re-export — both are far more common causes than an actual AXI/BRAM hardware fault.

## XDC Timing Constraints
### Key Findings
- `set_input_delay`/`set_output_delay` model the external device's clock-to-out/setup delay as observed at the FPGA pin relative to a reference clock edge — the value is the driving/receiving device's own timing, not the FPGA's internal setup requirement, and it can legitimately be negative depending on data/clock phase relationship; porting a datasheet number directly into XDC syntax without checking polarity is a frequent source of confusing timing reports.
- Every clock-domain crossing needs an explicit `set_clock_groups -asynchronous` declaration (or an equivalent `set_max_delay`/`set_false_path`); left undeclared, Vivado analyzes the crossing as if synchronous, which can either produce spurious failing paths or a false "pass" on a path that's actually a metastability risk.
- `set_max_delay -datapath_only` is now generally preferred over a blanket `set_false_path` for genuine CDC paths: a plain false path disables ALL timing analysis on that path including hold checks, while `-datapath_only` only relaxes the setup relationship while still bounding propagation delay — typically paired with `ASYNC_REG` on the destination register pair to force adjacent placement.
- For Zynq/Zynq UltraScale+ designs, the PS-generated fabric clock can be constrained directly from the PS clock pin, e.g. `create_clock -period 10.000 -name clk_fpga_0 [get_pins {zynq_ultra_ps_e_0/pl_clk0}]` — useful whenever custom logic is added downstream of the PS that Vivado's automatic clock propagation from the block design doesn't already cover on its own.

### Code Example
```tcl
# Board-level XDC additions only relevant once direct PL I/O exists
# (not required for the current pure PS<->PL AXI-only BRAM path).
create_clock -period 8.000 -name pl_clk0 [get_ports pl_clk0_p]

set_input_delay  -clock pl_clk0 -max 1.5 [get_ports {ext_data[*]}]
set_input_delay  -clock pl_clk0 -min 0.3 [get_ports {ext_data[*]}]
set_output_delay -clock pl_clk0 -max 1.2 [get_ports {ext_ctrl[*]}]
set_output_delay -clock pl_clk0 -min -0.5 [get_ports {ext_ctrl[*]}]

# Prefer -datapath_only over a blanket false path for genuine CDC.
set_max_delay -datapath_only -from [get_clocks clk_fpga_0] -to [get_clocks pl_clk0] 4.0
```

### Relevance to Your Project
The design is purely PS-driven AXI on a single PS-generated FCLK domain feeding both BRAM controllers through `kv260_top.vhd`, so none of the board-level I/O delay constraints apply today — they only matter once a signal crosses the board boundary through a physical pin. The CDC guidance becomes directly relevant the moment a PL-side clock independent of the PS FCLK (a free-running oscillator, an MMCM-derived clock for new logic) is introduced.

## Kria KV260 / K26 SoM
### Key Findings
- The K26 SOM supports JTAG, SD, and QSPI boot modes, selected by MODE[3:0] strapping pins exposed at the SOM connector; Kria Starter Kits ship with boot firmware pre-loaded in QSPI and a default QSPI32 boot mode configuration.
- Kria SOMs deliberately boot from read-only QSPI firmware as an anti-brick measure — for a bare-metal-only workflow with no PetaLinux/Linux image in the loop, JTAG remains the supported fast-iteration development path, not direct reprogramming of the QSPI boot image.
- K26/K24 SOM support in Vivado is delivered through official board files that automate board-peripheral configuration (DDR, FIXED_IO, board presets) when Block Automation is run on a freshly added Zynq UltraScale+ PS — these board files are the recommended starting point over hand-configuring every PS parameter from scratch.
- On the KV260 carrier specifically, most peripherals connect through the PS via MIO/EMIO as usual; this differs from the related KR260 carrier, where the PMOD and Raspberry Pi headers connect directly into K26 PL fabric rather than through MIO/EMIO — relevant only if this project or a variant ever targets KR260 instead.
- Since the 2022.1 Kria Linux images, the default "k26-starter-kits" shipped bitstream has essentially no functional PL logic beyond an EMIO mapping for carrier-board fan control — meaning a from-scratch bare-metal/PL design like this one genuinely starts from near-empty fabric rather than inheriting hidden logic from any shipped default image.

### Code Example
```tcl
# PS configuration matching a single-HPM-master, two-BRAM pattern;
# explicitly disabling the unused second GP master avoids a common
# validate_bd_design critical-warning source (enabled-but-unconnected port).
set_property -dict [list \
    CONFIG.PSU__USE__M_AXI_GP0 {1} \
    CONFIG.PSU__USE__M_AXI_GP1 {0} \
    CONFIG.PSU__MAXIGP0__DATA_WIDTH {32} \
] [get_bd_cells zynq_ultra_ps_e_0]
```

### Relevance to Your Project
Both BRAM0 and BRAM2 feeding off a single HPM master matches the official Kria baremetal AXI-BRAM reference pattern closely. Worth confirming in `create_bd.tcl` that any unused second HPM master is explicitly disabled rather than left merely unconnected (a common source of stray `validate_bd_design` warnings), and worth confirming JTAG is the boot mode used during active iteration rather than QSPI, given the read-only-firmware lockdown on Kria SOMs.

## AMD/Xilinx Tool Updates
### Key Findings
- Vivado 2025.1 adds a fully customizable RTL-based AXI Switch IP that bridges between different AXI interface types and widths — not needed for the current single-HPM-master BRAM0/BRAM2 layout, but the natural choice if a future revision needs to mix AXI4-Full and AXI4-Lite peripherals on the same interconnect without going through a generic AXI Interconnect/SmartConnect.
- Vivado 2025.1 also adds the ability to boot the processing system first and dynamically load the PL afterward, enabling faster OS bring-up with more flexible boot sequencing — primarily aimed at Linux-based flows, not directly relevant to this pure bare-metal app, but a platform capability worth being aware of on this toolchain version.
- A new Pblock planner in Vivado 2025.1 acts as a one-stop interface for creating and managing placement Pblocks — not currently needed for a design this small, but relevant if floorplanning becomes necessary as the design grows.
- Looking ahead: Vivado 2025.2 changes the AMD IP configuration file format from XML to JSON (better revision-control diffing, faster loading) and Vitis 2025.2 makes the Unified IDE the default while deprecating Classic Vitis IDE — this project is pinned to 2025.1 with Classic IDE still available, but any future toolchain bump should budget time for the BSP/platform-configuration workflow changing shape.
- The AXI BRAM Controller IP (PG078) underlying both BRAM0 and BRAM2 supports optional ECC in single- and dual-port configurations (`C_ECC = 1`) — not needed today, but a known lever if BRAM data-integrity becomes a concern as test patterns or data volume scale up.

### Relevance to Your Project
2025.1 remains current and stable for this design — none of the 2025.1 IP-level changes touch `axi_bram_ctrl` or the Zynq UltraScale+ PS block directly. If/when the toolchain is bumped to 2025.2+, re-run `validate_bd_design` after the first open of the block design on the new version (IP re-customization prompts on cross-version bumps are routine), and budget extra time for the Vitis workflow if migrating away from Classic IDE.
