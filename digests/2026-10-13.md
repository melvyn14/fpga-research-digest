## Executive Summary

- **AXI handshake deadlock risk:** VALID must stay asserted until READY completes the handshake.
  The PS AXI master can stall if the BRAM controller deasserts RREADY before data is consumed.
  Insert a Vivado AXI Protocol Checker IP during simulation to catch violations early.
- **Vivado 2025.1 new IP Integrator views:** Two dedicated panes (clocking/reset and
  interrupts/AXI-Lite) were added in Vivado 2025.1, streamlining the block design flow used by
  create_bd.tcl.
- **New RTL-based AXI Switch IP in 2025.1:** Replaces older AXI Interconnect for bridging AXI
  widths/types; worth evaluating for connecting additional PL peripherals alongside the two BRAMs.
- **Non-project TCL:** `synth_design` must run *after* `link_design` and *after* all `read_xdc`
  calls in non-project mode. Getting this order wrong in create_bd.tcl batch flows silently skips
  constraints.
- **KV260 boot is QSPI-fixed:** No boot mode switches. Standalone bare-metal apps must target the
  correct memory region (typically OCM or DDR) in the Vitis linker script — the auto-generated
  lscript.ld may place sections in the wrong region.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- **VALID must stay stable:** Per the AXI spec, once a source asserts VALID it must not deassert
  it until the handshake occurs. Violating this can cause silent deadlocks; synthesis does not
  flag it.
- **RREADY is not guaranteed:** The ZipCPU analysis of Vivado's auto-generated AXI-Lite slave
  (2018.3) showed it failed formal verification because it assumed RREADY is always high. The PS
  master on the Zynq UltraScale+ does hold RREADY high by default, but custom slaves must not
  rely on this.
- **Use AXI Register Slice for long paths:** The AXI Register Slice IP (available in the IP
  Catalog) adds exactly one clock cycle of latency and breaks long combinational paths that span
  from PS to PL BRAM, improving timing closure without changing protocol behavior.
- **AXI-Stream TREADY/TVALID:** When daisy-chaining stream blocks (e.g., future DMA additions),
  back-pressure via TREADY must be handled; failing to do so causes FIFO overflow rather than a
  visible protocol error.
- **Protocol checker during simulation:** Insert the Xilinx AXI Protocol Checker IP (or the
  open-source VHDL equivalent) at the AXI-Lite port of each BRAM controller to catch violations
  in behavioral simulation before synthesis.

### Code Example

```vhdl
-- AXI-Lite read handshake: RVALID must stay high until RREADY
-- Add this pattern in kv260_top.vhd if implementing a custom slave
process(clk)
begin
  if rising_edge(clk) then
    if rst_n = '0' then
      s_axi_rvalid <= '0';
      s_axi_rdata  <= (others => '0');
    else
      -- Latch read data on AR handshake
      if s_axi_arvalid = '1' and s_axi_arready = '1' then
        s_axi_rdata  <= bram_rdata;  -- data from BRAM read port
        s_axi_rvalid <= '1';
      -- Hold RVALID until master acknowledges with RREADY
      elsif s_axi_rvalid = '1' and s_axi_rready = '1' then
        s_axi_rvalid <= '0';
      end if;
    end if;
  end if;
end process;
```

### Relevance to Your Project

Your design connects the PS Cortex-A53 master to two Block Memory Generator cores at
`0xA0000000` (BRAM0) and `0xA0010000` (BRAM2) via an AXI-Lite slave interface. The hand-made
RVALID hold pattern above is exactly what the auto-generated AXI BRAM Controller implements
internally — understanding it helps when debugging unexpected read-back failures in main.c's
PASS/FAIL loop. If reads return wrong data, add an ILA probe on the AXI R channel to verify
RVALID/RREADY timing.

## Vivado Block Design / IP Integrator

### Key Findings

- **2025.1 dedicated panes:** IP Integrator gained two new views: one for clocking/reset
  connectivity and one for interrupts and AXI-Lite connections. These simplify the previously
  manual wiring of `axi_bram_ctrl` reset and clock ports.
- **New RTL-based AXI Switch IP:** Replaces the older AXI Interconnect fabric for routing AXI
  transactions. For a design expanding beyond two BRAMs, the AXI Switch is lighter-weight than a
  full SmartConnect.
- **Address Editor must be correct before synthesis:** The two BRAM controllers need addresses
  `0xA0000000` and `0xA0010000` locked in the Address Editor (or via TCL `assign_bd_address`
  calls) before running `generate_target`. A re-generate without re-validating the address map
  can silently shift addresses.
- **`upgrade_ip -all` footgun:** The `upgrade_ip [get_ips -all]` call returns sub-core IPs
  (internal to parent IPs), which can be removed when the parent is upgraded, leaving dangling Tcl
  object references. Upgrade only top-level IPs.
- **HDL wrapper regeneration:** After any IP parameter change, re-run
  `make_wrapper -files [get_files *.bd] -top` and delete the old wrapper before synthesis. The
  wrapper caches port widths.

### Code Example

```tcl
# Assign addresses for both BRAM controllers in create_bd.tcl
# (equivalent to what the Address Editor GUI does)
assign_bd_address [get_bd_addr_segs {axi_bram_ctrl_0/S_AXI/Mem0}]
set_property offset 0xA0000000 [get_bd_addr_segs \
  {processing_system7_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property range 8K [get_bd_addr_segs \
  {processing_system7_0/Data/SEG_axi_bram_ctrl_0_Mem0}]

assign_bd_address [get_bd_addr_segs {axi_bram_ctrl_1/S_AXI/Mem0}]
set_property offset 0xA0010000 [get_bd_addr_segs \
  {processing_system7_0/Data/SEG_axi_bram_ctrl_1_Mem0}]
set_property range 8K [get_bd_addr_segs \
  {processing_system7_0/Data/SEG_axi_bram_ctrl_1_Mem0}]
```

### Relevance to Your Project

The `create_bd.tcl` script in your repo recreates the block design programmatically. The address
assignments above correspond to the `0xA0000000` / `0xA0010000` addresses your main.c writes to.
If you ever see the PS reading all-zeros from one BRAM but not the other, confirm these offsets
match what Vivado's Address Editor shows after re-running the TCL. The 2025.1 clocking/reset pane
can also flag missing ARESETN wiring that used to be a silent mismatch.

## Vivado TCL Scripting

### Key Findings

- **Non-project mode ordering is strict:** In non-project batch mode, the sequence is:
  `read_vhdl` / `read_xdc` → `link_design` → `synth_design` → `opt_design` → `place_design`
  → `route_design` → `write_bitstream`. Putting `read_xdc` after `synth_design` means
  constraints attach to the wrong netlist objects.
- **No `create_project` in non-project mode:** Use `read_vhdl`, `read_bd`, and `read_xdc` to
  load sources. Project-mode commands like `add_files` and `launch_runs` are unavailable.
- **`write_checkpoint` is your save point:** At each stage after implementation commands, emit a
  checkpoint (`write_checkpoint -force out.dcp`). On failure you can resume from the last good
  checkpoint with `open_checkpoint`.
- **Mixing modes is a risk:** `synth_design` must not be called inside a Project Mode flow
  (i.e., a script that started with `create_project`). It prevents the project database from
  updating and blocks automatic report generation.
- **UG896 scripting examples (2025.2):** The examples section now covers IP parameter propagation
  in scripted flows — relevant for setting BRAM controller data width and depth from TCL.

### Code Example

```tcl
# Non-project batch build for the KV260 AXI-BRAM design
set_part xck26-sfvc784-2LV-c

read_vhdl ../vhdl/kv260_top.vhd
read_bd   ../bd/design_1.bd

# Constraints MUST come before synth_design, after link_design
read_xdc  ../xdc/kv260_top.xdc

link_design -part xck26-sfvc784-2LV-c -top kv260_top

synth_design -top kv260_top -part xck26-sfvc784-2LV-c
write_checkpoint -force post_synth.dcp

opt_design
place_design
phys_opt_design
route_design
write_checkpoint -force post_route.dcp

write_bitstream -force kv260_top.bit
write_hw_platform -fixed -force kv260_top.xsa
```

### Relevance to Your Project

Your `create_bd.tcl` runs inside Vivado to build the block design. If you want a fully scriptable
CI pipeline (build bitstream and XSA without the GUI), the non-project pattern above is the
standard approach. The `write_hw_platform -fixed` at the end generates the XSA that Vitis needs
to create the bare-metal BSP for main.c.

## Vitis Bare-Metal / Standalone

### Key Findings

- **xil_printf is lightweight printf:** The standalone BSP includes `xil_printf`, a stripped-down
  printf that targets the configured UART. It does not support float formatting — use `printf`
  from the standard libc (slower, larger binary) if you need `%f`.
- **Auto-generated lscript.ld may be wrong:** On Zynq designs, the Vitis linker script generator
  can place all sections in the wrong memory region. For a bare-metal KV260 app, verify that
  `.text`, `.data`, and `.bss` are in DDR (`0x00000000`) not OCM (`0xFFFC0000`). Heap and stack
  defaults are very small; start with 1 MB heap (`0x100000`) for safety.
- **BSP regeneration nuance:** Rebuilding the BSP after an XSA change regenerates `xparameters.h`
  with updated base addresses. If `XPAR_AXI_BRAM_CTRL_0_BASEADDR` changes, main.c must match.
- **2025.1 UG1076 covers AArch64 bare-metal linking:** The guide shows linking with
  `-Wl,--start-group,-lxil,-lgcc,-lc,--end-group`. The `-lxil` provides xil_printf and other BSP
  routines.
- **Interrupt controller:** For a standalone design that later needs interrupts (e.g., DMA
  completion), use `XScuGic` (GIC-400) rather than `XIntc` (which targets MicroBlaze).

### Code Example

```c
/* Robust BRAM write-readback pattern for main.c                       */
/* Uses xparameters.h addresses; regenerate BSP after any XSA change.  */
#include "xil_io.h"
#include "xil_printf.h"
#include "xparameters.h"

#define BRAM0_BASE  XPAR_AXI_BRAM_CTRL_0_BASEADDR   /* 0xA0000000 */
#define BRAM2_BASE  XPAR_AXI_BRAM_CTRL_1_BASEADDR   /* 0xA0010000 */
#define TEST_WORDS  16

int main(void) {
    int pass = 1;

    /* Write phase */
    for (int i = 0; i < TEST_WORDS; i++) {
        Xil_Out32(BRAM0_BASE + (i * 4), 0xDEAD0000 | i);
        Xil_Out32(BRAM2_BASE + (i * 4), 0xBEEF0000 | i);
    }

    /* Data memory barrier before readback */
    dmb();

    /* Readback phase */
    for (int i = 0; i < TEST_WORDS; i++) {
        u32 r0 = Xil_In32(BRAM0_BASE + (i * 4));
        u32 r2 = Xil_In32(BRAM2_BASE + (i * 4));
        if (r0 != (0xDEAD0000 | i)) { pass = 0; xil_printf("BRAM0[%d] FAIL: 0x%08X\r\n", i, r0); }
        if (r2 != (0xBEEF0000 | i)) { pass = 0; xil_printf("BRAM2[%d] FAIL: 0x%08X\r\n", i, r2); }
    }

    xil_printf(pass ? "ALL PASS\r\n" : "FAIL\r\n");
    while(1);
    return 0;
}
```

### Relevance to Your Project

Your main.c already implements this pattern. Key hardening suggestions: (1) add `dmb()` between
the write and readback loops to flush the AXI write buffer on the A53; (2) use
`XPAR_AXI_BRAM_CTRL_*_BASEADDR` constants from xparameters.h rather than hardcoded addresses so
an accidental address shift in the block design is caught at compile time rather than at runtime.

## XDC Timing Constraints

### Key Findings

- **`set_input_delay` / `set_output_delay` units are nanoseconds:** Values can be positive or
  negative depending on clock-to-data skew outside the device.
- **Always specify a clock:** Both commands require `-clock <clock_name>`. On Kria, use the PL
  fabric clock (`clk_pl_0`) from the PS block as the reference.
- **`-max` and `-min` for setup/hold:** Specify both max and min values; if only one is given,
  Vivado applies the same value for both setup and hold analysis, which can give overoptimistic
  hold results.
- **Synthesis is affected:** `set_input_delay` and `set_output_delay` affect not just timing
  analysis but synthesis register placement, so XDC must be sourced before `synth_design` in
  non-project flows.
- **For pure PS-to-PL paths (AXI only):** If your design has no board-level I/O (all signals stay
  in-package), you do not need `set_input_delay` / `set_output_delay`. The PS-PL AXI interface
  is constrained automatically by the Zynq device model. The main constraint needed is
  `create_clock` for any user-defined clocks, and possibly `set_clock_groups -asynchronous`
  if multiple clock domains are present.
- **UltraFast Design Methodology (UG949):** The AMD reference for I/O timing methodology on
  UltraScale+ devices. Pairs with UG903 (Using Constraints) for complete guidance.

### Code Example

```tcl
# kv260_top.xdc - Timing constraints for KV260 AXI-BRAM demo
# PL fabric clock (100 MHz from PS) — auto-created by Zynq block,
# but redeclare here to ensure synthesis sees it:
create_clock -period 10.000 -name clk_pl_0 [get_ports clk_pl_0]

# For a pure PS-PL AXI design with no external I/O,
# set_input_delay / set_output_delay are not required.

# If you add external GPIO or PMOD pins later:
# set_input_delay  -clock clk_pl_0 -max 2.0 [get_ports {gpio_in[*]}]
# set_input_delay  -clock clk_pl_0 -min 0.5 [get_ports {gpio_in[*]}]
# set_output_delay -clock clk_pl_0 -max 1.5 [get_ports {gpio_out[*]}]
# set_output_delay -clock clk_pl_0 -min 0.0 [get_ports {gpio_out[*]}]

# Prevent false paths between PS clock domains if using CDC:
# set_clock_groups -asynchronous \
#   -group [get_clocks clk_pl_0] \
#   -group [get_clocks clk_pl_1]
```

### Relevance to Your Project

Your current design routes all connectivity through the PS AXI interface with no external I/O
pins in the PL. You likely only need `create_clock` for the PL fabric clock; the AXI-BRAM paths
are automatically constrained by the IP. This XDC template doubles as a starting point when you
add board-level I/O (LEDs, buttons, PMOD) to kv260_top.vhd.

## Kria KV260 / K26 SoM

### Key Findings

- **Boot mode is QSPI-fixed:** There are no boot mode switches on Kria SOM boards. Boot is
  hard-wired to QSPI flash. Bare-metal standalone apps loaded via Vitis debugger (JTAG) bypass
  the boot ROM and run from JTAG download, so this doesn't affect your debug workflow, but it
  matters for standalone flash deployment.
- **Console UART is UART1:** Kria SOMs route the PS console to UART1 (not UART0). In Vitis BSP
  settings, ensure `stdin`/`stdout` are set to `psu_uart_1` (MIO36/37 on the K26, routed through
  the onboard FTDI USB-to-UART bridge to the USB-UART port on the KV260 carrier card).
- **MIO vs EMIO:** The K26 SOM exposes PS MIO signals on two 240-pin connectors to the carrier
  card. The KV260 carrier routes select MIO signals to headers and the USB-UART bridge. EMIO
  signals cross the PS-PL boundary and are available in the PL fabric — not used in your current
  design but relevant for adding GPIO to kv260_top.vhd.
- **Power domains:** The K26 has multiple power domains (PS, PL, BATT). PL fabric power must be
  enabled before accessing BRAM through the AXI interface. In bare-metal, this is handled by the
  FSBL/PMUFW; when loading via JTAG, Vitis initializes the PL.
- **2025.2 bare-metal KV260 project (Hackster):** A 2025.2-era bare-metal streaming demo on the
  KV260 confirms the Cortex-A53 bare-metal approach and uses `write_hw_platform` to export XSA,
  matching your flow.

### Code Example

```tcl
# In create_bd.tcl: configure UART1 in the Zynq UltraScale+ PS block
# (psu_cortexa53_0 or zynq_ultra_ps_e_0)
set_property -dict [list \
  CONFIG.PSU__UART1__PERIPHERAL__ENABLE {1} \
  CONFIG.PSU__UART1__PERIPHERAL__IO    {MIO 36 .. 37} \
  CONFIG.PSU__UART1__BAUDRATE          {115200} \
] [get_bd_cells zynq_ultra_ps_e_0]
```

### Relevance to Your Project

If your USB-UART terminal shows nothing after loading the bare-metal app, the most common cause
on the KV260 is that the BSP was built with `stdout = psu_uart_0` while the carrier card only
connects `psu_uart_1` to the USB-UART bridge. Confirm in Vitis BSP settings and
`create_bd.tcl` that UART1 on MIO 36..37 is enabled and selected.

## AMD/Xilinx Tool Updates (Vivado/Vitis 2025.x)

### Key Findings

- **Vivado 2025.1 key additions:**
  - **New RTL-based AXI Switch IP:** Replaces the AXI Interconnect for bridging AXI types and
    widths. Lighter-weight than SmartConnect for simple topologies.
  - **Two new IP Integrator dedicated views:** One for clocking/reset routing and one for
    interrupts and AXI-Lite connections. Reduces manual wiring errors in complex block designs.
  - **New device support:** Versal AI Edge Gen 2, Versal Prime Gen 2, and Spartan UltraScale+
    families added.
  - **Installer granularity:** Individual Versal device selection reduces download size.
- **Vitis AI 5.1 (uses Vivado/Vitis 2025.1.1):** Multiple NPU instances, mixed precision,
  Apptainer as Docker alternative. Not directly relevant to bare-metal BRAM work.
- **Open-source components (2025.1):** Linux kernel bumped to 6.12; Zephyr early-access support
  added for several AMD platforms.
- **Vitis 2025.2 now available:** Vitis Software Platform 2025.2 release highlights were posted
  on AMD's product page. Check the AMD release notes for embedded-specific changes.
- **UG896 Scripting Examples updated to 2025.2:** The scripting examples section (relevant to
  your create_bd.tcl) was refreshed for the 2025.2 cycle.

### Code Example

```tcl
# Vivado 2025.1: Use the new dedicated IP Integrator automation
# after create_bd.tcl assembles the design

write_hw_platform -fixed -force ./kv260_top.xsa
```

### Relevance to Your Project

The two new IP Integrator views in 2025.1 are directly useful when extending your block design.
The clocking/reset view will flag if `ARESETN` of either BRAM controller is floating — a common
silent bug that can cause the BRAM to stay in reset while the AXI bus is active, producing
all-zero readbacks in main.c without any bus error. The new AXI Switch IP is worth benchmarking
if you add a third AXI slave (e.g., a custom PL register bank) to the design.
