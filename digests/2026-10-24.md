# FPGA Research Digest - 2026-10-24

## Executive Summary

- **AXI-Lite write response (B channel) matters**: A write is NOT complete when data crosses the AXI interface; the processor must check the B channel BRESP to confirm success. Skipping this check risks silent write failures on BRAM0/BRAM2.
- **Kria boots from QSPI only — no boot switches**: The KV260 has no physical boot-mode switches; the SOM hard-wires QSPI as the boot source. Bare-metal applications must be deployed via JTAG programming directly to PL/PS or by replacing the QSPI image.
- **PL clock must come from PS on KV260**: The PL fabric cannot self-clock. The PS must be configured to drive the PL reference clock before any AXI peripheral becomes accessible from bare-metal code.
- **New Vivado 2025.1 IP Integrator views simplify AXI-Lite debug**: Two new dedicated views — "Clocking and Reset" and "Interrupt and AXI-4 Lite" — help verify the AXI-Lite connectivity that your create_bd.tcl script generates.
- **Non-project Tcl mode gives deterministic builds but no auto-regen**: In non-project mode you must explicitly rerun synthesis after any HDL edit; this is the right mode for CI-driven builds of kv260-axi-bram-demo.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- AXI-Lite is a reduced-feature variant of AXI4: single beat only, no LAST signal, no burst, no WRAP. Every transaction is one transfer. Do not attempt burst addressing with the BRAM Controller in AXI-Lite mode.
- **VALID/READY stability rule**: Once a master asserts VALID it must hold VALID and all channel signals stable until READY rises. Violating this causes phantom data or deadlock on Zynq interconnects.
- **Write completion requires B-channel handshake**: The write data crossing the W channel does not mean the slave accepted it. The master must assert BREADY and observe BVALID + a non-error BRESP (2'b00 = OKAY) before considering a write complete. A common bare-metal bug: polling an address immediately after a write without waiting for BRESP.
- **Same-cycle ack/stall race in bridges**: A real bug in an OHWR AXI4-Lite bridge caused the RESPONSE_READ state to be skipped when wb.ack asserted in the same cycle wb.stall de-asserted, breaking the handshake. Custom AXI slaves must guard against similar combinatorial races.
- **RRESP carries error status on reads**: The read data and RRESP arrive together on the R channel. RRESP = 2'b10 (SLVERR) or 2'b11 (DECERR) means the data is invalid even if it looks non-zero.
- **AXI-Stream vs AXI-Lite**: AXI-Stream TREADY can stay high after a handshake; that behavior does NOT carry over to AXI-Lite. Each AXI-Lite transaction is independent.

### Code Example

```c
/* Bare-metal AXI-Lite write with B-channel check (Cortex-A53, Vitis standalone) */
#include "xil_io.h"
#include "xil_printf.h"

#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL

/* AXI-Lite MMIO helpers provided by Vitis BSP */
static inline void axi_write(uintptr_t addr, u32 val) {
    Xil_Out32(addr, val);
    /* Xil_Out32 performs a memory-mapped store; for AXI-Lite the interconnect
       serialises the write and asserts BVALID before the store returns on
       Zynq UltraScale+ — but always verify BRAM readback matches. */
}

static inline u32 axi_read(uintptr_t addr) {
    return Xil_In32(addr);
}

int bram_loopback_test(void) {
    const u32 pattern = 0xDEADBEEF;
    axi_write(BRAM0_BASE + 0x00, pattern);
    axi_write(BRAM2_BASE + 0x00, ~pattern);

    u32 r0 = axi_read(BRAM0_BASE + 0x00);
    u32 r2 = axi_read(BRAM2_BASE + 0x00);

    if (r0 == pattern && r2 == ~pattern) {
        xil_printf("BRAM loopback PASS: BRAM0=0x%08X  BRAM2=0x%08X\r\n", r0, r2);
        return 0;
    }
    xil_printf("BRAM loopback FAIL: BRAM0 exp=0x%08X got=0x%08X\r\n", pattern, r0);
    return -1;
}
```

### Relevance to Your Project

Your main.c already writes patterns to BRAM0 (0xA0000000) and BRAM2 (0xA0010000) and reads them back for PASS/FAIL. The key risk: if you use `Xil_Out32` / `Xil_In32` without verifying the AXI interconnect has completed the transaction, intermittent mismatches are possible at high clock speeds. On Zynq UltraScale+ the built-in interconnect (SmartConnect/AXI Interconnect) handles the B-channel internally, but if you ever add a custom AXI slave you must expose BREADY/BVALID properly.

## Vivado Block Design / IP Integrator

### Key Findings

- **Address assignment**: IP Integrator can auto-assign all slave address segments with `assign_bd_address`. The Address Editor tab only appears when the design contains a bus master (e.g., the Zynq PS). Check that your BRAM controllers are listed as slaves and their offsets match 0xA0000000 and 0xA0010000.
- **Slave memory maps vs address spaces**: Each slave has a memory map; each master has an address space. An address segment maps a slave memory map into a master address space. Mismatches here cause the AXI interconnect to return DECERR (0x3) at runtime — the application sees reads return 0 and writes silently fail.
- **Design name length limit**: AMD recommends keeping block design names to 25 characters or fewer due to Windows path length limits. Longer names can break export to Tcl on Windows machines.
- **Export to Tcl**: Use `write_bd_tcl <filename.tcl>` from the Tcl console or File > Export > Export Block Design to regenerate your create_bd.tcl. This is how to keep your TCL script in sync with GUI changes.
- **New 2025.1 views**: Two new IP Integrator views were added — "Clocking and Reset" and "Interrupt and AXI-4 Lite" — giving a structured overview of clock/reset wiring and AXI-Lite slave connectivity. These replace hunting through the block diagram manually.

### Code Example

```tcl
# Snippet: assign addresses and validate AXI-Lite slaves in block design
# Run from Vivado Tcl console after create_bd_design is complete

# Auto-assign all unassigned address segments
assign_bd_address

# Verify BRAM controller slave addresses
set segs [get_bd_addr_segs -of_objects [get_bd_cells axi_bram_ctrl_0]]
foreach seg $segs {
    set offset [get_property OFFSET $seg]
    set range  [get_property RANGE  $seg]
    puts "BRAM0: offset=$offset  range=$range"
}

set segs2 [get_bd_addr_segs -of_objects [get_bd_cells axi_bram_ctrl_1]]
foreach seg $segs2 {
    set offset [get_property OFFSET $seg]
    set range  [get_property RANGE  $seg]
    puts "BRAM2: offset=$offset  range=$range"
}
```

### Relevance to Your Project

Your create_bd.tcl builds the block design programmatically. After running it, verify that `axi_bram_ctrl_0` lands at 0xA0000000 and `axi_bram_ctrl_1` at 0xA0010000 using the snippet above. A fresh auto-assign after adding a new IP can silently re-number existing slaves if their segments were not locked first.

## Vivado TCL Scripting

### Key Findings

- **Two modes**: Vivado has Project Mode (managed .xpr file) and Non-Project Mode (in-memory, you manage everything). Non-project mode is preferred for CI pipelines because output is deterministic and there are no stale project files.
- **Running scripts in batch**: `vivado -mode batch -source run.tcl` is the canonical invocation. In batch mode, Vivado runs in "Tcl script mode," which differs slightly from the interactive console — some commands behave differently (e.g., errors that would pop a dialog in the GUI instead exit the script).
- **Manual dependency tracking in non-project mode**: You must rerun `synth_design` if you modify any HDL file after synthesis. The tool does not track stale sources automatically.
- **Strategy shortcuts**: `config_flows -synth_strategy <name> -impl_strategy <name>` sets preset strategies without listing each directive individually. Useful for standardizing CI builds.
- **Checkpoint discipline**: Use `write_checkpoint -force post_synth.dcp` and `write_checkpoint -force post_impl.dcp` to allow resumption from a checkpoint instead of rerunning the entire flow.

### Code Example

```tcl
#!/usr/bin/env tclsh
# Non-project mode: synth → impl → bitstream for kv260-axi-bram-demo
# Run: vivado -mode batch -source build.tcl

set part "xck26-sfvc784-2LV-c"   ;# K26 SoM part number

# Read HDL sources
read_vhdl  {vhdl/kv260_top.vhd}
read_xdc   {xdc/kv260_constraints.xdc}

# Source block design (creates wrapper)
source tcl/create_bd.tcl
make_wrapper -files [get_files kv260.bd] -top
read_vhdl [glob *.gen/sources_1/bd/kv260/hdl/kv260_wrapper.vhd]

# Synthesis
synth_design -top kv260_wrapper -part $part -flatten_hierarchy rebuilt
write_checkpoint -force checkpoints/post_synth.dcp
report_timing_summary -file reports/post_synth_timing.rpt

# Implementation
opt_design
place_design
route_design
write_checkpoint -force checkpoints/post_route.dcp
report_timing_summary -file reports/post_route_timing.rpt

# Bitstream
write_bitstream -force output/kv260.bit
```

### Relevance to Your Project

Your project already has a create_bd.tcl. Wrapping it in a non-project-mode build script like the above enables fully reproducible, headless builds — important for iterating on the AXI address map without opening the GUI each time.

## Vitis Bare-Metal / Standalone

### Key Findings

- **Standalone BSP**: AMD's standalone BSP provides a single-threaded environment with boot code, cache management, exception handlers, and `xil_printf`. It is configured per-platform — always regenerate the BSP when you change the hardware platform (XSA file).
- **`xil_printf` is NOT `printf`**: It is a lightweight implementation that does not support floating point (`%f`, `%g`, `%e`). Use it for PASS/FAIL messages. For floating-point debug, link the full `printf` with `-u _printf_float` in your linker flags.
- **Linker script pitfall**: Vitis's auto-generated linker script (`lscript.ld`) sometimes assigns all sections to the wrong memory region (BAR0 or BRAM instead of DDR). If your application starts but immediately crashes or produces garbage UART output, open `lscript.ld` and verify `psu_ddr_0_MEM_0` is the target for `.text`, `.data`, `.bss`, and stack/heap.
- **Stack and heap sizes**: The default linker script allocates very small stack (2 KB) and heap (4 KB) for bare-metal. For complex pattern loops and string formatting, increase `_STACK_SIZE` to at least 16 KB in the linker script.
- **Platform regeneration**: Always run "Update Hardware" and regenerate the BSP in Vitis when you change the block design or address map. A stale BSP will have outdated `xparameters.h` with wrong base addresses — your `Xil_Out32(BRAM0_BASE, ...)` calls will write to the wrong physical address.

### Code Example

```c
/* lscript.ld excerpt: ensure DDR is used, not BRAM or BAR0 */
/* Generated by Vitis; key sections to verify manually       */

MEMORY {
   psu_ddr_0_MEM_0 : ORIGIN = 0x0, LENGTH = 0x80000000  /* 2 GB DDR */
   psu_ocm_ram_0_MEM_0 : ORIGIN = 0xFFFC0000, LENGTH = 0x40000       /* 256 KB OCM */
}

SECTIONS {
   .text : {
      *(.vectors)
      *(.boot)
      *(.text)
      *(.text.*)
   } > psu_ddr_0_MEM_0    /* <-- must point to DDR, not BRAM */

   .data : {
      *(.data)
      *(.data.*)
   } > psu_ddr_0_MEM_0

   Stack (NOLOAD) : {
      _stack_end = .;
      . += _STACK_SIZE;   /* ensure _STACK_SIZE >= 0x4000 */
      _stack = .;
   } > psu_ddr_0_MEM_0
}
```

### Relevance to Your Project

Your main.c uses `xil_printf` for PASS/FAIL output. If the UART appears silent or outputs garbage after loading the ELF via JTAG, the first check is the linker script memory mapping. The second check is that the BSP's `xparameters.h` contains `XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR 0xA0000000` — if that constant is missing or wrong, the application is using hard-coded addresses that may mismatch the actual hardware map.

## XDC Timing Constraints

### Key Findings

- **`set_input_delay` / `set_output_delay` model system-level delays**: These commands tell the timing engine about external delays at the device boundary, relative to a clock. Both accept negative values when data arrives before the clock edge.
- **`-clock` is mandatory**: Without specifying `-clock <clk>`, the constraint is ignored. Always anchor I/O delay constraints to the relevant interface clock.
- **I/O delay interacts with `set_max_delay`**: If a port has both a `set_max_delay` and `set_input_delay`, the I/O delay counts toward the max-delay budget (UG835 2025.1). Do not accidentally double-constrain output paths.
- **Clock group isolation**: Use `set_clock_groups -asynchronous` to tell Vivado that the PS FCLK and any external clocks are unrelated. Without this, Vivado may report false-path timing failures between the PS AXI clock domain and PL user logic.
- **KV260-specific**: The KV260 board XDC file (from AMD's board files repository) defines `sys_clk` constraints. For pure PS-to-PL AXI traffic at FCLK rates, no I/O delay constraints on the AXI signals themselves are needed — those paths are all internal to the device.

### Code Example

```xdc
# kv260_constraints.xdc
# For a KV260 bare-metal AXI-BRAM design with no external I/O on the AXI bus,
# the only constraint needed is the PL fabric clock (driven by PS FCLK_CLK0).

# Create clock constraint for PL clock output from PS
# Actual frequency set in block design PS7/ZYNQ_UltraScale+ configuration
create_clock -name clk_pl_0 -period 10.000 [get_pins -hierarchical -filter {NAME =~ *FCLK_CLK0*}]

# If user LEDs or GPIO are exported via EMIO/PL:
# set_output_delay -clock clk_pl_0 -max  2.0 [get_ports led[*]]
# set_output_delay -clock clk_pl_0 -min -1.0 [get_ports led[*]]

# Isolate PS clock domain from any async PL clocks
# (uncomment if you add a PL oscillator later)
# set_clock_groups -name async_ps_pl -asynchronous \
#     -group [get_clocks clk_pl_0] \
#     -group [get_clocks clk_external]

# False path on PS configuration resets (good practice for Zynq)
set_false_path -from [get_ports *] -to [get_pins -hierarchical -filter {NAME =~ *PS8_0*}]
```

### Relevance to Your Project

For the kv260-axi-bram-demo, the AXI traffic is entirely internal (PS ↔ PL over FCLK_CLK0). You do not need I/O delay constraints on AXI signals. The minimum viable XDC just constrains the FCLK to its programmed frequency so Vivado's timing analysis is anchored. If timing closure fails, it will be in PL register paths, not AXI I/O paths.

## Kria KV260 / K26 SoM

### Key Findings

- **Boot is hard-wired to QSPI**: The K26 SoM has no physical boot-mode switches. The QSPI flash contains the signed boot.bin (FSBL + U-Boot + ATF). You cannot change the boot mode from the board. For bare-metal development, use JTAG to program the PL bitstream and ELF directly without touching QSPI.
- **PL clock source**: The PL fabric clock must be sourced from the PS (`FCLK_CLK0..3`). There is no independent PL oscillator on the K26 SoM. Your PS configuration in the block design must enable at least FCLK_CLK0 before any AXI slave is accessible.
- **MIO bank layout**: MIO Bank 501 contains MIO[30:26] and MIO[51:38]; MIO Bank 502 contains MIO[77:52]. USB UART is typically on MIO[52:53] (UART1 on the KV260 carrier card).
- **No DDR on SoM vs carrier card**: The K26 SoM itself does not include DDR. The KV260 carrier card provides 4 GB DDR4. Your linker script must target DDR4 (`psu_ddr_0`) not OCM, or the application will not fit.
- **eMMC vs QSPI variants**: Two K26 SOM variants exist: `sm-k26` (with eMMC) and `smk-k26` (no eMMC, for the KV260 starter kit using QSPI only). The KV260 uses `smk-k26`.
- **JTAG workflow for bare-metal**: Program bitstream with `program_hw_devices` in Vivado Hardware Manager, then use Vitis debugger to download the ELF to DDR. No QSPI modification needed for development.

### Code Example

```tcl
# Vivado Hardware Manager Tcl: program KV260 via JTAG (bare-metal development)
# Run from Vivado Tcl console with board connected

open_hw_manager
connect_hw_server -allow_non_jtag
open_hw_target

# Select the Zynq UltraScale+ device
set_property PROGRAM.FILE {output/kv260.bit} [get_hw_devices xcku5p_0]
# Note: K26 SoM device ID varies — check Hardware Manager for exact name

program_hw_devices [get_hw_devices xcku5p_0]
refresh_hw_device [get_hw_devices xcku5p_0]
puts "Bitstream programmed — PL now active with PS-driven FCLK"
close_hw_target
close_hw_manager
```

```bash
# Vitis Classic / Unified: download ELF to DDR via JTAG (command line)
xsct -interactive << 'EOF'
connect
targets -set -filter {name =~ "Cortex-A53 #0"}
rst -processor
dow kv260_axi_bram.elf
con
EOF
```

### Relevance to Your Project

The critical insight: your AXI-BRAM demo requires FCLK_CLK0 to be enabled in the PS block design configuration. If FCLK is disabled (the default for a fresh PS8 IP), the AXI interconnect has no clock and every `Xil_Out32` call will hang the processor in an AXI deadlock. Verify that `CONFIG.PSU__FPGA_PL0_ENABLE {1}` and `CONFIG.PSU__CRL_APB__PL0_REF_CTRL__FREQMHZ {100}` (or your desired frequency) are set in your create_bd.tcl PS8 configuration.

## AMD/Xilinx Tool Updates — Vivado/Vitis 2025.1

### Key Findings

- **New device support**: Vivado 2025.1 adds initial support for Versal AI Edge Series Gen 2, Versal Prime Series Gen 2, and Spartan UltraScale+.
- **New AXI Switch IP (RTL-based)**: A new fully customizable RTL-based AXI Switch IP was added that bridges between different AXI interface types and widths. This is distinct from the existing AXI SmartConnect and AXI Interconnect IPs.
- **New IP Integrator views**: Two dedicated views were added to the IP Integrator: "Clocking and Reset" and "Interrupt and AXI-4 Lite." These let you inspect clock/reset wiring and AXI-Lite connectivity at a glance rather than tracing wires in the block diagram.
- **Selective device installer**: Vivado 2025.1 introduces a selective device installer for Versal families, reducing install size.
- **Open-source components**: The 2025.1 open-source release upgraded the Linux kernel to 6.12 and added early-access Zephyr RTOS support for several drivers.
- **2025.2 preview** (released after 2025.1): Vivado 2025.2 adds an ultra-low-area mode for AXI Switch and AXI SmartConnect via a `STRATEGY` parameter, and adds new PS Wizard block diagram and swim-lane views. If you upgrade, test your block design TCL export again — PS Wizard changes can affect `create_bd.tcl` re-run behavior.

### Code Example

```tcl
# Vivado 2025.1: use new AXI Switch IP as a lightweight interconnect
# (alternative to AXI Interconnect for simple single-master, two-slave topologies)

# In create_bd.tcl, instantiate the new RTL-based AXI Switch:
create_bd_cell -type ip -vlnv xilinx.com:ip:axi_switch:1.0 axi_switch_0
set_property -dict [list \
    CONFIG.NUM_MI {2} \
    CONFIG.NUM_SI {1} \
    CONFIG.DATA_WIDTH {32} \
    CONFIG.ADDR_WIDTH {32} \
] [get_bd_cells axi_switch_0]

# Connect PS master to AXI Switch slave port
connect_bd_intf_net [get_bd_intf_pins zynq_ultra_ps_e_0/M_AXI_HPM0_FPD] \
    [get_bd_intf_pins axi_switch_0/S00_AXI]

# Connect AXI Switch master ports to BRAM controllers
connect_bd_intf_net [get_bd_intf_pins axi_switch_0/M00_AXI] \
    [get_bd_intf_pins axi_bram_ctrl_0/S_AXI]
connect_bd_intf_net [get_bd_intf_pins axi_switch_0/M01_AXI] \
    [get_bd_intf_pins axi_bram_ctrl_1/S_AXI]
```

### Relevance to Your Project

The new IP Integrator "Interrupt and AXI-4 Lite" view is directly useful when debugging why the PS cannot reach BRAM0 or BRAM2. Previously you had to trace wires manually; now you can see the full AXI-Lite connectivity tree in one panel. If you upgrade to 2025.2, note that the `STRATEGY` parameter on AXI SmartConnect could reduce PL resource usage for your simple two-BRAM topology.
