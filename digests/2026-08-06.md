## Executive Summary

- **Critical AXI handshake rule:** Once VALID is asserted it must stay asserted until the corresponding
  READY rises — violating this rule in VHDL state machines is the single most common cause of AXI bus
  hangs on bare-metal Zynq designs, including the BRAM read/write paths at 0xA0000000 / 0xA0010000.
- **Vivado 2025 address-space bug:** A reported bug in the Vivado 2025.x AXI full peripheral limits
  the usable AXI address space to 1 KB (10-bit decode) even when the address-width parameter is
  widened; confirm your BRAM address ranges (0xA0000000 + 64 KB, etc.) decode correctly in the
  Address Editor before generating the bitstream.
- **Linker script stack default is only 400 bytes:** The Vitis bare-metal linker default
  `_STACK_SIZE = 100 words = 400 bytes` is dangerously small for any non-trivial C code; increase
  it explicitly via the lscript.ld or `-defsym` linker flag.
- **`write_bd_tcl` is version-locked:** The TCL that Vivado exports for a block design is only
  guaranteed to re-create that design in the same tool version; do not use a 2025.1-generated script
  in 2025.2 without re-exporting.
- **KV260 USB-UART is PS UART1 on MIO 36/37:** Always enable UART1 (not UART0) in the MPSoC PS
  configuration block and set stdout to `psu_uart_1` in the BSP settings to get xil_printf output
  over the USB-UART cable.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- **VALID-cannot-deassert rule (ARM IHI0022):** Once a source asserts `AWVALID`, `WVALID`, or
  `ARVALID`, it must hold them high until the corresponding READY is seen. Prematurely deasserting
  VALID causes a silent protocol violation that manifests as a hung transaction rather than an
  observable error — very hard to debug on bare metal without ILA.
- **BRAM controller read latency model:** The AXI BRAM Controller does not assert `RVALID` until
  both `ARVALID` **and** `ARREADY` have been sampled high in the same cycle (the address is accepted).
  The "READ LAG" metric (cycles between `ARVALID && ARREADY` and first `RVALID`) is typically 2–3
  clock cycles for AXI BRAM Controller v4.x.
- **Vivado 2025.x address-decode bug:** A community-reported bug limits AXI full peripheral usable
  address space to 1 KB (10-bit decode). Widening the `C_S_AXI_ADDR_WIDTH` generic to 16 bits does
  not propagate correctly. Workaround: verify in simulation or ILA that `araddr[15:10]` is actually
  reaching your BRAM logic.
- **AXI-Lite has no burst support:** AXI-Lite always transfers exactly one data word per transaction.
  `ARLEN` and `AWLEN` do not exist. Using AXI-Lite for your BRAM accesses means each C `Xil_Out32`
  / `Xil_In32` call is one complete AXI transaction.
- **AXI-Stream TREADY backpressure:** If you add streaming IP later, remember that a slave dropping
  TREADY stalls the entire pipeline. Always size FIFO depths to the latency of the slowest component.

### Code Example

```vhdl
-- AXI-Lite slave state machine: VALID hold discipline
-- Once s_axi_arvalid is asserted, hold s_axi_rvalid until s_axi_rready
process(aclk)
begin
  if rising_edge(aclk) then
    if aresetn = '0' then
      s_axi_rvalid <= '0';
      read_state   <= IDLE;
    else
      case read_state is
        when IDLE =>
          if s_axi_arvalid = '1' and s_axi_arready = '1' then
            -- Address accepted — latch address, move to DATA state
            bram_addr  <= s_axi_araddr(ADDR_BITS-1 downto 2);
            read_state <= DATA;
          end if;
        when DATA =>
          s_axi_rvalid <= '1';
          s_axi_rdata  <= bram_dout;  -- BRAM output registered one cycle earlier
          s_axi_rresp  <= "00";       -- OKAY
          -- Hold rvalid until master accepts
          if s_axi_rready = '1' then
            s_axi_rvalid <= '0';
            read_state   <= IDLE;
          end if;
      end case;
    end if;
  end if;
end process;
```

### Relevance to Your Project

Your bare-metal C code calls `Xil_In32(0xA0000000)` and `Xil_In32(0xA0010000)`. Each call drives one
complete AXI-Lite read transaction through `kv260_top.vhd` into the respective BRAM controller. If
the VHDL slave ever deasserts `ARVALID` prematurely (e.g., a state machine resets `arvalid` one cycle
too early), the PS will stall indefinitely waiting for `RVALID`. Use an ILA on `{ARVALID, ARREADY,
RVALID, RREADY}` to verify the 4-phase handshake on both BRAM ports.

## Vivado Block Design / IP Integrator

### Key Findings

- **No spaces in block-design names or paths:** Vivado silently misbehaves (failed generate, broken
  constraints) when the block design name or any directory on the project path contains a space. Use
  underscores or CamelCase only.
- **Address Editor auto-assign:** Click "Auto Assign Address" in the Address Editor after adding IPs.
  Addresses are only finalized when you do this; if you manually add IP after last running automation,
  the new slave has no assigned address and synthesis will produce a DRC error.
- **Connection Automation instantiates AXI Interconnect automatically:** Run Connection Automation
  after adding the Zynq MPSoC PS and your Block Memory Generators — Vivado will add the AXI
  Interconnect, Proc System Reset, and wire clocks/resets for you.
- **`write_bd_tcl` is version-specific:** The TCL file Vivado exports via File > Export > Export
  Block Design (or `write_bd_tcl` in the Tcl Console) only re-creates the design reliably in the
  exact same tool version it was generated in.
- **Include layout with `-include_layout`:** By default `write_bd_tcl` omits block placement; add
  `-include_layout` to preserve visual layout, which aids diff readability in version control.

### Code Example

```tcl
# Export block design to TCL for version control (run from Vivado Tcl console)
# Open your block design first: open_bd_design [get_files *.bd]
write_bd_tcl \
  -force \
  -include_layout \
  ./tcl/create_bd.tcl

# To reconstruct from scratch in the same Vivado version:
# source ./tcl/create_bd.tcl
# After sourcing, validate:
validate_bd_design
save_bd_design
generate_target all [get_files *.bd]
```

### Relevance to Your Project

Your `create_bd.tcl` script is the authoritative record of your block design. Ensure you regenerate
it from Vivado 2025.1 whenever you change IP parameters, address assignments, or connections. The
`generate_target all` step is required before synthesis — if you source the TCL but skip this step,
Vivado will synthesize against stale generated HDL.

## Vivado TCL Scripting

### Key Findings

- **Batch mode invocation:** `vivado -mode batch -source script.tcl` runs your TCL and exits.
  Add `-tclargs arg1 arg2` to pass runtime parameters; read them in TCL as `$argv`.
- **Non-project mode:** In non-project mode the developer explicitly calls `synth_design`,
  `opt_design`, `place_design`, `route_design`, and `write_bitstream` — no project file is created.
  This is ideal for CI pipelines.
- **Design checkpoints (`write_checkpoint`):** Save state after each implementation step. If routing
  fails, you can reload the placed checkpoint (`read_checkpoint -incremental`) rather than restarting
  from synthesis.
- **`create_bd_cell` in scripted block designs:** Used inside block-design TCL to add IP:
  `create_bd_cell -type ip -vlnv xilinx.com:ip:axi_bram_ctrl:4.1 axi_bram_ctrl_0`.
  Always specify the full VLNV string to avoid version ambiguity across tool releases.

### Code Example

```tcl
# Non-project mode batch script skeleton for KV260 bare-metal project
# Usage: vivado -mode batch -source build.tcl -tclargs "xck26-sfvc784-2LV-c"

set part [lindex $argv 0]
if {$part eq ""} { set part "xck26-sfvc784-2LV-c" }   ;# K26 part

# Read sources
read_vhdl   [glob ./vhdl/*.vhd]
read_xdc    [glob ./xdc/*.xdc]

# Read block design wrapper
read_vhdl   ./vivado/kv260_bd_wrapper.vhd
read_ip     [glob ./vivado/**/*.xci]

# Synthesize
synth_design -top kv260_top -part $part -flatten_hierarchy rebuilt
write_checkpoint -force ./checkpoints/post_synth.dcp

# Implement
opt_design
place_design
write_checkpoint -force ./checkpoints/post_place.dcp
route_design
write_checkpoint -force ./checkpoints/post_route.dcp

# Reports and bitstream
report_timing_summary -file ./reports/timing.rpt
report_utilization    -file ./reports/utilization.rpt
write_bitstream -force ./output/kv260_top.bit

puts "Build complete."
```

### Relevance to Your Project

Your existing `create_bd.tcl` fits directly into this non-project flow. Source it between the
`read_vhdl` block and `synth_design` to reconstruct the block design in CI:
`source ./tcl/create_bd.tcl`. Pass the K26 part string via `-tclargs` so the same script works
on different speed-grade variants without editing.

## Vitis Bare-Metal / Standalone

### Key Findings

- **Match tool versions:** Always use the same major.minor Vivado and Vitis release (e.g.,
  2025.1 + 2025.1). Mixing versions causes BSP driver mismatches and broken `xparameters.h`.
- **xil_printf vs printf:** `xil_printf` is a lightweight formatted-print that routes to the
  BSP stdout UART without requiring full `newlib` printf. For `%f` floating point you need full
  `printf` and must link `newlib_float_printf`; avoid it in bare-metal unless necessary.
- **Default stack is 400 bytes:** The linker script default `_STACK_SIZE = 0x64 (100 words = 400 bytes)`
  is dangerously small. Any C function with local arrays or deep call chains will silently corrupt
  the stack. Increase to at least 32 KB (`0x8000`) in `lscript.ld` or via BSP settings.
- **BSP stdout configuration:** In the BSP settings (`system.mss` / BSP editor), set
  `stdin` and `stdout` to `psu_uart_1` for the KV260 USB-UART. If left at default, xil_printf
  output goes nowhere.
- **Standalone BSP sources on GitHub:** All standalone drivers live at
  `github.com/Xilinx/embeddedsw/XilinxProcessorIPLib/drivers`. Useful when debugging driver
  behavior or adapting for custom IP.

### Code Example

```c
/* Robust bare-metal AXI-BRAM write/read/verify pattern
 * Assumes Xil_Out32/Xil_In32 drive AXI-Lite transactions to BRAM */

#include "xil_io.h"
#include "xil_printf.h"
#include "xparameters.h"

#define BRAM0_BASE  0xA0000000UL
#define BRAM1_BASE  0xA0010000UL
#define TEST_WORDS  8

static int bram_test(u32 base, const char *name) {
    u32 i, val;
    int errors = 0;

    /* Write phase */
    for (i = 0; i < TEST_WORDS; i++)
        Xil_Out32(base + (i << 2), 0xDEAD0000 | i);

    /* Read-back phase — explicit memory barrier ensures no store-to-load forwarding */
    Xil_DCacheFlush();   /* only needed if D-cache enabled; harmless if not */
    for (i = 0; i < TEST_WORDS; i++) {
        val = Xil_In32(base + (i << 2));
        if (val != (0xDEAD0000 | i)) {
            xil_printf("BRAM %s[%lu]: expected 0x%08lX got 0x%08lX\r\n",
                       name, i, 0xDEAD0000 | i, val);
            errors++;
        }
    }
    xil_printf("BRAM %s: %s (%d errors)\r\n", name, errors ? "FAIL" : "PASS", errors);
    return errors;
}

int main(void) {
    xil_printf("\r\n=== KV260 AXI-BRAM Test ===\r\n");
    int total = 0;
    total += bram_test(BRAM0_BASE, "BRAM0");
    total += bram_test(BRAM1_BASE, "BRAM1");
    xil_printf("Overall: %s\r\n", total ? "FAIL" : "PASS");
    return total;
}
```

### Relevance to Your Project

Your existing `main.c` already follows this pattern. Key additions here: the `Xil_DCacheFlush()`
call (critical if you ever enable the D-cache — on Cortex-A53 the cache may satisfy reads from
write-buffer rather than going out to AXI), and the structured `errors` counter replacing a simple
PASS/FAIL print to enable locating the first failing word address.

## XDC Timing Constraints

### Key Findings

- **`set_input_delay` and `set_output_delay` basics:** These commands specify external board-level
  delays relative to a clock edge. Values are in nanoseconds; both positive and negative values
  are valid depending on clock-to-data phase relationship.
- **Always provide both `-max` and `-min`:** `-max` covers setup analysis, `-min` covers hold
  analysis. Specifying only `-max` leaves hold unconstrained and Vivado may not flag hold violations.
- **PS-to-PL clock requires `create_clock` on the generated clock:** The Zynq MPSoC PS outputs
  a generated clock (`pl_clk0`) to the PL. Vivado auto-creates this clock from the block design;
  if you use a custom wrapper, add `create_clock -period 10.000 -name pl_clk0 [get_ports pl_clk0]`.
- **False paths on async resets:** If your VHDL uses an asynchronous `aresetn`, add
  `set_false_path -from [get_ports aresetn]` to prevent Vivado from trying to time the reset path.
- **Clock groups for PS and PL:** If you have multiple clock domains (e.g., PS clk + PL free-running
  clk), use `set_clock_groups -asynchronous` to mark them unrelated and avoid spurious cross-domain
  timing failures.

### Code Example

```tcl
# KV260 XDC constraints skeleton (kv260_top.xdc)
# Assumes pl_clk0 @ 100 MHz from PS block design

# PS-generated clock — Vivado IPI creates this automatically;
# include explicitly if using a wrapper netlist
create_clock -period 10.000 -name pl_clk0 \
  [get_ports pl_clk0]

# Asynchronous reset: no timing requirement
set_false_path -from [get_ports aresetn]

# If you add a free-running PL oscillator later:
# create_clock -period 20.000 -name pl_osc [get_ports pl_osc_clk]
# set_clock_groups -asynchronous \
#   -group [get_clocks pl_clk0] \
#   -group [get_clocks pl_osc]

# Example I/O constraints for external signals (not needed for PS↔PL AXI,
# but required if you route PL signals to the SOM240 connector)
# set_input_delay  -clock pl_clk0 -max 3.0 [get_ports {gpio_in[*]}]
# set_input_delay  -clock pl_clk0 -min 1.0 [get_ports {gpio_in[*]}]
# set_output_delay -clock pl_clk0 -max 2.0 [get_ports {gpio_out[*]}]
# set_output_delay -clock pl_clk0 -min 0.5 [get_ports {gpio_out[*]}]
```

### Relevance to Your Project

For a PS↔PL AXI-only design (no external I/O on the PL pins), the critical constraint is
`create_clock` on `pl_clk0` plus a false path on `aresetn`. Without the clock definition, Vivado
cannot perform timing analysis on the AXI interconnect paths between the PS and your BRAM
controllers, and timing sign-off is meaningless. Add `report_timing_summary -warn_on_violation`
to your build script to catch failures before programming.

## Kria KV260 / K26 SoM

### Key Findings

- **USB-UART is PS UART1 on MIO 36/37:** The KV260 carrier board routes MIO pins 36 (TX) and 37
  (RX) to the USB-UART bridge. In the Zynq MPSoC PS configuration, enable **UART1** and select
  MIO Bank 500 pins 36–37. Using UART0 sends output nowhere visible over USB.
- **PS MIO bank voltages:** PS MIO Bank 500 (MIO 0–25) runs at 1.8 V; Bank 501 (MIO 26–51,
  which includes the UART pins) also runs at 1.8 V. Do not connect 3.3 V signals directly to MIO.
- **EMIO routing to SOM240 connector:** EMIO GPIO passes PS → PL → SOM240_1 pin →
  KV260 carrier net. If you want to drive KV260 carrier-board LEDs or buttons from the PS, use
  EMIO with a thin PL wrapper — not MIO, which is not routed to the carrier in most cases.
- **Bare-metal Vivado board files:** Vivado ships board files for the KV260 that pre-configure
  the MPSoC PS (clocks, DDR, UART, USB, etc.) when you click "Run Block Automation". Always apply
  the board preset — it saves hours of manual PS tab configuration.
- **Boot modes on K26:** The K26 SoM supports SD card, JTAG, QSPI, and eMMC boot modes selected
  by the carrier board's boot-mode switches. For bare-metal development, JTAG boot (via Vitis
  "Program FPGA" then "Run") is fastest — no SD card required.

### Code Example

```tcl
# Vivado Tcl: configure PS UART1 on MIO 36/37 for KV260
# Run inside a block design Tcl script after create_bd_cell for Zynq MPSoC

set ps [get_bd_cells zynq_ultra_ps_e_0]

# Enable UART1 and set MIO mapping
set_property -dict [list \
  CONFIG.PSU__UART1__PERIPHERAL__ENABLE {1} \
  CONFIG.PSU__UART1__PERIPHERAL__IO    {MIO 36 .. 37} \
  CONFIG.PSU__UART1__BAUD_RATE         {115200} \
] $ps

# Confirm PL clock at 100 MHz (adjust if needed)
set_property CONFIG.PSU__CRL_APB__PL0_REF_CTRL__FREQMHZ {100} $ps
```

### Relevance to Your Project

If your `main.c` uses `xil_printf` and you see no output, the most common cause is that the BSP
stdout is pointing to the wrong UART, or UART1 is not enabled in the PS block. Verify in Vivado
that the PS block shows "UART 1" enabled on MIO 36–37, and in Vitis BSP Editor that `stdout` is
set to `psu_uart_1`. Also ensure your terminal application connects at **115200 8N1** to the
USB-UART port (not the JTAG port).

## AMD/Xilinx Tool Updates

### Key Findings

- **Vivado 2025.2 highlights:** SystemVerilog Interface support (simplified AXI connections between
  SV instances, automatic wrapper creation for AMD IP and Block Designs); new AXI Switch and AXI
  SmartConnect ultra-low-area mode via `STRATEGY` parameter; SLR crossing reporting improvements.
  Not relevant to KV260 directly but the AXI SmartConnect update may benefit designs with many
  AXI masters.
- **Vivado 2025.1 highlights (your current version):** Production support for Spartan UltraScale+
  devices; PS-first boot with dynamic PL load; new Pblock planner. The dynamic PL load feature is
  useful for future partial reconfiguration experiments on the K26.
- **Vivado 2026.1 is now available:** New tiered licensing model, additional device support, and
  major NoC/QoR improvements. If upgrading, re-export all block design TCLs from the new tool
  before committing — `write_bd_tcl` output is version-specific.
- **Known issue — AXI peripheral address decode (Vivado 2025.x):** Reported in community forums:
  AXI full peripheral address decode may be silently limited to 10 bits (1 KB) even when
  `C_S_AXI_ADDR_WIDTH` is set wider. Validate with behavioral simulation or ILA.
- **Vitis 2025.2 bare-metal:** No major bare-metal/standalone changes in 2025.2; AI Engine
  improvements are the focus. The `embeddedsw` standalone drivers remain at the same version for
  Cortex-A53.

### Code Example


### Relevance to Your Project

You are on Vivado/Vitis 2025.1. Before upgrading to 2025.2 or 2026.1, note: (1) re-run
`write_bd_tcl` to refresh `create_bd.tcl` in the new tool, (2) re-generate the BSP in Vitis
(the `standalone` library version may bump), and (3) re-validate timing — QoR improvements in
newer tools sometimes close timing that failed before, or introduce new critical paths via
retiming changes.
