# FPGA Research Digest - 2026-11-15

## Executive Summary
- **AXI-Lite handshake bug in Vivado's example slave**: Vivado's generated AXI-Lite slave code has known handshake errors (found via formal verification); always simulate or formally verify your AXI endpoints before hardware testing.
- **Don't script `apply_bd_automation` directly**: AMD explicitly recommends against calling this Tcl command manually — instead, run automation in the Vivado GUI and use `write_bd_tcl` to export a reproducible script. Use `assign_bd_address` to manage BRAM address segments at 0xA0000000 and 0xA0010000.
- **Vitis Unified IDE requires explicit platform creation**: Unlike the classic IDE, Vitis Unified requires you to manually create a Platform Component from your XSA before creating the application — a critical workflow change for the 2025.x toolchain.
- **AXI BRAM Controller ECC requires 32-bit or 64-bit data width**: ECC is only available when BRAM width is ≥32 bits; enabling it adds a second AXI4-Lite control port for status/correction registers — plan for this in the address map if adding ECC later.
- **New AXI Switch IP in Vivado 2025.1**: A fully customizable RTL-based AXI Switch IP shipped in 2025.1 that bridges AXI interface types/widths — but AMD notes it is NOT intended for use inside IP Integrator block diagrams. Useful for custom RTL wrapping the BRAM design.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings
- A transfer on the AXI-Lite bus occurs only when TVALID (or WVALID/RVALID) **and** TREADY (WREADY/RREADY) are both asserted simultaneously in the same clock cycle; either side may deassert its signal independently.
- **Critical bug**: ZipCPU's formal verification work found that Vivado's generated AXI-Lite slave core improperly drops READY lines to prevent new transactions when the outgoing acknowledgement channel is stalled. This bug was present through Vivado 2020.2 and may persist; the fix was to add an extra register stage.
- **BRAM controller verification**: Limited formal checks of Xilinx's AXI BRAM Controller found no handshake bugs, but only bounded model checks were run — not full proof.
- **AXI-Stream TLAST bug**: A Xilinx AXI-Stream master template was found to change TLAST while the channel is stalled (`M_AXIS_TVALID && !M_AXIS_TREADY`), violating protocol. Check IP version changelog in PG085 when instantiating AXI-Stream FIFOs.
- AXI4-Stream packet FIFO mode (PG085) uses TLAST for packet boundary detection and supports store-and-forward behavior. TKEEP bits are packed into the FIFO data word so null bytes are tracked.
- `XPM_FIFO_AXIS` (Vivado 2025.2 UG974) is the parameterized macro derived from XPM_FIFO_SYNC/ASYNC for AXI-Stream FIFOs — avoids manual constraint management.

### Code Example
```vhdl
-- AXI-Lite read-valid handshake: safe pattern to prevent protocol violation
-- Register RVALID independently from read address acceptance
process(S_AXI_ACLK)
begin
  if rising_edge(S_AXI_ACLK) then
    if S_AXI_ARESETN = '0' then
      axi_rvalid <= '0';
      axi_rresp  <= "00";
    else
      -- Assert RVALID one cycle after ARVALID/ARREADY handshake
      if (axi_arready = '1' and S_AXI_ARVALID = '1' and axi_rvalid = '0') then
        axi_rvalid <= '1';
        axi_rresp  <= "00"; -- OKAY response
      elsif (S_AXI_RREADY = '1') then
        -- Hold RVALID until master acknowledges with RREADY
        axi_rvalid <= '0';
      end if;
    end if;
  end if;
end process;
```

### Relevance to Your Project
Your kv260_top.vhd BRAM connectivity to the PS over AXI-Lite is exactly where these handshake bugs can silently corrupt reads. If the Cortex-A53 occasionally reads stale BRAM data despite correct writes, check whether your AXI BRAM Controller version has the RVALID/RREADY race. Run an AXI protocol checker (IP Catalog > Debug IP > AXI Protocol Checker) on the M_AXI connections from the Zynq block to BRAM0 and BRAM2.

## Vivado Block Design / IP Integrator

### Key Findings
- **Do not script `apply_bd_automation` directly**: AMD's UG835 says this command is designed for interactive IDE use, not scripting. Use the Vivado GUI for automation, then export the TCL with `write_bd_tcl`.
- **Address assignment**: Use `assign_bd_address` to assign unmapped segments. The `-boundary` option assigns at hierarchical boundaries for BDC designs.
- **Lock addresses** to protect them from "Unassign All" operations (available since ~2025.2 UG994): `set_property offset <addr> [get_bd_addr_segs ...]`.
- **Import/Export address maps**: Right-click in Address Editor → "Export to file" / "Import from file" to manage address maps in source control. Equivalent Tcl: use the commands documented in UG994.
- **Hierarchical BDC addressing**: All address assignments for Block Design Containers must be made from the top-level block design, not from within the sub-block.
- Vivado 2025.1 IP Integrator gained dedicated "Clocking and Reset" and "Interrupt and AXI-4 Lite" views plus a new Pblock planner.

### Code Example
```tcl
# TCL snippet: assign BRAM addresses after create_bd_design completes
# Run validate_bd_design first, then:
assign_bd_address [get_bd_addr_segs {bram_ctrl_0/S_AXI/Mem0}]
assign_bd_address [get_bd_addr_segs {bram_ctrl_1/S_AXI/Mem0}]

# Set specific base addresses matching your project (0xA0000000, 0xA0010000)
set_property offset 0xA0000000 [get_bd_addr_segs \
  {zynq_ultra_ps_e_0/Data/SEG_bram_ctrl_0_Mem0}]
set_property range  0x00010000 [get_bd_addr_segs \
  {zynq_ultra_ps_e_0/Data/SEG_bram_ctrl_0_Mem0}]

set_property offset 0xA0010000 [get_bd_addr_segs \
  {zynq_ultra_ps_e_0/Data/SEG_bram_ctrl_1_Mem0}]
set_property range  0x00010000 [get_bd_addr_segs \
  {zynq_ultra_ps_e_0/Data/SEG_bram_ctrl_1_Mem0}]

validate_bd_design
save_bd_design
```

### Relevance to Your Project
Your `create_bd.tcl` likely uses `apply_bd_automation` for connection wiring. For CI reproducibility, export the finalized block design as TCL (`write_bd_tcl`) and commit that — it captures the exact state including address assignments. The address lock feature ensures regeneration doesn't clobber your 0xA0000000/0xA0010000 BRAM assignments.

## Vivado TCL Scripting

### Key Findings
- **Non-Project mode** gives full flow control: `read_vhdl`, `read_xdc`, `synth_design`, `opt_design`, `place_design`, `route_design`, `write_bitstream`. No runs infrastructure; no auto-reports.
- Launch with: `vivado -mode batch -source build.tcl` for headless CI runs.
- **Source file ordering matters**: In non-project mode, files compile in the order `read_vhdl` / `read_verilog` commands appear; there is no dependency resolution.
- **Reports are not automatic**: You must call `report_timing_summary`, `report_utilization`, `report_drc` explicitly after each stage.
- **Checkpoint saves**: `write_checkpoint` after each stage enables incremental re-entry without re-running earlier stages (critical for long builds).
- The 2026.1 UG892 non-project example remains the reference template.

### Code Example
```tcl
#!/usr/bin/env tclsh
# Non-project mode build script for kv260 AXI-BRAM demo
set project_name "kv260_axi_bram"
set part_name    "xck26-sfvc784-2LV-c"

# Read sources
read_vhdl  -library work [glob ./vhdl/*.vhd]
read_xdc               ./constraints/kv260_top.xdc

# Synthesis
synth_design -top kv260_top -part $part_name -flatten_hierarchy rebuilt
write_checkpoint -force ./checkpoints/post_synth.dcp
report_timing_summary -file ./reports/post_synth_timing.rpt

# Implementation
opt_design
place_design
route_design
write_checkpoint -force ./checkpoints/post_route.dcp
report_timing_summary -file ./reports/post_route_timing.rpt
report_utilization    -file ./reports/utilization.rpt

# Bitstream
write_bitstream -force ./output/${project_name}.bit
```

### Relevance to Your Project
Your current `create_bd.tcl` runs in project mode. Consider adding a parallel non-project build script for CI gating — this lets you catch timing violations on every push without opening the Vivado GUI. The checkpoint pattern also makes the BRAM address tuning workflow faster (re-route only, skip re-synth).

## Vitis Bare-Metal / Standalone

### Key Findings
- **Vitis Unified IDE workflow change**: Unlike the classic IDE, the Unified IDE requires you to manually create a Platform Component (File > New Component > Platform) from your XSA before creating an application. The classic IDE did this automatically.
- **SDTgen**: The Unified IDE runs SDTgen internally to convert XSA → System Device Tree files; this is transparent to the user but explains why platform creation takes longer.
- **Console routing (STDIN/STDOUT)**: Check `standalone_stdin` and `standalone_stdout` in `vitis-comp.json` — these map `xil_printf()` output to a specific UART. For the KV260, this should point to `psu_uart_1` (the USB-UART).
- **BSP features**: The standalone BSP provides interrupt/exception handling, `xil_printf` (lite printf), cache management, and MMU/MPU configuration.
- **UART modes**: The UART driver supports polled mode (used by `xil_printf`) and interrupt mode. For debug builds, polled is simpler; for production use, interrupt-driven avoids CPU spin-wait.
- **Script-based workspace**: AMD provides a `unified_workspace.py` reference script for headless platform + application creation from XSA.

### Code Example
```c
/* Minimal AXI-BRAM bare-metal read/write test pattern */
#include "xil_printf.h"
#include "xil_io.h"
#include "sleep.h"

#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL
#define PATTERN     0xDEADBEEFUL

int test_bram(u32 base, const char *name) {
    u32 readback;

    /* Write pattern */
    Xil_Out32(base + 0x00, PATTERN);
    Xil_Out32(base + 0x04, ~PATTERN);

    /* Ensure write completes before read (data memory barrier) */
    dmb();

    /* Read back and verify */
    readback = Xil_In32(base + 0x00);
    if (readback != PATTERN) {
        xil_printf("FAIL: %s offset 0x00 expected 0x%08X got 0x%08X\r\n",
                   name, PATTERN, readback);
        return -1;
    }

    readback = Xil_In32(base + 0x04);
    if (readback != ~PATTERN) {
        xil_printf("FAIL: %s offset 0x04 expected 0x%08X got 0x%08X\r\n",
                   name, ~PATTERN, readback);
        return -1;
    }

    xil_printf("PASS: %s\r\n", name);
    return 0;
}

int main(void) {
    xil_printf("KV260 AXI-BRAM Test\r\n");
    test_bram(BRAM0_BASE, "BRAM0");
    test_bram(BRAM2_BASE, "BRAM2");
    return 0;
}
```

### Relevance to Your Project
Add a `dmb()` (data memory barrier) between your `Xil_Out32` and `Xil_In32` calls to prevent the Cortex-A53's out-of-order engine from reordering the AXI transactions. This is a common source of intermittent FAIL results in AXI-BRAM tests that pass in simulation. Also verify `standalone_stdout = psu_uart_1` in your BSP settings — if it defaults to `psu_uart_0`, xil_printf output will go to the wrong UART.

## XDC Timing Constraints

### Key Findings
- **`set_input_delay`**: Constrains logic from input ports to the first register stage; this associates the input port with a clock and lets Vivado compute setup/hold margins. The `-max` and `-min` forms constrain setup and hold paths separately.
- **`set_output_delay`**: For paths from the last register to output ports. If `set_max_delay` is also on the same port, the output delay value is folded into the max_delay computation.
- **`set_clock_groups`**: By default, Vivado times all paths between all clocks. Use `-asynchronous` to relax cross-clock-domain paths between the PS clock (pl_clk0 at 100 MHz) and any PL clocks. If you have a generated clock on the PL side, declare the groups explicitly.
- **Ordering**: `set_clock_groups` has minimal runtime impact; constraint ordering is flexible for this command.
- **`set_false_path`**: Use for signals that cross async clock domains without synchronizers (not recommended in production but common during early debug).

### Code Example
```tcl
# kv260_top.xdc — timing constraints for Kria KV260 AXI-BRAM demo

# Primary PS clock (driven by Zynq PS block output pl_clk0)
create_clock -period 10.000 -name clk_pl_0 [get_pins \
  zynq_ultra_ps_e_0/inst/PS8_i/PLCLK[0]]

# If you generate a secondary PL clock (e.g. 200 MHz from MMCM)
# create_clock -period 5.000 -name clk_pl_fast [get_pins mmcm_i/CLKOUT0]

# Declare PS and PL clocks as asynchronous if they come from different sources
# (Omit this if all logic runs on pl_clk0 only — no CDC required)
# set_clock_groups -asynchronous \
#   -group [get_clocks clk_pl_0] \
#   -group [get_clocks clk_pl_fast]

# BRAM address/data outputs to PL (internal paths — no I/O delay needed)
# For external IOs (e.g. debug headers), add:
# set_output_delay -clock clk_pl_0 -max 2.0 [get_ports dbg_*]
# set_output_delay -clock clk_pl_0 -min 0.5 [get_ports dbg_*]
```

### Relevance to Your Project
For a pure PS-to-PL AXI-BRAM design with no external IOs, the minimum viable XDC is just the `create_clock` on `pl_clk0`. Add `set_clock_groups -asynchronous` only if you later add a second clock domain. Timing closure failures on the AXI-BRAM path are usually caused by missing or incorrect `pl_clk0` constraints rather than I/O delays.

## Kria KV260 / K26 SoM

### Key Findings
- **SOM connectors**: SOM240_1 carries MIO signals, PS-GTR, HPIO/HDIO subset, and SOM power (shared between K26 and K24). SOM240_2 adds extra HPIO, HDIO, and GTH transceivers (K26 only).
- **MIO bank assignments (DS987)**: Bank 500: QSPI (MIO[5:0]), eMMC (MIO[23:13]), I2C (MIO[25:24]). Bank 501: PMU power-management pins (MIO[34:32]) + user I/O. Bank 502: user I/O. All three MIO banks are powered at **1.8V** by the SOM.
- **Power**: The SOM derives all SoC rails from a single +5V input. PL I/O supply voltages (VCCO) come from the carrier card (the KV260 starter kit provides 3.3V/1.8V rails via its carrier).
- **Boot flow**: BOOT.BIN on QSPI is the primary boot device. For bare-metal development, you can boot from JTAG directly — no BOOT.BIN required.
- **Supported tools**: DS986 lists Vivado 2025.1 as a supported tool version for the KV260 Starter Kit.
- **PMU overlay**: The KV260 and KR260 use different PMU overlay configurations (KR260 adds GEM0/GEM1 Ethernet from the carrier card). This affects power sequencing; use the correct overlay for the KV260.

### Code Example
```tcl
# KV260 Starter Kit board constraint — UART mapped through carrier USB bridge
# MIO 24/25 on KV260 carrier card connect to MIO UART1 (PS UART)
# This is NOT a PL XDC constraint; it is configured in the Zynq PS block:

# In create_bd.tcl — configure PS UART1 on MIO:
set_property -dict [list \
  CONFIG.PSU__UART1__PERIPHERAL__ENABLE {1} \
  CONFIG.PSU__UART1__PERIPHERAL__IO {MIO 24 .. 25} \
] [get_bd_cells zynq_ultra_ps_e_0]

# PL IO bank VCCO — must match carrier card supply voltage
# KV260 carrier provides 3.3V on HD bank 65 (connector pins)
set_property IOSTANDARD LVCMOS33 [get_ports <your_pl_port>]
set_property PACKAGE_PIN <pin>    [get_ports <your_pl_port>]
```

### Relevance to Your Project
Your bare-metal demo targets USB-UART output. Confirm the PS block in your `create_bd.tcl` configures UART1 on MIO 24–25 (the path to the KV260's USB-UART bridge). If you accidentally configure UART0 or use the wrong MIO pins, `xil_printf` output will be silent even though the code runs correctly — a common debug trap on first bring-up.

## AMD/Xilinx Tool Updates (2025.x)

### Key Findings
- **Vivado 2025.1 new devices**: Versal AI Edge Series Gen 2, Versal Prime Series Gen 2, and Spartan UltraScale+ are now supported.
- **Unified Selective Device Installer**: Install only specific Versal device families, reducing download size significantly.
- **New AXI Switch IP**: Fully customizable RTL-based block for bridging AXI interfaces and widths. Caveat: **not supported in IP Integrator block diagrams** — for RTL-only designs.
- **IP Integrator improvements**: New dedicated "Clocking and Reset" and "Interrupt and AXI-4 Lite" views; new Pblock planner in Vivado 2025.1.
- **Known issue — HBM timing (HBM-based boards only)**: Vivado 2025.1 adds `DONT_TOUCH` to HBM model, making timing closure harder. AMD acknowledged the issue; fix targeted for future release. Does NOT affect KV260 (no HBM).
- **Single-file download deprecated**: The single-file download option for the installer is being removed starting from Vivado 2025.2.
- **Embedded 2025.1 component upgrades**: Yocto Scarthgap 5.0.8, Xen 4.20, u-boot 2025.01, updated host OS support.
- **KV260 BSP 2025.1**: `xilinx-kv260-starterkit-v2025.1-05221048.bsp` is the released BSP file for 2025.1.
- **Vitis Unified IDE bare-metal template**: Vitis 2025.1 tutorial XD260 documents creating a bare-metal platform component from XSA — the starting point for custom Kria applications.

### Code Example
```python
# unified_workspace.py — AMD reference script pattern (XD260 tutorial)
# Creates a Vitis Unified IDE workspace from an XSA file
# Run with: vitis -s unified_workspace.py

import vitis

client = vitis.create_client()
client.set_workspace(path="./workspace")

# Create platform from XSA exported by Vivado
platform = client.create_platform_component(
    name       = "kv260_platform",
    hw_design  = "./kv260_top_wrapper.xsa",
    os         = "standalone",
    cpu        = "psu_cortexa53_0"
)
platform.build()

# Create bare-metal application from hello_world template
app = client.create_app_component(
    name     = "axi_bram_test",
    platform = "./workspace/kv260_platform/export/kv260_platform/kv260_platform.xpfm",
    domain   = "standalone_psu_cortexa53_0"
)
# Copy/link your sources instead of using template
client.vitis_logger().info("Workspace ready — add sources manually")
client.close()
```

### Relevance to Your Project
Upgrading to Vivado/Vitis 2025.1 from an older version will require re-generating the XSA and re-creating the Vitis platform component (the new Unified IDE flow). The KV260 BSP for 2025.1 is confirmed available. The new IP Integrator AXI-4 Lite view may simplify debugging your PS-to-BRAM address mapping during development.
