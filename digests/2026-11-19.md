# FPGA Research Digest - 2026-11-19

## Executive Summary
- **AXI-Lite deadlock risk**: VALID must never depend on READY from the slave — the most common AXI-Lite protocol violation seen in Xilinx designs; registering READY on the slave side avoids combinational loops and helps timing closure.
- **AXI Interconnect deprecation**: AMD is deprecating the legacy AXI Interconnect IP in favor of SmartConnect v1.0; migration is now recommended for all UltraScale+ designs, including Kria KV260.
- **Vivado 2025.1 non-project TCL flow**: The 2025.1 UG994 non-project script pattern (read_bd → make_wrapper → read_xdc → synth_design → impl_design → write_bitstream) is fully documented; use it to automate your KV260 build in CI/CD.
- **xil_printf limitation — no %f**: xil_printf in the standalone BSP does not support floating-point formatting; split float values into integer and fractional parts before printing to avoid silent format errors.
- **KV260 PL clocks come exclusively from PS**: The programmable logic has no independent oscillator; pl_clk0 (default 100 MHz) must be enabled in the PS IP and is the only reliable fabric clock source for the BRAM design.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings
- **VALID must not depend on READY**: The ARM AXI spec forbids a master from waiting for READY before asserting VALID. Any slave that waits for VALID before asserting READY is legal, but a master doing the reverse can deadlock with compliant slaves. This is the single most common AXI-Lite bug observed in Xilinx forum posts.
- **Payload stability after VALID**: Once a source raises VALID, it must hold VALID and all associated payload signals (AWADDR, WDATA, etc.) stable until the cycle in which both VALID and READY are sampled high. Dropping WDATA mid-transfer causes silent data corruption that often surfaces only under load.
- **Combinational READY→VALID paths cause timing violations**: Routing a slave's READY directly into the master's VALID logic creates a combinational loop that shows up as a hold-time violation or false path in Vivado's timing report. The recommended fix is to register READY in the slave (a "delayed ready" pattern) — adds one cycle latency but ensures clean timing closure.
- **Transfer completes on the rising clock edge where both VALID and READY are high**: Testing should cover three orderings: VALID precedes READY, READY precedes VALID, and both asserted simultaneously.
- **AXI-Stream TLAST and backpressure**: For streaming paths, TLAST marks the end of a packet frame; the protocol places no upper bound on how long a consumer can hold TREADY low. Downstream backpressure must be absorbed by a FIFO or flow-control mechanism upstream; never stall the PS DMA port without buffering.
- **XPM_FIFO_AXIS in Vivado 2025.1**: The `XPM_FIFO_AXIS` Xilinx Parameterized Macro (UG974) provides a fully compliant AXI-Stream FIFO that can be instantiated directly in VHDL without the IP catalog — useful when you want reproducible, source-controlled BRAM-backed buffering.

### Code Example
```vhdl
-- AXI-Lite slave: register READY to avoid combinational loops
-- VALID can depend on this registered value safely
process(clk)
begin
  if rising_edge(clk) then
    if rst = '1' then
      s_axi_awready_r <= '0';
    elsif s_axi_awvalid = '1' and s_axi_awready_r = '0' then
      s_axi_awready_r <= '1';  -- accept on next cycle
    else
      s_axi_awready_r <= '0';
    end if;
  end if;
end process;
s_axi_awready <= s_axi_awready_r;
```

### Relevance to Your Project
Your `kv260_top.vhd` top-level wraps two AXI BRAM controllers (BRAM0 at `0xA0000000`, BRAM2 at `0xA0010000`). The PS Cortex-A53 drives the AXI-Lite master from the M_AXI_HPM0_FPD port. Any READY/VALID ordering issue in those controllers will manifest as a hang in `main.c`'s write-then-readback loop. If you observe a FAIL response or the program stalls after the first write, instrument VALID/READY on the BRAM controller's S_AXI port in ILA (Integrated Logic Analyzer) to check for a deadlock condition.

## Vivado Block Design / IP Integrator

### Key Findings
- **AXI Interconnect is being deprecated**: AMD now recommends migrating from AXI Interconnect v2.1 to SmartConnect v1.0 for all UltraScale+ and newer families. Future Vivado releases will not carry forward the old interconnect. If your block design uses the old IP, regenerate with SmartConnect now to stay on a supported path.
- **Deselect unused HPM ports**: For single-master designs (one PS-to-PL path), deselect `AXI HPM1 FPD` in PS-PL Configuration → Master Interface to reduce resource usage and simplify the address map.
- **Connection Automation resolves most wiring**: After placing the PS IP and your AXI BRAM Controller instances, run `Run Connection Automation` to let Vivado wire `M_AXI_HPM0_FPD → SmartConnect → S_AXI`. Manually verify the resulting address segments in the Address Editor.
- **IP Upgrade in block design**: When opening a project from a previous Vivado version, use `upgrade_ip`, then `reset_target`, `generate_target`, and `make_wrapper` to regenerate all IP outputs before re-running implementation.
- **Validate before generating**: Always run `validate_bd_design` in Tcl (or the GUI's Validate Design button) before `generate_target`. Critical interface mismatches surface here rather than as cryptic synthesis errors downstream.

### Code Example
```tcl
# Validate and regenerate block design products
open_bd_design [get_files *.bd]
validate_bd_design
generate_target all [get_files *.bd]
make_wrapper -files [get_files *.bd] -top
add_files -norecurse [glob ./hdl_wrapper/*.vhd]
set_property top kv260_top_wrapper [current_fileset]
```

### Relevance to Your Project
Your `create_bd.tcl` builds the entire block design programmatically. After upgrading to Vivado 2025.1, run the upgrade flow above before rebuilding. If the script currently uses `axi_interconnect`, replace it with `axi_smartconnect` to avoid deprecation warnings and ensure forward compatibility.

## Vivado TCL Scripting

### Key Findings
- **Non-project mode is fully supported in 2025.1 (UG994)**: The recommended non-project Tcl sequence is: `read_bd` (or source a BD-creation script) → `make_wrapper` → `read_xdc` → `synth_design` → `opt_design` → `place_design` → `route_design` → `write_bitstream`. No project file is created; you manage all files explicitly.
- **OOC block designs must be pre-generated or use global synthesis**: If the block design is set for Out-of-Context synthesis, generate it first with `generate_target all`. Alternatively, use global synthesis mode (`-mode global` on `synth_design`) to avoid the OOC pre-generation requirement.
- **`write_bd_tcl` for round-trip scripts**: After editing a block design interactively, run `write_bd_tcl -force <path/to/script.tcl>` to export a reproducible script. This regenerates your `create_bd.tcl` with correct instance names and property values for the current Vivado version.
- **`assign_bd_address` auto-assigns unmapped segments**: Call it after all IP cells are connected and before `generate_target`. It maps every unmapped address segment to an available slot in the connected master's address space. Use `-offset` and `-range` to pin specific addresses (`0xA0000000`, `0xA0010000`) rather than relying on auto-placement.
- **Version guard in scripts**: Include a version check at the top of `create_bd.tcl` to warn users running mismatched Vivado versions before the script proceeds.

### Code Example
```tcl
# Pin BRAM addresses explicitly after auto-assign
assign_bd_address
set_property offset 0xA0000000 [get_bd_addr_segs {ps_i/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property range  64K         [get_bd_addr_segs {ps_i/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property offset 0xA0010000 [get_bd_addr_segs {ps_i/Data/SEG_axi_bram_ctrl_2_Mem0}]
set_property range  64K         [get_bd_addr_segs {ps_i/Data/SEG_axi_bram_ctrl_2_Mem0}]
```

### Relevance to Your Project
Your `create_bd.tcl` controls address assignment for BRAM0 and BRAM2. Explicitly pinning `0xA0000000` and `0xA0010000` as shown above ensures `main.c`'s hardcoded base addresses always match the hardware map, regardless of which order IP cells are created or what other segments exist.

## Vitis Bare-Metal / Standalone

### Key Findings
- **`xil_printf` does not support `%f`**: The lite-weight printf implementation in the standalone BSP omits floating-point formatting. Attempting `xil_printf("%f", val)` either prints nothing or garbage. Workaround: cast to `int` integer and fractional parts separately.
- **UART BSP settings must match hardware**: Standalone `stdin`/`stdout` BSP parameters must point to the actual UART instance (`psu_uart_1` on KV260). If the terminal is blank after a successful download, check the BSP settings and regenerate.
- **Stack defaults are very small**: UG1400 (2025.2) documents the default `_STACK_SIZE` as 100 words (400 bytes) and default `_HEAP_SIZE` as 0. Any non-trivial application needs both increased explicitly in `lscript.ld`.
- **Regenerate BSP after changing parameters**: Any change to BSP settings (UART selection, cache, TTC) requires clicking "Regenerate BSP Sources" before rebuilding the application; stale BSP code will silently use old settings.
- **2025.1 embeddedsw release notes**: The 2025.1 open-source component release notes for standalone include only minor cleanup (unused variables removed from `xil_printf.c`); no breaking API changes were introduced.

### Code Example
```c
/* xil_printf workaround for float values */
#include "xil_printf.h"

void print_float(float val) {
    int   integer_part  = (int)val;
    int   fractional    = (int)((val - integer_part) * 1000);
    xil_printf("%d.%03d\r\n", integer_part, fractional);
}

/* Bare-metal AXI-Lite write helper */
#define BRAM0_BASE 0xA0000000UL
#define BRAM2_BASE 0xA0010000UL

static inline void bram_write32(uintptr_t base, u32 offset, u32 val) {
    *(volatile u32 *)(base + offset) = val;
    /* Ensure write completes before read-back */
    dsb();
}
```

### Relevance to Your Project
`main.c` relies on `xil_printf` for PASS/FAIL output and on direct memory-mapped writes to `0xA0000000` and `0xA0010000`. Confirm `lscript.ld` allocates sufficient stack (at least 4 KB) and that the BSP `stdout` is set to `psu_uart_1`. Add a `dsb()` data synchronization barrier after each BRAM write before the read-back to avoid Cortex-A53 store-buffer races that could produce a spurious FAIL.

## XDC Timing Constraints

### Key Findings
- **`set_input_delay` / `set_output_delay` define the external environment**: These constraints describe the propagation delay outside the FPGA (from upstream source or to downstream destination). Vivado uses them to close setup and hold checks at I/O ports. For AXI-Lite signals that cross the PS-PL boundary, AMD handles PL-side timing automatically via PS IP constraints; custom XDC constraints are only needed for user I/O pins on PL bank pins.
- **Negative hold-side values are valid**: `set_output_delay -min` with a negative value is legal and common in source-synchronous SDR interfaces where data is launched on the same edge as the clock.
- **Removing an XDC file from one constraint set removes it from others in 2025.1**: This is a confirmed known issue in Vivado 2025.1. Workaround: duplicate the file per constraint set rather than sharing it, or use `set_property USED_IN` to scope a constraint file.
- **`report_timing -to [all_outputs]`**: Run after implementation to verify no unconstrained output paths remain.
- **Clock groups for PS-PL boundary**: For the KV260, the PS drives `pl_clk0` through the PS IP. Vivado's block design wrapper automatically creates the clock object; no manual `create_clock` is needed for `pl_clk0` itself, but any BUFG-driven clocks derived from it may need explicit `create_generated_clock` entries.

### Code Example
```tcl
# Example: constrain a user LED output driven by fabric logic
# pl_clk0 is defined automatically by the PS IP wrapper
# Data valid window example: 2ns setup, 1ns hold relative to rising pl_clk0
set_output_delay -clock [get_clocks pl_clk0] -max  2.0 [get_ports led_out]
set_output_delay -clock [get_clocks pl_clk0] -min -1.0 [get_ports led_out]

# Treat PS-PL AXI interface clocks as asynchronous to external clocks
set_clock_groups -asynchronous \
    -group [get_clocks pl_clk0] \
    -group [get_clocks -of_objects [get_pins */clk_wiz_0/clk_out1]]
```

### Relevance to Your Project
The KV260 AXI-BRAM demo drives no external synchronous I/O, so only `pl_clk0` constraints apply. If you add user LEDs, buttons, or PMOD signals in a future revision, apply `set_output_delay`/`set_input_delay` as above. Watch for the 2025.1 known issue if you reorganize constraint sets during project iteration.

## Kria KV260 / K26 SoM Platform Specifics

### Key Findings
- **PL clocks originate entirely in the PS**: There is no independent PL oscillator. `pl_clk0` (100 MHz by default) is generated by the PS IP and must be explicitly enabled in PS-PL Configuration. The PS must be initialized before any PL logic runs.
- **Boot order**: Primary boot from K26 SOM on-module QSPI flash; secondary fallback to microSD card (slot J11). JTAG is available on J3 (direct) and J4 (via FTDI, also provides USB-UART).
- **MIO bank layout**: Bank 500 serves onboard SOM peripherals (QSPI, SPI, I2C, eMMC). Bank 501 and 502 provide user-defined I/O for carrier card expansion. PL-attached connectors (Pmod headers) route to PL fabric banks, not MIO — assign them in XDC to PL bank pins, not MIO pins.
- **Power-on reset sequence**: A voltage monitor holds the PS power-on reset line low until all SOM rails are stable. This automatic sequencing means the BRAM design should be reliably ready when the Cortex-A53 begins executing after power-up — no explicit software delay is needed before the first AXI write.
- **PL-to-PS interrupt routing**: PL interrupts map to GIC SPI interrupt `121 + n` (n = PL interrupt index 0–15). For the BRAM demo, no PL interrupt is needed, but this mapping is critical if you add an ILA trigger-to-processor path later.
- **Boot FW versions (2025/2026)**: K26 Boot FW 1.06 targets the 2025.2 SDT flow. KV260 Boot FW 1.08 targets the 2026.6 component stack. Ensure your BOOT.BIN is built against the matching PDI/FSBL version.

### Code Example
```tcl
# PS IP configuration for KV260 single-clock bare-metal design
# In create_bd.tcl, after create_bd_cell for the Zynq UltraScale+ PS:
set_property -dict [list \
    CONFIG.PSU__USE__M_AXI_GP0        {1} \
    CONFIG.PSU__USE__M_AXI_GP1        {0} \
    CONFIG.PSU__FPGA_PL0_ENABLE       {1} \
    CONFIG.PSU__CRL_APB__PL0_REF_CTRL__FREQMHZ {100} \
    CONFIG.PSU__UART1__PERIPHERAL__ENABLE {1} \
    CONFIG.PSU__UART1__PERIPHERAL__IO    {MIO 36 .. 37} \
] [get_bd_cells zynq_ultra_ps_e_0]
```

### Relevance to Your Project
Disabling HPM1 FPD (`PSU__USE__M_AXI_GP1 {0}`) simplifies the address space to a single master, which is all the dual-BRAM demo requires. Explicitly setting `PL0_REF_CTRL__FREQMHZ` to 100 ensures repeatable timing closure. UART1 on MIO 36–37 matches the KV260 carrier card's FTDI routing that provides the USB-UART visible as `/dev/ttyUSB1` on the host.

## AMD/Xilinx Tool Updates — Vivado/Vitis 2025.x

### Key Findings
- **Vivado 2025.1 released June 2025**: New features include support for AMD Spartan UltraScale+ and next-generation Versal devices, a unified selective device installer for Versal, a new AXI Switch IP, and a GUI for `report_dfx_summary`.
- **Known issue — XDC file sharing across constraint sets**: Removing an XDC file from one constraint set removes it from all others in 2025.1. Workaround: duplicate constraint files per set.
- **Known issue — Python xsdb interface unavailable**: The Python `xsdb` interface is broken in Vivado Lab Tools 2025.1 and earlier. Use Tcl xsdb directly for TCF-based debugging.
- **Known issue — ECO flow clock routing**: An ECO flow clock routing problem is documented for 2025.1; affects post-route ECO runs. Avoidance: perform logic edits before full route rather than relying on ECO.
- **AXI Interconnect IP deprecation confirmed**: AMD's deprecation announcement covers all UltraScale+ designs. SmartConnect v1.0 replacement is recommended immediately.
- **embeddedsw 2025.1**: Minor cleanup only; no breaking API changes for standalone (baremetal) BSP drivers.
- **Vivado 2026.1 is now available**: If you are starting a new project, 2026.1 is the current release. The 2025.1 release is now a "legacy" version. New silicon support in 2026.x targets Versal Premium Gen2 and AI Edge Gen2.

### Code Example

# Non-project mode build script skeleton for Vivado 2025.1
# Run with: vivado -mode batch -source build.tcl

# Source the BD creation script (from create_bd.tcl)

### Relevance to Your Project
Switching to this non-project Tcl build script eliminates the `.xpr` project file from your repository and makes the full `kv260-axi-bram-demo` build reproducible with a single Vivado batch command. Combine it with `create_bd.tcl` and your XDC file for a fully scriptable CI-ready flow. Generate the `.xsa` platform file at the end so Vitis can directly consume it without a GUI step.
