## Executive Summary
- **VALID must never wait on READY** — the most commonly cited AXI bug across both vendor and community sources (zipcpu, AMD Adaptive Support, edaboard) is conditioning a master's VALID assertion on the slave's READY state, which creates a circular dependency and can deadlock the bus. This applies to any hand-rolled AXI-Lite logic you might add around the stock `axi_bram_ctrl` cores.
- **Simultaneous AW/AR acceptance is a classic slave bug**: allowing `AWVALID && AWREADY` and `ARVALID && ARREADY` to both fire in the same cycle without separately latching/buffering each can silently drop one of the two transactions — worth checking if you ever add a custom AXI-Lite control/status register block alongside the BRAM controllers.
- **Vivado's Address Editor enforces alignment, not just non-overlap**: a BRAM controller's mapped range must be a power-of-two-aligned block (e.g., a 64KB range needs 16 trailing zero bits), and address 0 should never be assigned to a peripheral since some drivers treat it as "unmapped." Useful to keep in mind if BRAM0/BRAM2 addresses are ever resized.
- **`xil_printf` silently going dark is almost always a UART instance mismatch** in the standalone BSP, not a hardware fault — the Vitis Unified IDE platform component can default `stdin`/`stdout` to the wrong UART (e.g., UART0 instead of the JTAG/USB-UART-bridge UART1), which looks identical to "the board froze" over a USB-UART terminal.
- **Vivado/Vitis 2025.1 is solid, supported ground for this toolchain** — IP-level fixes in 2025.1 (e.g., AXI Ethernet Buffer PTP handling, dynamic-addressing register updates, a peripheral/cache-AXI deadlock fix under frequency-optimized pipelines) are unrelated to `axi_bram_ctrl`/Zynq PS, and a mid-2026 community guide confirms active bare-metal KV260 work on the 2025.x line — no urgent upgrade pressure.

## AXI Protocol / AXI-Lite / AXI-Stream
### Key Findings
- The fundamental AXI handshake rule: READY may be withheld arbitrarily by the receiver, but VALID must never be made conditional on having first observed READY — the spec requires the active side to assert VALID whenever it wants a transfer, regardless of READY's current state, precisely to avoid a circular "I'll go first if you go first" deadlock.
- A slave that lets `AWVALID && AWREADY` and `ARVALID && ARREADY` both complete in the same clock cycle without independently latching each request can lose one of the two transactions if its internal pipeline only tracks a single in-flight operation.
- AW and W channel handshakes are independent and need not occur in the same cycle; a slave must wait for *both* to complete (which may arrive in either order, or interleaved) before issuing BVALID/BRESP.
- For AXI-Stream specifically: TKEEP may only go "sparse" (less than all-ones) on the TLAST beat of a packet, or at the very start of a packet when DRE/unaligned-transfer support is enabled — using sparse TKEEP mid-packet on IP that doesn't expect it is a common silent-corruption bug. IP using the AXI4-Stream Video Protocol subset ignores TKEEP/TSTRB entirely and expects them tied to all-ones if the ports exist.
- Functional testbenches that always drive READY high never exercise backpressure; the most commonly missed case in informal AXI verification is a master holding BREADY/RREADY low and checking that the slave correctly drops AWREADY/WREADY or ARREADY in response.

### Code Example
```vhdl
-- AXI-Lite write-address acceptance that asserts AWREADY independent of
-- any downstream condition, and never gates the BRAM-side write enable
-- on AWREADY having been "confirmed" by the master — avoids the
-- VALID-waits-for-READY antipattern in any hand-written AXI-Lite logic.
process(s_axi_aclk)
begin
  if rising_edge(s_axi_aclk) then
    if s_axi_aresetn = '0' then
      awready_r  <= '1';
      aw_latched <= '0';
    else
      if s_axi_awvalid = '1' and awready_r = '1' then
        awaddr_r   <= s_axi_awaddr;
        aw_latched <= '1';
        awready_r  <= '0';        -- back off until this AW is consumed
      elsif aw_latched = '1' and w_latched = '1' then
        -- both AW and W observed independently; safe to issue BRESP
        aw_latched <= '0';
        awready_r  <= '1';
      end if;
    end if;
  end if;
end process;

s_axi_awready <= awready_r;
```

### Relevance to Your Project
Both BRAM0 and BRAM2 sit behind the stock `axi_bram_ctrl` IP, which already implements correct AXI4-Lite handshaking, so none of the above are live bugs in the current design. They matter the moment you add a hand-written AXI-Lite peripheral (e.g., a control/status register or interrupt-flag block) instead of reusing vendor IP — review any such block against the VALID-before-READY rule and the simultaneous-AW/AR-acceptance bug before trusting it on hardware.

## Vivado Block Design / IP Integrator
### Key Findings
- Connection/Block Automation auto-instantiates supporting infrastructure (AXI Interconnect or SmartConnect, Processor System Reset, sometimes a Block Memory Generator) and wires it to the PS — convenient for prototyping, but anything it inserts has to be accounted for if you later rebuild the same design by hand from `create_bd.tcl`.
- Address Editor rules worth remembering: an address range must be aligned (a 4K range needs 12 trailing zero bits in its base address), address ranges between segments cannot overlap, and mapping a peripheral to address 0 should be avoided since some software drivers special-case address 0 as "not configured."
- After any manual peripheral address reassignment, re-run `validate_bd_design` — it's the step that actually checks parameter propagation (AXI4 vs AXI4-Lite link type, data-width negotiation, BRAM operating-mode propagation) across connections; `regenerate_bd_layout` only redraws the graphical layout and performs zero connectivity checking.
- `write_bd_tcl -no_ip_version -hier_blks` exports a block design as a reproducible Tcl script while pinning to the latest available IP version rather than baking in whatever version happened to be installed at export time — relevant if `create_bd.tcl` is regenerated from a live block design rather than maintained by hand.

### Code Example
```tcl
# Non-interactive validate/regenerate/save sequence, safe to drop into
# a batch build right before generate_target / write_bitstream.
open_bd_design [get_files kv260_bd.bd]
validate_bd_design
regenerate_bd_layout
save_bd_design

if {[get_msg_config -count -severity "Critical Warning"] > 0 || \
    [get_msg_config -count -severity "Error"] > 0} {
    puts "ERROR: block design validation reported errors/critical warnings, aborting"
    exit 1
}
```

### Relevance to Your Project
Your `create_bd.tcl` wires the PS, interconnect, and two `axi_bram_ctrl` instances explicitly rather than relying on GUI automation, which is the right call for a script under version control that must reproduce the same BRAM0 (`0xA0000000`)/BRAM2 (`0xA0010000`) address map every build. If the block design ever needs to be edited interactively in the GUI and re-exported, prefer `write_bd_tcl -no_ip_version` over a raw "Write Tcl" project export to keep the script diffable and IP-version-stable.

## Vivado TCL Scripting
### Key Findings
- Non-Project Mode keeps the design entirely in memory with no `.xpr` written to disk — the script is solely responsible for source ordering and there's no Vivado-managed "stale source" detection; every invocation re-reads sources from scratch unless you script your own checkpointing between stages.
- Standard non-project build sequence: `read_vhdl`/`read_verilog` → `read_xdc` → `synth_design -top <name> -part <part>` → `opt_design` → `place_design` → (optional `phys_opt_design`) → `route_design` → `write_bitstream`, with `write_checkpoint` calls between stages so a CI run can resume from the last good checkpoint instead of re-synthesizing.
- `vivado -mode batch -source script.tcl -tclargs <args>` is the standard headless invocation for CI: it runs to completion and exits, vs. `-mode tcl` which drops into an interactive prompt for script development.
- A script is the only way to guarantee a build server (Jenkins, GitHub Actions runner, etc.) produces bit-identical output every run — project settings, IP configuration, and constraints all live as text files in version control rather than inside a binary `.xpr`/IP-cache state.

### Code Example
```tcl
# Build pattern for two AXI BRAM controllers with explicit, version-stable
# address assignment matching BRAM0/BRAM2 in this project.
create_bd_cell -type ip -vlnv xilinx.com:ip:axi_bram_ctrl:4.1 axi_bram_ctrl_0
create_bd_cell -type ip -vlnv xilinx.com:ip:axi_bram_ctrl:4.1 axi_bram_ctrl_2

foreach {ctrl base} {axi_bram_ctrl_0 0xA0000000 axi_bram_ctrl_2 0xA0010000} {
    connect_bd_intf_net [get_bd_intf_pins zynq_ultra_ps_e_0/M_AXI_HPM0_FPD] \
                         [get_bd_intf_pins ${ctrl}/S_AXI]
    set_property offset $base \
        [get_bd_addr_segs "zynq_ultra_ps_e_0/Data/SEG_${ctrl}_Mem0"]
}

validate_bd_design
save_bd_design
```

### Relevance to Your Project
This pattern is consistent with how `create_bd.tcl` reportedly builds the two-BRAM layout. If a third BRAM or AXI-Lite peripheral is added later, extending the `foreach` table above (rather than hand-copying another connect/offset block) keeps address assignment centralized in one place and reduces the chance of an off-by-one in the base address.

## Vitis Bare-Metal / Standalone
### Key Findings
- `xil_printf` supports only `%d`, `%l`, `%x`, `%c`, `%s` (no `%f`) — it deliberately trades format richness for a much smaller code/stack footprint than libc `printf`, which matters when DDR/OCM allocation is tight in a minimal bare-metal app.
- The Vitis Unified IDE's platform component populates BSP `stdin`/`stdout` defaults that don't always match the carrier's USB-UART bridge — a commonly hit case is the BSP defaulting to UART0 when the JTAG/USB-UART bridge is actually on UART1 (`psu_uart_1`), which makes PASS/FAIL output vanish even though the application runs correctly. Fix is in `platform component > psu_cortexa53_0 > standalone > Board Support Package > standalone`, setting both `stdin` and `stdout`.
- GIC interrupt setup on Zynq UltraScale+ is a strict two-step process: registering and connecting the handler (`XScuGic_CfgInitialize`, `Xil_ExceptionRegisterHandler`, `XScuGic_Connect`) is necessary but not sufficient — you must also separately call `XScuGic_Enable(&GicInst, <intr_id>)`, or the handler is "registered but silent" with no error indication.
- `lscript.ld` is directly editable in the Vitis IDE under `<app>/src/lscript.ld` and defines where `.text`/`.data`/`.bss`/heap land in OCM/DDR; after re-exporting hardware (a new XSA) for the same app, re-check the linker script's memory region base/size, since a stale region from an older hardware platform can silently truncate the heap or place sections outside valid DDR.

### Code Example
```c
#include "xil_printf.h"
#include "xparameters.h"
#include "xil_io.h"

#define BRAM0_BASEADDR XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR /* 0xA0000000 */
#define BRAM2_BASEADDR XPAR_AXI_BRAM_CTRL_1_S_AXI_BASEADDR /* 0xA0010000 */

int test_bram(u32 base, const char *name) {
    u32 pattern = 0xA5A5A5A5;
    Xil_Out32(base, pattern);
    u32 readback = Xil_In32(base);
    if (readback == pattern) {
        xil_printf("%s: PASS (wrote 0x%x, read 0x%x)\r\n", name, pattern, readback);
        return 0;
    }
    xil_printf("%s: FAIL (wrote 0x%x, read 0x%x)\r\n", name, pattern, readback);
    return 1;
}
```

### Relevance to Your Project
This is the same write/readback/PASS-FAIL idiom described for `main.c`. If PASS/FAIL output ever stops appearing over USB-UART while the board otherwise seems to run, check the BSP's `stdout` UART selection before suspecting a hardware fault — it's a far more common cause than an actual AXI failure. The GIC two-step is only relevant if a future revision moves from polling to an interrupt-driven trigger (e.g., a timer or AXI GPIO "go" pin) for the BRAM test loop.

## XDC Timing Constraints
### Key Findings
- `set_input_delay`/`set_output_delay` model the external system-level delay relative to a clock edge at a primary I/O port; values can legitimately be negative depending on the data/clock phase relationship at the board level, so don't assume all delay numbers must be positive when translating a datasheet timing diagram into XDC.
- "Input delay -max" is effectively the driving device's clock-to-Q delay as seen at the FPGA pin, not literally the FPGA's own setup time — a frequent point of confusion when porting datasheet numbers directly into constraints.
- Every clock-domain crossing needs an explicit `set_clock_groups -asynchronous` declaration; an undeclared CDC is, by default, timed as if synchronous, which can either produce spurious timing failures (false negatives from over-constraining) or — more dangerously — falsely "pass" a path that's actually a metastability risk.
- Zynq UltraScale+-specific gotcha: assigning a clock root in the same clock region as a BUFG_GT driver can render outputs in certain other clock regions unroutable — a niche issue that only shows up once gigabit-transceiver-adjacent clocking is added to a design.

### Code Example
```tcl
# Board-level XDC additions only needed if direct PL I/O is added
# (not required for the current pure PS<->PL AXI-only BRAM path).
create_clock -period 8.000 -name pl_clk0 [get_ports pl_clk0_p]

set_input_delay  -clock pl_clk0 -max 1.5 [get_ports {ext_data[*]}]
set_input_delay  -clock pl_clk0 -min 0.3 [get_ports {ext_data[*]}]
set_output_delay -clock pl_clk0 -max 1.2 [get_ports {ext_ctrl[*]}]
set_output_delay -clock pl_clk0 -min -0.5 [get_ports {ext_ctrl[*]}]

set_clock_groups -asynchronous \
    -group [get_clocks -include_generated_clocks clk_fpga_0] \
    -group [get_clocks -include_generated_clocks pl_clk0]
```

### Relevance to Your Project
The design is purely PS-driven AXI on a single PS-generated FCLK domain feeding both BRAM controllers, so board-level `set_input_delay`/`set_output_delay` constraints don't apply today — those only matter once a signal crosses the board boundary through a physical I/O pin. The `set_clock_groups` guidance becomes relevant the instant a PL-side clock independent of the PS FCLK is added (e.g., a free-running oscillator feeding new logic in `kv260_top.vhd`).

## Kria KV260 / K26 SoM
### Key Findings
- Kria starter kits ship with boot firmware preloaded in QSPI defaulting to QSPI32 boot mode; the underlying selection is via the SOM's MODE[3:0] strapping pins, exposed on the KV260 starter carrier as a physical boot-mode switch, and documented boot-mode definitions live in the Zynq UltraScale+ TRM (UG1085) plus the Kria Carrier Card Design Guide (UG1091).
- The AMD-provided K26 board file encodes the SOM's required MIO configuration and a minimal hardware config sufficient to boot to Linux; custom carrier designs layer their own MIO/PL physical interfaces on top per UG1091 rather than fighting the board file's baseline.
- Since the 2022.1 Kria Linux images, the default "k26-starter-kits" bitstream has effectively no functional PL logic beyond an EMIO mapping for carrier fan control — a from-scratch bare-metal/PL design like this one is genuinely starting from near-empty fabric, not inheriting hidden default logic.
- The official documented baremetal AXI-BRAM reference flow (xilinx.github.io/kria-apps-docs) matches this project's shape closely: add an AXI BRAM Controller, run Connection Automation to tie its `S_AXI` to `M_AXI_HPM0_FPD`, set single-BRAM-interface mode, and explicitly deselect/disable any unused second HPM master port rather than leaving it dangling unconnected.
- A mid-2026 community guide ("Bare-metal 4K Streaming on KV260: The 2025.2 Guide") confirms the bare-metal + Vivado/Vitis 2025.x toolchain combination remains an actively maintained path for this exact board, so the 2025.1 toolchain in use here is well-supported, current ground.

### Code Example
```tcl
# PS configuration matching a single-HPM-master, BRAM0/BRAM2 pattern;
# explicitly disabling the unused second GP master avoids a common
# validate_bd_design critical-warning source (enabled-but-unconnected port).
set_property -dict [list \
    CONFIG.PSU__USE__M_AXI_GP0 {1} \
    CONFIG.PSU__USE__M_AXI_GP1 {0} \
    CONFIG.PSU__MAXIGP0__DATA_WIDTH {32} \
] [get_bd_cells zynq_ultra_ps_e_0]
```

### Relevance to Your Project
This matches the documented official Kria baremetal AXI-BRAM pattern almost exactly — both BRAM0 and BRAM2 feeding off `M_AXI_HPM0_FPD`. Worth confirming in `create_bd.tcl` that any unused second HPM master is explicitly disabled (`PSU__USE__M_AXI_GP1 {0}`) rather than merely unconnected, since an enabled-but-unconnected master is a frequently-ignored `validate_bd_design` critical warning.

## AMD/Xilinx Tool Updates
### Key Findings
- Vivado 2025.1 IP-level fixes include corrected PTP 1588 frame handling in the AXI Ethernet Buffer at the Buffer→MAC interface, an updated dynamic-addressing register-update path, a fix avoiding a potential deadlock between peripheral and cache-data AXI interfaces (frequency-optimized pipeline configurations only), and the GT Wizard Subsystem becoming the new GUI default for Versal devices — none of these touch `axi_bram_ctrl` or the Zynq UltraScale+ PS block directly.
- Vivado 2025.2 (the next release after the one this project uses) adds a new Pblock planner, an automatic Tcl migration script for old-to-new synthesis/implementation directives, simplified AXI wiring for SystemVerilog instances with automatic wrapper generation, and a new ultra-low-area `STRATEGY` mode for AXI Switch/AXI SmartConnect IP — relevant only if PL resource usage becomes a constraint on this design in the future.
- 2025.2 also changes the AMD IP configuration file format from XML to JSON (for better revision-control diffing and faster loading) and refreshes the IDE's look (new light/dark themes, revamped Welcome page) — worth knowing before assuming an older tutorial's screenshots still match a newer install.
- AXI BRAM Controller (PG078) v4.1 supports optional ECC in both single- and dual-port BRAM configurations (`C_ECC = 1`) — not needed today, but a known lever if BRAM reliability becomes a concern as test patterns scale up.

### Relevance to Your Project

No upgrade is needed; if/when 2025.2 is adopted, re-run `validate_bd_design` after the first open of the block design on the new toolchain, since IP re-customization prompts for `axi_bram_ctrl` and the Zynq UltraScale+ PS block are a routine part of cross-version bumps, and the new AXI SmartConnect ultra-low-area mode is worth evaluating only if PL resource pressure ever appears.
