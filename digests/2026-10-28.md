# FPGA Research Digest - 2026-10-28

## Executive Summary
- **AXI-Lite handshake bug in Vivado-generated slaves**: ZipCPU formal verification found protocol errors in Xilinx's own AXI-Lite slave template (2018.3 era, still unpatched in community use). Always verify RVALID/RDATA hold behavior and BREADY backpressure handling in any generated or custom slave — this directly affects your BRAM0 and BRAM2 AXI controllers.
- **K26 UART pinout**: Kria SOMs use UART1 for the PS console, not UART0. If your bare-metal `xil_printf` output is silent, your BSP STDIN/STDOUT is pointed at the wrong UART — update the standalone BSP UART device setting.
- **Boot mode is fixed to QSPI32**: There are no boot-mode switches on the KV260. The SOM ships factory-configured for QSPI32 boot. You cannot override this in hardware. Use JTAG for development, or program the QSPI flash for standalone boot.
- **Vivado 2025.2 new AXI Switch IP**: AMD added a new RTL-based AXI Switch with an ultra-low-area mode via `STRATEGY` parameter — relevant for adding future PL peripherals beyond your two BRAMs without redesigning the SmartConnect topology.
- **Constraint ordering matters for runtime**: AMD UG903 (2025.2) recommends placing clock definitions first, then `set_clock_groups`, then I/O delays, then timing exceptions — wrong ordering can cause silent constraint application failures that waste implementation runs.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings
- **RVALID must stay high until RREADY is asserted**: ZipCPU found that many AXI-Lite slave templates, including ones generated by Vivado, de-assert RVALID before the master accepts the data. This is a protocol violation that causes dropped reads under backpressure.
- **Never overwrite RDATA while RVALID is high**: An EDAboard thread on BRAM AXI controllers describes read data being corrupted when a new read request arrives before the master asserts RREADY. The fix: hold RVALID/RDATA until the transaction completes, then gate new reads.
- **BRAM output register adds one cycle latency**: When the BRAM IP's output register is enabled, the controller must account for an extra cycle between address presentation and valid data. Vivado's BRAM Controller IP handles this automatically, but custom wrappers must model it.
- **AXI Register Slice breaks long combinational paths**: Inserting a Register Slice (IP) on AXI buses between PL logic and the SmartConnect adds exactly one cycle of latency but can rescue timing on a congested implementation.
- **AXI-Lite has no burst support**: All transactions are single-beat. For your BRAM test pattern writes (`0xDEADBEEF`, etc.), AXI-Lite is correct. If you ever move to bulk transfer, switch to AXI4 full with bursting.

### Code Example
```vhdl
-- AXI-Lite read channel with correct hold behavior
-- RVALID must stay asserted until RREADY is seen
process(clk)
begin
  if rising_edge(clk) then
    if rst = '1' then
      s_axi_rvalid <= '0';
      s_axi_rdata  <= (others => '0');
    elsif s_axi_arvalid = '1' and s_axi_arready = '1' then
      -- Latch address and assert RVALID with data next cycle
      s_axi_rdata  <= bram_read_data;
      s_axi_rvalid <= '1';
    elsif s_axi_rvalid = '1' and s_axi_rready = '1' then
      -- Only deassert RVALID AFTER master accepts
      s_axi_rvalid <= '0';
    end if;
  end if;
end process;
```

### Relevance to Your Project
Your `kv260_top.vhd` wraps two AXI Block Memory Generators accessed from the Cortex-A53 at `0xA0000000` and `0xA0010000`. Vivado's Block Memory Controller IP uses correct hold logic, but if you add any custom AXI slave bridging or extend the design, verifying this pattern is critical. The single-cycle BRAM output register latency is already handled by the controller IP at default settings.

## Vivado Block Design / IP Integrator

### Key Findings
- **Run Connection Automation adds BRAM Controller + BMG automatically**: With a Zynq PS AXI master port added, "Run Connection Automation → All Automation" inserts an AXI SmartConnect, AXI BRAM Controller, and Block Memory Generator in one step, then wires them. No manual port dragging needed.
- **Address Editor only appears when a bus master exists**: If you don't see the Address Editor tab, check that the Zynq PS block has its AXI master port (M_AXI_HPM0_FPD or similar) enabled in the PS configuration.
- **Overlapping address ranges cause silent validation failures**: UG1165 (2025.2) documents a case where two HP ports were auto-assigned overlapping ranges. Always run "Validate Design" (F6) after any address assignment and check the Messages tab.
- **Range granularity**: BRAM Controller address ranges must be set to a power of two. For a 4KB BRAM, use 4K range; for 64KB, use 64K. The default auto-assignment may over-provision — check `BRAM_SIZE` matches your BMG depth × width.
- **Regenerate Layout frequently**: After modifying connections, use "Regenerate Layout" to avoid visual overlaps that can obscure unconnected ports.

### Code Example
```tcl
# TCL equivalent of "Run Connection Automation" for AXI BRAM
# Run inside a Vivado IP Integrator batch session
apply_bd_automation -rule xilinx.com:bd_rule:axi4 \
    -config {Master "/zynq_ultra_ps_e_0/M_AXI_HPM0_FPD" \
             Clk "Auto" }  \
    [get_bd_intf_pins axi_bram_ctrl_0/S_AXI]

# Assign address manually after automation
set_property offset 0xA0000000 \
    [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property range 64K \
    [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
```

### Relevance to Your Project
Your `create_bd.tcl` script builds the block design that connects both BRAM controllers. If the script ever fails on a clean Vivado installation, the most common root cause is address segment naming differing between Vivado versions. Use `get_bd_addr_segs -hierarchical` to discover the correct segment names before hardcoding them.

## Vivado TCL Scripting

### Key Findings
- **Non-project mode keeps no .xpr on disk**: In non-project mode, Vivado builds an in-memory project. This is ideal for CI/CD pipelines but means all reports and checkpoints must be explicitly written — there is no automatic run infrastructure.
- **Block designs in non-project mode need explicit generation**: Before synthesizing a BD in non-project mode, call `generate_target all [get_files *.bd]` or set `synth_checkpoint_mode` to `None` on the .bd source file. Otherwise synthesis will error on missing generated wrappers.
- **Batch invocation pattern**: `vivado -mode batch -source build.tcl -notrace` is the standard invocation. `-notrace` suppresses the echo of each command in the log, keeping output readable. Remove it for debugging.
- **Export hardware for Vitis from TCL**: After `write_bitstream`, use `write_hw_platform -fixed -include_bit -force ./output.xsa` to generate the XSA file Vitis needs for BSP generation. This replaces the older `write_sysdef` command removed in Vitis Unified.
- **`open_bd_design` vs `read_bd`**: In non-project mode, use `read_bd` to add the BD file to in-memory sources, then `open_bd_design [get_files *.bd]` to make it current. `read_bd` alone does not open it for editing.

### Code Example
```tcl
# Minimal non-project mode build script for KV260 AXI-BRAM design
# Invoke: vivado -mode batch -source build.tcl -notrace

read_vhdl   ../vhdl/kv260_top.vhd
read_bd     ../bd/system.bd
generate_target all [get_files system.bd]
make_wrapper -files [get_files system.bd] -top
read_vhdl   [glob ./system/hdl/system_wrapper.vhd]
read_xdc    ../xdc/kv260_top.xdc

synth_design -top system_wrapper -part xck26-sfvc784-2LV-c
opt_design
place_design
phys_opt_design
route_design
write_checkpoint  -force ./output/system_wrapper_routed.dcp
write_bitstream   -force ./output/system_wrapper.bit
write_hw_platform -fixed -include_bit -force ./output/kv260_design.xsa
```

### Relevance to Your Project
Your `create_bd.tcl` currently runs in project mode. Converting it to a non-project wrapper (or wrapping it in a CI-friendly batch script) will let you automate full bitstream regeneration from a clean checkout without launching the Vivado GUI — critical for reproducible builds.

## Vitis Bare-Metal / Standalone

### Key Findings
- **KV260 uses UART1, not UART0**: Kria SOM firmware and Linux use UART1 (`psuart1`). If `xil_printf` in your bare-metal application produces no output, verify the standalone BSP has `STDIN` and `STDOUT` set to `psuart1` (not `psuart0`) in the BSP settings.
- **`xil_printf` is not full printf**: It lacks floating-point formatting. If you need `%f` or `%g`, use the newlib-backed `printf` instead and increase the heap in `lscript.ld` (start with `0x10000` / 64KB).
- **Linker script stack/heap**: Vitis generates `lscript.ld` in the application's `src/` folder. Double-click it in Vitis to edit stack and heap sizes. For a simple pattern-check app the defaults (stack 0x400, heap 0x800) are typically sufficient — bump if you add printf or complex data structures.
- **BSP regeneration after XSA change**: Any time you re-export an XSA from Vivado (after adding IPs, changing addresses), you must regenerate the BSP in Vitis: right-click the platform component → "Update Hardware Specification". Old BSP `xparameters.h` will have stale base addresses.
- **Standalone BSP interrupt controller**: For AXI interrupt-driven designs, the BSP includes `XScuGic` (GIC-400 driver). For a polling-only BRAM demo, the BSP interrupt drivers are unused but still compiled in — this is normal.

### Code Example
```c
/* Minimal AXI-Lite BRAM write/read verification pattern
 * Using Xilinx standalone BSP memory-mapped I/O macros */
#include "xil_io.h"
#include "xil_printf.h"

#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL
#define TEST_PATTERN 0xDEADBEEFUL

int verify_bram(u32 base_addr, const char *name) {
    Xil_Out32(base_addr + 0x00, TEST_PATTERN);
    Xil_Out32(base_addr + 0x04, ~TEST_PATTERN);

    /* Memory barrier: ensure writes complete before reads */
    Xil_DCacheFlush();

    u32 r0 = Xil_In32(base_addr + 0x00);
    u32 r1 = Xil_In32(base_addr + 0x04);

    if (r0 == TEST_PATTERN && r1 == ~TEST_PATTERN) {
        xil_printf("%s: PASS (0x%08X, 0x%08X)\r\n", name, r0, r1);
        return 0;
    }
    xil_printf("%s: FAIL (got 0x%08X, expected 0x%08X)\r\n", name, r0, TEST_PATTERN);
    return -1;
}
```

### Relevance to Your Project
This pattern closely mirrors what your `main.c` implements. The key addition is `Xil_DCacheFlush()` — on Cortex-A53, the D-cache is enabled by the FSBL and the BSP runtime. Without a cache flush/invalidate between writes and reads to the same address range, you may read back cached data rather than what BRAM holds, producing false PASS results. Mark the BRAM address region as device memory or use `Xil_SetTlbAttributes` to disable caching for those addresses.

## XDC Timing Constraints

### Key Findings
- **Constraint ordering matters**: AMD UG903 (2025.2) recommends this sequence: (1) primary/virtual clocks, (2) generated clocks, (3) `set_clock_groups`, (4) I/O delays, (5) timing exceptions (`set_false_path`, `set_max_delay`). Violations in ordering can cause constraints to be silently ignored.
- **`set_clock_groups -asynchronous` vs `set_false_path`**: `set_clock_groups` suppresses timing analysis in both directions between two clocks and is faster to apply. `set_false_path -from CLK_A -to CLK_B` only applies one direction. For AXI clock domains, `set_clock_groups` is the standard approach.
- **`set_input_delay` is measured from the clock edge at the I/O buffer**: Vivado counts propagation delay from the source clock through the network to the capture flip-flop. For internal BRAM paths, `set_input_delay` is not needed — constraints apply between the PS AXI clock and PL logic automatically through `create_generated_clock` entries set by the Zynq PS IP.
- **On Zynq UltraScale+, the PS provides the PL clock**: The PL reference clock (`pl_clk0`) is a generated clock from the PS. Vivado's Zynq PS IP creates this automatically. Do not add a redundant `create_clock` on `pl_clk0` — it will cause a multi-driver conflict in timing analysis.
- **Validate timing after each constraint change**: Run `report_timing_summary -delay_type min_max -report_unconstrained` in the Tcl console after editing the XDC to confirm all paths are covered.

### Code Example
```xdc
# KV260 AXI-BRAM XDC timing constraints
# pl_clk0 is auto-created by the Zynq PS IP — do NOT add create_clock here

# If using asynchronous AXI and PL clocks (not typical for simple BRAM demo):
# set_clock_groups -asynchronous \
#     -group [get_clocks -of [get_pins */PS8_i/PLCLK[0]]] \
#     -group [get_clocks -of [get_pins */clk_wiz_0/clk_out1]]

# GPIO output (example: LED on KV260 carrier)
# KV260 carrier board LED: pin H11 on bank 45
set_property PACKAGE_PIN H11      [get_ports {led[0]}]
set_property IOSTANDARD  LVCMOS33 [get_ports {led[0]}]
set_output_delay -clock [get_clocks -of [get_pins */PS8_i/PLCLK[0]]] \
    -max 2.0 [get_ports {led[0]}]
set_output_delay -clock [get_clocks -of [get_pins */PS8_i/PLCLK[0]]] \
    -min 0.5 [get_ports {led[0]}]
```

### Relevance to Your Project
For a pure AXI-BRAM demo with no external I/O other than UART (which is a PS peripheral, not PL), you may need minimal XDC constraints. The most important constraint is confirming `pl_clk0` is not double-defined. Run `report_clock_interaction` after implementation to check for any CDC violations between your AXI clock and any generated clocks.

## Kria KV260 / K26 SoM

### Key Findings
- **Boot mode is hard-wired to QSPI32**: The K26 SoM has no boot-mode DIP switches. Boot mode pins are factory-configured for QSPI32 (boot from on-board QSPI flash). During development, use JTAG boot override through the carrier's JTAG header.
- **UART1 is the PS console**: Bank 500 (MIO pins used by the SOM) includes the UART1 interface routed to the carrier's USB-UART bridge. UART0 is not connected on the standard KV260 carrier board. Configure your BSP accordingly.
- **MIO bank voltages are 1.8V**: All three MIO banks (500, 501, 502) are powered at 1.8V by the SOM. External signals connected to MIO must be 1.8V or level-shifted. PL I/O (through the carrier high-density connector) uses carrier-defined supply voltages.
- **Bank 500 is SOM-reserved**: MIO bank 500 carries QSPI, eMMC, I2C, and TPM SPI. Do not remap these in your XDC or PS configuration. Bank 501/502 are available for user I/O.
- **Power sequencing**: The carrier board's PL VCCO rails come up after the SOM asserts its power-enable signals. PL I/O is not reliable until the SOM boot sequence completes — avoid driving PL outputs before the PS firmware initializes power management.
- **K26 SOM uses K26C (commercial temp) or K26I (industrial) variants**: Vivado part number is `xck26-sfvc784-2LV-c` (commercial). Confirm your part number before synthesis — the wrong part causes incorrect timing models.

### Code Example
```tcl
# Verify target part in Vivado TCL before synthesis
set target_part "xck26-sfvc784-2LV-c"
set current_part [get_property PART [current_project]]
if {$current_part ne $target_part} {
    puts "WARNING: Project part ($current_part) does not match expected ($target_part)"
    set_property PART $target_part [current_project]
}
puts "Building for: [get_property PART [current_project]]"
```

### Relevance to Your Project
Your project targets the KV260 with BRAM at `0xA0000000` and `0xA0010000` — both are in the AXI HP slave address space (PS-to-PL). Verify your Vivado PS configuration has `M_AXI_HPM0_FPD` enabled (not `M_AXI_HPM0_LPD`) and that the AXI clock frequency in the PS matches your PL design's timing budget. The default PS AXI master clock is 100 MHz for `HPM0_FPD`.

## AMD/Xilinx Tool Updates (2025.1 / 2025.2)

### Key Findings
- **New RTL-based AXI Switch IP in 2025.2**: AMD introduced a new AXI Switch IP with an ultra-low-area mode controlled by a `STRATEGY` parameter. This replaces some use cases of AXI SmartConnect for simple static routing scenarios.
- **Vitis 2025.2 adds "Integration Project" component**: The new Unified Vitis 2025.2 introduces an Integration Project concept that unifies platform, application, and system management in one component view — relevant when moving from the older application-project model.
- **AI Engine API enhancements (Versal-focused, but signals direction)**: 2025.1 and 2025.2 both include AI Engine API updates. Not directly relevant to KV260 bare-metal BRAM, but signals AMD's focus on Versal for new algorithm work.
- **UG973 (Vivado release notes) lists known issues via Answer Records**: For 2025.1-specific bugs, search AMD's support portal with "AR#" references from UG973. The most common issues involve IP regeneration after version upgrades.
- **Vitis Embedded Platforms UG1742 (2025.2)**: The release notes document changed BSP behavior, new supported platforms, and deprecated features. Review before upgrading from 2025.1 to 2025.2.
- **PhysOpt compile time reduction for Versal**: 2025.2 includes implementation speed improvements for Versal devices. Zynq UltraScale+ (K26) may also benefit from incremental improvements.
