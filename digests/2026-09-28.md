# FPGA Research Digest - 2026-09-28

## Executive Summary

- **AXI-Lite read-data channel ordering**: The `RDATA` channel requires the master to assert `RREADY` before or simultaneously with `RVALID`; a bare-metal A53 polling `Xil_In32()` in a loop does this correctly, but a hand-rolled VHDL master that deasserts `RREADY` between transactions can cause the `axi_bram_ctrl` to hang with `RVALID` permanently asserted if its output FIFO fills
- **Xil_Out32 / Xil_In32 use volatile pointers**: These functions cast the address to `volatile u32 *`, preventing the compiler from optimizing away repeated reads — critical for polling a BRAM status register; however they do NOT issue memory barriers, so pair them with `dmb()` / `dsb()` when ordering matters across CPU/DMA
- **Kria KV260 fixed QSPI boot**: The K26 SoM boots exclusively from QSPI; the embedded FSBL and PMU firmware are pre-programmed in factory flash. Bare-metal Vitis projects do not need to generate an FSBL — set the boot image to contain only the bitstream + application ELF
- **Vivado write_bd_tcl pitfall**: `write_bd_tcl` generates a script that re-creates the block design but does NOT preserve manual address segment assignments made through the GUI; always follow with `assign_bd_address` calls or use `get_bd_addr_segs` to export and re-apply segments in your automation script
- **XDC set_clock_groups for gated PL clocks**: On Zynq/Kria, the `pl_clk0` output from the PS is asynchronous to internal Vivado-generated clocks; add `set_clock_groups -asynchronous -group [get_clocks clk_fpga_0] -group [get_clocks clk_out1_*]` to prevent the timing engine from cross-analyzing unrelated domains and producing false critical-path warnings

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- **RREADY must be driven before RVALID**: The AXI4 specification allows a slave to wait for RREADY before asserting RVALID, but the Xilinx `axi_bram_ctrl` in default mode asserts RVALID as soon as data is ready regardless of RREADY. A master that deasserts RREADY can result in accumulated beats in the slave's output register — on the next read the returned value is the *previous* read's data shifted by one beat.
- **AXI-Lite has no ID signals**: Unlike AXI4 full (which uses ARID/AWID/RID/BID for out-of-order transactions), AXI-Lite has no ID fields. This means transactions are strictly in-order and the PS must complete the B-channel handshake (acknowledge BVALID) before issuing the next write.
- **AWPROT / ARPROT signal pitfall**: Protection type bits `[2:0]` default to `3'b000` (Normal, Secure, Data) when auto-connected in IP Integrator. Custom VHDL slaves that decode AWPROT for privilege checking must be aware the PS bare-metal runs at EL1 (Secure), which maps to `AWPROT[1]=1`; a slave checking `AWPROT == 3'b000` will see mismatches and may incorrectly refuse transactions.
- **AXI-Stream TVALID must not depend on TREADY**: The AXI-Stream spec explicitly prohibits a source from waiting for TREADY before asserting TVALID. Violating this creates a combinational deadlock. The Xilinx AXI4-Stream Data FIFO IP (`axis_data_fifo`) absorbs this by immediately accepting data regardless of downstream backpressure.
- **SmartConnect vs AXI Interconnect**: The newer `axi_smartconnect` IP is preferred over the legacy `axi_interconnect` for Zynq/Kria designs. SmartConnect handles clock-domain crossings automatically, includes lightweight clock converters, and avoids the manual `M_ACLK/S_ACLK` configuration that causes synthesis errors in the older IP.

### Code Example

```c
/* Bare-metal AXI-Lite write followed by confirmed read-back.
 * Always read BVALID implicitly by issuing the next Xil_In32
 * after the write — the A53 AXI master serializes this correctly. */
#define BRAM0_BASE 0xA0000000UL
#define BRAM2_BASE 0xA0010000UL

static int axi_bram_write_verify(u32 base, u32 offset, u32 pattern) {
    volatile u32 *addr = (volatile u32 *)(base + offset);
    /* Flush D-cache line before write so no dirty lines stale the PL view */
    Xil_DCacheFlushRange((INTPTR)addr, 4);
    *addr = pattern;
    dsb();                              /* ensure write completes before read */
    Xil_DCacheInvalidateRange((INTPTR)addr, 4);
    u32 readback = *addr;
    return (readback == pattern) ? 0 : -1;
}
```

### Relevance to Your Project

Your `main.c` writes patterns to `0xA0000000` (BRAM0) and `0xA0010000` (BRAM2). The `Xil_DCacheFlushRange` + `dsb()` + `Xil_DCacheInvalidateRange` sequence is the correct bare-metal idiom for ensuring the A53's D-cache doesn't serve stale data for BRAM read-back. Without the invalidate, a read immediately after a write can return the cached write value rather than the BRAM's actual content — masking a broken AXI connection.

## Vivado Block Design / IP Integrator

### Key Findings

- **Run Connection Automation order matters**: When IP Integrator's "Run Connection Automation" banner appears, run it for the AXI master interface first (Zynq PS `M_AXI_HPM0_FPD`) before running it for individual slave IPs. Running slave automation first creates dangling `S_AXI` ports with no SmartConnect assigned, requiring manual deletion and re-connection.
- **Address Editor automatic vs. manual segments**: IP Integrator auto-assigns base addresses when you run connection automation, but it picks arbitrary offsets if the default `0xA000_0000` range is occupied. Always verify the address map (`Window → Address Editor`) after automation and manually set `Offset Address` and `Range` for each BRAM controller.
- **Block design validation warnings on unconnected clocks**: The `validate_bd_design` TCL command reports warnings for any unconnected clock input (`ACLK`, `S_AXI_ACLK`). These become errors during bitstream generation if the IP's `CONFIG.ASSOCIATED_BUSIF` property is set. Connect all IPs to a single `pl_clk0` unless you need an explicit clock domain crossing.
- **Regenerate output products after IP property changes**: If you modify a Block Memory Generator property (e.g., switching from `Native` to `AXI4` interface or changing memory depth), you must right-click → "Reset Output Products" and then "Generate Output Products" before synthesis. Stale output products cause `synth_design` to fail with "IP is out-of-date."
- **Hierarchical block design for reuse**: Wrapping BRAM + controller in a hierarchy (`create_bd_cell -type hier`) allows re-instantiating the pair with different base addresses by parameterizing the hierarchy. This pattern avoids duplicating connection logic for BRAM0 and BRAM2.

### Code Example

```tcl
# Vivado TCL: create AXI BRAM controller + BRAM pair at a given base address
proc create_axi_bram_pair {name base_addr range_kb} {
    # Create Block Memory Generator (True Dual Port, 32-bit, AXI4 interface)
    set bram [create_bd_cell -type ip -vlnv xilinx.com:ip:blk_mem_gen:8.4 ${name}_bmg]
    set_property -dict [list \
        CONFIG.Memory_Type {True_Dual_Port_RAM} \
        CONFIG.Write_Width_A {32} \
        CONFIG.Read_Width_A  {32} \
        CONFIG.Write_Depth_A [expr {$range_kb * 1024 / 4}] \
    ] $bram

    # Create AXI BRAM Controller
    set ctrl [create_bd_cell -type ip -vlnv xilinx.com:ip:axi_bram_ctrl:4.1 ${name}_ctrl]
    set_property CONFIG.SINGLE_PORT_BRAM {1} $ctrl

    # Connect controller to BRAM
    connect_bd_intf_net [get_bd_intf_pins ${ctrl}/BRAM_PORTA] \
                        [get_bd_intf_pins ${bram}/BRAM_PORTA]

    # Assign address
    set seg [create_bd_addr_seg \
        -range [expr {$range_kb * 1024}] \
        -offset $base_addr \
        [get_bd_addr_spaces zynq_ultra_ps_e_0/Data] \
        [get_bd_addr_segs ${ctrl}/S_AXI/Mem0] \
        SEG_${name}]
    assign_bd_address [get_bd_addr_segs ${ctrl}/S_AXI/Mem0]
}

create_axi_bram_pair bram0 0xA0000000 64
create_axi_bram_pair bram2 0xA0010000 64
```

### Relevance to Your Project

Your `create_bd.tcl` script creates two BRAM pairs. The proc above encapsulates the pattern with parameterized naming and address assignment — reducing the script from ~60 duplicated lines to two calls. The explicit `assign_bd_address` call after `create_bd_addr_seg` is essential; omitting it leaves the segment unrouted and generates `DECERR` responses at runtime.

## Vivado TCL Scripting

### Key Findings

- **Non-project mode avoids `.xpr` dependency**: Using `open_project` in batch mode requires the `.xpr` file path, which changes when projects are relocated. Non-project mode scripts using `read_vhdl`, `read_bd`, `synth_design -top`, and `impl_design` are fully portable and easier to run in CI pipelines.
- **`write_bd_tcl` vs `write_project_tcl`**: `write_bd_tcl` exports only the block design; `write_project_tcl` exports the full project including source file sets, synthesis runs, and implementation strategies. For a repeatable CI flow, prefer `write_project_tcl -no_copy_sources` so paths remain relative.
- **`get_bd_*` vs `get_*` context**: Inside a block design context (after `open_bd_design`), use `get_bd_cells`, `get_bd_intf_pins`, `get_bd_addr_segs`. Outside a block design (after `close_bd_design`), these commands fail silently. Always check `[current_bd_design]` before issuing block design queries.
- **Batch synthesis timing capture**: Use `report_timing_summary -delay_type min_max -report_unconstrained -check_timing_verbose -file timing_summary.rpt` immediately after `impl_design` in batch scripts. This produces the same report as the GUI's "Report Timing Summary" and catches setup/hold violations before bitstream generation.
- **`set_property STEPS.SYNTH_DESIGN.ARGS.FLATTEN_HIERARCHY none`**: For debugging AXI connectivity issues, disable hierarchy flattening in synthesis so signal names in the ILA match your VHDL hierarchy. Re-enable `rebuilt` for final builds.

### Code Example

```tcl
#!/usr/bin/env vivado -mode batch -source

# Non-project mode: synthesize, implement, write bitstream
set part "xck26-sfvc784-2LV-c"
set top  "kv260_top"
set bd_tcl "tcl/create_bd.tcl"
set vhdl_src "vhdl/kv260_top.vhd"
set xdc_src  "xdc/kv260_top.xdc"

# Read sources
read_vhdl -vhdl2008 $vhdl_src
source $bd_tcl
make_wrapper -files [get_files *.bd] -top
read_vhdl [glob ./*/hdl/*_wrapper.vhd]
read_xdc $xdc_src

# Synthesize
synth_design -top ${top}_wrapper -part $part \
    -flatten_hierarchy none
write_checkpoint -force checkpoints/post_synth.dcp

# Implement
opt_design
place_design
route_design
write_checkpoint -force checkpoints/post_route.dcp

# Reports
report_timing_summary -file reports/timing_summary.rpt
report_utilization    -file reports/utilization.rpt

# Bitstream
write_bitstream -force output/${top}.bit
write_debug_probes -force output/${top}.ltx
```

### Relevance to Your Project

Your project uses `create_bd.tcl` sourced from Vivado. Wrapping this in the non-project flow above enables fully reproducible builds without opening the GUI — useful for iterating on BRAM address assignments or adding a second ILA probe without re-running the wizard. The checkpoint saves allow resuming from `post_synth.dcp` during implementation debugging.

## Vitis Bare-Metal / Standalone

### Key Findings

- **BSP `stdout` peripheral selection**: The Vitis standalone BSP sets `stdout` and `stdin` via the `stdin`/`stdout` BSP settings (mapped to a UART IP). On KV260, the PS UART1 is connected to the USB-UART bridge at J15; ensure `STDIN_BASEADDRESS` and `STDOUT_BASEADDRESS` in `xparameters.h` resolve to `XPAR_PSU_UART_1_BASEADDR` (0xFF010000). Selecting UART0 produces no output on the USB cable.
- **`xil_printf` vs `printf`**: `xil_printf` is a lightweight implementation that does NOT support floating-point format specifiers (`%f`, `%g`). It supports `%d`, `%u`, `%x`, `%s`, `%c`. For float output, link `libm` and use standard `printf` with the BSP's `LIBRARY_IS_NEWLIB_NANO=0` setting to pull in the full newlib `printf`.
- **GIC initialization sequence**: For Cortex-A53 bare-metal, always initialize the GIC before enabling interrupts in CPSR. The sequence is: `XScuGic_CfgInitialize()` → `XScuGic_Connect()` per IRQ → `XScuGic_Enable()` per IRQ → `Xil_ExceptionRegisterHandler(XIL_EXCEPTION_ID_IRQ_INT, ...)` → `Xil_ExceptionEnable()`. Reversing the last two steps causes a spurious FIQ on first interrupt.
- **Linker script DDR region**: The default Cortex-A53 standalone linker script places code at `0x0` (OCM, 256KB) and data in DDR starting at `0x100000`. For a bare-metal app larger than 256KB, override with a custom `lscript.ld` that maps `.text` and `.data` both to DDR (`ps_ddr_0` at `0x0` to `0x7FFFFFFF` on K26).
- **SDT vs. classic driver initialization**: Vitis 2025.1 uses the System Device Tree (SDT) flow by default for new projects. The SDT flow uses `BaseAddress` for `LookupConfig()` instead of `DeviceId`. Legacy examples using `XPAR_*_DEVICE_ID` macros require the BSP setting `USE_LEGACY_MACROS=1` or migration to the `XBram_LookupConfig(XPAR_*_BASEADDR)` API.

### Code Example

```c
/* GIC setup for a PL interrupt on IRQ #121 (first PL interrupt on ZynqMP) */
#include "xscugic.h"
#include "xil_exception.h"

static XScuGic gic;

static void pl_irq_handler(void *callback) {
    /* Clear the interrupt at the PL source before returning */
    u32 *irq_clear_reg = (u32 *)0xA0000014UL;  /* example: IP interrupt clear */
    *irq_clear_reg = 1;
}

int setup_pl_interrupt(void) {
    XScuGic_Config *cfg = XScuGic_LookupConfig(XPAR_SCUGIC_0_BASEADDR);
    if (!cfg) return XST_FAILURE;

    XScuGic_CfgInitialize(&gic, cfg, cfg->CpuBaseAddress);

    /* PL IRQ 0 maps to GIC SPI 121 on ZynqMP */
    XScuGic_Connect(&gic, 121,
                    (Xil_InterruptHandler)pl_irq_handler, NULL);
    XScuGic_SetPriorityTriggerType(&gic, 121,
                                    0xA0,   /* priority */
                                    0x3);   /* rising-edge trigger */
    XScuGic_Enable(&gic, 121);

    Xil_ExceptionRegisterHandler(XIL_EXCEPTION_ID_IRQ_INT,
                                  (Xil_ExceptionHandler)XScuGic_InterruptHandler,
                                  &gic);
    Xil_ExceptionEnable();
    return XST_SUCCESS;
}
```

### Relevance to Your Project

Your current project polls BRAM read-back over UART. Adding a PL interrupt (e.g., from a Xilinx `axi_intc` IP wired to a BRAM write-complete signal) would allow the A53 to sleep in WFI between transactions. The GIC setup above is the correct ZynqMP bare-metal interrupt pattern — the `XScuGic_SetPriorityTriggerType` call with `0x3` (rising-edge) is required for PL-generated level-to-edge converted interrupts.

## XDC Timing Constraints

### Key Findings

- **Primary clock for PL logic must reference `pl_clk0`**: The PS clock output on Kria (`pl_clk0`) is not automatically defined as a clock in XDC. You must either use `create_generated_clock` or rely on the Clocking Wizard IP, which auto-generates the constraint. Without this, the timing engine has no reference and reports `No clock found on...` errors on all AXI registers.
- **`set_false_path` for PS reset signals**: The PS `peripheral_aresetn` output is a synchronous reset synchronized to `pl_clk0`, but Vivado may still flag it as a multi-cycle path warning. Add `set_false_path -from [get_pins zynq_ultra_ps_e_0/pl_resetn0]` to silence the warning and prevent the tool from analyzing a reset tree that has no meaningful timing path.
- **`set_clock_groups -asynchronous` mandatory for multi-clock designs**: If your design has both `pl_clk0` (100 MHz) and a derived `pl_clk1` (200 MHz) from the same PS PLL, these are actually synchronous (same source). Use `-exclusive` not `-asynchronous` for gated clocks that never operate simultaneously; use `-asynchronous` only for truly unrelated oscillators.
- **I/O timing constraints on HDMI/IAS connectors**: The KV260 carrier card has HDMI and IAS (MIPI) connectors with series termination resistors. When adding external I/O paths, `set_input_delay` should reference the board's propagation delay (`-max 3.5 -min 0.5` ns are typical for HDMI traces) added to the clock uncertainty.
- **`report_cdc` for safe clock-domain crossing**: After adding `set_clock_groups`, run `report_cdc -details` to identify unprotected clock-domain crossings. For single-bit control signals (e.g., `start_bram_test`), insert a 2-FF synchronizer; for multi-bit buses, use a Gray-code counter or handshake protocol.

### Code Example

```tcl
# kv260_top.xdc - minimal timing constraints for AXI-BRAM demo

# PS clock output — define primary PL clock
# pl_clk0 is driven by the Zynq PS; 100 MHz is the typical default
create_clock -name pl_clk0 -period 10.000 \
    [get_pins zynq_ultra_ps_e_0/inst/PS8_i/PLCLK[0]]

# If a Clocking Wizard derives a 200 MHz clock from pl_clk0:
create_generated_clock -name clk_200m \
    -source [get_pins clk_wiz_0/clk_in1] \
    -multiply_by 2 \
    [get_pins clk_wiz_0/clk_out1]

# Declare pl_clk0 and clk_200m as synchronous (same PLL source)
# Use -exclusive only if one is gated off when the other runs
set_clock_groups -name ps_pll_group -asynchronous \
    -group [get_clocks pl_clk0] \
    -group [get_clocks clk_200m]

# Suppress false-path warning on PS reset output
set_false_path -from [get_pins zynq_ultra_ps_e_0/inst/PS8_i/PLRESETN[0]]

# BRAM address/data registers are internal — no I/O constraints needed
# Add only if you have external PMOD/GPIO signals:
# set_input_delay  -clock pl_clk0 -max 3.0 [get_ports {pmod_in[*]}]
# set_output_delay -clock pl_clk0 -max 2.5 [get_ports {pmod_out[*]}]
```

### Relevance to Your Project

The `create_clock` on `PLCLK[0]` is the single most important constraint for your AXI-BRAM demo. Without it, Vivado treats all AXI register paths as unconstrained and may over-optimize timing, producing a bitstream that meets timing numerically but fails on hardware due to unanalyzed paths. Add this constraint even if synthesis succeeds without it.

## Kria KV260 / K26 SoM

### Key Findings

- **Fixed QSPI boot — no custom FSBL needed**: The K26 SoM programs its boot firmware (FSBL + PMU FW) into factory QSPI flash, which is read-only. Bare-metal Vitis projects export only the application ELF + bitstream as a `BOOT.bin`. Attempting to include a custom FSBL will be ignored by the factory boot ROM; use the pre-programmed FSBL.
- **Boot image composition for bare-metal**: For a bare-metal application, the `BOOT.bin` created by Vitis's Boot Image tool should contain: (1) the bitstream (`.bit`) and (2) the application ELF. The factory FSBL handles PS initialization, clocks, DDR training, and bitstream programming before jumping to the ELF entry point.
- **MIO pin assignments on K26**: The K26 SoM exposes a fixed MIO mapping. UART1 (TX=MIO[12], RX=MIO[13]) connects to the USB-UART bridge accessible at `/dev/ttyUSB1` from the host. I2C0 (MIO[14], MIO[15]) connects to the PMIC. Do not remap these in the Zynq PS block design configurator — the factory FSBL assumes the MIO configuration matches the SoM's PCB routing.
- **PL power domain control**: The KV260's PL power domain is controlled by the PMU firmware. The bitstream is loaded into the PL by the FSBL; if bitstream programming fails (e.g., due to a mismatch between the Vivado part `xck26-sfvc784-2LV-c` and the actual device), the FSBL continues to the application without PL power — all PL-mapped AXI reads return 0. Confirm bitstream load success via the DONE LED (LD13) on the carrier card.
- **EMIO GPIO for PL debug signals**: MIO GPIO pins are fully consumed by the SoM's on-board peripherals. Use EMIO GPIO (PS GPIO extended through the PL fabric) to route debug signals to PMOD connectors on the carrier card. EMIO GPIO appears at `xck26` FPGA pins in the carrier card's XDC file; AMD provides the KV260 master XDC as part of the starter kit materials.

### Code Example

```tcl
# Zynq UltraScale+ PS configuration for KV260 (excerpt from create_bd.tcl)
# These settings match the K26 SoM MIO pinout — do not modify MIO assignments

set_property -dict [list \
    CONFIG.PSU__UART1__PERIPHERAL__ENABLE     {1} \
    CONFIG.PSU__UART1__PERIPHERAL__IO         {MIO 12 .. 13} \
    CONFIG.PSU__UART1__BAUD_RATE              {115200} \
    CONFIG.PSU__I2C0__PERIPHERAL__ENABLE      {1} \
    CONFIG.PSU__I2C0__PERIPHERAL__IO          {MIO 14 .. 15} \
    CONFIG.PSU__SD1__PERIPHERAL__ENABLE       {1} \
    CONFIG.PSU__SD1__PERIPHERAL__IO           {MIO 46 .. 51} \
    CONFIG.PSU__SD1__DATA_TRANSFER_MODE       {4Bit} \
    CONFIG.PSU__USE__M_AXI_GP0               {1} \
    CONFIG.PSU__USE__M_AXI_GP2               {0} \
    CONFIG.PSU__MAXIGP0__DATA_WIDTH          {32} \
    CONFIG.PSU__CRL_APB__PL0_REF_CTRL__FREQMHZ {100} \
] [get_bd_cells zynq_ultra_ps_e_0]

# Enable EMIO GPIO for PL debug output to PMOD
set_property CONFIG.PSU__GPIO_EMIO__PERIPHERAL__ENABLE {1} \
    [get_bd_cells zynq_ultra_ps_e_0]
set_property CONFIG.PSU__GPIO_EMIO__PERIPHERAL__IO     {32} \
    [get_bd_cells zynq_ultra_ps_e_0]
```

### Relevance to Your Project

The `PSU__USE__M_AXI_GP0` setting enables the 32-bit AXI-Lite master port that drives your BRAM controllers at `0xA0000000` and `0xA0010000`. Setting `DATA_WIDTH` to `32` (not `128`) avoids a SmartConnect data-width conversion that adds one pipeline stage and can produce unexpected read timing. The EMIO GPIO configuration provides 32 debug pins that can be routed to PMOD JA/JB connectors for logic analyzer capture without adding an ILA.

## AMD/Xilinx Tool Updates

### Key Findings

- **Vitis Unified IDE is now the default in 2025.1**: The classic Vitis IDE (Eclipse-based, `vitis -classic`) is no longer the default. The Unified IDE uses a VS Code-based front end with a new workspace model. Existing classic projects can be migrated via `File → Migrate from Classic Vitis`, which converts `.xpr`-linked platform references to the new XPFM format.
- **New Vitis 2025.1 tutorial: "Vitis Export to Vivado Flow"**: This tutorial documents a new round-trip flow where a Vitis AI Engine or HLS kernel is compiled separately, then the output kernel `.xo` is imported into Vivado IP Integrator as a standard IP. This replaces the previous Vitis-linked platform approach for non-AI-Engine designs.
- **Vitis Functional Simulation is new in 2025.1**: Allows simulating Vitis HLS kernels at the software level before RTL generation, using the standard C++ testbench. Not directly applicable to bare-metal AXI-BRAM projects but useful for validating data-processing IP before integration.
- **Vivado 2025.2 tutorial branch validated**: The `Xilinx/Vivado-Design-Tutorials` repo has a `2025.2` branch — the most recently validated release. IP cores in 2025.1 block designs are backward-compatible with 2025.2 synthesis; you can open and upgrade a 2025.1 `.xpr` in Vivado 2025.2 without redesigning the block diagram.
- **SDT (System Device Tree) adoption in 2025.1 BSP**: New Vitis bare-metal projects default to the SDT flow, which uses `xparams.h` and `BaseAddress`-based `LookupConfig()` instead of legacy `XPAR_*_DEVICE_ID`. The SDT flow improves portability across device families. Legacy macros remain available via the BSP option `USE_LEGACY_XILINX_DEFINES`.

### Code Example

```tcl
# Vitis Unified IDE scripting: create a bare-metal platform + app from XSA
# Replaces the classic 'xsct' flow in Vitis 2025.1

# Run in Vitis Unified IDE terminal or via: vitis -s create_project.tcl

set xsa_path   "./kv260_top_wrapper.xsa"
set platform   "kv260_platform"
set domain     "standalone_ps7_cortexa53_0"
set app_name   "axi_bram_test"
set app_src    "./src/main.c"

# Create platform
platform create -name $platform \
    -hw $xsa_path \
    -no-boot-bsp

# Add standalone domain for Cortex-A53 core 0
domain create -name $domain \
    -display-name "Standalone A53 Core 0" \
    -os standalone \
    -proc psu_cortexa53_0 \
    -arch 64

# Set stdout to UART1
bsp setlib -name standalone
bsp config stdin  psu_uart_1
bsp config stdout psu_uart_1
bsp regenerate

# Create application
app create -name $app_name \
    -platform $platform \
    -domain $domain \
    -template "Empty Application(C)"

# Add source
importsources -name $app_name -path $app_src

# Build
app build -name $app_name
```

### Relevance to Your Project

The `bsp config stdout psu_uart_1` call is the critical line — it ensures `xil_printf` output goes to UART1 (MIO 12/13 → USB cable) rather than UART0. This is a common source of "no output on terminal" bugs when migrating from classic Vitis to the Unified IDE, since the new project wizard defaults to the first available UART which may be UART0 on some SoM configurations.
