# FPGA Research Digest - 2026-09-09

## Executive Summary

- **CRITICAL (Vivado 2025.1/2025.2):** The Block Memory Generator (BRAM) and FIFO IPs are no longer available for direct instantiation from the IP Catalog — they now require IP Integrator or XPM macros. This directly affects your AXI-BRAM project if you ever need to recreate it from scratch or migrate.
- **AXI-Lite write-response deadlock:** The most common bare-metal AXI-Lite bug is accepting a write transaction (AWREADY/WREADY high) when the response buffer is already full (BVALID asserted but BREADY still low from the PS). Your main.c must keep polling or consume responses promptly.
- **KV260 PL clocking:** The PL gets no dedicated oscillator — the only clock source is the PS-generated PL fabric clock (fclk_clk0, default 100 MHz). Your XDC must not define a create_clock on an input pin; instead let the Zynq IP drive the clock and constrain downstream with `set_clock_groups`.
- **Bare-metal on KV260 via JTAG/XSDB:** The safest bare-metal flow is load-and-go over JTAG using XSDB (`dow`, `con`) without flashing QSPI. This avoids boot mode switch complexity during development.
- **Vivado 2025.2 adds ultra-low-area AXI SmartConnect mode:** A `STRATEGY` parameter on the AXI SmartConnect IP enables a new ultra-low-area mode — useful for resource-constrained designs.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- All five AXI4 channels use the VALID/READY two-way handshake; a transfer occurs only when **both** are asserted on the same rising clock edge.
- **Deadlock rule:** A master or slave must **never** make VALID conditional on READY from the same channel. The initiator asserts VALID first; the responder asserts READY when it can accept. Reversing this causes deadlock since neither side ever fires.
- **Write-response backpressure bug:** A slave that accepts a new write (raises AWREADY/WREADY) before clearing its response buffer (while BVALID is high and BREADY is low) will overwrite pending response data. The correct guard: only assert AWREADY and WREADY when `(not BVALID) or BREADY`.
- **Read-channel pitfall:** ARREADY gating on RREADY is similarly dangerous — if the slave only accepts an address when the data channel is free, a stalled master RREADY creates a full stall.
- Xilinx's own auto-generated AXI4-Lite slave templates in Vivado had this backpressure bug in older versions; Dan Gisselquist (ZipCPU) documented a VHDL-specific fix in 2021 (see Sources).

### Code Example

```vhdl
-- Correct AXI-Lite write-acceptance guard (VHDL)
-- Only accept a new address+data pair when either:
--   (a) no response is pending, OR
--   (b) the master is already consuming the response this cycle
process(S_AXI_ACLK)
begin
  if rising_edge(S_AXI_ACLK) then
    if S_AXI_ARESETN = '0' then
      s_axi_awready <= '0';
      s_axi_wready  <= '0';
    else
      -- Gate acceptance on response-buffer availability
      if (s_axi_awvalid = '1' and s_axi_wvalid = '1') and
         (bvalid_r = '0' or S_AXI_BREADY = '1') then
        s_axi_awready <= '1';
        s_axi_wready  <= '1';
      else
        s_axi_awready <= '0';
        s_axi_wready  <= '0';
      end if;
    end if;
  end if;
end process;
```

### Relevance to Your Project

Your `kv260_top.vhd` wraps two AXI-BRAM Controllers; those controllers are Xilinx-generated, so the handshake logic is handled internally — but your Cortex-A53 `main.c` must still drain the write-response channel. If you do a burst of consecutive `Xil_Out32()` calls without any readback, the PS AXI master may stall waiting for BREADY deassertion from a saturated write-response queue. Add a response drain or interleave reads between writes.

## Vivado Block Design / IP Integrator

### Key Findings

- **Address Editor auto-assign:** After adding AXI BRAM controllers, right-click the Address Editor → "Auto Assign Address." This sets BRAM0 at `0xA000_0000` and BRAM1 at `0xA001_0000` (or your custom offsets). Always validate the block design (`validate_bd_design`) after address changes.
- **Connection Automation:** Clicking "Run Connection Automation" handles AXI interconnect wiring and BRAM port connection automatically; inspect what it generated before accepting.
- **TCL console logging:** Every GUI action is echoed to Vivado's TCL console in real time. Copy those commands to build a reproducible `create_bd.tcl` script — a reliable way to capture exactly what the GUI did.
- **Separate your XDC files:** Keep carrier-board pin constraints (KV260 SOM240 connector) in a dedicated `.xdc`, separate from timing constraints. This makes the design portable.
- **Block design upgrade:** After a Vivado version upgrade, always run `upgrade_ip` on stale IPs before synthesis; stale IPs can cause silent mismatches.

### Code Example

```tcl
# Vivado IP Integrator: Add and configure AXI BRAM Controller via TCL
create_bd_cell -type ip -vlnv xilinx.com:ip:axi_bram_ctrl:4.1 axi_bram_ctrl_0
set_property -dict [list \
  CONFIG.DATA_WIDTH {32} \
  CONFIG.SINGLE_PORT_BRAM {1} \
] [get_bd_cells axi_bram_ctrl_0]

# Create BRAM (Embedded Memory Generator - must be in IPI in Vivado 2025.x)
create_bd_cell -type ip -vlnv xilinx.com:ip:emb_mem_gen:1.0 emb_mem_gen_0
set_property CONFIG.MEMORY_TYPE {True_Dual_Port_RAM} \
  [get_bd_cells emb_mem_gen_0]

# Connect BRAM ports
connect_bd_intf_net [get_bd_intf_pins axi_bram_ctrl_0/BRAM_PORTA] \
                    [get_bd_intf_pins emb_mem_gen_0/BRAM_PORTA]

# Auto-assign addresses
assign_bd_address
```

### Relevance to Your Project

Your `create_bd.tcl` already automates the block design build. **Key upgrade note for Vivado 2025.1+:** if your TCL instantiates `blk_mem_gen`, replace it with `emb_mem_gen` (Embedded Memory Generator) — `blk_mem_gen` can no longer be instantiated standalone and must live inside IP Integrator.

## Vivado TCL Scripting

### Key Findings

- **Non-project mode:** Run `vivado -mode batch -source run.tcl` for fully automated, CI-friendly flows. The flow runs entirely in-memory; you must explicitly call `write_checkpoint` after each step to save intermediate state.
- **Journal files as recipe:** Vivado writes a `.jou` file logging every GUI action as TCL. After an interactive session, diff the journal against your existing script to capture any manual tweaks.
- **Non-project synthesis + implementation skeleton:**
  1. `read_vhdl / read_xdc`
  2. `synth_design -top <top> -part <part>`
  3. `write_checkpoint post_synth.dcp`
  4. `opt_design` → `place_design` → `route_design`
  5. `write_checkpoint post_route.dcp`
  6. `write_bitstream output.bit`
- **XPM in RTL:** When you need BRAM in RTL (not IPI), use Xilinx Parameterized Macros (`xpm_memory_spram`, `xpm_memory_tdpram`) which are always available regardless of IP Catalog restrictions.
- **Parameterized make targets:** Combine `make` with TCL variable passing: `vivado -mode batch -source run.tcl -tclargs my_part 100` and read args with `lindex $argv 0`.

### Code Example

```tcl
#!/usr/bin/env tclsh
# non_project_flow.tcl - Vivado non-project mode for kv260-axi-bram-demo

set part "xck26-sfvc784-2LV-c"

# Read design sources
read_vhdl [glob ../vhdl/*.vhd]
read_xdc  [glob ../constraints/*.xdc]

# Synthesis
synth_design -top kv260_top -part $part -flatten_hierarchy rebuilt
write_checkpoint -force ./checkpoints/post_synth.dcp
report_utilization -file ./reports/utilization_synth.rpt

# Implementation
opt_design
place_design
phys_opt_design
route_design
write_checkpoint -force ./checkpoints/post_route.dcp
report_timing_summary -file ./reports/timing.rpt -warn_on_violation

# Bitstream
write_bitstream -force ./output/kv260_top.bit
```

### Relevance to Your Project

Adding this non-project TCL script alongside your existing `create_bd.tcl` enables fully headless CI builds. The `xck26-sfvc784-2LV-c` part string matches the K26 SoM used on the KV260 carrier.

## Vitis Bare-Metal / Standalone

### Key Findings

- **Vitis 2025.2 Unified IDE:** The flow now imports an XSA (exported from Vivado) to create a platform project, then builds a standalone application on top. The platform includes the BSP with `xil_printf`, UART drivers, and PS init code.
- **BSP configuration for bare-metal on KV260:** Set `stdin`/`stdout` to `psu_uart_1` (connected to the USB-UART on the KV260 carrier). Confirm in `system.mss` that the standalone BSP is targeting `psu_cortexa53_0`.
- **xil_printf vs printf:** `xil_printf` is a lightweight formatted-print that skips floating-point support; use it for PASS/FAIL messages to avoid bloating the binary. For full `printf`, set `-DXIL_PRINTF_FLOAT` in BSP settings or link `libm`.
- **Memory map initialization:** Before any AXI peripheral access, call `Xil_SetTlbAttributes(0xA0000000ULL, NORM_NONCACHE)` (or `DEVICE_MEMORY`) to ensure cache is bypassed for MMIO regions. Cacheable writes to AXI peripherals cause silent data corruption.
- **GIC interrupt setup for bare-metal:** Use `XScuGic_Connect()` + `XScuGic_Enable()` to wire PL interrupts to the A53; the GIC base is at `0xF9010000` on Zynq UltraScale+.

### Code Example

```c
/* main.c fragment - cache-safe AXI-BRAM write/read with xil_printf */
#include "xil_io.h"
#include "xil_cache.h"
#include "xil_printf.h"

#define BRAM0_BASE  0xA0000000UL
#define BRAM1_BASE  0xA0010000UL
#define TEST_PATTERN 0xDEADBEEFUL

int main(void) {
    /* Mark AXI peripheral regions as non-cacheable (Device memory) */
    Xil_SetTlbAttributes(BRAM0_BASE, NORM_NONCACHE);
    Xil_SetTlbAttributes(BRAM1_BASE, NORM_NONCACHE);

    /* Write test pattern */
    Xil_Out32(BRAM0_BASE + 0x00, TEST_PATTERN);
    Xil_Out32(BRAM1_BASE + 0x00, ~TEST_PATTERN);

    /* Read back and verify */
    u32 r0 = Xil_In32(BRAM0_BASE + 0x00);
    u32 r1 = Xil_In32(BRAM1_BASE + 0x00);

    if (r0 == TEST_PATTERN && r1 == ~TEST_PATTERN) {
        xil_printf("PASS: BRAM0=0x%08X BRAM1=0x%08X\r\n", r0, r1);
    } else {
        xil_printf("FAIL: BRAM0=0x%08X (exp 0x%08X), BRAM1=0x%08X (exp 0x%08X)\r\n",
                   r0, TEST_PATTERN, r1, ~TEST_PATTERN);
    }
    return 0;
}
```

### Relevance to Your Project

This code mirrors your existing `main.c` pattern but adds the critical `Xil_SetTlbAttributes()` call. If your test passes in simulation but fails intermittently on hardware, missing TLB/cache attribute setup for the `0xA000_0000` region is the most likely cause.

## XDC Timing Constraints

### Key Findings

- **KV260 has no PL oscillator:** The only PL clock is PS-sourced (`fclk_clk0`). **Do not** add a `create_clock` constraint on any external pin — the clock is already defined inside the Zynq UltraScale+ IP. Only add `create_generated_clock` if you derive additional clocks from the PL fabric clock.
- **Clock groups for PS/PL boundary:** Declare `set_clock_groups -asynchronous -group [get_clocks clk_out1_*] -group [get_clocks clkfbout_*]` to suppress irrelevant cross-clock timing paths if you use a MMCM in PL.
- **AXI peripheral I/O delays:** For AXI-Lite to on-chip BRAM, `set_input_delay` / `set_output_delay` are generally not needed — all paths are internal. Only add them if you have off-chip I/O (PMOD, FMC) on the AXI data path.
- **Timing exception for BRAM:** A `set_multicycle_path` of 2 on BRAM read data is sometimes used when the BRAM is operating at 50 MHz but the system clock is 100 MHz (e.g., a 2-cycle read latency is expected).
- **KV260 carrier XDC:** Reference `Xilinx/Kria-PYNQ` repository for a well-maintained `base.xdc` with all carrier pin assignments.

### Code Example

```tcl
# kv260_timing.xdc - Minimal timing constraints for KV260 AXI-BRAM design

# PS provides fclk_clk0 at 100 MHz; Vivado infers this automatically
# from the Zynq UltraScale+ IP — no create_clock needed here.

# If you added a MMCM to derive a 50 MHz PL clock:
# create_generated_clock -name clk_50mhz \
#   -source [get_pins clk_wiz_0/inst/mmcme4_adv_inst/CLKIN1] \
#   -divide_by 2 \
#   [get_pins clk_wiz_0/inst/mmcme4_adv_inst/CLKOUT0]

# Suppress PS<->PL asynchronous CDC paths (safe for pure AXI designs)
set_clock_groups -asynchronous \
  -group [get_clocks -include_generated_clocks clk_pl_0] \
  -group [get_clocks -include_generated_clocks clk_pl_1]

# False path on resets (registered, multi-cycle safe)
set_false_path -from [get_cells -hierarchical -filter {NAME =~ *rst_*}] \
               -to   [all_registers]
```

### Relevance to Your Project

For your current AXI-Lite-to-BRAM design with a single 100 MHz fabric clock, the constraint file should be minimal — mostly pin assignments for UART, and the `set_clock_groups` above. Avoid over-constraining; let Vivado report on actual critical paths rather than suppressing them prematurely.

## Kria KV260 / K26 SoM

### Key Findings

- **No standalone PL clock:** The PL fabric must be clocked from the PS (`fclk_clk0`–`fclk_clk3`, each configurable 1–667 MHz). The PS must be initialized and running before the PL clock is active, which is handled automatically by the FSBL/PS init code in Vitis.
- **Bare-metal boot options:**
  1. **JTAG (XSDB):** `dow app.elf` + `con` — no flash, instant turnaround. Best for development.
  2. **SD Card (FAT):** Copy `BOOT.BIN` (FSBL + bitstream + app ELF, created by Vitis) to SD; select SD boot mode via the carrier switches.
  3. **QSPI32:** Default factory boot mode; used for production/demo.
- **MIO vs EMIO:** PS peripherals (UART, I2C, SPI) connect to the K26 SoM via MIO pins (fixed routing inside the package). GPIO lines routed to the PL carrier connector go through EMIO — they pass through the PL fabric and must be mapped in the XDC.
- **USB-UART:** On the KV260 carrier, UART1 (`psu_uart_1`) is connected to the CP2108 USB-to-UART bridge — this is the port that appears as `/dev/ttyUSB1` on Linux and is the target for `xil_printf` output.
- **Power domains:** The K26 SoM has three primary power rails: PS VCC (1.0 V core), PL VCCINT (0.85 V), and VCCO banks (1.2 V / 1.8 V / 3.3 V configurable). The carrier routes PMOD/RPi I/O through the 3.3 V VCCO bank.

### Code Example

```bash
# XSDB session for JTAG bare-metal load on KV260
# Run from Vitis workspace terminal after connecting USB-JTAG

xsdb
% connect
% targets -set -filter {name =~ "PSU"}
% rst
% targets -set -filter {name =~ "Cortex-A53 #0"}
% dow Debug/kv260_axi_bram.elf
% con

# UART output (on Linux host, UART1 = /dev/ttyUSB1 at 115200 baud):
# minicom -D /dev/ttyUSB1 -b 115200
```

### Relevance to Your Project

Your project targets the KV260 with UART over USB for PASS/FAIL output. Confirm Vitis BSP targets `psu_uart_1` (not uart0). During iterative development, JTAG via XSDB avoids repeated SD/QSPI flashing and lets you reload a new ELF in under 10 seconds.

## AMD/Xilinx Tool Updates (Vivado/Vitis 2025.x)

### Key Findings

- **BRAM/FIFO IP removal from standalone IP Catalog (2025.1):** `blk_mem_gen` and `fifo_generator` can no longer be instantiated directly from the IP Catalog in 2025.1+. They are only available inside IP Integrator as `emb_mem_gen` / embedded FIFO. **Workaround:** use XPM macros (`xpm_memory_spram`, `xpm_memory_tdpram`, `xpm_fifo_sync`) or RTL inference templates (Vivado infers BRAM correctly from behavioral VHDL).
- **Vivado 2025.2 new devices:** Adds Versal AI Edge Series Gen 2 (XC2VE35xx, XC2VE38xx) and Versal Prime Series Gen 2 (XC2VM35xx, XC2VM38xx) support.
- **AXI SmartConnect ultra-low-area mode (2025.2):** The AXI SmartConnect IP gains a `STRATEGY` parameter for ultra-low-area mode — reduces LUT count for simple single-master, single-slave topologies like the AXI-BRAM demo.
- **Vitis 2025.2 flow:** The Vitis Unified IDE remains the standard for bare-metal + RTOS + accelerated applications; the Vitis Classic IDE is fully deprecated.
- **2025.1 IP change log:** Available at AMD Adaptive Support article 000037919 without needing a full Vivado install.

### Code Example

```vhdl
-- XPM True Dual Port BRAM instantiation (works in RTL, no IP Catalog needed)
-- Replaces blk_mem_gen when targeting Vivado 2025.1+
library xpm;
use xpm.vcomponents.all;

xpm_memory_tdpram_inst : xpm_memory_tdpram
  generic map (
    ADDR_WIDTH_A       => 10,
    ADDR_WIDTH_B       => 10,
    DATA_WIDTH_A       => 32,
    DATA_WIDTH_B       => 32,
    MEMORY_SIZE        => 32768,   -- bits: 1024 words x 32 bits
    MEMORY_PRIMITIVE   => "block",
    READ_DATA_PIPELINE_STAGES_A => 1,
    READ_DATA_PIPELINE_STAGES_B => 1,
    READ_LATENCY_A     => 1,
    READ_LATENCY_B     => 1
  )
  port map (
    clka   => clk,   clkb   => clk,
    ena    => '1',   enb    => '1',
    wea    => wea,   web    => web,
    addra  => addra, addrb  => addrb,
    dina   => dina,  dinb   => dinb,
    douta  => douta, doutb  => doutb
  );
```

### Relevance to Your Project

If you ever move to Vivado 2025.1 or later, check whether your `create_bd.tcl` references `blk_mem_gen`. If so, either migrate to `emb_mem_gen` in IPI or switch to the XPM instantiation above. For your existing AXI-BRAM Controller IP (`axi_bram_ctrl`), the controller itself is still available — only the underlying BRAM primitive IP changed its instantiation path.
