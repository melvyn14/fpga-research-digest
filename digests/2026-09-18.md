# FPGA Research Digest - 2026-09-18

## Executive Summary

- **AXI-Lite backpressure bug**: Xilinx's own Vivado-generated AXI-Lite slave template has a known BREADY/BVALID handshake defect; manually review `*_axi_slave.vhd` stubs — if `BREADY` is sampled before `BVALID` is asserted, it can deadlock the write-response channel on your KV260 BRAM writes.
- **UART1 must be explicitly enabled**: The KV260 K26 SoM does NOT enable UART1 by default in the Zynq MPSoC PS config; MIO pins 36/37 (TX/RX) must be activated in Vivado's PS block configurator before `xil_printf` output reaches the USB-UART on J4.
- **Vivado 2025.2 AXI SmartConnect ultra-low-area mode**: A new `STRATEGY` parameter enables reduced-area mode for AXI Switch and SmartConnect IP — useful if address decode overhead matters in a future multi-BRAM design.
- **TCL UTF-8 BOM pitfall (2026)**: Vivado batch mode TCL scripts fail with "invalid command name" if the file has a UTF-8 BOM — ensure `create_bd.tcl` is saved as plain UTF-8 without BOM.
- **generate_target -force for stale BD outputs**: After any block design IP parameter change (e.g., BRAM data width), always run `generate_target -force {synthesis simulation} [get_files *.bd]` before synthesis to avoid stale netlists silently passing through.

## 1. AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- **VALID must never depend on READY**: The most pervasive AXI mistake is a master that waits for READY before asserting VALID. The spec forbids this — it can cause a permanent deadlock. On AXI-Lite this most commonly shows up in the write-response channel (BVALID/BREADY).
- **Xilinx generated slave template bug**: As of Vivado 2018.3 and persisting in later versions, the example AXI-Lite slave generated by the "Create and Package New IP" wizard has errors in the BVALID/BREADY logic. Validate any auto-generated wrapper against the ZIPCPU formal property set.
- **Backpressure on read/write channels**: If the PS holds RREADY or BREADY low (e.g., stall from interrupt handling), the slave must deassert ARREADY / AWREADY+WREADY respectively. Bare-metal code rarely stalls on these, but interrupt-driven code can.
- **AXI-Lite vs AXI-Stream**: AXI-Lite is address-mapped (5 channels: AW/W/B/AR/R) and suited for control registers. AXI-Stream is address-less (TVALID/TREADY/TDATA/TLAST) and used for bulk data flows (video, DSP pipelines). The BRAM demo uses AXI-Lite correctly — adding a DMA path in future would use AXI-Stream into an HP port.
- **Single read/write at a time**: Many AXI-Lite slaves can only service one read OR one write simultaneously. The Cortex-A53 PS can issue overlapping transactions; ensure your BRAM controller doesn't silently drop one.

### Code Example

```vhdl
-- Safe AXI-Lite write-response: assert BVALID only after both AWVALID+WVALID seen,
-- and hold it until BREADY seen -- never gate BVALID on BREADY.
process(S_AXI_ACLK)
begin
  if rising_edge(S_AXI_ACLK) then
    if S_AXI_ARESETN = '0' then
      bvalid_r <= '0';
    elsif aw_en = '1' and w_en = '1' and bvalid_r = '0' then
      bvalid_r <= '1';   -- fire BVALID once write completes
    elsif S_AXI_BREADY = '1' and bvalid_r = '1' then
      bvalid_r <= '0';   -- clear after master acknowledges
    end if;
  end if;
end process;
S_AXI_BVALID <= bvalid_r;
S_AXI_BRESP  <= "00";   -- OKAY
```

### Relevance to Your Project

Your project writes 32-bit patterns from the Cortex-A53 to BRAM0 (0xA0000000) and BRAM2 (0xA0010000) and reads them back. Both Block Memory Generators are connected via AXI BRAM Controller (pg078) instances, each as AXI-Lite slaves. The write-response channel handshake above is inside the AXI BRAM Controller IP, but if you ever replace or wrap these with custom logic, the BVALID ordering is the first thing to verify with simulation.

## 2. Vivado Block Design / IP Integrator

### Key Findings

- **Connection Automation auto-wires clocks and resets**: When you run `apply_bd_automation` on an AXI slave interface, Vivado also connects the associated `ACLK` and `ARESETN` ports to the nearest compatible clock/reset in the design — verify these match your PS clock frequency intent.
- **Address Editor unmapped peripheral error**: If block design validation reports "peripheral unmapped," right-click the Address Editor pane → **Auto-Assign Address**. In TCL: `assign_bd_address`.
- **Validate before generating**: Always call `validate_bd_design` before `generate_target` — it catches unconnected ports, mismatched widths, and address overlaps before a 30-minute synthesis run.
- **Vivado 2025.2 SV Interface support**: Vivado 2025.2 adds SystemVerilog Interface support in block designs for simplified AXI connections between SV module instances — useful if you later wrap the BRAM controllers in SV.
- **AXI SmartConnect preferred over AXI Interconnect**: The SmartConnect IP replaces the older AXI Interconnect for new designs and provides better timing closure, especially for multi-master/multi-slave topologies.

### Code Example

```tcl
# TCL snippet: validate BD, generate output products, create HDL wrapper
validate_bd_design
generate_target {synthesis simulation} [get_files *.bd] -force
make_wrapper -files [get_files *.bd] -top
add_files -norecurse [glob ./kv260.gen/sources_1/bd/*/hdl/*_wrapper.v]
set_property top kv260_wrapper [current_fileset]
```

### Relevance to Your Project

Your `create_bd.tcl` script builds the block design programmatically. After any IP parameter change (e.g., widening BRAM address space), `generate_target -force` ensures the synthesis netlist is regenerated — skipping it can cause `write_bitstream` to silently use a stale checkpoint.

## 3. Vivado TCL Scripting

### Key Findings

- **Non-project mode is faster**: Running `vivado -mode batch -source build.tcl` skips the `.xpr` project file and operates entirely in memory. Reports and checkpoints must be explicitly saved with `write_checkpoint` and `report_timing_summary`.
- **UTF-8 BOM causes silent failure (2026 finding)**: A TCL file saved with a UTF-8 BOM (byte-order mark, common from Windows editors) causes Vivado to fail with cryptic "invalid command name" errors. Always save TCL scripts as plain UTF-8.
- **Redirect logs explicitly**: In batch mode, use `-log my_run.log -journal my_run.jou` on the `vivado` invocation to capture logs; without it, `vivado.log` and `vivado.jou` are written to the CWD, which can be misleading in CI.
- **`apply_bd_automation` is scriptable**: The IP Integrator GUI's "Run Connection Automation" button maps to `apply_bd_automation` in TCL, making fully automated BD creation reproducible.
- **Source control tip**: Commit only the `.tcl` script (exported via File → Export → Export Block Design), not the generated BD sources; the script fully recreates the design.

### Code Example

```tcl
#!/usr/bin/env tclsh
# Non-project mode build: synth → impl → bitstream
set part "xck26-sfvc784-2LV-c"
set top  "kv260_wrapper"

read_vhdl   [glob ../vhdl/*.vhd]
read_xdc    ../xdc/kv260_top.xdc

# Regenerate BD output products first
source create_bd.tcl
generate_target {synthesis simulation} [get_files *.bd] -force
make_wrapper -files [get_files *.bd] -top
read_verilog [glob *.gen/sources_1/bd/*/hdl/*_wrapper.v]

synth_design   -top $top -part $part -flatten_hierarchy rebuilt
opt_design
place_design
route_design
write_checkpoint  -force ./output/post_route.dcp
report_timing_summary -file ./output/timing.rpt
write_bitstream   -force ./output/${top}.bit
```

### Relevance to Your Project

Your `create_bd.tcl` can be called from this non-project wrapper to produce `kv260_wrapper.bit` in a single `vivado -mode batch` invocation — suitable for CI (GitHub Actions, etc.) without a GUI license seat.

## 4. Vitis Bare-Metal / Standalone

### Key Findings

- **UART1 not enabled by default on KV260**: The KV260 K26 SoM PS configuration does not enable UART1 by default. In Vivado's Zynq MPSoC IP configurator → UART1, enable it and ensure MIO 36 (TX) and 37 (RX) are assigned. Without this, `xil_printf` output is silently dropped.
- **BSP `stdin`/`stdout` setting**: Even with UART1 MIO-wired, the standalone BSP must have `standalone_stdin` and `standalone_stdout` set to `psu_uart_1` in `xparameters.h` / BSP settings, otherwise `xil_printf` targets UART0 (which is not exposed on KV260).
- **`xil_printf` is lightweight but blocking**: `xil_printf` polls the UART transmit FIFO. It does not require interrupts and is safe in bare-metal. Use it for PASS/FAIL reporting. For formatted float output, use standard `printf` with `newlib` (larger footprint).
- **Linker script memory regions**: Vitis generates `lscript.ld` from the hardware description. For KV260 bare-metal, OCM is at `0xFFFC0000` (256 KB) and DDR starts at `0x00000000`. Place `.text` in DDR for large applications; OCM is useful for exception handlers needing deterministic latency.
- **Vitis 2026.1 Kria platform support**: The `Xilinx/kria-vitis-platforms` repo targets Vitis 2026.1 tools, indicating active platform maintenance through 2026.

### Code Example

```c
#include "xil_printf.h"
#include "xparameters.h"

/* AXI-Lite register write/read helpers for bare-metal */
static inline void axi_write(uintptr_t base, uint32_t offset, uint32_t val) {
    *(volatile uint32_t *)(base + offset) = val;
    /* Data Synchronization Barrier ensures write completes before read-back */
    __asm__ __volatile__("dsb sy" ::: "memory");
}

static inline uint32_t axi_read(uintptr_t base, uint32_t offset) {
    __asm__ __volatile__("dsb sy" ::: "memory");
    return *(volatile uint32_t *)(base + offset);
}

void run_bram_test(uintptr_t base, const char *name) {
    const uint32_t pattern = 0xDEADBEEF;
    axi_write(base, 0x0, pattern);
    uint32_t readback = axi_read(base, 0x0);
    if (readback == pattern)
        xil_printf("[PASS] %s: wrote 0x%08X, read 0x%08X\r\n", name, pattern, readback);
    else
        xil_printf("[FAIL] %s: wrote 0x%08X, read 0x%08X\r\n", name, pattern, readback);
}
```

### Relevance to Your Project

This is a hardened version of the core read/write loop in your `main.c`. The `dsb sy` barrier is critical on Cortex-A53: without it, the out-of-order write buffer can cause the AXI read to return a stale cached value before the write reaches the BRAM controller. Apply it before every AXI-Lite read-back.

## 5. XDC Timing Constraints

### Key Findings

- **`set_input_delay` / `set_output_delay` define external board timing**: These commands tell Vivado how long a signal takes to travel from the external source to the FPGA pin (input) or from the FPGA pin to the external destination (output). A positive `set_input_delay -max` value means data arrives `N ns` after the launching clock edge.
- **AXI-Lite interfaces need no I/O delays if internal only**: For PS-to-PL AXI connections (like BRAM controllers on HP/GP ports), all timing is internal to the Zynq MPSoC — no `set_input/output_delay` is needed. Only apply I/O constraints to physical package pins (UART, GPIO, etc.).
- **Clock groups for PS-derived clocks**: If your PL uses `pl_clk0` from the PS block, declare it with `create_clock` on the buffer output net, not on the PS port. Use `set_clock_groups -asynchronous` if you have multiple clock domains.
- **Programmable I/O delay elements**: Xilinx FPGAs provide IDELAY/ODELAY primitives for fine-grained I/O timing adjustment. For UART pins, this is rarely needed — constrain the UART MIO as asynchronous inputs with `set_false_path` since timing through the PS UART IP is internally managed.
- **Constraint Wizard**: Vivado 2025.x's Timing Constraint Wizard (Tools → Timing → Timing Wizard) can auto-generate `set_input_delay` / `set_output_delay` constraints by walking through each unconstrained I/O port.

### Code Example

```tcl
# kv260_top.xdc - Minimal constraints for KV260 AXI-BRAM bare-metal demo

# PL clock from PS (pl_clk0 at 100 MHz) - net name may vary by BD
# create_clock is only needed if pl_clk0 drives PL logic outside the PS block
# (for pure PS-to-PL AXI, Vivado derives the clock from the PS IP automatically)
# create_clock -period 10.000 -name pl_clk0 [get_pins ps_inst/inst/PS8_i/PLCLK[0]]

# UART MIO pins are PS-managed - false-path them to avoid spurious timing violations
set_false_path -from [get_ports *uart*]
set_false_path -to   [get_ports *uart*]

# Example: if any PL GPIO is connected to package pins
# set_property PACKAGE_PIN <pin>   [get_ports pl_gpio_out]
# set_property IOSTANDARD  LVCMOS18 [get_ports pl_gpio_out]
# set_output_delay -clock pl_clk0 -max 2.0 [get_ports pl_gpio_out]
# set_output_delay -clock pl_clk0 -min 0.5 [get_ports pl_gpio_out]
```

### Relevance to Your Project

Your KV260 AXI-BRAM demo is a pure PS-to-PL AXI transaction with no external I/O in the PL fabric. Your `.xdc` file needs only UART false-paths and any package pin assignments for LEDs/GPIOs you add. The `set_false_path` on UART prevents Vivado from reporting false timing violations on the PS-managed serial lines.

## 6. Kria KV260 / K26 SoM

### Key Findings

- **USB-UART is J4, MIO 36/37**: The micro-USB connector J4 provides both JTAG and UART via the onboard FTDI chip. UART TX/RX are on MIO 36/37 (PS UART1). MIO 10/11 are PS UART0, which is NOT routed to a connector on KV260 — a common source of "no UART output" bugs in bare-metal projects.
- **Boot modes**: KV260 ships in QSPI32 boot mode (pre-loaded firmware in QSPI flash). For bare-metal development, switch to JTAG boot mode by connecting XSCT/XSDB and using `targets -set -filter {name =~ "Cortex-A53 #0"}` then `dow` to download the ELF directly.
- **JTAG FTDI LS_OE_B pin**: The FTDI chip controls JTAG access — when the KV260's FTDI LS_OE_B pin is asserted, the onboard FTDI drives the JTAG lines, allowing Vivado Hardware Manager and Vitis XSCT to connect.
- **EMIO GPIO → PL path**: GPIO signals routed via EMIO go PS → PL fabric → SOM240_1 connector → KV260 carrier card net → Pmod. For bare-metal GPIO control of Pmod pins, use EMIO (not MIO) via `XGpioPs_WritePin()`.
- **Board files automate PS config**: The Kria KV260 board files in Vivado pre-populate the Zynq MPSoC configurator with the correct DDR, UART, MIO, and clock settings — always start from the board file rather than a blank PS configuration to avoid MIO mismatches.
- **GEM3 for KV260 Ethernet**: KV260 uses PS GEM3 (not GEM0/GEM1) for Ethernet; MIO init for PHY differs from KR260/KD240.

### Code Example

```tcl
# XSCT script: JTAG boot and download bare-metal ELF to Cortex-A53 #0
connect
targets -set -filter {name =~ "PSU"}
# Initialize PS (clocks, DDR, MIO) using the generated psu_init.tcl
source {./kv260.sdk/psu_init.tcl}
psu_init
after 1000
targets -set -filter {name =~ "Cortex-A53 #0"}
rst -processor
dow {./kv260.elf}
con
# Open terminal on /dev/ttyUSB1 (or COMx) at 115200 baud to see xil_printf output
```

### Relevance to Your Project

Your project uses `xil_printf` over USB-UART (J4) to report PASS/FAIL. The XSCT snippet above is the canonical way to load your bare-metal ELF without an FSBL — use `psu_init.tcl` (generated by Vitis from your XSA) to bring up DDR and clocks before `dow`. If UART output is missing, confirm UART1 is enabled in the PS block and that `standalone_stdout = psu_uart_1` in BSP settings.

## 7. AMD/Xilinx Tool Updates (Vivado/Vitis 2025.x / 2026.x)

### Key Findings

- **Vivado 2025.2**: New features include SystemVerilog Interface support in block designs (simplified AXI connections), ultra-low-area mode for AXI Switch/SmartConnect via `STRATEGY` parameter, RTL with NoC XPM support in block designs via module referencing, reduced PhysOpt compile time, and BUFG_FABRIC replication per-SLR.
- **Vitis 2025.2**: Enhanced AI Engine API for Versal AI Edge, new data types (MX6, MX4, cbfloat16), DMA-FIFO programming model. For traditional Zynq/Kria bare-metal, the main improvement is continued BSP library updates.
- **Vitis 2026.1**: The `kria-vitis-platforms` repo targets 2026.1 tools — indicates Kria board file and platform maintenance is ongoing. Check for updated XSA packages for KV260 when upgrading.
- **`xil_printf.h` known issue in Vitis 2025.2**: An AMD support thread reports `xil_printf.h` not found in Vitis 2025.2 standalone BSP under certain project configurations — workaround is to explicitly add the BSP `include` directory to the application's include path or use `#include <xil_printf.h>` (angle brackets, not quotes) after verifying BSP linkage.
- **UG973 / UG1742**: Full release notes for Vivado and Vitis 2025.2 are in UG973 and UG1742 respectively on docs.amd.com; check Answer Records linked there for known issues with AXI IP and BRAM controllers.
- **generate_target documented in UG835 (2025.2)**: The `-force` flag is fully documented; use `list_targets [get_ips]` to see what targets a specific IP version supports before calling `generate_target`.

### Code Example

```tcl
# Vivado 2025.x: inspect and regenerate all BD targets with force flag
# Run this after any IP parameter change to avoid stale synthesis netlists

open_project ./kv260/kv260.xpr

# List current target status for all IPs in the design
foreach ip [get_ips -all] {
    puts "IP: [get_property NAME $ip]  Status: [get_property STALE $ip]"
}

# Force regenerate output products for the block design
set bd_file [lindex [get_files *.bd] 0]
generate_target {synthesis simulation} [get_files $bd_file] -force
make_wrapper -files [get_files $bd_file] -top -force

puts "Output products regenerated for: $bd_file"
```

### Relevance to Your Project

If you upgrade from Vivado 2025.1 to 2025.2 or 2026.1, run the stale IP check above after opening the project — the AXI BRAM Controller and Block Memory Generator IPs will likely report as stale and need regeneration before synthesis will succeed cleanly. The `xil_printf.h` include path issue in Vitis 2025.2 is worth checking if you upgrade and lose UART output after a tool version bump.
