## Executive Summary
- **Xilinx's own AXI-Lite template VHDL/Verilog is widely reported as broken** (zipcpu: "Fixing Xilinx's Broken AXI-lite Design") — if you ever start from the Vivado-generated AXI-Lite peripheral template instead of the stock `axi_bram_ctrl` IP, audit it for combinational paths between input and output handshake signals before trusting it.
- **AXI BRAM Controller (PG078) dual-port mode trades resources for throughput**: in single-port mode the controller reads and writes through Port A only; in dual-port mode it writes via Port A and reads via Port B, which pipelines better but costs more BRAM/logic. Your two-BRAM, single-port-per-controller setup (BRAM0/BRAM2) is the simpler, resource-light choice and is fine for the polling PASS/FAIL pattern in `main.c`.
- **`Run Connection Automation` auto-creates the AXI Interconnect, Block Memory Generator, and Proc Sys Reset IP** and wires the AXI BRAM Controller to the PS via SmartConnect — useful to know if you ever rebuild the block design by hand instead of via `create_bd.tcl`, since manually replicating all of this is easy to get subtly wrong (e.g., forgetting Proc Sys Reset fan-out).
- **`apply_bd_automation` is preferred over manual cell wiring for reproducible Tcl**, but one Vivado-IP-flow guide explicitly recommends *against* relying on it for anything beyond basic AXI hookups in scripts meant to be maintained long-term — explicit `connect_bd_intf_net`/`connect_bd_net` calls are more stable across Vivado version bumps for the parts of your design you care about getting exactly right (e.g., dual-BRAM address mapping).
- **Vivado 2025.2's new ultra-low-area STRATEGY mode for AXI SmartConnect/AXI Switch** could shrink interconnect logic if you're ever resource-constrained on the K26's PL fabric — not urgent today since two `axi_bram_ctrl` instances are a tiny design, but worth remembering if the demo grows.

## AXI Protocol / AXI-Lite / AXI-Stream
### Key Findings
- The most-cited AXI mistake (per zipcpu's formal-verification series) is a master or slave waiting for READY before asserting VALID — this violates the spec and can deadlock the bus; VALID must be allowed to assert independently of READY.
- AWVALID and WVALID are independent channels; a slave must not assume AW is accepted before W arrives (or vice versa), and BVALID must only assert after *both* the AW and W sides of a transaction have completed.
- Backpressure is the case most functional testbenches miss: if the master holds BREADY or RREADY low, the slave must correspondingly drop AWREADY/WREADY or ARREADY — untested in simple "always-ready" simulations.
- Per zipcpu's critique, Xilinx's own AXI-Lite VHDL/Verilog template has had known correctness issues since at least 2016 (register-for-register translation from a flawed Verilog reference) — a reason to prefer vendor IP (`axi_bram_ctrl`) over hand-editing the Vivado-generated peripheral template for anything you ship.
- AXI-Stream IP like the Broadcaster has no default TREADY tie-off; an unconnected downstream stream port silently stalls the whole pipeline rather than erroring at build time.

### Code Example
```vhdl
-- Skid-buffered AXI-Lite write-address acceptance, avoiding the
-- VALID-waits-for-READY antipattern and keeping outputs registered.
process(s_axi_aclk)
begin
  if rising_edge(s_axi_aclk) then
    if s_axi_aresetn = '0' then
      awready_r <= '1';   -- ready to accept immediately out of reset
      aw_valid_d <= '0';
    else
      -- Accept AW whenever ready; never gate our own VALID/READY on the
      -- partner channel's state.
      if s_axi_awvalid = '1' and awready_r = '1' then
        awaddr_r   <= s_axi_awaddr;
        aw_valid_d <= '1';
        awready_r  <= '0';     -- back off for one cycle to drain
      elsif aw_valid_d = '1' and downstream_consumed = '1' then
        aw_valid_d <= '0';
        awready_r  <= '1';
      end if;
    end if;
  end if;
end process;

s_axi_awready <= awready_r;
```

### Relevance to Your Project
You're using the stock `axi_bram_ctrl` IP for both BRAM0 and BRAM2, which already implements the AXI4-Lite handshake correctly, so the deadlock/backpressure issues above are not currently live bugs. They become relevant only if you swap in a hand-written AXI-Lite peripheral (e.g., a status/control register block) — in that case, don't start from the raw Vivado peripheral template without reviewing it against the zipcpu critique first.

## Vivado Block Design / IP Integrator
### Key Findings
- Selecting "All Automation" in the Connection Automation dialog auto-instantiates AXI Interconnect/SmartConnect, Block Memory Generator, and Proc Sys Reset, and wires them to the PS — the GUI does in one click what `create_bd.tcl` does in many explicit Tcl calls.
- The Address Editor lets you shrink a BRAM controller's mapped Range (e.g., down to 4K) to conserve address space for future IP, as long as the Range still covers your actual BRAM depth — oversizing the range wastes address space but undersizing it truncates accessible memory.
- `validate_bd_design` propagates IP parameters across connections (width negotiation, AXI4 vs AXI4-Lite link-type negotiation, BRAM operation-mode propagation) — always re-run it after any manual port rewiring, since `regenerate_bd_layout` only redraws the graphical layout and performs no connectivity checking.
- One practitioner guide explicitly recommends minimizing reliance on `apply_bd_automation` for anything beyond the most basic AXI hookups in scripts meant to be version-control-friendly and stable across Vivado releases, favoring explicit `connect_bd_intf_net`/`connect_bd_net` for critical connections.

### Code Example
```tcl
# Validate, regenerate layout, and save non-interactively before export —
# safe to insert right before generate_target in a CI-style build.
open_bd_design [get_files kv260_bd.bd]
validate_bd_design
regenerate_bd_layout
save_bd_design

if {[get_msg_config -count -severity "Critical Warning"] > 0 || \
    [get_msg_config -count -severity "Error"] > 0} {
    puts "ERROR: block design validation failed, aborting build"
    exit 1
}
```

### Relevance to Your Project
Your `create_bd.tcl` builds the PS, interconnect, and two AXI BRAM Controllers explicitly rather than via GUI automation — that's the more reproducible approach for a script tracked in git. Keep doing connection wiring explicitly (`connect_bd_intf_net`) rather than reaching for `apply_bd_automation` if you extend the design, since the explicit form is what's already working and is less likely to change behavior across a future Vivado 2025.2 upgrade.

## Vivado TCL Scripting
### Key Findings
- Non-Project Mode keeps an in-memory design with no `.xpr` written to disk; the script author is fully responsible for source/order management and there's no incremental "stale file" detection — every rebuild re-reads sources from scratch unless you script checkpointing yourself.
- Standard non-project flow: `read_vhdl`/`read_verilog`, `read_xdc`, `synth_design -top <name> -part <part>`, then `opt_design` → `place_design` → (`phys_opt_design`, optional) → `route_design` → `write_bitstream`, with `write_checkpoint` between stages for resumability.
- `vivado -mode batch -source script.tcl -tclargs <args>` is the standard headless CI invocation — batch mode runs the script to completion and exits, as opposed to `-mode tcl` which drops you into an interactive Tcl prompt.
- `apply_bd_automation -rule xilinx.com:bd_rule:axi4 -config {...}` is the Tcl equivalent of "Run Connection Automation" and is far less brittle than manually instantiating every interconnect cell — useful for the parts of a script where you genuinely want default wiring (clock/reset) rather than full manual control.

### Code Example
```tcl
# Build pattern for two AXI BRAM controllers with explicit, version-stable
# wiring matching the BRAM0/BRAM2 base addresses in this project.
create_bd_cell -type ip -vlnv xilinx.com:ip:axi_bram_ctrl:4.1 axi_bram_ctrl_0
create_bd_cell -type ip -vlnv xilinx.com:ip:axi_bram_ctrl:4.1 axi_bram_ctrl_2

foreach {ctrl base} {axi_bram_ctrl_0 0xA0000000 axi_bram_ctrl_2 0xA0010000} {
    connect_bd_intf_net [get_bd_intf_pins zynq_ultra_ps_e_0/M_AXI_HPM0_FPD] \
                         [get_bd_intf_pins ${ctrl}/S_AXI]
    set_property offset $base \
        [get_bd_addr_segs "zynq_ultra_ps_e_0/Data/SEG_${ctrl}_Mem0"]
}

validate_bd_design
save_bd_design
```

### Relevance to Your Project
Your existing `create_bd.tcl` already favors explicit connections over automation, which is the right call for a script that needs to keep producing the same BRAM0/BRAM2 address layout build after build. If you ever add a third BRAM or peripheral, extending the `foreach` pattern above (rather than copy-pasting another block) keeps the address assignment centralized and harder to get wrong.

## Vitis Bare-Metal / Standalone
### Key Findings
- `xil_printf` only supports `%d`, `%l`, `%x`, `%c`, `%s` (no `%f`) — it trades floating-point/format richness for a much smaller code and stack footprint than libc `printf`, which matters on a bare-metal app with limited OCM/DDR allocation.
- The standalone BSP defaults `stdin`/`stdout` to a specific UART instance; if a platform's `vitis-comp.json` (or BSP settings dialog) has the wrong UART selected for your carrier's USB-UART bridge, your `xil_printf` PASS/FAIL output silently goes nowhere even though the app runs correctly.
- Bare-metal GIC interrupt setup is a two-step process: registering the ISR (`XScuGic_Connect` + setting priority/trigger type) is necessary but not sufficient — you must also explicitly enable the corresponding bit (`XScuGic_Enable`), or the handler stays "registered but silent."
- The linker script `lscript.ld` (editable directly in the Vitis IDE) defines where `.text`/`.data`/`.bss`/`.heap` land in OCM/DDR; after switching the underlying XSA/hardware platform, double-check the memory region base/size still matches, since a stale linker script can silently truncate the heap or place code outside valid DDR.

### Code Example
```c
#include "xil_printf.h"
#include "xparameters.h"
#include "xil_io.h"

#define BRAM0_BASEADDR XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR /* 0xA0000000 */
#define BRAM2_BASEADDR XPAR_AXI_BRAM_CTRL_1_S_AXI_BASEADDR /* 0xA0010000 */

int test_bram(u32 base, const char *name) {
    u32 pattern = 0xA5A5A5A5;
    Xil_Out32(base, pattern);
    u32 readback = Xil_In32(base);
    if (readback == pattern) {
        xil_printf("%s: PASS (wrote 0x%x, read 0x%x)\r\n", name, pattern, readback);
        return 0;
    }
    xil_printf("%s: FAIL (wrote 0x%x, read 0x%x)\r\n", name, pattern, readback);
    return 1;
}
```

### Relevance to Your Project
This is the same write/readback/PASS-FAIL idiom your `main.c` already uses against BRAM0/BRAM2. If a future revision drives the BRAM-write loop from an interrupt (e.g., a timer or AXI GPIO "go" pin) instead of pure polling, remember the GIC two-step above — a handler that's connected but never `XScuGic_Enable`'d is a classic silent failure mode that looks identical to "interrupt never fires" from the application's point of view.

## XDC Timing Constraints
### Key Findings
- `set_input_delay`/`set_output_delay` model the external system-level path delay relative to a clock edge at a primary I/O; the values can legitimately be negative depending on the data/clock phase relationship at the board level — don't assume all delay values must be positive.
- Input setup timing is effectively the driving device's clock-to-Q delay, not literally "setup time at the FPGA pin" — a common source of confusion when translating a datasheet's timing diagram directly into `set_input_delay -max`.
- Every clock domain crossing must be explicitly covered by `set_clock_groups -asynchronous`; undeclared CDCs default to being timed as synchronous, which can produce spurious timing failures (over-constraining) or, worse, falsely "pass" paths that are actually metastability risks.
- For Zynq UltraScale+ specifically, assigning a clock root in the same clock region as a BUFG_GT driver can make the design unroutable for outputs in certain other clock regions — a niche but documented gotcha when adding any gigabit-transceiver-adjacent clocking.

### Code Example
```tcl
# Board-level XDC additions needed only if you add direct PL I/O
# (not required for the pure PS<->PL AXI-only BRAM path today).
create_clock -period 8.000 -name pl_clk0 [get_ports pl_clk0_p]

set_input_delay  -clock pl_clk0 -max 1.5 [get_ports {ext_data[*]}]
set_input_delay  -clock pl_clk0 -min 0.3 [get_ports {ext_data[*]}]
set_output_delay -clock pl_clk0 -max 1.2 [get_ports {ext_ctrl[*]}]
set_output_delay -clock pl_clk0 -min -0.5 [get_ports {ext_ctrl[*]}]

set_clock_groups -asynchronous \
    -group [get_clocks -include_generated_clocks clk_fpga_0] \
    -group [get_clocks -include_generated_clocks pl_clk0]
```

### Relevance to Your Project
Your design is purely PS-driven AXI (a single clock domain feeding both BRAM controllers via the PS-generated FCLK), so board-level `set_input_delay`/`set_output_delay` constraints aren't needed today — those only apply once a port crosses the board boundary. The CDC/`set_clock_groups` guidance becomes relevant the moment you add any PL-side clock independent of the PS FCLK (e.g., a free-running oscillator feeding custom logic in `kv260_top.vhd`).

## Kria KV260 / K26 SoM
### Key Findings
- The Kria starter kits ship with boot firmware preloaded in QSPI, defaulting to QSPI32 boot mode; the underlying boot-mode selection is via the SOM's MODE[3:0] pins, which the carrier card ties off (exposed as a physical boot-mode switch on the KV260 starter carrier).
- The K26 board file (provided by AMD) encodes the SOM's required MIO configuration and provides a minimal bootable-to-Linux hardware config; you layer your own custom MIO/PL physical interfaces on top while following the Carrier Card Design Guide (UG1091).
- Starting with the 2022.1 Kria Linux images, the default "k26-starter-kits" bitstream has no functional PL logic of its own beyond an EMIO mapping for carrier fan control — meaning a from-scratch bare-metal design (like this project) is genuinely starting from near-empty PL fabric, not inheriting hidden default logic.
- The documented baremetal AXI-BRAM reference flow (xilinx.github.io/kria-apps-docs) matches this project closely: add an AXI BRAM Controller, run Connection Automation to tie `S_AXI` to `M_AXI_HPM0_FPD`, set the controller to single-BRAM-interface mode, and deselect the unused second HPM master port rather than leaving it dangling.
- A community 2025.2-era guide ("Bare-metal 4K Streaming on KV260") confirms the bare-metal + Vivado/Vitis 2025.x toolchain combination remains an actively maintained path for this exact board as of mid-2026, so 2025.1 is well-supported ground.

### Code Example
```tcl
# PS configuration matching the single-HPM-master, BRAM0/BRAM2 pattern
set_property -dict [list \
    CONFIG.PSU__USE__M_AXI_GP0 {1} \
    CONFIG.PSU__USE__M_AXI_GP1 {0} \
    CONFIG.PSU__MAXIGP0__DATA_WIDTH {32} \
] [get_bd_cells zynq_ultra_ps_e_0]
```

### Relevance to Your Project
This matches the documented official Kria baremetal AXI-BRAM pattern almost exactly — your BRAM0/BRAM2 controllers both feeding off `M_AXI_HPM0_FPD`. Confirm in your `create_bd.tcl` that the unused second HPM master (`PSU__USE__M_AXI_GP1`) is explicitly disabled rather than just unconnected, since an enabled-but-unconnected master is a common source of `validate_bd_design` critical warnings that get mistakenly ignored.

## AMD/Xilinx Tool Updates
### Key Findings
- Vivado 2025.1 added the ability to boot the processing system first and dynamically load PL logic later (fast OS bring-up with deferred bitstream load) and a new addressing GUI for automatic grouping of equivalent address spaces on newer Versal device families — not directly relevant to Zynq UltraScale+/K26 but indicates where AMD's address-editor tooling investment is headed.
- Vivado 2025.2 introduces a new Pblock planner, improved Directive/Subdirective QoR mapping (with an automatic Tcl-based migration script from old directives to new ones), simplified AXI connections for SystemVerilog instances with automatic IP/BD wrapper management, and a new ultra-low-area `STRATEGY` mode for AXI Switch/AXI SmartConnect IP.
- 2025.2 also ships a refreshed IDE look (new light/dark themes, revamped Welcome page) and adds Spartan UltraScale+ family support — cosmetic/unrelated to this project, but useful to know before assuming a UI screenshot from an older tutorial still matches your install.
- AXI BRAM Controller (PG078) v4.1 supports optional ECC regardless of single- or dual-port BRAM configuration (`C_ECC = 1`) — not something this project currently needs, but worth remembering if BRAM reliability ever becomes a concern (e.g., scaling up test patterns).

### Code Example
```tcl
# Quick version/part sanity check to run at the top of any build script,
# useful when moving between 2025.1 and a future 2025.2 toolchain.
puts "Vivado version: [version -short]"
if {[llength [get_parts -quiet -filter {PART_NAME =~ "*xck26*"}]] == 0} {
    puts "WARNING: K26/KV260 part files not found - check installed device support"
}
```

### Relevance to Your Project
2025.1 remains current and stable for this project; no urgent action needed. If/when you move to 2025.2, the new AXI SmartConnect ultra-low-area `STRATEGY` mode is worth a look if resource usage ever becomes a concern, and re-run `validate_bd_design` after the cross-version block-design open, since IP re-customization prompts for `axi_bram_ctrl` and the Zynq UltraScale+ PS block are common on a version bump.
