# FPGA Research Digest - 2026-10-31

## Executive Summary
- **AXI slave stall risk**: Xilinx embedded IP AXI slaves assert READY only after both address AND data are valid — a master that waits for READY before asserting VALID will deadlock. Critical check for BRAM0/BRAM2 write sequences in `main.c`.
- **BRAM address assignment in TCL**: Use `assign_bd_address -offset 0xA0000000 -range 64K` explicitly in `create_bd.tcl` to pin BRAM0 and BRAM2 controller segments at the addresses your bare-metal code expects (0xA0000000 / 0xA0010000).
- **AXI register slices for timing closure**: Insert AXI Register Slices between the PS master port and each BRAM controller if you hit timing violations during implementation — this is the recommended low-effort fix and takes seconds in IP Integrator.
- **Vivado 2025.1 XDC bug**: Answer Record 000037546 documents that removing an XDC file from one constraint set can silently remove it from all constraint sets. Back up your constraints before modifying sets.
- **BSP UART mis-routing is a common bare-metal gotcha**: After regenerating the platform from a new XSA, verify that `standalone_stdin` and `standalone_stdout` in `vitis-comp.json` are both set to `psu_uart_1` (MIO36/37 on K26). A mismatch silences all `xil_printf` output with no error.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings
- **Handshake rule**: A transfer occurs if and only if both VALID and READY are asserted on the same rising clock edge. Nothing happens unless `xVALID && xREADY`.
- **Slave deadlock**: AMD Answer Record 63381 — Xilinx embedded IP slave interfaces do not assert READY until the master has driven valid address, control, and data simultaneously. A master that waits for READY before asserting VALID will stall forever.
- **Write response timing**: BVALID may only be asserted by the slave after the final WVALID/WREADY handshake completes. Ignoring this can cause dropped B-channel responses.
- **Timing violations**: Adding AXI Register Slices between IP blocks is the simplest fix for setup violations on long AXI paths (AMD community recommendation, Vivado 2024.2+).
- **AXI-Stream TLAST bug**: ZipCPU found that Xilinx's AXI-Stream master template can assert TLAST on the penultimate beat while the channel is stalled (TREADY low), violating the protocol and producing packets of incorrect length.
- **Backpressure on streams**: AXI-Stream has no limit on how long a slave may deassert TREADY. Design your masters to tolerate indefinite stalling, or add FIFO buffers.
- **AXI-Lite has no TLAST**: AXI-Lite is strictly memory-mapped with single-beat transactions; TLAST, TDATA, and other stream signals don't apply.

### Code Example
```c
/* AXI-Lite write with volatile pointer — correct bare-metal pattern */
#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL

static inline void axi_write32(uintptr_t addr, uint32_t val) {
    /* volatile prevents the compiler from reordering or eliding MMIO access */
    *(volatile uint32_t *)addr = val;
}

static inline uint32_t axi_read32(uintptr_t addr) {
    return *(volatile uint32_t *)addr;
}

/* Write pattern to BRAM0 word 0, then read back */
axi_write32(BRAM0_BASE + 0x00, 0xDEADBEEF);
uint32_t rd = axi_read32(BRAM0_BASE + 0x00);
if (rd == 0xDEADBEEF) xil_printf("PASS\r\n");
else                  xil_printf("FAIL: got 0x%08X\r\n", rd);
```

### Relevance to Your Project
The `main.c` in `kv260-axi-bram-demo` writes patterns to BRAM0 at `0xA0000000` and BRAM2 at `0xA0010000`. The volatile-pointer approach above matches what Vitis generates, but be sure there are no gaps between your write and read that the compiler could optimize away. If you observe intermittent read-back failures, insert a `dsb()` or `Xil_DCacheFlush()` to rule out the A53's write buffer. Also confirm the AXI slave deadlock condition is not triggered by checking that your PS master AXI port is already driving valid address before checking BRESP.

## Vivado Block Design / IP Integrator

### Key Findings
- **Run Connection Automation**: Click the banner at the top of the canvas, then select *All Automation* to wire all eligible ports at once. The tool auto-assigns port names; rename them afterward in External Interface Properties.
- **Address overlap bug**: Connection Automation can produce overlapping address ranges when two master ports (e.g., HP0 and HP2) cover the same address space. If Vivado silently assigns the same offset to two slaves, open the Address Editor and manually resolve the conflict.
- **Address Editor tab**: The tab only appears when the design contains a bus master. If it doesn't appear, use `Window > Address Editor` from the main menu.
- **Auto vs manual assignment**: Use *Assign All* for a first pass, then manually fix any BRAM controller offsets that don't match what your software expects.
- **Output products auto-save**: Generating or resetting output products performs an automatic BD save. Running Generate before Validate will trigger Validate first and surface DRC errors.
- **Width converter**: Vivado defaults to full AXI4 for most peripherals, even when AXI-Lite suffices. Adding a width converter must be done manually; the tool won't warn you that you're adding unnecessary logic.

### Code Example
```tcl
# After placing IP in the block design, assign addresses explicitly
assign_bd_address -offset 0xA0000000 -range 64K \
    [get_bd_addr_segs bram_ctrl_0/S_AXI/Mem0]

assign_bd_address -offset 0xA0010000 -range 64K \
    [get_bd_addr_segs bram_ctrl_2/S_AXI/Mem0]

# Validate the design before generating output products
validate_bd_design

# Regenerate all output products
generate_target all [get_files *.bd]
```

### Relevance to Your Project
Your `create_bd.tcl` script drives the entire block design. Running it with the explicit `assign_bd_address` calls above guarantees that BRAM0 and BRAM2 are always mapped to exactly the base addresses your `main.c` hard-codes, regardless of Vivado version or any prior automated assignment that may differ between installs.

## Vivado TCL Scripting

### Key Findings
- **Non-project mode core commands**: `read_vhdl`, `read_ip`, `read_bd`, `read_xdc` load sources into memory. Output products must be generated manually with `generate_target` or `synth_ip`.
- **BD name length**: Keep block design names to 25 characters or fewer. Longer names cause Windows path-length failures; the Tcl variable `$design_name` should be short and descriptive.
- **Batch invocation**: `vivado -mode batch -source create_bd.tcl` runs the script headlessly. Append `-notrace` to suppress Tcl command echoing in CI logs.
- **Export to Tcl**: In the GUI, use *File > Export > Export Block Design* to regenerate a Tcl script from an existing `.bd`. Edit the result to remove project-specific `set_property` calls before checking it in.
- **assign_bd_address options**: Use `-offset`, `-range`, and `-target_address_space` for fixed mapping. The `-with_name` and `-with_locktype` options are available from 2023.2 onward — check UG835 for your installed version.
- **Path invalidation after hierarchy**: Cell paths change after `group_bd_cells` creates a hierarchy. Store paths before calling it, or re-query with `get_bd_cells` after.
- **Version guard**: Add a version check at the top of CI scripts: `if { [version -short] < "2025" } { error "Requires Vivado 2025 or later" }`.

### Code Example
```tcl
# create_bd.tcl — non-project batch skeleton
set design_name kv260_top
set part        xck26-sfvc784-2LV-c

# Create in-memory project
create_project -in_memory -part $part

# Load constraints
read_xdc constr/kv260.xdc

# Create block design
create_bd_design $design_name
current_bd_design $design_name

# Add Zynq UltraScale+ MPSoC
set zynq [create_bd_cell -type ip -vlnv xilinx.com:ip:zynq_ultra_ps_e:3.5 zynq_ultra_ps_e_0]

# Add BRAM controller and generator
set ctrl0 [create_bd_cell -type ip -vlnv xilinx.com:ip:axi_bram_ctrl:4.1 bram_ctrl_0]
set bram0 [create_bd_cell -type ip -vlnv xilinx.com:ip:blk_mem_gen:8.4 blk_mem_gen_0]

# Connect BRAM controller to BRAM
connect_bd_intf_net [get_bd_intf_pins $ctrl0/BRAM_PORTA] \
                    [get_bd_intf_pins $bram0/BRAM_PORTA]

# Assign address
assign_bd_address -offset 0xA0000000 -range 64K \
    [get_bd_addr_segs ${ctrl0}/S_AXI/Mem0]

validate_bd_design
generate_target all [get_files *.bd]
```

### Relevance to Your Project
Your existing `create_bd.tcl` is the automation backbone of the project. The version guard prevents subtle failures when the script is run on a different Vivado installation. The explicit `assign_bd_address` calls are particularly important because Vivado's auto-assignment is non-deterministic across versions and can place BRAM controllers at unexpected addresses, breaking `main.c` silently.

## Vitis Bare-Metal / Standalone

### Key Findings
- **xil_printf limitations**: No floating-point support. Print floats by splitting into integer and fractional parts: `xil_printf("%d.%03d\r\n", (int)f, (int)((f - (int)f) * 1000))`.
- **UART routing after XSA regeneration**: After exporting a new XSA from Vivado, Vitis may reset `standalone_stdin` / `standalone_stdout` to a default UART. Open `vitis-comp.json` and set both to `psu_uart_1` (K26's default UART on MIO36/37), then click *Regenerate BSP*.
- **Linker script**: Vitis generates `lscript.ld` automatically based on the hardware memory map. If BRAM appears as a memory region in the XSA, Vitis will list it in the linker script; you can redirect `.data` or stack there.
- **Interrupt controller**: For bare-metal A53, use `XScuGic` (Generic Interrupt Controller). PL interrupts enter via `pl_ps_irq[0:7]` in the block design.
- **Platform regeneration**: After any block design change, export a new XSA (`write_hw_platform -fixed -include_bit output.xsa`) and click *Update Hardware* in the Vitis platform component to sync BSP headers.
- **Startup**: The CRT (`_start`) sets up the MMU, caches, and exception vectors before calling `main()`. Don't call `Xil_DCacheFlush` before the cache is enabled, or it will fault.

### Code Example
```c
#include "xil_printf.h"
#include "xparameters.h"
#include "sleep.h"

/* KV260 BRAM base addresses — must match XDC/BD address assignment */
#define BRAM0_BASE  XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR
#define BRAM2_BASE  XPAR_AXI_BRAM_CTRL_1_S_AXI_BASEADDR

int main(void) {
    xil_printf("KV260 AXI BRAM demo starting\r\n");

    /* Write a walking-ones pattern to BRAM0 */
    for (int i = 0; i < 16; i++) {
        *(volatile uint32_t *)(BRAM0_BASE + i * 4) = (1u << i);
    }

    /* Verify */
    int pass = 1;
    for (int i = 0; i < 16; i++) {
        uint32_t rd = *(volatile uint32_t *)(BRAM0_BASE + i * 4);
        if (rd != (1u << i)) { pass = 0; break; }
    }
    xil_printf("BRAM0 walking-ones: %s\r\n", pass ? "PASS" : "FAIL");
    return 0;
}
```

### Relevance to Your Project
Using `XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR` (auto-generated into `xparameters.h` from the XSA) instead of hard-coded addresses makes the software portable across block design iterations, as long as the TCL `assign_bd_address` calls match what Vitis generates. The UART stdout check is critical — if you don't see `xil_printf` output over USB-UART, the BSP UART mapping is almost certainly the cause.

## XDC Timing Constraints

### Key Findings
- **Clock groups for async domains**: Use `set_clock_groups -asynchronous -group [get_clocks clk_pl] -group [get_clocks clk_ps]` for any asynchronous CDC paths. `set_clock_groups` has higher precedence than `set_max_delay` and will override it.
- **set_input_delay semantics**: `-max` controls the setup check (worst-case data arrival), `-min` controls the hold check (best-case data arrival), measured at the FPGA input pin relative to the capturing clock.
- **set_output_delay semantics**: `-max` sets the external setup requirement (how early data must arrive before the external clock edge), `-min` sets the external hold requirement.
- **False path vs. max delay**: Use `set_false_path` only when timing is truly irrelevant (e.g., reset). Use `set_max_delay -datapath_only` when you want Vivado to check the path but not count skew.
- **UG903 is the reference**: Vivado Design Suite User Guide Using Constraints UG903 for your specific release is the authoritative source for XDC syntax. The syntax has not changed significantly since 2022.1.
- **Vivado 2025.1 XDC bug**: Removing an XDC file from one constraint set silently removes it from all constraint sets (Answer Record 000037546). Save a backup before modifying constraint sets.

### Code Example
```tcl
# kv260.xdc — minimal constraints for KV260 AXI-BRAM demo

# PL clock from PS (100 MHz via FCLK_CLK0)
# The clock is defined automatically from the Zynq IP; no create_clock needed.
# If using an external oscillator on a carrier card:
# create_clock -period 10.000 -name pl_clk [get_ports pl_clk_i]

# Asynchronous clock groups between PS and PL clocks
set_clock_groups -asynchronous \
    -group [get_clocks -include_generated_clocks clk_pl_0_100M] \
    -group [get_clocks -include_generated_clocks clk_ps]

# Example: external GPIO input with 5 ns external delay
# set_input_delay -clock [get_clocks clk_pl_0_100M] -max 5.0 [get_ports gpio_in[*]]
# set_input_delay -clock [get_clocks clk_pl_0_100M] -min 1.0 [get_ports gpio_in[*]]

# Relax Vivado's default CDC analysis on PS reset
set_false_path -from [get_pins -hierarchical -filter {NAME =~ *PS_0/inst/*FCLKRESETN*}]
```

### Relevance to Your Project
The KV260 AXI-BRAM demo currently uses only a PS-generated PL clock, so the minimal XDC above is sufficient. The key practice is to prevent Vivado from timing across PS/PL domain boundaries with `set_clock_groups`. If you add any external I/O (LEDs, GPIO), follow the `set_input_delay`/`set_output_delay` pattern before any timing reports show missing constraints.

## Kria KV260 / K26 SoM

### Key Findings
- **Boot mode strapping**: The primary boot device is selected by the `MODE[3:0]` pins on the carrier card. The SOM pulls all mode pins high to 1.8V through resistors; the carrier must pull them low to select a different mode. Quad-SPI uses MIO[5:0]; eMMC uses MIO[13:22].
- **MIO bank voltages**: All three MIO banks (500, 501, 502) are powered by the SOM at 1.8V. Bank 501 covers MIO[26:51], bank 502 covers MIO[52:77]. Do not drive them with 3.3V logic.
- **Reserved MIO pins**: MIO[32:34] are reserved for PMU power management. MIO31 is the hardware-requested shutdown input. Do not use these in your PL design.
- **Default UART**: The K26 boot firmware and PetaLinux BSP default to MIO36 (TX) and MIO37 (RX) for UART1. For bare-metal work over USB-UART, confirm your Vivado PS configuration maps `UART1` to these pins.
- **Power domains**: Three domains — Always-On, PS (supports PS MIO and PS-GTR peripherals), and PL (supports PL HDIO). The SOM exposes power-good signals for FPD, LPD, and PL rails. A `PWROFF` control turns off all SOM rails.
- **PL slave address space**: On Zynq UltraScale+, PL slave space starts at `0x4000_0000` for GP ports. AXI HP/HPM ports have different base addresses. For `M_AXI_HPM0_FPD`, PL space begins at `0xA000_0000` — which is exactly the base address used in this project.

### Code Example
```tcl
# Vivado TCL — configure PS UART1 to MIO36/37 for K26 USB-UART
set_property -dict [list \
    CONFIG.PSU__UART1__PERIPHERAL__ENABLE {1} \
    CONFIG.PSU__UART1__PERIPHERAL__IO     {MIO 36 .. 37} \
] [get_bd_cells zynq_ultra_ps_e_0]

# Configure M_AXI_HPM0_FPD master for PL access
set_property -dict [list \
    CONFIG.PSU__USE__M_AXI_GP0         {1} \
    CONFIG.PSU__MAXIGP0__DATA_WIDTH    {32} \
] [get_bd_cells zynq_ultra_ps_e_0]
```

### Relevance to Your Project
The project's Cortex-A53 bare-metal code communicates over USB-UART for PASS/FAIL output. If the PS configuration in `create_bd.tcl` doesn't explicitly route UART1 to MIO36/37, the carrier board's USB-UART bridge won't receive output. Similarly, the `M_AXI_HPM0_FPD` master port configuration must be enabled for AXI-Lite transactions to reach the BRAM controllers at `0xA0000000` and `0xA0010000`.

## AMD/Xilinx Tool Updates (Vivado/Vitis 2025.x)

### Key Findings
- **Vivado 2025.1 IP changelog**: Mostly catalog taxonomy updates. Notable addition: new GT Wizard support for Versal devices. Most AXI and BRAM IP versions are unchanged from 2024.2.
- **Vitis 2025.1 new features**: CFLOAT MAC support and a Vector IFFT float block added (primarily for AI Engine targets, not relevant to KV260 bare-metal).
- **Known issue — XDC constraint sets**: Removing an XDC file from one constraint set removes it from all constraint sets silently (Answer Record 000037546). Workaround: check all constraint sets after any modification.
- **Known issue — DRC HDPR-6**: A spurious `HDPR-6` DRC error during `place_design` in 2025.1 can be worked around by running `set_property SEVERITY {Warning} [get_drc_checks HDPR-6]` in your TCL implementation script.
- **Known issue — MIPI C-PHY/D-PHY**: An IP-specific issue in 2025.1.1 affects MIPI designs; not relevant to AXI-BRAM demos.
- **Vitis file dialog failure**: On AlmaLinux 9.5 and RHEL 9.5, the Vitis Unified IDE file-open dialog fails. Workaround: use the Tcl console or CLI (`vitis -s <script.py>`) on those platforms.
- **2026.1 is now current**: As of late 2026, Vivado/Vitis 2026.1 is the latest release. If you plan to migrate, check the IP Catalog for any AXI BRAM Controller version changes.

### Code Example
```tcl
# Workaround for Vivado 2025.1 HDPR-6 spurious DRC error
# Add to your implementation TCL script before place_design
set_property SEVERITY {Warning} [get_drc_checks HDPR-6]

# Guard script to warn if running on wrong Vivado version
set vivado_ver [version -short]
if { [string compare $vivado_ver "2025.1"] < 0 } {
    puts "WARNING: Script tested on Vivado 2025.1; current version is $vivado_ver"
    puts "         Some commands may behave differently."
}

# Safely remove an XDC from only one constraint set (avoids the 2025.1 multi-set bug)
# Instead of: remove_files -fileset constrs_1 [get_files kv260.xdc]
# Do this:
set_property used_in_synthesis  true  [get_files kv260.xdc]
set_property used_in_implementation true [get_files kv260.xdc]
# Then add to a second constraint set without removing from the first:
add_files -fileset constrs_2 [get_files kv260.xdc]
```

### Relevance to Your Project
The XDC constraint-set bug directly affects the KV260 project if you maintain separate `synthesis` and `implementation` constraint sets (a common practice for timing-exception-only constraints). The HDPR-6 workaround is a quick addition to your implementation script that prevents a false DRC failure from blocking bitstream generation in CI. The version guard in `create_bd.tcl` will also catch accidental runs on 2026.x where command syntax may have changed.
