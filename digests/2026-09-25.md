# FPGA Research Digest - 2026-09-25

## Executive Summary

- **AXI-Lite VALID must never be de-asserted once raised without a completed handshake** — the most common implementation bug; can cause silent data loss on your BRAM writes at 0xA0000000 / 0xA0010000 if the AXI Interconnect stalls.
- **Vivado 2025.2 changed IP config format from XML to JSON** — Block Memory Generator and FIFO Generator are now feature-frozen; AMD recommends migrating to XPM_MEMORY and XPM_FIFO macros for new designs.
- **AXI SmartConnect gains an ultra-low-area mode** (`STRATEGY` parameter) in 2025.2 — useful if fabric resources are tight on K26 after instantiating two BRAM controllers.
- **Kria K26 bare-metal flow requires FSBL or direct JTAG** — the SOM ships in QSPI32 boot mode; for iterative bare-metal development it is fastest to override to JTAG mode and program bitstream + ELF directly from Vitis.
- **SystemVerilog Interface support added in Vivado 2025.2** — AXI connections between SV instances now get automatic wrapper creation, which simplifies top-level wiring even when using VHDL wrapper + SV sub-blocks.

> **Note on project source files:** The kv260-axi-bram-demo repository (`melvyn14/kv260-axi-bram-demo`) was inaccessible in this session (only the digest repository is in scope). Code examples below are derived from documentation and community sources, mapped to the known project structure.

## 1. AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- **VALID must not depend on READY** (AXI spec rule): a master that waits for ARREADY before asserting ARVALID creates a dependency loop and can deadlock certain Interconnect configurations. This is the single most-cited bug in formal verification of AXI-Lite slaves.
- **Backpressure on BREADY**: if the PS holds BREADY low, the AXI Interconnect will stall AWREADY and WREADY upstream — ensure the bare-metal driver reads the write-response channel promptly, or configure the Interconnect's `C_S_AXI_DATA_WIDTH` to accept and discard write responses automatically.
- **AXI-Stream TKEEP / TSTRB are optional** — only TDATA, TVALID, and TREADY are mandatory. TLAST marks end-of-packet and is required when using the AXI4-Stream Data FIFO IP.
- **All AXI signals sample on the rising clock edge**; changes must occur after the rising edge — do not use combinational output directly on AXI signals from a slow path.

### Code Example

```vhdl
-- AXI-Lite read channel: ARVALID raised independently of ARREADY
-- Compliant pattern: raise ARVALID as soon as address is available,
-- hold it until ARREADY is seen
process(clk)
begin
  if rising_edge(clk) then
    if rst = '1' then
      arvalid_r <= '0';
    elsif start_read = '1' then
      arvalid_r <= '1';                  -- assert unconditionally
    elsif s_axi_arready = '1' then
      arvalid_r <= '0';                  -- de-assert only after handshake
    end if;
  end if;
end process;
s_axi_arvalid <= arvalid_r;
```

### Relevance to Your Project

Your `main.c` drives AXI-Lite writes to BRAM0 (`0xA0000000`) and BRAM2 (`0xA0010000`) via Xilinx `Xil_Out32` / `Xil_In32`. These are direct memory-mapped accesses — the Zynq PS AXI master handles the handshake internally. However, if you extend the project to a custom AXI-Lite peripheral in your `kv260_top.vhd`, the VALID-before-READY rule applies to any slave logic you write.

## 2. Vivado Block Design / IP Integrator

### Key Findings

- **Connection Automation** in IP Integrator auto-instantiates AXI Interconnect, Block Memory Generator, and Proc Sys Reset when connecting an AXI BRAM Controller to the Zynq MPSoC IP — it handles address assignment automatically.
- **Address Editor tab** only appears when a bus master IP (Zynq MPSoC) is present in the block design; use **Auto-Assign Address** (right-click in Address Editor) to resolve "unmapped peripherals" validation errors.
- **Address locking via TCL**: `set_property locktype local [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]` — prevents auto-reassignment when regenerating the design; critical for fixed-address bare-metal drivers.
- **Do not use spaces** in block design names or directory paths — causes cryptic Vivado errors during implementation.
- **Selectively upgrade IP**: Vivado 2025.2 allows upgrading individual IPs within a block design without regenerating the entire design (UG994 — Selectively Upgrading IP in Block Designs).

### Code Example

```tcl
# Lock BRAM address segment so it stays at 0xA0000000 after regeneration
set_property offset 0xA0000000 [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property range 64K          [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property locktype local     [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]

set_property offset 0xA0010000 [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_1_Mem0}]
set_property range 64K          [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_1_Mem0}]
set_property locktype local     [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_1_Mem0}]
```

### Relevance to Your Project

Your `create_bd.tcl` script builds the block design programmatically. The address locking snippet above ensures BRAM0 and BRAM2 remain at their expected addresses across repeated `source create_bd.tcl` invocations — without it, Vivado may reassign addresses if you add IPs and re-run auto-assign.

## 3. Vivado TCL Scripting

### Key Findings

- **`write_project_tcl -force recreate.tcl`** exports the entire existing Vivado project as a reproducible TCL script — use this to capture a known-good state before making risky changes.
- **Batch mode invocation**: `vivado -mode batch -source build.tcl -tclargs arg1 arg2` — args accessible inside the script as `$argv`. Vivado opens, runs, and exits automatically.
- **Journal file (`.jou`)**: every GUI action is logged; replaying the journal is a quick way to script a sequence you performed interactively.
- **Non-project mode** reads sources and runs synthesis/implementation entirely in-memory; you are responsible for re-running stages when sources change — suitable for CI pipelines but adds management overhead.
- **`synth_design -top` and `impl_design`** are the key non-project mode commands; use `write_bitstream -force` at the end.

### Code Example

```tcl
# Minimal non-project mode build script for KV260 AXI-BRAM demo
set part "xck26-sfvc784-2LV-c"

read_vhdl  [glob ./vhdl/*.vhd]
read_xdc   [glob ./constraints/*.xdc]

# Synthesise
synth_design -top kv260_top -part $part -flatten_hierarchy rebuilt

# Implement
opt_design
place_design
route_design

# Timing check
set wns [get_property SLACK [get_timing_paths -max_paths 1 -nworst 1]]
if {$wns < 0} {
    puts "ERROR: Timing not met, WNS = $wns ns"
    exit 1
}

write_bitstream -force ./output/kv260_top.bit
puts "Build complete."
```

### Relevance to Your Project

Your `create_bd.tcl` likely uses project mode (`create_project`). Adding the above non-project snippet as an optional CI path lets you validate the design headlessly (e.g., in GitHub Actions) without committing a full `.xpr` project.

## 4. Vitis Bare-Metal / Standalone

### Key Findings

- **BSP is derived from the exported XSA** (Hardware Specification Archive) from Vivado — re-export XSA and update the Vitis platform whenever the block design changes (especially if BRAM addresses or AXI peripheral counts change).
- **`xil_printf` vs `printf`**: `xil_printf` is a lightweight formatted output that skips floating-point support and is safe for bare-metal UART; use it for PASS/FAIL status messages. `printf` requires the full C library and larger stack.
- **UART on KV260**: the lowest-numbered Serial Port shown in your host terminal for KV260 is the correct one for `xil_printf` output (UART1, connected to the USB-UART bridge on the carrier card).
- **Linker script (.ld)**: the default bare-metal linker script places `.text` and `.data` in DDR (starting at `0x0`). For tight demos, verify `_stack_end` doesn't overlap your AXI peripheral region starting at `0xA0000000`.
- **KV260 bare-metal via JTAG**: in Vitis, use **Xilinx → Program Device** then **Run As → Launch on Hardware** — this bypasses the QSPI boot flow and loads directly via JTAG, ideal for iterative testing.

### Code Example

```c
#include "xil_printf.h"
#include "xil_io.h"

#define BRAM0_BASE 0xA0000000UL
#define BRAM2_BASE 0xA0010000UL
#define TEST_PATTERN 0xDEADBEEFUL

static int test_bram(u32 base, const char *name) {
    Xil_Out32(base, TEST_PATTERN);
    u32 read_val = Xil_In32(base);
    if (read_val == TEST_PATTERN) {
        xil_printf("%s: PASS (0x%08X)\r\n", name, read_val);
        return 0;
    } else {
        xil_printf("%s: FAIL (got 0x%08X, expected 0x%08X)\r\n",
                   name, read_val, TEST_PATTERN);
        return -1;
    }
}

int main(void) {
    xil_printf("KV260 AXI-BRAM Demo\r\n");
    int status = 0;
    status |= test_bram(BRAM0_BASE, "BRAM0");
    status |= test_bram(BRAM2_BASE, "BRAM2");
    xil_printf("Overall: %s\r\n", status == 0 ? "PASS" : "FAIL");
    return status;
}
```

### Relevance to Your Project

This is essentially the pattern your `main.c` implements. Key addition: the `status |=` accumulation ensures both BRAMs are always tested even if the first fails, giving you actionable output rather than early exit.

## 5. XDC Timing Constraints

### Key Findings

- **`set_input_delay` / `set_output_delay` are relative to a reference clock** — always specify `-clock` explicitly; omitting it causes Vivado to pick an arbitrary clock and produces misleading timing reports.
- **Positive input delay** = data arrives after the clock edge (source synchronous, launch on same edge). **Negative input delay** = data arrives before the clock edge — less common, verify with oscilloscope.
- **For internal AXI paths (PS↔PL)**, Vivado auto-generates PS clock constraints from the Zynq MPSoC IP; you do NOT need to manually constrain the AXI clock — doing so can create conflicting constraints and false paths.
- **`create_clock` on PL clocks** is required for any user-created clocks in `kv260_top.vhd` that aren't sourced from the PS. Example: if you add a PLL, constrain its output clock.
- **Clock groups**: use `set_clock_groups -asynchronous` between the PS-sourced clock and any independent oscillator on the carrier card to suppress spurious CDC (clock-domain crossing) timing violations.

### Code Example

```tcl
# kv260_top.xdc — example constraints for KV260 AXI-BRAM demo

# PS provides the AXI clock at 100 MHz via clk_wiz or direct FCLK
# Vivado auto-constrains FCLK_CLK0; only add this if using a custom PLL output
# create_clock -period 10.000 -name clk_pl [get_ports clk_pl_i]

# Example: external async reset input from carrier card GPIO
set_input_delay -clock [get_clocks -of_objects [get_pins zynq_ultra_ps_e_0/FCLK_CLK0]] \
                -max 2.0 [get_ports ext_rst_n]
set_input_delay -clock [get_clocks -of_objects [get_pins zynq_ultra_ps_e_0/FCLK_CLK0]] \
                -min 0.5 [get_ports ext_rst_n]

# If a secondary async clock exists on the board, declare it async to AXI clock
# set_clock_groups -asynchronous \
#   -group [get_clocks clk_axi] \
#   -group [get_clocks clk_external]
```

### Relevance to Your Project

For a pure PS↔PL AXI-BRAM design with no external I/O (other than UART), timing constraints are minimal — Vivado auto-handles the AXI clock. The main constraint to add is `set_false_path` on the reset synchroniser if you implement one in VHDL, and input delays on any board-level signals routed through `kv260_top.vhd`.

## 6. Kria KV260 / K26 SoM

### Key Findings

- **Boot modes**: K26 ships in **QSPI32** boot mode. For iterative bare-metal FPGA development, switch to **JTAG** mode by moving the SW1 boot-mode switch on the KV260 carrier card — this skips FSBL and lets Vitis program the device directly.
- **MIO vs EMIO**: Most fixed peripherals (Ethernet, SD, I2C, UART) use MIO pins baked into the SOM. GPIO on the RPi/PMOD headers of the KV260 are connected to PL EMIO — these require custom VHDL logic and XDC pin constraints.
- **AXI clock to PL**: the PS exposes up to 4 free-running clocks (`FCLK_CLK0`–`FCLK_CLK3`) to the PL, configurable from 0.1 MHz to ~533 MHz. 100 MHz (`FCLK_CLK0`) is the standard AXI clock for BRAM controllers.
- **Power domains**: the K26 SOM manages its own power sequencing. Do not apply external power to PL pins before the SOM has completed its power-on sequence — relevant if you build custom carrier cards.
- **Vivado board files for K26**: install via `xhub:board_part install kv260` or from the Xilinx board store. These preload the MIO configuration so you don't have to configure PS pins manually in the Zynq MPSoC IP GUI.

### Code Example

```tcl
# In create_bd.tcl: configure Zynq MPSoC for KV260 minimal bare-metal
set_property -dict [list \
  CONFIG.PSU__USE__M_AXI_GP0 {1} \
  CONFIG.PSU__MAXIGP0__DATA_WIDTH {32} \
  CONFIG.PSU__UART1__PERIPHERAL__ENABLE {1} \
  CONFIG.PSU__UART1__PERIPHERAL__IO {MIO 36 .. 37} \
  CONFIG.PSU__FPGA_PL0_ENABLE {1} \
  CONFIG.PSU__CRL_APB__PL0_REF_CTRL__FREQMHZ {100} \
] [get_bd_cells zynq_ultra_ps_e_0]

# After adding BRAM controllers, assign addresses
assign_bd_address
validate_bd_design
```

### Relevance to Your Project

Your `create_bd.tcl` should contain something similar to the above. Verify that `PSU__USE__M_AXI_GP0` is enabled (this is the AXI master port the PS uses to reach your BRAMs) and that `FCLK_CLK0` is set to 100 MHz to match the AXI BRAM Controller's input clock requirement.

## 7. AMD/Xilinx Tool Updates — Vivado/Vitis 2025.x

### Key Findings

- **IP config format changed from XML to JSON** (2025.x): improves git diff readability and reduces load time. If you track `.xci` files in git, expect different diffs after upgrading tools.
- **Block Memory Generator and FIFO Generator are feature-frozen**: AMD recommends `XPM_MEMORY_SPRAM`, `XPM_MEMORY_DPRAM`, and `XPM_FIFO_*` macros for all new designs. For existing projects using BRAM Controller + BMG, no migration is required but no new features will be added.
- **AXI SmartConnect ultra-low-area mode** (2025.2): set `STRATEGY = area` via a property — reduces LUT usage for simple point-to-point AXI connections (like PS→BRAM Controller).
- **SystemVerilog Interface support** (2025.2): automatic wrapper generation for SV modules with interface ports makes mixed VHDL/SV designs easier to manage in block design.
- **Versal-focused QoR enhancements** dominate 2025.2 release notes (BUFG replication, retiming control) — less directly relevant to K26 Zynq UltraScale+ but the Vivado tool improvements (faster compile, JSON config) apply to all device families.

### Code Example

```tcl
# Vivado 2025.x: use XPM_MEMORY_SPRAM instead of Block Memory Generator IP
# Instantiate in VHDL as a component or directly as a primitive

# In TCL (non-project mode): read XPM library
read_ip [get_ips xpm_memory_spram_0]  ;# if using IP catalog
# Or directly in VHDL source, no IP catalog entry needed:

# xpm_memory_spram generic map example (VHDL):
# MEMORY_SIZE       => 65536,  -- 64K bits = 8KB
# MEMORY_PRIMITIVE  => "block",
# READ_DATA_WIDTH_A => 32,
# WRITE_DATA_WIDTH_A => 32,
# ADDR_WIDTH_A      => 11,     -- 2048 x 32-bit words
# READ_LATENCY_A    => 1

# Migrate from BRAM Controller + BMG to XPM for standalone BRAM access:
# Replace axi_bram_ctrl + blk_mem_gen with axi_bram_ctrl + XPM instantiation
# The AXI BRAM Controller can drive an XPM BRAM port directly.
```

### Relevance to Your Project

Your current design uses the standard AXI BRAM Controller + Block Memory Generator flow — this continues to work in 2025.x with no changes required. When you next revise the block design, consider using XPM_MEMORY to reduce IP management overhead (no `.xci` file, no IP re-generation step).
