# FPGA Research Digest - 2026-10-01

## Executive Summary

- **AXI-Lite write-response deadlock**: If BVALID is asserted while BREADY is low and the slave keeps AWREADY/WREADY high, a lost write response can permanently hang the bus — directly relevant to your dual-BRAM write loop in main.c.
- **AXI BRAM Controller PG078**: In AXI4-Lite mode the controller is single-ported; data width is 32-bit by default but configurable up to 1024-bit — ensure your BRAM0/BRAM2 data-width settings match the AXI bus width in your block design.
- **Vivado 2025.1 new Pblock Planner**: The 2025.x release family includes a redesigned placement tool; the `write_bd_tcl -ignore_minor_versions` flag is now preferred to keep TCL scripts forward-compatible across minor IP versions.
- **Boot mode override on K26 SoM**: The KV260 defaults to QSPI boot; for JTAG bare-metal loading you must write `0xFF5E0200` (MPSoC BOOT_MODE_USER register) and issue a PS reset — important for iterative debug cycles.
- **XPM_FIFO_AXIS in 2025.2**: AMD's built-in parameterized AXI-Stream FIFO macro (`XPM_FIFO_AXIS`) is now documented in UG974 for UltraScale+; useful if you extend the demo to stream data over AXI-Stream to a PL accelerator.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- **Handshake rule**: A transfer occurs only when both VALID and READY are asserted in the same clock cycle; neither side may wait for the other to assert first (deadlock risk).
- **Write-response deadlock**: If the slave asserts BVALID but the master holds BREADY low, the slave must NOT accept new write addresses. If AWREADY/WREADY remain high during a stalled B-channel, the response is lost and the bus hangs. This is the most common AXI-Lite bug in custom peripherals.
- **Registered ready signals**: Combinatorial AWREADY/WREADY worsen timing closure. Registering them incurs one extra cycle of latency but dramatically improves Fmax — critical for designs targeting >100 MHz.
- **Write address / write data ordering**: The write data channel (W) may precede the write address channel (AW) by at most one clock; AW may precede W by at most two clocks. Violations cause silent data corruption.
- **AXI-Stream TLAST**: Required by Xilinx DMAs and packet-mode FIFOs. Assert TLAST on the last beat of each packet; if your transfer is always a single word, tie TLAST high.
- **XPM_FIFO_AXIS**: Xilinx's native parameterized AXI-Stream FIFO (UG974 / UG1485, 2025.2) instantiates directly in VHDL/Verilog without needing an IP core; supports TDATA, TKEEP, TLAST, TUSER, TID.

### Code Example

```vhdl
-- AXI-Lite slave: registered AWREADY prevents combinatorial paths
-- and avoids the BVALID/BREADY deadlock pattern
process(clk)
begin
  if rising_edge(clk) then
    if rst_n = '0' then
      s_axi_awready <= '0';
    elsif s_axi_awvalid = '1' and s_axi_awready = '0'
          and not (s_axi_bvalid = '1' and s_axi_bready = '0') then
      -- Only accept new address when B-channel is not stalled
      s_axi_awready <= '1';
    else
      s_axi_awready <= '0';
    end if;
  end if;
end process;
```

### Relevance to Your Project

Your `main.c` writes 32-bit patterns to BRAM0 (`0xA0000000`) and BRAM2 (`0xA0010000`) via AXI-Lite. If the AXI BRAM Controller's write-response channel is stalled (e.g., the Cortex-A53 does not drain BREADY fast enough), subsequent writes will silently queue or hang. Ensure your bare-metal write loop reads back BRESP after every write or uses non-blocking polling; the Xilinx AXI BRAM controller's BRESP should always return `OKAY (2'b00)` for in-range addresses.

## Vivado Block Design / IP Integrator

### Key Findings

- **Connection Automation**: After placing the Zynq PS and AXI BRAM Controller IPs, use *Run Connection Automation* to wire AXI-Lite interfaces, clocks, and resets automatically. This generates the correct AXI Interconnect or SmartConnect IP.
- **Address Editor**: Each AXI slave must be assigned a unique address range in the Address Editor. BRAM0 at `0xA0000000` and BRAM2 at `0xA0010000` each require 64 KB (minimum) mapped in the M_AXI_GP0 master space.
- **Regeneration after IP update**: If you upgrade Vivado and the IP version changes, run *Report IP Status* then *Upgrade All* before re-generating output products. Stale output products cause silent simulation/synthesis mismatches.
- **SmartConnect vs AXI Interconnect**: SmartConnect (Vivado 2018.3+) is preferred for new designs — it auto-configures register slices and improves timing. For the KV260 AXI-BRAM demo a single SmartConnect with one master (HP0/GP0) and two slaves (BRAM0/BRAM2) is the minimal topology.
- **validate_bd_design**: Always call this TCL command before generating bitstream; it catches unconnected clocks, missing constraints, and protocol mismatches.

### Code Example

```tcl
# Minimal block design snippet for KV260 dual-BRAM
# Create SmartConnect for 1 master → 2 BRAM slaves
create_bd_cell -type ip -vlnv xilinx.com:ip:smartconnect:1.0 smartconnect_0
set_property CONFIG.NUM_SI {1} [get_bd_cells smartconnect_0]
set_property CONFIG.NUM_MI {2} [get_bd_cells smartconnect_0]

# Connect Zynq HP0 to SmartConnect master
connect_bd_intf_net [get_bd_intf_pins zynq_ultra_ps_e_0/M_AXI_HPM0_FPD] \
    [get_bd_intf_pins smartconnect_0/S00_AXI]

# Connect slaves
connect_bd_intf_net [get_bd_intf_pins smartconnect_0/M00_AXI] \
    [get_bd_intf_pins axi_bram_ctrl_0/S_AXI]
connect_bd_intf_net [get_bd_intf_pins smartconnect_0/M01_AXI] \
    [get_bd_intf_pins axi_bram_ctrl_1/S_AXI]

# Assign addresses
assign_bd_address [get_bd_addr_segs {axi_bram_ctrl_0/S_AXI/Mem0}]
assign_bd_address [get_bd_addr_segs {axi_bram_ctrl_1/S_AXI/Mem0}]
set_property offset 0xA0000000 [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property offset 0xA0010000 [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_1_Mem0}]

validate_bd_design
```

### Relevance to Your Project

Your `create_bd.tcl` script builds the block design programmatically. The `assign_bd_address` / `set_property offset` pattern above directly maps BRAM0 to `0xA0000000` and BRAM2 to `0xA0010000`, which are the hardcoded base addresses in your `main.c`. Verifying these match after every re-run of the TCL script prevents silent address mismatches that appear as PASS on BRAM0 but garbage reads on BRAM2.

## Vivado TCL Scripting

### Key Findings

- **Batch mode invocation**: `vivado -mode batch -source build.tcl` runs the script headlessly; add `-nojournal -nolog` to suppress GUI artifacts in CI pipelines.
- **`write_bd_tcl` flags**: `-no_ip_version` removes hardcoded IP version from `create_bd_cell` calls (useful for sharing scripts); `-ignore_minor_versions` resolves to the latest minor version automatically — preferred for 2025.x to avoid "IP version not found" errors after minor Vivado updates.
- **Non-project mode**: Drive synthesis, implementation, and bitstream generation via `synth_design`, `opt_design`, `place_design`, `route_design`, `write_bitstream` TCL commands directly. Save checkpoints with `write_checkpoint` after each step for incremental flows.
- **`create_bd_design` tip**: Always call `current_bd_design [get_bd_designs <name>]` before modifying an existing design to ensure you're operating on the correct BD in multi-BD projects.
- **Version-safe scripting**: Use `[version -short]` to gate tool-version-specific workarounds; check IP VLNV with `get_ipdefs -all` before instantiation to confirm availability.

### Code Example

```tcl
#!/usr/bin/env tclsh
# Non-project mode bitstream generation for kv260-axi-bram-demo
# Usage: vivado -mode batch -source build_nonproject.tcl

set part "xck26-sfvc784-2LV-c"
set bd_tcl  "tcl/create_bd.tcl"
set xdc     "constraints/kv260_top.xdc"
set output  "output"

file mkdir $output

# Read sources
read_vhdl  [glob src/vhdl/*.vhd]
read_xdc   $xdc

# Recreate block design from TCL
source $bd_tcl
make_wrapper -files [get_files *.bd] -top
read_vhdl [glob $output/*.v]

# Implement
synth_design  -top kv260_top -part $part -flatten_hierarchy rebuilt
write_checkpoint -force $output/post_synth.dcp

opt_design
place_design
route_design
write_checkpoint -force $output/post_route.dcp
write_bitstream  -force $output/kv260_top.bit

puts "Build complete: $output/kv260_top.bit"
```

### Relevance to Your Project

Your `create_bd.tcl` is already the right approach for reproducible block design creation. Wrapping it in a non-project-mode outer script (as above) means a `git clone` + single `vivado -mode batch` command fully rebuilds the bitstream — eliminating the Vivado project `.xpr`/`.cache` directories from version control and making CI integration straightforward.

## Vitis Bare-Metal / Standalone

### Key Findings

- **BSP standalone library**: The Vitis standalone BSP provides `xil_printf` (lightweight, no floating-point) and `printf` (full libc — significantly larger code footprint). For UART-only status messages as in your PASS/FAIL output, prefer `xil_printf`.
- **Interrupt controller (xscugic)**: AMD bare-metal drivers do NOT auto-initialize the GIC; you must call `XScuGic_LookupConfig`, `XScuGic_CfgInitialize`, and `Xil_ExceptionRegisterHandler` explicitly in your application. Without this, interrupts silently never fire.
- **BSP regeneration**: After changing the block design (adding/removing PS AXI slaves), you must delete and recreate the BSP in Vitis. Stale BSPs retain old `xparameters.h` base addresses and can cause `Xil_Out32` writes to go to wrong addresses.
- **Linker script memory regions**: The default DDR region starts at `0x00000000` for the Cortex-A53 bare-metal app. Ensure your stack/heap sizes are adequate; the default 0x2000 stack is often too small for complex printf-heavy apps.
- **Cache coherency**: On Zynq UltraScale+ the L1/L2 data cache is enabled by default. AXI BRAM writes from the PS may be cached and not immediately visible if you don't flush (`Xil_DCacheFlush()`) before reading back — critical for your PASS/FAIL verification loop.

### Code Example

```c
/* Cache-safe AXI BRAM write/readback pattern for KV260 bare-metal */
#include "xil_io.h"
#include "xil_cache.h"
#include "xil_printf.h"

#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL
#define TEST_WORDS  16

int bram_test(u32 base_addr, const char *name) {
    u32 pattern, read_val;
    int pass = 1;

    for (int i = 0; i < TEST_WORDS; i++) {
        pattern = 0xDEAD0000 | (u32)i;
        Xil_Out32(base_addr + (i * 4), pattern);
    }

    /* Flush data cache before readback to ensure AXI transactions complete */
    Xil_DCacheFlush();

    for (int i = 0; i < TEST_WORDS; i++) {
        read_val = Xil_In32(base_addr + (i * 4));
        if (read_val != (0xDEAD0000 | (u32)i)) {
            xil_printf("%s[%d]: FAIL got 0x%08X\r\n", name, i, read_val);
            pass = 0;
        }
    }
    return pass;
}

int main(void) {
    xil_printf("KV260 AXI BRAM Demo\r\n");
    xil_printf("BRAM0: %s\r\n", bram_test(BRAM0_BASE, "BRAM0") ? "PASS" : "FAIL");
    xil_printf("BRAM2: %s\r\n", bram_test(BRAM2_BASE, "BRAM2") ? "PASS" : "FAIL");
    return 0;
}
```

### Relevance to Your Project

The `Xil_DCacheFlush()` call between writes and reads is the single most common source of "PASS on BRAM0, FAIL on BRAM2" phantom failures on Zynq UltraScale+ bare-metal. Your existing main.c may already include this; if not, this is the first fix to try if you see intermittent read-back mismatches.

## XDC Timing Constraints

### Key Findings

- **Primary clock constraint**: The KV260's PL clock comes from the Zynq PS clock manager (`pl_clk0`). Always derive timing from this clock in XDC; do NOT create a `create_clock` on a PL pin — the PS clock is already constrained internally.
- **`set_input_delay -max` / `-min`**: For system-synchronous I/O, `-max` sets the setup requirement (clock-to-valid data time) and `-min` sets the hold requirement. Both are measured relative to the launching clock edge.
- **Clock groups for PS/PL boundary**: Use `set_clock_groups -asynchronous` between the PS internal clocks and any independent PL oscillator clocks to prevent Vivado from creating false paths across truly async domains.
- **Timing Constraints Wizard**: In Vivado GUI, run *Tools → Timing Constraints Wizard* after synthesis to get auto-generated constraint templates for all detected I/O ports — much less error-prone than hand-writing XDC.
- **I/O standard constraints**: Every I/O buffer in the XDC needs a `set_property IOSTANDARD` or implementation will fail with DRC errors. For the KV260 PMOD/GPIO pins use `LVCMOS33` or `LVCMOS18` depending on the bank voltage.

### Code Example

```tcl
# KV260 XDC timing constraints skeleton
# The PL clock is driven by the Zynq PS clock manager — DO NOT create_clock on a pin
# The PS-sourced pl_clk0 is auto-constrained; reference it by name:

# Constrain UART TX/RX (PS MIO — already handled by PS7; include for documentation)
# PL-side GPIO example (PMOD connector, HDA bank, 1.8V IO)
set_property IOSTANDARD LVCMOS18 [get_ports {led[*]}]
set_property PACKAGE_PIN A12    [get_ports {led[0]}]  ;# HDA20 on KV260

# False path for async reset synchronizer
set_false_path -from [get_ports {rst_n}]

# Clock groups: isolate PS clock from any PL oscillator clock
# (Only needed if you add a separate oscillator to the design)
# set_clock_groups -asynchronous \
#     -group [get_clocks clk_pl_0] \
#     -group [get_clocks {clk_osc_125}]

# Input/output delay for external synchronous signals (example)
# set_input_delay  -clock clk_pl_0 -max 3.0 [get_ports {gpio_in[*]}]
# set_input_delay  -clock clk_pl_0 -min 0.5 [get_ports {gpio_in[*]}]
# set_output_delay -clock clk_pl_0 -max 2.0 [get_ports {gpio_out[*]}]
# set_output_delay -clock clk_pl_0 -min 0.0 [get_ports {gpio_out[*]}]
```

### Relevance to Your Project

Your `kv260_top.vhd` is primarily a PS-PL connectivity wrapper — the timing-critical paths are internal to the Zynq PS and the AXI BRAM Controller IP (both pre-timed). The most important XDC items for your current design are: IOSTANDARD for any GPIO pins, a `set_false_path` on asynchronous reset inputs, and ensuring `pl_clk0` is the only clock driving your logic. Adding explicit `set_clock_groups` now will prevent issues if you later add a PL-side PLL.

## Kria KV260 / K26 SoM

### Key Findings

- **Boot mode**: KV260 defaults to QSPI boot. For bare-metal JTAG debugging write `0x0` to MPSoC BOOT_MODE_USER register at `0xFF5E0200` and trigger a system reset using `PS_SRSTB`. This lets Vitis load your ELF directly over JTAG without touching the QSPI flash.
- **SOM240_1 connector**: Provides access to MIO banks MIO501/MIO502, HPIO bank 66 (HPA), HDIO bank 45 (HDA), and PS-GTR transceivers. The on-board fan PWM is on HDA20 (physical pin A12) — it must be driven via EMIO or a PL timer to prevent thermal shutdown.
- **PS AXI masters**: The Zynq UltraScale+ on the K26 exposes `M_AXI_HPM0_FPD` (GP0, 128-bit) and `M_AXI_HPM1_FPD` (GP1) as PL-accessible masters for control-path traffic. Your BRAM accesses use GP0 (`0xA000_0000`–`0xAFFF_FFFF` is in the PL address space accessible from this port).
- **HP ports for DMA**: The four HP (High Performance) ports provide 128-bit paths from PL masters into PS DRAM — relevant if you add a PL DMA engine later.
- **JTAG vs QSPI workflow**: For iterative development, use JTAG mode (tcl: `fpga -file kv260_top.bit; dow application.elf; con`) to skip the QSPI flash write/verify cycle. Switch to QSPI only for deployment.
- **Platform creation (XD101)**: AMD's 2025.1 tutorial "Custom Kria SOM Platform Creation Example" (docs.amd.com XD101) walks through creating a Vitis Unified platform from scratch for custom carrier cards.

### Code Example

```tcl
# Vitis/XSCT script: load bitstream + ELF over JTAG on KV260
# Run with: xsct jtag_load.tcl

connect
targets -set -filter {name =~ "APU*"}

# Override boot mode to JTAG (write BOOT_MODE_USER register)
mwr 0xFF5E0200 0x00000000
rst -system

# Program PL with bitstream
fpga -file output/kv260_top.bit

# Select Cortex-A53 core 0
targets -set -filter {name =~ "Cortex-A53 #0"}
rst -processor

# Load and run the bare-metal ELF
dow build/kv260_axi_bram.elf
con

puts "KV260 loaded. Monitor UART at 115200 baud."
```

### Relevance to Your Project

The JTAG-mode XSCT script above directly supports your development cycle: program the bitstream, load the bare-metal ELF, and observe PASS/FAIL output on UART — all without touching QSPI flash. The `mwr 0xFF5E0200 0x00000000` step is the key unlock for the KV260's default QSPI boot setting.

## AMD/Xilinx Tool Updates (2025.x)

### Key Findings

- **Vivado 2025.1**: Adds production support for Spartan UltraScale+ (XCSU10P/25P/35P), Versal AI Edge Gen 2 / Prime Gen 2 early access. New **Pblock Planner** GUI for interactive floorplanning. `boot-first PS` feature allows PS to power up and load firmware before the PL bitstream is loaded — relevant for Kria deployment flows.
- **Vivado 2025.2**: Adds XPM_FIFO_AXIS documentation in UG974 (UltraScale+ libraries), calibrated skew compensation for SSIT devices, and NoC time-slicing QoS controls.
- **Vitis 2025.1 known issues**: File/Directory Selection Dialog does not open on AlmaLinux 9.5 / RHEL 9.5 (workaround: use command-line XSCT). LD_PRELOAD conflicts in the Unified IDE on some Linux distros. `write_bd_tcl -ignore_minor_versions` is documented and recommended in UG835 2025.2.
- **Vitis 2025.1 AI Engine enhancements**: Enhanced GEMV, FFT, bitonic sorting for Versal AI engines — not directly relevant to KV260 but indicates the 2025.x family is heavily Versal-focused; Zynq UltraScale+ support continues unchanged.
- **Vitis AI 5.1**: Uses Vitis/Vivado 2025.1.1 — if you later add an ML inference overlay, align to this version.

### Relevance to Your Project

The `-ignore_minor_versions` flag for `write_bd_tcl` ensures your `create_bd.tcl` remains usable when AMD releases Vivado 2025.2 or later 2025.x patches without requiring manual VLNV version bumps. Add it to your export step now to avoid a common "IP version not found" error that breaks the TCL flow on collaborators' machines running slightly different minor Vivado versions.
