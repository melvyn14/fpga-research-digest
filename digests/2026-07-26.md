# FPGA Research Digest - 2026-07-26

## Executive Summary
- **AXI-Lite VALID rule**: once AWVALID/WVALID is asserted it must not be de-asserted until the corresponding READY is received — violating this is the #1 source of silent bus hangs in bare-metal BRAM writes; review every master state machine in `main.c`.
- **AXI BRAM Controller dual-port pitfall**: the default IP configuration uses a single BRAM port; for two independent masters (or to double bandwidth) you must explicitly enable the second port in the IP GUI, otherwise AXI4-Lite stalls waiting for port B.
- **Non-project TCL flow**: `write_hw_platform -force -include_bit <name>.xsa` is the correct 2025.x command to produce a Vitis-consumable XSA with embedded bitstream; `write_bitstream` alone does not produce the XSA.
- **Kria bare-metal boot**: The KV260 ships in QSPI32 boot mode. For JTAG-only bare-metal development you must switch the boot mode switch (SW1) to JTAG before powering on, or the QSPI firmware takes over and the PL is never loaded from Vitis.
- **Vivado 2025.2 licensing change**: Starting with the 2026.1 release, AMD is moving Vivado to a new tiered licensing model; plan your toolchain upgrade path now before the 2025.1 license model is deprecated.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings
- All five AXI channels (AW, W, B, AR, R) use the same VALID/READY handshake sampled on the **rising clock edge**; all signal changes must occur after the rising edge, never before.
- **Critical VALID rule**: once AWVALID or WVALID is asserted by a master, it **must not** be de-asserted until the corresponding READY response is received from the slave. Dropping VALID prematurely causes silent transaction corruption or bus hang.
- **READY can depend on VALID, but not vice-versa**: TVALID (and AWVALID/WVALID) must be driven purely by the master's own state — never gated on whether the slave's READY is high. This prevents circular combinatorial loops that deadlock on the first transaction.
- **AXI-Lite write requires both AW and W channels**: a slave asserting AWREADY does not imply it has consumed the data; both the write address and write data handshakes must complete before the slave drives BVALID to confirm the transaction.
- **AXI-Stream TLAST hazard**: if TVALID is asserted with TLAST on the second-to-last beat while TREADY is low, the channel is stalled with a premature end-of-packet signal. Many Xilinx IPs will not forward the packet without seeing TLAST on the final beat, causing silent data loss. Even some Xilinx template AXI-Stream masters contain this bug.
- **BRAM write-enable timing**: a known simulation bug in AXI BRAM Controller asserts write-enable one clock early, writing an extra word to an off-by-one address. Verify with ILA in hardware if write data appears at unexpected locations.

### Code Example
```c
/* Safe AXI-Lite write: poll BVALID before issuing next transaction */
#define AXI_BRAM0_BASE 0xA0000000UL

static inline void axi_write32(uint32_t addr, uint32_t data) {
    volatile uint32_t *p = (volatile uint32_t *)addr;
    *p = data;
    /* Memory barrier ensures store completes before next access */
    __asm__ volatile("dsb sy" ::: "memory");
}

static inline uint32_t axi_read32(uint32_t addr) {
    __asm__ volatile("dsb sy" ::: "memory");
    return *(volatile uint32_t *)addr;
}

/* Pattern write-then-read-back verification */
void verify_bram(uint32_t base, uint32_t num_words) {
    for (uint32_t i = 0; i < num_words; i++)
        axi_write32(base + i * 4, 0xDEAD0000 | i);
    for (uint32_t i = 0; i < num_words; i++) {
        uint32_t got = axi_read32(base + i * 4);
        if (got != (0xDEAD0000 | i))
            xil_printf("FAIL @ 0x%08X: expected 0x%08X got 0x%08X\r\n",
                        base + i*4, 0xDEAD0000|i, got);
    }
}
```

### Relevance to Your Project
The `main.c` in `kv260-axi-bram-demo` writes patterns to BRAM0 at `0xA0000000` and BRAM2 at `0xA0010000`. The `dsb sy` barrier between write and readback is essential on Cortex-A53 because the AXI interconnect may reorder transactions without it. If you see intermittent FAIL results, add barriers and verify the AXI BRAM Controller IP is not set to single-port mode when both masters need simultaneous access.

## Vivado Block Design / IP Integrator

### Key Findings
- **`write_bd_tcl` version lock**: scripts produced by `write_bd_tcl` are only guaranteed reproducible within the same Vivado release version. Do not use a 2024.x-generated script in 2025.1 without verifying every IP VLNV string has been updated.
- **Connection Automation**: `apply_bd_automation` with the correct board preset automatically configures the Zynq UltraScale+ PS, clock wizard, and AXI interconnect wiring — running it manually saves hours of manual pinout work on the KV260.
- **Address Editor**: the AXI Interconnect only routes transactions to the correct slave if each slave's address segment is correctly mapped in the Address Editor. Overlapping ranges cause silent misdirected writes that are very difficult to debug without an ILA.
- **`validate_bd_design`**: always run this before generating output products. It checks for unconnected required ports, clock/reset mismatches, and address segment collisions.
- **Layout preservation**: pass `-include_layout` to `write_bd_tcl` to preserve the graphical block placement, making the exported script much more maintainable.

### Code Example
```tcl
# Minimal non-project block design creation template for KV260 AXI-BRAM
open_project kv260_project/kv260_project.xpr
open_bd_design [get_files *.bd]

# Re-run connection automation to apply board presets
apply_bd_automation -rule xilinx.com:bd_rule:zynq_ultra_ps_e \
    [get_bd_cells zynq_ultra_ps_e_0]

# Validate before generating
validate_bd_design

# Generate output products (OOC synthesis)
generate_target all [get_files *.bd]

# Create HDL wrapper
make_wrapper -files [get_files *.bd] -top
add_files -norecurse [glob ./kv260_project/kv260_project.gen/sources_1/bd/*/hdl/*_wrapper.v]

# Synthesize, implement, write bitstream and XSA in one shot
launch_runs impl_1 -to_step write_bitstream -jobs 8
wait_on_run impl_1
write_hw_platform -fixed -force -include_bit ./output/kv260_top.xsa
```

### Relevance to Your Project
Your `create_bd.tcl` script creates the block design with the Zynq PS, AXI Interconnect, and two AXI BRAM Controller + Block Memory Generator pairs. Using `validate_bd_design` before `generate_target` will catch address map collisions between the two BRAMs (BRAM0 at `0xA0000000` and BRAM2 at `0xA0010000`) before they become runtime bugs.

## Vivado TCL Scripting

### Key Findings
- **Non-project mode** (`-nolog -nojournal` or running `vivado -mode batch`) is cleaner for CI/CD pipelines; it avoids `.xpr` project files but requires you to manually call `read_vhdl`, `read_xdc`, `synth_design`, `opt_design`, `place_design`, `route_design`, and `write_bitstream` in sequence.
- **`write_hw_platform`** (not the older `write_sysdef`) is the correct command in 2025.x to generate the XSA for Vitis. Use `-include_bit` to embed the bitstream so Vitis can program the device automatically on run.
- **`ipx::*` commands** allow full IP packager manipulation from TCL — useful for automating custom IP packaging in a pipeline alongside `create_bd.tcl`.
- **Only user-changed parameters are written** by `write_bd_tcl`; default parameters and tool-propagated parameters after propagation are silently omitted. This means a re-sourced script may behave differently from the original if IP defaults change between tool versions.
- **`get_bd_cells`, `get_bd_nets`, `get_bd_intf_pins`** are the primary object-query commands for navigating block designs in TCL; always prefer these over hard-coded string names.

### Code Example
```tcl
# Non-project mode full flow for KV260 AXI-BRAM demo
set outputDir ./output
file mkdir $outputDir

# Read design sources
read_vhdl -library work [glob ./vhdl/*.vhd]
read_xdc ./xdc/kv260_top.xdc

# Source the block design creator
source ./tcl/create_bd.tcl

# Synthesize (OOC on block design handled automatically)
synth_design -top kv260_top -part xck26-sfvc784-2LV-c

# Implementation
opt_design
place_design
route_design

# Generate outputs
write_checkpoint -force $outputDir/route.dcp
report_timing_summary -file $outputDir/timing.rpt
write_bitstream -force $outputDir/kv260_top.bit

# Export for Vitis
write_hw_platform -fixed -force -include_bit $outputDir/kv260_top.xsa
```

### Relevance to Your Project
Your `create_bd.tcl` is designed to recreate the block design from scratch. Wrapping it in the non-project mode flow above lets you run the entire Vivado flow (`vivado -mode batch -source run_all.tcl`) from a CI script or Makefile — building from clean with a single command and producing the XSA ready for Vitis.

## Vitis Bare-Metal / Standalone

### Key Findings
- **BSP UART**: on the KV260 / K26 SoM, the PS UART1 (`UART1` in the PS IP configuration) is routed to the USB-UART on the carrier card. Ensure the `stdin`/`stdout` BSP configuration in `system.mss` points to `psu_uart_1` — not `psu_uart_0` — or `xil_printf` output will be silent.
- **Stack and heap defaults are tiny**: the Vitis-generated linker script defaults `_STACK_SIZE` to 400 bytes and `_HEAP_SIZE` to 0. Any use of `malloc`, `printf` (not `xil_printf`), or recursive functions will silently corrupt memory. Set via linker flags: `-Wl,-defsym,_STACK_SIZE=0x2000 -Wl,-defsym,_HEAP_SIZE=0x1000`.
- **`xil_printf` vs `printf`**: `xil_printf` is the lightweight version with no floating-point support and no heap dependency. For simple PASS/FAIL messages use `xil_printf`; only bring in `printf` if you need `%f` and have sized the heap accordingly.
- **AArch64 bare metal size**: to minimize EL3 bare metal application size, avoid `newlib` and use the `xil_` prefixed functions. The AMD wiki documents a specific set of compiler flags for minimal AArch64 builds.
- **PL must be programmed before PS accesses PL addresses**: in bare-metal, the PL is NOT automatically programmed from the bitstream embedded in the XSA unless you use the FSBL or explicitly call `XFpga_PL_BitStream_Load()`. Without PL programming, writes to `0xA0000000` will hang the AXI bus and stall the CPU.

### Code Example
```c
#include "xil_printf.h"
#include "xparameters.h"

/* BRAM base addresses from xparameters.h (generated by Vitis BSP) */
#define BRAM0_BASE  XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR  /* 0xA0000000 */
#define BRAM2_BASE  XPAR_AXI_BRAM_CTRL_1_S_AXI_BASEADDR  /* 0xA0010000 */
#define BRAM_DEPTH  1024  /* words */

int main(void) {
    xil_printf("\r\n--- KV260 AXI-BRAM Bare Metal Test ---\r\n");

    int pass = 1;
    for (int i = 0; i < BRAM_DEPTH; i++) {
        Xil_Out32(BRAM0_BASE + i*4, 0xA0000000 | i);
        Xil_Out32(BRAM2_BASE + i*4, 0xB0000000 | i);
    }
    __asm__ volatile("dsb sy" ::: "memory");

    for (int i = 0; i < BRAM_DEPTH; i++) {
        uint32_t v0 = Xil_In32(BRAM0_BASE + i*4);
        uint32_t v2 = Xil_In32(BRAM2_BASE + i*4);
        if (v0 != (0xA0000000 | i) || v2 != (0xB0000000 | i)) {
            xil_printf("FAIL i=%d: BRAM0=0x%08X BRAM2=0x%08X\r\n", i, v0, v2);
            pass = 0;
        }
    }
    xil_printf(pass ? "PASS\r\n" : "FAIL\r\n");
    return 0;
}
```

### Relevance to Your Project
Your `main.c` uses this exact pattern. The most common failure mode is silent UART output because `psu_uart_1` is not set as stdout, or a hang because the PL bitstream was never loaded. Double-check `xparameters.h` base addresses match `0xA0000000` and `0xA0010000` — if Vitis regenerated the BSP after an IP address change they may have shifted.

## XDC Timing Constraints

### Key Findings
- **PS clocks are auto-constrained**: the Zynq UltraScale+ PS IP automatically generates clock constraints for all PS output clocks (pl_clk0 etc.). You do not need to manually `create_clock` for these, but you do need to `create_clock` for any external clock input (e.g., a differential LVDS clock on the KV260 carrier).
- **`set_input_delay` / `set_output_delay`**: specify system-level external path delay relative to a clock edge at the device interface. Values are in nanoseconds and can be negative (when data arrives before the clock edge). For purely internal PS-to-PL AXI paths (no I/O pins involved) these constraints are not needed.
- **`set_clock_groups -asynchronous`**: use this when PS and PL run from different PLLs with no known phase relationship. **Warning**: this suppresses all cross-domain timing checks including those inside Xilinx AXI interconnect FIFOs — you must implement proper CDC synchronization circuits in your design first, or the constraint merely hides a real metastability problem.
- **Separating clock groups**: if you have three clocks (e.g., pl_clk0, clk_wiz_out, and a free-running LVDS), placing all three in one `set_clock_groups -asynchronous` call can create false "non-existent path" errors. Split into two separate calls.
- **Timing Constraint Wizard**: available in Vivado's Tools menu; it auto-detects I/O cells and generates template constraints — useful starting point but always review the generated XDC before accepting.

### Code Example
```tcl
# KV260 XDC: define external differential clock (125 MHz on KV260 J1 connector)
# PS clocks (pl_clk0 etc.) are already auto-constrained by the PS IP
create_clock -period 8.000 -name clk_125mhz [get_ports clk_125mhz_p]

# Clock from clock wizard output (200 MHz for AXI interconnect)
# This is derived from pl_clk0; the tool handles the relationship automatically.
# Only add this if using an EXTERNAL input, not a generated clock.

# Declare PS pl_clk0 and clk_wiz output as asynchronous to external clock
set_clock_groups -asynchronous \
    -group [get_clocks clk_125mhz] \
    -group [get_clocks -of [get_nets -hierarchical -filter {NAME =~ *clk_out*}]]

# For IO registers on Pmod (if used):
set_input_delay  -clock clk_125mhz -max 2.0 [get_ports {pmod_*}]
set_input_delay  -clock clk_125mhz -min 0.5 [get_ports {pmod_*}]
set_output_delay -clock clk_125mhz -max 1.5 [get_ports {pmod_*}]
set_output_delay -clock clk_125mhz -min 0.0 [get_ports {pmod_*}]

# Bitstream settings for KV260 configuration (QSPI/JTAG)
set_property BITSTREAM.CONFIG.OVERTEMPSHUTDOWN ENABLE [current_design]
```

### Relevance to Your Project
Your `kv260_top.vhd` top-level wraps the block design. If it has any VHDL-level clock buffering or clock gating, those clocks need `create_clock` entries. For a pure AXI-BRAM demo with no external I/O, your timing constraints can be minimal — just the board-supplied clock and the PS auto-constraints. Run `report_timing_summary` after route to confirm no critical negative slack (WNS < 0).

## Kria KV260 / K26 SoM

### Key Findings
- **Architecture**: the KV260 carrier board connects to the K26 SoM via a 240-pin SOM240_1 connector. All peripherals (USB-UART, SD card, Ethernet, USB 3.0, DisplayPort) route through this connector to the Zynq UltraScale+ MPSoC on the module.
- **Boot mode**: ships in **QSPI32** mode (SW1 all down). For bare-metal JTAG development, switch SW1 to JTAG mode before power-on. The board's QSPI firmware will otherwise start Linux or a prior boot image before your Vitis debug session can attach.
- **UART routing**: `UART1` (PS MIO48/49) is routed to the USB-UART (Silicon Labs CP2105) on the carrier. `UART0` is routed to the JTAG header. The Vivado board preset assigns `psu_uart_1` as the default stdout.
- **PL power domain**: the PL banks use separate `VCCINT_PL` and `VCCO_PL` supplies. The KV260 provides 0.72 V for VCCINT_PL and 1.8 V / 3.3 V options for VCCO. Confirm your XDC `set_property IOSTANDARD` values match the carrier-provided voltage.
- **EMIO GPIO**: GPIO routed via EMIO passes through the PL fabric to the SOM240 pins and then to the carrier Pmod connectors. A PL bitstream must be loaded before EMIO GPIO lines are driven.
- **KV260 board files**: Vivado 2021.1+ ships board files for KV260 (`kv260`). Running block design automation with these board files auto-configures the PS, DDR, and clocks correctly — always use `apply_bd_automation` with the KV260 board preset rather than configuring the PS by hand.

### Code Example
```tcl
# Block design automation for KV260 — apply board preset to PS
# Run this immediately after adding the Zynq UltraScale+ PS IP
apply_bd_automation \
    -rule xilinx.com:bd_rule:zynq_ultra_ps_e \
    -config {apply_board_preset "1"} \
    [get_bd_cells zynq_ultra_ps_e_0]

# The automation configures:
#  - DDR4 for K26 (lpddr4)
#  - pl_clk0 at 100 MHz
#  - UART1 on MIO48/49 (USB-UART)
#  - USB0, ENET0 per carrier routing

# Verify UART assignment in BSP (system.mss) after XSA import:
#   stdin  = psu_uart_1
#   stdout = psu_uart_1
```

```c

#include "xuartps.h"
/* If UART doesn't appear, verify: */
```

### Relevance to Your Project
The KV260 bare-metal JTAG boot flow is the most critical operational step for your project. Without setting SW1 to JTAG mode, the QSPI firmware boots and the PL remains unprogrammed, causing every AXI access to `0xA0000000`/`0xA0010000` to hang the bus. The PS IP board preset automation also ensures the memory map, DDR, and UART are correct without manual PS configuration.

## AMD/Xilinx Tool Updates (2025.x)

### Key Findings
- **Vivado 2025.1** was released July 8, 2025 (UG973 v2025.1). Official release notes are at `docs.amd.com/r/2025.1-English/ug973-vivado-release-notes-install-license`.
- **Vivado 2025.2** added: SystemVerilog Interface support for simplified AXI connections in IP Integrator, reduced physical optimization compile time, and a new **ultra-low-area mode** for AXI Switch and AXI SmartConnect IP — useful for resource-constrained PL designs.
- **Vitis 2025.1 unified IDE**: continued unification of HLS, Vitis Classic, and the embedded development flows. UG1742 (Vitis Release Notes) details the changes. The `vitis -unified` CLI replaces the older `xsct`-based flows for platform and application creation.
- **Vivado 2026.1 licensing change**: AMD is moving to a new tiered licensing model starting with the 2026.1 release. The current (2025.x) free Webpack edition and paid editions are the last to use the existing model — plan tool version locks before upgrading.
- **`write_hw_platform` replaces `write_sysdef`**: the older `write_sysdef` command was removed in recent releases. Ensure any legacy TCL scripts in your repo use `write_hw_platform` for XSA export.
- **Vitis Export to Vivado** (XD101 tutorial): a new 2025.1 workflow allows Vitis-managed block design changes to be exported back to Vivado for incremental hardware iteration without full rebuild — useful for projects that iterate frequently between software and hardware changes.

### Code Example

### Relevance to Your Project
If your `create_bd.tcl` was generated with an older Vivado version, check it for `write_sysdef` calls and replace them with `write_hw_platform`. Also verify the `create_bd.tcl` VLNV strings (e.g., `xilinx.com:ip:axi_bram_ctrl:4.1`) match the IP versions shipped with your installed Vivado 2025.1 to avoid "IP version not found" errors on re-source.
