# FPGA Research Digest - 2026-08-21

## Executive Summary

- **AXI-Lite write channel synchronization**: Both AWVALID and WVALID must be received before the slave may assert BVALID; naive implementations that gate AWREADY on WVALID can deadlock — Xilinx quietly fixed their own demo core after Vivado 2016.3, so always reference the latest template.
- **BRAM address assignment for dual-BRAM layout**: In the Vivado Address Editor, manually set BRAM0 offset to `0xA000_0000` and BRAM2 to `0xA001_0000` with a 64 KB range each; "Run Connection Automation" does not always honour existing address assignments without explicit override.
- **PSU_INIT.TCL bypasses FSBL for faster bare-metal debug**: On KV260, replace the FSBL in your Vitis debug configuration with `psu_init.tcl` to shave minutes off each debug cycle and avoid FSBL boot-loop issues that can prevent xil_printf from appearing on UART.
- **Non-project mode TCL builds are faster and CI-friendly**: Running synthesis, implementation, and bitstream generation from a single `.tcl` script with `vivado -mode batch -source build.tcl` keeps no project files on disk and reproduces bit-for-bit in CI without GUI state pollution.
- **Vivado 2025.1 / 2026.1 tool chain progression**: AMD shipped 2025.1 (Vivado release notes UG973, May 2025) and 2026.1 is now available; the 2026.1 licensing model changed — verify your license type before upgrading if you rely on free-tier Webpack.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- All five AXI channels (AW, W, B, AR, R) use independent VALID/READY handshakes sampled on the rising clock edge; signal changes must occur after the rising edge.
- The write address (AW) and write data (W) channels are independent — a slave must accept whichever arrives first and buffer it until the other arrives; only then may it drive BVALID high on the response (B) channel.
- A classic pitfall: gating `AWREADY` on both `AWVALID AND WVALID` introduces a potential deadlock if the master drives them sequentially — this bug existed in early Xilinx AXI-Lite example templates prior to Vivado 2016.3 and was silently corrected.
- `WSTRB` (write strobes) provides byte-lane granularity: one bit per 8-bit lane of WDATA. For a 32-bit bus `WSTRB = 4'b1111` enables all bytes; `4'b0001` writes only the LSB. AXI-Lite mandates that slaves support all valid strobe combinations even if the underlying BRAM ignores narrower writes.
- AXI-Lite vs AXI4 for BRAM: Xilinx's AXI BRAM Controller (PG078) supports both protocols. AXI4 unlocks burst transactions (up to 256 beats) for higher throughput; AXI-Lite restricts to single-beat, making it simpler for register-map style access which is ideal for the KV260 demo's pattern-write/read-back test.

### Code Example

```c
/* Bare-metal AXI-Lite write via memory-mapped pointer */
#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL

static inline void axi_write32(uint32_t addr, uint32_t data)
{
    /* Volatile prevents compiler reordering across AXI transactions */
    *(volatile uint32_t *)addr = data;
    /* dsb() (Data Synchronisation Barrier) ensures the AXI write
       completes before the subsequent read-back begins */
    __asm__ volatile("dsb sy" ::: "memory");
}

static inline uint32_t axi_read32(uint32_t addr)
{
    return *(volatile uint32_t *)addr;
}

/* Write a walking-ones pattern to BRAM0 */
void write_pattern(void)
{
    for (int i = 0; i < 16; i++)
        axi_write32(BRAM0_BASE + (i * 4), (uint32_t)(1u << (i % 32)));
}
```

### Relevance to Your Project

The `main.c` in kv260-axi-bram-demo writes test patterns to `0xA0000000` (BRAM0) and `0xA0010000` (BRAM2). The `dsb sy` barrier is critical: without it the Cortex-A53 out-of-order pipeline may reorder the write and the immediately following read-back, causing a false PASS. The WSTRB insight matters if you extend the demo to test sub-word writes — confirm the BRAM controller is configured for byte-write enable (`C_USE_ECC = 0`, `C_WRITE_MODE_A = WRITE_FIRST`).

## Vivado Block Design / IP Integrator

### Key Findings

- **Run Block Automation first, then Connection Automation**: Block Automation sets up the Zynq PS with correct DDR/fixed-IO configuration; running Connection Automation before it can result in AXI clocks being wired to the wrong source.
- **Address Editor manual entry**: After running Connection Automation, switch to the Address Editor tab and verify offsets. IP Integrator assigns sequential offsets by default — you must manually enter `0xA000_0000` and `0xA001_0000` for BRAM0 and BRAM2 respectively and set range to `64K`.
- **Validate Design** (`validate_bd_design` in Tcl) propagates parameters between IPs — it is mandatory before generating the wrapper because width negotiation (AXI4 vs AXI4-Lite, bus width) happens here, not during synthesis.
- **Regenerate layout** with `regenerate_bd_layout` after adding IPs via Tcl to produce a readable canvas; otherwise blocks stack at 0,0.
- When connecting two BRAM controllers to the same Zynq PS AXI master, use an **AXI SmartConnect** (not the deprecated AXI Interconnect) for better timing QoR — SmartConnect auto-registers the AXI channels which improves timing closure at higher frequencies.

### Code Example

```tcl
# Snippet: set BRAM addresses in IP Integrator via Tcl
# Run after create_bd_cell and connect_bd_intf_net calls

assign_bd_address [get_bd_addr_segs {axi_bram_ctrl_0/S_AXI/Mem0}]
set_property offset 0xA0000000 \
    [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property range 64K \
    [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]

assign_bd_address [get_bd_addr_segs {axi_bram_ctrl_1/S_AXI/Mem0}]
set_property offset 0xA0010000 \
    [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_1_Mem0}]
set_property range 64K \
    [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_1_Mem0}]

validate_bd_design
save_bd_design
```

### Relevance to Your Project

Your `create_bd.tcl` script drives the full block design. If address assignments are missing or ordered before `assign_bd_address`, synthesis succeeds but the PS will silently issue AXI transactions to unmapped space, producing no bus error on AXI-Lite (no interrupt is generated by default) and the read-back will return 0x00000000 — indistinguishable from a BRAM that was never written.

## Vivado TCL Scripting

### Key Findings

- **Non-project mode**: No `.xpr` file is created; all design state lives in memory. Run with `vivado -mode batch -source build.tcl`. Faster than project mode and produces reproducible output in CI environments.
- **Batch vs Tcl mode**: In batch mode Vivado auto-exits after the script; in Tcl mode it drops to an interactive prompt. For CI use `-mode batch`. The key gotcha: batch mode does NOT forward unknown commands to the OS shell — always prefix external calls with `exec` (e.g., `exec git log -1`).
- **Design checkpoints** (`write_checkpoint post_route.dcp`) are the only persistent state in non-project mode. Write them after each major step (synth, impl, route) so you can resume without re-running everything.
- **open_checkpoint** lets you re-enter at any stage: `open_checkpoint post_route.dcp; write_bitstream top.bit`.
- Avoid `source` inside `catch` blocks for complex scripts — exceptions from nested `source` calls can be silently swallowed.

### Code Example

```tcl
# Minimal non-project mode build script for kv260-axi-bram-demo
set TOP       kv260_top
set PART      xck26-sfvc784-2LV-c
set XDC_FILE  ../constraints/kv260_top.xdc
set BD_SCRIPT create_bd.tcl

# 1. Create in-memory project context
read_vhdl [glob ../vhdl/*.vhd]
source $BD_SCRIPT
generate_target all [get_files *.bd]
make_wrapper -files [get_files *.bd] -top
read_vhdl [glob *.bd/hdl/*.vhd]
read_xdc $XDC_FILE

# 2. Synthesis
synth_design -top $TOP -part $PART -flatten_hierarchy rebuilt
write_checkpoint -force post_synth.dcp

# 3. Implementation
opt_design
place_design
route_design
write_checkpoint -force post_route.dcp

# 4. Reports and bitstream
report_timing_summary -file timing_summary.rpt
report_utilization    -file utilization.rpt
write_bitstream -force $TOP.bit
```

### Relevance to Your Project

The existing `create_bd.tcl` is designed to be `source`d inside Vivado. Wrapping it in the non-project build above eliminates the need to maintain a `.xpr` and makes the repo self-contained — any developer can run `vivado -mode batch -source build.tcl` to regenerate the bitstream from scratch.

## Vitis Bare-Metal / Standalone

### Key Findings

- **PSU_INIT.TCL replaces FSBL for debug**: In the Vitis debug configuration, under "Target Setup → Pre-Run TCL Script", point to `psu_init.tcl` (generated in the BSP) instead of using an FSBL ELF. This skips the full boot sequence and gets the PS configured in seconds, resolving the common issue of xil_printf output not appearing at the UART terminal.
- **UART configuration**: The KV260's USB-UART bridge (J4 micro-USB) connects to UART0 (MIO[22:23]) at 115200 baud by default. If xil_printf is silent, verify in the BSP settings that `STDIN_BASEADDRESS` and `STDOUT_BASEADDRESS` are both set to `XUARTPS_0_BASEADDR` (0xFF000000), not UART1.
- **BSP regeneration after XSA change**: Every time you export the XSA from Vivado, you must right-click the platform in Vitis and select "Update Hardware" — the BSP re-generates driver header files including address maps. Forgetting this step after an address-editor change is a very common source of mismatch between the C `#define`s and the actual hardware.
- **Linker script heap/stack**: The default standalone linker script (`lscript.ld`) allocates 0x2000 bytes for stack and 0x800 for heap. For any application doing `malloc` or using `xil_printf` with wide format strings, increase heap to at least `0x4000`.
- **Cache coherency**: The Cortex-A53 data cache is enabled by default in standalone. When accessing BRAM via AXI (not OCM), disable the D-cache for that region or call `Xil_DCacheFlushRange` before reading back data written by the PS.

### Code Example

```c
#include "xil_printf.h"
#include "xil_cache.h"
#include "xparameters.h"

#define BRAM0_BASE  XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR  /* 0xA0000000 */
#define BRAM2_BASE  XPAR_AXI_BRAM_CTRL_1_S_AXI_BASEADDR  /* 0xA0010000 */
#define TEST_WORDS  16

int run_bram_test(uint32_t base, const char *name)
{
    /* Flush and invalidate D-cache for the BRAM region before access */
    Xil_DCacheFlushRange(base, TEST_WORDS * 4);

    for (int i = 0; i < TEST_WORDS; i++)
        Xil_Out32(base + (i * 4), 0xDEAD0000 | i);

    Xil_DCacheFlushRange(base, TEST_WORDS * 4);

    int pass = 1;
    for (int i = 0; i < TEST_WORDS; i++) {
        uint32_t rd = Xil_In32(base + (i * 4));
        if (rd != (0xDEAD0000 | (uint32_t)i)) {
            xil_printf("[FAIL] %s[%d]: wrote 0x%08X read 0x%08X\r\n",
                       name, i, 0xDEAD0000 | i, rd);
            pass = 0;
        }
    }
    xil_printf("[%s] %s\r\n", pass ? "PASS" : "FAIL", name);
    return pass;
}

int main(void)
{
    xil_printf("KV260 AXI-BRAM test starting...\r\n");
    int ok = run_bram_test(BRAM0_BASE, "BRAM0") &
             run_bram_test(BRAM2_BASE, "BRAM2");
    xil_printf("Overall: %s\r\n", ok ? "PASS" : "FAIL");
    return ok ? 0 : 1;
}
```

### Relevance to Your Project

This mirrors the intent of your `main.c` but adds `Xil_DCacheFlushRange` calls that prevent false-PASS results from the D-cache serving stale data. The `XPAR_AXI_BRAM_CTRL_*_BASEADDR` constants come from the BSP-generated `xparameters.h`, ensuring the addresses stay in sync with the Vivado Address Editor.

## XDC Timing Constraints

### Key Findings

- **set_input_delay / set_output_delay syntax (UG835, 2025.1)**: Values are in nanoseconds, relative to a specified clock edge. Positive `set_input_delay` means data arrives that many ns after the reference clock edge at the FPGA pin.
- **Clock groups for PS-to-PL**: The Zynq PS generates `pl_clk0` which feeds PL logic. Any path crossing from the PS (static timing) to user PL registers must be covered by a `set_clock_groups -asynchronous` or `set_false_path` constraint, or timing will be over-constrained with unreachable requirements.
- **For a BRAM-only design with no external IO**, you typically need only: (a) a primary clock constraint on `pl_clk0`, and (b) false paths on JTAG/config interfaces.
- **set_false_path vs set_multicycle_path**: Use `set_false_path` for signals that genuinely cross asynchronous clock domains; use `set_multicycle_path` only for intentionally slow paths within a single clock domain (e.g., a control register sampled every N cycles).
- **CDC crossing lint**: Run `report_cdc` after route to catch any unconstrained clock-domain crossings that the static timing analysis may have silently skipped.

### Code Example

```tcl
# Minimal XDC for KV260 AXI-BRAM bare-metal design
# pl_clk0 drives all PL logic; no external IO in this design

# Primary PL clock from Zynq PS (actual freq set in block design)
create_clock -period 10.000 -name pl_clk0 [get_pins zynq_ultra_ps_e_0/inst/PS8_i/PLCLK[0]]

# False path on PS-to-PL configuration paths (JTAG, DONE, INIT)
set_false_path -from [get_ports PS_DONE]
set_false_path -from [get_ports PS_ERROR_OUT]

# Async clock groups: isolate PS clock domains from any other user clocks
# (add your own clocks here if you later add external oscillators)
# set_clock_groups -asynchronous -group [get_clocks pl_clk0] \
#                                -group [get_clocks clk_ext]

# Timing exceptions for reset synchronisers (if any)
# set_false_path -to [get_cells -hierarchical -filter {NAME =~ *rst_sync*}]
```

### Relevance to Your Project

Since the kv260-axi-bram-demo has no external IO pins (all communication is through the PS UART and JTAG), you only need the `pl_clk0` definition and the PS interface false paths. Adding more constraints than necessary will cause Vivado to flag invalid paths as timing violations, making it harder to spot real issues.

## Kria KV260 / K26 SoM

### Key Findings

- **Default boot mode is QSPI32**: The KV260 Starter Kit ships with pre-loaded boot firmware in QSPI. The `MODE[3:0]` pins on the SOM connector control the boot sequence — the carrier card ties them to `0b0010` for QSPI32. Do not modify the QSPI contents during development; use JTAG boot mode instead.
- **JTAG boot for bare-metal development**: In Vitis, connect via JTAG (micro-USB J4), use `psu_init.tcl` instead of FSBL, and program the FPGA and PS application directly over JTAG without touching QSPI. This is the recommended flow for iterative development.
- **EMIO vs MIO**: MIO pins are hard-wired to PS peripherals (UART, I2C, SPI, ENET) and are fixed in the SOM. EMIO routes PS peripheral signals through the PL fabric to carrier card expansion connectors — useful for GPIOs on the Raspberry Pi header or PMOD connectors on the KV260 carrier board.
- **Fan control via EMIO**: The KV260 carrier board fan is controlled via an EMIO GPIO from the PS. The default Linux bitstream maps this; if you replace the bitstream with your own, include the EMIO fan GPIO or the board will overheat under sustained PS load.
- **Power domains**: The K26 SOM has separate power rails for PS (VCCINT_PS, VCC_PSBATT) and PL (VCCINT, VCCO banks). The PL banks default to 1.8 V on the KV260 carrier for the HP/HD banks — verify your VCCO matches your XDC `set_property IOSTANDARD` values if you later add external IO.

### Code Example

```tcl
# Switch KV260 to JTAG boot mode via XSCT (run in Vitis XSCT console)
# Connect before power cycling or after a hard reset

connect
after 1000
targets -set -filter {name =~ "PSU"}
# Switch boot mode register to JTAG (mode = 0)
mwr 0xFF5E0200 0x0100  ;# BOOT_MODE_USER: set USER_MODE=1, BOOT_MODE=0 (JTAG)
rst -system
after 2000
targets -set -filter {name =~ "APU*"}
source [lindex [glob -directory . psu_init.tcl] 0]
psu_init
```

### Relevance to Your Project

When iterating on the kv260-axi-bram-demo, the JTAG boot path above lets you reprogram both the PL bitstream and the PS application in a single Vitis launch without touching QSPI. Pair it with the `psu_init.tcl` debug configuration described in the Vitis section to get UART output appearing within seconds of hitting "Debug."

## AMD/Xilinx Tool Updates (Vivado/Vitis 2025.x)

### Key Findings

- **Vivado 2025.1** (released May 2025, UG973): Adds device support for Versal AI Edge Series Gen 2, Versal Prime Series Gen 2, and Spartan UltraScale+. Introduces a Unified Selective Device Installer to reduce download size. QoR improvements for Versal SSIT devices (Calibrated Deskew). Zynq UltraScale+ toolchain is mature and stable with no breaking changes reported.
- **Vitis 2025.1** (released July 2025, UG1742): New Vitis IDE with a redesigned backend ("Vitis Server") replacing the Eclipse-based IDE. Classic tools (`hw_server`, `bootgen`, `program_flash`) are retained as command-line utilities. Supports Versal, Zynq MPSoC, Zynq 7000, and MicroBlaze targets.
- **2026.1 is now available**: AMD released 2026.1 with a changed licensing model — verify license compatibility before upgrading. The 2026.1 Vitis known issues list (AR #000040220) documents regressions; review before migrating your KV260 project.
- **Hardware Design Fast Iteration (XD101)**: New in 2025.1 — a "Vitis Export to Vivado" flow allows you to iterate on hardware in Vivado and export back into a Vitis platform without rebuilding the full platform from scratch, reducing round-trip time.
- **BIST tutorial updated for 2025.1**: A KV260 BIST (Built-In Self-Test) tutorial was republished on Hackster.io specifically for Vivado/Vitis 2025.1, confirming the tool flow is stable for KV260 bare-metal work.
