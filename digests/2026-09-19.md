# FPGA Research Digest - 2026-09-19

## Executive Summary

- **AXI-Lite write handshake bug**: Xilinx's own template AXI-Lite slave code had a read-side backpressure bug (where the slave didn't properly lower ARREADY when RREADY was held low by the master). If your KV260 BRAM reads stall intermittently, verify your slave correctly deasserts ARREADY when RREADY is low.
- **TCL non-project mode** is the cleanest way to script bitstream generation from CI or headless servers — `vivado -mode batch -source build.tcl` with `synth_design`, `opt_design`, `place_design`, `route_design`, `write_bitstream` sequentially is the canonical pattern.
- **Kria JTAG vs QSPI boot**: For iterative bare-metal development, JTAG boot (using `psu_init.tcl` instead of FSBL) is the fastest iteration loop; QSPI32 is the production flow that survives power-cycling without a host.
- **BSP stdout must match your UART**: Vitis bare-metal `xil_printf` silently fails if the BSP's `stdout` peripheral is misconfigured. Verify in the BSP settings that stdout maps to your UART PS device before chasing missing serial output.
- **Vivado 2025.1** introduced a new Pblock planner and "boot PS first / load PL on-the-fly" capability, which simplifies iterative AXI-PL debugging workflows.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- The AXI-Lite handshake completes when both `VALID` and `READY` on a channel are asserted on the same rising clock edge. Never advance state if only one is high.
- The most common AXI-Lite slave bug (ZipCPU analysis): raising `AWREADY`/`WREADY` independently without checking `BREADY`. If the master holds `BREADY` low, the slave must not overwrite the write-response register or assert `BVALID` again until `BREADY` goes high.
- For a clean Xilinx-style AXI-Lite slave, only assert `AWREADY` when *both* `AWVALID` and `WVALID` are true simultaneously — this avoids partial-channel deadlocks.
- AXI-Stream (for future DMA work): `TREADY` is the single backpressure signal. Data is consumed only when both `TVALID` and `TREADY` are high on the rising edge — identical handshake to AXI-Lite but with optional `TKEEP`/`TLAST` for framing.
- Xilinx fixed the write-channel bug in their template after Vivado 2016.3, but the read-channel bug (ARREADY vs RREADY) persisted longer — always verify with a formal tool like SymbiYosys or at minimum a directed testbench if using custom slaves.

### Code Example

```vhdl
-- Minimal AXI-Lite write handshake state machine (VHDL)
-- Only accept write address+data simultaneously; hold BVALID until BREADY
process(S_AXI_ACLK)
begin
  if rising_edge(S_AXI_ACLK) then
    if S_AXI_ARESETN = '0' then
      axi_awready <= '0';
      axi_wready  <= '0';
      axi_bvalid  <= '0';
    else
      -- Accept address+data in the same cycle
      if S_AXI_AWVALID = '1' and S_AXI_WVALID = '1' and
         axi_awready = '0' and axi_bvalid = '0' then
        axi_awready <= '1';
        axi_wready  <= '1';
      else
        axi_awready <= '0';
        axi_wready  <= '0';
      end if;

      -- Assert BVALID one cycle after handshake
      if axi_awready = '1' then
        axi_bvalid <= '1';
        axi_bresp  <= "00"; -- OKAY
      elsif S_AXI_BREADY = '1' then
        axi_bvalid <= '0'; -- Clear only after master acknowledges
      end if;
    end if;
  end if;
end process;
```

### Relevance to Your Project

Your project writes patterns to BRAM0 (`0xA0000000`) and BRAM2 (`0xA0010000`) over AXI-Lite and reads them back. If you ever see a PASS on write but a read returns garbage, the most likely cause is a BREADY/BVALID stall leaving the slave in an undetermined state. Checking that your AXI BRAM Controller handshake completes cleanly (BVALID deasserted before next transaction) is the first thing to verify in simulation.

## Vivado Block Design / IP Integrator

### Key Findings

- **Export block design to TCL** via `File → Export → Export Block Design` (or `write_bd_tcl`) to get a reproducible script. This script may not be portable across major Vivado versions, but within the same major release (e.g., 2025.1) it is stable.
- **Connection automation**: After adding a new IP, clicking *Run Connection Automation* wires AXI slaves to the nearest AXI interconnect and sets up clock/reset. Always inspect the result — it sometimes creates a second AXI interconnect when one would do.
- **Address Editor**: Each AXI slave needs a unique, non-overlapping address range. The auto-assigned ranges start at `0xA000_0000` for HP/GP masters — exactly where your BRAM0 lives. Double-check after adding/removing IPs that no two slaves share an address segment.
- Vivado 2025.1 added dedicated "Clocking and Reset" and "AXI-4 Lite" views in IP Integrator for cleaner navigation of complex block designs.
- **Regenerate output products** after any IP parameter change; failing to do so can cause simulation mismatches or synthesis errors that appear unrelated to the parameter change.

### Code Example

```tcl
# Recreate block design from scratch (snippet)
# Usage: vivado -mode batch -source create_bd.tcl

create_project kv260_demo ./kv260_demo -part xck26-sfvc784-2LV-c
set_property board_part xilinx.com:kv260:part0:1.4 [current_project]

create_bd_design "kv260_bd"

# Add Zynq UltraScale+ MPSoC
set zynq_ps [create_bd_cell -type ip -vlnv xilinx.com:ip:zynq_ultra_ps_e:3.5 zynq_ultra_ps_e_0]
apply_bd_automation -rule xilinx.com:bd_rule:zynq_ultra_ps_e \
  -config {apply_board_preset 1} $zynq_ps

# Add AXI BRAM Controller + Block Memory Generator
set bram_ctrl [create_bd_cell -type ip -vlnv xilinx.com:ip:axi_bram_ctrl:4.1 axi_bram_ctrl_0]
set bram      [create_bd_cell -type ip -vlnv xilinx.com:ip:blk_mem_gen:8.4  blk_mem_gen_0]
set_property CONFIG.MEMORY_DEPTH 4096 $bram

connect_bd_intf_net [get_bd_intf_pins axi_bram_ctrl_0/BRAM_PORTA] \
                    [get_bd_intf_pins blk_mem_gen_0/BRAM_PORTA]

# Run connection automation and set address
apply_bd_automation -rule xilinx.com:bd_rule:axi4 \
  -config {Master /zynq_ultra_ps_e_0/M_AXI_HPM0_FPD Clk Auto} \
  [get_bd_intf_pins axi_bram_ctrl_0/S_AXI]

assign_bd_address [get_bd_addr_segs axi_bram_ctrl_0/S_AXI/Mem0]
set_property offset 0xA0000000 \
  [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property range 64K \
  [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]

validate_bd_design
save_bd_design
```

### Relevance to Your Project

This mirrors what `create_bd.tcl` should be doing for your two BRAMs. The critical step is the explicit `set_property offset` call — Connection Automation will assign a default range, but may not land on exactly `0xA0000000` or `0xA0010000`. Always confirm in the Address Editor after automation runs.

## Vivado TCL Scripting

### Key Findings

- **Non-project mode** is ideal for CI/headless builds: no `.xpr` file is created; the entire build lives in memory and exits cleanly after `write_bitstream`.
- Invoke with: `vivado -mode batch -source build.tcl -log build.log -journal build.jou`
- **Hook scripts** (`pre_synth.tcl`, `post_route.tcl`) can be defined in a project to run automatically at specific flow stages — useful for custom DRC checks or reporting.
- Use `get_timing_paths -max_paths 10 -nworst 1 -setup` after `route_design` to programmatically check WNS before committing to `write_bitstream`.
- `write_bd_tcl` with `-no_ip_version` flag produces more portable TCL that upgrades gracefully across patch releases.
- Parameterized block design scripts: use TCL procedures/variables to parameterize IP settings (e.g., BRAM depth, AXI data width) so the same script generates multiple variants.

### Code Example

```tcl
#!/usr/bin/env tclsh
# Non-project mode build: RTL-to-bitstream
# Usage: vivado -mode batch -source build_nonproject.tcl

set PART "xck26-sfvc784-2LV-c"
set TOP  "kv260_top"
set OUTDIR "./output"

file mkdir $OUTDIR

# Read sources
read_vhdl -library work [glob ./vhdl/*.vhd]
read_xdc   ./constraints/kv260_timing.xdc

# Synthesize
synth_design -top $TOP -part $PART -flatten_hierarchy rebuilt
write_checkpoint -force $OUTDIR/post_synth.dcp

# Implement
opt_design
place_design
phys_opt_design
route_design
write_checkpoint -force $OUTDIR/post_route.dcp

# Check timing before writing bitstream
set wns [get_property SLACK [get_timing_paths -max_paths 1 -nworst 1 -setup]]
if {$wns < 0} {
  puts "ERROR: Timing failed! WNS = $wns ns"
  exit 1
}

write_bitstream -force $OUTDIR/$TOP.bit
write_hw_platform -fixed -force -file $OUTDIR/$TOP.xsa
puts "Build complete. WNS = $wns ns"
```

### Relevance to Your Project

Your `create_bd.tcl` is the block-design portion. This non-project script pattern wraps it end-to-end, making your entire KV260 build reproducible in a single command — critical for re-running after Vivado IP catalog updates or when handing the project to others.

## Vitis Bare-Metal / Standalone

### Key Findings

- **BSP `stdout` configuration**: In Vitis, after creating a platform project from your `.xsa`, navigate to BSP settings and confirm `stdin`/`stdout` point to `psu_uart_1` (the PS UART connected to the USB-UART bridge on KV260). Wrong assignment means `xil_printf` output goes nowhere.
- **xil_printf vs printf**: `xil_printf` is a lightweight non-buffered printf that doesn't require the C runtime `_write` syscall shim. Prefer it for bare-metal; full `printf` requires `libm` and a heap, which linker scripts must accommodate.
- **Linker script memory regions**: The default bare-metal linker script puts `.text` in OCM or DDR depending on the target processor and BSP. For A53 bare-metal on KV260, ensure `.text` is in DDR (starting at `0x0000_0000` or as configured) and `.stack`/`.heap` are adequately sized (default 8KB stack can overflow with recursive calls).
- **Interrupt controller**: Zynq UltraScale+ uses a GIC-400 (ARM Generic Interrupt Controller). The `XScuGic` driver in embeddedsw is the standalone wrapper. For simple BRAM-read/write polling (your current design), no interrupt setup is needed.
- **BSP drivers location**: `$VITIS_INSTALL/data/embeddedsw/XilinxProcessorIPLib/drivers/` — all driver source is available there and on GitHub at `github.com/Xilinx/embeddedsw`.

### Code Example

```c
/* Bare-metal AXI-BRAM read/write with polling verification */
#include "xil_printf.h"
#include "xil_io.h"
#include "xparameters.h"  /* Generated by BSP: contains BRAM base addresses */

/* If xparameters.h is not used, define manually: */
#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL
#define BRAM_SIZE   0x4000U       /* 16 KB = 4096 x 32-bit words */

static int bram_test(u32 base, const char *name)
{
    u32 i, readback;
    int errors = 0;

    /* Write incrementing pattern */
    for (i = 0; i < BRAM_SIZE / 4; i++) {
        Xil_Out32(base + (i * 4), 0xDEAD0000 | i);
    }

    /* Fence: ensure all writes complete before reads */
    Xil_DCacheFlushRange(base, BRAM_SIZE);

    /* Read back and verify */
    for (i = 0; i < BRAM_SIZE / 4; i++) {
        readback = Xil_In32(base + (i * 4));
        if (readback != (0xDEAD0000 | i)) {
            xil_printf("  MISMATCH @ 0x%08X: exp=0x%08X got=0x%08X\r\n",
                       base + i*4, 0xDEAD0000 | i, readback);
            errors++;
            if (errors > 5) break; /* Stop after first few errors */
        }
    }

    xil_printf("%s: %s (%d errors)\r\n", name,
               errors == 0 ? "PASS" : "FAIL", errors);
    return errors;
}

int main(void)
{
    int total = 0;
    xil_printf("\r\n=== KV260 AXI-BRAM Test ===\r\n");
    total += bram_test(BRAM0_BASE, "BRAM0");
    total += bram_test(BRAM2_BASE, "BRAM2");
    xil_printf("=== Overall: %s ===\r\n", total == 0 ? "PASS" : "FAIL");
    return total;
}
```

### Relevance to Your Project

This is a more defensive version of your `main.c` pattern — it adds a cache flush between write and read (critical on A53 which has D-cache enabled by default in Vitis), stops after 5 mismatches to keep UART output readable, and reports per-address failures to help isolate whether errors are in BRAM0 or BRAM2.

## XDC Timing Constraints

### Key Findings

- For an AXI-Lite PS-to-PL design (all clocks from PS clock wizard), there are **no external I/O delays** to constrain — `set_input_delay`/`set_output_delay` apply only to pins connected to external chip pins, not AXI signals.
- **Clock groups**: If you have the PL driven by `pl_clk0` from the PS and also have a separate free-running oscillator, declare them as `set_clock_groups -asynchronous` to prevent the tool from trying to time cross-domain paths.
- `create_clock` is required for any clock that enters the FPGA on an input pin. PS-sourced clocks (`pl_clk0`) are auto-declared by the Zynq IP.
- KV260 reference constraint files are in the Kria-PYNQ repo (`kv260/base/vivado/constraints/base.xdc`) — useful as a starting template for pin assignments and clock declarations.
- Post-route timing summary: `report_timing_summary -file timing_summary.rpt` — always check WNS > 0 and WHS > 0 before programming hardware.

### Code Example

```tcl
# kv260_timing.xdc — minimal timing constraints for KV260 AXI-BRAM demo
# pl_clk0 is auto-constrained by the Zynq UltraScale+ IP (100 MHz default)
# No external I/O to constrain — all signals are PS-internal AXI

# If adding a PL-only free-running clock on a CMOS pin:
# create_clock -period 10.000 -name pl_user_clk [get_ports user_clk_in]

# Declare PS clock and any PL derivative as asynchronous if used together:
# set_clock_groups -asynchronous \
#   -group [get_clocks clk_pl_0] \
#   -group [get_clocks clk_out1_kv260_bd_clk_wiz_0_0]

# False path for reset synchronizer (if manual reset bridge used):
# set_false_path -from [get_pins */reset_sync_reg[0]/C] \
#                -to   [get_pins */reset_sync_reg[1]/D]

# Bitstream config — required for KV260 (Zynq UltraScale+):
set_property CONFIG_VOLTAGE      1.8 [current_design]
set_property CFGBVS              GND [current_design]
set_property BITSTREAM.GENERAL.COMPRESS TRUE [current_design]
```

### Relevance to Your Project

Since your KV260 demo is a pure PS-master → AXI interconnect → BRAM design with no external I/O in the PL, your XDC file mostly needs the `CONFIG_VOLTAGE`/`CFGBVS` properties and the bitstream compression flag. Adding `set_clock_groups` becomes important if you ever add a separate PL clock domain (e.g., for a custom IP at a different frequency than `pl_clk0`).

## Kria KV260 / K26 SoM

### Key Findings

- **Boot mode**: KV260 ships preset to **QSPI32**. For bare-metal development, switch to JTAG boot using XSDB/XSCT (`targets -set -filter {name =~ "PSU"}; mwr 0xff5e0200 0x0100`). This lets you skip the FSBL and use `psu_init.tcl` directly for fast iteration.
- **Bare-metal flow**: Export `.xsa` from Vivado → create Platform in Vitis → create Application project targeting A53 core 0 → build → run via JTAG. For production: package into BOOT.BIN with `bootgen` and flash to QSPI.
- **PS-PL master interfaces**: KV260 uses `M_AXI_HPM0_FPD` and `M_AXI_HPM1_FPD` from the PS. These are 128-bit AXI HP masters that get down-converted to 32-bit via the AXI Interconnect to reach the BRAM controllers. The default `pl_clk0` is 100 MHz.
- **EMIO GPIO**: GPIO signals can be routed through EMIO (PS GPIO banks 2/3) to appear in the PL without consuming package pins. Useful for debug LEDs or control signals without modifying XDC.
- **USB-UART**: On KV260 carrier card, UART1 (PS UART at `0xFF01_0000`) connects to the USB-UART bridge. Vitis BSP must set `stdout=psu_uart_1`.

### Code Example

```tcl
# XSDB script: switch KV260 to JTAG boot and load bare-metal ELF
# Run from Vitis XSCT console or: xsct jtag_boot.tcl

connect
targets -set -filter {name =~ "PSU"}

# Switch to JTAG boot mode (clears QSPI32 boot mode bits)
mwr 0xFF5E0200 0x0100
rst -system

after 3000

# Initialize PS (replaces FSBL for JTAG development)
source $env(XILINX_VITIS)/scripts/vitis/util/zynqmp_utils.tcl
psu_init

# Download and run the bare-metal ELF on APU core 0
targets -set -filter {name =~ "A53*#0"}
rst -processor
dow ./Debug/kv260_bram_test.elf
con
puts "Application running. Check UART for PASS/FAIL output."
```

### Relevance to Your Project

This XSDB script replaces the manual "right-click → Run" flow in Vitis GUI and can be used for automated test runs. For your BRAM test project, you can run this from a Makefile target (`make run`) to load the ELF and immediately see PASS/FAIL output on the UART — enabling a clean test loop without touching the GUI.

## AMD/Xilinx Tool Updates (Vivado/Vitis 2025.x)

### Key Findings

- **Vivado 2025.1 highlights**: New Pblock Planner (visual floor planner improvements), production support for Spartan UltraScale+ (XCSU10P/25P/35P), and ability to boot the PS first then dynamically load the PL bitstream — useful for KV260 workflows where you want the PS running before PL configuration.
- **Vitis 2025.1**: Enhanced Versal AI Engine support (GEMV/FFT, bitonic sorting), improved DSP library functions. For Zynq UltraScale+ (non-Versal) bare-metal work, the embeddedsw driver updates are the key change — check the embeddedsw GitHub changelog for any `axi_bram_ctrl` or `psu_uart` driver updates.
- **Vivado 2025.2** (released mid-2025): Vivado What's New page indicates further improvements including enhanced directive/subdirective support mapped via TCL in the Advanced Flow.
- **Vitis 2026.1**: Now available — check known issues at `adaptivesupport.amd.com` before upgrading mid-project.
- **Known issues pattern**: Always search `000040220` style AMD support articles before upgrading tools on an active project. Vitis 2026.x known issues article is at AMD Adaptive Support.
- **IP catalog updates**: When opening a project in a newer Vivado version, always upgrade IPs with `upgrade_ip [get_ips]` and re-run `generate_target all` before synthesis to avoid using stale IP netlists.

### Code Example

```tcl
# TCL snippet: upgrade all IPs in a project and regenerate targets
# Run after opening project in a new Vivado version

open_project ./kv260_demo/kv260_demo.xpr

# Report IPs that need upgrade
set stale_ips [get_ips -filter {UPGRADE_VERSIONS != ""}]
if {[llength $stale_ips] > 0} {
  puts "Upgrading [llength $stale_ips] IP(s)..."
  upgrade_ip $stale_ips
  generate_target all $stale_ips
  export_ip_user_files -no_script -sync -force -quiet
}

# Re-export the block design TCL for source control
write_bd_tcl -no_ip_version ./tcl/create_bd_upgraded.tcl
puts "IP upgrade complete. Review create_bd_upgraded.tcl for changes."
```

### Relevance to Your Project

If you open your KV260 project in Vivado 2025.2 or later after having built with 2025.1, this script safely upgrades IP versions in place before resynthesizing. The `write_bd_tcl` at the end gives you a diff-able record of what changed in the block design — important for spotting inadvertent parameter changes in the AXI BRAM Controller or Block Memory Generator.
