# FPGA Research Digest - 2026-11-13

## Executive Summary
- **AXI VALID/READY correctness:** VALID must never depend combinationally on READY — once raised it must hold until the handshake completes. Vivado's own example AXI-Lite slave core has a known bug where it drops READY prematurely, stalling the response channel. Verify your custom VHDL slave against this rule.
- **BRAM byte-address pitfall:** When the AXI BRAM Controller has 32-bit addresses enabled, software must increment by 4 (word stride), not 1. A stride mismatch is a common silent failure when reading back patterns.
- **TCL address assignment:** Use `assign_bd_address` with explicit `-offset`, `-range`, and `-target_address_space` arguments rather than relying on GUI automation. This keeps the BRAM0/BRAM2 base addresses (0xA0000000 / 0xA0010000) reproducible across regenerations.
- **Vitis 2025.1 BSP change:** AMD deprecated all Kria XSCT BSPs in 2025.1. Migrate to the Vitis Unified IDE component flow for standalone projects on the KV260.
- **KV260 AXI crash hazard:** At least one community report (element14) describes boot crashes when AXI-enabled `.dtbo`/`.bit.bin` files are loaded on the K26. For bare-metal (no OS), load the bitstream directly via JTAG/XSDB to bypass this path entirely.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings
- **VALID independence rule:** A master's VALID signal must not be gated by READY. The receiver may wait for VALID before asserting READY, but the reverse creates a protocol deadlock. This is AXI spec rule A3.3.1.
- **Hold-until-accepted:** Once a source asserts VALID it may not deassert it until READY has been high for at least one clock edge (the handshake). Dropping VALID early causes silent transaction loss.
- **Vivado example core bug (confirmed):** ZipCPU formal verification showed that Vivado's generated AXI-Lite slave drops READY while the write-response channel is stalled, allowing a second address-phase transaction to arrive before the first response completes — an illegal state.
- **Combinational feedback pitfall:** Driving VALID combinatorially from READY in custom VHDL creates a zero-delay loop that simulation may mask but synthesis will not. Use registered outputs for VALID.
- **AXI-Lite vs full AXI:** AXI-Lite has no burst, no byte lane strobes on reads, and requires separate address/data phases per access. It is correct for BRAM register-mapped access but unsuitable for bulk transfers where AXI4 bursts would be faster.

### Code Example
```vhdl
-- Correct AXI-Lite slave write-address acceptance
-- AWREADY deasserts after handshake, re-asserts when ready for next
process(clk)
begin
  if rising_edge(clk) then
    if rst_n = '0' then
      awready <= '0';
    elsif awready = '0' and s_axi_awvalid = '1' and s_axi_wvalid = '1' then
      awready <= '1';  -- accept only when both AW and W valid
    else
      awready <= '0';
    end if;
  end if;
end process;
-- AWVALID from master: once high, holds until awready='1'
-- Never: awvalid <= awready;  -- illegal combinational dependency
```

### Relevance to Your Project
Your `kv260_top.vhd` wraps the Xilinx AXI Interconnect driving BRAM0 (0xA0000000) and BRAM2 (0xA0010000). If either BRAM controller's BREADY drops mid-burst on a read, the interconnect can stall. Add `report_cdc -severity ERROR` to your implementation run and check for unintended paths between the PS AXI clock and any combinational READY logic.

## Vivado Block Design / IP Integrator

### Key Findings
- **Generate before non-project use:** A block design must be fully generated (`generate_target all`) before it can be added to a non-project flow. Adding an ungenerated BD produces a locked-IP error.
- **OOC global-mode prerequisite:** Out-of-context block designs must be upgraded and regenerated in global synthesis mode before joining the non-project synthesis flow. Use `upgrade_ip [get_bd_cells -hierarchical *]` in a project-mode script first.
- **Connection automation caveat:** `apply_bd_automation` is convenient in the GUI but inserts non-deterministic wiring when scripted. Prefer explicit `connect_bd_intf_net` calls for AXI interfaces and `connect_bd_net` for scalar signals to keep the script reproducible.
- **Validation is mandatory:** Always call `validate_bd_design` before `save_bd_design`. Saving without validation can write an internally inconsistent BD file that fails silently on the next open.
- **Re-export pattern:** After any GUI modification, re-export via File → Export → Export Block Design and diff against the previous TCL to audit changes.

### Code Example
```tcl
# Minimal IP Integrator block design creation (non-project mode)
create_project -in_memory -part xck26-sfvc784-2LV-c

# Create block design
create_bd_design "kv260_bd"
set_property target_language VHDL [current_project]

# Add Zynq UltraScale+ MPSoC
set zynq [create_bd_cell -type ip -vlnv xilinx.com:ip:zynq_ultra_ps_e:3.5 zynq_ultra_ps_e_0]
apply_preset $zynq  ; # apply board preset (KV260)

# Add AXI BRAM Controller
set bram_ctrl [create_bd_cell -type ip -vlnv xilinx.com:ip:axi_bram_ctrl:4.1 axi_bram_ctrl_0]
set_property CONFIG.SINGLE_PORT_BRAM {1} $bram_ctrl

# Connect M_AXI_HPM0_FPD to BRAM controller
connect_bd_intf_net [get_bd_intf_pins zynq_ultra_ps_e_0/M_AXI_HPM0_FPD] \
    [get_bd_intf_pins axi_bram_ctrl_0/S_AXI]

# Assign address
assign_bd_address [get_bd_addr_segs {axi_bram_ctrl_0/S_AXI/Mem0}] \
    -offset 0xA0000000 -range 64K \
    -target_address_space [get_bd_addr_spaces zynq_ultra_ps_e_0/Data]

validate_bd_design
save_bd_design
```

### Relevance to Your Project
Your `create_bd.tcl` likely uses this pattern for both BRAM controllers. Verify that the offset and range arguments match the linker script's `0xA0000000`/`0xA0010000` base addresses. A range that is too small silently wraps addresses rather than erroring.

## Vivado TCL Scripting

### Key Findings
- **Net vs. interface commands:** `connect_bd_net` wires scalar ports (clk, reset, enables); `connect_bd_intf_net` wires interface bundles (AXI, BRAM). Using the wrong command on an AXI port silently disconnects the interface.
- **Explicit address assignment:** Use `assign_bd_address` with `-offset`, `-range`, and `-target_address_space`. Avoid the GUI automation equivalent (`assign_bd_address` with no arguments) in scripts — it picks addresses non-deterministically.
- **Avoid `apply_bd_automation` in CI:** The automation rules can change between Vivado versions; explicit connections are version-stable.
- **Non-project batch invocation:** Run as `vivado -mode batch -source create_bd.tcl` to avoid GUI initialization overhead in CI.
- **Regenerating the script:** `write_bd_tcl -force -include_layout output.tcl` on an open BD generates a complete, editable source script.
- **Validation at end:** Always end a BD script with `validate_bd_design` followed by `save_bd_design` to catch unconnected pins before synthesis.

### Code Example
```tcl
# Pattern for explicit AXI connection and address assignment
# (safe for scripted/CI use)

# Wire up clocks and resets explicitly
connect_bd_net [get_bd_pins zynq_ultra_ps_e_0/pl_clk0] \
               [get_bd_pins axi_bram_ctrl_0/s_axi_aclk]
connect_bd_net [get_bd_pins zynq_ultra_ps_e_0/pl_resetn0] \
               [get_bd_pins axi_bram_ctrl_0/s_axi_aresetn]

# Assign second BRAM at 0xA0010000
assign_bd_address [get_bd_addr_segs {axi_bram_ctrl_1/S_AXI/Mem0}] \
    -offset 0xA0010000 \
    -range 64K \
    -target_address_space \
        [get_bd_addr_spaces zynq_ultra_ps_e_0/Data]

# Export for re-use
write_bd_tcl -force -include_layout ./tcl/create_bd_exported.tcl

validate_bd_design
save_bd_design
generate_target all [get_files *.bd]
```

### Relevance to Your Project
Your `create_bd.tcl` should use explicit address assignment for BRAM0 (0xA0000000) and BRAM2 (0xA0010000). If a regeneration moves these addresses, `main.c`'s hardcoded base addresses silently fail. Lock the offsets in TCL and cross-check with `report_bd_path`.

## Vitis Bare-Metal / Standalone

### Key Findings
- **UART console routing:** In BSP settings, `STDIN`/`STDOUT` must be explicitly set to the PS UART instance connected to the USB-UART bridge (typically `psu_uart_1` on KV260). Without this, `xil_printf` output goes to the wrong peripheral.
- **xil_printf vs printf:** `xil_printf` has no float support and no heap allocation. It is safe for bare-metal. `printf` requires a semihosting stub or a full libc — do not use it without explicit linker support.
- **GIC initialization pattern:** Use `XScuGic_CfgInitialize` with the config from `XScuGic_LookupConfig(XPAR_SCUGIC_0_DEVICE_ID)`. Register ISRs with `XScuGic_Connect`, enable with `XScuGic_Enable`, then call `Xil_ExceptionEnable()`.
- **2025.1 BSP breaking change:** AMD deprecated all Kria XSCT BSPs (`kv260_revB`, etc.) in 2025.1. Standalone projects must now use the Vitis Unified IDE component flow, which generates the BSP from the XSA automatically.
- **Linker script:** The default `lscript.ld` places all segments in DDR. For a bare-metal AXI test, ensure `.data` and stack are not placed at an AXI slave address range (0xA000_0000 region) to avoid write aliases.

### Code Example
```c
#include "xil_printf.h"
#include "xparameters.h"
#include "xil_io.h"

/* AXI BRAM base addresses from xparameters.h (generated by Vitis from XSA) */
#define BRAM0_BASE  XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR  /* 0xA0000000 */
#define BRAM2_BASE  XPAR_AXI_BRAM_CTRL_1_S_AXI_BASEADDR  /* 0xA0010000 */

static void bram_test(u32 base, const char *name) {
    u32 pattern = 0xDEADBEEF;
    Xil_Out32(base, pattern);
    u32 rd = Xil_In32(base);
    if (rd == pattern)
        xil_printf("%s PASS (read 0x%08X)\r\n", name, rd);
    else
        xil_printf("%s FAIL (wrote 0x%08X, read 0x%08X)\r\n",
                   name, pattern, rd);
}

int main(void) {
    xil_printf("KV260 AXI-BRAM test\r\n");
    bram_test(BRAM0_BASE, "BRAM0");
    bram_test(BRAM2_BASE, "BRAM2");
    return 0;
}
```

### Relevance to Your Project
Your `main.c` hardcodes `0xA0000000`/`0xA0010000`. The pattern above uses `xparameters.h` constants instead, so a future address reassignment in the block design automatically updates the C code after BSP regeneration. Consider migrating to this pattern.

## XDC Timing Constraints

### Key Findings
- **I/O delay purpose:** `set_input_delay` and `set_output_delay` associate an external clock with top-level ports, giving the timing engine a valid launch/capture reference. Without them, Vivado reports unconstrained I/O paths — not an error, but the design may still meet timing by luck.
- **Zynq PS I/O:** For PS-side signals (MIO, UART, I2C) you do not write XDC constraints — the PS7/PSUE IP handles those internally. Only PL I/O ports (from `kv260_top.vhd`'s port list) need XDC constraints.
- **Clock groups:** Use `set_clock_groups -asynchronous` between unrelated clocks (e.g., the PL free-running clock and an external reference) to prevent false timing paths across unrelated domains.
- **Ordering for runtime:** AMD recommends placing `create_clock` before all derived clock constraints, then I/O delays, then `set_clock_groups`, then false paths. This ordering reduces constraint solver runtime.
- **Minimum constraint set for AXI-BRAM:** At minimum, constrain `pl_clk0` from the PSUE and add `set_false_path` for any asynchronous reset inputs.

### Code Example
```xdc
# Constrain the PL clock (100 MHz, sourced from PSUE pl_clk0)
# Note: Vivado auto-derives this from the PSUE IP; explicit constraint is a cross-check
create_clock -period 10.000 -name pl_clk0 [get_pins zynq_ultra_ps_e_0/inst/PS8_i/PLCLK[0]]

# If a 2nd PL clock is added later, declare it async to the first
# set_clock_groups -asynchronous -group [get_clocks pl_clk0] \
#                                -group [get_clocks pl_clk1]

# False path for active-low reset input (async assertion is intentional)
set_false_path -from [get_pins zynq_ultra_ps_e_0/inst/PS8_i/PLRESETN[0]] \
               -to   [all_registers]

# No set_input_delay / set_output_delay needed for AXI-BRAM:
# both master (PS) and slaves (BRAM ctrl) are on the same pl_clk0 domain.
```

### Relevance to Your Project
Your KV260 design is fully synchronous on `pl_clk0` with no external I/O on the PL side, so I/O delay constraints are not required. The critical constraint is `create_clock` (or verifying the PSUE auto-derives it) and a `set_false_path` on the reset. Run `report_timing_summary` after implementation and confirm zero unconstrained endpoints.

## Kria KV260 / K26 SoM

### Key Findings
- **Boot order:** The K26 uses QSPI flash (512 Mbit, on-module) as the primary boot device (pre-programmed at the factory). The KV260 carrier adds an SD card as the secondary boot device. Boot mode is selected by resistor-strapped MODE pins (not a DIP switch).
- **MIO bank layout:** Bank 500 carries on-SOM peripherals (QSPI, eMMC, I2C management, TPM SPI). Banks 501 and 502 are routed to the carrier-card connector and are customizable. MIO pin conflicts here are a frequent source of custom carrier failures.
- **Bare-metal bitstream loading:** For pure bare-metal (no Linux), load the bitstream over JTAG using `xsdb` / `program_hw_devices`. Avoid loading `.bit.bin` via the Kria App Manager boot path — that path expects a device-tree overlay and can crash the boot if the DT is inconsistent with the hardware.
- **AXI crash report:** An element14 community thread documents a K26 that crashes during boot when an AXI-enabled `.dtbo` + `.bit.bin` are loaded via the platform management path. Erasing and reflashing the QSPI restores it. Root cause: the AXI slave address not matching the device tree node.
- **Platform files:** The KV260 Vivado board files include `kv260_cc` constraints that map the PL I/O to the KV260 carrier's physical header pins.

### Code Example
```tcl
# XSDB script to load bitstream on KV260 over JTAG (bare-metal)
# Run from: xsdb load_bitstream.tcl

connect
target -set -filter {name =~ "PSU"}
mwr 0xFFFF0000 0x0000000E   ; # release PL reset

target -set -filter {name =~ "PL"}
fpga -f ../impl/kv260_top.bit

puts "Bitstream loaded"

# Optionally launch bare-metal ELF on APU core 0
target -set -filter {name =~ "APU*Core0"}
rst -processor
dow ../vitis/kv260_bsp/kv260_app/Debug/kv260_app.elf
con
```

### Relevance to Your Project
Your PS-to-PL connectivity test (`main.c` writing to 0xA0000000/0xA0010000) works exactly this way. The XSDB script above matches the standard bare-metal workflow for your stack. After `fpga -f` loads the bitstream, `pl_clk0` starts toggling and the AXI Interconnect becomes live; the `dow` + `con` sequence then runs your PASS/FAIL loop.

## AMD/Xilinx Tool Updates (2025.1)

### Key Findings
- **New device support:** Vivado 2025.1 adds Versal AI Edge Series Gen 2, Versal Prime Series Gen 2, and Spartan UltraScale+ family devices. No changes to Zynq UltraScale+ (xck26) support.
- **New AXI Switch IP:** A new AXI Switch IP core was added, but it is RTL-only and not usable inside IP Integrator block designs. For block design AXI routing, the AXI Interconnect and SmartConnect remain the supported paths.
- **Single File Download deprecated:** The Single File Download installer option is removed starting in 2025.2. Downloading Vivado now requires the web installer or the full multi-file package.
- **IP version bumps:** FIR Compiler updated to v7.2; Video Processing Subsystem to v2.3; DisplayPort 2.1 TX/RX Subsystems v1.0 added for 2025.1.
- **Kria XSCT BSP deprecation (critical):** All Kria-specific XSCT BSPs (`kv260_revB`, etc.) are deprecated in 2025.1. Projects using legacy XSCT BSP generation workflows must migrate to the Vitis Unified IDE component flow.
- **OpenAMP changes:** 2025.1 open-source release notes document removal of Zynq 7000 SoC support from OpenAMP, and auto-detection changes for baremetal firmware builds.

### Code Example
```tcl
# Check IP version in a 2025.1 project script to guard against upgrades
# Run inside Vivado Tcl console or a batch script

set bram_ctrl_ip [get_ips -all axi_bram_ctrl_0]
if {[llength $bram_ctrl_ip] > 0} {
    set ver [get_property VERSION $bram_ctrl_ip]
    puts "AXI BRAM Controller version: $ver"
    # Warn if not the expected version for 2025.1 catalog
    if {$ver ne "4.1"} {
        puts "WARNING: Expected axi_bram_ctrl 4.1, got $ver — regenerate IP."
    }
}

# Lock IP to prevent silent upgrades in future Vivado versions
set_property IS_LOCKED true $bram_ctrl_ip
```

### Relevance to Your Project
If you open your KV260 project in Vivado 2025.1 for the first time, you will see an IP upgrade prompt for all cores in the catalog. Run the version-check snippet above before accepting upgrades to confirm the expected IP versions. The AXI BRAM Controller version should be 4.1 for 2025.1; accepting an unexpected bump may change timing behavior.
