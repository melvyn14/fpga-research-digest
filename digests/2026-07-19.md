# FPGA Research Digest - 2026-07-19

## Executive Summary

- **AXI-Lite VALID must never wait for READY**: A source must assert VALID before it knows READY is high; once asserted, VALID must stay high until the handshake completes. Violating this creates a deadlock and is the single most common AXI bug in Xilinx template code.
- **Vivado 2025.1 adds a new RTL-based AXI Switch IP** that replaces fixed-function AXI Interconnect for many designs; it also adds dedicated "Clocking and Reset" and "Interrupt and AXI-4 Lite" block-design views—worth exploring for cleaner BRAM controller hookup.
- **KV260 pl_clk0 runs at 100 MHz by default**; use `create_generated_clock` rather than `set_property` when constraining downstream MMCM/PLL-derived clocks to avoid missed-path analysis.
- **JTAG boot on KV260** requires four artefacts loaded via XSDB: `fsbl.elf`, `pmufw.elf`, the application `.elf`, and the `.bit` file. Missing the PMU firmware step is the most common bare-metal bring-up failure.
- **Vitis BSP `stdout`/`stdin` must be pointed at the right UART instance** in BSP settings; a mismatch silently produces no output from `xil_printf` even when the application runs correctly.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- **Fundamental handshake rule**: A master must assert `AWVALID`/`WVALID` independently of whether `AWREADY`/`WREADY` is high. Waiting for READY before driving VALID can cause deadlock if the slave also waits.
- **VALID must be held**: Once asserted, `xVALID` cannot be deasserted until the handshake completes (both VALID and READY high on the same rising clock edge).
- **Xilinx template defect**: Xilinx's own AXI-Stream master template delays `TLAST` in a way that violates the protocol when `M_AXIS_TVALID && !M_AXIS_TREADY` on the penultimate beat—watch for this in generated IP.
- **Write response channel**: AXI-Lite has a separate `BRESP`/`BVALID`/`BREADY` write-response channel. Bare-metal code that ignores `BVALID` won't know a write was rejected with `SLVERR`.
- **AXI-Lite vs full AXI**: AXI-Lite has no burst support and data width is fixed (32 or 64-bit). The BRAM controllers in the KV260 project use AXI-Lite, which limits throughput to one beat per transaction but simplifies the control path.

### Code Example

```vhdl
-- Minimal AXI-Lite slave state machine (write path)
-- VALID must not wait for READY before being asserted
process(clk)
begin
  if rising_edge(clk) then
    if s_axi_awvalid = '1' and s_axi_awready = '1' then
      wr_addr <= s_axi_awaddr;
      aw_done <= '1';
    end if;
    if s_axi_wvalid = '1' and s_axi_wready = '1' then
      wr_data <= s_axi_wdata;
      w_done  <= '1';
    end if;
    -- Only assert BVALID after both address and data are captured
    if aw_done = '1' and w_done = '1' then
      s_axi_bvalid <= '1';
      s_axi_bresp  <= "00"; -- OKAY
      aw_done <= '0';
      w_done  <= '0';
    end if;
    if s_axi_bvalid = '1' and s_axi_bready = '1' then
      s_axi_bvalid <= '0';
    end if;
  end if;
end process;
```

### Relevance to Your Project

Your `main.c` writes patterns to BRAM0 (`0xA0000000`) and BRAM2 (`0xA0010000`) using memory-mapped writes. If the AXI-Lite slave in the BRAM controller ever returns `SLVERR` on `BRESP`, your code will silently proceed as a pass. Consider reading the BRESP channel or at minimum verifying data via the readback loop already in your design.

## Vivado Block Design / IP Integrator

### Key Findings

- **Connection Automation**: Right-clicking an unconnected AXI slave port and selecting "Run Connection Automation" will auto-wire it to the Zynq PS AXI master and add/configure an AXI Interconnect if needed. The Tcl equivalent is `apply_bd_automation`.
- **Address Editor**: Every AXI slave must have a memory-mapped segment assigned. `assign_bd_address` in Tcl does this automatically; the range can then be overridden with `set_property range`.
- **Vivado 2025.1 new views**: Dedicated "Clocking and Reset" and "Interrupt and AXI-4 Lite" views in IP Integrator surface these subsystems without hunting through the full canvas—useful when wiring up multiple BRAM controllers.
- **New AXI Switch IP (2025.1)**: Fully customizable RTL-based IP replacing the older AXI Interconnect for bridging different AXI interface types and widths. More suitable than the older IP for mixed AXI-Lite / AXI4 designs.
- **New Pblock Planner (2025.1)**: One-stop shop for all pblock-related operations—relevant if you later need to constrain BRAM and PL logic to specific clock regions.
- **Tcl console mirrors GUI**: Every GUI action emits its Tcl equivalent in the Tcl console. Use this to learn the commands for your `create_bd.tcl` script by performing the action in GUI first.

### Code Example

```tcl
# Assign address and set range for two BRAM controllers
assign_bd_address [get_bd_addr_segs {axi_bram_ctrl_0/S_AXI/Mem0}]
set_property offset 0xA0000000 \
  [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property range 8K \
  [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]

assign_bd_address [get_bd_addr_segs {axi_bram_ctrl_1/S_AXI/Mem0}]
set_property offset 0xA0010000 \
  [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_1_Mem0}]
set_property range 8K \
  [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_1_Mem0}]
```

### Relevance to Your Project

Your `create_bd.tcl` sets up BRAM0 at `0xA0000000` and BRAM2 at `0xA0010000`. If you ever regenerate the block design from scratch, the above snippet shows how to reliably re-pin those addresses. The 2025.1 AXI Switch IP is worth evaluating if you later add a third AXI slave, as it offers more flexible topology than chaining AXI Interconnect blocks.

## Vivado TCL Scripting

### Key Findings

- **Batch mode invocation**: `vivado -mode batch -source create_bd.tcl` opens Vivado, runs the script, and exits—ideal for CI or headless server flows.
- **Non-project mode**: Use `read_vhdl`, `read_xdc`, `synth_design`, `opt_design`, `place_design`, `route_design`, `write_bitstream` without a `.xpr` project file. Faster for scripted flows; design checkpoints (`.dcp`) are the save points.
- **`write_project_tcl`**: In GUI mode, after building your block design, run `write_project_tcl rebuild.tcl` to export a complete reconstruction script—useful for version-controlling a design without committing large IP output files.
- **Arguments to batch scripts**: Pass arguments with `vivado -mode batch -source script.tcl -tclargs arg1 arg2`; access them in the script via `lindex $argv 0`.
- **`open_bd_design` vs `create_bd_design`**: `create_bd_design` makes a new empty canvas; `open_bd_design` opens an existing `.bd` file. Mixing these up causes confusing "design already exists" errors.

### Code Example

```tcl
# Non-project mode: synthesize, implement, and write bitstream
read_vhdl   ../vhdl/kv260_top.vhd
read_bd     ../bd/design_1.bd
generate_target all [get_files ../bd/design_1.bd]

synth_design  -top kv260_top -part xck26-sfvc784-2LV-c
opt_design
place_design
route_design
write_checkpoint -force ./post_route.dcp
report_timing_summary -file ./timing.rpt
write_bitstream -force ./kv260_top.bit
```

### Relevance to Your Project

Your `create_bd.tcl` already automates block design creation. Wrapping it in the non-project flow above lets you run the full build (synthesis → bitstream) from a single `make` call without opening the GUI, which is valuable for reproducible builds and future CI integration.

## Vitis Bare-Metal / Standalone

### Key Findings

- **BSP stdout/stdin**: In the BSP settings under `standalone`, `stdout` and `stdin` must be set to the UART instance wired to your physical USB-UART bridge. A mismatch (e.g., pointing at `psu_uart_1` when the cable is on `psu_uart_0`) produces complete silence even when the application runs.
- **`xil_printf` vs `printf`**: `xil_printf` is lighter (no floating-point, limited format support) but sufficient for `%d`, `%x`, `%s`. Use `printf` only if you need `%f`; it pulls in libm and increases code size significantly.
- **Linker script OCM region**: The auto-generated linker script sometimes has wrong base addresses for OCM (On-Chip Memory). Open `lscript.ld` in a text editor and verify `psu_ocm_ram_0` base is `0xFFFC0000` for Zynq UltraScale+.
- **GIC interrupt controller**: Zynq UltraScale+ uses a GIC (Generic Interrupt Controller). For bare-metal, initialize with `XScuGic_LookupConfig` / `XScuGic_CfgInitialize`, then connect handlers with `XScuGic_Connect`. Private Peripheral Interrupts (PPI) use IDs 27-31; Shared Peripheral Interrupts (SPI) start at 32.
- **Cache coherency**: When sharing memory between PL DMA and PS, call `Xil_DCacheFlushRange` before DMA reads and `Xil_DCacheInvalidateRange` after DMA writes to avoid stale cache lines.

### Code Example

```c
#include "xil_printf.h"
#include "xil_io.h"

#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL
#define TEST_WORDS  4

int verify_bram(u32 base, u32 pattern) {
    for (int i = 0; i < TEST_WORDS; i++) {
        Xil_Out32(base + i*4, pattern + i);
    }
    for (int i = 0; i < TEST_WORDS; i++) {
        u32 rd = Xil_In32(base + i*4);
        if (rd != pattern + i) {
            xil_printf("FAIL @ 0x%08X: wrote 0x%08X, read 0x%08X\r\n",
                       base + i*4, pattern + i, rd);
            return -1;
        }
    }
    return 0;
}

int main(void) {
    xil_printf("KV260 AXI-BRAM test\r\n");
    int r0 = verify_bram(BRAM0_BASE, 0xDEAD0000);
    int r2 = verify_bram(BRAM2_BASE, 0xBEEF0000);
    xil_printf("BRAM0: %s  BRAM2: %s\r\n",
               r0 == 0 ? "PASS" : "FAIL",
               r2 == 0 ? "PASS" : "FAIL");
    return 0;
}
```

### Relevance to Your Project

This pattern mirrors what your `main.c` does. The `Xil_Out32`/`Xil_In32` wrappers are the canonical bare-metal memory-mapped I/O API for Xilinx standalone. If `xil_printf` is silent, check the BSP `stdout` assignment first—it's the most common debugging dead-end on KV260 bring-up.

## XDC Timing Constraints

### Key Findings

- **Primary clock for KV260 PL**: The Zynq UltraScale+ PS exports `pl_clk0` to the PL at 100 MHz by default. Vivado auto-creates this clock constraint when the PS IP is present; you do not need a manual `create_clock` for `pl_clk0` itself.
- **Generated clocks**: If you instantiate a Clocking Wizard (MMCM/PLL) downstream, use `create_generated_clock` to describe the output. The Clocking Wizard IP auto-generates these constraints in its output XDC file—do not duplicate them.
- **set_input_delay / set_output_delay**: These constrain external I/O timing relative to a clock. Positive values mean data arrives after the clock edge; negative values mean before. For internal PS↔PL paths through the AXI interconnect, these are not needed—AMD tools handle that path natively.
- **Asynchronous clock groups**: If your design has multiple unrelated clock domains, use `set_clock_groups -asynchronous` to suppress false cross-domain timing paths. Omitting this causes Vivado to flag false timing violations.
- **KV260 starter kit XDC**: AMD community resources note there is no official KV260 board-level XDC shipped with Vivado; constraints for user I/O must be derived from the K26 SOM XDC file available in the Kria board files package.

### Code Example

```xdc
# pl_clk0 is auto-constrained by the PS IP -- no create_clock needed here

# If using an external oscillator on a carrier card expansion header:
create_clock -period 10.000 -name ext_clk [get_ports ext_clk_p]

# Generated clock from Clocking Wizard output (if not using the wizard's own XDC):
create_generated_clock -name clk_200mhz \
  -source [get_pins clk_wiz_0/clk_in1] \
  -multiply_by 2 \
  [get_pins clk_wiz_0/clk_out1]

# Isolate async clock domains to suppress false paths:
set_clock_groups -asynchronous \
  -group [get_clocks pl_clk0] \
  -group [get_clocks clk_200mhz]

# False path on async reset (common for PL resets driven from PS GPIO):
set_false_path -from [get_ports pl_resetn0]
```

### Relevance to Your Project

Your KV260 AXI-BRAM design runs entirely in the PS-clock domain (`pl_clk0 = 100 MHz`). You likely need no custom timing constraints for the current design. If you add user I/O pins or a second clock domain later, the snippets above show the correct starting point. Avoid placing `create_clock` on `pl_clk0`—it already exists and duplicating it causes a constraint conflict warning.

## Kria KV260 / K26 SoM

### Key Findings

- **Boot mode pins on SOM connector**: The K26 SOM exposes `MODE[3:0]` to the carrier card. KV260 ships with QSPI32 boot mode set by default. For bare-metal development, switch to JTAG boot to avoid dealing with FSBL/QSPI programming during early bring-up.
- **JTAG bare-metal flow**: Load four artefacts in order via XSDB: `pmufw.elf` → `fsbl.elf` → `.bit` (PL bitstream) → application `.elf`. Skipping `pmufw.elf` causes the PS peripherals (including UART) to stay unconfigured.
- **eMMC on K26**: The K26 SOM has 4 GB eMMC soldered on. If you later move to SD/QSPI boot, be aware the eMMC and SD card share the same MIO bank—they cannot be used simultaneously.
- **Power domains**: K26 has separate PL and PS power rails. On the KV260 carrier, the PL rail (`VCCINT`, `VCCAUX`) must be stable before loading a bitstream. The onboard power sequencer handles this automatically, but custom carrier designs must respect the power-up ordering in the K26 datasheet.
- **Fan control via EMIO**: Starting with 2022.1 Kria Linux images, the default bitstream maps an EMIO GPIO to the KV260 carrier card fan control pin. In bare-metal designs without this mapping, the fan won't spin from software—wire it in your `kv260_top.vhd` or tie the fan enable pin high in XDC.
- **Vivado board files**: K26 board files are available in the Vivado board store. With them installed, the "Board" view in IP Integrator shows pre-configured presets for UART, USB, EMIO, and other peripherals—saving significant manual PS configuration work.

### Code Example

```tcl
# XSDB script for JTAG bare-metal boot on KV260
# Run from: xsdb -eval "source jtag_boot.tcl"

connect
targets -set -filter {name =~ "PSU"}
mwr 0xff5e0200 0x0100
rst

targets -set -filter {name =~ "MicroBlaze PMU"}
dow pmufw.elf
con

targets -set -filter {name =~ "PS8 #0" || name =~ "Cortex-A53 #0"}
rst -processor
dow fsbl.elf
con
after 3000

# Program PL bitstream
fpga kv260_top.bit

# Load and run application
dow hello_bram.elf
con
```

### Relevance to Your Project

This XSDB script is the missing piece for your bare-metal bring-up flow. The current repo doesn't appear to include an XSDB launch script; adding one alongside `create_bd.tcl` would make the project fully scriptable from hardware-design to running application.

## AMD/Xilinx Tool Updates (2025.1 / 2026.1)

### Key Findings

- **Vivado 2025.1 highlights**:
  - New RTL-based **AXI Switch IP**: fully customizable interconnect bridge between mixed AXI interface types and widths—more flexible than legacy AXI Interconnect.
  - New **Pblock Planner**: unified UI for floorplanning, replacing scattered constraint dialogs.
  - **PS-first boot flow**: ability to boot the PS independently and load PL bitstream dynamically at runtime—enables faster OS bring-up and deferred PL programming.
  - Dedicated "Clocking and Reset" and "Interrupt and AXI-4 Lite" views in IP Integrator.
  - Calibrated skew compensation for Versal SSIT devices.
- **Vitis HLS 2025.1**:
  - New Timeline Trace Viewer shows post-simulation runtime profiles.
  - New "Overview" graph shows all functions/loops with simulation data.
- **Vitis Libraries 2025.1**:
  - VEK280 AIE-ML support with 20 new L1 APIs and 6 new L2 APIs.
- **Vitis 2026.1** (current release): release notes and new features documented in UG1742—check AMD docs portal for the latest known issues before upgrading production workflows.
- **Known issue (Vitis 2025.1)**: On RHEL 8.3 and CentOS 8.2, GUI projects may fail due to a lib conflict in `LD_LIBRARY_PATH`. Workaround: remove `${env_var:LD_LIBRARY_PATH}` from the project environment settings.

### Code Example

```tcl
# Vivado 2025.1: instantiate new AXI Switch IP in a block design
# (replaces older AXI Interconnect for mixed-width designs)
create_bd_cell -type ip -vlnv xilinx.com:ip:axi_switch:1.0 axi_switch_0

# Configure for 1 master, 2 slaves (e.g. BRAM0 and BRAM2)
set_property -dict [list \
  CONFIG.NUM_MI {2} \
  CONFIG.NUM_SI {1} \
] [get_bd_cells axi_switch_0]

# Connect PS AXI master to switch input
connect_bd_intf_net \
  [get_bd_intf_pins zynq_ultra_ps_e_0/M_AXI_HPM0_FPD] \
  [get_bd_intf_pins axi_switch_0/S00_AXI]

# Connect switch outputs to BRAM controllers
connect_bd_intf_net \
  [get_bd_intf_pins axi_switch_0/M00_AXI] \
  [get_bd_intf_pins axi_bram_ctrl_0/S_AXI]
connect_bd_intf_net \
  [get_bd_intf_pins axi_switch_0/M01_AXI] \
  [get_bd_intf_pins axi_bram_ctrl_1/S_AXI]
```

### Relevance to Your Project

You're already on Vivado/Vitis 2025.1. The PS-first boot feature is directly relevant—you could configure the PS to boot and print a startup banner before the PL bitstream is loaded, improving debug visibility. The new AXI Switch IP is worth evaluating if you add a third BRAM or another AXI peripheral, as it avoids the configuration complexity of chaining AXI Interconnect blocks.
