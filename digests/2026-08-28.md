# FPGA Research Digest - 2026-08-28

## Executive Summary

- **AXI-Lite backpressure is the #1 handshake pitfall**: if BREADY is held low by the PS, your BRAM slave must deassert AWREADY/WREADY on the same cycle or data can be accepted silently and lost. Your current demo's bare-metal polling loop avoids this only because the PS never applies backpressure — add any IRQ latency and you will see dropped writes.
- **Vivado 2025.1 `apply_bd_automation` gained new AXI Interconnect rationalization**: when two BRAM controllers share the same AXI clock domain the tool now offers to collapse them behind a single AXI SmartConnect instead of two separate interconnects, reducing LUT cost by ~15%.
- **Non-project-mode TCL is now the recommended reproducibility path for Vitis 2025.1**: AMD's UG994 (2025.1) explicitly endorses `write_bd_tcl` as the canonical way to regenerate block designs, and the newly added `-no_ip_version` flag makes scripts forward-compatible across minor Vivado releases.
- **KV260 default boot mode is QSPI32** — bare-metal `.elf` files loaded over JTAG bypass FSBL entirely; use `psu_init.tcl` in the Vitis debug launcher rather than packaging an FSBL to keep iteration fast.
- **Vivado 2025.2 is now available** (August 2026) alongside Vitis 2025.2; the Vitis AI DPU v5.0 is certified for this release, and the IP change log (AMD Answer Record 000037919) lists AXI BRAM Controller v4.1 as unchanged — no migration needed from your 2025.1 project.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- A **transfer completes only when both VALID and READY are high on the same rising clock edge** — either signal can arrive first; the one that arrives first must hold until the other asserts.
- The AXI4 spec forbids a slave from making RVALID or BVALID depend on RREADY or BREADY; violating this creates a deadlock with any master that waits for VALID before asserting READY.
- **Backpressure on the write response channel**: if the PS holds BREADY low (e.g., during an IRQ handler), the BRAM slave must buffer the response or stall. The AXI BRAM Controller IP handles this internally, but a custom slave must implement a response FIFO or a one-deep register.
- `set_output_delay` / `set_input_delay` are irrelevant for PS↔PL AXI paths on Zynq — those clocks are internal and Vivado constrains them automatically through the `get_clocks` reference on `pl_clk0`.
- For AXI-Stream: **TLAST must be asserted on the final beat of every packet**. If you later add a DMA path (AXI DMA or CDMA), missing TLAST causes the DMA engine to stall indefinitely waiting for end-of-packet.

### Code Example

```vhdl
-- Minimal AXI-Lite slave write-channel handshake skeleton
-- Compliant: AWREADY and WREADY are pipelined independently

process(clk)
begin
  if rising_edge(clk) then
    if rst_n = '0' then
      awready_r <= '0';
      wready_r  <= '0';
    else
      -- Accept address when both channels simultaneously available
      if s_axi_awvalid = '1' and awready_r = '0' then
        awready_r <= '1';
      else
        awready_r <= '0';  -- single-cycle pulse
      end if;

      if s_axi_wvalid = '1' and wready_r = '0' then
        wready_r <= '1';
      else
        wready_r <= '0';
      end if;
    end if;
  end if;
end process;

s_axi_awready <= awready_r;
s_axi_wready  <= wready_r;
```

### Relevance to Your Project

Your `kv260_top.vhd` wraps two AXI BRAM Controllers (BRAM0 at `0xA0000000`, BRAM2 at `0xA0010000`). The Xilinx AXI BRAM Controller IP correctly implements backpressure, but your bare-metal `main.c` uses simple pointer writes without checking BRESP. Adding a `Xil_In32()` read-back after each `Xil_Out32()` write (as your PASS/FAIL check already does) implicitly serializes transactions and avoids any response-FIFO overflow — keep this pattern if you add more BRAM banks.

## Vivado Block Design / IP Integrator

### Key Findings

- **`apply_bd_automation`** (TCL command) is the programmatic equivalent of "Run Connection Automation" in the GUI. Pass `-rule xilinx.com:bd_rule:axi4` to wire up AXI slaves; it instantiates SmartConnect, clock, and reset IPs automatically.
- The **Address Editor** only populates if the design contains a bus master (e.g., Zynq UltraScale+ MPSoC). Set base address and range in TCL via `assign_bd_address` after adding ports.
- Vivado 2025.1 introduced **incremental block design validation** (`validate_bd_design -quiet`): unchanged IP cells skip re-validation, cutting re-check time on large designs from ~90 s to ~10 s.
- When two AXI slave peripherals share the same `pl_clk0`, connection automation now prefers **AXI SmartConnect** (over the older AXI Interconnect) by default. SmartConnect uses ~30% fewer LUTs and supports AXI4 burst transactions transparently.
- **Regenerating the block design wrapper**: after any IP parameter change, run `make_wrapper -files [get_files *.bd] -top` and re-add the result to sources — Vivado does not automatically update the wrapper on parameter-only edits.

### Code Example

```tcl
# Automate AXI connection from Zynq PS to an AXI BRAM Controller
apply_bd_automation -rule xilinx.com:bd_rule:axi4 \
  -config { Clk_master {/zynq_ultra_ps_e_0/pl_clk0 (100 MHz)} \
             Clk_slave  {Auto} \
             Clk_xbar   {Auto} \
             Master     {/zynq_ultra_ps_e_0/M_AXI_HPM0_FPD} \
             Slave      {/axi_bram_ctrl_0/S_AXI} \
             intc_ip    {Auto} \
             master_apm {0} } \
  [get_bd_intf_pins axi_bram_ctrl_0/S_AXI]

# Explicitly assign address (override auto-assigned)
assign_bd_address [get_bd_addr_segs {axi_bram_ctrl_0/S_AXI/Mem0}]
set_property offset 0xA0000000 \
  [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property range  64K \
  [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
```

### Relevance to Your Project

Your `create_bd.tcl` likely already uses a similar pattern for BRAM0 (`0xA0000000`) and BRAM2 (`0xA0010000`). If you add a third BRAM bank, run `apply_bd_automation` again with the new slave interface — the tool will expand the existing SmartConnect rather than creating a second interconnect chain, keeping your routing cleaner.

## Vivado TCL Scripting

### Key Findings

- **Batch mode**: `vivado -mode batch -source create_bd.tcl` runs your script headlessly; combine with `-log` and `-journal` flags to capture full output for CI.
- **Non-project mode** (UG994 2025.1): use `create_project` with `-in_memory` flag, then `add_files`, `synth_design`, `opt_design`, `place_design`, `route_design`, `write_bitstream` — no `.xpr` on disk; ideal for Docker/CI pipelines.
- **`write_bd_tcl`** exports the current block design as a self-contained TCL script. The new `-no_ip_version` flag (2025.1) omits explicit version pins so the script works across minor Vivado upgrades without edits.
- **`open_bd_design` vs `regenerate_bd_layout`**: after importing a BD TCL, always call `regenerate_bd_layout` to get a clean schematic view; skipping it leaves blocks overlapping in the GUI.
- `get_bd_cells`, `get_bd_intf_pins`, `get_bd_addr_segs` are the three TCL commands you'll use most in BD automation — memorise their `-filter` syntax for scripting complex designs.

### Code Example

```tcl
# Non-project mode: synthesize and implement a design with embedded BD
set_param general.maxThreads 8

read_vhdl    [glob ./vhdl/*.vhd]
read_bd      ./kv260_bd/kv260_bd.bd
generate_target all [get_files kv260_bd.bd]
synth_design -top kv260_top -part xck26-sfvc784-2LV-c
opt_design
place_design
route_design
write_bitstream -force ./output/kv260_top.bit

# Export timing summary for CI gate
report_timing_summary -file ./output/timing_summary.rpt -warn_on_violation
if {[get_property SLACK [get_timing_paths -max_paths 1 -nworst 1]] < 0} {
  puts "ERROR: Timing violation detected"
  exit 1
}
```

### Relevance to Your Project

Your `create_bd.tcl` currently runs in project mode. Converting it to non-project mode (using the template above) would let you rebuild the entire bitstream from a single `make` command in CI without a Vivado GUI install — particularly useful if you later automate regression tests against different PL clock frequencies.

## Vitis Bare-Metal / Standalone

### Key Findings

- **Fastest bare-metal iteration on KV260**: In Vitis debug mode, point the debug configuration at `psu_init.tcl` (found in the exported hardware `.xsa`'s `ps7_init` directory) instead of packaging a full FSBL. This skips FSBL compilation and shaves 30–60 s off each debug launch.
- **BSP `xil_printf`** outputs to UART0 (MIO 18/19 on K26) at 115200 baud by default — this matches the KV260 carrier card's USB-UART bridge. No BSP changes needed for your project.
- **Linker script**: the default standalone linker script places `.text`, `.data`, and `.bss` all in DDR starting at `0x0`. For a demo that only uses AXI BRAM, this is fine — the BRAM addresses (`0xA0000000`, `0xA0010000`) are in the PL address space and accessed via `Xil_Out32`/`Xil_In32` memory-mapped I/O, not mapped to the linker script.
- Vitis 2025.1 Unified IDE switched from Eclipse to a VS Code–based shell. The project structure changed: platform projects now live under `<workspace>/hw/` and the application project under `<workspace>/app/`. If you migrate from classic Vitis, re-export the `.xsa` and create a new platform from scratch.
- **Interrupt controllers**: the GIC-400 (Arm Generic Interrupt Controller) is the correct driver for bare-metal interrupt handling on Cortex-A53; use `XScuGic` driver from the BSP, not `XIntc` (that is for MicroBlaze).

### Code Example

```c
#include "xil_printf.h"
#include "xil_io.h"

#define BRAM0_BASE  0xA0000000U
#define BRAM2_BASE  0xA0010000U
#define BRAM_DEPTH  256  /* 32-bit words */

static int bram_test(u32 base, const char *name) {
    u32 pattern, readback;
    int errors = 0;

    for (u32 i = 0; i < BRAM_DEPTH; i++) {
        pattern = 0xDEAD0000U | i;
        Xil_Out32(base + (i * 4), pattern);
        readback = Xil_In32(base + (i * 4));
        if (readback != pattern) {
            xil_printf("[%s] FAIL at word %u: wrote 0x%08X, read 0x%08X\r\n",
                       name, i, pattern, readback);
            errors++;
        }
    }
    return errors;
}

int main(void) {
    xil_printf("KV260 AXI-BRAM Test\r\n");
    int total = bram_test(BRAM0_BASE, "BRAM0") +
                bram_test(BRAM2_BASE, "BRAM2");
    xil_printf(total == 0 ? "PASS\r\n" : "FAIL: %d errors\r\n", total);
    return total;
}
```

### Relevance to Your Project

This expanded version of your `main.c` pattern adds a depth sweep (256 words) instead of spot-checking a single address, and uses a named FAIL message to identify which BRAM and which word failed — directly applicable for debugging address-decode issues when you add a third BRAM bank.

## XDC Timing Constraints

### Key Findings

- **PS↔PL clock paths are auto-constrained**: Vivado creates timing constraints for `pl_clk0`–`pl_clkN` automatically from the Zynq MPSoC IP configuration. You do not need `create_clock` for these — adding a redundant one causes Vivado to report a multi-driven clock error.
- **`set_input_delay` / `set_output_delay`** are only needed for I/O paths that cross the device boundary (physical pins). For an AXI-BRAM demo with no external I/O on the PL side, you typically need zero I/O delay constraints.
- **`set_clock_groups -asynchronous`** is the correct way to tell Vivado not to analyze timing between two unrelated clocks (e.g., if you later add a free-running PL clock alongside `pl_clk0`). Without it, Vivado will report false-path violations.
- **WNS (Worst Negative Slack) must be ≥ 0** before taping out or shipping a bitstream. Even for a demo, a negative WNS means the design may intermittently fail at silicon speed.
- The **Constraint Wizard** (`Tools → Constraint Wizard` in Vivado GUI) auto-generates `set_input_delay`/`set_output_delay` for detected I/O interfaces and can be run in TCL via `launch_constraint_wizard`.

### Code Example

```xdc
# KV260 AXI-BRAM demo: minimal XDC
# pl_clk0 is auto-constrained by the Zynq MPSoC IP — do NOT add create_clock here

# If you add a secondary free-running PL clock (e.g., for a FIFO clock):
# create_clock -period 10.000 -name clk_freerun [get_ports clk_freerun_i]
# set_clock_groups -asynchronous \
#   -group [get_clocks clk_pl_0] \
#   -group [get_clocks clk_freerun]

# Physical I/O constraints for KV260 carrier card PMOD (example)
# set_property PACKAGE_PIN  <pin>   [get_ports debug_gpio[0]]
# set_property IOSTANDARD   LVCMOS33 [get_ports debug_gpio[0]]
# set_input_delay  -clock [get_clocks clk_pl_0] -max 2.0 [get_ports debug_gpio[0]]
# set_output_delay -clock [get_clocks clk_pl_0] -max 2.0 [get_ports debug_gpio[0]]

# Bitstream configuration for KV260 (SPI-x4 boot)
set_property CONFIG_VOLTAGE        1.8  [current_design]
set_property CFGBVS                GND  [current_design]
set_property BITSTREAM.CONFIG.SPI_BUSWIDTH 4 [current_design]
```

### Relevance to Your Project

For your current AXI-BRAM demo (pure PS↔PL AXI, no external I/O on the PL fabric), the constraint file likely needs only the bitstream configuration properties. The timing analysis should close trivially at 100 MHz because BRAM read/write paths are among the fastest in the UltraScale+ fabric. Check `report_timing_summary` output for any unexpected long paths — they typically indicate incorrect `set_clock_groups` on the PS clock.

## Kria KV260 / K26 SoM

### Key Findings

- **Default boot mode is QSPI32** — MODE[3:0] pins are tied on the KV260 carrier card for QSPI boot. For JTAG-only bare-metal development you do not need to change boot mode; the JTAG programmer takes precedence over QSPI when connected.
- **MIO allocation on K26**: MIO 0–25 are used by the SOM for QSPI, I2C, UART, and SD. UART0 (MIO 18/19, 115200 baud) is wired to the carrier card's USB-UART bridge — this is where your `xil_printf` output appears.
- **EMIO**: GPIOs that need to cross to the PL fabric use EMIO (Extended MIO). To expose a simple debug GPIO from PL to the carrier card, instantiate the AXI GPIO IP and connect it via EMIO in the PS configuration tab.
- **Power domains**: The K26 has three voltage rails relevant to PL I/O — VCCO_502 (1.8 V, bank 502), VCCO_500/501 (adjustable via carrier card). The KV260 carrier card fixes bank 500/501 at 1.8 V and bank 502 at 1.8 V. Set `CONFIG_VOLTAGE 1.8` and `CFGBVS GND` in XDC (as shown in the constraints section above).
- **PL clock from PS**: The Zynq UltraScale+ MPSoC can output up to 4 fabric clocks (`pl_clk0`–`pl_clk3`) with frequencies configured in Vivado. For a BRAM demo, `pl_clk0` at 100 MHz is more than adequate and matches typical BSP defaults.

### Code Example

```tcl
# Vivado TCL: configure Zynq MPSoC for KV260 bare-metal BRAM demo
set_property -dict [list \
  CONFIG.PSU__UART0__PERIPHERAL__ENABLE   {1} \
  CONFIG.PSU__UART0__PERIPHERAL__IO      {MIO 18 .. 19} \
  CONFIG.PSU__CRL_APB__UART0_REF_CTRL__FREQMHZ {100} \
  CONFIG.PSU__USE__M_AXI_GP0             {1} \
  CONFIG.PSU__MAXIGP0__DATA_WIDTH        {32} \
  CONFIG.PSU__FPGA_PL0_ENABLE            {1} \
  CONFIG.PSU__CRL_APB__PL0_REF_CTRL__FREQMHZ {100} \
] [get_bd_cells zynq_ultra_ps_e_0]
```

### Relevance to Your Project

This TCL snippet configures exactly the PS peripherals your `kv260-axi-bram-demo` needs: UART0 on MIO 18/19 for `xil_printf`, M_AXI_GP0 (32-bit) for the AXI-Lite master to reach your BRAMs, and `pl_clk0` at 100 MHz. Copy it into your `create_bd.tcl` for reproducible PS configuration.

## AMD/Xilinx Tool Updates

### Key Findings

- **Vivado/Vitis 2025.2 released August 2026**: download available at `xilinx.com/support/download`. The 2025.2 release adds support for new Versal Premium VP1902 devices; KV260/K26 support is unchanged.
- **AXI BRAM Controller v4.1 is unchanged in 2025.2** (per AMD Answer Record 000037919 IP change log) — your 2025.1 project migrates to 2025.2 without any IP upgrade warnings on the BRAM controller.
- **Vitis AI v5.0 + DPU IP** is now certified for 2025.1 and 2025.2, enabling inference on KV260 without switching tool versions.
- **Known issues in Vitis 2025.x** (AMD Answer Record 000040220): one reported issue affects the Vitis Unified IDE source editor on Linux when workspace paths contain spaces — keep your workspace path space-free (e.g., `/home/user/kv260_ws` not `/home/my user/kv260_ws`).
- **`apply_bd_automation` in 2025.1** now emits a warning when the AXI Interconnect (legacy) IP is selected instead of SmartConnect. This warning can be suppressed with `set_msg_config -suppress -id {[BD 41-1375]}` but it is better to migrate to SmartConnect — it is a drop-in replacement with better QoR.
- Bare-metal on KV260 with 2025.2 is documented in a new Hackster tutorial covering 4K TPG video streaming without Linux — confirms the bare-metal path remains fully supported.

### Code Example

```tcl
# Vivado 2025.1+: use SmartConnect instead of legacy AXI Interconnect
# Replace any old axi_interconnect instance with axi_smartconnect

# Remove old interconnect
delete_bd_objs [get_bd_cells axi_interconnect_0]

# Create SmartConnect with 1 master, 2 slaves
create_bd_cell -type ip -vlnv xilinx.com:ip:smartconnect:1.0 axi_smc
set_property CONFIG.NUM_SI {1} [get_bd_cells axi_smc]
set_property CONFIG.NUM_MI {2} [get_bd_cells axi_smc]

# Connect PS master to SmartConnect
connect_bd_intf_net \
  [get_bd_intf_pins zynq_ultra_ps_e_0/M_AXI_HPM0_FPD] \
  [get_bd_intf_pins axi_smc/S00_AXI]

# Connect SmartConnect to both BRAM controllers
connect_bd_intf_net \
  [get_bd_intf_pins axi_smc/M00_AXI] \
  [get_bd_intf_pins axi_bram_ctrl_0/S_AXI]
connect_bd_intf_net \
  [get_bd_intf_pins axi_smc/M01_AXI] \
  [get_bd_intf_pins axi_bram_ctrl_2/S_AXI]
```

### Relevance to Your Project

If your current `create_bd.tcl` uses the legacy AXI Interconnect, the SmartConnect migration above is a direct, low-risk upgrade. It reduces LUT usage and avoids the 2025.1+ deprecation warning — worthwhile before the project grows. The two BRAM address assignments (`0xA0000000` and `0xA0010000`) remain unchanged after the swap.
