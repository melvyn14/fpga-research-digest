# FPGA Research Digest - 2026-07-08

## Executive Summary
- **AXI-Lite BRESP/RRESP error checking is unimplemented in most bare-metal demos**: your `main.c` should read back the response channel after every write to catch DECERR (address decode failure) vs SLVERR (slave error), which can silently mask mis-addressed transactions to BRAM0/BRAM2.
- **Vivado 2025.1 introduces a new fully-customisable RTL-based AXI Switch IP** and dedicated "Clocking and Reset" / "Interrupt and AXI4-Lite" views in IP Integrator — review these views in your block design to catch any undriven clock/reset pins on the BRAM controllers.
- **xil_printf does not perform `\r\n` expansion** — `\n` alone moves the cursor down without a carriage return on most terminal emulators; use `\r\n` in your PASS/FAIL prints to avoid staircase output on the KV260 UART.
- **Non-project TCL batch mode** (`vivado -mode batch -source build.tcl`) is the cleanest way to make your `create_bd.tcl` fully reproducible: add `synth_design`, `place_design`, `route_design`, and `write_bitstream` after the BD creation to get a single-command end-to-end build.
- **KV260 JTAG boot via XSDB** writes the bitstream, PMU firmware, FSBL, and application ELF to Cortex-A53 core 0 in sequence — ideal for iterating on the AXI-BRAM read/write loop without touching the SD card.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings
- AXI-Lite uses five channels: Write Address (AW), Write Data (W), Write Response (B), Read Address (AR), and Read Data (R). All channels share the same VALID/READY handshake; signals driven by an initiator must not change once VALID is asserted until the corresponding READY is received.
- **BRESP/RRESP codes**: `2'b00` = OKAY, `2'b01` = EXOKAY (exclusive), `2'b10` = SLVERR (slave error), `2'b11` = DECERR (decode error, address not mapped). Most bare-metal drivers ignore these — silent DECERR means your write silently did nothing.
- The AXI4 spec requires **both** the Write Address and Write Data channels to complete their handshake before the slave can assert BVALID on the B channel. Out-of-order arrival is legal; the slave must handle whichever comes first.
- AXI-Lite is capable of 100% bus utilisation, but many naive slave implementations only achieve 50% because they wait for a response handshake to complete before accepting the next address — the ZipCPU `easyaxil` pattern with skidbuffers fixes this.
- The Xilinx AXI Interconnect coalesces multiple B-channel responses under downsizing/upsizing and sets the aggregate BRESP to the **worst-case** error seen: DECERR > SLVERR > OKAY.

### Code Example
```c
/* Bare-metal AXI-Lite write with BRESP check via Xil_In32 polling */
#include "xil_io.h"
#include "xil_printf.h"

#define BRAM0_BASE  0xA0000000UL
#define AXI_OKAY    0x0

/* Xil_Out32 performs a 32-bit memory-mapped write; the AXI BRAM controller
   generates BVALID after completing the write. Poll by reading back. */
static inline int axi_write_verify(uintptr_t addr, u32 data) {
    Xil_Out32(addr, data);
    u32 readback = Xil_In32(addr);
    /* BRAM is synchronous-read; a mismatch indicates wiring or decode error */
    return (readback == data) ? 0 : -1;
}

int main(void) {
    if (axi_write_verify(BRAM0_BASE + 0x00, 0xDEADBEEF) != 0) {
        xil_printf("FAIL: BRAM0 write/read mismatch\r\n");
        return 1;
    }
    xil_printf("PASS: BRAM0 0xDEADBEEF round-trip OK\r\n");
    return 0;
}
```

### Relevance to Your Project
Your `main.c` writes patterns to `0xA0000000` (BRAM0) and `0xA0010000` (BRAM2) then reads back for PASS/FAIL. Adding `BRESP` checking by comparing write vs readback — as shown above — will definitively distinguish a mis-mapped address (DECERR, readback returns 0 or garbage) from a real write success, making the PASS/FAIL verdict more trustworthy.

## Vivado Block Design / IP Integrator

### Key Findings
- **New in Vivado 2025.1**: Dedicated "Clocking and Reset" and "Interrupt and AXI4-Lite" views in the IP Integrator canvas surface unconnected clock/reset nets that previously required manual inspection.
- `apply_bd_automation` is convenient but can introduce surprise clock buffers or address overlaps. For a minimal demo, prefer explicit `connect_bd_net` and `connect_bd_intf_net` calls — they make every connection auditable in the TCL log.
- **Address Editor**: `assign_bd_address` auto-assigns slave segment offsets; follow with `set_property range` and `set_property offset` to pin your BRAM controllers to exactly `0xA0000000` and `0xA0010000`. Never rely on the auto-assigned values without verifying in the Address Editor tab.
- After editing any IP property, always run `validate_bd_design` before `save_bd_design` — it catches unresolved interfaces and clock-domain mismatches before synthesis.
- Block design export via **File → Export → Export Block Design** (or `write_bd_tcl`) produces a self-contained TCL that recreates the entire IPI canvas — this is the canonical way to version-control a block design.

### Code Example
```tcl
# Explicitly pin AXI BRAM controller addresses after auto-assign
assign_bd_address

# BRAM0 at 0xA000_0000, 64 KB
set seg0 [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property offset 0xA0000000 $seg0
set_property range  0x00010000 $seg0

# BRAM2 at 0xA001_0000, 64 KB
set seg1 [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_1_Mem0}]
set_property offset 0xA0010000 $seg1
set_property range  0x00010000 $seg1

validate_bd_design
save_bd_design
```

### Relevance to Your Project
Your `create_bd.tcl` almost certainly calls `assign_bd_address` — the snippet above adds the explicit `set_property` calls that lock BRAM0 and BRAM2 to exactly the addresses your `main.c` uses (`0xA0000000`, `0xA0010000`). Without these, a tool upgrade or IP refresh can silently re-assign addresses and produce a FAIL that looks like a hardware bug.

## Vivado TCL Scripting

### Key Findings
- **Non-project mode** (`vivado -mode batch -source build.tcl`) runs entirely in-memory with no `.xpr` file. Faster for CI/CD, but you must save design checkpoints (`write_checkpoint`) manually at each stage since there is no automatic state persistence.
- The standard non-project flow: `read_vhdl` → `read_xdc` → `synth_design -top <top> -part <part>` → `opt_design` → `place_design` → `route_design` → `write_bitstream`.
- `write_bd_tcl` / **Export Block Design** exports the IPI canvas as a standalone TCL; combining this with a wrapper non-project script gives a fully reproducible build from a clean git checkout.
- Useful diagnostic: `report_timing_summary -file timing.rpt` and `report_utilization -file util.rpt` should be called after `route_design` in any batch script to catch timing failures before committing a bitstream.
- Batch mode exits Vivado automatically when the script finishes (or on the first TCL error), making it safe for CI pipelines — error exit code propagates to the shell.

### Code Example
```tcl
# Minimal non-project batch build for KV260 AXI-BRAM demo
# Usage: vivado -mode batch -source build.tcl

set part "xck26-sfvc784-2LV-c"
set top  "kv260_top"

# Source the block design TCL to recreate the IPI canvas in memory
source tcl/create_bd.tcl
make_wrapper -files [get_files kv260.bd] -top
read_vhdl vhdl/kv260_top.vhd
read_xdc  constraints/kv260.xdc

synth_design  -top $top -part $part
write_checkpoint -force output/post_synth.dcp
opt_design
place_design
route_design
write_checkpoint -force output/post_route.dcp
report_timing_summary  -file output/timing.rpt
report_utilization     -file output/util.rpt
write_bitstream -force output/$top.bit

puts "Build complete: output/$top.bit"
```

### Relevance to Your Project
Your repo has `tcl/create_bd.tcl` but likely relies on the Vivado GUI to run synthesis and implementation. Wrapping it in the batch script above makes the full KV260 build reproducible from a single command, enabling GitHub Actions CI for the AXI-BRAM demo.

## Vitis Bare-Metal / Standalone

### Key Findings
- **`xil_printf` does not expand `\n` to `\r\n`**: on most USB-UART terminal emulators connected to the KV260 UART0, `\n` alone causes a line-down without carriage return (staircase output). Always use `\r\n` in bare-metal PASS/FAIL prints.
- **`xil_printf` has no floating-point support** and no format-string buffer — it directly outputs characters. For any complex formatting use `snprintf` + `print` (or enable the full `printf` in BSP settings, which increases code size).
- **BSP heap/stack**: the default linker script for Cortex-A53 standalone allocates a modest heap and stack. If you add large arrays or deep recursion, edit `lscript.ld`: increase `_STACK_SIZE` and `_HEAP_SIZE` under the `ps_ddr_0` region.
- **Cache coherency**: The Cortex-A53 L1/L2 caches are enabled by the standalone BSP startup code. AXI-mapped peripherals (BRAM controllers) are in the **device** memory region and bypass the cache, so `Xil_Out32`/`Xil_In32` go directly to the AXI fabric — no explicit cache flush needed for MMIO reads/writes.
- **Vitis 2025.2** (successor to 2025.1): the SDT (System Device Tree) based flow is now the default; BSP configuration is done via YAML `linker_constraints` keys rather than GUI property pages.

### Code Example
```c
/* Robust UART output pattern for KV260 bare-metal */
#include "xil_printf.h"
#include "xil_io.h"

#define BRAM0_BASE 0xA0000000UL
#define BRAM2_BASE 0xA0010000UL

static const struct {
    uintptr_t base;
    const char *name;
} brams[] = {
    { BRAM0_BASE, "BRAM0" },
    { BRAM2_BASE, "BRAM2" },
};

int main(void) {
    static const u32 patterns[] = { 0xDEADBEEF, 0xCAFEBABE, 0xA5A5A5A5 };
    int fail = 0;

    for (int b = 0; b < 2; b++) {
        for (int p = 0; p < 3; p++) {
            u32 offset = p * 4;
            Xil_Out32(brams[b].base + offset, patterns[p]);
            u32 got = Xil_In32(brams[b].base + offset);
            if (got != patterns[p]) {
                xil_printf("%s[0x%02X]: FAIL expected 0x%08X got 0x%08X\r\n",
                           brams[b].name, offset, patterns[p], got);
                fail++;
            }
        }
    }
    xil_printf(fail ? "OVERALL: FAIL (%d errors)\r\n"
                    : "OVERALL: PASS\r\n", fail);
    return fail;
}
```

### Relevance to Your Project
The pattern above extends your existing PASS/FAIL loop to test multiple offsets within each BRAM and report the exact address and value on failure — much more useful than a single binary PASS/FAIL when chasing AXI address-decode or BRAM depth issues.

## XDC Timing Constraints

### Key Findings
- **KV260 PL clock must come from the PS**: the `pl_clk0` output of the Zynq UltraScale+ PS block is the primary fabric clock. In XDC, declare it with `create_clock -name pl_clk0 -period <ns> [get_ports pl_clk0]` only if it exits the PS as a port; in IPI designs it's usually an internal net and Vivado infers it automatically.
- **AXI-only designs with no external I/O** often need zero XDC constraints beyond the part/board file defaults — Vivado will auto-constrain the PS clock domains. The most common error is adding a redundant `create_clock` that conflicts with the PS-inferred constraint.
- `set_clock_groups -asynchronous` is needed when your design crosses between `pl_clk0` and any other clock (e.g., a free-running oscillator or a BUFG from an MMCM). For a single-clock AXI-BRAM design, this is not required.
- KV260 XDC constraint info: get the board-specific XDC from the Kria PYNQ repository (`Kria-PYNQ/kv260/base/vivado/constraints/base.xdc`) as a reference for pin assignments and I/O standards.
- AMD community note: for KV260 timing constraint files, the recommended approach is to derive constraints from the K26 SOM schematic and the SOM-provided `.xdc` rather than creating them from scratch.

### Code Example
```tcl
# kv260.xdc — minimal constraints for PS-only AXI-BRAM demo
# No external clock port — pl_clk0 is inferred from the PS IP

# If you DO bring pl_clk0 out to a top-level port:
# create_clock -name clk_pl_0 -period 10.000 [get_ports clk_pl_0]

# Prevent tools from trying to time paths across unrelated clock domains
# (only needed if a second clock source exists)
# set_clock_groups -name async_grp -asynchronous \
#     -group [get_clocks clk_pl_0] \
#     -group [get_clocks clk_external]

# I/O false paths for debug/status outputs (LED, GPIO)
# set_false_path -from [get_cells *] -to [get_ports led_o]

# Bitstream configuration for KV260
set_property BITSTREAM.CONFIG.OVERTEMPSHUTDOWN ENABLE [current_design]
set_property CONFIG_VOLTAGE 1.8 [current_design]
```

### Relevance to Your Project
A pure PS-PL AXI design like the KV260 AXI-BRAM demo typically needs almost no XDC beyond board-file defaults. The example above is the safe minimal baseline — it avoids the common mistake of double-defining the PS clock, which causes a "clock already defined" critical warning that can mask real timing issues.

## Kria KV260 / K26 SoM

### Key Findings
- **Boot modes**: KV260 supports JTAG, QSPI, and SD card boot. For bare-metal development, JTAG via XSDB is the fastest iteration loop — program the bitstream, download FSBL + PMU firmware + ELF, and start Cortex-A53 core 0 without touching the SD card.
- **JTAG boot sequence via XSDB**: (1) `fpga -file kv260_top.bit`, (2) `dow pmufw.elf`, (3) `dow fsbl.elf`, (4) `dow kv260.elf`, (5) `con`. The PMU firmware must be loaded before the FSBL or the PS will not complete initialization.
- **SD card boot mode switch**: Set `0xff5e0200 = 0xE100` via XSDB memory write then trigger system reset — or physically set the boot mode DIP switches on the KV260 carrier card.
- **PS MIO Bank 500** hosts I2C for SOM management; **Bank 501** has optional PMU input pins. PL I/O is exclusively via the expansion connector — no direct MIO to PL path.
- **Power domains**: The K26 SoM has separate power rails for PS, PL, and I/O banks. The carrier card (KV260 CC) provides all rails; a custom carrier must supply `VCC_PSPLL`, `VCC_PSBATT`, and the PL bank voltages per DS987.

### Code Example
```tcl
# XSDB script: program KV260 via JTAG and run bare-metal application
# Usage: xsdb boot_jtag.tcl

connect
target 1
# Program PL fabric
fpga -file output/kv260_top.bit

# Load PS firmware in correct order
target 9
dow pmufw.elf
target 8
rst -processor
dow fsbl/fsbl.elf
con
after 3000

# Load and run application on Cortex-A53 core 0
target 10
rst -processor
dow output/kv260.elf
con

puts "Application running — connect to UART for PASS/FAIL output"
```

### Relevance to Your Project
This XSDB script replaces the manual GUI workflow for every iteration of the AXI-BRAM write/read test. Once your bitstream and ELF are built, a single `xsdb boot_jtag.tcl` programs the KV260 and starts the Cortex-A53, letting you see the PASS/FAIL on the USB-UART within seconds.

## AMD/Xilinx Tool Updates (Vivado/Vitis 2025.x)

### Key Findings
- **Vivado 2025.1 headline features**:
  - New **RTL-based AXI Switch IP**: fully customisable bridge between AXI interface types/widths with an `ultra-low-area` mode via the `STRATEGY` parameter.
  - **PS-first boot**: the PS can now boot and load Linux before the PL bitstream is applied, enabling diverse boot sequences and faster OS bring-up.
  - **Pblock Planner**: new GUI for creating and visualising Pblocks (floorplanning).
  - Dedicated **"Clocking and Reset"** and **"Interrupt and AXI4-Lite"** views in IP Integrator — surfaces undriven clock/reset pins at design time.
  - Improved Directive/Subdirective support for QoR improvements in implementation.
- **Vitis 2025.1 / 2025.2**: SDT (System Device Tree) based flow is now the default for embedded software; BSP configuration moves from GUI property pages to YAML files. `xil_printf.h` header include paths changed in 2025.2 — a community report shows include errors on default projects; workaround is to verify BSP library paths in the platform component settings.
- **Download centre**: as of the digest date, AMD is distributing **Vivado/Vitis 2026.1** at the primary download URL. If you are pinned to 2025.1, use the archived download link directly.

### Code Example
```tcl
# Vivado 2025.1: create AXI Switch IP with ultra-low-area mode
# (New IP in 2025.1 — replaces AXI Interconnect in area-constrained designs)
create_bd_cell -type ip -vlnv xilinx.com:ip:axi_switch:1.0 axi_switch_0
set_property CONFIG.STRATEGY {ultra_low_area} [get_bd_cells axi_switch_0]
set_property CONFIG.NUM_SI {1} [get_bd_cells axi_switch_0]
set_property CONFIG.NUM_MI {2} [get_bd_cells axi_switch_0]

# Connect to Zynq PS HPM0 master
connect_bd_intf_net [get_bd_intf_pins zynq_ultra_ps_e_0/M_AXI_HPM0_FPD] \
                    [get_bd_intf_pins axi_switch_0/S00_AXI]

# Route to BRAM controllers
connect_bd_intf_net [get_bd_intf_pins axi_switch_0/M00_AXI] \
                    [get_bd_intf_pins axi_bram_ctrl_0/S_AXI]
connect_bd_intf_net [get_bd_intf_pins axi_switch_0/M01_AXI] \
                    [get_bd_intf_pins axi_bram_ctrl_1/S_AXI]
```

### Relevance to Your Project
If you upgrade from the AXI Interconnect to the new AXI Switch IP in 2025.1, the `ultra_low_area` strategy could save meaningful LUT resources in the KV260 PL — worthwhile as you add more AXI slaves beyond the two BRAM controllers. The new "Clocking and Reset" IPI view is immediately useful for verifying that both BRAM controllers share the same `pl_clk0` and `proc_sys_reset_0` net.
