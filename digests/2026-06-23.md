## Executive Summary
- **Kria SOMs lock the boot mode to QSPI by design** — the Kria boot flow forces booting from read-only QSPI boot firmware specifically to prevent bricking the SOM, which is a real gotcha for bare-metal-only workflows (no Linux/PetaLinux in the loop): JTAG boot is the supported path for iterative bare-metal development on the KV260, not QSPI reprogramming, until you're ready to deploy.
- **Xilinx's own reference AXI-Lite VHDL/Verilog slave template has a documented backpressure bug** (zipcpu.com formal-verification finding): it never checks `RVALID=1 && RREADY=0` before re-asserting `ARREADY`, so it can accept a new read request while a previous read response is still stuck waiting for `RREADY`, which can freeze the bus. Not a live risk here since both BRAM0/BRAM2 sit behind the stock `axi_bram_ctrl` IP (correctly implemented), but a sharp edge if any custom AXI-Lite register/status block is ever hand-rolled alongside the BRAM controllers.
- **The official Kria baremetal AXI-BRAM reference flow matches this project's shape almost exactly**: AXI BRAM Controller IP, `S_AXI` tied to `M_AXI_HPM0_FPD` via Connection Automation, single-BRAM-interface mode — confirming the project's architecture follows AMD's documented pattern rather than an unusual configuration.
- **Vivado's Address Editor enforces power-of-two alignment, not just non-overlap** — a range must have enough trailing zero bits to match its size (e.g., 64KB needs 16 trailing zero bits), directly relevant if BRAM0/BRAM2 address ranges or offsets are ever resized in `create_bd.tcl`.
- **No urgent toolchain pressure**: Vivado/Vitis 2025.1 IP-level fixes (AXI Ethernet PTP, dynamic addressing, peripheral/cache-AXI deadlock under frequency-optimized pipelines) don't touch `axi_bram_ctrl` or the Zynq UltraScale+ PS block, and a mid-2026 community guide confirms the 2025.x bare-metal KV260 workflow remains actively maintained.

## AXI Protocol / AXI-Lite / AXI-Stream
### Key Findings
- The core handshake rule: a slave's `xREADY` may be withheld arbitrarily, but it must be **registered**, with no combinatorial path from input VALID/payload to output READY on the same cycle — the spec text is "there must be no combinatorial paths between input and output signals" on master and slave AXI interfaces.
- Xilinx's reference AXI-Lite slave template (both VHDL and Verilog flavors, generated by the IP wizard) has a real, formally-verified bug: it doesn't check `S_AXI_RVALID='1' and S_AXI_RREADY='0'` before re-raising `ARREADY`, so under backpressure it can accept a second read request before the first response has actually been consumed, freezing the bus.
- High-performance AXI slave design recommendation from the spec and community guides: keep `ARREADY`/`AWREADY` high by default when not busy, rather than dropping them low and re-raising per-transaction — this avoids unnecessary stalls on every request.
- For AXI4-Stream specifically: `TVALID`, `TREADY`, and `TLAST` are the only mandatory control signals; `TKEEP`/`TSTRB`/`TUSER`/`TID`/`TDEST` are optional and IP-specific — useful if a future revision of this project ever streams data instead of just doing register-style AXI-Lite read/write.
- Testbenches that always drive `READY` high never exercise backpressure paths — the single most commonly missed verification case is a master holding `BREADY`/`RREADY` low and confirming the slave correctly stalls `AWREADY`/`WREADY` or `ARREADY` in response.

### Code Example
```vhdl
-- Registered ARREADY that correctly tracks in-flight read responses,
-- avoiding the documented Xilinx reference-design bug where a new
-- read request can be accepted while a prior RVALID is still stalled.
process(s_axi_aclk)
begin
  if rising_edge(s_axi_aclk) then
    if s_axi_aresetn = '0' then
      arready_r <= '1';
      rvalid_r  <= '0';
    else
      if s_axi_arvalid = '1' and arready_r = '1' then
        raddr_r   <= s_axi_araddr;
        arready_r <= '0';   -- do not accept another AR until this read drains
        rvalid_r  <= '1';
      elsif rvalid_r = '1' and s_axi_rready = '1' then
        rvalid_r  <= '0';
        arready_r <= '1';   -- only now safe to accept the next AR
      end if;
    end if;
  end if;
end process;

s_axi_arready <= arready_r;
s_axi_rvalid  <= rvalid_r;
```

### Relevance to Your Project
Both BRAM0 and BRAM2 sit behind the stock `axi_bram_ctrl` IP, which implements correct AXI4-Lite/AXI4 handshaking — the Xilinx reference-design bug above is specific to the hand-generated AXI-Lite *peripheral template* (used when creating a custom IP core), not to `axi_bram_ctrl`. It only becomes relevant the moment a custom AXI-Lite control/status register block is added alongside the BRAM controllers (e.g., a "go/done" flag or test-pattern selector) — review any such block against the registered-ARREADY pattern above before trusting it on hardware.

## Vivado Block Design / IP Integrator
### Key Findings
- Connection Automation auto-inserts supporting infrastructure (AXI Interconnect/SmartConnect, Processor System Reset) and wires it to the PS; convenient for prototyping but anything it silently adds has to be accounted for if `create_bd.tcl` is later maintained by hand instead of regenerated from a live GUI session.
- Address Editor alignment rule: an address range must be aligned such that its base address has enough trailing zero bits to match the range size (a 4K range needs 3 trailing hex zeros, i.e., 12 trailing zero bits) — `Vivado` will flag a misaligned offset as invalid rather than silently rounding it.
- `validate_bd_design` is the step that actually checks connectivity and parameter propagation (AXI4 vs AXI4-Lite link type, data-width negotiation, BRAM operating-mode propagation); `regenerate_bd_layout` only redraws the graphical layout with zero connectivity checking — running only the latter after an edit gives false confidence.
- Saving the block design periodically (Ctrl+S) during interactive GUI editing is recommended since IPI sessions can be lost on a crash with no auto-recovery as robust as the regular project save.

### Code Example
```tcl
# Non-interactive validate/regenerate/save sequence, safe to drop into
# a batch build right before generate_target / write_bitstream.
open_bd_design [get_files kv260_bd.bd]
validate_bd_design
regenerate_bd_layout
save_bd_design

if {[get_msg_config -count -severity "Critical Warning"] > 0 || \
    [get_msg_config -count -severity "Error"] > 0} {
    puts "ERROR: block design validation reported errors/critical warnings, aborting"
    exit 1
}
```

### Relevance to Your Project
A `create_bd.tcl` that wires the PS and both `axi_bram_ctrl` instances explicitly (rather than relying on GUI automation) is the right call for a script under version control that must reproduce the same BRAM0 (`0xA0000000`)/BRAM2 (`0xA0010000`) address map every build. If the design is ever edited interactively in the GUI, re-export with `write_bd_tcl -no_ip_version` rather than a raw project export, to keep the script diffable and IP-version-stable, and always re-run `validate_bd_design` (not just `regenerate_bd_layout`) before trusting a post-edit build.

## Vivado TCL Scripting
### Key Findings
- Non-Project Mode keeps the design entirely in memory with no `.xpr` written to disk — the script alone is responsible for source ordering, and there's no Vivado-managed "stale source" detection; every invocation re-reads sources from scratch unless checkpointing is scripted explicitly between stages.
- Standard non-project build sequence: `read_vhdl`/`read_verilog` → `read_xdc` → `synth_design -top <name> -part <part>` → `opt_design` → `place_design` → (optional `phys_opt_design`) → `route_design` → `write_bitstream`, with `write_checkpoint` calls between stages so a CI run can resume from the last good checkpoint instead of re-synthesizing from scratch.
- `vivado -mode batch -source script.tcl -tclargs <args>` is the standard headless CI invocation — it runs to completion and exits; `-mode tcl` instead drops into an interactive prompt, useful only during script development.
- A fully scripted build is the only way to guarantee a build server produces bit-identical output run-to-run — project settings, IP configuration, and constraints all live as text files in version control rather than inside a binary `.xpr`/IP-cache state that can drift between machines.

### Code Example
```tcl
# Build pattern for two AXI BRAM controllers with explicit, version-stable
# address assignment matching BRAM0/BRAM2 in this project.
create_bd_cell -type ip -vlnv xilinx.com:ip:axi_bram_ctrl:4.1 axi_bram_ctrl_0
create_bd_cell -type ip -vlnv xilinx.com:ip:axi_bram_ctrl:4.1 axi_bram_ctrl_2

foreach {ctrl base} {axi_bram_ctrl_0 0xA0000000 axi_bram_ctrl_2 0xA0010000} {
    connect_bd_intf_net [get_bd_intf_pins zynq_ultra_ps_e_0/M_AXI_HPM0_FPD] \
                         [get_bd_intf_pins ${ctrl}/S_AXI]
    set_property offset $base \
        [get_bd_addr_segs "zynq_ultra_ps_e_0/Data/SEG_${ctrl}_Mem0"]
}

validate_bd_design
save_bd_design
```

### Relevance to Your Project
This pattern is consistent with how `create_bd.tcl` reportedly builds the two-BRAM layout. If a third BRAM or an AXI-Lite control peripheral is added later, extending the `foreach` table above — rather than hand-copying another connect/offset block — keeps address assignment centralized in one place and reduces the chance of an off-by-one in the base address, which would be hard to spot since both BRAM0 and BRAM2 currently differ only in their low 16 address bits.

## Vitis Bare-Metal / Standalone
### Key Findings
- `xil_printf` supports only `%d`, `%l`, `%x`, `%c`, `%s` (no `%f`/floating point) and interprets standard escape sequences like `\n` — it deliberately trades format richness for a much smaller code/stack footprint than libc `printf`, which matters when DDR/OCM allocation is tight in a minimal bare-metal app.
- The standalone BSP's `stdin`/`stdout` UART selection is a platform-component setting, not something inferred from hardware automatically — a commonly hit failure mode is the BSP defaulting to the wrong UART instance relative to the carrier's actual USB-UART bridge, which makes PASS/FAIL output vanish even though the application is running correctly on hardware.
- GIC interrupt setup on Cortex-A53 (Zynq UltraScale+) is a strict multi-step process: `XScuGic_CfgInitialize`, `Xil_ExceptionRegisterHandler`, and `XScuGic_Connect` register and wire the handler, but a separate `XScuGic_Enable(&GicInst, <intr_id>)` call is required afterward — skipping it leaves the handler "registered but silent" with no error indication.
- `lscript.ld` (the linker script) is directly editable in the Vitis IDE under `<app>/src/lscript.ld` and defines where `.text`/`.data`/`.bss`/heap land in OCM/DDR; after re-exporting hardware (a new XSA) for the same app, the linker script's memory region base/size should be re-checked, since a stale region from an older hardware platform can silently truncate the heap or place sections outside valid DDR.

### Code Example
```c
#include "xil_printf.h"
#include "xparameters.h"
#include "xil_io.h"

#define BRAM0_BASEADDR XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR /* 0xA0000000 */
#define BRAM2_BASEADDR XPAR_AXI_BRAM_CTRL_1_S_AXI_BASEADDR /* 0xA0010000 */

int test_bram(u32 base, const char *name) {
    u32 pattern = 0xA5A5A5A5;
    Xil_Out32(base, pattern);
    u32 readback = Xil_In32(base);
    if (readback == pattern) {
        xil_printf("%s: PASS (wrote 0x%x, read 0x%x)\r\n", name, pattern, readback);
        return 0;
    }
    xil_printf("%s: FAIL (wrote 0x%x, read 0x%x)\r\n", name, pattern, readback);
    return 1;
}
```

### Relevance to Your Project
This is the same write/readback/PASS-FAIL idiom described for `main.c`. If PASS/FAIL output ever stops appearing over USB-UART while the board otherwise seems to run, check the BSP's `stdout` UART selection in the platform component before suspecting a hardware fault — far more common than an actual AXI failure. The GIC two-step is only relevant if a future revision moves from polling to an interrupt-driven trigger (e.g., a timer or AXI GPIO "go" pin) for the BRAM test loop.

## XDC Timing Constraints
### Key Findings
- `set_input_delay`/`set_output_delay` model the external system-level delay relative to a clock edge at a primary I/O port; the "input delay -max" value is effectively the driving device's clock-to-Q delay as seen at the FPGA pin (not the FPGA's own setup time), and values can legitimately be negative depending on the data/clock phase relationship — a frequent point of confusion when porting datasheet numbers directly into XDC.
- Every clock-domain crossing needs an explicit `set_clock_groups -asynchronous` declaration; an undeclared CDC is, by default, timed as if synchronous, which can either produce spurious timing failures (false negatives from over-constraining) or — more dangerously — falsely "pass" a path that's actually a metastability risk.
- Timing exceptions for known-safe paths use `set_false_path` and `set_multicycle_path`, but both should be scoped as narrowly as possible (specific pins/cells, not broad wildcards) to avoid accidentally masking a real timing violation elsewhere in the design.
- Zynq UltraScale+-specific gotcha: assigning a clock root in the same clock region as a `BUFG_GT` driver can render outputs in certain other clock regions unroutable — a niche issue that only shows up once gigabit-transceiver-adjacent clocking is added to a design.

### Code Example
```tcl
# Board-level XDC additions only needed if direct PL I/O is added
# (not required for the current pure PS<->PL AXI-only BRAM path).
create_clock -period 8.000 -name pl_clk0 [get_ports pl_clk0_p]

set_input_delay  -clock pl_clk0 -max 1.5 [get_ports {ext_data[*]}]
set_input_delay  -clock pl_clk0 -min 0.3 [get_ports {ext_data[*]}]
set_output_delay -clock pl_clk0 -max 1.2 [get_ports {ext_ctrl[*]}]
set_output_delay -clock pl_clk0 -min -0.5 [get_ports {ext_ctrl[*]}]

set_clock_groups -asynchronous \
    -group [get_clocks -include_generated_clocks clk_fpga_0] \
    -group [get_clocks -include_generated_clocks pl_clk0]
```

### Relevance to Your Project
The design is purely PS-driven AXI on a single PS-generated FCLK domain feeding both BRAM controllers through `kv260_top.vhd`, so board-level `set_input_delay`/`set_output_delay` constraints don't apply today — those only matter once a signal crosses the board boundary through a physical I/O pin. The `set_clock_groups` guidance becomes relevant the instant a PL-side clock independent of the PS FCLK is added (e.g., a free-running oscillator feeding new logic).

## Kria KV260 / K26 SoM
### Key Findings
- Kria SOMs force booting from read-only QSPI boot firmware specifically to prevent bricking the device — this is a deliberate Kria-platform design decision, distinct from a generic Zynq UltraScale+ board, and means a pure bare-metal-only workflow (no Linux/PetaLinux image involved at all) should iterate via JTAG boot mode rather than attempting to reprogram QSPI directly during development.
- The official documented baremetal AXI-BRAM reference flow (xilinx.github.io/kria-apps-docs) matches this project's shape closely: add an AXI BRAM Controller, run Connection Automation to tie its `S_AXI` to `M_AXI_HPM0_FPD`, set single-BRAM-interface mode, and explicitly disable any unused second HPM master port rather than leaving it dangling unconnected.
- The K26 board file (used in Vivado board-aware flows) encodes the SOM's required MIO configuration and a minimal hardware config sufficient to boot to Linux; custom carrier designs layer their own MIO/PL physical interfaces on top per the Carrier Card Design Guide (UG1091) rather than fighting the board file's baseline.
- Since the 2022.1 Kria Linux images, the default "k26-starter-kits" bitstream has effectively no functional PL logic beyond an EMIO mapping for carrier fan control — a from-scratch bare-metal/PL design like this one is genuinely starting from near-empty fabric, not inheriting hidden default logic.
- A mid-2026 community guide ("Bare-metal 4K Streaming on KV260: The 2025.2 Guide") confirms the bare-metal + Vivado/Vitis 2025.x toolchain combination remains an actively maintained path for this exact board, so the 2025.1 toolchain in use here is well-supported, current ground.

### Code Example
```tcl
# PS configuration matching a single-HPM-master, BRAM0/BRAM2 pattern;
# explicitly disabling the unused second GP master avoids a common
# validate_bd_design critical-warning source (enabled-but-unconnected port).
set_property -dict [list \
    CONFIG.PSU__USE__M_AXI_GP0 {1} \
    CONFIG.PSU__USE__M_AXI_GP1 {0} \
    CONFIG.PSU__MAXIGP0__DATA_WIDTH {32} \
] [get_bd_cells zynq_ultra_ps_e_0]
```

### Relevance to Your Project
This matches the documented official Kria baremetal AXI-BRAM pattern almost exactly — both BRAM0 and BRAM2 feeding off `M_AXI_HPM0_FPD`. Worth confirming in `create_bd.tcl` that any unused second HPM master is explicitly disabled (`PSU__USE__M_AXI_GP1 {0}`) rather than merely unconnected. Also worth confirming the development boot mode is JTAG (not QSPI) given the read-only-QSPI-firmware lockdown — accidentally writing a bare-metal-only boot image to QSPI on a Kria SOM is a documented way to get into a bad boot state.

## AMD/Xilinx Tool Updates
### Key Findings
- Vivado 2025.1 IP-level fixes include corrected PTP 1588 frame handling in the AXI Ethernet Buffer at the Buffer→MAC interface, an updated dynamic-addressing register-update path, and a fix avoiding a potential deadlock between peripheral and cache-data AXI interfaces under frequency-optimized pipeline configurations — none of these touch `axi_bram_ctrl` or the Zynq UltraScale+ PS block directly.
- Vivado 2025.1 also adds the ability to boot the processing system first and dynamically load the PL on the fly, enabling faster bring-up of the OS with a more flexible boot sequence — primarily aimed at Linux-based flows, not directly applicable to a pure bare-metal app, but worth knowing as a 2025.1-era platform capability.
- Vivado 2025.2 (the next release after the one this project uses) adds a new Pblock planner, an automatic Tcl migration script for old-to-new synthesis/implementation directives, and changes the AMD IP configuration file format from XML to JSON (for better revision-control diffing and faster loading) — relevant mainly if/when this project's toolchain is bumped.
- Vitis 2025.2 makes the Unified IDE the default, with the Classic Vitis IDE deprecated — anyone following an older Classic-IDE bare-metal tutorial on a 2025.2+ install should expect a materially different workflow for BSP/platform configuration.
- AXI BRAM Controller (PG078) v4.1 supports optional ECC in both single- and dual-port BRAM configurations (`C_ECC = 1`) — not needed today, but a known lever if BRAM reliability becomes a concern as test patterns scale up.

No upgrade is needed; if/when 2025.2 is adopted, re-run `validate_bd_design` after the first open of the block design on the new toolchain (IP re-customization prompts for `axi_bram_ctrl` and the Zynq UltraScale+ PS block are routine on cross-version bumps), and budget extra time if migrating from Classic Vitis IDE workflows, since 2025.2 defaults to the Unified IDE.
