# FPGA Research Digest - 2026-08-18

## Executive Summary

- **CRITICAL — Vivado 2025.1+: Block Memory Generator IP no longer available in IP Catalog for direct instantiation.** Embedded Memory Generator and FIFO must now be used exclusively within IP Integrator/Block Design. If you are regenerating your project from TCL or switching Vivado versions, your `create_bd.tcl` flow already handles this correctly — but be aware that standalone `generate_target` flows for BRAM will break.
- **AXI-Lite BRESP/handshake pitfall:** Both AW and W channels must complete before asserting BVALID. A common bug is clearing `aw_hs_done`/`w_hs_done` flags at the wrong time, causing the slave to miss a transaction after a stalled write. Verify your AXI BRAM Controller responds with BVALID only after seeing both AWVALID+AWREADY and WVALID+WREADY.
- **KV260 JTAG boot mode cannot be set by hardware switches.** Use XSDB/XSCT TCL commands to write boot mode registers. For bare-metal debug sessions in Vitis, remove the SD card and use `psu_init.tcl` instead of an FSBL to load your bitstream and elf cleanly.
- **`write_bd_tcl` regeneration caveat:** Only user-modified IP parameters are written to the exported TCL; tool-propagated defaults are omitted. After importing on a new machine or version, always run `validate_bd_design` and check for unresolved IP before synthesis.
- **Vivado 2026.1 shifts to tiered licensing.** If you are planning to upgrade tools, note that device family licensing is now separate — ensure your license covers the Kria K26 (Zynq UltraScale+) family before upgrading.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- AXI-Lite handshake rule: a source must assert VALID and hold it until the handshake completes (both VALID and READY high on the same rising edge). VALID must not be deasserted while waiting for READY.
- WSTRB (write strobe) byte enables map directly to the BRAM byte-write-enable (`we`) pins via the AXI BRAM Controller. Setting `WSTRB=4'b0000` is the correct way for a master to abort a write without side effects; the controller will not write to BRAM.
- Address latching: latch `AWADDR` into a register (`awaddr_q`) on the cycle that `AWVALID && AWREADY` fires, not combinationally. Use bits `[addr_width-1:2]` to select among multiple register/offset slots.
- Both AW and W channels must complete independently; assert `BVALID` only after both `aw_hs_done` and `w_hs_done` flags are set. Clear these flags on the `BVALID && BREADY` handshake, not before.
- A concurrent read and write to an AXI-Lite slave with a single AR and AW channel can cause lost transactions if not properly arbitrated. Xilinx's AXI Interconnect handles this internally, but custom slaves must gate `ARREADY` or `AWREADY` while the other channel is in progress.

### Code Example

```c
/* Bare-metal AXI-Lite write then read-back for BRAM at base 0xA0000000 */
#define BRAM0_BASE  0xA0000000UL
#define BRAM_SIZE   0x2000U

/* Write a 32-bit word — PS AXI master drives WSTRB=0xF automatically */
static inline void bram_write32(uintptr_t base, uint32_t offset, uint32_t val) {
    *(volatile uint32_t *)(base + offset) = val;
    dsb();   /* Data Synchronisation Barrier — ensures write completes before read */
}

static inline uint32_t bram_read32(uintptr_t base, uint32_t offset) {
    uint32_t v = *(volatile uint32_t *)(base + offset);
    dsb();
    return v;
}

/* Pattern test */
uint32_t pattern = 0xDEADBEEF;
bram_write32(BRAM0_BASE, 0x00, pattern);
uint32_t readback = bram_read32(BRAM0_BASE, 0x00);
xil_printf("BRAM0[0x00] = 0x%08X  %s\r\n", readback,
           readback == pattern ? "PASS" : "FAIL");
```

### Relevance to Your Project

Your `main.c` writes patterns over AXI-Lite to BRAM0 (0xA0000000) and BRAM2 (0xA0010000). Add `dsb()` barriers between each write and its read-back to prevent the Cortex-A53 store buffer from reordering the transaction and giving a false PASS on the first cycle. The ARM barrier is needed even for memory-mapped I/O when the MMU region is marked as Device memory.

## Vivado Block Design / IP Integrator

### Key Findings

- **BRAM/FIFO IP Catalog change (2025.1+):** Embedded Memory Generator and Embedded FIFO Generator IPs are no longer available for standalone instantiation from the IP Catalog — they must be used inside IP Integrator block designs only. Your `create_bd.tcl` approach is already the correct path going forward.
- `Run Connection Automation` in IP Integrator automatically adds and connects an AXI Interconnect, AXI BRAM Controller, Block Memory Generator, and Processor System Reset when you select a BRAM port. For two BRAMs (BRAM0 + BRAM2), run automation twice and verify the address editor assigns non-overlapping 64KB (or larger) ranges.
- AXI Protocol selection matters: if you use AXI4 (full) instead of AXI4-Lite for the BRAM controller, you gain burst capability for higher-bandwidth block transfers. AXI4-Lite is simpler and sufficient for single-word tests.
- `validate_bd_design` propagates parameters between IPs (width negotiation, link type). Always run this before generating output products.
- After updating IPs in 2025.1, Vivado may not detect the update automatically — close and reopen the project to force re-detection.

### Code Example

```tcl
# In create_bd.tcl: add two BRAM controllers and run automation
create_bd_cell -type ip -vlnv xilinx.com:ip:axi_bram_ctrl:4.1 axi_bram_ctrl_0
create_bd_cell -type ip -vlnv xilinx.com:ip:axi_bram_ctrl:4.1 axi_bram_ctrl_2

# Set AXI4-Lite single-port mode
set_property -dict [list \
    CONFIG.SINGLE_PORT_BRAM {1} \
    CONFIG.MEM_DEPTH {8192} \
] [get_bd_cells axi_bram_ctrl_0]

# After connecting to AXI Interconnect master port:
assign_bd_address [get_bd_addr_segs {axi_bram_ctrl_0/S_AXI/Mem0}]
set_property offset 0xA0000000 [get_bd_addr_segs \
    {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property range 64K [get_bd_addr_segs \
    {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]

assign_bd_address [get_bd_addr_segs {axi_bram_ctrl_2/S_AXI/Mem0}]
set_property offset 0xA0010000 [get_bd_addr_segs \
    {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_2_Mem0}]
set_property range 64K [get_bd_addr_segs \
    {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_2_Mem0}]
```

### Relevance to Your Project

Your two BRAMs at 0xA0000000 and 0xA0010000 are 64KB apart — make sure each BRAM range in the Address Editor is set to exactly 64K to avoid address aliasing between them. If the range is set to 128K for BRAM0, it will overlap BRAM2's base address and produce unpredictable read-back behavior.

## Vivado TCL Scripting

### Key Findings

- Two modes: **Project Mode** (Vivado manages sources/state) vs **Non-Project Mode** (developer manages everything in-memory). Non-project mode is more script-friendly for CI and reproducibility.
- Batch launch: `vivado -mode batch -source create_bd.tcl` opens Vivado, runs the script, and exits. Ideal for automated builds.
- **`write_bd_tcl`** exports a block design to a reproducible TCL file: `write_bd_tcl -include_layout ./tcl/create_bd.tcl`. Only user-changed IP parameters are emitted; tool-propagated defaults are excluded.
- **IP Integrator in Non-Project Mode (2025.1, UG994):** You can create, modify, and export block designs without a project file using `create_bd_design`, `open_bd_design`, and `write_bd_tcl`.
- The exported TCL is tied to the Vivado version it was generated in — do not expect cross-version portability without re-running parameter propagation.

### Code Example

```tcl
# Non-project mode: synthesize and implement from a BD TCL
set outputDir "./output"
file mkdir $outputDir

# Create in-memory project
create_project -in_memory -part xck26-sfvc784-2LV-c

# Source the BD creation script
source ./tcl/create_bd.tcl

# Generate output products (includes BRAM init files, wrappers)
generate_target all [get_files *.bd]

# Synthesize
synth_design -top kv260_top -part xck26-sfvc784-2LV-c \
    -flatten_hierarchy rebuilt

# Implement
opt_design
place_design
route_design

# Write bitstream
write_bitstream -force $outputDir/kv260_top.bit

# Write XSA for Vitis
write_hw_platform -fixed -force -file $outputDir/kv260_top.xsa
```

### Relevance to Your Project

This non-project mode script pattern means your `create_bd.tcl` can drive a fully automated build that produces a bitstream and XSA without ever opening the Vivado GUI. Pair it with a `Makefile` target for reproducible CI builds of the kv260-axi-bram-demo.

## Vitis Bare-Metal / Standalone

### Key Findings

- **AXI INTC (Interrupt Controller):** The LogiCORE AXI Interrupt Controller merges multiple PL interrupt inputs and forwards them to the PS via an AXI4-Lite register interface. Bare-metal drivers do NOT auto-initialize interrupt controllers — you must call `XIntc_Initialize()` and `XIntc_Connect()` explicitly after BSP generation.
- **xil_printf:** Configured via BSP settings; `stdout` must point to the UART peripheral (UART1 on KV260 → PS MIO). In Vitis Unified (2023.2+), this is set in the `platform.spr` standalone domain settings under `stdin`/`stdout`.
- **Linker script:** The default generated `lscript.ld` may assign incorrect base addresses for DDR or OCM regions. Always verify `psu_ddr_0_MEM_0` base (should be `0x00000000`) and size match your actual DDR configuration before building.
- **BSP driver path:** Standalone drivers are at `<Vitis>/data/embeddedsw/XilinxProcessorIPLib/drivers`. You can also source drivers directly from the Xilinx `embeddedsw` GitHub repo for the most current versions.
- **Kria bare-metal boot flow:** Remove SD card, boot in JTAG mode via XSDB, run `psu_init.tcl` to initialize DDR, then download bitstream and ELF. No FSBL needed for pure bare-metal debug.

### Code Example

```c
#include "xil_printf.h"
#include "xparameters.h"
#include "xil_io.h"
#include "sleep.h"

#define BRAM0_BASEADDR  XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR  /* 0xA0000000 */
#define BRAM2_BASEADDR  XPAR_AXI_BRAM_CTRL_2_S_AXI_BASEADDR  /* 0xA0010000 */

int main(void) {
    xil_printf("\r\n=== KV260 AXI-BRAM Test ===\r\n");

    /* Write and read-back test for BRAM0 */
    Xil_Out32(BRAM0_BASEADDR + 0x00, 0xCAFEBABE);
    Xil_Out32(BRAM0_BASEADDR + 0x04, 0xDEADBEEF);

    u32 r0 = Xil_In32(BRAM0_BASEADDR + 0x00);
    u32 r1 = Xil_In32(BRAM0_BASEADDR + 0x04);

    xil_printf("BRAM0[0] = 0x%08lX  %s\r\n", r0,
               r0 == 0xCAFEBABE ? "PASS" : "FAIL");
    xil_printf("BRAM0[4] = 0x%08lX  %s\r\n", r1,
               r1 == 0xDEADBEEF ? "PASS" : "FAIL");

    return 0;
}
```

### Relevance to Your Project

Use `Xil_Out32`/`Xil_In32` (from `xil_io.h`) rather than raw pointer casts — these macros handle cache/barrier semantics correctly on Cortex-A53 and map directly to `XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR` from `xparameters.h`, keeping your code portable across address changes in the block design.

## XDC Timing Constraints

### Key Findings

- `set_input_delay -clock <clk> <delay_ns> [get_ports <port>]` specifies the external path delay on a primary input relative to a clock edge, in nanoseconds. Can be positive or negative depending on clock-data phase relationship at the FPGA boundary.
- `set_output_delay -clock <clk> <delay_ns> [get_ports <port>]` does the same for output ports. Use `-max` and `-min` variants for setup and hold constraints independently.
- For pure PS-to-PL AXI designs (no external I/O timing), you generally only need a `create_clock` for the PL fabric clock (`pl_clk0`) and a `set_clock_groups -asynchronous` between unrelated clock domains.
- The KV260 PYNQ Composable Pipeline XDC (available on GitHub at `Xilinx/PYNQ_Composable_Pipeline`) is a good real-world reference for KV260 pin-level constraints.
- For Zynq UltraScale+ (K26), the PS clocks are defined internally; add only PL-side constraints. The PS-to-PL clock (`pl_clk0`) is typically 100 MHz or 200 MHz as configured in the Zynq PS IP.

### Code Example

```xdc
# Clock constraint for PL fabric clock (100 MHz from PS)
# The pin name is defined by the Zynq PS IP — do not add create_clock to it;
# Vivado infers it automatically from the PS configuration.
# However, if you have an external oscillator input:
# create_clock -period 10.000 -name sys_clk [get_ports sys_clk_p]

# For an AXI-only design (no external I/O), these are the key constraints:
# 1. Mark PS clock groups as asynchronous to avoid false paths
set_clock_groups -asynchronous \
    -group [get_clocks clk_pl_0] \
    -group [get_clocks clk_pl_1]

# 2. If you have any registered outputs to LEDs or GPIO, constrain them:
set_output_delay -clock [get_clocks clk_pl_0] -max 2.0 [get_ports {led[*]}]
set_output_delay -clock [get_clocks clk_pl_0] -min -1.0 [get_ports {led[*]}]

# 3. False path to async reset if used
set_false_path -from [get_ports sys_rst_n]
```

### Relevance to Your Project

Since your kv260-axi-bram-demo is PS-to-PL only (no external FPGA I/O beyond UART which is PS MIO), your XDC file likely needs very few constraints. At minimum: a `set_clock_groups -asynchronous` if you have multiple PL clocks, and `set_false_path` for any async resets from the PS. Over-constraining (adding `set_input_delay` to ports that don't exist) will cause critical warnings that can mask real timing issues.

## Kria KV260 / K26 SoM

### Key Findings

- **Boot modes:** The KV260 Starter Kit ships with QSPI boot firmware pre-loaded and is read-only (for the Linux-oriented flow). For bare-metal, the KV260 has no physical boot mode switches — use XSDB/XSCT TCL to switch to JTAG mode by writing to the boot mode register programmatically.
- **JTAG bare-metal flow:** (1) Power on KV260, (2) Connect JTAG, (3) In XSCT: `connect; targets; source psu_init.tcl; after 1000; fpga -file design.bit; loadelf app.elf; con`
- **MIO assignment:** KV260 peripheral MIO pins are assigned on the SOM: UART1 is on MIO48/49 (PS-side USB-UART bridge), I2C is on MIO bank 500 at 1.8V. Do not attempt to remap UART1 MIO in your PS configuration or you will lose the console.
- **Power domains:** The K26 SOM recommends three carrier-card power domains: Always-On (5V main), PL Power (VCCINT), and I/O Power (per bank voltage). Keep bank voltage consistent with connected I/O standards — the PL I/O on KV260 is primarily 1.8V or 3.3V depending on the connector.
- **EMIO:** For PL signals that need to route to the PS (interrupts, control signals), use EMIO. The Zynq UltraScale+ supports EMIO GPIO, EMIO UART, EMIO SPI, etc. In your block design, connect PL interrupt lines from the AXI Interconnect to the PS IRQ inputs via the `pl_ps_irq` port.

### Code Example

```tcl
# XSCT script: boot KV260 in JTAG mode (bare-metal debug flow)
# Run this in the XSCT console after connecting JTAG:

connect
target 1
# Switch to JTAG boot mode (write boot mode register)
mwr 0xFF5E0200 0x0100
after 100

# Initialize PS (DDR, clocks, MIO) — use the psu_init.tcl from your XSA
source {./psu_init.tcl}
after 2000

# Program PL bitstream
target 1
fpga -file {./kv260_top.bit}

# Load bare-metal ELF on Cortex-A53 core 0
target 5
dow {./kv260_axi_bram.elf}

# Run
con
```

### Relevance to Your Project

This is the exact XSCT sequence for loading your kv260-axi-bram-demo bitstream and ELF during development. Save it as `debug_boot.tcl` and run `xsct debug_boot.tcl` from the Vitis command shell. This eliminates needing a boot image (BOOT.BIN) during iteration — much faster than QSPI programming for every test cycle.

## AMD/Xilinx Tool Updates (2025.x / 2026.x)

### Key Findings

- **Vivado 2026.1 (latest as of this digest):** New tiered licensing model — device family licenses are now sold separately. Ensure your license covers Zynq UltraScale+ (K26 family) before upgrading. New device support: Versal RF Series, AI Edge Series Gen 2, Spartan UltraScale+.
- **BRAM/FIFO IP change (2025.1+):** Embedded Memory Generator and Embedded FIFO Generator are **no longer available standalone in the IP Catalog** — they must be used within IP Integrator block designs only. This is a breaking change for any scripts that `create_ip` a BRAM directly.
- **2025.1 Vivado IP Change Log (AR 000037919):** Comprehensive list of all IP core version changes in 2025.1. Check this before regenerating IPs in an existing project.
- **Vitis 2025.1 release notes (UG1742):** Documents changes to the Unified IDE; the Vitis Classic flow is being phased toward the Unified Vitis flow. If your `create_bd.tcl` workflow still relies on `hsi` commands, check whether they remain available in 2025.1+.
- **QoR improvements in 2026.1:** Retiming updates, XPM memory optimization, and mixed RAM directives improve timing closure for memory-intensive designs.

### Code Example

```tcl
# Check Vivado version in a TCL script — adapt behavior accordingly
set vivado_version [version -short]
puts "Running Vivado version: $vivado_version"

# In 2025.1+ BRAM must be added via IP Integrator only
# Correct approach (works 2025.1+):
if {[string match "2025*" $vivado_version] || \
    [string match "2026*" $vivado_version]} {
    puts "INFO: Using IP Integrator BRAM flow (2025.1+ required)"
    # BRAM is added inside create_bd.tcl via create_bd_cell
    source ./tcl/create_bd.tcl
} else {
    puts "INFO: Legacy direct IP instantiation flow"
    create_ip -name blk_mem_gen -vendor xilinx.com -library ip -version 8.4 \
        -module_name bram_0
}

# Export XSA for Vitis after implementation
write_hw_platform -fixed -force ./output/design.xsa
```

### Relevance to Your Project

If you ever regenerate the kv260-axi-bram-demo project on Vivado 2025.1 or later (which you are currently using), your `create_bd.tcl`-based BRAM instantiation is the correct and only supported path. Any older documentation suggesting `create_ip -name blk_mem_gen` for standalone BRAM IP will fail with a "not available" error. Your existing workflow is already aligned with this change.
