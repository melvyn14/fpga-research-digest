# FPGA Research Digest - 2026-10-06

## Executive Summary

- **AXI deadlock prevention**: Never gate VALID on READY in a custom AXI-Lite slave — the "assert and wait" rule is mandatory; violating it creates deadlocks that are hard to reproduce in simulation.
- **BRAM read latency**: The AXI BRAM Controller introduces at least 1 extra cycle of read latency on top of the BRAM primitive itself; bare-metal code must not read the result on the same cycle as the address phase completes.
- **KV260 UART quirk**: The KV260 uses UART1 (not UART0) for the console — if xil_printf output is silent, check that the BSP `stdin`/`stdout` peripheral is set to `psu_uart_1`, not `psu_uart_0`.
- **Vivado 2025.1 new AXI Switch IP**: A new RTL-instantiable `AXI Switch` IP bridges different AXI types and widths — useful for tying the PS M_AXI_GP port to multiple BRAM controllers without SmartConnect overhead.
- **TCL non-project mode tip**: In non-project mode `set_part xck26-sfvc784-2LV-c` must be called before any `create_ip`/`create_bd_cell` command; forgetting it causes silent IP generation failures or wrong device targets.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- **Valid-before-Ready rule**: The AXI spec requires that a master assert VALID independently of READY. Gating VALID on READY is illegal and can deadlock two compliant endpoints simultaneously waiting for the other.
- **Formal verification gap**: When AMD's Vivado-generated AXI-Lite slave template was subjected to formal property checking, multiple spec violations were found — do not assume generated IP is deadlock-free; always validate custom wrappers.
- **BRAM Controller latency pipeline**: Primitive BRAM read latency is 1 clock cycle; the AXI BRAM Controller adds register stages for timing closure. The default `READ_LATENCY` parameter is 1 (no extra register), but setting it to 2 or higher helps when timing is tight at 100 MHz+.
- **AXI-Lite write response**: The BRESP channel must be accepted (BREADY asserted) before a second write transaction can begin in a simple slave. Bare-metal code that fires back-to-back writes without checking BVALID/BREADY may silently drop data.
- **AXI-Stream TKEEP/TLAST**: For streaming peripherals, TLAST marks the end of a packet; improperly driving TLAST can corrupt downstream packet-length calculations — keep it tied high for single-word transfers.

### Code Example

```c
/* AXI-Lite bare-metal write + read-back with proper response polling */
#define BRAM0_BASE 0xA0000000UL

static inline void axi_write32(u32 addr, u32 data) {
    *(volatile u32 *)addr = data;
    /* Zynq PS AXI-Lite master handles BVALID/BREADY in hardware;
       insert a memory barrier so the CPU doesn't reorder the next read */
    __asm__ __volatile__("dsb sy" ::: "memory");
}

static inline u32 axi_read32(u32 addr) {
    __asm__ __volatile__("dsb sy" ::: "memory");
    return *(volatile u32 *)addr;
}

/* Usage */
axi_write32(BRAM0_BASE + 0x00, 0xDEADBEEF);
u32 val = axi_read32(BRAM0_BASE + 0x00);
if (val == 0xDEADBEEF) xil_printf("PASS\r\n");
else xil_printf("FAIL: got 0x%08X\r\n", val);
```

### Relevance to Your Project

The KV260 AXI-BRAM demo writes patterns to BRAM0 (0xA0000000) and BRAM2 (0xA0010000) from the Cortex-A53. The `dsb sy` barrier is essential between a write and the subsequent read-back — without it the A53 out-of-order engine can reorder the load before the store completes on the AXI bus, giving false FAILs that only appear at optimization levels `-O1` and above.

## Vivado Block Design / IP Integrator

### Key Findings

- **Vivado 2025.1 new views**: IP Integrator now has dedicated "Clocking and Reset" and "Interrupt and AXI-4 Lite" panels — use them to quickly audit clock/reset connectivity without scrolling a large block design canvas.
- **Address Editor grouping**: Vivado 2025.1 auto-groups equivalent address spaces for Versal Gen 2 devices; for Zynq UltraScale+ (K26) the address editor still requires manual range-setting after `assign_bd_address`.
- **Connection Automation pitfall**: After running `apply_bd_automation`, always review the auto-generated AXI Interconnect or SmartConnect — the tool sometimes inserts an extra level of SmartConnect when a direct connection would work, adding unnecessary latency.
- **Validate Design**: Always run `validate_bd_design` in TCL before `generate_target` — it catches unconnected required ports, missing clock/reset associations, and address overlaps that would otherwise produce cryptic implementation errors.
- **Regenerate targets**: After editing a block design outside Vivado (e.g., with a TCL script), run `generate_target all [get_files *.bd]` before opening the project in the GUI, otherwise stale wrappers cause synthesis errors.

### Code Example

```tcl
# Verify and generate block design from TCL (project mode)
open_bd_design [get_files *.bd]
validate_bd_design
generate_target all [get_bd_designs]
make_wrapper -files [get_files *.bd] -top
add_files -norecurse [glob ./*/hdl/*_wrapper.v]
set_property top kv260_top_wrapper [current_fileset]
```

### Relevance to Your Project

The `create_bd.tcl` script in kv260_claude/kv260/tcl/ should include `validate_bd_design` before `generate_target` to catch address assignment issues between BRAM0 (0xA0000000) and BRAM2 (0xA0010000). A 64 KB range on each BRAM controller is the default; verify it hasn't been auto-assigned to an overlapping region.

## Vivado TCL Scripting

### Key Findings

- **Non-project mode requirement**: In non-project mode, call `set_part xck26-sfvc784-2LV-c` before any IP creation; omitting this causes IP to target a default device and generates incorrect netlists.
- **Batch mode invocation**: `vivado -mode batch -source create_bd.tcl -notrace` suppresses verbose trace output; use `-log run.log` to capture results for CI pipelines.
- **`assign_bd_address` auto-assigns but doesn't validate**: The command maps slave segments into the master address space but does not check for conflicts — follow with `get_bd_addr_segs` to print the result and verify.
- **Exporting hardware**: Use `write_hw_platform -fixed -force -file design.xsa` (Vivado 2020.2+) instead of the deprecated `export_hardware`; the `.xsa` is required by Vitis 2025.1 for BSP generation.
- **Persisting IP repository**: Add `set_property ip_repo_paths` before `update_ip_catalog` when using custom IP; otherwise a re-run of the TCL script on a fresh Vivado instance cannot find the IP.

### Code Example

```tcl
# Minimal non-project AXI-BRAM block design (Vivado 2025.1)
set_part xck26-sfvc784-2LV-c

create_bd_design "kv260_bd"

# Zynq UltraScale+ PS
create_bd_cell -type ip -vlnv xilinx.com:ip:zynq_ultra_ps_e:3.5 zynq_ultra_ps_e_0
apply_bd_automation -rule xilinx.com:bd_rule:zynq_ultra_ps_e \
    -config { apply_board_preset "1" } [get_bd_cells zynq_ultra_ps_e_0]

# AXI BRAM Controller + Block Memory Generator (BRAM0)
create_bd_cell -type ip -vlnv xilinx.com:ip:axi_bram_ctrl:4.1 axi_bram_ctrl_0
create_bd_cell -type ip -vlnv xilinx.com:ip:blk_mem_gen:8.4   blk_mem_gen_0
set_property CONFIG.Memory_Type {True_Dual_Port_RAM} [get_bd_cells blk_mem_gen_0]

# Wire BRAM to controller
connect_bd_intf_net [get_bd_intf_pins axi_bram_ctrl_0/BRAM_PORTA] \
                    [get_bd_intf_pins blk_mem_gen_0/BRAM_PORTA]
connect_bd_intf_net [get_bd_intf_pins axi_bram_ctrl_0/BRAM_PORTB] \
                    [get_bd_intf_pins blk_mem_gen_0/BRAM_PORTB]

# Connect PS M_AXI_HPM0_LPD -> BRAM controller
connect_bd_intf_net [get_bd_intf_pins zynq_ultra_ps_e_0/M_AXI_HPM0_LPD] \
                    [get_bd_intf_pins axi_bram_ctrl_0/S_AXI]

# Clocks and resets
connect_bd_net [get_bd_pins zynq_ultra_ps_e_0/pl_clk0] \
               [get_bd_pins axi_bram_ctrl_0/s_axi_aclk]
connect_bd_net [get_bd_pins zynq_ultra_ps_e_0/pl_resetn0] \
               [get_bd_pins axi_bram_ctrl_0/s_axi_aresetn]

# Assign address
assign_bd_address [get_bd_addr_segs axi_bram_ctrl_0/S_AXI/Mem0]
set_property offset 0xA0000000 \
    [get_bd_addr_segs zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0]
set_property range  64K \
    [get_bd_addr_segs zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0]

validate_bd_design
generate_target all [get_bd_designs]
write_hw_platform -fixed -force -file kv260_bram.xsa
```

### Relevance to Your Project

This template mirrors what `create_bd.tcl` likely does for BRAM0 and BRAM2. Replicate the cell/connect/assign block for a second controller at offset 0xA0010000. The `write_hw_platform` command at the end produces the `.xsa` that Vitis 2025.1 needs for BSP generation.

## Vitis Bare-Metal / Standalone

### Key Findings

- **UART1 vs UART0**: KV260 routes the console to UART1 (`psu_uart_1`); set `stdin`/`stdout` in the BSP settings to `psu_uart_1` or xil_printf will produce no output.
- **BSP `sleep` functions**: Standalone BSP provides `sleep()` (seconds) and `usleep()` (microseconds) backed by the A53 global timer — use these instead of polling loops for delays in bare-metal tests.
- **Linker script heap/stack**: The default generated `lscript.ld` may allocate only 0x400 bytes of heap; for any `malloc`-using libraries, increase `_HEAP_SIZE` to at least `0x10000` in the linker script.
- **Cache coherency**: The A53 data cache is enabled by default in standalone BSP; when writing to PL-mapped memory (like BRAM), use `Xil_DCacheFlushRange(addr, len)` before/after to avoid stale cache lines corrupting the read-back.
- **`xil_printf` vs `printf`**: `xil_printf` is a lightweight implementation without floating-point support. Use `%d`, `%x`, `%s` — avoid `%f`; it silently outputs nothing on some BSP versions.

### Code Example

```c
#include "xil_printf.h"
#include "xil_cache.h"
#include "sleep.h"

#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL
#define TEST_WORDS  16

int main(void) {
    volatile u32 *bram0 = (volatile u32 *)BRAM0_BASE;
    volatile u32 *bram2 = (volatile u32 *)BRAM2_BASE;
    int pass = 1;

    xil_printf("KV260 AXI-BRAM test starting...\r\n");

    /* Write patterns */
    for (int i = 0; i < TEST_WORDS; i++) {
        bram0[i] = 0xA0000000 + i;
        bram2[i] = 0xA0010000 + i;
    }

    /* Flush D-cache to ensure stores hit PL BRAM */
    Xil_DCacheFlushRange(BRAM0_BASE, TEST_WORDS * 4);
    Xil_DCacheFlushRange(BRAM2_BASE, TEST_WORDS * 4);

    /* Invalidate so reads come from PL, not cache */
    Xil_DCacheInvalidateRange(BRAM0_BASE, TEST_WORDS * 4);
    Xil_DCacheInvalidateRange(BRAM2_BASE, TEST_WORDS * 4);

    /* Read back and verify */
    for (int i = 0; i < TEST_WORDS; i++) {
        if (bram0[i] != (u32)(0xA0000000 + i)) { pass = 0; break; }
        if (bram2[i] != (u32)(0xA0010000 + i)) { pass = 0; break; }
    }

    xil_printf("Result: %s\r\n", pass ? "PASS" : "FAIL");
    return 0;
}
```

### Relevance to Your Project

The cache flush/invalidate pattern is the most common source of silent FAIL on the KV260 AXI-BRAM demo — the A53 data cache shadows the BRAM writes, so the read-back hits the cache, not PL memory, and always returns the "written" value even if the AXI transaction never completed. Adding `Xil_DCacheFlushRange` + `Xil_DCacheInvalidateRange` is the definitive fix.

## XDC Timing Constraints

### Key Findings

- **Recommended constraint order**: AMD UG903 mandates this order — primary clocks → generated clocks → clock groups → I/O delays → false paths → max/min delays → multicycle paths. Deviating causes Vivado to silently apply constraints in the wrong order.
- **PS-PL interface clock**: The PS generates `pl_clk0` internally; it appears as a `create_clock` in the PS IP but not in the XDC. No `create_clock` is needed in the XDC for `pl_clk0` — add one only for external oscillators brought into the PL directly.
- **AXI-Lite I/O constraints**: For a PS-to-PL AXI-Lite connection that stays entirely on-chip, `set_input_delay`/`set_output_delay` are NOT needed — these apply only to signals crossing PCB traces (i.e., FPGA pins). Omitting them reduces constraint clutter and avoids incorrect path analysis.
- **`set_clock_groups -asynchronous`**: Use this between PS clocks and any asynchronous PL clocks (e.g., a differential clock from the SFP cage on KV260). Without it, Vivado tries to time paths that cross truly asynchronous domains and will report false critical warnings.
- **False path for reset**: Register-synchronizer reset paths should be false-pathed: `set_false_path -to [get_cells -hierarchical -filter {NAME =~ *sync_reset*}]`.

### Code Example

```tcl
# KV260 XDC snippet — minimal constraints for PS+PL AXI-BRAM design

# 1. PS pl_clk0 is auto-constrained by the PS IP; no create_clock needed here.

# 2. If a PL-side oscillator (e.g. 25 MHz on SI5332) is used for a secondary clock:
# create_clock -period 40.000 -name clk_pl_ext [get_ports clk_pl_ext_p]

# 3. Declare the PS clock group async relative to any PL oscillator
set_clock_groups -asynchronous \
    -group [get_clocks clk_pl_clk0] \
    -group [get_clocks clk_pl_ext]

# 4. False-path the synchronizer reset chain
set_false_path -to [get_cells -hierarchical -filter {NAME =~ *sync_rst_reg*}]

# 5. Constrain GPIO output if any PL pins are driven
# (KV260 PL I/O at 3.3V on HD banks, 1.8V on HP banks)
# set_output_delay -clock clk_pl_clk0 -max 2.0 [get_ports {led[*]}]
# set_output_delay -clock clk_pl_clk0 -min 0.5 [get_ports {led[*]}]
```

### Relevance to Your Project

The kv260_top.vhd wrapper drives `pl_clk0` to the AXI BRAM controllers. Since all logic is PS-sourced and on-chip, the only required XDC entries are the clock-groups declaration (if using any secondary PL clock) and false-paths for reset synchronizers. Skipping I/O delay constraints for the PS-PL AXI signals is correct — they are not board-level I/Os.

## Kria KV260 / K26 SoM

### Key Findings

- **Boot mode is fixed to QSPI**: The KV260 has no boot-mode switches; it always boots from the on-SOM 512 Mb QSPI flash. The SD card is the secondary boot device for the OS image, not the primary. For bare-metal JTAG development, the JTAG boot override in Vitis handles this transparently.
- **UART1 for console**: All Kria SOMs route the PS console to UART1 (`MIO 36/37`), not UART0. The USB-to-UART bridge on the KV260 carrier card connects to UART1 — configuring BSP to use UART0 produces no output.
- **MIO vs EMIO**: The KV260 exposes 52 PS MIO pins (1.8 V) for PS peripherals (USB, SD, UART, I2C, SPI, CAN, GPIO) and routes PL I/O through the carrier card's HD/HP banks. PL GPIO signals must use EMIO (driven through the PS GPIO block) or direct PL port connections — they cannot use MIO pins.
- **Power domains**: K26 has full-power domain (FPD) and low-power domain (LPD). The M_AXI_HPM0_LPD port (used for the AXI-BRAM demo at lower addresses) is in the LPD and runs at up to 333 MHz with 32-bit data width. The FPD HP ports support 128-bit and are better for DMA-heavy designs.
- **PL clock frequency**: `pl_clk0` defaults to 99.999 MHz when generated by the PS IP with default settings. For BRAM timing, this is well within the 500 MHz BRAM capability — no special timing tuning needed.

### Code Example

```tcl
# KV260 PS configuration in block design TCL
# Key settings for bare-metal AXI-BRAM demo

set_property -dict [list \
    CONFIG.PSU__UART1__PERIPHERAL__ENABLE  {1} \
    CONFIG.PSU__UART1__PERIPHERAL__IO      {MIO 36 .. 37} \
    CONFIG.PSU__CRL_APB__PL0_REF_CTRL__FREQMHZ {100} \
    CONFIG.PSU__USE__M_AXI_GP0             {1} \
    CONFIG.PSU__MAXIGP0__DATA_WIDTH        {32} \
    CONFIG.PSU__USE__M_AXI_GP2             {0} \
    CONFIG.PSU__USE__S_AXI_GP0             {0} \
] [get_bd_cells zynq_ultra_ps_e_0]
```

### Relevance to Your Project

Enabling `PSU__UART1` and setting `PSU__CRL_APB__PL0_REF_CTRL__FREQMHZ` to 100 are the two most important PS settings for the KV260 AXI-BRAM demo. The `M_AXI_GP0` (HPM0_LPD) at 32-bit width is the correct master for the 0xA000_0000 range. Check that `DATA_WIDTH` is 32 — a 128-bit mismatch with the BRAM controller (which defaults to 32-bit) causes the AXI interconnect to insert width converters and doubles read latency.

## AMD/Xilinx Tool Updates

### Key Findings

- **Vivado 2025.1 — New AXI Switch IP**: A new RTL-instantiable `AXI Switch` IP (unlike SmartConnect which is integrator-only) allows fine-grained AXI topology control directly in VHDL/Verilog top-level code.
- **Vivado 2025.1 — New device support**: Versal AI Edge Series Gen 2 and Versal Prime Series Gen 2 added; Spartan UltraScale+ now fully supported. Zynq UltraScale+ (KV260) support unchanged but benefits from tooling improvements.
- **Vitis 2025.2 — Multi-port M-AXI cache**: New multi-port cache for M-AXI interfaces in HLS kernels improves PL-to-PS memory bandwidth — relevant when upgrading the bare-metal demo to include an HLS accelerator.
- **Vitis 2025.2 — AXI Stream sideband APIs**: New C++ APIs for AXI Streams with sideband signals (TKEEP, TSTRB, TUSER) reduce boilerplate for HLS streaming kernels.
- **Open-source component releases**: Xilinx Wiki publishes 2025.1 release notes for open-source components including device-tree-xlnx, U-Boot, and Linux kernel patches — useful if the bare-metal demo evolves toward a Linux + PetaLinux flow.
- **UG1742 (Vitis Release Notes)**: The authoritative source for known issues, deprecated APIs, and migration notes for each release — always check before upgrading tool versions.

### Code Example

```tcl
# Vivado 2025.1: New AXI Switch IP instantiation in TCL
# Bridges PS M_AXI_HPM0_LPD to two BRAM controllers without SmartConnect
create_bd_cell -type ip -vlnv xilinx.com:ip:axi_switch:1.0 axi_switch_0
set_property -dict [list \
    CONFIG.NUM_MI {2} \
    CONFIG.NUM_SI {1} \
    CONFIG.ADDR_WIDTH {32} \
    CONFIG.DATA_WIDTH {32} \
] [get_bd_cells axi_switch_0]

# Connect PS master to switch input
connect_bd_intf_net [get_bd_intf_pins zynq_ultra_ps_e_0/M_AXI_HPM0_LPD] \
                    [get_bd_intf_pins axi_switch_0/S00_AXI]

# Connect switch outputs to BRAM controllers
connect_bd_intf_net [get_bd_intf_pins axi_switch_0/M00_AXI] \
                    [get_bd_intf_pins axi_bram_ctrl_0/S_AXI]
connect_bd_intf_net [get_bd_intf_pins axi_switch_0/M01_AXI] \
                    [get_bd_intf_pins axi_bram_ctrl_2/S_AXI]
```

### Relevance to Your Project

The new AXI Switch IP is a lighter-weight alternative to SmartConnect for the two-BRAM topology in the kv260-axi-bram-demo. If the current design uses SmartConnect and experiences unexpected timing or address-decode issues, replacing it with AXI Switch (Vivado 2025.1+) gives direct control over routing. Check UG1742 for any known issues with AXI BRAM Controller 4.1 under 2025.1 before upgrading.
