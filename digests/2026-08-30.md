# FPGA Research Digest - 2026-08-30

## Executive Summary

- **AXI-Lite byte-addressing trap**: addresses increment by 4 (32-bit words), not 1 — writing 4096 "bytes" actually spans 16 KB of address space and will fault if your BRAM is sized for 4 KB. Audit every `Xil_Out32`/`Xil_In32` offset in `main.c`.
- **BREADY/RREADY backpressure must be handled**: if the PS holds either low, your slave must deassert the corresponding READY immediately or the transaction stalls/deadlocks — this bug survived in Xilinx's own example cores past 2016.3.
- **Vivado 2025.1 boot-then-load-PL feature**: the PS can now power up, run code, and dynamically load the bitstream on the fly without a full FSBL reboot cycle — very useful for KV260 bare-metal bring-up iteration.
- **XSA export changed in 2025.x**: `write_hw_platform` (not `export_hardware`) is the canonical TCL command; always pass `-fixed` and `-include_bit` for bare-metal Vitis flows.
- **KV260 bare-metal boot path**: JTAG debug works without FSBL if you use `PSU_INIT.TCL` in Vitis; QSPI32 is the default boot mode on stock boards — plan your target deployment accordingly.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- All five AXI channels (AW, W, B, AR, R) use the same VALID/READY handshake. The transaction completes only on the rising edge where both are high simultaneously.
- **Backpressure bug**: if the master holds BREADY (write-response) or RREADY (read-data) low, the slave must deassert AWREADY/WREADY or ARREADY respectively. This is the most commonly missed edge case when testing with simple simulation stimulus.
- **Protocol rule**: a source (VALID side) must never wait for READY before asserting VALID — doing so creates a deadlock if both sides wait for the other.
- The Xilinx AXI-Lite demonstration core shipped with Vivado had a documented read bug present after 2016.3; verify your slave implementation with formal tools (e.g., Symbiyosys with the ZipCPU AXI-Lite property file) rather than simulation alone.
- AXI-Lite does not support burst transfers; every access is a single beat. For BRAM block reads, AXI-Full (with burst support) or multiple single transactions are required.
- Address alignment: AXI-Lite requires word-aligned addresses. A 32-bit data width means valid addresses are multiples of 4. Misaligned accesses produce a SLVERR response.

### Code Example

```c
/* Correct AXI-Lite word-addressed BRAM access pattern */
#define BRAM0_BASE   0xA0000000UL
#define BRAM2_BASE   0xA0010000UL

/* Write word N (byte offset = N*4) */
static inline void bram_write(u32 base, u32 word_idx, u32 value) {
    Xil_Out32(base + (word_idx << 2), value);
}

/* Read word N back */
static inline u32 bram_read(u32 base, u32 word_idx) {
    return Xil_In32(base + (word_idx << 2));
}

/* Verify pattern across first 64 words */
int verify_bram(u32 base, u32 pattern) {
    for (u32 i = 0; i < 64; i++) {
        bram_write(base, i, pattern ^ i);
    }
    for (u32 i = 0; i < 64; i++) {
        u32 rd = bram_read(base, i);
        if (rd != (pattern ^ i)) return -1;
    }
    return 0;
}
```

### Relevance to Your Project

Your two BRAMs at `0xA0000000` (BRAM0) and `0xA0010000` (BRAM2) are separated by 64 KB. Ensure your BRAM range in the Address Editor is ≤ 64 KB (typically 8 KB or 16 KB) so the regions don't overlap. The `Xil_Out32`/`Xil_In32` calls in `main.c` must use word offsets (`*4`), not byte counts — this is the most likely source of a silent PASS that actually reads back stale data from a wrongly-addressed location.

## Vivado Block Design / IP Integrator

### Key Findings

- **Connection automation**: Right-click on an unconnected port → "Run Connection Automation" auto-wires clocks, resets, and AXI interfaces to the Zynq PS — faster than manual wiring and less error-prone.
- **Address Editor**: After placing the AXI BRAM Controller, the Address Editor tab must assign non-overlapping base addresses. The default range is often 4 KB — increase to match your BRAM depth.
- **Regeneration**: After changing IP parameters, run "Generate Output Products" → "Global" synthesis to rebuild the IP netlist; failing to do so leaves stale netlists that silently use old parameters.
- **Block design wrapper**: Vivado generates a VHDL/Verilog wrapper for the block design. In Vivado 2025.x this is `kv260_top_wrapper.vhd` (or `.v`). If you replace the top-level VHDL manually, ensure the entity port names exactly match the generated wrapper's ports.
- **Validation**: Always run "Validate Design" (F6) before synthesis — it catches undriven resets, clock mismatches, and AXI width mismatches without a long synthesis run.

### Code Example

```tcl
# After sourcing create_bd.tcl, validate and generate outputs
validate_bd_design
generate_target all [get_files *.bd]
export_ip_user_files -of_objects [get_files *.bd] -no_script -sync -force -quiet
```

### Relevance to Your Project

The `create_bd.tcl` script in `kv260_claude/kv260/tcl/` recreates the block design headlessly. After any IP version upgrade (e.g., moving from Vivado 2024.x to 2025.1), run `upgrade_ip [get_ips *]` inside the script before `generate_target` to avoid stale IP warnings that can cause bitstream mismatches.

## Vivado TCL Scripting

### Key Findings

- **Non-project mode** gives full control without a `.xpr` file: source files, constraints, and IP are loaded with `read_vhdl`, `read_xdc`, `read_ip`, then synthesized with `synth_design`, implemented with `opt_design`/`place_design`/`route_design`, and a bitstream written with `write_bitstream`.
- **`write_project_tcl`**: from an open project, this command dumps a reproducible TCL script that recreates the entire project — useful for CI/CD and version control.
- **XSA export (2025.x)**: use `write_hw_platform -fixed -include_bit -force output.xsa` — the older `export_hardware` command is deprecated and may silently omit the bitstream in newer versions.
- **Batch mode**: invoke headlessly with `vivado -mode batch -source script.tcl` — no GUI license required for `Implementation` license tier.
- **IP Integrator in non-project mode**: after `create_bd_design`, all `create_bd_cell`, `connect_bd_net`, and `assign_bd_address` commands work identically to project mode.

### Code Example

```tcl
#!/usr/bin/env tclsh
# Non-project mode full flow for KV260 AXI-BRAM design

set part "xck26-sfvc784-2LV-c"
set board "xilinx.com:kv260_som:part0:1.4"

# Load sources
read_vhdl    [glob ./vhdl/*.vhd]
read_xdc     [glob ./xdc/*.xdc]

# Recreate block design
source ./tcl/create_bd.tcl
make_wrapper -files [get_files *.bd] -top
read_vhdl    [glob ./kv260/*.srcs/sources_1/bd/*/hdl/*_wrapper.vhd]

# Synthesize
synth_design -top kv260_top_wrapper -part $part

# Implement
opt_design
place_design
route_design

# Write outputs
write_bitstream -force ./output/kv260_top.bit
write_hw_platform -fixed -include_bit -force ./output/kv260_top.xsa

puts "Build complete."
```

### Relevance to Your Project

Automating the build via a single `vivado -mode batch -source build.tcl` call makes it trivial to regenerate after VHDL edits. The `create_bd.tcl` you already have is the hard part — wrapping it in the non-project flow above eliminates reliance on the `.xpr` GUI project state.

## Vitis Bare-Metal / Standalone

### Key Findings

- **BSP configuration**: the standalone BSP (`standalone_v8_x`) exposes settings like `stdin`/`stdout` UART selection, `hypervisor_guest` mode, and `enable_sw_intrusive_profiling` — all configurable via the BSP Settings panel or `mss` file.
- **`xil_printf` vs `printf`**: `xil_printf` is a lightweight implementation (no float support, smaller footprint). For format strings with `%f`, link against the full `printf` by adding `-lm` and using `printf` — but this inflates BSS/text by ~30 KB.
- **FSBL alternative for debug**: set Vitis debug launch configuration to use `PSU_INIT.TCL` (instead of FSBL) — this initializes DDR and clocks via XSDB scripts without requiring a bootable FSBL binary, cutting iteration time significantly.
- **Linker script**: the default linker script places `.text` in OCM (256 KB). For anything larger, redirect `.text` and `.data` to DDR (`ps_ddr_0` region). The linker script editor in Vitis 2025.x auto-populates regions from the XSA memory map.
- **Interrupt controller**: for bare-metal AXI IP interrupts, instantiate `XScuGic` (GIC-400 on Cortex-A53) and register handlers via `XScuGic_Connect`. Don't use the deprecated `XIntc` (MicroBlaze-era).

### Code Example

```c
#include "xil_printf.h"
#include "xparameters.h"
#include "xil_io.h"

/* xparameters.h defines XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR etc.
   Always use these macros instead of hard-coded addresses so
   the BSP stays in sync with the Address Editor in Vivado. */

int main(void) {
    xil_printf("KV260 AXI-BRAM Test\r\n");

    const u32 pattern = 0xDEADBEEF;
    Xil_Out32(XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR + 0x00, pattern);
    Xil_Out32(XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR + 0x04, ~pattern);

    u32 r0 = Xil_In32(XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR + 0x00);
    u32 r1 = Xil_In32(XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR + 0x04);

    if (r0 == pattern && r1 == ~pattern)
        xil_printf("PASS: BRAM0 read-back correct\r\n");
    else
        xil_printf("FAIL: got 0x%08X / 0x%08X\r\n", r0, r1);

    return 0;
}
```

### Relevance to Your Project

Using `XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR` (generated from the XSA) instead of hard-coded `0xA0000000` ensures your C code automatically tracks any address changes in Vivado's Address Editor — a defensive habit that prevents subtle mismatches as the design evolves.

## XDC Timing Constraints

### Key Findings

- **`set_input_delay` / `set_output_delay`**: values are in nanoseconds, relative to a reference clock edge at the device boundary. They model the external PCB path delay so the timing analyzer can close paths to/from I/O registers correctly.
- **Both `-max` and `-min` needed for SDR**: for single-data-rate I/O, provide both `-max` (setup) and `-min` (hold) variants. Missing `-min` leaves the hold path unconstrained.
- **`-add_delay`**: use this flag when the same port has multiple constraints (e.g., a pin clocked by two different clocks in a DDR scheme) — without it, the second `set_input_delay` silently overwrites the first.
- **AXI-Lite to BRAM (PS-internal path)**: the AXI-Lite from Zynq PS to PL crosses the PS-PL interface. Vivado automatically constrains this interface from the PS clock; you only need external `set_input_delay`/`set_output_delay` for pins that go to real I/O pads, not for PS-to-PL-only paths.
- **Clock groups for Zynq**: `set_clock_groups -asynchronous -group [get_clocks clk_pl_0] -group [get_clocks clk_ps_0]` is required if you have both PL fabric and PS clocks active and any cross-domain path exists.

### Code Example

```tcl
# KV260 XDC — Timing for external I/O (example: 125 MHz ref clock)
create_clock -period 8.000 -name sys_clk [get_ports sys_clk_p]

# PS-PL AXI clock (generated by the Zynq IP, no create_clock needed —
# Vivado auto-derives it from the PS configuration)

# External GPIO input with 2 ns board delay, 1 ns hold margin
set_input_delay -clock sys_clk -max 2.0 [get_ports gpio_in[*]]
set_input_delay -clock sys_clk -min 1.0 [get_ports gpio_in[*]]

# External GPIO output with 3 ns board delay
set_output_delay -clock sys_clk -max 3.0 [get_ports gpio_out[*]]
set_output_delay -clock sys_clk -min 0.5 [get_ports gpio_out[*]]

# Isolate PS and PL clock domains if both are used
set_clock_groups -asynchronous \
    -group [get_clocks -of_objects [get_pins */PL0_REF_CLK]] \
    -group [get_clocks sys_clk]
```

### Relevance to Your Project

For a pure PS-to-PL AXI-BRAM design with no external I/O (only USB-UART), your XDC only needs the `create_clock` for any external oscillator and the physical pin location constraints (`set_property PACKAGE_PIN` / `IOSTANDARD`). The AXI paths are fully internal and constrained automatically by the Zynq PS block. This is why a minimal XDC still produces a timing-clean bitstream for this demo.

## Kria KV260 / K26 SoM

### Key Findings

- **Boot mode**: MODE[3:0] pins on the SOM connector select the boot device. Stock KV260 boards ship with QSPI32 preset. For bare-metal development, JTAG mode (all MODE pins low) is the fastest iteration path — load bitstream + ELF directly from Vitis without flashing QSPI.
- **MIO/EMIO**: MIO 0–25 are PS-native (accessible without PL bitstream). USB-UART typically uses MIO 36/37 (UART1) on the KV260 carrier. EMIO signals route through the PL fabric and are only functional after the bitstream is loaded.
- **Power domains**: VCCO for sideband signals is 1.8 V. PL I/O banks have separate VCCO — check the K26 XDC file and Carrier Card Design Guide before driving external signals.
- **`PSU_INIT.TCL` for JTAG debug**: avoids full FSBL; Vitis generates this script from the XSA and uses XSDB to configure clocks, DDR, and MIO before loading the ELF. Enables kernel-less, FSBL-less bare-metal debug.
- **Kria-specific constraint**: the K26 SOM XDC file (`kv260_som.xdc`) defines all MIO, DDR, and PS-PL interface pin assignments. Import it as a constraint file rather than re-defining individually.

### Code Example

```tcl
# XSDB script for JTAG bare-metal debug on KV260 (run from Vitis XSCT console)
connect
targets -set -filter {name =~ "PSU"}
rst -system
after 3000

# Initialize PS (clocks, DDR, MIO) without FSBL
source {./psu_init.tcl}
psu_init

targets -set -filter {name =~ "Cortex-A53 #0"}
rst -processor

# Load bitstream into PL
fpga -f {./output/kv260_top.bit}

# Load and run ELF
dow {./output/kv260_top.elf}
con
```

### Relevance to Your Project

This XSDB flow replaces a full SD/QSPI boot cycle during development, reducing the edit-compile-test loop from minutes to seconds. The `psu_init.tcl` is auto-generated by Vitis when you create a bare-metal platform from the XSA — verify it exists in your platform's `hw` folder before running debug sessions.

## AMD/Xilinx Tool Updates (2025.x)

### Key Findings

- **Vivado 2025.1**: production-ready Spartan UltraScale+ devices (XCSU10P, XCSU25P, XCSU35P) added; new "boot PS first, load PL dynamically" capability for fast OS bring-up without PL-blocking boot; UG973 is the canonical release notes reference.
- **Vivado 2025.2**: new device support for Versal AI Edge Series Gen 2 and Versal Prime Series Gen 2; reduced physical optimization compile time; global/module-level retiming control improvements.
- **Vitis 2025.2**: AI Engine API enhancements (block floating-point MX6/MX4/cbfloat16); new DSP library functions (Cumulative Sum, Euclidean Distance, Function Approximation); `read-only shared buffers` and repeated MEM tile read access in the programming model.
- **Known issues (Vitis 2026.x tracker)**: AMD publishes an Adaptive Support article (000040220) tracking Vitis 2026.x known issues — bookmark and check before filing support cases for unexpected behavior.
- **`write_project_tcl` (2025.2 UG835)**: updated to correctly handle IP revision changes and block design container references — re-export if you generated your `create_bd.tcl` on an older version.

### Code Example

```tcl
# Vivado 2025.x: dynamic PL loading after PS boot
# (set in Zynq UltraScale+ PS IP configuration)
# In IP Integrator, under PS → Miscellaneous → "Boot Mode":
# Enable "Enable PL Power Sequencing" = YES
# This allows the boot sequence: PS boots → loads Linux/RTOS → mounts SD →
# calls fpgautil or xmutil to load PL bitstream at runtime.

# TCL equivalent for creating the PS with this feature enabled:
set_property CONFIG.PSU__FPGA_PL0_ENABLE {1} [get_bd_cells zynq_ultra_ps_e_0]
set_property CONFIG.PSU__FPGA_PL1_ENABLE {0} [get_bd_cells zynq_ultra_ps_e_0]

# For bare-metal, leave PL enable at 0 and load bitstream via JTAG/XSDB instead.
```

### Relevance to Your Project

The 2025.1 "PS-first boot" feature is not directly useful for bare-metal, but it confirms the PS-to-PL isolation model: the PS runs independently of PL power state, which is why your `PSU_INIT.TCL` + JTAG flow works without a full bitstream. Staying on Vivado/Vitis 2025.1 (matching your project stack) avoids mixing 2025.2 IP cores with a 2025.1 block design database — a common source of IP upgrade warnings that slow down CI builds.
