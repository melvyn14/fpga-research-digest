# FPGA Research Digest - 2026-10-15

## Executive Summary

- **AXI-Lite write not complete until B-channel response**: A write transaction is only done when the write response (BRESP/BVALID) arrives, not when the write-data phase completes — bare-metal polling loops must wait for BVALID after each BRAM write at 0xA0000000 / 0xA0010000.
- **VALID must stay asserted until handshake**: Dropping VALID before READY is seen can deadlock AXI channels silently in hardware; simulation often misses it — add a Xilinx Protocol Checker IP to the block design during bring-up.
- **Vivado 2025.1 new AXI Switch IP**: RTL-instantiable AXI Switch bridges interface types and widths without being confined to IP Integrator, unlike SmartConnect. Useful for future design expansion.
- **Vitis BSP xil_printf uses xparameters.h UART base address**: In 2023.x+ the peripheral base-address model replaced device-ID lookups; confirm XPAR_XUARTPS_0_BASEADDR in xparameters.h matches your KV260 PS UART configuration.
- **Ubuntu 24.04 + Vitis 2025.1 incompatibility reported**: Community reports Vitis 2025.1 fails to start on Ubuntu 24.04 — if developing on that distro, stay on 2024.2.2 or use a Docker/VM workaround until AMD issues a patch.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- **Write-response requirement**: AXI-Lite specifies a write is complete only upon receipt of BVALID + BREADY handshake on the response channel; writing a pattern to BRAM and immediately reading without waiting for BVALID risks stale data.
- **VALID must stay asserted**: ARM AXI spec IHI0022 and the Xilinx PG058 BRAM guide both state VALID must not be de-asserted before a handshake occurs; violations cause deadlock that synthesis tools do not flag — only protocol checkers catch this.
- **Ready/VALID deadlock rule**: A sender must not wait for READY before asserting VALID; doing so creates a circular dependency if the receiver also waits. Assert-and-hold pattern: drive VALID high, wait until READY is sampled high in the same clock edge.
- **Register Slice for timing closure**: Inserting a one-cycle AXI Register Slice IP on the interconnect path between Zynq PS and BRAM Controller breaks long combinational paths without changing observable protocol behavior — low-risk timing closure technique.
- **AXI-Stream TLAST for packet boundaries**: When using AXI-Stream (e.g. future DMA expansion), TLAST marks the final beat of a packet; the receiver must not de-assert TREADY until after TLAST is processed, or a stream can stall.
- **AXI-Stream DMA startup order**: Start the S2MM DMA receive channel before the upstream data producer begins sending; the AXI DMA pulls TREADY low after ~4 beats if not ready, according to PG021.
- **BRAM latency configuration**: Block Memory Generator (PG058) latency is configurable; if you increase it from the default, add matching wait cycles or a ready pipeline stage in the AXI BRAM Controller interface.

### Code Example

```c
/* AXI-Lite write with B-channel response poll */
#define BRAM0_BASE 0xA0000000UL

static inline void axi_bram_write32(uintptr_t base, uint32_t offset, uint32_t data)
{
    volatile uint32_t *addr = (volatile uint32_t *)(base + offset);
    *addr = data;
    /* AXI-Lite: no explicit B-channel in direct-mapped BRAM; AXI BRAM Controller
       absorbs the response internally, but add a dsb() to flush the write buffer. */
    __asm__ volatile ("dsb sy" ::: "memory");
}

static inline uint32_t axi_bram_read32(uintptr_t base, uint32_t offset)
{
    volatile uint32_t *addr = (volatile uint32_t *)(base + offset);
    uint32_t val = *addr;
    __asm__ volatile ("dsb sy" ::: "memory");
    return val;
}
```

### Relevance to Your Project

The KV260 bare-metal demo writes test patterns to BRAM0 at 0xA0000000 and BRAM1 at 0xA0010000 and reads them back. Inserting `dsb sy` memory barriers after each write ensures the Cortex-A53 write buffer is drained before the subsequent read; without this, the PS may return cached data rather than the PL-side BRAM value. The `dsb sy` idiom is essential for bare-metal AXI peripheral access on ARMv8.

## Vivado Block Design / IP Integrator

### Key Findings

- **Address Editor tab visibility**: The Address Editor tab only appears when the block design contains at least one AXI bus master. If missing, open it via Window → Address Editor.
- **Auto-assign and manual override**: Right-click in the Address Editor → Assign All auto-assigns base addresses to all AXI slaves; addresses can be overridden manually by clicking the cell. Segments must be power-of-2 aligned and non-overlapping.
- **BRAM Controller segment range**: For AXI BRAM Controller, the Range column in the Address Editor sets the accessible window. A 64 KB range is typical for small BRAM configs; set it to match the actual BRAM depth × width.
- **Re-validate after manual address changes**: After any manual address assignment, run Validate Design (F6) or `validate_bd_design` in Tcl; unvalidated changes may cause mismatches in the generated hardware handoff (.xsa).
- **New 2025.1 IP Integrator views**: Vivado 2025.1 adds dedicated "Clocking and Reset" and "Interrupts and AXI4-Lite" views in IP Integrator, making bus connectivity inspection easier without manually tracing wires.
- **Block automation for Zynq PS**: After adding the Zynq UltraScale+ MPSoC IP, run Block Automation to configure PS interfaces automatically; this creates M_AXI_HPM0_FPD or M_AXI_HPM0_LPD masters that connect to AXI Interconnect / SmartConnect.
- **Regenerate Layout before export**: Call Regenerate Layout in the block design canvas before exporting hardware (.xsa) to ensure the graphical representation matches the netlist, reducing confusing cross-tool errors.

### Code Example

```tcl
# Address assignment in Tcl (run inside Vivado project or source in batch mode)
open_bd_design [get_files *.bd]

# Assign all unassigned AXI slave segments automatically
assign_bd_address

# Override BRAM0 base address explicitly
set_property offset 0xA0000000 [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property range  64K         [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]

# Override BRAM1 base address
set_property offset 0xA0010000 [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_1_Mem0}]
set_property range  64K         [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_1_Mem0}]

validate_bd_design
save_bd_design
```

### Relevance to Your Project

Your `create_bd.tcl` script sets up the two AXI BRAM Controllers targeting 0xA0000000 (BRAM0) and 0xA0010000 (BRAM2). Scripting the address assignment with `assign_bd_address` followed by explicit overrides is the cleanest repeatable approach — it avoids manual GUI address entry when regenerating the block design from scratch in CI or on a new machine.

## Vivado TCL Scripting

### Key Findings

- **Non-project mode runs entirely in memory**: No project files are created; synthesis, implementation, and bitstream generation are driven by Tcl commands. Useful for CI pipelines where you want a clean, reproducible build artifact with no intermediate `.xpr` state.
- **Manual DCP checkpointing**: In non-project mode you must explicitly save design checkpoints. `write_checkpoint post_synth.dcp` after synthesis and `write_checkpoint post_route.dcp` after routing allows incremental reruns without full resynthesis.
- **Source file management**: Non-project mode requires `read_vhdl`, `read_xdc`, and `read_ip` calls for every source; the project mode `.xpr` does this automatically. Store source lists in a variable for maintainability.
- **Non-project mode is not faster**: An empirical benchmark (Vivado 2024.2) found both project and non-project modes had nearly identical runtime; the advantage is reproducibility and CI cleanliness, not speed.
- **`config_flows` for strategies**: Use `config_flows -synth_strategy {Vivado Synthesis Defaults}` or implementation strategies like `Performance_ExplorePostRoutePhysOpt` for targeted experiments.
- **Source `create_bd.tcl` inside project flow**: In project mode, source the block design TCL script via `source create_bd.tcl` then call `generate_target all [get_files *.bd]` to produce HDL wrappers before synthesis.

### Code Example

```tcl
#!/usr/bin/env tclsh
# Non-project batch build for KV260 AXI BRAM demo
# Run: vivado -mode batch -source build.tcl

set TOP       kv260_top
set PART      xck26-sfvc784-2LV-c
set BD_SCRIPT tcl/create_bd.tcl
set XDC       xdc/timing.xdc

# Read sources
read_vhdl vhdl/${TOP}.vhd

# Build block design (script must call save_bd_design internally)
source $BD_SCRIPT
generate_target all [get_files *.bd]

# Add top-level wrapper that instantiates the BD
make_wrapper -files [get_files *.bd] -top
read_vhdl [glob *.gen/sources_1/bd/*/hdl/*_wrapper.vhd]

read_xdc $XDC

# Synthesize
synth_design -top ${TOP}_wrapper -part $PART
write_checkpoint -force post_synth.dcp

# Implement
opt_design
place_design
route_design
write_checkpoint -force post_route.dcp

# Outputs
write_bitstream -force ${TOP}.bit
write_hw_platform -fixed -force ${TOP}.xsa
```

### Relevance to Your Project

Wrapping `create_bd.tcl` in a larger non-project batch script gives you a single `vivado -mode batch -source build.tcl` invocation that produces both `kv260_top.bit` and `kv260_top.xsa`. This eliminates GUI dependency for the build, making the demo fully reproducible from a fresh Vivado 2025.1 install.

## Vitis Bare-Metal / Standalone

### Key Findings

- **xil_printf vs stdio**: Vitis standalone BSP provides `xil_printf` as a lighter-weight alternative to `printf`. It uses the PS UART base address from `xparameters.h` (XPAR_XUARTPS_0_BASEADDR) and avoids bringing in the full C runtime, reducing bare-metal image size.
- **BSP available in embeddedsw on GitHub**: The Vitis BSP sources are on GitHub under `Xilinx/embeddedsw` with release tags matching tool versions; use `rel-2025.1` tag for Vitis 2025.1.
- **Peripheral base-address model (2023.x+)**: Device ID lookups (`XPAR_AXI_GPIO_0_DEVICE_ID`) have been replaced by base-address lookups (`XPAR_AXI_GPIO_0_BASEADDR`) in the generated `xparameters.h`. Use `XGpio_LookupConfig(XPAR_AXI_GPIO_BUTTONS_BASEADDR)` style calls.
- **Linker script pitfall — peripheral vs DDR**: Vitis-generated linker scripts can accidentally place `.data`/`.bss`/`.text` sections in the first mapped AXI peripheral space instead of DDR; always inspect the generated `lscript.ld` and verify all sections reside in DDR (ps8_ddr_0 or equivalent).
- **xil_printf output routing**: `xil_printf` routes to whichever UART is assigned `stdout` in the MSS file (BSP settings); on KV260, this is typically UART1 (MIO 38/39) which maps to the USB-UART bridge. Confirm the MSS setting matches your `xdc/` pin assignments.
- **Cache coherency for DMA**: When using AXI DMA, invalidate/flush the relevant cache lines (using `Xil_DCacheFlushRange` / `Xil_DCacheInvalidateRange`) around DMA buffer regions; the Cortex-A53 L1/L2 cache is not coherent with PL DMA by default.

### Code Example

```c
#include "xil_printf.h"
#include "xparameters.h"
#include "sleep.h"

/* Direct AXI-Lite BRAM access via memory-mapped I/O */
#define BRAM0_BASE ((volatile uint32_t *)0xA0000000UL)
#define BRAM1_BASE ((volatile uint32_t *)0xA0010000UL)

#define PATTERN_A  0xDEADBEEFUL
#define PATTERN_B  0xCAFEBABEUL

int main(void)
{
    xil_printf("KV260 AXI BRAM Test\r\n");

    /* Write patterns */
    BRAM0_BASE[0] = PATTERN_A;
    BRAM1_BASE[0] = PATTERN_B;

    /* DSB barrier ensures write buffer flush before read */
    __asm__ volatile ("dsb sy" ::: "memory");

    /* Read back and verify */
    uint32_t r0 = BRAM0_BASE[0];
    uint32_t r1 = BRAM1_BASE[0];

    if (r0 == PATTERN_A && r1 == PATTERN_B) {
        xil_printf("PASS: BRAM0=0x%08X BRAM1=0x%08X\r\n", r0, r1);
    } else {
        xil_printf("FAIL: BRAM0=0x%08X (exp 0x%08X) BRAM1=0x%08X (exp 0x%08X)\r\n",
                   r0, PATTERN_A, r1, PATTERN_B);
    }
    return 0;
}
```

### Relevance to Your Project

This matches the exact structure of your `main.c`: write patterns to BRAM0 and BRAM1, read back, print PASS/FAIL over USB-UART. The `dsb sy` barrier is the critical addition — without it the Cortex-A53 write buffer can cause a false PASS by returning the locally buffered write value rather than the actual PL BRAM value.

## XDC Timing Constraints

### Key Findings

- **Constraint application order matters**: Define clocks first, then I/O delays, then exceptions (`set_clock_groups`, `set_false_path`, `set_multicycle_path`). Placing exceptions before clocks can result in the exception being silently ignored.
- **Clock groups silence cross-domain timing**: `set_clock_groups -asynchronous` between the PS clock domain and PL clock domain tells the timing engine to ignore paths crossing that boundary — it does not make those crossings safe. Pair with proper CDC synchronizers in RTL.
- **Auto-derived generated clocks**: Vivado auto-derives generated clocks from PLL/MMCM outputs; these usually do not need explicit `create_generated_clock` constraints. Over-constraining generated clocks can slow routing.
- **set_input_delay / set_output_delay for I/O paths**: For AXI paths between PS and PL, the PS serves as both source and destination; use `set_false_path` on PS–PL interface paths or provide setup/hold values from the Zynq UltraScale+ datasheet.
- **UG903 (2025.2 ed.)**: The authoritative AMD XDC reference; the constraint ordering guidance and valid-command list are in Chapter 2.

### Code Example

```tcl
# Minimal XDC for KV260 AXI-BRAM demo
# Assumes 100 MHz PL clock sourced from PS via FCLK_CLK0

# Create the primary PL clock (FCLK_CLK0 = 100 MHz)
create_clock -period 10.000 -name clk_pl_0 [get_ports clk_pl_0]

# PS-to-PL AXI paths are internal to the PS; use false_path to avoid
# over-constraining the timing closure on AXI HP/GP interfaces
set_false_path -from [get_clocks clk_pl_0] -to [get_ports *]

# If adding async PL clock domains, declare them mutually asynchronous
# set_clock_groups -asynchronous -group [get_clocks clk_pl_0] \
#                                -group [get_clocks clk_pl_user]
```

### Relevance to Your Project

For a bare-metal AXI-BRAM demo the timing critical path is the PL fabric logic running at 100 MHz off the PS FCLK. The `create_clock` on `clk_pl_0` and `set_false_path` on output I/Os is the minimal viable XDC. Adding an AXI Register Slice between PS and BRAM Controller gives timing margin if closure fails at higher FCLK frequencies.

## Kria KV260 / K26 SoM

### Key Findings

- **Single 5 V power input**: The K26 SoM's internal supplies all derive from a single 5 V rail; PL I/O bank supplies (VCCO) are defined by the carrier card. The KV260 carrier sets these — check the KV260 schematic for VCCO values for the relevant MIO/EMIO banks.
- **MIO 38/39 = UART1 (USB-UART bridge)**: On the KV260, PS UART1 (MIO38=TX, MIO39=RX) connects to the on-board FTDI USB-UART bridge and appears as a USB serial port on the host. This is the `xil_printf` / `stdout` target.
- **Boot modes via BOOT_MODE strap pins**: The K26 SoM supports JTAG (0b0000), QSPI32 (0b0010), and SD/eMMC boot modes via MIO-resident strap pins; the KV260 carrier exposes a DIP switch for boot mode selection. For development, JTAG mode is used with Vitis/XSCT.
- **EMIO vs MIO**: PL-connected GPIOs use EMIO (Extendable MIO) routed from the PS GPIOx bank through the AXI GPIO or directly via EMIO signals. For the AXI BRAM demo, no GPIO is needed — the AXI HP/GP AXI master from the PS directly addresses BRAM through the interconnect.
- **K26 onboard memory**: 4 GB 64-bit DDR4, 512 Mb QSPI, 16 GB eMMC, 64 Kb EEPROM. For bare-metal, the linker script `ps8_ddr_0` section maps to DDR4 starting at 0x00000000.
- **Bare-metal on Cortex-A53**: Vitis targets APU (A53) bare-metal. Set the build target to `cortex-a53 (Application Processor)` in the domain configuration. EL1 is the typical bare-metal execution level for Vitis standalone apps.

### Code Example

```tcl
# Vivado XDC: constrain KV260 USB-UART (PS UART1 via MIO — no XDC needed for MIO)
# MIO pins are configured through PS block, not XDC.
# Example: configure UART1 in the Zynq PS block design Tcl

set_property -dict [list \
  CONFIG.PSU__UART1__PERIPHERAL__ENABLE   {1} \
  CONFIG.PSU__UART1__PERIPHERAL__IO       {MIO 38 .. 39} \
] [get_bd_cells zynq_ultra_ps_e_0]

# Verify in generated xparameters.h that stdout maps to UART1:
# #define STDOUT_BASEADDRESS    XPAR_PSU_UART_1_BASEADDR
```

### Relevance to Your Project

For USB-UART PASS/FAIL output to work, the PS block in Vivado must have UART1 enabled on MIO 38/39 and the Vitis BSP `stdin/stdout` MSS setting must point to `psu_uart_1`. This is the most common misconfiguration on fresh KV260 bare-metal projects where `xil_printf` produces no output.

## AMD/Xilinx Tool Updates (2025.1)

### Key Findings

- **Vivado 2025.1 released**: New device support for Versal AI Edge Gen 2, Versal Prime Gen 2, and Spartan UltraScale+.
- **New RTL-instantiable AXI Switch IP**: Unlike SmartConnect (IP Integrator only), the new AXI Switch IP can be instantiated directly in RTL/VHDL, bridging AXI interface types and data widths. Useful for custom interconnect fabrics outside IP Integrator.
- **IP Integrator new views**: "Clocking and Reset" view and "Interrupts and AXI4-Lite" view added to the IP Integrator canvas, improving visibility of common connectivity patterns.
- **Open-source components (Linux)**: For Linux-based Zynq flows (not bare-metal), Vivado 2025.1 aligns with Linux kernel 6.12, U-Boot 2025.01, and TF-A 2.12 for Zynq UltraScale+.
- **Vitis 2025.1 Ubuntu 24.04 issue**: Community reports Vitis 2025.1 GUI fails to start on Ubuntu 24.04 LTS; the workaround is to use Ubuntu 22.04 or run Vitis in a container. AMD has not published an official fix date as of the search date.
- **New pblock planner**: A GUI-based pblock planner for grouping equivalent address spaces was added in 2025.1, primarily targeting Versal Prime Gen 2 and AI Edge Gen 2 devices.

### Code Example

```tcl
# Vivado 2025.1: Check installed IP catalog version for AXI BRAM Controller
# Run inside Vivado Tcl console to confirm IP versions available

foreach ip [get_ipdefs -filter {VLNV =~ *axi_bram_ctrl*}] {
  puts "Found IP: $ip"
}
# Expected output on 2025.1:
# Found IP: xilinx.com:ip:axi_bram_ctrl:4.1

# New AXI Switch IP (2025.1+): query its existence
foreach ip [get_ipdefs -filter {VLNV =~ *axi_switch*}] {
  puts "Found IP: $ip"
}

# Example: update an existing IP instance to latest catalog version
update_ip_catalog -rebuild -scan_changes
upgrade_ip [get_ips axi_bram_ctrl_0]
report_ip_status
```

### Relevance to Your Project

Running `update_ip_catalog` and `upgrade_ip` on your existing `axi_bram_ctrl` instances when moving from an older Vivado version to 2025.1 ensures you pick up any AXI BRAM Controller bug fixes or parameter changes. The new "Interrupts and AXI4-Lite" view in IP Integrator is directly useful for tracing your PS M_AXI_HPM connections to the two BRAM Controllers.
