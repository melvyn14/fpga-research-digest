## Executive Summary
- **The most common AXI-Lite deadlock bug is asserting VALID conditional on READY** — the spec explicitly forbids this (a master/slave must raise VALID unconditionally whenever it wants to transfer, regardless of READY's state); the safe direction is READY depending on VALID, never the reverse. Worth a direct check on any hand-written control logic that sits in front of the two `axi_bram_ctrl` instances.
- **`validate_bd_design` does real connectivity/parameter-propagation checking; `regenerate_bd_layout` is purely cosmetic** — running only the latter after editing `create_bd.tcl`-derived state gives false confidence that BRAM width/mode negotiation actually succeeded.
- **Address Editor alignment is a hard rule, not a suggestion**: a memory range's base address must have enough trailing zero bits to match the range size — directly relevant if BRAM0 (`0xA0000000`)/BRAM2 (`0xA0010000`) ranges are ever resized away from their current 64KB-aligned offsets.
- **Vitis 2025.2 makes the Unified IDE the default and deprecates Classic Vitis IDE** — this project is pinned to 2025.1 (still has Classic IDE available), but any future toolchain bump should budget time for the BSP/platform-configuration workflow changing shape.
- **Kria SOMs force boot from read-only QSPI firmware by design** (anti-brick measure) — for a pure bare-metal-only workflow with no PetaLinux in the loop, JTAG boot mode is the supported iteration path, not direct QSPI reprogramming.

## AXI Protocol / AXI-Lite / AXI-Stream
### Key Findings
- The single most cited AXI handshake mistake: asserting VALID *based on* the state of READY. The spec requires the opposite dependency — VALID must be raised whenever the source wants to transfer, independent of READY; READY is the side that's allowed to depend on VALID. Get this backwards and both sides can wait forever for each other.
- A second common bug found even in Xilinx's own AXI-Lite example/demo cores: allowing `AWVALID && AWREADY` and `ARVALid && ARREADY` to both fire in the same cycle without resolving which one's request actually gets serviced, silently dropping one of the two transactions.
- `BVALID` may only be asserted by the slave after the corresponding `WVALID`/`WREADY` handshake for that same write has already completed — asserting it earlier or simultaneously is a protocol violation that produces undefined behavior on stricter verification IP, even if it happens to work on a given board.
- Combinatorial paths from input VALID directly to output READY (or vice versa) are explicitly disallowed by the AXI spec — even though some Xilinx-generated cores have shipped with this pattern, it is not spec-compliant and tends to worsen timing closure (longer round-trip per handshake) without saving real logic.
- Backpressure is the most under-tested case: a master holding `BREADY` low must cause the slave to correctly hold/lower `AWREADY`/`WREADY`; simulation testbenches that always drive READY high never exercise this path and let the bug ship.

### Code Example
```vhdl
-- Correct handshake direction: READY depends on internal busy state and VALID,
-- never asserts VALID conditional on the other side's READY.
process(s_axi_aclk)
begin
  if rising_edge(s_axi_aclk) then
    if s_axi_aresetn = '0' then
      awready_r <= '0';
      wready_r  <= '0';
      bvalid_r  <= '0';
    else
      -- Only raise AWREADY/WREADY together once both AW and W are valid
      -- (synchronizes the two channels) and no prior write is still pending.
      if s_axi_awvalid = '1' and s_axi_wvalid = '1' and bvalid_r = '0' then
        awready_r <= '1';
        wready_r  <= '1';
      else
        awready_r <= '0';
        wready_r  <= '0';
      end if;

      -- BVALID only goes high the cycle AFTER the AW/W handshake completed.
      if awready_r = '1' and wready_r = '1' then
        bvalid_r <= '1';
      elsif s_axi_bready = '1' then
        bvalid_r <= '0';
      end if;
    end if;
  end if;
end process;

s_axi_awready <= awready_r;
s_axi_wready  <= wready_r;
s_axi_bvalid  <= bvalid_r;
```

### Relevance to Your Project
Both BRAM0 and BRAM2 sit behind the stock `axi_bram_ctrl` IP, which already implements spec-correct handshaking, so the project isn't exposed to these bugs today. The VALID-depends-on-READY antipattern above is the first thing to check if `kv260_top.vhd` ever grows a hand-written AXI-Lite peripheral (e.g., a status/control register for selecting which BRAM pattern to run) instead of relying entirely on `axi_bram_ctrl` + BRAM.

## Vivado Block Design / IP Integrator
### Key Findings
- Connection Automation, when run on an `axi_bram_ctrl` instance, will auto-insert an AXI Interconnect/SmartConnect and a Processor System Reset IP and wire them to the Zynq PS — convenient in the GUI, but anything it silently adds needs to be accounted for the moment `create_bd.tcl` is hand-maintained instead of being a literal GUI export.
- Block Automation on a freshly dropped Zynq/Zynq UltraScale+ PS block (with "Apply Board Preset" checked) configures DDR/FIXED_IO and board-default PS settings in one step — useful at initial bring-up but it can silently overwrite manually-tuned PS configuration if re-run after the fact.
- `validate_bd_design` performs the real check: connectivity, AXI4-vs-AXI4-Lite interface compatibility, data-width negotiation, and BRAM operating-mode propagation between `axi_bram_ctrl` and its Block Memory Generator. `regenerate_bd_layout` only redraws the graphical layout and does zero connectivity checking — relying on it alone after an edit is a false sense of security.
- The Address Editor becomes active only once a master with an address space (Zynq/Zynq UltraScale+ PS, MicroBlaze, etc.) is present in the diagram; manual offset/range edits there are immediately validated for alignment, not deferred to synthesis time.

### Code Example
```tcl
# Non-interactive validate/regenerate/save sequence, safe to run right
# before generate_target / write_bitstream in a headless build.
open_bd_design [get_files kv260_bd.bd]
validate_bd_design
regenerate_bd_layout
save_bd_design

if {[llength [get_msg_config -severity {CRITICAL WARNING}]] > 0} {
    puts "ERROR: block design has unresolved critical warnings, aborting build"
    exit 1
}
```

### Relevance to Your Project
A `create_bd.tcl` that explicitly instantiates and connects both `axi_bram_ctrl` instances (rather than depending on GUI automation having been run once and frozen into a checked-in `.bd`) is the right call for reproducible builds. If the design is ever touched interactively in the GUI again, re-export with `write_bd_tcl` and diff it against the existing script rather than assuming GUI automation reproduces byte-identical connectivity.

## Vivado TCL Scripting
### Key Findings
- Non-Project Mode keeps the entire design in memory with no `.xpr` on disk — the script alone owns source ordering and there is no Vivado-managed staleness detection; every run re-reads sources from scratch unless checkpointing (`write_checkpoint`/`read_checkpoint`) is added explicitly between stages.
- Standard headless invocation: `vivado -mode batch -source script.tcl -tclargs <args>`, which runs to completion and exits — `-mode tcl` instead opens an interactive Tcl console useful only while developing/debugging a script.
- `connect_bd_net` is for plain nets (clocks, resets, single-bit signals); `connect_bd_intf_net` is specifically for interface pins (AXI4, AXI4-Lite, BRAM_PORT) — mixing them up is a common copy-paste error that produces a confusing "incompatible interface" error rather than a silent no-op.
- `validate_bd_design` is what actually propagates parameters between connected IP (width negotiation, BRAM operating mode) — it should be called immediately after the last `connect_bd_intf_net`/`connect_bd_net` in a script, before `save_bd_design`, not only at the very end of the whole build.
- A fully scripted, non-project build is the only way to guarantee bit-identical output across machines/CI runs, since project settings, IP configuration, and constraints all live in version-controlled text rather than a binary `.xpr`/IP-cache state that can silently drift.

### Code Example
```tcl
# Pattern for two AXI BRAM controllers with table-driven, version-stable
# address assignment — extendable if a third BRAM is ever added.
foreach {ctrl base} {axi_bram_ctrl_0 0xA0000000 axi_bram_ctrl_2 0xA0010000} {
    create_bd_cell -type ip -vlnv xilinx.com:ip:axi_bram_ctrl:4.1 $ctrl
    set bmg "${ctrl}_bmg"
    create_bd_cell -type ip -vlnv xilinx.com:ip:blk_mem_gen:8.4 $bmg

    connect_bd_intf_net [get_bd_intf_pins zynq_ultra_ps_e_0/M_AXI_HPM0_FPD] \
                         [get_bd_intf_pins ${ctrl}/S_AXI]
    connect_bd_intf_net [get_bd_intf_pins ${ctrl}/BRAM_PORTA] \
                         [get_bd_intf_pins ${bmg}/BRAM_PORTA]

    set_property offset $base [get_bd_addr_segs "zynq_ultra_ps_e_0/Data/SEG_${ctrl}_Mem0"]
}

validate_bd_design
save_bd_design
```

### Relevance to Your Project
This table-driven shape matches the described two-BRAM layout in `create_bd.tcl`. Extending the `foreach` table (rather than hand-copying another `create_bd_cell`/`connect_bd_intf_net` block) is the safest way to add a third BRAM or AXI-Lite peripheral later, since it keeps the BRAM0/BRAM2 address assignment centralized — the two existing bases currently differ only in their low 16 bits, which is exactly the kind of typo a copy-paste block invites.

## Vitis Bare-Metal / Standalone
### Key Findings
- `xil_printf` supports a restricted format set (`%d`, `%l`, `%x`, `%c`, `%s`, no floating point) and trades richness for a much smaller code/stack footprint than libc `printf` — relevant when DDR/OCM budget is tight in a minimal bare-metal app like this one.
- The standalone BSP's stdin/stdout UART is a platform-component configuration choice, not something auto-detected from the hardware — picking the wrong UART instance relative to the board's actual USB-UART bridge is a common failure mode where the application runs correctly but PASS/FAIL text never appears.
- GIC interrupt setup on Cortex-A53 under Zynq UltraScale+ standalone BSP is multi-step: `XScuGic_CfgInitialize` → `Xil_ExceptionRegisterHandler` → `XScuGic_Connect`, and a separate `XScuGic_Enable(&GicInst, <intr_id>)` call afterward — omitting the enable call leaves a correctly-registered handler that simply never fires, with no error reported.
- Vitis auto-generates a default linker script (`lscript.ld`) from the hardware platform's memory map; after re-exporting hardware (a new XSA) for an existing app, the linker script's region base/size should be re-checked — a stale region inherited from an older XSA can silently place sections outside valid DDR/OCM.
- `xil_exception.h` provides nested-interrupt-handling macros usable on Cortex-A53 (64-bit), Cortex-A9, and Cortex-R5 — only relevant if a future revision moves the BRAM test trigger from polling to an interrupt source (timer, AXI GPIO "go" pin, etc.).

### Code Example
```c
#include "xil_printf.h"
#include "xparameters.h"
#include "xil_io.h"

#define BRAM0_BASEADDR XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR /* 0xA0000000 */
#define BRAM2_BASEADDR XPAR_AXI_BRAM_CTRL_1_S_AXI_BASEADDR /* 0xA0010000 */

int test_bram_word(u32 base, u32 offset, const char *name) {
    u32 pattern = 0x5A5A5A5A;
    Xil_Out32(base + offset, pattern);
    u32 readback = Xil_In32(base + offset);
    if (readback != pattern) {
        xil_printf("%s @0x%x: FAIL (wrote 0x%x, read 0x%x)\r\n",
                   name, offset, pattern, readback);
        return 1;
    }
    xil_printf("%s @0x%x: PASS\r\n", name, offset);
    return 0;
}
```

### Relevance to Your Project
This mirrors the write/readback/PASS-FAIL idiom described for `main.c`. If PASS/FAIL output silently stops appearing over USB-UART while the board otherwise seems to boot, check the BSP's stdout UART selection in the platform component first — it is a far more common cause than an actual AXI/BRAM hardware fault. Re-check `lscript.ld` after any hardware (XSA) re-export, since the project regenerates its block design from `create_bd.tcl` and could pick up a changed memory map.

## XDC Timing Constraints
### Key Findings
- `set_input_delay`/`set_output_delay` model the external system-level delay relative to a clock edge at a primary I/O port — the "max" input delay value is effectively the driving device's clock-to-out delay as observed at the FPGA pin, not the FPGA's own setup requirement, and the value can legitimately be negative depending on data/clock phase. This is a frequent point of confusion when porting datasheet numbers directly into XDC syntax.
- Every clock-domain crossing needs an explicit `set_clock_groups -asynchronous` (or equivalent false-path) declaration; left undeclared, Vivado times the crossing as if synchronous by default, which can produce nonsensical timing reports in either direction (spurious failures, or a false "pass" on a path that's actually a metastability risk).
- Current best practice for true CDC paths favors `set_max_delay -datapath_only` over a blanket `set_false_path`, since the latter disables ALL timing analysis on the path (including hold checks), whereas `-datapath_only` only relaxes the setup relationship while still bounding the propagation delay — combined with tagging registers `ASYNC_REG` to force adjacent placement and minimize skew.
- For Zynq/Zynq UltraScale+ designs, the PS-generated fabric clock can be constrained directly off the PS clock pin, e.g. `create_clock -period 10.000 -name clk_fpga_0 [get_pins {zynq_ultra_ps_e_0/pl_clk0}]`, useful when adding custom logic downstream of the PS that Vivado's automatic clock inference doesn't already cover.

### Code Example
```tcl
# Board-level XDC additions only needed once direct PL I/O is added
# (not required for the current pure PS<->PL AXI-only BRAM path).
create_clock -period 8.000 -name pl_clk0 [get_ports pl_clk0_p]

set_input_delay  -clock pl_clk0 -max 1.5 [get_ports {ext_data[*]}]
set_input_delay  -clock pl_clk0 -min 0.3 [get_ports {ext_data[*]}]
set_output_delay -clock pl_clk0 -max 1.2 [get_ports {ext_ctrl[*]}]
set_output_delay -clock pl_clk0 -min -0.5 [get_ports {ext_ctrl[*]}]

# Prefer -datapath_only over a blanket false path for genuine CDCs.
set_max_delay -datapath_only -from [get_clocks clk_fpga_0] -to [get_clocks pl_clk0] 4.0
```

### Relevance to Your Project
The design is purely PS-driven AXI on a single PS-generated FCLK domain feeding both BRAM controllers through `kv260_top.vhd`, so none of the board-level I/O delay constraints apply today — they only matter once a signal crosses the board boundary through a physical pin. The CDC guidance becomes directly relevant the moment a PL-side clock independent of the PS FCLK (a free-running oscillator, an MMCM-derived clock for new logic) is added.

## Kria KV260 / K26 SoM
### Key Findings
- Kria SOMs are deliberately locked to boot from read-only QSPI boot firmware to prevent bricking the device — for a bare-metal-only workflow with no PetaLinux/Linux image involved, JTAG boot mode is the supported iteration path during development, not direct QSPI image reprogramming.
- The official Kria documentation describes a baremetal AXI-BRAM reference flow that matches this project's shape closely: add an AXI BRAM Controller, run Connection Automation to tie its `S_AXI` to `M_AXI_HPM0_FPD`, configure single-BRAM-interface mode, and explicitly disable any unused second HPM master port rather than leaving it dangling.
- Since the 2022.1 Kria Linux images, the default "k26-starter-kits" shipped bitstream has effectively no functional PL logic beyond an EMIO mapping for carrier-board fan control — a from-scratch bare-metal/PL design like this one genuinely starts from near-empty fabric, not inheriting hidden default logic from the shipped image.
- Most peripherals on the KV260 carrier connect through MIO/EMIO as usual, but the PMODs and RPi header on the related KR260 carrier connect directly into K26 PL fabric, not MIO/EMIO — worth knowing if this project (or a future variant) ever targets the KR260 carrier instead of KV260.
- A mid-2026 community guide ("Bare-metal 4K Streaming on KV260: The 2025.2 Guide") demonstrates a from-scratch Vivado/Vitis 2025.2 PL design feeding a bare-metal app directly to the DisplayPort output — confirming the bare-metal + 2025.x toolchain path on this exact board remains an actively maintained and current workflow, not a dead-end approach.

### Code Example
```tcl
# PS configuration matching a single-HPM-master, BRAM0/BRAM2 pattern;
# explicitly disabling the unused second GP master avoids a common
# validate_bd_design critical-warning source (enabled-but-unconnected port).
set_property -dict [list \
    CONFIG.PSU__USE__M_AXI_GP0 {1} \
    CONFIG.PSU__USE__M_AXI_GP1 {0} \
    CONFIG.PSU__MAXIGP0__DATA_WIDTH {32} \
] [get_bd_cells zynq_ultra_ps_e_0]
```

### Relevance to Your Project
This matches the documented official Kria baremetal AXI-BRAM pattern almost exactly — both BRAM0 and BRAM2 feeding off a single HPM master. Worth confirming in `create_bd.tcl` that any unused second HPM master is explicitly disabled rather than merely unconnected, and worth confirming the development boot mode used for iterating on this bare-metal app is JTAG rather than QSPI, given the read-only-QSPI-firmware lockdown on Kria SOMs.

## AMD/Xilinx Tool Updates
### Key Findings
- Vivado 2025.1 adds the ability to boot the processing system first and dynamically load the PL on the fly (faster OS bring-up with a more flexible boot sequence) — primarily aimed at Linux-based flows, not directly applicable to a pure bare-metal app, but a useful platform capability to be aware of on this toolchain version.
- A fully customizable RTL-based AXI Switch IP is new in 2025.1, serving as a bridge between different AXI interface types and widths — not needed for the current single-HPM-master BRAM0/BRAM2 layout, but relevant if a future revision needs to bridge AXI4-Full and AXI4-Lite peripherals on the same interconnect.
- Vivado 2025.2 (the release after the one this project uses) changes the AMD IP configuration file format from XML to JSON for better revision-control diffing and faster loading, and adds a new Pblock planner and a modernized IDE look-and-feel with light/dark themes.
- Vitis 2025.2 makes the Unified IDE the default; the Classic Vitis IDE is deprecated starting with that release. This project on 2025.1 still has Classic IDE available, but any future bump to 2025.2+ should budget time for BSP/platform-configuration workflow differences if following older Classic-IDE-based bare-metal tutorials.
- AXI BRAM Controller (PG078) v4.1 — the IP underlying both BRAM0 and BRAM2 in this project — supports optional ECC in single- and dual-port configurations (`C_ECC = 1`); not needed today but a known lever if BRAM reliability becomes a concern as test patterns scale up.

### Code Example

### Relevance to Your Project
2025.1 remains current and stable for this design — none of the 2025.1 IP-level changes touch `axi_bram_ctrl` or the Zynq UltraScale+ PS block. If/when the toolchain is bumped to 2025.2+, re-run `validate_bd_design` after the first open of the block design on the new version (IP re-customization prompts on cross-version bumps are routine), and budget extra time for the Vitis workflow if migrating away from Classic IDE, since 2025.2 defaults to the Unified IDE.
