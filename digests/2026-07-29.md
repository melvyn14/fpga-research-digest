# FPGA Research Digest - 2026-07-29

## Executive Summary

- **Vivado 2025 AXI address-decode bug**: A confirmed regression in Vivado 2025.x limits custom AXI-full/AXI-Lite peripherals to a 1 KB usable address space regardless of the configured address width parameter — directly relevant to your BRAM0/BRAM2 windows at 0xA0000000 and 0xA0010000. Use the AMD AXI BRAM Controller IP (pg078) rather than a custom slave to avoid this issue.
- **AXI BRAM Controller byte vs word addressing**: The AXI BRAM Controller addresses bytes while the underlying BRAM addresses words. A 32-bit wide BRAM accessed at byte offset 0x4 maps to BRAM word address 1, not 4 — a common source of PASS/FAIL mismatches in read-back tests.
- **Kria KV260 JTAG bare-metal flow**: Placing the board in JTAG boot mode (via the mode pins or XSDB) and downloading FSBL + bitstream + application .elf is the fastest iteration loop for PS-to-PL connectivity testing — no SD card reflash required.
- **Vivado 2025.2 AXI SmartConnect**: The new ultra-low-area mode (`STRATEGY` parameter) for AXI SmartConnect reduces LUT overhead in designs with few masters/slaves, useful for keeping your KV260 top-level resource budget small.
- **xil_printf limitation**: `xil_printf` does not support `%f`; use only `%d`, `%x`, `%s`, `%c`, `%l` in your bare-metal UART print calls. Mixing in `printf` from the C stdlib pulls in a larger BSP and can cause linker-script conflicts.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- **VALID/READY handshake rule**: Once a master asserts `AWVALID` or `WVALID`, it must hold the signal and all associated payload signals stable until the corresponding `AWREADY`/`WREADY` is received. Deasserting early causes protocol violations and silent data corruption.
- **AXI-Lite write response channel (BVALID/BREADY)**: Masters must consume the write response (`BVALID`) before issuing a new write address on `AWVALID`. Polling the AXI BRAM Controller without draining `BVALID` can stall the interconnect.
- **AXI-Stream TLAST**: In AXI4-Stream, `TLAST` marks the last beat of a packet. FIFO Generator IP in AXI-Stream mode uses TLAST to track packet boundaries; omitting it causes FIFO to never assert empty correctly.
- **Vivado 2025 1 KB address-space bug**: Confirmed on the Digilent forum — custom AXI-full peripherals created via the "Create and Package New IP" wizard in Vivado 2025 have a broken address-width parameter; the auto-generated RTL decodes only 10 address bits. Workaround: use AMD's catalog IP (AXI BRAM Controller, AXI GPIO) instead of the scaffold, or patch the generated `*_S_AXI.vhd` to extend the address decode manually.
- **AXI-Lite read channel ordering**: `ARVALID`/`ARREADY` handshake must complete before `RVALID`/`RREADY`. The AXI BRAM Controller in single-port mode adds one extra read-latency cycle; account for this in polling loops by reading twice and discarding the first result if using a tight back-to-back read.

### Code Example

```vhdl
-- AXI-Lite write state machine skeleton (safe VALID hold pattern)
type axi_wr_state_t is (IDLE, ADDR, DATA, RESP);
signal wr_state : axi_wr_state_t := IDLE;

process(clk)
begin
  if rising_edge(clk) then
    case wr_state is
      when IDLE =>
        s_axi_awvalid <= '0'; s_axi_wvalid <= '0';
        if start_write = '1' then
          s_axi_awaddr  <= target_addr;
          s_axi_wdata   <= write_data;
          s_axi_wstrb   <= "1111";
          s_axi_awvalid <= '1';
          s_axi_wvalid  <= '1';
          wr_state <= ADDR;
        end if;
      when ADDR =>
        -- Hold AWVALID until AWREADY
        if s_axi_awready = '1' then
          s_axi_awvalid <= '0';
          wr_state <= DATA;
        end if;
      when DATA =>
        -- Hold WVALID until WREADY
        if s_axi_wready = '1' then
          s_axi_wvalid <= '0';
          s_axi_bready <= '1';  -- ready to accept response
          wr_state <= RESP;
        end if;
      when RESP =>
        if s_axi_bvalid = '1' then
          s_axi_bready <= '0';
          wr_state <= IDLE;
        end if;
    end case;
  end if;
end process;
```

### Relevance to Your Project

Your `main.c` performs bare-metal memory-mapped writes directly to `0xA0000000` (BRAM0) and `0xA0010000` (BRAM2). The Cortex-A53's AXI master holds up VALID signals correctly because the processor handles the handshake in hardware — but if you ever add a VHDL AXI master wrapper or custom DMA, the state machine above is the safe pattern. The `BVALID` drain issue is relevant if you extend to burst writes.

## Vivado Block Design / IP Integrator

### Key Findings

- **`apply_bd_automation` surprises**: The automation command infers connections from port names and IP metadata, but can make wrong choices (e.g., connecting a data clock to a config clock input). Prefer explicit `connect_bd_net` / `connect_bd_intf_net` calls in TCL scripts for reproducibility.
- **Address Editor after adding IP**: After adding a new AXI slave IP to a block design, run `assign_bd_address` in TCL or use the Address Editor GUI. Missing this step causes synthesis to succeed but runtime accesses to silently fail.
- **Regenerate output products**: After editing any IP parameter, regenerate output products (`generate_target all [get_files *.bd]`) before synthesis. Stale output products from prior parameter-propagation runs are a common cause of mismatched interfaces.
- **Version-locked TCL exports**: BD TCL files exported with `write_bd_tcl` are tied to the IP catalog version. Running a 2025.1-exported script under 2025.2 may fail on version checks — use `set_property ip_repo_paths` and `update_ip_catalog` at the top of the script to pre-validate.
- **Validate design before synthesis**: `validate_bd_design` catches unconnected mandatory ports and address-segment conflicts before the slow synthesis step.

### Code Example

```tcl
# Minimal block design setup for PS + AXI BRAM Controller (reproducible)
create_bd_design "kv260_bd"

# Zynq UltraScale+ PS
set ps [create_bd_cell -type ip -vlnv xilinx.com:ip:zynq_ultra_ps_e:3.5 zynq_ultra_ps_e_0]
apply_bd_automation -rule xilinx.com:bd_rule:zynq_ultra_ps_e \
  -config {apply_board_preset "1"} [get_bd_cells zynq_ultra_ps_e_0]

# AXI BRAM Controller
set bram_ctrl [create_bd_cell -type ip \
  -vlnv xilinx.com:ip:axi_bram_ctrl:4.1 axi_bram_ctrl_0]
set_property CONFIG.DATA_WIDTH {32} $bram_ctrl
set_property CONFIG.SINGLE_PORT_BRAM {1} $bram_ctrl

# Block Memory Generator (True Dual Port)
set bram [create_bd_cell -type ip \
  -vlnv xilinx.com:ip:blk_mem_gen:8.4 blk_mem_gen_0]
set_property CONFIG.Memory_Type {True_Dual_Port_RAM} $bram

# Connect AXI master port from PS to BRAM controller
connect_bd_intf_net [get_bd_intf_pins zynq_ultra_ps_e_0/M_AXI_HPM0_FPD] \
  [get_bd_intf_pins axi_bram_ctrl_0/S_AXI]

# Connect BRAM controller to BRAM
connect_bd_intf_net [get_bd_intf_pins axi_bram_ctrl_0/BRAM_PORTA] \
  [get_bd_intf_pins blk_mem_gen_0/BRAM_PORTA]

# Assign addresses
assign_bd_address [get_bd_addr_segs axi_bram_ctrl_0/S_AXI/Mem0]
set_property offset 0xA0000000 \
  [get_bd_addr_segs zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0]
set_property range 64K \
  [get_bd_addr_segs zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0]

validate_bd_design
save_bd_design
```

### Relevance to Your Project

Your `create_bd.tcl` script instantiates two BRAM controllers at `0xA0000000` and `0xA0010000`. The `assign_bd_address` + explicit offset/range pattern above is the correct reproducible approach. If you notice the two address segments overlapping in the Address Editor, it is because the default range assigned is larger than 64 KB — manually setting `range 64K` keeps the two 0x10000-apart windows non-overlapping.

## Vivado TCL Scripting

### Key Findings

- **Non-project mode**: Use `read_vhdl`, `read_xdc`, `synth_design`, `opt_design`, `place_design`, `route_design`, `write_bitstream` in sequence for a fully scripted flow without a `.xpr` project file. Faster in CI and avoids project-file corruption issues.
- **`write_bd_tcl` vs. `write_project_tcl`**: `write_bd_tcl` exports only the block design; `write_project_tcl` exports the full project including file sets, runs, and board files. For a source-control-friendly repo, `write_bd_tcl` is usually the right choice.
- **Only changed parameters are exported**: Default IP parameters are not written to the exported TCL. This means importing a script on a fresh tool installation with a different IP catalog version may silently use different defaults — always pin critical parameters explicitly in the TCL.
- **`get_bd_cells -hierarchical`**: When block designs contain hierarchical groupings, plain `get_bd_cells` only searches the top level. Use the `-hierarchical` flag to reach nested cells.
- **`report_utilization -file`**: Run this at the end of implementation in the TCL script to capture a utilization snapshot without opening the GUI.

### Code Example

```tcl
# Non-project mode implementation flow for KV260 bare-metal demo
set part "xck26-sfvc784-2LV-c"

read_vhdl   [glob ./vhdl/*.vhd]
read_xdc    [glob ./xdc/*.xdc]
read_bd     ./bd/kv260_bd.bd

synth_design  -top kv260_top -part $part -mode out_of_context
opt_design
place_design
phys_opt_design
route_design

write_bitstream -force ./output/kv260_top.bit
report_utilization  -file ./output/utilization.rpt
report_timing_summary -file ./output/timing.rpt -warn_on_violation

# Check for timing violations and fail the script if any exist
set wns [get_property STATS.WNS [get_runs impl_1]]
if {$wns < 0} {
  puts "ERROR: Timing not met. WNS = $wns ns"
  exit 1
}
```

### Relevance to Your Project

Your `create_bd.tcl` already follows the explicit-connection pattern. Adding the non-project synthesis flow above means you can rebuild the entire bitstream from source with one `vivado -mode batch -source build.tcl` command — valuable for reproducible CI. The WNS check prevents silently shipping a design with setup-time violations.

## Vitis Bare-Metal / Standalone

### Key Findings

- **UART BSP parameter**: For KV260, set `standalone_stdin` and `standalone_stdout` to `psu_uart_1` in the BSP settings. If you see garbled output, check this setting first — it defaults to `psu_uart_0` on some board presets, but the KV260 USB-UART bridge connects to UART1.
- **`xil_printf` format support**: Only `%d`, `%i`, `%u`, `%x`, `%X`, `%o`, `%c`, `%s`, `%l` are supported. `%f` is not implemented. Using `%f` silently prints nothing and advances the format pointer, corrupting subsequent format arguments.
- **Regenerate BSP after XDC/BD changes**: Any time you change the block design (add IP, change addresses), regenerate the BSP in Vitis. The `xparameters.h` constants (`XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR`) are derived from the hardware handoff `.xsa` file and go stale if you skip regeneration.
- **Linker script DDR placement**: The auto-generated `lscript.ld` allocates all available DDR to the application. For a tiny bare-metal demo, the defaults are fine, but if you add a second processor domain (e.g., R5), manually partition the DDR regions in both linker scripts to avoid overlap.
- **Interrupt controller (GIC)**: The Cortex-A53 on Zynq UltraScale+ uses the GICv2. `XScuGic_Connect` registers a handler; `XScuGic_Enable` enables the specific interrupt ID. The AXI BRAM Controller does not generate interrupts, but if you add a custom IP with an interrupt output, wire it to `pl_ps_irq0[0:0]` in the block design and register it at GIC interrupt ID 121.

### Code Example

```c
#include "xparameters.h"
#include "xil_printf.h"
#include "xil_io.h"

#define BRAM0_BASE  XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR
#define BRAM2_BASE  XPAR_AXI_BRAM_CTRL_1_S_AXI_BASEADDR
#define TEST_PATTERN 0xDEADBEEFU

/* Write a pattern to every 32-bit word in a BRAM region, then read back */
int bram_loopback_test(u32 base, u32 size_bytes) {
    u32 offset, readback;
    /* Write phase */
    for (offset = 0; offset < size_bytes; offset += 4)
        Xil_Out32(base + offset, TEST_PATTERN ^ offset);
    /* Data memory barrier before read-back */
    dsb();
    /* Verify phase */
    for (offset = 0; offset < size_bytes; offset += 4) {
        readback = Xil_In32(base + offset);
        if (readback != (TEST_PATTERN ^ offset)) {
            xil_printf("FAIL @ 0x%08X: wrote 0x%08X, read 0x%08X\r\n",
                       base + offset, TEST_PATTERN ^ offset, readback);
            return -1;
        }
    }
    return 0;
}

int main(void) {
    xil_printf("KV260 AXI-BRAM loopback test\r\n");
    if (bram_loopback_test(BRAM0_BASE, 0x10000) == 0)
        xil_printf("BRAM0 PASS\r\n");
    if (bram_loopback_test(BRAM2_BASE, 0x10000) == 0)
        xil_printf("BRAM2 PASS\r\n");
    return 0;
}
```

### Relevance to Your Project

Your existing `main.c` does PS-to-PL pattern writes and read-backs using `Xil_Out32`/`Xil_In32`. The `dsb()` (Data Synchronization Barrier) call above is important: without it, the Cortex-A53 may reorder the read-back before the write has propagated through the AXI interconnect, giving false FAILs. Also note that `XPAR_AXI_BRAM_CTRL_1_S_AXI_BASEADDR` maps to whichever BRAM controller is instance 1 in your BSP — verify it matches 0xA0010000 in `xparameters.h`.

## XDC Timing Constraints

### Key Findings

- **K26 SOM trace delays**: When constraining I/O on the KV260 carrier card, the physical trace length from the MPSoC package through the SOM board-to-board connector to the carrier card must be included in `set_input_delay` / `set_output_delay`. AMD provides a Trace Delay File (XTP688) with per-pin values.
- **Clock group asynchronous**: PL clocks generated from the PS PLL and clocks from external oscillators on the carrier card are asynchronous. Declare them with `set_clock_groups -asynchronous` to prevent Vivado from trying (and failing) to compute a common period between them.
- **PS to PL clock constraints**: Clocks driven from the PS (`pl_clk0`) are automatically constrained by the Zynq UltraScale+ IP; you do not need to add a `create_clock` constraint for them. Adding a duplicate `create_clock` on the same net causes a multi-driven clock warning and unpredictable timing results.
- **`set_input_delay` syntax**: The delay value is in nanoseconds relative to a clock edge. A negative value means the data arrives before the capturing clock edge. For AXI interfaces that are purely internal to the PL (BRAM, PS-PL AXI ports), `set_input_delay` is not needed — only constrain signals crossing the device boundary.
- **PMOD / GPIO timing**: KV260 carrier card PMOD pins are general-purpose I/O. If used for high-speed signals, add `set_input_delay`/`set_output_delay` constraints and match the board trace delay from the carrier card XDC reference file (XTP686).

### Code Example

```tcl
# KV260 XDC: async clock groups (pl_clk0 from PS + external 100 MHz osc)
# pl_clk0 is auto-constrained by the PS IP; just declare the async relationship
create_clock -period 10.000 -name clk_ext_100 [get_ports clk_ext_100_p]

set_clock_groups -asynchronous \
  -group [get_clocks clk_pl_0]   \
  -group [get_clocks clk_ext_100]

# Constrain a carrier-card PMOD output (example: SOM trace + carrier trace = 2.5 ns)
set_output_delay -clock clk_pl_0 -max  2.500 [get_ports pmod_out[*]]
set_output_delay -clock clk_pl_0 -min -1.000 [get_ports pmod_out[*]]

# False path for configuration/status registers that are quasi-static
set_false_path -from [get_cells -hierarchical -filter {NAME =~ *config_reg*}] \
               -to   [get_ports led_out[*]]
```

### Relevance to Your Project

Your KV260 AXI-BRAM demo uses no I/O crossing the device boundary (all signals are internal PS-PL AXI). The only XDC you need is a `set_clock_groups -asynchronous` declaration if you drive a PL clock from any source other than `pl_clk0`. If you later add PMOD-connected logic, the output-delay template above is the starting point.

## Kria KV260 / K26 SoM

### Key Findings

- **Default boot mode is QSPI32**: The KV260 ships with pre-loaded boot firmware in QSPI non-volatile memory and boots to QSPI32 mode by default. For bare-metal development, the fastest workflow is to override the boot mode to JTAG via the mode pins, then use XSDB/XSCT to download FSBL + bitstream + application ELF without reflashing QSPI.
- **JTAG bare-metal four-file flow**: JTAG boot requires: (1) `fsbl.elf`, (2) `pmufw.elf`, (3) your bitstream `.bit`, (4) your application `.elf`. XSDB downloads them in order using `fpga -f`, then loads the ELF with `dow`.
- **EMIO GPIO**: The K26 SOM exposes EMIO signals via the SOM-to-carrier board-to-board connector. The KV260 carrier card maps one EMIO to the fan control pin. Accidentally driving the EMIO fan control signal low in your PL design will spin the fan at full speed — note this if your block design routes any EMIO GPIO.
- **PS UART1 on USB**: On the KV260 carrier card, the USB-UART bridge (Silicon Labs CP2104) connects to MIO48/49, which map to `psu_uart_1`. Set the BSP accordingly; `psu_uart_0` is not connected to the carrier card USB port.
- **Power sequencing**: The K26 SOM handles VCC_PSPLL, VCC_PSINTLP, and VCCO_PSIO power rails internally. Carrier card designers must provide the 5 V input; the SOM regulates down. For bare-metal testing on the starter kit, the supplied 12 V power brick + USB-C cable is sufficient.

### Code Example

```tcl
# XSDB script to boot bare-metal on KV260 over JTAG
connect
targets -set -filter {name =~ "PSU"}

# Initialize the PS
mwr 0xffca0038 0x1ff
after 1000

# Download and run PMU firmware
targets -set -filter {name =~ "MicroBlaze PMU"}
dow /path/to/pmufw.elf
con

# Download and run FSBL on APU0
targets -set -filter {name =~ "Cortex-A53 #0"}
rst -processor
dow /path/to/fsbl.elf
con

# Load bitstream
fpga -f /path/to/kv260_top.bit

# Load bare-metal application
targets -set -filter {name =~ "Cortex-A53 #0"}
rst -processor
dow /path/to/kv260_axi_bram_demo.elf
con
# UART output should now appear on /dev/ttyUSB1 at 115200 8N1
```

### Relevance to Your Project

This XSDB script is the direct deployment mechanism for your `kv260-axi-bram-demo`. It avoids SD card reflashing during iterative development. Note `ttyUSB1` — because the CP2104 on the KV260 enumerates two virtual COM ports, with UART1 (your `xil_printf` output) on the second one (`/dev/ttyUSB1` on Linux, `COM4` or similar on Windows).

## AMD/Xilinx Tool Updates

### Key Findings

- **Vivado 2025.2 new device support**: Adds Versal AI Edge Series Gen 2 (XC2VE350x, XC2VE380x) and Versal Prime Series Gen 2. Zynq UltraScale+ support is unchanged but benefits from infrastructure improvements.
- **AXI SmartConnect ultra-low-area mode**: New `STRATEGY` parameter in AXI SmartConnect IP enables a reduced-area synthesis mode, trading some routing flexibility for lower LUT count — useful for KV260 designs that are LUT-constrained.
- **SystemVerilog interface support in IP Integrator**: Vivado 2025.2 adds simplified AXI connections between SV module instances with automatic wrapper generation. VHDL users are unaffected but should be aware that mixed-language BD workflows now behave differently.
- **PhysOpt compile time reduction**: Physical optimization compile times are reduced in 2025.2 for Versal targets. For Zynq UltraScale+ on KV260, the improvement is incremental but the global/module-level retiming controls are new knobs worth exploring for timing closure.
- **Vivado 2025.1 AXI address decoder regression**: Confirmed bug (Digilent forum) where the "Create and Package New IP" scaffold generates a broken 10-bit address decoder regardless of the configured AXI address width. Affects 2025.1; check if patched in 2025.2 before relying on scaffold-generated slaves.
- **Open source component releases**: AMD published 2025.2 release notes for open-source components (device-tree-xlnx, meta-xilinx, u-boot-xlnx). For bare-metal developers this is less relevant, but updating to 2025.2 FSBL aligns with the latest security patches.

### Code Example

```tcl
# Vivado 2025.2: Enable ultra-low-area mode on AXI SmartConnect
set smartconnect [get_bd_cells axi_smc]
set_property CONFIG.NUM_SI  {1} $smartconnect
set_property CONFIG.NUM_MI  {2} $smartconnect
# Ultra-low-area: reduce crossbar logic (single master, few slaves only)
set_property CONFIG.STRATEGY {1} $smartconnect

# Check the IP version you have in the catalog
report_ip_status -name ip_status
# Look for axi_interconnect or smartconnect entries with "Upgrade available"
# Upgrade in batch:
upgrade_ip [get_ips -filter {UPGRADE_VERSIONS != ""}]
generate_target all [get_ips]
```

### Relevance to Your Project

If you upgrade to Vivado 2025.2, run `upgrade_ip` on your block design to pick up the updated AXI BRAM Controller and SmartConnect IP. The ultra-low-area SmartConnect mode is directly applicable since your design has exactly one AXI master (PS HPM0) and two AXI slaves (BRAM0, BRAM2) — the minimal topology where the reduced crossbar trades off nothing functional.
