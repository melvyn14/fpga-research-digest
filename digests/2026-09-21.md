# FPGA Research Digest - 2026-09-21

## Executive Summary
- **AXI Interconnect is deprecated** as of Vivado 2024.2+; migrate to AXI SmartConnect for all new KV260 designs — the project's two BRAM controllers should connect via SmartConnect, not the legacy Interconnect IP.
- **VALID must never wait for READY** — the cardinal AXI rule most often violated in Zynq bare-metal tests; if your PS write to BRAM occasionally hangs, a combinatorial BREADY dependency is the prime suspect.
- **JTAG boot requires an explicit boot-mode change** on the KV260 (default is QSPI32); use XSDB `mwr` commands to switch boot mode before downloading bare-metal ELF files.
- **AXI Interconnect → SmartConnect migration** is a single right-click "Replace IP" in Vivado 2025.1 IP Integrator; doing this now future-proofs the block design against tool EOL warnings.
- **Vivado 2025.2 / 2026.1** introduced SystemVerilog interface support for AXI ports and reduced physical-optimization compile time — upgrade paths from 2025.1 are smooth.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings
- **VALID must never wait for READY.** Once a master or slave asserts VALID, it must hold it until READY goes high. Pulling VALID low prematurely is the most common deadlock cause in Zynq AXI-Lite designs.
- **BREADY held low stalls the write-response channel.** The PS must deassert its BREADY only briefly; if a custom peripheral doesn't drive BREADY high within a bounded number of cycles, the transaction queue on the PS interconnect will stall.
- **AWVALID and WVALID timing:** For AXI-Lite, masters may send the address (AWVALID) and data (WVALID) simultaneously or sequentially. Slaves must accept both before generating BVALID/BRESP.
- **Xilinx's own example AXI-Lite cores** historically had bugs with AWREADY/WREADY deassertion; always verify with Vivado's built-in protocol checker (right-click net → "Mark Debug", enable AXI Protocol Checker IP).
- **AXI4 vs AXI4-Lite for BRAM:** AXI BRAM Controller supports both modes. For the KV260 bare-metal demo using word-by-word writes, AXI4-Lite is sufficient and simpler to verify. Use AXI4 only if burst transfers (LEN > 0) are needed.

### Code Example
```c
/* Bare-metal AXI-Lite write with explicit read-back verification */
#define BRAM0_BASE  0xA0000000UL
#define BRAM1_BASE  0xA0010000UL

static inline void axi_write32(uintptr_t addr, uint32_t val) {
    *(volatile uint32_t *)addr = val;
    /* DSB ensures the AXI write completes before the subsequent read */
    __asm__ volatile("dsb sy" ::: "memory");
}

static inline uint32_t axi_read32(uintptr_t addr) {
    uint32_t v = *(volatile uint32_t *)addr;
    __asm__ volatile("dsb sy" ::: "memory");
    return v;
}

int bram_self_test(uintptr_t base, uint32_t pattern) {
    axi_write32(base + 0x00, pattern);
    axi_write32(base + 0x04, ~pattern);
    uint32_t r0 = axi_read32(base + 0x00);
    uint32_t r1 = axi_read32(base + 0x04);
    return (r0 == pattern && r1 == ~pattern) ? 0 : -1;
}
```

### Relevance to Your Project
The `bram_self_test()` pattern directly maps to what main.c does at BRAM0 (`0xA0000000`) and BRAM2 (`0xA0010000`). Adding `dsb sy` barriers after each write is critical on Cortex-A53 — without them the out-of-order execution pipeline may issue the read before the write completes on the AXI bus, giving false FAIL results.

## Vivado Block Design / IP Integrator

### Key Findings
- **AXI SmartConnect replaces AXI Interconnect.** Starting Vivado 2024.2 the old AXI Interconnect was marked discontinued; Vivado 2025.x emits warnings and 2026.x treats it as deprecated. Use SmartConnect for all new connections.
- **Connection Automation** (Run Connection Automation) wires the PS HPM0 → SmartConnect → AXI BRAM Controller and auto-instantiates Processor System Reset. Accept the default clock unless you have a custom PL clock.
- **Address Editor auto-assign** sets a default 64K or 8K range per BRAM Controller. For the KV260 project with two controllers at `0xA0000000` and `0xA0010000`, manually enter 64K ranges to match the C code offsets.
- **Regenerate Layout** after every IP addition: the canvas auto-route sometimes misses connections visually while the netlist is correct — always run Validate Design (F6) before generating bitstream.
- **SmartConnect resource cost:** SmartConnect uses more LUTs than the legacy Interconnect for small 1-master/1-slave topologies. For a minimal BRAM demo, resource overhead is negligible (<1% on K26).

### Code Example
```tcl
# Replace legacy AXI Interconnect with SmartConnect in TCL
# Run after sourcing the existing block design
set old_ic [get_bd_cells axi_interconnect_0]
if {[llength $old_ic]} {
    delete_bd_objs $old_ic
}

# Add SmartConnect
create_bd_cell -type ip -vlnv xilinx.com:ip:smartconnect:1.0 axi_smc
set_property CONFIG.NUM_SI {1} [get_bd_cells axi_smc]
set_property CONFIG.NUM_MI {2} [get_bd_cells axi_smc]

# Reconnect PS HPM0 → SmartConnect
connect_bd_intf_net [get_bd_intf_pins zynq_ultra_ps_e_0/M_AXI_HPM0_FPD] \
    [get_bd_intf_pins axi_smc/S00_AXI]
connect_bd_intf_net [get_bd_intf_pins axi_smc/M00_AXI] \
    [get_bd_intf_pins axi_bram_ctrl_0/S_AXI]
connect_bd_intf_net [get_bd_intf_pins axi_smc/M01_AXI] \
    [get_bd_intf_pins axi_bram_ctrl_1/S_AXI]
```

### Relevance to Your Project
If `create_bd.tcl` uses the legacy `axi_interconnect`, replace it with `smartconnect` to avoid deprecation warnings in Vivado 2025.1 and silence future tool complaints. The two BRAM controllers fit cleanly as M00/M01 on a single SmartConnect instance.

## Vivado TCL Scripting

### Key Findings
- **Non-Project Mode** (UG892) is ideal for CI pipelines: `read_vhdl`, `read_xdc`, `synth_design`, `opt_design`, `place_design`, `route_design`, `write_bitstream` — no `.xpr` file needed.
- **Batch launch:** `vivado -mode batch -source script.tcl` runs headless; exit code 0 means success. Use `-log` and `-journal` to capture output.
- **Block design regeneration:** In non-project mode, open a saved `.bd` snapshot with `open_bd_design`, then call `generate_target all [get_files *.bd]` before synthesis.
- **`write_project_tcl`** exports a complete project recreation script from the GUI — the gold standard for reproducible builds. Run it after every major block design change.
- **TCL proc for address assignment:**
  ```tcl
  assign_bd_address [get_bd_addr_segs {axi_bram_ctrl_0/S_AXI/Mem0}]
  ```
  Always call this before `validate_bd_design` to avoid unassigned-address errors.

### Code Example
```tcl
#!/usr/bin/env tclsh
# non_project_build.tcl — headless build for kv260-axi-bram-demo
set part "xck26-sfvc784-2LV-c"

read_vhdl  [glob ./vhdl/*.vhd]
read_xdc   [glob ./xdc/*.xdc]

# Regenerate block design wrapper
open_project ./kv260/kv260.xpr
open_bd_design [get_files kv260_bd.bd]
generate_target all [get_files kv260_bd.bd]
make_wrapper -files [get_files kv260_bd.bd] -top
add_files -norecurse \
    ./kv260/kv260.gen/sources_1/bd/kv260_bd/hdl/kv260_bd_wrapper.vhd

# Full implementation
synth_design -top kv260_bd_wrapper -part $part
opt_design
place_design
route_design
write_bitstream -force ./output/kv260.bit
write_hw_platform -fixed -force ./output/kv260.xsa
puts "Build complete: kv260.bit / kv260.xsa"
```

### Relevance to Your Project
A script like this turns the current GUI-only flow into a reproducible single-command build. The `write_hw_platform` output (`.xsa`) feeds directly into Vitis to regenerate the BSP without re-opening the GUI.

## Vitis Bare-Metal / Standalone

### Key Findings
- **BSP is rebuilt from the `.xsa` file.** After any hardware change (new AXI address, added IP), export a new XSA from Vivado and update the Vitis platform project — the BSP drivers regenerate automatically.
- **`xil_printf` vs `printf`:** `xil_printf` is a lightweight subset (~3KB code overhead) that supports `%d`, `%x`, `%s` but NOT `%f`. Use it for all PASS/FAIL output; avoid `printf` in bare-metal to reduce binary size.
- **UART stdout:** Set `stdin`/`stdout` to `psu_uart_1` (USB-UART on KV260) in the BSP settings — not `psu_uart_0` which goes to the J2 debug header.
- **Linker script (`lscript.ld`):** Default places code and data in DDR at `0x0` (EL3 reset vector). For pure BRAM demos, all AXI slave regions must fall within the `0xA0000000`–`0xBFFFFFFF` PL AXI window defined by the Zynq MP AXI slave range.
- **Cache coherency:** On Cortex-A53, the L1/L2 caches are enabled by the Vitis standalone startup code. AXI BRAM is in a non-cached region by default (marked Device memory in the MMU table), so no explicit cache flush is needed for BRAM reads/writes.

### Code Example
```c
#include "xil_printf.h"
#include "xparameters.h"  /* generated by Vitis BSP */

/* Use BSP-generated base addresses rather than hardcoding */
#define BRAM0_BASE  XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR  /* 0xA0000000 */
#define BRAM1_BASE  XPAR_AXI_BRAM_CTRL_1_S_AXI_BASEADDR  /* 0xA0010000 */

int main(void) {
    xil_printf("KV260 AXI-BRAM self-test\r\n");

    const uint32_t patterns[] = {0xDEADBEEF, 0xCAFEBABE, 0xA5A5A5A5, 0x12345678};
    int pass = 1;

    for (int i = 0; i < 4; i++) {
        *(volatile uint32_t *)(BRAM0_BASE + i * 4) = patterns[i];
        *(volatile uint32_t *)(BRAM1_BASE + i * 4) = ~patterns[i];
    }
    for (int i = 0; i < 4; i++) {
        uint32_t r0 = *(volatile uint32_t *)(BRAM0_BASE + i * 4);
        uint32_t r1 = *(volatile uint32_t *)(BRAM1_BASE + i * 4);
        if (r0 != patterns[i] || r1 != ~patterns[i]) {
            xil_printf("FAIL @ offset 0x%02x: BRAM0=0x%08x BRAM1=0x%08x\r\n",
                       i * 4, r0, r1);
            pass = 0;
        }
    }
    xil_printf(pass ? "PASS\r\n" : "OVERALL FAIL\r\n");
    return 0;
}
```

### Relevance to Your Project
Using `XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR` instead of the literal `0xA0000000` means the binary automatically tracks address changes when the block design is regenerated — no manual constant updates in `main.c`. The pattern loop also tests four words per BRAM, catching partial connectivity failures.

## XDC Timing Constraints

### Key Findings
- **Zynq PS clocks need no create_clock** — the PS clock outputs (`pl_clk0`, `pl_clk1`) are auto-constrained by Vivado from the PS7/ZYNQMP IP. Only add `create_clock` for external oscillator pins (e.g., a differential clock on the SOM carrier).
- **`set_input_delay` / `set_output_delay`** apply to PL I/O pins, not to PS-PL AXI ports. For a pure PS↔BRAM design with no external ports, you need zero I/O timing constraints.
- **False paths on clock domain crossings:** If you add a PL clock domain separate from `pl_clk0`, use `set_clock_groups -asynchronous` to prevent Vivado from routing impossible cross-domain paths.
- **`write_inferred_xdc`** (new in Vivado 2025.2) writes a constraint file from timing analysis results — useful for capturing inferred register-to-register paths.
- **Minimum required XDC for KV260 bare-metal:** Package pin and I/O standard for any PL-facing GPIO; all PS↔PL AXI paths are handled by tool-inferred constraints.

### Code Example
```tcl
# kv260_constraints.xdc
# Only constraints needed for the KV260 AXI-BRAM demo (no external PL I/O).
# PS-PL AXI clock is auto-constrained from pl_clk0.

# If a separate PL logic clock is used (e.g., for debug or future IP):
# create_clock -period 10.000 -name pl_clk0 [get_pins zynq_ultra_ps_e_0/inst/PS8_i/PLCLK[0]]

# Prevent cross-domain analysis if multiple PL clocks are added later:
# set_clock_groups -asynchronous \
#     -group [get_clocks clk_pl_0] \
#     -group [get_clocks clk_pl_1]

# I/O standard for PMOD or RPi header pins (example, not used in BRAM demo):
# set_property IOSTANDARD LVCMOS33 [get_ports {gpio_tri_io[*]}]

# Mark all PS-PL AXI paths as multicycle if running PL at < 100 MHz:
# set_multicycle_path 2 -setup -from [get_clocks clk_pl_0] \
#                              -to   [get_clocks clk_pl_0]
```

### Relevance to Your Project
The AXI-BRAM demo has no external PL ports, so the XDC file is nearly empty. The most common constraint error is accidentally adding `create_clock` on the PS clock pin (which causes a conflict with the auto-inferred constraint). Keep the XDC minimal and let Vivado's PS IP handle all PS-sourced clock constraints.

## Kria KV260 / K26 SoM

### Key Findings
- **Default boot mode is QSPI32.** The KV260 Starter Kit ships with Kria boot firmware in QSPI. To run a custom bare-metal ELF over JTAG, you must switch boot mode using XSDB before downloading — do NOT overwrite the QSPI firmware.
- **JTAG boot mode switch via XSDB:**
  ```tcl
  connect; targets -set -filter {name =~ "PSU"}
  mwr 0xFFCA0010 0x0   ;# multiboot offset = 0
  mwr 0xFF5E0200 0x0100 ;# boot mode = JTAG
  rst -system
  ```
- **PS-PL AXI window:** The KV260 K26 SOM exposes the Zynq MPSoC `HPM0_FPD` (128-bit, 333 MHz) and `HPM1_FPD` ports to PL. For BRAM controllers at `0xA0000000`, connect to HPM0_FPD (GP0) — HPM1 is also valid but less commonly used.
- **UART for USB console:** `psu_uart_1` on MIO 36–37 maps to the USB-UART bridge on the KV260 carrier card. Connect a terminal at 115200 8N1 after powering the board.
- **Power sequencing:** PL power (VCCO_HP banks) depends on the carrier card's regulators and comes up after PS. Always ensure the bitstream is downloaded before running AXI accesses; Vitis debug flow programs the PL automatically from the XSA.

### Code Example
```tcl
# jtag_boot.tcl — Switch KV260 to JTAG boot and load bare-metal ELF
# Run from Vitis XSDB console: xsdb jtag_boot.tcl

connect
target 1 ;# typically the Zynq MPSoC target

# Disable authentication, select JTAG boot mode
mwr 0xFFCA0010 0x0
mwr 0xFF5E0200 0x0100
rst -system
after 3000

# Initialize PS (required before PL config from Vitis)
targets -set -filter {name =~ "PSU"}
rst -processor
source [lindex $argv 0] ;# pass psu_init.tcl from XSA export

# Download bitstream and ELF
fpga -f ../output/kv260.bit
targets -set -filter {name =~ "Cortex-A53 #0"}
dow  ../output/kv260_bram_demo.elf
con
puts "Application running — open serial terminal at 115200"
```

### Relevance to Your Project
This script is the missing automation link in the kv260-axi-bram-demo workflow. Instead of manually clicking through Vitis debug, `xsdb jtag_boot.tcl psu_init.tcl` runs the full boot → bitstream → ELF download in one command, making the demo fully scriptable.

## AMD/Xilinx Tool Updates (Vivado/Vitis 2025.x / 2026.x)

### Key Findings
- **Vivado 2025.2** introduced SystemVerilog Interface support for simplified AXI port connections in IP Integrator — AXI buses can now be typed as SV interfaces in RTL, reducing wrapper verbosity.
- **Vivado 2026.1** (latest) adds Versal AI Edge Gen 2 support, improved SLR crossing reporting, and new ECO legalizer features. The K26 is based on Zynq MPSoC so these features don't directly apply, but the IP Integrator usability improvements benefit all projects.
- **AXI Interconnect fully deprecated** in 2024.2+. All Vivado tool-generated example designs now use SmartConnect exclusively.
- **Vitis 2026.1 known issues:** AI Engine API changes break some HLS IP; irrelevant for pure Zynq MPSoC bare-metal projects on the KV260.
- **`write_inferred_xdc`** (Vivado 2025.2+) auto-captures timing constraints from analysis results — run it after route_design to get a starting XDC for designs that previously had none.
- **Vitis Classic vs Vitis Unified:** AMD continues deprecating Vitis Classic. By 2025.1, Vitis Unified is the default IDE. Bare-metal standalone flows work in both, but new projects should use Unified.

### Code Example
```tcl
# Vivado 2025.x: Capture inferred timing constraints after route
# Run in Vivado Tcl Console after route_design completes

open_checkpoint ./output/post_route.dcp
report_timing_summary -file ./output/timing_report.txt

# Write all inferred constraints to a starting XDC
write_inferred_xdc -force ./xdc/kv260_inferred.xdc
puts "Inferred XDC written — review and incorporate into kv260_constraints.xdc"

# Check for timing violations; fail build if WNS < 0
set wns [get_property SLACK [get_timing_paths -max_paths 1 -nworst 1]]
if {$wns < 0} {
    puts "ERROR: Timing violation WNS = $wns ns"
    exit 1
}
puts "Timing clean: WNS = $wns ns"
```

### Relevance to Your Project
Running `write_inferred_xdc` on the KV260 BRAM demo build captures the PS-PL clock constraints that Vivado infers automatically, documenting the timing model explicitly. Checking WNS in the build script prevents committing a bitstream with timing violations — a common root cause of intermittent BRAM read errors in hardware.
