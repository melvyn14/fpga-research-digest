# FPGA Research Digest - 2026-08-23

## Executive Summary

- **AXI-Lite VALID must not be de-asserted once raised**: The master must keep `AWVALID`/`WVALID` high until the slave asserts `AWREADY`/`WREADY`. Dropping VALID early is the single most common cause of silent write failures in BRAM designs — verify this invariant in simulation before trusting PASS/FAIL results.
- **KV260 PL has no independent clock**: The PL fabric on the KV260 gets its clock exclusively from the PS (via FCLKCLK). Ensure the PS block is configured to output a PL fabric clock (e.g., 100 MHz on FCLK_CLK0) in `create_bd.tcl`; without it the design loads but nothing runs.
- **Vivado 2026.1 is now available** (downloads page live as of August 2026). If you are still on 2025.1, it is worth checking the upgrade path — 2025.2 added SystemVerilog Interface support for simplified AXI connections and improved Versal QoR.
- **xil_printf vs printf**: For UART output in your bare-metal `main.c`, prefer `xil_printf` (lower code-size, no floating-point dependency) but be aware it does not support `%f`. Use it for PASS/FAIL status strings; it links to a lightweight UART driver already in the BSP.
- **Non-project-mode TCL with `write_hw_platform`**: After bitstream generation in batch mode, call `write_hw_platform -fixed -include_bit ./kv260.xsa` to produce the XSA file Vitis needs; omitting `-include_bit` produces an XSA without the bitstream and causes a confusing Vitis import error.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- All five AXI channels (AW, W, B, AR, R) use VALID/READY handshake. A transfer occurs only when **both** VALID and READY are high on the same rising clock edge.
- **Critical rule**: Once a master asserts VALID, it **must not** de-assert it until READY is received from the slave. Violating this rule can cause the AXI BRAM Controller to miss transactions silently — the transaction disappears with no error, producing false "reads back 0" results.
- For AXI-Lite specifically, write data and address channels are independent: `AWVALID` and `WVALID` may be asserted simultaneously or in either order; the slave (BRAM Controller) accepts the transaction only when it has seen both.
- The AXI BRAM Controller defaults to a 1-cycle read latency (configurable up to 128). At 100 MHz, nominal throughput is one read/write per clock cycle.
- AXI-Stream port naming matters in Vivado IP Integrator: prefix ports with `s_axis_` / `m_axis_` so the tool's connection automation recognises them as AXI-S interfaces and connects them correctly.

### Code Example

```c
/* Bare-metal AXI-Lite single write with explicit memory barrier */
#include "xil_io.h"

/* Write 32-bit word at word offset within BRAM0 (base 0xA0000000) */
static inline void bram_write(u32 base, u32 word_offset, u32 value) {
    Xil_Out32(base + (word_offset << 2), value);
    /* dsb ensures the write is visible to PL before next read */
    __asm__ volatile("dsb sy" ::: "memory");
}

static inline u32 bram_read(u32 base, u32 word_offset) {
    __asm__ volatile("dsb sy" ::: "memory");
    return Xil_In32(base + (word_offset << 2));
}
```

### Relevance to Your Project

Your `main.c` writes patterns to BRAM0 (`0xA0000000`) and BRAM2 (`0xA0010000`) and reads them back. The memory barrier (`dsb sy`) above is necessary on Cortex-A53 because the processor can reorder reads ahead of writes; without it a read that immediately follows a write may return stale cached data. Add this to your write/verify loop to eliminate false FAILs caused by the A53 store buffer.

## Vivado Block Design / IP Integrator

### Key Findings

- **Run Connection Automation after every IP addition**: Vivado will auto-connect AXI, clock, and reset nets. After running automation, verify the AXI Interconnect's `ACLK` is sourced from the same clock as the PS (`FCLK_CLK0`) — a mismatch produces timing failures.
- **Address Editor "Assign All"**: Click _Assign All_ to let Vivado auto-assign addresses; then manually verify that BRAM0 is at `0xA0000000` and BRAM2 at `0xA0010000` matching your software constants. The Address Editor shows both offset and range — set range to at least the BRAM depth (e.g., 8K for an 8KB BRAM).
- **Save `.bd` before Validate**: Use `Ctrl+S` frequently. Vivado does not auto-save `.bd` files, and a validation error on an unsaved state is difficult to roll back.
- **Regenerate Output Products**: After changing IP parameters (e.g., BRAM data width, ECC mode), right-click the BD → _Generate Output Products_ → _Global_ to ensure synthesis picks up the new configuration.
- **Out-of-context synthesis** (OOC) dramatically speeds up iteration by caching IP synthesis results — enabled by default in Project mode but not in non-project mode.

### Code Example

```tcl
# Vivado TCL: Validate and regenerate BD, then synthesize
proc refresh_bd {bd_name} {
    open_bd_design [get_files ${bd_name}.bd]
    validate_bd_design
    generate_target all [get_files ${bd_name}.bd]
    make_wrapper -files [get_files ${bd_name}.bd] -top
    add_files -norecurse [glob ./*/hdl/*.v]
}

# After modifying create_bd.tcl:
# vivado -mode batch -source tcl/create_bd.tcl
# Then call refresh_bd inside the script before launch_runs
```

### Relevance to Your Project

Your `create_bd.tcl` script creates the block design programmatically. When you modify the BRAM size or AXI base address in the script, run `validate_bd_design` as part of the script to catch connection errors (dangling ports, address overlaps) before bitstream generation — this prevents silent misconfigurations that produce FAIL at runtime.

## Vivado TCL Scripting

### Key Findings

- **Non-project mode is fully scriptable**: `read_vhdl`, `read_xdc`, `synth_design`, `opt_design`, `place_design`, `route_design`, `write_bitstream` — each command maps to a discrete design step with no implicit state.
- **Pass arguments with `-tclargs`**: `vivado -mode batch -source build.tcl -tclargs "PART=xck26-sfvc784-2LV-c"` — inside the script, `$argv` holds the argument list.
- **`write_hw_platform` is mandatory for Vitis**: After `write_bitstream`, call `write_hw_platform -fixed -include_bit ./output/kv260.xsa` to bundle the bitstream with hardware metadata. Without `-include_bit`, Vitis import will warn that no bitfile is present.
- **Using IP Integrator in Non-Project Mode**: Call `create_bd_design`, configure IPs, then call `generate_target all` before synthesis. The BD TCL approach (`write_bd_tcl`) is ideal for version control — it exports the entire BD as a reproducible script.
- **Report generation is manual**: Unlike Project mode, non-project mode produces no automatic timing/utilization reports. Explicitly call `report_timing_summary` and `report_utilization` after route to ensure timing is met.

### Code Example

```tcl
# Non-project mode build script skeleton for KV260 AXI-BRAM design
set part "xck26-sfvc784-2LV-c"
set project_name "kv260_axi_bram"

# Read sources
read_vhdl [glob ./vhdl/*.vhd]
read_xdc  [glob ./xdc/*.xdc]

# Create block design
source ./tcl/create_bd.tcl
generate_target all [get_files ${project_name}.bd]
make_wrapper -files [get_files ${project_name}.bd] -top
read_vhdl [glob ./*/hdl/wrappers/*.v]

# Synthesis
synth_design -top ${project_name}_wrapper -part $part -flatten_hierarchy rebuilt

# Implementation
opt_design
place_design
phys_opt_design
route_design

# Reports
report_timing_summary -file ./reports/timing.rpt
report_utilization    -file ./reports/utilization.rpt

# Outputs
write_bitstream -force ./output/${project_name}.bit
write_hw_platform -fixed -include_bit -force ./output/${project_name}.xsa
```

### Relevance to Your Project

This pattern is directly applicable to your `create_bd.tcl` workflow. Wrapping the entire flow in a single non-project script makes CI/CD trivial — a single `vivado -mode batch -source build.tcl` reproduces the full bitstream from source. Add `report_timing_summary` to catch setup/hold violations before flashing to the KV260.

## Vitis Bare-Metal / Standalone

### Key Findings

- **xil_printf vs printf**: `xil_printf` uses ~4KB of code space vs ~60KB for full `printf`. It supports `%d`, `%s`, `%x`, `%u` but **not** `%f`. For PASS/FAIL printing in your BRAM demo, `xil_printf` is the right choice.
- **BSP MSS file drives driver generation**: The `system.mss` (Microprocessor Software Specification) file in the Vitis BSP project references your XSA and lists which drivers to generate. If you update the hardware (new XSA), right-click the platform → _Update Hardware Specification_ to regenerate BSP headers (`xparameters.h`) with new base addresses.
- **`xparameters.h` is your source of truth**: After BSP generation, check `XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR` and `XPAR_AXI_BRAM_CTRL_1_S_AXI_BASEADDR` in this file — they must match your `main.c` hard-coded addresses (`0xA0000000`, `0xA0010000`).
- **Linker script `lscript.ld`**: By default the standalone BSP places stack/heap in OCM (on-chip memory, 256KB). For a BRAM verification app that may exceed OCM, modify `lscript.ld` to allocate `.bss`/`.data` in DDR (`ps_ddr_0` at `0x00000000`).
- **Interrupt controller**: For GIC (Generic Interrupt Controller) in standalone, use `XScuGic_Connect()` from `xscugic.h`. The Cortex-A53 GIC is at `0xF9000000`; the instance ID is `XPAR_SCUGIC_SINGLE_DEVICE_ID`.

### Code Example

```c
/* main.c pattern for KV260 BRAM write/read verification */
#include "xil_printf.h"
#include "xil_io.h"
#include "xparameters.h"

#define BRAM0_BASE  XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR
#define BRAM2_BASE  XPAR_AXI_BRAM_CTRL_1_S_AXI_BASEADDR
#define TEST_WORDS  256

int main(void) {
    u32 i, readback, errors = 0;

    xil_printf("KV260 AXI-BRAM Test\r\n");

    /* Write pattern */
    for (i = 0; i < TEST_WORDS; i++) {
        Xil_Out32(BRAM0_BASE + (i << 2), 0xDEAD0000 | i);
        Xil_Out32(BRAM2_BASE + (i << 2), 0xBEEF0000 | i);
    }

    /* Memory barrier: flush A53 store buffer before reading back */
    __asm__ volatile("dsb sy" ::: "memory");

    /* Verify */
    for (i = 0; i < TEST_WORDS; i++) {
        readback = Xil_In32(BRAM0_BASE + (i << 2));
        if (readback != (0xDEAD0000 | i)) {
            xil_printf("FAIL BRAM0[%d]: got 0x%08X\r\n", i, readback);
            errors++;
        }
        readback = Xil_In32(BRAM2_BASE + (i << 2));
        if (readback != (0xBEEF0000 | i)) {
            xil_printf("FAIL BRAM2[%d]: got 0x%08X\r\n", i, readback);
            errors++;
        }
    }

    xil_printf(errors == 0 ? "PASS\r\n" : "FAIL: %d errors\r\n", errors);
    return 0;
}
```

### Relevance to Your Project

This is a direct enhancement of your existing `main.c`. Using `XPAR_*` constants from `xparameters.h` instead of hard-coded `0xA0000000`/`0xA0010000` makes the code resilient to address remapping in the block design. The `dsb sy` barrier ensures the A53 store buffer is flushed before readback, eliminating a class of intermittent FAIL results.

## XDC Timing Constraints

### Key Findings

- **Virtual clock for I/O constraints**: For AXI-Lite ports that are internal to the PS-PL boundary, you typically do **not** need `set_input_delay`/`set_output_delay` — the PS-PL interface uses dedicated routing that Vivado constrains automatically. Only apply I/O delays to external FPGA pins (UART, GPIO on the carrier card).
- **`set_clock_groups -asynchronous`**: Use this to tell Vivado not to check timing between unrelated clocks (e.g., a 100 MHz PL fabric clock and a 48 MHz USB clock). Without it, Vivado reports false timing violations across the clock boundary.
- **Kria PS clocks are auto-constrained**: The `zynq_ultra_ps_e` IP automatically creates timing constraints for `FCLK_CLK0`–`FCLK_CLK3`. You do not need to declare them in your XDC — adding a duplicate `create_clock` causes a "multiple clocks on the same source" DRC.
- **`set_false_path` for async resets**: If you use an asynchronous reset that crosses from PS to PL without synchronization, mark it: `set_false_path -from [get_pins ps_inst/FCLK_RESET0_N]`. For a synchronous design with proper reset synchronizers this is not needed.
- **Timing report discipline**: After route, always run `report_timing_summary -max_paths 20 -nworst 5`. A WNS (Worst Negative Slack) ≥ 0 means timing is met; a negative WNS means the design will behave incorrectly at the target frequency.

### Code Example

```xdc
# kv260_top.xdc — constraints for KV260 AXI-BRAM demo
# PS clocks are auto-constrained by the Zynq PS IP — do NOT redeclare them here

# Isolate the 100 MHz PL fabric clock from any debug clocks
set_clock_groups -asynchronous \
    -group [get_clocks clk_pl_0] \
    -group [get_clocks dbg_hub/clkdiv_clk]

# UART TX/RX on carrier card MIO (PS-managed) — no XDC constraint needed
# If you have PL-side UART on EMIO, constrain it:
# set_input_delay  -clock [get_clocks clk_pl_0] -max 3.0 [get_ports uart_rxd]
# set_output_delay -clock [get_clocks clk_pl_0] -max 2.0 [get_ports uart_txd]

# Async reset path (use only if reset is not synchronised in RTL)
# set_false_path -from [get_nets sys_reset_n]
```

### Relevance to Your Project

Your bare-metal AXI-BRAM demo uses the PS-managed UART (MIO), so no I/O delay constraints are needed for that path. The critical XDC task for your design is ensuring `clk_pl_0` (your `FCLK_CLK0`) is the only active clock on the PL side and is not falsely paired with debug hub clocks by Vivado's timing engine — the `set_clock_groups` line above prevents spurious timing violations in the implementation report.

## Kria KV260 / K26 SoM

### Key Findings

- **No independent PL clock**: Unlike many FPGA boards, the KV260 carrier card provides no external oscillator to the PL fabric. The PL clock **must** come from the PS (`FCLK_CLK0` in the Zynq PS IP). In your block design, verify `FCLK_CLK0` is enabled and connected to the AXI Interconnect's `ACLK`.
- **Default boot mode is QSPI32**: The board ships with a QSPI-based boot FW. For bare-metal JTAG debug, connect the USB/JTAG cable, let the board boot fully (Linux loads), then launch Vitis and use _Program FPGA_ + _Run/Debug_ — the JTAG interface becomes available after the boot ROM releases it.
- **MIO pinout is fixed on K26**: The 26 MIO pins are connected to QSPI, SD card, UART0 (MIO38/39 — this is your USB-UART), I2C, and power management. You cannot reassign them. Your PS block must be configured with UART0 on MIO38/39 (the default for KV260 board files).
- **EMIO for PL GPIO**: Any additional GPIO from the PL goes through EMIO — up to 96 bits. EMIO pins appear on the `emio_gpio_i/o/t` buses of the PS. You can route them to the Raspberry Pi header (J2) on the carrier card.
- **Power domains**: The K26 SOM has separate VCC_PSINTLP (PS low-power domain) and VCC_PSBATT (battery backup for RTC/BBRAM). Ensure the carrier card powers up in the documented sequence; the KV260 starter kit handles this automatically.

### Code Example

```tcl
# create_bd.tcl snippet: Configure PS for KV260 with UART0 on MIO38/39 and 100 MHz PL clock
set ps [create_bd_cell -type ip -vlnv xilinx.com:ip:zynq_ultra_ps_e:3.5 ps_0]

set_property -dict [list \
    CONFIG.PSU__UART0__PERIPHERAL__ENABLE {1} \
    CONFIG.PSU__UART0__PERIPHERAL__IO {MIO 38 .. 39} \
    CONFIG.PSU__FPGA_PL0_ENABLE {1} \
    CONFIG.PSU__CRL_APB__PL0_REF_CTRL__FREQMHZ {100} \
    CONFIG.PSU__USE__M_AXI_GP0 {1} \
    CONFIG.PSU__SAXIGP2__DATA_WIDTH {32} \
] $ps

# Connect PL clock and reset
connect_bd_net [get_bd_pins ps_0/pl_clk0] [get_bd_pins ps_0/maxihpm0_fpd_aclk]
```

### Relevance to Your Project

This snippet ensures the PS is correctly configured for the KV260 platform: UART0 on MIO38/39 (the USB-UART path for `xil_printf` output), a 100 MHz PL fabric clock sourced from the PS, and the HP0 AXI master interface enabled for PS-to-PL transactions. If any of these are misconfigured in your `create_bd.tcl`, the BRAM test will either produce no UART output or fail to generate AXI transactions.

## AMD/Xilinx Tool Updates

### Key Findings

- **Vivado 2026.1 is now available** (downloads page live as of August 2026). This release follows 2025.2, which added: (1) **SystemVerilog Interface support** in IP Integrator for simplified AXI port connections; (2) Versal AI Edge Gen 2 and Versal Prime Gen 2 device support; (3) Improved SLR crossing reporting; (4) ECO legalizer for DRC checks; (5) Segmented Configuration support in Hardware Manager.
- **Vitis 2025.2 highlights**: AI Engine API enhancements (new data types: block floating-point MX6/MX4), DMA-FIFO programming model, hardware-in-the-loop verification with MATLAB/Python testbench support, and C++ support in Vitis Functional Simulation.
- **Vitis Export to Vivado (XD101 flow)**: A new 2025.1+ workflow allows hardware design iteration without re-running the full platform build. You export a partial hardware change from Vitis back to Vivado, regenerate only the changed IPs, and reimport — useful for incremental BRAM parameter tuning.
- **Known issue in Vivado 2025.1**: IP Integrator may incorrectly report "address not assigned" for BRAM controllers when the address space is modified after initial synthesis. Workaround: close and reopen the block design before re-running synthesis.
- **Zynq UltraScale+ End-of-Life notice**: AMD announced that the K26 SOM (Zynq UltraScale+ based) remains in production with no planned EOL, but mainstream Zynq-7000 support is winding down in newer tool versions.

### Code Example

```tcl
# Vivado 2025.1+: Vitis Export to Vivado fast-iteration flow
# After modifying BD (e.g., BRAM size), re-export XSA without full rebuild:
open_project ./kv260.xpr
open_bd_design [get_files kv260.bd]

# Make your change (e.g., increase BRAM depth)
set_property CONFIG.MEMORY_DEPTH {8192} [get_bd_cells axi_bram_ctrl_0]
validate_bd_design
generate_target all [get_files kv260.bd]

# Re-synthesize only out-of-context IP (fast)
launch_runs impl_1 -to_step write_bitstream -jobs 8
wait_on_run impl_1

# Export updated XSA for Vitis
write_hw_platform -fixed -include_bit -force ./output/kv260_updated.xsa
puts "XSA exported — import into Vitis and update platform"
```

### Relevance to Your Project

If you upgrade from Vivado 2025.1 to 2025.2 or 2026.1, the SystemVerilog Interface feature will simplify your AXI-BRAM block design by using interface-level ports instead of individual signal connections. The Vitis Export flow is immediately useful: when you want to change BRAM depth or add a third BRAM, you can re-export the XSA and update the Vitis platform without rebuilding from scratch, saving significant build time.
