# FPGA Research Digest - 2026-09-04

## Executive Summary

- **AXI-Lite backpressure bug**: Xilinx example cores historically mishandle BREADY=0 — the slave must gate AWREADY/WREADY too; validate yours against formal AXI rules before tapeout.
- **BRAM address boundary**: `axi_bram_ctrl` raises silent errors when the configured BRAM depth (e.g. 8 KB) is smaller than the base-address offset the CPU writes — verify your address editor range matches BRAM depth exactly.
- **Non-project TCL batch flow** lets you drive synthesis → implementation → bitstream from a single `vivado -mode batch -source build.tcl` call — ideal for CI and for the KV260 demo's `create_bd.tcl` approach.
- **Vitis BSP stdout**: set the `stdout` parameter to `psu_uart_1` (the KV260's USB-UART MIO) in the standalone BSP or `xil_printf` will silently drop output.
- **AMD 2026.1 toolchain** is now the latest release (superseding 2025.1); if you stay on 2025.1 ensure you applied the Vitis patch for standalone BSP linker script generation regressions noted in the 2025.1 release.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- All five AXI channels use the same VALID/READY two-way handshake; a transfer completes only when **both** signals are high on a rising clock edge.
- **Backpressure pitfall**: if the master holds BREADY (write response ready) low, the slave must lower AWREADY and WREADY too — a logic path most developers forget in simulation and only discover under real bus contention.
- **`elseif` bug**: Xilinx example AXI-Lite slave cores prior to Vivado 2016.3 used `elsif` chains that caused the write address and write data channels to depend on each other's ready signals incorrectly; the fixed pattern uses independent registered ready signals.
- **Write ordering rule**: the AXI4 spec requires both the Write Address channel (AW) and the Write Data channel (W) to complete before the slave sends a Write Response (B channel) — the order of AW vs W arrival is undefined; your slave must accept either first.
- AXI-Stream has no address channel; TLAST marks end-of-frame and TKEEP/TSTRB identify valid byte lanes — often ignored in simulation but required for correct hardware operation.

### Code Example

```vhdl
-- AXI-Lite slave write handshake: independent ready signals (fixed pattern)
process(s_axi_aclk)
begin
  if rising_edge(s_axi_aclk) then
    if s_axi_aresetn = '0' then
      aw_en   <= '1';
      awready <= '0';
    else
      if aw_en = '1' and s_axi_awvalid = '1' and awready = '0' then
        awready <= '1';
        aw_en   <= '0';
      elsif s_axi_bready = '1' and bvalid = '1' then
        aw_en   <= '1';  -- re-arm only after response accepted
        awready <= '0';
      else
        awready <= '0';
      end if;
    end if;
  end if;
end process;
```

### Relevance to Your Project

Your KV260 demo writes patterns over AXI-Lite to BRAM0 (0xA0000000) and BRAM2 (0xA0010000). The backpressure pitfall is most likely to surface if you ever add a second bus master or a traffic generator — validate the slave's BREADY path. The write ordering rule is also relevant if you move to a burst write flow.

## Vivado Block Design / IP Integrator

### Key Findings

- **TCL mirroring**: every action in the IP Integrator GUI is logged to the TCL console verbatim — use this to learn the API by doing then copying.
- **Export to TCL**: `File → Export → Export Block Design...` (or `write_bd_tcl`) produces a self-contained script that recreates the block design; **version-lock warning** — the generated TCL references IP version strings and will fail in a different Vivado version without manual IP version bumps.
- **Connection automation**: `apply_bd_automation` is the TCL equivalent of the GUI "Run Connection Automation" button; it can auto-route AXI connections, clock, and reset with a single call.
- **Address editor discipline**: always call `assign_bd_address` explicitly in your TCL script after adding a new AXI slave — relying on the GUI auto-assign leaves address ranges that differ between re-runs.
- `validate_bd_design` should be the last call before `generate_target` — it catches unconnected ports and clock domain violations before synthesis.

### Code Example

```tcl
# Automate AXI connection and address assignment for a new BRAM controller
apply_bd_automation -rule xilinx.com:bd_rule:axi4 \
    -config {Master "/zynq_ultra_ps_e_0/M_AXI_HPM0_FPD" \
             Clk    "Auto" } \
    [get_bd_intf_pins axi_bram_ctrl_0/S_AXI]

# Explicit address assignment (reproducible across runs)
set_property offset 0xA0000000 [get_bd_addr_segs \
    {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property range  64K        [get_bd_addr_segs \
    {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]

validate_bd_design
generate_target all [get_files *.bd]
```

### Relevance to Your Project

Your `create_bd.tcl` script builds the two-BRAM block design programmatically. Explicit `set_property offset` calls (rather than relying on auto-assign) ensure that BRAM0 is always at 0xA0000000 and BRAM2 at 0xA0010000 regardless of the order IPs were added — matching the hardcoded addresses in `main.c`.

## Vivado TCL Scripting

### Key Findings

- **Non-project mode** runs the entire design flow in memory with no `.xpr` file: read sources → synthesize → implement → write bitstream. Invoked with `vivado -mode batch -source build.tcl`.
- **Design checkpoints (DCP)** should be written after each major step (`write_checkpoint -force post_synth.dcp`) — they let you resume from mid-flow without re-running expensive steps.
- **`-mode tcl`** starts Vivado in interactive TCL mode without a GUI; useful for debugging scripts before switching to batch.
- Version-safe tip: use `version` and `get_parts` at the top of your script to assert the correct Vivado version and part name, failing fast with a clear error rather than producing a corrupt bitstream.

### Code Example

```tcl
# Non-project batch flow skeleton for KV260 demo
set part "xck26-sfvc784-2LV-c"
set top  "kv260_top"

read_vhdl   [glob src/*.vhd]
read_xdc    constraints/timing.xdc
read_ip     [glob ip/*.xci]
generate_target all [get_ips]

synth_design -top $top -part $part -flatten_hierarchy rebuilt
write_checkpoint -force checkpoints/post_synth.dcp
report_utilization -file reports/utilization_synth.rpt

opt_design
place_design
route_design
write_checkpoint -force checkpoints/post_route.dcp
report_timing_summary -max_paths 10 -file reports/timing.rpt

write_bitstream -force output/$top.bit
```

### Relevance to Your Project

Adding a non-project batch wrapper around your existing `create_bd.tcl` gives you a reproducible one-command build: `vivado -mode batch -source build_all.tcl`. This enables CI and eliminates "works on my machine" issues when switching between Vivado 2025.1 and 2026.1.

## Vitis Bare-Metal / Standalone

### Key Findings

- **BSP stdout setting** is critical: in the standalone BSP `system.mss`, `stdout` must point to the correct UART instance (`psu_uart_1` on KV260) or `xil_printf` output is silently dropped — this is the #1 bare-metal bring-up failure.
- The standalone BSP provides `xil_printf` (lightweight, no heap/malloc required) and `printf` (full libc, requires heap in linker script); for the KV260 BRAM demo, `xil_printf` is preferred to keep the binary small.
- **Linker script heap/stack**: bare-metal default gives 8 KB heap and 2 KB stack in OCM; if your pattern buffers grow, increase `_HEAP_SIZE` and `_STACK_SIZE` in `lscript.ld`.
- **Cache coherency**: Cortex-A53 data cache can mask AXI writes to PL slaves — call `Xil_DCacheFlushRange(addr, size)` after writing patterns, or disable the D-cache with `Xil_DCacheDisable()` during bring-up.
- Interrupt controller (AXI INTC) requires `XIntc_Initialize`, `XIntc_Connect`, and `XIntc_Start` before any interrupt sources can fire; the interrupt vector table must also be set up via `Xil_ExceptionRegisterHandler`.

### Code Example

```c
#include "xil_printf.h"
#include "xil_cache.h"

#define BRAM0_BASE 0xA0000000UL
#define BRAM2_BASE 0xA0010000UL
#define PATTERN    0xDEADBEEFUL

void write_and_verify(u32 base, u32 pattern) {
    volatile u32 *bram = (volatile u32 *)base;

    /* write */
    bram[0] = pattern;
    Xil_DCacheFlushRange((UINTPTR)bram, 4);  /* flush before PL reads it */

    /* read back */
    u32 readback = bram[0];
    if (readback == pattern)
        xil_printf("PASS @ 0x%08X: wrote 0x%08X, read 0x%08X\r\n",
                   base, pattern, readback);
    else
        xil_printf("FAIL @ 0x%08X: wrote 0x%08X, read 0x%08X\r\n",
                   base, pattern, readback);
}

int main(void) {
    Xil_DCacheDisable();   /* safest for initial bring-up */
    write_and_verify(BRAM0_BASE, PATTERN);
    write_and_verify(BRAM2_BASE, PATTERN ^ 0xFFFFFFFF);
    return 0;
}
```

### Relevance to Your Project

The cache flush call is the most common reason a KV260 bare-metal AXI-BRAM test reads back stale data and prints FAIL even when the bus transaction succeeded. `Xil_DCacheDisable()` during initial bringup eliminates this variable entirely.

## XDC Timing Constraints

### Key Findings

- `set_input_delay -clock <clk> -max <ns> [get_ports <port>]` models external hold; `-min` models setup — both `-max` and `-min` variants are needed for a fully constrained interface.
- `set_output_delay` has the same syntax and similarly requires both `-max` and `-min` for complete constraint coverage.
- **Clock groups**: `set_clock_groups -asynchronous -group <clk_A> -group <clk_B>` tells the timing engine not to analyze paths between two unrelated clocks — essential when your PL logic uses a free-running clock independent of the PS AXI clock.
- For AXI interfaces sourced by the PS (`pl_clk0`), the clock is defined in the block design and exported automatically to the XDC — you do **not** need to re-create it with `create_clock`.
- Xilinx Constraint Wizard (in Vivado 2025.1+) can auto-generate initial I/O constraints — useful starting point, but always review generated constraints manually.

### Code Example

```xdc
# Clock already defined by the block design (pl_clk0 = 100 MHz)
# Add async group if you have a second PL clock domain
set_clock_groups -asynchronous \
    -group [get_clocks -include_generated_clocks clk_pl_0] \
    -group [get_clocks -include_generated_clocks clk_out1_*]

# Example I/O constraints for a hypothetical external GPIO
set_input_delay  -clock [get_clocks clk_pl_0] -max 3.0 [get_ports gpio_i[*]]
set_input_delay  -clock [get_clocks clk_pl_0] -min 0.5 [get_ports gpio_i[*]]
set_output_delay -clock [get_clocks clk_pl_0] -max 2.5 [get_ports gpio_o[*]]
set_output_delay -clock [get_clocks clk_pl_0] -min 0.0 [get_ports gpio_o[*]]

# False path on async reset (if used)
set_false_path -from [get_ports aresetn]
```

### Relevance to Your Project

The AXI-Lite signals to your BRAMs are fully internal (PS→PL over the AXI interconnect), so external I/O constraints are minimal. The `set_clock_groups` call matters if you add a second PL clock in a future revision — without it Vivado will flag thousands of false violations between unrelated clock domains.

## Kria KV260 / K26 SoM

### Key Findings

- **Default boot mode**: KV260 ships with QSPI32 boot mode and a Xilinx-supplied boot firmware in QSPI. For bare-metal development, the easiest path is JTAG boot (no BOOT.BIN required) — hold PS_MODE pins via the carrier or use XSDB to halt and load ELF.
- **MIO allocation on KV260**: PS GEM3 is assigned to Ethernet (unlike KR260 which uses GEM1) — this matters if you add networking. USB-UART is routed through PS MIO 38–39 via the carrier card's CP2102 bridge.
- **K26 SOM resources**: 49 MIO pins, 4 PS-GTR lanes (USB3/DP/PCIe/SGMII), 4 GB LPDDR4 on-module, 16 GB eMMC, onboard QSPI flash.
- **BRAM resource limit**: the K26 contains 144 × 36Kb BRAM tiles (total ~5.1 Mb / 637 KB) — keep BRAM instances small or use UltraRAM for larger buffers.
- **PL power domain**: the PL must be powered before AXI transactions to PL slaves succeed — in bare-metal JTAG flow this happens automatically, but in production BOOT.BIN flows you must ensure `psu_init` has run and PL power rail is stable before issuing AXI reads.

### Code Example

```tcl
# XSDB/XSCT commands to load and run a bare-metal ELF over JTAG
# Run from: xsct connect_and_run.tcl

connect
targets -set -nocase -filter {name =~ "*APU*"}
rst -system
after 3000

targets -set -nocase -filter {name =~ "*A53*0"}
rst -processor -clear-registers
dow /path/to/kv260_bram_demo.elf
con
after 5000

# Read back UART output on /dev/ttyUSB1 at 115200 baud
```

### Relevance to Your Project

The XSDB script above replaces the Vitis IDE Run/Debug flow for headless bare-metal testing on KV260 — useful for CI. The PL power note is the most common reason AXI reads return 0xDEAD or bus-error on first boot: ensure `psu_init` completes before your `main()` executes.

## AMD/Xilinx Tool Updates

### Key Findings

- **2026.1 is now the current release** (download page updated September 2026); 2025.1 remains the LTS baseline for KV260 bare-metal flows until 2026.1 achieves full board-file support.
- **Vitis 2025.1 notable changes**: Vitis installer bundles Vivado — no separate Vivado download needed. Third-party tool marketplace added to Vitis IDE for productivity plugins.
- **AI Engine enhancements in 2025.x**: 2D-parallel AIE + PL architecture for GEMV and FFT, vectorized SIMD sorting/correlation/convolution — not directly relevant to BRAM demo but signals where AMD is investing.
- **Kria Vitis platforms** GitHub repo (`Xilinx/kria-vitis-platforms`) targets 2026.1 toolchain as of September 2026 — if you need the latest platform files, you may need to upgrade from 2025.1.
- **2025.1 open-source release notes** (Xilinx Wiki page 3277651969) detail PetaLinux component versions — relevant if you ever add Linux alongside bare-metal.

### Code Example

```tcl
# Check Vivado tool version at start of build script (fail fast)
set required_version "2025.1"
set actual_version   [version -short]
if {[string compare $actual_version $required_version] != 0} {
    puts "ERROR: Expected Vivado $required_version, got $actual_version"
    puts "       Build aborted to prevent bitstream mismatch."
    exit 1
}

# Check target part is available
set target_part "xck26-sfvc784-2LV-c"
if {[llength [get_parts $target_part]] == 0} {
    puts "ERROR: Part $target_part not found. Install the Zynq UltraScale+ device family."
    exit 1
}
puts "INFO: Vivado $actual_version with part $target_part - OK"
```

### Relevance to Your Project

Version-gating the build script ensures that a colleague running 2026.1 gets a clear failure message rather than a subtly broken bitstream, which is especially important when IPs change signatures between Vivado minor releases.
