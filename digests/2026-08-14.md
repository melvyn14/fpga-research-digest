# FPGA Research Digest - 2026-08-14

## Executive Summary

- **BRAM Controller early-write bug**: The AXI BRAM Controller can assert write-enable one clock cycle early, silently writing to the *previous* accessed address. Add a one-cycle pipeline stage or configure `S_AXI_CTRL` latency appropriately if you see spurious data corruption.
- **BRAM/FIFO IPs removed from IP Catalog in Vivado 2025+**: AMD pulled the Embedded Memory Generator and FIFO Generator from direct RTL instantiation — they are now block-design-only. For your bare-metal project's RTL wrappers, use XPM macros (`XPM_MEMORY_SPRAM`, etc.) instead.
- **Vivado 2025.2 AXI SmartConnect**: New ultra-low-area mode via `STRATEGY` parameter reduces LUT cost of narrow-width AXI interconnect; worth enabling if you add more peripherals to the KV260 design.
- **AXI-Lite VALID deassert rule**: Once `AWVALID`, `WVALID`, or `ARVALID` is asserted, it **must not** be deasserted until the corresponding `READY` fires. Violating this can cause simulation-only passing designs to deadlock on real hardware.
- **Kria bare-metal JTAG boot requires 4 files**: `pmufw.elf`, `fsbl.elf`, the bitstream (`.bit`), and the application `.elf` — all must be loaded in order via XSDB; Cortex-A53 cores are held in reset until explicitly released.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- **Handshake immutability**: Once a master asserts `VALID`, it must hold all driven signals (address, data, control) stable until the slave asserts `READY`. The `VALID` line itself must stay high until `READY` — toggling it mid-transaction is a protocol violation that hardware may not catch.
- **Backpressure path**: If a master holds `BREADY` (write-response ready) low, the slave must keep `AWREADY` and `WREADY` de-asserted. This path is rarely exercised in simulation-only testing and is a common real-hardware bug.
- **AXI BRAM Controller early-write errata**: The IP has been documented to assert write-enable one clock cycle ahead of the intended data cycle, potentially corrupting the previous BRAM address. Workaround: use ECC mode (which adds correction logic) or insert a one-cycle bubble by keeping WVALID low for an extra cycle at the start of a burst.
- **AXI4 vs AXI4-Lite**: AXI4-Lite has no burst support — each transaction is a single beat. For your KV260 AXI-BRAM project, AXI4-Lite is the correct choice since you are reading/writing individual 32-bit registers. Use full AXI4 only if you later switch to DMA bursts.
- **AXI write transaction ordering**: AXI allows write address and write data channels to be presented independently; the BRAM controller may accept both simultaneously or in either order. Your C code `Xil_Out32` generates both channels in order, which is safe.

### Code Example

```vhdl
-- Minimal AXI4-Lite slave write-channel state machine
-- Avoids the VALID-deassert violation by holding AWREADY/WREADY
-- only when internal state is ready to consume both channels.

type axi_wr_state_t is (IDLE, GOT_ADDR, GOT_DATA, SEND_RESP);
signal wr_state : axi_wr_state_t := IDLE;

process(clk) begin
  if rising_edge(clk) then
    -- defaults
    S_AXI_AWREADY <= '0';
    S_AXI_WREADY  <= '0';
    S_AXI_BVALID  <= '0';

    case wr_state is
      when IDLE =>
        -- Accept address and data simultaneously when both valid
        if S_AXI_AWVALID = '1' and S_AXI_WVALID = '1' then
          S_AXI_AWREADY <= '1';
          S_AXI_WREADY  <= '1';
          wr_addr       <= S_AXI_AWADDR;
          wr_data       <= S_AXI_WDATA;
          wr_strb       <= S_AXI_WSTRB;
          wr_state      <= SEND_RESP;
        elsif S_AXI_AWVALID = '1' then
          S_AXI_AWREADY <= '1';
          wr_addr       <= S_AXI_AWADDR;
          wr_state      <= GOT_ADDR;
        end if;

      when GOT_ADDR =>
        if S_AXI_WVALID = '1' then
          S_AXI_WREADY <= '1';
          wr_data      <= S_AXI_WDATA;
          wr_strb      <= S_AXI_WSTRB;
          wr_state     <= SEND_RESP;
        end if;

      when SEND_RESP =>
        -- Perform register write
        reg_file(to_integer(unsigned(wr_addr(5 downto 2)))) <= wr_data;
        S_AXI_BVALID  <= '1';
        S_AXI_BRESP   <= "00"; -- OKAY
        if S_AXI_BREADY = '1' then
          wr_state <= IDLE;
        end if;

      when others =>
        wr_state <= IDLE;
    end case;
  end if;
end process;
```

### Relevance to Your Project

Your `kv260_top.vhd` wraps two AXI BRAM controllers at `0xA0000000` (BRAM0) and `0xA0010000` (BRAM2). The early-write errata above means your first write after a read to the previous BRAM address could be silently corrupted. If your PASS/FAIL test shows intermittent single-word mismatches, instrument the BRAM enable signals with an ILA and check for the extra write pulse described above.

## Vivado Block Design / IP Integrator

### Key Findings

- **TCL-first workflow**: After interactively building a block design, use `File → Export → Export Block Design...` (or `write_bd_tcl`) to save a reproducible TCL script. This script can recreate the entire BD from scratch in a new project — critical for CI/CD and team collaboration.
- **VLNV IP identification**: Every IP in the catalog is referenced by `Vendor:Library:Name:Version` (VLNV). In TCL, use `create_bd_cell -type ip -vlnv xilinx.com:ip:axi_bram_ctrl:4.1 axi_bram_ctrl_0`. Hardcoding the version (`:4.1`) prevents Vivado from silently upgrading IPs across tool versions.
- **`apply_bd_automation`**: The "Run Connection Automation" GUI action maps to `apply_bd_automation` in TCL, which handles clock/reset wiring automatically. Run it after adding each IP to avoid manual net creation.
- **IP upgrade warnings**: When opening a BD from a previous Vivado version, IP locks trigger upgrade dialogs. In batch mode, use `upgrade_ip [get_ips]` in your TCL script to non-interactively upgrade all locked IPs.
- **Address Editor**: `assign_bd_address` in TCL mirrors the Address Editor. After adding a new AXI slave, always call `assign_bd_address` or the bitstream will not expose the peripheral at the expected address.

### Code Example

```tcl
# Reproducible block design fragment for KV260 AXI-BRAM
# Run in Vivado TCL console or batch mode

proc create_axi_bram { cell_name base_addr size_kb } {
    # Instantiate BRAM controller
    set ctrl [create_bd_cell -type ip \
        -vlnv xilinx.com:ip:axi_bram_ctrl:4.1 $cell_name]
    set_property -dict {
        CONFIG.SINGLE_PORT_BRAM 1
        CONFIG.DATA_WIDTH       32
        CONFIG.MEM_DEPTH        [expr { $size_kb * 1024 / 4 }]
    } $ctrl

    # Instantiate paired BRAM
    set bram_name "${cell_name}_mem"
    set bram [create_bd_cell -type ip \
        -vlnv xilinx.com:ip:blk_mem_gen:8.4 $bram_name]
    set_property CONFIG.Memory_Type {Simple_Dual_Port_RAM} $bram

    # Connect BRAM controller <-> BRAM
    connect_bd_intf_net \
        [get_bd_intf_pins $ctrl/BRAM_PORTA] \
        [get_bd_intf_pins $bram/BRAM_PORTA]

    # Wire AXI slave port to interconnect (assumes zynq_ultra_ps_e_0 exists)
    apply_bd_automation -rule xilinx.com:bd_rule:axi4 \
        -config { Clk_master {/zynq_ultra_ps_e_0/pl_clk0} \
                  Clk_slave  {Auto}                        \
                  Master     {/zynq_ultra_ps_e_0/M_AXI_HPM0_FPD} } \
        [get_bd_intf_pins $ctrl/S_AXI]

    # Set base address
    set_property offset $base_addr \
        [get_bd_addr_segs $ctrl/S_AXI/Mem0]
    set_property range  [expr { $size_kb * 1024 }] \
        [get_bd_addr_segs $ctrl/S_AXI/Mem0]
}

# Usage
create_axi_bram axi_bram_ctrl_0 0xA0000000 4
create_axi_bram axi_bram_ctrl_1 0xA0010000 4

validate_bd_design
save_bd_design
```

### Relevance to Your Project

Your `create_bd.tcl` script is the canonical rebuild entry-point for the KV260 project. Locking VLNV versions (`:4.1`) in it protects against silent IP upgrades when colleagues or CI systems run it on newer Vivado installs. The `create_axi_bram` helper above mirrors your two-BRAM pattern and can be directly reused.

## Vivado TCL Scripting

### Key Findings

- **Non-project mode advantages**: No `.xpr` file; sources managed explicitly via `read_vhdl`, `read_xdc`. Design checkpoints (`.dcp`) become the save unit. Ideal for fully scripted builds without GUI dependency.
- **Batch mode invocation**: `vivado -mode batch -source build.tcl -tclargs "PART=xck26-sfvc784-2LV-c"` — pass arguments into TCL via `lindex $argv 0`.
- **`write_checkpoint` at each stage**: Save DCPs after synthesis, optimization, placement, and routing. This allows resuming at any stage without re-running prior steps.
- **`open_checkpoint` for incremental compile**: Start implementation from a synth DCP using `open_checkpoint synth.dcp` then `opt_design`, avoiding full re-synthesis when only HDL changes at the leaf level.
- **`report_timing_summary -file`**: Always emit timing reports to files in batch mode, as interactive timing windows are unavailable.
- **TCL version fragility**: Vivado IP Integrator TCL APIs change across tool versions. Pin your script to a specific tool version and test on upgrade.

### Code Example

```tcl
# Non-project mode RTL-to-bitstream for KV260 AXI-BRAM
# Usage: vivado -mode batch -source build.tcl

set PART    "xck26-sfvc784-2LV-c"
set TOP     "kv260_top"
set OUTDIR  "./output"
file mkdir $OUTDIR

# --- Read sources ---
read_vhdl [glob ./vhdl/*.vhd]
read_xdc  ./constraints/kv260_top.xdc

# --- Synthesis ---
synth_design -top $TOP -part $PART \
             -flatten_hierarchy rebuilt \
             -directive PerformanceOptimized
write_checkpoint -force "$OUTDIR/post_synth.dcp"
report_utilization -file "$OUTDIR/util_synth.rpt"
report_timing_summary -file "$OUTDIR/timing_synth.rpt"

# --- Implementation ---
opt_design
place_design   -directive Explore
phys_opt_design
route_design   -directive AggressiveExplore
write_checkpoint -force "$OUTDIR/post_route.dcp"

# --- Reports ---
report_timing_summary -warn_on_violation \
    -file "$OUTDIR/timing_route.rpt"
report_io    -file "$OUTDIR/io.rpt"
report_power -file "$OUTDIR/power.rpt"

# --- Bitstream ---
write_bitstream -force "$OUTDIR/$TOP.bit"

# --- Vitis XSA export ---
write_hw_platform -fixed -include_bit \
    -file "$OUTDIR/$TOP.xsa"
puts "Build complete: $OUTDIR/$TOP.bit"
```

### Relevance to Your Project

Your `create_bd.tcl` uses project mode (`create_project`). Consider adding a companion `build_impl.tcl` in non-project mode for CI: source `create_bd.tcl` to build the BD in memory, then call `generate_target all`, `export_ip_user_files`, and continue with `synth_design` — this eliminates GUI dependency in automated pipelines.

## Vitis Bare-Metal / Standalone

### Key Findings

- **Core selection**: For the Kria KV260 (K26 SoM = Zynq UltraScale+ MPSoC), target `psu_cortexa53_0` with 64-bit architecture. Do not target Cortex-R5 unless you explicitly need real-time guarantees.
- **UART assignment**: In BSP settings, set `stdin` and `stdout` to `psu_uart_1` (the UART routed to the KV260's USB-UART bridge via MIO 52/53). Using the wrong UART instance causes `xil_printf` output to be silently discarded.
- **`xparameters.h` base addresses**: Auto-generated from the XSA; look for `XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR` (= `0xA0000000`) and `XPAR_AXI_BRAM_CTRL_1_S_AXI_BASEADDR` (= `0xA0010000`). Use these in C code rather than hardcoding, so re-exported XSAs automatically update the map.
- **Vitis 2023.2+ change**: Device IDs for AXI peripherals are no longer auto-generated in `xparameters.h` in newer flows — initialize using base addresses directly, not `XPAR_*_DEVICE_ID`.
- **`Xil_Out32` / `Xil_In32`**: These are memory-mapped I/O functions in `xil_io.h`. They issue a cache-bypass store/load on Cortex-A53; no explicit cache flush needed for peripheral register access (peripherals are mapped as Device memory).
- **Linker script pitfall**: The default linker script places `.text` in DDR at `0x00000000`. If your BRAM is at `0xA0000000`, ensure your linker script does not overlap with AXI peripheral regions. Check the generated `lscript.ld` and widen DDR range if needed.

### Code Example

```c
/* main.c — bare-metal AXI-BRAM read/write test for KV260
 * Uses Xil_Out32/Xil_In32 for AXI-Lite register access.
 * BRAM0: 0xA0000000, BRAM2: 0xA0010000
 */
#include "xil_printf.h"
#include "xil_io.h"
#include "xparameters.h"

#define BRAM0_BASE  XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR
#define BRAM2_BASE  XPAR_AXI_BRAM_CTRL_1_S_AXI_BASEADDR
#define BRAM_WORDS  256   /* 1 KB */

static int bram_test(u32 base, const char *name)
{
    u32 pattern, readback;
    int errors = 0;

    /* Write ascending pattern */
    for (int i = 0; i < BRAM_WORDS; i++) {
        pattern = 0xA5000000u | (u32)i;
        Xil_Out32(base + (i * 4), pattern);
    }

    /* Readback and verify */
    for (int i = 0; i < BRAM_WORDS; i++) {
        pattern  = 0xA5000000u | (u32)i;
        readback = Xil_In32(base + (i * 4));
        if (readback != pattern) {
            xil_printf("[%s] FAIL @ offset 0x%03X: "
                       "expected 0x%08X, got 0x%08X\r\n",
                       name, i * 4, pattern, readback);
            errors++;
        }
    }
    return errors;
}

int main(void)
{
    int total_errors = 0;
    xil_printf("KV260 AXI-BRAM test start\r\n");

    total_errors += bram_test(BRAM0_BASE, "BRAM0");
    total_errors += bram_test(BRAM2_BASE, "BRAM2");

    if (total_errors == 0)
        xil_printf("PASS: all BRAM words verified\r\n");
    else
        xil_printf("FAIL: %d errors\r\n", total_errors);

    return total_errors;
}
```

### Relevance to Your Project

This is a direct improvement of the test pattern your `main.c` likely implements. Key additions: using `XPAR_*` macros instead of literal addresses, iterating all 256 words (not just a few), and printing the exact failing address/value for faster debug. The `bram_test` function can be parameterized to stress-test different patterns (walking 1s, alternating 0x55/0xAA, etc.).

## XDC Timing Constraints

### Key Findings

- **`set_clock_groups -asynchronous` has highest priority**: This constraint cannot be overridden by subsequent `set_false_path` or `set_multicycle_path` — apply it carefully only to genuinely asynchronous domains.
- **PS-PL clock on KV260**: The Zynq UltraScale+ PS generates `pl_clk0` (typically 100 MHz, configurable in the Zynq PS IP). This clock is automatically defined in Vivado; do not manually `create_clock` for it.
- **AXI interconnect clocks**: If your AXI interconnect and fabric logic share `pl_clk0`, they are synchronous — no `set_clock_groups` needed. Only add asynchronous constraints if you introduce a second PL clock.
- **KV260 PL fabric pin constraints**: The KV260 carrier card routes most IOs through the K26 SoM FPGA IO banks (500, 501, 504, 505). Pin assignments should reference the SOM pinout, not the carrier card connector IDs.
- **`set_input_delay` / `set_output_delay`**: Required for signals crossing the FPGA boundary (external IOs). Not needed for internal AXI connections between PS and PL, which are analyzed automatically.
- **False path for CDC registers**: For any registers crossing from `pl_clk0` to a slower fabric clock, use `set_false_path -from [get_clocks pl_clk0] -to [get_clocks my_slow_clk]` rather than `set_clock_groups`, to preserve analysis within each domain.

### Code Example

```tcl
# kv260_top.xdc — XDC constraints for KV260 AXI-BRAM demo

# pl_clk0 is created automatically by Vivado from the PS IP.
# Do NOT add a manual create_clock for it.

# set_clock_groups -asynchronous \
#     -group [get_clocks pl_clk0] \
#     -group [get_clocks osc_clk_50]

# -------------------------------------------------------
# Example: LED output on KV260 carrier (MIO is in PS,
# PL LED would be on a specific bank 505 pin)
# -------------------------------------------------------
# set_property PACKAGE_PIN  K2   [get_ports {led[0]}]
# set_property IOSTANDARD   LVCMOS33 [get_ports {led[0]}]
# set_output_delay -clock [get_clocks pl_clk0] -max 2.0 [get_ports {led[0]}]
# set_output_delay -clock [get_clocks pl_clk0] -min 0.5 [get_ports {led[0]}]

# -------------------------------------------------------
# Timing exceptions for synchronizer chains (2-FF CDC):
# -------------------------------------------------------
# set_false_path -to [get_cells -hierarchical -filter {NAME =~ *sync_reg[0]}]

# Report timing after implementation — catch violations early
# report_timing_summary -warn_on_violation -file timing.rpt
```

### Relevance to Your Project

Your KV260 AXI-BRAM design uses only `pl_clk0` from the PS — a fully synchronous system. Your XDC file therefore needs minimal constraints: only `PACKAGE_PIN`/`IOSTANDARD` for any PL IOs (e.g., status LEDs), and no `set_clock_groups` for the AXI paths. Vivado infers all AXI timing from the PS clock automatically. If timing fails on the AXI BRAM path, the fix is usually reducing `pl_clk0` frequency in the Zynq PS IP, not adding timing exceptions.

## Kria KV260 / K26 SoM

### Key Findings

- **JTAG bare-metal boot requires 4 artefacts**: PMU firmware (`pmufw.elf`), FSBL (`fsbl.elf`), PL bitstream (`.bit`), and application ELF (`.elf`). All are loaded over JTAG in order via XSDB commands.
- **Boot mode for JTAG**: Remove the SD card before powering on; the KV260 defaults to JTAG boot when no SD is present. Alternatively, write `0x0100` to register `0xFF5E0200` via XSDB to force JTAG mode in software.
- **Cortex-A53 held in reset**: After JTAG connect, all A53 and R5F cores are in reset. You must explicitly release A53 #0 with the XSDB `rst -processor -cores` command before it can execute code.
- **UART routing**: The KV260 USB-UART bridge (FT4232H) is connected to PS MIO 52 (`UART1_RX`) and MIO 53 (`UART1_TX`). In your BSP, stdout must be `psu_uart_1` for `xil_printf` to appear on the USB-UART COM port.
- **MIO bank layout**: MIO bank 500 carries I2C (MIO 0–1), QSPI, and UART; bank 501 carries additional peripherals. PL IOs use EMIO or dedicated FPGA banks 64–67 on the XCK26.
- **Power sequencing**: The K26 SoM manages power sequencing via its on-board PMIC. Do not rely on the carrier card for power-on sequencing; the SOM brings up PS power rails before PL.

### Code Example

```tcl
# xsdb_jtag_boot.tcl — XSDB script to load bare-metal app on KV260
# Usage: xsdb xsdb_jtag_boot.tcl
# Requires: KV260 powered on with SD removed (JTAG boot mode)

connect

# Target 1 = PSU, force JTAG boot mode
targets -set -nocase -filter {name =~ "PSU"}
mwr 0xFF5E0200 0x0100
rst -system

after 3000

# Load PMUFW into MicroBlaze PMU
targets -set -nocase -filter {name =~ "MicroBlaze PMU"}
dow ./fsbl/pmufw.elf
con

after 1000

# Load FSBL + app into Cortex-A53 #0
targets -set -nocase -filter {name =~ "Cortex-A53 #0"}
rst -processor -cores
dow ./fsbl/fsbl.elf
con

after 3000

# Program PL bitstream
targets -set -nocase -filter {name =~ "PSU"}
fpga ./output/kv260_top.bit

after 2000

# Load and run application
targets -set -nocase -filter {name =~ "Cortex-A53 #0"}
rst -processor
dow ./Debug/kv260_app.elf
con

puts "KV260 bare-metal boot complete - check UART for PASS/FAIL"
```

### Relevance to Your Project

This XSDB script directly targets your KV260 AXI-BRAM project's artefacts. The key insight is the ordering: PMUFW → FSBL → bitfile → app. Skipping PMUFW causes voltage scaling and DDR initialization to fail silently. Skipping FSBL means DDR is unconfigured and your AXI transactions will fault. Always load all four in order for a reliable bare-metal bring-up.

## AMD/Xilinx Tool Updates (Vivado/Vitis 2025.x)

### Key Findings

- **BRAM/FIFO IPs removed from RTL flow (2025.1+)**: `Embedded Memory Generator` and `FIFO Generator` are no longer instantiable directly from the IP Catalog in RTL projects. They are now IP Integrator (block design) only. For RTL-based designs, AMD now recommends `XPM_MEMORY_*` and `XPM_FIFO_*` macros.
- **Vivado 2025.2 AXI SmartConnect**: Added `STRATEGY` parameter for ultra-low-area mode, reducing LUT overhead for AXI interconnects with narrow data widths (good for resource-constrained PL designs on the K26).
- **Vivado 2025.2 simplified AXI wrapper creation**: Automatic wrapper creation and management for all AMD IP in block designs reduces manual TCL for complex port mappings.
- **Vitis 2025.1 released July 2025**: UG1742 covers updates. Notable: improved Vitis Classic compatibility layer, updated BSP drivers. Vitis 2026.1 is already available as of August 2026.
- **AXI deadlock bug fix (2025.1)**: A potential deadlock between peripheral and cache data AXI interfaces (frequency-optimized pipeline mode) was patched. If you observed intermittent hangs in 2024.x, upgrading to 2025.1+ resolves this.
- **2026.x is current**: AMD has released Vivado/Vitis 2026.1. The 2025.1 stack your project uses remains fully functional and supported; upgrading is optional but 2026.1 adds further AXI and platform improvements.

### Code Example

```vhdl
-- XPM_MEMORY_SPRAM: replacement for legacy Embedded Memory Generator
-- Use this in RTL designs with Vivado 2025.1+ where BRAM IP
-- is no longer directly instantiable from IP Catalog.

library ieee;
use ieee.std_logic_1164.all;
library xpm;
use xpm.vcomponents.all;

entity bram_xpm_wrapper is
  port (
    clka  : in  std_logic;
    ena   : in  std_logic;
    wea   : in  std_logic_vector(3 downto 0);  -- byte enables
    addra : in  std_logic_vector(9 downto 0);  -- 1024 locations
    dina  : in  std_logic_vector(31 downto 0);
    douta : out std_logic_vector(31 downto 0)
  );
end entity;

architecture rtl of bram_xpm_wrapper is
begin
  xpm_mem_inst : xpm_memory_spram
    generic map (
      ADDR_WIDTH_A        => 10,
      AUTO_SLEEP_TIME     => 0,
      BYTE_WRITE_WIDTH_A  => 8,    -- enable byte-wide write enables
      CASCADE_HEIGHT      => 0,
      ECC_BIT_RANGE       => "7:0",
      ECC_MODE            => "no_ecc",
      MEMORY_INIT_FILE    => "none",
      MEMORY_INIT_PARAM   => "",
      MEMORY_OPTIMIZATION => "true",
      MEMORY_PRIMITIVE    => "block",  -- force BRAM (not LUT)
      MEMORY_SIZE         => 32768,   -- bits = 1024 * 32
      MESSAGE_CONTROL     => 0,
      READ_DATA_WIDTH_A   => 32,
      READ_LATENCY_A      => 2,
      READ_RESET_VALUE_A  => "0",
      RST_MODE_A          => "SYNC",
      USE_MEM_INIT        => 0,
      WAKEUP_TIME         => "disable_sleep",
      WRITE_DATA_WIDTH_A  => 32,
      WRITE_MODE_A        => "read_first"
    )
    port map (
      clka        => clka,
      ena         => ena,
      wea         => wea,
      addra       => addra,
      dina        => dina,
      douta       => douta,
      injectdbiterra => '0',
      injectsbiterra => '0',
      regcea      => '1',
      rsta        => '0',
      sleep       => '0'
    );
end architecture;
```

However, if you ever move any BRAM to a standalone RTL instantiation (e.g., for a custom AXI slave without the BRAM Controller IP), you must use `XPM_MEMORY_SPRAM` instead of `blk_mem_gen`.
