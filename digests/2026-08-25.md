## Executive Summary

1. **AXI-Lite backpressure bug**: If your PS master holds `BREADY` low, the AXI BRAM controller
   must lower `AWREADY`/`WREADY` accordingly; getting this wrong produces silent read-back
   corruption — the most common cause of spurious FAIL in PS→PL connectivity demos.
2. **Vivado 2025.x BRAM/FIFO change**: Embedded Memory Generator and FIFO Generator IPs are no
   longer instantiable from the IP Catalog alone — they must live inside IP Integrator block
   designs. If you try to add them to a standalone RTL project directly, you'll get an error.
3. **KV260 UART BSP gotcha**: The KV260 JTAG/UART header is UART1, but the standalone BSP
   defaults `stdin`/`stdout` to UART0. Without changing `standalone_stdin`/`standalone_stdout`
   to `psu_uart_1` in BSP settings, `xil_printf` output is invisible.
4. **2025.2 IP config format change**: AMD switched IP configuration files from XML to JSON in
   Vivado 2025.2. Any TCL automation that parses `.xci` XML will break — migrate to the new
   JSON `.xci` format or use the provided migration API.
5. **XSDB bare-metal boot flow for KV260**: The recommended JTAG flow is to push `fsbl.elf` +
   `pmufw.elf` + your bitstream + `app.elf` via XSDB script; relying on `Run As → Launch on
   Hardware` alone without an FSBL often hangs at PL initialization on Kria.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- **VALID must not deassert**: Once a master asserts `AWVALID`, `WVALID`, or `ARVALID`, it must
  hold them high until the corresponding `READY` handshake completes. Deasserting early is a
  protocol violation that causes sporadic failures in simulation but not synthesis.
- **Backpressure propagation**: If the master holds `BREADY` low, a compliant slave must hold
  `AWREADY`/`WREADY` low too. Xilinx's own BRAM controller reference core has historically
  mishandled this; always stress-test with delayed BREADY.
- **AXI-Stream TKEEP must match bus width**: `TKEEP` must be enabled both in the IP core GUI
  and the software driver / device tree. Omitting `TKEEP` on a 32-bit bus causes byte-lane
  errors on partial-width writes.
- **TLAST and data-width conversion**: Up-converting AXI-Stream beats requires that all beats of
  the new larger beat share identical `TID`/`TDEST`; an early `TLAST` before the wider beat
  fills will flush partial data silently.
- **Packet-mode FIFO depth**: In packet mode, the entire packet is buffered before output.
  Size the FIFO depth to `max_packet_bytes / (bus_width_bytes)` plus pipeline margin; undersizing
  stalls the FIFO and introduces hard-to-debug latency spikes.

### Code Example

```vhdl
-- Minimal AXI-Lite slave: correct BREADY backpressure handling
process(clk)
begin
  if rising_edge(clk) then
    if rst = '1' then
      s_axi_awready <= '0';
      s_axi_wready  <= '0';
      s_axi_bvalid  <= '0';
    else
      -- Only accept write address/data when master is ready to receive response
      if s_axi_bvalid = '0' or s_axi_bready = '1' then
        s_axi_awready <= '1';
        s_axi_wready  <= '1';
      else
        -- Master holding BREADY low: stall upstream channels
        s_axi_awready <= '0';
        s_axi_wready  <= '0';
      end if;

      if s_axi_awvalid = '1' and s_axi_awready = '1' and
         s_axi_wvalid  = '1' and s_axi_wready  = '1' then
        -- Latch write; assert BVALID
        s_axi_bvalid <= '1';
        s_axi_bresp  <= "00"; -- OKAY
      elsif s_axi_bready = '1' then
        s_axi_bvalid <= '0';
      end if;
    end if;
  end if;
end process;
```

### Relevance to Your Project

Your `kv260-axi-bram-demo` has the PS Cortex-A53 as AXI master writing to BRAM0 at `0xA0000000`
and BRAM2 at `0xA0010000`. The most likely cause of a FAIL result is the PS holding `BREADY` low
during burst or back-to-back transactions while the AXI BRAM Controller hasn't lowered its
`AWREADY`. Add a short loop in your C test that writes then immediately reads without any
`Xil_DCacheFlushRange` — if it PASS there but FAIL under cache operations, the issue is cache,
not AXI. If it FAILs in simple back-to-back writes, the backpressure path is suspect.

## Vivado Block Design / IP Integrator

### Key Findings

- **Connection Automation adds reset/interconnect automatically**: After running
  `Run Connection Automation`, Vivado inserts a `Processor System Reset` and `AXI Interconnect`
  (or `AXI SmartConnect` in 2024+) — do not manually wire reset and clocking after running this.
- **Address Editor — always click "Assign All"**: Manually typed offsets can be overridden on
  re-synthesis. Use the Address Editor's "Assign All" button and lock the segment to prevent
  regeneration from shifting your base addresses.
- **IP version upgrades on open**: Opening a project in a newer Vivado version flags stale IP.
  Use `report_ip_status` in TCL to check before upgrading; upgrading in batch avoids GUI prompts.
- **2025.2 BRAM/FIFO only in IPI**: As of 2025.1/2025.2, Embedded Memory Generator and FIFO
  Generator are instantiable only through IP Integrator, not as standalone IP Catalog items.
- **2025.2: IP config files now JSON**: The `.xci` config format changed from XML to JSON.
  Any CI scripts that grep/parse `.xci` XML need updating.
- **Module reference vs. RTL block**: Adding your VHDL top-level as a module reference inside
  a block design (right-click canvas → Add Module) lets you keep the block design for PS/AXI
  wiring while keeping RTL outside IPI — useful for the `kv260_top.vhd` wrapper.

### Code Example

```tcl
# Address Editor: lock AXI BRAM base addresses after assignment
open_bd_design [get_files *.bd]
assign_bd_address
# Lock BRAM0 at 0xA000_0000, 64K range
set_property offset 0xA0000000 [get_bd_addr_segs {processing_system7_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property range 64K          [get_bd_addr_segs {processing_system7_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
# Lock BRAM2 at 0xA001_0000
set_property offset 0xA0010000 [get_bd_addr_segs {processing_system7_0/Data/SEG_axi_bram_ctrl_1_Mem0}]
set_property range 64K          [get_bd_addr_segs {processing_system7_0/Data/SEG_axi_bram_ctrl_1_Mem0}]
validate_bd_design
save_bd_design
```

### Relevance to Your Project

Your `create_bd.tcl` should lock the BRAM segment addresses as above to prevent Vivado from
reassigning them across tool versions. Also consider adding `report_ip_status -name ip_status`
before any synthesis run in CI to catch stale IP early rather than mid-synthesis.

## Vivado TCL Scripting

### Key Findings

- **Non-project mode**: Source files, constraints, and runs are all managed explicitly in TCL —
  no `.xpr` file on disk. Best for CI: `vivado -mode batch -source build.tcl` exits automatically
  after completion. Reports must be explicitly generated with `report_timing_summary` etc.
- **Project mode from TCL**: Use `create_project` + `add_files` + `launch_runs impl_1 -to_step
  write_bitstream` for a reproducible project-mode build. This is what `write_project_tcl`
  exports when you use File → Export → Export as TCL script.
- **IP Integrator in non-project mode**: Requires `create_bd_design` before any `create_bd_cell`
  calls; then `generate_target all [get_files *.bd]` before synthesis.
- **Batch log inspection**: In non-project mode, parse `vivado.log` for `CRITICAL WARNING` and
  `ERROR` strings in your CI script — the tool exit code alone doesn't distinguish routing errors
  from timing failures.
- **`generate_target` vs `export_ip_user_files`**: Always run `generate_target` first, then
  `export_ip_user_files -of_objects [get_ips *]` before synthesis; skipping either step causes
  "IP locked" errors on first synthesis run.

### Code Example

```tcl
# Non-project mode: full build flow skeleton for kv260-axi-bram-demo
set part "xck26-sfvc784-2LV-c"

# 1. Read sources
read_vhdl -library work [glob ./vhdl/*.vhd]
read_xdc   ./constraints/kv260_top.xdc

# 2. Create & populate block design inline
source ./tcl/create_bd.tcl

# 3. Generate all IP targets (OOC synthesis stubs, wrapper HDL)
generate_target all [get_files *.bd]
make_wrapper -files [get_files *.bd] -top
read_vhdl [glob ./kv260.gen/sources_1/bd/*/hdl/*_wrapper.vhd]

# 4. Synthesis
synth_design -top kv260_wrapper -part $part
opt_design

# 5. Implementation
place_design
route_design

# 6. Reports (explicit in non-project mode)
report_timing_summary -file timing_summary.rpt
report_utilization    -file utilization.rpt

# 7. Bitstream
write_bitstream -force output/kv260_top.bit
```

### Relevance to Your Project

Wrapping your existing `create_bd.tcl` in the non-project skeleton above lets you run headless
CI builds. The `set part "xck26-sfvc784-2LV-c"` is the correct part string for the K26 SoM
on the KV260 carrier with the `-2LV` speed grade.

## Vitis Bare-Metal / Standalone

### Key Findings

- **UART1 vs UART0 on KV260**: The physical USB-UART header (J4) maps to `psu_uart_1` (UART1).
  The BSP generator defaults `standalone_stdin`/`standalone_stdout` to `psu_uart_0`. **Fix**:
  In BSP settings, set both to `psu_uart_1`, regenerate BSP, rebuild — otherwise all
  `xil_printf` output is discarded silently.
- **`xil_printf` limitations**: No floating-point support (`%f` is not handled); use `%d` with
  integer scaling. Max format string length is also limited — long format strings silently
  truncate on some BSP versions.
- **Linker script memory regions**: The default `lscript.ld` for ZynqMP places the application
  in DDR at `0x0`. For KV260 bare-metal, ensure the OCM and DDR regions match your memory map;
  the PSU DDR starts at `0x00000000` and extends to `0x7FFFFFFF` (2 GB on K26).
- **Interrupt controller**: For AXI peripheral interrupts, instantiate `XScuGic` (GIC-400 on
  ZynqMP), not the older `XIntc`; the latter is for MicroBlaze.
- **Cache coherency with AXI BRAM**: Call `Xil_DCacheFlushRange(base_addr, length)` before
  reading back from BRAM if data caching is enabled. Alternatively, mark the BRAM address range
  as Device memory in the MPU table to bypass the cache entirely.

### Code Example

```c
#include "xil_printf.h"
#include "xil_cache.h"
#include "xparameters.h"

#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL
#define TEST_WORDS  16

void bram_write_read_test(u32 base, const char *name) {
    volatile u32 *bram = (volatile u32 *)base;
    u32 errors = 0;

    /* Write pattern */
    for (int i = 0; i < TEST_WORDS; i++)
        bram[i] = 0xDEAD0000 | (u32)i;

    /* Flush D-cache before readback to avoid stale cache hits */
    Xil_DCacheFlushRange(base, TEST_WORDS * sizeof(u32));

    /* Readback check */
    for (int i = 0; i < TEST_WORDS; i++) {
        u32 expected = 0xDEAD0000 | (u32)i;
        if (bram[i] != expected) {
            xil_printf("  [%s] word[%d]: got 0x%08X, expected 0x%08X\r\n",
                       name, i, (unsigned)bram[i], (unsigned)expected);
            errors++;
        }
    }
    xil_printf("%s: %s (%u errors)\r\n", name, errors ? "FAIL" : "PASS", (unsigned)errors);
}

int main(void) {
    xil_printf("\r\n=== KV260 AXI-BRAM Test ===\r\n");
    bram_write_read_test(BRAM0_BASE, "BRAM0");
    bram_write_read_test(BRAM2_BASE, "BRAM2");
    xil_printf("=== Done ===\r\n");
    return 0;
}
```

### Relevance to Your Project

The cache flush before readback is the single most common fix for projects exactly like yours:
a pattern is written, read back immediately, and reports FAIL because the CPU read the stale
D-cache line rather than the PL-side BRAM value. If your PASS/FAIL is intermittent, add the
`Xil_DCacheFlushRange` call immediately after the write loop.

## XDC Timing Constraints

### Key Findings

- **`set_input_delay` / `set_output_delay` model board-level timing**: These are NOT internal
  FPGA paths — they tell the timing engine what delay exists outside the FPGA on board traces
  and external components, relative to the clock at the FPGA pin.
- **For AXI-BRAM demo (PL internal only)**: If all your logic is PS→AXI→BRAM inside the PL
  with no external I/O timing paths, `set_input_delay`/`set_output_delay` on external ports
  are optional. Focus on `create_clock` for your PL clock and letting the tool close timing
  internally.
- **`set_clock_groups -asynchronous`**: Use this between the PS clock domains (fclk_clk0 etc.)
  and any free-running PL clocks to prevent false timing paths across unrelated domains.
- **Timing Constraint Wizard**: In Vivado 2025.x, use `Edit Timing Constraints → Wizard` after
  synthesis to auto-detect unconstrained paths; it generates starter XDC stubs you can refine.
- **`-max` and `-min` for setup/hold**: Always specify both `-max` (setup) and `-min` (hold)
  for input and output delay constraints; omitting `-min` leaves hold paths unconstrained.

### Code Example

```tcl
# kv260_top.xdc — minimal constraints for AXI-BRAM bare-metal demo

# PL fabric clock from PS (100 MHz example)
# The PS drives fclk_clk0; constrain it so the timing engine knows the clock period
create_clock -period 10.000 -name fclk_clk0 \
    [get_pins -hierarchical -filter {NAME =~ */FCLKCLK[0]}]

# Treat PS and any external asynchronous clocks as unrelated
set_clock_groups -asynchronous \
    -group [get_clocks fclk_clk0] \
    -group [get_clocks -of_objects [get_pins -hierarchical -filter {NAME =~ */clk_out*}]]

# False path on async reset (if present in VHDL top)
set_false_path -from [get_ports sys_rst_n]

# No external I/O timing needed for a pure PS-to-PL BRAM design
# Add set_input_delay / set_output_delay only when you add real external ports (GPIO, SPI, etc.)
```

### Relevance to Your Project

The `kv260_top.vhd` wrapper likely only connects the PS clock and AXI signals internally, so
the XDC above is the complete set you need. If Vivado reports "no clocks found" warnings during
implementation, the `create_clock` targeting `FCLKCLK[0]` is the fix.

## Kria KV260 / K26 SoM

### Key Findings

- **Boot mode default is QSPI32**: KV260 Starter Kits ship with QSPI as default boot mode.
  For development/debug, switch to JTAG boot via XSDB: write `0x1FF5E0010` to `0xFF5E0010`
  (BOOT_MODE_USER register) and reset.
- **USB-UART is J4 on the carrier (UART1)**: The micro-USB debug connector (J4) exposes
  two COM ports: the first is JTAG, the second is UART1. Always use the second port at 115200 8N1.
- **EMIO GPIO available for PL logic**: MIO pins are largely consumed by DDR4, QSPI, eMMC,
  USB3, Ethernet, and DisplayPort. Use EMIO GPIO (routed through the PL fabric) to connect
  custom PL signals back to the PS.
- **Bare-metal needs FSBL for PL init**: Without an FSBL, the PS DDR, PLL, and clocks are
  not initialized, and BRAM access from the PS fails. The minimal XSDB flow must load
  `fsbl.elf` + `pmufw.elf` before your application.
- **KV260 board file for Vivado**: AMD provides a KV260 board file package. Install it via
  `Tools → Board Repository` so `apply_board_preset` correctly configures DDR4, QSPI, and UART.
  Without it, you get an unconstrained DDR interface that fails DRC.

### Code Example

```tcl
# XSDB script: JTAG boot flow for KV260 bare-metal AXI-BRAM demo
# Run from Vitis XSCT console or: xsct this_script.tcl

connect

# Switch to JTAG boot mode (override QSPI)
targets -set -filter {name =~ "PSU"}
mwr 0xFF5E0010 0x00000000   ;# JTAG boot mode
mwr 0xFF5E0000 0x00000001   ;# PS-only reset to apply boot mode

after 2000

# Select A53 #0
targets -set -filter {name =~ "Cortex-A53 #0"}

# Load FSBL (initializes DDR4, PLLs, clock)
dow ./fsbl/Debug/fsbl.elf
con; after 5000; stop

# Load PMU firmware
targets -set -filter {name =~ "MicroBlaze PMU"}
dow ./pmufw/Debug/pmufw.elf
con; after 2000

# Back to A53, load bitstream + application
targets -set -filter {name =~ "Cortex-A53 #0"}
fpga -file ./output/kv260_top.bit
dow ./app/Debug/app.elf
con

# UART output now visible on J4 second COM port at 115200
```

### Relevance to Your Project

If `xil_printf("PASS\r\n")` never appears on your serial terminal, the two most likely causes
are (1) wrong UART (use UART1 / second COM port on J4) and (2) FSBL not loaded so clocks
aren't initialized. Run the XSDB script above and watch for the FSBL's own boot messages first;
if those appear, your application ELF is being reached.

## AMD/Xilinx Tool Updates (Vivado / Vitis 2025.x)

### Key Findings

- **Vivado 2025.2 highlights**:
  - SystemVerilog Interface support with auto wrapper creation for AMD IP and BDs
  - AXI Switch and AXI SmartConnect now support `ultra-low-area` mode via `STRATEGY` parameter
  - New SLR crossing report for better QoR analysis on stacked silicon devices
  - IP configuration files changed from XML to JSON (`.xci` format)
  - Module reference support for RTL with NoC XPMs in top-level BD
- **BRAM/FIFO IP restricted to IPI in 2025.x**: Embedded Memory Generator and FIFO Generator
  no longer appear in standalone IP Catalog for direct instantiation. If your flow relied on
  `create_ip -name blk_mem_gen` outside a BD, it will break on 2025.1+.
- **Vitis 2025.2 known issue**: `LD_PRELOAD` with `libctxXrandrhook.so` causes Vitis Unified
  IDE crashes on some Linux desktop configurations. Workaround: `unset LD_PRELOAD` before
  launching Vitis.
- **Vitis AI 5.1 uses Vivado/Vitis 2025.1.1**: Indicates 2025.1 is a stable, actively-patched
  release; `.1.1` patch likely fixes the most critical 2025.1 GA issues.
- **2026.1 downloads already available**: AMD has released 2026.1, suggesting 2025.x is at
  end-of-active-development; consider whether to move to 2025.2 or 2026.1 for long-term projects.

### Code Example

```tcl
# 2025.x compatibility: use ip_integrator for BRAM instead of standalone blk_mem_gen
# Old (breaks in 2025.1+):
#   create_ip -name blk_mem_gen -vendor xilinx.com -library ip ...

# New: create inside a block design
open_bd_design [get_files *.bd]

# Add BRAM controller
create_bd_cell -type ip -vlnv xilinx.com:ip:axi_bram_ctrl:4.1 axi_bram_ctrl_0

# Add BRAM (Embedded Memory Generator — only valid inside IPI in 2025.x)
create_bd_cell -type ip -vlnv xilinx.com:ip:emb_mem_gen:1.0   emb_mem_gen_0

# Connect BRAM controller to Embedded Memory Generator
connect_bd_intf_net [get_bd_intf_pins axi_bram_ctrl_0/BRAM_PORTA] \
                    [get_bd_intf_pins emb_mem_gen_0/BRAM_PORTA]

# Check and migrate IP versions (important when moving 2024.x -> 2025.x)
report_ip_status -name ip_status
upgrade_ip [get_ips -filter {UPGRADE_VERSIONS != ""}]
```

### Relevance to Your Project

If you ever upgrade the `kv260-axi-bram-demo` project from Vivado 2024.x to 2025.x, run
`report_ip_status` first. The biggest breaking change is the BRAM/FIFO IP restriction — your
block design should already use the BRAM inside IPI (via `axi_bram_ctrl` + `blk_mem_gen`),
but confirm that no standalone IP instantiation exists in your RTL or TCL scripts.
