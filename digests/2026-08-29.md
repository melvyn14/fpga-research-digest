# FPGA Research Digest - 2026-08-29

## Executive Summary
- **AXI BRAM write-enable timing bug**: The Xilinx AXI BRAM Controller has a documented issue where the write-enable asserts one clock early and extends one clock too long if the BRAM Enable signal is not properly driven — confirm your BRAM0/BRAM2 enable tie-off in kv260_top.vhd.
- **write_bd_tcl version lock**: The TCL script produced by `write_bd_tcl` embeds the Vivado version and cannot be used across releases; pin your `create_bd.tcl` to Vivado 2025.1 and add `-ignore_minor_versions` only for patch differences.
- **QSPI lock on KV260 Starter Kit**: The Starter Kit QSPI is locked to prevent bricking; the SOM purchased separately has no such restriction. For bare-metal, create BOOT.BIN (fsbl.elf + pmufw.elf + .bit + app.elf) and load it into a user partition, not the protected AMD partition.
- **Vivado 2025.2 SystemVerilog interfaces**: Automatic AXI wrapper generation for SV instances is now available — relevant if you plan to migrate the VHDL top to a mixed-language design.
- **PL-to-PS interrupt wiring**: For future interrupt-driven BRAM reads, connect AXI INTC output to the Zynq PS pl_ps_irq input, then use XScuGic on the A53 to route to your ISR — the AXI INTC ISR register is read via AXI-Lite.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings
- **Handshake invariants**: Once `VALID` is asserted by a master/slave, it must not be de-asserted until the corresponding `READY` handshake completes. Violating this can cause silent data corruption or deadlock.
- **Write-enable timing bug in AXI BRAM Controller**: A documented issue causes the write-enable to assert one clock early and remain asserted one clock too long, writing an extra word to the *previous* address. Root cause: the `BRAM Enable` signal was not correctly tied, allowing an extra clock of write-enable to leak through.
- **No read/write collision detection**: The AXI BRAM Controller does not detect or arbitrate simultaneous read and write port collisions within the BRAM — the application must ensure the PS does not read while a write is in flight to the same address.
- **AXI-Stream sideband signals**: `TLAST` marks the last beat of a packet; `TKEEP` qualifies valid bytes within a beat (default to `1` when all bytes are valid); `TUSER` carries ancillary metadata per beat. Tie `TKEEP` and `TSTRB` to all-ones when your AXI-Stream data has no partial beats.

### Code Example
```vhdl
-- Safe AXI-Lite master handshake: hold AWVALID/WVALID until both AWREADY and WREADY seen
-- Do NOT drop AWVALID after asserting it; wait for AWREADY
process(clk)
begin
  if rising_edge(clk) then
    if rst = '1' then
      awvalid_r <= '0';
      wvalid_r  <= '0';
    elsif start_write = '1' then
      awvalid_r <= '1';
      wvalid_r  <= '1';
    else
      if s_axi_awready = '1' then awvalid_r <= '0'; end if;
      if s_axi_wready  = '1' then wvalid_r  <= '0'; end if;
    end if;
  end if;
end process;

s_axi_awvalid <= awvalid_r;
s_axi_wvalid  <= wvalid_r;
```

### Relevance to Your Project
Your `main.c` drives BRAM0 (0xA0000000) and BRAM2 (0xA0010000) via AXI-Lite. Verify that the Cortex-A53 bare-metal writes use blocking memory-mapped I/O (stores followed by a data memory barrier `dmb sy`) so that the AXI-Lite write channel fully completes before the subsequent read. The write-enable timing bug is also worth confirming in simulation: drive BRAM Enable statically high from the block design and check the waveforms for any spurious writes to the previous address.

## Vivado Block Design / IP Integrator

### Key Findings
- **Connection Automation vs. manual wiring**: Use `apply_bd_automation` in Tcl for routine connections (AXI master→slave, clock/reset), but always inspect the resulting address assignments in the Address Editor — automation can assign overlapping ranges when multiple BRAM controllers share the same master.
- **Regenerate outputs after property changes**: After modifying an IP's parameters via `set_property CONFIG.*`, call `generate_target all [get_files *.bd]` and then `export_ip_user_files` to ensure downstream synthesis sees updated wrappers.
- **Default parameters are not written by `write_bd_tcl`**: Only user-changed parameters appear in the exported Tcl. If you rely on a default that happens to differ across IP versions, you must explicitly set it in your script.
- **Include layout with `-include_layout`**: By default, block design XY coordinates are not exported; add this flag when sharing scripts so teammates get the same visual layout.

### Code Example
```tcl
# Recreate block design programmatically (non-project mode snippet)
create_bd_design "kv260_bd"

# Instantiate Zynq MPSoC PS
set ps [create_bd_cell -type ip -vlnv xilinx.com:ip:zynq_ultra_ps_e:3.5 zynq_ultra_ps_e_0]
apply_bd_automation -rule xilinx.com:bd_rule:zynq_ultra_ps_e \
    -config {apply_board_preset "1"} [get_bd_cells zynq_ultra_ps_e_0]

# Instantiate AXI BRAM Controller + Block Memory Generator for BRAM0
set bram_ctrl0 [create_bd_cell -type ip -vlnv xilinx.com:ip:axi_bram_ctrl:4.1 axi_bram_ctrl_0]
set_property CONFIG.SINGLE_PORT_BRAM {1} $bram_ctrl0
set bmg0 [create_bd_cell -type ip -vlnv xilinx.com:ip:blk_mem_gen:8.4 blk_mem_gen_0]
apply_bd_automation -rule xilinx.com:bd_rule:bram_cntlr \
    -config {BRAM "Auto"} [get_bd_intf_pins axi_bram_ctrl_0/BRAM_PORTA]

# Connect AXI-Lite from PS to BRAM controller
apply_bd_automation -rule xilinx.com:bd_rule:axi4 \
    -config {Master "/zynq_ultra_ps_e_0/M_AXI_HPM0_FPD" Clk "Auto"} \
    [get_bd_intf_pins axi_bram_ctrl_0/S_AXI]

# Assign address (ensure no overlap with BRAM2 at 0xA0010000)
assign_bd_address -target_address_space /zynq_ultra_ps_e_0/Data \
    [get_bd_addr_segs axi_bram_ctrl_0/S_AXI/Mem0] -range 64K -offset 0xA0000000

validate_bd_design
save_bd_design
```

### Relevance to Your Project
Your `create_bd.tcl` script instantiates BRAM0 at 0xA0000000 and BRAM2 at 0xA0010000. Confirm address segment sizes (64KB minimum for AXI BRAM Controller) don't overlap, and that both controllers are driven by the same HPM0_FPD master port — they must appear as separate address segments under the same master.

## Vivado TCL Scripting

### Key Findings
- **Non-Project Mode with block designs**: If a block design is generated with Out-Of-Context (OOC) synthesis set, it can be dropped into a non-project flow via `read_bd`. Without pre-generation, you must use global synthesis mode or generate the BD inline.
- **`write_bd_tcl` is version-locked**: The exported script embeds the Vivado version string and will refuse to run in a different release. Use `-ignore_minor_versions` only for patch-level (e.g. 2025.1.1 → 2025.1.2) differences.
- **`write_project_tcl` for full reproducibility**: Use `File > Project > Write Tcl` with the "Recreate Block Designs using Tcl" checkbox enabled to get a single script that reconstructs both the Vivado project and all block designs from scratch — the gold standard for CI pipelines.
- **Stripping project commands**: For embedding in a CI/CD pipeline, strip the `create_project`/`set_property DIRECTORY` preamble from the exported script and replace with your own `open_project` or in-memory flow invocation.

### Code Example
```tcl
# Export block design to Tcl (run in Vivado Tcl console or batch mode)
write_bd_tcl -force -include_layout ./tcl/create_bd.tcl

# In batch/non-project mode: source the BD script then implement
vivado -mode batch -source run_impl.tcl

# run_impl.tcl skeleton for non-project mode
read_vhdl [glob ./vhdl/*.vhd]
read_xdc  ./xdc/kv260_top.xdc
source    ./tcl/create_bd.tcl        ;# recreates the block design
make_wrapper -files [get_files kv260_bd.bd] -top
read_vhdl [glob ./bd/kv260_bd/hdl/*.vhd]

synth_design  -top kv260_top -part xck26-sfvc784-2LV-c
opt_design
place_design
route_design
write_bitstream -force kv260_top.bit
write_hw_platform -fixed -include_bit -force ./kv260_top.xsa
```

### Relevance to Your Project
Your `create_bd.tcl` is the reproducibility artifact. Running it against a clean Vivado 2025.1 install should recreate the exact block design. Add `validate_bd_design` as the second-to-last command (before `save_bd_design`) to catch mismatched AXI widths or unconnected required ports during script replay rather than at synthesis.

## Vitis Bare-Metal / Standalone

### Key Findings
- **BSP stdout assignment**: Set `stdin`/`stdout` in the BSP settings to `psu_uart_1` (the USB-UART on KV260) so that `xil_printf` routes to the correct UART instance. Misassignment is the most common cause of a "silent" application.
- **Linker script DDR region**: In `lscript.ld`, verify that the heap and stack are placed in DDR (`psu_ddr_0_MEM_0`) and not in OCM — OCM is 256 KB and silently overflows for larger applications.
- **PL-to-PS interrupt wiring (AXI INTC + XScuGic)**: Connect the AXI INTC `irq` output to `pl_ps_irq[0:0]` on the PS. On the A53, initialize XScuGic, register your ISR at the correct GIC interrupt ID (121+PL interrupt index for ZU+), then call `XScuGic_Connect` and `XScuGic_Enable`. The AXI INTC ISR register must also be cleared (via AXI-Lite write) at the end of the ISR.
- **Vitis 2025.2 xil_printf.h path change**: A reported issue in 2025.2 is that `xil_printf.h` is not found when building standalone apps — ensure your include path references `${XILINX_VITIS}/data/embeddedsw/lib/bsp/standalone/src/common`.

### Code Example
```c
/* Minimal AXI-Lite BRAM write + read with memory barrier on Cortex-A53 */
#include "xil_io.h"
#include "xil_printf.h"

#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL
#define TEST_PATTERN 0xDEADBEEFUL

int main(void) {
    u32 rd0, rd2;

    /* Write patterns */
    Xil_Out32(BRAM0_BASE, TEST_PATTERN);
    Xil_Out32(BRAM2_BASE, ~TEST_PATTERN);

    /* Data memory barrier: ensure AXI-Lite write completes before read */
    dmb();

    /* Read back */
    rd0 = Xil_In32(BRAM0_BASE);
    rd2 = Xil_In32(BRAM2_BASE);

    if (rd0 == TEST_PATTERN && rd2 == ~TEST_PATTERN)
        xil_printf("PASS: BRAM0=0x%08X BRAM2=0x%08X\r\n", rd0, rd2);
    else
        xil_printf("FAIL: BRAM0=0x%08X (exp 0x%08X)  BRAM2=0x%08X (exp 0x%08X)\r\n",
                   rd0, TEST_PATTERN, rd2, ~TEST_PATTERN);
    return 0;
}
```

### Relevance to Your Project
This is the core test pattern for your project. Confirm that `dmb()` (or `Xil_DCacheFlushRange` if the cache is enabled) is called between writes and reads to prevent the A53 store buffer from returning stale cached values instead of the actual BRAM contents. If the PS cache is disabled for the BRAM address region (the normal bare-metal default for device memory), the barrier ensures ordering at the AXI bus level.

## XDC Timing Constraints

### Key Findings
- **`set_input_delay` / `set_output_delay` syntax**: Both commands specify external path delays in nanoseconds relative to a clock edge at the device boundary. Negative values are valid and represent data that arrives before the capturing edge.
- **`-max` and `-min` variants are mandatory for SDC correctness**: Without both `-max` and `-min`, Vivado uses the single value for both setup and hold analysis, which can mask hold violations.
- **`set_clock_groups -asynchronous`**: Use this between the PS clock domain (from the Zynq PLL) and any free-running PL reference clocks to tell the timing engine they have no phase relationship — missing this causes false cross-domain paths to be flagged.
- **Impact on synthesis**: `create_clock`, `create_generated_clock`, `set_input_delay`, and `set_output_delay` all influence synthesis retiming in Vivado 2025.x — place your XDC in the constraints set before synthesis, not post-synthesis.

### Code Example
```tcl

# PS-derived 100 MHz AXI clock (generated inside Zynq, named by IPI)
create_generated_clock -name axi_clk \
    -source [get_pins zynq_ultra_ps_e_0/pl_clk0] \
    -divide_by 1 \
    [get_nets zynq_ultra_ps_e_0/pl_clk0]

# Asynchronous relationship between PL clock and any board oscillator
# (uncomment if you add an external PL clock input)
# set_clock_groups -asynchronous \
#     -group [get_clocks axi_clk] \
#     -group [get_clocks board_osc]

# False path on BRAM address/data outputs (internal PS AXI, no I/O constraints needed)
# I/O delays only needed if you add GPIO/EMIO signals to the XDC

# Example: constrain an LED output driven from the AXI-BRAM readback result
# set_output_delay -clock axi_clk -max 2.0 [get_ports led_pass]
# set_output_delay -clock axi_clk -min 0.5 [get_ports led_pass]
```

### Relevance to Your Project
A pure PS-to-PL AXI design with no external I/O (only UART over MIO) typically needs no `set_input_delay`/`set_output_delay` constraints. However, adding `set_clock_groups -asynchronous` between `pl_clk0` and any future free-running reference prevents phantom cross-domain timing failures when the design is extended with additional clock sources.

## Kria KV260 / K26 SoM

### Key Findings
- **QSPI partition lock**: The KV260 Starter Kit QSPI flash is locked so that accidental writes cannot overwrite the AMD-signed boot firmware. Bare-metal BOOT.BIN must be written to a *user* partition (slot 1 or 2), not the protected slot 0. Only a SOM purchased separately has full QSPI access.
- **Bare-metal BOOT.BIN composition**: The required components are `fsbl.elf` (First-Stage Bootloader), `pmufw.elf` (PMU firmware), the PL bitstream `.bit`, and the application `.elf`. All four must be packaged with Bootgen into a single `BOOT.BIN`.
- **PL reset after QSPI programming**: After writing BOOT.BIN, press the `POR_B` reset button (or power-cycle) to complete a full power-on reset — a soft reset alone does not reprogram the PL from QSPI.
- **EMIO for carrier-card GPIOs**: The KV260 starter bitstream provides EMIO mapping for the fan control pin; custom designs should allocate EMIO MIO indices carefully to avoid conflicts with the carrier card's board-level signals (see KV260 schematic MIO mapping table, DS986).
- **Debugging bare-metal on KV260**: Connect Vitis Classic debugger via the USB-JTAG port; the pre-loaded FSBL will pause at the XSDB hook if the correct FSBL debug build is used, allowing ELF loading without full QSPI reprogramming during development.

### Code Example
```tcl
# Bootgen BIF file for KV260 bare-metal BOOT.BIN
# Save as kv260_bm.bif, then run:
#   bootgen -image kv260_bm.bif -arch zynqmp -o BOOT.BIN -w

the_ROM_image:
{
    [fsbl_config] a53_x64
    [bootloader, destination_cpu=a53-0] ./fsbl/fsbl.elf
    [pmufw_image]                        ./pmufw/pmufw.elf
    [destination_device=pl]              ./bitstream/kv260_top.bit
    [destination_cpu=a53-0, exception_level=el-3, trustzone] ./app/kv260_axi_bram.elf
}
```

### Relevance to Your Project
Your demo requires the PL bitstream (containing BRAM0 and BRAM2 at their respective AXI addresses) to be loaded before the application runs. The BIF file above is the exact packaging needed. During development, skip QSPI and use Vitis JTAG download (`program_hw_devices` + `dow` in xsdb) to iteratively load the bitstream and ELF without flashing QSPI each iteration.

## AMD/Xilinx Tool Updates (Vivado/Vitis 2025.x)

### Key Findings
- **Vivado 2025.2 — SystemVerilog interface support**: AXI connections between SystemVerilog instances now get automatic wrapper generation in IP Integrator. Mixed-language designs (VHDL top + SV submodules) benefit from simplified AXI wiring in block design.
- **Vivado 2025.2 — BUFG_FABRIC replication**: Per-SLR and per-VNoC column replication for high-fanout nets reduces clock distribution penalties in large Versal designs; this feature does not affect ZU+ / KV260 but is relevant when targeting larger parts.
- **Vitis 2025.2 — xil_printf.h header path issue**: Some users report `xil_printf.h not found` in fresh 2025.2 standalone BSP projects — workaround is to add the explicit BSP include path or rebuild the BSP after updating the platform.
- **Vivado 2025.1 is the current stable target for KV260**: The 2025.2 release targets primarily Versal Gen 2 devices; for KV260 (xck26), stay on 2025.1 unless a specific fix in 2025.2 is needed.
- **New DSP library in Vitis 2025.2**: Cumulative Sum, Euclidean Distance, and Function Approximation functions added to the Vitis DSP library — not directly applicable to the BRAM demo but useful for signal-processing extensions.

### Code Example
```tcl
# Vivado 2025.1 batch-mode implementation script
# Run: vivado -mode batch -source implement.tcl -log impl.log

set part "xck26-sfvc784-2LV-c"
set top  "kv260_top"

# Source the BD recreation script (version-locked to 2025.1)

# Add HDL wrapper and sources

# Implementation flow
launch_runs synth_1 -jobs 4
wait_on_run synth_1

wait_on_run impl_1

# Export XSA for Vitis
write_hw_platform -fixed -include_bit -force ./${top}.xsa
puts "Done. XSA written to ${top}.xsa"
```

### Relevance to Your Project
This script ties together the full Vivado 2025.1 flow from your `create_bd.tcl` through bitstream generation and XSA export. Running this in CI (GitHub Actions or a local make target) ensures every change to `kv260_top.vhd` or `create_bd.tcl` produces a verified bitstream without manual GUI steps.
