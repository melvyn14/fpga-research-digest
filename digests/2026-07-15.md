# FPGA Research Digest - 2026-07-15

## Executive Summary
- **AXI write-channel sync is the #1 bare-metal pitfall**: your slave (AXI BRAM ctrl) must not assert AWREADY/WREADY until *both* AWVALID and WVALID are high; if either is missing the transaction stalls silently.
- **Vivado 2025.1 ships a new RTL-based AXI Switch IP** with configurable width/type bridging — useful when you want to fan out from the PS HPM port to additional PL peripherals beyond the current two BRAMs.
- **Kria K26 default boot mode is QSPI32** — for bare-metal iteration, switch to JTAG boot via XSDB so you avoid reflashing every run; revert to QSPI for final deployment.
- **The AXI Protocol Checker IP (PG101)** can be inserted in-line in your block design during bring-up to catch handshake violations (VALID de-asserted before READY, response-channel timeout) before they appear as silent PASS/FAIL mismatches in your C test loop.
- **XDC for a simple AXI-Lite design needs fewer than 20 lines** — one `create_clock` on the PL clock, `set_clock_groups -asynchronous` for the PS/PL crossing, and `set_false_path` on async resets; over-constraining creates phantom critical paths.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings
- A transfer completes only when **both VALID and READY are high on the same rising clock edge** — neither side may de-assert VALID once it has been raised until the handshake completes (AXI spec rule, not optional).
- The **write address (AW) and write data (W) channels are independent**; a correct AXI-Lite slave raises AWREADY and WREADY only after checking that *both* AWVALID and WVALID are high. Raising AWREADY early can corrupt burst ordering even in AXI-Lite single-beat transactions.
- ZipCPU formal verification of Xilinx's own AXI-Lite demo core found a **read-channel bug that was still present as of Vivado 2016.3+** — third-party RTL should always be checked with the AXI Protocol Checker IP (PG101) or formal tools before trusting read-back results.
- BREADY held low by the master forces the slave to hold BVALID; if your C code never reads the response register in the AXI BRAM controller's status, the write pipeline can stall after a few transactions.
- AXI-Stream: if `M_AXIS_TVALID` is high and `M_AXIS_TREADY` is low on the penultimate beat of a burst, `M_AXIS_TLAST` being asserted while stalled is a **protocol violation** — guard with `tready` check before advancing `tlast`.

### Code Example
```c
/* Bare-metal AXI-Lite write to BRAM0 at 0xA0000000, then read-back verify */
#include "xil_io.h"

#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL
#define PATTERN     0xDEADBEEFUL

static int axi_bram_test(u32 base, const char *name) {
    Xil_Out32(base + 0x00, PATTERN);
    Xil_Out32(base + 0x04, ~PATTERN);
    u32 r0 = Xil_In32(base + 0x00);
    u32 r1 = Xil_In32(base + 0x04);
    int pass = (r0 == PATTERN) && (r1 == (~PATTERN & 0xFFFFFFFF));
    xil_printf("%s: %s (wrote 0x%08X, read 0x%08X)\r\n",
               name, pass ? "PASS" : "FAIL", PATTERN, r0);
    return pass;
}
```

### Relevance to Your Project
Your `main.c` writes patterns to BRAM0 (`0xA0000000`) and BRAM2 (`0xA0010000`) and reads them back. The most likely cause of a silent FAIL is a stalled B-channel response — ensure your C code reads or at least the AXI BRAM controller is configured to auto-clear BRESP. Add the AXI Protocol Checker IP in parallel with both AXI BRAM controllers during simulation/bring-up to catch any handshake violation before concluding hardware is broken.

## Vivado Block Design / IP Integrator

### Key Findings
- **"Run Connection Automation"** wires clocks, resets, and AXI interfaces automatically — always run it after adding each new IP rather than wiring by hand; it avoids mis-matched clock domains on the AXI interconnect.
- **Address Editor**: set each BRAM segment's Range to the **minimum needed** (4 KB for typical 4 KB BRAMs) rather than leaving the default 64 KB or 1 MB — this avoids address decode ambiguity when multiple slaves share the same interconnect.
- **Export Block Design → TCL**: `File → Export → Export Block Design` generates a self-contained `.tcl` that can recreate the entire block design from scratch — essential for CI and version control (store the `.tcl`, not the `.bd` XML, to keep diffs readable).
- **"Validate Design" (F6)** reports unconnected ports and interface width mismatches; run it after every major change before synthesis; do not rely solely on synthesis to catch interface errors.
- Vivado 2025.1 added a **new Pblock Planner** for physical-region-constrained IP placement — useful when you add a third BRAM later and want to pin it to a specific die region on the K26.

### Code Example
```tcl
# Minimal block design creation sequence for AXI-BRAM demo
# Run: vivado -mode batch -source create_bd.tcl

create_project kv260_proj ./kv260_proj -part xck26-sfvc784-2LV-c
set_property board_part xilinx.com:kv260_som:part0:1.4 [current_project]

create_bd_design "kv260_bd"

# Zynq UltraScale+ PS
set ps [create_bd_cell -type ip -vlnv xilinx.com:ip:zynq_ultra_ps_e:3.5 zynq_ultra_ps_e_0]
apply_bd_automation -rule xilinx.com:bd_rule:zynq_ultra_ps_e \
    -config {apply_board_preset "1"} [get_bd_cells zynq_ultra_ps_e_0]

# AXI BRAM Controller 0
set bram0_ctrl [create_bd_cell -type ip -vlnv xilinx.com:ip:axi_bram_ctrl:4.1 axi_bram_ctrl_0]
set bram0_gen  [create_bd_cell -type ip -vlnv xilinx.com:ip:blk_mem_gen:8.4 blk_mem_gen_0]
connect_bd_intf_net [get_bd_intf_pins $bram0_ctrl/BRAM_PORTA] \
                    [get_bd_intf_pins $bram0_gen/BRAM_PORTA]

# Run automation and assign addresses
apply_bd_automation -rule xilinx.com:bd_rule:axi4 \
    -config {Master "/zynq_ultra_ps_e_0/M_AXI_HPM0_FPD" Clk "Auto"} \
    [get_bd_intf_pins $bram0_ctrl/S_AXI]

assign_bd_address [get_bd_addr_segs {axi_bram_ctrl_0/S_AXI/Mem0}]
set_property offset 0xA0000000 \
    [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property range 4K \
    [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]

validate_bd_design
save_bd_design
```

### Relevance to Your Project
Your `create_bd.tcl` script should follow this pattern — explicitly setting offset `0xA0000000` (BRAM0) and `0xA0010000` (BRAM2) in the Address Editor via TCL guarantees the C code's hardcoded base addresses match the hardware map. A common failure mode is Vivado auto-assigning a different offset on block design regeneration.

## Vivado TCL Scripting

### Key Findings
- **Non-project mode** (`vivado -mode batch -source script.tcl`) keeps no `.xpr` file — you manage sources manually and must call `write_checkpoint` to save intermediate state; ideal for CI pipelines.
- **Export Block Design** (via GUI or `write_bd_tcl`) is the recommended way to capture block design state; the exported script is portable and removes GUI-only project metadata when manually trimmed.
- **`report_utilization`**, **`report_timing_summary`**, and **`report_cdc`** can all be called from batch TCL after `opt_design` / `place_design` / `route_design` — pipe results to log files for automated pass/fail checking.
- Variable scoping: TCL proc-scoped variables do not persist between `source` calls; use global variables or pass state through return values when chaining multiple sourced scripts.
- **`open_bd_design`** vs **`current_bd_design`**: always call `open_bd_design` when working with a `.bd` file that was not created in the same TCL session, or you'll get "No current block design" errors.

### Code Example
```tcl
# Non-project mode: synthesize, implement, write bitstream, export XSA
# Usage: vivado -mode batch -source build_all.tcl

read_vhdl      [glob ../vhdl/*.vhd]
read_bd        ./kv260_bd/kv260_bd.bd
read_xdc       ../constraints/kv260_timing.xdc

synth_design   -top kv260_top -part xck26-sfvc784-2LV-c -flatten_hierarchy rebuilt
write_checkpoint ./checkpoints/post_synth.dcp -force

opt_design
place_design
phys_opt_design
route_design

write_checkpoint ./checkpoints/post_route.dcp -force
report_timing_summary -file ./reports/timing_summary.rpt
report_utilization    -file ./reports/utilization.rpt

write_bitstream -force ./output/kv260_top.bit

# Export XSA for Vitis
write_hw_platform -fixed -include_bit -force \
    -file ./output/kv260.xsa
```

### Relevance to Your Project
Replacing the GUI-driven build with a non-project TCL script like this makes your project fully reproducible from a clean clone. The `write_hw_platform` at the end produces the `.xsa` that Vitis consumes to generate your BSP and linker script — critical for keeping the BRAM address map in C in sync with the hardware.

## Vitis Bare-metal / Standalone

### Key Findings
- **Standalone BSP** (`standalone_domain`) must be regenerated whenever the `.xsa` changes — outdated BSP is a silent source of wrong base-address macros like `XPAR_AXI_BRAM_CTRL_0_BASEADDR`.
- `xil_printf` is a lightweight `printf` variant that **does not support floating-point** by default — use `%d`, `%x`, `%u`; for float, link the full `printf` or convert manually.
- **JTAG boot for iteration**: set boot mode to JTAG via XSDB (`targets -set -filter {name =~ "APU*"}; dow app.elf; con`), avoiding QSPI reflash during development.
- **QSPI boot for deployment**: package `BOOT.BIN` with `bootgen` using a BIF file specifying FSBL + bitstream + ELF; the K26 ships pre-configured for QSPI32 boot.
- AXI Interrupt Controller: change **Interrupt Output Connection from "Bus" to "Single"** in the IP customization dialog *before* running connection automation — otherwise the PS interrupt input won't wire automatically.
- `Xil_DCacheFlushRange` / `Xil_ICacheInvalidateRange` are needed before reading back BRAM if D-cache is enabled — a cached read will return the write-buffer value, not the actual BRAM content, causing false PASSes.

### Code Example
```c
/* Cache-safe BRAM write-read test for Vitis standalone */
#include "xil_cache.h"
#include "xil_io.h"
#include "xil_printf.h"

#define BRAM0_BASE   XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR
#define TEST_WORDS   16U

void bram_selftest(void) {
    /* Write phase */
    for (u32 i = 0; i < TEST_WORDS; i++) {
        Xil_Out32(BRAM0_BASE + (i * 4), 0xA5A50000 | i);
    }

    /* Flush D-cache so reads hit the BRAM, not the write buffer */
    Xil_DCacheFlushRange((UINTPTR)BRAM0_BASE, TEST_WORDS * 4);

    /* Read and verify */
    u32 pass = 1;
    for (u32 i = 0; i < TEST_WORDS; i++) {
        u32 expected = 0xA5A50000 | i;
        u32 actual   = Xil_In32(BRAM0_BASE + (i * 4));
        if (actual != expected) {
            xil_printf("FAIL @ word %u: expected 0x%08X got 0x%08X\r\n",
                       i, expected, actual);
            pass = 0;
        }
    }
    if (pass) xil_printf("BRAM0 selftest: PASS (%u words)\r\n", TEST_WORDS);
}
```

### Relevance to Your Project
Your current test writes a fixed pattern and reads it back — if the Cortex-A53 D-cache is enabled (it is by default in Vivado-generated BSPs for Zynq UltraScale+), adding `Xil_DCacheFlushRange` before the read-back is the single most likely fix if you observe intermittent FAIL results. The `XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR` macro from the BSP should match your hardcoded `0xA0000000`; if they diverge, the BSP is stale.

## XDC Timing Constraints

### Key Findings
- **A minimal AXI-Lite design needs fewer than 20 XDC lines**: one `create_clock` on the PL clock (from the PS clock output), `set_clock_groups -asynchronous` for PS/PL crossing, and `set_false_path` on async resets.
- **Do not use `set_false_path -from [get_clocks *] -to [get_clocks *]`** — this silences all timing analysis and masks real violations. Be specific about which clock pairs cross asynchronously.
- `set_input_delay` / `set_output_delay` are only required if PL I/O pins are involved; an internal PS→PL AXI-Lite path with no external I/O pads needs neither.
- **`report_cdc`** (after `route_design`) lists all detected clock-domain crossings with recommended constraints — use it as a checklist rather than hand-writing CDCs.
- Splitting `set_clock_groups -asynchronous` into one command per clock pair (rather than one global command listing all clocks) prevents "non-existent path" warnings that can obscure real issues.

### Code Example
```tcl
# kv260_timing.xdc - minimal constraints for PS→PL AXI-Lite BRAM demo

# PL Fabric clock: PS outputs 100 MHz on pl_clk0
# The actual clock net name comes from your block design wrapper
create_clock -name pl_clk0 -period 10.000 \
    [get_pins zynq_ultra_ps_e_0/inst/PS8_i/PLCLK[0]]

# PS and PL clocks are asynchronous (separate PLLs)
# List each pair explicitly to avoid "non-existent path" warnings
set_clock_groups -name ps_pl_async -asynchronous \
    -group [get_clocks -include_generated_clocks pl_clk0] \
    -group [get_clocks -include_generated_clocks clk_pl_0]

# Async resets cross clock domains by design - exclude from timing
set_false_path -from [get_pins zynq_ultra_ps_e_0/inst/PS8_i/PLFPGARESETN[*]]

# UART TX pin (if routed through PL) - adjust delay to match board trace
# set_output_delay -clock pl_clk0 -max 2.0 [get_ports uart_rtl_txd]
# set_output_delay -clock pl_clk0 -min 0.0 [get_ports uart_rtl_txd]
```

### Relevance to Your Project
Your AXI-BRAM demo has no external PL I/O clocks (the PS drives `pl_clk0` to the interconnect), so the XDC above is nearly complete for your design. The UART is routed through PS MIO on the KV260, not through PL, so no PL UART output delays are needed. The critical constraint to verify is that `set_clock_groups` correctly names the generated clocks — run `report_clocks` after synthesis to confirm the names.

## Kria KV260 / K26 SoM

### Key Findings
- **Default boot mode is QSPI32** — the on-board DIP switch controls this; for development, changing to **JTAG boot** (via XSDB/XSCT) means you skip reflashing the flash for every iteration.
- The K26 has **49 MIO pins** dedicated to PS peripherals (UART0 on MIO42/43 for UART-USB, GigE, USB); PMOD and RPi headers on the KV260 carrier connect to **PL fabric** (not MIO), requiring XDC pin assignments and a PL GPIO or custom IP.
- **AXI address range for PL**: `M_AXI_HPM0_FPD` covers `0x8000_0000`–`0xBFFF_FFFF` for PL slaves — your BRAM0 (`0xA000_0000`) and BRAM2 (`0xA001_0000`) sit within this window.
- There is **no device tree in the default QSPI boot binary** for KV260 baremetal apps; the BSP provides all peripheral configuration via C/`xparameters.h`.
- K26 SoM crashing while enabling AXI nodes is a known issue when the bitstream is not loaded before the PS attempts AXI transactions — always load the bitstream (via JTAG `fpga` command or BOOT.BIN) before running the ELF.

### Code Example
```tcl
# XSDB session: JTAG-boot bare-metal ELF on KV260 without reflashing QSPI
# Run in Vitis XSDB console or: xsdb -eval "source boot_jtag.tcl"

connect

# Reset and hold in JTAG boot mode (overrides DIP switch for this session)
targets -set -filter {name =~ "PSU"}
rst -system

# Program PL bitstream first - MUST precede any AXI transaction
targets -set -filter {name =~ "xck26*"}
fpga -file /path/to/kv260_top.bit

# Load ELF onto A53 core 0
targets -set -filter {name =~ "Cortex-A53 #0"}
rst -processor
dow /path/to/kv260.elf

# Optional: set breakpoint at main
bpadd -addr &main

# Run
con
```

### Relevance to Your Project
This XSDB flow eliminates the QSPI reflash loop during active development of your AXI-BRAM demo. The ordering matters: `fpga -file` (loads bitstream) must run *before* `dow` and `con`, otherwise the PS accesses unmapped AXI addresses and hangs. The UART output (`xil_printf`) will appear on the USB-UART port (ttyUSB1 typically) as soon as `con` runs.

## AMD/Xilinx Tool Updates (Vivado/Vitis 2025.x)

### Key Findings
- **Vivado 2025.1** key additions:
  - **PS-first boot**: PL can be programmed *after* OS boots, enabling faster bring-up and dynamic PL reconfiguration flows.
  - **New Pblock Planner**: GUI tool for creating physical implementation constraints blocks.
  - **Fully customizable RTL-based AXI Switch IP**: configurable AXI data-width bridging and interface-type translation — replaces ad-hoc interconnect customization.
  - **NoC time-slicing QoS** for Versal bandwidth management.
- **Vivado 2025.2** is now available (downloads page confirms), indicating the 2025.x series has reached its second point release with additional stability and IP updates.
- **Vitis 2026.1** release notes are already published, suggesting AMD has accelerated the release cadence — worth checking for Zynq UltraScale+ standalone library updates before starting a new project.
- The **2025.1 Open Source Component Release Notes** on the AMD Wiki document changes to the Standalone BSP, lwIP, and FreeRTOS libraries — relevant if you plan to add a lightweight TCP/IP stack over the UART or Ethernet on the KV260.

### Code Example
```tcl
# Vivado 2025.1: customizable AXI Switch IP instantiation
# Bridges HPM0_FPD (32-bit AXI) to a 64-bit wide BRAM controller

    -vlnv xilinx.com:ip:axi_crossbar:2.1 axi_crossbar_0

set_property -dict [list \
    CONFIG.NUM_SI  {1} \
    CONFIG.NUM_MI  {2} \
    CONFIG.DATA_WIDTH {32} \
] [get_bd_cells axi_crossbar_0]

# New in 2025.1: RTL-based AXI Switch alternative with type bridging

# set_property CONFIG.DATA_WIDTH_CONVERSION {true} [get_bd_cells axi_switch_0]

# Address map for two BRAM controllers

    [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]

    [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_1_Mem0}]
```

### Relevance to Your Project
If you plan to expand beyond two BRAMs or add a third AXI slave (GPIO, timer, custom IP), the new AXI Switch IP in 2025.1 is a cleaner choice than nesting multiple AXI Interconnect IPs. The PS-first boot capability also opens the door to loading your `kv260_top.bit` from Linux at runtime rather than hardcoding it in BOOT.BIN — a useful workflow for iterative PL development while keeping the PS environment stable.
