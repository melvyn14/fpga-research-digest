# FPGA Research Digest - 2026-09-01

## Executive Summary
- **AXI BRAM controller write-enable glitch**: the IP can assert write-enable one clock cycle early and hold it longer than expected, silently corrupting BRAM contents — tie `bram_en` correctly and verify with ILA captures
- **`apply_bd_automation` is the canonical connection helper**: it wires clocks, resets, and interconnects automatically for any slave AXI-MM port; call it after every `create_bd_cell` in your TCL script instead of hand-wiring
- **Match Vivado + Vitis versions exactly**: the XSA exported from Vivado 2025.1 is only guaranteed compatible with Vitis 2025.1; mixing releases silently breaks BSP generation and linker output
- **Kria QSPI32 is the default boot mode**: for bare-metal iteration you can switch to JTAG/USB boot via a register write + reset, then run ELF directly from Vitis without regenerating BOOT.BIN each time
- **Vivado 2025.2 adds `STRATEGY` ultra-low-area mode** for AXI Switch and AXI SmartConnect — useful when fitting tight resource budgets on the K26

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings
- AXI-Lite uses five independent channels: Write Address (AW), Write Data (W), Write Response (B), Read Address (AR), Read Data (R)
- **VALID/READY handshake rule**: once the master asserts VALID, it must hold data stable until READY is seen; VALID must not be deasserted mid-transaction — violating this is the most common cause of spurious bus timeouts
- **AXI BRAM controller timing bug** (AMD support confirmed): the IP can assert write-enable a clock cycle early, potentially writing an extra word; the "BRAM Enable" pin must be driven correctly to gate this
- AXI-Stream: `TVALID` is the only mandatory signal — once asserted it cannot be deasserted until `TREADY` is seen (sticky VALID rule); `TLAST` marks end-of-packet and is required for packet-mode FIFOs
- In packet-mode FIFO, data is withheld on the master side until `TLAST` is received — plan latency accordingly in burst-heavy designs

### Code Example
```c
/* AXI-Lite write + read-back with explicit write-response check */
#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL

static inline void axi_write(uintptr_t base, uint32_t offset, uint32_t val) {
    *(volatile uint32_t *)(base + offset) = val;
    /* Memory barrier: ensure store completes before any subsequent load */
    __asm__ volatile("dsb sy" ::: "memory");
}

static inline uint32_t axi_read(uintptr_t base, uint32_t offset) {
    __asm__ volatile("dsb sy" ::: "memory");
    return *(volatile uint32_t *)(base + offset);
}

int axi_bram_test(void) {
    const uint32_t pattern = 0xDEADBEEF;
    axi_write(BRAM0_BASE, 0x00, pattern);
    axi_write(BRAM2_BASE, 0x00, ~pattern);
    uint32_t r0 = axi_read(BRAM0_BASE, 0x00);
    uint32_t r2 = axi_read(BRAM2_BASE, 0x00);
    return (r0 == pattern && r2 == ~pattern) ? 0 : -1;
}
```

### Relevance to Your Project
Your `main.c` writes patterns to BRAM0 (`0xA0000000`) and BRAM2 (`0xA0010000`) and reads them back. The `dsb sy` barrier ensures the A53 does not speculate reads past the preceding writes over AXI-Lite — without it, the "PASS" print can race the actual completion of the AXI transaction on the PL side.

## Vivado Block Design / IP Integrator

### Key Findings
- `apply_bd_automation` (UG835) is the primary Designer Assistance command: it configures selected IPI objects and auto-creates interconnects, clock buffers, and reset synchronisers
- IP Integrator's Tcl extension mechanism allows per-IP automation callbacks — useful for custom IP that needs parameter propagation hooks
- Connection automation for slave AXI-MM ports automatically adds an AXI Interconnect (or SmartConnect) and ties the clock/reset net
- Vivado 2025.2: SystemVerilog interfaces are now supported in block designs, enabling simplified AXI connections between SV RTL instances and automatic wrapper generation for AMD IP

### Code Example
```tcl
# Minimal block design TCL: Zynq PS + two AXI BRAM controllers
create_bd_design "kv260_bd"

# Add Zynq UltraScale+ PS
create_bd_cell -type ip -vlnv xilinx.com:ip:zynq_ultra_ps_e:3.5 zynq_ps
apply_bd_automation -rule xilinx.com:bd_rule:zynq_ultra_ps_e \
    -config {apply_board_preset 1} [get_bd_cells zynq_ps]

# Add two AXI BRAM Controllers
create_bd_cell -type ip -vlnv xilinx.com:ip:axi_bram_ctrl:4.1 axi_bram_ctrl_0
create_bd_cell -type ip -vlnv xilinx.com:ip:axi_bram_ctrl:4.1 axi_bram_ctrl_1

# Connection automation wires up clk, rst, and SmartConnect automatically
apply_bd_automation -rule xilinx.com:bd_rule:axi4 \
    -config {Master "/zynq_ps/M_AXI_HPM0_FPD" Clk "Auto"} \
    [get_bd_intf_pins axi_bram_ctrl_0/S_AXI]
apply_bd_automation -rule xilinx.com:bd_rule:axi4 \
    -config {Master "/zynq_ps/M_AXI_HPM0_FPD" Clk "Auto"} \
    [get_bd_intf_pins axi_bram_ctrl_1/S_AXI]

# Assign addresses
assign_bd_address
validate_bd_design
save_bd_design
```

### Relevance to Your Project
Your `create_bd.tcl` script builds the block design that connects the Zynq PS to the two BRAM controllers. Using `apply_bd_automation` for each slave port guarantees the SmartConnect, clock buffer, and reset are inserted correctly — manually wiring these is a common source of "simulation passes, hardware fails" bugs.

## Vivado TCL Scripting

### Key Findings
- **Non-project mode** gives full reproducible builds with no hidden project state: sources are explicit, outputs are deterministic — ideal for CI
- Full non-project RTL-to-bitstream chain: `read_vhdl` → `read_xdc` → `synth_design` → `opt_design` → `place_design` → `route_design` → `write_bitstream -force`
- Batch invocation: `vivado -mode batch -source build.tcl` exits with non-zero status on any TCL error — use this for CI pass/fail
- Use `write_hw_platform -fixed -force` at the end of the TCL script to export the XSA for Vitis without opening the GUI
- `report_timing_summary -file timing.rpt` and `report_utilization -file util.rpt` should be called before `write_bitstream` to catch violations early

### Code Example
```tcl
# Non-project mode build: VHDL sources + XDC → bitstream + XSA
set PART "xck26-sfvc784-2LV-c"
set TOP  "kv260_top"

read_vhdl   [glob ./vhdl/*.vhd]
read_xdc    ./constraints/kv260_top.xdc

synth_design -top $TOP -part $PART -flatten_hierarchy rebuilt
opt_design
place_design
phys_opt_design
route_design
phys_opt_design  ;# second pass after routing often recovers WNS

report_timing_summary -file reports/timing_post_route.rpt
report_utilization    -file reports/util_post_route.rpt

# Fail the script if timing is not met
set wns [get_property SLACK [get_timing_paths -max_paths 1 -nworst 1]]
if {$wns < 0} { error "Timing not met: WNS = $wns ns" }

write_bitstream -force output/kv260_top.bit
write_hw_platform -fixed -force -file output/kv260.xsa
```

### Relevance to Your Project
A non-project TCL build means your Vivado project is fully reproducible from the repo — no `.xpr` binary needed. The WNS guard before `write_bitstream` stops you from programming a board with a failing design, which would produce unpredictable AXI read/write behaviour on BRAM0/BRAM2.

## Vitis Bare-Metal / Standalone

### Key Findings
- **BSP stdout assignment**: in BSP settings, `stdout`/`stdin` must point to the `psuart1` (or whichever UART instance the carrier card routes to USB) — if set to `none`, `xil_printf` compiles but produces no output
- Always select **Cortex-A53 (APU) core 0** with the `standalone` OS for bare-metal KV260 work; selecting the R5 FSBLs or the PMU core is a common mistake when the SoM has multiple processors
- **Linker script pitfall**: Vitis auto-generates `lscript.ld` with OCM and DDR regions; verify the `DDR` region base matches your PS configuration (default: `0x00000000`, 2 GB) — a mismatch causes silent load failures
- Standalone library `xil_io.h` provides `Xil_Out32(addr, val)` / `Xil_In32(addr)` which add the correct memory barriers for AXI-mapped peripherals — prefer these over raw pointer casts in Vitis projects
- `xil_printf` is lighter than `printf` (no floating point, no heap) — it is the correct choice for bare-metal UART output on the KV260

### Code Example
```c
#include "xil_io.h"
#include "xil_printf.h"
#include "sleep.h"

#define BRAM0_BASE 0xA0000000U
#define BRAM2_BASE 0xA0010000U

int main(void) {
    xil_printf("KV260 AXI-BRAM Test\r\n");

    /* Write test patterns */
    Xil_Out32(BRAM0_BASE + 0x00, 0xCAFEBABEU);
    Xil_Out32(BRAM2_BASE + 0x00, 0x12345678U);

    usleep(10); /* allow AXI transaction to complete */

    /* Read back and verify */
    uint32_t d0 = Xil_In32(BRAM0_BASE + 0x00);
    uint32_t d2 = Xil_In32(BRAM2_BASE + 0x00);

    if (d0 == 0xCAFEBABEU && d2 == 0x12345678U)
        xil_printf("PASS: BRAM0=0x%08X  BRAM2=0x%08X\r\n", d0, d2);
    else
        xil_printf("FAIL: BRAM0=0x%08X  BRAM2=0x%08X\r\n", d0, d2);

    return 0;
}
```

### Relevance to Your Project
`Xil_Out32` / `Xil_In32` include the DMB/DSB barriers mandated for Cortex-A53 device-memory accesses — they are strictly correct for AXI-mapped BRAM whereas raw `*(volatile uint32_t*)` casts rely on the compiler not reordering around the volatile (which GCC honours, but it is not guaranteed by the ARM architecture spec without explicit barriers).

## XDC Timing Constraints

### Key Findings
- `set_input_delay` specifies the external data arrival time before the capturing clock edge, in nanoseconds; positive values mean data arrives late relative to the clock
- `set_output_delay` specifies the setup/hold margin required by the receiving device after the launching clock edge; both commands accept `-min` and `-max` variants for hold/setup analysis
- Both commands have **real impact on synthesis** (not just implementation) when Vivado's synthesis uses timing-driven placement — always add them before synthesis, not after
- For pure internal PS-to-PL AXI paths (no I/O pads), `set_input_delay` / `set_output_delay` are not needed; focus on `create_clock` for the PL clock and `set_clock_groups -asynchronous` between the PS clocks and any additional PL clocks
- AMD UG903 (2025.2) and UG835 (2025.1) are the authoritative references; `set_input_delay` / `set_output_delay` command syntax is unchanged from prior versions

### Code Example
```tcl
# kv260_top.xdc - timing constraints for KV260 bare-metal AXI-BRAM demo

# PL fabric clock from PS (100 MHz, driven via pl_clk0)
create_clock -period 10.000 -name clk_pl_0 [get_ports pl_clk0]

# If a second PL clock exists (e.g. 200 MHz for a memory controller):
# create_clock -period 5.000 -name clk_pl_1 [get_ports pl_clk1]
# set_clock_groups -asynchronous -group [get_clocks clk_pl_0] \
#                                -group [get_clocks clk_pl_1]

# Example I/O constraint if the design has external signals
# (not required for the AXI-BRAM demo since all paths are PS↔PL internal)
# set_input_delay  -clock clk_pl_0 -max 2.0 [get_ports {ext_in[*]}]
# set_input_delay  -clock clk_pl_0 -min 0.5 [get_ports {ext_in[*]}]
# set_output_delay -clock clk_pl_0 -max 1.5 [get_ports {ext_out[*]}]
# set_output_delay -clock clk_pl_0 -min 0.3 [get_ports {ext_out[*]}]

# False path for reset synchroniser (async assert, sync deassert)
set_false_path -from [get_ports pl_resetn0]
```

### Relevance to Your Project
The KV260 AXI-BRAM demo has no external I/O timing paths — all data moves over internal AXI between the PS and BRAM in the PL. Your only mandatory XDC entries are `create_clock` for `pl_clk0` and a `set_false_path` on the reset port. Adding unnecessary `set_input_delay` / `set_output_delay` on internal signals can mislead the timing engine; the template above shows exactly what the project needs.

## Kria KV260 / K26 SoM

### Key Findings
- **Default boot mode is QSPI32**: the SoM ships with factory firmware in QSPI; the KV260 carrier card reads this on every power cycle — you must generate and write `BOOT.BIN` (FSBL + bitstream + ELF) for standalone bare-metal apps
- **JTAG boot shortcut**: set the boot mode switches to JTAG (all low on SW1), then use Vitis → "Program FPGA" + "Run as Launch on Hardware" to download bitstream + ELF without touching QSPI — fastest iteration loop
- **SOM240_1 connector**: all PS MIO signals (UART, SD, QSPI, I2C, etc.) and PL EMIO signals route through this 240-pin connector between the K26 SoM and the KV260 carrier card — check `UG1089` (KV260 Starter Kit User Guide) for the definitive pin mapping
- **EMIO path**: `GPIO(EMIO)` → PL fabric → ZynqMP package pin → SOM240_1 → KV260 carrier I/O; plan for 1-2 clock cycles of extra latency vs. MIO paths
- **Power domains**: K26 has separate VCC_PSPLL (PS PLL), VCC_PSINTLP (PS low-power), and VCCINT_PL (PL fabric) rails; the carrier card manages sequencing — do not drive PL I/O before PL power-good

### Code Example
```tcl
# Vitis XSCT script: load bitstream + ELF over JTAG (no BOOT.BIN required)
connect
targets -set -filter {name =~ "PSU"}
mwr  0xffff0000 0x14000000   ;# set boot mode to JTAG
rst  -system
after 3000

targets -set -filter {name =~ "PL"}
fpga -file ./output/kv260_top.bit

targets -set -filter {name =~ "Cortex-A53 #0"}
dow    ./Debug/kv260_axi_bram.elf
con
```

### Relevance to Your Project
Using the XSCT JTAG flow above eliminates the BOOT.BIN generation step entirely — critical for fast iteration when testing the AXI-BRAM PS-to-PL connectivity. When your PASS/FAIL result is stable, switch back to QSPI32 boot with a full BOOT.BIN for standalone operation.

## AMD/Xilinx Tool Updates (2025.x)

### Key Findings
- **Vivado 2025.2** (latest as of this digest): reduced physical optimisation (PhysOpt) compile time; BUFG_FABRIC replication per-SLR and per-VNoC column for high-fanout net relief
- **New `STRATEGY` parameter** for AXI Switch and AXI SmartConnect: setting `STRATEGY=1` enables ultra-low-area mode — valuable when fitting the K26's limited PL resources
- **SystemVerilog interface support in block design** (2025.2): AXI connections between SV RTL instances are now first-class in IPI, with automatic wrapper generation
- **Vitis 2026.x known issues** have been published (AMD article 000040220), indicating the 2026.1 toolchain has been released; consider staying on 2025.1 for stability on KV260 bare-metal until the 2026.x known-issues list clears
- **Versal AI Edge Gen 2 and Versal Prime Gen 2** are newly supported device families in 2025.2 — no direct impact on KV260/K26, but IP version bumps that ship with these releases may affect existing designs on re-synthesis

### Code Example
```tcl
# Enable ultra-low-area SmartConnect mode in block design TCL
set_property -dict [list \
    CONFIG.NUM_MI {2} \
    CONFIG.STRATEGY {1} \
] [get_bd_cells axi_smc]
# STRATEGY=1 reduces LUT count at the cost of throughput; acceptable for
# single-master, low-frequency AXI-Lite to BRAM where MBW is not a concern

# Regenerate IPs after a tool version upgrade to pick up new defaults
upgrade_ip [get_ips]
report_ip_status -file reports/ip_status.rpt
```

### Relevance to Your Project
If you ever upgrade from Vivado 2025.1, run `upgrade_ip` in your block design TCL script before re-synthesising — AXI BRAM Controller and AXI SmartConnect both received version bumps in 2025.2 and the new defaults (including the STRATEGY parameter) can silently change resource usage and timing. The `report_ip_status` call makes this visible.
