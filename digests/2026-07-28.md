# FPGA Research Digest - 2026-07-28

## Executive Summary

- **Vivado 2025 AXI address decode bug**: An active bug in Vivado 2025.x limits AXI-Full peripherals to only 1 KB of usable address space due to a 10-bit address decoder constraint — your BRAM0 at `0xA0000000` and BRAM2 at `0xA0010000` use AXI-Lite which is not affected, but any future AXI4-Full expansion IP should be tested carefully.
- **AXI handshake golden rule**: Once `VALID` is asserted by a master, it must not be de-asserted until `READY` is received from the slave — violating this causes silent data corruption or deadlock with the BRAM controller.
- **KV260 has no physical boot mode switches**: JTAG boot requires the SD card to be absent; four files are needed (`fsbl.elf`, `pmufw.elf`, `<app>.elf`, `<wrapper>.bit`) loaded via XSDB/TCL script.
- **`xil_printf` does not support `%f`**: Only `%d`, `%l`, `%x`, `%c`, `%s` are supported in standalone BSP — any floating-point formatting in your PASS/FAIL output must use integer arithmetic or `printf` from newlib.
- **AMD 2025.1 IP release includes AXI deadlock fix**: A bug causing deadlock between peripheral and cache AXI interfaces (frequency-optimized pipeline path) is patched in 2025.1 — upgrading IP cores in your block design is recommended.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- **Handshake invariant**: A transfer completes only when both `VALID` and `READY` are high on the same rising clock edge. The master must keep `VALID` asserted and all associated signals stable until `READY` arrives — lowering `VALID` early is the most common source of silent BRAM write failures.
- **AXI-Lite vs AXI4 vs AXI-Stream**:
  - AXI-Lite: memory-mapped, single-beat, no burst — ideal for control/status registers (your BRAM access pattern).
  - AXI4 (Full): memory-mapped, burst up to 256 beats — used for DMA, high-bandwidth data.
  - AXI-Stream: no address channel, unlimited burst, unidirectional — used for video/DSP pipelines.
- **Vivado 2025 AXI-Full address bug**: A reported issue in Vivado 2025.x limits AXI Full peripherals to a 1 KB usable address space due to an apparent 10-bit address decode limit. AXI-Lite controllers (as used in the BRAM controller) are not affected. Workaround: use AXI-Lite BRAM controller, or apply Digilent's documented patch.
- **BRAM controller port modes**: The AXI BRAM Controller IP supports both single-port and dual-port BRAM configurations. ECC is available only at 32-, 64-, or 128-bit data widths. In single-port mode the controller uses one BRAM port exclusively over AXI; dual-port allows a second independent port (e.g., for a soft-core processor).
- **AXI response codes**: `OKAY` (0b00), `EXOKAY` (0b01, exclusive access), `SLVERR` (0b10, slave error), `DECERR` (0b11, decode error). Reading from an unmapped address returns `DECERR` — your bare-metal code should check `BRESP`/`RRESP` to distinguish bad addresses from BRAM errors.

### Code Example

```vhdl
-- Minimal AXI-Lite slave write handshake (combinational ready)
-- AWREADY/WREADY pulse for one cycle when both VALID signals are seen
process(clk)
begin
  if rising_edge(clk) then
    if rst = '1' then
      axi_awready <= '0';
      axi_wready  <= '0';
    elsif (s_axi_awvalid = '1' and s_axi_wvalid = '1'
           and axi_awready = '0' and axi_wready = '0') then
      axi_awready <= '1';
      axi_wready  <= '1';
    else
      axi_awready <= '0';
      axi_wready  <= '0';
    end if;
  end if;
end process;
```

### Relevance to Your Project

Your Cortex-A53 writes to BRAM0 (`0xA0000000`) and BRAM2 (`0xA0010000`) via AXI-Lite. The handshake rules above govern every write/read the PS issues. If your PASS/FAIL test ever reads back garbage without a bus error, a `VALID` timing violation in the interconnect or BRAM controller wrapper is the first place to check. Since you are using AMD's IP BRAM Controller, the handshake is handled internally — but any custom VHDL wrapper interfacing to that AXI port must obey these rules strictly.

## Vivado Block Design / IP Integrator

### Key Findings

- **Address alignment is mandatory**: Addresses must be aligned to their range. A peripheral with a 4 KB range (`0x1000`) must have three trailing hex zeros (e.g., `0xA0000000`). Misaligned addresses cause block design validation errors and prevent bitstream generation.
- **Assign All button**: The Address Editor's "Assign All" button auto-assigns all unmapped slaves. You can then override specific addresses manually. After auto-assignment, always verify BRAM addresses haven't shifted — Vivado sometimes reassigns them when IP is added or regenerated.
- **Locking addresses**: You can lock individual address segments via the Address Editor context menu. This prevents Vivado from moving an address during re-auto-assignment — useful when you have hard-coded addresses in firmware (`0xA0000000`, `0xA0010000`).
- **Vivado 2025 AXI-Full 1 KB limit**: When adding new AXI-Full peripherals in Vivado 2025.x, the address decode may silently limit usable space to 1 KB. Validate by writing to offset `0x400` and reading back.
- **Connection Automation**: After placing IPs, use "Run Connection Automation" for clock/reset and AXI connections. For the Zynq PS, the automation wires `M_AXI_HPM0_FPD` to the AXI Interconnect and propagates `pl_clk0` and `pl_resetn0`.

### Code Example

```tcl
# In create_bd.tcl — lock BRAM addresses after assignment to prevent drift
set_property offset 0xA0000000 [get_bd_addr_segs {mig_7series_0/S_AXI/Mem0}]
set_property range 64K          [get_bd_addr_segs {mig_7series_0/S_AXI/Mem0}]

# Lock the segment so re-run of assign_bd_address won't move it
set_property -dict [list \
  CONFIG.LOCK_SEGMENT {true} \
] [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]

# Validate the block design before exporting
validate_bd_design
```

### Relevance to Your Project

Your TCL `create_bd.tcl` script likely calls `assign_bd_address` to set `0xA0000000` (BRAM0) and `0xA0010000` (BRAM2). If you add more IP in the future and re-run connection automation, those addresses may be reassigned. Locking them in the script ensures your firmware constants stay valid across block design iterations.

## Vivado TCL Scripting

### Key Findings

- **Batch mode invocation**: `vivado -nolog -nojournal -mode batch -source build.tcl` runs a TCL script headlessly. `-nolog` and `-nojournal` suppress file creation for CI environments.
- **Non-project mode**: Reads source files into memory, requires manual `generate_target`, `synth_design`, `opt_design`, `place_design`, `route_design`, `write_bitstream`. No auto-tracking of source changes — suitable for reproducible CI builds.
- **Project mode export**: In the Vivado GUI, File → Export → Export Block Design generates a `.tcl` script that recreates the block design. This is the recommended way to create `create_bd.tcl` — generate once in GUI, version control the TCL.
- **`generate_target`**: Must be called before synthesis on block designs to generate HDL wrappers and IP output products. Common omission when moving to non-project mode.
- **`write_hw_platform`** (formerly `write_sysdef`): After bitstream, this generates the `.xsa` (Xilinx Support Archive) consumed by Vitis to create the BSP and hardware platform.

### Code Example

```tcl
# Minimal non-project mode build script for KV260 AXI-BRAM design
set design_name  kv260_top
set part         xck26-sfvc784-2LV-c
set board_part   xilinx.com:kv260_som:part0:1.4

# Create in-memory project
create_project -in_memory -part $part

# Read sources
read_vhdl   [glob ./vhdl/*.vhd]
read_xdc    [glob ./xdc/*.xdc]

# Source block design creation script
source ./tcl/create_bd.tcl

# Generate HDL wrapper and targets
make_wrapper -files [get_files ${design_name}.bd] -top
read_vhdl [glob ./${design_name}.gen/sources_1/bd/${design_name}/hdl/*.vhd]
generate_target all [get_files ${design_name}.bd]

# Run implementation
synth_design  -top ${design_name}_wrapper -part $part
opt_design
place_design
route_design
write_bitstream -force ./output/${design_name}.bit
write_hw_platform -fixed -force ./output/${design_name}.xsa
```

### Relevance to Your Project

Your `create_bd.tcl` is designed to recreate the block design from scratch. Wrapping it in the non-project mode script above gives you a single-command CI build: `vivado -mode batch -source build.tcl`. The `.xsa` output feeds directly into Vitis to regenerate the BSP and recompile `main.c` without GUI interaction.

## Vitis Bare-Metal / Standalone

### Key Findings

- **BSP UART configuration**: In Vitis, open `vitis-comp.json` in the Settings folder and ensure `standalone_stdin` and `standalone_stdout` are set to `psu_uart_1` (MIO36/MIO37 on KV260). If set to the wrong UART, `xil_printf` output goes nowhere and the board appears unresponsive.
- **`xil_printf` format limitations**: Supports `%d`, `%ld`, `%x`, `%lx`, `%c`, `%s` only — **no `%f`**. For floating-point output use `printf` (newlib), but note this increases binary size significantly and requires `_REDEFINE_EXTNAME` or `-u _printf_float` linker flags.
- **Standalone BSP drivers**: Available for all PS peripherals (`xuartps`, `xgpiops`, `xspips`, etc.) under `XilinxProcessorIPLib/drivers`. AXI peripherals mapped to PL are accessed via raw memory reads/writes (`Xil_Out32`/`Xil_In32`) or with generated driver headers.
- **OCM vs DDR linker placement**: By default, the Cortex-A53 standalone linker script places the application in DDR (`psu_ddr_0`). For ultra-fast startup without DDR initialization, you can place code in OCM (`psu_ocm_ram_0`, 256 KB at `0xFFFC0000`) — but OCM is shared with FSBL and PMU firmware.
- **Cache coherency**: When the A53 writes to PL-accessible memory regions (e.g., AXI-mapped BRAM), ensure you flush D-cache with `Xil_DCacheFlushRange()` before the PL reads, or disable caching for that region via the MPU.

### Code Example

```c
#include "xil_printf.h"
#include "xil_io.h"

#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL
#define TEST_OFFSET 0x00000000UL
#define TEST_PATTERN 0xDEADBEEFUL

int bram_test(u32 base, const char *name) {
    /* Write pattern */
    Xil_Out32(base + TEST_OFFSET, TEST_PATTERN);

    /* Flush cache so PL sees the write (if caching enabled for region) */
    Xil_DCacheFlushRange(base + TEST_OFFSET, 4);

    /* Read back */
    u32 readback = Xil_In32(base + TEST_OFFSET);

    if (readback == TEST_PATTERN) {
        xil_printf("%s PASS: wrote 0x%08lX, read 0x%08lX\r\n",
                   name, (u32)TEST_PATTERN, readback);
        return 0;
    } else {
        xil_printf("%s FAIL: wrote 0x%08lX, read 0x%08lX\r\n",
                   name, (u32)TEST_PATTERN, readback);
        return -1;
    }
}

int main(void) {
    xil_printf("KV260 AXI-BRAM Test\r\n");
    int result = 0;
    result |= bram_test(BRAM0_BASE, "BRAM0");
    result |= bram_test(BRAM2_BASE, "BRAM2");
    xil_printf("Overall: %s\r\n", result == 0 ? "PASS" : "FAIL");
    return result;
}
```

### Relevance to Your Project

This is essentially what your `main.c` does. Key points to verify: (1) UART is configured to `psu_uart_1` in the BSP so output appears on USB-UART; (2) use `%08lX` not `%08X` for `u32` types to avoid truncation warnings; (3) add `Xil_DCacheFlushRange` if the test fails intermittently — the default Cortex-A53 memory map in Vitis marks PL regions as device memory (non-cacheable), so this may already be handled, but it's worth confirming in the MPU settings.

## XDC Timing Constraints

### Key Findings

- **K26 SOM device**: `xck26-sfvc784-2LV-c` (speed grade -2LV, VCCINT = 0.72 V). All XDC constraints must target this exact part string.
- **Primary clock**: `pl_clk0` from the Zynq PS (typically 100 MHz or 200 MHz). Declare it with `create_clock` pointing to the port on the block design wrapper — Vivado auto-generates this constraint when you export from IP Integrator.
- **`set_clock_groups -asynchronous`**: Use this to tell the timing engine that two clocks never interact — for example, if you add a PL-side clock from a PL\_CLK pin separate from `pl_clk0`. Without it, Vivado attempts cross-domain timing analysis and may report false violations.
- **AXI paths are fully pipelined**: AXI interconnect registers all paths, so timing between PS and BRAM controller is usually met automatically at 100–200 MHz. Timing failures in AXI designs typically come from user logic outside the interconnect.
- **XDC files from AMD for K26**: The K26 SOM ships with reference XDC files mapping `SOM240_x` connector signals to PS/PL pin names. Always start from the official AMD `kv260_som_part0.xdc` reference rather than building constraints from scratch.

### Code Example

```xdc
# Declare PL clock from Zynq PS (auto-exported from block design, shown for reference)
# This line is typically auto-generated in the wrapper XDC; do NOT duplicate it.
# create_clock -period 10.000 -name clk_pl_0 [get_ports clk_pl_0]

# If you add a second independent PL clock source (e.g., external oscillator on carrier):
create_clock -period 8.000 -name clk_ext [get_ports ext_clk_i]

# Declare the two clocks as asynchronous to suppress false cross-domain paths
set_clock_groups -asynchronous \
    -group [get_clocks clk_pl_0] \
    -group [get_clocks clk_ext]

# False path for async reset synchronizer input (common pattern)
set_false_path -from [get_ports rst_n_i] -to [all_registers]

# Output delay for any PL-driven signal to carrier card connector
# (adjust for board trace length per UG1091 carrier card design guide)
set_output_delay -clock clk_pl_0 -max 2.0 [get_ports {som240_1_*}]
set_output_delay -clock clk_pl_0 -min -1.0 [get_ports {som240_1_*}]
```

### Relevance to Your Project

Your AXI-BRAM demo probably needs no timing constraints beyond what Vivado auto-generates for `pl_clk0`. The most likely timing issue arises when you add custom VHDL logic between the AXI interconnect and the BRAM controller, or when you introduce a second clock. The `set_clock_groups -asynchronous` pattern above is the safe default any time two clocks coexist in your design.

## Kria KV260 / K26 SOM

### Key Findings

- **No physical boot mode switches**: Unlike ZCU102/ZCU104, the KV260 has no SW switches to change boot mode. Boot mode is set via PS register write through JTAG (TCL command `mwr 0xFF5E0200 0x0100` for JTAG mode) or by removing the SD card to force JTAG fallback.
- **JTAG boot requires 4 files**: `fsbl.elf` (First Stage Bootloader), `pmufw.elf` (PMU Firmware), your application `.elf`, and the PL bitstream `.bit`. Load them via XSDB (`device program`, `dow`, `con`) in the correct order.
- **UART default pins**: AMD's boot firmware and PetaLinux BSP default UART to **MIO36 (TX) and MIO37 (RX)** — connected to the USB-UART chip on the KV260 Starter Kit. Always configure your BSP `standalone_stdout` to `psu_uart_1`.
- **SOM240 connectors**: The KV260 exposes SoM I/O via two SOM240 connectors. SOM240_1 provides MIO banks 500/501/502, HPIO bank 66 (HPA), HDIO bank 45 (HDA), and PS-GTR transceivers. EMIO signals (PL-to-PS) are accessed via the `emio_*` ports on the Zynq PS IP in your block design.
- **Power domains**: The K26 SOM manages all voltage rails internally. The carrier card must supply only: VADJ_FMC (1.2/1.8/2.5/3.3V selectable), 12V main supply, 5V, 3.3V, and 1.8V. Supply tolerance at the SOM connector: +3%/−2%.
- **SD card as secondary boot**: The onboard SD card slot is the secondary boot device holding the OS image. For bare-metal development without Linux, boot via JTAG and bypass the SD card entirely.

### Code Example

```tcl
# XSDB script to load bare-metal application via JTAG on KV260
# Run from Vitis XSDB console: xsdb load_baremetal.tcl

connect

# Target the APU (Cortex-A53 core 0)
targets -set -filter {name =~ "APU*"}

# Reset the system (keeps JTAG connection)
rst -system

# Program the PL bitstream first
fpga -file ./output/kv260_top_wrapper.bit

# Now target A53 core 0 for software load
targets -set -filter {name =~ "*A53*#0"}

# Load FSBL and PMU firmware (required to initialize DDR)
dow ./output/fsbl.elf
dow -data ./output/pmufw.elf 0xFFD80000

# Load application
dow ./output/kv260_axi_bram.elf

# Run
con
```

### Relevance to Your Project

This XSDB script is the exact flow for iterative development of your AXI-BRAM demo: flash the bitstream, load the ELF, and capture UART output — all without rebooting or re-flashing the SD card. For a faster iteration loop, set up a `Makefile` target that calls `vivado -mode batch -source build.tcl && xsdb load_baremetal.tcl` to go from source to running hardware in one command.

## AMD/Xilinx Tool Updates (Vivado/Vitis 2025.x)

### Key Findings

- **Vivado 2025.2 released**: AMD has released Vivado/Vitis 2025.2. The 2025.1 IP changelog is publicly accessible via AMD support article 000037919 without installing the tools. Vivado 2025.2 "What's New" page lists further improvements.
- **AXI deadlock fix in 2025.1**: A bug causing deadlock between peripheral and cache data AXI interfaces in the frequency-optimized pipeline path has been fixed. This could affect designs using the AXI Interconnect at high clock frequencies with cache-enabled Cortex-A53. Regenerate your IP cores in Vivado 2025.1+ to pick up this fix.
- **AXI peripheral 64-bit width bug fixed**: A bug in AXI IP that incorrectly set peripheral and cache AXI interface sizes with 64-bit peripheral data width and wide cache interface data widths is also patched in 2025.1.
- **Non-project mode in 2025.1 (UG994)**: AMD's 2025.1 UG994 documents updated IP Integrator behavior in non-project mode. `generate_target` output product handling has been clarified — you must explicitly call it before synthesis or simulation.
- **UG835 (TCL Command Reference)** updated to 2025.2: `set_clock_groups`, `create_hw_target`, and related commands have updated documentation. Check for deprecated options if migrating from older scripts.
- **IP Basics (UG896) updated for 2025.1**: Documents changes to IP cataloging, interface definitions, and the IP packager flow.

### Code Example

```tcl
# Upgrade all IP cores in a project to latest versions (run after opening project)
# Useful when migrating from 2024.x to 2025.1
set ip_list [get_ips]
foreach ip $ip_list {
    set ip_name [get_property NAME $ip]
    set upgrade_available [get_property UPGRADE_VERSIONS $ip]
    if {$upgrade_available ne ""} {
        puts "Upgrading IP: $ip_name to $upgrade_available"
        upgrade_ip $ip
    }
}

# Re-generate all output products after upgrade
generate_target all [get_ips]

# Lock upgraded IPs to prevent further auto-upgrade
# (comment out if you want to always track latest)
# set_property -name {IP_LOCKED} -value true [get_ips]

puts "IP upgrade complete. Run validate_bd_design to check for errors."
```

### Relevance to Your Project

If you created your block design in Vivado 2024.x and opened it in 2025.1, Vivado will prompt you to upgrade IPs. Run the script above to batch-upgrade all IPs and pick up the AXI deadlock fix. After upgrading, run `validate_bd_design` and re-generate the wrapper before rebuilding. If the AXI peripheral 1 KB address bug affects your design (it shouldn't with AXI-Lite BRAM controller), check the Digilent forum thread for the workaround.
