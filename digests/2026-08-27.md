# FPGA Research Digest - 2026-08-27

## Executive Summary

- **AXI-Lite deadlock risk**: Never make READY combinationally dependent on VALID — both must be independently drivable or the interconnect can deadlock. Your BRAM reads at 0xA0000000 / 0xA0010000 are safe if you use Xilinx's generated AXI BRAM Controller, which handles this correctly.
- **Vivado 2025 AXI-full 1 kB bug**: Custom AXI-full slave peripherals generated by Vivado 2025.x have a known bug limiting usable address space to 1 kB. Your design uses AXI-Lite (not custom AXI-full), so you are unaffected — but keep this in mind if you extend to a custom PL IP.
- **AXI BRAM Controller single-port note**: In AXI-Lite mode the controller only supports 32-bit data width and single-beat transfers; Port A is used for both reads and writes when single-port is selected. Verify your Block Memory Generator is configured to match.
- **Non-project mode TCL tip**: Save design checkpoints (`write_checkpoint`) after each major stage (synth, impl) when automating builds — without this you lose state if the run crashes, and report generation must be scripted explicitly.
- **Vivado IP update silent failure**: In 2025.1, Vivado sometimes fails to detect when an IP has been updated; close and reopen the project after upgrading any IP to be safe, then re-run `validate_bd_design`.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- The VALID/READY handshake governs all five AXI channel types (AW, W, B, AR, R). Once VALID is asserted by the source it **must stay high** until the handshake completes (both VALID and READY high on the rising clock edge).
- **Critical rule**: READY of a slave must never be combinationally dependent on VALID of the master — this creates a combinational cycle that violates the AXI spec and can deadlock the fabric interconnect.
- AXI-Lite does **not** support burst transfers; every transaction is a single 32-bit (or 64-bit) data beat. The AXI BRAM Controller configured in AXI-Lite mode enforces 32-bit width.
- All AXI signals are sampled on the **rising clock edge**; signal changes must occur after the rising edge (i.e., registered outputs).
- `XPM_FIFO_AXIL` (UG974) is a parameterized macro available in Vivado 2025.x for lightweight FIFO bridging over AXI-Lite — useful if you ever need buffering between PS and a custom PL FIFO.

### Code Example

```c
/* Bare-metal AXI-Lite BRAM write/read pattern (KV260 PS Cortex-A53)
   BRAM0 base: 0xA0000000, BRAM2 base: 0xA0010000
   Uses direct memory-mapped I/O — no driver library required.        */

#include <stdint.h>
#include "xil_printf.h"
#include "xil_io.h"

#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL

static inline void axi_write(uintptr_t base, uint32_t offset, uint32_t val) {
    Xil_Out32(base + offset, val);
}

static inline uint32_t axi_read(uintptr_t base, uint32_t offset) {
    return Xil_In32(base + offset);
}

void bram_test(uintptr_t base, const char *name) {
    const uint32_t PATTERN = 0xDEADBEEF;
    axi_write(base, 0x00, PATTERN);
    uint32_t rd = axi_read(base, 0x00);
    xil_printf("%s @ 0x%08lX: wrote 0x%08X, read 0x%08X -- %s\r\n",
               name, base, PATTERN, rd,
               (rd == PATTERN) ? "PASS" : "FAIL");
}

int main(void) {
    xil_printf("KV260 AXI-BRAM Demo\r\n");
    bram_test(BRAM0_BASE, "BRAM0");
    bram_test(BRAM2_BASE, "BRAM2");
    return 0;
}
```

### Relevance to Your Project

Your `main.c` writes patterns to BRAM0 at `0xA0000000` and BRAM2 at `0xA0010000` over AXI-Lite. The handshake rules above explain why a delay of a few cycles between write and read is sometimes necessary on slower BRAM configurations — the AXI BRAM Controller may be in the middle of completing the write-response (B channel) when the read (AR channel) arrives. If you ever see stale reads, add a `dsb()` (data synchronization barrier) between the write and the read to ensure the write completes.

## Vivado Block Design / IP Integrator

### Key Findings

- **Connection Automation**: After adding IPs in IP Integrator, use *Run Connection Automation* (right-click canvas or the green banner) to wire AXI interfaces, clocks, and resets automatically. It adds `proc_sys_reset` and `axi_interconnect` as needed.
- **Address Editor**: The *Address Editor* tab assigns memory-mapped ranges to AXI slaves. Click *Assign All* to let Vivado auto-assign; then verify offsets match what your C code expects (`0xA0000000`, `0xA0010000`). Manually enter values in the *Offset Address* and *Range* columns if auto-assignment picks wrong addresses.
- **Always `validate_bd_design`** in TCL after making block design changes; this catches connectivity mismatches and address overlaps before synthesis.
- **Save frequently** with Ctrl+S (GUI) or `save_bd_design` (TCL); IP Integrator does not auto-save.
- After IP upgrade (e.g., upgrading `axi_bram_ctrl` to a newer version), close and reopen the project before re-generating the design — Vivado 2025.1 has a known silent-miss on IP update detection.

### Code Example

```tcl
# Validate and regenerate block design outputs
open_bd_design [get_files *.bd]
validate_bd_design
generate_target all [get_files *.bd]
make_wrapper -files [get_files *.bd] -top
add_files -norecurse [glob ./*/hdl/vhdl/*_wrapper.vhd]
set_property top kv260_top [current_fileset]
update_compile_order -fileset sources_1
```

### Relevance to Your Project

Your `create_bd.tcl` script builds the block design programmatically. Running `validate_bd_design` at the end of that script (before synthesis) will catch issues like unmapped AXI addresses or missing clock connections early, saving a full synthesis run.

## Vivado TCL Scripting

### Key Findings

- **Two modes**: *Project mode* manages sources and runs for you; *Non-project mode* gives you full control but requires explicit checkpointing and report generation.
- **Batch mode**: Launch with `vivado -mode batch -source script.tcl`; Vivado exits automatically after the script completes. Unknown commands are **not** forwarded to the OS — use `exec` explicitly for system calls.
- **Design checkpoints**: In non-project mode, use `write_checkpoint` after synthesis and implementation to preserve state. Without them, a crash means a full re-run.
- **IP Integrator in non-project mode** is documented in UG994 (2025.1); use `create_bd_design`, add IPs with `create_bd_cell`, connect with `connect_bd_intf_net`, then `validate_bd_design`.
- **Useful Tcl procs**: `get_ports`, `get_cells`, `get_nets` with `-hierarchical` and `-filter` flags enable precise targeting in complex designs.

### Code Example

```tcl
#!/usr/bin/env vivado -mode batch -source
# Non-project mode: synthesize, implement, write bitstream

set part "xck26-sfvc784-2LV-c"

# Read sources
read_vhdl [glob ./vhdl/*.vhd]
read_xdc  ./constraints/kv260_top.xdc

# Synthesize
synth_design -top kv260_top -part $part -flatten_hierarchy rebuilt
write_checkpoint -force ./checkpoints/post_synth.dcp
report_timing_summary -file ./reports/post_synth_timing.rpt

# Implement
opt_design
place_design
phys_opt_design
route_design
write_checkpoint -force ./checkpoints/post_route.dcp
report_timing_summary -file ./reports/post_route_timing.rpt
report_utilization   -file ./reports/utilization.rpt

# Bitstream
write_bitstream -force ./output/kv260_top.bit
```

### Relevance to Your Project

Adding this non-project mode script to your repo alongside `create_bd.tcl` lets CI (or another developer) rebuild the entire design from source with one command. The checkpoint after synthesis is especially valuable for your project because full Vivado implementation runs can take 10–20 minutes on the KV260 bitwidth.

## Vitis Bare-Metal / Standalone

### Key Findings

- **BSP generation**: Vitis generates a standalone BSP containing `xil_printf`, `xil_io.h` (for `Xil_In32`/`Xil_Out32`), and processor-specific startup code. Always regenerate the BSP after changes to the block design's address map.
- **stdout redirection**: `xil_printf` routes output to the UART configured in the BSP settings. For KV260 this is typically PS UART1 (USB-UART). Confirm `stdin`/`stdout` are mapped to `psu_uart_1` in the BSP's `system.mss`.
- **Cache coherency**: On Cortex-A53, the D-cache can mask AXI writes to PL if you don't flush/disable it. For simple bare-metal BRAM demos, disabling the D-cache (`Xil_DCacheDisable()`) is the safest approach. For production, mark the BRAM address range as device memory in the MPU.
- **Linker script**: The default `lscript.ld` places code in DDR. For maximum speed on small demos, you can place the entire binary in OCM (On-Chip Memory, 256 kB) to eliminate DDR latency.
- **embeddedsw GitHub**: All Xilinx bare-metal drivers (`xgpiops`, `xuartps`, etc.) are open-source at https://github.com/Xilinx/embeddedsw.

### Code Example

```c
/* BSP cache management for bare-metal AXI-PL access on Zynq UltraScale+ */
#include "xil_cache.h"
#include "xil_mmu.h"

void init_mpu_for_pl(void) {
    /* Mark PL AXI region as Strongly Ordered (non-cacheable, non-bufferable)
       to guarantee AXI transactions complete before the next CPU instruction. */
    /* Region: 0xA0000000 - 0xA001FFFF (covers BRAM0 + BRAM2) */
    Xil_SetTlbAttributes(0xA0000000, NORM_NONCACHE | STRONG_ORDERD_SHARED);
    Xil_DCacheFlush();  /* flush any pending cached writes first */
}

/* Call once before any BRAM access: */
/* init_mpu_for_pl(); */
```

### Relevance to Your Project

If you're seeing intermittent FAIL results on the BRAM read-back test, a D-cache coherency issue is the most common root cause on A53-based designs. The MPU attribute approach above is the production-safe fix; `Xil_DCacheDisable()` is the quick debug shortcut.

## XDC Timing Constraints

### Key Findings

- **`set_input_delay`**: Specifies the external path delay on a primary input relative to a clock edge. Syntax: `set_input_delay -clock <clk> -max <ns> [get_ports <port>]`. Use both `-max` and `-min` for setup and hold.
- **`set_output_delay`**: Specifies the external path delay on a primary output relative to a clock edge. Same `-max`/`-min` pair required for complete coverage.
- **Clock groups**: Use `set_clock_groups -asynchronous -group {clk_a} -group {clk_b}` to tell the timing engine that two clocks are unrelated — prevents false paths across async boundaries.
- **Zynq PS clocks**: The PS generates PL clocks (`pl_clk0` etc.). These are already constrained by the PS7/ZYNQMP IP; you should **not** add a `create_clock` on them — just reference them in your XDC with `get_clocks -of_objects [get_pins */PS8_i/PLCLK[0]]`.
- **Timing Constraints Wizard**: Available in Vivado GUI under Tools → Timing Constraints — it generates XDC templates with timing diagrams, reducing errors on DDR/source-synchronous interfaces.

### Code Example

```tcl
# kv260_top.xdc - minimal constraints for KV260 AXI-BRAM demo

# PS PL clock 0 is 100 MHz (configured in block design PS IP)
# Do NOT create_clock on pl_clk0 — the PS IP already defines it.

# External LED output (example — adjust for your carrier card pinout)
set_property PACKAGE_PIN   D5  [get_ports led_0]
set_property IOSTANDARD    LVCMOS33 [get_ports led_0]
set_output_delay -clock [get_clocks -of_objects \
    [get_pins kv260_top_i/zynq_ultra_ps_e_0/inst/PS8_i/PLCLK[0]]] \
    -max 2.0 [get_ports led_0]
set_output_delay -clock [get_clocks -of_objects \
    [get_pins kv260_top_i/zynq_ultra_ps_e_0/inst/PS8_i/PLCLK[0]]] \
    -min 0.5 [get_ports led_0]

# Prevent timing analysis across unrelated clock domains (if you add PL clocks)
# set_clock_groups -asynchronous -group {pl_clk0} -group {your_other_clk}
```

### Relevance to Your Project

Your current design has no external I/O timing paths (the BRAM is internal PL), so `set_input_delay`/`set_output_delay` are not strictly needed now. However, if you add external signals (UART passthrough, PMOD, or camera interface), you'll need them. The PS clock reference pattern above prevents the common mistake of double-constraining the PS-generated clock.

## Kria KV260 / K26 SoM

### Key Findings

- **Boot modes**: K26 supports JTAG, SD card, and QSPI32. Factory default is QSPI32. For development, JTAG boot (via XSCT/XSDB) is fastest — no need to write an SD card for each iteration.
- **MIO configuration**: The K26 SOM's MIO assignments are fixed by the SOM hardware. Carrier-card-specific MIO assignments must follow the *Kria SOM Carrier Card Design Guide*. The KV260 starter kit uses PS UART1 on MIO pins for USB-UART — this is why `xil_printf` works without any additional VHDL.
- **Power domains**: Three domains — Always On (5V main), PL (1.8V/3.3V I/O), and PS. The Always On domain powers up first; PL power rails must be stable before programming the bitstream.
- **EMIO vs MIO**: MIO pins are routed directly to the PS (fast, no PL resource). EMIO pins pass through the PL fabric and require a corresponding VHDL port and XDC constraint. Your AXI-BRAM demo uses only MIO (PS UART, PS-to-PL over AXI), so EMIO is not needed.
- **Bare-metal loading via JTAG**: Use XSCT: `connect; targets 2; fpga kv260_top.bit; targets 4; dow kv260_app.elf; run` (target 2 = PS, target 4 = APU A53 core 0).

### Code Example

```tcl
# XSCT script to load bitstream + ELF over JTAG (no SD card needed)
# Run in Vitis XSCT console or: xsct load_and_run.tcl

connect

# Program PL with bitstream
targets 2
fpga -f ./output/kv260_top.bit

# Load and run ELF on A53 core 0
targets 4
rst -processor
dow ./Debug/kv260_app.elf
con
```

### Relevance to Your Project

Using XSCT for JTAG loading is the fastest inner-loop workflow for your BRAM demo — edit C code in Vitis, build, run the XSCT script, and check UART output. No SD card writing, no BOOT.BIN generation. This cuts iteration time from ~2 minutes (SD write + reboot) to ~10 seconds.

## AMD/Xilinx Tool Updates (Vivado/Vitis 2025.x)

### Key Findings

- **Vivado 2026.1 is now available** (as of mid-2026), with download available from AMD's adaptive SoC tools page. If you're on 2025.1, an upgrade path exists.
- **Vitis 2025.1 release notes** (UG1742, released 2025-07-08) detail what's new across the embedded software platform.
- **Known bug — AXI-full 1 kB limit**: Custom AXI-full slave peripherals generated by Vivado 2025.x are limited to 1 kB address space due to a bug in the generated RAM template. **Workaround**: manually fix the address decode in the generated `user_logic.vhd`, or use a full BRAM Controller IP instead of a custom peripheral.
- **IP update silent miss**: Vivado 2025.1 may not recognize when an IP has been updated (no prompt to upgrade). Fix: close and reopen the project, then run *Report IP Status* from the IP Integrator toolbar.
- **IP Release Notes**: Master Answer Record 000037919 on Adaptive Support documents all IP changes in 2025.1, including AXI deadlock fixes between peripheral and cache AXI interfaces.
- **AXI Ethernet fix**: A bug where PTP 1588 frames were mishandled at the AXI Ethernet Buffer → MAC interface was fixed in 2025.1.

### Code Example

```tcl
# TCL to check and upgrade all IPs in a project (run in Vivado Tcl console)
# Useful after upgrading to a new Vivado version

set ip_list [get_ips]
foreach ip $ip_list {
    set status [get_property UPGRADE_VERSIONS $ip]
    if {$status ne ""} {
        puts "Upgrading IP: [get_property NAME $ip]"
        upgrade_ip $ip
    }
}
# Always re-validate after upgrading IPs
validate_bd_design
report_ip_status -file ./reports/ip_status.rpt
```

### Relevance to Your Project

If you're building on Vivado 2025.1, run the IP status check above whenever you reopen the project after a Vivado version change. The AXI BRAM Controller (axi_bram_ctrl) is a frequently updated IP; mismatched versions between what's in your XPR and what's installed can cause cryptic synthesis errors.
