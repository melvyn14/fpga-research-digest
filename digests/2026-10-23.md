# FPGA Research Digest - 2026-10-23

## Executive Summary

- **AXI BRAM read latency trap**: The Block Memory Generator's "Primitive Output Register" option silently adds a second read-latency cycle. If your bare-metal C loop reads back stale data, check PG058 and disable the output register or add a two-cycle wait.
- **Vivado 2025.1 IP Integrator new views**: IP Integrator now ships dedicated Clocking/Reset and Interrupt/AXI-Lite views, reducing the manual wiring needed for your BRAM Controller and Zynq PS blocks.
- **No boot-mode switches on Kria**: The K26 SOM has no DIP switches — boot mode is hard-coded to QSPI. For bare-metal debug you must either program the QSPI with a BOOT.BIN or use JTAG-attach mode from Vitis/XSCT; you cannot change the boot mode by flipping a header pin.
- **AXI VALID must stay asserted**: Once the master asserts AWVALID or WVALID, it must hold the signal high until the slave acknowledges with AWREADY/WREADY. Dropping early causes a silent deadlock that simulation may not catch unless you enable the Xilinx AXI Protocol Checker IP.
- **XDC `set_clock_groups` is required for PS–PL paths**: On ZynqMP (and therefore Kria), the PS clock domains are independent of PL-generated clocks. Without `set_clock_groups -asynchronous`, Vivado will attempt (and fail) to close timing across unrelated domains, generating false-negative slack violations.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- **VALID hold rule (deadlock risk)**: AXI spec requires that once AWVALID, WVALID, or ARVALID is asserted by the master, it must remain asserted until the corresponding READY is seen. A master that de-asserts VALID prematurely (e.g., after a timeout) violates the protocol. Vivado synthesis does not flag this; only an AXI Protocol Checker or Simulation assertion catches it.
- **Register Slice to break timing paths**: When the AXI path between the PS and your BRAM Controller is long (multiple hierarchy levels in the block design), inserting an `axi_register_slice` IP adds one pipeline stage per channel and dramatically improves timing closure. The tradeoff is +1 cycle of transaction latency.
- **BRAM Controller read latency**: The AXI BRAM Controller IP (PG201/PG058) has a default read latency of 1 clock cycle for the BRAM primitive. Enabling the Block Memory Generator's "Primitive Output Register" changes this to 2 cycles. If the controller's `C_READ_LATENCY` parameter does not match the BRAM generator setting, reads return wrong data with no error signal.
- **Read vs. write channel independence**: The AXI spec allows AR (read address) and AW (write address) channels to operate concurrently. A common mistake in custom AXI slaves is to stall AR until the last write completes — this is unnecessary and reduces throughput. The AXI BRAM Controller handles this correctly; custom wrappers must as well.
- **System ILA for live AXI debug**: Add an `axi_dbg_hub` or `system_ila` to your block design connected to the AXI-Lite bus. This lets you probe AWADDR, AWVALID, AWREADY, WDATA, WSTRB, BRESP, ARADDR, RDATA, and RRESP in a live ChipScope session without modifying source code.

### Code Example

```vhdl
-- AXI-Lite slave read path: assert RVALID only after ARVALID+ARREADY handshake
-- Failure to latch ARADDR before de-asserting is a common bug
process(S_AXI_ACLK)
begin
  if rising_edge(S_AXI_ACLK) then
    if S_AXI_ARESETN = '0' then
      axi_arready <= '0';
      axi_araddr  <= (others => '0');
    else
      if axi_arready = '0' and S_AXI_ARVALID = '1' then
        axi_arready <= '1';
        axi_araddr  <= S_AXI_ARADDR;  -- latch before ARVALID drops
      else
        axi_arready <= '0';
      end if;
    end if;
  end if;
end process;
```

### Relevance to Your Project

Your design uses two AXI-Lite BRAM slaves (BRAM0 at `0xA0000000`, BRAM2 at `0xA0010000`). If reads are failing intermittently, first check whether the Block Memory Generator for either BRAM has "Primitive Output Register" enabled — if so, set `C_READ_LATENCY=2` in the BRAM Controller configuration to match. Adding a System ILA to the AXI buses in `create_bd.tcl` is the fastest way to confirm which channel is misbehaving.

## Vivado Block Design / IP Integrator

### Key Findings

- **Vivado 2025.1 new IP Integrator views**: AMD added dedicated functional views for Clocking and Reset, Interrupt, and AXI-4 Lite connectivity. These views filter the block design canvas to show only relevant IP and connections, reducing visual noise when wiring the PS block to downstream IP.
- **Address Editor only appears with a bus master**: The Address Editor tab is hidden until at least one IP in the block design acts as an AXI master (e.g., the Zynq PS, a MicroBlaze, or a DMA engine). If the tab is missing, check that the master port is connected to the Interconnect.
- **`assign_bd_address` is idempotent in scripts**: Calling `assign_bd_address` in a TCL script is safe to call multiple times. If a segment is already assigned, it is skipped. Use `-import_from_file <csv>` (available since Vivado 2024.1) to drive all address assignments from a version-controlled CSV instead of hard-coded offsets in the script.
- **Excluded vs. unassigned paths**: An unassigned path in the Address Editor does NOT prevent a master from reaching a slave. You must explicitly set the segment state to "Excluded" if you want to block access. This matters on designs with an AXI SmartConnect that fans out to multiple slaves.
- **Paths window (2025.1)**: The new Paths tab in IP Integrator shows base address, range, high address, and address width at every hop. The "Show Inactive Apertures" checkbox reveals all available, unassigned apertures, which is useful for diagnosing address-map gaps.

### Code Example

```tcl
# Assign both BRAM segments with fixed base addresses, then verify
assign_bd_address [get_bd_addr_segs {axi_bram_ctrl_0/S_AXI/Mem0}] \
    -range 8K -offset 0xA0000000
assign_bd_address [get_bd_addr_segs {axi_bram_ctrl_2/S_AXI/Mem0}] \
    -range 8K -offset 0xA0010000

# Confirm assignments
foreach seg [get_bd_addr_segs] {
    set base [get_property OFFSET $seg]
    set range [get_property RANGE $seg]
    puts "Segment: [get_property NAME $seg]  Base: $base  Range: $range"
}
```

### Relevance to Your Project

Your `create_bd.tcl` script calls `assign_bd_address` for both BRAM controllers. The fixed offsets `0xA0000000` and `0xA0010000` must match the `#define` values in `main.c`. Use the Paths window in Vivado 2025.1 to confirm the full address chain from `zynq_ultra_ps_e_0/M_AXI_HPM0_FPD` → SmartConnect/Interconnect → each BRAM Controller reaches the correct base address without truncation.

## Vivado TCL Scripting

### Key Findings

- **Non-project mode (batch-clean)**: In non-project mode (`vivado -mode tcl -source script.tcl`), Vivado processes the entire compile in memory and writes no project file. You must manually call `write_checkpoint`, `write_bitstream`, and `write_hw_platform` — there is no automatic save. AMD UG892 (2026.1 edition) covers this workflow.
- **`create_bd` in non-project mode**: UG994 (2025.1) includes a sample non-project script that sequences: `source create_bd.tcl` → `make_wrapper -top` → `generate_target all` → `synth_design` → `impl_design` → `write_bitstream`. The wrapper generation step is often forgotten in non-project flows.
- **Checkpoint discipline**: Save a DCP after each major step (post-synth, post-impl). If you run synthesis and implementation in the same Tcl session without checkpoints, a crash loses all work. Pattern: `write_checkpoint -force post_synth.dcp` immediately after `synth_design`.
- **Batch invocation pattern**: `vivado -mode batch -source run.tcl -nojournal -nolog` suppresses the journal and log files that pollute CI directories.
- **Tcl proc for repeated BD sources**: Wrapping your block design source call in a proc that checks `[get_bd_designs]` before calling `create_bd` prevents double-creation errors in iterative development.

### Code Example

```tcl
# Non-project mode: full compile from BD script to bitstream
set part "xck26-sfvc784-2LV-c"
set top  "kv260_top"

# Read sources
read_vhdl  [glob ./vhdl/*.vhd]
read_xdc   [glob ./xdc/*.xdc]

# Build block design
source ./tcl/create_bd.tcl
make_wrapper -files [get_files *.bd] -top
add_files -norecurse [glob ./kv260.gen/sources_1/bd/*/hdl/*.v]

# Compile
synth_design  -top $top -part $part -flatten_hierarchy rebuilt
write_checkpoint -force checkpoints/post_synth.dcp
opt_design
place_design
route_design
write_checkpoint -force checkpoints/post_route.dcp

# Output
write_bitstream -force output/${top}.bit
write_hw_platform -fixed -include_bit -force output/${top}.xsa
```

### Relevance to Your Project

The `create_bd.tcl` in your project is already structured for sourcing from a batch script. Adding `write_checkpoint` calls after synthesis and implementation will let you resume a failed compile from the last clean point — critical in a CI/CD environment or when iterating on timing closure.

## Vitis Bare-Metal / Standalone

### Key Findings

- **`xil_printf` vs. `printf`**: The standalone BSP ships both. `xil_printf` is a lightweight, non-floating-point implementation that uses ~3 KB of code space. Standard `printf` pulls in the full newlib runtime (~40 KB). For a bare-metal PASS/FAIL output over USB-UART, `xil_printf` is the correct choice and is already in your project.
- **BSP source location**: The standalone BSP source ships with Vitis at `$XILINX_VITIS/data/embeddedsw/lib/bsp/standalone/` and is also on GitHub at `Xilinx/embeddedsw`. Release tags match Vitis versions (e.g., `xilinx_v2025.1`).
- **Linker script DDR placement**: Vitis generates a linker script that maps `.text`, `.data`, and `.bss` to the first available memory region. On designs where BRAM appears before DDR in the memory map, sections can land in BRAM (8 KB), causing an instant stack overflow at boot. Verify `lscript.ld` maps `_STACK_SIZE` and `.text` to `ps_ddr_0` (DDR4), not to any `axi_bram_ctrl` segment.
- **Interrupt controller (GIC)**: The Cortex-A53 on ZynqMP uses the GIC-400. In bare-metal, initializing the interrupt controller requires `XScuGic_CfgInitialize` followed by `Xil_ExceptionEnable()`. Forgetting `Xil_ExceptionEnable()` means interrupts are never delivered — a common silent failure.
- **BSP `STDIN`/`STDOUT` setting**: In the BSP configuration dialog (or `mss` file), the `STDIN` and `STDOUT` parameters must point to the UART peripheral connected to your USB-UART bridge (`psu_uart_0` on KV260). If they are unset or point to the wrong UART, `xil_printf` produces no output.

### Code Example

```c
/* Minimal AXI-Lite BRAM write-readback loop with xil_printf */
#include "xil_io.h"
#include "xil_printf.h"

#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL
#define TEST_WORDS  16

int main(void) {
    u32 pattern, readback;
    int pass = 1;

    xil_printf("KV260 AXI-BRAM test starting...\r\n");

    /* Write phase */
    for (int i = 0; i < TEST_WORDS; i++) {
        pattern = 0xDEAD0000 | (u32)i;
        Xil_Out32(BRAM0_BASE + i * 4, pattern);
        Xil_Out32(BRAM2_BASE + i * 4, ~pattern);
    }

    /* Read-back phase */
    for (int i = 0; i < TEST_WORDS; i++) {
        readback = Xil_In32(BRAM0_BASE + i * 4);
        if (readback != (0xDEAD0000 | (u32)i)) {
            xil_printf("FAIL BRAM0[%d]: expected 0x%08X got 0x%08X\r\n",
                       i, 0xDEAD0000 | i, readback);
            pass = 0;
        }
    }

    xil_printf(pass ? "PASS\r\n" : "FAIL\r\n");
    return 0;
}
```

### Relevance to Your Project

Your `main.c` follows this exact pattern. Two items to audit: (1) confirm `lscript.ld` does not place any section at `0xA0000000`–`0xA001FFFF` (your BRAM address range), and (2) confirm `BSP STDOUT` is set to `psu_uart_1` (the USB-UART on the KV260 carrier) — using the wrong UART instance is the most common "silent" bare-metal failure.

## XDC Timing Constraints

### Key Findings

- **`set_clock_groups -asynchronous` for PS clocks**: The PS on ZynqMP generates independent clock domains (`clk_fpga_0` through `clk_fpga_3`). These are unrelated to any PL-generated clocks. Without `set_clock_groups -asynchronous -group [get_clocks clk_fpga_0] -group [get_clocks <pl_clk>]`, Vivado will try to close timing between unrelated clocks and report false failures.
- **AXI-Lite ports typically need no I/O delays**: `set_input_delay` and `set_output_delay` apply to signals crossing the device boundary (board traces to pads). The AXI-Lite signals between the PS and PL on ZynqMP are internal and do not cross board traces, so these constraints are not needed for PS-to-PL AXI paths.
- **`set_input_delay` -max/-min distinction**: UG835 (2025.1) clarifies that when both `set_max_delay` and `set_input_delay` exist on a port, the input delay is added to the max_delay computation. Using `-max` and `-min` separately allows correct hold analysis in addition to setup.
- **Only constraints that affect synthesis**: UG903 (2025.2) lists the constraints considered during synthesis: `create_clock`, `create_generated_clock`, `set_input_delay`, `set_output_delay`, and `set_clock_groups`. All other constraints are implementation-only.
- **Migrating from `OFFSET IN/OUT`**: Pre-2014 UCF used `OFFSET IN`/`OFFSET OUT`. In XDC, these become `set_input_delay`/`set_output_delay`. UG911 has a direct migration table.

### Code Example

```tcl
# kv260_top.xdc — typical constraints for Kria KV260 bare-metal AXI-BRAM design
# The PS provides pl_clk0; no external oscillator is used on PL fabric

# 1. Primary PL clock from PS (100 MHz typical)
create_clock -period 10.000 -name pl_clk0 [get_pins zynq_ultra_ps_e_0/pl_clk0]

# 2. Async relationship between PS and any independent PL clocks
# (uncomment if you add a PL clock wizard)
# set_clock_groups -asynchronous \
#     -group [get_clocks pl_clk0] \
#     -group [get_clocks clk_out1_clk_wiz_0]

# 3. False path on async reset (PS reset is synchronised in fabric)
set_false_path -from [get_pins zynq_ultra_ps_e_0/pl_resetn0] \
               -to   [all_registers]

# 4. Bitstream configuration (SPI x4 for QSPI boot)
set_property BITSTREAM.GENERAL.COMPRESS     TRUE   [current_design]
set_property BITSTREAM.CONFIG.SPI_BUSWIDTH  4      [current_design]
set_property CONFIG_VOLTAGE                 1.8    [current_design]
```

### Relevance to Your Project

Your design uses a single PS-derived clock. The key constraint is the `create_clock` on `pl_clk0` — without it, all timing analysis is relative to a virtual clock and warnings proliferate. The `set_false_path` on `pl_resetn0` prevents a false hold violation on the reset path to every register in your BRAM controller wrappers.

## Kria KV260 / K26 SoM

### Key Findings

- **No boot mode switches**: The K26 SOM has no user-accessible boot mode pins. The default boot source is QSPI flash, with SD card as secondary. You cannot select JTAG boot by toggling a header. To debug bare-metal with JTAG, you attach Vitis/XSCT after the FSBL runs and halts, or use a custom BOOT.BIN that calls `XFsbl_HookBeforeHandoff` to pause and wait.
- **Connector I/O and MIO**: Two 240-pin Samtec connectors on the K26 expose PS MIO (bank 0, pins 0–25 for boot/config, bank 1 pins 26–51 for user functions), PS-GTR transceivers, the PS I2C platform control bus, and PL HPIO/HDIO. MIO 46–51 on the KV260 carrier are connected to the USB-UART bridge (FTDI FT4232HL channel D → `psu_uart_1`).
- **Power domains**: The K26 SOM manages multiple power rails: VCCINT (PL core), VCCAUX (PL aux), VCC_PSINTLP (PS low-power), VCC_PSINTFP (PS full-power), and VCCO for each I/O bank. On the KV260 carrier, rail sequencing is handled by the TPS65988 PD controller; the PL fabric does not power up until the PS completes early boot.
- **Boot flow for bare-metal**: AMD's recommended flow is: QSPI → BootROM → FSBL → PMU FW → ATF (TF-A) → bare-metal app (loaded by FSBL directly, skipping U-Boot). This requires configuring the FSBL partition type as "ELF" and placing the app ELF as partition 3 in the BOOT.BIN BIF file.
- **FWUEN button for recovery**: Holding the FWUEN button (SW3) during reset forces the KV260 into JTAG/recovery mode, allowing XSCT to connect and reprogram QSPI without a working BOOT.BIN.

### Code Example

```tcl
# XSCT script: connect to KV260 via JTAG, load bare-metal ELF directly
# Assumes Vivado hardware server is running on localhost:3121

connect -url TCP:localhost:3121
targets -set -filter {name =~ "PSU"}
rst -system

# Wait for FSBL to initialize PS (DDR, clocks, MIOs)
after 3000

# Switch to A53 core 0
targets -set -filter {name =~ "Cortex-A53 #0"}

# Download ELF (built from Vitis bare-metal project)
dow ./Release/kv260_bram_test.elf
con

# To halt and read UART output: stop; rrd
```

### Relevance to Your Project

Since your project targets JTAG-driven debug, the XSCT script above is the correct flow. The 3-second delay after `rst -system` gives the FSBL time to complete DDR initialization — skipping this causes `dow` to fail with a bus error because DDR is not yet enabled. If you see `Error: No current target` after `rst`, confirm the Vivado hardware server is running (`open_hw_manager` in Vivado → `connect_hw_server`).

## AMD/Xilinx Tool Updates (Vivado/Vitis 2025.1)

### Key Findings

- **New device support**: Vivado 2025.1 adds Versal AI Edge Gen 2, Versal Prime Gen 2, and Spartan UltraScale+ to the device catalog. Kria KV260 (K26 SoM, xck26) is supported as before.
- **Selective installer**: The 2025.1 installer allows per-device selection for Versal product families, reducing the download size significantly compared to the monolithic installer.
- **New AXI Switch IP (RTL-based)**: A new RTL-based AXI Switch IP replaces the older HLS-based version. It offers lower latency and smaller resource usage for designs that need lightweight M:N AXI routing without full SmartConnect overhead.
- **IP Integrator functional views**: IP Integrator gained three new "views" — Clocking and Reset, Interrupt, and AXI-4 Lite — that filter the canvas to show only the relevant subset of IP and connections. This reduces the wiring complexity when working with Zynq PS IP that has many ports.
- **Known issue (Vitis AI 5.1 / 2025.1.1)**: When using the Vitis AI accelerator, batch size is limited to 1 when tail stages are accelerated on AIE. Multiple-process X+ML applications are not yet supported. These limitations are specific to AI accelerator flows, not bare-metal AXI-BRAM work.
- **Vivado 2026.1 UG892 update**: AMD has already published a 2026.1 edition of UG892 (Design Flows Overview), indicating an upcoming tool release. No feature list is publicly available yet as of this digest date.

### Code Example

```tcl
# Vivado 2025.1: Use the new assign_bd_address -import_from_file feature

# seg_name,            base_address, range

# Then in create_bd.tcl:

# Validate after import
validate_bd_design

```

### Relevance to Your Project

The `assign_bd_address -import_from_file` feature (available from Vivado 2024.1 onward) is directly applicable to your `create_bd.tcl`. Moving the two BRAM address assignments (`0xA0000000`, `0xA0010000`) into a versioned CSV decouples the address map from the TCL logic, making it easier to audit mismatches between hardware and `main.c` `#define` values. The new IP Integrator AXI-Lite view will also make it easier to verify the PS → Interconnect → BRAM Controller connection chain at a glance.
