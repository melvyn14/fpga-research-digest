# FPGA Research Digest - 2026-11-24

## Executive Summary
- **AXI-Lite slave ready/valid dependency bug** (ZipCPU formal analysis): Vivado-generated AXI-Lite slaves have historically failed to track whether a previous response was accepted before accepting a new address — verify your BRAM controller's read-data hold logic handles back-pressure correctly.
- **Non-project mode requires manual `generate_target`**: Unlike project mode, Vivado's non-project TCL flow does not auto-generate IP output products; you must call `generate_target all [get_ips]` or use `synth_ip` before `write_bitstream`, otherwise IP is silently stale.
- **Fixed XSA export for bare-metal**: For Vitis 2025.1 bare-metal projects (like your KV260 demo), use `write_hw_platform -fixed` after implementation — without `-fixed` you create an extensible platform intended for Vitis acceleration flows, not standalone BSP generation.
- **K26 QSPI32 default boot**: KV260 Starter Kits ship with QSPI32 boot mode and a pre-programmed boot FW. For bare-metal AXI-BRAM testing you do not need to generate FSBL separately — the existing boot image infrastructure can be reused.
- **Vivado 2025.1 adds VHDL 2019 simulation constructs**: Relevant if you plan to add simulation testbenches to the BRAM read/write test; the new constructs allow more expressive assertions and coverage.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings
- **Valid/ready dependency flaw in generated slaves**: ZipCPU's formal verification work found that Vivado-generated AXI-Lite slave cores did not check whether a prior R-channel response was consumed before accepting a new read address. The core would overwrite `RDATA` while `RVALID` was still asserted but `RREADY` was not. The fix is to hold `RDATA`/`RVALID` until `RREADY` is seen, then and only then lower `RVALID` and accept a new `ARVALID`.
- **VALID must be deasserted after reset**: AXI spec requires all VALID signals to be low out of reset. A common mistake is not driving `AWVALID`, `WVALID`, `ARVALID`, `RVALID`, and `BVALID` to `'0'` in the reset branch. This can cause false transactions to initiate on power-up.
- **AXI-Lite has no burst support**: Unlike AXI4, AXI-Lite is single-beat only (no `AWLEN`, no `WLAST`). The BRAM Controller in AXI-Lite mode therefore performs one 32-bit access per handshake cycle. For high-throughput patterns, consider AXI4 (burst) mode on the BRAM Controller.
- **AXI-Stream handshake**: Transfer occurs exactly when both `TVALID` and `TREADY` are high in the same clock cycle. `TLAST` marks the final beat of a packet. `TREADY` on a stream FIFO stays high as long as there is room in the FIFO (XPM_FIFO_AXIS in FWFT mode).
- **OHWR bridge state-machine bug**: An AXI-Lite bridge that merged its acknowledge and stall checking in the same cycle could skip the response-read state, causing the handshake to stall permanently. Always verify state transition logic handles simultaneous condition changes.

### Code Example
```vhdl
-- Minimal AXI-Lite slave: safe RVALID/RDATA hold pattern
process(clk)
begin
  if rising_edge(clk) then
    if rst_n = '0' then
      s_axi_rvalid <= '0';
      s_axi_arready <= '1';
    else
      -- Accept new read address only when previous response is consumed
      if s_axi_arvalid = '1' and s_axi_arready = '1' then
        s_axi_rdata   <= bram_read_data;
        s_axi_rvalid  <= '1';
        s_axi_arready <= '0';  -- stop accepting new addresses
      end if;
      -- Release only after master has accepted the data
      if s_axi_rvalid = '1' and s_axi_rready = '1' then
        s_axi_rvalid  <= '0';
        s_axi_arready <= '1';  -- ready for next address
      end if;
    end if;
  end if;
end process;
```

### Relevance to Your Project
Your KV260 AXI-BRAM demo drives two Block Memory Generators (BRAM0 at `0xA0000000`, BRAM2 at `0xA0010000`) over AXI-Lite from the Cortex-A53. If the BRAM Controller's read path lacks the hold logic above, a fast read loop in `main.c` could read stale data (`RDATA` overwritten before `RREADY` was asserted), causing sporadic FAIL results even when the write succeeded. Verifying `RVALID` hold behavior is the first debug step for any intermittent read failures.

## Vivado Block Design / IP Integrator

### Key Findings
- **Connection automation safety**: `apply_bd_automation` can mis-infer clock domains when you have multiple clocks. Always confirm clock assignments in the Address Editor after running automation — it doesn't validate that IP clock ports match what you intended.
- **Address editor segment locking**: Each AXI slave must have a unique, non-overlapping address segment assigned before `generate_target`. Failing to assign addresses causes a DRC error at bitstream generation rather than at block design validation.
- **IP locking after board/part mismatch**: If you regenerate a block design on a different part or with a different board file (e.g., moving between KV260 revisions), all IP is locked. Use `upgrade_ip [get_ips -filter {UPGRADE_VERSIONS != ""}]` selectively — not `upgrade_ip [get_ips -all]`, which AMD explicitly warns against.
- **Re-using an existing `.bd` file in scripts**: Use `read_bd` to load a saved `.bd` file. If output products are missing, set `synth_checkpoint_mode None` on the file object, then call `generate_target all`.
- **Regeneration tip**: After changing a parameter of an existing IP (e.g., BRAM depth), always call `generate_target all [get_ips <ip_name>]` and then re-run `synth_ip` to regenerate the DCP stub.

### Code Example
```tcl
# Re-create block design from existing .bd and regenerate outputs
open_project my_project.xpr
open_bd_design [get_files *.bd]

# Lock check: upgrade only outdated IPs (never use -all)
set upgradeable [get_ips -filter {UPGRADE_VERSIONS != ""}]
if {[llength $upgradeable] > 0} {
    upgrade_ip $upgradeable
}

# Regenerate output products for all IPs
generate_target all [get_ips]

# Validate block design before proceeding
validate_bd_design
save_bd_design
```

### Relevance to Your Project
Your `create_bd.tcl` script automates the entire block design for the KV260 AXI-BRAM demo. If you ever re-run the script on a fresh Vivado install or after updating the board files, the IP locking risk applies directly. The selective `upgrade_ip` pattern above prevents the tool from silently corrupting shared IP settings.

## Vivado TCL Scripting

### Key Findings
- **Non-project mode basics**: Launch with `vivado -mode batch -source your_script.tcl`. No `.xpr` file is created; you manage all state yourself. Reports, intermediate DCPs, and output products must all be explicitly scripted.
- **State tracking is manual**: Unlike project mode, Vivado does not detect when a source file changes on disk. If you modify `kv260_top.vhd` and re-run synthesis without calling `read_vhdl` again, the tool uses a stale netlist.
- **generate_target is required**: In non-project mode, IP output products are never automatically created. Call `generate_target all [get_ips]` after adding IP, or use `synth_ip [get_ips]` which also generates targets automatically.
- **write_ip_tcl for IP capture**: After customizing IP in the GUI, use `write_ip_tcl -force ip_snapshot.tcl` to capture exact customization parameters. This is more reliable for version control than committing `.xci` files.
- **XSA export ends the script**: The last step in a complete non-project build is `write_hw_platform -fixed design.xsa` after `write_bitstream`. Without `-fixed`, Vitis treats the XSA as an extensible platform and will not generate a standard BSP.

### Code Example
```tcl
# Minimal non-project build script for KV260 AXI-BRAM demo
set part "xck26-sfvc784-2LV-c"
set top  "kv260_top"

# Create in-memory design
create_project -in_memory -part $part

# Read sources
read_vhdl  -library work  ../vhdl/kv260_top.vhd
read_xdc                  ../xdc/kv260_timing.xdc

# Source block design creation script
source      ../tcl/create_bd.tcl

# Generate IP output products
generate_target all [get_ips]

# Synthesis
synth_design -top $top -part $part -flatten_hierarchy rebuilt
write_checkpoint -force post_synth.dcp

# Implementation
opt_design
place_design
route_design
write_checkpoint -force post_route.dcp

# Reports (must be explicit in non-project mode)
report_timing_summary -file timing_summary.rpt
report_utilization    -file utilization.rpt

# Bitstream + XSA
write_bitstream -force $top.bit
write_hw_platform -fixed -include_bit -force ${top}.xsa
```

### Relevance to Your Project
This script pattern maps directly onto your repository's `create_bd.tcl` structure. Running it in batch mode on a CI server means every push to the repo can fully rebuild the bitstream without opening the Vivado GUI — useful for verifying that hardware changes didn't break timing on the AXI interconnect.

## Vitis Bare-Metal / Standalone

### Key Findings
- **BSP stdout configuration**: `xil_printf` routes to whichever UART is designated as stdout in the BSP settings. For the KV260 / Zynq UltraScale+, this is typically `psu_uart_1` (UART1 on MIO40/MIO41, available via USB-UART on the KV260 board). Verify `STDIN_BASEADDRESS` and `STDOUT_BASEADDRESS` in `xparameters.h` after BSP generation.
- **Standalone library xil_printf vs. printf**: `xil_printf` is a lightweight, non-floating-point implementation. It does not support `%f` or `%e`. Use `printf` from `xil_printf.h` only if you've enabled the full libc in BSP settings (`use_xil_printf = false`).
- **Linker script memory regions**: The default linker script places code and data in DDR. For the KV260, DDR starts at `0x00000000` and extends to 2 GB on the K26 SoM. If your bare-metal app exceeds the default `.text` section size, edit `lscript.ld` to extend the `ps7_ddr_0` region.
- **Vitis 2025.1 new BSP items**: AMD added new bare-metal BSPs for several Zynq UltraScale+ MPSoC boards in 2025.1, plus a watchdog timer (WDT) compilation fix and an RPU clock MUX change. Check the What's New page if you're using the RPU core.
- **interrupt_controller initialization**: If you add GIC-based interrupts later, `XScuGic_CfgInitialize` must be called before `Xil_ExceptionEnable`. Calling `Xil_ExceptionEnable` first with no handler registered causes an unhandled exception trap on the first interrupt.

### Code Example
```c
/* Minimal AXI-BRAM read/write test with correct xil_printf usage */
#include "xil_printf.h"
#include "xparameters.h"

#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL
#define TEST_PATTERN 0xDEADBEEFUL

static inline void bram_write(u32 base, u32 offset, u32 val) {
    *(volatile u32 *)(base + offset) = val;
}

static inline u32 bram_read(u32 base, u32 offset) {
    return *(volatile u32 *)(base + offset);
}

int main(void) {
    xil_printf("AXI-BRAM test start\r\n");

    bram_write(BRAM0_BASE, 0, TEST_PATTERN);
    bram_write(BRAM2_BASE, 0, ~TEST_PATTERN);

    u32 rd0 = bram_read(BRAM0_BASE, 0);
    u32 rd2 = bram_read(BRAM2_BASE, 0);

    if (rd0 == TEST_PATTERN && rd2 == ~TEST_PATTERN)
        xil_printf("PASS: BRAM0=0x%08X  BRAM2=0x%08X\r\n", rd0, rd2);
    else
        xil_printf("FAIL: BRAM0=0x%08X  BRAM2=0x%08X\r\n", rd0, rd2);

    return 0;
}
```

### Relevance to Your Project
This is the core pattern your `main.c` implements. The key addition here is the `volatile` qualifier on pointer casts — without it the compiler may optimize away repeated reads of the same address, making `rd0` and `rd2` appear identical even when BRAM contents differ. If you're seeing spurious PASS results, check that your pointer casts use `volatile u32 *`.

## XDC Timing Constraints

### Key Findings
- **I/O delays describe external timing**: `set_input_delay` and `set_output_delay` tell Vivado about delays *outside* the FPGA (PCB trace, source synchronous device setup/hold). They do not constrain FPGA-internal paths — those are handled by `create_clock` and placement.
- **Ordering matters**: I/O delay constraints should appear in the XDC *before* timing exceptions (`set_false_path`, `set_multicycle_path`). Vivado applies constraints in file order; placing exceptions first can override delays that haven't been defined yet.
- **Clock groups for PS-PL boundary**: The PS-PL AXI clock (from `pl_clk0` / `FCLK_CLK0`) and any external reference clocks should be placed in separate asynchronous clock groups: `set_clock_groups -asynchronous -group [get_clocks clk_pl_0] -group [get_clocks sys_clk]`.
- **`-add_delay` for multi-condition ports**: If a port has both setup and hold delays from different sources, use `set_input_delay -add_delay` to stack constraints rather than replace them.
- **BRAM internal timing**: The AXI BRAM Controller and Block Memory Generator handle their own internal timing via IP-generated `.xdc` constraints. Do not add manual BRAM read/write timing unless you are using out-of-context synthesis with a custom wrapper.

### Code Example
```tcl
# XDC snippet: PS-generated PL clock + async clock group for KV260
# PS provides 100 MHz clock to PL via FCLK_CLK0
create_clock -period 10.000 -name clk_pl_0 [get_pins psu_0/PLCLK[0]]

# If a board-level oscillator drives a free-running input:
create_clock -period 8.000  -name sys_clk  [get_ports sys_clk_i]

# Declare PS clock and board oscillator as asynchronous
set_clock_groups -asynchronous \
    -group [get_clocks clk_pl_0] \
    -group [get_clocks sys_clk]

# Example: GPIO input with 2 ns external trace delay
set_input_delay -clock clk_pl_0 -max 2.0 [get_ports gpio_in[*]]
set_input_delay -clock clk_pl_0 -min 0.5 [get_ports gpio_in[*]]

# Example: GPIO output with 1 ns trace + load delay
set_output_delay -clock clk_pl_0 -max 1.0 [get_ports gpio_out[*]]
set_output_delay -clock clk_pl_0 -min 0.0 [get_ports gpio_out[*]]
```

### Relevance to Your Project
Your KV260 AXI-BRAM demo uses the PS-generated `FCLK_CLK0` as the sole PL clock. The `create_clock` targeting `psu_0/PLCLK[0]` is the correct pin reference in a Vivado block design for Zynq UltraScale+. If your `.xdc` currently constrains only the AXI clock, adding the `set_clock_groups -asynchronous` line prevents Vivado from attempting to analyze timing across the PS boundary, reducing false negative timing violations in timing reports.

## Kria KV260 / K26 SoM

### Key Findings
- **MIO banking**: The K26 SoM has three MIO banks. MIO500 is consumed by onboard peripherals (QSPI, eMMC, I2C, TPM SPI). MIO501 and MIO502 are user-defined and routed through the SOM240_1 and SOM240_2 connectors on the KV260 carrier.
- **Default QSPI32 boot**: KV260 Starter Kits ship with QSPI32 boot mode and a pre-programmed boot firmware. For bare-metal AXI-BRAM testing, AMD explicitly states you do not need to generate FSBL separately — the platform's existing boot components handle PS initialization.
- **Bitstream management via PMC**: The Kria platform uses the Platform Management Controller (PMC) for dynamic MIO configuration between carrier card variants (KV260 vs KR260). MIO for the specific carrier (UART, fan control) is set by the PMC at boot, not by your FSBL.
- **Fixed boot image sectors**: The KV260 has fixed boot image sectors in QSPI. For development, download the released Linux BOOT.bin from the SOM Wiki and program it into the designated sector. Your bare-metal bitstream is then loaded on top via JTAG or as a partial reconfiguration.
- **Authoritative pinout source**: The KV260/K26 SoM pin assignments live in DS987 (Kria K26 SOM Data Sheet). The carrier card design guide UG1091 defers to DS987 for SOM240_1 and SOM240_2 connector pinouts. Always use the latest DS987 revision for board-bring-up.

### Code Example
```tcl
# Vivado block design: Set PS UART1 for KV260 USB-UART (MIO40/MIO41)
# This should be in your create_bd.tcl under the zynq_ultra_ps_e_0 config

set_property CONFIG.PSU__UART1__PERIPHERAL__ENABLE {1} \
    [get_bd_cells zynq_ultra_ps_e_0]
set_property CONFIG.PSU__UART1__PERIPHERAL__IO {MIO 40 .. 41} \
    [get_bd_cells zynq_ultra_ps_e_0]

# Verify MIO40 and MIO41 are on the correct voltage bank (1.8V on K26)
set_property CONFIG.PSU__IOU__SLCR__MIO_BANK2__INPUT_POWER_RAIL {VCCO_MIO2_500} \
    [get_bd_cells zynq_ultra_ps_e_0]

# Enable PL clock at 100 MHz for AXI interconnect
set_property CONFIG.PSU__FPGA_PL0_ENABLE {1} \
    [get_bd_cells zynq_ultra_ps_e_0]
set_property CONFIG.PSU__CRL_APB__PL0_REF_CTRL__FREQMHZ {100} \
    [get_bd_cells zynq_ultra_ps_e_0]
```

### Relevance to Your Project
Your bare-metal demo uses USB-UART for PASS/FAIL output. The properties above confirm the correct MIO assignment for UART1 on the KV260 carrier's USB-UART bridge (connected to MIO40/41). If `xil_printf` output never appears on the terminal, the most common cause is UART1 not being enabled or mapped to the wrong MIO bank in the PS configurator.

## AMD/Xilinx Tool Updates (Vivado/Vitis 2025.1)

### Key Findings
- **VHDL 2019 simulation constructs added**: Vivado 2025.1 now supports VHDL 2019 simulation constructs. This enables `conditional expressions in sensitivity lists`, improved `generate` statements, and enhanced assertion syntax in testbenches.
- **Unified Selective Device Installer**: Vivado 2025.1 introduced a unified installer for all Versal devices, simplifying tool footprint management when working across multiple device families.
- **DFX debugging GUI**: `report_dfx_summary` now has GUI support in Vivado 2025.1, providing direct access to Dynamic Function eXchange (partial reconfiguration) debug data without needing to parse TCL output manually.
- **Spartan UltraScale+ production**: XCSU10P, XCSU25P, and XCSU35P devices reached production status in 2025.1. Not directly relevant to KV260/K26, but indicates toolchain maturity for UltraScale+ family.
- **Vitis 2025.1 BSP fixes**: New bare-metal BSPs added for Zynq UltraScale+ MPSoC boards; WDT (watchdog timer) compilation bug fixed; RPU clock MUX behavior changed for MPSoC/RFSoC. If your project later uses the RPU core, check the 2025.1 release notes before migrating.
- **Vitis AI 5.0 verified with 2025.1**: Vitis AI DPU IP v5.0 is validated against Vivado/Vitis/PetaLinux 2025.1. Relevant if the KV260 AXI-BRAM demo evolves toward an ML inference pipeline.

### Code Example
```vhdl
-- VHDL 2019 feature: conditional expression in sensitivity list (Vivado 2025.1+)
-- Useful for parameterized testbenches
library ieee;
use ieee.std_logic_1164.all;

entity bram_tb is
end entity;

architecture sim of bram_tb is
    constant CLK_PERIOD : time := 10 ns;
    signal clk     : std_logic := '0';
    signal rst_n   : std_logic := '0';
    signal wr_en   : std_logic := '0';
    signal wr_data : std_logic_vector(31 downto 0) := (others => '0');
    signal rd_data : std_logic_vector(31 downto 0);
begin
    clk <= not clk after CLK_PERIOD / 2;

    stim : process
    begin
        rst_n <= '0';
        wait for 20 ns;
        rst_n <= '1';
        wait until rising_edge(clk);

        -- Write pattern
        wr_en   <= '1';
        wr_data <= x"DEADBEEF";
        wait until rising_edge(clk);
        wr_en   <= '0';

        -- Read back and check
        wait until rising_edge(clk);
        assert rd_data = x"DEADBEEF"
            report "BRAM read mismatch: got " & to_hstring(rd_data)
            severity failure;

        report "Simulation PASS";
        wait;
    end process;
end architecture;
```

### Relevance to Your Project
Adding a VHDL 2025.1-compatible testbench (as above) to your repository lets you simulate the AXI-BRAM read/write logic before generating a bitstream. The `assert` with `to_hstring` (a VHDL 2008+ feature, available in Vivado 2025.1 simulation) gives you readable failure messages that mirror the PASS/FAIL output your `main.c` produces on hardware — making simulation and hardware results directly comparable.
