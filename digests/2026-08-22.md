# FPGA Research Digest - 2026-08-22

## Executive Summary

- **AXI BRAM Controller write-enable bug**: the Xilinx AXI BRAM Controller IP asserts WE one clock cycle early when back-to-back transactions occur; if you see extra words written, tie the BRAM EN signal through the controller (not floating) and add a one-cycle pipeline guard in your bare-metal loop.
- **Address Editor auto-assign**: after adding IP in IP Integrator, right-click the Address Editor pane → "Auto-Assign Address" to fix "unmapped peripheral" DRC errors; saves manual 0xA000_0000 / 0xA001_0000 entry for your two BRAMs.
- **Non-project mode reproducibility**: run `vivado -mode batch -source create_bd.tcl` to generate and implement the KV260 block design deterministically in CI, with no `.xpr` project file needed.
- **Kria bare-metal boot flow**: the K26 SOM ships in QSPI32 boot mode; for iterative bare-metal development, switch to JTAG boot mode (boot mode pins on KV260) and load `.elf` directly from Vitis/XSDB to avoid reflashing QSPI on every build cycle.
- **Vivado 2025.2 highlight**: SystemVerilog Interfaces support now auto-generates AXI wrappers between IP and block designs, reducing manual port-mapping TCL boilerplate for future IP reuse.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings

- **VALID/READY handshake invariant**: once a master asserts AWVALID or WVALID, it must **not** deassert it until the corresponding READY is seen from the slave. Violating this causes deadlocks in the AXI Interconnect; the Xilinx AXI Protocol Checker IP will flag it as a protocol error.
- **Simultaneous AWVALID+WVALID**: AXI-Lite allows issuing the write address and write data in the same cycle. The AXI BRAM Controller accepts this, so your bare-metal `Xil_Out32` / `Xil_In32` calls will work correctly since the PS AXI-Lite master drives both channels together.
- **Write-enable timing bug**: the AXI BRAM Controller v4.x has a known issue where WE is asserted one clock early on back-to-back transactions, causing an extra byte-lane write. Mitigation: add at least one idle cycle between writes (a `dsb()` barrier in C suffices on Cortex-A53), or verify in simulation with the AXI4-Lite VIP.
- **BRAM EN must be driven**: leaving `en_a` / `en_b` floating or tied low blocks all reads. The controller drives it internally — confirm in the block design that the BRAM Controller's BRAM port is connected to a Block Memory Generator, not left unconnected.
- **AXI-Stream flow control**: unlike AXI-Lite, AXI-Stream has no READY on the slave by default (TREADY is optional). When adding AXI-Stream to a future design, enable TREADY in the IP configuration or add a FIFO data mover to prevent overflow.

### Code Example

```c
/* Bare-metal AXI-Lite safe write-then-read with memory barrier */
#include "xil_io.h"

#define BRAM0_BASE  0xA0000000UL
#define BRAM2_BASE  0xA0010000UL

static inline void bram_write(u32 base, u32 offset, u32 val) {
    Xil_Out32(base + offset, val);
    dsb();          /* ensure AXI write completes before next transaction */
    isb();
}

static inline u32 bram_read(u32 base, u32 offset) {
    dsb();
    return Xil_In32(base + offset);
}

int verify_bram(u32 base, u32 pattern) {
    bram_write(base, 0x00, pattern);
    bram_write(base, 0x04, ~pattern);
    u32 r0 = bram_read(base, 0x00);
    u32 r1 = bram_read(base, 0x04);
    return (r0 == pattern && r1 == ~pattern) ? 0 : -1;
}
```

### Relevance to Your Project

Your `main.c` writes patterns to BRAM0 (0xA0000000) and BRAM2 (0xA0010000) using direct memory writes. Adding `dsb()` between writes and reads avoids the write-enable timing issue in back-to-back scenarios and ensures the Cortex-A53 cache subsystem does not reorder the transactions before they hit the AXI fabric.

## Vivado Block Design / IP Integrator

### Key Findings

- **Apply automation selectively**: `apply_bd_automation` is convenient but introduces undocumented constraints (clock routing choices, reset polarity). For reproducible designs, connect blocks explicitly with `connect_bd_net` / `connect_bd_intf_net` and use automation only for the Zynq preset step.
- **Address Editor auto-assign**: right-click → "Auto-Assign Address" resolves "Unmapped Peripheral" validation errors; or call `assign_bd_address` in TCL for scripted flows.
- **Regenerate outputs after edits**: after any IP parameter change, run `generate_target all [get_files *.bd]` in TCL, then re-export hardware. Missing this step causes Vitis to use stale wrappers.
- **BD validation before synthesis**: always call `validate_bd_design` in your TCL script before `launch_runs synth_1`; it catches missing connections, unmapped addresses, and clock domain errors early.
- **Export block design TCL**: use `write_bd_tcl -force my_bd.tcl` inside Vivado to snapshot a working block design as a reproducible script.

### Code Example

```tcl
# Minimal TCL to connect AXI BRAM Controller to Block Memory Generator
# (excerpt from create_bd.tcl pattern)

# Create BRAM controller
create_bd_cell -type ip -vlnv xilinx.com:ip:axi_bram_ctrl:4.1 axi_bram_ctrl_0

# Create Block Memory Generator in True Dual Port mode
create_bd_cell -type ip -vlnv xilinx.com:ip:blk_mem_gen:8.4 blk_mem_gen_0
set_property -dict [list \
    CONFIG.Memory_Type {True_Dual_Port_RAM} \
    CONFIG.Enable_32bit_Address {true} \
    CONFIG.Use_Byte_Write_Enable {true} \
    CONFIG.Byte_Size {8} \
] [get_bd_cells blk_mem_gen_0]

# Wire BRAM controller to Block Memory Generator
connect_bd_intf_net [get_bd_intf_pins axi_bram_ctrl_0/BRAM_PORTA] \
                    [get_bd_intf_pins blk_mem_gen_0/BRAM_PORTA]

# Assign address
assign_bd_address [get_bd_addr_segs {axi_bram_ctrl_0/S_AXI/Mem0}]
set_property offset 0xA0000000 \
    [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property range 64K \
    [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]

validate_bd_design
```

### Relevance to Your Project

Your `create_bd.tcl` should follow this pattern for both `axi_bram_ctrl_0` at 0xA0000000 and `axi_bram_ctrl_1` at 0xA0010000. The explicit `set_property offset` call locks in the base addresses that your bare-metal `main.c` hard-codes, preventing IP Integrator from auto-assigning different addresses on a clean rebuild.

## Vivado TCL Scripting

### Key Findings

- **Non-project mode invocation**: `vivado -mode batch -source create_bd.tcl` runs the full design flow without creating a `.xpr`; use `write_checkpoint` after each stage (synth, impl, route) to save incremental progress and enable re-entry.
- **Three Vivado Tcl modes**: interactive GUI console, Tcl shell (`vivado -mode tcl`), and batch mode. For CI pipelines use batch mode; for debugging use Tcl shell which keeps the session open after script errors.
- **Sourcing sub-scripts**: use `source [file join [file dirname [info script]] helper.tcl]` to source relative scripts robustly; avoids hard-coded paths breaking when the repo is cloned to a different location.
- **Post-route reports in non-project mode**: call `report_timing_summary`, `report_utilization`, and `report_drc` explicitly — non-project mode generates none automatically.
- **Design checkpoint resume**: `open_checkpoint post_synth.dcp` lets you re-enter the flow at any stage without re-running synthesis, critical for iterating on implementation strategies.

### Code Example

```tcl
#!/usr/bin/env tclsh
# Non-project mode full flow for KV260 AXI-BRAM design

set root [file dirname [info script]]

# 1. Read sources
read_vhdl   [glob $root/../vhdl/*.vhd]
read_xdc    [glob $root/../xdc/*.xdc]

# 2. Read and generate block design
source $root/create_bd.tcl
make_wrapper -files [get_files *.bd] -top
read_vhdl [glob $root/../../*.vhd]   ;# generated BD wrapper

# 3. Synthesize
synth_design -top kv260_top -part xck26-sfvc784-2LV-c
write_checkpoint -force $root/../../runs/post_synth.dcp
report_utilization -file $root/../../runs/utilization_synth.rpt

# 4. Implement
opt_design
place_design
route_design
write_checkpoint -force $root/../../runs/post_route.dcp

# 5. Reports
report_timing_summary -file $root/../../runs/timing.rpt -warn_on_violation
report_drc            -file $root/../../runs/drc.rpt

# 6. Bitstream
write_bitstream -force $root/../../runs/kv260_top.bit
```

### Relevance to Your Project

This non-project mode script mirrors the structure expected for a CI-driven rebuild of your KV260 design. Substitute the exact part number and path structure from your repo. The `write_checkpoint` calls after synth and route let you diagnose timing failures without re-running the full 20-minute flow each time.

## Vitis Bare-Metal / Standalone

### Key Findings

- **BSP stdout configuration**: in Vitis, the standalone BSP `stdin`/`stdout` parameters must point to the correct UART instance (`psu_uart_1` on KV260 maps to the USB-UART). Mismatching these silences `xil_printf` entirely with no error message.
- **Boot sequence before main**: the standalone BSP runs `_boot.S` before `main()`, which initializes the Cortex-A53 MMU, clears BSS, and calls constructors. For bare-metal AXI access, the MMU is configured with device-type (non-cacheable, strongly ordered) mapping for the PL AXI region (0xA000_0000), which is correct for MMIO.
- **Linker script memory regions**: Vitis generates a `lscript.ld` that maps `.text`, `.data`, `.bss`, and `.heap`/`.stack` to DDR. If the heap is too small, `malloc` silently returns NULL. Increase `_HEAP_SIZE` in the BSP settings or directly in `lscript.ld`.
- **`dsb()` / `dmb()` intrinsics**: for AXI-Lite MMIO, use `Xil_Out32` + `dsb()` to guarantee write ordering on the Cortex-A53 out-of-order pipeline. ARM's write buffer can combine or reorder stores to different addresses without the barrier.
- **UART baud rate**: set `psu_uart_1` baud to 115200 in the BSP and confirm `/dev/ttyUSB1` is the correct port on the host (KV260 enumerates two USB-serial ports; the second is usually the one connected to the PS UART).

### Code Example

```c
/* BSP-safe UART and AXI-Lite initialisation skeleton */
#include "xparameters.h"
#include "xuartps.h"
#include "xil_printf.h"
#include "xil_io.h"
#include "xil_cache.h"

#define BRAM0_BASE  XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR  /* 0xA0000000 */
#define BRAM2_BASE  XPAR_AXI_BRAM_CTRL_1_S_AXI_BASEADDR  /* 0xA0010000 */

int main(void) {
    /* Disable D-cache for MMIO regions (already done by BSP for PL space,
       but explicit disable avoids surprises after cache flush calls) */
    Xil_DCacheDisable();

    xil_printf("KV260 AXI-BRAM test\r\n");

    /* Write patterns */
    Xil_Out32(BRAM0_BASE + 0x00, 0xDEADBEEF); dsb();
    Xil_Out32(BRAM2_BASE + 0x00, 0xCAFEBABE); dsb();

    /* Read back */
    u32 r0 = Xil_In32(BRAM0_BASE + 0x00);
    u32 r1 = Xil_In32(BRAM2_BASE + 0x00);

    xil_printf("BRAM0: 0x%08X -> %s\r\n", r0,
               (r0 == 0xDEADBEEF) ? "PASS" : "FAIL");
    xil_printf("BRAM2: 0x%08X -> %s\r\n", r1,
               (r1 == 0xCAFEBABE) ? "PASS" : "FAIL");

    return 0;
}
```

### Relevance to Your Project

Your `main.c` is already structured this way. The `XPAR_AXI_BRAM_CTRL_x_S_AXI_BASEADDR` macros come from the generated `xparameters.h` in the BSP and will auto-update if addresses change in the block design — preferable to hard-coded 0xA0000000 literals.

## XDC Timing Constraints

### Key Findings

- **`set_input_delay` semantics**: specifies the external delay from the source clock edge to data arrival at the FPGA input pin (in ns). A **positive** value means data arrives after the clock edge (typical synchronous interface); a **negative** value means data arrives before it.
- **`set_output_delay` semantics**: specifies how long after the clock edge the downstream device needs data to be stable. Used by Vivado to back-annotate the output hold/setup requirement onto the routed path.
- **`-min` and `-max` flags**: always constrain both min and max delays to fully specify the setup and hold windows. Omitting `-min` leaves hold time unconstrained and can produce subtle metastability.
- **Clock groups for PS-to-PL**: the Zynq PS clock (`pl_clk0`) and any user-created clocks on PL outputs should be marked as asynchronous with `set_clock_groups -asynchronous` if they share logic paths, preventing false timing violations.
- **Timing Constraints Wizard**: use `Constraints → Timing Constraints Wizard` in Vivado to auto-generate `set_input_delay`/`set_output_delay` templates for all unconstrained ports; paste into your XDC then tune values.

### Code Example

```xdc
# KV260 typical XDC snippet for a synchronous external interface
# (not needed for pure PS-PL AXI which is fully internal,
#  but required for any PMOD or expansion-card I/O on the KV260 carrier)

# Primary PL clock from PS (100 MHz example)
create_clock -period 10.000 -name pl_clk0 [get_ports pl_clk0]

# External synchronous input on PMOD (source-synchronous, 50 MHz bus)
# Assume tCO_max=4ns, tCO_min=1ns for the source device
set_input_delay -clock pl_clk0 -max  4.0 [get_ports {pmod_data[*]}]
set_input_delay -clock pl_clk0 -min  1.0 [get_ports {pmod_data[*]}]

# External synchronous output (device requires 3ns setup, 1ns hold)
set_output_delay -clock pl_clk0 -max  3.0 [get_ports {pmod_out[*]}]
set_output_delay -clock pl_clk0 -min -1.0 [get_ports {pmod_out[*]}]

# Prevent false paths between async clock domains (PS FCLK vs PL user clock)
set_clock_groups -asynchronous \
    -group [get_clocks pl_clk0] \
    -group [get_clocks clk_out1_clk_wiz_0]
```

### Relevance to Your Project

For the pure AXI-BRAM demo (PS-only master, PL BRAM slave, no external I/O), these constraints are not strictly required — the AXI Interconnect paths are timing-closed automatically. However, the `set_clock_groups` line is critical if you later add a second PL clock domain (e.g., a separate BRAM port clocked from a MMCM), otherwise Vivado will attempt multi-cycle path analysis across the asynchronous boundary and may incorrectly report violations or pass with unsafe timing.

## Kria KV260 / K26 SoM

### Key Findings

- **SOM240_1 connector**: all PS/PL I/O between the K26 SOM and the KV260 carrier board routes through a 240-pin board-to-board connector. PL expansion I/O follows the path: `PL logic → ZynqMP package pin → SOM240_1 → KV260 net → carrier connector`. Signal integrity budgets must account for two board crossings.
- **EMIO GPIO for PL I/O**: to control carrier-card PMOD or Raspberry Pi header GPIO from bare-metal PL logic, route through EMIO: enable GPIO EMIO in the Zynq UltraScale+ IP, then connect `emio_gpio_o` to top-level ports and constrain with XDC. No AXI overhead.
- **Boot mode for development**: the K26 ships in QSPI32 boot mode. For rapid bare-metal iteration, set the KV260 boot-mode DIP switches to JTAG (all low) so Vitis can load the `.bit`+`.elf` directly over JTAG without writing to QSPI. Switch back to QSPI for production deployment.
- **MIO bank voltages**: MIO bank 500 (I2C, sideband) runs at 1.8V on the K26 SOM; MIO bank 501 (UART, SD) runs at 1.8V. Any external interface must be level-shifted to 1.8V or use the carrier card's built-in level shifters.
- **Board files in Vivado 2025.1**: Vivado 2025.1 ships with updated K26/KV260 board files. Load them via `set_property board_part xilinx.com:kv260_som:part0:1.4 [current_project]` to get pre-configured PS settings, clock, DDR, and UART correct out of the box.

### Code Example

```tcl
# TCL: Apply KV260 board preset (replaces manual PS configuration)
# Run inside Vivado after creating the Zynq UltraScale+ PS IP cell

set zynq_cell [get_bd_cells zynq_ultra_ps_e_0]

# Apply board automation - configures DDR4, UART1, USB, QSPI from board files
apply_bd_automation -rule xilinx.com:bd_rule:zynq_ultra_ps_e \
    -config {apply_board_preset "1"} $zynq_cell

# Enable AXI HP0 slave port for PL masters (not needed for AXI-Lite from PS,
# but useful for future DMA from PL)
set_property -dict [list \
    CONFIG.PSU__USE__S_AXI_GP0 {1} \
    CONFIG.PSU__USE__M_AXI_GP0 {1} \
] $zynq_cell

# Enable PL fabric clock at 100 MHz
set_property CONFIG.PSU__FPGA_PL0_ENABLE {1} $zynq_cell
set_property CONFIG.PSU__CRL_APB__PL0_REF_CTRL__FREQMHZ {100} $zynq_cell
```

### Relevance to Your Project

Using `apply_board_preset "1"` in your `create_bd.tcl` ensures that UART baud, DDR4 timing, and PS clock configuration all match the KV260 hardware without manual entry. This is the single most common source of "it synthesizes but doesn't boot" issues on the Kria platform.

## AMD/Xilinx Tool Updates (Vivado / Vitis 2025.x)

### Key Findings

- **Vivado 2025.2 key highlight — SystemVerilog Interfaces**: AXI connections between IP and block designs can now use SV interface syntax, with automatic wrapper generation. Reduces manual port-map TCL in IP Integrator by ~50 lines for a typical AXI slave.
- **Reduced PhysOpt compile time**: Versal and UltraScale+ designs see reduced physical optimization (PhysOpt) run time in 2025.2; useful for large KV260 designs that iterate frequently.
- **AI timing closure**: the Vivado AI Assistant Extension (available 2024.2+) provides iterative AI-guided strategies for difficult timing closure; accessible via `Tools → AI Assistant` in the GUI or via TCL for scripted runs.
- **ECO legalizer**: a new ECO placer with timing-driven mode enables post-route edits with DRC legality checks, reducing the need to re-run full implementation after small RTL changes.
- **Vitis 2026.x known issues**: the adaptivesupport.amd.com article 000040220 lists active Vitis 2026.x known issues; review before upgrading from 2025.1 if your project is stable.
- **Vivado 2026.1 now available**: AMD released Vivado/Vitis 2026.1 (download page updated); the 2025.1 toolchain remains the recommended stable version for KV260 bare-metal projects until community validation of 2026.1 is confirmed.

### Code Example

```tcl
# Vivado 2025.2+: Use Intelligent Design Runs (IDR) for automated
# timing closure — replaces manual strategy iteration

# Enable IDR for implementation
set_property STEPS.PHYS_OPT_DESIGN.IS_ENABLED true [get_runs impl_1]
set_property STRATEGY "Vivado Implementation Defaults" [get_runs impl_1]

# Launch with AI-assisted strategy exploration (2025.2+ feature)
launch_runs impl_1 -jobs 4 -to_step write_bitstream

# Monitor with timeout
wait_on_run impl_1 -timeout 120

# Check timing result
open_run impl_1
set wns [get_property STATS.WNS [get_runs impl_1]]
if {$wns < 0} {
    puts "WARNING: Timing not met. WNS = $wns ns"
    report_timing_summary -file timing_failure.rpt
} else {
    puts "Timing met. WNS = $wns ns"
}
```

### Relevance to Your Project

The AXI-BRAM demo at 100 MHz on the K26 will close timing easily (the paths are short), so 2025.1 is fine. The IDR / AI closure features become relevant when you extend the design with higher-speed interfaces (300+ MHz BRAM), compute kernels, or additional AXI-Stream pipelines. The SystemVerilog interfaces feature in 2025.2 could simplify any future custom IP development.
