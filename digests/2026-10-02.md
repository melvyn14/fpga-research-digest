# FPGA Research Digest - 2026-10-02

## Executive Summary
- **AXI-Lite backpressure bug**: Xilinx AXI BRAM Controller slaves must keep AWREADY/WREADY low when the write-response channel is stalled; missing this check causes silent dropped writes at 0xA0000000/0xA0010000.
- **WSTRB byte-lane masking**: Each of the 4 bits of WSTRB on a 32-bit bus independently enables one byte; bare-metal byte writes must use `*(volatile uint8_t*)` or clear unused WSTRB lanes or the BRAM stores garbage in the masked bytes.
- **xparameters.h is the single source of truth** for MMIO base addresses in Vitis; your `main.c` literal `0xA0000000`/`0xA0010000` constants should be cross-checked against `XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR` after each hardware export.
- **Vivado 2025.1 IP Integrator** adds dedicated "Clocking and Reset" and "Interrupt and AXI-4 Lite" views, making it easier to audit your PS-PL clock/reset plumbing without digging into raw block-design XML.
- **Non-project TCL flow**: Running `vivado -mode batch -source create_bd.tcl` is reliable for CI/CD, but requires explicit `write_checkpoint` calls — unlike project mode, no checkpoint is auto-saved after synthesis or implementation.

## AXI Protocol / AXI-Lite / AXI-Stream

### Key Findings
- The five AXI4-Lite channels (AW, W, B, AR, R) each use an independent VALID/READY handshake; a transfer completes only when **both** VALID and READY are high on the same rising clock edge.
- Once VALID is asserted, the initiator must **not** deassert it until READY is received — violating this creates non-deterministic behavior in the BRAM controller.
- A common slave implementation pitfall: raising `AWREADY` only when both `AWVALID` and `WVALID` are simultaneously true ties the two channels together. While this works for a single outstanding transaction, it blocks the address channel if the data channel is stalled.
- The write-response channel (B) provides backpressure back to the master; a slave that ignores `BREADY` can silently drop or corrupt subsequent writes.
- WSTRB (write strobe) width = data bus width / 8. On a 32-bit bus, 4 bits each gate one byte lane. Setting `WSTRB = 4'b1111` writes all four bytes; `4'b0001` writes only byte 0.
- Vivado 2025 BRAMs require the read process to be **synchronous with the clock**; asynchronous read processes cannot map to synchronous BRAM primitives and result in inference failures.

### Code Example
```c
/* Bare-metal 32-bit AXI-Lite write/read to BRAM — checks for stuck channel */
#include "xil_io.h"
#define BRAM0_BASE 0xA0000000UL
#define BRAM2_BASE 0xA0010000UL

static inline void bram_write32(u32 base, u32 offset, u32 val) {
    Xil_Out32(base + offset, val);
    /* Xil_Out32 wraps a memory-barrier + store; WSTRB driven 0xF by AXI master */
}

static inline u32 bram_read32(u32 base, u32 offset) {
    return Xil_In32(base + offset);
}

void axi_bram_selftest(void) {
    const u32 pattern = 0xDEADBEEF;
    bram_write32(BRAM0_BASE, 0x00, pattern);
    u32 rb = bram_read32(BRAM0_BASE, 0x00);
    xil_printf("BRAM0[0]: wrote 0x%08X, read 0x%08X => %s\r\n",
               pattern, rb, (rb == pattern) ? "PASS" : "FAIL");
}
```

### Relevance to Your Project
Your `main.c` writes patterns to BRAM0 (0xA0000000) and BRAM2 (0xA0010000) then reads them back. The backpressure check is critical: if any write transaction stalls on the B-channel (e.g., BREADY not asserted in time), subsequent writes may be silently ignored. Ensure the AXI BRAM Controller IP is configured with a non-zero write-response latency budget in the timing constraints, and verify `BREADY` tie-off in the SmartConnect configuration.

## Vivado Block Design / IP Integrator

### Key Findings
- The **Address Editor** tab in IP Integrator appears only when the design contains a bus master (e.g., Zynq PS AXI Master port). It auto-assigns addresses but supports manual override and range adjustment.
- Default AXI BRAM instance address space is 64K starting at 0xC0000000; adjust the **Range** field to match your design's actual BRAM depth.
- Use `set_property locktype local [get_bd_addr_segs {...}]` to lock a segment in the Address Editor — prevents automation from reassigning it during block diagram regeneration.
- **Vivado 2025.1** adds two new IP Integrator views: "Clocking and Reset" and "Interrupt and AXI-4 Lite". These expose PS-PL clock/reset and interrupt wiring without requiring the full block diagram canvas.
- IP that **cannot** be selectively upgraded (must upgrade all at once): Zynq/Zynq UltraScale+ MPSoC, AXI Interconnect, AXI SmartConnect — plan full regeneration when moving tool versions.
- After `validate_bd_design`, always run `generate_target all [get_files *.bd]` before exporting to Vitis; skipping this step leaves stale wrapper files.

### Code Example
```tcl
# Lock BRAM0 address segment to prevent automation reassignment
set_property locktype local \
  [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]

# Manually set BRAM0 base address and range
set_property offset 0xA0000000 \
  [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]
set_property range 64K \
  [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_0_Mem0}]

# Set BRAM2 address
set_property offset 0xA0010000 \
  [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_1_Mem0}]
set_property range 64K \
  [get_bd_addr_segs {zynq_ultra_ps_e_0/Data/SEG_axi_bram_ctrl_1_Mem0}]
```

### Relevance to Your Project
Your `create_bd.tcl` script should include address segment locking to guarantee BRAM0 stays at 0xA0000000 and BRAM2 at 0xA0010000 across regenerations. Without locking, a `assign_bd_address` call can silently reassign these addresses and your `main.c` will access wrong memory regions.

## Vivado TCL Scripting

### Key Findings
- **Non-project mode** processes everything in memory; no project file is written to disk. This is ideal for CI pipelines but requires explicit `write_checkpoint` calls at each design stage.
- The in-memory project is created implicitly when you run `read_vhdl`, `read_xdc`, `synth_design`, etc.
- `config_flows -synth_strategy <name> -impl_strategy <name>` applies preset directives without specifying individual options per command — use `Performance_ExplorePostRoutePhysOpt` for timing-critical paths.
- Example scripts are installed at `<install_dir>/Vivado/2025.1/examples/Vivado_Tutorial/`.
- Always use `catch` blocks around `synth_design` and `impl_design` to handle errors in batch mode without aborting the entire script silently.
- `report_timing_summary -file timing.rpt` and `report_utilization -file util.rpt` should be called after implementation to capture artifacts even in non-project flows.

### Code Example
```tcl
# Non-project batch flow skeleton for KV260 AXI-BRAM design
read_vhdl  ./vhdl/kv260_top.vhd
read_xdc   ./constraints/kv260.xdc

# Read the block design TCL and re-create the BD in memory
source     ./tcl/create_bd.tcl
generate_target all [get_files *.bd]
make_wrapper -files [get_files *.bd] -top
read_vhdl  [glob ./ip/*.srcs/sources_1/bd/*/hdl/*_wrapper.vhd]

synth_design -top kv260_top -part xck26-sfvc784-2LV-c
write_checkpoint -force post_synth.dcp

opt_design
place_design
route_design
write_checkpoint -force post_route.dcp

report_timing_summary -file timing_summary.rpt
report_utilization    -file utilization.rpt
write_bitstream -force kv260_axi_bram.bit
```

### Relevance to Your Project
Your `create_bd.tcl` already encapsulates block design creation. Wrapping it in the non-project flow above gives you a single-command CI build: `vivado -mode batch -source build_all.tcl`. Add `write_checkpoint` after synthesis to enable incremental implementation on subsequent runs — saves 30–50% implementation time for iterative changes.

## Vitis Bare-Metal / Standalone

### Key Findings
- The standalone BSP supports Cortex-A53 (the K26's APU) with `xil_printf` as a lightweight printf that avoids pulling in the full libc `printf` (smaller binary, no float formatting unless patched).
- `xparameters.h` is generated by Vitis during platform creation and contains all peripheral base addresses from the Vivado hardware export (`.xsa` file). Always reference it instead of hardcoded addresses.
- The linker script `lscript.ld` is auto-generated in the application's `src/` folder; double-click it in Vitis to open the GUI editor for stack/heap sizing.
- For Cortex-A53 bare-metal, stack defaults to 0x2000 (8KB) and heap to 0x2000; increase these for deeply recursive functions or large local arrays.
- BSP source is included with the Vitis installation and available on the [Xilinx GitHub](https://github.com/Xilinx/embeddedsw) — useful for understanding `Xil_Out32`/`Xil_In32` memory barrier semantics.
- The Vitis 2025.1 standalone domain defaults to using the Cortex-A53 EL3 execution level for bare-metal, which is important for peripheral access rights.

### Code Example
```c
/* xparameters.h cross-check pattern — do NOT hardcode addresses in main.c */
#include "xparameters.h"

/* These are generated from the .xsa after Vivado hardware export */
#ifndef XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR
  #error "BRAM0 base address not found in xparameters.h — re-export hardware"
#endif
#ifndef XPAR_AXI_BRAM_CTRL_1_S_AXI_BASEADDR
  #error "BRAM2 base address not found in xparameters.h — re-export hardware"
#endif

#define BRAM0_BASE  XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR
#define BRAM2_BASE  XPAR_AXI_BRAM_CTRL_1_S_AXI_BASEADDR

/* Use xil_printf for lightweight UART output — avoids full libc printf */
xil_printf("BRAM0 base: 0x%08X\r\n", (unsigned)BRAM0_BASE);
```

### Relevance to Your Project
Your current `main.c` likely has literal `0xA0000000` and `0xA0010000` addresses. Replacing these with `XPAR_AXI_BRAM_CTRL_0_S_AXI_BASEADDR` from `xparameters.h` means the code automatically tracks any address reassignment in the block design without a manual find-and-replace. The `#error` guards above catch a stale hardware export at compile time rather than at runtime.

## XDC Timing Constraints

### Key Findings
- `set_input_delay` specifies the external path delay on a primary input port **relative to a clock edge** at the FPGA interface (in ns, positive or negative depending on phase relationship).
- `set_output_delay` specifies the external path delay on a primary output port relative to a clock edge; positive values represent setup requirements of the downstream device.
- For AXI interfaces internal to the PS-PL boundary (e.g., the HP slave ports on Zynq UltraScale+), **no XDC input/output delay constraints are needed** — the PS handles its own AXI clock domain internally.
- For external I/O (UART TX/RX, GPIO, fan control), always constrain with `-clock [get_clocks <clkname>] -max <setup_margin> -min <hold_margin>`.
- Use `set_clock_groups -asynchronous` to explicitly declare independent clock domains (e.g., PL logic clock vs. PS reference clock) to prevent false cross-domain timing paths.
- XDC files are processed **sequentially in source order**; constraints on a clock must appear before constraints referencing that clock.

### Code Example
```tcl
# KV260 XDC timing constraint example
# PL fabric clock from PS (300 MHz typical for HP ports)
create_clock -period 3.333 -name clk_pl_0 [get_ports {pl_clk0}]

# External UART TX output constraint (115200 baud, minimal timing)
set_output_delay -clock clk_pl_0 -max 2.0 [get_ports {uart_tx}]
set_output_delay -clock clk_pl_0 -min 0.5 [get_ports {uart_tx}]

# Declare PS and PL clocks as asynchronous groups to suppress false paths
set_clock_groups -asynchronous \
  -group [get_clocks clk_pl_0] \
  -group [get_clocks {clk_out1_*}]

# False path for BRAM reset (synchronizer not required — static at init)
set_false_path -from [get_ports {aresetn}]
```

### Relevance to Your Project
Your KV260 AXI-BRAM demo's critical timing path is the PS AXI master → SmartConnect → AXI BRAM Controller → BRAM. This path is entirely within the PL clock domain driven by `pl_clk0` from the PS. You need no `set_input/output_delay` for this path, but you **do** need `set_false_path` on your reset signals and `set_clock_groups -asynchronous` if your `kv260_top.vhd` uses any secondary clocks.

## Kria KV260 / K26 SoM

### Key Findings
- The K26 SoM integrates a Zynq UltraScale+ MPSoC with DDR memory, QSPI flash, eMMC (on SM variant), and a security module into a compact BGA module.
- Two 240-pin connectors expose: PS MIO, PS-GTR transceivers, PS I2C platform control bus, PL HPIO, PL HDIO, PL GTH transceivers, and power/sequencing signals.
- **Boot sequence**: K26 boots from QSPI using a minimal device tree with limited peripherals. After boot, **carrier card (CC) detection** occurs and a device tree overlay is applied to enable carrier-specific functionality.
- Two SOM variants: `sm-k26` (with eMMC) and `smk-k26` (without eMMC — used on starter kit with pre-programmed QSPI firmware).
- PL I/O voltage rails are **carrier-card defined** (not fixed on the SOM), so check your carrier's schematic for correct IOSTANDARD constraints before driving PL pins.
- For bare-metal (no OS), you bypass the QSPI boot Linux entirely: JTAG-load your ELF directly to DDR via `xsdb` after POR, or use FSBL + bitstream in a BOOT.BIN on SD card.
- MIO bank voltages on K26: Bank 500 (MIO 0–25) runs at 1.8V, Bank 501 (MIO 26–51) at 1.8V; confirm before using PS UART (MIO 36/37 on KV260 carrier).

### Code Example
```tcl
# XDC IOSTANDARD for KV260 carrier PL I/O — check carrier schematic first
# Example: PMOD connector on KV260 uses 3.3V LVCMOS
set_property IOSTANDARD LVCMOS33 [get_ports {pmod_gpio[*]}]
set_property PACKAGE_PIN H12     [get_ports {pmod_gpio[0]}]  ;# J2 pin 1

# PS UART MIO pins are NOT in XDC — routed through PS configuration
# In block design TCL:
# set_property CONFIG.PSU__UART0__PERIPHERAL__ENABLE 1 \
#   [get_bd_cells zynq_ultra_ps_e_0]
# set_property CONFIG.PSU__UART0__UART0__IO {MIO 36 .. 37} \
#   [get_bd_cells zynq_ultra_ps_e_0]
```

### Relevance to Your Project
For your bare-metal KV260 AXI-BRAM demo, UART output goes via PS UART0 on MIO 36/37 (standard KV260 carrier wiring). This is configured entirely in the PS block in IP Integrator — no XDC entry required. If your UART output is silent, verify: (1) PS UART0 is enabled with `MIO 36..37`, (2) baud rate matches your terminal (115200 default for Vitis apps), and (3) you're connected to the correct USB-UART port (KV260 carrier has FTDI FT4232H with multiple channels).

## AMD/Xilinx Tool Updates (Vivado/Vitis 2025.1)

### Key Findings
- **Vivado 2025.1** was released with notable IP Integrator ease-of-use enhancements: dedicated "Clocking and Reset" and "Interrupt and AXI-4 Lite" views, a new **Pblock planner**, and enhanced addressing GUI for Versal Prime Gen 2 / Versal AI Edge Gen 2.
- A new `config_flows` option supports `-synth_strategy` and `-impl_strategy` flags for non-project mode, making it easier to apply preset optimization strategies without per-command directive lists.
- **Vitis 2025.1** focuses heavily on Versal AI Engine enhancements (DSP library updates, MATLAB/Python simulation for AI Engine subsystems, independent AIE partition runtime control). Less directly relevant to Zynq UltraScale+ bare-metal, but the standalone BSP has no breaking changes.
- **Vitis-AI v5.0** (released with 2025.1) is verified compatible with Vitis, Vivado, and PetaLinux 2025.1.
- The 2025.1 release example scripts are at `<install_dir>/Vivado/2025.1/examples/Vivado_Tutorial/`.
- **IP selective upgrade limitation** (unchanged from earlier releases): Zynq UltraScale+ MPSoC and AXI SmartConnect/Interconnect still require full-design upgrade — no selective partial upgrade.
- Vivado 2025.2 (already available at time of writing) adds further Versal Gen 2 addressing GUI features; for Zynq-based designs like KV260, 2025.1 and 2025.2 are functionally equivalent.

### Code Example
```tcl
# Use config_flows strategy in non-project mode (Vivado 2025.1+)
synth_design -top kv260_top -part xck26-sfvc784-2LV-c

# Apply implementation preset — no need to specify per-step directives
config_flows -impl_strategy Performance_ExplorePostRoutePhysOpt

opt_design
place_design
phys_opt_design
route_design

# Generate reports using the built-in report infrastructure
report_clock_interaction -delay_type min_max -file clock_interaction.rpt
report_cdc               -details         -file cdc.rpt
report_timing_summary    -max_paths 50    -file timing_summary.rpt
```

### Relevance to Your Project
For your KV260 AXI-BRAM project using Vivado 2025.1, the new IP Integrator views are directly useful: the "Clocking and Reset" view lets you quickly verify that `pl_clk0` is connected to both the AXI BRAM Controller and SmartConnect without tracing wires across the full block diagram. If you upgrade to 2025.2, no behavioral changes to the Zynq MPSoC IP or AXI BRAM Controller are expected.
